# 02 - 典型故事

> **文档目的**：通过 3 个端到端故事，让你理解打印系统在实际业务场景中的完整运行过程
> **读者定位**：需要理解业务细节的开发者、测试人员、产品经理

---

## 故事一：结账打印（Happy Day）

### 故事背景

老王在收银台完成了一笔收款，系统需要打印结账单给顾客。

### 故事线

```text
收银员在 POS 界面点击「结账」按钮
    │
    ▼
系统开始结账流程：计算金额、保存支付、更新账单状态
    │
    ├──▶ 计算订单金额
    ├──▶ 保存支付明细（支付方式、金额、时间）
    ├──▶ 更新账单状态为"已关闭"
    ├──▶ 处理会员积分（如有）
    └──▶ 触发打印：结账完成后自动启动打印任务
    │
    ▼
打印任务编排
    │
    ├──▶ 准备数据：收集账单信息、菜品明细、支付明细、会员信息
    ├──▶ 选择队列：找到对应的打印队列（主队列优先，故障时切备用）
    └──▶ 创建任务：持久化到数据库，状态设为"等待中"
    │
    ▼
模板渲染
    │
    ├──▶ 加载"顾客小票"对应的打印模板（JSON 格式行+列布局）
    ├──▶ 遍历模板的每一行
    │       ├──▶ 表格行：遍历数据列表，每行生成一条记录
    │       └──▶ 普通行：直接渲染固定文本
    └──▶ 替换占位符：{数据源ID,字段名} → 实际值
    │
    ▼
队列分发
    │
    ├──▶ 每个打印机有独立的工作线程
    ├──▶ 工作线程从队列取出任务，状态变为"打印中"
    └──▶ 根据打印机类型找到对应的处理器
    │
    ▼
打印执行
    │
    ├──▶ 热敏打印机（如汉印）：通过 OPOS SDK 驱动硬件
    ├──▶ 云打印机（如佳博）：通过 HTTP API 发送打印内容
    └──▶ 标签打印机（如芯烨）：通过 TSPL 协议发送标签指令
    │
    ▼
结果处理
    │
    ├──▶ 成功：状态更新为"成功"，小票从打印机吐出
    │          顾客收到小票，结账流程完成
    │
    └──▶ 失败：状态更新为"失败"，记录失败原因
                需要人工修复后重新打印
```

### 步骤说明

| 步骤 | 业务描述 | 说明 |
|------|----------|------|
| 1 | 收银员完成结账 | 结账操作触发打印，收银员无需额外操作 |
| 2 | 系统编排打印任务 | 收集数据、选择队列、创建任务，全自动完成 |
| 3 | 模板渲染打印内容 | 模板引擎把数据填入模板，生成最终打印内容 |
| 4 | 队列分发到打印机 | 任务按队列分配给对应打印机的工作线程 |
| 5 | 打印机执行硬件输出 | 根据打印机类型选择协议，驱动硬件打印 |
| 6 | 处理打印结果 | 成功则更新状态，失败则记录原因等待人工处理 |

### 关键设计点

1. **异步执行**：收银员在步骤2就看到结账成功，打印在后台执行，不阻塞结账流程
2. **双保险存储**：文件系统保证可靠性，Redis 计数保证性能
3. **协议解耦**：业务代码不关心打印机类型，由 Handler 层统一抽象

## 故事二：厨打分发（多部门场景）

### 故事背景

顾客点了川菜和粤菜，分别由出品部A（川菜）和出品部B（粤菜）负责。

### 故事线

```text
服务员完成点菜
    │
    ▼
系统收到点菜请求，开始处理后厨打印
    │
    ├──▶ 查询菜品与出品部门的映射关系
    │       ├──▶ 宫保鸡丁 → 出品部A（川菜）
    │       └──▶ 叉烧 → 出品部B（粤菜）
    │
    ├──▶ 按部门分组菜品
    │       ├──▶ 出品部A：宫保鸡丁、麻婆豆腐
    │       └──▶ 出品部B：叉烧、烧鹅
    │
    ├──▶ 为出品部A创建打印任务，投递到部门A的打印机队列
    ├──▶ 为出品部B创建打印任务，投递到部门B的打印机队列
    │
    └──▶ 两个任务并行执行，各自打印后厨标签
            ├──▶ 出品部A的标签机打印川菜菜单
            └──▶ 出品部B的标签机打印粤菜菜单
    │
    ▼
后厨人员看到标签，开始备餐
```

### 步骤说明

| 步骤 | 业务描述 | 说明 |
|------|----------|------|
| 1 | 服务员完成点菜 | 系统自动触发后厨打印，无需手动操作 |
| 2 | 查询菜品与部门映射 | 每个菜品归属哪个出品部门，由系统配置决定 |
| 3 | 按部门分组 | 同一部门的菜品合并到一张标签，减少纸张浪费 |
| 4 | 创建多个打印任务 | 每个部门独立任务，可配置不同的打印机 |
| 5 | 并行分发打印 | 各部门任务同时打印，互不阻塞 |
| 6 | 后厨开始备餐 | 每个部门只看到自己负责的菜品 |

### 关键设计点

1. **部门分组**：每个部门只看到自己的菜品
2. **并行分发**：不同部门的任务可以并行打印，互不阻塞
3. **独立队列**：每个部门可配置独立的打印机

## 故事三：打印失败与重试

### 故事背景

网络打印机突然断电，任务执行失败。

### 故事线

```text
打印机正在打印时突然断电，网络连接中断
    │
    ▼
工作线程检测到打印操作失败（网络超时）
    │
    ├──▶ 线程把任务状态更新为"失败"，记录失败原因
    │
    ▼
系统检查重试策略
    │
    ├──▶ 当前已重试次数：0 次（未超过最大重试限制 3 次）
    │
    ├──▶ 按照指数退避策略，安排第 1 次重试，延迟 1 分钟
    │
    ├──▶ 1 分钟后，系统自动重新执行打印
    │       ├──▶ 成功 → 任务状态更新为"成功"，流程结束
    │       └──▶ 失败 → 继续重试，延迟递增（2 分钟、4 分钟）
    │
    └──▶ 如果超过 3 次仍失败，任务标记为"失败"，不再自动重试
            └──▶ 需要人工介入：修复打印机后，在管理页面手动重打
```

### 重试策略

| 重试次数 | 延迟时间 | 说明 |
|----------|----------|------|
| 第 1 次 | 1 分钟 | 应对短暂网络抖动 |
| 第 2 次 | 2 分钟 | 等待打印机重启 |
| 第 3 次 | 4 分钟 | 最后一次尝试 |
| 超过 3 次 | — | 标记为失败，等待人工处理 |

### 关键设计点

1. **指数退避**：避免频繁重试加重网络负担
2. **有限重试**：防止无限重试消耗资源
3. **异步调度**：重试任务在后台延迟执行，不阻塞主流程
