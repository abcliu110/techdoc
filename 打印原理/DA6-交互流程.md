## 一、核心交互场景

### 场景一：创建打印任务（UC-1）

```
参与者: 业务系统（收银/订单）、PosPrnJobServicePlus、ActiveMQ
前置条件: 存在有效的打印队列配置，业务单据数据已准备好
后置条件: 打印任务已创建，消息已发布，等待分发

流程:
┌────────────┐    ┌──────────────────────┐    ┌───────────┐    ┌────────────┐
│ 业务系统    │    │ PosPrnJobServicePlus │    │   DB      │    │  ActiveMQ  │
└─────┬──────┘    └──────────┬───────────┘    └─────┬─────┘    └─────┬──────┘
      │                      │                      │               │
      │ create(dto)          │                      │               │
      │─────────────────────▶│                      │               │
      │                      │                      │               │
      │                      │ 生成lid              │               │
      │                      │──────────────────────────────────────▶│
      │                      │ INSERT pos_prn_job (PENDING)         │
      │                      │───────────────────▶│                  │
      │                      │◀────────────────────│                  │
      │                      │                      │               │
      │                      │ keepToFile()        │               │
      │                      │────────────────────▶│ .job文件       │
      │                      │                      │               │
      │                      │ Redis SET count:{lid}=0 (TTL 15min) │
      │                      │──────────────────────────────────────▶│
      │                      │                      │               │
      │                      │ 事务COMMIT           │               │
      │                      │───────────────────▶│                  │
      │                      │                      │               │
      │                      │ Publish PrintTaskCreated              │
      │                      │──────────────────────────────────────▶│
      │                      │                      │               │
      │ 返回lid              │                      │               │
      │◀─────────────────────│                      │               │
```

**异常分支**：
1. 队列不存在 → 抛出BizException，任务创建失败
2. DB写入失败 → 事务回滚，无消息发布
3. 文件写入失败 → 事务回滚，无任务记录
4. Redis不可用 → 回退到DB计数（BR-13）

**为什么这样设计**：
- 任务创建与文件写入同步，保证原子性
- 消息在事务提交后发布，保证消费时数据存在（BR-12）
- Redis计数使用15分钟TTL，避免历史数据残留

### 场景二：打印任务分发（UC-2）

```
参与者: ActiveMQ、PrintJobActiveMQListener、PrinterWorkerService、打印机
前置条件: 存在PENDING状态的打印任务，ActiveMQ中有消息
后置条件: 任务分发给打印机执行，或标记FAILED

流程:
┌────────────┐    ┌───────────────────────┐    ┌──────────────────┐    ┌────────────┐
│  ActiveMQ  │    │ PrintJobActiveMQListener│    │ PrinterWorker   │    │   打印机   │
└─────┬──────┘    └───────────┬───────────┘    └───────┬──────────┘    └─────┬──────┘
      │                        │                       │                    │
      │ Consume PrintTaskCreated                       │                    │
      │──────────────────────▶│                       │                    │
      │                        │                       │                    │
      │                        │ put(jobLid)           │                    │
      │                        │──────────────────────▶│                    │
      │                        │                       │                    │
      │                        │                       │ 查询转移规则        │
      │                        │                       │ ──────────────────▶│
      │                        │                       │◀────────────────────│
      │                        │                       │                    │
      │                        │                       │ 查询队列主打印机    │
      │                        │                       │───────────────────▶│
      │                        │                       │◀────────────────────│
      │                        │                       │                    │
      │                        │                       │ 检查打印机状态      │
      │                        │                       │───────────────────▶│
      │                        │                       │◀ NORMAL/BUSY/FAULT │
      │                        │                       │                    │
      │                        │                       │ getFromFile()      │
      │                        │                       │──────────────────────────────────▶│ .job文件
      │                        │                       │◀──────────────────────────────────│
      │                        │                       │                    │
      │                        │                       │ DriverHandler.handle()           │
      │                        │                       │────────────────────────────────────────▶│
      │                        │                       │◀────────────────────────────────────────│
      │                        │                       │                    │
      │                        │                       │ UPDATE status=SUCCESS              │
      │                        │                       │──────────────────────────────────────▶│
      │                        │                       │                    │
      │ 任务分发完成            │                       │                    │
      │◀────────────────────────│                       │                    │
```

**异常分支**：
1. 主打印机FAULT → 切换到备用打印机（2秒延迟）
2. 主备都FAULT → 标记status=FAILED，failureReason记录
3. 主备都BUSY → 任务阻塞等待
4. 转移规则命中 → 使用targetPrinter替代原打印机
5. 转移后目标也故障 → 标记FAILED

**为什么这样设计**：
- 主备failover保证打印可用性（BR-10）
- 转移规则在队列路由前执行，优先于静态配置
- Virtual Thread并发控制避免打印机过载

### 场景三：重打打印任务（UC-4）

```
参与者: 收银员、PosPrnJobServicePlus、业务系统
前置条件: 存在SUCCESS状态的打印任务，.job文件未过期
后置条件: 生成新的打印任务（lid不同），正常分发

流程:
┌────────────┐    ┌──────────────────────┐    ┌───────────┐    ┌────────────┐
│ 收银员     │    │ PosPrnJobServicePlus │    │   文件    │    │  ActiveMQ  │
└─────┬──────┘    └──────────┬───────────┘    └─────┬─────┘    └─────┬──────┘
      │                      │                      │               │
      │ reprint(lid)         │                      │               │
      │─────────────────────▶│                      │               │
      │                      │                      │               │
      │                      │ 校验原任务status=SUCCESS            │
      │                      │────────────────────▶│               │
      │                      │◀────────────────────│               │
      │                      │                      │               │
      │                      │ 读取.job文件内容    │               │
      │                      │────────────────────▶│               │
      │                      │◀────────────────────│ 打印内容      │
      │                      │                      │               │
      │                      │ 生成新lid            │               │
      │                      │ INSERT新任务         │               │
      │                      │────────────────────▶│               │
      │                      │                      │               │
      │                      │ 写入新.job文件       │               │
      │                      │────────────────────▶│               │
      │                      │                      │               │
      │                      │ Redis INCR count:{newLid}           │
      │                      │                      │               │
      │                      │ Publish PrintTaskReprinted          │
      │                      │─────────────────────────────────────▶│
      │                      │                      │               │
      │ 返回新lid            │                      │               │
      │◀─────────────────────│                      │               │
```

**异常分支**：
1. 原任务status≠SUCCESS → 抛出BizException，拒绝重打（BR-03）
2. .job文件不存在 → 抛出BizException，提示"文件已清理"
3. .job文件解析失败 → 抛出BizException
4. 新任务创建失败 → 事务回滚

**为什么这样设计**：
- 重打创建新任务（新lid），保证历史可追溯
- 状态校验BR-03防止重复重打已失败任务
- 文件读取保证重打内容与原任务一致

### 场景四：WMS云端打印（UC-5）

```
参与者: WMS系统、pos4cloud、WmsPrintRenderService、EscPosRenderService
前置条件: 存在WMS单据数据，已配置对应打印样式
后置条件: 返回Base64编码的ESC/POS字节流

流程:
┌────────────┐    ┌───────────────────────┐    ┌──────────────────────┐
│ WMS系统    │    │ pos4cloud Feign接口   │    │ WmsPrintRenderService│
└─────┬──────┘    └───────────┬───────────┘    └───────────┬──────────┘
      │                        │                           │
      │ render(mid, sid, type, data)                       │
      │──────────────────────▶│                           │
      │                        │                           │
      │                        │ 加载打印样式 (mid/sid/type)│
      │                        │──────────────────────────▶│
      │                        │◀──────────────────────────│ 样式模板
      │                        │                           │
      │                        │                           │ 参数替换 {@fieldName}
      │                        │                           │
      │                        │                           │ 合并数据到模板
      │                        │                           │
      │                        │                           │ EscPosRenderService生成字节流
      │                        │                           │
      │                        │ 返回Base64编码的ESC/POS   │
      │◀───────────────────────│                           │
```

**异常分支**：
1. 样式未配置 → 抛出BizException
2. 数据源缺失字段 → 参数替换为空，显示空白
3. 字符集不匹配 → GBK编码确保中文正确（BR-16）

**为什么这样设计**：
- 渲染服务与执行分离，支持本地和云端不同执行方式
- Base64编码便于传输和日志记录
- 样式按商户+门店+类型加载，保证多租户隔离（BR-18）

### 场景五：打印任务状态查询（UC-6）

```
参与者: 前端、PosPrnJobServicePlus、Redis、文件系统
前置条件: 用户有权限查询指定商户+门店的打印任务
后置条件: 返回任务列表和实时状态

流程:
┌────────────┐    ┌──────────────────────┐    ┌───────────┐    ┌────────────┐
│ 前端页面   │    │ PosPrnJobServicePlus │    │   Redis   │    │   文件系统 │
└─────┬──────┘    └──────────┬───────────┘    └─────┬─────┘    └─────┬──────┘
      │                      │                      │               │
      │ listVO(mid, sid, dateRange)                  │               │
      │─────────────────────▶│                      │               │
      │                      │                      │               │
      │                      │ 查询pos_prn_job列表  │               │
      │                      │────────────────────▶│               │
      │                      │◀────────────────────│ 任务列表      │
      │                      │                      │               │
      │                      │ 批量获取Redis计数    │               │
      │                      │─────────────────────▶│               │
      │                      │◀─────────────────────│ count:{lid}   │
      │                      │                      │               │
      │                      │ resolveEffectiveStatus()             │
      │                      │  (综合print+status+count+file存在)   │
      │                      │                      │               │
      │                      │ 返回任务VO列表       │               │
      │◀─────────────────────│                      │               │
```

**状态计算逻辑**：
```
resolveEffectiveStatus():
  if (status == SUCCESS) → 成功
  else if (status == FAILED) → 失败
  else if (status == PENDING):
      if (count > 0) → 正在打印
      else → 等待打印
```

**异常分支**：
1. Redis不可用 → 回退到DB的prnCount字段（BR-13）
2. 文件不存在 → 状态显示"详情不可查"
3. 文件解析失败 → 返回空内容

**为什么这样设计**：
- Redis计数提供实时状态，DB作为持久化存储
- 状态计算综合多因素，避免单一状态不一致
- 批量获取Redis减少网络开销
