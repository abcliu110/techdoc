## §1 设计评估（REV-*）

### 1.1 设计意图追溯

#### 核心设计决策总结

| 决策 | 意图 | 当时约束 | 当前合理性 | 是否退化 |
|------|------|---------|-----------|---------|
| DEC-001 文件分离 | 大内容不存 DB，按日期清理 | DB 存大文本效率低 | 仍合理 | 否 |
| DEC-002 Redis 计数 | 高频计数不压 DB | 频繁更新 DB 有性能瓶颈 | 仍合理 | 否 |
| DEC-003 逗号分隔主备 | 简化查询，减少表关联 | 设计初期规模小 | 仍合理但有限制 | **部分退化**（业务增长后 N:N 需求出现） |
| DEC-004 三套实现 | 场景差异大，策略模式隔离 | 本地/离线/云打印差异大 | 仍合理 | 否（OnlineImpl 空实现是未完成，非退化） |
| DEC-005 事务后 MQ | 保证消费者读到已提交数据 | 分布式事务复杂 | 仍合理 | 否 |
| DEC-006 枚举硬编码 | 编译期类型安全 | 样式与业务逻辑强关联 | **部分过期**（WMS 增长快，枚举膨胀） | **退化中** |
| DEC-007 Virtual Thread | 简化并发编程 | Java 21 正式发布 | 仍合理 | 否 |

**结论**：7 个决策中 5 个仍合理，2 个出现退化信号（DEC-003 逗号分隔、DEC-006 枚举膨胀）。退化不是因为当时决策错，而是**业务规模增长**——这正是设计退化的典型模式：在 N 规模时合理的决策，在 10N 规模时成为约束。

### 1.2 设计合理性评估（五维度）

#### 评估对象 1：打印任务生命周期（PosPrnJobServicePlus）

| 维度 | 评分 | 证据 | 说明 |
|------|------|------|------|
| 职责分配 | 4/5 | {DA7 §1.1: 7 个核心方法} | 职责内聚（创建/重打/删除/计数/状态计算），但状态计算（resolveEffectiveStatus）与 CRUD 混在同一类中 |
| 抽象层次 | 3/5 | {DA7 §1.1} | **抽象泄漏**：keepToFile() 直接操作文件路径（`{appDir}/jobs/{date}/{lid}.job`），getFromFile() 同样。Service 层不应感知文件路径格式 |
| 关注点分离 | 3/5 | {DA7 §1.1} | 文件操作、Redis 操作、MQ 发布、DB 操作全部在同一个 Service 类中。四个关注点（文件/缓存/消息/持久化）未分离 |
| 一致性 | 4/5 | {DA7 §1.1: resolveEffectiveStatus()} | 状态计算逻辑统一（print+status 双字段），但状态枚举（PENDING/SUCCESS/FAILED）与状态计算逻辑的耦合未显式表达 |
| 演进能力 | 3/5 | {DA7 DEC-006} | 枚举膨胀已经开始影响演进（新增样式类型需改代码发版）；文件操作硬编码路径，切换存储策略需改 Service 代码 |

**综合**：3.4/5。**核心问题**：Service 类承担了太多关注点，且抽象层次不统一。

#### 评估对象 2：打印分发与执行（PrinterWorkerService 三实现）

| 维度 | 评分 | 证据 | 说明 |
|------|------|------|------|
| 职责分配 | 5/5 | {DA7 §1.3: Local/Offline/Online} | 三实现职责清晰，策略模式使用得当 |
| 抽象层次 | 4/5 | {DA7 §1.3} | 接口（PrinterWorkerService）与实现（Local/Offline/Online）分离，但 OnlineImpl 空实现暴露了接口设计超前于能力交付 |
| 关注点分离 | 5/5 | {DA7 §1.3} | 本地/离线/云打印关注点完全分离，通过策略模式统一 |
| 一致性 | 5/5 | {DA7 §1.3} | 三实现统一接口 handlePrnJob()，行为一致 |
| 演进能力 | 4/5 | {DA7 DEC-004} | 策略模式支持新增实现，但 OnlineImpl 空实现说明"接口设计先于实现"的风险 |

**综合**：4.6/5。**最佳设计**，是打印系统中最值得保留的架构模式。

#### 评估对象 3：打印队列与打印机路由（REL-05 / REL-09）

| 维度 | 评分 | 证据 | 说明 |
|------|------|------|------|
| 职责分配 | 3/5 | {DA7 §5.2: 逗号分隔} | 队列配置同时承担了"打印机列表"和"主备策略"两个职责，逗号分隔无法区分优先级权重 |
| 抽象层次 | 2/5 | {DA7 §5.2: E-001:54-59} | **严重抽象泄漏**：路由逻辑（"遍历逗号列表，返回第一台健康打印机"）直接依赖字符串解析，没有抽象出"路由策略"概念 |
| 关注点分离 | 3/5 | {DA7 §5.2} | 打印机选择逻辑（路由策略）与健康检查逻辑（PrinterStatus）在同一方法中 |
| 一致性 | 4/5 | {DA7 §5.2} | 主备 failover 行为一致，但"逗号顺序即优先级"是隐性契约，未显式表达 |
| 演进能力 | 2/5 | {DA7 DEC-003} | **最弱的演进能力**：新增备机数量、按状态过滤、并发修改逗号字符串均有竞态风险；支持"按权重路由"或"按场景路由"需要完整重写 |

**综合**：2.8/5。**最薄弱设计**，也是整个打印系统最大的重构候选。

#### 评估对象 4：打印样式与渲染（PosPrnStyleRow / WmsPrintRenderService）

| 维度 | 评分 | 证据 | 说明 |
|------|------|------|------|
| 职责分配 | 4/5 | {DA7 §1.4: 渲染/生成/加载/替换} | 职责清晰，但渲染和生成耦合（WmsPrintRenderService 同时做渲染和 ESC/POS 生成） |
| 抽象层次 | 3/5 | {DA7 DEC-006} | 枚举硬编码在编译期（70+业务+50+WMS），但 WMS 部分增长快，硬编码的抽象层次不匹配变化频率 |
| 关注点分离 | 4/5 | {DA7 §1.4} | 样式加载、渲染、参数替换分离，但渲染和生成混在一起 |
| 一致性 | 3/5 | {DA7 §1.6: PrnStyleTypeEnum} | 单一枚举承载多域类型（业务+WMS），类型耦合 |
| 演进能力 | 2/5 | {DA7 DEC-006} | 新增 WMS 样式需改枚举代码发版，无法独立扩展 |

**综合**：3.2/5。**枚举膨胀是主要风险**，渲染与生成分离是次要优化。

### 1.3 设计退化识别

| 退化路径 | 起点 | 当前状态 | 退化原因 |
|---------|------|---------|---------|
| 逗号分隔主备 | 初期 N:2（主+备），字符串简单 | 业务增长后 N:N 需求出现，字符串无法扩展 | 规模增长 |
| 枚举膨胀 | 初期 70+ 业务枚举，WMS 枚举未出现 | WMS 50+ 枚举持续增长，硬编码限制扩展 | 新域引入 |
| OnlineImpl 空实现 | 规划三套架构，Online 预留接口 | 接口设计完成但实现为空，架构声明与实现不符 | 交付滞后 |
| 状态计算逻辑 | 双字段（print+status）组合出有效状态 | 逻辑集中在一个方法，新增状态需同步修改 | 设计未显式化 |

**模式**：所有退化都不是"当时设计错了"，而是**"设计时假设的规模/场景与实际不符"**——这恰恰说明设计评估需要区分"设计是否合理"和"设计是否适应当前规模"。

### 1.4 架构健康度评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构风格匹配度 | 4/5 | 分层架构（业务层→消息层→执行层→驱动层）匹配打印业务场景，但云端层（pos4cloud）与核心打印层（pos2plugin）的职责边界模糊 |
| 分层合理性 | 3/5 | **分层泄漏**：PosPrnJobServicePlus 同时做业务逻辑、文件操作、Redis 操作、MQ 发布——四个关注点在同一层 |
| 依赖方向正确性 | 4/5 | 业务层→消息层→执行层→驱动层，依赖方向正确；但云端层（pos4cloud）依赖驱动层（pos10printer），**跨层依赖** |
| 技术选型合理性 | 4/5 | ActiveMQ（消息队列）、Redis（计数）、Virtual Thread（并发）、文件系统（临时存储）——选型合理，但 ActiveMQ 的幂等性和死信策略未确认 |
| 扩展性 | 3/5 | 策略模式（PrinterWorkerService）扩展性好，但逗号分隔路由和枚举硬编码是扩展瓶颈 |

**架构健康度综合**：3.6/5。**核心问题**：业务层关注点混用 + 路由建模反模式 + 枚举膨胀。

## §2 业务本质（ESS-*）

### 2.1 技术实现剥离

| 技术实现（产物原文） | 业务本质 |
|---------------------|---------|
| Redis INCR 计数 + 15 分钟 TTL | 系统需要统计打印次数，允许短暂不准确，不需要严格持久化 |
| .job 文件按日期存储，15 分钟过期改名 .del，30 天物理删除 | 打印内容需要临时缓存，支持重打，但不需要长期保留 |
| 逗号分隔字符串存储主备打印机 ID | 一个队列可以有多个备选打印机，运行时选一个 |
| 枚举 PrnStyleTypeEnum（70+业务 + 50+WMS） | 不同类型的打印需要不同的样式模板 |
| TransactionSynchronization 事务后发 MQ | 消息消费时数据必须已持久化 |
| PrinterWorkerService 三套实现（Local/Offline/Online） | 不同运行环境需要不同的打印执行方式 |
| Virtual Thread 实现并发控制 | 多个打印任务可以并发执行，但单任务内部顺序执行 |

### 2.3 业务边界划分

| 业务域 | 职责 | 核心概念 | 变化频率 | 对外能力 |
|--------|------|---------|---------|---------|
| **打印请求** | 接收打印请求，管理任务生命周期 | 打印请求、任务状态、重打/删除 | 低 | 发起打印、重打、删除、查询 |
| **打印路由** | 决定打印任务发到哪个设备 | 打印目标、主备策略、转移规则 | 中 | 设备选择、故障转移、动态重路由 |
| **打印执行** | 发送指令到打印设备 | 打印设备、设备状态、打印协议 | 低 | 本地打印、离线打印、云端打印 |
| **打印样式** | 管理打印内容的格式 | 样式类型、样式模板、参数替换 | 高 | 模板加载、渲染、ESC/POS 生成 |
| **打印统计** | 统计打印次数和状态 | 计数、历史记录 | 低 | 计数查询、统计报告 |

**边界划分判断**：当前实现中，"打印请求"和"打印路由"的职责在同一个 Service 类中（PosPrnJobServicePlus），但业务本质上是两个独立的业务域——请求管理不需要知道路由细节，路由也不需要知道请求的内容。**这是当前设计最值得重构的边界。**

## §3 目标设计（TGT-*）

### 3.1 目标业务模型

基于业务本质（§2），目标业务模型应该：

**保留**（现状已经合理的）：
- 打印请求生命周期管理（创建/重打/删除/状态计算）——ESS 稳定层，不变
- 三实现架构（Local/Offline/Online）——ESS 打印执行域，不变
- 事务后 MQ 发布——ESS 稳定机制，不变
- 文件与元数据分离——ESS 稳定模式，不变

**调整**（现状需要改进的）：
- **打印路由从"队列+逗号字符串"升级为"路由策略对象"**——ESS 打印路由域，变化频率中
- **打印样式从"枚举硬编码"演进为"类型配置化"**——ESS 打印样式域，变化频率高
- **打印请求与打印路由的职责分离**——ESS 边界划分，当前混在同一 Service 中

| 变化 | 从 | 到 | 原因 |
|------|----|----|------|
| 打印路由分离 | 路由逻辑混在 PosPrnJobServicePlus 中 | 独立 PrintDispatchService + RouteStrategy | 职责分离（REV-01 评估结论） |

### 3.3 设计决策记录（TGT-DEC-*）

#### TGT-DEC-01：打印路由域独立

| 字段 | 内容 |
|------|------|
| 决策点 | 为什么要把打印路由从 PosPrnJobServicePlus 中分离出来？ |
| 现状 | 路由逻辑（队列选择、主备 failover、转移规则）混在 PosPrnJobServicePlus 中，与请求管理耦合 |
| 目标 | 独立 PrintDispatchService，请求管理只负责"发起请求"，路由负责"发给谁" |
| 候选 | A. 现状（不分离）；B. 轻量分离（路由逻辑提取到独立方法，仍在同一类）；C. 域分离（独立 Service + 独立数据模型） |
| 选择与理由 | 选择 C。因为路由策略需要独立演进（新增策略类型、支持权重），与请求管理的生命周期不同 |
| 取舍代价 | 增加一个 Service 类的复杂度；需要处理事务边界（请求创建 + 路由决策是同一个事务？） |
| 触发条件 | 立即（当前混用已导致 REV-01 评估评分 3.4，是核心瓶颈） |

#### TGT-DEC-02：路由策略对象化

| 字段 | 内容 |
|------|------|
| 决策点 | 用什么模型替代逗号分隔字符串？ |
| 现状 | primaryPrinter / standbyPrinter 两个逗号分隔字段，遍历取第一台健康打印机 |
| 目标 | RouteStrategy 接口 + 实现，支持主备/加权/轮询，数据模型用关联表或 JSON 配置 |
| 候选 | A. 关联表（route_strategy_device 表，策略 → 设备 N:N，带权重/优先级）；B. JSON 配置字段（strategyConfig JSON，存策略类型+设备列表+参数）；C. 保持现状 |
| 选择与理由 | 选择 B（JSON 配置）。兼容性最好（不新增表，存量数据可迁移）；查询复杂度低；支持未来扩展。关联表虽然更范式化，但迁移成本高（需改队列配置接口） |
| 取舍代价 | JSON 配置的约束不如关联表强（无外键约束，需应用层校验）；但权衡迁移成本后，JSON 是更现实的过渡方案 |
| 触发条件 | 需要新增"按权重路由"或"按场景路由"策略时 |

#### TGT-DEC-03：打印样式类型配置化

| 字段 | 内容 |
|------|------|
| 决策点 | 用什么替代枚举硬编码？ |
| 现状 | PrnStyleTypeEnum 70+ 业务 + 50+ WMS 枚举，新增需改代码发版 |
| 目标 | PrintStyleRegistry 动态注册，类型定义在 DB 或配置中心，运行时加载 |
| 候选 | A. 数据库配置（style_type 表，code+name+renderer）；B. 配置中心（Nacos/Apollo）；C. 枚举+扩展点（保留枚举，增加 SPI 扩展机制） |
| 选择与理由 | 选择 A（数据库配置）。WMS 类型增长快，需要独立扩展；枚举保留作为系统内置类型（业务核心），WMS 类型走 DB 配置。逐步迁移，不一次性全部替换 |
| 取舍代价 | 失去编译期类型检查（需运行时校验）；新增类型查询成本；但权衡后，WMS 类型的动态化需求 > 编译期检查的收益 |
| 触发条件 | WMS 类型超过 100 种时（当前 50+，按增长趋势 6 个月内可达） |

#### TGT-DEC-04：跨域服务提取

| 字段 | 内容 |
|------|------|
| 决策点 | 是否要把文件/计数/消息操作提取为独立服务？ |
| 现状 | 文件操作（keepToFile/getFromFile）、Redis 计数（incrPrnCount）、MQ 发布（TransactionSynchronization）全部在 PosPrnJobServicePlus 中 |
| 目标 | PrintFileService、PrintCountService、PrintMessageService 三个独立服务，PosPrnJobServicePlus 只做编排 |
| 候选 | A. 提取为独立 Service（每个关注点一个类）；B. 提取为内部 Helper（同一包内，不暴露接口）；C. 现状 |
| 选择与理由 | 选择 A。因为三个关注点的变化频率不同（文件存储策略可能变、计数方式可能变、消息队列可能变），独立后各自演进不受影响 |
| 取舍代价 | 增加 3 个类；调用链路变长（Service → Service → 基础设施）；但职责分离的收益 > 复杂度增加 |
| 触发条件 | 立即（当前混用已导致 REV-01 评估评分 3.4） |

## §4 迁移路径（MIG-*）

### 迁移路线图

```
阶段1（立即）：修复 P1 缺陷 + 跨域服务提取
阶段2（短期）：打印路由域分离 + 路由策略对象化
阶段3（中期）：打印样式类型配置化
阶段4（长期）：打印执行域补齐 + 架构演进评估
```

### MIG-01：阶段 1 — 修复 P1 缺陷 + 提取跨域服务（建议 1-2 周）

| 项 | 内容 |
|----|------|
| 目标 | 消除 P1 风险，为后续重构打好基础 |
| 步骤 | ① 提取 PrintFileService（封装文件操作，支持存储策略切换）② 提取 PrintCountService（封装 Redis 计数，支持回退策略）③ 提取 PrintMessageService（封装 MQ 发布，支持幂等）④ 状态持久化：pos_prn_printer 表补 status 字段，启动时恢复 ⑤ 消息幂等：消费时检查任务状态/计数 |
| 兼容策略 | ①-③ 提取后保留原方法签名（委托到新 Service），存量调用方零改动；④ 补列默认值，存量行自动兼容；⑤ 功能开关控制 |
| 验证设计 | ①②③ 影子模式：新旧实现并行，对比输出一致；④⑤ A-B：修复前后行为对比 |
| 回滚方案 | ①-③ 回滚 = 删除新 Service + 恢复原方法体；④ 回滚 = 删除列（确认无写入）；⑤ 回滚 = 关闭开关 |
| 风险 | 提取过程中可能漏掉调用方（需全量扫描）；状态持久化可能影响现有状态流转 |

### MIG-02：阶段 2 — 打印路由域分离 + 路由策略对象化（建议 2-4 周）

| 项 | 内容 |
|----|------|
| 目标 | 路由逻辑从请求管理中分离，路由策略对象化 |
| 步骤 | ① 创建 PrintDispatchService（路由决策逻辑从 PosPrnJobServicePlus 迁移）② 创建 RouteStrategy 接口 + PrimaryBackupStrategy 实现（替代逗号遍历逻辑）③ 队列配置加 strategyConfig JSON 字段（兼容存量逗号字段）④ 迁移逻辑：读队列时优先读 strategyConfig，不存在则从逗号字段兼容 ⑤ 存量数据迁移脚本：逗号 → JSON 配置 |
| 兼容策略 | ③ 双字段共存（strategyConfig 新字段 + primaryPrinter/standbyPrinter 旧字段），读新写旧 → 读新写新 → 清旧 三步走 |
| 验证设计 | 影子模式：新旧路由逻辑并行，对比路由结果一致 |
| 回滚方案 | 每步可回滚：① 回滚 = 恢复 PosPrnJobServicePlus 路由逻辑；③ 回滚 = 删除 strategyConfig 字段；⑤ 回滚 = 从 JSON 恢复逗号数据 |
| 风险 | 路由结果不一致（新旧逻辑差异）；存量数据迁移失败 |

### MIG-03：阶段 3 — 打印样式类型配置化（建议 4-8 周）

| 项 | 内容 |
|----|------|
| 目标 | 枚举膨胀问题解决，WMS 类型可动态扩展 |
| 步骤 | ① 创建 style_type 表（code/name/renderer/mid/sid/status）② 创建 PrintStyleRegistry（运行时加载，缓存）③ 业务核心枚举保留（70+ 业务枚举，变化频率低）④ WMS 枚举迁移到 DB（50+ 枚举 → 配置数据）⑤ 接口兼容：新增样式类型接口支持 DB 注册，旧枚举接口保留 |
| 兼容策略 | ③ 业务枚举保留，不迁移（编译期检查的收益 > 动态化收益）；④ WMS 枚举只迁移，不改运行时行为；⑤ 接口层做适配（新旧查询合并） |
| 验证设计 | A-B：新旧类型加载方式并行，对比渲染结果一致 |
| 回滚方案 | ④ 回滚 = 从 DB 恢复枚举代码（枚举值不变，只改加载方式） |
| 风险 | 运行时加载性能（需缓存）；WMS 类型迁移遗漏 |

### MIG-04：阶段 4 — 打印执行域补齐（建议 4-8 周）

| 项 | 内容 |
|----|------|
| 目标 | OnlineImpl 补齐，三套架构完整可用 |
| 步骤 | ① 确认 OnlineImpl 是否有调用方（EVO-U-03 取证）② 设计云打印通道（消息转发 / 云端打印服务）③ 实现 OnlineImpl ④ 灰度上线 |
| 兼容策略 | 功能开关控制，逐步放量 |
| 验证设计 | 影子模式：OnlineImpl 与 LocalImpl 并行，对比打印结果一致 |
| 回滚方案 | 开关关闭 = 回退到 LocalImpl |
| 风险 | 云打印通道的延迟和可靠性；网络分区下的行为 |
