# 309 个复杂 UI 原型业务真实性升级设计

## 1. 已批准目标

把现有 309 个“可点击交互示意”升级为可用于产品、业务和研发联合评审的企业业务原型。

- 01-17 类共 279 项采用 B 级“任务真实”：每项围绕一个明确角色和业务任务形成操作闭环。
- 18 类 30 项采用 C 级“系统真实”：每项串联多个业务对象、规则、角色和下游结果。
- 全套共享“工业设备企业经营”业务世界，避免同一客户、商品、订单、组织和状态在不同组件中互相矛盾。
- 保留 13 册、309 个组件 ID、HTML 文件名、Hash 深链接和独立 renderer 约束。

## 2. 统一业务世界

企业：华辰工业设备集团。核心组织包括总部、华东事业部、华南事业部、上海销售部、苏州工厂、华东仓和华南仓。

稳定角色：销售代表林晓、销售经理周宁、财务经理陈敏、仓库主管王蕾、采购经理罗强、实施顾问李明、系统管理员赵峰。

稳定对象：

- 客户：星河科技 `C-1008`、远山零售 `C-1021`、青禾制造 `C-1036`。
- 商品：工业网关 X2 `GW-X2`、边缘控制器 E5 `EC-E5`、传感器套件 S1 `SS-S1`。
- 单据：销售订单 `SO-20260714-018`、采购申请 `PR-20260714-006`、合同 `CT-2026-088`、发票 `INV-2026-0714`、工单 `WO-2026-0418`。
- 关键事实：订单金额 201,000 元、申请折扣 12%、客户可用信用 160,000 元、华东仓 X2 可售 8 台、华南仓可售 35 台、逾期应收 42,000 元。

这些值可以因组件任务发生受控变化，但相同身份和基础事实不得无理由改变。

## 3. B 级任务真实标准

每个 01-17 类组件必须显式具备：

1. 角色与任务：页面上能看出“谁正在处理什么”。
2. 业务对象：至少一个稳定编号、名称或关系上下文。
3. 决策依据：至少一条可见规则、权限、容量、金额、状态或时间约束。
4. 真实操作链：2-5 个关键动作，不能只用一个按钮改变状态字符串。
5. 异常或冲突：至少一个可触发并可恢复的失败、越权、冲突、空态或边界状态。
6. 业务结果：操作影响业务对象、待办、库存、权限、审计、指标或下游步骤之一。
7. 可解释状态：状态栏用于自动化指纹，页面主体同时呈现人能理解的结果和原因。

组件本质仍是第一优先级。例如虚拟表格要处理大订单行窗口化，权限矩阵要处理角色授权差异，状态机要处理合法和非法转换；不能把所有组件都做成销售订单表单。

### 3.1 统一生产级底线

309 项无论类别和复杂度，都必须满足同一组最低验收条件：

1. 初始态可理解：角色、任务、业务对象、规则和当前状态均在主体区域可见。
2. 主路径可完成：用户能通过 2-5 个连续动作得到明确业务结果，而不是只改变演示文案。
3. 非理想路径可触发：至少覆盖一个与组件本质相关的空态、校验失败、拒绝、冲突、脏数据确认、加载失败或边界状态。
4. 失败可恢复：非理想路径必须提供重试、撤销、清除、返回、修正输入或重新授权中的适用动作。
5. 状态可解释：结果区域同时显示发生了什么、为什么发生、影响哪个对象或后续步骤。
6. 操作可达：原生交互控件可通过键盘到达，焦点可见，名称和状态可被辅助技术理解。
7. 布局可用：桌面端和移动端均无阻断式裁切、不可达滚动、遮挡或控制目标过小。
8. 生命周期可靠：切换组件和重置后恢复一致初态，不泄漏监听器、计时器或前一组件状态。
9. 运行安全：控制台无未处理异常，用户输入通过安全 DOM API 输出，不执行注入内容。

“统一”只代表验收底线一致，不代表所有组件拥有相同数量的状态、同样复杂的页面或同一种业务流程。只实现与组件本质相关的状态，避免为了凑矩阵制造无意义场景。

## 4. C 级系统真实标准

18 类每项在 B 级基础上还必须包含：

- 至少三个关联业务对象或模块。
- 至少两个角色或职责边界。
- 一个跨模块约束或联动结果。
- 一段可追踪的事件、状态时间线或审计记录。
- 主路径与异常路径均可操作，并显示对金额、库存、排期、权限或 SLA 的影响。

## 4.1 风险分层附加标准

在统一底线之上，按组件风险增加验收深度：

- 低风险展示与导航：重点验证信息层级、上下文保持、键盘导航、响应式和返回路径。
- 数据处理类（表格、树、表单、查询、选择器）：增加批量/边界数据、校验、空结果、加载与提交失败、脏数据确认；涉及共享记录时演示冲突处理。
- 创作编排类（编辑器、低代码、流程规则）：增加撤销/重做或等价恢复、未保存变更、校验定位、预览/发布失败和版本差异。
- 安全协作类（权限、组织、消息协作）：增加拒绝原因、数据范围、审计记录、并发冲突、离线/重试和重复操作保护。
- 业务复合类：增加跨模块规则、金额/库存/排期/SLA 影响、职责边界、事件时间线和补偿路径。

风险层级只允许增加要求，不允许豁免统一底线。高风险组件不得用一次点击或状态字符串变化代替完整演示。

## 5. 类别到业务任务映射

- 01 布局：经营驾驶舱、订单工作台、设备监控和多岗位工作区的空间组织。
- 02 表格：订单、库存、应收、采购和设备台账的高密度处理。
- 03 树：组织、产品分类、仓库库位、权限、依赖和客户关系层级。
- 04 表单：客户、合同、销售订单、采购申请、工单和费用申请录入。
- 05 查询：订单履约、库存短缺、应收风险、工单 SLA 和审计检索。
- 06 选择器：客户、商品、组织、人员、仓库、时间、地址和业务对象选择。
- 07 编辑器：合同条款、规则、SQL、模板、报表和设备配置编辑。
- 08 低代码：订单应用、工单应用、报表、数据源、事件、发布和版本治理。
- 09 流程规则：销售审批、采购审批、信用规则、库存调拨和设备告警编排。
- 15 导航：不同岗位进入任务、对象、搜索、收藏和工作区的路径。
- 16 权限：租户、组织、对象、字段、动作、数据范围、策略和审计治理。
- 17 协作：订单会话、合同批注、工单协作、通知、冲突和离线重放。
- 18 复合：订单履约、库存、价格、财务、人力、CRM、物流、工单、教育、医疗和设备系统闭环；非工业领域组件使用集团培训、职业健康等合理子域承载。

## 6. 源码边界

- 新增 `prototype-suite/business-world.mjs`：只保存稳定业务实体、格式化和无行为 UI 原子 helper。
- 各类别文件继续显式导出每个 renderer；任务规则、状态机和操作必须写在对应 renderer 内。
- 交互 contract 增加 `business` 元数据：`level`、`role`、`task`、`objects`、`rule`、`exception`、`effect`。
- 不允许通过一个通用 `taskRenderer(config)` 或循环生成 309 个行为。

## 7. 验收门禁

静态门必须验证：

- 309 项均有业务元数据；01-17 为 B、18 为 C。
- 每项至少 2 个 contract step，并包含正常路径和异常/边界路径标识。
- B 项至少一个业务对象和一个业务结果；C 项至少三个对象且声明跨模块结果。
- renderer 仍为 309 个唯一函数引用，无 default/fallback renderer。
- 页面不得出现占位语句、无意义“记录 1/客户 A/按钮 1”等虚假数据。
- 每项声明适用的非理想状态和恢复动作；高风险类别声明对应的附加风险能力。
- 交互控件使用可聚焦的原生元素或等价语义，不以无语义元素模拟按钮。

浏览器门逐项验证：

- 初始页面呈现角色、任务、对象和规则。
- 执行主路径后得到声明的业务结果。
- 执行异常或边界路径后显示原因和恢复动作。
- 重置恢复一致初态，无跨组件状态泄漏。
- 桌面与移动无阻断溢出，控制台无异常，用户输入无 XSS。
- 键盘可以完成主路径并到达恢复动作，焦点顺序与可见状态合理。
- 浏览器断言读取主体中的业务对象、结果、原因和恢复状态，不以机器状态字符串发生变化作为唯一通过条件。

## 8. 兼容和回滚

- 外部 HTML、Hash 和导航协议保持不变。
- 旧 renderer 源码由同路径替换，构建产物可由构建脚本重建。
- 回滚时恢复类别模块、contract 和共享样式，再重新构建 14 个 HTML。
- 不新增第三方运行依赖。

## 9. 失败预演

- 失败：只是加业务文案，交互仍为空。防护：contract 强制两条路径并验证主体结果。
- 失败：所有原型都变成订单页面。防护：类别映射和组件决定性差异逐项审查。
- 失败：共享 helper 演变成行为模板。防护：helper 只做数据与 DOM 原子，禁止接受规则/状态配置。
- 失败：309 项数据互相矛盾。防护：稳定身份统一从 business-world 导入，变化需由操作产生。
- 失败：C 级页面堆信息但没有联动。防护：必须验证跨模块结果和事件时间线。
