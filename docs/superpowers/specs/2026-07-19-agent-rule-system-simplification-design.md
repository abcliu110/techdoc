# AI Agent 规则体系精简与一致性修正设计

## 目标

在不削弱安全底线的前提下，删除重复、过时和互相冲突的规则，保留职责清晰的分层文档，并让 `D:\AGENTS.md` 与 `D:\CLAUDE.md` 最终字节一致。

## 已确认问题

- `L4` 事故/回归规则没有明确继承敏感业务规则，存在事故场景遗漏 `L3` 安全约束的风险。
- 根入口、分析方法、调试规范使用了不同的证据和诊断标签。
- TDD、特征化测试和既有行为保护的先后顺序不一致。
- 根入口把 UTF-8 中文文件读取一律写成 `-Raw`，与 Windows 编码专项规则冲突。
- 验证规则把“命令执行完”或“报告生成”混同为业务成功。
- CRM 写操作被统一建议使用 `Propagation.SUPPORTS`，与写事务要求冲突。
- Shadow Mode 示例记录完整结果对象，违反日志最小化和脱敏要求。
- `NOT NULL` 与默认值强绑定，可能制造虚假业务值。
- “保留旧逻辑”没有给安全漏洞、越权、跨租户和财务完整性错误设置例外。

## 备选方案

### 方案 A：合并成一个大入口文件

优点是查找路径最短；缺点是入口会继续膨胀，项目规则、领域规则和操作系统规则难以独立维护。该方案不采用。

### 方案 B：保留模块化文件，删除重复定义并建立单一事实源

根入口只负责路由、不可覆盖的安全底线和交付契约；专项文件分别负责思考、调试、验证、Windows、Java/CRM、可观测性和小程序自动化。引用处不再复述完整规则，只写触发条件和链接。该方案改动可控，采用此方案。

### 方案 C：只修当前发现的几处矛盾

改动最小，但重复清单和多套术语会继续漂移，无法满足“哪些可以去掉”的精简目标。该方案不采用。

## 结构设计

### 保留的文件

- `D:\AGENTS.md`、`D:\CLAUDE.md`：工作区入口和路由。
- `D:\workspace-reference.md`：项目、图谱和同步映射数据。
- `D:\知识.md`：可复用故障记忆。
- `D:\agent-rules\10-thinking.md`：复杂判断和方案设计。
- `D:\agent-rules\15-evolution-and-observability.md`：演进、开关、可观测性和回滚。
- `D:\agent-rules\20-debugging.md`：复现、假设、实验和根因。
- `D:\agent-rules\30-verification.md`：验收标准、执行结果和证据完整性。
- `D:\agent-rules\40-windows-encoding.md`：Windows、PowerShell 和编码。
- `D:\agent-rules\50-domain-java-crm.md`：Java/CRM 领域约束。
- `D:\agent-rules\60-ai-prompting-and-modeling.md`：仅保留确有独立价值的模型协作规则。
- `D:\agent-rules\70-miniprogram-automation.md`：小程序自动化专项规则。
- `既有系统安全修改代码AI执行规范.md`：保留为既有系统变更的详细规范，但缩短重复内容。

### 删除或收缩的内容

- 删除根入口和专项文档中重复的完整检查清单、编码说明、交付模板和安全红线复述，保留一个权威定义和短引用。
- 删除“风险等级互相替代”的含义，改为“操作基线 + 业务风险标签 + 场景标签”的规则取并集。
- 删除无条件要求功能开关、包装层、Shadow Mode 和默认值的绝对表述，改成按风险和兼容性证据触发。
- 删除 Shadow Mode 中记录完整对象的示例。
- 删除把 Review 任务等同于实施任务的前置义务。
- 删除多套互相竞争的事实标签；通用分析统一使用五档证据类型，Bug 排查另用“已复现根因 / 有证据候选 / 待验证假设”表示诊断状态。
- 删除“报告存在即成功”的终态定义，拆成业务成功、执行完成和阻塞。

## 核心规则

### 路由

先按任务操作确定 L0/L1/L2 基线，再叠加敏感业务和事故/回归标签；最终必读规则是所有命中项的并集。L4 不再覆盖 L3。

### 既有行为与 TDD

统一顺序为：旧行为基线 PASS → 新需求或缺陷用例 RED → 最小实现 → 新旧回归。安全漏洞、越权、跨租户、密钥泄露和财务完整性错误不作为必须保留的兼容契约，但修复前仍需识别调用方和迁移影响。

### 证据与诊断

通用分析使用“直接事实、主流共识、经验判断、推断、假设”。Bug 根因另外记录诊断状态，避免把证据类型和复现状态混为一谈。只有复现且因果实验成立时才能写“已复现根因”。

### 验证

固定验收标准不能为通过测试而修改。验证结果必须区分：业务成功、命令执行完成但业务失败、因外部条件阻塞。检查退出码、报告正文、产物可读性和清理阶段错误。

### 数据、事务和日志

写操作使用满足原子性要求的事务传播；只读查询才允许采用只读或支持型传播。日志按安全字段白名单记录，不序列化请求、响应、事件或结果对象。新增 `NOT NULL` 字段优先采用 expand/contract 和真实回填，不强制虚假默认值。

## 错误处理与兼容性

- 更深层项目规则可以增加约束，但不能覆盖根入口的封闭安全底线。
- 规则文件缺失时报告具体路径；与当前任务无关的可选文件不应阻塞任务。
- 对已有文档内容采用局部编辑，不做全文件重排或无关格式化。
- 与用户已有修改重叠的文件先读取精确 diff，再基于当前工作树合并。

## 验证设计

- 静态检查风险路由是否明确取并集、L4 是否继承敏感业务约束。
- 静态检查 TDD 顺序、证据标签、`-Raw` 使用条件和验证终态只有一套权威定义。
- 扫描完整对象日志示例、无条件 `SUPPORTS` 写事务和无条件默认值要求。
- 比较 `D:\AGENTS.md` 与 `D:\CLAUDE.md` 的 SHA-256，要求完全一致。
- 对所有修改的中文文件运行 UTF-8、BOM、连续问号、替换字符和 mojibake 扫描。

## 非目标

- 不把所有专项规则合并进根入口。
- 不新增规则引擎、生成器或新的外部依赖。
- 不修改与本次审计结论无关的项目规则和业务文档。
- 不自动提交或推送用户工作区中的其他改动。
