# POS 增量同步租户安全与文档对齐设计

## 目标

修复 POS 门店增量同步 UPDATE 的租户范围缺失和完整事件日志问题，并让同步关系文档只描述当前源码能够证明的链路。

## 已确认问题

- `IncrementalSyncDataService` 的删除条件使用 `mid/sid/lid`，更新条件只使用 `lid`，两者租户范围不一致。
- 增量同步在 ERROR 级别输出完整事件内容，可能包含业务和个人数据。
- 旧 `pos4cloud/KafkaListenerForSync` 已删除；当前 `pos5sync` 同名监听器只打印消息，旧 Kafka → Netty 主链路叙述已经过期。
- 动态表映射文档没有固定源码版本、环境和验证时间，容易把历史观察写成当前事实。

## 备选方案

### 方案 A：只改文档

可消除误导，但不会修复跨租户 UPDATE 风险和日志泄露。该方案不采用。

### 方案 B：最小修改 UPDATE 条件、日志和对应文档

沿用现有实体映射和同步流程，只收紧谓词、缩小日志字段，并更新证据描述。该方案变更面最小，采用此方案。

### 方案 C：重写整个同步框架

没有证据表明当前任务需要替换 Canal、映射或传输架构，风险和回归面过大。该方案不采用。

## 代码设计

### UPDATE 租户范围

- 先用现有行为测试确认非目标同步路径仍可工作。
- 新增失败测试，要求 UPDATE 构造与 DELETE 相同的实际租户边界：`mid`、`sid`、`lid`。
- 生产代码只修改 UPDATE 条件构造，不重写类映射、反射赋值或批处理流程。
- 如果具体实体没有其中某个字段，测试和实现必须根据项目真实模型选择已有隔离键，不能回退为全量或仅主键更新。

安全漏洞不作为必须保留的旧行为；兼容目标是保持同一租户内的更新语义和其他事件类型不变。

### 日志

- 删除完整事件、完整数据行和完整结果对象的日志参数。
- ERROR 只用于实际失败；接收和处理摘要使用合适级别。
- 白名单字段限定为事件类型、表名、行数、trace 标识和经过脱敏或哈希的业务键；不记录消息正文。

## 文档设计

- 删除已不存在的 `pos4cloud/KafkaListenerForSync` 作为当前主链路的描述。
- 将 `pos5sync` 监听器标为“当前仅记录消息，未证明承担同步落库”。
- 保留 `tbl_name → CLASS_MAP → 实体 → 本地表` 的查表方法，因为它仍是当前门店增量落表的有效证据路径。
- 动态映射表增加来源文件、commit、环境和验证日期；无法从源码确认的项标为待验证，不写成事实。
- 与用户已修改的同步文档按当前工作树合并，不覆盖现有新增内容。

## 测试与验证

- 按“旧行为基线 PASS → 新租户条件 RED → 最小实现 → 新旧回归”执行。
- 运行目标模块的最小单元测试，确认 UPDATE 同时包含实际租户键和业务键。
- 增加或运行日志静态检查，确认目标类不再序列化完整事件。
- 使用 `git show` 和当前源码搜索核对旧监听器删除提交及现存监听器行为。
- 对文档中的每条当前链路抽样回查源码路径和 commit。
- Java 文件验证为 UTF-8 无 BOM；不做无关格式化。

## 回滚与边界

- 代码回滚仅恢复本次谓词和日志变更；文档可独立回滚。
- 若收紧谓词暴露历史数据缺少租户键，应停止写入并报告数据修复需求，不能放宽为仅 `lid`。
- 不修改消息拓扑、表映射注册机制或数据库结构。
- 不自动运行生产同步、不连接生产数据库、不发送真实消息。
