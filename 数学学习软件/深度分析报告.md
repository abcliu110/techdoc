# 数学学习软件深度分析报告

> 分析对象：`math-explorer` 项目（React 19 + TypeScript + Vite，约 8700 行源码）及 8 份配套设计文档
> 分析视角：以「培养学生数学思维」为目标，检验设计承诺与代码实现的一致性
> 分析日期：2026-10-05

---

## 一、总体结论

**这是一个「文档深度」远超「实现深度」的项目。**

- 设计文档层面：理论体系完整（六大思维分类、理解六步法、理解障碍诊断表、知识点-思维矩阵），单看文档可以打 8 分。
- 代码实现层面：六步法在落地时发生了**系统性退化**——6 个步骤中有 4 个退化为「看内容 → 点按钮 → 过关」的点击流水线，真正需要学生动脑产出的环节几乎全部失守。实现深度大约 3-4 分。
- 核心症结：`架构设计-v2.md` 第一条原则——**「组件能力决定数据结构」**。这个原则把教学法降级为工程的附属品：不是「培养思维需要什么交互」，而是「现有组件支持什么交互，教学法就退化成什么」。深度缺失不是执行遗漏，而是架构决策的直接后果。

---

## 二、六步法的逐步退化对照（核心发现）

设计文档（《如何促进学生深度理解.md》）定义的六步法，与代码实际行为的逐步对照：

| 步骤 | 设计承诺 | 代码实际行为 | 退化程度 |
|------|---------|-------------|---------|
| 1 具象操作 | 学生拖动、拆分、试错探索，操作反馈即时 | `kind=split` 被定义为 **auto 模式**（架构v2 明写"直接完成"）；guess/balance/segment 为揭示模式——点一下看答案 | ⚠️ 严重 |
| 2 图示表达 | 学生自己画图、图形↔符号双向转换 | 有 `visualOptions` 时是选择题（四选一）；没有时是揭示模式。**没有"学生自己画"的能力** | ⚠️ 中等 |
| 3 语言描述 | 学生用自己的话写出理解，系统按关键词校验、AI 追问 | `VerbalStep.tsx`：点「查看提示」直接展示全部 `expectedKeywords`，再点「我理解了」即过关。**不需要任何输入**；数据里的 `minKeywords: 2`、`requireUnderstanding: true` 配置存在但**代码从未校验** | ❌ 完全失守 |
| 4 符号表示 | 图形→符号双向转换练习 | 单个填空题（如输入 `3/4`），做对即过 | ⚠️ 中等 |
| 5 灵活应用 | 变式矩阵（基础/换场景/逆向/综合/开放题） | 实际只有 3 道选择题/填空题（same-form + different-scenario + reverse），无综合题、无开放题 | ⚠️ 中等 |
| 6 反思内化 | 学生写总结、自评、元认知监控 | `ReflectionStep.tsx` 有 bug：`handleSaveAnswer` 把学生输入**存成空字符串 `''`**（第 38-42 行），用户打的字被直接丢弃；完成条件是 `auto`，零校验 | ❌ 完全失守 |

**一句话概括**：六步法里最需要「学生产出」的三步（语言描述、反思内化、具象探索），恰好是退化最狠的三步。剩下的流程实质是：**看动画 → 做选择题 → 看关键词 → 填一个空 → 做 3 道题 → 点个分**。这是「多媒体版讲练」，不是「探究式学习」。

## 三、关键代码证据

### 3.1 VerbalStep —— 「语言描述」不需要语言

`src/components/steps/VerbalStep.tsx`：

```typescript
const handleReveal = useCallback(() => {
  setRevealed(true);
  showResultFeedback(true, '这些关键词帮助你理解！');
}, [showResultFeedback]);

const handleUnderstand = useCallback(() => {
  handleComplete({ correctCount: 1, totalCount: 1 });  // 永远满分
}, [handleComplete]);
```

- 没有文本输入框（组件注释明写"无需打字输入"——这是有意的设计退让，不是 bug，但恰是深度缺失的根源）。
- `correctCount: 1, totalCount: 1` 硬编码满分，意味着**只要点了按钮，这步的学习数据就是"完全掌握"**，直接污染后续所有学情统计。

### 3.2 ReflectionStep —— 反思内容被丢弃 + 自评分数污染成绩单

`src/components/steps/ReflectionStep.tsx` 第 38-42 行：

```typescript
const handleSaveAnswer = useCallback(() => {
  setAnswers(prev => ({
    ...prev,
    [currentPromptIndex]: ''   // ← bug：丢弃了 textarea 里用户输入的内容
  }));
```

第 57-63 行：

```typescript
handleComplete({
  selfAssessment,
  userInput: summary,
  correctCount: selfAssessment   // ← 学生给自己打几分，就算答对几题
});
```

学生在自评滑块点「完全懂(5分)」，这个 5 会作为 `correctCount` 进入 `Learn.tsx` 的得分率计算（第 182-184 行），**学习报告的"得分率"可以被主观自评直接刷高**。能力雷达图的数据基础不可信。

### 3.3 架构 v2 把退化合法化

`架构设计-v2.md` 第 26-34 行定义：

```
// 揭示模式 (reveal): 无需用户输入
// - 显示内容 → 点"查看答案/提示" → 显示结论 → 点"我理解了"
```

六个步骤类型中，**四种支持或仅支持揭示模式**（Concrete 部分、Pictorial 部分、Verbal 全部、Symbolic 全部）。也就是说，当前架构下「学生全程零产出也能通关」是被设计允许的合法路径。

### 3.4 数据与类型的隐性不一致

- `Question.correctAnswer: string` 混合两种语义：旧模式里存**选项索引**（`'0'`、`'1'`、`'2'`），六步应用题里存**答案文本**（`'2/5'`、`'137'`）。靠 `question.type` 隐式区分，新增数据极易出错。
- 例：`fraction-basics.ts` fb-app-1，选项 `['1/2','1/3','1/4','4/1']`，`correctAnswer: '2'`——人读数据时极易误读为"答案是 2"。

## 四、内容覆盖率：六步法只覆盖了 24%

| 岛屿 | 知识点总数 | 有六步数据 | 只有旧模式（概念+几道题） |
|------|-----------|-----------|--------------------------|
| 数与运算 | 8 | 4（分数初步、分数比较、字母表示数、方程） | 4（巧算、运算律、分数乘法、比和比例） |
| 图形探索 | 4 | 0 | 4（全部） |
| 逻辑挑战 | 9 | 1（鸡兔同笼） | 8 |
| **合计** | **21** | **5（24%）** | **16（76%）** |

- 旧模式知识点恰好就是文档批判的「传统模式」：一两句概念解释 + 1~3 道 difficulty 1-2 的选择题（如"长方体有几个面？"）。
- `Learn.tsx` 第 79-97 行：无 steps 的知识点直接显示「此知识点尚未更新为六步学习模式」并拒绝学习——**整个图形岛事实上不可学**。
- `Learn.tsx` 第 34-42 行硬编码 `pointId` 特判（`fraction-basics-new`、`algebra-basics`），数据路由不具备通用性，每加一个六步知识点都要改页面代码。

## 五、对照「培养数学思维」目标的差距分析

设计文档自己提出的核心机制，在代码中的落地情况：

| 文档承诺的思维培养机制 | 出处 | 代码实现 | 状态 |
|----------------------|------|---------|------|
| 错题诊所：错误模式识别 → 思维根因 → 针对性干预 | 产品方案 §4.4 | 无错误模式库、无根因分析，错题仅记录对错 | ❌ 未实现 |
| AI 助教追问（"你说得很好，能举个例子吗？"） | 深度理解 §2.2-3 | `followUpQuestions` 只是静态文本展示，无交互 | ❌ 未实现 |
| 自适应理解支持（按 Level 1-4 动态调整策略） | 深度理解 §3.2 | 只有静态 `hintLevels[]` 数组，与作答表现无关联 | ❌ 未实现 |
| 错误资源化：展示典型错误、分析为什么错 | 深度理解 §5.3-4 | 答错只显示预设 explanation，不分析学生的错法 | ❌ 未实现 |
| 猜想→验证循环（"你发现了什么规律？→ 验证我的猜想"） | 产品方案 §5.1 | 无任何猜想输入与验证机制 | ❌ 未实现 |
| 认知冲突设计（制造预期违背，激发思考） | 深度理解 §5.1 | 无 | ❌ 未实现 |
| 一题多解（"还有别的解法吗？"） | 深度理解 §3.1 | 数据结构与 UI 均不支持多解法 | ❌ 未实现 |
| 思维可见：记录思考过程 | 共同原则 #1 | `StepResult` 只记 attempts/hintsUsed，无操作轨迹、无错误尝试序列 | ⚠️ 表面实现 |
| 学习报告/能力雷达图 | 产品方案 §6 | 数据源被自评分数和硬编码满分污染（见 §3.1/3.2） | ⚠️ 数据不可信 |

**最致命的缺失**：数学思维培养的研究共识是「学生必须产出——说、写、画、猜、证」，而当前实现中学生唯一能产出的只有「选择」和「填一个空」。探究、猜想、说理、证明、反思——全部缺席。

## 六、值得肯定的部分（客观评价）

1. **理论文档本身有留存价值**：思维分类体系、理解障碍诊断表（什么错→什么根源→什么干预）、知识点-思维矩阵，可以作为后续内容开发的知识库。
2. **数据模型骨架是对的**：`types.ts` 的 `StepContent` 判别联合、`VariantItem` 四种变式类型、`AdaptiveConfig`、`CompletionCriteria` 的可扩展设计，说明抽象能力是有的——问题不在「不会设计」，而在「实现时向工程便利性投降」。
3. **六步法框架本身符合认知科学**（CPA 具象-形象-抽象 + 元认知），方向没有错。
4. 工程层面有基本规范意识：组件行数限制、CSS 隔离、verify 脚本、评审文档。

## 七、改进路线建议（按投入产出比排序）

### P0：堵住「零产出通关」——小改动，大效果

| 改动 | 涉及文件 | 工作量 |
|------|---------|--------|
| 修复 ReflectionStep 输入丢弃 bug | `ReflectionStep.tsx:38` | 10 分钟 |
| VerbalStep 恢复文本输入 + 关键词匹配校验（数据里 `minKeywords`/`expectedKeywords` 现成可用），不达标不给过 | `VerbalStep.tsx` | 0.5 天 |
| 自评分数不再计入 `correctCount`，成绩单只统计客观作答 | `ReflectionStep.tsx:61` | 10 分钟 |
| Reflection 完成条件从 `auto` 改为「至少写 N 个字」 | 数据层 + 组件 | 0.5 天 |

### P1：让「深度」真正发生——每步加一种必须产出的交互

| 步骤 | 改造方向 |
|------|---------|
| 具象操作 | split 从 auto 改为「学生必须自己动手分对才算完成」（`requiredSplit` 配置已存在，接上校验即可） |
| 图示表达 | 加「学生自己涂/画」模式（SplitCircle 组件已有分割能力，扩展为可涂色） |
| 语言描述 | 关键词覆盖度评分 → 低于阈值触发追问（followUpQuestions 已存在，做成真正的一问一答） |
| 灵活应用 | 每知识点补「开放题」变式：答案不唯一，提交后展示多种解法对比（数据结构加 `openEnded` 类型） |

### P2：补思维培养的专属机制

1. **猜想-验证组件**：找规律、鸡兔同笼、面积推导类知识点天然适配。流程：观察 → 输入猜想（文本/选择）→ 系统用动画验证或推翻 → 修正猜想。这是「逻辑思维」最直接的训练器。
2. **认知冲突题**：在每个知识点数据中标注一个「典型错误预期」（如 1/2+1/3=2/5），先让学生暴露直觉错误，再可视化推翻。错题诊所的第一块砖。
3. **错误模式库落地**：把《数学思维体系分析文档》§3 各节的「理解障碍诊断表」结构化进数据层（`wrongAnswerPatterns: { pattern, rootCause, remediation }[]`），答错时按模式匹配给干预，而不是统一显示 explanation。

### P3：工程治理

1. `correctAnswer` 拆为 `correctAnswer`（input 题）与 `correctOptionIndex: number`（choice 题），消除语义混用。
2. 移除 `Learn.tsx` 的 pointId 硬编码，知识点注册改为统一 registry。
3. 把 16 个旧模式知识点按六步法补齐，或暂时从地图隐藏——「不可学」和「旧模式」混在地图上会稀释产品定位。

### 一个原则性建议

把 `架构设计-v2.md` 第一条原则反转过来：**教学法需求决定组件能力，而不是反过来**。每个新知识点设计时，先回答「这一步学生必须产出什么」，再决定组件长什么样。这条不改，P0-P2 做完还会退化回去。

## 八、结论

用户感觉「没有深度」是准确的，而且可以精确定位：

- **不是理念没深度**——六步法、错误诊断、思维矩阵的文档设计有深度；
- **是深度在实现层被系统性抽掉了**——所有要求学生「产出」的环节都被替换成了「点击确认」，且架构文档把这种替换合法化；
- **当前产品实际形态** = 一套做得比较精致的「动画讲解 + 轻量刷题」应用，距离「培养数学思维」的目标差的是「学生必须思考才能前进」这个最根本的机制。

好消息是：数据模型和组件骨架已具备扩展条件，P0+P1 的改造量约 3-5 天，即可让产品从「能看」变成「有深度」。

## 九、二次评审（验证轮）

> 对第一轮报告逐条核实，并补读全部 6 个步骤组件 + 全部六步数据文件。结论：**第一轮的判断方向全部成立，且有两处实际情况比第一轮写的更严重**，另有多处新发现。

### 9.1 对第一轮结论的修正（Errata）

| 第一轮表述 | 核实结果 | 修正 |
|-----------|---------|------|
| 符号表示步是「单个填空题，做对即过」 | ❌ 不准确 | `SymbolicStep.tsx` **没有输入框**：点「查看答案」→ 显示答案 →「我理解了」。且答案是**硬编码特判**：`instruction.includes('3/4')` 显示 3/4、`includes('x-3=10')` 显示方程，否则显示「请看题目要求」。退化程度比第一轮所述更严重 |
| 灵活应用步是「3 道选择/填空题」 | ❌ 不准确 | `ApplicationStep.tsx` **学生根本不用答题**：选择题直接标绿显示正确答案（第 81-89 行），填空题直接显示答案（第 97-102 行），学生只点「下一题」；`handleFinish` 硬编码 `correctCount: variants.length` 满分（第 36 行）。这是六步中退化最彻底的一步 |
| correctAnswer 语义混用是「极易出错的隐患」 | ⚠️ 需弱化 | 核实 QuestionCard/ApplicationStep 后确认：choice 题存索引、input 题存文本是**自洽约定**，现有数据均遵守。真正的问题不是混用，而是该约定未在类型系统表达（`correctAnswer: string` 无法区分），且真正的判分 bug 在别处（见 9.2-③） |

### 9.2 新发现的严重问题

**① `completionCriteria` 整套配置是死代码（实锤第一轮核心论点）**

grep 证据：`completionCriteria`、`minCorrect`、`minKeywords` 只出现在 5 个数据文件和 `types.ts` 中，**没有任何组件消费它们**。也就是说：

- 数据里精心声明的 `minCorrect: 3, totalQuestions: 4`（方程应用步）、`minKeywords: 2, requireUnderstanding: true`（各语言步）、`requiredSplit: 2`（具象步）——全部不生效；
- `StepContainer.handleComplete`（第 29-39 行）无条件写入 `completed: true`，**整个 App 不存在任何过关验证逻辑**。架构 v2 自称「验证逻辑必须在组件内部完成」——实际没有任何组件做验证。

**② PictorialStep 选择题正确答案永远是 A（判分硬编码）**

`PictorialStep.tsx` 第 208 行：`const isCorrect = i === 0;` —— 无视 `completionCriteria.config.correct`，写死第一个选项为正确答案。目前数据恰好都把正确答案放第一个所以没暴露，但：(a) 学生刷两题即可发现「选 A 必对」；(b) 无选项洗牌机制；(c) 任何内容作者把正确答案放其他位置就会判分错误。

**③ ConcreteStep 用正则从中文文案里抠数字（工程脆弱性）**

`ConcreteStep.tsx` 第 64、129、196 行：guess/balance/segment 三种可视化都靠 `scenario.description.match(/正则/)` 从自然语言描述中提取数字。场景文案稍改（如「20 克」改成「二十克」或调整语序），可视化立刻静默出错并回退到默认值（`parseInt(match[1]) : 2`），且无任何报错。**数据与渲染之间没有结构化契约**。《代数思想六步设计.md》规划的 `BalanceScale`、`SegmentDiagram`、`EquationBuilder` 专用组件均未实现，被 regex 解析替代。

**④ SplitCircle 的「分割」实为「点选」，且有文案 bug**

- 「把披萨平均分成 2 份」的实际交互：饼图的 n 份**已经预先画好**，学生逐一点击全部 n 份即完成（`SplitCircle.tsx:118-127`，判定条件是 `selectedParts.length === denominator`）。没有「分」的动作，更与「是否平均」无关——数学上最核心的「等分」概念在交互中完全缺席。
- 文案 bug：`ConcreteStep.tsx:279` 传 `successMessage="你把"`，SplitCircle 拼接为 `✓ {successMessage}{denominator}份！` → 实际显示「✓ 你把2份！」，语句不通。

**⑤ PictorialStep 揭示模式硬编码鸡兔同笼**

`PictorialStep.tsx` 第 115-133 行：揭示模式的 SVG 图示把「8 个头、26 条腿」写死在组件里。任何其他知识点的 pictorial 揭示步都会错误显示鸡兔同笼的图。组件与内容耦合。

**⑥ 数据错误：方程应用步 eq-app-3 答案与解析自相矛盾**

`equation-basics.ts` 第 199-212 行：「3x + 5 = 20 表示什么意思？」选项 A「3 和 x 的和加 5 等于 20」（数学错误读法）、B/C 为正确读法、D「以上都对」。数据标 `correctAnswer: '3'`（D），但解析只支持 B——**若 D 正确则 A 必须正确，而 A 在数学上是错的**。这是一道答案本身错误的选择题（且在 ApplicationStep 里会被直接标绿展示给学生）。

**⑦ StepContainer 计数缺陷**

`attempts` 在 `showResultFeedback` 和 `handleComplete` 中各 +1，一次操作记 2 次尝试，学情数据中的尝试次数系统性虚高。

### 9.3 二次评审后的六步退化对照（修订版）

| 步骤 | 实际交互 | 学生需要的产出 | 过关依据 |
|------|---------|--------------|---------|
| 1 具象操作 | 点满 n 份 / 点「揭示答案」 | 点击 | 无（硬编码满分） |
| 2 图示表达 | 选择题（答案恒为 A）或点「查看说明」 | 点击 | 选 A 或无 |
| 3 语言描述 | 点「查看提示」看关键词 | 无 | 无（硬编码满分） |
| 4 符号表示 | 点「查看答案」 | 无 | 无（硬编码满分） |
| 5 灵活应用 | 浏览标好答案的题目 | 无 | 无（硬编码满分） |
| 6 反思内化 | 可写但内容被丢弃 + 自评点击 | 点表情 | 无（auto） |

**修订结论：整个六步流程中，学生全程可以不做任何思考性产出即满分通关，且这是当前代码的唯一路径。** 唯一存在真实判分逻辑的是旧版练习组件 `QuestionCard.tsx`（第 57-61 行有答案比对）——讽刺的是，有验证的是被定位为「旧模式」的部分。
