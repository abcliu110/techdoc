# 数学学习软件跨平台架构与发布方案

## 1. 平台目标

系统需要同时支持完整功能：

- Windows/macOS/Linux 桌面端。
- Android 手机和平板端。
- Web 浏览器端。

三端都必须支持学习、交互、进度保存、能力报告、复习和内容更新。Web 不是只读报告页面，而是完整学习端。

当前项目已经使用 Tauri 2，并配置了 Windows 安装包和 Android `apk/aab` 构建目标，这是桌面端和 Android 端的基础。但 Web 端不能直接复用 Tauri 的原生数据库能力，必须补齐浏览器运行时适配和跨设备同步能力。

## 2. 总体架构原则

```text
                 ┌────────────────────┐
                 │  统一 React UI 层   │
                 └─────────┬──────────┘
                           │
                 ┌─────────▼──────────┐
                 │  统一应用用例层     │
                 └─────────┬──────────┘
                           │
                 ┌─────────▼──────────┐
                 │  纯 TypeScript 领域层│
                 └─────────┬──────────┘
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
  Tauri Desktop       Tauri Android       Browser Web
  SQLite Adapter      SQLite Adapter       IndexedDB/API
```

业务规则、学习会话、数学验证、内容模型和评分逻辑必须保持平台无关。平台差异只能出现在基础设施适配层。

## 3. 推荐技术路线

### 3.1 UI 和业务核心

继续使用 React + TypeScript + Vite，抽取以下平台无关模块：

```text
src/domain/          学习会话、评分、能力、成就
src/application/     开始学习、提交动作、完成结算、复习
src/content/         数学思想和学习单元
src/presentation/    React 页面和组件
src/platform/        平台适配
```

### 3.2 桌面和 Android

继续使用 Tauri 2：

- 桌面端由 Rust/Tauri 承载 WebView。
- Android 端使用 Tauri Android 构建 `apk/aab`。
- 本地数据库使用 SQLite，但通过统一 Repository 接口访问。
- 原生能力通过平台服务抽象，不允许页面直接调用 Tauri API。

### 3.3 Web

Web 端是完整学习端，有两种运行模式：

**离线模式：**使用 IndexedDB（推荐 Dexie）保存本地进度、会话和内容缓存，支持已缓存内容的完整学习。

**在线模式：**使用后端 API 保存账户、进度、证据、报告和同步数据。浏览器端不应直接连接 SQLite。

建议先实现 IndexedDB 离线模式，再增加 API Repository 和同步服务，不让 UI 感知存储差异。Web 端的学习能力不能依赖 Tauri API。

## 4. 存储抽象

定义平台无关的仓储接口：

```ts
interface ProgressRepository {
  get(userId: string, pointId: string): Promise<LearningProgress | null>
  save(progress: LearningProgress): Promise<void>
}

interface SessionRepository {
  saveDraft(session: LearningSession): Promise<void>
  getDraft(sessionId: string): Promise<LearningSession | null>
  complete(sessionId: string, result: SessionResult): Promise<void>
}
```

实现方式：

```text
TauriProgressRepository  -> tauri-plugin-sql / SQLite
WebProgressRepository    -> Dexie / IndexedDB
SyncProgressRepository   -> HTTP API + 本地缓存
```

页面和应用用例只能依赖接口，不能导入 `@tauri-apps/plugin-sql`、Dexie 或浏览器 API。

## 5. 平台能力抽象

以下能力必须封装：

```ts
interface PlatformServices {
  storage: StorageService
  clock: Clock
  network: NetworkStatus
  notifications?: NotificationService
  fileExport?: FileExportService
  haptics?: HapticsService
}
```

平台差异：

| 能力 | 桌面 | Android | Web |
|---|---|---|---|
| 本地数据库 | SQLite | SQLite | IndexedDB |
| 文件导出 | 原生文件选择器 | 系统分享/下载 | 浏览器下载 |
| 通知 | 系统通知 | 系统通知 | 浏览器通知（可选） |
| 网络状态 | 原生/浏览器 API | 原生/浏览器 API | 浏览器 API |
| 触觉反馈 | 无或可选 | 支持 | 可选 |
| 更新 | Tauri updater | 商店/包更新 | 静态资源发布 |

## 6. Web 与原生的关键差异

### 6.1 数据库

当前使用 Tauri SQL 的代码不能直接在 Web 构建中运行。必须在构建入口选择 Repository，或者使用运行时工厂：

```ts
const repositories = isTauri()
  ? createTauriRepositories()
  : createWebRepositories()
```

不能通过在页面中判断平台来分散处理。

### 6.2 路由

Web 使用浏览器历史路由时需要服务器配置所有路径回退到 `index.html`。桌面和 Android 使用本地资源时要验证深链接和返回键行为。

### 6.3 返回和生命周期

Android 必须处理系统返回键、应用挂起和恢复；桌面需要处理窗口关闭；Web 需要处理刷新和浏览器后退。未完成会话必须先保存草稿。

### 6.4 屏幕和输入

布局必须支持 320px 手机宽度、平板横屏和桌面大屏。拖动、点击和键盘输入应提供等价操作，不能只依赖鼠标。

## 7. 内容和资源策略

- 数学内容和业务规则打包为平台无关资源。
- 图片、动画和可视化避免使用只支持单一 WebView 的能力。
- 离线学习单元需要明确资源清单和版本。
- Web 支持按思想主线或岛屿懒加载。
- Android 和桌面支持资源缓存和增量更新。

## 8. 账号与同步策略

建议分两阶段：

### 第一阶段：本地优先

- 三端都能在已缓存内容下离线学习。
- 每个平台独立保存用户数据。
- 支持导出/导入学习数据。

### 第二阶段：云同步

- 引入用户账号和设备 ID。
- 学习会话、进度、证据采用事件或版本号同步。
- 冲突按领域规则解决，不能简单用最后写入覆盖。
- 内容版本和学习记录版本必须一并同步。

## 9. 构建与发布矩阵

| 平台 | 构建命令 | 产物 | 发布方式 |
|---|---|---|---|
| Windows | `npm run tauri:build` | MSI/NSIS | 安装包或更新器 |
| macOS | `npm run tauri:build` | DMG/应用包 | 签名、公证、下载 |
| Linux | `npm run tauri:build` | AppImage/deb | 下载或发行版仓库 |
| Android | `npm run tauri:build -- --apk` | APK/AAB | 测试包/应用商店 |
| Web | `npm run build` | dist 静态资源 | CDN/静态托管 |

CI 必须按平台分别构建，不能只在 Windows 构建后假设 Android 和 Web 可用。

## 10. 需要立即修复的跨平台问题

1. 把 Tauri SQL 访问从业务代码中抽离，否则 Web 构建和运行不可靠。
2. 把 `toISOString().split('T')[0]` 替换为平台无关的本地日期服务。
3. 处理 Android 返回键、挂起恢复和桌面窗口关闭时的会话保存。
4. 验证所有可视化在触摸屏、键盘和窄屏下可用。
5. 取消对本地文件路径、窗口 API 和平台路径的直接依赖。
6. 增加 Web IndexedDB Repository 和数据库迁移。
7. 为三端建立独立的构建、冒烟和端到端测试矩阵。
8. 为 Web 配置 SPA 路由回退、资源缓存和版本清理。

## 11. 跨平台验收标准

- 同一学习单元在桌面、Android 和 Web 的步骤、评分和业务结果一致。
- 任一平台离线完成学习后，数据不会丢失。
- 应用挂起、刷新、关闭和重新打开后，会话按规则恢复或明确标记放弃。
- 三端都支持触摸、鼠标或键盘可用的等价交互。
- Web 不依赖 Tauri API，桌面和 Android 不依赖浏览器专有存储。
- 内容版本、进度、证据和报告在三端使用同一领域模型。
- 三端构建和核心流程测试全部通过。

## 12. 最终建议

当前项目可以保留 Tauri 2 作为桌面和 Android 容器，同时使用 Vite 发布完整 Web 应用，但必须先建立平台适配层。推荐的长期结构是“一个平台无关的数学学习核心 + 三套基础设施适配器”，而不是为桌面、Android 和 Web 分别复制一套业务代码。

三端职责如下：

```text
桌面端：完整学习、离线数据、键盘鼠标、窗口能力
Android：完整学习、离线数据、触摸、返回键、系统生命周期
Web：完整学习、IndexedDB 离线缓存、账号同步、浏览器交互
```

最终验收必须覆盖三端完整学习闭环，而不是只验证 Web 报告访问。
