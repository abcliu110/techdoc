## 1. 一句话结论与本质模型

### 1.1 一句话结论

**（主流共识）数据模型不是 UI 蓝图，UI 也不是数据模型的皮肤。UI 是领域事实在特定角色、任务、状态和权限下的有目的投影，同时是用户向领域模型提交受约束业务命令的入口。**

可以形式化为：

```text
页面视图 = Project(
  领域事实,
  对象关系,
  用户角色,
  当前任务,
  业务状态,
  权限策略,
  数据规模,
  设备与使用上下文
)

可用动作 = Policy(
  用户角色,
  目标对象,
  当前状态,
  业务规则,
  风险等级
)

新领域状态 = Transition(
  当前领域状态,
  用户命令,
  权限,
  业务不变量,
  预期数据版本
)
```

因此，映射天然是多对多：

```text
一个领域对象  ──> 列表、详情、选择器、看板、日历、报表等多个视图
多个领域对象  ──> 一个面向任务的工作台或处理页面
一个业务功能  ──> 页面、按钮、菜单、批处理、自动任务等多个入口
一个页面      ──> 多个查询和业务命令
```

### 1.2 核心原则：语义保持，表征自由

同一领域语义可以自由选择不同 UI 表征，但以下语义不得被扭曲：

1. 对象身份和业务键。
2. 值的类型、单位、精度和空值含义。
3. 关系的基数、方向、所有权和生命周期。
4. 聚合边界和事务一致性边界。
5. 状态及其合法转换。
6. 权限、租户和数据范围。
7. 指标口径、时间口径和数据来源。
8. 命令的前置条件、影响范围和失败结果。

UI 可以省略当前任务不需要的信息，也可以把多个模型组合成一个读视图；但它不能为了视觉便利而改变业务含义。

### 1.3 核心张力

数据模型与 UI 的关系长期围绕四组张力展开：

| 数据模型倾向 | UI 倾向 | 正确协调方式 |
|---|---|---|
| 保持业务语义和不变量稳定 | 降低用户认知和操作成本 | 用任务视图投影稳定事实 |
| 写模型围绕一致性边界组织 | 页面围绕任务闭环组织 | 读可跨边界组合，写回权威边界 |
| 存储模型倾向规范化 | 查询页面倾向聚合和冗余 | 建立专用查询模型或视图模型 |
| 模型追求通用和可演进 | 页面追求角色与场景适配 | 复用语义，不强求复用同一页面 |

**好的设计不消灭业务的本质复杂度，而是组织本质复杂度，并消除数据库结构、服务边界、历史补丁带来的附加复杂度。**

### 1.4 五级递进映射框架

本文按五个尺度逐层拆解：

```text
第一级：字段级映射
字段/值 → 显示、输入、选择、校验、格式和反馈
新增语义：值、单位、精度、空值、约束、来源

第二级：实体级映射
实体 → 标识、摘要、列表项、详情、编辑、状态、历史和动作
新增语义：稳定身份、生命周期、实体能力

第三级：实体间映射
实体/聚合根之间 → 组成、引用、关联、导航、选择、主从和流程继续
新增语义：基数、所有权、生命周期依赖、一致性边界

第四级：模块间映射
业务能力模块之间 → 组合读取、业务交接、跨模块任务、事件和责任回归
新增语义：能力归属、规则权威、流程责任、模块契约

第五级：系统间映射
独立信息系统之间 → 门户、深链接、集成状态、异步同步、冲突和对账
新增语义：系统权威、身份映射、信任边界、时延、最终一致性
```

这五级不是“字段堆成实体、实体堆成模块”的纯粹包含关系。每上升一级，都会出现下一级无法自行推导的新语义和失败模式：

| 层级 | 核心对象 | UI 主要回答 | 该层不能被下层替代的内容 |
|---|---|---|---|
| 字段级 | 一个业务值 | 这个值是什么、如何读写 | 单位、空值、约束和输入语义 |
| 实体级 | 有稳定身份的对象 | 这是谁、现在怎样、能做什么 | 身份、生命周期、状态和历史 |
| 实体间 | 对象关系或聚合协作 | 它属于谁、关联谁、如何到达 | 所有权、基数、一致性和导航 |
| 模块间 | 业务能力与责任边界 | 哪个能力负责、如何交接任务 | 规则权威、责任归属和流程协作 |
| 系统间 | 独立运行与治理边界 | 数据来自哪里、何时同步、失败怎么办 | 信任、时延、契约、冲突和对账 |

### 1.5 五级共同分析模板

每一级都用同一组问题拆解，保证方法可递归使用：

```text
1. 模型语义：这一层真正表达什么？
2. 任务投影：谁为了什么任务需要看什么？
3. UI 表征：用什么结构显示、输入、导航或分组？
4. 业务命令：用户能改变什么，由谁维护不变量？
5. 状态与权限：何时可见、可用、只读或禁止？
6. 异常与恢复：空、错、冲突、延迟和部分成功如何表达？
7. 质量判据：是否语义保真、任务闭环、可追踪、可演进？
```

### 1.6 复杂 UI 映射总谱：五级尺度与五层产物必须同时使用

五级递进框架按业务尺度展开字段、实体、关系、模块和系统；它仍不足以直接回答“最终会出现哪些复杂界面”。设计时还要沿另一条轴，把每个尺度依次转换为五层 UI 产物：

```text
业务尺度轴：字段 → 实体 → 关系 → 模块 → 系统

UI 产物轴：
L1 数据形状    原子、可选、联合、对象、集合、树、图、时序、空间、多维……
L2 操作语义    查看、录入、选择、查找、比较、分组、调度、匹配、审批……
L3 UI 表达     控件、表格、卡片、树、图表、地图、时间线、看板、画布……
L4 页面模式    列表、详情、主从、工作台、向导、驾驶舱、设计器、异常中心……
L5 导航体系    嵌入、预览、抽屉、跳转、钻取、流程继续、深链接、上下文恢复……
```

两条轴形成矩阵，而不是一条固定流水线。例如一个 `Order[]` 位于“实体集合”尺度，但它可以按任务投影为表格、卡片、看板、日历、时间线、地图、透视表或异常队列，再分别装入列表页、主从工作台、驾驶舱或任务中心。

因此完整映射公式是：

```text
候选 UI 集合 = Candidates(
  数据形状,
  关系语义,
  时间/空间/状态特征,
  用户操作,
  数据规模,
  角色与权限,
  风险与一致性,
  设备与协作方式
)

最终 UI = SelectAndCompose(候选 UI 集合, 页面任务, 导航上下文)
```

任何“类型 → 唯一控件”“实体 → 唯一详情页”“关系 → 唯一跳转方式”的结论都不完整。

### 1.7 L1：数据形状到候选 UI 表达全集

下表是集中式入口。后续章节分别解释字段、实体、关系和页面层的细节。

| 数据形状或业务结构 | 典型候选 UI | 优点 | 缺点与拒绝条件 |
|---|---|---|---|
| 原子标量 | 文本框、数字框、增减器、滑块、单选、只读格式化值 | 简单、可直接校验 | 数据库类型不足以决定控件；必须补语义、单位、范围和任务 |
| `Optional<T>` | 可清空输入、未设置/不适用选项、继承值提示、空状态 | 保留“无值”的真实语义 | 只留空白会混淆未知、未填、清除和无权限 |
| `Union<A,B>` / 多态值 | 类型选择 + 分支子表单、分段模式、不同详情模板 | 保留不同变体各自字段和规则 | 把所有分支字段平铺会产生大量无效字段和条件显示 |
| 值对象 Product | 地址组合、金额+币种、数值+单位、起止区间 | 维持整体语义与整体校验 | 拆成无关联字段会丢失组合不变量 |
| 动态属性 `Map<K,V>` | 键值编辑器、动态属性表、Schema 表单、JSON 高级模式 | 能容纳扩展字段 | 原始 JSON 只适合技术用户；未知键仍需类型、权限和冲突规则 |
| 单对象实体 | 对象头、摘要卡、详情、编辑表单、打印视图、历史页 | 身份、状态与动作边界清楚 | 一个实体不应被固定成一个万能详情页 |
| 同构集合 `T[]` | 数据表格、列表、卡片网格、虚拟列表、分组列表 | 适合查找、扫描、比较和批处理 | 表格不适合强视觉对象；卡片不适合高密度精确比较 |
| 组成集合 | 明细表、重复卡片、主从编辑、子编辑页 | 可表达父子共同生命周期 | 大集合或独立子对象不应全部嵌入父表单 |
| 层级 / 递归树 | 树、级联、树表、面包屑、组织图、目录 | 表达祖先路径、父子结构与继承 | 深树需要搜索、懒加载和路径回显；组织图不适合大规模精确管理 |
| 图 / 网络 / DAG | 邻接列表、关系图、依赖图、路径高亮、拓扑画布 | 当拓扑、路径、影响传播是主任务时非常有效 | 关系图不适合普通查找和批量编辑；必须提供列表替代和聚焦机制 |
| 状态机 | 状态徽标、合法动作区、步骤条、看板、状态图、迁移历史 | 把当前状态和合法变化联系起来 | 禁止把状态 code 映射为可任意修改的下拉框 |
| 事件流 / 审计流 | 活动流、时间线、前后值 Diff、事件详情、责任追踪 | 能解释“如何变成现在这样” | 技术日志不能直接冒充业务历史；大事件流需分组和筛选 |
| 时间点 / 时间区间 | 日期、日历、议程、时间轴、甘特、资源排期 | 能表达先后、重叠、占用和依赖 | 时区、边界包含性和多种业务时间不能混用 |
| 时序指标 | 折线、面积、阶梯图、火花线、异常带、事件叠加 | 显示趋势、周期与突变 | 少量离散点不需要图；必须标明采样、缺失和聚合口径 |
| 空间点/线/面 | 地图点位、聚类、轨迹、区域层、地图列表联动 | 空间邻近、覆盖、路径成为可见事实 | 无空间决策时地图只是装饰；需处理坐标精度、隐私和聚合尺度 |
| 多维事实 / OLAP | 分组表、交叉表、透视表、热力图、图表、钻取 | 可切片、比较、汇总并回到明细 | 指标口径不清、汇总与明细不一致时会误导决策 |
| 版本 / 谱系 | 版本列表、并排 Diff、修订树、来源/去向链、恢复入口 | 表达时间有效性和来源关系 | 当前版本、法律快照和可编辑草稿必须区分 |
| 文件 / 媒体 / 文档 | 上传队列、预览、画廊、播放器、批注、区块编辑器 | 匹配内容本身的阅读和编辑方式 | 需处理扫描、版本、权限、保留期、转码和失败恢复 |
| 规则 / 表达式 / DSL | 条件构建器、决策表、规则树、公式编辑器、测试台 | 让业务规则可组合、解释和验证 | 自由代码风险高；图形规则也不能掩盖优先级、冲突和版本 |
| 权限 / 范围模型 | 权限矩阵、资源树、范围选择、继承说明、有效权限预览 | 同时表达主体、资源、能力和范围 | 勾选界面不能代替服务端授权；继承与拒绝优先级必须可解释 |
| 对账 / 匹配模型 | 双栏匹配、候选队列、差异表、核销工作台 | 能并列证据、余额和匹配动作 | 自动匹配必须显示置信度；一对多与撤销/补偿不可隐藏 |

### 1.8 L2：操作语义决定同一数据使用哪种复杂界面

| 用户操作 | 对集合或关系执行的变换 | 候选复杂 UI | 关键取舍 |
|---|---|---|---|
| 查找 Locate | 搜索、筛选、排序、定位 | 搜索结果页、筛选表格、树搜索、地图列表 | 精确条件与快速探索的平衡 |
| 浏览 Browse | 扫描对象并形成概览 | 列表、卡片墙、目录、活动流 | 信息密度与识别速度 |
| 比较 Compare | 同维度并置、基准和差异 | 表格、比较矩阵、并排详情、版本 Diff | 对齐维度必须稳定，避免视觉位置误导 |
| 录入 Edit | 创建或修改受约束事实 | 表单、内联编辑、明细表、向导 | 频率、错误成本、保存边界和草稿 |
| 选择 Select | 从候选中引用一个或多个对象 | 单选/多选、搜索选择器、穿梭框、树选择 | 候选规模、可搜索性和选后摘要 |
| 分组 Group | 按维度或状态形成集合 | 分组列表、看板、树、分面 | 分组语义和拖拽是否等于业务命令 |
| 聚合 Analyze | 求和、计数、比率和分布 | KPI、透视表、图表、驾驶舱 | 口径、刷新时点和钻取明细 |
| 监控 Monitor | 观察实时或异步状态 | 运行台、指标墙、告警流、状态拓扑 | 新鲜度、噪声、阈值和责任人 |
| 调度 Schedule | 安排时间、资源和依赖 | 日历、甘特、资源泳道、冲突面板 | 重叠、容量、依赖和拖拽写入规则 |
| 路径探索 Traverse | 在层级或网络中寻找路径 | 树、关系图、面包屑、依赖链 | 全局结构与当前焦点 |
| 匹配 Reconcile | 在两组事实间建立对应 | 双栏匹配、差异表、候选建议 | 匹配证据、余额、置信度和撤销 |
| 审批 Decide | 基于证据执行受控命令 | 待办详情、风险摘要、并排证据、动作区 | 证据完整性、权限、理由和幂等 |
| 批处理 Batch | 对选择集执行同类动作 | 批处理栏、批量向导、作业进度和逐项回执 | 冻结选择集、部分成功和失败重试 |
| 设计 Configure | 组合结构、规则或流程 | 表单设计器、流程画布、规则构建器、属性面板 | 所见即所得、验证、版本和发布边界 |
| 协作 Collaborate | 评论、指派、提及和共同处理 | 评论流、任务侧栏、在线状态、变更记录 | 业务事实与讨论内容要分离 |
| 恢复 Recover | 处理错误、冲突、异步失败 | 差异合并、重试台、补偿向导、草稿恢复 | 不能只显示错误；必须保住已完成工作和可恢复上下文 |

### 1.9 L3：复合视图模式总目录

复杂界面不是“更大的控件”，而是多个字段、关系、投影和动作围绕一个判断组成的视图。

| 复合视图族 | 典型组成 | 最擅长 | 优点 | 缺点/边界 |
|---|---|---|---|---|
| 数据表格 | 列、排序、筛选、选择、合计、批处理 | 精确扫描和跨行比较 | 密度高、键盘和批处理效率高 | 窄屏差；视觉对象和复杂嵌套不适合 |
| 卡片网格 | 图片/图标、摘要、状态、快捷动作 | 视觉识别和少量关键差异 | 识别快、响应式友好 | 密度低、列对齐和精确比较弱 |
| 主从视图 | 集合导航 + 当前对象详情 | 连续处理队列或集合 | 少跳转、上下文持续 | 宽屏依赖；选中状态、URL 和移动端堆叠更复杂 |
| 树 / 树表 | 展开层级、路径、节点属性 | 层级浏览与管理 | 祖先和子级关系直观 | 深树和大树需要搜索、懒加载与虚拟化 |
| 看板 | 状态列、卡片、在制品限制、迁移动作 | 观察状态分布和流动 | 阻塞与队列一眼可见 | 卡片信息有限；拖拽不能绕过状态机 |
| 日历 / 排期 | 时间格、事件、资源、冲突 | 时间占用、重叠和安排 | 时间心智直接 | 大量事件拥挤；时区和跨日复杂 |
| 甘特 / 依赖 | 区间条、里程碑、依赖连线、关键路径 | 计划、顺序和依赖 | 范围和依赖同时可见 | 不适合普通事件流；横向滚动和依赖编辑复杂 |
| 时间线 / 活动流 | 时间、事件、行为人、前后状态 | 历史、审计和因果解释 | 顺序清楚、可追溯 | 大事件流需折叠、分组和业务化摘要 |
| 地图 / 轨迹 | 点、线、面、聚类、列表联动 | 邻近、覆盖、路径和区域 | 空间关系无需文字解释 | 精确比较弱；隐私、坐标和尺度风险高 |
| 透视 / 矩阵 | 行维度、列维度、指标、总计、钻取 | 多维聚合和交叉比较 | 高密度揭示结构差异 | 认知负担高；口径和空值桶必须明确 |
| 图表 / 驾驶舱 | KPI、趋势、分布、基准、异常、钻取 | 解释整体态势 | 模式和异常快速可见 | 装饰化风险；不能代替明细和精确值 |
| 网络 / 血缘图 | 节点、边、方向、类型、路径、影响范围 | 拓扑探索与影响分析 | 多跳关系和传播路径可见 | 节点一多迅速失控；需过滤、聚焦和列表替代 |
| 双栏匹配 / 对账台 | 两侧集合、候选连线、差异、余额、核销动作 | 匹配独立事实 | 证据与动作同时可见 | 复杂一对多匹配需要明确余额、撤销和并发 |
| 条件 / 规则构建器 | 条件组、运算符、值、优先级、测试结果 | 配置规则和查询 | 比自由代码更可读、可验证 | 深层嵌套仍复杂；必须显示自然语言解释 |
| 设计器画布 | 元素树、画布、属性、工具栏、预览、发布 | 设计表单、流程、报表 | 结构、所见结果与配置并置 | 状态多、快捷键多、版本和撤销体系复杂 |
| 富文档工作区 | 内容区、目录、批注、附件、版本、协作者 | 长内容创作和审阅 | 内容、讨论和版本形成闭环 | 与结构化业务字段的边界必须明确 |

### 1.10 L4：页面模式总目录

| 页面模式 | 组合的复合视图 | 适用任务 | 主要优点 | 主要缺点/拒绝条件 |
|---|---|---|---|---|
| 搜索/列表页 | 筛选器 + 表格/卡片 + 批处理 | 找到并处理对象集合 | 通用、可保存视图 | 不能承担单对象全部复杂编辑 |
| 对象详情页 | 对象头 + 摘要 + 关系 + 历史 + 动作 | 理解一个对象并决策 | 身份和上下文稳定 | 容易膨胀成万能详情和过多 Tab |
| 创建/编辑页 | 字段组 + 明细 + 校验 + 草稿 + 提交 | 建立或修订业务事实 | 写入边界清楚 | 跨聚合大保存和长表单风险高 |
| 分步向导 | 步骤 + 局部校验 + 摘要确认 | 低频、复杂、依赖顺序的任务 | 降低单屏负担 | 隐藏后续信息；不适合熟练用户高频录入 |
| 主从工作台 | 队列/列表 + 详情 + 动作 | 连续审核、客服、异常处置 | 上下文持续、吞吐量高 | 移动端和深链接复杂 |
| 看板工作台 | 看板 + 筛选 + WIP + 详情预览 | 状态流动与阻塞处理 | 过程可见 | 不适合精确跨项比较 |
| 调度工作台 | 日历/甘特 + 资源 + 冲突 + 未排任务 | 安排时间和容量 | 约束在同一视图决策 | 交互和并发复杂，需稳定缩放尺度 |
| 分析驾驶舱 | KPI + 图表 + 透视 + 筛选 + 钻取 | 监控与解释指标 | 总览到明细 | 易追求“漂亮”而缺少行动和口径 |
| 异常中心 | 异常队列 + 原因 + 影响 + 处置 + 回执 | 例外驱动运营 | 聚焦需要响应的变化 | 只有告警无责任、上下文和恢复即失效 |
| 审批/任务中心 | 待办 + 风险摘要 + 证据 + 命令 + 下一项 | 快速连续决策 | 任务闭环和责任明确 | 证据不足会诱导错误快速审批 |
| 360 视图 | 主对象 + 跨模块摘要 + 活动 + 关系 + 指标 | 全面理解客户/商品/供应商 | 减少跨模块搜集 | 聚合读取不能伪装成共同所有权和一次保存 |
| 对账/匹配工作台 | 双栏集合 + 候选 + 差异 + 核销 + 未匹配 | 财务、库存、数据同步对账 | 证据和决策并列 | 一对多、拆分、撤销和补偿必须显式 |
| 配置/设计器页 | 导航树 + 画布 + 属性 + 验证 + 版本发布 | 构建结构、流程、规则 | 能支持复杂配置 | 需要撤销、预览、草稿、发布和权限全套状态 |
| 门户/角色首页 | 待办 + 指标 + 最近对象 + 快捷入口 | 建立角色工作起点 | 聚合今天最重要任务 | 不能退化为模块链接和无行动数字卡 |

### 1.11 L5：页面到页面的导航模式与上下文契约

| 导航模式 | 适用关系/任务 | 优点 | 缺点与必须保存的上下文 |
|---|---|---|---|
| 同页嵌入 | 组成关系、强协同信息 | 零跳转、比较直接 | 页面可能过载；保存边界必须统一或明确分离 |
| 展开/折叠 | 次要详情、低频解释 | 保持主任务连续 | 内容发现性弱；展开状态需可预测 |
| 浮层/Popover | 轻量解释和快捷动作 | 成本最低 | 空间小、不可承载复杂任务 |
| 模态弹窗 | 短暂选择、确认、小编辑 | 完成后直接回填当前任务 | 禁止深层导航和弹窗套弹窗；关闭时处理未保存输入 |
| 侧边抽屉 | 关联预览、列表行快速处理 | 保留背景页面 | 窄屏差；背景与抽屉的对象身份和保存边界易混淆 |
| 主从分栏 | 队列连续处理 | 高吞吐、上下文持续 | 必须同步选中项、URL、键盘焦点和移动端退化方式 |
| 独立页面 | 独立生命周期对象、复杂任务 | URL、权限、历史和布局边界清楚 | 返回时恢复筛选、排序、页码、滚动和选中集 |
| 标签页子路由 | 同一主对象的稳定投影 | 身份上下文不变 | Tab 不是对象边界；需支持深链和浏览器历史 |
| 钻取/上卷 | 指标到维度到明细 | 分析链清楚 | 必须显示当前口径、过滤路径和返回层级 |
| 流程继续 | 向导、审批、队列下一项 | 引导合法下一步 | 需提供退出、回退、草稿和完成后的落点 |
| 跨模块/系统深链 | 独立权威对象或外部能力 | 直接到目标上下文 | 需处理身份、权限、来源、回跳地址和目标不可用 |
| 并排比较/新窗口 | 多对象或版本对照 | 同时保留多个上下文 | 状态同步、窗口失效和操作目标容易混淆 |

每次页面导航至少维护以下上下文契约：

```text
来源路由与来源对象
筛选、排序、分组和搜索词
分页/游标、滚动位置和选中项
当前 Tab、展开节点和时间/空间视口
未保存草稿、并发版本和临时选择集
完成、取消、失败后的返回目标
权限变化、对象删除或目标不可用时的降级路径
```

### 1.12 同一个销售订单模型的十四种合法 UI 投影

| UI 投影 | 使用的数据形状/关系 | 主任务 | 为什么合适 | 不适用或代价 |
|---|---|---|---|---|
| 订单搜索表格 | `Order[]` + 客户摘要 + 状态 | 查找、比较、批处理 | 列对齐、密度和筛选效率高 | 不适合理解一张订单的完整上下文 |
| 订单卡片网格 | `Order[]` + 商品图/门店/状态 | 视觉浏览 | 对移动端和视觉对象友好 | 精确金额和跨项比较弱 |
| 订单详情 | 单订单聚合 + 跨聚合摘要 + 历史 | 理解、决策、追溯 | 对象身份、状态、关系和合法动作集中 | 容易塞入过多 Tab 和跨边界编辑 |
| 订单录入 | 命令参数 + `OrderLine[]` 组成集合 | 创建订单 | 聚合内事实共同校验和保存 | 不应直接编辑库存、信用和发票等外部事实 |
| 分步下单向导 | 客户→商品→交付→确认 | 低频复杂创建 | 每步聚焦一类依赖和错误 | 高频熟练用户操作慢、前后信息不同时可见 |
| 履约看板 | 订单按履约状态分组 | 监控流动和阻塞 | 队列、WIP 和异常分布直观 | 拖拽必须调用合法状态命令，不适合金额精确比较 |
| 发货日历 | 计划发货时间区间 + 仓库/承运商 | 排期和冲突识别 | 时间占用和重叠直观 | 无准确排期或跨时区口径不清时误导 |
| 履约甘特 | 订单、拣货、发货、运输依赖 | 计划依赖和延期 | 区间、里程碑和前置关系同屏 | 普通订单浏览过重，数据维护成本高 |
| 客户订单时间线 | Customer → Order → Event | 理解客户历史 | 顺序和关键事件可解释 | 不适合批量筛选和精确列比较 |
| 区域订单地图 | 交付位置 + 路线 + 状态 | 配送覆盖和路径判断 | 空间聚类与邻近直观 | 地图不能代替地址精度、列表和权限裁剪 |
| 销售透视表 | 订单事实 × 客户/商品/时间维度 | 分析结构和差异 | 多维汇总、展开和钻取能力强 | 认知负担高，指标口径必须稳定 |
| 销售驾驶舱 | KPI + 趋势 + 分布 + 异常 | 监控经营态势 | 从总体快速发现异常 | 只显示图而无口径、明细和行动会沦为装饰 |
| 异常订单工作台 | 异常队列 + 原因 + 影响 + 处置 | 连续处理异常 | 把跨模块证据和命令围绕处置组合 | 组合读取不能越权修改各模块事实 |
| 订单审批中心 | 待办 + 金额/毛利/信用风险 + 历史 | 审批决策 | 证据、规则、理由和命令同屏 | 摘要缺失或自动下一条过快会放大审批错误 |

这十四种 UI 都来自同一订单事实，但它们不是同一页面换布局；它们使用了不同查询投影、操作语义、风险控制和导航上下文。

### 1.13 复杂 UI 的统一优缺点评价量表

比较候选 UI 时，不只写笼统的“直观”或“复杂”，至少逐项评价：

| 维度 | 核心问题 |
|---|---|
| 语义保真 | 是否保留类型、单位、关系、状态、来源和不变量？ |
| 任务适配 | 是否直接支持用户当前的查找、比较、录入、分析或处置？ |
| 信息密度 | 每屏承载量是否匹配任务，是否因密度过高或过低损害判断？ |
| 比较能力 | 是否能在稳定维度上并置多个对象、时间或版本？ |
| 关系可见性 | 所有权、层级、依赖、路径和来源是否足够清楚？ |
| 操作效率 | 高频操作的点击、键盘、跨页和等待成本如何？ |
| 规模能力 | 10、1,000、100,000 条数据时分别如何加载、筛选和渲染？ |
| 状态完备 | 正常、空、加载、错误、冲突、异步、部分成功是否可处理？ |
| 权限与风险 | 最小披露、禁用原因、确认、审计、幂等和回滚是否匹配风险？ |
| 上下文连续 | 跳转、刷新、返回和任务完成后能否恢复筛选、位置和草稿？ |
| 设备与无障碍 | 桌面、移动、键盘、屏幕阅读和触控是否有可用替代？ |
| 实现与维护成本 | 数据投影、实时性、组件复杂度和测试成本是否值得？ |

可以用 0–3 分评价，但以下任一项为 0 时直接否决：语义保真、服务端权限、业务命令合法性、关键错误恢复。

### 1.14 导航原理：导航是任务上下文的受控变换

导航的本质不是“从页面 A 打开页面 B”，而是改变用户当前关注对象、任务或分析粒度，同时决定哪些上下文被继承、压栈、替换、并列或丢弃。

可以把任一时刻的导航上下文表示为：

```text
NavigationContext = {
  route,              // 当前可寻址位置
  focus,              // 当前主对象、集合、节点或指标
  query,              // 搜索、筛选、排序、分组、分页/游标
  view,               // Tab、展开节点、地图视口、时间范围、缩放级别
  selection,          // 当前项、批量选择集、比较对象集
  draft,              // 未保存输入、向导进度、并发版本
  history,            // 用户实际访问路径
  returnContract      // 完成、取消、失败后回到哪里以及恢复什么
}
```

#### 1.14.1 八种基本导航变换

| 变换 | 状态变化 | 常见 UI | 原理 | 主要风险 |
|---|---|---|---|---|
| `Select` 聚焦 | 路由框架不变，只替换 `focus` | 主从列表、树节点详情、地图点位详情 | 同一任务空间内切换当前对象 | 选中项、URL 和键盘焦点不同步 |
| `Push` 前进 | 新上下文压入历史栈 | 列表→详情、详情→关联对象 | 保留来源，形成可逆浏览路径 | 返回后丢筛选、页码和滚动位置 |
| `Replace` 替换 | 当前历史项被新状态替换 | 筛选同步 URL、登录重定向、分页 | 更新可寻址状态但不制造无意义历史 | 误用会让浏览器返回跨越用户预期位置 |
| `Overlay` 叠加 | 保留背景上下文，临时增加局部任务 | Popover、模态、抽屉 | 子任务完成后直接回填背景任务 | 深层叠加、关闭时丢草稿、背景对象已变化 |
| `Drill` 钻取 | 增加过滤和分析粒度 | KPI→维度→明细、地图聚类→点位 | 从汇总事实逐步解释到构成事实 | 不显示过滤路径和口径，无法正确上卷 |
| `Advance` 流程前进 | 按状态机进入下一合法任务 | 向导、审批下一项、履约步骤 | 由业务状态和前置条件决定下一步 | 伪装线性流程、跳过分支、失败后无恢复点 |
| `Jump` 深链跳转 | 直接恢复一个完整目标上下文 | 收藏、通知、跨模块/系统链接 | 路由携带足够身份和视图状态以便重建 | 权限变化、对象失效、身份映射和回跳地址 |
| `Fork` 并列上下文 | 保留多个独立焦点 | 对比页、分栏、新窗口 | 同时观察两个对象、版本或方案 | 操作目标混淆、窗口状态过期和同步困难 |

#### 1.14.2 导航容器与导航语义不能混为一谈

弹窗、抽屉、标签页和页面只是**呈现容器**；选择、钻取、流程前进和深链才是**导航语义**。同一种语义可由不同容器承载：关联对象预览可以使用抽屉，也可以进入独立页；选择哪个容器取决于任务长度、所需空间、可寻址性和返回上下文，而不是关系类型本身。

| 导航问题 | 应判断的原则 |
|---|---|
| 是否改变主对象身份 | 改变时应有清楚的对象标题、路由或焦点状态 |
| 是否需要独立 URL | 需要收藏、分享、刷新恢复或权限边界时优先独立路由 |
| 是否必须同时参考来源 | 必须时用主从、抽屉或并排；否则可独立页面 |
| 子任务能否一次完成 | 能则 Overlay；需要深层操作和历史则 Push |
| 返回是什么意思 | 浏览器返回、业务取消、流程完成和回到来源是四种不同语义 |
| 是否存在未保存状态 | 导航前要保存草稿、确认放弃或阻止离开，不能静默丢失 |
| 目标是否可能失效 | 提供权限不足、对象删除和链接过期的恢复落点 |

#### 1.14.3 四种“返回”必须区分

```text
浏览历史返回：回到用户实际访问的上一个上下文。
层级返回：回到信息架构中的父层，例如组织子节点回到上级组织。
业务取消：放弃当前命令并回到发起任务的位置。
任务完成返回：根据 returnContract 回到队列、详情、来源页面或下一任务。
```

面包屑表达层级，不等于浏览器历史；“返回订单”表达业务来源，不一定等于父路由；审批完成后进入下一项是流程继续，也不应破坏用户返回待办队列的能力。

#### 1.14.4 导航原型应验证的状态

- 深链刷新后能否恢复主对象、Tab、筛选和分析口径。
- 从列表进入详情再返回时，筛选、排序、页码、滚动和选择集是否仍在。
- 抽屉或弹窗关闭时，背景对象是否仍是打开它时的对象。
- 向导回退、刷新、超时和失败后，已完成步骤及草稿能否恢复。
- 钻取后能否看到完整过滤路径并逐级上卷。
- 跨系统跳转遇到无权限或对象不存在时，是否提供可理解的替代落点。
- 多窗口或对比模式中，命令明确作用于哪一个对象或版本。

### 1.15 树形结构原理：先证明它是树，再选择树形 UI

树形 UI 适用于具有层级不变量的数据，而不是任何“看起来有上下级”的数据。严格有根树满足：

```text
存在一个根节点 root；
除根外每个节点恰有一个父节点；
从根到任一节点存在唯一简单路径；
不存在环；
节点可拥有 0..N 个子节点。
```

一旦某节点允许多个父节点，结构就是 DAG；一旦允许环，就是一般图。它们可以在界面上局部显示成树，但必须明确这是选定主路径后的**树投影**，不能把其他父关系或环静默删除。

#### 1.15.1 各种层级结构及其 UI 原理

| 结构 | 不变量或核心语义 | 候选 UI | 优点 | 缺点/边界 |
|---|---|---|---|---|
| 单根树 | 一个根、单父、唯一路径 | 展开树、树表、面包屑 | 全局层级与路径稳定 | 深层节点难找，需要搜索和路径回显 |
| 森林 | 多个互不相交根节点 | 多根树、虚拟总根、根分组 | 保留多个独立层级 | 虚拟总根只是 UI 便利，不应写回领域模型 |
| 分类树 / Taxonomy | 父类包含子类，对象可被归类 | 分类树、级联、分面、叶子选择 | 浏览和逐层收敛自然 | 对象多分类时“分类结构”和“对象归属”是多对多，不再是单树 |
| 组织树 | 行政归属、负责人、有效期 | 树表、组织图、节点详情 | 汇报层级和节点属性可见 | 矩阵汇报、项目关系和历史调动不能强塞进单父树 |
| 目录/文件树 | 路径身份、父目录和稳定顺序 | 目录树、面包屑、文件列表 | 导航和路径心智成熟 | 移动节点会改变路径；大目录需懒加载和虚拟化 |
| 物料清单/BOM | 组成、数量、替代件、版本 | 可展开 BOM、树表、用量汇总 | 组成结构直观 | 同一零件被多处复用时本质是 DAG，展开树会重复节点 |
| 权限继承树 | 权限沿资源或组织路径继承 | 范围树、权限树、有效权限预览 | 范围选择和继承来源清楚 | Allow/Deny、例外和多角色合并不能只显示勾选结果 |
| 决策树 | 条件节点导向互斥结果 | 分支图、条件摘要、路径测试 | 一条决策路径可解释 | 共享子规则和回跳会成为 DAG/图；规则优先级需显式 |
| 版本/修订树 | 一个版本可产生多个后继分支 | 版本树、分支线、Diff | 分叉、来源和合并历史可追踪 | 合并版本拥有多个父节点，完整结构是 DAG |
| 懒加载大树 | 子节点按需请求，节点数未知 | 异步树、虚拟树、搜索定位 | 支持大规模结构 | 展开、选择、计数和权限状态可能暂不完整 |
| DAG 多父结构 | 无环但节点可有多个父节点 | 依赖图、血缘图、主路径树 + 其他父引用 | 保留共享依赖和多来源 | 硬转树会复制节点并造成身份、选择和统计歧义 |
| 一般图 | 多父、双向、可有环 | 网络图、邻接列表、路径探索 | 能表达任意关系 | 不适合用普通树的展开、级联和继承规则 |

#### 1.15.2 树 UI 的五种不同任务

| 用户任务 | 最合适的树形表达 | 原因 |
|---|---|---|
| 浏览结构 | 展开树 + 搜索 | 同时观察父子和兄弟节点 |
| 选择一个路径节点 | 级联选择或树选择器 | 逐层收敛，并回显完整路径 |
| 管理节点属性 | 树表或主从树 | 层级与多列属性/详情并列 |
| 查看当前位置 | 面包屑 | 只表达祖先路径，不承担全树浏览 |
| 理解汇报或组成 | 组织图/BOM 展开图 | 空间布局强调上下级或组成关系 |

不要用面包屑替代树浏览，也不要用树控件替代单纯的分组列表。树的优势来自“路径和祖先关系影响任务”，若用户只需按某字段分组或筛选，分组表、分面和普通列表通常更简单。

#### 1.15.3 节点状态必须分层

树节点至少存在四类互不等价的状态：

```text
结构状态：是否有子节点、是否已加载、是否展开。
选择状态：未选、已选、部分选；父子是否联动。
业务状态：启用、停用、归档、异常、无权限。
任务状态：当前焦点、搜索命中、拖拽目标、正在加载或保存。
```

`部分选中` 只表示可见/已知后代的选择聚合，不能被误解为业务状态；在懒加载树中，父节点勾选是否包含尚未加载的后代必须由明确规则决定。

#### 1.15.4 树的关键工程与交互边界

- **身份与路径分离**：节点 ID 应稳定；移动目录或组织节点后路径可以改变。
- **顺序是否有业务意义**：若顺序可编辑，需要独立顺序字段、并发策略和拖拽回执。
- **防环**：移动或重新挂载节点前必须验证目标不是当前节点的后代。
- **删除语义**：删除节点时明确级联删除、提升子节点、禁止删除或归档。
- **权限裁剪**：用户看不到中间祖先时，需要安全的路径摘要，不能泄露无权节点。
- **懒加载选择**：选父节点是否代表“当前已加载后代”还是“该节点下全部对象”必须显式。
- **搜索定位**：搜索命中后应加载并展开祖先路径，而不只显示脱离上下文的节点名。
- **大规模策略**：使用懒加载、虚拟滚动、服务端搜索和局部计数，不一次展开整棵树。
- **历史有效性**：组织、分类和版本树随时间变化时，当前树与历史快照必须区分。
- **DAG 降级**：若数据多父，使用图或“主路径树 + 其他父引用”，并提示重复投影不代表重复对象。

#### 1.15.5 树形原型必须覆盖的测试

1. 根、叶、单子节点、深链和宽节点是否都可理解。
2. 节点搜索后是否能展开祖先并定位焦点。
3. 展开与选择是否互不混淆，键盘左右/上下操作是否可用。
4. 半选、禁用、无权限、未加载和业务异常是否有不同表达。
5. 移动节点时是否防止形成环，并说明权限与受影响对象。
6. 大树是否支持懒加载、虚拟化和服务端路径搜索。
7. 多父节点是否被正确识别为 DAG，而非静默复制成多个“不同”节点。
8. 返回树页面时是否恢复展开路径、选中节点和滚动位置。

## 2. 理论基础：它不是一套单一理论

### 2.1 理论来源

“数据模型到 UI 映射”没有一个包办全部问题的单一理论。完整方法来自多个理论层的组合：

| 理论或方法 | 回答的问题 | 在本文中的作用 |
|---|---|---|
| 类型系统与代数数据类型 | 数据具有什么结构形状 | 解释原子、可选、并集、积、集合和递归结构如何形成控件候选 |
| 关系模型与查询代数 | 如何选择、关联、分组和聚合事实 | 解释列表、筛选、分组表、透视表、报表和工作台的形成 |
| 领域驱动设计 DDD | 对象身份、不变量和一致性边界是什么 | 解释实体、值对象、聚合根、跨聚合引用和业务命令 |
| CQRS 与任务读模型 | 写正确和读高效为什么需要不同模型 | 解释一个写模型为什么能产生多个页面投影 |
| 状态机与事件模型 | 对象如何合法变化、如何追溯历史 | 解释状态徽标、动作区、步骤条、看板和时间线 |
| 任务中心设计与 HCI | 用户要完成什么，如何理解和操作 | 解释控件的可供性、自然映射、反馈和任务闭环 |
| 信息可视化理论 | 哪种视觉编码适合哪种数据和任务 | 解释表格、图表、地图、网络图和时间表达的选择 |
| 信息架构与格式塔原则 | 如何组织、分组和导航信息 | 解释 Section、Tab、步骤、层级、邻近和视觉层次 |
| 模型驱动 UI / CAMELEON | 如何从概念与任务逐级形成界面 | 提供“任务与概念 → 抽象 UI → 具体 UI → 最终 UI”的转换框架 |

### 2.2 本文提出的综合工作方法

本文将这些理论整合为 **领域—任务—表征双向映射法**，简称 **DTRM（Domain–Task–Representation Mapping）**。

**（直接事实）DTRM 是本文为了便于工程实践而使用的综合方法名称，不是一个已有行业标准的正式名称。**

DTRM 由两条链组成：

```text
正向设计链：领域语义 → 用例/任务 → 查询与命令 → 视图模型 → UI 表征

反向理解链：UI 证据 → 用户任务 → 查询投影 → 候选对象/关系
            → 候选状态/规则/边界 → 其他证据验证
```

它要求设计同时满足两点：

1. **向前可生成**：领域事实和任务能够稳定推导出页面、字段、导航、动作和反馈。
2. **向后可追踪**：每一个重要 UI 元素都能追溯到业务事实、任务、命令、规则或风险。

## 3. 映射前必须区分的模型层

“数据模型”不是一个单一模型。复杂信息系统至少存在以下模型：

```text
现实业务
  ↓ 抽象
领域模型：对象、身份、值、关系、聚合、状态、不变量、事件
  ↓ 面向用例
应用模型：查询、命令、前置条件、结果、失败
  ↓ 面向任务
任务模型：角色、目标、步骤、决策、频率、风险、异常
  ↓ 面向读取
视图模型：选择、连接、聚合、派生、排序、脱敏、权限裁剪
  ↓ 面向交互
UI 模型：页面、区域、控件、导航、反馈、临时状态

领域模型
  ↓ 持久化设计（另一条链）
逻辑数据模型 → 物理存储模型：表、列、外键、索引、分区、缓存
```

### 3.1 各层回答的问题

| 模型层 | 回答的问题 | 不应承担的责任 |
|---|---|---|
| 领域模型 | 业务世界里有什么，什么必须恒真 | 不决定按钮颜色和页面布局 |
| 应用模型 | 用户能查询什么、执行什么命令 | 不等同于数据库 CRUD |
| 任务模型 | 谁为了什么目标，在何种情境下工作 | 不决定物理表结构 |
| 视图模型 | 该任务一次需要哪些信息 | 不维护最终业务不变量 |
| UI 模型 | 信息如何呈现、操作和反馈 | 不取代服务端鉴权和校验 |
| 存储模型 | 数据如何持久化和高效访问 | 不直接决定用户心智结构 |

### 3.2 只有简单 CRUD 才近似重合

对于低风险、低关系复杂度、无复杂生命周期的基础资料维护，可能近似成立：

```text
一张逻辑表 ≈ 一个简单实体 ≈ 一个列表 + 一个表单
```

一旦出现以下任意条件，就不应继续机械映射：

- 跨对象决策。
- 主从整体校验。
- 状态流转和审批。
- 高风险命令。
- 多角色差异。
- 大规模集合。
- 指标分析和钻取。
- 异步处理或部分成功。
- 历史快照、审计和补偿。

## 4. 第一级：字段级映射模式全集

### 4.1 字段不是“列名 + 数据库类型”

一个可以正确映射到 UI 的字段描述，应至少包括：

```text
字段语义 =
  数据形状
× 业务角色
× 单位与精度
× 空值语义
× 约束
× 来源和权威性
× 生命周期
× 用户操作
× 状态策略
× 权限策略
× 数据规模
× 使用上下文
```

例如，数据库中的 `customer_id BIGINT` 不能直接生成数字输入框。它在领域中是“订单对客户聚合根的引用”，在 UI 中通常应表现为：

```text
异步客户搜索选择器
+ 客户名称/编码摘要
+ 信用或停用状态提示
+ 查看客户详情的导航
+ 提交时使用稳定客户标识
```

#### 4.1.1 字段的完整语义元模型

一个可被正确表征的字段，应被建模为：

```text
Field = <
  identity,             // 这是哪个业务事实
  shape,                // 标量、和、积、集合、引用、递归
  semanticRole,         // 标识、分类、度量、状态、时间、引用等
  valueDomain,          // 可取值集及其稳定性
  unitAndPrecision,     // 单位、精度、舍入和显示尺度
  nullAlgebra,          // 未填、未知、不适用、无权限等空值语义
  constraints,         // 格式、范围、唯一、跨字段和状态约束
  provenance,          // 手工录入、导入、同步、派生或继承
  authority,           // 哪个人或系统是权威修改方
  temporality,         // 事实时间、记录时间、有效期和版本
  sensitivity,         // 敏感级别、披露和审计要求
  mutability,          // 不变、可编辑、条件可编辑或只能通过命令改变
  scale                // 值域、数据量、更新频率和延迟
>
```

映射上下文另外是：

```text
Context = <
  role, task, pageMode, businessState, risk,
  device, locale, accessibilityNeed, dataVolume
>
```

因此，字段没有脱离上下文的“默认 UI”：

```text
Representation = map(Field, Context)
```

（主流共识）这与模型驱动 UI 中“任务/领域模型 → 抽象 UI → 具体 UI”的分层一致：数据类型只能给出候选表征，用户任务才能给出最终表征。

### 4.2 “全部映射模式”的完备性边界

控件库、设备和交互形式会继续发明，因此不存在一张永久封闭的“所有控件名称”清单。但映射的生成维度可以穷举。任意字段 UI 都是下列四类决定的组合：

```text
字段 UI
  = 映射拓扑          // 值与 UI 是 0:1、1:1、1:N、N:1 还是 N:M
  × 任务操作          // 读、录、选、查、比、组、聚、导、解释
  × 表征通道          // 文字、位置、长度、色彩、形状、声音、触觉等
  × 交互和政策状态  // 可见、可编辑、必填、验证、权限、反馈、冲突
```

这个分类在“组合算子”层面是封闭的，在“具体控件”层面是开放的。新出现的语音、AR 或 AI 控件仍需回答这四类问题。

#### 4.2.1 映射拓扑：字段与 UI 不是一对一

字段级基数必须同时包含数据字段和纯交互状态，不能只统计“数据库列对应几个控件”：

| 映射基数 | 规范形式 | 可见结果 | 典型用途 | 完整性要求 |
|---|---|---|---|---|
| `1:0` | `F → ∅` | 无直接可见表达 | 租户、版本、内部标志、服务端默认值 | 必须说明维护者、审计与诊断入口，不能因隐藏而失控 |
| `1:1` | `F → U` | 单一主要表达 | 读取、录入、筛选 | 格式、空值、权限与校验仍是映射的一部分 |
| `1:N` | `F → {U1…Un}` | 同值多表征或多任务视图 | 状态徽标、筛选项、看板列、历史趋势 | 各表征须共享值域、状态和单位口径 |
| `N:1` | `{F1…Fn} → U` | 复合值或摘要 | 地址、金额币种、姓名、时间区间 | 必须定义组合、拆分、空值和局部编辑规则 |
| `N:M` | `{F1…Fn} → g → {U1…Um}` | 条件、派生或分析表征 | 风险等级、能力控制、差异、图表 | 必须公开派生口径、刷新时点与不可编辑性 |
| `0:1` | `∅ → U` | 无持久化字段的 UI 状态 | 展开、焦点、未保存、加载、确认、命令反馈 | 不得伪装成领域事实；刷新、撤销和恢复语义要明确 |

基数轴回答“多少事实形成多少表达”；用途轴回答“用户拿它做什么”。二者正交，同一个金额字段可以在详情中是 `1:1 + 只读展示`，在趋势图中是 `1:N + 可视化编码`，在含税总价中是 `N:1 + 聚合派生`。

| 编号 | 拓扑模式 | 形式 | 含义 | ERP 例子 |
|---|---|---|---|---|
| T0 | 省略/隐式映射 | `F → ∅` | 字段不直接出现，由服务端、上下文或默认值维护 | 租户 ID、行版本、内部删除标志 |
| T1 | 直接映射 | `F → U` | 一个业务值由一个可见元素表达 | 备注 → 文本区 |
| T2 | 格式化/变换映射 | `F → φ(F) → U` | 保持语义，改变显示格式或尺度 | 分值金额 → `¥1,234.56` |
| T3 | 解码/查找映射 | `code → label/summary` | 把稳定存储值解码成用户可识别概念 | `customer_id` → 客户名称、编码和状态 |
| T4 | 分解映射 | `F → U1...Un` | 一个领域值被拆成多个协作元素 | 时间区间 → 开始、结束、时区、时长 |
| T5 | 复合映射 | `F1...Fn → U` | 多个字段共同构成一个可理解的 UI 值 | 金额 + 币种 → 金额控件 |
| T6 | 多重表征 | `F → U1...Un` | 同一字段在同一任务中有互补表征 | 交付率 → 数值 + 进度条 + 趋势 |
| T7 | 跨视图重用 | `F × C1...Cn → U1...Un` | 同一字段按页面任务改变表征 | 订单状态在列表为徽标，在看板为列，在报表为分组维度 |
| T8 | 派生/聚合映射 | `F1...Fn → g(F) → U` | UI 表达的是计算事实，不是某一列 | 明细数量与单价 → 订单总额 |
| T9 | 政策/行为映射 | `F → UI policy` | 字段值决定可见、必填、可编辑或动作资格，本身未必显示 | 开票类型决定专票信息区是否必填 |
| T10 | 结构/分支映射 | `F → UI structure` | 字段选择不同表单分支、步骤或区域 | 促销类型切换折扣、满减、赠品配置 |
| T11 | 视觉编码映射 | `F → visual channel` | 值被编码为位置、长度、色相、形状等 | 欠款额 → 条形长度 |
| T12 | 时态/历史映射 | `F(t) → sequence` | 展示值随时间变化，而非只显示当前快照 | 库存量 → 变化趋势和异动时间线 |
| T13 | 差异/对比映射 | `(Fbefore,Fafter) → diff` | 表达修改、版本或方案之间的差异 | 合同修订前后金额高亮 |
| T14 | 导航/操作线索映射 | `F → destination/affordance` | 字段提供导航、拨号、复制、下载等可供性 | 运单号 → 物流轨迹链接 |

一个字段可以同时使用多个拓扑算子。例如“客户”可以同时经过 T3 解码为摘要、T14 形成详情导航、T9 根据信用状态决定是否允许提交订单。

#### 4.2.2 一个重要补充：字段不仅映射成“可见控件”

字段还可以映射为：

- 标签和单位：决定如何命名和如何解读。
- 格式化器：决定小数、日期、时区、货币和缩写。
- 校验器：决定可接受值及错误信息。
- 可见性和披露策略：决定显示、脱敏、按需显示还是完全不返回。
- 编辑性策略：决定可编辑、只读、禁用、条件可编辑或仅允许命令改变。
- 布局和分支：决定字段组、条件区域、排序优先级和空间占用。
- 交互可供性：决定搜索、复制、跳转、扫码、拨号、预览和下载。
- 查询能力：决定能否筛选、排序、分组、聚合、搜索和钻取。
- 状态和反馈：决定未保存、验证中、冲突、过期、同步失败和审批状态的表达。

只检查“字段是否有控件”，会漏掉大部分真正影响 UI 品质的映射。

### 4.3 按用户操作穷举字段的表征族

（主流共识）UI 映射的选择应由“用户对数据做什么”驱动。从任务操作看，字段表征可分为下列完整家族：

| 操作族 | 用户意图 | 典型表征模式 |
|---|---|---|
| 识别 Identity | 确认“这是谁/哪个” | 主标题、编码、头像/缩略图、标识摘要、复制标识 |
| 读取 Read | 准确获得当前值 | 字面值、格式化值、解码标签、单位、空状态、脱敏值 |
| 扫描 Scan | 在高密度数据中快速定位 | 对齐列、紧凑值、条件高亮、图标加文字、徽标 |
| 录入 Create | 输入一个新值 | 自由输入、格式化输入、扫码/相机/语音采集、文件上传 |
| 修订 Edit | 在保留旧值语义下修改 | 内联编辑、表单编辑、差异编辑、乐观更新与冲突解决 |
| 选择 Select | 从受控值域中取值 | 单选、多选、搜索选择、树选择、对象选择、级联选择 |
| 直接操纵 Manipulate | 用空间动作改变值 | 拖拽排序、滑块、时间轴拖拽、地图选点、图像裁剪 |
| 确认 Confirm | 对值或声明明确表态 | 是/否单选、确认复选、签名、二次验证；不与业务命令混同 |
| 搜索 Search | 按值或文本找到对象 | 全文搜索、前缀/模糊搜索、自动完成、搜索建议 |
| 筛选 Filter | 缩小候选集 | 精确值、集合、区间、相对时间、空值、层级和组合条件 |
| 排序 Sort | 按字段建立顺序 | 升/降序、多列优先级、业务顺序、空值位置 |
| 分组 Group | 把对象分成可比较的集合 | 分组行、折叠组、看板列、树层级、分面 |
| 聚合 Aggregate | 对一组值计算数量、和、率或分布 | 合计行、KPI、分组指标、透视表、统计图 |
| 比较 Compare | 识别对象、时间或版本差异 | 对齐列、差异高亮、基准线、同比/环比、版本 Diff |
| 监控 Monitor | 观察状态、阈值和变化 | 状态徽标、进度、趋势、告警、刷新时间、数据新鲜度 |
| 导航 Navigate | 由值到相关对象、地址或任务 | 详情链接、预览、钻取、外部地址、返回来源上下文 |
| 解释 Explain | 理解值“从何而来、为何如此” | 口径、公式、来源、时间戳、责任方、规则命中解释 |
| 审计 Audit | 追溯谁在何时如何修改 | 前后值、操作人、原因、版本、时间线 |
| 交换 Exchange | 导入、导出、复制、打印或分享 | 导入列映射、文件格式、剪贴板形式、打印表征、隐私剪裁 |

这些操作族比控件名称更稳定。例如“选择客户”无论实现为弹窗、命令面板、语音或 AI 候选，本质都是“在受权限和状态约束的对象集上做查找与选择”。

为避免操作目录遗漏，评审时按下列用途轴逐项过门：身份和标签；只读展示；录入和修改；选择和引用；搜索和筛选；排序和排名；分组和分类；比较和差异；聚合和派生；状态和能力控制；导航和钻取；校验和错误反馈；权限、脱敏和披露；时间、历史和审计；导入、导出、打印和交换；可视化编码。某一用途不适用时记录“不适用及理由”，不能以“页面上已有字段”代替检查。

字段语义覆盖清单也应独立于控件清单维护：文本、长文本、富文本、数字、金额、计量、比例、Boolean、枚举、字典、状态、日期、时间、区间、时区、颜色、文件、图片、音视频、位置、地址、坐标、几何、引用、集合、JSON/动态结构、派生值、敏感值、审计值、版本值和技术控制值。它们可以复用表征算子，但不能丢失各自的单位、值域、来源、生命周期和披露约束。

#### 4.3.1 字段级异常、冲突、延迟与恢复

| 情形 | UI 必须表达 | 恢复动作 | 禁止做法 |
|---|---|---|---|
| 本地校验失败 | 具体字段、规则与修复方向 | 保留输入并定位错误 | 清空表单或只报“参数错误” |
| 跨字段约束失败 | 冲突字段组及业务原因 | 导航到最小冲突集合 | 把错误挂在任意一个字段上 |
| 异步校验中/失败 | 校验对象、进度、最后结果 | 重试、改值或人工核验 | 校验未完成即显示已通过 |
| 并发版本冲突 | 本地值、远端值、版本和影响 | 刷新、比较、合并或放弃 | 最后写入静默覆盖 |
| 引用失效/无权限 | 已选对象、失效原因或披露边界 | 重选、申请权限或回到权威入口 | 把无权限误写成“对象不存在” |
| 派生值陈旧 | 口径、数据时点与刷新状态 | 刷新或进入来源明细 | 把缓存值冒充实时事实 |
| 上传/导入部分成功 | 成功项、失败项和可重试标识 | 只重试失败项并防重复 | 只给一个总失败提示 |

### 4.4 从数据形状得到控件候选，而不是最终答案

类型系统可以提供第一层候选：

| 数据形状 | 形式化理解 | UI 候选 |
|---|---|---|
| 原子值 Scalar | 一个不可再拆的业务值 | 文本、数字、日期、只读文本、状态值 |
| 可选值 Optional | `None` 或 `Some(T)` | 可清空输入、未知/不适用选择、空状态 |
| 积类型 Product | 多个字段共同构成一个值 | 地址、金额币种、时间范围等复合控件 |
| 和类型 Sum | 多种互斥分支之一 | 单选、分段控件、类型选择后的条件区域 |
| 集合 Collection | 多个同类型元素 | 重复字段、子表、标签集合、附件列表 |
| 递归类型 Recursive | 元素包含同类型子元素 | 树、级联选择、目录、面包屑 |
| 引用 Reference | 指向有独立身份的对象 | 选择器、对象摘要、链接、预览 |
| 派生值 Derived | 由其他事实计算 | 只读值、指标、解释和来源时间 |

类型只回答“数据是什么形状”，任务才回答“应该如何呈现和操作”。

### 4.5 按业务角色选择表达

| 字段业务角色 | 常见 UI 表达 | 关键要求 |
|---|---|---|
| 身份标识 | 编号、标题、稳定链接、复制按钮 | 稳定、唯一、可识别 |
| 描述属性 | 文本、富文本、摘要 | 适合阅读和编辑长度 |
| 分类属性 | 单选、下拉、标签、筛选项 | 受控词汇和一致命名 |
| 度量值 | 数量、金额、比例、单位组合 | 精度、单位、范围和舍入规则 |
| 时间事实 | 日期、时间、区间、时区提示 | 区分业务时间、系统时间和有效期 |
| 业务状态 | 状态徽标、状态说明、动作区 | 不应直接等同为可编辑枚举 |
| 对象引用 | 搜索选择器、对象摘要、导航 | 显示可识别信息，提交稳定标识 |
| 计算/派生值 | 只读值、指标、趋势、公式解释 | 标明口径、来源和更新时间 |
| 审计字段 | 操作者、时间线、版本信息 | 不允许普通用户直接编辑 |
| 敏感字段 | 脱敏值、按需查看、二次验证 | 最小披露和审计 |
| 控制字段 | 通常不直接展示 | 不把技术标志伪装成业务概念 |

### 4.6 字段语义到 UI 的模式库

下表不是“类型到单一控件”的规则，而是每种语义在读取、编辑和分析任务中的候选族。一个具体字段可以命中多行。

#### 4.6.1 标量和值对象

| 字段语义 | 读取/识别映射 | 录入/编辑映射 | 查询/分析映射 | 关键判据 |
|---|---|---|---|---|
| 稳定标识 ID | 编号、短缩识别、复制、链接 | 通常系统生成或受控编码 | 精确搜索、前缀搜索 | 稳定性高于可读性；不用存储 ID 代替对象名称 |
| 名称/短文本 | 文本、标题、截断加完整值 | 单行输入、自动补全 | 全文、前缀、模糊搜索和排序 | 长度、唯一性、语言与同名消歧 |
| 业务编码 | 等宽文本、分段显示、复制 | 授权输入、扫码、规则生成 | 精确/前缀匹配 | 不要对编码做数学格式化或丢失前导零 |
| 长文本 | 分段、摘要、展开/收起 | 多行输入、字数和草稿 | 全文检索、命中摘要 | 阅读与编辑需要不同表征 |
| 富文本/结构化内容 | 渲染内容、大纲、附件引用 | 受控编辑器、源码模式、模板 | 全文与结构筛选 | 消毒、版本、粘贴和导出语义 |
| 布尔值 | 是/否文本、状态或徽标 | Switch、Checkbox、是/否单选 | 三态筛选：全部/是/否 | 先区分设置、选择、明确回答、事实和业务命令 |
| 单值分类/Enum | 文本、标签、徽标 | Radio、Select、Segmented | 分面、分组、筛选、占比 | 值域规模、稳定性、频率和是否存在业务转换 |
| 集合分类/Set | Chip、标签集、摘要 | Checkbox Group、Multi-select、Transfer | 包含/不包含、任一/全部匹配 | 是否可重复、是否有顺序、是否需要关系属性 |
| 整数/计数 | 数值、紧凑数量、负号 | 数字输入、Stepper、键盘 | 区间、直方分布、总和 | 是数量还是编码；是否允许负值 |
| 小数/高精度数 | 按精度格式化、对齐 | 精度受控数字输入 | 区间、分布、统计 | 存储精度、计算精度和显示精度应分离 |
| 金额 Money | 值 + 币种 + 税/含税口径 | 金额与币种复合输入 | 合计、区间、对比、趋势 | 精度、舍入、汇率时点和正负方向 |
| 数量 Quantity | 值 + 单位 | 数值 + 单位/换算 | 按同一计量基准汇总 | 不能直接相加不同量纲或未换算单位 |
| 比例/百分比 | 数值 + `%`、进度或差值 | 百分比输入、Slider（范围窄且容差允许时） | 占比、基准线、趋势 | 区分 `0.15` 和 `15%`，分母必须可解释 |
| 评分/评级 | 分数、星级、文字等级 | 受控评级或分数输入 | 分布、排名、与基准比较 | 名义、有序还是等距尺度决定可计算方式 |
| 顺序/优先级 | 序号、级别、位置 | 选级、拖拽排序、数字输入 | 排序和分组 | 顺序变化是否需要原子更新和冲突处理 |
| 数值区间 | 下界–上界、包含性 | 双输入、双滑块 | 区间重叠、包含筛选 | 开/闭区间、无上界/无下界和单位 |
| 日期/时间点 | 本地化日期、相对时间、时区 | 日期/时间选择、快捷值 | 绝对/相对时间筛选、时间趋势 | 区分日期、当地时间、瞬时时刻和业务时区 |
| 时间区间 | 开始–结束、时长、进度 | 区间选择、日历拖拽 | 重叠、包含、空档、甘特图 | 顺序、边界包含性、跨日和夏令时 |
| 持续时长 Duration | 人可读时长、单位 | 分段时长输入 | 区间、分布、SLA 对比 | “1 个月”不等于固定秒数 |
| 周期/重复规则 | 人话摘要、下次执行时间 | 周期构建器、日历规则 | 按周期、下次运行和失败筛选 | 时区、例外日、结束条件和错过策略 |
| 地址值对象 | 格式化地址块、地图预览 | 分段输入、自动完成、地图选点 | 行政区筛选、距离/范围 | 地址文本、标准编码和坐标不是同一事实 |
| 地理点/线/面 | 地图标记、路径、边界 | 选点、绘制、编辑几何 | 范围、包含、距离、空间聚合 | 坐标系、精度、位置隐私 |
| 颜色/样式令牌 | 色块 + 名称/令牌 | 色板或受控令牌选择 | 通常不作业务分析尺度 | 不能仅用色彩表达重要语义 |

#### 4.6.2 引用、集合、媒体和系统字段

| 字段语义 | 读取/识别映射 | 录入/编辑映射 | 查询/分析映射 | 关键判据 |
|---|---|---|---|---|
| 单对象引用 | 对象摘要、链接、预览 | 异步搜索选择、对象拾取器 | 按对象精确筛选、分组 | 显示人可识别摘要，提交稳定标识，维持租户和状态边界 |
| 层级引用 | 完整路径、面包屑、树位置 | Tree Select、Cascader、搜索树 | 后代/祖先范围筛选 | 要明确选中节点是否包含后代 |
| 对象集合引用 | 摘要、Chip、关联列表 | 多选搜索、Transfer、关联表编辑 | 包含某对象、数量和关联属性 | 关系若有角色、有效期或顺序，应升格为关联实体 |
| 递归/树结构 | 树、大纲、路径 | 树编辑、拖拽层级 | 层级筛选、展开聚合 | 防循环、移动语义、级联权限 |
| 可重复值组 | 列表、标签、摘要 | 重复字段、子表、行编辑 | 数量、包含、集合聚合 | 顺序、唯一性、最小/最大个数 |
| 文件/附件 | 名称、大小、类型、预览、下载 | 上传、拖放、扫描、版本替换 | 类型、时间、上传人、内容搜索 | 扫毒、权限、版本、保留期和下载审计 |
| 图像 | 缩略图、放大、标注 | 上传、相机、裁剪、旋转 | 元数据、标签、相似搜索 | 原图/派生图、方向、替代文本和敏感内容 |
| 音频/视频 | 播放器、波形、字幕、时长 | 上传、录制、裁剪 | 元数据、转录文本、时间点 | 带宽、转码状态、字幕和播放权限 |
| 公式/表达式 | 人话解释、源式、计算结果 | 表达式编辑器、函数和字段拾取 | 依赖和影响查询 | 类型、循环依赖、版本、沙箱和重算时机 |
| 派生指标 | 指标值、口径、来源时间、趋势 | 通常不直接编辑，可编辑其规则 | 分组、对比、钻取到构成事实 | 公式、粒度、分母、时间窗口和新鲜度 |
| 业务状态 | 状态名、解释、时间和合法动作 | 通过业务命令转换，不直接编辑 code | 待办队列、看板、状态分布 | 当前值必须与合法转换和权限一起表达 |
| 审计字段 | 创建/修改人、时间、来源 | 不允许普通业务表单修改 | 审计筛选、时间线、责任追溯 | 是系统事实，不是用户声明 |
| 版本/并发标记 | 通常隐藏；冲突时显示版本差异 | 随提交携带，不手工编辑 | 版本和历史查询 | 映射成冲突检测和恢复交互，不映射成数字输入 |
| 敏感事实 | 脱敏、最小摘要、按需显示 | 受信通道、二次验证、不回显 | 严格限制筛选、导出和聚合粒度 | 不返回比 CSS 隐藏更安全；查看与导出均应审计 |
| 多语言值 | 按当前语言显示，可显示回退来源 | 分语言编辑、翻译状态 | 按语言分析的全文搜索 | 区分缺失翻译、回退值和原文 |
| JSON/扩展属性 | 结构化查看、摘要或专用视图 | Schema 表单、键值编辑或源码编辑 | 只对已定义语义的键建立筛选 | 不应把未受控 JSON 当作所有业务扩展的默认出口 |
| 技术控制字段 | 默认不显示，诊断场景显示 | 由系统或管理工具维护 | 运维和诊断筛选 | 不向业务用户泄漏存储、分片、同步实现细节 |

#### 4.6.3 Boolean 不是 Switch：最小反例

| 真实语义 | 合适表达 | 不合适表达 |
|---|---|---|
| 可立即切换、低风险且可逆的设置 | Switch | 高风险状态转换直接 Switch |
| 一组项目中的选择 | Checkbox | 用 Switch 表示“已选择” |
| 必须明确回答的是/否问题 | 是/否单选 | 用未勾选同时表示“否”和“未回答” |
| 只读事实 | 状态文本或徽标 | 伪装成可操作开关 |
| 触发业务过程 | 明确命名的命令按钮 | 把“批准”简化为 true/false 字段编辑 |

#### 4.6.4 Enum 不是 Select

- 普通分类：下拉、单选、分段控件。
- 高频筛选：Filter、Chip、Tab，但需确认选项互斥且稳定。
- 业务状态：状态徽标加合法动作，不能默认生成任意状态下拉框。
- 类型判别：选择后切换对应的字段组，体现和类型分支。

#### 4.6.5 受控值域如何选择控件

| 值域特征 | 首选候选 | 原因 |
|---|---|---|
| 2–5 个稳定且需并列比较的单选项 | Radio；极紧凑、文字短时可 Segmented | 选项可见，减少记忆与展开成本 |
| 选项不多但空间紧张 | Select | 压缩空间，代价是选项不可同时比较 |
| 值域较大或人可记忆关键字 | Searchable Select/Autocomplete | 从“浏览所有项”转为“搜索候选” |
| 值域很大、远程、有权限和状态 | 异步对象选择器 | 需分页、去抖、语义搜索、租户裁剪和候选摘要 |
| 有层级路径 | Tree Select/Cascader | 保留父子语义和路径上下文 |
| 多选且需看已选结果 | Checkbox Group、Multi-select、Chip | 保留集合语义 |
| 多选且需排序、配额或关系属性 | Transfer 或关联明细表 | 选择已不是单值问题，需管理关系实体 |
| 选项需视觉预览 | Swatch、缩略图网格、样例 | 光看名称不足以做决策 |

表中的数量不是绝对标准；真实选择还受选项文本长度、使用频率、熟练度、设备和无障碍需求影响。

#### 4.6.6 时间不是 DatePicker

- 计划发生时间：可编辑日期或时间范围。
- 已发生时间：只读时间和事件上下文。
- 有效期：开始/结束成组，并校验顺序和边界。
- 截止时间：日期加剩余时间、逾期状态和时区。
- 创建时间：审计信息，不是业务日期输入框。

#### 4.6.7 金额不是 Decimal

金额不是普通 Decimal。正确表达至少包含：

```text
数值 + 币种 + 精度 + 舍入规则 + 税口径 + 正负方向 + 权威来源
```

订单总额若由明细计算，应作为可解释的派生值展示；不能让用户同时编辑明细和总额而不定义冲突规则。

#### 4.6.8 语法受约束的字符串不是普通文本

| 语义 | 输入映射 | 读取/操作映射 | 不变量与安全要求 |
|---|---|---|---|
| 电子邮件 | 邮箱输入法、基本语法提示、验证状态 | 发邮件操作、复制、部分脱敏 | “格式合法”不等于“地址存在”或“已验证归属” |
| 电话号码 | 国家/地区码 + 本地号码、电话键盘 | 拨号、发消息、复制、脱敏 | 存储规范化值，保留分机号；不用数值类型存储 |
| URL/URI | URL 输入、协议与域名校验 | 可识别链接、预览、复制 | 不自动信任用户提供的协议和目标，外跳要有安全策略 |
| 邮政编码/行政编码 | 随国家或地区变化的格式化输入 | 分段显示、地区查找 | 格式是上下文相关的，不用一个全局正则伪装通用性 |
| 证件号/银行卡号/账号 | 分段输入、校验位提示、安全粘贴 | 部分脱敏、按需披露、复制受控 | 敏感数据最小化、加密/令牌化、查看和导出审计 |
| 密码/PIN | 不回显的密码输入、显示切换、密码管理器支持 | 永不显示原值；只提供重置/变更状态 | 密码原文不可读；不用“原密码长度”的星号回显 |
| API 密钥/Token | 生成或安全导入，设定权限与过期时间 | 仅创建时显示一次、后续显示指纹和末位 | 撤销、轮换、范围和最后使用可审计 |
| 验证码/OTP | 分位或单框输入、自动填充、倒计时 | 验证结果，不回显值 | 短效、单次使用、重发频控和尝试次数 |
| IP/MAC/设备标识 | 格式化输入、扫描或自动检测 | 等宽显示、复制、设备导航 | 版本、标准化、敏感性与动态地址语义 |
| 条码/二维码内容 | 扫描优先、手动输入回退 | 人可读编码 + 码图、复制/重新扫描 | 先确认编码规则和发行方；不盲目执行扫码得到的 URL 或命令 |
| 源代码/SQL/规则 DSL | 带语法、补全、格式化和静态检查的编辑器 | 等宽阅读、行号、差异、执行结果 | 沙箱、超时、资源限制、权限、版本和审批 |
| 正则表达式/匹配模式 | 模式编辑器 + 测试样例 + 匹配解释 | 源式、命中结果与性能告警 | 防止灾难性回溯，不让黑箱模式直接进入高风险流程 |
| 数字签名/哈希/校验和 | 通常由系统生成，不手工编辑 | 指纹摘要、验证结果、复制 | 算法、密钥、完整值和“验证成功”是不同信息 |

#### 4.6.9 字段值的采集通道

“用哪个控件”之前，还应决定“值从哪个交互通道进入系统”。一个字段可以有主通道和回退通道。

| 采集通道 | 适用字段 | 关键设计要求 |
|---|---|---|
| 键盘录入 | 文本、数字、日期、编码 | 匹配键盘类型、允许粘贴、不在输入期间破坏未完成值 |
| 候选选择 | 枚举、字典、对象引用 | 值域、搜索、权限、状态和候选摘要 |
| 直接操纵 | 顺序、区间、坐标、几何、裁剪 | 需要精确数值回馈和键盘替代方式 |
| 扫码/RFID/NFC | 商品码、设备、会员、批次 | 明确扫描结果、重复扫描和误读恢复；不默默执行高风险命令 |
| 相机/扫描件/OCR | 图像、票据、证件、文字 | 展示识别置信和原图，要求用户核对高风险值 |
| 文件上传/导入 | 附件、媒体、批量行 | 类型、大小、安全检查、解析预览、错误行和幂等 |
| 语音/听写 | 备注、搜索词、命令候选 | 转录结果可编辑；高风险命令需要显式确认 |
| 位置/传感器采集 | 坐标、时间、温度、重量、设备状态 | 来源设备、精度、采样时间、校准状态和隐私权限 |
| 签名/手写 | 同意、交接、签收、注释 | 区分手写图像、身份验证、数字签名和法律效力 |
| 系统计算 | 派生值、审计字段、状态 | 显示口径、时间和责任边界；不伪装成手工输入 |
| 外部同步/消息 | 主数据、库存、物流、支付结果 | 显示权威系统、延迟、同步错误和重复消息处理语义 |
| AI/OCR 建议 | 分类、文本、匹配、预测值 | 作为候选显示来源和置信；未被授权自动写入时，接受前不是业务事实 |
| 继承/默认 | 组织、客户、商品、模板带入值 | 明确值已存在、来源及覆盖/恢复继承方式 |

采集通道的选择也是映射的一部分。例如仓库中的商品码主通道应是扫码，回退通道才是手工输入；把它只映射成通用 Input，数据类型虽然没错，任务映射却是失败的。

### 4.7 空值是一个和类型，不是空白

从 UI 角度看，`Optional<T>` 往往还不够。更完整的模型是：

```text
ValueState<T> =
    Present(T)
  | NotEntered
  | Unknown
  | NotApplicable
  | NotExist
  | Redacted
  | Forbidden
  | Pending
  | Failed(reason)
  | Stale(lastKnownValue, asOf)
  | DeletedReference
```

| 值状态 | UI 应表达 | 不应如何处理 |
|---|---|---|
| 未录入 | 未填、必填提示、可录入入口 | 与用户明确填写的空字符串混同 |
| 未知 | “未知”并允许后续补全 | 自动解读为否定值或 0 |
| 不适用 | “不适用”及原因 | 标记为数据质量缺失 |
| 业务不存在 | “无”、空集合或不存在说明 | 显示为加载中 |
| 已脱敏 | 遮罩值和披露状态 | 显示为真实值本身就是星号 |
| 无权限 | 仅在需要告知存在性时显示“无权查看”；否则服务端不返回 | 返回真值后只用 CSS 隐藏 |
| 待计算/待同步 | 独立的等待状态和预期时间 | 显示为 0 或— |
| 失败 | 错误、可重试性、最后成功值 | 安静地变成空白 |
| 过期 | 旧值 + “截至何时” + 刷新入口 | 把旧值伪装成当前事实 |
| 引用对象已删除 | 保留历史标识与失效说明 | 突然显示空值，丢失审计线索 |

一个页面若用同一个“—”表示上述全部情况，用户无法区分“没有数据”、“数据尚未准备好”和“不允许看数据”。

### 4.8 约束如何映射到交互

| 领域约束 | UI 表达 | 服务端责任 |
|---|---|---|
| 必填 | 标签、输入时提示、提交前定位 | 最终拒绝缺失值 |
| 类型/格式 | 合适输入法、格式化、即时提示 | 重新解析和校验 |
| 范围 | 单位、范围提示、Slider/Stepper（仅适合时） | 验证上下界 |
| 唯一性 | 异步检查和冲突建议 | 唯一约束或原子校验 |
| 跨字段规则 | 联动提示、条件区域、摘要 | 统一业务规则校验 |
| 条件必填 | 随业务条件出现并解释原因 | 不信任前端显隐 |
| 状态限制 | 只读、禁用或不展示，并说明原因 | 验证当前状态 |
| 权限限制 | 可见/可编辑策略 | 最终鉴权和数据范围控制 |
| 并发控制 | 版本冲突提示、比较和刷新 | 乐观锁、行锁或原子条件更新 |

UI 校验负责早反馈和可理解性；服务端约束负责业务正确性。两者不能相互替代。

#### 4.8.1 约束反馈的三个时机

| 时机 | 用途 | 例子 |
|---|---|---|
| 操作前 | 设置正确期望，避免明知不可行的输入 | 显示可用库存、允许日期范围、命名规则 |
| 操作中 | 尽早发现局部可确认问题 | 格式、长度、范围、跨字段联动 |
| 提交后 | 由权威边界确认唯一、权限、并发和最新业务状态 | 客户编码冲突、版本过期、状态已被他人修改 |

禁用控件若会让用户疑惑，应给出原因和恢复条件；彻底不适用或不允许知道存在性时，才考虑不展示。

### 4.9 来源、权威性和生命周期的映射

同一个值的数字相同，不代表其可信度、可编辑性和时效性相同。

| 字段来源/状态 | UI 映射 | 用户可做什么 |
|---|---|---|
| 手工录入 | 可编辑值，可显示录入人和时间 | 按权限修改 |
| 默认值 | 明确已填值，不伪装为 Placeholder | 接受或覆盖 |
| 建议值 | 候选和理由，未接受前不当作业务事实 | 接受、修改或拒绝 |
| 继承值 | 值 + 继承来源 | 继续继承、局部覆盖、恢复继承 |
| 计算值 | 只读值 + 公式/口径 + 计算时间 | 修改输入或进入规则管理 |
| 外部同步值 | 来源系统、最后同步时间、同步状态 | 刷新、查看源、在权威系统修改 |
| 已核验/已批准值 | 核验状态、人和时间 | 通过撤销或重新审批命令改变 |
| 被覆盖值 | 当前值 + 原建议/继承值 + 覆盖原因 | 编辑、恢复原值 |
| 过期缓存值 | 最后已知值 + as-of 时间 + 过期说明 | 刷新或继续使用并承担风险 |
| 冲突值 | 本地值、服务端值、差异与版本 | 保留、采用、合并或重新输入 |

当来源会影响决策时，它就是任务信息，不能永远藏在 Tooltip 里。

### 4.10 从字段到可视化通道的映射

字段不只映射到表单控件，还会映射到图表和高密度列表的视觉变量。（主流共识）信息可视化的基本要求是：先保证表达性，再优化感知效率。可视化不能暗示原数据中不存在的顺序或精度。

| 数据尺度 | 首选视觉通道 | 辅助通道 | 不当用法 |
|---|---|---|---|
| 名义分类 | 分区位置、文字标签 | 色相、形状、图标 | 用长度暗示类别大小或只用颜色区分 |
| 有序分类 | 排序位置、长度 | 亮度、大小 | 使用无顺序色相暗示等级 |
| 定量数值 | 共同标尺上的位置、长度 | 大小、明度 | 需精确比较时使用面积、角度、3D 体积 |
| 时间 | 有序位置、时间轴 | 连线、区间长度 | 不等间时间点却按等距排列 |
| 地理 | 地理位置 | 色、大小、等值线 | 只因为有地名就使用地图，导致无法精确比较 |
| 网络关系 | 节点与连线 | 大小、色、线型 | 用力导向图替代可扫描的表格或分组列表 |

视觉通道的选择顺序可压缩为：

```text
数据尺度
→ 用户任务（查值/比较/排名/趋势/分布/异常）
→ 能正确表达该尺度的通道
→ 其中感知最准确、最易扫描的通道
→ 文字、单位、图例和无障碍冗余表征
```

颜色适合辅助检出异常和分类，不适合单独承载高风险状态或精确数值。

### 4.11 同一字段应有“表征配置文件”

字段到 UI 通常是 `1:N` 而非 `1:1`。应按任务定义表征配置：

| 上下文 | 字段表征的关注点 |
|---|---|
| 新建 | 默认、建议、录入速度、条件必填、提交前验证 |
| 编辑 | 原值、可编辑性、变更影响、未保存和冲突 |
| 详情阅读 | 准确、可读、来源、空值、相关导航 |
| 列表扫描 | 紧凑、对齐、可排序、可筛选、异常可见 |
| 选择器 | 对象识别、搜索键、候选资格、选中后摘要 |
| 筛选器 | 运算符、值域、空值、时间相对性和组合条件 |
| 分组/透视 | 分组粒度、排序、“其他”和空值桶 |
| 分析 | 尺度、聚合方式、基准、时间窗口、钻取口径 |
| 批量修改 | 适用范围、保留原值、部分成功策略和预览差异 |
| 导入 | 源列映射、解析格式、错误行、幂等键和缺省值 |
| 导出/打印 | 格式、单位、时区、字典解码、脱敏和精度 |
| 审计 | 原值、新值、行为人、时间、原因、版本 |
| 移动端/扫码端 | 主任务、快速采集、单手操作、断网草稿和错误恢复 |

例如“订单金额”字段可以有：

```text
列表：币种符号 + 小数对齐 + 右对齐
详情：金额 + 币种 + 税口径 + 计算来源
编辑：若为派生值则只读，并在明细改变后重算
筛选：区间 + 币种基准
分析：统一币种折算 + 聚合 + 趋势 + 钻取到订单
导出：未缩写精确值 + 独立币种列 + 明确口径
```

### 4.12 字段映射决策顺序

对每个字段按以下顺序决策：

```text
1. 它表达的是哪个业务事实，而不是哪一列？
2. 它是输入、输出、选择条件、派生结果，还是命令参数？
3. 用户在当前任务中要读取、比较、录入、选择还是确认它？
4. 它的单位、空值、约束、来源和更新时间是什么？
5. 当前状态和角色是否允许查看或修改？
6. 值域和数据规模多大，是否需要搜索、分页或虚拟化？
7. 哪种控件最自然地表达上述语义和操作？
8. 成功、错误、冲突和未保存状态如何反馈？
```

**控件选择必须是最后一步，而不是第一步。**

#### 4.12.1 可执行的选择算法

```text
STEP 1  定义业务事实和不变量
STEP 2  确定当前角色的任务操作
STEP 3  确定映射拓扑：省略、直接、解码、分解、复合、派生等
STEP 4  区分业务值、值状态、来源状态和交互状态
STEP 5  选择能保留该语义的抽象交互
STEP 6  根据值域、规模、频率、设备和风险选具体控件
STEP 7  补齐约束、权限、来源、时效、反馈和无障碍表征
STEP 8  用极端值、空值、错误、冲突和不同角色验证
```

### 4.13 如何判断字段映射是好的

字段级评判不是“控件是否漂亮”，而是下列不变量是否成立：

| 评判维度 | 好映射的证据 | 典型失败 |
|---|---|---|
| 语义保真 | 用户读到的概念与领域事实一致 | 把状态当可任意编辑枚举，把 ID 当数字 |
| 任务匹配 | 表征直接支持读、比、录、选等当前操作 | 列表为编辑优化，却难以扫描和比较 |
| 自然映射 | 操作方式与结果关系直观 | 用没有方向提示的图标修改风险等级 |
| 状态完备 | 有值、空值、等待、失败、过期、冲突可区分 | 全部显示为空白或 0 |
| 可供性真实 | 看起来可操作的就真能操作，不可操作的原因可理解 | 用“禁用”代替权限设计，或只读值长得像输入框 |
| 精度与单位 | 输入、显示、计算、导出之间无量纲或舍入歧义 | 把元与分、原始比率与百分比混用 |
| 来源可解释 | 会影响决策的来源、口径、时间可获知 | 缓存旧值伪装成实时值 |
| 权限与隐私 | 服务端裁剪、最小披露、查看和导出可审计 | 把敏感值返回前端再隐藏 |
| 规模适应 | 值域从 10 增到 1 万时，搜索、分页和虚拟化可演进 | 一万客户全量下拉 |
| 无障碍 | 键盘、读屏、焦点、文字冗余和错误关联完整 | 仅用颜色、占位符或 Hover 表达必要信息 |
| 本地化 | 数字、日期、时区、币种、文字方向与输入法受支持 | 将显示格式当作存储事实 |
| 往返一致 | 在可编辑场景中，显示、解析、修改、提交后不丢失语义 | 格式化后不能无歧义地还原，却还允许直接编辑 |

#### 4.13.1 字段映射的十二个最小测试

```text
1. 语义测试：隐去数据库列名，用户能否说出这个值是什么？
2. 操作测试：用户能否用它直接完成当前的读/录/选/比任务？
3. 非法可供性测试：UI 是否暗示了服务端不允许的操作？
4. 空值测试：未知、不适用、无权、待计算和失败能否区分？
5. 边界值测试：最小、最大、负数、高精度、超长文本如何表达？
6. 规模测试：值域和数据量放大 10 倍、100 倍后，映射是否仍可用？
7. 角色测试：无权、只读、可编辑和审计角色看到的是否正确？
8. 状态测试：业务状态变化后，字段可见、必填和可编辑性是否与服务端一致？
9. 本地化测试：切换语言、时区、币种和数字格式后是否仍无歧义？
10. 无障碍测试：不看颜色、不用鼠标、使用读屏时能否理解和操作？
11. 来源测试：值过期、被继承、被覆盖或由外部同步时，用户能否作出正确判断？
12. 冲突恢复测试：值在编辑期间被他人修改时，能否看差异并保留有用输入？
```

### 4.14 字段级反模式

| 反模式 | 本质问题 |
|---|---|
| `VARCHAR → Input`、`BOOLEAN → Switch`、`ENUM → Select` | 把存储形状当作业务语义 |
| 所有字段在新建、列表、详情、筛选共用同一控件配置 | 忽略用户操作与上下文 |
| 用 Placeholder 代替标签和单位 | 输入后语义线索消失，无障碍与回看失败 |
| 把隐藏、禁用、只读当成同一件事 | 混淆存在性、权限、当前状态和可操作性 |
| 空、0、否、未知共用一个值 | 丢失值状态语义，甚至改变业务事实 |
| 只做前端校验 | UI 拦截无法成为权威业务约束 |
| 存储格式、显示格式和导出格式混为一体 | 本地化、精度、可计算性与往返一致性冲突 |
| 把对象引用显示为裸 ID | 把参照完整性转嫁为用户记忆负担 |
| 所有大值域都下拉加载 | 忽略规模、延迟、搜索和权限裁剪 |
| 仅用红绿表达成功/失败 | 把关键语义绑定到单一低可访问性通道 |
| 派生值可编辑但未定义输入与派生的冲突规则 | 存在两个事实权威来源 |
| 把业务状态用任意下拉框修改 | 绕过状态机、权限、副作用和审计 |
| 把 AI 建议直接显示成已确认值 | 混淆候选、事实与责任边界 |

## 5. 第二级：实体级映射模式全集

### 5.1 实体级映射的本质

字段回答“一个值是什么”，实体则新增三个不可约简的语义：

```text
稳定身份：不同时间和页面中，如何确认它仍是同一个对象？
生命周期：它如何创建、变化、关闭、失效或归档？
业务能力：围绕它可以查询什么、执行什么命令？
```

实体到 UI 不是“实体对应一个页面”，而是：

```text
实体 E
× 任务 T
× 角色 R
× 状态 S
× 数据规模 N
→ 实体视图族 ViewFamily(E)
```

一个成熟实体通常形成一组相互关联的视图，而不是一个万能页面。

### 5.2 实体级映射模式总表

实体模式按七个正交视图族组织：单实体；实体集合；状态/过程；时间/空间；分析；协作；映射基数。下表中的具体页面只是这些视图族在任务、角色和规模约束下的实例。

| 模式 | UI 形态 | 主要任务 | 适用条件 | 关键风险 |
|---|---|---|---|---|
| 身份表达 | 标题、编号、图标、稳定链接 | 识别当前对象 | 所有有稳定身份的实体 | 名称相同导致误认，编号语义不清 |
| 微型引用 | 名称 + 编码 + 少量摘要 | 在别处识别该实体 | 选择器、列表单元格、关系摘要 | 信息太少无法区分同名对象 |
| 列表行 | 表格一行、紧凑列表项 | 查找、扫描、比较 | 同类对象集合，信息维度稳定 | 列过多、状态和动作混乱 |
| 卡片摘要 | 卡片、Tile、媒体对象 | 浏览、识别、快速判断 | 视觉或少量差异比列对齐更重要 | 密度低，不适合大量精确比较 |
| 搜索结果 | 命中摘要、关键词高亮 | 从大集合定位对象 | 对象量大、入口不确定 | 排名不可解释、摘要缺上下文 |
| 选择候选 | 选择器结果项 | 建立实体引用 | 目标是独立实体且允许选择 | 把不可选对象隐藏而不解释原因 |
| 对象摘要 | Header、Summary、关键指标区 | 快速确认身份和当前态势 | 详情、抽屉、工作台中的主对象 | 摘要与正文口径不一致 |
| 完整详情 | 单页详情、分区详情 | 理解实体全貌 | 低频深度查看、需关系和历史 | 万能详情页、无任务优先级 |
| 快速预览 | Popover、抽屉、Quick View | 补充上下文而不中断任务 | 只需少量信息和低风险动作 | 抽屉不断嵌套、承担完整任务 |
| 创建表单 | 页面、弹窗、向导 | 建立实体最小业务事实 | 创建命令边界明确 | 照搬全部实体字段 |
| 编辑表单 | 页面、行内编辑、局部面板 | 修改允许变化的属性 | 字段可编辑性和状态规则明确 | 将编辑等同为通用 PATCH |
| 快速编辑 | 行内编辑、Popover 编辑 | 修改单一低风险属性 | 高频、可逆、校验局部 | 隐藏副作用和跨字段约束 |
| 批量编辑 | 批处理栏、批量向导 | 对多个实体执行同类命令 | 对象可独立成功或有明确原子策略 | 把批量命令误作循环单条更新 |
| 状态表达 | 徽标、进度、状态摘要 | 理解当前生命周期 | 有受控状态机 | 把 Enum 当状态机 |
| 能力/动作表达 | 主按钮、动作菜单、命令面板 | 对实体执行合法命令 | 状态、权限和风险已知 | 动作按技术 CRUD 命名 |
| 历史表达 | 时间线、审计日志、版本差异 | 解释“如何变成现在这样” | 状态或字段变化需追溯 | 把技术日志直接给业务用户 |
| 活动流 | 评论、任务、通知、协作记录 | 围绕实体协作 | 多角色共同完成事实 | 活动与权威业务事件混淆 |
| 状态看板卡 | 看板卡、泳道项 | 观察实体在状态间流动 | 大量同类实体、状态迁移是主任务 | 卡片信息不足、拖拽绕过规则 |
| 时间投影 | 日历项、甘特任务、时间轴节点 | 安排和理解时间 | 实体有关键时间点或区间 | 将多个时间含义混成一个日期 |
| 空间投影 | 地图点、区域、轨迹 | 理解位置和覆盖 | 空间关系决定任务 | 精确度和聚合尺度误导 |
| 指标贡献项 | 钻取明细、事实行 | 解释聚合指标由谁构成 | 实体是指标事实或维度成员 | 汇总口径与实体详情不一致 |
| 打印/凭证投影 | 单据、标签、凭证、PDF | 法定留存、交接或线下使用 | 版式和历史快照有契约 | 直接打印当前主数据导致历史变化 |
| 导入/导出投影 | 模板行、CSV/Excel、批量校验结果 | 批量交换实体数据 | 字段边界和错误定位明确 | 模板暴露内部字段或绕过规则 |
| 嵌入式实体片段 | 另一页面中的摘要区 | 支撑跨实体任务 | 只读组合或边界清晰的局部命令 | 用户误以为可在此维护权威实体 |

### 5.3 一个实体到多个 UI（`1:N`）

这是最常见的实体映射：

```text
Customer
├─ 客户列表行：发现和比较
├─ 客户选择器项：建立引用
├─ 客户摘要：在订单中补充上下文
├─ 客户详情：理解客户全貌
├─ 客户编辑：维护主数据
├─ 客户 360：组合交易和互动关系
├─ 地图点：区域拜访任务
└─ 分析维度：客户分层和销售贡献
```

这些视图必须共享身份、名称、状态和权限语义，但允许字段集合、密度、排序和操作完全不同。

### 5.4 多个实体到一个 UI（`N:1`）

一个面向任务的页面常组合多个实体：

```text
履约工作台 =
  订单实体摘要
+ 客户信用摘要
+ 商品/库存可用量
+ 发货实体状态
+ 当前处理人的任务和权限
```

这是查询投影，不表示这些实体属于同一个聚合，也不表示可以用一个通用“保存”原子修改。

### 5.5 一个实体视图中的分组模式

实体详情的分组可能来自：

- **身份组**：编号、名称、当前状态和所有者。
- **属性组**：稳定业务主题或值对象。
- **决策组**：当前任务必须同时比较的字段。
- **能力组**：当前状态和权限允许的命令。
- **关系组**：相关实体摘要和导航。
- **历史组**：事件、版本和审计。
- **异常组**：阻塞、缺失、冲突和恢复动作。

分组服务于理解和任务，不必复制实体类的字段声明顺序。

### 5.6 实体级选择判据

选择实体 UI 模式时依次判断：

```text
1. 任务是识别、查找、比较、理解、创建、编辑、执行、追溯还是分析？
2. 用户同时处理一个实体还是实体集合？
3. 实体的关键差异更适合列对齐、视觉浏览、时间、空间还是状态表达？
4. 操作频率、风险、可逆性和批量语义是什么？
5. 需要多少关系、历史和异常上下文才能完成判断？
6. 是否应保留来源列表、筛选和选中状态？
```

### 5.7 实体级反模式

- 一个实体永远只生成“列表 + 通用表单”。
- 列表、详情、选择器和报表各自定义不同名称与状态口径。
- 详情页包含所有字段，却无法回答用户最常见的判断。
- 所有命令都收进“更多”，没有主次和风险层级。
- 直接编辑状态、审计字段和派生值。
- 预览抽屉承担完整复杂任务，并出现多层嵌套抽屉。
- 批量操作没有说明全回滚、部分成功还是遇错即停。
- 删除实体只问“是否确认”，不解释关联影响和恢复能力。

### 5.8 实体与 UI 不是一一对应：完整映射基数

实体与 UI 的对应关系至少包含五种基数。它们不是互相排斥的技术方案，而是同一系统中会同时存在的投影关系：

| 映射基数 | 含义 | 典型例子 | 设计重点 |
|---|---|---|---|
| `1:0` | 实体存在，但没有独立 UI | 幂等记录、内部调度实例、技术关联实体 | 不为“数据库里有表”强造页面；仅在诊断、审计或运维场景暴露 |
| `1:1` | 一个实体有一个主要权威视图 | 简单配置项、低复杂度基础资料 | 仍需区分查看和命令权限，不能把详情等同于数据库行 |
| `1:N` | 一个实体形成多个任务视图 | 订单列表行、详情、录入、审核卡、打印单据 | 身份、状态、单位和口径必须跨视图一致 |
| `N:1` | 多个实体组合成一个任务页面 | 履约工作台、客户 360、异常处理台 | 组合读取不等于共同所有权，也不等于一次原子保存 |
| `N:M` | 多类实体进入多个角色/流程页面 | ERP 中订单、库存、发货分别进入销售、仓管、财务视图 | 需要双向追踪“页面为何需要该事实、命令归谁负责” |

由此可见，`实体 = 页面` 只适用于极小部分简单 CRUD。成熟信息系统的基本单位不是孤立页面，而是**实体视图族**和**任务页面族**。

### 5.9 实体视图族的语义完备性

“把实体所有字段放上页面”不等于完整。实体的 UI 是否完备，应检查它是否按实际任务覆盖了以下语义面：

| 实体语义面 | UI 要回答的问题 | 候选表征 |
|---|---|---|
| 身份 | 我正在处理的是谁，如何避免同名误认 | 名称、编码、主标识、稳定链接、来源 |
| 当前事实 | 它现在有哪些对任务有用的属性 | 摘要、详情分区、只读投影 |
| 生命周期 | 它处于哪个阶段，如何到达当前状态 | 状态摘要、进度、时间线、版本历史 |
| 业务能力 | 当前允许执行什么，为什么允许或禁止 | 主动作、动作菜单、禁用原因、前置条件 |
| 关系 | 它由什么组成、引用谁、被谁引用 | 子表、关系摘要、相关列表、导航 |
| 责任 | 谁拥有、负责、审批或跟进 | 负责人、组织范围、任务分派、权限提示 |
| 异常 | 什么阻碍任务完成，如何恢复 | 异常区、缺失项、冲突说明、修复动作 |
| 证据 | 结论和变化由什么事实支撑 | 来源、附件、审计、评论、事件 |
| 分析位置 | 它在集合、指标和趋势中处于什么位置 | 排名、对比、指标贡献、钻取 |
| 外部表征 | 如何交接、打印、导入导出或被外部识别 | 单据、标签、文件行、外部编号 |

不要求每个实体都拥有全部视图。正确做法是先按角色任务确定必需语义面，再选择最小充分的视图族。没有任务依据的“完备”只会制造万能详情页。

### 5.10 实体映射的六个质量测试

1. **身份连续性测试**：从列表、选择器、详情、弹窗到打印件，用户能否确认它始终是同一个实体？
2. **任务差异测试**：不同视图是否因任务不同而真正改变字段、密度、排序和动作，而非简单复制同一表单？
3. **生命周期测试**：创建、修改、停用、归档和恢复是否匹配实体真实生命周期？
4. **命令合法性测试**：页面只能产生当前状态和权限允许的业务命令，还是能任意 PATCH 字段？
5. **规模测试**：实体从 10 个增长到 10 万个后，查找、选择、批处理和历史浏览是否仍成立？
6. **来源一致性测试**：同一事实出现在多个视图时，名称、单位、口径、更新时间和权威来源是否一致？

## 6. 第三级：实体间关系映射模式全集

### 6.1 关系不是只有基数

关系的完整语义至少包括：

```text
关系语义 =
  基数
× 方向
× 所有权
× 生命周期依赖
× 一致性边界
× 删除/失效规则
× 是否有关系属性
× 顺序
× 时间有效性
× 数据规模
× 访问频率
× 当前任务
```

因此，两个同为 `1:N` 的关系，可能需要完全不同的 UI。

### 6.2 基础关系映射

| 关系类型 | 常见 UI | 关键判断 |
|---|---|---|
| 一对一组成 | 同一表单中的字段组、详情区 | 是否同生命周期、整体保存 |
| 一对一引用 | 对象摘要、链接、选择器 | 目标是否具有独立身份 |
| 一对多组成 | 明细子表、重复表单、主从编辑 | 子项是否只能通过根创建和修改 |
| 一对多引用 | 关联列表、摘要计数、独立页 | 子对象是否独立增长和分页 |
| 简单多对多分类 | 多选、标签选择、穿梭框 | 关系本身是否无额外业务属性 |
| 带属性的多对多 | 关联实体列表或编辑器 | 数量、角色、有效期等关系属性必须显式表达 |
| 层级关系 | 树、级联选择、面包屑 | 父子、继承、移动和历史规则 |
| 时间关系 | 时间线、日历、甘特图 | 顺序、区间、依赖和历史 |
| 状态关系 | 状态条、看板、动作区 | 合法转换和前置条件 |
| 网络关系 | 关联列表或关系图 | 只有拓扑本身是任务时才优先用图 |

### 6.3 同一个 `1:N` 为什么会产生多种 UI

| 场景 | 推荐表达 | 原因 |
|---|---|---|
| 数量小、同生命周期、整体提交 | 可编辑明细表 | 保持聚合整体性 |
| 数量大、独立生命周期 | 摘要计数 + 独立关联页 | 支持分页、筛选和独立权限 |
| 高频浏览和对照 | 列表 + 详情分栏 | 保留集合上下文，减少跳转 |
| 关注发生顺序 | 时间线 | 时间顺序比表格列更重要 |
| 关注状态分布和流动 | 看板 | 状态分组和迁移是主任务 |
| 关注指标差异 | 分组表、透视表、图表 | 任务是聚合分析而非逐项编辑 |

所以 UI 的丰富性来自“对同一关系执行不同任务”，不是来自任意更换组件。

### 6.4 多对多关系必须识别关联实体

例如“商品属于多个价目表，价目表包含多个商品”。如果关系只表达成员资格，可以使用多选。

但如果关系还包含：

- 销售价。
- 起止有效期。
- 最小订购量。
- 客户等级。
- 审批状态。

那么“价目表商品”已经是业务对象。UI 应使用关联明细表或专用编辑页，不能继续压缩成多选框。

### 6.5 关系表达必须匹配用户任务

同一关系在不同任务中可以采用不同表达：

| 用户任务 | 对关系的操作 | UI 表达 |
|---|---|---|
| 创建对象 | 选择关联目标 | 搜索选择器、级联选择 |
| 理解对象 | 查看关联摘要 | 摘要卡、关键字段、计数 |
| 深入调查 | 遍历关联对象 | 链接、抽屉、关联页、关系图 |
| 比较多个对象 | 同维度对照 | 表格、比较矩阵、分栏 |
| 分析结构 | 聚合、分组和钻取 | 透视表、图表、树、钻取链 |
| 维护关系 | 增删或修改关系属性 | 关系编辑器、关联实体表单 |

### 6.6 聚合根、跨聚合关系与导航

#### 6.6.1 聚合不是页面容器

**（主流共识）DDD 聚合定义的是业务不变量和一致性边界，不是视觉卡片、Tab 或页面边界。**

两者存在关联，但不能机械等同：

- 一个聚合根可以投影成多个页面。
- 一个页面可以组合读取多个聚合根。
- 聚合内部对象可以在根的控制下整体编辑。
- 跨聚合写入应通过目标聚合根的明确业务命令完成。

核心规则：

> **读可以跨聚合组合；写必须回到维护该不变量的权威聚合边界。**

#### 6.6.2 聚合内部的 UI 表达

对于订单聚合：

```text
SalesOrder（聚合根）
├─ OrderHeader（根属性/值对象）
├─ ShippingAddress（值对象）
├─ OrderLine[]（聚合内实体）
└─ OrderAdjustment[]（聚合内实体或值）
```

适合的 UI 通常是：

- 订单头摘要和字段组。
- 地址复合控件。
- 可编辑订单行子表。
- 统一的保存、提交和整体校验。
- 总额、税额等派生汇总。

聚合根负责保证订单行、金额、状态等整体不变量；UI 不应让用户绕过根单独把某一行保存成互相矛盾的状态。

#### 6.6.3 聚合根之间的 UI 表达

订单常引用多个独立聚合根：

```text
SalesOrder ──引用──> Customer
SalesOrder ──引用──> Product
SalesOrder ──关联──> Shipment
SalesOrder ──关联──> Invoice
SalesOrder ──查询──> InventoryAvailability
SalesOrder ──查询──> CreditAssessment
```

常见导航语义：

| 导航语义 | 目的 | UI 模式 |
|---|---|---|
| 选择 Select | 建立或替换引用 | 搜索选择器、对象选择页 |
| 查看 View | 理解被引用对象 | 稳定链接、详情页 |
| 窥视 Peek | 临时补充上下文，不离开任务 | 抽屉、Popover、侧边预览 |
| 枢轴切换 Pivot | 把目标对象变成新的工作中心 | 从订单进入客户 360 或发货详情 |
| 相关集合 Related list | 查看当前对象的关联对象 | 关联页签、独立关联列表 |
| 流程继续 Continue | 触发下游业务过程 | “创建发货单”“申请开票”业务命令 |
| 分析钻取 Drill | 从汇总追到构成事实 | 指标 → 分组 → 明细 → 单据 |
| 返回上下文 Return | 完成查看后回到原任务 | 保留筛选、分页、选中对象和滚动位置 |

#### 6.6.4 选择器不是简单下拉框

跨聚合选择器至少要考虑：

- 目标对象稳定身份。
- 用户用于识别它的名称、编码和关键摘要。
- 可选对象的数据范围和权限。
- 停用、冻结、信用异常等不可选原因。
- 大数据量下的搜索、分页和缓存。
- 已选对象发生变化后的快照或实时引用策略。
- 清除或替换引用的业务影响。

#### 6.6.5 跨聚合命令不能伪装成大表单保存

反模式：在一个“万能订单详情页”中同时修改客户主档、订单、库存、发货和发票，然后点击一个“全部保存”。

问题在于：

- 多个聚合的不变量和权限不同。
- 事务可能无法原子覆盖所有边界。
- 部分成功和异步结果无法解释。
- 用户无法理解哪个对象已经改变。

正确方式通常是：

```text
跨聚合组合读取
+ 明确标识各对象及状态
+ 每个业务动作调用权威命令
+ 展示处理中、部分成功、失败和补偿结果
+ 保留审计和关联标识
```

#### 6.6.6 导航必须保存任务上下文

跨对象导航的质量，不只看“能否到达”，还要看“能否回来继续工作”。至少应保存：

- 来源页面和来源任务。
- 原筛选、排序、分页和分组。
- 当前选中对象或行。
- 未保存状态及离开保护。
- 返回后的数据新鲜度。
- 多窗口或并行处理状态。

### 6.7 实体间关系映射模式总目录

关系模式必须先按语义分类，再选择 UI 投影；基数只用于约束数量，不足以决定交互：

| 关系语义 | 关键不变量 | UI 候选 | 异常与恢复 |
|---|---|---|---|
| 组成/聚合内部 | 子项生命周期受根控制，写入守住聚合不变量 | 嵌入字段组、子表、重复区 | 子项校验、并发版本；随根原子提交或明确草稿 |
| 跨聚合引用 | 各自独立身份与权威命令 | 选择器、自动完成、摘要、链接 | 引用停用、无权、陈旧；重选或回权威对象处理 |
| 普通关联 | 双方可独立存在，关系可单独增删 | 关联列表、关系编辑器、矩阵 | 重复关联、悬空；去重并保留变更证据 |
| 带属性的关联实体 | 关系本身有身份、属性或生命周期 | 子表、关联详情、对账行 | 属性冲突、有效期重叠；编辑关联实体而非两端对象 |
| 分类/成员 | 类别规则与成员资格独立 | 标签、树选择、成员列表、分面 | 循环分类、失效类别；校验路径并迁移成员 |
| 层级/树/路径 | 父子约束、无环或路径规则 | 树、级联选择、面包屑 | 循环、孤儿、移动冲突；阻断非法移动并显示影响 |
| 网络/图 | 多路径、方向、权重或关系类型 | 网络图、邻接列表、路径详情 | 图过密、路径过期；聚焦子图并显示过滤条件 |
| 顺序/依赖 | 前后约束或稳定排序 | 拖拽序列、甘特、依赖图 | 环依赖、序号竞争；检测环并重新编号 |
| 时间有效 | 关系仅在时间区间内成立 | 时间线、日历、有效期编辑 | 区间重叠、时区差异；比较区间并裁决 |
| 状态转换 | 只允许合法迁移并伴随守卫/副作用 | 状态图、步骤、看板、流程继续 | 非法迁移、处理中；调用命令并追踪回执 |
| 因果/来源/派生 | 来源链和计算口径可追溯 | 血缘、来源摘要、钻取 | 来源缺失、重算差异；保留版本并重新计算 |
| 替代/版本/修订 | 新旧对象不可混同，适用范围明确 | 版本列表、Diff、替代提示 | 旧引用、并行版本；选择生效版本并迁移引用 |
| 对应/匹配/对账 | 匹配证据、差异和核销状态可审计 | 并列比较、矩阵、对账台 | 一对多歧义、金额差异；人工裁决、撤销与补偿 |

UI 表现可归入六类算子：嵌入（字段组、子表、重复区域）；选择（选择器、自动完成、级联、关系编辑器）；并列（摘要、关联列表、主从分栏、矩阵）；导航（链接、面包屑、预览、抽屉、枢轴切换、返回上下文）；结构可视化（树、网络、时间线、日历、甘特、看板）；业务动作（继续流程、创建下游对象、钻取、比较、匹配和对账）。关系语义与表现是多对多组合，不存在“`1:N` 固定用子表”的规则。

仅按 `1:1 / 1:N / N:M` 分类是不充分的，因为基数只描述“有几个”，没有描述“为什么相关”。对 UI 真正有决定力的是关系语义。下表给出企业信息系统中可复用的关系模式族；具体组件仍可继续变化，但都应能归入某一种语义族或其组合。

| 关系模式族 | 领域语义 | UI 映射候选 | 关键问题 |
|---|---|---|---|
| 组成 Composition | 部分属于整体，通常依赖整体生命周期 | 字段组、嵌套表单、明细子表、树形明细 | 子项能否脱离根独立存在和修改 |
| 引用 Reference | 一个实体用稳定身份指向另一个独立实体 | 对象选择器、微型引用、摘要、稳定链接 | 显示实时主档还是交易时快照 |
| 关联 Association | 双方独立，关系表达业务联系 | 相关列表、关系页、双向导航 | 谁维护关系，是否需要双向可见 |
| 关联实体 Association Entity | 关系本身有身份、属性或生命周期 | 关系明细表、专用表单、关系详情 | 不能压缩为多选或标签 |
| 分类 Classification | 对象属于类别或标签 | 单选、多选、标签、分类树、分面筛选 | 类别是互斥枚举、层级主档还是开放标签 |
| 层级 Hierarchy | 父子、上下级、包含或汇总层级 | 树、级联、面包屑、缩进表、上钻下钻 | 是否允许多父、移动、继承和历史生效 |
| 顺序 Sequence | 对象有稳定业务顺序 | 排序列表、步骤条、序号列、拖拽排序 | 排序是视觉偏好还是业务事实 |
| 前置依赖 Dependency | B 必须在 A 后或满足 A 才能执行 | 依赖图、甘特连线、禁用动作及原因 | 依赖失败、循环依赖和解除条件如何表达 |
| 状态转换 Transition | 同一实体或流程在合法状态间变化 | 状态图摘要、进度条、看板、合法动作 | 状态不是可任意编辑的枚举 |
| 因果/派生 Derivation | 结果由一组来源事实或规则计算 | 公式说明、来源展开、血缘钻取、差异解释 | 用户能否追到结果来源和计算时点 |
| 时间有效 Temporal | 关系只在某时间点或区间成立 | 时间轴、有效期编辑器、日历、版本对比 | 当前关系与历史关系不能混淆 |
| 空间 Spatial | 邻近、覆盖、包含、路径或区域归属 | 地图、区域层、轨迹、距离排序 | 坐标精度、聚合尺度和权限范围 |
| 事件关联 Event | 业务事件由谁产生、影响谁 | 活动流、事件时间线、通知、关联跳转 | 业务事件与技术日志应分离 |
| 责任/参与 Responsibility | 某角色、组织或人员对对象承担职责 | 负责人、参与人、泳道、任务箱、RACI 摘要 | 责任、权限、关注和通知不是同一关系 |
| 权限/范围 Scope | 主体可在某范围执行某能力 | 范围树、授权矩阵、继承说明、有效权限预览 | UI 隐藏不能替代服务端授权 |
| 相似/替代 Similarity | 对象相似、可替换、可推荐或有优先级 | 对比表、候选列表、推荐、替代链 | 相似度和替代条件必须可解释 |
| 版本/谱系 Lineage | 新对象由旧版本复制、修订、拆分或合并 | 版本历史、差异、来源/去向链、谱系图 | 当前版本、法律快照和可编辑版本须区分 |
| 对账/匹配 Reconciliation | 两组独立事实需要匹配、核销或解释差异 | 双栏匹配、差异表、候选匹配、核销动作 | 匹配置信度、余额和未匹配项必须可见 |
| 统计/维度 Analytical | 事实按维度聚合、比较并钻取 | 分组表、透视表、图表、指标到明细钻取 | 汇总口径必须与明细构成一致 |
| 网络 Network | 多节点多边关系本身是分析对象 | 邻接列表、关系图、路径高亮 | 只有拓扑探索是主任务时才优先使用图 |

“完整目录”在这里指**语义模式类别完整**，不指穷举所有组件外观。一个关系可以同时具备多种语义，例如组织关系既是层级，又具有时间有效性、权限继承和责任范围；UI 需要组合表达这些语义，而不是机械选择一个控件。

### 6.8 关系到 UI 的五种投影方式

同一关系并不总要显示成一块“关联信息”。根据任务，它可以投影为五类交互：

| 投影方式 | 用户意图 | UI 结果 | 典型例子 |
|---|---|---|---|
| 建立/维护 | 创建、替换、解除或修改关系属性 | 选择器、关系编辑器、拖拽、批量关联 | 订单选择客户、维护员工岗位有效期 |
| 识别/解释 | 知道当前对象和谁相关、为何相关 | 微型引用、摘要、来源说明、禁用原因 | 订单显示客户及信用状态 |
| 遍历/导航 | 沿关系从当前对象到目标对象 | 链接、预览、枢轴切换、相关页 | 客户到订单、订单到发货单 |
| 比较/协调 | 同时看关系两端或多个成员 | 分栏、矩阵、主从列表、核对台 | 银行流水与收款单匹配 |
| 聚合/分析 | 看关系集合的分布、路径或贡献 | 分组、图表、树、网络、钻取 | 客户到区域销售贡献、物料谱系 |

关系可以存在但不直接可见。例如系统自动维护的反向引用，可只在删除影响分析或审计中按需展示。是否显示关系由任务决定，关系的真实性和约束则不能因未显示而消失。

### 6.9 聚合根之间的导航模式族

聚合根之间导航的本质是“改变工作上下文”，而不是“打开另一个 URL”。按上下文变化程度，可以区分：

| 导航模式 | 上下文变化 | 适合场景 | 必须保留的信息 |
|---|---|---|---|
| 原位揭示 Reveal | 不改变主对象，只展开目标摘要 | 快速确认少量事实 | 当前焦点、展开位置 |
| 临时窥视 Peek | 暂时查看目标，关闭后继续原任务 | 核对身份、状态、少量历史 | 来源对象、未保存状态 |
| 并列比较 Compare | 两个或多个聚合同时成为上下文 | 匹配、核对、差异决策 | 两端身份、选择和滚动位置 |
| 枢轴切换 Pivot | 目标聚合成为新的工作中心 | 深入调查关联对象 | 来源路径、返回任务、过滤条件 |
| 流程交接 Handoff | 从源聚合发起目标聚合的业务过程 | 订单创建发货、申请开票 | 源标识、交接参数、处理状态 |
| 批量遍历 Batch traverse | 在关联集合中连续处理对象 | 审核队列、异常逐项处理 | 队列、已处理/未处理、返回位置 |
| 分析钻取 Drill | 从汇总逐级进入分组和事实 | 指标解释、根因分析 | 过滤口径、时间范围、维度路径 |
| 外部深链 Deep link | 跳到另一个模块或系统的权威视图 | 目标只能在外部维护 | 身份映射、登录态、返回链接、数据时点 |

选择原则：仅需确认少量事实时用 Reveal/Peek；需要在目标上完成完整任务时用 Pivot；由源触发新的业务责任时用 Handoff。把所有关系都做成详情页跳转，会制造上下文丢失；把所有关系都塞进抽屉，又会把抽屉变成隐蔽的万能页面。

### 6.10 关系映射选择算法

对任意实体关系，依次回答：

```text
1. 这是什么语义关系，而不只是几对几？
2. 两端是否有独立身份和生命周期？关系本身是否也是实体？
3. 谁拥有创建、修改、解除和失效关系的权威？
4. 当前任务是维护、识别、遍历、比较还是聚合该关系？
5. 关系规模、方向、顺序、时间有效性和历史要求是什么？
6. 用户操作是同聚合原子保存、跨聚合命令，还是异步交接？
7. 删除、冻结、冲突、延迟和部分成功时，UI 如何解释与恢复？
```

回答完前四项，才能选结构；回答完后三项，才能判断交互是否安全。

### 6.11 关系映射的反模式与评价

典型反模式：

- 只看外键和基数，不识别组成、引用、责任、时间和关系属性。
- 所有 `N:M` 都生成多选框，导致关系属性和生命周期丢失。
- 用树表达任意关联，暗示不存在的父子关系和继承。
- 在跨聚合页面中提供“全部保存”，掩盖多个事务和部分失败。
- 只提供“能过去”的链接，不保留来源任务、过滤和未保存状态。
- 只展示实时主档，覆盖交易发生时具有法律或业务意义的快照。
- 关系图用于装饰，用户的真实任务仍是查找、比较或批处理。

评价一项关系映射是否良好，至少检查：

1. **语义保真**：用户是否能分辨组成、引用、分类、责任、状态、历史和分析关系？
2. **基数保真**：空、一个、多个、超大集合及重复关系是否都有合理表达？
3. **所有权保真**：用户是否知道在哪里能改、谁负责、何时只读？
4. **时间保真**：当前、历史、计划和交易快照是否被区分？
5. **导航连续**：跨对象后能否回来继续原任务，且上下文不丢失？
6. **失败可解释**：目标停用、权限不足、引用失效、同步延迟和部分成功是否可见？

### 6.12 跨实体视图族完备目录与异常闭环

| 视图族 | 必备模式 | 选择判据 | 主要异常与恢复 |
|---|---|---|---|
| 单实体 | 身份、摘要、详情、创建、编辑、预览、打印、历史 | 深度、风险、可编辑性、是否需历史快照 | 并发冲突、状态禁止、打印快照失效；比较版本或回到权威命令 |
| 实体集合 | 列表、表格、卡片、搜索结果、选择结果、队列、批处理 | 比较维度、视觉差异、集合规模、任务紧迫性 | 分页漂移、选中集失效、部分成功；冻结条件、逐项回执、失败项重试 |
| 状态/过程 | 看板、时间线、步骤、生命周期视图 | 状态流动是否为主任务、是否允许操纵 | 非法迁移、并发抢占、长时处理；说明责任并查询真实状态 |
| 时间/空间 | 日历、甘特、地图、轨迹 | 时间或空间关系是否决定决策 | 时区、重叠、定位精度、数据延迟；标注尺度并允许校正 |
| 分析 | 指标贡献、分组、比较、钻取 | 目标是解释集合而非维护单体 | 口径不一致、刷新延迟、钻取缺项；显示口径与数据时点 |
| 协作 | 活动流、评论、任务、关注 | 多角色围绕对象协同且不改变事实权威 | 通知重复、评论冒充事实、任务失主；区分业务事件与协作记录 |
| 基数 | `1:0`、`1:1`、`1:N`、`N:1`、`N:M` | 实体是否直接暴露、任务是否跨实体 | 身份错配、所有权混淆；稳定标识、来源和权威入口 |

实体级总反模式是把“字段齐全”当“任务完整”。任何实体视图族都必须回答身份、当前事实、合法能力、关系上下文、历史证据和异常恢复中与任务相关的部分；不相关部分可以省略，但不得把省略伪装成不存在。

## 7. 跨层组合、导航和分组

### 7.1 分组有多种语义来源

“放在一起”不等于“属于同一个实体或聚合”。UI 分组至少有以下类型：

| 分组类型 | 来源 | 示例 | 常见 UI |
|---|---|---|---|
| 值对象分组 | 多字段共同构成一个值 | 地址、金额币种、时间范围 | Fieldset、复合控件 |
| 聚合组成分组 | 同一生命周期和一致性边界 | 订单头、订单行 | 主从区域、明细表 |
| 业务主题分组 | 用户对对象的稳定认知主题 | 基本、金额、履约、审批 | Section、页面区域 |
| 任务分组 | 完成任务的阶段和步骤 | 填写、复核、提交 | Step、向导 |
| 状态分组 | 对象当前处理状态 | 待办、异常、完成 | Tab、看板列、队列 |
| 查询分组 | 对集合按维度划分 | 按客户、地区、月份 | Group By、透视表、图表 |
| 权限分组 | 不同角色可见或可操作范围 | 成本信息、敏感资料 | 权限区域、按需披露 |
| 风险分组 | 操作影响和确认等级 | 普通操作、危险操作 | 独立危险区、复核区 |
| 时间分组 | 时间阶段或事件序列 | 今天、逾期、历史变更 | 时间线、日期组、日历 |
| 视觉分组 | 降低认知负担 | 邻近、对齐、共同区域 | 留白、标题、分隔线 |

### 7.2 分组控件的语义不能混用

| UI 结构 | 它应表达什么 | 常见误用 |
|---|---|---|
| Section/Fieldset | 同时可见、语义相关的信息 | 用卡片数量代替真正的信息架构 |
| Tab | 并列、可切换且通常互斥展示的视图 | 把必须同时比较的信息拆开 |
| Accordion | 低频、可按需展开的复杂信息 | 隐藏关键状态或错误 |
| Step/Wizard | 有先后依赖、逐步承诺的任务 | 仅为缩短长表单而强行切步 |
| Tree | 真正的父子或包含层级 | 用树表达普通分类或任意关联 |
| Table Group | 查询结果按维度临时分区 | 把查询分组误认为领域所有权 |
| Kanban/Swimlane | 状态或责任维度下的流动 | 状态并非互斥却强制分列 |
| Card | 一个可独立识别的摘要单位 | 所有页面区域都套成卡片 |

### 7.3 格式塔原则只解决“如何被看成一组”

邻近、相似、共同区域、连续性等格式塔原则可以帮助用户感知分组，但不能决定业务分组是否正确。

正确顺序是：

```text
先确定业务或任务上的组
→ 再选择 Section、Tab、Step 等交互结构
→ 最后用邻近、对齐、标题、留白等视觉手段强化
```

### 7.4 分组冲突的判断方法

一个字段可能同时属于多个分组。例如“信用额度”在领域上属于客户信用，在任务上属于订单审批，在权限上只对特定角色可见。

解决方式不是复制出多个可编辑字段，而是：

- 明确权威来源。
- 在不同任务视图中生成只读投影或编辑入口。
- 保证命名、口径和更新时间一致。
- 通过导航回到权威维护位置。

### 7.5 三个分组测试

1. **语义测试**：用户是否能用业务语言解释为什么这些信息在一起？
2. **任务测试**：用户做出同一个判断时，所需信息是否同时可见？
3. **移动测试**：把该组移到另一位置是否改变业务含义？若不会，它可能只是视觉分组；若会，则可能是结构或任务分组。

## 8. 查询投影与页面模式生成

### 8.1 从领域事实到页面的投影算子

丰富页面不是靠堆组件，而是靠对领域事实执行不同、可解释的投影：

| 投影算子 | 含义 | UI 结果 |
|---|---|---|
| Select | 选择任务需要的字段 | 列表列、详情摘要 |
| Filter | 按条件缩小对象集合 | 筛选、保存视图、队列 |
| Join | 组合相关对象摘要 | 订单显示客户名、库存状态 |
| Sort/Rank | 按优先级组织 | 排序、待办优先级、排行榜 |
| Group | 按维度分组 | 分组列表、看板列、透视表 |
| Aggregate | 汇总多个事实 | KPI、合计、趋势、仪表盘 |
| Derive | 计算新值 | 毛利、可用库存、风险等级 |
| Hierarchize | 形成层级结构 | 树、目录、组织层级 |
| Temporalize | 按时间组织 | 时间线、日历、甘特图 |
| Compare | 同维度并置比较 | 表格、比较矩阵、差异视图 |
| Mask | 按权限脱敏 | 部分隐藏、按需查看 |
| State-trim | 按当前状态裁剪动作 | 可用动作、禁用原因 |
| Contextualize | 补充当前任务上下文 | 来源、范围、责任人、下一步 |

### 8.2 页面模式的生成公式

可以把页面模式写成：

```text
页面模式 =
  数据拓扑
× 任务操作符
× 使用上下文
× 风险等级
× 同步机制
```

其中：

- 数据拓扑：单对象、集合、主从、层级、网络、时间、空间、状态流、指标。
- 任务操作符：查找、比较、录入、选择、审核、核对、调度、监控、分析、协作。
- 使用上下文：角色、频率、熟练度、设备、数据量、响应时限。
- 风险等级：可逆/不可逆、金额、库存、权限、对外影响。
- 同步机制：请求响应、实时更新、乐观更新、异步任务、本地草稿。

### 8.3 同一个订单模型形成多种页面

| 页面 | 主投影 | 主要任务 |
|---|---|---|
| 订单列表 | 集合 + 筛选 + 排序 | 查找、比较、批处理 |
| 订单详情 | 聚合 + 关联摘要 + 历史 | 理解、决策、追溯 |
| 订单录入 | 聚合 + 命令参数 | 创建并守住整体约束 |
| 履约看板 | 状态分组 + 异常 | 监控流动、处理阻塞 |
| 客户 360 中的订单 | 客户关系投影 | 理解客户全局关系 |
| 发货日历 | 时间投影 | 安排和发现冲突 |
| 销售分析 | 聚合 + 维度 + 钻取 | 解释趋势和差异 |
| 审批中心 | 角色 + 待办 + 风险摘要 | 快速判断并执行审批 |

这些页面不是重复建设，而是同一组业务事实针对不同任务的合法投影。

## 9. 系统—模块—功能—页面关系

### 9.1 它们不是同一棵树

系统、模块、功能和页面属于不同语义层：

| 层次 | 回答的问题 | UI 中常见体现 |
|---|---|---|
| 系统 | 哪个完整业务运行环境 | 应用外壳、租户、组织、身份、全局导航、搜索 |
| 模块 | 哪组业务能力和不变量由同一边界负责 | 一级导航、工作区、稳定术语、模块权限 |
| 功能 | 用户能完成什么查询或命令 | 页面、按钮、菜单、批处理、步骤、自动任务 |
| 页面 | 某角色在某上下文中如何完成一次任务 | 路由、工作台、详情、向导、看板、弹窗 |
| 页面区域 | 哪组事实和动作共同支撑一个判断 | 摘要、明细、关系、历史、异常、操作栏 |
| 控件 | 最小显示、输入、选择或命令载体 | 字段、选择器、表格、图表、按钮 |

关系天然多对多：

- 一个模块包含多个能力和用例。
- 一个功能可能由多个页面共同完成。
- 一个功能也可能只是按钮、批处理或后台自动化，不单独占页面。
- 一个页面可以承载多个紧密相关的查询和命令。
- 一个角色工作台可以跨多个模块组合读取。
- 同一聚合根可以出现在不同模块视图和页面中。

### 9.2 应同时维护两张图

```text
业务责任图：
系统 → 业务域/模块 → 业务能力 → 用例 → 查询/命令
                              ↓
                        聚合根/规则/事件

交互交付图：
应用外壳 → 导航/工作区 → 页面/路由 → 页面区域 → 控件/动作
```

两张图通过追踪关系连接，而不是强制逐层一一对应。

核心原则：

```text
模块按业务能力和不变量归属划分；
功能按用户意图和用例划分；
页面按任务闭环划分；
菜单只是一种入口组织，不是业务模型本身。
```

### 9.3 UI 中的多种导航体系

ERP 不应只有“模块菜单”一种入口。成熟系统通常同时存在：

| 导航体系 | 示例 | 服务的心智模型 |
|---|---|---|
| 能力导航 | 销售、采购、库存、财务 | 我在哪个业务责任域工作 |
| 对象导航 | 客户、商品、订单、仓库 | 我要找哪个业务对象 |
| 流程导航 | 报价 → 订单 → 履约 → 结算 | 业务现在走到哪一步 |
| 角色导航 | 销售、仓管、财务工作台 | 我今天要完成什么工作 |
| 事件导航 | 待办、预警、异常、逾期 | 哪些变化需要我响应 |
| 分析导航 | 指标、趋势、驾驶舱、钻取 | 为什么会出现这个结果 |
| 上下文导航 | 相关对象、返回来源、最近访问 | 如何保持当前任务连续 |

### 9.4 跨模块页面何时是合理的

“订单履约工作台”可以读取销售订单、客户信用、库存和物流数据。它跨模块并不天然破坏模块化，因为页面服务的是“判断并完成履约”这一连贯任务。

判断原则是：

```text
跨模块组合读取可以围绕任务；
业务写入仍由各模块的权威命令负责；
页面不能把服务边界泄漏成用户必须手工拼接的步骤。
```

## 10. 第四级：模块间映射模式全集

### 10.1 模块到 UI 的模式族

模块首先是**业务能力、规则权威和责任边界**，其次才可能成为导航分组。一个模块可以没有独立菜单，一个菜单也可能组合多个模块。模块到 UI 的主要模式如下：

| 映射模式 | UI 形态 | 适用条件 | 主要风险 |
|---|---|---|---|
| 独立工作区 | 一级入口、模块首页、局部导航 | 术语、对象、权限和高频任务具有稳定内聚性 | 把组织架构或微服务数量机械变成菜单 |
| 对象中心 | 围绕客户、商品、订单等对象组织列表和详情 | 用户以业务对象识别工作 | 对象跨模块时归属含糊 |
| 能力中心 | 报价、定价、补货、结算等能力入口 | 用户意图比对象类型更稳定 | 能力名过于抽象，用户找不到具体任务 |
| 流程阶段 | 报价、订单、履约、开票等阶段导航 | 端到端流程和交接点是主要心智模型 | 把非线性、可并行流程伪装成固定步骤 |
| 角色工作台 | 销售、仓管、财务、管理者工作台 | 单个角色需跨模块完成连续任务 | 复制各模块规则，形成第二套业务逻辑 |
| 事件/异常中心 | 待办、预警、失败、逾期、冲突队列 | 工作由事件和例外驱动 | 只有消息没有处置上下文和闭环 |
| 查询聚合页 | 跨模块仪表盘、360 视图、联查页 | 决策需要多模块事实同时可见 | 聚合读取被误解为共同事务和所有权 |
| 嵌入式片段 | 其他模块页面中的只读摘要或低风险动作 | 当前任务只需少量外部能力 | 片段逐步膨胀成隐藏的完整模块 |
| 选择/引用服务 | 主数据选择器、统一对象搜索 | 多模块需要引用同一权威对象 | 各模块复制主数据、口径和可选规则 |
| 公共能力入口 | 附件、审批、评论、通知、规则配置 | 能力横切多个模块且契约稳定 | 横切模块侵入业务模型或暴露技术细节 |
| 后台自动化 | 无业务页面，仅有配置、状态或审计 | 功能由规则、事件、计划任务自动执行 | 因“没有页面”而失去可观察性和恢复入口 |
| 管理/控制面 | 模块配置、策略、授权、集成管理 | 低频高风险管理任务 | 与日常业务操作混在一起，权限过宽 |

模块可采用 `1:0、1:1、1:N、N:1、N:M` 的 UI 映射：后台模块可以没有日常页面；一个模块可以产生多个角色视图；一个工作台也可以组合多个模块。正确边界由能力和任务共同决定，不由页面数量决定。

### 10.2 模块间关系的语义模式

模块之间也不只是“调用关系”。不同关系需要不同的 UI 证据和恢复策略：

| 模块关系模式 | 业务含义 | UI 映射 | 不应泄漏给用户的内容 |
|---|---|---|---|
| 主数据供给 | 一个模块维护权威对象，其他模块引用 | 统一选择器、来源摘要、回到主档维护 | 表名、服务地址、复制机制 |
| 规则/策略供给 | 定价、信用、税务、权限等模块提供决策 | 计算结果、规则解释、禁用原因、策略入口 | 内部规则引擎实现 |
| 查询组合 | 多模块事实组合支持一个判断 | 360 视图、工作台、联查、仪表盘 | 多次 API 调用和服务拆分 |
| 命令委托 | 当前模块请求另一模块执行权威命令 | 明确动作、结果状态、目标对象链接 | 把外部字段直接做成本地编辑 |
| 流程交接 | 上游完成后将责任移交下游 | 下一步动作、交接摘要、待办、状态轨迹 | 用户手工复制数据和重复录入 |
| 事件通知 | 模块发布事实变化，其他模块响应 | 活动、通知、处理中/已处理状态 | 消息主题、重试次数等技术术语，除非运维场景 |
| 协同编排 | 一个业务过程协调多个模块命令 | 流程进度、各步骤责任、补偿/重试 | 伪装成单数据库事务 |
| 对账核销 | 模块各自持有事实，需要匹配和解释差异 | 对账台、差异、匹配候选、核销动作 | 用覆盖某一方数据掩盖差异 |
| 分析汇集 | 业务事实进入统一指标和分析语义层 | KPI、维度分析、钻取回业务单据 | 将分析延迟的数据冒充实时交易状态 |
| 横切能力 | 审批、附件、评论、通知作用于多个模块 | 一致的嵌入组件、统一任务中心 | 让横切能力成为所有业务对象的所有者 |
| 扩展/插件 | 模块通过稳定扩展点接收附加能力 | 扩展区、动作插槽、可见来源 | 扩展破坏核心任务布局和命令语义 |
| 迁移/共存 | 新旧模块在一段时间共同承担能力 | 来源标识、只读/可写权威说明、迁移状态 | 同一事实双写但不解释冲突权威 |

### 10.3 跨模块 UI 的组合结构

| 组合结构 | 适用任务 | 边界控制 |
|---|---|---|
| 摘要嵌入 | 只需外部模块少量事实 | 只读为默认，标记数据时点，提供权威入口 |
| 关联导航 | 需要进入外部模块深入处理 | 保留来源上下文和返回路径 |
| 原位委托 | 在当前任务中执行一个明确外部命令 | 命令归属、权限、结果和失败必须明确 |
| 分栏协同 | 需要同时比较或核对两个模块事实 | 两端身份和更新时间并列展示 |
| 流程工作台 | 连续协调多个模块的交接和异常 | 每一步责任、状态、补偿和下一步明确 |
| 统一任务队列 | 角色按优先级处理跨模块待办 | 统一摘要，不统一抹平各模块业务规则 |
| 共享主数据选择 | 引用权威模块维护的客户、商品、组织等对象 | 显示权威来源、可选规则与摘要，不复制维护能力 |
| 事件/通知中心 | 汇聚待办、业务事件、预警和异常 | 区分知会与待处置，保留责任模块和回执 |
| 跨模块搜索/命令入口 | 从统一入口定位对象或发起明确命令 | 搜索可聚合；写命令路由到权威模块并显示归属 |
| 指标汇总与钻取 | 汇总多模块指标并回到事实明细 | 统一口径、数据时点和钻取身份，不假装实时交易视图 |

跨模块页面不应把“每个模块的全部详情”拼成巨页。最小充分原则是：为了完成当前判断，只投影必要事实；需要修改外部模块时，调用其公开命令或导航至其权威工作区。

### 10.4 模块映射质量判据、异常与反模式

1. **能力内聚**：模块入口中的任务是否共享稳定术语、对象和规则，而非只是菜单凑组？
2. **权威唯一**：每个业务事实和命令是否有明确维护模块？同一事实有多个副本时是否标明权威与时点？
3. **任务闭环**：跨模块任务是否能在连贯上下文完成，而非要求用户手工搬运数据？
4. **读写分明**：跨模块组合读取是否与跨模块写入、交接和异步处理清楚区分？
5. **边界适度可见**：正常路径不暴露技术拆分；当权限、时延、部分失败和责任变化影响用户时又能准确说明？
6. **独立演进**：模块内部实现变化但公开语义不变时，其他模块页面是否无需成片修改？
7. **失败可恢复**：下游不可用、事件延迟、交接失败和对账差异是否有状态、责任人和恢复入口？
8. **导航多元**：系统是否同时支持能力、对象、流程、角色、事件和分析入口，而非只有一棵模块菜单树？

模块级反模式包括：微服务一个一级菜单、数据库一个表一个功能、所有跨模块动作都跳页、所有跨模块事实都复制成本地字段、角色工作台复制业务规则，以及用统一外壳掩盖事实口径冲突。

跨模块写入必须显式区分未发起、已受理、处理中、部分成功、完成、失败、超时和已补偿。页面应传递组织、租户和权限上下文，但接收模块仍须重新授权；不能把前端携带的上下文当作可信权限。模块内嵌和深链接要保存来源筛选、选中对象与返回路径，任务结束后责任必须回归维护不变量的权威模块。

模块级不变量是：**读可以围绕任务跨模块组合；写必须回到维护不变量的权威模块。** 部分成功时逐项给出权威回执，失败项用幂等标识重试；跨模块“统一保存”只有在存在明确编排、补偿与责任模型时才成立。

## 11. 第五级：系统间映射模式全集

### 11.1 系统边界到 UI

系统是可以独立运行、部署、治理或承担信任责任的边界。跨系统后会出现模块层没有的新语义：

```text
权威系统与副本
+ 身份和对象标识映射
+ 不同登录与信任边界
+ 网络和对方系统可用性
+ 契约版本与调用限额
+ 同步时延、最终一致性和冲突
+ 跨组织责任、审计和合规
```

因此，跨系统 UI 不能只复用“模块跳转”思路。它必须根据影响程度决定：哪些技术边界对业务用户透明，哪些数据来源、时点、外部处理状态和失败责任必须显式表达。

### 11.2 系统间关系模式总目录

| 系统关系模式 | 业务拓扑 | UI 映射重点 |
|---|---|---|
| 权威源与消费方 | 一个系统维护权威事实，其他系统读取副本 | 来源、更新时间、只读说明、权威详情入口 |
| 请求方与服务方 | 本系统请求外部系统即时完成能力 | 请求参数摘要、等待、成功/失败、可重试性 |
| 异步委托 | 外部系统稍后处理任务 | 已受理、处理中、完成、失败、超时、取消、关联号 |
| 发布/订阅 | 系统通过事件传播事实变化 | 业务状态和响应结果；技术事件细节仅给运维 |
| 双向同步 | 两个系统都可能产生变化 | 同步状态、冲突、胜出规则、人工解决入口 |
| 批量交换 | 定时通过文件或批次交换数据 | 批次、校验、部分成功、错误行、重跑和版本 |
| 门户聚合 | 一个门户汇聚多个独立系统入口或摘要 | 统一身份、导航、来源标识、降级与深链接 |
| 联邦查询 | 实时或近实时查询多个系统 | 每个来源状态、局部失败、数据时点、不可比口径 |
| 跨系统流程 | 一个业务过程经过多个系统和组织 | 全局关联号、阶段、责任方、交接证据、补偿 |
| 身份联邦 | 一个身份在多个系统获得会话和授权 | 登录跳转、授权范围、过期、退出和重新认证 |
| 外部扩展 | 第三方系统嵌入、插件或回调扩展本系统 | 来源、信任提示、授权、隔离、异常退回 |
| 分析汇聚 | 多系统事实进入数仓或分析平台 | 指标口径、刷新频率、血缘、钻回源系统 |
| 新旧共存/迁移 | 两个系统在迁移期共同提供能力 | 哪边可写、对象迁移状态、回退和历史查询 |
| 边缘/离线同步 | 门店、设备或移动端离线运行后同步云端 | 离线状态、待同步队列、冲突、最后成功时间 |
| 人工接力 | 无可靠机器接口，由人完成跨系统交接 | 交接包、检查清单、外部编号、完成确认和审计 |

### 11.3 系统到 UI 的表征模式族

| UI 表征模式 | 用户看到什么 | 适用条件 | 风险控制 |
|---|---|---|---|
| 完全透明集成 | 像本地能力一样得到结果 | 调用快速可靠、失败可被本系统完整处理 | 不得隐藏影响业务决定的数据陈旧或失败 |
| 来源标识投影 | 外部事实及来源、时点、权威链接 | 数据是副本或延迟会影响判断 | 来源不能只是技术系统代码 |
| 外部深链接 | 跳到外部系统权威对象或任务 | 完整能力只能在外部完成 | SSO、对象映射、权限失败和返回上下文 |
| 新窗口/伴随视图 | 保留本系统任务，同时打开外部权威视图 | 需要并行核对、外部系统不可嵌入 | 防止对象错配和窗口上下文混淆 |
| 嵌入远程界面 | 在当前壳中显示外部页面或微前端 | 信任、性能、样式、生命周期契约明确 | 身份隔离、错误边界、加载与版本兼容 |
| 联邦工作台 | 一个任务页面组合多个系统摘要和动作 | 跨系统判断高频且价值高 | 明确来源、局部失败、不可原子保存 |
| 异步处理跟踪器 | 请求进度、外部编号、结果和重试 | 处理时间不可预测或跨组织 | 幂等、取消、超时、重复受理和人工升级 |
| 同步状态面板 | 最后同步、积压、失败对象、重放 | 双向或离线同步对业务可见 | 不只给红绿灯，要给影响和恢复动作 |
| 冲突解决台 | 两边版本、差异、规则建议、选择结果 | 无法自动确定权威值 | 保留证据、审计和可逆性 |
| 对账匹配台 | 两系统事实并列、匹配、核销、差异 | 金额、库存、状态需周期核对 | 不允许简单覆盖差异 |
| 导入/导出向导 | 文件模板、字段映射、校验、执行结果 | 只能批量交换或作为降级路径 | 模板版本、敏感信息、错误行和重复导入 |
| 连接配置/授权页 | 端点、账号、授权范围、健康状态 | 管理员建立集成 | 密钥脱敏、最小权限、测试与撤销 |
| 映射管理页 | 本地对象与外部对象的 ID/编码对应 | 标识体系不同且不能自动匹配 | 唯一性、失效、合并和历史映射 |
| 降级/人工队列 | 自动集成失败后的待处理事项 | 外部系统不可用但业务不能完全停止 | 明确责任、期限、补录和恢复后去重 |
| 外部结果凭证 | 回执、签名、支付结果、物流轨迹、法定文件 | 外部结果具有证据效力 | 保存原始关联号、时间、验证状态和快照 |

### 11.4 系统边界的可见性原则

系统边界是否展示给用户，取决于它是否改变业务语义，而不是工程团队是否拆了服务：

```text
不影响任务含义、时效、责任和恢复
→ 可以透明处理技术边界

影响数据新鲜度、权限、责任方、完成时点、失败恢复或法律证据
→ 必须显式展示业务可理解的来源、状态和后果
```

例如，内部服务拆成五个微服务不应产生五个加载面板；但银行尚未确认付款、门店数据尚未同步、第三方发票平台已受理未开具，则必须成为一等业务状态。

### 11.5 跨系统状态模型

跨系统动作不能只有“成功/失败”。一个通用但需按业务裁剪的状态集合是：

```text
本地草稿
→ 待发送
→ 已发送/已受理
→ 外部处理中
→ 外部完成

异常分支：
发送失败 / 受理不确定 / 外部拒绝 / 超时 / 部分完成
/ 回调丢失 / 本地落库失败 / 数据冲突 / 已取消 / 已补偿
```

UI 需要表达的是这些状态的业务含义、证据和下一步，而不是 HTTP 状态码、消息 offset 或内部异常栈。对于“受理不确定”，不得直接诱导用户重复提交；应先查询外部结果或使用幂等标识恢复。

### 11.6 系统映射质量判据、异常与反模式

1. **权威清晰**：用户能否知道事实由哪个系统维护，本地显示是实时、缓存、快照还是推断？
2. **身份可靠**：本地对象与外部对象是否通过稳定映射关联，而非只靠名称或人工猜测？
3. **时间诚实**：更新时间、同步延迟、处理中和最终确认是否被准确区分？
4. **信任正确**：认证、授权、租户/组织范围和敏感信息是否跨系统保持最小权限？
5. **局部失败**：一个外部来源失败时，页面能否保留其他可用信息，并明确缺失会影响什么？
6. **操作可恢复**：超时、重复提交、部分成功、冲突和回调丢失是否有查询、重试、补偿或人工接管路径？
7. **上下文连续**：深链接或系统切换是否保持对象身份、来源任务和可返回路径？
8. **语义一致**：不同系统对状态、金额、单位、时区和指标的定义是否经过显式映射，而非同名即等价？
9. **证据可审计**：跨系统请求、关联号、回执、人工决定和冲突解决是否可追踪？
10. **降级可用**：外部系统不可用时，是安全阻断、只读降级、排队还是人工处理，是否与业务风险匹配？

系统级反模式包括：用一个统一门户假装数据已经统一；外部失败只显示“系统异常”；同步时间和权威来源不可见；深链接无法定位同一对象；超时后允许盲目重复提交；两边冲突时默认最后写入覆盖；把 iframe 当作集成架构；以及把技术在线状态误当成业务流程已完成。

### 11.7 从系统到 UI 的完整追踪链

对跨系统页面，建议额外维护如下追踪：

```text
用户任务
→ 本地业务对象/命令
→ 外部系统及权威能力
→ 身份与字段语义映射
→ 同步/请求/事件契约
→ UI 来源、状态和动作
→ 超时、重复、冲突和部分成功
→ 重试/查询/补偿/人工接管
→ 业务审计与回执
```

这条链断在任何一处，UI 都可能在“看起来统一”的同时制造事实失真。

## 12. DTRM 正向设计

### 12.1 页面不是数据容器，而是控制回路

一个完整业务页面通常包含：

```text
上下文：我正在处理谁、什么对象、哪个范围
事实：当前已知什么，数据来自哪里、何时更新
判断：什么正常、异常、重要或需要比较
能力：当前状态和权限下可以做什么
命令：用户决定执行什么业务动作
反馈：系统接受、拒绝、处理中还是部分完成
恢复：失败、冲突或中断后如何继续
```

### 12.2 常见页面语法

| 页面语法 | 组合方式 | 适用任务 |
|---|---|---|
| 集合页 | 筛选 + 表格/列表 + 批处理 + 预览 | 查找、比较、批量操作 |
| 对象详情 | 身份 + 摘要 + 分组事实 + 关系 + 历史 + 动作 | 理解、决策、追溯 |
| 主从编辑 | 根字段 + 明细集合 + 汇总 + 整体命令 | 创建或修改聚合 |
| 任务工作台 | 队列 + 当前对象 + 决策信息 + 命令 + 反馈 | 高频连续处理 |
| 状态看板 | 状态分组 + 卡片摘要 + 状态命令 | 监控对象流动 |
| 向导 | 步骤 + 局部校验 + 复核 + 提交 | 多步、高风险、低频任务 |
| 分析页 | 指标 + 维度 + 趋势 + 解释 + 钻取 | 判断差异和原因 |
| 异常中心 | 异常队列 + 证据 + 责任 + 处置 + 恢复 | 处理失败和阻塞 |
| 时间/资源页 | 时间轴 + 资源 + 冲突 + 调度命令 | 排期、预约、调度 |

### 12.3 丰富不等于无边界组合

页面丰富性的合理来源是：

- 同一事实的不同任务视角。
- 多个相关事实的任务型组合。
- 状态、时间、关系和指标的不同视觉编码。
- 针对角色、频率和风险的信息密度调整。

不合理的“丰富”包括：

- 所有对象都做成卡片、Tab 和弹窗的组合。
- 同一页面混入多个无关任务。
- 为了减少页面数而制造万能详情页。
- 用视觉变化掩盖语义和任务结构没有变化。

### 12.4 DTRM 正向设计流程

#### 12.4.1 第一步：建立领域语义图

识别：

- 核心业务名词和稳定身份。
- 实体、值对象和聚合根。
- 关系、基数、方向和生命周期。
- 状态机、业务事件和历史。
- 规则、不变量、权限和租户边界。
- 指标、维度、单位和口径。

产出：领域语义图和关系卡。

#### 12.4.2 第二步：建立角色任务图

对每个角色识别：

- 进入系统的目标。
- 需要回答的问题。
- 需要读取和比较的事实。
- 可以执行的业务命令。
- 任务频率、熟练度和时限。
- 操作风险和异常路径。

产出：角色—任务—场景表。

#### 12.4.3 第三步：分离查询和命令

```text
查询：用户为了判断需要看什么？
命令：用户决定改变什么业务状态？
```

每个命令定义：

- 业务意图。
- 目标聚合根。
- 输入参数。
- 前置状态。
- 权限和数据范围。
- 业务不变量。
- 成功结果。
- 失败、冲突和补偿结果。

#### 12.4.4 第四步：构造任务视图模型

使用选择、连接、分组、聚合、派生、脱敏和状态裁剪等算子，生成“完成当前任务所需的全部且仅有的信息”。

视图模型允许：

- 跨聚合组合读取。
- 为查询反规范化。
- 包含权限和可执行动作摘要。
- 包含来源、版本和更新时间。

视图模型不允许：

- 成为新的业务事实权威来源。
- 绕过聚合根直接写回多个模型。
- 在前端复制最终业务规则。

#### 12.4.5 第五步：选择页面和交互表征

依次选择：

```text
页面模式 → 页面区域 → 分组方式 → 关系表达 → 字段控件
          → 导航方式 → 动作表达 → 反馈和恢复
```

不要反过来从控件库开始拼页面。

#### 12.4.6 第六步：建立双向追踪

核心矩阵：

```text
角色
→ 目标/任务
→ 页面/区域
→ 展示事实
→ 查询来源
→ 用户动作
→ 业务命令
→ 目标聚合根
→ 前置状态
→ 规则/权限
→ 成功反馈
→ 失败恢复
```

#### 12.4.7 第七步：用真实场景验证

至少覆盖：

- 首次创建。
- 正常查看和修改。
- 不同角色和数据范围。
- 每个关键业务状态。
- 空数据、少量数据和大规模数据。
- 并发冲突和数据过期。
- 业务校验失败。
- 异步处理中和部分成功。
- 撤销、补偿或再次提交。

## 13. UI 逆向模型

### 13.1 正确目标：提取可观察领域模型

UI 是领域模型的有损投影。因此从 UI 反向分析的目标不是“猜数据库表”，而是：

```text
UI 证据
→ 可观察业务对象、关系、状态、规则和任务
→ 多个候选模型解释
→ API、导出、文档、数据和运行行为验证
→ 经验证的领域知识
```

### 13.2 UI 线索与候选模型

| UI 线索 | 可以提出的候选解释 | 不能直接断定 |
|---|---|---|
| 稳定业务名词 | 实体、值对象或视图概念 | 一定存在同名表 |
| 编号、编码、稳定链接 | 对象身份和业务键 | 物理主键类型 |
| 字段组 | 值对象、业务主题或视觉分组 | 一定是同一实体或聚合 |
| 重复明细行 | 集合、组成或查询结果 | 一定是子表 |
| 搜索选择器 | 对独立对象的引用 | 真实外键实现 |
| 关联页和跳转 | 对象关系 | 一定跨服务或跨聚合 |
| 状态徽标和条件按钮 | 状态机及合法命令候选 | 全部状态和全部转换 |
| 必填、禁用、错误提示 | 规则、不变量或权限候选 | 后端一定实施相同校验 |
| 时间线和日志 | 事件、审计或历史快照 | 一定采用事件溯源 |
| 合计、毛利、可用量 | 派生值和指标口径候选 | 计算发生在哪一层 |
| 待办、通知、异常 | 异步事件和工作分派 | 消息中间件实现 |
| 导入、导出、同步 | 系统边界和外部契约 | 内部存储结构 |

### 13.3 UI 驱动的领域逆向步骤

1. 盘点系统、模块、菜单、路由和角色入口。
2. 收集同一页面在不同角色和业务状态下的表现。
3. 从稳定名词、编号和详情入口识别候选对象身份。
4. 从字段类型、字段组和重复结构识别值对象、集合和关系。
5. 从选择器、链接、抽屉和关联页识别引用及导航语义。
6. 从按钮、禁用原因和错误提示识别命令、前置条件和规则。
7. 从状态徽标、步骤、看板和历史识别状态机与事件。
8. 从筛选、分组、报表和钻取识别查询维度、指标和事实粒度。
9. 建立候选领域图、状态图、页面投影图和证据矩阵。
10. 用接口、导出、打印、业务文档、数据样本和运行行为交叉验证。

### 13.4 逆向分析的证据矩阵

| UI 证据 | 模型假设 | 其他可能解释 | 置信度 | 最小验证动作 |
|---|---|---|---|---|
| 订单页有可编辑明细行并整体提交 | 订单行属于订单聚合 | 前端批量调用多个独立对象接口 | 中 | 观察接口和部分失败行为 |
| 客户使用搜索选择器并可打开独立详情 | 客户是独立聚合根 | 只是独立查询视图 | 中高 | 检查客户独立生命周期和命令 |
| “审核”仅在已提交状态出现 | 存在状态转换和权限策略 | 纯前端显示规则 | 中 | 直接调用命令验证服务端拒绝逻辑 |

### 13.5 仅凭 UI 无法确认的内容

- 物理表结构和规范化程度。
- 中间表、缓存、物化视图或搜索索引。
- 真实事务边界和锁策略。
- 服务端是否正确鉴权。
- 并发、幂等和租户隔离是否成立。
- 后台任务、消息投递和外部集成实现。
- 隐藏字段、历史数据兼容和迁移策略。

这些必须通过其他证据验证，不能把 UI 推断写成直接事实。

## 14. 质量评判

### 14.1 先过否决门槛

以下任一项失败，都不能称为好映射：

1. **业务语义错误**：身份、金额、单位、基数、状态或指标口径被扭曲。
2. **非法状态转换**：UI 可以绕过命令随意修改状态。
3. **权限错误**：只依赖隐藏按钮，没有服务端鉴权和数据范围控制。
4. **不变量破坏**：金额、库存、审批、租户等核心约束可能失守。
5. **边界伪装**：跨聚合、跨模块写入被包装成无法解释的整体保存。
6. **失败不可恢复**：冲突、超时、部分成功或草稿丢失后只能重来。
7. **来源不可追踪**：关键值和结果无法说明来源、时间和计算口径。

### 14.2 映射不变量

以下规则可作为设计的“守恒定律”：

| 不变量 | 检查问题 |
|---|---|
| 身份守恒 | 同一业务对象在不同页面是否保持稳定身份和名称？ |
| 语义守恒 | 字段换成不同控件后，业务含义是否未改变？ |
| 单位守恒 | 数量、金额、比例、时区和精度是否一致？ |
| 关系守恒 | UI 是否正确表达组成、引用、层级、时间和基数？ |
| 生命周期守恒 | UI 是否避免把独立对象误作从属对象整体删除或保存？ |
| 命令合法性 | 每个动作是否对应合法业务命令和前置状态？ |
| 权威性 | 显示值和写入命令是否指向正确的权威来源？ |
| 往返一致性 | 领域变化能否正确反映到 UI，UI 是否只能产生合法变化？ |
| 来源可追踪 | 派生值、指标和历史是否能追到事实、口径和时间？ |
| 上下文连续 | 跨对象导航后能否返回并继续原任务？ |

### 14.3 质量维度

| 维度 | 好映射的表现 | 可观察证据 |
|---|---|---|
| 语义保真 | 使用业务语言，正确表达对象、关系和状态 | 术语一致、误解率低 |
| 任务闭环 | 页面支持完成完整判断和操作 | 完成率、完成时间 |
| 最小充分 | 决策信息完整但不泄漏无关复杂度 | 无关字段少、查找时间短 |
| 关系可读 | 能区分组成、引用、层级、历史和指标 | 关系误操作少 |
| 状态透明 | 当前状态、允许动作、阻塞原因和下一步明确 | 重复提交和咨询少 |
| 操作局部性 | 判断信息和动作处于同一上下文 | 跨页次数和记忆负担低 |
| 角色适配 | 信息密度和动作匹配角色、频率与风险 | 不同角色效率稳定 |
| 反馈与恢复 | 成功、失败、冲突、处理中均可理解和恢复 | 重做率、草稿丢失率低 |
| 一致性 | 同一概念跨页面同名、同口径、同行为 | 培训和切换成本低 |
| 可追踪性 | 字段和动作可追到来源、规则和责任模块 | 评审与排错速度快 |
| 可演进性 | 新状态或规则只影响可预测的少数位置 | 变更页面数和重复条件少 |
| 存储独立性 | 存储正规化或服务拆分不迫使 UI 改变 | 技术重构对体验影响小 |

### 14.4 六个关键测试

1. **投影测试**：该角色完成任务需要的信息是否全部且仅有？
2. **关系测试**：UI 是否保留当前任务所需的关系、基数和生命周期语义？
3. **命令测试**：每个按钮能否说清业务意图、目标聚合根、前置条件和结果？
4. **往返测试**：领域状态变化能否反映到 UI，UI 动作能否形成合法状态转换？
5. **反事实测试**：数据库正规化或服务拆分变化、业务语义不变时，UI 是否被迫改变？
6. **规模测试**：从 10 条变成 1 万条、从正常状态变成异常状态后，交互结构是否仍成立？

还应补充：

- 角色测试。
- 权限越界测试。
- 并发冲突测试。
- 异步和部分成功测试。
- 新增状态/规则的变化测试。

### 14.5 0–3 分评审量表

在通过否决门槛之后，可以对每个质量维度评分：

| 分数 | 含义 |
|---|---|
| 0 | 映射错误或缺失，用户可能产生错误业务结果 |
| 1 | 能工作但依赖猜测、记忆、跨页拼接或人工补救 |
| 2 | 能稳定完成正常任务，语义和反馈基本清晰 |
| 3 | 正常、异常、角色、规模和演进场景均成立且可追踪 |

不建议把所有页面机械合成一个审美总分。高频运营页应提高效率、密度和上下文连续的权重；支付、审批、库存等高风险页面应提高正确性、权限、可恢复性和审计的权重。

## 15. 反模式

| 反模式 | 表面现象 | 暴露的模型问题 |
|---|---|---|
| 一张表一个页面 | 菜单、表名、页面一一对应 | 存储模型泄漏，缺少任务模型 |
| 字段类型直接生成控件 | Boolean 都是 Switch，Enum 都可编辑 | 缺少业务语义和命令模型 |
| 状态下拉框 | 用户能任意改状态 | 状态机和前置条件缺失 |
| 万能详情页 | 所有关系和功能塞进大量 Tab | 页面边界没有按任务划分 |
| 跨聚合大保存 | 一个保存按钮修改多个独立对象 | 一致性边界和失败语义不清 |
| 前端拼业务规则 | 多接口拼接、前端判断权限和状态 | 查询/命令契约不足 |
| 隐藏即权限 | 看不到按钮就认为安全 | 权限模型未落实到服务端 |
| Tab 等于聚合 | 每个 Tab 被当成实体或服务 | 视觉分组被误当领域边界 |
| Group By 等于所有权 | 报表分组被当成领域层级 | 查询维度与领域关系混淆 |
| 无来源的指标卡 | 数字漂亮但无法钻取和解释 | 指标口径和数据血缘缺失 |
| 只支持正常状态 | 异常时整页报错或数据丢失 | 失败、补偿和恢复模型缺失 |
| UI 状态污染业务状态 | `isExpanded`、当前页等被持久化为业务字段 | UI 模型与领域模型未分离 |
| 元数据无限扩张 | 为特殊页面不断增加配置开关 | 模型驱动边界失控，配置变成第二套代码 |

## 16. ERP 完整案例：销售订单到多种 UI

### 16.1 候选领域结构

```text
Customer（客户聚合根）

Product（商品聚合根）

SalesOrder（销售订单聚合根）
├─ orderNo
├─ customerId              -> Customer 引用
├─ orderDate
├─ currency
├─ status                  -> 状态机
├─ shippingAddress         -> 值对象
├─ lines[]                 -> 聚合内 OrderLine
│  ├─ productId            -> Product 引用
│  ├─ quantity
│  ├─ unitPrice
│  └─ lineAmount           -> 派生值
└─ totalAmount             -> 聚合派生值

Shipment（发货聚合根）
Invoice（发票聚合根）
Payment（收款聚合根）
InventoryAvailability（库存查询模型）
CreditAssessment（信用查询模型）
```

### 16.2 字段映射

| 领域字段 | 语义 | UI 表达 | 关键约束 |
|---|---|---|---|
| orderNo | 稳定业务身份 | 标题、链接、复制 | 创建后通常不可随意修改 |
| customerId | 跨聚合引用 | 异步客户选择器 + 摘要 + 详情导航 | 数据范围、停用状态、信用提示 |
| orderDate | 业务发生日期 | 日期输入/只读事实（依状态而定） | 账期和时区规则 |
| currency | 金额值对象的一部分 | 币种选择或继承客户默认值 | 与价格、税额精度一致 |
| status | 业务生命周期 | 状态徽标 + 可执行动作 | 禁止任意下拉修改 |
| quantity | 精确计量 | 数量输入 + 单位 | 正数、最小单位、库存约束 |
| unitPrice | 单价 | 金额输入或价格来源只读值 | 权限、价目表、精度 |
| totalAmount | 派生值 | 只读汇总 + 计算说明 | 与订单行和优惠口径一致 |
| createdAt | 系统审计时间 | 操作记录/元信息 | 不作为订单业务日期编辑 |

### 16.3 关系与导航映射

| 关系 | 关系语义 | UI 表达 |
|---|---|---|
| Order → OrderLine | 聚合内组成、整体保存 | 可编辑明细表、整体校验和汇总 |
| Order → Customer | 跨聚合引用 | 选择器、摘要、客户 360 导航 |
| OrderLine → Product | 跨聚合引用 | 商品搜索、规格摘要、商品预览 |
| Order → Shipment | 独立下游聚合 | 发货摘要、关联列表、创建发货命令 |
| Order → Invoice | 独立财务聚合 | 开票状态、关联发票、申请开票命令 |
| Order → Inventory | 跨模块查询 | 每行可用量和更新时间，只读 |
| Order → Event | 历史事实 | 时间线、操作者和前后状态 |

### 16.4 页面分组

```text
订单身份与状态
├─ 订单号、客户、订单日期、状态、责任人

订单明细（聚合组成）
├─ 商品、数量、单价、优惠、行金额

金额汇总（派生与风险）
├─ 未税金额、税额、优惠、应收总额

履约与信用（任务决策）
├─ 可用库存、信用状态、交期、阻塞原因

关联业务（跨聚合导航）
├─ 发货单、发票、收款单

历史与审计
└─ 状态事件、操作者、时间、失败记录
```

这些分组来自不同语义：订单明细是聚合组成；金额汇总是派生事实；履约与信用是任务型组合；关联业务是跨聚合导航；历史是事件投影。它们不能因为都显示在一个页面上就被误认为同一个聚合。

### 16.5 同一模型的页面族

```text
订单列表       = 订单集合 + 客户摘要 + 状态 + 筛选 + 批处理
订单详情       = 订单聚合 + 跨聚合摘要 + 历史 + 合法动作
订单录入       = 创建命令参数 + 订单行 + 校验 + 汇总
履约工作台     = 待履约订单 + 库存 + 信用 + 发货命令
审批中心       = 当前审批人待办 + 风险摘要 + 审批命令
发货日历       = 订单/发货的时间投影 + 资源冲突
客户 360       = 以客户为中心的订单关系投影
销售分析       = 订单事实 + 客户/商品/时间维度 + 钻取
异常中心       = 库存不足、信用阻塞、接口失败 + 处置动作
```

### 16.6 示例评审

一个好的履约工作台应满足：

- 读取可以组合订单、库存、信用和发货信息。
- 每个值注明业务时间或更新时间，避免把不同时间截面的数据当成同时事实。
- “创建发货单”是明确命令，而不是直接改订单 `status`。
- 库存不足、信用阻塞和并发变化有可解释反馈。
- 从订单进入客户或库存详情后能返回原处理队列。
- 页面不允许直接修改客户信用、库存余额和发票状态。

### 17.6 设计与评审清单

#### 17.6.1 字段

- [ ] 字段以业务语义而不是数据库类型定义。
- [ ] 单位、精度、空值、来源和更新时间明确。
- [ ] 输入、输出、筛选、派生和命令参数已区分。
- [ ] Boolean、Enum 和状态没有被机械映射。
- [ ] 敏感字段遵守最小披露。
- [ ] UI 校验和服务端最终约束职责清晰。

#### 17.6.2 关系与聚合

- [ ] 关系基数、方向、所有权和生命周期明确。
- [ ] 组成关系与引用关系没有混淆。
- [ ] 带业务属性的多对多关系已建模为关联对象。
- [ ] 聚合边界由不变量决定，而不是由页面分区决定。
- [ ] 跨聚合读取和写入责任已分离。
- [ ] 跨对象导航能保存和恢复任务上下文。

#### 17.6.3 分组与页面

- [ ] 每个分组能说明来源：领域、任务、状态、查询、权限、风险或视觉。
- [ ] Tab、Step、Accordion、Tree 和 Group By 没有混用语义。
- [ ] 页面围绕一个连贯任务，而不是围绕一张表或一个服务。
- [ ] 当前状态、可执行动作、阻塞原因和下一步明确。
- [ ] 正常、空、加载、错误、冲突、异步和部分成功状态完整。

#### 17.6.4 系统架构

- [ ] 系统、模块、功能、页面没有强制一一对应。
- [ ] 模块按业务能力和不变量归属划分。
- [ ] 页面按角色任务闭环划分。
- [ ] 功能既考虑页面入口，也考虑按钮、批处理和自动化入口。
- [ ] 技术服务边界没有直接泄漏给用户。
- [ ] 查询模型和命令模型均有明确权威来源。

#### 17.6.5 质量与验证

- [ ] 已通过语义、状态、权限、不变量、失败恢复等否决门槛。
- [ ] 已运行投影、关系、命令、往返、反事实和规模测试。
- [ ] 重要映射可以双向追踪。
- [ ] 使用真实角色、真实状态和代表性数据量验证。
- [ ] 通过任务完成率、时间、错误率和跨页次数获取实际证据。
- [ ] 新增状态或规则的影响范围可预测。

## 18. 理论边界与参考

### 18.1 适合元数据自动生成的范围

以下场景适合字段和关系元数据驱动：

- 低风险基础资料 CRUD。
- 大量同质列表、详情和简单表单。
- 稳定字段类型、校验、权限和布局。
- 标准一对多明细和简单选择器。

### 18.2 需要任务专用设计的范围

以下场景通常需要专用视图模型和交互：

- 跨聚合、跨模块决策。
- 复杂状态机和审批。
- 高频运营工作台。
- 金额、库存、权限等高风险操作。
- 大规模集合、实时协作和异步过程。
- 指标分析、钻取和异常处置。

### 18.3 AI 和生成式 UI 的边界

AI 可以协助：

- 根据任务选择视图。
- 解释复杂对象和指标。
- 生成查询、摘要或操作建议。
- 在多个合法页面投影之间切换。

AI 不应替代：

- 对象身份和领域语义。
- 权限、租户和数据范围。
- 状态机和业务不变量。
- 高风险命令的确认、审计和幂等。
- 指标口径和权威数据源。

生成式 UI 仍必须在确定性领域模型和命令契约之上工作。

### 18.6 最终压缩

#### 三句话版

1. 数据模型定义业务事实、关系、状态和不变量；UI 根据角色和任务选择性地表达这些语义。
2. 字段、关系、聚合、状态和指标都可以产生多种合法 UI，选择取决于任务、生命周期、权限、规模和风险，而不是数据库类型。
3. 好映射必须语义保真、任务闭环、命令合法、边界清晰、失败可恢复，并能从领域到 UI、从 UI 到业务依据双向追踪。

#### 一句话版

> **数据模型到 UI 的优秀映射，是在不破坏领域语义和业务约束的前提下，为不同角色与任务生成最合适的观察、导航、分组和行动方式。**

## 19. 商业软件 UI 模式语言与行业标杆逆向

### 19.1 为什么“控件和页面大全”仍然不够

前文已经覆盖字段、实体、关系、模块、系统、页面、导航、树/DAG/图等映射层级，但成熟商业软件还必须回答一个更完整的问题：**用户如何在正确业务范围内完成一项可追踪、可恢复、受风险约束的任务。**

```text
进入正确业务范围
→ 找到待处理对象
→ 恢复查询或队列上下文
→ 理解对象、证据和数据时点
→ 编辑或作出业务决定
→ 提交受约束命令
→ 等待同步或异步处理
→ 查看整体与逐项结果
→ 处理校验失败、冲突、例外或部分成功
→ 审计、复用视图并继续下一项
```

（主流共识）复杂商业页面不是由某一张表、某一个对象或某一个控件决定的，而是下列因素共同投影的结果：

```text
商业页面 = ApplicationShell(
  核心页面模式(
    领域事实,
    关系与状态,
    角色任务,
    查询与命令,
    数据规模
  ),
  生产率模式,
  风险治理层,
  运行与恢复层,
  协作责任层,
  设备适配
)
```

这不是把所有能力都塞进一页。它是一种**组合语法**：先确定一个核心页面模式，再按真实约束增加必要的壳层、治理、恢复和协作能力。

#### 19.1.1 标杆逆向的正确分析单位

分析商业软件时，不能只记录“它有列表页、详情页、仪表盘”，也不能从公开 UI 猜测物理表结构。正确的逆向单位是一条可验证映射：

```text
可确认的数据概念
→ 映射算子
→ 可观察 UI 元素
→ 用户任务
→ 优点 / 代价 / 边界
→ 官方证据
```

一条完整记录至少回答：

| 维度 | 要回答的问题 |
|---|---|
| 模型输入 | 是字段、对象、关系、集合、状态、事件、指标、权限还是任务？ |
| 确定性 | 官方文档明确，还是从 UI 反推的可观察领域模型？ |
| 映射算子 | 直接显示、格式化、解码、组合、投影、聚合、导航还是命令？ |
| UI 输出 | 最终成为标题、列、卡片、筛选器、看板列、图表、动作还是反馈？ |
| 任务原因 | 用户是在识别、比较、选择、编辑、决策、追踪还是恢复？ |
| 替代表达 | 同一模型还可以映射成哪些其他 UI？为什么这里不用？ |
| 代价边界 | 当前表达牺牲了什么，在什么规模或任务下应该更换？ |

确定性必须分三层：

1. **官方明确模型概念**：官方文档直接提到 table、field、relationship、resource、project item、status、time series、customer、payment 等。
2. **可观察领域模型推断**：从官方描述的页面和行为可以合理推断对象、关系、状态或命令，但不声称它就是内部代码模型。
3. **不可确认物理模型**：内部表名、主外键、存储格式、索引、服务边界和事务实现；没有源码或 Schema 不能从 UI 下结论。

#### 19.1.2 数据模型到 UI 的十五种基本映射方法

这些方法是可组合的映射算子，不是互斥页面模板。同一字段、对象或集合常同时经过多种算子。

| 编号 | 映射方法 | 输入模型 → UI 输出 | 优点 | 代价 / 缺点 | 适用条件 | 拒绝条件或替代 |
|---|---|---|---|---|---|---|
| M1 | 直接映射 | 原子值 → 文本、输入框、复选框 | 最短、透明、易生成 | 容易泄露存储结构；语义表达能力弱 | 业务值与人类表达近似一致 | ID、状态机、金额、引用不能机械直接映射 |
| M2 | 格式化映射 | 值 → 格式化文本/视觉编码 | 保留值语义并降低阅读成本 | 可能隐藏精度、时区或真实量级 | 日期、金额、百分比、单位、相对时间 | 审计场景必须能查看绝对原值与口径 |
| M3 | 解码映射 | code/ID → 名称、摘要、图标 | 用户按业务概念识别，不接触主键 | 依赖字典/搜索服务；摘要可能过期 | 枚举、外键、状态码、人员与资源引用 | 大候选不用全量下拉；需保留稳定 ID |
| M4 | 分解映射 | 一个复合值 → 多个协作控件 | 各组成部分可分别理解和编辑 | 组合、局部空值与一致性复杂 | 时间区间、地址、经纬度、姓名 | 若整体不可拆分，使用一个专用复合控件 |
| M5 | 复合映射 | 多字段 → 一个 UI 概念 | 更符合人的概念模型，减少碎片 | 需要定义拆分、保存和部分错误 | 金额+币种、客户摘要、库存摘要 | 不能把不同权威来源伪装成一个可整体编辑值 |
| M6 | 派生映射 | 多事实/规则 → 指标、风险、进度 | 快速表达结果和判断线索 | 口径、时点和可解释性成本高 | 合计、完成率、健康度、风险等级 | 派生值不能伪装成直接可编辑事实 |
| M7 | 政策映射 | 状态/权限/规则 → 可见、只读、必填、禁用 | 把约束带入操作界面，减少无效动作 | UI 不是最终安全边界；原因可能不透明 | 条件字段、状态资格、权限裁剪 | 服务端仍须鉴权和校验；高风险要解释原因 |
| M8 | 结构映射 | 类型/关系/任务 → Section、Tab、Step、Tree | 将复杂度组织成可理解结构 | 容易把视觉分组误当业务边界 | 字段分组、流程步骤、层级关系 | 无层级不要用树；无依赖顺序不要强拆向导 |
| M9 | 对象投影 | 实体 → 行、卡片、对象头、选择结果 | 同一身份可适配多任务 | 多投影间可能术语、状态不一致 | 列表识别、详情理解、选择确认 | 必须共享稳定身份与核心状态语义 |
| M10 | 集合投影 | 对象集合 → 列表、表格、看板、日历、路线图 | 同一集合按比较任务切换视角 | 每种投影只擅长部分任务 | 比较字段、观察状态流、安排时间 | 不能把视觉位置当无语义装饰；拖拽须回写字段 |
| M11 | 关系导航映射 | 对象关系 → 嵌入、摘要、链接、主从、树、图 | 保留对象边界并支持到达相关事实 | 返回上下文、权限和加载状态复杂 | 组成、引用、一对多、多对多、层级、多父 | 小组成可嵌入；大集合或独立生命周期对象应跳转 |
| M12 | 状态—命令映射 | 状态机 → 徽标、合法动作、看板列、步骤 | 防止把业务状态当普通枚举任意修改 | 需要前置条件、失败、并发和审计 | 订单、审批、任务、同步生命周期 | 状态下拉只适合无副作用的普通分类字段 |
| M13 | 时态映射 | 当前值+历史/事件 → 时间线、版本 Diff、趋势 | 解释变化、来源和责任 | 事件噪音、时间口径和版本存储成本 | 审计、活动、修订、指标趋势 | 当前快照仍用直接/对象投影；时间线不替代详情 |
| M14 | 查询/聚合映射 | 查询、筛选、维度、度量 → 表格、图表、Dashboard | 服务分析、监控和大规模检索 | 查询状态、指标口径、刷新与权限复杂 | List Report、报表、驾驶舱、Analytical List | 无稳定口径或不能钻回事实时不应可视化 |
| M15 | 运行反馈映射 | 请求/任务/逐项结果 → Loading、进度、回执、恢复中心 | 让延迟、失败和部分成功可理解、可恢复 | 任务身份、幂等、重试和补偿成本 | 异步、跨系统、批处理、离线同步 | 秒级同步不必建任务中心；不可重试错误不显示重试 |

#### 19.1.3 同一个模型为什么会有多种合法 UI

以 `ProjectItem` 集合为例：

| 模型选择 | 映射方法 | UI | 最擅长的任务 | 主要弱点 |
|---|---|---|---|---|
| Item + 多字段 | M9 + M10 | Table | 密集比较、排序、筛选、批量编辑 | 状态流和时间跨度不直观 |
| Item + status | M12 + M10 | Board | 观察流动、WIP、通过拖拽提交状态命令 | 列多或卡片多后失控，精确比较弱 |
| Item + date/iteration | M13 + M10 | Roadmap | 计划、依赖时间、拖动调整日期 | 无日期对象无法合理放置，精确字段少 |
| Item + query | M14 | 保存视图 | 复用某个角色的筛选、分组和排序 | 视图版本、共享权限和字段变更需治理 |

这四种表达不是升级链，也没有一个“最先进”。它们是同一模型按不同任务选择不同字段子集和映射方法形成的**并列投影**。

#### 19.1.4 标杆软件逐元素逆向：数据概念如何成为 UI

##### A. Microsoft Power Apps Model-driven apps

（直接事实）官方明确模型驱动应用由 tables、columns、relationships、forms、views、charts、dashboards 和 navigation 组成。

| 数据概念 | 映射方法 | UI 元素 | 为什么这样映射 | 优点 | 代价 / 替代 |
|---|---|---|---|---|---|
| Table / row | M9 对象投影 | 记录行、对象详情 | 行具有稳定身份，可在集合和单对象任务间切换 | 自动形成一致 CRUD 骨架 | 专业任务可能需要跨表专用工作台 |
| Column | M1/M2/M3 | 表单字段、视图列、筛选项 | 类型和元数据提供控件候选；任务决定显示位置 | 高度可生成、跨设备一致 | 仅靠类型不能推导高风险命令和复杂复合字段 |
| Relationship | M11 | 关联导航、相关记录、查找选择器 | 关系既用于编辑引用，也用于记录间导航 | 对象关系可直接发现和到达 | 大集合、权限裁剪和返回上下文仍需设计 |
| View/query | M10/M14 | 记录列表、列、排序和筛选 | 同一表按角色/任务选择不同字段和记录集 | 一个模型形成多任务投影 | 保存视图、数据量和查询性能需要治理 |
| Chart/Dashboard | M6/M14 | 图表和仪表盘 | 对视图结果聚合和视觉编码 | 从明细快速发现趋势 | 指标口径和钻回明细必须明确 |
| Security role | M7 | 可见页面、字段、动作范围 | 权限模型裁剪可见数据和能力 | 生成 UI 与安全角色协调 | UI 隐藏仍不能替代服务端授权 |

边界：官方证明其元模型和页面构成，不证明任意复杂业务都应自动生成，也不公开内部物理表实现。

#### 19.1.5 如何比较同一模型的不同映射方法

不要问“哪个 UI 最好”，而要问“哪个映射在当前任务中损失最少”。统一比较六项：

| 判据 | 关键问题 |
|---|---|
| 语义保真 | 类型、单位、身份、关系、状态和来源是否仍准确？ |
| 任务效率 | 用户是在读、比、找、选、改、批、审还是解释？该 UI 是否针对该操作？ |
| 规模适应 | 1 个、10 个、1 万个对象时是否仍成立？ |
| 状态完整 | 空、加载、无权限、旧数据、冲突和部分成功是否可表达？ |
| 风险控制 | 命令的影响、权限、前置条件、审计和恢复是否明确？ |
| 实现成本 | 查询模型、状态同步、无障碍、响应式和维护复杂度是否值得？ |

选择规则可以压缩为：

```text
先用最朴素且语义正确的映射
→ 用代表性任务和数据量验证
→ 发现具体覆盖缺口
→ 叠加最小必要映射算子
→ 保留原映射在其擅长的场景
```

### 19.2 八个朴素事实：商业 UI 为什么必然出现

先暂时忘记表格、看板、工作台、仪表盘等模式名称，从最朴素的事实出发：

1. **事实本身不可见**：数据库中的值不会自动进入人的认知，所以最早的 UI 只是“标签 + 格式化值”。
2. **人不仅要看，还要改变事实**：一旦允许修改，就从文本演进出输入控件、校验、保存和反馈。
3. **人的注意力有限**：字段和对象增加后，不能全部平铺；必须出现分组、摘要、渐进披露和任务投影。
4. **对象有身份，关系有含义**：数据不再是孤立值后，需要对象头、详情、列表、相关对象和导航。
5. **改变事实必须守住规则**：金额、库存、权限和状态不能任意改值，所以输入控件会演进成受约束业务命令、事务编辑器和审批动作。
6. **数量改变交互方式**：一个对象可以平铺，十个需要列表，一万个需要查询、分页和保存视图，百万级还需要服务端搜索、虚拟化和后台批处理。
7. **时间、多人和外部系统会制造不确定性**：加载、旧数据、并发冲突、异步、部分成功和离线不是异常边角，而是正常业务状态空间。
8. **风险越高，越需要证据和责任**：不可逆或高影响操作会自然产生影响预览、原因、复核、职责分离、审计、版本和恢复模式。

因此，商业 UI 不是设计师凭空发明的一组样式，而是**人在有限注意力下观察并安全改变复杂业务事实时，被约束一步步逼出来的交互结构**。

### 19.3 统一演进机制：新模式从原模式的适用边界之外长出来

任何 UI 模式的演进都可以用同一条链解释：

```text
原始业务问题
→ 最朴素可行 UI
→ 新约束出现
→ 原模式没有负责覆盖的新问题出现
→ 引入新 UI 模式
→ 新模式解决主要矛盾
→ 同时引入新的状态、成本和边界
→ 下一轮约束继续推动演进
```

可以形式化为：

```text
P(n+1) = Evolve(P(n), Pressure)

Pressure =
  数据量增长
  + 关系复杂度增长
  + 状态与时间增长
  + 任务频率增长
  + 角色与责任增长
  + 并发与延迟增长
  + 风险与合规增长
  + 设备与环境变化
```

演进不是“旧设计错误，新模式全面取代旧模式”。旧模式在原约束下仍然正确，甚至仍是成本最低、认知最直接的最佳方案。例如：一个 Boolean 设置仍适合使用开关；只有当它承载高风险业务状态时，才需要在开关之外引入原因、权限、确认和审计。**新模式扩大了可处理的问题范围，也扩大了实现和认知成本；原模式仍保留在它擅长的局部。**

#### 19.3.1 六种演进关系：不是单线替换

| 演进关系 | 朴素含义 | 例子 | 原模式是否保留 |
|---|---|---|---|
| 语义细化 | 同一种表达根据数据语义变得更精确 | 文本框 → 数字框、日期选择器、对象选择器 | 保留；自由文本仍用于真正开放的文本 |
| 结构组合 | 多个原子模式组成一个更完整任务结构 | 字段控件 + 分组 + 明细表 + 合计 → 事务编辑器 | 保留；原子控件仍是组成部分 |
| 任务分化 | 同一数据因任务不同产生并列投影 | 订单集合 → 表格 / 看板 / 日历 / 路线图 | 全部并存，没有唯一“高级版” |
| 横切叠加 | 在原页面上增加状态、权限、审计或协作层 | 列表 + 保存视图 + 批处理 + 部分成功回执 | 保留；列表仍是核心读取结构 |
| 规模升级 | 数据量或频率变化后更换访问机制 | 下拉 → 搜索选择；静态列表 → 分页/虚拟化工作台 | 小规模时继续使用原模式 |
| 媒介适配 | 同一任务因设备和环境改变表达 | 桌面高密度表格 → 移动任务卡 + 单项处理 | 按设备并存，而不是互相替代 |

因此，“演进”更像一棵模式分化树和一套组合语言，而不是版本号从 V1 线性升级到 V2：

```text
原模式
├─ 在原场景继续使用
├─ 按新语义细化
├─ 与其他模式组合
├─ 因任务不同分化成并列投影
└─ 叠加规模、状态、治理和设备适配层
```

#### 19.3.2 演进时必须保持的不变量

无论 UI 变得多复杂，以下语义不能在演进中丢失：

- 同一个对象仍有稳定身份。
- 同一个业务值仍保留类型、单位、精度和空值含义。
- 关系的方向、基数、所有权和生命周期不被视觉布局扭曲。
- 状态只能通过合法命令迁移。
- 权限、租户、数据范围和服务端校验仍然生效。
- 查询摘要、指标和 AI 建议不能冒充权威业务事实。
- 异步、失败、冲突和部分成功必须能回到明确责任和恢复动作。

#### 19.3.3 判断是否需要扩展，而不是盲目升级

只有使用范围扩展后出现原模式没有负责覆盖的新问题，才引入下一模式：

```text
旧模式仍能让目标用户正确、高效、安全地完成任务
→ 保留旧模式

使用范围扩展后出现新的数据量、状态、权限或恢复问题
→ 明确原模式的适用边界和新增覆盖缺口
→ 只增加解决该缺口所需的模式，同时保留原模式擅长的部分
```

这能避免两种错误：一是复杂业务仍停留在“表格 + 表单”；二是简单业务为了显得高级而堆叠工作台、设计器和仪表盘。

### 19.4 十条从朴素 UI 到商业软件模式的演进链

#### 19.4.1 一个值：文本 → 语义字段 → 复合字段

```text
原始问题：让人看见或输入一个值。
朴素方案：标签 + 文本；需要修改时加文本框。
新增约束：出现类型、单位、范围、精度、候选集和空值语义。
覆盖缺口：自由文本不负责限制类型，也无法独立解释金额、日期、引用和状态。
演进方案：数字框、增减器、日期选择、金额+币种、对象选择器、状态徽标。
新增代价：控件需要校验、格式、键盘、无障碍和本地化策略。
继续演进：多个字段共同维护一个业务不变量时，进入事务表单。
```

#### 19.4.2 一组字段：平铺表单 → 分组表单 → 事务编辑器 → 向导

```text
原始问题：一次录入一个对象的若干属性。
朴素方案：字段从上到下平铺，点击保存。
新增约束：字段增多、主从明细、派生合计、跨字段规则、草稿和并发出现。
覆盖缺口：平铺表单不负责步骤引导、跨区错误定位、草稿恢复和整体不变量。
演进方案：语义分组 + 错误摘要 + 明细表 + 草稿 + 事务编辑器。
新增代价：Dirty、离开拦截、草稿版本、冲突合并和计算解释。
继续演进：任务低频、步骤有依赖且一次展示认知负担过高时，演进为可恢复向导。
```

向导不是“长表单的自动升级”。如果步骤可以任意顺序完成或用户需要频繁跨区比较，分组表单比向导更合适。

#### 19.4.3 一个对象：详情表 → 对象页 → Object 360

```text
原始问题：查看一个对象的完整信息。
朴素方案：键值详情表。
新增约束：对象有稳定身份、状态、合法动作、关联对象、历史和风险。
覆盖缺口：键值表擅长准确读值，但不负责回答“这是谁、现在怎样、能做什么、为何如此”。
演进方案：对象身份头 + 状态 + 摘要 + 合法动作 + 相关列表 + 活动/审计。
新增代价：信息容易膨胀；跨聚合读取和写入边界容易混淆。
继续演进：关系和角色继续增加时，形成角色化 Object 360；大关联集合拆入独立列表。
```

#### 19.4.4 多个对象：列表 → 数据表 → List Report → 集合工作台

```text
原始问题：从多个同类对象中找到一个。
朴素方案：名称列表。
新增约束：需要比较多字段、排序、筛选、分页、保存查询和批量操作。
覆盖缺口：简单列表擅长浏览少量对象，但不负责多字段对齐、大规模查询、上下文恢复和批量范围。
演进方案：数据表 → List Report → 保存视图、列设置、跨页选择和批处理工作台。
新增代价：URL 状态、查询快照、虚拟化、逐项鉴权和部分成功回执。
继续演进：主要任务若变成状态流动，演进为看板；若变成责任处理，演进为 Worklist。
```

#### 19.4.5 状态变化：状态文本 → 合法动作 → 看板 → 工作流/审批

```text
原始问题：让用户知道对象当前处于什么状态。
朴素方案：显示状态文本或下拉框。
新增约束：状态转换有前置条件、副作用、权限、责任人和时限。
覆盖缺口：下拉框适合普通枚举选择，但不负责状态命令的前置条件、副作用、审计和流程责任。
演进方案：状态徽标 + 当前合法动作；集合需要观察流动时使用看板。
新增代价：拖拽必须回写明确状态命令，并处理失败、并发和权限。
继续演进：出现领取、转派、会签、退回、SLA 和证据时，演进为 Worklist / Approval Workspace。
```

#### 19.4.6 页面之间：链接 → 返回契约 → 应用壳 → 多任务工作区

```text
原始问题：从页面 A 到页面 B。
朴素方案：超链接和浏览器返回。
新增约束：来源列表有筛选/页码/焦点；系统有组织、环境、角色、通知和全局任务。
覆盖缺口：普通链接负责到达目标，但不负责恢复复杂来源上下文、业务范围和深链重新鉴权。
演进方案：可寻址路由 + 返回契约 + 面包屑/对象导航 + Application Shell。
新增代价：范围切换必须重算权限、查询和草稿；壳层占据空间。
继续演进：用户需要并行核对多个长任务时，演进为多标签/分栏 Multi-task Workspace。
```

#### 19.4.7 层级关系：缩进列表 → 树 → TreeGrid → DAG/图

```text
原始问题：表达父子层级。
朴素方案：缩进列表。
新增约束：需要展开、搜索、选择、移动、属性比较、懒加载和权限继承。
覆盖缺口：缩进列表适合静态小层级，但不负责持久展开、搜索、移动和多列属性比较。
演进方案：Tree → Tree Select / Cascader → TreeGrid。
新增代价：半选、未加载后代、防环、移动并发和路径恢复。
继续演进：同一节点出现多个父级时，树的不变量失效，演进为 DAG 或“主路径树 + 其他父引用”；出现环时使用一般图。
```

#### 19.4.8 等待和失败：Spinner → 进度 → 后台任务 → 异常恢复中心

```text
原始问题：操作不能立即完成。
朴素方案：Spinner 和“请稍候”。
新增约束：处理时间变长、用户可离开、批量项可独立成功、外部系统会超时。
覆盖缺口：Spinner 适合短等待，但不负责长任务受理、阶段进度、离开后查找和结果恢复。
演进方案：阶段进度 + 任务号 + Background Job。
新增代价：需要持久任务、取消语义、幂等键、尝试历史和通知。
继续演进：失败分类、部分成功、补偿和人工接管增加后，演进为 Exception / Recovery Center。
```

#### 19.4.9 权限和规则：隐藏按钮 → 角色矩阵 → 有效权限 → 治理设计器

```text
原始问题：某些人不能做某些事。
朴素方案：隐藏或禁用按钮。
新增约束：出现角色、组织范围、字段/数据权限、继承、Allow/Deny、多角色和职责冲突。
覆盖缺口：隐藏或禁用按钮可以降低无效操作，但不负责解释有效权限，也不能替代服务端鉴权。
演进方案：角色权限矩阵 + 范围树 + 有效权限解释。
新增代价：必须显示配置来源、合并优先级和影响范围。
继续演进：规则可配置、需模拟/版本/发布/回滚时，演进为 Permission / Rule Governance Designer。
```

#### 19.4.10 汇总决策：总数 → 图表 → Dashboard → Analytical List

```text
原始问题：了解整体结果。
朴素方案：显示总数或汇总表。
新增约束：需要趋势、维度比较、时间窗口、目标、异常和数据时点。
覆盖缺口：总数适合快速读值，单图适合表达单一关系；它们不负责多指标口径、联动筛选和行动出口。
演进方案：图表 → Dashboard / Cockpit。
新增代价：指标口径、刷新时间、局部数据源失败和行级权限必须可见。
继续演进：用户需要从异常直接进入对象集合并处理时，演进为 Analytical List；开放探索则进入 Report / Exploration。
```

### 19.6 从标杆表象校验演进规律

#### 19.6.1 跨产品稳定规律

1. **应用壳是业务上下文控制器**：账户、组织、环境、模块、全局搜索、最近访问、通知和后台任务共同决定“用户当前在哪个业务范围工作”。
2. **同一模型需要多投影**：表格服务密集比较，Board 服务状态流，Roadmap 服务时间计划，Dashboard 服务指标决策，详情页服务对象理解与命令。
3. **资源集合与资源详情是骨架，不是终点**：成熟产品会叠加保存视图、批处理、360 关系、审计、沙盒、错误恢复等能力。
4. **状态页面是一等模式**：Loading、Empty、Result、Exception、Saving feedback 反复出现在多个设计系统中；正常态只占状态空间的一部分。
5. **视觉操作必须有领域回写语义**：拖动卡片不是改变位置，而是提交状态命令；拖动时间条不是装饰，而是修改日期或迭代字段。
6. **高风险操作需要有意摩擦**：影响预览、原因、二次确认、审批、审计和恢复策略取决于不可逆性，不能统一套一个确认框。
7. **响应式是任务重组**：窄屏下高密度工作台应转为队列卡片与单项处理，而不是把桌面表格压扁。
8. **AI 是横切建议层**：它可以帮助搜索、摘要和建议，但不得绕过权限、状态机、数据时点和人工确认。

#### 19.6.2 不能机械迁移的产品特例

- Datadog 的自由画布适合监控诊断，不适合作为金额、订单或权限录入页的默认布局。
- GitHub Board 的拖拽适合状态可视化，但高风险状态仍需服务端前置条件、权限和并发校验。
- 模型驱动应用适合结构化、流程驱动场景；跨聚合决策、高风险操作和专业工作台仍需任务专用设计。
- 支付产品的组织、沙盒和审计壳层是高价值参照，但不能照搬其领域对象或信息层级。
- 设计系统模式说明“如何保持一致”，不能替代具体产品的领域建模和用户研究。

### 19.7 八族二十四种商业软件模式总谱

| 模式族 | 模式 | 映射输入 | 主要页面输出 | 核心收益 | 主要代价或拒绝条件 |
|---|---|---|---|---|---|
| 应用壳层 | Application Shell | 租户/组织/环境/角色 + 模块图 | 全局头、侧栏、业务范围切换、搜索、通知 | 稳定定位与跨模块发现 | 单模块小工具不必建立重壳；切换范围必须处理草稿和权限失效 |
| 应用壳层 | Role Home / Launchpad | 角色目标 + 高频入口 + 指标/待办摘要 | 岗位首页、快捷动作、最近访问 | 缩短进入高频任务路径 | 不能把所有模块卡片堆成门户；低频角色不值得专页 |
| 应用壳层 | Multi-task Workspace | 并行对象 + 长任务 + 来源上下文 | 多标签/分栏工作区、草稿状态 | 支持核对和任务切换 | 移动端、低频任务和强单线程流程不适合；需处理多标签冲突 |
| 集合与生产率 | Resource Index / List Report | 同构对象集合 + 结构化筛选 + 比较 | 表格/列表、筛选、排序、保存视图 | 密度高、可定位、可批量操作 | 项目少且视觉差异大时卡片更合适；必须定义选择范围 |
| 集合与生产率 | Worklist / Queue | 待处理任务 + SLA + 责任和优先级 | 队列、领取/释放、下一项 | 连续处理效率高 | 无明确责任或任务不可排序时不应伪装成队列 |
| 集合与生产率 | Board / Schedule / Roadmap | 状态或时间维度 + 可回写字段 | 看板、日历、时间线、路线图 | 流动与计划直观 | 没有单值状态/时间字段、拖拽风险高或规模过大时拒绝 |
| 对象与交易 | Object Page / 360 | 稳定对象身份 + 关系 + 生命周期 | 对象头、摘要、相关列表、时间线、动作 | 在一个对象上下文中理解事实和关系 | 不得形成跨聚合大保存；超大关系集进入独立页 |
| 对象与交易 | Transaction Editor | 聚合根 + 明细 + 跨字段不变量 | 事务表单、明细表、草稿、错误摘要 | 维护整体一致性 | 纯查询或独立对象批量编辑不适用；必须有并发与离开契约 |
| 对象与交易 | Comparison / Reconciliation | 两组或多组记录 + 匹配规则 + 差异 | 并排比较、匹配、差异解释、处置 | 把差异变成可审核决策 | 数据不可比、口径不一致或自动匹配不可解释时拒绝自动处置 |
| 工作流与队列 | Approval / Case Workspace | 流程实例 + 证据 + 合法命令 + 责任人 | 任务详情、证据、通过/退回/转派 | 决策有依据、有责任和审计 | 不应允许任意编辑状态；无业务决策时不必引入审批 |
| 工作流与队列 | Wizard / Guided Process | 有依赖顺序的复杂输入 + 可恢复步骤 | 步骤导航、分段校验、草稿 | 降低一次性复杂任务认知 | 步骤可自由完成或频繁往返时会增加阻力 |
| 工作流与队列 | Operations Console | 多对象实时状态 + 异常 + 调度命令 | 运行表、时间轴、告警、控制动作 | 监控与干预形成闭环 | 非实时、低频后台任务用普通列表即可 |
| 分析与决策 | Analytical List | 明细集合 + 指标 + 维度 + 筛选 | 指标摘要 + 图表 + 可钻取明细 | 分析与行动在同一筛选上下文 | 指标口径不稳定或不能钻回明细时会误导 |
| 分析与决策 | Dashboard / Cockpit | 多指标 + 时间窗口 + 目标/阈值 | 网格或时间同步驾驶舱 | 快速发现异常与趋势 | 指标过多、时点不一致或无行动出口会成为装饰墙 |
| 分析与决策 | Report / Exploration | 语义层 + 维度/度量 + 查询历史 | 透视、分组、钻取、订阅、快照 | 支持重复和开放分析 | 正式监管报表与探索式分析不可混为同一保存语义 |
| 协作与责任 | Activity / Timeline | 业务事件 + 评论 + 审计 + 时间 | 活动流、事实时间线、评论区 | 恢复上下文和责任线索 | 评论不能冒充业务事实；不同事件源需标识 |
| 协作与责任 | Assignment / Handoff | 请求者、责任人、承诺、交付物、回执 | 指派、认领、交接检查和验收 | 责任闭环可追踪 | 只有聊天而无责任状态时不能称为交接 |
| 协作与责任 | Notification Center | 事件 + 订阅 + 优先级 + 确认要求 | 通知、待办、提醒、已读/确认 | 异步触达并回到任务 | 不能用通知代替任务队列；需去重和关闭反馈 |
| 治理与高风险 | Permission / Scope Designer | 主体 × 资源 × 动作 × 范围 × 继承 | 权限矩阵、范围树、有效权限解释 | 变更可预览、可解释、可审计 | 单纯复选框不能表达 Deny、继承、多角色合并和职责冲突 |
| 治理与高风险 | Rule / Configuration Designer | 条件、动作、优先级、版本和依赖 | 规则构建器、模拟、测试、发布 | 把配置变化变成可验证发布 | 低频简单参数无需设计器；无版本/测试时风险过高 |
| 治理与高风险 | Audit / Version Workspace | 版本、事件、操作者、Diff、有效期 | 审计时间线、版本比较、恢复/回滚 | 解释谁何时为何改变什么 | 日志不完整或回滚不安全时不得提供虚假“恢复”按钮 |
| 集成与恢复 | Import / Export Workbench | 文件/查询集合 + 映射 + 校验 + 权限 | 导入向导、预览、逐行结果；后台导出 | 批量交换可预检、可回执 | 小量手录不必导入；敏感导出需独立权限、水印和审计 |
| 集成与恢复 | Background Job / Exception Center | 异步任务 + 批次 + 错误分类 + 重试能力 | 进度、日志、失败项、仅重试失败项 | 长任务不中断前台，失败可恢复 | 不可重试错误不能显示通用重试；需明确幂等和取消语义 |
| 集成与恢复 | Sync / Conflict Resolver | 多来源版本 + 权威规则 + 冲突字段 | 同步状态、三方比较、采用/合并/推迟 | 最终一致过程对用户可见 | 无来源证据或不可逐字段合并时只允许重新加载/人工升级 |

### 19.8 模式选择函数：从数据形状到商业页面

```text
Pattern = choose(
  task,            // 找、比、录、批、审、调度、解释、配置
  objectTopology,  // 单对象、集合、聚合、层级、流程、跨系统
  stateMachine,    // 状态数量、合法命令、责任流转
  volume,          // 候选数量、行数、更新频率、并发编辑者
  risk,            // 可逆性、金额/权限/合规影响
  latency,         // 同步、异步、离线、最终一致
  collaboration,   // 责任、评论、交接、共同编辑
  device           // 桌面、移动、触控、键盘密度
)
```

#### 19.8.1 快速决策树

```text
任务核心是“找一批同构对象并比较”吗？
├─ 是 → Resource Index / List Report
│       ├─ 按责任和 SLA 连续处理 → Worklist
│       ├─ 按状态流动 → Board
│       └─ 指标判断后下钻 → Analytical List
└─ 否
    ├─ 围绕一个稳定对象理解全貌 → Object Page / 360
    ├─ 一次命令需维护主从整体不变量 → Transaction Editor
    ├─ 需要基于证据作流程决定 → Approval / Case Workspace
    ├─ 两套事实需要匹配并解释差异 → Reconciliation Workbench
    ├─ 大批量或长时间执行 → Import / Background Job
    ├─ 修改规则、权限或产品行为 → Governance Designer
    └─ 多指标发现异常并下钻 → Dashboard / Cockpit
```

#### 19.8.2 组合规则

正确组合示例：

```text
支付运营台
= Application Shell（账户/环境）
+ Resource Index（交易集合）
+ Object 360（客户/付款上下文）
+ Command Risk（退款影响与原因）
+ Background Job（批量导出）
+ Audit（活动日志）
```

```text
订单审批中心
= Application Shell（组织/角色）
+ Worklist（责任和 SLA）
+ Approval Workspace（证据与命令）
+ Object 360（订单关系）
+ Activity（业务事件和评论分离）
+ Conflict/Recovery（过期、冲突、重试）
```

组合限制：一个页面应有一个主任务和一个主要提交边界。可以跨聚合读取证据，但不能因为都在同屏就把多个聚合合并成一个任意保存事务。

### 19.9 商业页面的状态空间必须显式建模

每个核心模式至少要回答下列状态，而不是只设计“有数据且网络正常”：

| 状态 | 与其他状态的区别 | 页面必须给出的信息与动作 |
|---|---|---|
| 首次加载 | 尚无可用内容，可能没有旧快照 | 加载范围、骨架稳定性、取消或超时反馈 |
| 增量刷新 | 已有内容仍可读，正在获取更新 | 数据时点、后台刷新标记，不阻断当前任务 |
| 真空数据 | 当前业务范围内确实没有对象 | 为什么为空、首个创建或导入动作 |
| 筛选无结果 | 数据可能存在，只是条件不命中 | 当前条件、清除/修改筛选，不显示“去创建”误导 |
| 无权限 | 对象可能存在但不可披露或操作 | 可安全披露的原因、申请权限或返回，不泄露敏感事实 |
| 对象失效 | 已删除、归档、迁移或链接过期 | 最后已知身份、状态、回到来源或查找替代对象 |
| 数据过期 | 读到旧版本，尚未必发生写冲突 | 版本/时点、刷新；不得静默覆盖 |
| 网络/服务错误 | 请求未完成或依赖失败 | 失败范围、可否重试、已保存内容和关联号 |
| 校验失败 | 命令已被业务规则拒绝 | 错误摘要、字段/行定位、如何修正 |
| 并发冲突 | 当前提交基于旧版本 | 我的版本、最新版本、基线差异，以及重载/合并/放弃 |
| 异步处理中 | 命令已受理但结果未定 | 任务号、进度、可否离开、取消和结果入口 |
| 部分成功 | 批量项结果不同 | 成功/失败/跳过数量、逐项原因、只重试失败项 |
| 离线待同步 | 本地已接受但权威系统未确认 | 本地队列、最后同步、冲突策略和撤销限制 |

### 19.10 十个核心模式深拆

下面统一用“业务问题 → 模型与任务 → 页面/导航 → 命令与状态 → 权限风险 → 优缺点与边界 → 验收”的结构拆解。配套 HTML 第 07 节提供这些模式的交互原型和状态切换。

#### 19.10.1 Application Shell：应用外壳与业务范围

- **业务问题**：用户先要确认“我在哪个账户、组织、门店、账套、环境和角色下工作”，再进入对象任务。
- **模型与任务**：Tenant/Organization/Environment/Role/Module/RecentItem/Notification/Job；任务是定位、切换范围、全局发现和恢复最近工作。
- **页面与导航**：全局头 + 主导航 + 业务范围切换 + 全局搜索/命令面板 + 最近/收藏 + 通知/待办/后台任务。模块导航、对象导航、流程导航和浏览历史互相正交。
- **命令与状态**：切换范围不是普通下拉选择；必须重算菜单、权限、查询、当前对象、保存视图和草稿适用性。
- **权限风险**：隐藏菜单不等于服务端授权；切换后旧标签和深链接需要重新鉴权。生产/沙盒、法人/门店等高风险上下文要持续可见。
- **优点**：形成稳定空间心智，降低跨模块查找和错范围操作。
- **缺点/拒绝条件**：壳层过重会吞噬内容空间；单模块、单租户、短流程工具可用轻壳。
- **验收**：切换组织后无越权旧数据；未保存草稿有明确保留/丢弃/迁移结果；浏览器前进后退与深链可恢复上下文。

#### 19.10.2 Resource Index / List Report：高级集合工作台

- **业务问题**：在数十到数百万个同构对象中查找、比较、分组、选择和批处理。
- **模型与任务**：查询投影 + 稳定行身份 + 筛选/排序/分组 + 用户视图偏好 + SelectionSet。
- **页面与导航**：搜索、结构化筛选、分面、保存/共享视图、列配置、密度、表格/列表、分页或虚拟化；进入详情后返回要恢复 URL、页码/游标、滚动和焦点。
- **命令与状态**：“选择本页”与“选择符合条件的全部 12,438 条”必须分开；批处理要冻结查询快照或明确执行时重新求值。
- **权限风险**：导出当前页、选择集和全部查询结果是三种不同授权与审计事件；批处理需要逐项鉴权。
- **优点**：密度高、重复任务效率高、可形成岗位视图。
- **缺点/拒绝条件**：小集合、强视觉对象或每项结构差异大时卡片更好；移动端应转为任务卡片和单项处理。
- **验收**：大数据下无全量加载；返回上下文准确；部分成功逐项回执；数据刷新后选择集语义不含糊。

#### 19.10.3 Object Page / 360：对象工作空间

- **业务问题**：围绕一个稳定身份对象理解当前状态、关键事实、风险、关系、历史和合法动作。
- **模型与任务**：聚合根身份 + 查询型跨聚合摘要 + 生命周期 + 关系集合 + 活动事件。
- **页面与导航**：对象身份头、状态/关键指标、合法动作、事实分区、相关列表、活动/审计；锚点用于同页定位，Tab 子路由用于稳定投影，关联链接进入独立对象。
- **命令与状态**：状态变化后必须重新计算合法动作；相关对象可同屏读取，但写命令返回各自权威边界。
- **权限风险**：字段级脱敏、相关列表裁剪、敏感查看审计；已删除、归档、迁移和无权限不能都显示为 404。
- **优点**：对象心智稳定，适合客户、订单、合同、资产等 360 理解。
- **缺点/拒绝条件**：把所有关系全塞入会形成“万能详情页”；高频队列处理更适合主从或 Worklist。
- **验收**：不同角色投影不泄露；对象身份和数据时点固定可见；动作资格与服务端一致；大关系集可进入独立页并返回。

#### 19.10.4 Transaction Editor：事务编辑器

- **业务问题**：创建或修改一个必须整体守住不变量的聚合，如订单主表、明细、税费、折扣和合计。
- **模型与任务**：服务端草稿 + 聚合根 + 组成明细 + 派生值 + 预期版本 + 校验错误路径。
- **页面与导航**：对象头、分组表单、可编辑明细、合计解释、错误摘要；子编辑页返回父草稿；离开前处理 Dirty 状态。
- **命令与状态**：区分默认值、继承值、建议值、派生值和锁定值；支持显式保存、草稿、提交审批，而不是把所有按钮当同义“保存”。
- **权限风险**：金额和状态由业务命令改变；服务端维护不变量；并发时三方比较基线/我的版本/最新版本。
- **优点**：保存边界和业务整体一致，适合高价值主从交易。
- **缺点/拒绝条件**：页面长、校验复杂；独立生命周期对象不应被强行纳入同一事务。
- **验收**：错误能定位到折叠区/Tab/明细行；刷新后草稿可恢复；冲突不静默覆盖；计算口径可解释。

#### 19.10.5 Worklist / Approval Center：任务与审批中心

- **业务问题**：按责任、优先级和 SLA 连续处理审批、案件、异常或服务请求。
- **模型与任务**：ProcessInstance/Task/Assignee/Candidate/SLA/Evidence/Decision/ProcessVersion。
- **页面与导航**：队列 + 任务详情/证据 + 决策动作 + 流程历史；完成后可进入下一项或返回原队列位置。
- **命令与状态**：领取、释放、转派、委派、加签、退回补充、撤回、升级的状态语义不同；顺序、并行、会签和法定人数需由流程定义决定。
- **权限风险**：决策理由、附件证据、职责分离和 Maker-Checker；运行中实例必须绑定流程版本。
- **优点**：责任、时限、证据和决策形成闭环。
- **缺点/拒绝条件**：把普通通知做成待办会制造队列噪音；自动跳下一项要防止误操作。
- **验收**：重复提交幂等；任务被他人领取时即时反馈；退回/撤回/驳回历史和当前责任清晰。

#### 19.10.6 Reconciliation Workbench：对账与差异处置

- **业务问题**：把内部记录、外部记录和匹配规则放到同一证据空间，处理未匹配、金额差、时间差和重复项。
- **模型与任务**：SourceRecordA/SourceRecordB/MatchCandidate/Rule/Difference/Disposition/Audit。
- **页面与导航**：差异队列、并排证据、候选匹配、字段 Diff、处置结果；从汇总钻到明细，再回到相同差异集合。
- **命令与状态**：匹配、拆分、合并、挂账、忽略、升级人工各有独立理由和审计；自动匹配显示规则与置信依据。
- **权限风险**：来源和数据时点可见；不能用 UI 合计掩盖口径差异；财务处置通常需复核。
- **优点**：减少跨系统来回核对，把异常变成结构化任务。
- **缺点/拒绝条件**：高密度、学习成本高；来源不可比时不得强制“对平”。
- **验收**：每个差异可追溯源记录和规则；局部失败不丢已完成项；重新拉取数据后能识别已处置项。

#### 19.10.7 Import / Batch Workbench：导入与批处理

- **业务问题**：一次处理大量独立记录，并允许预检、后台执行、部分成功和仅重试失败项。
- **模型与任务**：File/Schema/ColumnMapping/Transform/Validation/Batch/ItemResult/IdempotencyKey。
- **页面与导航**：上传 → 识别 → 列映射 → 类型转换 → 预校验 → 重复策略 → 预览 → 执行 → 逐行结果。
- **命令与状态**：明确新增、更新、跳过、覆盖、合并；原子导入与部分成功是业务策略，不是技术默认值。
- **权限风险**：模板和导入范围受权限约束；敏感错误文件脱敏；大文件后台执行需任务号、取消和断点语义。
- **优点**：把不可控文件操作变为可解释、可恢复流程。
- **缺点/拒绝条件**：步骤多；几十条简单数据可能直接表格粘贴更高效。
- **验收**：同一文件重传不重复产生副作用；错误行可下载并只重试失败项；中断后结果可恢复。

#### 19.10.8 Background Job / Exception Center：后台任务与异常恢复

- **业务问题**：命令已受理但需较长时间或依赖外部系统，用户必须知道进度、失败范围和下一步。
- **模型与任务**：Job/Batch/Attempt/ItemResult/ErrorClass/RetryPolicy/CorrelationId/Compensation。
- **页面与导航**：任务列表、进度、阶段、日志摘要、失败项、关联对象和重试/取消/补偿入口；应用壳提供持久任务入口。
- **命令与状态**：区分可重试、需修数据、需授权、不可恢复；重试要保留幂等键和尝试历史。
- **权限风险**：日志脱敏；补偿不是数据库回滚；取消只是请求，需说明是否已产生部分副作用。
- **优点**：前台可离开，失败可定位和恢复。
- **缺点/拒绝条件**：对秒级同步操作建立任务中心会增加认知成本。
- **验收**：刷新/重新登录后可找到任务；部分成功数量一致；重复重试不重复副作用；结果链接回到正确业务对象。

#### 19.10.9 Permission / Rule Designer：治理设计器

- **业务问题**：管理员要安全地改变“谁在什么范围能做什么”或“条件满足时系统如何行动”。
- **模型与任务**：主体、资源、动作、字段、数据范围、继承、Allow/Deny、规则优先级、版本、依赖和发布环境。
- **页面与导航**：范围树/权限矩阵或规则构建器 + 有效结果预览 + 来源解释 + 测试模拟 + Diff + 发布/回滚。
- **命令与状态**：草稿、已发布、生效、历史版分离；Undo/Redo 只恢复编辑操作，不等于回滚已生效业务影响。
- **权限风险**：职责分离、冲突权限检查、二次认证、Maker-Checker、变更影响分析和审计。
- **优点**：复杂治理可解释、可测试、可版本化。
- **缺点/拒绝条件**：自由度高会放大错误；简单稳定参数应使用普通设置页。
- **验收**：能解释有效权限来源；Deny/继承/多角色合并结果准确；发布前能模拟代表性主体和对象。

#### 19.10.10 Analytical Cockpit：分析驾驶舱

- **业务问题**：从指标、趋势和异常发现问题，并下钻到可行动的业务对象。
- **模型与任务**：Metric/Dimension/Grain/Filter/TimeWindow/Baseline/Threshold/DataFreshness/Lineage。
- **页面与导航**：指标摘要、统一筛选、同步时间轴或网格面板、事件叠加、钻取路径、明细出口和订阅。
- **命令与状态**：筛选和时间窗口是共享查询上下文；钻取必须保留分析路径；报告快照和实时驾驶舱是不同对象。
- **权限风险**：行级权限、敏感小样本、指标口径、刷新时间和数据质量提示；聚合数不能泄露被裁剪明细。
- **优点**：把分散指标组织为决策入口。
- **缺点/拒绝条件**：无口径、无时点、无行动出口的仪表盘只制造视觉噪音。
- **验收**：同一筛选下汇总与明细可解释一致；局部数据源失败不冒充零值；移动端保留关键异常和下钻任务。

### 19.11 导航在商业软件中的五条正交轴

前文的 Select/Push/Replace/Overlay/Drill/Advance/Jump/Fork 描述“导航如何改变状态”。商业软件还要同时设计另外四条轴：

| 轴 | 候选 | 核心问题 |
|---|---|---|
| 业务层级 | 系统、租户、组织、模块、对象类型、对象实例、任务、工具 | 用户当前位于哪个业务边界？ |
| 发现方式 | 菜单、搜索、命令面板、最近、收藏、通知、深链、推荐 | 用户如何知道入口存在？ |
| 承载容器 | 页面、Tab、分栏、抽屉、弹窗、Popover、新窗口 | 新上下文占用何种空间和历史？ |
| 状态变换 | Select、Push、Replace、Overlay、Drill、Advance、Jump、Fork | 哪些状态保留，哪些改变？ |
| 状态所有权 | URL、History、局部 UI、用户偏好、服务端草稿、任务实例 | 刷新、返回、跨设备后由谁恢复？ |

关键异常契约：租户切换使旧对象失效；权限变化使菜单、数据和动作重新求值；对象删除使深链进入失效态；会话过期保存本地意图但重新鉴权；多标签编辑检测版本冲突；移动端返回先关闭临时层，再返回来源任务。

### 19.12 树形结构在商业治理界面中的再深入

树不能只展示层级，还要在真实治理任务中处理四类困难：

1. **结构管理树**：移动、排序、归档、删除、撤销；移动前验证目标不是自身后代，发布前显示受影响路径与对象。
2. **懒加载选择树**：未加载后代是 unknown，不是 empty；父级全选必须声明选择当前已加载节点还是整个服务端子树；失败节点可重试。
3. **有效权限树**：节点勾选只是配置输入，最终权限来自继承、Allow/Deny、多角色合并和数据范围；每个结果要解释来源。
4. **BOM/DAG 投影**：同一零件可被多个父件引用，树中重复出现仍是同一对象；选择、库存和变更影响需按稳定 ID 去重。

进一步的数据持久化取舍：邻接表适合直接子节点和频繁移动；物化路径适合路径读取但移动需批量更新；Nested Set 适合读多写少的整棵子树；Closure Table 适合祖先/后代查询但存储和写入成本更高。UI 选择不能掩盖这些规模与一致性边界。

### 19.13 AI 辅助商业界面的控制契约

标杆设计系统开始把 AI 作为横切层，但 AI 不能成为第九种绕过领域规则的页面模式。AI 输出至少分为：建议、摘要、解释、预测和拟执行命令。

必须显式显示：

- 证据和数据时点。
- 不确定性与不适用范围。
- 建议值与权威事实的视觉差异。
- 可局部采用、拒绝、修改和撤销。
- 执行前的目标对象、影响范围和最终业务命令。
- 权限、租户、状态机和服务端校验仍然生效。
- 自动化失败时如何转人工、恢复原任务和保留关联号。

最小反例：一个 AI 摘要把“客户评论中提到将付款”显示成“已付款”。它把非权威协作文本升级成业务事实，破坏了来源和状态语义；无论模型多准确都属于不合格映射。

### 19.14 商业模式评审量表

每项 0–3 分；任一“不变量与安全”“失败恢复”“任务闭环”为 0 分时直接否决，不以总分抵消。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 模型语义 | 字段/状态含义被扭曲 | 主要对象可识别 | 关系、来源和时态基本正确 | 对象、关系、状态、口径可双向追踪 |
| 任务闭环 | 只能看或填，无法完成任务 | 主路径勉强可完成 | 主路径和常见分支完整 | 进入、处理、回执、继续下一项完整 |
| 生产率 | 重复定位和输入严重 | 有基础筛选/快捷动作 | 保存视图、键盘、批处理合理 | 高密度与低错误率经真实任务验证 |
| 不变量与安全 | UI 可绕过业务规则/权限 | 依赖客户端提示 | 服务端校验、鉴权和并发策略明确 | 风险分级、影响预览、审计和职责分离完整 |
| 状态完整性 | 只有正常态 | 有空和加载 | 有错误、过期、无权限 | 冲突、异步、部分成功、离线均有契约 |
| 失败恢复 | 失败后只能重来 | 通用重试 | 能定位范围并保留进度 | 可仅重试失败项、合并冲突或补偿并审计 |
| 导航连续性 | 跳转后丢上下文 | 仅浏览器返回 | URL/历史恢复主要状态 | 深链、跨页、跨设备和异常返回契约完整 |
| 规模与设备 | 只在样例数据/桌面成立 | 有简单响应式 | 分页/虚拟化和移动替代 | 在代表性规模、断点和无障碍条件下验证 |
| 可解释性 | 用户不知道为何可见/失败 | 有通用说明 | 来源、规则、时点基本可见 | 权限、指标、AI、自动匹配均能解释证据 |
| 演进治理 | 直接改线上行为 | 有配置但无版本 | 草稿、发布、历史分离 | Diff、模拟、影响分析、回滚/补偿边界清楚 |

### 19.15 本章结论与后续边界

（已确认）现有方法论的下一层不是继续枚举控件，而是加入“商业软件产品模式”桥接层：

```text
数据模型
→ 查询/命令与任务模型
→ 复合视图
→ 核心页面模式
→ 应用壳、生产率、治理、恢复、协作和设备适配
→ 完整商业任务闭环
```

本文负责解释“为什么数据、关系、任务和风险映射到某种商业模式”；更细的模式内部规范可继续沉淀在 `03-界面模型模式` 专题目录；配套 HTML 负责演示模式如何切换正常、加载、无权限、冲突、处理中和部分成功等状态。这样可以避免把当前文档复制成另一套界面模式百科，同时保留从数据模型到 UI 决策的完整追踪链。
