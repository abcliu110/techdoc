## 2. 角色与职责

### 2.1 角色定义

| 角色 | 主要职责 | 禁止行为 |
|------|---------|---------|
| **研究设计者** | 执行阶段一，形成采集合同 | 访问目标产品、搜索产品截图 |
| **证据采集者** | 执行阶段二，记录事实并冻结证据包 | 预判产品设计、执行不可逆操作 |
| **UI 拆解者** | 从冻结证据建立页面、区域、组件和元素实例 | 重新访问产品 |
| **领域分析者** | 建立数据语义、实体关系和候选模型假设 | 凭经验补造产品行为 |
| **模式综合者** | 进行跨产品比较，形成模式卡和设计规则 | 将单案例直接升级为通用模式 |
| **质量审计者** | 检查证据引用、事实与推断、覆盖率 | 修改原始证据 |

### 2.2 角色拆分执行约束

- 除证据采集者外，其他角色不得访问目标产品
- 所有角色只能引用同一冻结证据包
- 禁止不同时间、版本和账号状态造成证据漂移

---

## 3. 批次规模约束

> 单批次规模必须满足以下约束，超出时必须拆成独立批次：

| 维度 | 最大值 | 说明 |
|------|--------|------|
| 角色数 | 1 | 同一批次只研究同一角色的使用场景 |
| 核心任务数 | 3 | 超出拆分为独立批次 |
| 目标产品数 | 3 | 超出拆分为独立批次 |
| 平台类型 | 不限 | 但必须全部在采集合同中声明 |
| 视口类型 | 不限 | 但必须全部在采集合同中声明 |

多批次通过 `batch_id` 关联，共享上下文在主批次中定义。

## 4. 阶段一：采集合同制定

### 4.1 步骤 0：目标产品能力预研（可选）

**触发条件**：研究设计者对目标产品能力了解不足，无法确定研究问题是否与产品能力匹配。

**操作步骤**：

1. 查阅 E3–E5 级别来源（官方静态截图、可信第三方评测、培训或公开视频）
2. 记录目标产品的已知能力范围
3. 评估研究问题与产品能力的匹配度
4. 确定需要在采集合同中确认的关键假设

**输出**：
- 目标产品能力预研报告（标记为"预研线索"）
- 需要在采集时验证的关键假设列表

**约束**：
- 预研结果只能影响任务脚本的任务列表，不得影响预期结论
- 预研来源必须单独记录，不混入正式证据台账
- 预研线索在正式采集时需经 E1/E2 验证后才能计入证据链

---

### 4.2 步骤 1：重述目标并冻结边界

**操作步骤**：

1. 重述主研究问题（只能有一个）
2. 列出次级问题（每个都必须服务于主问题）
3. 明确包含：产品、角色、对象、关系、任务、平台、设备
4. 明确排除：功能、角色、设备、版本、证据来源
5. 定义研究成功标准和停止条件
6. 列出本批次不能回答的问题

**禁止措辞**：
- "全面研究"
- "深入分析"
- "尽可能完整"
- "优秀 UI"

**输出**：研究边界声明文档

---

### 4.3 步骤 2：建立研究问题到证据的追踪矩阵

**操作步骤**：

对每个研究问题填写：

| 字段 | 填写要求 |
|------|---------|
| question_id | 唯一编号 |
| 问题文本 | 明确、可验证 |
| 为什么需要回答 | 业务价值说明 |
| 需要观察的用户任务 | 具体任务描述 |
| 需要观察的页面和组件 | 页面类型和组件类型 |
| 需要触发的状态 | 状态列表 |
| 可接受的证据类型 | FULL/COMP/VIDEO 等 |
| 可以支持的结论 | 明确范围 |
| 不能支持的结论 | 明确范围 |
| 完成判据 | 可计数、可审核 |

**约束**：每个研究问题至少对应一个完整用户任务；没有任务或证据路径的问题不得进入采集批次。

---

### 4.4 步骤 3：定义统一任务脚本

**操作步骤**：

为每个产品使用语义等价的任务脚本。每条任务脚本必须包含：

| 字段 | 填写要求 |
|------|---------|
| task_id | 唯一编号 |
| 用户角色与权限 | 明确角色和权限集 |
| 用户目标 | 业务目标描述 |
| 业务对象和关系 | 涉及的实体和关系 |
| 数据前置条件 | 采集时的数据状态要求 |
| 起点 | 任务起始位置 |
| 按顺序排列的用户动作 | 每个动作的描述 |
| 每一步预期到达的界面类别 | 不得预设具体产品设计 |
| 每一步取证点 | 截图/录屏时机 |
| 成功结束状态 | 明确的任务完成状态 |
| 取消、返回和恢复路径 | 异常路径处理 |
| 禁止执行的高风险动作 | 不可逆操作列表 |
| 无法完成时的记录方式 | 异常记录格式 |

**每一步必须明确以下证据要求**：

| 证据类型 | 触发条件 |
|---------|---------|
| 全页截图 | 每个关键节点 |
| 页面区域截图 | 任务相关分区 |
| 组件局部截图 | 合同指定状态 |
| 连续录屏 | 连续交互、动画、焦点、拖拽、异步变化或上下文恢复 |
| URL、面包屑、导航来源 | 每次页面切换 |
| 焦点、键盘、触摸或拖拽行为 | 可安全验证时 |
| 前后状态差异 | 状态变化时 |
| 官方文档补证 | 合同指定时 |

### 4.5 步骤 4：建立六维覆盖矩阵

**覆盖矩阵维度**：角色 × 任务 × 页面 × 组件 × 状态 × 设备 × 数据规模 × 权限

> 语言与主题作为矩阵外的固定采集参数，在任务输入中统一声明。

**单元格填写规则**：

| 填写值 | 含义 | 说明 |
|--------|------|------|
| MUST | 本批次必须采集 | 无条件执行 |
| SHOULD | 条件允许时采集 | 尽力而为 |
| NA | 业务上不适用 | 必须说明理由 |
| UNTRIGGERABLE | 理论相关但无法安全触发 | 指定替代来源 |
| OUT | 明确不在本批次范围 | 无需说明 |

**页面类型检查清单**：
- [ ] 应用壳与全局导航
- [ ] 模块入口或工作台
- [ ] 列表、搜索结果、详情、创建和编辑
- [ ] 关联对象查看与选择
- [ ] 批量操作
- [ ] 流程、审批、活动或审计
- [ ] 设置、报表、看板、日历、树、地图或关系图（仅在任务相关时）

**组件交互状态检查清单**：
- [ ] default、hover、focus、active
- [ ] selected、expanded、collapsed
- [ ] disabled、readonly、hidden
- [ ] dragging、drop-target（若支持拖拽）

**业务状态检查清单**：
- [ ] initial、loading、empty、populated、partial
- [ ] validation-error、system-error、warning、success
- [ ] no-permission、masked、offline、stale、conflict
- [ ] async-processing、cancelled、completed

**数据规模检查清单**：
- [ ] 零条
- [ ] 一条
- [ ] 少量、可在首屏完整展示
- [ ] 中量、需要滚动或分页
- [ ] 大量、需要搜索、虚拟化、聚合或延迟加载

**无法触发状态的处理优先级**：
1. 真实产品安全触发
2. 官方文档或官方演示补证
3. 官方发布说明补证
4. 仍无证据则记为 UNKNOWN

---

### 4.6 步骤 5：固定 UI 拆解粒度

**四级 UI 结构**：

| 级别 | 定义 | 示例 |
|------|------|------|
| L1 页面 | 具有独立任务上下文、路由或模态任务边界的完整界面 | 客户列表页、客户详情页 |
| L2 区域 | 承担一个可描述职责的页面分区 | 页头、筛选区、关联记录区 |
| L3 组件 | 具有独立语义、状态或交互契约的复用单元 | 表格、选择器、步骤条 |
| L4 元素 | 组件内可辨识的交互或内容元素 | 标签、值、图标、行操作、分页器 |

**采集约定**：
- 默认采集至 L4
- 只有研究目标明确要求重建设计系统时，才继续测量 CSS 属性或生成视觉 Token 候选
- 不得把 DOM 节点数量当成 UI 元素数量
- 不得为了"细"而把每个包装容器当成独立元素

### 4.8 步骤 7：预先定义证据编号与文件规则

**证据编号格式**：

```
{PRODUCT}-{ROLE}-{TASK}-{PAGE}-{TYPE}-{SEQ}
```

**示例**：
```
SF-SALES-CUSTOMER-DETAIL-FULL-E001
SF-SALES-CUSTOMER-DETAIL-COMP-E002
SF-SALES-CUSTOMER-CREATE-VIDEO-E003
SF-SALES-CUSTOMER-DETAIL-VIDEO-FRAME-E004
```

**TYPE 受控值**：

| TYPE | 含义 | 说明 |
|------|------|------|
| FULL | 全页截图 | 保留页面整体结构 |
| REGION | 页面区域截图 | 突出任务相关分区 |
| COMP | 组件截图 | 覆盖合同指定状态 |
| VIDEO | 完整录屏 | 连续交互记录 |
| VIDEO-FRAME | 录屏关键帧 | manifest.yaml 中记录父录屏编号 |
| DOM | DOM 或可访问性结构摘要 | 结构化数据 |
| DOC | 官方文档 | 文档类证据 |
| NOTE | 客观操作记录 | 纯文本记录 |

**文件命名规则**：
- 文件名必须包含证据编号
- 任何裁剪图必须保留对全页证据的引用
- 确保能恢复上下文

**目录结构**：
```
evidence-package/
  manifest.yaml
  collection-contract/
  product-context/
  task-runs/
  screenshots/full-page/
  screenshots/regions/
  screenshots/components/
  recordings/
  official-sources/
  observations/
  coverage/
  unknowns/
  checksums/
```

### 4.9 阶段一门禁检查

#### 门禁检查清单

| 检查项 | 要求 | 不通过处理 |
|--------|------|-----------|
| 研究问题追踪 | 每个研究问题至少有一个任务和一条证据路径 | 补充任务或调整问题范围 |
| 任务脚本完整性 | 每条任务有明确入口、步骤和结束状态 | 完善任务脚本 |
| 取证时机定义 | 每个关键步骤规定了截图或录屏时机 | 补充取证点定义 |
| 覆盖矩阵 | 六维覆盖矩阵无空白格 | 补充缺失格子的取值 |
| MUST 状态触发 | 所有 MUST 状态都有真实触发或替代取证方案 | 确定触发方案或调整状态等级 |
| 任务脚本语义等价 | 所有产品使用语义等价的任务脚本 | 统一任务脚本结构 |
| 证据编号定义 | 已定义证据编号、文件名、元数据和目录结构 | 完善编号体系 |
| 不可逆动作清单 | 已列明不可逆动作、隐私边界和访问限制 | 补充清单 |
| 覆盖率定义 | 已定义覆盖率、停止条件和冻结条件 | 补充定义 |

#### 通过条件

**全部满足**后，才允许进入阶段二，输出《采集合同》。

**不通过处理**：修订合同，不得提前浏览产品。

### 5.2 步骤 2：按任务脚本逐步采集

**操作步骤**：

每到一个关键节点，按合同执行以下动作：

1. 保存全页截图，保留页面整体结构、应用壳和导航上下文
2. 保存任务区域截图，突出当前任务相关分区

### 5.6 步骤 6：来源强度分级

| 强度 | 定义 | 约束 |

### 5.7 步骤 7：采集窗口内覆盖检查与补漏

**覆盖率计算**：

| 指标 | 计算公式 |
|------|---------|
| 任务步骤取证率 | 有证据的计划步骤 / 全部计划步骤 |
| 核心页面取证率 | 已取证核心页面 / 计划核心页面 |
| 必采组件取证率 | 已取证 MUST 组件 / 全部 MUST 组件 |
| 可触发状态覆盖率 | 已取证可安全触发状态 / 全部可安全触发状态 |
| 全计划状态覆盖率 | 已取证状态 / 全部 MUST 与 SHOULD 状态（只做透明报告） |
| 元数据完整率 | 字段完整的证据 / 全部证据 |
| 证据引用可达率 | 文件存在且可打开的证据 / 台账证据 |
| 无证据事实结论数 | 无法追溯到证据的结论数量 |

**触发门禁（达到则冻结，低于则透明报告并冻结）**：

| 指标 | 目标 | 低于目标处理 |
|------|------|-------------|
| 任务步骤取证率 | 100% | 列出未取证步骤及原因 |
| 核心页面取证率 | 100% | 列出未取证页面及原因 |
| 必采组件取证率 | 100% | 列出未取证组件及原因 |
| 可触发状态覆盖率 | 100% | 列出未触发状态及原因 |
| 元数据完整率 | 100% | 列出缺失元数据的证据 |
| 证据引用可达率 | 100% | 列出不可达证据 |
| 无证据事实结论数 | 0 | 将无证据结论降级为假设或未知 |

**补漏约束**：
- 补漏只能发生在当前采集窗口仍打开时
- 补漏只能补采合同已列内容
- 发现新的研究方向时，只记录到下一批次建议，不得临时扩大本批次
- 全计划状态覆盖率不得为了达到数字而伪造危险状态

### 5.8 步骤 8：冻结证据包

**冻结前必须完成**：

1. 生成证据清单
2. 校验所有引用文件存在
3. 记录每个文件的来源和采集时间
4. 计算文件校验值（或采用其他可检测后续修改的机制）

6. 记录冻结时间和冻结人/代理

│   ├── regions/                     # 区域截图

├── recordings/                      # 录屏文件
│   └── {evidence_id}.mp4
├── official-sources/                # 官方来源
│   └── {evidence_id}/

│   └── {evidence_id}-observation.yaml

**冻结确认**：

| 确认项 | 要求 |
|--------|------|
| 所有证据已生成 | manifest.yaml 中所有文件存在 |
| 所有引用可达 | 证据引用可达率 = 100% |
| 元数据完整 | 元数据完整率 = 100% |
| 原始证据只读 | 文件权限已设置为只读 |
| 在线采集能力已关闭 | 阶段三只能读取冻结证据 |

**冻结后禁止行为**：
- 重新访问产品补证
- 修改原始证据文件
- 将分析产物覆盖原始证据

## 6. 阶段三：离线分析

### 6.1 步骤 1：第一轮 — 证据整理，不做设计评价

**操作步骤**：

1. 截图去重，但不删除唯一状态证据
2. 全页、区域、组件和录屏互相建立引用
3. 按产品、角色、任务、页面、组件和状态分组
4. 把任务步骤与证据编号关联
5. 校验版本、来源、环境和元数据
6. 标记冲突证据和不可比较证据
7. 生成证据覆盖报告

**约束**：不做设计评价，只做事实整理。

---

### 6.2 步骤 2：第二轮 — UI 原子化拆解

**拆解层级**：

```
产品
→ 角色与任务
→ 任务流程
→ 信息架构与导航
→ 页面
→ 页面区域
→ 组件
→ 元素
→ 视觉测量与 Token 候选
→ 状态
→ 交互和反馈
```

**约束**：每个实例必须保留来源证据，不得把多个产品的不同实现提前合并。

---

### 6.3 步骤 3：第三轮 — 产品实例分析

**分析维度**：

| 维度 | 分析要点 |
|------|---------|
| 用户角色和任务 | 它面对的用户角色和任务是什么 |
| 设计选择 | 它采用什么页面、导航、组件和交互组合 |
| 用户需求 | 用户需要理解什么信息、做什么决策 |
| 证据分类 | 哪些结果是直接观察，哪些是交互验证 |
| 收益迹象 | 在当前证据覆盖范围内，有哪些收益迹象 |
| 代价分析 | 代价、认知负担、操作成本和失败风险是什么 |
| 失效条件 | 在什么数据规模、权限、设备或任务变化后会失效 |
| 未知项 | 有哪些未知项 |

**约束**：
- "收益"和"代价"必须绑定具体任务，不得只写"清晰、美观、易用、灵活"
- 优缺点评价至少检查以下方面：

| 检查类别 | 检查项 |
|---------|--------|
| 任务效率 | 任务成功与完成路径 |
| 可用性 | 可发现性和可理解性 |
| 操作效率 | 扫描、搜索和比较效率 |
| 成本 | 点击、输入、记忆和上下文切换成本 |
| 认知负荷 | 信息密度与认知负荷 |
| 错误处理 | 错误预防、反馈、撤销和恢复 |
| 学习曲线 | 新手学习与熟练用户效率 |
| 扩展性 | 大数据规模和复杂关系适应性 |
| 兼容性 | 响应式、国际化和无障碍 |
| 信任度 | 性能感知、权限、隐私、审计和信任 |
| 工程成本 | 工程复杂度和维护成本（只能作为设计实现推断，需标明证据不足） |

### 6.4 步骤 4：第四轮 — 跨产品比较

**比较前提条件**：

| 条件 | 要求 |
|------|------|
| 问题一致性 | 回答同一个研究问题 |
| 角色等价性 | 用户角色和任务语义等价 |
| 条件一致性 | 数据规模、权限、设备和版本差异已经显式记录 |
| 证据充分性 | 证据强度足以支持比较 |
| 不可比因素 | 不可比因素已经列出 |

**比较维度**：

| 维度 | 检查项 |
|------|--------|
| 信息架构 | 信息架构和入口 |
| 页面布局 | 页面类型和布局 |
| 关系处理 | 关系展示、选择、维护和导航 |
| 状态反馈 | 状态和反馈 |
| 上下文保持 | 上下文保留与返回 |
| 批量操作 | 扫描、比较和批量操作 |
| 扩展性 | 数据量扩展 |
| 风险控制 | 权限、风险和错误恢复 |
| 兼容性 | 响应式、键盘和无障碍 |
| 适用条件 | 优势成立条件、代价和失效条件 |

**约束**：不得因为多个产品都采用某方案，就推断该方案必然更好。共同出现只能说明它是候选模式线索。

---

### 6.5 步骤 5：第五轮 — 模式归纳和晋级

**知识等级固定**：

```
原始证据
→ 客观观察
→ 产品实例
→ 候选模式
→ 已验证模式
→ 条件化设计规则
→ 设计决策
```

**晋级门槛**：

| 等级 | 晋级门槛 |
|------|---------|
| 产品实例 | 至少一份可追溯的 E1 或 E2 证据 |
| 候选模式 | 至少两个独立产品针对等价问题采用语义相似方案，并明确差异 |
| 已验证模式 | 至少三个独立产品、至少一个反例或替代方案、适用条件和失效条件明确 |
| 条件化设计规则 | 来源于已验证模式，具有明确输入条件、输出建议、拒绝条件、替代方案和验证方法 |
| 最佳实践 | 不得仅由竞品观察产生；还需要可用性测试、业务结果、可靠研究或项目实验证据 |

> 以上数量是本知识库的治理门槛，不是统计学证明。证据质量优先于案例数量。

**每张模式卡必须包含**：

| 字段 | 说明 |
|------|------|
| 模式名称、别名和所属类别 | 基本标识 |
| 要解决的问题 | 问题描述 |
| 用户角色与任务 | 适用范围 |
| 领域语义 | 业务含义 |
| 前置条件和约束 | 适用前提 |
| 核心结构和交互流程 | 解决方案 |
| 页面、组件和元素构成 | 结构组成 |
| 状态矩阵 | 状态覆盖 |
| 数据规模、权限和风险 | 约束条件 |
| 响应式、国际化和无障碍要求 | 兼容性要求 |
| 优点及其成立条件 | 收益分析 |
| 代价、缺点和承担者 | 代价分析 |
| 失败模式和规模临界点 | 失效条件 |
| 不适用条件 | 排除条件 |
| 反例、替代方案和选择判据 | 替代方案 |
| 正面和反面商业实例 | 案例支持 |
| 证据编号、来源强度和置信度 | 证据追溯 |
| 验收或可用性测试建议 | 验证方法 |

### 6.6 步骤 6：第六轮 — 生成设计规则

**规则格式**（必须写成条件规则）：

```text
如果：
- 用户角色和核心任务是……
- 领域对象或关系是……
- 数据规模是……
- 权限、风险、频率和设备约束是……

那么：
- 优先选择某页面、导航、组件和状态组合；

因为：
- 它在这些条件下优先保证……
- 代价是……，由……承担；

不要使用，当：
- 出现这些失效条件……

替代方案：
- 方案 A，适合……
- 方案 B，适合……

证据和置信度：
- 证据编号……
- 置信度……

验证方式：
- 用什么任务、指标或可用性测试验证。
```

### 6.7 步骤 7：第七轮 — 建立场景化 UI 评价体系

**约束**：不要用一套固定权重评价所有页面。先识别页面的主要任务类型，再设置评价权重。

**评价维度**：

| 维度 | 说明 |
|------|------|
| 任务适配 | 与用户任务的匹配程度 |
| 信息架构和导航 | 导航结构合理性 |
| 视觉层级和信息密度 | 视觉层次和密度 |
| 可发现性和可理解性 | 用户能否快速找到和理解 |
| 操作效率和上下文保持 | 操作便捷性和状态保持 |
| 扫描、比较、筛选和批量处理 | 数据操作效率 |
| 状态可见性和反馈 | 状态提示和反馈 |
| 错误预防、撤销和恢复 | 错误处理能力 |
| 一致性和可学习性 | 界面一致性 |
| 大数据量与复杂关系适应 | 扩展能力 |
| 响应式、国际化和无障碍 | 兼容性 |
| 性能感知 | 性能体验 |
| 权限、隐私、审计和用户信任 | 安全和信任 |
| 领域语义匹配程度 | 业务语义准确性 |

**每个分数必须包含**：

| 字段 | 说明 |
|------|------|
| 评分锚点 | 1、3、5 分分别代表什么可观察行为 |
| 引用证据 | 支持评分的证据编号 |
| 影响的用户任务 | 评分影响的用户任务 |
| 严重程度和发生频率 | 问题影响评估 |
| 适用前提 | 评分适用的前提条件 |
| 评价置信度 | 当前评分的置信度 |
| 改进建议和副作用 | 改进方向及潜在影响 |

**约束**：
- 不得使用没有行为锚点的"8.7 分"式伪精确评分
- 总分只能用于同一任务、同一权重和同等证据条件下的辅助比较
- 不能代替设计判断

---

### 6.8 步骤 8：第八轮 — 谨慎反推候选领域模型

**约束**：只生成候选概念模型，不生成真实物理数据库结论。

**允许使用的线索**：

| UI 观察 | 推断方向 |
|---------|---------|
| 反复出现且具有稳定身份的业务名词 | 候选实体 |
| 总是成组展示、编辑和校验的字段 | 候选值对象 |
| 选择器、关联列表、子表格和创建并关联 | 候选关系与基数 |
| 关系行自身具有日期、角色、数量等字段 | 候选关联实体 |
| 状态标签、动作可用条件和时间线 | 候选状态机 |
| 按钮和批量操作 | 候选命令 |
| 活动流、通知和审计记录 | 候选事件或审计模型 |
| 独立保存、权限和生命周期 | 聚合边界候选 |
| 指标卡、报表和跨对象页面 | 查询模型或读取投影候选 |

**每个候选模型必须包含**：

| 字段 | 说明 |
|------|------|
| candidate_type | 实体、值对象、属性、关系、状态、命令、事件、规则、权限、聚合边界或查询模型 |
| candidate_name | 候选名称 |
| evidence_ids | 支持证据 |
| reasoning_chain | 推理链 |
| counter_evidence | 反证 |
| alternative_explanations | 其他可能解释 |
| confidence | 置信度 |
| validation_questions | 需要怎样验证 |
| cannot_infer | 明确不能推出的实现事实 |

**置信度定义**：

| 置信度 | 定义 |
|--------|------|
| high | 多个独立交互和官方证据一致，且主要替代解释已排除 |
| medium | 有直接 UI 证据，但仍存在合理替代解释 |
| low | 仅有静态或间接线索，只能作为待验证方向 |

**聚合边界置信度补充**：
- 当 E2（官方文档、官方设计系统）明确声明某设计意图时，可将聚合边界置信度从 low 提升至 medium
- 仍需在 `cannot_infer` 中标注"设计意图 ≠ 实现事实"
- 不得直接声称该聚合已在数据库层面实现

**禁止仅凭 UI 宣称**：

| 禁止项 | 说明 |
|--------|------|
| physical_table | 真实表名、列名 |
| foreign_key | 外键和索引 |
| database_cardinality | 一对多关系的数据库实现方式 |
| transaction_strategy | 事务一致性和锁策略 |
| cascade_strategy | 级联删除 |
| api_structure | API、事件或消息结构 |
| service_boundary | 微服务边界 |
| aggregate_ownership | 聚合根的最终归属 |

### 6.9 步骤 9：第九轮 — 建立可用于新设计的知识索引

**知识库检索能力**：必须支持从以下输入检索：

- 用户角色和任务
- 业务领域和对象
- 数据语义
- 实体关系和基数
- 状态与业务流程
- 数据规模
- 权限、风险和使用频率
- 设备、输入方式和无障碍条件
- 页面、导航、组件和交互问题

**检索结果必须返回**：

- 候选模式及排序理由
- 适用和不适用条件
- 优点、代价和失败边界
- 替代方案
- 商业实例和反例
- 证据与置信度
- 仍需验证的问题

**基于知识库生成新 UI 时，输出必须包含**：

- 推荐的信息架构
- 页面框架
- 导航和上下文恢复契约
- 组件组合
- 完整状态矩阵
- 响应式、国际化和无障碍要求
- 被拒绝的替代方案及原因
- 设计风险和验证计划
- 引用的模式卡和证据

## 10. 验收标准

本提示词执行成功，不以"报告很长"为标准，而以以下结果为准：

- 研究问题、任务脚本和证据之间可以双向追踪
- 每个产品事实都有可打开的证据
- 每个组件都保留业务任务、视觉结构、交互状态和适用边界
- 实体关系同时记录展示、选择、维护、导航和上下文恢复
- 优缺点都绑定角色、任务、数据规模和约束
- 单案例没有被误写为通用模式
- 模式具备适用条件、代价、失效条件、反例和替代方案
- UI 评价分数具有行为锚点和证据，不存在伪精确总分
- 领域模型结论明确标为候选假设，并包含反证与替代解释
- 冻结后没有再次在线补证；证据不足处被诚实标记为未知
- 新 UI 方案能够说明"为何选择、为何不选其他方案、证据来自哪里、需要怎样验证"
