# 既有系统业务分析理论 - 实践指南

> 本指南基于完整的遗留系统分析方法论框架，提供精炼的实践操作手册，帮助团队快速上手并正确执行既有系统的业务分析。

---

## 一、理论核心速览

### 1.1 理论定位

**核心定义**：既有系统业务分析是一套系统化的逆向工程方法论，通过从运行中的系统提取、验证、抽象业务知识，形成可迁移的领域模型。

**本质三句话**：
1. 从运行系统中逆向提取业务知识的系统化方法
2. 形成可验证、可迁移的领域模型
3. 让隐性知识显性化、主观判断客观化、经验驱动证据化

### 1.2 三跳理论：业务分析的认识路径

既有系统业务分析的理论对象不是代码文本本身，而是代码所承载、但未必被直接命名的业务知识。知识形成遵循三次跃迁：

```text
具体代码、数据与运行痕迹
    → 业务对象
    → 业务模式
    → 领域模型
```

- **代码到业务对象**，是把技术实现解释为具有身份、责任、生命周期和业务意义的概念；对象不是类名的同义词，而是可由多种实现共同承载的业务存在物。
- **业务对象到业务模式**，是从多个对象、规则与协作关系中归纳可重复的结果生成机制；模式不是流程截图，而是可跨具体入口识别的共同结构。
- **业务模式到领域模型**，是依据业务能力、责任边界与变化边界组织模式；领域模型不是数据库关系图，而是对稳定业务结构及其依赖关系的解释。

这三跳构成分析层的认识论约束：不能从单一代码证据直接宣称已经得到领域模型；也不能因为已画出对象图，就认为已识别业务模式。后续的七要素、对象分类、规则依赖图和证据分级，分别用于补足每次跃迁所需的观察与论证。

### 1.3 适用场景判断（3秒决策）

**✓ 适用**（5个条件）：
- 有源代码或可反编译
- 数据库可访问或有数据字典
- 有业务人员可访谈或历史文档
- 系统仍在运行可观察
- 业务逻辑有规律可循

**✗ 不适用**（5个排除）：
- 全新业务领域无参考
- 系统已下线无代码数据文档
- 纯创意类系统无规则
- AI黑盒决策不可解释
- 频繁变化分析结果快速过期

## 三、分析层实践指南

### 3.1 七要素提取（核心方法）

**执行步骤**：

```text
步骤1：识别业务事实
- 从代码、数据库、文档中提取所有业务相关信息
- 不做解释，只记录原始事实

步骤2：逐条归类（按依赖顺序）
- 主体（Who）：谁使用系统？有哪些角色？
- 目标（What）：用户想达成什么？
- 规则（Rules）：业务必须遵守什么约束？
- 协作（Collaboration）：角色之间如何配合？
- 时序（Timing）：业务有时间维度吗？
- 资源（Resource）：哪些对象被创建、消耗或转移？
- 信息（Information）：哪些数据被创建、传递或存储？

步骤3：互斥性检查
- 每个事实只能归入一个要素
- 如果能归入两个，重新判断本质

步骤4：技术与业务分离
- Handler、DTO、Mapper等技术对象不归入业务要素
- 数据库约束不是业务规则（是技术保障）
```

**快速判断卡**：

| 事实类型 | 判断标准 | 归类 |
|---------|---------|------|
| "收银员" | 是谁？ | 主体 |
| "完成点餐" | 想做什么？ | 目标 |
| "满100可用券" | 必须遵守？ | 规则 |
| "服务员→系统→厨房" | 如何配合？ | 协作 |
| "营业时间10:00-22:00" | 何时/多久？ | 时序 |
| "桌台从空闲到占用" | 被操作的对象？ | 资源 |
| "订单数据传递" | 传递的数据？ | 信息 |

**常见错误避坑**：
- ❌ "UserController是主体" → ✓ "收银员是主体，UserController是技术入口"
- ❌ "目标是录入订单" → ✓ "目标是完成点餐，录入是手段"
- ❌ "规则是NOT NULL约束" → ✓ "规则是订单必须有顾客，NOT NULL是保障"

### 3.2 对象分类（5秒决策树）

```text
发现一个类/表/接口？

Q1: 有业务身份吗？（billNo、memberId等）
├─ 否 → Q2: 是请求/响应吗？
│      ├─ 是 → 【命令/结果】
│      └─ 否 → Q3: 是框架类？
│             ├─ 是 → 【技术组件】
│             └─ 否 → 【值对象候选】
│
└─ 是 → Q4: 有生命周期吗？（创建→使用→结束）
       ├─ 否 → 【值对象候选】
       └─ 是 → Q5: 状态变化有业务意义吗？
              ├─ 否 → 【技术对象】
              └─ 是 → Q6: 能独立存在吗？
                     ├─ 否 → 【实体成员】
                     └─ 是 → Q7: 是聚合对外入口吗？
                            ├─ 否 → 【实体】
                            └─ 是 → 【聚合根候选】→ 走5条判定
```

**聚合根5条判定（必须全满足）**：

| 条件 | 验证问题 | 代码证据 |
|------|---------|---------|
| 1. 对外唯一入口 | 外部只通过它引用聚合？ | 外部引用Order，不直接引用OrderDetail |
| 2. 生命周期控制 | 它创建和删除内部对象？ | Order.create()创建Detail |
| 3. 维护不变式 | 它维护聚合级约束？ | Order.calculateTotal()保证总价=Σ明细 |
| 4. 事务边界 | 聚合内修改在一个事务？ | @Transactional包含Order和Detail |
| 5. 发布事件 | 它发布领域事件？ | Order.publishEvent(OrderCreated) |

**实体识别卡必填5问**：
1. 业务身份是什么？（与技术主键的区别）
2. 生命周期谁控制？（创建、使用、结束）
3. 哪些业务动作会读写它？（具体方法和行号）
4. 哪些状态变化有证据？（状态转换路径）
5. 与其他概念的关系？（关系类型、数量、一致性）

### 3.3 规则提取与依赖图

**规则提取步骤**：

```text
步骤1：提取显性规则
- 扫描所有if/else、switch语句
- 记录判断条件和执行动作

步骤2：提取隐性规则（重点）
- 代码追踪法：看变量赋值逻辑和依赖关系
- 异常场景法：问"如果没有XX会怎样？"
- 业务访谈法：给业务方看代码，问"对吗？"

步骤3：建立规则依赖图
- 强依赖：A必须先于B（B用到A的结果）
- 弱依赖：A和B都要但顺序无关
- 互斥依赖：A和B不能同时生效
- 条件依赖：某条件下A依赖B

步骤4：推导执行顺序
- 从依赖图做拓扑排序
- 标注优先级（salience）
```

**规则依赖矩阵模板**：

| 规则 | R001 | R002 | R003 | R004 |
|------|------|------|------|------|
| R001 | - | 互斥 | 组合 | 输入 |
| R002 | 互斥 | - | 组合 | 输入 |
| R003 | 输出 | 输出 | - | 互斥 |
| R004 | 输出 | 输出 | 互斥 | - |

**关系说明**：
- 依赖：A依赖B，B先执行
- 互斥：A和B不能同时生效
- 组合：A和B结果需要组合
- 输入：A的输出是B的输入
- 输出：A产生B需要的数据

### 3.4 证据分级（强制标注）

| 层级 | 定义 | 判断标准 | 标注方式 |
|------|------|---------|---------|
| **L1 直接事实** | 可定位的代码/数据 | 文件名+行号 | `OrderService.java:85` |
| **L2 代码推断** | 由代码推出的结论 | 完整调用链 | `Controller→Service→Repo` |
| **L3 业务语义** | 对代码的业务解释 | 代码+文档/访谈 | `代码OrderService:85 + 访谈记录2024-01-15` |
| **L4 业务推断** | 未被确认的假设 | 单一推理 | `【待确认】假设：...` |
| **L5 未知** | 证据不足或冲突 | 无法确认 | `【未知】需要...验证` |

**强制约束**：
- L4/L5不能作为设计依据
- 所有P0结论必须≥L3
- L4必须有验证计划
- L5不得伪装成已知

## 四、评价层实践指南

### 4.1 扩展性评分（目标≥60分）

**评分公式**：
```text
总分 = (规则扩展性×30% + 概念扩展性×25% + 流程扩展性×25% + 集成扩展性×20%) × 20

单项扩展性 = 5 - (代码改动率 × 5)
代码改动率 = 新增功能导致的改动行数 / 系统总代码行数
```

**快速评估表**：

| 维度 | ★★★★★ | ★★★★ | ★★★ | ★★ | ★ |
|------|--------|------|-----|-----|---|
| **规则** | 只需配置 | 改少量代码<10% | 改中量代码10-30% | 改大量代码30-50% | 需重构>50% |
| **概念** | 零改动 | 加字段 | 加表 | 改表结构 | 重建模型 |
| **流程** | 编排配置 | 加分支 | 改状态机 | 重构流程 | 推翻重来 |
| **集成** | 加配置 | 加适配器 | 改适配器 | 改协议 | 不支持 |

### 4.2 反模式识别（必查项）

| 反模式 | 识别特征 | 修复建议 |
|--------|---------|---------|
| **硬编码魔法值** | 100、0.1等散落代码中 | 配置化 |
| **if-else地狱** | 嵌套>3层 | 策略模式/规则引擎 |
| **重复代码** | 相似逻辑多处实现 | 抽象为公共方法 |
| **循环依赖** | A→B→C→A | 依赖倒置/中介者 |
| **上帝类** | 一个类>2000行 | 拆分为多个类 |
| **过拟合** | 只适配当前需求 | 预留扩展点 |

### 4.3 变化点分析

**公式**：
```text
优先级 = 变化频率 × 当前改动成本

变化频率：高（每月）、中（每季度）、低（每年）
改动成本：高（>1人周）、中（1-3人日）、低（<1人日）
```

**决策矩阵**：

| 变化点 | 频率 | 当前成本 | 优先级 | 改进方案 |
|--------|------|---------|--------|---------|
| 新增支付渠道 | 高 | 高 | 🔴 极高 | 策略模式 |
| 新增会员等级 | 中 | 中 | 🟡 中 | 配置化 |
| 新增促销规则 | 高 | 高 | 🔴 极高 | 规则引擎 |
| 新增报表类型 | 低 | 低 | 🟢 低 | 保持现状 |

## 六、验证层实践指南

### 6.1 门禁脚本使用

**Windows PowerShell**：
```powershell
.\check-level1-skeleton.ps1 -RootPath "D:\产出目录"
echo $LASTEXITCODE  # 查看退出码
```

**Linux/macOS Bash**：
```bash
./check-level1-skeleton.sh "/path/to/产出目录"
echo $?  # 查看退出码
```

**退出码含义**：
- 0 = 通过，可进入下一阶段
- 2 = 骨架文件缺失，需补建
- 3 = Level 2孤立，需先建Level 1
- 4 = 清单不一致，需同步
- 5 = 内容为占位符，需填写实质内容

**强制约束**：退出码非0禁止进入下一阶段

### 6.2 覆盖度验证（三重检查）

| 检查项 | 计算公式 | 通过标准 |
|--------|---------|---------|
| **功能覆盖度** | 已覆盖功能数 / 老系统功能总数 | ≥95% |
| **规则覆盖度** | 语义一致规则数 / 老系统规则总数 | =100% |
| **数据覆盖度** | 一致数据行数 / 总数据行数 | ≥99% |

### 6.3 质量评分（目标≥80分）

**评分公式**：
```text
质量分 = (概念完整率×20% + 规则完整率×30% + 流程完整率×20% + 术语一致率×15% + 依赖完整率×15%) × 100

概念完整率 = 已建模对象数 / 候选对象数
规则完整率 = 已提取规则数 / 代码分支数
流程完整率 = 已覆盖入口数 / P0入口总数
术语一致率 = 一致术语数 / 总术语数
依赖完整率 = 已分析依赖数 / 总依赖数
```

## 七、常见问题速查

### 7.1 五大常见错误

| 错误 | 表现 | 避坑方法 |
|------|------|---------|
| 跳过Level 1 | 直接分析Level 2 | 强制G1门禁 |
| 技术对象冒充 | DTO当实体 | 5条判定强制走完 |
| 推断当事实 | L4写成L1 | 强制标注证据层级 |
| 人工放水 | 不跑脚本直接过 | 退出码强制阻断 |
| 只分析不评价 | 没有评分 | 评价层强制产出 |

### 7.2 时间投入速算

| 系统规模 | 代码量 | 分析 | 评价 | 设计 | 验证 | 总计 |
|---------|--------|------|------|------|------|------|
| 小型 | <5万行 | 1-2周 | 3-5天 | 1周 | 1周 | 4-5周 |
| 中型 | 5-20万 | 2-4周 | 1-2周 | 2-3周 | 2周 | 7-11周 |
| 大型 | 20-50万 | 1-2月 | 3-4周 | 1-2月 | 1月 | 3-5月 |

### 7.3 紧急故障处理

**场景1：分析中断恢复**
1. 读取检查点.md获取最后位置
2. 读取索引.md确认已完成项
3. 运行门禁脚本验证状态一致性
4. 从中断点继续

**场景2：门禁不通过**
1. 查看脚本退出码
2. 根据退出码定位问题
3. 修复后重新运行
4. 退出码=0后才能继续

**场景3：评分不达标**
1. 查看各维度分项得分
2. 识别最低分维度
3. 针对性改进
4. 重新评分直到达标
