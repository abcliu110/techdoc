# 大型遗留系统分析方法论：code-review-graph 图谱驱动版

> **版本**：v2.1  
> **适用对象**：大型遗留系统、多模块单体、微服务及其前后端关联仓库  
> **核心工具**：`code-review-graph`  
> **核心原则**：机器全量建图；全量类摘要卡优先；以类卡和图谱关系逐层向上归纳；结论回填结构化事实；文档只是面向人的视图。  
> **更新日期**：2026-09-09

---

## 1. 要解决的根本问题

大型系统分析失败的根因通常不是 AI 不会推理，而是代码、调用、数据、配置、任务、消息和外部依赖的总量超过单次上下文窗口。问题不在于“要不要总结所有类”，而在于不能让 AI 把所有类的**完整源码和长篇解释同时保留在一个上下文中**。

本方法采用“**全类先摘要、后逐层归纳**”的顺序：先覆盖仓库内每个可解析类，为每个类生成统一、短小、可检索的类摘要卡；再利用类卡之间的图谱关系，向上归纳技术组件、业务能力和业务闭环。类卡保存在外部事实层，AI 每次只装载当前归纳所需的一小组类卡与必要源码证据。

```text
全量代码实体与静态关系
  └─ code-review-graph 持久化为外部图谱
      └─ 为每个类生成统一的类摘要卡（全量覆盖、外部持久化）
          └─ 从类卡 + 图谱边归纳技术组件
              └─ 从组件归纳业务能力与业务闭环
                  └─ 将证据、语义、未知项回填事实层
                      └─ 生成领域图、流程卡、规则卡、状态机和风险报告
```

因此，图谱不是“自动完成业务分析的工具”，而是 AI 的**外部长期记忆、关系索引与上下文压缩器**。

### 1.1 两件必须区分的事

| 动作 | 执行者 | 目标 | 是否需要把全部代码放进 AI 上下文 |
|---|---|---|---|
| 全量类摘要卡 | AI + 类卡生成流程 | 为每一个可解析类生成统一、可检索、带证据的短摘要 | 分批处理；不得把全部源码同时放进上下文 |
| 向上归纳 | AI + 人类复核 | 从全类卡与图谱边归并技术组件、业务能力、规则、状态和业务闭环 | 仅加载当前归纳单元相关类卡与最小证据 |

**必须先覆盖全部可解析类，但禁止无结构地逐类长篇阅读和写散乱说明。** 每个类先形成固定字段、受长度约束、带图谱证据链接的“类摘要卡”；类、方法、字段仍是底层证据节点，业务结论则在类卡之上逐层归纳。

### 1.2 成功标准

一次分析任务完成时，应能同时回答：

1. 当前业务问题处于哪条全局业务闭环；
2. 关联哪些入口、协调服务、数据对象、状态、消息、任务和外部边界；
3. 哪些关系由静态代码直接证实，哪些依赖配置、运行数据或业务专家确认；
4. 异常、重试、补偿、幂等和人工收敛在哪里发生；
5. 新结论是否已经回填为可检索事实，而非只写进一份孤立 Markdown。

## 2. 图谱的职责、边界与事实分层

`code-review-graph` 的职责是保存、检索并压缩**静态代码事实**；它不能仅凭类名或调用关系自动证明完整业务语义。分析过程中必须把“图谱证明了什么”与“需要额外验证什么”分开。

### 2.1 五层记忆模型

```text
L0 系统压缩摘要
   系统边界、部署形态、主链路、关键不变量、最高风险、全局未知项
L1 领域/能力摘要
   能力职责、核心对象、上下游、关键状态、事件与边界
L2 业务闭环摘要
   正常流、拒绝流、异步流、重试、补偿、人工收敛与验收结果
L3 全类摘要卡库
   每个类的统一职责摘要、关键方法、直接关系、数据/边界、证据和处理状态
L4 图谱事实索引
   文件、类、函数、调用、继承、导入、测试、社区、执行流、影响面
L5 原始证据
   源码、SQL/DDL、配置、日志、Trace、接口样本、运行数据、业务访谈
```

`code-review-graph` 主要覆盖 L4，并能从 L4 为每个类构建 L3 类摘要卡，再把 AI 精确带到 L5。L0 至 L2 是在全类卡覆盖完成后产生的向上归纳结论，必须能回链到 L3/L4/L5 的证据、置信度和待验证项。

### 2.2 关系证据的等级

| 等级 | 含义 | 可作为什么结论的依据 |
|---|---|---|
| S1 静态直接证实 | 图谱边与源码直接证明调用、继承、导入或测试关系 | “A 调用了 B” |
| S2 静态推断 | 由命名、包结构、相邻逻辑或多个静态关系归纳 | “A 很可能承担订单协调职责” |
| R1 运行/配置证实 | 配置、日志、Trace、数据库数据或环境观察证明 | “该任务在生产按此频率运行” |
| B1 业务确认 | 业务负责人或领域专家明确确认 | “此状态代表经营意义上的结算完成” |
| U 未确认 | 当前仓库或资料不能证明 | 只能写入未知项，不能当作事实 |

任何业务结论至少标记其依据等级。尤其是反射、IoC、字符串路由、动态 SQL、数据库触发器、MQ Topic、前端动态调用、云端对端逻辑和历史数据语义，不能因图中没有边就被判定为“不存在”。

### 2.3 图谱中不等于业务域的结构

| 图谱结构 | 可提供的信号 | 不能直接得出的结论 |
|---|---|---|
| 包/目录 | 实现归属、命名边界 | 业务边界或组织责任 |
| 社区（community） | 静态耦合聚类 | 限界上下文已被确认 |
| 执行流（flow） | 从某入口可达的调用链 | 所有运行时路径、完整事务边界 |
| 高扇出类 | 协调或基础设施候选 | 它一定是领域服务 |
| 高扇入类 | 共用能力或核心模型候选 | 它一定是聚合根 |
| 无调用者节点 | 静态孤立候选 | 死代码 |

因此，正确顺序是“图谱建立全量类清单 → 每个类生成摘要卡 → 类卡与图谱边归并技术组件 → 结合配置/运行证据 → 归纳业务语义”，而不是跳过类覆盖、从少数图谱标签直接写业务结论。

## 3. 启动前：确定仓库、边界和保存策略

### 3.1 一个图谱对应一个代码仓库

图谱的 `--repo` 必须是实际业务仓库根，不要传工作区根目录。例如多仓库工作区中的后端、前端和 POS 本地服务应分别建图；跨仓关系在各仓图谱中登记为外部契约，不要为了图方便把无关仓库复制到同一仓库。

```powershell
# 查看当前已注册的仓库，确认不要误选工作区根目录
code-review-graph repos

# 首次纳入多仓库注册表（按实际仓库路径替换）
code-review-graph register "D:\mywork\nms4cloud" --alias nms4cloud

# 查看指定仓库图谱是否已经存在，并输出机器可读统计
code-review-graph status --repo "D:\mywork\nms4cloud" --json
```

若目标不是 Git 仓库、源码仅是反编译快照或需要把图谱数据库放到专用磁盘，可使用 `--data-dir <目录>`；同一仓库后续所有命令必须使用同一 `--data-dir`。

### 3.2 建图范围声明

在首次建图前写一份简短的“分析启动契约”，至少明确：

- 仓库路径、分支/快照日期、提交 ID（若存在）；
- 一方代码、三方依赖、生成文件、构建产物分别是否纳入；
- 后端、前端、脚本、SQL、配置、部署文件各自的覆盖范围；
- 可访问的数据库、日志、Trace、接口文档和业务专家；
- 不在本次仓库内的云端服务或硬件侧边界；
- 全量建图完成时间、后续增量同步策略与负责人。

这份声明防止“图谱没有索引到某目录”被误解成“系统没有这部分行为”。

## 4. 阶段 A：全量建图，只建立代码事实

首次分析时由工具完成全量解析。AI 不在这个阶段逐个阅读类，也不输出业务结论。

```powershell
$repo = "D:\mywork\nms4cloud"

# 首次：解析全部可纳入范围的文件，并执行流程、社区和全文索引后处理
code-review-graph build --repo $repo

# 验收：记录节点、边、流程、社区等统计信息
code-review-graph status --repo $repo --json
```

如首次只希望尽快取得原始静态结构，可使用 `--skip-postprocess`；但在进行系统骨架和业务闭环分析前，必须补做完整后处理：

```powershell
code-review-graph postprocess --repo $repo
code-review-graph status --repo $repo --json
```

### 4.1 阶段 A 的最小验收

- `status` 能显示目标仓库，而不是工作区根目录；
- 统计规模与仓库现实相符：文件、类、函数不应明显为零或异常偏小；
- 分析启动契约中声明的源码目录确实纳入；
- 流程和社区后处理已完成，或被明确登记为暂缓；
- 缺少语言解析、生成代码、反编译文件、二进制依赖等范围缺口已记录。

**不要因为“建图成功”就宣称“业务分析完成”。** 建图只说明可检索的静态索引已就绪。

## 5. 阶段 B：先总结全部类，建立类摘要卡库

这一阶段是后续一切“向上分析”的输入层：**所有可解析类必须先有且仅有一张类摘要卡。** 不允许直接从少数热门 Service、Controller 或图谱社区跳到领域结论；否则大量 DTO、转换器、配置、异步任务、DAO、异常处理器和基础设施类会在归纳时丢失。

这里的“总结全部类”不是把每个 `.java` / `.ts` 文件完整塞进同一轮上下文，也不是为每个类写一页散文。正确方式是按固定粒度批处理：图谱先提供类清单和关系，AI 每批读取有限数量的类及其一跳关系，写入简短的、可复查的类摘要卡；写完立即持久化，然后再处理下一批。

### 5.1 先冻结全类清单，作为覆盖率分母

全类清单必须在本轮分析的仓库快照上生成并冻结，至少包含：类的图谱节点 ID、全限定名、文件、语言、父类/接口、所属社区、是否测试类、是否可达入口、直接调用方/被调用方数量和摘要生成状态。它是“是否已总结所有类”的唯一分母。

推荐优先按图谱社区分批；一个过大的社区再按目录或文件前缀拆分。对于每个社区，先取得完整成员清单，然后对其中每个类都创建卡片：

```powershell
$repo = "D:\mywork\nms4cloud"

# 1. 先列出全部静态社区，作为默认的批次边界
code-review-graph communities --repo $repo --sort size --min-size 1

# 2. 取得一个社区的完整成员；成员清单是该批次的类覆盖分母
code-review-graph community --repo $repo --id <community-id> --members

# 3. 对成员中的每个关键类，取得最小结构和一跳关系
code-review-graph query --repo $repo children_of "<qualified-class-name>"
code-review-graph query --repo $repo callers_of "<qualified-class-name>"
code-review-graph query --repo $repo callees_of "<qualified-class-name>"
code-review-graph query --repo $repo inheritors_of "<qualified-class-name>"
code-review-graph query --repo $repo file_summary "<class-file-path>"
```

`community --members` 未覆盖的孤立类、测试类、生成类或社区外节点也必须进入全类清单。它们不能因为没有静态强连接而被静默丢弃，应登记为“孤立/基础设施/测试/生成候选”，并标明是否需要人工确认。

### 5.2 类摘要卡的固定字段与长度约束

每张类摘要卡应控制在约 80–200 个中文字符的主摘要，加上结构化字段；复杂类可以增加“关键方法摘要”，但不复制整段源码。建议存到独立的 `class-cards.yaml` / JSONL / SQLite 表中，再由工具生成阅读视图；不要把数千张卡堆成一份大 Markdown。

```yaml
- id: CLS-000421
  qualified_name: com.example.order.PayConfirmService
  file: src/main/java/com/example/order/PayConfirmService.java
  language: Java
  kind: Class
  class_role: 应用协调服务
  summary: >
    接收支付确认，校验订单当前状态，协调支付流水、订单状态与履约事件写入；
    本类未证明对端回调重试语义，需结合 MQ/HTTP 配置验证。
  key_methods:
    - name: confirm
      role: 支付确认主入口及状态协调
    - name: validatePayResult
      role: 支付结果前置校验
  inbound:
    - <graph-node-or-qualified-caller>
  outbound:
    - <graph-node-or-qualified-callee>
  data_or_boundary:
    - OrderMaster.status
    - PayFlow
    - FulfillmentEvent
  inferred_capabilities:
    - 支付确认
    - 订单最终一致性
  concerns:
    - 回调重复与乱序处理待运行证据
  evidence:
    - EVD-421
  confidence: S1
  analysis_status: 已摘要
  snapshot: <commit-or-analysis-date>
```

所有类都使用同一基础卡片，但按类别控制摘要深度：

| 类别 | 必须总结的内容 | 不必强行补出的内容 |
|---|---|---|
| Controller / Handler / Listener | 入口协议、请求类型、委托目标、鉴权/异常边界 | 其下层完整业务规则 |
| Service / Facade / Use Case | 协调目标、关键方法、状态/数据副作用、上下游 | 未由源码证明的业务意图 |
| Entity / Aggregate / DTO / VO | 身份、字段组、生命周期、持久化/API角色 | 不存在的业务行为 |
| Repository / Mapper / DAO | 数据对象、读写意图、查询/更新边界 | 表字段的经营含义（除非有证据） |
| Converter / Assembler | 转换方向、字段丢失/默认值、调用位置 | 它是业务规则的假设 |
| Config / Factory / Adapter | 配置项、创建/路由机制、外部边界 | 运行环境的真实值 |
| Task / Retry / Consumer | 触发来源、处理对象、重试/补偿候选 | 对端投递保证 |
| Exception / Security / Filter | 生效范围、拦截行为、错误/权限语义 | 所有调用链均受其保护的假设 |
| Test | 覆盖的类/场景、断言行为、缺口 | 测试未覆盖路径的正确性 |
| 基类 / 工具类 / 常量类 | 被复用能力、继承/引用范围、潜在横切影响 | 业务域归属 |

### 5.3 类摘要的批处理纪律

1. 固定一个批次（优先一个社区，超大时按目录拆分），先锁定其中所有类；
2. 对每个类先读取图谱结构字段与一跳关系；只有职责不清、状态写入、外部调用、动态行为或副作用会改变摘要时才打开源码片段；
3. 先写“静态事实摘要”，再写不超过两句的职责解释；事实与推断分开标记；
4. 每完成一个类立即写入类卡库，不依赖当前对话记忆保存；
5. 批次结束后对照该批全类清单检查 `已摘要 + 已排除 + 待人工确认 = 批次总数`；
6. 不允许以“类看起来简单”为由漏掉类；简单类可使用极短卡片，但必须有分类、用途、证据和状态；
7. 一个类的摘要只描述本类责任和直接关系，不提前将它命名为某个业务域或闭环成员；领域归属是下一阶段的向上结论。

### 5.4 全类摘要阶段的验收门禁

| 指标 | 通过条件 |
|---|---|
| 类清单覆盖率 | `已摘要 + 已排除 + 待人工确认 = 冻结全类清单总数` |
| 未处理类 | 必须为 0；无法解析类须有原因与补救计划 |
| 卡片唯一性 | 每个图谱类节点/全限定名在同一快照仅有一张有效卡 |
| 证据可追溯 | 每张卡均可回链到图谱节点、文件和快照；关键类另有源码符号/行号 |
| 摘要粒度 | 不复制整段源码；主摘要受长度控制；复杂逻辑拆到关键方法列表 |
| 不确定性 | 动态依赖、运行配置和推断必须显式标为 `U` / `S2`，不得伪装为事实 |

只有全类摘要阶段通过，才允许进入“从类卡向上归纳”。

## 6. 阶段 C：从全类摘要卡提取系统技术骨架

现在才将类卡按图谱关系和职责标签归并成技术协作单元。先取得结构总览、社区和入口流程：

```powershell
$repo = "D:\mywork\nms4cloud"

# 系统级依赖方向与耦合概览
code-review-graph architecture --repo $repo --detail-level standard

# 静态耦合社区：是类卡聚类候选，不直接等同业务域
code-review-graph communities --repo $repo --sort size --min-size 5

# 从入口出发的已存执行流，优先看关键性高的流
code-review-graph flows --repo $repo --sort criticality --limit 30
```

对每个有价值的社区或执行流，将其成员类卡、跨社区边和必要源码一并加载；先归纳入口、协调、数据、异步、边界和横切能力，再决定是否形成技术组件：

```powershell
code-review-graph community --repo $repo --id <community-id> --members
code-review-graph flow --repo $repo --id <flow-id> --source
```

### 6.1 必须优先识别的骨架节点

| 类别 | 图谱切入方式 | 后续人工/AI 要确认的事实 |
|---|---|---|
| 业务入口 | `flows`、`search` | HTTP、RPC、MQ、监听器、定时任务、CLI、文件导入、IPC 的实际触发条件 |
| 协调节点 | 入口流中的高扇出函数 | 调度哪些对象、事务/异常边界在哪里 |
| 数据节点 | 入口流中的 Repository、Mapper、DAO、实体 | 表、关键字段、读写语义、事实源位置 |
| 状态节点 | 搜索 `status`、`state`、状态枚举与写入方法 | 全部迁移、前置条件、非法状态和历史语义 |
| 异步节点 | 搜索 `task`、`retry`、`compensate`、`consumer` | 触发器、重试策略、幂等键、补偿和人工收敛 |
| 外部边界 | 搜索 Client、Publisher、Listener、Adapter | 协议、契约、超时、认证、失败处理和对端责任 |
| 配置节点 | 搜索配置类、读取点、开关名 | 适用范围、默认值、版本和运行时覆盖方式 |

此阶段形成的产物是“技术骨架登记册”：每个候选节点只记录职责假设、关联图谱节点、证据位置、置信度和待验证问题；不要过早把它写成聚合根或业务域。

## 7. 阶段 D：用图谱组装“最小充分上下文包”

AI 的分析单元不是一个包、一个类或一篇 Markdown，而是一个可验收的业务问题或业务闭环。每次开始前，先通过图谱取得**够用但不过量**的子图，再读取必要源文件。

### 7.1 标准查询顺序

以“分析订单支付成功后为什么会触发哪些后续动作”为例：

```powershell
$repo = "D:\mywork\nms4cloud"

# 1. 精确或模糊定位候选类、函数、文件
code-review-graph search --repo $repo "payment" --kind Function --limit 30
code-review-graph search --repo $repo "OrderService" --kind Class --limit 10

# 2. 从关键节点向上确认全部已知调用者，避免只从一个入口看问题
code-review-graph query --repo $repo callers_of "<qualified-function-or-class-name>"

# 3. 向下查看直接协作对象；只对真正相关的节点继续展开
code-review-graph query --repo $repo callees_of "<qualified-function-or-class-name>"

# 4. 需要查看接口实现、父子结构或文件摘要时使用对应预定义查询
code-review-graph query --repo $repo inheritors_of "<interface-or-base-class>"
code-review-graph query --repo $repo children_of "<class-name>"
code-review-graph query --repo $repo file_summary "<relative-or-absolute-file-path>"
```

可用的 `query` 关系只包括 `callers_of`、`callees_of`、`imports_of`、`importers_of`、`children_of`、`tests_for`、`inheritors_of` 与 `file_summary`。没有图谱关系的动态行为，必须用源码、配置、日志或运行环境补证，不能伪造为图谱结论。

### 7.2 上下文包的固定结构

每个任务只携带下列信息；超过预算时先压缩摘要或拆分任务，而不是继续堆叠源码。

```text
[任务]
- 待回答的业务问题、边界和验收条件。

[L0 全局约束]
- 系统身份、事实源、部署/一致性模式、全局不变量、最高风险、相关未知项。

[L1 关联能力]
- 当前问题直接涉及的领域/能力及其上游、下游、外部边界。

[L2 目标闭环]
- 正常路径、异常路径、异步路径、关键状态、必须验证的副作用。

[L3 已覆盖的类摘要卡]
- 与当前问题有关的入口类、协调类、实体/DTO、DAO、任务、消费者、配置、测试和横切类卡。
- 每张卡保留类责任、关键方法、直接入/出边、数据/边界、证据等级和待确认项。

[L4 图谱关系子图]
- 在 L3 类卡之间补充当前问题所需的调用方、被调用方、继承、导入、社区和执行流关系；只展开会改变结论的边。

[L5 最小原始证据]
- 仅包含 L3/L4 指向且仍无法确认的函数、配置、SQL、接口契约、日志或 Trace 片段。

[未知项]
- 不能由当前资料证明的事实、所需证据及责任方。
```

### 7.3 上下文预算与停止规则

建议每个闭环按“先图后源码”分批进行：

1. 先读取 L0、关联 L1 和图谱子图摘要；
2. 只展开一个入口或一个关键状态写入点的直接调用者/被调用者；
3. 新发现异步、外部或跨域边时，登记为待扩展节点；
4. 只有该节点会改变业务结论、状态迁移、数据副作用、异常处理或置信度时，才读取源码；
5. 连续一轮没有新增入口、状态、读写、副作用、异常路径或证据等级时，停止扩展并记录缺口。

这条停止规则是防止 AI 为追求“读得更多”而重新耗尽上下文的核心机制。

## 8. 阶段 E：从技术骨架向上归纳业务闭环

图谱提供的是“谁依赖谁、谁调用谁”；业务分析要在此基础上完成三次抽象跃迁：

```text
类 / 函数 / 字段 / 调用边
  → 技术协作单元（入口、协调、存储、异步、边界）
    → 业务能力（点餐、收款、履约、库存、日结等）
      → 业务闭环（目标、责任、状态、规则、资源、时间、异常、证据）
```

### 8.1 业务闭环的选择原则

闭环应按“业务结果可验证”切分，不按包名切分。好的闭环例子：

- 顾客需求确认至可履约；
- 支付发起至资金与订单最终一致；
- 退款/反结账至资金、权益、库存和凭证的回补；
- 商品可售控制至占用、扣减、释放和日结；
- 主数据变更至终端生效和失败补偿；
- 班次交接至资金核对、经营归档和责任确认。

“分析 `order` 包”或“分析 `PayService` 类”只能作为取证任务，不是业务分析交付单位。

### 8.2 每个闭环的强制问题

| 维度 | 必须回答的问题 |
|---|---|
| 目标 | 系统要为谁产生什么可验证结果？失败代价是什么？ |
| 主体 | 谁发起、执行、批准、监督、受益和承担后果？ |
| 对象 | 哪些对象有独立身份、生命周期、历史和规则？ |
| 资源 | 库存、桌台、资金、设备、时间窗口、额度等如何占用和释放？ |
| 规则 | 哪些是不变量，哪些是策略，何时生效，冲突如何处理？ |
| 时间 | 业务发生、生效、结算、超时、版本和历史解释以什么时间为准？ |
| 不确定性 | 重复、并发、超时、断网、回调乱序、外部失败如何收敛？ |
| 证据 | 每项结论的图谱节点、源码、配置、日志和确认状态是什么？ |

### 8.3 一个闭环的最小完成条件

对每个闭环至少完成以下追踪，才可称为“已分析”：

```text
正向：入口 → 协调 → 状态/数据变化 → 同步或异步副作用
反向：核心对象/状态字段 → 全部已知写入者与读取者
横向：替代入口、消息消费者、定时任务、配置分支与外部调用
异常：拒绝、重试、补偿、幂等、人工处理与未收敛结果
回填：新事实、冲突、证据等级、覆盖状态、未知项
```

如果当前图谱只证明部分静态链路，交付应写“局部静态闭环候选”，不能宣称完整运行闭环。

## 9. 阶段 F：图谱取证后回填“业务事实层”

图谱数据库是代码关系索引，不能取代业务语义、证据等级和未知项登记。每次分析结束，先回填结构化事实，再生成面向人的 Markdown。

本目录已有 `产物输出规范-数据驱动配套/`，其原则是“数据是源，文档是视图”。应沿用这套机制；其中**类摘要卡库是所有向上归纳的前置事实层**。若现有数据模式尚未包含它，应新增独立的 `class-cards.yaml`（或等价 JSONL/SQLite 表），不要把类卡混进 `entities.yaml`：代码类不天然等于业务实体。

| 图谱发现 | 回填位置 | 必填内容 |
|---|---|---|
| 全部类及其统一摘要 | `class-cards.yaml` / JSONL / SQLite | 图谱节点、全限定名、类角色、摘要、关键方法、直接关系、证据、快照、处理状态 |
| 业务对象、候选聚合与关系 | `entities.yaml` | 对象 ID、职责、领域、状态、关系、关联类卡与图谱/源码证据 |
| 业务规则和依赖 | `rules.yaml` | 规则类型、适用条件、优先级、证据等级、冲突与未知项 |
| 状态转换 | `states.yaml` | 起止状态、触发器、前置条件、持久化与副作用、证据 |
| 正常/异常/补偿流程 | `flows.yaml` | 步骤、入口、调用链、失败/补偿、关联事件和证据 |
| 异步事实 | `events.yaml` | 触发者、订阅者、Topic/契约、幂等键、重试与证据 |
| 技术债务、覆盖缺口 | `quality.yaml` | 风险、影响、优先级、待补证责任和完成条件 |
| 原始证据 | `evidence.yaml` | 图谱节点/命令、文件、符号、行号、快照、置信度 |

### 9.1 证据登记的推荐格式

现有 `evidence.yaml` 的 `locate`、`file`、`line`、`commit`、`snippet` 和 `confidence` 字段可用于保存原始证据。建议在 `locate` 中使用稳定可复查的图谱查询描述，例如：

```yaml
- id: EVD-042
  locate: "code-review-graph query callers_of com.example.order.PayService.confirm"
  file: "src/main/java/com/example/order/PayService.java"
  line: "118-167"
  commit: "<分析快照提交ID或日期>"
  confidence: L4
  snippet: "支付确认后写订单状态，并发布履约事件；异常分支待补运行证据。"
```

这里的命令是证据定位提示，不替代源码行号。图谱索引重建后，仍应能通过文件、符号和快照重新取得事实。

### 9.2 回填的不可省略字段

每条由 AI 新增或修订的事实至少携带：

- 全局唯一 ID；
- 所属闭环、领域和上下游能力；
- 陈述内容及其适用范围；
- 图谱节点或查询路径；
- 源码/配置/日志等原始证据；
- 证据等级与置信度；
- 已知反例、边界条件、未确认项；
- 最后校验的仓库快照与日期。

没有证据、置信度和未知项的自然语言总结，不得作为后续 AI 的权威记忆。

## 10. 阶段 G：持续同步与增量分析

图谱一旦落后于代码，所有调用关系和影响分析都可能失效。每次分析或评审前先按改动规模更新图谱。

```powershell
$repo = "D:\mywork\nms4cloud"

# 常规改动：仅重新解析差异文件，并显示变更风险摘要
code-review-graph update --repo $repo --brief

# 指定与某个基线比较；适用于发布分支、合并或排障基线
code-review-graph update --repo $repo --base "origin/main" --brief

# 已确认图谱是最新时，纯读取当前变更的影响，不重新解析
code-review-graph detect-changes --repo $repo --base "origin/main" --brief

# 对指定文件做调用影响面分析，控制深度和返回数量
code-review-graph impact --repo $repo --files "src/main/java/com/example/order/PayService.java" --depth 3 --max-results 100
```

当发生首次建图、图谱损坏、解析规则升级、仓库大规模迁移或长期未同步时，再使用 `build` 重建。不要对日常少量改动反复全量建图。

### 10.1 变更后的最小循环

```text
代码/配置变更
  → code-review-graph update
  → status 确认图谱刷新
  → impact / detect-changes 找到受影响类、调用边和执行流
  → 先更新受影响类的摘要卡及其证据快照
  → 由变更后的类卡重新检查组件、业务事实、未知项和阅读视图
  → 补读最小源码、配置和测试
  → 运行针对性测试或手工验证
```

### 10.2 图谱维护的安全边界

- `build`、`update`、`postprocess` 会更新本地图谱数据；使用前确认 `--repo` 指向目标仓库；
- `detect-changes` 和 `impact` 是只读分析，可用于先判断是否值得深挖；
- `embed --embedding-provider openai/google/minimax` 可能将源代码派生文本传到第三方并产生费用；未获明确授权时不使用云端嵌入；
- `visualize --serve` 会启动本地服务，仅在需要可视化时使用；
- `dead-code`、`large-functions`、`refactor` 的结果都是候选，不应直接删改遗留代码。

## 11. 图谱与类卡驱动的全局验收门禁

传统门禁只检查“文档存在”和“引用行号有效”；图谱驱动分析还必须检查全局关系是否形成足够闭包。

| 门禁 | 验收问题 | 可用图谱动作 | 不能由图谱单独证明的部分 |
|---|---|---|---|
| G0 图谱可用 | 目标仓库、范围和统计是否正确？ | `status`、`architecture` | 被排除目录的运行行为 |
| G1 全类清单 | 冻结快照中的每个可解析类是否进入唯一清单？ | `communities --members`、`search --kind Class`、文件清单交叉核对 | 解析器未支持的语言/生成物 |
| G2 类卡覆盖 | 每个类是否存在唯一有效类卡，且 `已摘要 + 已排除 + 待人工确认 = 总数`？ | 类卡库统计、快照比对 | 无法静态解析类的真实职责 |
| G3 入口覆盖 | 每个 HTTP、RPC、MQ、任务、IPC、批处理入口是否归属到类卡、组件和闭环？ | `flows`、`search` | 动态注册、配置启停的实际入口 |
| G4 数据覆盖 | 核心实体、表、状态字段是否有已知读写者、类卡和事实源？ | `search`、`query callers_of/callees_of` | 动态 SQL、触发器、直接库操作 |
| G5 状态覆盖 | 每个关键状态迁移是否有触发、前置、持久化、异常和下游副作用？ | 调用子图 + 源码取证 | 运行时乱序、历史数据例外 |
| G6 异步覆盖 | 每个消息、任务、回调是否有生产、消费、重试和幂等结论？ | `flows`、`search`、调用子图 | Topic 配置、对端消费者、实际投递语义 |
| G7 跨域覆盖 | 每个外部调用知道协议、契约、超时、失败和责任边界吗？ | `imports_of`、调用子图 | 对端实现、网络与权限策略 |
| G8 闭环交付 | 核心业务闭环是否由对应类卡归纳而来，并含正常、异常、补偿、未知项和证据？ | 类卡关联、事实层校验、生成视图 | 业务目标和真实操作流程需人类确认 |

全局覆盖率应分维度报告，而不是汇总成一个虚假的“分析完成百分比”。例如入口覆盖率、状态字段覆盖率、异步契约覆盖率、证据 L4/L5 比例、未确认项数量和运行验证比例应分别统计。

## 12. 可直接复用的端到端执行清单

```powershell
# 0. 设定唯一目标仓库。不要使用多仓库工作区根目录。
$repo = "D:\mywork\nms4cloud"

# 1. 构建/刷新完整静态图谱，并冻结本轮分析快照。
code-review-graph status --repo $repo --json
code-review-graph build --repo $repo
code-review-graph status --repo $repo --json

# 2. 导出或取得全类清单：必须覆盖社区成员、孤立类、测试类和社区外节点。
#    JSON 导出可作为节点清单来源；随后按 Class 节点、文件扫描和图谱统计交叉核对。
code-review-graph visualize --repo $repo --mode full --format json
code-review-graph communities --repo $repo --sort size --min-size 1

# 3. 分批为清单中的每个类写入唯一类摘要卡；批次优先按社区，再按目录拆分。
code-review-graph community --repo $repo --id <community-id> --members
code-review-graph query --repo $repo children_of "<qualified-class-name>"
code-review-graph query --repo $repo callers_of "<qualified-class-name>"
code-review-graph query --repo $repo callees_of "<qualified-class-name>"
#    每个类完成后立即写入 class-cards.yaml / JSONL / SQLite。
#    达到“已摘要 + 已排除 + 待人工确认 = 冻结全类总数”后才进入下一步。

# 4. 只使用已覆盖的类卡和图谱边归纳技术组件、业务能力及可验证业务闭环。
code-review-graph architecture --repo $repo --detail-level standard
code-review-graph flows --repo $repo --sort criticality --limit 30
code-review-graph flow --repo $repo --id <flow-id> --source

# 5. 针对闭环中的证据缺口才打开源码/配置/SQL/日志，
#    然后把对象、规则、状态、流程、事件、证据和未知项回填到事实层。

# 6. 生成/校验阅读视图（目录内已有数据驱动配套工具）。
Push-Location ".\产物输出规范-数据驱动配套\tools"
python validate-data.py "..\data\<项目名>"
python render-artifacts.py "..\data\<项目名>" "..\generated\<项目名>"
python check-artifacts.py "..\generated\<项目名>"
Pop-Location

# 7. 后续改动前先增量更新，先更新受影响类卡，再重新向上归纳。
code-review-graph update --repo $repo --brief
code-review-graph impact --repo $repo --files "<changed-file>" --depth 3 --max-results 100
```

命令中的 `<项目名>`、`<业务术语或关键类名>`、`<qualified-name>` 与 `<changed-file>` 必须替换为实际值。分析任务的输出不是命令执行成功，而是“有证据、有边界、有未知项、可回填、可复核”的业务闭环事实。

## 13. 常见误区

| 误区 | 为什么失败 | 正确做法 |
|---|---|---|
| 让 AI 在一个上下文中读完所有类 | 上下文必然耗尽，且早期结论会被遗忘 | 先为每个类生成并持久化受限长度的类摘要卡，再按批加载类卡向上归纳 |
| 社区就是业务域 | 社区只反映静态耦合 | 用社区产生候选，再以责任、对象、规则和变化边界确认 |
| 一张架构图就够 | 架构图通常隐藏状态、数据、异常和补偿 | 从入口、数据、状态、异步、外部边界做双向闭环 |
| 图中没有调用边就说明不存在 | 动态框架、配置、反射和跨仓调用会漏边 | 将其标为 U，补配置、运行和对端证据 |
| 多写报告即可积累记忆 | Markdown 无法稳定检索、去重、更新和覆盖校验 | 先回填结构化事实，报告作为视图 |
| 只从 `callees_of` 向下追 | 会遗漏替代入口、定时任务、消息消费者和回写者 | 同时追 `callers_of`、入口流、状态读写和异步节点 |
| `dead-code` 结果可直接删除 | 反射、框架、脚本或外部调用常被静态图漏掉 | 仅作为人工核查候选，结合运行证据确认 |
| 依赖云端嵌入搜索 | 可能泄露源码派生文本并增加成本 | 默认使用本地图谱查询；云端嵌入需明确授权 |

## 14. 结论

`code-review-graph` 的价值不是让 AI 一次装下整个系统，而是先把全量代码关系持久化到外部图谱，再将每一个类压缩为可检索、可回溯的类摘要卡。之后，AI 每次只加载：

\[
\text{当前归纳层所需的类摘要卡}
+
\text{关联的全局约束}
+
\text{类卡之间的图谱关系}
+
\text{必要的最小源码证据}
+
\text{明确登记的未知项}
\]

正确路径是：

```text
全量建图 → 冻结全类清单 → 全类摘要卡 → 技术组件 → 业务能力 → 业务闭环
        → 结构化回填 → 增量更新受影响类卡 → 重新向上归纳
```

系统规模不再决定 AI 能否保持全局位置；它只决定类卡的生成批次、图谱构建时间和待验证边界的数量。

> **最终原则**：图谱是全局事实索引，类摘要卡是自下而上的分析原子，闭环是业务交付单位，YAML/数据库是长期记忆，Markdown 是阅读视图；任何一层都不能替代另一层。
