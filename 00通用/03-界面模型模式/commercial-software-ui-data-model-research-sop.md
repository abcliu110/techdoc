# 商业标杆软件 UI 与数据模型逆向研究 SOP

版本：1.0  
适用对象：具备联网检索、网页浏览、截图理解和结构化输出能力的 AI 研究代理  
研究目的：从商业软件公开可观察的 UI 与交互证据中，重建其信息架构、领域模型候选、UI 与模型映射机制及设计取舍，并沉淀为可复用的商业软件设计知识。

## 0. 总纲

本研究不是截图收集、功能盘点或界面临摹，而是一次“商业软件逆向认知工程”。

研究主链：

```text
行业问题与用户任务
-> 系统边界与系统关系
-> 模块边界与业务能力
-> 页面结构与导航路径
-> 页面中的实体、关系、状态、动作和规则
-> 候选领域模型与读写模型
-> 模型如何投影为 UI
-> UI 如何允许用户观察和改变业务世界
-> 设计取舍、适用边界与可迁移原则
```

### 0.1 必须回答的核心问题

1. 软件把现实业务世界划分成了哪些系统、模块、业务对象和流程？
2. 系统、模块、页面和实体之间的关系如何通过导航表达？
3. 页面中的字段、列表、详情、页签、按钮、状态、时间线和报表分别在投影什么模型？
4. 哪些 UI 是领域模型的直接投影，哪些是任务型组合视图、分析读模型或个性化视图？
5. 这种映射优先保障了什么，又牺牲了什么？
6. 哪些结论可迁移为自己的设计原则，哪些只在该行业、角色、规模或产品约束下成立？

### 0.2 结论边界

- 可以推导：候选领域对象、逻辑属性、对象关系、聚合边界、状态机、业务动作、规则、权限边界、指标口径、读模型和集成边界。
- 不可仅凭 UI 断言：真实表名、物理表数量、主外键实现、范式、索引、分库分表、事件存储方式和内部服务拓扑。
- 所有推导必须标为“候选模型”，除非得到官方数据字典、API Schema、导入导出 Schema 或其他直接证据确认。

## 1. 研究输入与范围冻结

开始前填写《研究任务卡》，未填写不得进入采集阶段。

| 字段 | 要求 |
|---|---|
| 研究对象 | 产品名、厂商、产品线 |
| 研究版本 | 版本号或观察日期；SaaS 无版本号时记录日期 |
| 行业场景 | 例如 CRM 销售、ERP 采购、ITSM 事件管理 |
| 用户角色 | 至少指定一个主角色；不同角色不得混采 |
| 套餐/部署 | Free/Pro/Enterprise，Cloud/On-premise |
| 地域/语言 | 不同地区版本和术语可能不同 |
| 研究主线 | 一个端到端任务，例如“线索到回款” |
| 深度边界 | 全产品地图、单系统、单模块或单业务旅程 |
| 对比对象 | 若做横向研究，统一研究场景和角色 |
| 截止日期 | 所有证据必须可追溯至该日期之前 |

### 1.1 研究单元

一次研究以一个“产品版本 × 套餐 × 地域 × 用户角色 × 业务场景”为最小单元。任何一个维度改变，都应建立新单元，禁止混合成一个结论。

### 1.2 三种研究范围

- 全景级：建立系统宇宙、产品模块地图和全局导航，仅做关键模块抽样。
- 模块级：完整拆解一个模块的对象、页面、流程、权限和指标。
- 任务级：沿一个端到端用户任务跨系统追踪，最适合分析真实导航与上下文传递。

建议顺序：先做全景级定边界，再选择高价值模块做模块级，最后用任务级验证模型是否真正闭环。

## 2. 证据协议

### 2.1 来源优先级

| 等级 | 来源 | 可支持的结论 |
|---|---|---|
| E1 直接证据 | 可操作的官方产品、官方试用/沙箱、官方 API/Schema、官方数据字典、官方导入导出模板 | UI 行为、字段、状态、对象与接口契约 |
| E2 强证据 | 官方帮助文档、管理员指南、官方培训、发布说明、官方演示视频 | 功能结构、业务语义、版本行为 |
| E3 佐证 | 官方应用市场、官方集成文档、可信实施伙伴材料、认证课程 | 扩展关系、典型配置、实施语义 |
| E4 弱证据 | 高质量第三方评测、用户教程、公开截图/视频 | 发现线索；关键结论必须再验证 |
| E5 线索 | 搜索摘要、论坛、营销聚合页、无版本截图 | 只生成待验证问题，不得单独支撑结论 |

原则：搜索引擎是发现工具，不是证据本身；优先保存其指向的原始页面。

### 2.2 查询矩阵

AI 必须围绕同一研究对象组合检索，不得只搜索“产品名 + UI”。

```text
产品名 + product tour / demo / getting started
产品名 + navigation / workspace / module / app
产品名 + object / entity / record / data model
产品名 + API reference / schema / metadata
产品名 + import template / export fields
产品名 + workflow / lifecycle / status / approval
产品名 + roles / permissions / sharing / visibility
产品名 + relationship / parent child / related records
产品名 + dashboard / report / metric definition
产品名 + integration / webhook / event / release notes
产品名 + 业务对象名 + create/edit/detail/list
产品名 + 业务任务 + tutorial
```

对每个核心结论至少使用两类不同来源交叉验证；状态、权限、关系基数和业务规则等高风险结论，必须尽量包含一个 E1 或两个相互独立的 E2。

### 2.3 证据台账

每条证据分配唯一编号 `EV-{产品缩写}-{四位序号}`，记录：

| 字段 | 内容 |
|---|---|
| Evidence ID | 唯一编号 |
| 页面标题/画面 | 原始标题或视频时间点 |
| URL | 直接来源地址 |
| 发布者 | 官方、伙伴或第三方 |
| 证据等级 | E1-E5 |
| 产品上下文 | 版本、套餐、地域、语言、角色 |
| 采集时间 | ISO 日期时间 |
| 原始摘录 | 原文、字段序列、交互步骤；不得先改写 |
| 截图/帧 | 文件名或可定位引用 |
| 支持的观察 | 只能写该证据直接显示的内容 |
| 局限 | 看不到什么、可能受什么条件影响 |

截图必须包含足以定位上下文的导航、标题或地址信息；局部裁剪另存，但不能替代上下文截图。视频证据必须记录精确时间码。

### 2.4 确定性标签

所有研究语句必须使用以下标签之一：

- `[O-观察]`：页面、文档或可复现实验直接显示。
- `[C-确认]`：由高等级直接证据确认的模型事实。
- `[I-推断]`：由一个或多个观察推导，必须给出推理链与候选解释。
- `[H-假设]`：证据不足，只能进入待验证清单。
- `[X-未知]`：公开资料无法判断，不得补全。

禁止使用“显然、应该、一般是”代替证据标签。

### 2.5 合规边界

- 仅使用公开资料、合法获得的试用账户和被授权的环境。
- 遵守网站条款、robots、速率限制、版权和隐私要求。
- 不绕过登录、付费墙、验证码、访问控制或技术保护。
- 不采集个人数据、客户真实业务数据、密钥或敏感配置。
- 引用截图和原文只用于研究证据，记录来源与日期。

## 3. 八阶段执行流程

### 阶段 A：业务问题与角色建模

先研究产品解决的现实业务问题，再看页面。输出：

1. 目标行业与价值链位置。
2. 关键角色、职责、决策、输入与输出。
3. 角色的核心任务和成功指标。
4. 端到端业务旅程及异常路径。
5. 行业不变量与产品特有做法分离。

门槛：如果无法用业务语言描述用户为什么使用该系统，则禁止进入 UI 建模。

### 阶段 B：重建系统宇宙

识别同一厂商产品族及外部系统，建立《系统关系图》。逐个系统记录：

- 系统目标和主要角色。
- 拥有的核心业务能力与主数据。
- 与其他系统之间的入口、跳转和嵌入方式。
- 上下文是否保留：身份、租户、当前记录、筛选条件、返回位置。
- 数据交换线索：导入导出、同步、API、Webhook、事件、共享主数据。
- 边界类型：独立产品、子系统、模块、插件、外部集成；不确定时保留多候选。

导航证据包括：全局产品切换器、应用启动器、跨产品深链、统一搜索、通知中心、用户/组织切换器、嵌入面板。

### 阶段 C：重建模块与全局导航

遍历所有一级、二级导航，生成《模块-能力-导航矩阵》：

| 模块 | 业务能力 | 主要对象 | 主要角色 | 入口 | 下级页面 | 跨模块跳转 | 全局/上下文导航 |
|---|---|---|---|---|---|---|---|

判定导航主要表达哪一种组织原则：

- 按业务能力：销售、服务、财务。
- 按核心对象：客户、订单、资产。
- 按用户任务：收件箱、待审批、我的工作。
- 按流程阶段：获客、成交、履约。
- 按组织/空间：项目、团队、工作区、门店。
- 混合结构：明确每一层采用的原则及切换成本。

同时记录全局导航、局部导航、上下文导航和关系导航。不要把菜单层级直接等同于系统架构层级。

### 阶段 D：建立页面清单与任务路径

页面编号 `PG-{模块缩写}-{四位序号}`。每个页面记录：

- 页面名称、URL/路由形态、所属模块和入口。
- 页面类型：工作台、列表、看板、日历、详情、编辑、向导、关系页、报表、设置等。
- 面向角色、用户目标、进入前提、离开路径。
- 主对象、辅助对象、主要动作、状态反馈。
- 面包屑、页签、返回、深链、最近访问、收藏等导航机制。
- 创建/编辑后返回哪里，筛选、分页和上下文是否保留。

随后选择 3-5 条高价值任务路径，按“起点 -> 操作 -> 页面 -> 数据变化 -> 反馈 -> 下一步”逐步走查。必须包含至少一条异常或撤销路径。

### 阶段 E：页面解剖

对关键页面按下列层次标注，元素编号 `EL-{Page ID}-{三位序号}`：

1. 页面框架：标题、对象标识、状态、主动作、次动作。
2. 信息区块：摘要、字段组、关系页签、时间线、附件、讨论、指标。
3. 集合组件：表格、看板、树、日历、图表、嵌套列表。
4. 交互组件：筛选、排序、搜索、批量操作、内联编辑、向导。
5. 反馈机制：校验、权限提示、空状态、加载、冲突、撤销、审计。
6. 个性化：保存视图、列配置、布局、角色差异、管理员元数据配置。

每个元素至少记录：可见文本、数据形态、可执行动作、前置条件、结果、关联证据、初步模型含义。

### 阶段 F：由 UI 生成候选领域模型

#### F1. 映射规则

| UI 证据 | 首选模型解释 | 必须排查的替代解释 |
|---|---|---|
| 独立列表 + 创建 + 详情 + 永久标识 | 候选实体/聚合根 | 搜索索引、报表读模型、外部对象 |
| 详情字段组 | 属性或值对象 | 计算字段、跨对象投影、展示格式 |
| 详情页签“相关 X” | 对象关系 | 动态查询、权限过滤、嵌入应用 |
| 单选/多选关联控件 | to-one / to-many 关系候选 | 枚举、标签、派生建议 |
| 父子表格/行项目 | 聚合或组合关系 | 普通多对多、快照、视图拼接 |
| 状态标签 + 条件动作 | 状态机和命令 | 派生状态、权限导致的按钮变化 |
| 时间线/活动流 | 事件、审计记录或交互历史 | 多源聚合读模型 |
| 向导步骤 | 长事务、阶段性命令或流程编排 | 纯前端分步录入 |
| 看板列 | 状态/阶段枚举 | 用户自定义分类或队列 |
| 树/层级导航 | 自引用层级或包含结构 | 分类视图、权限继承树 |
| 仪表盘/报表 | 指标、事实和维度的读模型 | 缓存快照、外部 BI 数据集 |
| 全局搜索 | 跨对象检索能力 | 不能据此证明共享存储 |
| 隐藏/禁用字段和动作 | 权限或状态约束 | 套餐、功能开关、上下文差异 |
| 自动填充/联动字段 | 派生规则、默认规则或复制语义 | 客户端便利行为 |
| 重复检测/合并 | 身份识别与唯一性规则 | 模糊搜索提示 |
| 导入导出/API Schema | 对象、字段和契约强证据 | 传输 DTO 不等于领域/物理模型 |

#### F2. 候选模型对象

为每个候选项建立卡片：

- `EN-*` 实体/值对象：身份、属性、生命周期、拥有者。
- `RL-*` 关系：两端对象、语义、方向、候选基数、必选性、生命周期依赖。
- `SM-*` 状态机：状态、允许转换、触发动作、守卫条件、副作用、终态。
- `BR-*` 业务规则：条件、动作、范围、例外、来源。
- `CM-*` 命令：发起角色、目标对象、输入、校验、结果。
- `EVT-*` 领域/集成事件候选：发生时机、载荷线索、订阅方线索。
- `PM-*` 权限模型：主体、资源、动作、范围、继承、字段级限制。
- `MT-*` 指标：名称、计算口径、时间窗、粒度、维度、刷新线索。
- `BC-*` 业务边界：拥有对象、规则和术语；跨边界引用方式。

#### F3. 推断纪律

1. 一条 UI 观察先生成不少于两个合理解释，再用新证据淘汰。
2. 关系基数不能由一个页面上的当前数据量判断；寻找创建控件、过滤器、API、导入模板和帮助文档。
3. “一个页面”不等于“一个实体”，“一个页签”不等于“一张表”，“一个字段”不等于“持久化列”。
4. 区分写模型、事务详情读模型、搜索模型、分析模型和个性化视图。
5. 区分核心领域对象、配置元数据、身份权限对象和外部系统代理对象。
6. 对聚合边界只在共同创建、共同保存、级联删除、一致性约束或事务动作有证据时提出。
7. 对每个关键模型元素列出反证条件：发现什么证据会使该模型失效。

#### F4. 置信度计算

置信度不是主观印象。按以下维度各记 0-2 分：

- 来源强度：E1=2，E2/E3=1，E4/E5=0。
- 独立交叉验证：两类独立来源=2，同类多来源=1，单来源=0。
- 行为验证：可重复操作并观察结果=2，仅文档描述=1，无=0。
- 替代解释排除：主要替代项已排除=2，部分排除=1，未排除=0。
- 上下文一致：版本/角色/套餐完全一致=2，部分未知=1，冲突=0。

总分：8-10 高，5-7 中，0-4 低。任何高置信模型结论至少要有一个 E1 或两个独立 E2；否则最高只能为中。

### 阶段 G：建立 UI 与模型双向映射

必须同时建立两张矩阵，缺一不可。

#### G1. UI -> 模型矩阵

| Page/Element ID | UI 表象 | 用户意图 | 读取对象/属性/关系 | 执行命令 | 状态/规则/权限 | 证据 ID | 结论标签与置信度 |
|---|---|---|---|---|---|---|---|

#### G2. 模型 -> UI 矩阵

| Model ID | 模型元素 | 创建入口 | 查看位置 | 编辑方式 | 关系导航 | 状态反馈 | 权限表现 | 未被 UI 暴露的部分 |
|---|---|---|---|---|---|---|---|---|

然后逐项解释映射机制：

- 对象如何选择页面原型。
- 属性如何分组、排序、渐进披露。
- 关系如何选择页签、子表、链接、图谱、时间线或嵌入卡片。
- 状态如何决定按钮、颜色、可编辑性和下一步引导。
- 权限如何改变导航、数据范围、字段和动作。
- 命令如何通过按钮、批量操作、向导和自动化呈现。
- 事件如何通过通知、活动流、审计和实时刷新呈现。
- 分析模型如何通过指标、图表和钻取呈现。

### 阶段 H：取舍评估、比较与沉淀

不要写泛化的“体验好、功能强”。每一项评价使用如下格式：

```text
设计选择：
解决的问题：
优先保障：
牺牲/成本：
成立条件：
失效边界：
证据：
可迁移原则：
不可照搬部分：
```

至少从以下维度评估：信息架构可理解性、跨模块上下文保持、任务效率、信息密度、关系可见性、状态可见性、错误预防、可撤销性、权限可解释性、一致性、个性化、扩展性、学习成本、移动/无障碍适应。

跨产品比较必须统一：同一行业任务、相近角色、相同分析粒度、接近的版本时间和同一评价量表。比较“模型和取舍”，禁止只比较功能数量或视觉风格。

最终把结论沉淀为三类知识：

- 领域知识：对象、关系、状态、规则、指标和行业不变量。
- 设计语法：何种模型与任务条件下选择何种导航和页面模式。
- 决策知识：某选择解决什么、代价是什么、何时迁移或拒绝。

## 5. 质量门槛与重做条件

### 5.1 完成门槛

- 所有关键页面和模型结论均可回指 Evidence ID。
- 所有关键 Evidence 均说明它支持什么、不支持什么。
- 系统、模块、页面、实体四层之间存在可追踪链路。
- 至少完成一个端到端主任务和一个异常/撤销路径。
- 每个关键关系包含语义、方向、候选基数及反证条件。
- 每个状态转换包含触发、守卫、权限和可见反馈。
- 已区分观察、确认、推断、假设和未知。
- 已区分领域模型、读模型、传输模型和物理存储未知项。
- 优缺点均写明成立条件和代价。
- 跨产品比较使用相同场景和量表。
- 公开资料无法确认的内容留为未知，不用常识补齐。

### 5.2 强制重做

出现任一情况，相关章节退回采证或建模阶段：

- 用单张截图断言数据库结构或关系基数。
- 不区分不同版本、角色、套餐或地域的界面。
- 页面清单很多，但没有用户任务和业务状态变化。
- ER 图中的对象无法回指页面或文档证据。
- UI 元素无法解释它读取或改变了什么模型。
- 将报表列、搜索结果、页签或 DTO 直接当作物理实体。
- 优缺点只有形容词，没有约束、代价和失效边界。
- 只走成功路径，未检查权限、异常、撤销和审计。
- 依赖搜索摘要或第三方文章支撑核心结论。

### 5.3 饱和停止条件

当以下条件同时满足时停止继续采集：

1. 连续三个新的高质量来源不再产生新核心对象、关系、状态或导航机制。
2. 核心任务、异常路径和主要角色已覆盖。
3. 高风险结论已达到证据门槛或明确标为未知。
4. UI -> 模型与模型 -> UI 两张矩阵的关键项均已闭环。
5. 新采集只增加视觉变体，不改变模型或设计取舍。

## 6. AI 执行控制协议

AI 每完成一个阶段必须输出：

```text
本阶段新增观察：
本阶段确认结论：
本阶段推断及推理链：
仍存在的替代解释：
证据缺口：
下一阶段最小检索动作：
是否达到阶段门槛：是/否
```

如果为“否”，不得伪装完成；应返回上一阶段执行最小补证动作。单个研究任务建议由不同代理分工，但由一个主代理统一 ID、术语、版本上下文和最终裁决：

- 采证代理：只收集与登记，不做模型定论。
- 导航/页面代理：重建结构与任务路径。
- 建模代理：提出多候选模型和反证。
- 批判代理：专门寻找证据冲突、替代解释和越界推断。
- 综合代理：完成双向映射、取舍评估与跨产品归一化。

## 7. 可直接交给 AI 的主提示词

```text
你是一名“商业软件逆向认知研究员”，兼具产品架构、信息架构、交互设计、领域建模、数据建模和证据审计能力。

目标：研究【产品】在【版本/观察日期】【套餐】【地域/语言】下，面向【用户角色】完成【业务场景】时，如何划分系统、模块、页面、实体、关系、状态、规则、权限和指标；重建候选领域模型，并解释模型如何映射为 UI、UI 如何允许用户观察和改变业务世界。

你不是在做截图收集、功能罗列、视觉点评或数据库猜测。必须执行以下纪律：
1. 只使用公开互联网资料、合法试用环境和用户明确提供的材料。
2. 优先级：可操作官方产品/官方 Schema > 官方文档与培训 > 官方伙伴材料 > 可信第三方 > 搜索线索。
3. 每条证据分配 Evidence ID，记录 URL、发布者、版本/角色/套餐/地域、采集时间、原始摘录、支持范围和局限。
4. 所有语句标记为 [O-观察]、[C-确认]、[I-推断]、[H-假设] 或 [X-未知]。
5. 每个关键推断给出：证据 -> 推理步骤 -> 候选结论 -> 替代解释 -> 反证条件 -> 置信度。
6. 禁止把一个页面当一个实体、一个页签当一张表、一个字段当持久化列、一个 API DTO 当领域模型、一个报表当事务模型。
7. 不能从 UI 直接断言真实数据库结构；只能输出候选领域/逻辑/读写模型，除非有直接 Schema 证据。
8. 对版本、角色、套餐、地域不一致的材料分开记录，不得混合。
9. 同时建立 UI->模型和模型->UI 两张追踪矩阵。
10. 优缺点必须说明解决的问题、优先保障、牺牲、成立条件、失效边界和证据。

依次执行：
A. 冻结研究任务卡和术语。
B. 建立来源清单与证据台账。
C. 描述行业问题、角色、任务和业务旅程。
D. 重建系统关系、系统间导航和数据/身份上下文传递。
E. 重建模块、业务能力、全局/局部/上下文/关系导航。
F. 建立页面清单并走查主路径及异常/撤销路径。
G. 解剖关键页面的字段、集合、关系、动作、状态、规则、权限、反馈和个性化。
H. 为实体、关系、状态机、规则、命令、事件、权限、指标和业务边界建立多候选模型。
I. 使用新证据排除替代解释，标注反证条件和置信度。
J. 建立双向映射矩阵并逐项解释映射机制。
K. 分析设计取舍、适用边界和可迁移设计语法。
L. 执行证据审计和质量门槛检查；不达标则补证，不得直接结束。

每阶段输出：新增观察、确认结论、推断链、替代解释、证据缺口、下一步最小检索动作、阶段门槛结果。

最终交付：研究任务卡、证据台账、系统关系图、模块导航矩阵、页面清单、任务路径、页面解剖、候选领域模型、状态/规则/权限模型、UI->模型矩阵、模型->UI矩阵、设计取舍、跨产品比较、可迁移设计语法、未知项与下一步证据计划。
```

## 8. 一句话原则

先把商业软件当作一个可观察的业务世界，证明它如何组织对象和行动；再把 UI 当作模型的投影去解释，而不是先看见界面元素就猜数据库。
