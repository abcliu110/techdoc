# 方向 7：模式库实证验证方法学

> 目标：定义模式如何从"假设"升级为"经验证模式"，建立证据收集、验证SOP和成熟度分级机制。
> 理论基线：[`13-界面模型深层逻辑与模式体系.md`](13-界面模型深层逻辑与模式体系.md) §14.5（模式语言记录格式中的 Evidence 字段）。
> 背景：现有 25 个模式的 `maturity` 全部未标注，金蝶云苍穹报告因证据不足作废。本方向补全这一缺失层。

## 0. 为什么需要实证验证方法学

现有模式体系存在三个实证问题：

1. **模式无成熟度标注**：25 个模式全部以"已验证"口吻描述，但实际上多数只有理论推导，没有真实系统正例。
2. **证据不足导致报告作废**：金蝶云苍穹 v1 报告因未满足证据台账、覆盖门槛和优先级证据要求而作废。
3. **无法证伪**：模式没有定义"什么证据能证明它无效"，无法排除"看起来很对但实际无效"的模式。

实证验证方法学的目标是让每个模式拥有可收集的证据、可执行的验证SOP和可分级的成熟度。

## 1. 模式成熟度分级

### 1.1 四级成熟度

| 级别 | 名称 | 含义 | 证据要求 | 可用于 |
|---|---|---|---|---|
| L0 | hypothetical（假设） | 理论推导得出，无实证 | 无 | 理论探讨 |
| L1 | assumed（推断） | 有 1-2 个真实系统正例，无反例 | ≥1 正例 | 试点验证 |
| L2 | tested（测试） | 有可用性测试数据支持 | ≥3 正例 + 可用性测试 | 生产使用 |
| L3 | verified（验证） | 有多系统、多场景验证 + A/B 数据 | ≥5 正例 + A/B测试 + 0 反例 | 全面推广 |

## 2. 证据类型

### 2.1 证据层级

| 层级 | 类型 | 强度 | 示例 |
|---|---|---|---|
| E1 | 直接观察-截图 | 高 | 真实系统截图，标注模式结构 |
| E2 | 直接观察-视频 | 高 | 操作录屏，标注交互流程 |
| E3 | 直接观察-实测 | 最高 | 亲自操作真实系统验证 |
| E4 | 交叉验证-知识库 | 中 | 已验证的知识库条目 |
| E5 | 高可信推断 | 中低 | 基于文档和API的推断 |
| E6 | 文档引用 | 低 | 官方文档描述 |
| E7 | 可用性测试 | 高 | 真实用户任务测试数据 |
| E8 | A/B测试 | 最高 | 对照实验数据 |
| E9 | 反例 | 特殊 | 证明模式无效或失效的案例 |

### 2.2 证据台账格式

每条证据必须记录：

```yaml
evidence:
  id: "E-LR-001"
  pattern: "ListReport"
  type: "E3-直接观察-实测"
  source:
    system: "金蝶云苍穹社区版"
    version: "2026-07"
    url: "https://..."
    accessedAt: "2026-07-12"
  observer: "AI Agent"
  description: "订单列表页存在 filterRegion + rowSummary + statusBadge + pagination"
  screenshot: "evidence/E-LR-001.png"
  strengths: ["直接观察", "可复现"]
  limitations: ["仅社区版", "未测试大数据量"]
  supportsInvariant: ["FILTER-1", "STATUS-1"]
```

## 3. 验证SOP

### 3.1 单模式验证SOP（L0→L1→L2→L3）

**L0→L1（理论推导到推断）：**
- 模式有完整的 Context/Problem/Solution/Consequences
- 至少 1 个真实系统正例（E1-E3）
- 无已知反例（E9）
- → 升级为 L1 assumed

**L1→L2（推断到测试）：**
- 至少 3 个不同系统的正例
- 至少 1 次可用性测试（E7）
- 记录所有已知反例和失效条件
- → 升级为 L2 tested

**L2→L3（测试到验证）：**
- 至少 5 个不同系统的正例
- 至少 1 次 A/B 测试（E8）
- 无未解释的反例
- 覆盖至少 2 种行业场景
- → 升级为 L3 verified

### 3.2 系统级抽样验证SOP

用于验证一个真实系统使用了哪些模式、是否遵循不变量。

**阶段 1：系统范围界定**
- 确定系统类型（ERP/CRM/POS/WMS/财务）
- 确定分析模块（≤10个核心模块）
- 确定用户角色（≤5个核心角色）
- 确定环境（版本、租户、数据量）

**阶段 2：证据收集**
- 每个模块至少3个页面截图（E1）
- 核心交互流程录屏（E2）
- 关键页面亲自操作（E3）
- 建立证据台账

**阶段 3：模式识别**
- 从证据中识别使用的模式
- 记录每个模式的槽位实现情况
- 标注置信度

**阶段 4：不变量校验**
- 对每个识别的模式运行不变量校验
- 记录通过/失败/警告
- 收集反例

**阶段 5：覆盖度评估**
- 计算 25 个模式的覆盖比例
- 识别未使用的模式及其原因
- 识别新模式候选

**阶段 6：报告生成**
- 证据台账附录
- 模式覆盖矩阵
- 不变量校验结果
- 反例分析
- 改进建议（按优先级）

### 3.3 可用性测试SOP

**步骤 1：定义任务**
- 从模式的 `verification.usabilityTest` 选取任务
- 定义成功标准（点击数、时间、错误率）

**步骤 2：招募参与者**
- ≥5 名符合目标角色的用户
- 覆盖新手和熟练用户

**步骤 3：执行测试**
- 任务前说明（不引导操作方式）
- 观察记录（点击路径、时间、错误、主观评价）
- 任务后访谈（理解困难点）

**步骤 4：分析**
- 计算成功率、平均时间、错误率
- 识别失败模式（找不到、看不懂、做不对、无法恢复）
- 对照不变量分析失败原因

**步骤 5：结论**
- 模式是否达到成功标准
- 记录改进建议
- 更新模式成熟度

### 3.4 A/B测试SOP

**步骤 1：定义假设**
- "模式A比模式B在任务T上的成功率更高/时间更短/错误更少"

**步骤 2：设计实验**
- 控制组：使用现有模式（或替代模式）
- 实验组：使用待验证模式
- 样本量：≥100用户/组（统计显著性）
- 指标：成功率、时间、错误率、主观满意度

**步骤 3：执行**
- 随机分配用户到控制组/实验组
- 收集指标数据

**步骤 4：分析**
- 统计显著性检验（p < 0.05）
- 效应量计算
- 分组分析（新手vs熟练、高频vs低频）

**步骤 5：结论**
- 模式是否优于替代方案
- 记录适用边界
- 更新模式成熟度

## 4. 反例库

### 4.1 反例的作用

反例不是模式的否定，而是模式的边界。一个成熟的模式必须声明"在什么情况下会失效"。

### 4.2 反例记录格式

```yaml
counterExample:
  id: "CE-LR-001"
  pattern: "ListReport"
  system: "某ERP系统"
  description: "List Report 用于展示审批流程节点，但审批节点只有5-8个，不需要筛选和分页"
  failureMode: "任务-页面失配"
  rootCause: "对象数量少时不需要List Report，应使用Object Page或流程图"
  boundaryCondition: "对象数 < 10 时不应使用 List Report"
  suggestedFix: "改用 Object Page 或流程图视图"
```

### 4.3 已知反例分类

| 反例类型 | 含义 | 示例 |
|---|---|---|
| 数量边界反例 | 对象太少/太多导致模式失效 | List Report 用于5个对象 |
| 任务失配反例 | 模式与任务不匹配 | Dashboard 用于精确查值 |
| 状态失配反例 | 状态复杂度不匹配 | 简单状态用Wizard |
| 风险失配反例 | 风险控制不足 | 高风险操作用Inline Edit |
| 规模失配反例 | 数据规模超出模式能力 | 10万行用客户端排序 |
| 协作失配反例 | 多人协作场景未考虑 | Worklist无分配和交接 |
| 可访问性反例 | 可访问性契约缺失 | 状态只靠颜色区分 |

## 6. 验证报告模板

```yaml
verificationReport:
  meta:
    pattern: "Exception Center"
    verificationDate: "2026-07-15"
    verifier: "AI Agent"
    targetMaturity: "L2 tested"

  positiveEvidence:
    - system: "系统A"
      type: "E3"
      description: "存在异常分级、绑定对象、处理动作"
      evidenceId: "E-EXC-001"
    - system: "系统B"
      type: "E3"
      description: "存在重复异常聚合和处理留痕"
      evidenceId: "E-EXC-002"
    - system: "系统C"
      type: "E2"
      description: "异常进入业务可处理流程"
      evidenceId: "E-EXC-003"

  usabilityTest:
    participants: 5
    task: "处理3笔支付异常"
    results:
      successRate: "80%"
      avgTime: "45s"
      errorRate: "10%"
    conclusion: "达到成功标准"

  counterExamples:
    - id: "CE-EXC-001"
      system: "系统D"
      description: "异常只在日志中，无业务界面"
      failureMode: "系统-业务失配"

  invariantResults:
    - id: "EXC-1"
      passCount: 3
      failCount: 1
    - id: "IDEM-1"
      passCount: 2
      failCount: 0

  maturityDecision: "L2 tested"
  nextSteps: "补充A/B测试以升级L3"
```

## 7. 与其他方向的关系

- **方向 1**：验证结果写入规约的 `identity.maturity` 和 `verification` 属性。
- **方向 2**：涌现模式需走 L0→L1 验证流程。
- **方向 4**：可访问性契约的测试作为可用性测试的必检项。
- **方向 6**：Agent-Native 模式优先走验证流程，从 L0 升级。
- **方向 8**：行业不变量映射作为反例检测的约束来源。
