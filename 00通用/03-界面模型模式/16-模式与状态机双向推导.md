# 方向 3：模式与状态机双向推导

> 目标：建立业务对象状态机与 UI 模式之间的双向推导机制——给定状态机推导模式集合，给定页面反推隐含状态机。
> 理论基线：[`13-界面模型深层逻辑与模式体系.md`](13-界面模型深层逻辑与模式体系.md) §3（状态与能力）、§10.3（Petri Net）、§10.4（Saga）。
> 依赖：[`14a-模式形式化规约.md`](14a-模式形式化规约.md) 的 `stateMachine` 和 `invariants.CAP-1`。

## 0. 为什么需要双向推导

现有文档在 §3.3 给出了能力模型公式：

```
availableActions = f(业务状态, 角色与权限, 数据范围, 业务不变量, 锁与并发版本, 时间窗, 策略与风险)
nextState = T(currentState, action, externalEvents)
```

但这个公式停留在概念层。设计师拿到一个业务对象的状态机后，仍无法直接回答：

1. 这个对象需要哪些页面模式？
2. 每个状态下页面应展示哪些操作？
3. 当前页面是否覆盖了所有状态转移路径？
4. 状态机本身是否有缺陷（死状态、不可达、缺补偿）？

双向推导把这四个问题变成可计算的规则。

## 1. 业务对象状态机模型

### 1.1 状态机定义

```yaml
# 业务对象状态机元模型
stateMachine:
  objectType: "Order"          # 业务对象类型
  states:                      # 状态集合
    - name: "draft"
      type: "initial"          # initial | normal | final | error
      invariant: "金额可任意修改"
    - name: "pendingPayment"
      type: "normal"
      invariant: "库存未锁定"
    - name: "paid"
      type: "normal"
      invariant: "库存已锁定"
    - name: "shipped"
      type: "normal"
      invariant: "物流单号已生成"
    - name: "completed"
      type: "final"
      invariant: "订单不可修改"
    - name: "cancelled"
      type: "final"
      invariant: "库存已释放"
    - name: "refunding"
      type: "error"
      invariant: "退款流程进行中"
    - name: "refunded"
      type: "final"
      invariant: "资金已退回"

  transitions:                 # 状态转移
    - from: "draft"
      to: "pendingPayment"
      action: "submitOrder"
      guard: "必填字段已填 + 库存可满足"
      effect: "生成订单号"
    - from: "pendingPayment"
      to: "paid"
      action: "paymentCallback"
      guard: "支付金额 = 应付金额"
      effect: "锁定库存"
    - from: "pendingPayment"
      to: "cancelled"
      action: "cancelOrder"
      guard: "超时未支付 OR 用户取消"
      effect: "无"
    - from: "paid"
      to: "shipped"
      action: "ship"
      guard: "仓库权限 + 库存锁有效"
      effect: "生成物流单号"
    - from: "paid"
      to: "refunding"
      action: "requestRefund"
      guard: "退款权限"
      effect: "进入退款流程"
    - from: "shipped"
      to: "completed"
      action: "confirmReceipt"
      guard: "超时自动确认 OR 用户确认"
      effect: "释放库存锁"
    - from: "refunding"
      to: "refunded"
      action: "refundCallback"
      guard: "退款金额 ≤ 已付金额"
      effect: "退回资金 + 释放库存"
    - from: "refunding"
      to: "paid"
      action: "rejectRefund"
      guard: "审核驳回"
      effect: "恢复原状态"

  parallelBranches:            # 并行分支（Petri Net 语义）
    - branch: "物流跟踪"
      forkFrom: "shipped"
      places: ["warehouseProcessing", "inTransit", "delivered"]
      joinTo: "completed"

  compensationPaths:           # 补偿路径（Saga 语义）
    - trigger: "支付回调超时"
      detectedAt: "pendingPayment"
      compensation: "查询渠道结果 → 已支付则补记订单 → 未支付则取消"
    - trigger: "发货后退款"
      detectedAt: "shipped"
      compensation: "拦截物流 → 退回仓库 → 退款"
```

### 1.2 状态属性

每个状态除 `name` 和 `type` 外，还应标注以下属性，用于推导 UI：

| 属性 | 含义 | 用于推导 |
|---|---|---|
| `type` | initial/normal/final/error | 推导页面入口和终态处理 |
| `invariant` | 该状态下不变的业务规则 | 推导操作可用性和禁用原因 |
| `responsibleRole` | 该状态下的责任角色 | 推导 Worklist 分配 |
| `sla` | 该状态的最大停留时间 | 推导 Aging 和超时升级 |
| `editable` | 该状态下对象是否可编辑 | 推导表单模式选择 |
| `reversible` | 该状态是否可回退 | 推导补偿/撤销操作 |

## 2. 正向推导：状态机 → 模式集合

### 2.1 推导规则

给定业务对象状态机，按以下规则推导所需 UI 模式。

#### 规则 F1：对象发现

```
IF objectType.hasManyInstances (>100)
THEN require("ListReport")
IF objectType.hasHierarchy
THEN require("TreeGrid")
IF objectType.states.filter(type="normal" AND responsibleRole≠null).count > 0
THEN require("Worklist")  # 有责任分配的状态需待办
```

#### 规则 F2：对象理解

```
IF objectType.fields.count > 10 OR objectType.relations.count > 2
THEN require("ObjectPage")
IF objectType.transitions.count > 3
THEN require("Timeline")  # 状态转移多需时间线
IF objectType.relations.count > 0
THEN require("RelatedLists")
```

#### 规则 F3：对象操作

```
FOR EACH state IN states WHERE editable=true:
  IF state.fields.count < 5 AND state.riskLevel="low"
  THEN require("SimpleForm")
  IF state.fields.count > 15 OR state.hasSectionDependency
  THEN require("SectionedForm")
  IF state.transitions.filter(from=state).count > 1 AND hasOrderDependency
  THEN require("Wizard")

FOR EACH transition WHERE action.riskLevel="high":
  THEN require("ModalForm")  # 高风险确认
  IF transition.effect.affectsBatch
  THEN require("ImpactPreview")
```

#### 规则 F4：监控与分析

```
IF objectType.hasAggregatableMetric
THEN require("Dashboard")
IF objectType.metric.needsExplanation
THEN require("Drill-down")
IF objectType.states.filter(type="error").count > 0
THEN require("ExceptionCenter")
```

#### 规则 F5：协作与治理

```
FOR EACH state WHERE responsibleRole ≠ null:
  IF state.sla ≠ null
  THEN require("Aging")
  IF state.requiresHandoff
  THEN require("Handoff")

IF objectType.transitions.filter(action.requiresApproval).count > 0
THEN require("MakerChecker")
IF objectType.hasAuditRequirement
THEN require("AuditLog")
```

#### 规则 F6：并行与补偿

```
IF stateMachine.parallelBranches.count > 0
THEN require("ParallelStepper")
THEN require("DependencyGraph")  # 展示并行分支
THEN require("JoinGate")  # 汇合条件

IF stateMachine.compensationPaths.count > 0
THEN require("StepProgress")  # 补偿步骤进度
THEN require("Reconciliation")  # 补偿后对账
```

## 3. 反向推导：页面 → 隐含状态机

### 3.1 反向推导的场景

当接手一个已有系统或审查一个设计稿时，需要从页面反推它隐含的状态机假设，并检测缺陷。

### 3.2 反向推导规则

#### 规则 R1：从操作按钮反推状态

```
FOR EACH button ON page:
  IF button.disabled AND button.disabledReason exists
  THEN infer:
    stateMachine.hasState(currentState)
    stateMachine.transition(action=button.action)
      .guard = NOT(button.disabledReason)
```

#### 规则 R2：从状态徽章反推状态

```
FOR EACH statusBadge ON page:
  infer:
    stateMachine.hasState(badge.value)
  IF badge.hasExplanatoryText
  THEN infer:
    state.hasInvariant = badge.explanatoryText
```

#### 规则 R3：从 Timeline 反推转移

```
FOR EACH event IN timeline WHERE eventType="businessStateChange":
  infer:
    stateMachine.transition(
      from=event.beforeState,
      to=event.afterState,
      action=event.triggerAction,
      operator=event.operator,
      time=event.time
    )
```

#### 规则 R4：从表单字段反推不变量

```
FOR EACH field IN form WHERE field.required=true:
  infer:
    stateMachine.transition(action=form.submitAction)
      .guard.includes(field.name + " is not empty")

FOR EACH field WHERE field.validation exists:
  infer:
    state.invariant.includes(field.validation)
```

### 3.3 反向推导示例

给定一个订单详情页设计稿，反推隐含状态机：

```yaml
inferredStateMachine:
  inferredFrom:

    - "页面有'取消'按钮，在'待支付'状态下可点击，其他状态置灰"
    - "Timeline 显示：待支付→已支付→待发货→已发货→已完成"
    - "退款流程有单独的 Timeline"

  inferredStates: ["draft", "pendingPayment", "paid", "shipped", "completed", "cancelled", "refunding", "refunded"]

  inferredTransitions:
    - { from: "pendingPayment", to: "cancelled", action: "cancel" }
    - { from: "pendingPayment", to: "paid", action: "paymentCallback" }
    - { from: "paid", to: "shipped", action: "ship" }
    - { from: "paid", to: "refunding", action: "requestRefund" }
    - { from: "shipped", to: "completed", action: "confirmReceipt" }
    - { from: "shipped", to: "refunding", action: "requestRefund" }

  defects:

    - id: "D-2"

    - id: "D-3"
```

## 4. 状态机缺陷检测

### 4.1 缺陷类型

| 缺陷类型 | 含义 | 检测方法 | 严重性 |
|---|---|---|---|
| **死状态** | 无出转移且非终态 | `state.transitions.filter(from=state).count=0 AND state.type≠final` | error |
| **不可达状态** | 无入转移且非初始态 | `state.transitions.filter(to=state).count=0 AND state.type≠initial` | error |
| **缺补偿路径** | 有不可逆高风险操作但无补偿 | `transition.risk=high AND transition.reversible=false AND no compensationPath` | error |
| **缺守卫** | 转移无业务条件约束 | `transition.guard=null AND transition.action.risk≠low` | warning |
| **缺 SLA** | 有责任角色的状态无超时 | `state.responsibleRole≠null AND state.sla=null` | warning |
| **缺并行汇合** | 有并行分支但无 Join | `parallelBranch.exists AND joinTo=null` | error |
| **状态-操作失配** | 操作在错误状态可用 | 反推后 `availableActions` 与状态不变量矛盾 | error |
| **终态可编辑** | 终态状态仍允许编辑 | `state.type=final AND state.editable=true` | error |

### 4.2 检测算法

```python
def detect_state_machine_defects(sm: StateMachine) -> list:
    defects = []

    for state in sm.states:
        # 死状态
        if not has_outgoing_transition(sm, state) and state.type != "final":
            defects.append(Defect(state, "deadState", "error"))
        # 不可达状态
        if not has_incoming_transition(sm, state) and state.type != "initial":
            defects.append(Defect(state, "unreachableState", "error"))
        # 缺 SLA
        if state.responsibleRole and not state.sla:
            defects.append(Defect(state, "missingSLA", "warning"))
        # 终态可编辑
        if state.type == "final" and state.editable:
            defects.append(Defect(state, "finalStateEditable", "error"))

    for t in sm.transitions:
        # 缺守卫
        if not t.guard and t.action.risk != "low":
            defects.append(Defect(t, "missingGuard", "warning"))
        # 缺补偿
        if t.action.risk == "high" and not t.reversible:
            if not has_compensation_path(sm, t):
                defects.append(Defect(t, "missingCompensation", "error"))

    for branch in sm.parallelBranches:
        if not branch.joinTo:
            defects.append(Defect(branch, "missingJoin", "error"))

    return defects
```

## 5. 状态-模式-能力模板库

### 5.1 常见业务对象的状态机模板

| 业务对象 | 典型状态 | 典型转移 | 必需模式 | 常见缺陷 |
|---|---|---|---|---|
| 订单 | 草稿/待付/已付/待发/已发/完成/取消/退款 | 8+ 转移 | ListReport, ObjectPage, Timeline, Worklist, ModalForm, ExceptionCenter | 缺补偿路径、缺 SLA |
| 审批 | 待审/审核中/通过/驳回/撤回 | 5 转移 | Worklist, MakerChecker, Timeline, AuditLog | 缺职责分离检测 |
| 库存调整 | 待审/已审/执行中/完成/失败 | 5 转移 | Wizard, ImpactPreview, BackgroundTask, Reconciliation | 缺幂等重试 |
| 主数据 | 草稿/待审/生效/停用/归档 | 5 转移 | SectionedForm, MakerChecker, EffectiveTimeline, AuditLog | 缺双时态 |
| 对账 | 待对/对账中/差异/已处理/日结 | 5 转移 | Reconciliation, ExceptionCenter, MakerChecker | 缺日结门禁 |

### 5.2 状态类型到模式的映射

| 状态类型 | 推荐模式 | 原因 |
|---|---|---|
| initial | SimpleForm / Wizard | 创建流程 |
| normal (editable) | SectionedForm / DrawerForm | 编辑流程 |
| normal (read-only, awaiting) | ObjectPage + Aging + Timeline | 等待外部事件 |
| normal (actionable) | ObjectPage + Worklist | 等待用户操作 |
| error | ExceptionCenter + ModalForm | 异常处理 |
| final (read-only) | ObjectPage + Timeline + AuditLog | 只读追溯 |

## 6. 与其他方向的关系

- **方向 1**：正向推导的模式集合进入方向 1 的规约校验；反向推导的缺陷作为不变量违反报告。
- **方向 2**：推导出的多模式组合需经过方向 2 的冲突检测。
- **方向 4**：每个状态下的操作需满足可访问性契约。
- **方向 7**：状态机缺陷检测规则作为实证验证的检查项。
- **方向 8**：行业不变量（如借贷必平）作为状态机的 `invariant`，参与缺陷检测。
