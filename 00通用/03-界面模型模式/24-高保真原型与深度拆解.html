解决什么问题

用户需从数万条订单中快速找到目标。核心矛盾：数据量大但用户只需关注其中几条。

SAP Fiori 怎么做

  • Smart Filter Bar：核心筛选默认展开，高级筛选折叠。遵循 Hick-Hyman 定律——选项收敛降低决策时间。
  • 状态徽章三重编码：✓确认(绿)、⏳审批(橙)、📦交货(蓝)、⚠冻结(红)。图标+文本+颜色三者同时用，不只靠颜色——SAP Fiori Guidelines 硬性要求。
  • 批量操作栏渐进出现：未选中不占空间，选中后从顶部滑入。含"影响预览"按钮。
  • 行摘要聚合：订单号+客户+金额+状态+交货日，一眼区分对象。
标杆洞察：Smart Filter Bar 与表格共享同一 OData 上下文，保证图表和明细口径一致。

Ant Design Pro 差异

ProTable 把低频操作（刷新/密度/列设置/全屏）收敛到右上角图标组。这是"高频外露低频收敛"的工程实现。

✗ 反模式：SAP GUI 传统 ALV——所有筛选平铺、所有按钮平铺，30+列20+按钮，认知负荷极高。
理论桥接：§2 信息分层；§3 状态轴（筛选=状态过滤器）；§13 信息-认知失配。

解决什么问题

一个订单在数据库里涉及 8+ 张表（订单/商品/支付/物流/优惠/发票/日志…）。Object Page 把这些散落的数据聚合成用户能理解的一个完整业务对象。

SAP Fiori 怎么做

  • 对象头部：订单号+状态+金额+客户+主操作。一眼知道"这是哪个对象、什么状态、能干什么"。
  • 分区锚点导航：概览/行项目/合作伙伴/定价/交货/状态历史。点击标签自动滚动到对应分区，滚动时高亮当前标签——比 Tab 切换更流畅。
  • SAP 官方规范：对象详情页由页眉、内容区域、操作区域三部分组成。

Salesforce Lightning 的差异

  • 三列布局：左列 Highlights（4-6个关键字段），中列详情+Related Lists，右列 AI 建议+提醒。
  • 可组合：管理员通过 Lightning App Builder 拖拽组件定制不同角色布局。Object Page 从"固定结构"进化到"可组合架构"。
  • Highlights Panel 只展示 4-6 个关键字段，严格遵守信息分层。

金蝶云苍穹的特色

采用单据头+明细分录+状态命令栏——中国 ERP 经典结构。命令栏随状态动态调整：草稿态显示"暂存+提交"，待审态显示"审批+驳回"。这是能力模型（CAP-1）的实践。

标杆洞察：Object Page 的本质是"数据库语言→用户心理模型的翻译器"。SAP 按业务语义分区，Salesforce 按角色组合，金蝶按单据头分录——三种变体都在解决同一个问题。
理论桥接：§1 数据-心理失配；§3.2 状态四问（是什么/为什么/怎么办/如何恢复）；§5 可追溯性。

解决什么问题

用户问"这个状态怎么变成这样的"——业务事实的可追溯性。财务对账、问题排查、责任追溯都依赖追踪形成过程。

三层事件模型

  • 系统自动事件（蓝色圆点）：支付回调、库存锁定、物流推送。触发者是系统。
  • 人工操作事件（橙色圆点）：客服审核、运营修改。记录操作人+时间+前后值+原因。
  • 业务状态事件（绿色圆点）：状态机流转。记录前状态→后状态+触发条件。

Salesforce vs SAP 差异

Salesforce 的 Activity Timeline 偏沟通记录（邮件/电话/会议/任务），用不同图标区分类型，支持筛选。SAP 的状态历史偏业务状态机事件，严格记录前后状态值，支持审计回溯。

标杆洞察：Salesforce 用图标+文本区分事件类型（不只靠颜色），符合可访问性。Ant Design 把 Timeline 拆成"进度概览(Steps)+详细日志(Timeline)"两层——前者一眼看到流程走到哪，后者追踪每步细节。
理论桥接：§5 可追溯性（三层事件）；§5.3 状态流转完整表达（时间+事件类型+操作人+前后状态+原因）。

解决什么问题

一个客户关联订单、合同、案例、活动等。如何在不喧宾夺主的情况下完整呈现。

Salesforce 怎么做

  • 默认只展示5条最近记录，避免喧宾夺主。
  • 只展示关键字段（订单号/金额/状态/日期），完整字段跳转独立页。
  • 关联列表内只做查看和轻量操作，复杂操作跳转独立页面。
  • 2025年推出 Dynamic Related Lists——可按筛选条件动态过滤，例如只展示"本年度金额>1万的订单"。

SAP Fiori 的差异

SAP 把 Related Lists 融入 Object Page 分区结构（如"交货"分区展示关联交货单），而非像 Salesforce 作为独立组件堆叠。优势是上下文连贯，劣势是关联对象多时分区很长——SAP 通过默认折叠次要分区解决。

标杆洞察：Salesforce 三个关键约束确保"不喧宾夺主"：①默认5条 ②只展示关键字段 ③轻量操作。Dynamic Related Lists 进一步允许按上下文动态过滤。
理论桥接：§1 信息聚合；§2 信息分层（关联列表=二级信息，不是详情页核心）。

解决什么问题

连续处理多个对象时减少页面跳转带来的上下文切换。客服处理今日退款——每次点进去处理完再跳回列表再点下一个，每次跳转丢失上下文。

SAP Fiori — Flexible Column Layout

  • 支持最多三栏并列：列表→详情→子详情。订单→支付单→物流流水三级展开。
  • 栏宽可拖拽调整，窄屏自动退化为单栏。
  • 切换选中项时右侧详情同步更新，左侧筛选和排序状态不变。

Microsoft Fluent UI

Outlook、Teams、SharePoint 中大量使用。Fluent UI 提供 DetailsList 支持键盘方向键导航（↑↓切换项，Enter打开），这是技能型用户高频操作的效率保障。

标杆洞察：SAP Flexible Column Layout 解决了"主从只有两层不够"的问题——订单关联支付单，支付单又关联银行流水，三级展开让用户追踪完整链路。窄屏退化时保留上下文（返回列表时筛选状态不变）。
理论桥接：§2 认知负荷（减少跳转=减少上下文切换）；§3 状态轴（列表栏本质是状态过滤）。

解决什么问题

不同复杂度的业务录入如何选择合适的表单承载方式。短确认用弹窗，列表内编辑用抽屉，复杂录入用独立页。

Ant Design Pro — 表单全家桶

  • ModalForm：弹窗表单，适合1-3字段短确认（退款/取消/填写原因）。
  • DrawerForm：抽屉表单，保留列表上下文的快速编辑。关键约束：抽屉内不嵌套抽屉（NEST-1）。
  • StepsForm：分步表单，最后一步总览确认。
  • ProForm(分组)：配置化表单，支持分组、依赖联动。

Microsoft Fluent UI — Dialog vs Panel

Microsoft 明确区分 Dialog（阻断式，必须处理才能继续）和 Panel（非阻断式，可忽略）。Dialog 用于高风险操作（删除/提交），Panel 用于需参考当前页面的编辑。这是风险分层的体现。

标杆洞察：Ant Design Pro 把表单模式做成了一一对应的组件——开发者根据场景选组件即选模式。这是模式从"设计指导"到"工程组件"的落地。
理论桥接：§6 表单（业务承诺）；§6.3 表单复杂度；§4 操作风险（高风险用 Modal 确认）。

解决什么问题

长流程多步骤，让用户每次只专注于当前步骤。单页30+字段用户不知道从哪开始。

Google Material — Stepper

  • 水平Stepper（≤5步）和垂直Stepper（移动端或>5步）。
  • 支持线性（必须按顺序，适合有依赖）和非线性（可跳转，适合并行填写）。

SAP Fiori Wizard

每步对应一个业务决策点，不只是字段分组——供应商选择→物料选择→数量日期→价格条件→确认提交。步骤间有数据依赖。这是 Wizard 与 Sectioned Form 的关键区别。

标杆洞察：Ant Design StepsForm 的"最后一步总览确认"是关键设计——用户提交前可看到所有步骤的填写结果，降低错误率。
理论桥接：§2 渐进披露；§6.3 表单复杂度（有顺序依赖→Wizard）。
