# 方向 1：模式形式化规约与可机器校验

> 目标：把 25 个核心模式从自然语言描述变成可机器校验的规约，让模式从"文档参考"升级为"设计 lint / CI 校验规则"。
> 理论基线：[`13-界面模型深层逻辑与模式体系.md`](13-界面模型深层逻辑与模式体系.md) §14.5 模式语言的记录格式。

## 0. 为什么需要形式化

现有模式文档用自然语言描述 Context / Problem / Solution / Consequences，存在三个问题：

1. **不可校验**：设计稿或代码是否遵循了 List Report 的"高频外露、低频收敛"，只能靠人工判断。
2. **不可组合计算**：两个模式能否同屏共存，没有形式化判定规则。
3. **不可自动验证**：可用性测试、性能阈值、可访问性契约无法从模式描述直接推导出测试用例。

形式化规约的目标是让每个模式拥有一份**可被 lint 工具、设计工具和测试框架解析的结构化定义**。

## 1. 规约的整体结构

每个模式的形式化规约包含六个层：

```yaml
# 规约元模型
specVersion: "1.0"
pattern: <模式名>
layer:
  identity:        # 身份层：模式是什么
  slots:           # 槽位层：模式由哪些语义槽位组成
  invariants:      # 不变量层：槽位之间必须成立的约束
  stateMachine:    # 状态层：模式自身的交互状态机
  verification:    # 验证层：如何证明模式被正确实现
  composition:     # 组合层：与其他模式的兼容/互斥关系（见方向 2）
```

### 1.1 身份层（Identity）

```yaml
identity:
  id: "ListReport"
  aliases: ["查询列表", "List Report", "列表报告"]
  category: "列表与对象发现"
  primaryTask: "查找/筛选对象"
  parentPattern: null
  theoryRef: "§2 信息分层; §3 状态轴; §13 信息-认知失配"
  maturity: "verified"  # verified | assumed | hypothetical（见方向 7）
```

### 1.2 槽位层（Slots）

槽位是模式中具有独立语义的组成部分。每个槽位有类型、必要性、约束和默认值。

```yaml
slots:
  - name: filterRegion
    type: container
    mandatory: true
    subSlots:
      - name: coreFilters
        mandatory: true
        constraint: "默认展开的筛选字段数 ≤ 5"
      - name: advancedFilters
        mandatory: false
        defaultStrategy: "collapsed"
    constraints:
      - "coreFilters 展开时不得遮挡 rowSummary"

  - name: rowSummary
    type: repeating
    mandatory: true
    constraints:
      - "每行至少包含 3 个可区分字段（对象身份 + 主状态 + 核心数值）"
      - "状态用文本+图标表达，颜色只作辅助"

  - name: statusBadge
    type: component
    mandatory: true
    constraints:
      - "不得仅用颜色区分状态"
      - "状态与优先级分开表达"

  - name: primaryAction
    type: action
    mandatory: true
    constraints:
      - "高频动作外露在行末，数量 ≤ 2"
      - "主操作按钮必须反映当前能力（见不变量 CAP-1）"

  - name: secondaryActions
    type: actionGroup
    mandatory: false
    defaultStrategy: "overflowMenu"
    constraints:
      - "低频动作收入'更多'菜单"

  - name: bulkSelection
    type: interaction
    mandatory: false
    constraints:
      - "若存在 bulkSelection，则必须存在 bulkActionBar 和 impactPreview"
      - "批量操作栏在选中 ≥1 项时显示"

  - name: pagination
    type: component
    mandatory: true
    constraints:
      - "行数 > 1000 时必须切换为虚拟滚动（见方向 5）"
```

### 1.3 不变量层（Invariants）

不变量是槽位之间、模式与业务规则之间必须成立的硬约束，用 `IF ... THEN ...` 规则表达。

```yaml
invariants:
  - id: CAP-1
    name: "能力一致性"
    rule: "IF action.visible THEN action.availableBy(state, permission, scope, invariant, lock, timeWindow, policy) = true"
    severity: error
    rationale: "§3.3 能力模型；§13 角色-能力失配"
    fixHint: "不可用操作应置灰并说明原因，不直接隐藏（除非角色无权知道该操作存在）"

  - id: BULK-1
    name: "批量影响预览"
    rule: "IF bulkSelection.selectedCount > 0 AND bulkAction.isHighRisk THEN impactPreview.required = true"
    severity: error
    rationale: "§4 操作风险分层；§6 配置特殊性"

  - id: STATUS-1
    name: "状态非颜色依赖"
    rule: "IF statusBadge.present THEN statusBadge.text.required = true AND statusBadge.icon.required = true"
    severity: error
    rationale: "§13 反模式；§14.3 局部启发式边界"

  - id: FILTER-1
    name: "筛选不遮挡摘要"
    rule: "IF filterRegion.expanded THEN rowSummary.visible = true"
    severity: warning
    rationale: "§2 信息分层"

  - id: PERF-1
    name: "大数据量虚拟化"
    rule: "IF rowSummary.rowCount > 1000 THEN virtualScroll.enabled = true"
    severity: warning
    rationale: "方向 5 性能边界"
```

### 1.4 状态层（State Machine）

模式自身的交互状态机，用于驱动可访问性契约（方向 4）和测试用例生成（方向 7）。

```yaml
stateMachine:
  states:
    - idle          # 初始空闲
    - filtering     # 筛选中
    - loading       # 查询加载中
    - resultsShown  # 结果已展示
    - rowSelected   # 行已选中（单选）
    - bulkSelected  # 批量选中
    - actionInvoked # 动作已触发
    - actionConfirming # 动作确认中（高风险）
    - error         # 错误态

  transitions:
    - from: idle
      to: filtering
      trigger: "focusFilterRegion"
    - from: filtering
      to: loading
      trigger: "submitQuery"
    - from: loading
      to: resultsShown
      trigger: "querySuccess"
    - from: loading
      to: error
      trigger: "queryFailure"
    - from: resultsShown
      to: rowSelected
      trigger: "selectRow"
    - from: resultsShown
      to: bulkSelected
      trigger: "selectCheckbox"
    - from: rowSelected
      to: actionConfirming
      trigger: "invokeHighRiskAction"
      guard: "action.isHighRisk"
    - from: bulkSelected
      to: actionConfirming
      trigger: "invokeBulkAction"
      guard: "bulkAction.isHighRisk"
    - from: actionConfirming
      to: loading
      trigger: "confirmAction"
    - from: actionConfirming
      to: resultsShown
      trigger: "cancelAction"
    - from: error
      to: filtering
      trigger: "retryQuery"
```

### 1.5 验证层（Verification）

每个模式必须声明可验证的条款，用于设计审查、自动化测试和可用性测试。

```yaml
verification:
  designReview:
    - id: DR-1
      check: "筛选区核心字段默认展开，高级筛选折叠"
      method: "designInspection"
    - id: DR-2
      check: "每行至少 3 个可区分字段"
      method: "designInspection"
    - id: DR-3
      check: "状态徽章有文本+图标，不只靠颜色"
      method: "designInspection"

  automatedTest:
    - id: AT-1
      check: "所有可见主操作按钮对应的动作在当前状态+权限下可用"
      method: "assertCapabilityConsistency"
      input: "遍历每个状态×每个角色"
    - id: AT-2
      check: "批量高风险操作前出现影响预览"
      method: "assertImpactPreview"
    - id: AT-3
      check: "行数 > 1000 时 DOM 节点数 < 200（虚拟滚动生效）"
      method: "assertVirtualScroll"

  usabilityTest:
    - id: UT-1
      task: "找到一笔 1280 元的待发货订单"
      successCriteria:
        - "maxClicks: 3"
        - "maxTime: 5s"
        - "errorRate: < 5%"
    - id: UT-2
      task: "批量发货 3 笔订单"
      successCriteria:
        - "maxClicks: 8"
        - "impactPreviewShown: true"
```

### 1.6 组合层（Composition）

声明与其他模式的兼容性，详细规则见方向 2。

```yaml
composition:
  compatible:
    - pattern: "MasterDetail"
      constraint: "本模式作为 Master 侧"
    - pattern: "ViewManagement"
      constraint: "叠加在 filterRegion 之上"
    - pattern: "BulkOperation"
      constraint: "通过 bulkSelection 槽位接入"
  mutuallyExclusive:
    - pattern: "Dashboard"
      reason: "Dashboard 是低密度概览，List Report 是高密度明细，同屏产生认知冲突"
  emergent:
    - combo: ["ListReport", "Worklist", "Assignment", "Aging"]
      emerges: "任务接力工作台"
      see: "方向 2 §3"
```

## 3. 不变量规则库

所有模式共用的不变量规则统一编号，避免重复定义。

### 3.1 能力与状态类

| ID | 规则 | 适用模式 | 理论依据 |
|---|---|---|---|
| CAP-1 | 可见操作必须在当前状态+权限+范围+不变量+锁+时间窗+策略下可用 | 所有含操作的模式 | §3.3 |
| STATUS-1 | 状态不得仅靠颜色表达 | 所有含状态徽章的模式 | §14.3 |
| TRACE-1 | 详情分区必须可追溯到 Timeline | Object Page | §5 |
| TRACE-2 | Timeline 必须区分系统/人工/业务三层事件 | Timeline | §5.2 |
| CAUSAL-1 | Timeline 不得仅凭时间邻近暗示因果 | Timeline, Correlated Timeline | §10.6 |

### 3.2 风险与操作类

| ID | 规则 | 适用模式 | 理论依据 |
|---|---|---|---|
| RISK-1 | 高风险操作必须说明后果 | Modal Form, Exception Center | §4 |
| RISK-2 | 高风险字段不得使用 Inline Edit | Inline Edit | §4 |
| BULK-1 | 批量高风险操作前必须展示影响预览 | List Report, Data Grid | §4, §6.4 |
| IDEM-1 | 重试动作必须与幂等语义配套 | Exception Center, Background Task | §10.4 |
| EXC-1 | 异常处理动作必须受控（前置证据+影响预览+适用条件） | Exception Center | §8.2 |
| NEST-1 | 弹窗/抽屉不得嵌套同类容器 | Modal Form, Drawer Form | §13 |
| SEP-1 | 权限配置必须能检测职责分离违规（如自批） | Permission Matrix | §9.5 |

## 4. 校验引擎设计

### 4.1 校验流程

```
设计稿 / 组件代码 / 页面原型
        │
        ▼
  ┌─ 解析器 ─┐
  │ 提取槽位 │  ← 从设计稿标注或代码 AST 提取
  │ 和状态   │
  └────┬────┘
       │
       ▼
  ┌─ 规约匹配 ┐
  │ 匹配模式 │  ← 确定页面使用哪些模式
  │ 实例     │
  └────┬────┘
       │
       ▼
  ┌─ 不变量校验 ┐
  │ 逐条检查   │  ← 对每个模式实例运行 invariants
  │ invariants │
  └────┬────┘
       │
       ▼
  ┌─ 组合校验 ┐
  │ 检查模式间 │  ← 见方向 2
  │ 兼容性     │
  └────┬────┘
       │
       ▼
  ┌─ 验证生成 ┐
  │ 生成测试   │  ← 从 verification 生成测试用例
  │ 用例       │
  └────┬────┘
       │
       ▼
  校验报告
  ├─ error：违反不变量
  ├─ warning：潜在问题
  └─ pass：通过
```

### 4.2 校验报告格式

```yaml
report:
  page: "订单列表页"
  detectedPatterns:
    - pattern: "ListReport"
      confidence: 0.95
      evidence: "存在 filterRegion + rowSummary + statusBadge + pagination"
  invariantResults:
    - id: "CAP-1"
      status: "fail"
      detail: "退款按钮在'已完成'状态下仍可见，但后端会拒绝"
      severity: "error"
      fixHint: "在'已完成'状态下隐藏退款按钮或置灰并说明原因"
    - id: "STATUS-1"
      status: "pass"
    - id: "BULK-1"
      status: "warning"
      detail: "批量发货前无影响预览"
      severity: "warning"
  compositionResults:
    - combo: ["ListReport", "ViewManagement"]
      status: "compatible"
  generatedTests:
    - id: "AT-1"
      status: "generated"
      file: "tests/list-report-capability.spec.ts"
```

### 4.3 嵌入位置

校验引擎可嵌入三个位置：

| 位置 | 时机 | 形态 |
|---|---|---|
| 设计工具 | 设计师交付前 | Figma / Sketch 插件，检查设计稿槽位完整性 |
| 代码 CI | 提交前 | ESLint 自定义规则或独立 lint 工具，检查组件实现 |
| 运行时 | 上线前 | E2E 测试，检查状态机遍历和不变量 |

- 本规约的 `invariants` 是 `13-界面模型模式详解.md` 中"理论桥接"部分的形式化表达。
- 本规约的 `verification` 是方向 7（实证验证方法学）的测试用例来源。
- 本规约的 `composition` 是方向 2（组合代数）的计算输入。

## 6. 落地路径

1. **第一步**：为 25 个核心模式各写一份完整 YAML 规约（约 25 × 150 行）。
2. **第二步**：实现解析器，从 React/Vue 组件 AST 提取槽位。
3. **第三步**：实现不变量校验引擎，输出校验报告。
4. **第四步**：实现设计工具插件，从设计稿标注提取槽位。
5. **第五步**：接入 CI 和 E2E 测试框架。

第一步可在不写代码的情况下作为设计审查清单使用；后续步骤逐步自动化。
