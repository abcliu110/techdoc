# 方向 6：Agent-Native UI 模式演进

> 目标：定义 AI 从"辅助"变为主控时的下一代界面模式，补充现有 `11-AI辅助与智能化界面模型.md` 的"AI 作为辅助"范式。
> 理论基线：[`13-界面模型深层逻辑与模式体系.md`](13-界面模型深层逻辑与模式体系.md) §14.3（自动化功能分配）、§3.5（韧性状态与控制权交接）、§9.5（商业完整性）。
> 与现有文档关系：本文档是 `11-AI辅助与智能化界面模型.md` 的演进版，不是替代。

## 0. 为什么需要 Agent-Native UI

现有 `11-AI辅助与智能化界面模型.md` 覆盖了 AI Copilot、可解释推荐、人工确认、Shadow Mode、Approval Gate、Override。这些模式的共同假设是 **"用户发起任务，AI 辅助完成"**。

但 AI 能力正在从辅助走向主控：

- **Agent 主动发起**：AI 不等用户提问，主动发现异常并建议处理方案。
- **多 Agent 协作**：多个 Agent 分工处理不同业务对象，需要协调界面。
- **Agent 与人协商**：Agent 的建议与人的判断冲突时，需要协商而非简单确认。
- **AI 生成事实进入系统**：AI 的推断结果如何成为系统事实？需要溯源链。

现有模式无法回答这些新问题。本文档定义下一代 Agent-Native UI 模式。

## 1. AI 介入程度的演进谱系

```
Level 0: 无 AI
  用户完全手动操作

Level 1: AI 辅助（现有 11 号文档覆盖）
  Copilot / 可解释推荐 / 人工确认
  → 用户发起，AI 建议，人决策

Level 2: AI 准备（Approval Gate）
  AI 准备完整动作，人批准
  → AI 做了大量工作，人只做最终决策

Level 3: AI 执行，人监督（Guardrailed Automation）★ 本文档重点
  AI 在护栏内自动执行，人监督异常
  → AI 主动发起，人被动监督

Level 4: 多 Agent 协作 ★ 本文档重点
  多个 Agent 分工协作，人协调冲突
  → Agent 间协作，人作为协调者

Level 5: Agent 主导，人例外
  Agent 全权处理，人只在异常时介入
  → Agent 为主，人为例外
```

现有文档覆盖 Level 1-2。本文档定义 Level 3-5 的模式。

## 2. Agent-Native 新模式清单

| # | 模式 | 解决的核心问题 | 对应 Level |
|---|---|---|---|
| AN-1 | Proactive Proposal | Agent 主动发现并建议 | 3 |
| AN-2 | Multi-Agent Orchestration | 多 Agent 分工协作的界面 | 4 |

## 3. 模式详解

### AN-1: Proactive Proposal（主动提议）

#### 解决的核心问题

Agent 不等用户提问，主动发现业务异常或机会，并提出处理建议。

#### 与现有 Copilot 的区别

| 特征 | Copilot（现有） | Proactive Proposal（新） |
|---|---|---|
| 发起方 | 用户 | Agent |
| 时机 | 用户提问时 | Agent 发现异常时 |
| 上下文 | 用户提供的上下文 | Agent 主动扫描 |
| 打断性 | 无打断 | 可能有打断，需控制频率 |

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **触发条件透明** | 说明 Agent 为什么在这个时机提议 |
| **证据引用** | 提议必须引用数据来源和扫描范围 |
| **置信度表达** | 标注提议的置信度和不确定性 |
| **替代方案** | 提供至少一个替代方案 |
| **打断控制** | 高严重度主动弹出，低严重度进入待办 |
| **拒绝反馈** | 用户拒绝后，Agent 记录并校准 |
| **频率限制** | 避免提议疲劳，同类型提议聚合 |

#### 标准结构

```
┌─ Agent 主动提议 ─────────────────────────────────┐
│ ⚡ Agent 发现 3 笔支付异常待处理                  │
│                                                   │
│ 触发条件：支付回调超时 > 5分钟（每5分钟扫描）      │
│ 扫描范围：今日全部订单                             │
│ 置信度：高（3笔均超时，渠道确认未支付）             │
│                                                   │
│ 建议处理：取消这3笔订单并通知顾客重新支付           │
│ 依据：支付渠道确认未收到款项                       │
│                                                   │
│ 替代方案：                                        │
│  [A] 取消订单+通知顾客（推荐）                     │
│  [B] 等待10分钟后重新检查                          │
│  [C] 转人工逐一核验                               │
│                                                   │
│  [采纳A] [采纳B] [采纳C] [拒绝并反馈]             │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §3.5 韧性状态：Agent 主动监测是"预见"能力的体现。
- §14.3 自动化功能分配：Agent 负责信息获取和分析，人保留选择和执行。
- §8 异常闭环：Proactive Proposal 是异常从"被动发现"到"主动发现"的演进。

### AN-2: Multi-Agent Orchestration（多 Agent 编排）

#### 解决的核心问题

多个 Agent 分工处理不同业务对象（支付Agent、库存Agent、物流Agent），界面如何展示各 Agent 的状态、依赖和冲突。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **Agent 身份卡** | 每个 Agent 有身份、职责、当前状态 |
| **依赖关系图** | 展示 Agent 间的数据依赖和触发关系 |
| **并行状态视图** | 多 Agent 并行执行时的进度对比 |
| **冲突检测** | 两个 Agent 的输出矛盾时高亮冲突 |
| **汇合点标注** | 标注哪些 Agent 结果需要汇合后才能继续 |
| **控制权分配** | 明确每个 Agent 的控制级别（建议/批准/执行） |

#### 标准结构

```
┌─ 多 Agent 编排视图 ──────────────────────────────┐
│                                                   │
│  订单 #SO202607120001 处理中                       │
│                                                   │
│  ┌─ 支付Agent ──┐  ┌─ 库存Agent ──┐  ┌─ 物流Agent ┐│
│  │ 状态：已完成  │  │ 状态：执行中  │  │ 状态：等待  ││
│  │ 置信度：高    │  │ 置信度：中    │  │ 等待：库存  ││
│  │ ✓ 支付确认   │  │ ○ 锁定库存中  │  │   Agent完成 ││
│  └──────┬───────┘  └──────┬───────┘  └──────┬─────┘│
│         │                 │                  │      │
│         └────── 汇合点 ───┘                  │      │
│                ↓                              │      │
│         库存锁定完成后 ────────────────────────┘      │
│                ↓                                     │
│         物流Agent 开始执行                             │
│                                                   │
│  ⚠ 冲突：库存Agent 建议部分发货，支付Agent 已全额扣款 │
│  [查看冲突详情] [人工裁决]                          │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §10.3 并行工作流：多 Agent 编排本质是 Petri Net 的 Fork/Join。
- §10.5 边界对象：各 Agent 的输出需通过共享核心对齐。
- §13 术语-语义失配：不同 Agent 可能对"完成"有不同定义。

### AN-3: Negotiation Panel（协商面板）

#### 解决的核心问题

Agent 的建议与人的判断冲突，或两个 Agent 的输出矛盾时，如何通过协商而非简单确认解决。

#### 与现有 Approval Gate 的区别

| 特征 | Approval Gate（现有） | Negotiation Panel（新） |
|---|---|---|
| 关系 | 人审批 AI | 平等协商 |
| 冲突 | AI 准备，人接受/拒绝 | 双方各有立场和证据 |
| 结果 | 二选一 | 可能产生折中方案 |
| 理由 | AI 附带理由 | 双方都提供理由和证据 |

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **双方立场** | 同时展示 Agent 立场和人的立场 |
| **证据对比** | 双方证据并排展示 |
| **约束标注** | 标注不可妥协的硬约束 |
| **折中方案** | 系统建议折中方案（如有） |
| **决策记录** | 协商过程和结果完整记录 |
| **升级路径** | 无法协商一致时升级人工裁决 |

#### 标准结构

```
┌─ 协商面板：退款金额争议 ─────────────────────────┐
│                                                   │
│  ┌─ Agent 立场 ──────────┐  ┌─ 人工立场 ─────────┐│
│  │ 退款 ¥128（全额）      │  │ 退款 ¥80（部分）    ││
│  │                       │  │                    ││
│  │ 证据：                 │  │ 证据：              ││
│  │ - 顾客主张商品损坏     │  │ - 商品仅外包装磨损  ││
│  │ - 照片显示功能受损     │  │ - 功能正常          ││
│  │ - 7天无理由退款政策    │  │ - 建议折价补偿      ││
│  │                       │  │                    ││
│  │ 置信度：高(85%)        │  │ 置信度：中(60%)     ││
│  └───────────────────────┘  └────────────────────┘│
│                                                   │
│  硬约束：7天无理由退款政策适用                      │
│                                                   │
│  系统建议折中：退款 ¥100 + 补寄包装                 │
│  依据：功能正常但包装确实磨损，折中方案双方可接受    │
│                                                   │
│  [采纳折中] [坚持全额] [坚持部分] [升级主管裁决]    │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §9.3 共同基础与承诺闭环：协商需要共享足够的事实和约束。
- §14.4 因果证据层级：双方证据需区分构成/相关/干预/反事实。
- §4.2 风险自适应防护：协商是高风险操作的防护层。

### AN-4: Provenance Chain（溯源链）

#### 解决的核心问题

AI 生成的事实（如 Agent 自动取消的订单）如何进入 Timeline？需要区分"系统事件/人工事件/AI 推断事件"为四层，并标注置信度和可追溯证据。

#### 与现有 Timeline 的区别

现有 Timeline 三层事件：系统自动、人工操作、业务状态。AI 时代需扩展为四层：

| 事件层 | 触发者 | 记录内容 | 可信度 |
|---|---|---|---|
| 系统自动 | 支付回调/定时任务 | 事件名、时间、结果 | 高（事实） |
| 人工操作 | 客服/运营 | 操作人、时间、前后值、原因 | 高（事实） |
| 业务状态 | 状态机流转 | 前后状态、触发条件 | 高（事实） |
| **AI 推断**（新） | Agent | 模型版本、输入数据、推断逻辑、置信度、人工确认状态 | 中（候选事实） |

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **四层事件区分** | AI 推断事件用独立图标和颜色标注 |
| **模型版本记录** | 记录推断使用的模型版本和策略版本 |
| **输入数据引用** | 推断依据的数据可点击查看原始证据 |
| **置信度标注** | 标注推断置信度和不确定性范围 |
| **确认状态** | 候选→人工确认→成为事实 的状态流转 |
| **可撤销** | 人工确认前可撤销 AI 推断 |

#### 标准结构

```
┌─ 时间线（含 AI 推断层）──────────────────────────┐
│                                                   │
│  07-12 14:30  系统    订单完成                     │
│  07-12 14:00  AI推断  🤖 Agent建议发货             │
│               模型：Logistics-v2.1                 │
│               依据：库存已锁定+支付已确认+SLA 2h    │
│               置信度：92%                          │
│               状态：✓ 人工确认（张三 14:05）        │
│  07-12 11:00  人工    客服张三 添加备注             │
│  07-12 10:33  系统    库存锁定                     │
│  07-12 10:32  系统    支付成功                     │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §5 可追溯性：AI 推断事件是可追溯性的新维度。
- §3.4 多维状态：AI 推断的"数据状态"需标注模型版本和数据时间。
- §9.5 商业完整性：AI 生成事实需通过受控动作才能成为系统事实。

### AN-5: Drift & Confidence Decay（漂移与置信度衰减）

#### 解决的核心问题

模型随时间漂移，旧推荐的置信度逐渐降低。界面如何表达这种衰减，避免用户信任过期的 AI 结论。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **模型版本时间** | 标注模型训练数据截止时间 |
| **衰减指示器** | 随时间推移，置信度可视化衰减 |
| **过期标记** | 超过有效期后标记为"需重新评估" |
| **重新推断入口** | 提供用最新模型重新推断的操作 |
| **漂移监控** | 展示模型在近期数据上的表现指标 |

#### 标准结构

```
┌─ AI 推荐补货数量 ────────────────────────────────┐
│                                                   │
│  推荐：SKU001 补货 50 件                           │
│  模型：Inventory-Rec-v3.2                         │
│  训练数据截止：2026-06-30                          │
│  推断时间：2026-07-10                              │
│                                                   │
│  置信度衰减：                                      │
│  07-10 ████████████████████ 92%（高）              │
│  07-12 ██████████████████   85%（高）              │
│  07-15 ████████████████     78%（中）← 今天        │
│  07-20 █████████████        65%（中）              │
│  07-25 ██████████           52%（低）→ 需重新评估   │
│                                                   │
│  ⚠ 此推荐基于 15 天前的模型，建议重新推断           │
│  [用最新模型重新推断] [采纳当前推荐] [忽略]         │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §3.4 数据状态：AI 推断的数据新鲜度需独立标注。
- §14.4 预测不确定性：点估计需附带合理区间和适用条件。
- §14.3 信任校准：置信度衰减是信任校准的时间维度。

### AN-6: Control Handoff Dashboard（控制权交接看板）

#### 解决的核心问题

多个 Agent 在不同控制级别运行时，用户如何全局掌握"谁在控制什么、哪些需要接管"。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **Agent 控制级别矩阵** | 每个 Agent 当前的控制级别（建议/批准/执行/自主） |
| **接管入口** | 一键从 Agent 接管控制权 |
| **回退路径** | 接管后如何安全回退给 Agent |
| **接管理由记录** | 接管时必须记录原因 |
| **接管窗口** | 标注接管的时间窗口和安全状态 |

#### 标准结构

```
┌─ 控制权交接看板 ─────────────────────────────────┐
│                                                   │
│  Agent          控制级别    状态      操作          │
│  ────────────────────────────────────────────────  │
│  支付Agent      自主执行    ✓ 正常    [接管]       │
│  库存Agent      批准后执行   ⚠ 需审批  [审批]       │
│  物流Agent      建议模式    ● 等待人   [处理建议]   │
│  退款Agent      已接管      👤 人工中  [回退给Agent]│
│                                                   │
│  接管记录：                                        │
│  07-12 14:00 张三 接管退款Agent                    │
│  原因：连续3笔退款金额异常，需人工核验              │
│  预计回退：核验完成后                               │
└───────────────────────────────────────────────────┘
```

#### 理论桥接

- §3.5 韧性状态与控制权交接：Control Handoff 的全局视图。
- §14.3 自动化功能分配：控制级别需明确且可切换。
- §10.1 控制回路：控制权振荡需检测和防止。

### AN-7: Agent Audit Trail（Agent 审计追溯）

#### 解决的核心问题

Agent 的决策过程如何审计？不同于人工操作的审计，Agent 审计需要记录模型版本、输入数据、推断逻辑和置信度。

#### 与现有 Audit Log 的区别

| 特征 | Audit Log（现有） | Agent Audit Trail（新） |
|---|---|---|
| 记录对象 | 人工操作 | Agent 决策 |
| 核心字段 | 操作人、时间、前后值 | 模型版本、输入数据、推断逻辑、置信度 |
| 追溯目标 | 谁做了什么 | AI 为什么这样做 |
| 复现性 | 不需要 | 需要可复现推断过程 |

#### 标准结构

```
┌─ Agent 审计追溯 ─────────────────────────────────┐
│                                                   │
│  事件：Agent 自动取消订单 #SO202607120003          │
│  时间：2026-07-12 14:05                           │
│  Agent：Payment-Monitor-v1.5                      │
│  模型版本：Payment-Forecast-v2.1                  │
│  策略版本：Cancel-Policy-2026Q2                   │
│                                                   │
│  输入数据：                                        │
│  - 支付回调超时：5min                             │
│  - 渠道查询结果：未支付                            │
│  - 历史同类订单：95%最终未支付                     │
│                                                   │
│  推断逻辑：                                        │
│  IF 超时 > 5min AND 渠道未确认 THEN 自动取消       │
│                                                   │
│  置信度：92%                                      │
│  控制级别：自主执行（Guardrailed）                 │
│  护栏检查：✓ 金额 < ¥500 ✓ 24h内可恢复             │
│                                                   │
│  人工复核：不需要（自主执行级别）                   │
│  可复现：[用相同输入重新推断]                      │
└───────────────────────────────────────────────────┘
```

### AN-8: Boundary Proposal（能力边界提议）

#### 解决的核心问题

Agent 在接近自身能力边界时（置信度下降、输入异常、超出训练分布），应主动提议将控制权交给人工。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **边界检测** | 检测输入超出训练分布、置信度低于阈值 |
| **边界标注** | 明确标注"Agent 认为此情况超出其能力" |
| **上下文转移** | 完整转移推断上下文给人工 |
| **不强行执行** | 边界处不自动执行，必须人工确认 |

---

### AN-9: Batch Agent Review（批量 Agent 结果审核）

#### 解决的核心问题

Agent 自主处理了 100 笔订单后，人如何高效审核这批结果，而非逐笔查看。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **结果汇总** | 成功/失败/异常分类统计 |
| **异常优先** | 异常结果优先展示 |
| **抽样审核** | 按风险等级抽样全量审核 |
| **批量接受** | 低风险正常结果批量接受 |
| **批量拒绝** | 异常结果批量拒绝并回退 |

---

### AN-10: Agent Maturity Gate（Agent 成熟度门禁）

#### 解决的核心问题

新的 Agent 或模型版本上线前，如何验证其成熟度达到可自主执行的标准。

#### 核心设计要素

| 要素 | 设计要求 |
|---|---|
| **Shadow Mode 验证** | 后台运行并与人工结果对比 |
| **准确率门禁** | 准确率达标后才允许上线 |
| **分级上线** | 建议→批准→自主 逐级放开 |
| **回滚机制** | 上线后表现下降时可回滚到上一版本 |
| **护栏配置** | 自主执行前配置额度、范围和不变量护栏 |

## 7. 与其他方向的关系

- **方向 1**：Agent-Native 模式的形式化规约复用方向 1 的格式，新增 `agentContract` 属性。
- **方向 2**：Agent-Native 模式可与现有模式组合（如 `Worklist ⊕ ControlHandoffDashboard`）。
- **方向 3**：Agent 的自主执行是状态机的新触发者，需扩展状态机模型。
- **方向 4**：Agent-Native 模式的可访问性契约补充见上节。
- **方向 7**：Agent-Native 模式处于 `maturity: hypothetical`，需优先走实证验证。
- **方向 8**：行业场景的 Agent 应用（如财务自动对账Agent）需叠加行业不变量。
