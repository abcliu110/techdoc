List Report — 列表报告
SAP FioriAnt Design ProIBM Carbon金蝶云苍穹
核心问题
大量对象中快速定位和批量处理。核心矛盾：列表可能有数万行，用户需在几秒内找到目标对象。

案例 1：SAP Fiori Elements — 销售订单 List Report（命名来源）

SAP Fiori ElementsS/4HANA 销售订单管理
SAP Fiori Elements 的 List Report 是这一模式的命名来源。通过 CDS View + OData 自动生成列表页。核心结构：顶部 Smart Filter Bar 默认展开核心字段、折叠高级筛选；中间 Smart Table 展示行摘要（订单号+客户+金额+状态+交货日期）；行末外露主操作；选中行后顶部出现批量操作栏。SAP 官方设计规范明确：列表窗格和对象详情窗格在大窗口并排显示，紧凑窗口则单窗格堆叠切换。
┌─ Smart Filter Bar ────────────────────────────────┐ │ [销售组织▼] [渠道▼] [日期] [搜索__] [Go] [Hide Filters]│ │ ▸ 高级筛选（折叠） │ └──────────────────────────────────────────────────┘ ┌─ 批量操作栏（选中后出现）──────────────────────────┐ │ 已选 3 项 [批量审批] [批量拒绝] [导出] [影响预览] │ └──────────────────────────────────────────────────┘ ┌─ Smart Table ──────────────────────────────────────┐ │ ☑ 订单号 客户 金额 状态 交货日 操作│ │ ☑ SO00100 Siemens ¥128,000 [✓确认] 07-20 [查看] │ │ ☑ SO00101 BMW ¥56,000 [⏳审批] 07-22 [查看] │ │ ☐ SO00102 BASF ¥89,500 [📦交货] 07-15 [查看] │ └──────────────────────────────────────────────────┘
标杆洞察：Smart Filter Bar 实现"核心筛选默认展开+高级筛选折叠"信息分层，且筛选与表格共享同一 OData 上下文，保证图表和明细口径一致。状态徽章用图标+文本+颜色三重编码，不只靠颜色——这是 SAP Fiori Design Guidelines 的硬性要求。

案例 2：Ant Design Pro — ProTable 查询表格

Ant Design Pro中后台标准列表页
ProTable 是 Ant Design Pro 对 List Report 的工程化实现。核心是 QueryFilter + ProTable + 工具栏三段式。QueryFilter 默认展示前 N 个字段，更多折叠；ProTable 支持行选择、排序、筛选、固定列、可编辑行；工具栏支持导出、密度、列设置、全屏。
标杆洞察：ProTable 把"低频操作收敛到工具栏"做得很彻底——刷新、密度、列设置、全屏都放表格右上角图标组。这是 Hick-Hyman 定律的直接体现：选项收敛降低决策时间。

案例 3：金蝶云苍穹 — 应用管理列表

金蝶云苍穹社区版开发平台→应用管理
采用 卡片式对象管理+分面筛选变体。顶部提供搜索、业务云筛选、来源分类（全部/金蝶/自建/第三方）；主体展示应用卡片，每张聚合名称、编码、启用状态、版本号和管理动作集（详情、脚本、菜单、导出、禁用、预览）。
标杆洞察：金蝶选择卡片而非表格，因应用对象数量有限（几十个），卡片能在有限数量下提供更完整对象上下文。同时提供卡片/列表双视图切换应对数量增长——信息密度自适应的工程解法。

案例 4：IBM Carbon — Data Table + Batch Actions

IBM Carbon Design System企业数据密集型系统
Carbon Data Table 定义了可访问性标杆：语义化 table 结构，支持键盘方向键导航、行展开、批量工具栏和分页。批量操作工具栏在选中行后从底部滑入，不遮挡数据。
标杆洞察：Carbon 批量操作栏是"渐进出现"的——未选中不占空间，选中后底部滑入。渐进披露比常驻工具栏更节省认知负荷。
✗ 反模式：SAP GUI 传统 ALV 表格
传统 SAP GUI 的 ALV 所有筛选项平铺、所有按钮平铺，不符合"高频外露低频收敛"。用户面对 30+ 列和 20+ 按钮，认知负荷极高。
✓ Fiori List Report 通过 Smart Filter Bar 和工具栏收敛解决。
理论桥接：§2 信息分层（列表行是一级信息，详情是二级）；§3 状态轴（筛选本质是状态过滤器）；§13 信息-认知失配（高频外露低频收敛）。

Object Page — 对象详情页
SAP FioriSalesforce Lightning金蝶云苍穹
核心问题
把散落在多个数据库表中的数据，聚合成用户能理解的业务对象。一个订单在数据库里涉及 8+ 张表。

案例 1：SAP Fiori — Object Page（命名来源）

SAP Fiori ElementsS/4HANA 销售订单详情
SAP Object Page 分为 对象头部（Object Header）+ 内容分区（Sections）。头部展示订单号、状态、金额、客户、主操作按钮；内容区按业务语义分区：概览、行项目、合作伙伴、定价、交货、状态历史。每个分区有锚点导航，支持快速跳转。
┌─ Object Header ────────────────────────────────┐ │ 订单 SO00100 [创建交货] [打印] │ │ 状态：[✓已确认] 金额¥128,000 客户：Siemens AG │ │ 概览|行项目|合作伙伴|定价|交货|状态历史 ← 锚点 │ └───────────────────────────────────────────────┘ ┌─ 行项目 ────────────────────────────────────────┐ │ 物料 描述 数量 单价 金额 状态 │ │ M001 电机A型 100 ¥1,200 ¥120,000 [可用] │ │ M002 控制器B 20 ¥400 ¥8,000 [可用] │ └───────────────────────────────────────────────┘
标杆洞察：SAP Object Page 的关键设计是分区锚点导航与滚动联动——点击标签自动滚动到分区，滚动时高亮当前标签。比 Tab 切换更流畅，因为用户可以连续浏览所有分区而不丢失位置。SAP 官方规范明确：对象详情页由页眉、内容区域、操作区域三部分组成。

案例 2：Salesforce Lightning — Record Page

Salesforce LightningCRM 客户/商机/合同记录页
Salesforce Record Page 采用 三列布局：左列 Highlights Panel（客户名+评分+主要联系方式，只展示4-6个关键字段）；中列详情分区和 Related Lists；右列组件侧栏（关键提醒、推荐操作、AI 建议）。页面布局可按角色和记录类型通过 Lightning App Builder 动态调整。
标杆洞察：Salesforce 的 Record Page 是"可组合"的——管理员拖拽组件定制不同角色布局。这是 Object Page 从"固定结构"到"可组合架构"的演进。Highlights Panel 只展示 4-6 个最关键字段，严格遵守信息分层。

案例 3：金蝶云苍穹 — 单据详情页

金蝶云苍穹办公用品领用申请单
采用 单据头+明细分录+状态命令栏结构。单据头展示申请上下文；明细分录展示物品明细（可多行增删）；底部命令栏展示操作（暂存、提交、审批、打印）。状态变化时命令栏动态调整——草稿态显示"暂存+提交"，待审态显示"审批+驳回"。
标杆洞察：金蝶"单据头+分录"是中国 ERP 经典结构，本质是 Object Page 领域化变体，比 SAP 分区式更强调"主从结构"。命令栏随状态动态调整操作，这是能力模型（CAP-1）的实践。
理论桥接：§1 数据-心理失配（Object Page 是数据库语言到用户心理模型的"翻译器"）；§3.2 状态四问；§5 可追溯性。

Timeline — 时间线
Salesforce LightningSAP FioriAnt Design
核心问题
让用户理解"这个状态是怎么变成这样的"——业务事实的可追溯性。

案例 1：Salesforce Lightning — Activity Timeline

Salesforce Lightning客户/商机记录页活动时间线
Salesforce Activity Timeline 在 Record Page 中列展示按时间倒序的活动流，区分邮件、电话、会议、任务、备注等不同类型事件，每种用不同图标标注。点击活动可展开详情不跳转页面。支持筛选（只看邮件/只看电话）和内联添加。
┌─ Activity Timeline ───────────────────────┐ │ 📧 邮件 今天 14:30 │ │ 回复了客户关于报价的邮件 │ │ ☎ 电话 今天 11:00 张三 │ │ 沟通合同条款，客户要求折扣 │ │ 📅 会议 昨天 15:00 李四,王五 │ │ 产品演示会议，客户反馈积极 │ │ ✓ 任务 07-13 完成 张三 │ │ 发送产品资料包 │ └─────────────────────────────────────────┘
标杆洞察：Salesforce Timeline 把不同类型活动用图标+文本区分（不只靠颜色），符合可访问性。活动类型筛选器让用户在长时间线中快速聚焦——信息分层在时间维度的应用。

案例 2：SAP Fiori — 状态历史分区

SAP Fiori销售订单状态流转
SAP Object Page 内嵌状态历史分区，展示业务状态机流转完整记录：每个节点含时间、操作人、前状态→后状态、触发条件。不同于 Salesforce 活动流（偏沟通记录），SAP 状态历史更偏业务状态机事件。
标杆洞察：SAP 严格记录"前状态→后状态"，支持状态回溯审计。对应三层事件模型——系统自动事件（信用检查）、人工操作事件（确认订单）、业务状态事件（状态机流转）三层分开标注。

案例 3：Ant Design — Steps + Timeline 组件

Ant Design审批流程追踪
用 Steps 展示审批进度（已通过/当前/待审批），用 Timeline 展示详细操作日志。常见组合：上半部分 Steps 概览，下半部分 Timeline 详情。
标杆洞察：Ant Design 把 Timeline 拆成"进度概览+详细日志"两层，前者一眼看到流程走到哪，后者追踪每步细节。信息分层在时间线的应用。
理论桥接：§5 可追溯性（三层事件：系统/人工/业务状态）；§5.3 状态流转完整表达（时间+事件类型+操作人+前后状态+原因）。

Related Lists — 关联列表
Salesforce LightningSAP Fiori
核心问题
一个业务对象关联的其他对象，如何在不喧宾夺主的情况下完整呈现。

案例 1：Salesforce Lightning — Related Lists（命名来源）

Salesforce Lightning客户记录页关联订单/合同/案例
在客户 Record Page 中列展示该客户关联的订单、合同、案例、活动等列表。每个 Related List 默认展示 5 条最近记录，可点击"View All"跳转独立页面查看完整列表。支持内联筛选、排序和快速新建。2025年 Salesforce 推出 Dynamic Related Lists，可按筛选条件动态过滤关联记录、自定义展示字段和顺序。
标杆洞察：Salesforce Related Lists 三个关键约束：①默认只展示5条（避免喧宾夺主）；②只展示关键字段（完整跳转独立页）；③关联列表内只做查看和轻量操作（复杂操作跳转）。Dynamic Related Lists 进一步允许按上下文动态过滤——例如只展示"本年度金额>1万的订单"。

案例 2：SAP Fiori — Object Page Line Items

SAP Fiori订单详情中的交货单/发票关联
SAP Object Page 每个分区本身就是一个 Related List——"交货"分区展示关联交货单，"定价"分区展示定价条件，"发票"分区展示关联发票。通过分区锚点导航而非独立 Tab。
标杆洞察：SAP 把 Related Lists 融入 Object Page 分区结构，而非像 Salesforce 那样作为独立组件堆叠。优势是上下文连贯，劣势是当关联对象多时分区会很长——SAP 通过默认折叠次要分区解决。
理论桥接：§1 信息聚合（Related Lists 把关联对象"聚"到主对象下）；§2 信息分层（关联列表是二级信息，不是详情页核心）。

Master-Detail — 主从布局
Microsoft FluentSAP FioriAnt Design
核心问题
连续处理多个对象时，减少页面跳转带来的上下文切换。

案例 1：SAP Fiori — Flexible Column Layout

SAP Fiori订单→支付→物流三级展开
SAP 的 Flexible Column Layout 是 Master-Detail 的进阶版，支持最多三栏并列：列表→详情→子详情。用户在列表选中订单，中间展示订单详情，右侧可展开支付单或物流详情。栏宽可拖拽调整，窄屏自动退化为单栏。
┌─ 列表 ────┬─ 详情 ──────┬─ 子详情 ────┐ │ [搜索] │ 订单SO001 │ 支付单 │ │ ●SO001 │ [✓确认] │ PAY001 │ │ SO002 │ ¥128,000 │ 微信¥128,000│ │ SO003 │ Siemens AG │ [✓已支付] │ │ │ [发货][退款]│ 10:32 │ └──────────┴────────────┴────────────┘
标杆洞察：SAP Flexible Column Layout 解决了"主从只有两层不够"的问题——订单关联支付单，支付单又关联银行流水，三级展开让用户追踪完整链路。窄屏退化时保留上下文（返回列表时筛选状态不变）。

案例 2：Microsoft Fluent UI — List Details

Microsoft Fluent UIOutlook 邮件列表+阅读窗格
Microsoft 在 Outlook、Teams、SharePoint 中大量使用 Master-Detail。左侧列表选中项高亮，右侧详情区同步更新。Fluent UI 官方组件库提供 DetailsList 支持键盘方向键导航（↑↓切换项，Enter打开）。
标杆洞察：Microsoft 特别强调键盘导航——↑↓键在主列对象间切换，Tab键进入从面板。这是技能型用户高频操作的效率保障。
理论桥接：§2 认知负荷（减少跳转=减少上下文切换）；§3 状态轴（列表栏本质是状态过滤）。

Dashboard — 角色工作台
SAP FioriSalesforce Lightning金蝶云苍穹
核心问题
角色每天开始工作时，如何在几秒内了解全局状态、快速进入任务。

案例 1：SAP Fiori — Overview Page

SAP Fiori Overview Page管理者概览
SAP Overview Page 顶部全局筛选（日期/组织），主体为 KPI 卡片+Smart Chart 网格。每张 KPI 卡片展示指标值、趋势箭头、目标达成率，点击可钻取到 Analytical List Page。卡片可拖拽重排，按角色配置。
标杆洞察：每个 KPI 卡片都可钻取——点击"销售额"进入 Analytical List Page，再钻取到订单明细。实现了"指标→维度→明细→对象"完整钻取链。全局筛选控制所有卡片保证口径一致。

案例 2：Salesforce Lightning — Dashboard + Report Chart

Salesforce Lightning销售经理首页
Salesforce Dashboard 由多个 Report Chart 组合，图表数据来自 Salesforce Report。点击图表自动跳转到对应 Report，再从 Report 钻取到具体记录。
标杆洞察：每个图表直接关联一个 Report——"图表→报表→记录"完整钻取链，且数据口径一致（都来自同一 Report）。Dashboard 组件可拖拽组合，按角色定制。

案例 3：金蝶云苍穹 — 可配置工作台

金蝶云苍穹社区版办公用品领用工作台
采用 可配置工作台+行动卡片。页面围绕业务主题组织，提供立即查看、忽略、调整布局和全屏。
标杆洞察："调整布局"让工作台从"固定首页"进化为"可个性化工作区"——Dashboard 从"千人一面"到"角色定制"的演进。
✗ 反模式：首页只堆图表不提供钻取
用户问"为什么销售额下降了"，页面无法回答。
✓ SAP 每个卡片可钻取；Salesforce 每个图表关联 Report。
理论桥接：§2 信息分层（KPI→图表→明细）；§7 钻取链路；§14.4 Goodhart 效应（KPI 需护栏指标）。

Worklist — 待办工作列表
SAP FioriSalesforce LightningAnt Design Pro
核心问题
把当前角色真正可处理的任务组织成队列，让用户看清责任、优先级、等待时间和下一步。

案例 1：SAP Fiori — My Inbox

SAP Fiori My InboxS/4HANA 审批中心
SAP My Inbox 是 Worklist 模式的标杆。它聚合来自 SAP Business Workflow 和外部系统的审批任务，按状态展示待审批/已审批/已委托。每个任务卡片展示任务标题、发起人、金额、提交时间、SLA 倒计时。支持批量审批、委托、拒绝（需填原因）。
标杆洞察：My Inbox 聚合多来源审批任务到统一队列——这是 Worklist 的核心价值：不是"一个列表"，而是"按角色+状态计算出的可处理任务集合"。SLA 倒计时让老化可见，避免任务饥饿。

案例 2：Salesforce Lightning — List View + Kanban

Salesforce Lightning商机看板
Salesforce 的 Kanban View 是 Worklist 的可视化变体。每一列代表一个销售阶段，卡片代表商机。用户可拖拽卡片在阶段间移动。每列顶部显示该阶段商机金额合计。支持按字段分组、汇总和筛选。Salesforce 官方文档明确：Kanban 几乎可在任何列表视图中查看，适用于大多数对象。
┌─ Kanban：商机按阶段 ────────────────────────┐ │ 资格认定 需求分析 方案报价 谈判 │ │ ┌────────┐ ┌────────┐ ┌────────┐ │ │ │ BMW │ │ Siemens│ │ BASF │ │ │ │ ¥56K │ │ ¥128K │ │ ¥89K │ │ │ │ 张三 │ │ 李四 │ │ 王五 │ │ │ └────────┘ └────────┘ └────────┘ │ │ 合计¥56K 合计¥128K 合计¥89K │ │ ← 拖拽卡片在阶段间移动 → │ └─────────────────────────────────────────────┘
标杆洞察：Salesforce Kanban 把"阶段流转"从下拉框选择变成了拖拽操作——更直观地映射了"对象在阶段间推进"的心理模型。每列金额合计让销售经理一眼看到漏斗分布。结合 Path 组件（在 Record Page 顶部展示阶段进度+关键字段+指南），形成了完整的阶段流转工作台。

案例 3：Ant Design Pro — 待办列表

Ant Design Pro中后台审批中心
Ant Design Pro 的待办列表通常用 ProTable 实现，通过筛选条件固定展示"待处理"状态的任务。常见组合：Tab 切换（待办/已办/全部）+ 表格（任务名/发起人/时间/优先级/操作）+ 批量审批。
标杆洞察：Ant Design Pro 的 Tab 切换本质是"状态过滤器"——待办 Tab 只展示"待处理"状态，无需用户手动筛选。这是 Worklist 与 List Report 的关键区别。
理论桥接：§3 状态与能力（Worklist 只呈现可执行任务）；§10.2 排队与流动（展示老化、SLA、WIP 限制）；§9 协作（责任分配+交接）。

表单族 — Simple / Sectioned / Drawer / Modal Form

SAP S/4HANAPFCG 角色配置

标杆洞察：SAP 把"操作权限"和"数据范围"分离——ACTVT 控制能做什么，BUKRS 控制能看哪些公司的数据。权限模拟让管理员在配置后直接验证效果，不需要切换账号登录。

✗ 反模式：权限只配置不审计

Salesforce 的 Customer 360 是该模式的命名来源。在客户 Record Page 上聚合：基本信息、联系方式、交易历史（订单 Related List）、沟通记录（Activity Timeline）、服务工单（Cases）、合同（Contracts）、团队成员、AI 推荐（Einstein 建议）。三列布局：左列 Highlights，中列详情+Related Lists，右列组件+AI建议。

案例 2：Microsoft Dynamics 365 — Customer Insights

Microsoft Dynamics 365Customer Insights 客户画像
Microsoft Customer Insights 聚合多源数据（CRM/ERP/电商/社交媒体），通过身份解析（Identity Resolution）合并同一客户的不同标识。展示客户画像、交易历史、行为轨迹和预测评分（流失风险/生命周期价值）。
标杆洞察：Microsoft Customer Insights 的身份解析展示置信度和匹配规则——当两个标识可能是同一客户时，展示匹配依据和置信度，而非自动合并。这对应 ID-1 不变量（身份映射必须展示置信度和冲突处理流程）。
理论桥接：§1 数据聚合（多渠道数据→统一客户视图）；§10.5 边界对象（跨系统同名对象保留来源）；§9.6 上下文完整性（最小披露——按角色展示必要数据）；方向 8 INV-COM-002（敏感数据脱敏）。

总结：标杆系统的共性规律

1. 模式不是组件，是任务-对象-状态的映射

标杆系统不约而同地把"模式"作为设计语言的单位——SAP Fiori 直接命名了 List Report、Object Page、Overview Page、Worklist；Salesforce 命名了 Record Page、Related Lists、Path、Kanban。模式不是视觉组件，而是"特定任务×特定对象×特定状态"的解法。

2. 信息分层是所有模式的共同骨架

无论 SAP 的 Smart Filter Bar（核心筛选展开+高级折叠）、Salesforce 的 Highlights Panel（只展示4-6个关键字段）、还是 Ant Design Pro 的 QueryFilter（前N个字段默认展示），都在执行同一个原则：第一层（当前任务应看到的）→第二层（理解背景）→第三层（排查问题时才看）。

3. 状态驱动操作可用性

金蝶的命令栏随状态动态调整、SAP 的 Object Page 操作按状态机计算、Salesforce 的 Path 标注当前阶段可用动作——所有标杆系统都遵循能力模型：availableActions = f(状态, 权限, 范围, 不变量, 锁, 时间窗, 策略)。

4. 钻取链路必须完整

SAP 的 Visual Filter→明细表→Object Page、Salesforce 的 Dashboard→Report→Record、Power BI 的层级钻取——所有标杆系统都保证指标→维度→明细→业务对象的完整链路，且每层保留筛选上下文。

5. 风险分层决定承载方式

Microsoft 区分 Dialog（阻断）和 Panel（非阻断）、Ant Design 区分 ModalForm 和 DrawerForm、SAP 区分 Toast/Strip/Dialog/Page——所有系统都按风险级别选择不同承载容器。高风险用阻断式确认+影响预览，低风险用非阻断式反馈。

6. 协作状态必须显式

SAP My Inbox 展示审批任务的责任人和 SLA、Salesforce 的 Assignment + Queues 展示任务分配——所有系统都把"谁负责、等待谁、何时超时"显式化，而非依赖口头沟通。

7. AI 时代的共同方向

Salesforce Einstein、SAP Joule、Microsoft Copilot 都在向上下文感知+可解释推荐+人工确认+信任层方向演进。AI 推荐展示置信度和依据，高风险操作保留人工确认，敏感数据经过脱敏——这正是方向 6（Agent-Native UI）的产业实践。

8. 可访问性是内置而非补丁

IBM Carbon 的语义化表格、SAP Fiori 的三重状态编码、Microsoft Fluent 的键盘导航——所有标杆设计系统都把可访问性作为模式的内置契约，而非事后补丁。

关键启示

启示 1：没有一种标杆系统覆盖了所有模式。SAP 在 ERP 页面范式最完整，Salesforce 在 CRM 对象页和销售流程最成熟，Ant Design Pro 在中后台工程落地最轻量，Microsoft 在 AI 集成最前沿。选型时应按行业和任务借鉴对应标杆。
启示 2：模式不是"选一个用"，而是"组合使用"。真实页面通常是"核心模式+局部模式+风险/协作/恢复机制"的组合，如 Worklist + Assignment + Aging + Handoff 组合成"任务接力工作台"。
启示 3：所有标杆系统都在向 AI 演进——但都遵循"上下文感知+可解释推荐+人工确认+信任层"的共同原则。AI 不是"放一个聊天框"，而是校准用户对自动化能力的信任。
启示 4：反模式的修正往往就是下一个模式的引入——"异常只在日志"的修正就是 Exception Center；"首页堆图表"的修正就是 Dashboard+Drill-down；"权限只配置不审计"的修正就是 Audit Log。反模式识别是模式选型的第一步。
