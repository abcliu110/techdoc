# 方向 2：模式组合代数与冲突图谱

> 目标：把"模式可组合"从自然语言描述变成可计算的代数体系，回答"哪些模式能同屏共存、哪些互斥、组合后涌现什么、如何检测冲突"。
> 理论基线：[`13-界面模型深层逻辑与模式体系.md`](13-界面模型深层逻辑与模式体系.md) §10.3（Petri Net 并行汇合）、§13（反模式分类）、§14.2（派生设计原则）。
> 依赖：[`14a-模式形式化规约.md`](14a-模式形式化规约.md) 的 `composition` 层。

## 0. 为什么需要组合代数

现有文档说"一个真实页面通常是核心模式 + 局部模式 + 风险/协作/恢复机制的组合"，但没有回答四个问题：

1. **兼容性**：任意两个模式能否同屏共存？
2. **涌现性**：组合后是否产生新模式？
3. **冲突性**：组合后是否产生认知矛盾或状态机死锁？
4. **稳定性**：组合后的状态空间是否可控？

组合代数把这四个问题形式化。

## 1. 组合算子

定义五种组合算子，覆盖企业系统页面中模式之间的所有关系类型。

### 1.1 算子定义

| 算子 | 符号 | 语义 | 示例 |
|---|---|---|---|
| 叠加 | `⊕` | 模式 B 叠加在模式 A 的某个槽位上，A 的结构不变 | `ListReport ⊕ ViewManagement` = 列表 + 保存视图 |
| 嵌入 | `⊗` | 模式 B 作为模式 A 的一个槽位的内容 | `ObjectPage ⊗ Timeline` = 详情页嵌入时间线 |
| 并列 | `∥` | 模式 A 和 B 同屏分区展示 | `Dashboard ∥ Worklist` = 左侧看板 + 右侧待办 |
| 主从 | `▷` | A 是主面板，B 是从面板，A 的选择驱动 B | `ListReport ▷ ObjectPage` = Master-Detail |
| 替代 | `∨` | A 和 B 在不同状态下互斥出现 | `EmptyState ∨ ListReport` = 空态或列表 |

### 1.2 算子性质

```
叠加 ⊕：满足交换律（A ⊕ B = B ⊕ A），不满足结合律的槽位约束
         —— 叠加顺序影响槽位冲突优先级

嵌入 ⊗：不满足交换律（A ⊗ B ≠ B ⊗ A）
         —— ObjectPage ⊗ Timeline ≠ Timeline ⊗ ObjectPage

并列 ∥：满足交换律和结合律
         —— 但受屏幕空间约束，并列模式数 ≤ 3

主从 ▷：不满足交换律
         —— A ▷ B 表示 A 驱动 B，反过来语义不同

替代 ∨：满足交换律和结合律
         —— 由状态机决定当前激活哪个
```

## 2. 兼容性矩阵

### 2.1 二元兼容性

对 25 个核心模式两两计算兼容性。结果分四档：

| 档位 | 含义 | 处理方式 |
|---|---|---|
| `✓ 兼容` | 可直接组合，无额外约束 | 允许 |
| `✓ 有条件兼容` | 可组合但需满足约束条件 | 检查条件 |
| `△ 注意` | 可组合但产生认知负荷或空间压力 | 需验证 |
| `✗ 互斥` | 不可同屏组合 | 禁止 |

### 2.2 兼容性规则库

兼容性不是手工穷举，而是由以下规则推导。

#### 规则 R1：信息密度冲突

```
IF patternA.density = "high" AND patternB.density = "high"
AND operator = "∥"（并列）
THEN compatibility = "✗ 互斥"
REASON "两个高密度模式并列超出认知负荷"
```

适用：`ListReport ∥ DataGrid` → 互斥；`Dashboard ∥ Worklist` → 有条件兼容（Dashboard 低密度）。

#### 规则 R2：焦点竞争冲突

```
IF patternA.focusType = "overview" AND patternB.focusType = "detail"
AND operator = "∥"
THEN compatibility = "△ 注意"
REASON "概览和明细同屏会争夺注意力，需明确主从"
FIX "改用 ▷（主从）而非 ∥（并列）"
```

适用：`Dashboard ∥ Drill-down` → 注意；`Dashboard ▷ Drill-down` → 兼容。

#### 规则 R3：容器嵌套深度

```
IF nestingDepth(A ⊗ B ⊗ C ...) > 2
THEN compatibility = "✗ 互斥"
REASON "嵌套超过 2 层产生层级混乱（NEST-1）"
```

适用：`ObjectPage ⊗ RelatedLists ⊗ ListReport` → 互斥（3 层嵌套）。

#### 规则 R4：状态机一致性

```
IF patternA.stateMachine AND patternB.stateMachine
SHARE a state variable (e.g., "selectedObject")
AND their transitions CONFLICT on that variable
THEN compatibility = "✗ 互斥"
REASON "两个模式对同一状态变量的转移冲突，产生死锁"
```

适用：`Wizard ⊗ InlineEdit` → 互斥（Wizard 控制步骤状态，InlineEdit 控制编辑状态，冲突）。

#### 规则 R5：上下文保留一致性

```
IF patternA.requiresContextPreservation = true
AND patternB.disruptsContext = true
AND operator ∈ {"⊗", "∥"}
THEN compatibility = "✗ 互斥"
REASON "B 破坏 A 需要的上下文"
```

适用：`MasterDetail ⊗ ModalForm` → 互斥（Modal 打断主从上下文）。

#### 规则 R6：风险层级一致性

```
IF patternA.riskLevel = "high" AND patternB.riskLevel = "low"
AND operator = "∥"
THEN compatibility = "△ 注意"
REASON "低风险操作区可能被误用于高风险对象，需物理隔离"
```

#### 规则 R7：数据口径一致性

```
IF patternA.dataScope AND patternB.dataScope
ARE used in operator "∥" or "▷"
AND patternA.dataScope ≠ patternB.dataScope
THEN compatibility = "✓ 有条件兼容"
CONDITION "必须统一筛选上下文（DRILL-1）"
```

适用：`AnalyticalListPage ▷ ObjectPage` → 有条件兼容（必须共享筛选上下文）。

## 3. 涌现模式

某些组合不是简单叠加，而是涌现出具有独立语义的新模式。

### 3.1 涌现规则

```
IF combo(A, B, C, ...) produces emergentBehavior
WHERE emergentBehavior ∉ behaviors(A) ∪ behaviors(B) ∪ behaviors(C) ...
THEN record as EmergentPattern
```

### 3.2 已识别的涌现模式

| 组合 | 涌现模式 | 涌现语义 | 理论依据 |
|---|---|---|---|
| `Worklist ⊕ Assignment ⊕ Aging ⊕ Handoff` | **任务接力工作台** | 不只是待办列表，而是责任流转+老化监控+交接闭环 | §9 协作 |
| `ListReport ⊕ ViewManagement ⊕ BulkOperation ⊕ ImpactPreview` | **批量处置工作台** | 不只是列表，而是可保存策略的批量处置流水线 | §4 风险 |
| `ObjectPage ⊗ Timeline ⊗ AuditLog ⊗ RelatedLists` | **业务对象全息页** | 不只是详情，而是对象的形成过程+关联网络+变更追溯 | §1, §5 |
| `Dashboard ⊕ Drill-down ⊕ ExceptionCenter ⊕ Worklist` | **角色驾驶舱** | 不只是看板，而是感知-钻取-处置-追踪的闭环 | §2, §7, §8 |
| `ConfigPage ⊕ Simulation ⊕ VersionHistory ⊕ MakerChecker` | **规则治理工作台** | 不只是配置，而是模拟-发布-审计-双审的规则治理 | §6.4, §9.5 |
| `Reconciliation ⊕ ExceptionCenter ⊕ MakerChecker ⊕ AuditLog` | **财务对账闭环** | 不只是核对，是发现-归因-调整-审计的财务闭环 | §8, §10.4 |
| `Wizard ⊕ DraftHandling ⊕ ConflictResolution` | **可中断长流程** | 不只是向导，是可中断-可恢复-可冲突解决的长流程 | §9.4 |
| `AnalyticalListPage ▷ ObjectPage ⊗ Timeline` | **分析-追溯链** | 不只是分析，是从指标到对象到过程的完整证据链 | §7 |

涌现模式应作为独立模式记录，拥有自己的 `identity`、`slots`、`invariants`，并标注其来源组合。

```yaml
  category: "涌现模式"
  parentCombo: ["Worklist", "Assignment", "Aging", "Handoff"]
  emergentProperty: "责任流转闭环"
  theoryRef: "§9 协作"

```

## 4. 冲突检测

### 4.1 冲突类型

| 冲突类型 | 检测规则 | 示例 |
|---|---|---|
| **认知冲突** | R1 两个高密度模式并列 | `ListReport ∥ DataGrid` |
| **焦点冲突** | R2 概览与明细并列 | `Dashboard ∥ ObjectPage` |
| **嵌套冲突** | R3 嵌套深度 > 2 | `ObjectPage ⊗ RelatedLists ⊗ ListReport` |
| **状态冲突** | R4 状态机转移冲突 | `Wizard ⊗ InlineEdit` |
| **上下文冲突** | R5 上下文破坏 | `MasterDetail ⊗ ModalForm` |
| **风险冲突** | R6 风险层级不一致 | `PermissionMatrix ∥ SimpleForm` |
| **口径冲突** | R7 数据口径不一致 | `AnalyticalListPage ∥ ListReport`（不同筛选） |
| **语义重叠** | 两个模式功能重叠 | `Timeline ∥ AuditLog` |

### 4.2 冲突检测算法

```python
def detect_conflicts(patterns: list, operator: str) -> list:
    conflicts = []
    for i, a in enumerate(patterns):
        for b in patterns[i+1:]:
            # R1: 信息密度冲突
            if a.density == "high" and b.density == "high" and operator == "∥":
                conflicts.append(Conflict(a, b, "R1", "认知冲突"))
            # R2: 焦点竞争冲突
            if a.focusType == "overview" and b.focusType == "detail" and operator == "∥":
                conflicts.append(Conflict(a, b, "R2", "焦点冲突", fix="改用 ▷"))
            # R3: 容器嵌套深度
            if nesting_depth(patterns) > 2 and operator == "⊗":
                conflicts.append(Conflict(a, b, "R3", "嵌套冲突"))
            # R4: 状态机一致性
            if state_conflict(a.stateMachine, b.stateMachine):
                conflicts.append(Conflict(a, b, "R4", "状态冲突"))
            # R5: 上下文保留
            if a.requiresContext and b.disruptsContext and operator in ("⊗", "∥"):
                conflicts.append(Conflict(a, b, "R5", "上下文冲突"))
            # R6: 风险层级
            if a.riskLevel != b.riskLevel and operator == "∥":
                conflicts.append(Conflict(a, b, "R6", "风险冲突", severity="warning"))
            # R7: 数据口径
            if a.dataScope != b.dataScope and operator in ("∥", "▷"):
                conflicts.append(Conflict(a, b, "R7", "口径冲突",
                    condition="需统一筛选上下文"))
            # R8: 语义重叠
            if semantic_overlap(a, b):
                conflicts.append(Conflict(a, b, "R8", "语义重叠", severity="warning"))
    return conflicts
```

### 4.3 冲突修复建议

每个冲突类型关联修复策略：

| 冲突类型 | 修复策略 |
|---|---|
| 认知冲突 | 改 `∥` 为页面切换（Tab 或路由） |
| 焦点冲突 | 改 `∥` 为 `▷`（主从），或拆为两个页面 |
| 嵌套冲突 | 减少嵌套层级，将第 3 层改为跳转独立页 |
| 状态冲突 | 合并状态机或移除冲突模式 |
| 上下文冲突 | 改 `⊗` 为跳转，或使用非打断式容器（Side Panel） |
| 风险冲突 | 物理隔离高风险区和低风险区 |
| 口径冲突 | 引入统一筛选上下文管理器 |
| 语义重叠 | 明确分工（如 Timeline 看业务事件，AuditLog 看操作审计） |

## 5. 组合稳定性分析

### 5.1 状态空间爆炸

组合后的状态空间是各模式状态机的笛卡尔积。

```
combinedStates = |S_A| × |S_B| × ... × |S_n|
```

当组合模式数 > 4 时，状态空间可能超过 1000，导致测试不可行。

### 5.2 稳定性判据

| 组合模式数 | 状态空间 | 稳定性 | 建议 |
|---|---|---|---|
| 1-2 | < 50 | 稳定 | 可自由组合 |
| 3 | 50-200 | 基本稳定 | 需测试关键路径 |
| 4 | 200-1000 | 需验证 | 需状态空间缩减 |
| 5+ | > 1000 | 不稳定 | 拆分为多页面 |

### 5.3 状态空间缩减

对大组合采用以下缩减策略：

- **共享状态变量**：多个模式共享同一状态变量（如 `selectedObject`），减少笛卡尔积维度。
- **互斥状态组**：某些状态不可能同时出现，剪枝。
- **抽象化**：只测试关键状态组合，忽略中间态。

### 5.4 Petri Net 验证

对包含并行分支的组合（如 `Wizard ⊕ ParallelSteps`），用 Petri Net 验证：

- **无死锁**：不存在所有 Token 都无法推进的状态。
- **无孤儿任务**：不存在永远无法到达的 Place。
- **可终止性**：从任意可达状态都存在到达终态的路径。

```text
验证流程：
1. 将组合的状态机映射为 Petri Net
2. Place = 模式状态，Transition = 模式间转移
3. Fork/Join = 并行模式分叉与汇合
4. 运行可达性分析
5. 检测死锁、孤儿和不可终止路径
```

## 6. 组合模式 catalog

### 6.1 常见组合方案

按任务场景给出推荐组合方案：

#### 场景 1：客服退款处理工作台

```
Worklist ▷ ObjectPage ⊗ Timeline
  ⊕ Assignment ⊕ Aging ⊕ ImpactPreview
  ⊗ ModalForm（退款确认）
```

- 兼容性：全部 ✓ 兼容
- 涌现：任务接力工作台
- 状态空间：8 × 6 × 4 = 192（需验证关键路径）
- 风险门禁：退款走 ModalForm + ImpactPreview

#### 场景 2：财务对账工作台

```
Reconciliation
  ⊕ ExceptionCenter
  ⊕ MakerChecker
  ⊕ AuditLog
  ⊕ Drill-down（差异钻取）
```

- 兼容性：全部 ✓ 兼容
- 涌现：财务对账闭环
- 状态空间：7 × 7 × 3 = 147（基本稳定）
- 不变量：RECON-2（日结门禁）+ IDEM-1（幂等）

#### 场景 3：低代码规则配置工作台

```
ConfigPage
  ⊕ RuleBuilder
  ⊕ Simulation
  ⊕ VersionHistory
  ⊕ MakerChecker
  ⊕ ImpactPreview
```

- 兼容性：全部 ✓ 兼容
- 涌现：规则治理工作台
- 状态空间：6 × 5 × 5 × 3 = 450（需状态空间缩减）
- 不变量：CONFIG-1 + ROLLBACK-1 + SEP-1

#### 场景 4：经营分析驾驶舱

```
Dashboard
  ∥ Worklist（待办区作为槽位）
  ▷ Drill-down（指标钻取）
  ▷ ObjectPage ⊗ Timeline（追到业务对象）
  ⊕ ExceptionCenter（异常摘要）
```

- 兼容性：Dashboard ∥ Worklist 有条件兼容（Worklist 作为 Dashboard 槽位，非独立并列）
- 涌现：角色驾驶舱
- 状态空间：5 × 8 × 5 × 6 = 1200（需拆分或抽象化）
- 建议：Drill-down 和 ObjectPage 作为独立页面，通过路由跳转

## 7. 组合校验流程

```
1. 识别页面使用的所有模式
2. 确定模式间的算子（⊕ ⊗ ∥ ▷ ∨）
3. 运行冲突检测（R1-R8）
4. 若有 ✗ 互斥 → 返回错误
5. 若有 △ 注意 → 生成警告 + 修复建议
6. 计算组合状态空间
7. 若状态空间 > 1000 → 建议拆分
8. 检测涌现模式，记录为独立模式候选
9. 若含并行分支 → 运行 Petri Net 验证
10. 输出组合校验报告
```

## 8. 与方向 1 的关系

- 方向 1 的 `composition` 属性是本方向的计算输入。
- 本方向的兼容性矩阵反向写入方向 1 的 `composition.mutuallyExclusive` 和 `composition.compatible`。
- 本方向的涌现模式作为新模式候选，需走方向 7 的实证验证流程。
- 本方向的冲突检测结果作为方向 1 校验引擎的 `compositionResults` 输出。
