# 数据模型与界面模式映射大型手册

> 副标题：从业务事实、任务视图到低代码运行时与工程治理
>
> 面向产品经理、业务分析师、交互设计师、低代码平台设计人员、架构师和开发人员。

## 手册导读

### 这本手册解决什么问题

当人们谈论“数据模型生成 UI”，最容易想到的是：字符串生成输入框、枚举生成下拉框、日期生成日期选择器。这种类型映射有用，但只触及问题最浅的一层。

真正困难的问题是：

```text
为什么同一张订单会形成列表、详情、编辑、审批和报表五种界面？
为什么同一个字段在一个页面可编辑，在另一个页面只能查看？
为什么读取时可以组合和聚合，写入时却不能把结果直接改回去？
当页面配置、业务状态和权限规则冲突时，谁拥有最终决定权？
低代码平台如何把多组 Schema 变成可执行、可解释、可迁移的页面？
数据、接口、组件和规则持续演化时，如何保证旧页面仍然正确？
AI 能否根据模型动态生成 UI，它可以决定什么，又不能决定什么？
```

本手册从一个订单案例出发，逐层回答这些问题。核心不是教人堆叠更多模型和框架，而是建立一套判断方法：在什么约束下，需要哪种映射；映射产生了什么信息损失；谁维护业务真相；怎样验证结果正确；何时复杂架构是不必要的。

### 全书核心命题

> UI 不是数据的复制品，而是业务事实在任务上下文中的可交互投影；读取组织事实，写入表达意图，治理保证多种表达仍指向同一业务真相。

可以用一组逐步深化的公式表达：

```text
最简映射：数据类型 → 默认组件

场景映射：业务数据 + 页面场景 → 任务视图

完整映射：业务事实 × 任务 × 权限 × 状态 × 环境 × 时间 → 可交互UI

交互闭环：读取投影 → UI草稿 → 用户意图 → 业务校验 → 新业务事实
```

这四层不是一条必须逐级采用的技术路线。简单 CRUD 可能只需要前两层；订单、支付、审批、低代码平台等复杂场景，需要根据风险覆盖更多层次。

### 证据与适用边界

本文区分三类内容：

具体采用哪种模式属于场景化设计判断，不能脱离现有系统、业务风险和数据规模直接套用。

- **通用原理**：数据投影、权限边界、读写非对称、并发和版本等稳定工程原理。
- **设计判断**：ViewModel、BFF、CQRS、Schema 运行时等模式的选择，依赖具体约束。
- **平台观察**：低代码部分参考了本地竞品知识库中的官方资料和源码初证，但不把跨产品归纳写成任何单个产品的既成事实。

文中出现的公式用于澄清关系与边界，不意味着实现必须采用函数式语言、关系数据库、DDD、CQRS 或某种特定框架。

### 符号约定

## 第一篇　从直觉到本质：数据为什么会变成不同界面

### 开篇：同一张订单，为什么会长出五种完全不同的界面

假设数据库里有一张订单：

```text
order_id    = O202607130001
customer_id = 1001
status      = PAID
amount      = 1288.00
paid_at     = 2026-07-13 10:25:16
items       = 5条商品明细
```

如果“数据库字段决定 UI”，这张订单应该只有一种界面：把这些字段逐个摆到页面上。

但真实系统不是这样工作的。

| 使用者 | 他真正想知道什么 | 界面会变成什么 |
|---|---|---|
| 客户 | 我的订单到哪一步了 | 商品卡片、金额、物流进度、退款入口 |
| 客服 | 客户遇到了什么问题 | 客户资料、订单时间线、异常记录、补救动作 |
| 仓库 | 现在要拣什么、发什么 | SKU、数量、库位、拣货状态、发货按钮 |
| 财务 | 钱是否收到、账是否对上 | 实付金额、支付渠道、退款、对账状态 |
| 管理者 | 这批订单说明了什么 | 销售额、转化率、异常率、趋势图 |

五个界面使用的是同一批业务事实，却几乎没有相同的页面结构。

原因在于：

> 数据库模型描述“系统保存了什么事实”，UI 描述“某个人此刻要借助这些事实完成什么任务”。

所以，UI 不是数据库模型换了一层皮肤，而是数据库事实在特定任务、角色、状态和终端下的一次**有目的的投影**。

这也是全文最重要的结论：

> 同一个数据模型可以映射多个 UI，是因为数据事实相对稳定，而用户任务天然是多样的。多个 UI 的价值，是让同一批事实服务不同任务；它的代价，是系统必须治理这些不同表达之间的语义一致性。

### 1. 数据库与 UI 回答的不是同一个问题

#### 1.1 数据库模型回答“事实怎样保存”

数据库主要关心：

- 有哪些实体、字段和关系。
- 哪些数据必须持久化。
- 主键、外键和唯一约束是什么。
- 如何保证查询、事务和数据一致性。

它倾向于稳定、完整、适合机器处理。

#### 1.2 UI 回答“用户怎样完成任务”

UI 主要关心：

- 用户此刻要解决什么问题。
- 哪些信息最重要，哪些信息应该暂时隐藏。
- 数据应以文本、标签、表格、时间线还是图表表达。
- 当前允许查看、编辑或执行哪些动作。
- 操作失败后，用户如何理解和恢复。

它倾向于选择性、场景化、适合人理解。

#### 1.3 两者的根本差异

| 维度 | 数据库模型 | UI 模型 |
|---|---|---|
| 中心 | 事实与存储 | 用户与任务 |
| 主要对象 | 表、列、关系、约束 | 页面、区块、字段、组件、动作 |
| 数据范围 | 尽量保存完整事实 | 只使用当前任务需要的事实 |
| 数据粒度 | 原始记录 | 摘要、组合、明细、聚合 |
| 变化原因 | 业务事实和存储策略变化 | 角色、流程、体验和终端变化 |
| 写入表达 | 插入、更新、删除 | 保存草稿、支付、审批、发货、退款 |
| 安全方式 | 查询范围与写入约束 | 隐藏、只读、脱敏、禁用、动作入口 |

因此，“一张表生成一个固定页面”只是最简单的一种实现，并不是数据与 UI 的天然关系。

### 2. 为什么一个模型可以映射出多个 UI

#### 2.1 UI 是一个带上下文的投影函数

可以把页面理解为下面的函数：

```text
UI视图 = Project(
  业务事实，
  用户任务，
  用户角色与权限，
  当前业务状态，
  终端与交互环境，
  时间与数据新鲜度要求
)
```

同一份订单数据没有变化，只要函数的其他输入发生变化，输出的 UI 就会变化。

例如：

```text
订单 + “快速查找”       → 订单列表
订单 + “全面理解”       → 订单详情
订单 + “修改草稿”       → 编辑表单
订单 + “进行业务决策”   → 审批页面
订单集合 + “分析趋势”   → 经营报表
```

用更直观的数学形式表示，就是同一个订单模型经过不同的映射函数，形成不同的 UI：

```text
列表UI = f₁(订单数据)
详情UI = f₂(订单数据)
编辑UI = f₃(订单数据)
审批UI = f₄(订单数据, 用户权限, 订单状态)
报表UI = f₅(一组订单数据)
```

这里的 `f₁～f₅` 代表不同的选择、关联、计算、格式化、权限过滤和交互组织规则。只要映射函数不同，同一份订单数据就可以形成不同的 UI。

上面的写法是为了突出“同一数据、不同投影”的简化模型。严格来说，列表、详情和编辑页面同样会受到任务、权限、状态、展示规则和设备环境影响，因此可以进一步统一为：

```text
第 i 个UI = F(
  订单数据或订单集合,
  第 i 个页面场景,
  当前任务,
  用户权限,
  业务状态,
  展示规则,
  设备环境
)
```

两种表达的作用不同：

- `f₁～f₅` 强调一个数据模型可以产生多个不同的任务视图，直观易懂。
- `F(数据, 上下文)` 强调这些视图背后共享一套统一的映射机制，更完整严谨。

这与一组原始数据可以生成明细表、统计表和图表是同一个原理：**数据源没有限定唯一表达方式，使用目的才决定表达方式。**

#### 2.2 映射保持的是业务含义，不是字段形状

数据库中保存：

```text
customer_id = 1001
```

不同 UI 可以表达为：

```text
列表：星海商贸
详情：星海商贸 / VIP客户 / 上海
编辑：客户选择器，实际提交 customer_id
审批：客户等级、信用额度和风险记录
报表：华东区客户群体
```

它们的结构不同，但都能追溯到同一个“订单所属客户”业务概念。

因此，映射的核心不是：

```text
varchar → Input
```

而是：

```text
这个值代表什么业务概念？
当前任务需要如何理解它？
用户可以对它做什么？
```

一个 `varchar` 可以是姓名、手机号、状态码、URL、颜色、身份证号或物流单号。物理类型相同，业务语义不同，UI、校验、脱敏和操作方式就完全不同。

#### 2.3 一个对象天然存在多种观察尺度

同一对象可以从不同粒度观察：

```text
一条订单记录       → 详情或编辑表单
多条订单摘要       → 列表
订单与关联对象组合 → 客服工作台
订单状态变化       → 时间线或流程图
大量订单聚合       → 报表和经营大屏
```

所以“同一个模型对应多个 UI”不但合理，而且是复杂系统从“数据管理”走向“任务支持”时常见的演进结果。

### 3. 不要把四种模型混成一个模型

在小型 CRUD 系统中，一个对象可能同时被用于数据库、接口和页面，看起来很省事。但业务复杂之后，四个问题会逐渐分开。

| 模型 | 它回答的问题 | 订单示例 |
|---|---|---|
| 持久化模型 | 数据怎样存 | 订单表、明细表、客户外键 |
| 领域模型或业务逻辑 | 什么变化是合法的 | 待支付订单才能支付，已发货订单不能直接删除 |
| 读取模型 / ViewModel | 页面要怎样看 | 客户名称、商品数、格式化金额、可用动作 |
| 写入模型 / Command | 用户想做什么 | 创建订单、支付订单、取消订单、批准退款 |

这四种模型不是所有项目都必须建立的四层框架，也不是一条不可改变的顺序流水线。它们首先是四个不同的设计问题。

简单数据维护可以采用：

```text
数据库实体 → DTO → 表单
```

复杂业务则更适合：

```text
读取：数据源 → 页面专用投影 → UI
写入：用户意图 → 业务命令 → 规则校验 → 数据变化
```

是否拆分，取决于页面与存储结构的差异、业务风险和维护成本，而不是为了套用某个架构名词。

### 4. 同一个数据模型映射到不同 UI，到底“不同”在哪里

差异不只是组件不同，至少包含以下八个维度。

#### 4.1 数据选择不同：看哪些事实

订单列表只需要订单号、客户、金额、状态和时间；订单详情还要商品、支付、物流和操作记录；审批页面可能只强调金额、风险和历史决策。

这叫**选择投影**：从完整对象中选择当前任务需要的数据。

#### 4.2 信息粒度不同：看原始值还是摘要

```text
商品明细 → 5件商品
多次支付 → 已支付 ¥1,288.00
多个状态事件 → 当前“待发货”
一批订单 → 今日销售额 ¥368,420
```

列表偏摘要，详情偏展开，报表偏聚合。

#### 4.3 语义表达不同：机器值怎样变成人能理解的含义

```text
customer_id = 1001 → 星海商贸
status = PAID      → 已支付
amount = 128800    → ¥1,288.00
```

这里发生了引用查找、字典解释、单位换算和格式化。

#### 4.4 视觉形态不同：同一语义怎样表达

同一个 `status` 可以是：

| 场景 | 表达形式 |
|---|---|
| 列表 | 彩色 Badge |
| 查询区 | 多选下拉框 |
| 详情页 | 状态说明和步骤条 |
| 工作台 | 按状态划分的任务泳道 |
| 报表 | 状态分布图 |

数据没有改变，改变的是用户理解它的方式。

#### 4.5 可编辑性不同：看得到不等于改得了

订单金额可以在创建草稿时由商品明细计算；在详情页只读；在审批页作为判断依据；在报表中作为聚合指标。

同一个字段是否可编辑，通常由以下条件共同决定：

```text
业务状态 + 用户权限 + 字段来源 + 当前任务
```

#### 4.6 动作集合不同：页面允许用户做什么

```text
待支付 → 支付、取消
已支付 → 发货、申请退款
已发货 → 确认收货、查看物流
已完成 → 售后、评价
```

动作不是字段的装饰，而是业务状态和用户权限在 UI 上的投影。

#### 4.7 权限与敏感度不同：同一事实能显示到什么程度

```text
财务：13812341234
客服：138****1234
仓库：可能完全不返回手机号
```

这里不只是 UI 样式不同，接口返回的数据范围本身也应不同。不能先把完整敏感信息发送到浏览器，再依赖前端隐藏。

#### 4.8 时间语义不同：看到的是实时值、快照还是聚合结果

订单详情通常希望接近实时；经营报表可能按小时刷新；审批页面可能必须保留“提交审批时的快照”；大屏可能接受几分钟延迟。

因此，不同 UI 还会选择不同的数据新鲜度、一致性和缓存策略。

#### 4.9 用订单把这些差异放在一起

| 维度 | 列表 | 详情 | 编辑 | 审批 | 报表 |
|---|---|---|---|---|---|
| 核心任务 | 找 | 看懂 | 修改 | 决策 | 分析 |
| 数据范围 | 少量摘要 | 完整关联信息 | 可修改部分 | 决策证据 | 聚合指标 |
| 粒度 | 一行一个订单 | 一个订单完整展开 | 表单和子表 | 关键事实加历史 | 一批订单 |
| `customerId` | 客户名称 | 客户摘要卡片 | 客户选择器 | 客户风险信息 | 客户分类维度 |
| `status` | Badge | 步骤条 | 通常只读 | 决定可用动作 | 状态分布 |
| `amount` | 格式化金额 | 金额构成 | 输入或自动计算 | 风险阈值提示 | SUM、AVG |
| 允许动作 | 查看 | 按状态执行动作 | 保存草稿 | 通过或驳回 | 筛选、下钻、导出 |
| 时间要求 | 较新 | 接近实时 | 必须防并发覆盖 | 可能需要决策快照 | 可接受统计延迟 |

这张表揭示了一个关键事实：

> 不同 UI 的差异，本质上是“同一对象在不同任务中的解释契约不同”，而不是简单换了几种组件。

## 第二篇　映射操作与读写机制：数据如何成为交互

### 5. 映射不是只有“字段到控件”

#### 5.1 常见映射操作

| 映射操作 | 示例 | 特点 |
|---|---|---|
| 直接映射 | `remark → TextArea` | 结构基本不变 |
| 格式转换 | `128800分 → ¥1,288.00` | 改变表达，不改变含义 |
| 引用查找 | `customerId → 客户名称` | 显示值与稳定标识分离 |
| 选择投影 | 完整订单 → 列表摘要 | 丢弃当前任务不需要的数据 |
| 组合 | 省、市、地址 → 完整地址 | 多个值组合成一个展示值 |
| 拆分 | 日期区间 → 开始时间、结束时间 | 一个输入形成多个值 |
| 派生 | 出生日期 → 年龄 | 由原始事实计算，不应独立写回 |
| 聚合 | 明细金额 → 订单总额 | 多条数据归约成一个结果 |
| 条件映射 | 状态为草稿时允许编辑 | 依赖上下文，不只是字段值 |
| 动作映射 | “支付”按钮 → `PayOrder` | 映射的是意图，不是字段 |

#### 5.2 数据类型只能提供默认值，不能决定最终 UI

低代码或代码生成工具通常会建立默认规则：

```text
string   → Input
boolean  → Switch
date     → DatePicker
enum     → Select
```

这只能解决“没有更多信息时用什么组件”的问题。

更可靠的解析顺序是：

```text
页面显式配置
  > 当前场景与业务语义的映射
  > 逻辑数据类型默认值
  > 物理数据类型默认值
  > 通用兜底组件
```

例如金额字段：

```text
decimal + money + list   → MoneyCell
decimal + money + edit   → MoneyInput
decimal + money + report → Statistic / ChartMeasure
```

真正决定 UI 的不是 `decimal`，而是 `money + 当前场景`。

### 6. 读取映射与写入映射不是互为镜像

这是数据模型与 UI 设计中最容易被忽略、也最容易制造缺陷的地方。

#### 6.1 读取可以有损，写回不能靠猜

读取时可以把多个值组合起来：

```text
province + city + detailAddress → 上海市浦东新区……
```

但用户修改“完整地址”后，系统未必能可靠拆回省、市和详细地址。

读取时也可以聚合：

```text
订单明细 → 总金额
```

但修改总金额，不能反推出每条明细应怎样改变。

因此：

> 读取模型可以是有损投影；任何可编辑 UI 都必须单独定义写入结构和写回规则。

#### 6.2 用户提交的最好是“意图”，不一定是完整对象

简单数据维护可以直接提交字段变化：

```text
PATCH /customer/1001
{ "remark": "重点客户" }
```

如果字段修改本身就是完整业务语义，这种方式最简单，也完全合理。

但支付、审批、库存、退款等操作不只是改一个字段，它们通常还伴随权限、前置条件、副作用、审计和并发控制。这时更适合提交业务命令：

```json
{
  "command": "PayOrder",
  "orderId": "O202607130001",
  "paymentMethod": "WECHAT_PAY",
  "requestId": "unique-request-id"
}
```

而不是：

```json
{
  "status": "PAID"
}
```

两者的区别是：

```text
字段更新：告诉系统“结果改成什么”
业务命令：告诉系统“用户想完成什么”
```

服务端再根据当前状态、权限、金额、幂等和并发条件决定这个意图能否成立。

#### 6.3 写回链路

```text
界面草稿
  ↓ 基础输入校验
用户意图 / Command
  ↓ 身份、数据范围、业务状态与并发校验
合法业务变化
  ↓ 事务和持久化
新的业务事实
  ↓ 重新投影
更新后的 UI
```

UI 校验用于及时反馈；服务端校验用于保证正确性。二者可以复用规则定义，但不能只保留前者。

## 第三篇　架构模式与落地方法：如何选择而不是套用

### 7. 常见模式：它们不是一条升级路线，而是在解决不同问题

“直接映射、ViewModel、Schema、BFF、CQRS、状态机”经常被放在一张列表里比较，但它们并不是同一维度的互斥选项。

它们分别回答不同的问题：

| 设计问题 | 常见选择 |
|---|---|
| UI 结构由谁定义 | 手写页面、注解约定、UI Schema |
| 页面读取什么数据形状 | 实体 DTO、页面 ViewModel、专用查询投影 |
| 多个数据源在哪里组合 | 前端、页面 API/BFF、后端查询服务 |
| 用户怎样写入 | 通用 CRUD、表单命令、状态/流程命令 |
| 查询与写入是否使用同一模型 | 共享模型、分离 ReadModel、CQRS 投影 |

实际系统通常是这些选择的组合，而不是只能选择一个架构标签。

#### 7.1 直接 CRUD 映射

```text
实体/DTO → 表格和表单 → 字段更新
```

**优点**：路径短、开发快、模型少、容易理解。

**缺点**：页面容易被存储结构绑住；跨对象任务、复杂权限和状态动作表达较弱。

**适合**：低风险内部数据维护、字典配置、简单主数据管理。

**不适合**：把支付、退款、库存、审批等高风险行为简化成任意字段修改。

#### 7.2 注解或约定驱动

```text
字段类型 + 业务注解 + 命名约定 → 默认组件、标签和校验
```

**优点**：比完全手写高效，可以生成标准化页面。

**缺点**：复杂场景会积累大量例外；同一字段在多个页面中的差异不容易表达。

**适合**：脚手架、标准中后台和默认页面生成。

#### 7.3 页面专用 ViewModel / ReadModel

```text
Order
├── OrderListItemViewModel
├── OrderDetailViewModel
├── OrderEditViewModel
└── OrderApprovalViewModel
```

**优点**：数据形状与用户任务高度匹配，页面契约清晰，可以组合关联数据和派生信息。

**缺点**：模型和映射代码增加；如果公共业务语义没有集中维护，容易重复和漂移。

**适合**：复杂业务页面、核心用户流程、多对象组合页面。

#### 7.4 Schema / 元数据驱动 UI

```text
字段语义 + View Schema + 组件注册表 + 上下文规则 → 页面
```

**优点**：页面可配置、可生成、可规模化复用，特别适合动态表单和低代码平台。

**缺点**：配置本身会演变成一门语言；调试链路变长；复杂交互可能迫使 Schema 不断膨胀。

**适合**：页面重复度高、租户差异明显、需要业务人员配置的场景。

**边界**：标准能力配置化，独特交互和高风险业务保留代码扩展点，不追求“任何东西都能配置”。

#### 7.5 BFF / 页面 API

```text
页面需求 → 页面API/BFF → 组合多个服务或数据源 → 页面模型
```

**优点**：前端取数简单，可以针对 Web、移动端等终端优化数据形状。

**缺点**：接口数量和组合逻辑增加；跨服务调用可能带来延迟和数据时间点不一致。

**适合**：多终端、跨服务聚合、页面需要多个后端能力的系统。

**边界**：BFF 负责页面适配，不应偷偷成为核心业务规则的唯一所在地。

#### 7.6 专用查询投影 / CQRS

```text
业务写入 → 同步或事件传播 → 面向查询的投影 → 列表、搜索、报表
```

**优点**：读取结构可以完全按查询和展示优化，适合搜索、聚合和高读取负载。

**缺点**：需要处理投影更新、失败恢复、数据延迟和一致性问题。

**适合**：读写结构差异显著，且查询规模、性能或聚合复杂度已经提供足够证据的系统。

**边界**：普通 CRUD 不应为了架构形式而默认引入 CQRS。

#### 7.7 任务 / 状态驱动 UI

```text
业务状态 + 用户角色 + 当前任务 → 信息、动作和流程反馈
```

**优点**：页面直接服务业务过程，合法动作和状态关系清晰。

**缺点**：状态、动作和权限如果分散在多端，会迅速失去一致性；过度细化的状态机也会增加维护成本。

**适合**：订单、工单、审批、售后等有明确状态转换的领域。

**边界**：需要集中维护合法转换，但不等于所有简单流程都必须引入状态机框架。

### 8. 同一模型映射多个 UI 的优点与代价

#### 8.1 它带来的价值

##### 价值一：页面真正服务用户任务

用户不需要理解表结构、外键和内部状态码，只需要完成“找到订单”“判断风险”“发出商品”等任务。

##### 价值二：降低认知负担

```text
列表负责找
详情负责看懂
表单负责录入和修改
审批页负责决策
报表负责发现规律
```

一个万能页面同时承担这些职责，通常意味着每个职责都做得不好。

##### 价值三：让同一批数据服务多个角色和终端

不必为客服、财务、仓库和管理层复制多套业务数据，只需提供不同视图和操作边界。

##### 价值四：存储结构和产品体验可以相对独立演进

数据库可以为了一致性和查询进行设计；UI 可以为了理解和操作重新分组、组合和布局。

##### 价值五：可以为不同查询目标做性能优化

列表只取摘要，详情按需加载关联数据，报表使用聚合投影，各自不必搬运完整实体。

#### 8.2 它引入的成本

##### 成本一：视图模型会增加

```text
OrderListView
OrderDetailView
OrderEditView
OrderApprovalView
OrderReportView
```

更多模型不一定是坏事；真正的问题是它们有没有清晰边界、命名和测试。

##### 成本二：同一业务概念可能产生语义漂移

如果列表叫“已完成”、详情叫“已签收”、报表又统计为“已关闭”，用户看到的是三个互相冲突的系统。

##### 成本三：查询和组合链路更复杂

页面可能需要关联多个表或调用多个服务，带来 N+1 查询、瀑布调用、缓存和数据新鲜度问题。

##### 成本四：写回不再天然简单

组合值、派生值和聚合值通常不可逆，需要单独设计编辑模型和 Command。

##### 成本五：权限与测试矩阵变大

```text
页面 × 角色 × 业务状态 × 动作 × 终端
```

组合数量增加后，必须用集中规则和自动化测试控制，而不能依靠人工记忆。

#### 8.3 核心张力

这套设计最大的张力是：

```text
页面表达自由度
        ↕
业务语义一致性与治理成本
```

如果所有 UI 都直接复制数据库，治理简单但体验僵硬；如果每个 UI 都自由解释数据，体验灵活但系统容易语义分裂。

正确方向不是选择一个极端，而是：

> 共享稳定的业务语义、状态、权限和指标口径；允许每个页面独立选择数据、布局、组件、信息密度和交互方式。

每增加一个 UI，本质上都增加了一个新的“任务解释契约”。它需要被定义、测试和演进，而不是只多画一个页面。

### 9. 低代码平台应该怎样做这种映射

低代码平台的核心难题并不是“根据字段类型生成输入框”，而是：

> 如何既提供可预测的默认映射，又允许同一业务语义在不同任务场景中有不同表达，同时不让配置失去控制。

#### 9.1 建议区分五类元数据

| 元数据 | 回答的问题 | 示例 |
|---|---|---|
| Data Schema | 数据是什么、怎样存 | decimal、是否为空、关联对象 |
| Semantic Schema | 它在业务上代表什么 | money、phone、orderStatus |
| View Schema | 当前页面怎样表达 | 列表列、详情卡片、编辑组件 |
| Action Schema | 用户可以做什么 | 支付、审批、发货、退款 |
| Permission Schema | 谁能看、改、执行 | 记录范围、字段权限、动作权限 |

它们不是五个必须顺序经过的技术层，而是运行时共同决定 UI 的五组信息。

#### 9.2 组件解析公式

```text
Component = Resolve(
  字段业务语义，
  页面类型，
  查看或编辑模式，
  业务状态，
  用户权限，
  终端环境，
  页面显式覆盖
)
```

推荐的覆盖优先级：

```text
页面显式配置
  > 场景级映射规则
  > 业务语义默认组件
  > 逻辑类型默认组件
  > 物理类型默认组件
  > 通用兜底组件
```

#### 9.3 金额字段示例

```json
{
  "field": "amount",
  "dataType": "decimal",
  "semanticType": "money",
  "currency": "CNY",
  "scale": 2,
  "views": {
    "list":   { "component": "MoneyCell" },
    "detail": { "component": "MoneyDisplay" },
    "edit":   { "component": "MoneyInput" },
    "report": { "component": "Metric", "aggregations": ["SUM", "AVG"] }
  }
}
```

这份定义不是说一个字段拥有四个固定组件，而是提供四种场景默认值；具体页面仍可以在受控范围内覆盖。

#### 9.4 什么适合配置，什么应留在代码或服务端

适合配置化：

- 字段选择、排序、分组和布局。
- 标签、帮助文本和标准格式。
- 标准组件选择。
- 简单显隐、只读和基础校验。
- 常规筛选、排序和聚合。

更适合代码或受控扩展点：

- 复杂跨对象业务规则。
- 金额、库存、支付等高风险变化。
- 复杂异步流程和失败恢复。
- 高度定制的交互体验。
- 需要事务、幂等和并发控制的动作。

低代码平台成熟的标志不是“所有东西都能配置”，而是知道：

```text
哪些变化高度重复，值得配置化；
哪些变化具有业务风险，必须保留受控边界。
```

### 10. 如何设计一个新的数据模型到 UI 映射

#### 第一步：先写任务，不要先画字段

先回答：

```text
谁在使用？
他为什么进入这个页面？
离开页面时，什么结果代表任务完成？
```

如果答不清这三问，页面通常只能退化成数据库字段陈列。

#### 第二步：列出业务事实与不变量

明确：

- 核心对象和关系。
- 状态与合法转换。
- 金额、数量、权限等不能被破坏的规则。
- 哪些值是原始事实，哪些值是计算结果。

#### 第三步：定义页面的“问题—答案契约”

每个页面都应该回答一个核心问题：

```text
列表：我要找的对象在哪里？
详情：这个对象到底发生了什么？
编辑：哪些内容现在可以合法修改？
审批：我依据什么作出决定？
报表：一组对象呈现出什么规律？
```

然后再决定所需数据和组件。

#### 第四步：建立映射矩阵

| UI 元素 | 业务含义 | 数据来源 | 转换规则 | 显示条件 | 编辑条件 | 写入目标 |
|---|---|---|---|---|---|---|
| 客户选择器 | 订单所属客户 | Customer | ID 与名称查找 | 始终显示 | 仅草稿 | `customerId` |
| 订单金额 | 应付总额 | Items | 明细求和 | 始终显示 | 通常只读 | 服务端重算 |
| 支付按钮 | 支付订单 | Order | 状态与权限判断 | 待支付且有权限 | 不适用 | `PayOrder` |

这张表把产品语义、数据来源和工程实现放进同一个可检查的契约中。

#### 第五步：分别设计读取与写入

读取侧回答：

- 页面需要什么数据形状。
- 由谁关联、计算和格式化。
- 数据允许多旧。
- 空值和异常怎样表达。

写入侧回答：

- 用户提交字段变化还是业务命令。
- 谁负责最终校验和计算。
- 怎样防止重复提交和并发覆盖。
- 失败后用户怎样恢复。

#### 第六步：明确共享与独立的边界

应该共享：

- 业务概念和稳定标识。
- 枚举 code 与状态语义。
- 金额、指标和派生值的计算口径。
- 服务端权限与合法状态转换。
- 基础组件和格式化能力。

允许页面独立：

- 展示哪些字段。
- 信息顺序和分组。
- 使用何种组件。
- 信息密度和交互方式。
- 页面级草稿、加载和错误状态。

### 11. 选型判据

| 场景 | 优先考虑 | 原因 |
|---|---|---|
| 简单、稳定、内部 CRUD | 实体 DTO + 标准表单 | 最低成本已经足够 |
| 页面围绕复杂业务任务 | 页面 ViewModel / ReadModel | 数据形状与任务匹配 |
| 大量标准页面需动态配置 | Schema + 组件注册表 | 复用默认映射和配置能力 |
| 多终端或多服务组合 | 页面 API / BFF | 统一页面取数与终端适配 |
| 报表、搜索、复杂聚合 | 专用查询模型 | 按读取目标优化结构 |
| 读写差异和规模已显著 | CQRS 投影 | 用同步复杂度换查询自由度 |
| 动作强依赖角色与状态 | 任务/状态驱动 UI + Command | 集中控制合法动作 |

一个可靠的原则是：

> 从满足当前约束的最小模式开始，只有当页面差异、配置规模、查询性能或业务风险提供了证据时，才增加新的模型和层次。

不要因为系统里有表单就建立通用低代码引擎，也不要因为有报表就默认引入 CQRS。

---

### 12. 必须守住的十条底线

1. **数据库字段不是 UI 语义的全部来源。**物理类型只能提供默认映射。
2. **同一业务概念必须保持同一口径。**列表、详情和报表不能各算各的。
3. **稳定标识与显示值必须分离。**显示名称可以变化，关联不能依赖名称。
4. **读取可以有损，写回必须明确。**组合和聚合结果不能靠猜测反向修改。
5. **UI 隐藏不是安全边界。**记录、字段和动作权限必须由服务端保证。
6. **高风险状态变化不能退化为任意字段修改。**支付、库存、退款等操作要经过业务规则。
7. **派生值必须明确唯一计算来源。**避免前端、后端和报表各有一套算法。
8. **不同 UI 必须明确时间语义。**实时、快照、缓存和统计延迟不能混为一谈。
9. **并发和重复提交必须有处理策略。**尤其是编辑、支付、审批和库存操作。
10. **不要追求万能模型或万能 Schema。**复用稳定语义，允许任务视图保持差异。

### 13. 产品、低代码与研发如何形成共同语言

#### 产品和业务人员负责说明

- 谁在什么场景下完成什么任务。
- 页面必须回答什么问题。
- 信息优先级和业务口径是什么。
- 什么状态下允许什么动作。
- 空数据、异常和失败时用户应该怎样继续。

#### 低代码或平台设计人员负责说明

- 哪些能力可以形成元数据和默认映射。
- 组件注册、覆盖优先级和扩展点怎样工作。
- 配置怎样版本化、测试和迁移。
- 哪些复杂度不能继续塞进 Schema。

#### 架构和开发人员负责说明

- 数据来自哪里，由谁关联、计算和聚合。
- 页面使用实体 DTO、ViewModel 还是专用投影。
- 用户操作提交字段变化还是 Command。
- 权限、状态、并发、一致性和性能怎样保证。
- 映射规则和接口怎样被测试、监控和演进。

三方必须共同确认的是：

```text
这个页面在解释哪个业务事实？
它为什么这样解释？
它允许用户做什么？
最终由谁保证解释和操作是正确的？
```

---

### 14. 基础篇小结

数据模型与 UI 的映射，不是：

```text
字段 → 控件
```

而是：

```text
业务事实
  × 用户任务
  × 角色与权限
  × 业务状态
  × 终端与时间要求
  → 任务视图
```

数据库模型回答“这个世界有哪些事实”；UI 回答“此刻是谁，要借助哪些事实，完成什么事情”。

同一个数据库模型之所以可以映射到不同 UI，是因为页面不是数据的复制品，而是数据面向任务的一次解释。它的优势是让体验、角色和终端得到精准适配；它的代价是每一种解释都需要维护语义、权限、写回、一致性和测试。

一句话压缩：

> 共享事实与语义，分离任务与表达；读取用投影，写入传真正意图，最终由服务端守住业务不变量。

## 第四篇　形式化模型：把“映射”说清楚

前面的订单案例建立了直觉：同一批事实可以形成多个任务视图。但如果要设计低代码平台、Schema 引擎或大型业务系统，只靠“根据场景生成页面”还不够。还需要回答：映射的输入到底有哪些，输出是什么，规则怎样组合，哪些转换可以写回，发生冲突时谁优先，以及如何证明多个 UI 仍在解释同一个业务事实。

形式化的目的不是制造数学感，而是消除模糊边界。

### 15. 映射函数的完整输入与输出

#### 15.1 从 `fᵢ(D)` 到 `M(D, C)`

前文的简化公式是：

```text
列表UI = f₁(订单数据)
详情UI = f₂(订单数据)
编辑UI = f₃(订单数据)
审批UI = f₄(订单数据, 用户权限, 订单状态)
报表UI = f₅(一组订单数据)
```

这组公式擅长解释“同一数据可以产生不同 UI”。进一步抽象，可以把所有 `fᵢ` 看成同一个映射机制在不同上下文中的实例：

```text
M : D × C → U
```

其中：

```text
D = 可用的业务事实和数据集合
C = 当前上下文
U = 生成的可交互界面
```

上下文 `C` 可以继续展开：

```text
C = (T, R, P, S, E, L, Q, τ)

T = Task，当前任务
R = Role，用户角色与职责
P = Permission，记录、字段和动作权限
S = State，业务对象状态
E = Environment，设备、终端和交互环境
L = Locale，语言、地区、币种和单位
Q = Quality，性能、实时性和数据质量要求
τ = Time，当前时刻、业务时间或快照时间
```

因此，更完整的表达是：

```text
U = M(D, T, R, P, S, E, L, Q, τ)
```

这里有一个重要结论：页面差异不一定来自数据差异。即使 `D` 完全相同，只要任务、权限、状态、终端或时间语义不同，UI 就可以不同。

#### 15.2 UI 输出也不是一棵静态组件树

如果把 `U` 只理解成“组件树”，就会遗漏动作、导航和运行时状态。更完整的 UI 输出可以表示为：

```text
U = (V, I, A, N, Σ, X)

V = View，展示结构和组件树
I = Interaction，输入、选择、拖拽等交互规则
A = Action，当前允许发出的业务动作
N = Navigation，可到达的页面、对象和返回路径
Σ = UI State，加载、草稿、错误、选中、展开等界面状态
X = Explanation，为什么显示、隐藏、只读或禁用的解释信息
```

这能解释为什么两个页面即使显示相同字段，也可能不是同一个 UI：它们允许的动作、导航路径、局部状态和解释责任可能完全不同。

### 16. 一个 UI 映射函数内部做了什么

一个典型映射可以分解为若干操作：

```text
U = Render ∘ Layout ∘ Interact ∘ Bind ∘ Policy ∘ Interpret ∘ Query (D, C)
```

从右向左理解：

```text
Query      从数据源选择、关联、聚合所需事实
Interpret  把物理值解释成业务语义
Policy     应用记录、字段、动作和状态规则
Bind       将业务语义绑定到展示值、输入值和动作
Interact   定义编辑、选择、提交和反馈方式
Layout     按任务组织信息层级和空间结构
Render     在具体终端上渲染组件
```

这不是要求所有系统都实现七层框架，而是一张责任检查图。实际项目可以合并其中若干步骤，但不能因为代码放在一起，就认为这些责任不存在。

#### 16.1 为什么顺序很重要

如果在权限过滤之前就把完整手机号发送给前端，再由组件显示为 `138****1234`，展示结果看似正确，但数据已经越过安全边界。

如果在业务语义解释之前只根据数据库类型选组件，`varchar` 就无法区分手机号、状态码和物流单号。

如果在数据聚合之后仍允许直接写回聚合值，系统就无法知道应该修改哪些原始记录。

因此，映射不是任意拼装。某些约束必须在数据越过边界之前执行，某些派生值必须标为只读，某些动作必须回到服务端重新判定。

### 17. 用关系代数理解读取映射

很多 UI 读取映射都可以用几类基础操作解释。这里借用关系代数符号，不要求实现必须使用关系数据库。

#### 17.1 选择：`σ`

从一组记录中选择满足条件的部分：

```text
待发货订单 = σ(status = PAID ∧ shipment = PENDING)(Orders)
```

对应 UI：保存视图、任务列表、筛选结果、异常队列。

#### 17.2 投影：`π`

只取当前任务所需字段：

```text
订单列表行 = π(orderId, customerId, amount, status, createdAt)(Order)
```

对应 UI：列表摘要、搜索结果、选择器选项。

#### 17.3 连接：`⋈`

组合来自不同对象或来源的事实：

```text
订单详情 = Order ⋈ Customer ⋈ Payment ⋈ Shipment
```

对应 UI：详情页、客服工作台、审批上下文。

#### 17.4 分组与聚合：`γ`

把多条事实归约为统计结果：

```text
门店日销售额 = γ(storeId, businessDate; SUM(paidAmount))(Orders)
```

对应 UI：报表、指标卡、趋势图。

#### 17.5 排序、分页与窗口

```text
最近异常订单 = TopN(按异常时间倒序, 20)
```

对应 UI：工作台、无限列表、排行榜。

这些操作揭示了为什么报表 UI 不能被理解成“订单实体换了一种组件”：它面对的已经不是一条订单，而是由选择、连接和聚合产生的新读取模型。

### 18. 映射的基数：一对一不是唯一关系

#### 18.1 一对一：一个值对应一个 UI 值

```text
remark ↔ TextArea
```

如果没有额外格式化和业务限制，这类映射最接近直接绑定。

#### 18.2 多对一：多个事实形成一个 UI 值

```text
province + city + detailAddress → 完整地址
items[] → 商品数量
payments[] → 已支付总额
```

多对一映射通常会丢失信息，不能假设可以直接反向写回。

#### 18.3 一对多：一个事实形成多个 UI 表达

```text
orderStatus → Badge + 步骤条当前位置 + 动作可用性 + 帮助文案
```

这说明一个字段不必只绑定一个组件。一个业务事实可以同时影响视觉、交互和动作。

#### 18.4 多对多：多个对象共同决定一组界面元素

```text
订单 + 客户信用 + 用户权限 + 风险规则
  → 风险提示 + 审批字段 + 可用动作 + 审批说明
```

复杂审批页、工作台和跨域页面通常属于这一类。

### 19. 映射的可逆性与信息损失

#### 19.1 什么叫可逆

设读取函数为 `get`，把业务数据映射到 UI；写入函数为 `put`，把用户修改解释回业务输入。

理想的可逆关系至少希望满足：

```text
put(D, get(D)) = D
```

意思是：用户不修改界面，把读取到的值原样提交，不应意外改变业务数据。

还希望满足：

```text
get(put(D, U新)) = U新
```

意思是：合法保存用户输入后，再读取应看到相同的有效结果。

这类思想在双向变换中常被称为 `Lens`。它不是要求项目引入某个 Lens 框架，而是提供两个有用的正确性判据。

#### 19.2 哪些映射通常可逆

```text
字符串字段 ↔ 文本输入
稳定ID ↔ 选择器的选中值
开始/结束时间 ↔ 日期区间控件
整数分值 ↔ 受控小数金额输入
```

即使形式上可逆，仍要处理精度、时区、单位和空值语义。

#### 19.3 哪些映射天然有损

```text
多条明细 → 总金额
出生日期 → 年龄
状态历史 → 当前状态
完整手机号 → 脱敏手机号
多个地址字段 → 一段不可结构化文本
```

有损值可以展示，但通常应该只读，或者提供独立、结构化的编辑入口。

#### 19.4 信息损失要显式标注

建议为派生字段记录：

| 属性 | 需要回答的问题 |
|---|---|
| 来源 | 它由哪些事实产生 |
| 算法 | 计算规则和版本是什么 |
| 新鲜度 | 实时、缓存还是快照 |
| 可逆性 | 是否允许从该值写回 |
| 权威方 | 谁拥有最终计算权 |
| 失败语义 | 无法计算时显示什么 |

“页面显示得出来”不代表“这个值已经被正确建模”。

### 20. 一个 UI 也可以组合多个模型

前文主要讨论“一种数据模型生成多个 UI”，反方向同样重要：一个 UI 经常由多个模型共同构成。

```text
客服订单工作台 = h(
  订单,
  客户,
  支付,
  物流,
  售后工单,
  当前用户任务
)
```

这类组合带来四个设计问题：

1. **组合边界在哪里**：由前端、页面 API、BFF、查询服务还是数据库视图完成。
2. **失败是否独立**：物流服务失败时，订单主体是否仍然可用。
3. **时间点是否一致**：订单、支付和物流是否代表同一业务时刻。
4. **动作归谁处理**：页面可以组合读取，但写入命令仍要交给拥有业务规则的服务。

可以把组合 UI 表示为：

```text
U = Compose(U订单, U客户, U支付, U物流, U任务)
```

但 `Compose` 不是简单把卡片拼在一起。它还需要统一对象身份、错误策略、加载策略、权限和信息优先级。

### 21. 规则如何组合，冲突时谁优先

低代码和动态 UI 中，组件配置往往来自多个来源：

```text
平台默认值
数据类型规则
业务语义规则
页面场景规则
角色或租户规则
页面实例配置
运行时状态规则
```

如果只说“后配置覆盖前配置”，很快就会遇到安全和可解释性问题。

#### 21.1 展示类规则可以按特异性覆盖

一个可用的默认顺序是：

```text
页面实例
  > 页面场景
  > 业务语义
  > 逻辑类型
  > 物理类型
  > 平台兜底
```

越具体的规则越优先。例如订单编辑页对金额的显式配置，可以覆盖通用 `money` 的默认布局。

#### 21.2 安全规则不能被普通展示配置覆盖

权限和安全通常采用收紧原则：

```text
最终可见 = 页面希望显示 ∩ 用户允许读取
最终可编辑 = 页面希望编辑 ∩ 用户允许修改 ∩ 状态允许修改
最终可执行 = 页面声明动作 ∩ 动作权限 ∩ 当前状态合法动作
```

可以理解为“允许条件取交集，拒绝优先”。租户配置不能用 `visible: true` 绕过服务端字段权限。

#### 21.3 冲突结果必须可解释

运行时最好能回答：

```text
为什么这个字段使用 MoneyInput？
为什么这个字段只读？
为什么“退款”按钮没有出现？
哪条规则覆盖了哪条默认值？
```

否则平台配置越灵活，排查成本越高。

### 22. 依赖图：一个字段变化会影响什么

动态表单经常存在依赖：

```text
商品数量 × 单价 → 明细金额
明细金额之和 → 订单总额
订单总额 + 客户等级 → 审批路径
订单状态 + 用户权限 → 可用动作
```

可以表示为有向图：

```text
G = (V, E)

V = 字段、派生值、规则、组件、动作
E = “变化会影响”的依赖关系
```

依赖图用于决定：

- 哪些值需要重新计算。
- 哪些校验需要重新执行。
- 哪些组件需要重新渲染。
- 哪些动作需要重新判定。

必须防止循环依赖：

```text
A依赖B，B又依赖A
```

可采取的策略包括：禁止循环、要求显式计算顺序、使用稳定点计算，或者将其中一个值改为命令触发而不是自动派生。默认应优先选择禁止或消除循环，因为它最容易解释和测试。

### 23. 空值不是一个含义

UI 中的“没有值”至少可能表示：

```text
不存在：该对象没有这个属性
未知：业务上存在，但目前不知道
未加载：数据尚未获取
无权限：数据存在，但当前用户不能看
不适用：该字段在当前场景没有意义
已清空：用户主动删除了原值
计算失败：派生值无法得到
```

如果都压成 `null` 或空字符串，界面就无法给出正确反馈，写回时也无法区分“保持不变”和“清空字段”。

建议在接口或 ViewModel 中明确区分：

```text
value       真实值
presence    present / absent / unknown / notApplicable
loading     是否正在加载
masked      是否已脱敏
editable    是否可编辑
error       获取或计算失败原因
```

不是每个字段都要返回一个复杂包装对象，但高风险或强语义字段必须有表达这些状态的能力。

### 24. 对象身份：显示值变化，关联不能漂移

UI 经常显示名称，业务关联依赖稳定标识：

```text
显示：星海商贸
身份：customerId = 1001
```

如果名称改变，历史订单仍应关联同一个客户；如果两个客户同名，选择器也必须能区分。

对象身份设计需要回答：

- 使用数据库主键、业务编号还是全局 ID。
- ID 在租户、区域和系统之间是否唯一。
- 对象被合并、迁移或删除后，旧链接如何处理。
- UI 深链接和收藏是否仍能定位对象。
- 列表刷新后，选中状态是否按身份而不是行号恢复。

身份是跨 UI 保持同一业务对象语义的锚点。

### 25. 时间是映射的一等输入

同一个字段可能有多个时间版本：

```text
当前客户等级
下单时客户等级
审批时风险快照
报表统计口径下的历史等级
```

因此 UI 显示的值不只取决于“哪个对象”，还取决于“哪个时间语义”：

```text
Value = Read(objectId, field, effectiveTime, version)
```

常见时间语义：

| 类型 | 含义 | 适用场景 |
|---|---|---|
| 当前值 | 此刻最新事实 | 日常详情和操作页 |
| 业务生效时间 | 规则在何时有效 | 价格、合同、组织关系 |
| 系统记录时间 | 系统何时知道 | 审计、追溯和纠错 |
| 快照 | 某次决策时冻结的事实 | 审批、结算、对账 |
| 聚合窗口 | 一段时间的统计 | 报表和指标 |

如果时间语义没有标明，用户看到的两个“客户等级”可能都正确，却属于不同时间，从而产生表面矛盾。

### 26. 映射正确性的四个层次

一个页面“能显示”只证明了最浅的一层。

#### 层次一：结构正确

字段、组件、布局和数据绑定符合 Schema。

#### 层次二：语义正确

金额、状态、单位、指标和对象身份解释一致。

#### 层次三：行为正确

编辑、校验、提交、权限和状态转换符合业务规则。

#### 层次四：时间与运行正确

在并发、缓存、服务失败、权限变化和版本升级下仍能给出可解释结果。

大型系统真正难的是后三层。只做字段到控件的映射，解决的是结构正确；一个可持续的映射体系还必须治理语义、行为和运行时正确性。

## 第五篇　交互模型：UI 不只是数据的终点

把业务数据投影成页面，只解释了读取方向。真正的界面还要承载用户意图、局部草稿、校验反馈、异步结果和导航上下文。UI 既是业务事实的观察窗口，也是用户发起业务变化的入口。

### 27. 三种状态不能混在一起

一个编辑页面至少同时存在三种状态：

```text
业务状态 D    服务端已经确认的事实
界面草稿 W    用户尚未提交的工作副本
交互状态 Σ    加载、选中、展开、错误、焦点等临时状态
```

例如编辑订单：

```text
D.status       = DRAFT
D.quantity     = 2
W.quantity     = 3
Σ.quantityDirty = true
Σ.saving        = false
```

用户输入 `3` 后，数据库中的数量仍然是 `2`。如果系统把草稿状态直接当成业务事实，就会在自动保存、多人协作、离开页面和失败恢复时产生混乱。

#### 27.1 业务状态

由服务端或权威数据源确认，能够被其他用户和系统观察到，需要遵守事务、权限和业务不变量。

#### 27.2 草稿状态

由当前用户在当前编辑会话中持有。它可能不完整、暂时非法，也可能依赖尚未提交的其他字段。

#### 27.3 交互状态

只服务当前界面体验，例如某个区块是否展开、列表选中了哪一行、请求是否正在加载。这些状态通常不属于业务模型。

设计 ViewModel 时，必须知道某个属性属于哪一种状态，不能因为它们都出现在前端对象中就混为一谈。

### 28. 草稿是一条分支，不是业务真相

可以把编辑过程理解为从业务事实分出一条临时分支：

```text
D₀ ──创建草稿──> W₀ ──用户编辑──> W₁ ──校验──> W₂
 │                                           │
 └────────其他人修改────────> D₁             │
                                             ↓
                                     提交并尝试合并
```

提交时需要比较：

```text
基线版本 D₀
当前服务端版本 D₁
用户草稿 W₂
```

如果 `D₁ = D₀`，通常可以直接提交；如果不同，需要判断冲突字段、重新计算规则，或者要求用户刷新。

#### 28.1 常见草稿策略

| 策略 | 优点 | 代价 | 适用场景 |
|---|---|---|---|
| 本地临时草稿 | 快、实现简单 | 换设备和清缓存会丢失 | 短表单、低风险编辑 |
| 服务端草稿记录 | 可跨设备、可恢复 | 需要草稿生命周期和清理 | 长流程、复杂单据 |
| 自动保存 | 降低丢失风险 | 需要节流、冲突和失败提示 | 内容创作、低冲突对象 |
| 显式保存 | 边界清晰、便于事务校验 | 用户可能忘记保存 | 核心业务表单 |
| 协同编辑 | 多人实时协作 | 合并、身份和冲突成本高 | 文档、设计协作 |

自动保存不是天然更好。金额、库存或状态敏感的业务单据，频繁把半成品写成正式事实可能比丢草稿更危险。

### 29. 校验不是一层，而是一条责任链

```text
输入级校验
  ↓
字段级校验
  ↓
跨字段校验
  ↓
对象业务规则
  ↓
跨对象约束
  ↓
权限、并发和外部系统校验
```

#### 29.1 UI 适合承担什么

- 必填、长度、格式和明显范围错误。
- 用户输入后的即时反馈。
- 跨字段的本地可计算提示。
- 在提交前整理完整错误列表。

#### 29.2 服务端必须承担什么

- 权限和数据范围。
- 最新业务状态下的合法性。
- 唯一性、库存、额度、金额等共享约束。
- 并发、事务和外部系统结果。
- 任何不能信任客户端自行保证的规则。

同一规则可以在 UI 复制一份用于体验，但服务端仍然是权威执行者。规则共享可以通过统一 Schema、生成代码或共享库实现，但不能把“前端已经校验”当成服务端省略校验的理由。

### 30. 命令、事件和字段更新的边界

#### 30.1 字段更新适合表达局部事实变化

```text
修改客户备注
更新联系人称呼
调整草稿显示顺序
```

如果变化局部、低风险、没有复杂副作用，通用 `PATCH` 往往是最小且清晰的方案。

#### 30.2 命令适合表达业务意图

```text
提交订单
批准退款
确认发货
取消合同
```

命令通常包含：

```text
目标对象
期望执行的动作
动作所需参数
基线版本或条件
请求唯一标识
```

#### 30.3 事件描述已经发生的事实

```text
OrderPaid
ShipmentCreated
RefundApproved
```

UI 通常发出命令，不应伪造领域事件。事件由拥有业务规则的服务在命令成功后产生，用于通知其他投影或系统。

### 31. 动作是状态机、权限和任务的交集

可用动作可以形式化为：

```text
AvailableActions =
  DeclaredActions(page)
  ∩ AllowedByState(object)
  ∩ AllowedByPermission(user, object)
  ∩ RelevantToTask(task)
```

例如订单状态为 `PAID`：

```text
状态允许：发货、退款
用户权限允许：发货
当前任务相关：处理待发货订单
最终显示：发货
```

即使 UI 已经计算出可用动作，提交后服务端仍要使用最新状态重新判定。页面打开后到用户点击之间，状态和权限都可能变化。

### 32. 错误也是 UI 模型的一部分

一个成熟的页面不能只定义成功状态，还应定义失败如何被理解和恢复。

| 错误类型 | UI 应回答的问题 | 常见恢复方式 |
|---|---|---|
| 输入错误 | 哪个值不合法，怎样改 | 定位字段并保留草稿 |
| 权限变化 | 为什么现在不能操作 | 刷新权限、返回或申请权限 |
| 并发冲突 | 哪些数据已被别人修改 | 对比、刷新、合并或重试 |
| 部分数据失败 | 哪个区块不可用 | 局部重试，不阻断主体 |
| 业务拒绝 | 哪条规则阻止了动作 | 展示业务原因和可行下一步 |
| 网络未知结果 | 请求是否可能已经成功 | 查询最终状态，避免盲目重试 |
| 系统故障 | 用户应做什么 | 保留草稿、提供追踪编号 |

错误不应只映射成一个统一 Toast。错误发生的位置、影响范围和恢复方式不同，UI 表达也应该不同。

### 33. 加载、空白和无权限不是同一状态

对于一个关联区块：

```text
Loading     正在获取
Empty       已成功获取，但没有数据
Forbidden   当前用户无权读取
Failed      获取失败
Stale       有旧数据，但刷新失败
Partial     只获取到部分数据
```

如果全部显示为“暂无数据”，用户无法判断应该等待、创建数据、申请权限还是联系支持。

一个页面的状态空间可以表示为：

```text
Σ = Σdata × Σdraft × Σrequest × Σpermission × Σnavigation
```

实际实现不应穷举所有组合，而应为关键区块定义独立、可组合的状态边界，避免一个次要服务失败导致整页不可用。

### 34. 导航也是数据与任务的映射

页面映射解决“当前怎样看”，导航映射解决“下一步可以去哪里”。大型软件的导航可以表达为：

```text
Navigation = N(
  业务能力图,
  当前用户与权限,
  当前工作空间,
  当前任务,
  当前对象及状态,
  历史和收藏,
  设备环境
)
```

完整导航更接近图，而不是一棵树：

```text
G = (V, E)

V = 领域、模块、页面、对象、任务、动作
E = 包含、关联、跳转、返回、搜索命中、状态转换
```

左侧菜单是图中的稳定主干；搜索、待办、对象关联、最近访问和状态动作是其他边。当前用户看到的是完整导航图在权限、空间和任务条件下的子图。

这与数据模型到 UI 的映射是同一种思想：

```text
完整业务图 + 当前上下文 → 当前可见、可达、可操作的导航子图
完整业务事实 + 当前上下文 → 当前可见、可理解、可操作的任务视图
```

### 35. 上下文恢复属于正确性，不只是体验优化

用户从“上海门店、待发货、第 3 页”进入订单详情，返回后如果回到默认订单列表，他需要重新构造刚才的工作上下文。

导航状态至少可能包括：

```text
当前工作空间
查询与筛选条件
排序和分页
滚动位置
选中对象
打开来源
未提交草稿
```

状态转换可以表示为：

```text
Sₜ₊₁ = δ(Sₜ, Aₜ)
```

其中 `Sₜ` 是当前上下文，`Aₜ` 是点击、搜索、切换空间或执行业务动作，`Sₜ₊₁` 是操作后的新状态。

对高频工作流来说，上下文丢失会直接增加任务成本和误操作风险，因此应作为导航契约的一部分测试。

### 36. 多端映射：共享语义，不强求共享页面结构

桌面端、移动端、大屏和语音界面可以共享：

- 业务概念和稳定标识。
- 状态、权限和动作语义。
- 指标、金额和派生值口径。
- 接口契约或读取模型的一部分。

但不应强求共享：

- 组件树。
- 信息密度。
- 导航结构。
- 操作节奏。
- 错误反馈形式。

例如订单列表在桌面端可以是十二列表格，在移动端可能是三行摘要卡片，在语音界面中则可能变成“朗读三个异常订单”。它们共享任务和业务语义，不共享具体视觉结构。

### 37. 可访问性也是映射上下文

设备环境不只包括屏幕尺寸，还包括用户的感知与操作能力：

```text
键盘操作
屏幕阅读器
高对比度
缩放与大字号
减少动画
触控目标尺寸
```

如果状态只通过颜色表达，`PAID → 绿色` 的映射对色觉障碍用户是不完整的。正确映射应同时提供文本、语义标签和程序可访问名称。

因此：

```text
表现形式 = Resolve(业务语义, 任务, 终端, 可访问性需求)
```

可访问性不是生成 UI 后再补的样式，而是映射函数的一项输入约束。

## 第六篇　低代码与动态 UI：从元数据到可执行界面

第三篇已经说明低代码平台需要区分 Data、Semantic、View、Action 和 Permission 五类元数据。本篇继续追问：这些元数据如何经过设计、发布、编译和运行，最终成为一次确定、可解释、可迁移的界面决策。

本篇关注单次发布与运行如何发生；第七篇则关注多版本、多租户和长期演化中，如何持续证明这些运行结果仍然正确。

本篇关于运行时分层、规则治理和版本机制的内容属于通用架构判断。节点化 UI Schema、字段响应式状态等具体观察参考了本地低代码竞品知识库中的官方资料或源码初证；这些证据不代表所有产品都采用同一种内部实现。

### 38. 低代码平台真正编译的不是页面，而是任务解释契约

最初级的低代码生成器做的是：

```text
数据库字段 -> 默认控件 -> CRUD 页面
```

成熟的业务低代码平台要处理的则是：

```text
稳定的业务事实
  + 业务语义
  + 页面任务
  + 角色与数据范围
  + 当前业务状态
  + 终端能力
  + 页面显式覆盖
  -> 当前用户此刻可见、可理解、可执行的任务视图
```

因此，低代码运行时不是一个“读 JSON 并递归渲染组件”的工具，而是一台受约束的解释器。它接收多组元数据和运行时上下文，执行选择、合并、校验、权限收敛、组件解析、数据绑定与动作绑定，最后产生 UI。

可以把这个过程形式化为：

```text
RuntimeUI = Render(
  Compile(
    DataSchema,
    SemanticSchema,
    ViewSchema,
    ActionSchema,
    PermissionSchema,
    Context,
    Registry
  ),
  RuntimeData,
  RuntimeState
)
```

这里至少存在两个阶段：

- **编译阶段**：检查引用、合并默认规则、解析依赖、收敛权限、生成稳定的运行计划。
- **执行阶段**：取数、求值、绑定状态、渲染组件、响应用户操作并重新计算受影响部分。

如果平台没有这层区分，所有逻辑都会挤进组件渲染过程。结果通常是错误晚发现、性能难定位、规则无法解释、历史版本不可稳定回放。

这一章的核心张力是：

```text
配置自由度
      <->
运行时的确定性、可解释性与安全性
```

平台不应追求无限表达力，而应追求：在明确边界内，任何一个运行结果都能解释“它由哪组规则、哪个版本、什么上下文共同决定”。

### 39. 设计态、发布态与运行态必须分离

一个页面配置在生命周期中并不是同一个对象。

| 形态 | 服务对象 | 应包含的内容 | 不应泄露到下一阶段的内容 |
|---|---|---|---|
| 设计态模型 | 页面设计者 | 选中状态、拖拽位置、物料信息、属性面板、草稿、辅助标记 | 设计器临时状态 |
| 发布态模型 | 审核、版本与部署系统 | 稳定标识、组件声明、规则、绑定、权限引用、依赖版本 | 未校验引用、临时草稿 |
| 运行态计划 | 渲染器与规则引擎 | 已解析组件、依赖图、查询计划、权限结果、表达式计划 | 设计器协议、无关配置 |
| 实例态状态 | 当前用户会话 | 字段值、脏状态、校验结果、加载状态、展开状态 | 不应持久化的瞬时 UI 状态 |

转换链路是：

```text
DesignerTree
  -> normalize
  -> validate
  -> publish snapshot
  -> compile
  -> RuntimePlan
  -> instantiate(context, data)
  -> RuntimeUI
```

这条链路中有三个必须守住的不变量：

1. **已发布快照不可被草稿直接覆盖。**线上页面必须指向明确版本，而不是“当前最新配置”。
2. **相同版本与相同上下文应产生确定的运行计划。**动态数据会变化，但规则解析结果不能随机漂移。
3. **每次转换都必须保留稳定标识和来源信息。**否则无法做差异比较、错误定位、迁移和回滚。

本地知识库中的 Designable 与 Formily 资料也支持这种边界划分：设计器节点树服务拖拽和属性编辑，发布或运行结构服务渲染与校验。这个分离不是框架偏好，而是版本治理和运行稳定性的前提。

#### 39.1 为什么不能只保存整页大 JSON

整页 JSON 适合原型，但当页面需要局部修改、插件插槽、模板复用、多人编辑和版本迁移时，它会暴露几个问题：

- 一个小改动造成整页 diff，难以审查。
- 节点没有稳定身份，引用和权限难以绑定。
- 插入、移动、复制只能重写大对象。
- 局部迁移和依赖分析困难。
- 冲突通常在最后保存时才暴露。

更可维护的抽象是带稳定 ID 的节点图或节点树：

```text
Page
  -> SchemaNode(id, type, props, parentId, order)
  -> Binding(sourceId, targetId, expression)
  -> Rule(ruleId, dependencies, effect)
  -> PermissionRef(subject, resource, operation)
  -> Version(versionId, parentVersionId, status)
```

NocoBase 的 UI Schema 存储源码初证展示了 `schema -> nodes`、`nodes -> schema`、`patch`、`insertAdjacent`、`duplicate` 和 `remove` 等操作。这说明“节点化”不仅是存储形式，更决定平台能否支持局部演进。

但节点化也不是目的本身。页面很小、没有局部协作与迁移需求时，版本化整页文档更简单。选型判据是变更和治理需求，不是节点表看起来更专业。

### 40. 元数据编译流水线

低代码平台可以把发布过程设计成一条显式流水线。每一步只回答一种问题，失败时返回可定位的诊断，而不是让运行时白屏。

```text
草稿配置
  -> 1. 语法与结构校验
  -> 2. 标识与引用解析
  -> 3. 默认值和继承合并
  -> 4. 语义类型与组件解析
  -> 5. 数据依赖和规则图构建
  -> 6. 权限与动作收敛
  -> 7. 查询与加载计划生成
  -> 8. 静态风险检查
  -> 9. 生成不可变发布快照
  -> 10. 生成运行时计划与缓存
```

#### 40.1 语法与结构校验

检查 Schema 自身是否合法，例如：

- 节点类型是否存在。
- 必填属性是否齐全。
- 子节点类型是否允许放在当前父节点下。
- 标识是否重复。
- 配置值是否满足属性约束。

这一阶段只判断“配置是否是一段合法语言”，不判断它是否满足业务语义。

#### 40.2 标识与引用解析

低代码 Schema 中的字段、查询、动作、组件、表达式和权限策略彼此引用。发布前应把所有引用解析为稳定标识，并检测：

- 字段已删除或改名。
- 组件插件未安装或版本不兼容。
- 动作引用了不存在的命令。
- 表达式引用了不可达的数据节点。
- 循环依赖或跨边界依赖。

名称用于显示，稳定 ID 用于关联。只用字段名连接规则，会让重命名变成破坏性变更。

#### 40.3 默认值与继承合并

一个字段的最终配置通常来自多层来源：

```text
物理类型默认值
  <- 逻辑类型默认值
  <- 业务语义默认值
  <- 场景模板
  <- 页面配置
  <- 租户配置
  <- 当前实例的运行时限制
```

“后者一定覆盖前者”并不总是安全。布局、标签和组件样式可以覆盖；权限和数据范围只能收窄，不能由页面配置放宽。平台必须为每类属性定义不同的合并代数。

#### 40.4 依赖图构建

规则和绑定不是孤立字符串，而是一张依赖图：

```text
country -> provinceOptions
province -> cityOptions
items[*].price, items[*].quantity -> totalAmount
status, currentRole -> availableActions
```

发布前构建依赖图，可以检测环路、计算影响范围，并让运行时只重新计算受影响的节点。Formily 的字段级状态和响应式机制提供了一条重要启发：复杂表单的性能瓶颈往往不是字段总数，而是一次变化触发了多少无关计算与渲染。

#### 40.5 静态风险检查

编译阶段还应检查无法仅靠类型系统发现的问题：

- 隐藏字段是否仍可由客户端提交。
- 金额或库存计算是否只存在于前端。
- 动作是否缺少服务端权限与状态校验。
- 表达式是否访问敏感数据。
- 远程数据源是否会形成 N+1 请求。
- 页面是否引用非确定的“最新版本”资产。
- 规则是否存在永远无法到达的分支。

静态检查不能替代运行验证，但能把大量错误从用户操作时前移到发布时。

---

### 41. 组件解析不是一个 if-else，而是一项可解释决策

原文给出了组件解析公式：

```text
Component = Resolve(
  字段业务语义，
  页面类型，
  查看或编辑模式，
  业务状态，
  用户权限，
  终端环境，
  页面显式覆盖
)
```

大型平台还需要回答两个问题：解析规则如何组织，以及冲突时为什么选中了这个组件。

推荐把候选选择拆成“过滤、评分、覆盖、验证”四步：

```text
候选组件集合
  -> 按能力与安全约束过滤
  -> 按语义和场景匹配度评分
  -> 应用允许的显式覆盖
  -> 验证最终组件契约
```

例如 `amount` 字段在编辑页解析为 `MoneyInput`，诊断信息不应只返回组件名，还应返回决策轨迹：

```text
field: amount
selected: MoneyInput
because:
  semanticType = money
  view = edit
  mode = editable
  currency = CNY
overriddenBy: page.node.orderAmount
rejected:
  NumberInput: semantic match lower
  MoneyDisplay: does not support edit capability
```

这样的“解释计划”能同时服务设计器预览、线上诊断和自动化测试。

#### 41.1 组件必须声明契约

组件注册表不能只有 `name -> ReactComponent`。一个可治理的组件至少应声明：

```text
ComponentContract {
  id
  version
  supportedSemanticTypes
  supportedModes
  valueShape
  eventContract
  requiredCapabilities
  allowedChildren
  accessibilityContract
  migrationHandlers
}
```

其中最容易被忽略的是 `valueShape` 与 `eventContract`。同样是选择器，有的提交稳定 ID，有的提交完整对象，有的提交标签字符串；如果注册表没有明确契约，页面看起来正常，写回时却会产生隐蔽错误。

#### 41.2 显式覆盖不等于无限覆盖

页面设计者可以把金额的列表展示由 `MoneyCell` 改为 `MoneyWithTrend`，但不应把一个受保护的服务端动作替换成任意脚本，也不应通过配置绕过字段权限。

可以把属性分为三类：

| 类别 | 示例 | 合并原则 |
|---|---|---|
| 表达属性 | 标签、顺序、布局、提示文案 | 页面可覆盖 |
| 能力属性 | 是否可编辑、可导出、可批量操作 | 上下文与权限共同收敛 |
| 安全属性 | 数据范围、字段读取权、动作授权 | 只能由可信边界决定，客户端配置不能放宽 |

### 42. 规则系统：优先级只是最后手段

当平台同时支持显隐、必填、只读、计算、联动、权限和流程状态时，规则冲突一定会出现。例如：

```text
页面配置：amount 可编辑
业务状态：已支付订单不可修改 amount
字段权限：财务角色可修改 amount
合规策略：已开票订单任何人不可修改 amount
```

如果只给规则配置一个数字优先级，系统虽然能算出结果，却难以解释，也容易让高优先级配置意外突破安全边界。

更稳妥的办法是先按规则性质分层：

```text
最终能力 = 页面期望能力
         ∩ 组件支持能力
         ∩ 业务状态允许能力
         ∩ 角色与数据权限允许能力
         ∩ 平台安全策略允许能力
```

对于 `visible`、`editable`、`executable` 等安全相关能力，合并通常采用“最小权限”原则：任一可信约束拒绝，最终就拒绝。对于标签、布局等表达属性，才采用覆盖或优先级。

#### 42.1 建议的冲突决策顺序

1. **先分域。**安全、业务、交互和视觉规则不能混在同一优先级空间。
2. **再定合并算子。**布尔能力用交集，数值范围用收窄，集合权限用交集，样式和标签可覆盖。
3. **同域内再比较特异性。**页面节点规则通常比全局默认更具体。
4. **特异性相同才使用显式优先级。**优先级是消歧工具，不是全部治理模型。
5. **仍无法确定就阻止发布。**静默挑选一个结果会把配置错误带到生产。

#### 42.2 规则执行需要确定性

至少要明确：

- 同一轮中规则以什么顺序求值。
- 一个规则修改另一个规则的输入时是否再次传播。
- 如何检测循环联动。
- 异步数据返回晚于用户新输入时如何丢弃过期结果。
- 规则异常时使用上一次值、默认值、禁用状态还是阻止提交。

对计算规则，最好要求纯函数式输入输出；对通知、Webhook、启动审批等副作用，必须离开字段联动引擎，进入有幂等、重试和审计能力的动作执行系统。

#### 42.3 规则解释与模拟

设计器应能回答：

```text
当前字段为什么隐藏？
哪条规则令它只读？
如果角色变为财务、状态变为草稿，结果是什么？
修改这条规则会影响哪些字段、页面和动作？
```

因此每次求值最好生成结构化轨迹：

```text
RuleTrace {
  inputSnapshot
  matchedRules
  skippedRules
  conflictResolution
  finalEffects
  duration
  errors
}
```

轨迹中的敏感数据必须脱敏，并设置采样和保留期限，不能为了可观测性复制整份业务对象。

### 43. 数据获取：先生成页面查询计划，再请求数据

动态页面常见的失败方式，是每个组件各自取数：客户选择器查客户、地址组件查地区、明细表查商品，最终形成瀑布请求和 N+1 查询。

运行时应先从页面依赖图生成查询计划：

```text
ViewSchema + Bindings + PermissionScope
  -> RequiredDataGraph
  -> QueryPlan
  -> execute
  -> PageReadModel
```

查询计划至少要处理：

- 当前首屏真正需要哪些字段。
- 哪些关联可批量加载。
- 哪些区块可以延迟加载。
- 相同查询能否合并和去重。
- 权限过滤应在哪个数据源执行。
- 数据的时间点与新鲜度要求是什么。
- 部分数据源失败时页面如何降级。

这里的关键边界是：页面 Schema 可以声明“需要什么”，但不能决定“有权读取什么”。数据范围必须进入服务端查询，而不是先取回全量数据再由前端隐藏。

#### 43.1 空值、无权限和加载失败不是同一种状态

低代码组件不能把以下情况都显示成 `--`：

```text
真实值为空
字段无权查看
数据仍在加载
远程数据源失败
字段不适用于当前对象
数据已被脱敏
```

运行时值应携带最小状态信息：

```text
RuntimeValue<T> =
  | { state: "ready", value: T | null }
  | { state: "loading" }
  | { state: "forbidden" }
  | { state: "masked", display: string }
  | { state: "error", errorCode: string, retryable: boolean }
  | { state: "not-applicable" }
```

具体实现可以不同，但语义必须区分，否则用户无法判断“没有数据”还是“系统坏了”，开发人员也无法准确监控。

---

### 44. 动作运行时：按钮背后必须是受控命令

低代码页面的危险不在显示错一个标签，而在把高风险业务动作退化成通用字段更新或任意客户端脚本。

动作 Schema 应描述用户意图及其契约：

```text
ActionDefinition {
  actionId
  commandType
  inputSchema
  visibleWhen
  enabledWhen
  requiredPermission
  allowedStates
  confirmationPolicy
  idempotencyPolicy
  resultHandling
}
```

运行链路应是：

```text
点击动作
  -> 客户端基础校验与确认
  -> 生成 Command + requestId + expectedVersion
  -> 服务端重新检查身份、数据范围、业务状态
  -> 执行业务事务与副作用协调
  -> 返回新事实或处理状态
  -> 失效相关投影并重新加载
```

`visibleWhen` 与 `enabledWhen` 用于体验，不是授权。即使攻击者绕过 UI 直接调用命令，服务端仍必须拒绝非法状态、越权数据和重复请求。

#### 44.1 动作失败后的恢复协议

动作不只有成功和失败。运行时还需区分：

- 校验失败：保留输入并定位字段。
- 版本冲突：展示差异，允许刷新、合并或放弃。
- 网络超时且结果未知：用 `requestId` 查询结果，不能直接重试制造重复副作用。
- 异步处理中：显示可追踪的任务状态。
- 部分副作用失败：核心事务状态与补偿状态必须可查询。

通用 Toast 无法承担这些语义。动作契约应声明结果类型，页面再选择合适的恢复方式。

### 45. 版本、发布、迁移与回滚

低代码配置一旦进入生产，就成为与代码、接口同样真实的运行契约。平台至少需要区分：

```text
Draft -> Validated -> Published -> Deprecated -> Retired
```

#### 45.1 发布快照

一次发布应固定：

- 页面 Schema 版本。
- 依赖的数据模型版本。
- 组件和插件兼容范围。
- 规则与表达式版本。
- 权限策略引用方式。
- 编译器版本和编译结果摘要。

运行时不能无条件绑定“最新组件”或“最新字段定义”，否则未修改页面也可能因依赖升级而改变行为。

#### 45.2 兼容性分类

| 变更 | 常见风险 | 建议处理 |
|---|---|---|
| 增加可选字段 | 旧页面通常可继续运行 | 新版本可按需采用 |
| 字段显示名改变 | 关联通常不受影响 | 使用稳定 ID，刷新文案 |
| 字段类型改变 | 组件、校验和历史数据都可能不兼容 | 新版本字段或显式迁移 |
| 删除字段 | 规则、绑定、报表可能断链 | 先标记弃用，完成引用扫描 |
| 组件值契约改变 | 写回可能静默损坏 | 提升主版本并提供迁移器 |
| 权限规则收紧 | 页面功能减少 | 允许即时收紧并提供影响报告 |
| 权限规则放宽 | 数据暴露风险 | 单独审核，不随页面迁移自动放宽 |

#### 45.3 迁移器

Schema 迁移应是显式、幂等、可审计的转换：

```text
migrate(schema, fromVersion, toVersion) -> migratedSchema + diagnostics
```

迁移前后应检查：

- 节点稳定 ID 是否保留。
- 引用是否仍可解析。
- 行为是否发生有意变化。
- 未识别配置是保留、隔离还是阻止发布。
- 能否用旧快照回滚。

不要用“读取时顺手修一下”替代版本迁移。隐式修复使同一份快照在不同时间产生不同结果，也无法审计谁改变了生产行为。

#### 45.4 回滚的真实边界

页面配置回滚是双向门，业务数据迁移通常不是。若新页面已经写入旧版本无法理解的数据，仅回滚 Schema 可能让页面无法读取历史记录。

因此发布前要区分：

```text
仅表达变更 -> 通常可直接回滚页面快照
契约变更 -> 需要兼容窗口或双读双写
数据变更 -> 需要数据迁移与逆向方案
权限变更 -> 回滚前还要重新评估暴露风险
```

### 46. 插件与扩展：能力要开放，故障域要封闭

组件、数据源、规则操作符和动作处理器通常都需要扩展。但扩展点越强，平台运行时越容易失去确定性。

建议把扩展分为声明式和命令式两类：

- **声明式扩展**：组件契约、字段语义、校验器、格式化器、查询适配器。优先使用，容易检查和缓存。
- **命令式扩展**：自定义脚本、复杂动作、生命周期钩子。能力更强，应进入受控执行边界。

插件生命周期至少包括：

```text
install -> validate -> enable -> migrate -> observe -> disable -> uninstall
```

每个插件需要声明：

- 插件 ID 与版本。
- 平台兼容范围。
- 提供和依赖的能力。
- 所需数据与网络权限。
- 安装、升级和卸载迁移。
- 禁用后的页面降级方式。

#### 46.1 自定义脚本的边界

允许任意脚本直接访问页面上下文、浏览器全局对象和内部 API，会让 Schema 变成无法治理的代码分发渠道。更稳妥的原则是：

1. 能用声明式规则表达的，不开放脚本。
2. 脚本只获得最小能力对象，不获得平台内部对象。
3. 网络、数据源和敏感字段访问需要显式授权。
4. 执行设置时间、内存和调用次数上限。
5. 脚本版本随发布快照固定，执行结果可追踪。
6. 涉及核心业务不变量的逻辑必须在服务端领域边界重新验证。

“脚本沙箱”不是绝对安全承诺。真正的安全来自能力最小化、隔离、审计与服务端不变量共同作用。

---

### 47. 缓存与性能：缓存的是计划，不是权限结论

低代码运行时可缓存的对象包括：

- 解析后的发布快照。
- 组件注册表索引。
- 表达式编译结果。
- 依赖图和查询模板。
- 与用户无关的静态格式配置。

需要谨慎缓存的是：

- 记录级权限结果。
- 依赖业务状态的动作集合。
- 包含租户、用户、地区或时间上下文的规则结果。
- 敏感数据的投影。

缓存键必须包含所有会影响结果的上下文。若无法完整列出上下文，就不应缓存最终结果，而应缓存与上下文无关的中间计划。

推荐把性能预算拆成：

```text
T_total = T_schema_load
        + T_compile_or_cache
        + T_data_fetch
        + T_rule_eval
        + T_render
        + T_interaction_update
```

只测首屏总时间无法判断慢在 Schema、数据源、规则还是组件。运行时应分别采集这些阶段的时延和命中率。

#### 47.1 局部更新

当字段 `quantity` 变化时，应从依赖图定位 `lineAmount`、`totalAmount` 和相关校验，而不是重新执行整页规则并渲染整棵组件树。

但局部响应也有边界：如果规则允许动态读任意字段，平台无法静态知道依赖范围。此时要么要求显式声明依赖，要么接受更保守的重算成本，并在设计器中显示性能警告。

---

### 48. 可观测性：必须能回答“为什么这个用户看到这个页面”

传统前端日志通常只记录组件报错。动态 UI 还需要观察“配置决定过程”。建议建立以下关联标识：

```text
requestId
tenantId
appId
pageId
releaseVersion
runtimePlanHash
userRoleSnapshot
dataSnapshotVersion
actionId
```

平台应能查询：

- 当前页面使用了哪个发布版本。
- 哪个组件或规则来自哪个插件版本。
- 某字段为何隐藏、只读或脱敏。
- 某动作为何不可见、禁用或被服务端拒绝。
- 一次字段变化触发了哪些规则和查询。
- 页面慢在编译、取数、求值还是渲染。

#### 48.1 诊断信息分层

| 使用者 | 需要的信息 |
|---|---|
| 最终用户 | 可理解的状态、失败原因和恢复动作 |
| 页面设计者 | 节点、规则、绑定、版本与影响范围 |
| 平台运维 | 请求链路、阶段耗时、缓存、数据源与错误码 |
| 安全审计 | 谁在何时以何版本读取或执行了什么 |

不要把内部堆栈、表达式源码和敏感数据直接展示给最终用户；也不要只给平台设计者一个“渲染失败”的黑箱提示。

---

### 49. 测试策略：测试的是解释结果，而不只是 Schema 能否解析

动态 UI 的测试对象可以分成五层：

#### 49.1 Schema 合约测试

- 节点类型与属性是否合法。
- 引用是否可解析。
- 组件值契约是否匹配字段和命令输入。
- 旧版本是否能通过迁移器转换。

#### 49.2 规则决策表测试

用代表性上下文验证最终能力：

| 角色 | 订单状态 | 开票状态 | amount 可见 | amount 可编辑 |
|---|---|---|---|---|
| 客服 | 草稿 | 未开票 | 是 | 否 |
| 财务 | 草稿 | 未开票 | 是 | 是 |
| 财务 | 已支付 | 未开票 | 是 | 否 |
| 财务 | 已支付 | 已开票 | 是 | 否 |

测试应断言最终结果和解释轨迹中的关键规则，而不只比较一大段脆弱的页面快照。

#### 49.3 投影与写回契约测试

- 页面读取模型是否保持业务口径。
- 组件输出是否能生成合法 Command。
- 派生值是否不会被当成原始事实写回。
- 服务端是否拒绝越权、过期版本和非法状态命令。

#### 49.4 迁移与回滚测试

- 历史发布快照是否仍可编译。
- 迁移是否幂等。
- 插件升级后旧页面是否进入兼容或明确阻断状态。
- 回滚后是否仍能读取新版本产生的数据。

#### 49.5 性能与稳定性测试

- 大表单字段变化的影响范围。
- 规则环路和异步竞态。
- 数据源超时与部分失败。
- 插件缺失、禁用或升级失败时的降级。
- 缓存是否跨租户或跨权限上下文污染。

### 50. 一个订单审批页怎样被编译出来

下面把前面的机制放回订单案例。

#### 50.1 输入

```text
DataSchema:
  Order(id, customerId, status, amount, revision)

SemanticSchema:
  amount = money(CNY)
  status = orderStatus

ViewSchema:
  approval page
  amount node requests MoneyDisplay
  action area requests Approve / Reject

PermissionSchema:
  approver can read assigned orders
  senior approver required when amount > 10000

Context:
  userRole = approver
  orderStatus = PENDING_APPROVAL
  amount = 1288
  device = desktop
```

#### 50.2 编译结果

```text
1. amount 解析为 MoneyDisplay，而不是 MoneyInput。
2. 客户信息和风险信息进入页面查询计划。
3. Approve / Reject 组件通过状态与角色能力过滤。
4. amount > 10000 的高级审批规则未命中。
5. 两个动作绑定到 ApproveOrder / RejectOrder Command。
6. Command 自动携带 orderId、requestId 与 expectedRevision。
```

#### 50.3 用户点击“通过”

```text
UI -> ApproveOrder(orderId, comment, expectedRevision, requestId)
   -> 服务端重新检查任务归属、状态、金额规则与 revision
   -> 写入审批事实与审计记录
   -> 返回新的订单状态
   -> 失效审批页和相关列表投影
   -> 页面重新编译动作集合，“通过/驳回”消失
```

这说明动态 UI 的“动态”并不是客户端任意改变页面，而是页面根据新的业务事实和上下文重新得到一个受规则约束的解释结果。

---

### 51. 平台建设的最小可行分层

不要一开始建设万能低代码引擎。可按风险和证据逐步扩展。

#### 第一阶段：标准页面生成

```text
Data Schema
+ Semantic Type
+ Component Registry
+ View Schema
+ 基础服务端权限
```

目标是稳定生成列表、详情和简单表单，守住稳定 ID、读写契约和服务端安全边界。

#### 第二阶段：发布与规则治理

```text
Draft / Published Version
+ 规则依赖图
+ 冲突解析
+ 发布前检查
+ 诊断轨迹
```

目标是让配置可测试、可解释、可回滚，而不是继续堆组件数量。

#### 第三阶段：任务与动作运行时

```text
Action Schema
+ Command Contract
+ 状态与权限收敛
+ 幂等和并发
+ 异步结果恢复
```

目标是支持订单、工单和审批等任务界面，而不是把业务过程伪装成 CRUD。

#### 第四阶段：生态与规模化

```text
插件生命周期
+ Schema 迁移
+ 多租户覆盖策略
+ 查询计划优化
+ 可观测性与容量治理
```

只有当复用规模、团队协作或外部扩展需求出现证据时，才进入这一阶段。

---

### 52. 低代码运行时的十二条底线

1. 设计态、发布态、运行态和实例态不能混成一份可变 JSON。
2. 发布版本必须不可变，并能追溯依赖、编译器和插件版本。
3. 字段、节点、规则和动作之间使用稳定 ID 关联，显示名不能充当主键。
4. 权限、业务状态和安全策略只能收窄能力，页面配置不能放宽它们。
5. 每类属性必须定义自己的合并算子，不能用一个通用优先级解决全部冲突。
6. 规则需要依赖图、循环检测、确定执行语义和可解释轨迹。
7. 字段联动只处理可控计算；通知、Webhook、支付和审批启动进入幂等动作系统。
8. 页面 Schema 声明需要什么数据，服务端权限决定允许读取什么数据。
9. 组件必须声明值、事件、能力和版本契约，不能只注册一个渲染函数。
10. 缓存优先保存与用户无关的编译计划，不能遗漏权限上下文缓存最终页面结果。
11. Schema、组件和数据契约变更必须有兼容分类、迁移器和回滚边界。
12. 平台必须能解释：在某个版本和上下文下，为什么这个用户看到了这个字段和动作。

### 53. 一句话总结

> 低代码平台不是把字段自动换成组件，而是把业务事实、任务、权限、状态和版本编译成一份可执行、可解释、可迁移的界面契约；真正的成熟度不在“能配置多少”，而在“配置发生变化后仍能保证正确、安全和可治理”。

## 第七篇　工程治理：让映射长期保持正确

前面的形式化模型和低代码运行时说明了“页面怎样生成”。工程治理回答另一个更难的问题：当数据、权限、组件、规则、用户和组织不断变化时，如何保证页面没有悄悄改变业务含义，没有越权，没有把旧数据解释错，也没有在高并发和部分故障下给出错误行动建议。

因此，本篇不重复定义运行时组件，而是把第六篇的运行机制转化为真值责任、权限边界、质量门禁、测试证据、迁移流程和可观测指标。

治理不是在架构图外围增加审批流程，而是把映射的关键性质变成可验证、可观测、可迁移和可回滚的契约。

### 54. 真值来源：同一个概念由谁说了算

一个大型系统里，同一个值可能出现在多个位置：

```text
订单服务中的实付金额
支付服务中的成功交易金额
列表投影中的格式化金额
报表仓库中的销售额
浏览器草稿中的预估金额
```

它们不应该都被称为“真值”。建议为重要业务概念建立语义登记：

| 属性 | 要回答的问题 |
|---|---|
| 业务名称 | 这个概念叫什么 |
| 精确定义 | 包含和排除什么 |
| 稳定标识 | 跨接口和页面怎样引用 |
| 权威来源 | 哪个服务或数据集拥有最终解释权 |
| 计算版本 | 算法、舍入和口径版本是什么 |
| 时间语义 | 当前值、业务生效值还是快照 |
| 更新方式 | 同步写入、事件投影还是批处理 |
| 消费方 | 哪些 UI、API、报表和规则依赖它 |

例如“销售额”如果没有说明使用支付时间还是下单时间、退款如何扣减、跨币种如何折算，图表即使计算无误也没有稳定业务含义。

#### 54.1 权威来源不等于唯一副本

为了性能和分析，可以存在列表投影、缓存和数据仓库副本。关键是明确：

```text
谁产生权威事实
副本如何更新
允许延迟多久
冲突时以谁为准
如何发现和修复漂移
```

“最后更新时间更新的副本”不一定更正确；它可能使用了旧口径重新计算。

### 55. 权限模型：先限制数据，再决定表现

权限至少包含：

```text
租户或工作空间范围
对象类型权限
记录或数据范围
字段读取与修改权限
动作与流程权限
设计、发布和运维权限
```

可以形式化为：

```text
ReadableData = QueryNeed ∩ TenantScope ∩ RecordScope ∩ FieldScope

EditableFields = PageEditable
               ∩ FieldWritePermission
               ∩ AllowedByBusinessState

ExecutableActions = DeclaredActions
                  ∩ ActionPermission
                  ∩ AllowedByBusinessState
                  ∩ CurrentTaskScope
```

这里的交集应尽量在可信服务端边界计算。前端拿到的数据应当已经最小化，而不是先获得完整对象再隐藏字段。

#### 55.1 隐藏、禁用和只读表达不同语义

| 表现 | 含义 | 典型场景 |
|---|---|---|
| 隐藏 | 用户不需要知道或无权知道 | 敏感字段、无关功能 |
| 禁用 | 用户知道功能存在，但当前条件不满足 | 状态未到、依赖未完成 |
| 只读 | 可以查看，但不能修改 | 已确认金额、审计信息 |
| 脱敏 | 可以知道部分事实 | 客服查看手机号 |

是否隐藏属于产品与安全共同判断，不能机械地把所有无权限项都隐藏，也不能用禁用状态泄露敏感能力。

#### 55.2 多租户边界不能在映射中丢失

页面查询、选择器、关联查找、导出、搜索、缓存键和异步事件都必须保留租户或业务范围。最危险的错误往往不是主页面越权，而是：

- 客户选择器搜索到其他租户客户。
- 关联名称批量查询遗漏租户条件。
- 页面缓存没有把租户加入键。
- 导出或报表使用了全局数据集。
- 后台投影恢复时丢失租户上下文。

### 56. 时间与一致性：页面显示的是哪个时刻的事实

不同 UI 可以接受不同新鲜度，但必须明确声明：

| 页面 | 常见要求 | 主要风险 |
|---|---|---|
| 编辑页 | 基线版本 + 提交时最新校验 | 覆盖别人修改 |
| 详情页 | 接近实时或标明缓存时间 | 基于旧状态执行动作 |
| 审批页 | 决策快照 + 必要当前值 | 混淆历史证据和当前事实 |
| 列表 | 可接受短缓存 | 状态标签短暂滞后 |
| 报表 | 明确统计截止时间 | 把延迟数据当实时数据 |

#### 56.1 最终一致性需要用户可理解

如果订单支付成功后，列表投影需要数秒更新，UI 可以：

- 立即使用命令结果更新当前对象。
- 标记后台仍在同步。
- 让列表刷新时以新版本覆盖临时状态。
- 超过预期延迟后提供查询与诊断入口。

不能一边采用最终一致性，一边向用户承诺所有页面瞬间完全一致。

#### 56.2 快照需要记录形成条件

一个审批快照至少应能追溯：

```text
快照时间
业务对象版本
规则或口径版本
创建原因
关键来源版本
```

否则事后无法判断审批人当时看到的是什么。

### 57. 查询计划与性能预算

页面性能问题通常不是组件渲染单独造成的，而是整条映射链路共同作用：

```text
T总 = T加载Schema
    + T解析规则
    + T鉴权
    + T查询与组合
    + T传输
    + T渲染
    + T交互重算
```

每类页面应有不同预算和策略：

- 列表限制字段、关系和行数，批量获取显示值。
- 详情区分首屏核心区块和延迟区块。
- 选择器使用服务端搜索、分页和稳定身份。
- 报表限制时间范围、维度基数和下钻深度。
- 大表单根据依赖图局部重算，而不是全页求值。

#### 57.1 识别 N+1 和瀑布调用

典型危险路径：

```text
查询20条订单
→ 每条查询1次客户
→ 每条查询1次支付状态
→ 每条再计算1次权限
```

应优先改为面向页面的批量查询或读取投影。BFF、查询服务、数据库连接或批量接口只是不同实现选择，关键是让页面依赖形成可见查询计划。

#### 57.2 缓存键必须包含所有决定结果的上下文

可能影响结果的维度包括：

```text
tenantId, user/role, dataScope, objectState,
locale, currency, schemaVersion, componentVersion,
businessRuleVersion, snapshotTime
```

如果无法完整列出影响维度，优先缓存与用户无关的中间计划，而不是缓存最终页面或权限结果。

### 58. 并发、版本与幂等

#### 58.1 防止静默覆盖

编辑命令建议携带基线版本：

```json
{
  "orderId": "O202607130001",
  "expectedVersion": 7,
  "changes": { "remark": "工作日送货" }
}
```

服务端发现当前版本为 `8` 时，应返回冲突，而不是静默覆盖。是否允许自动合并取决于字段语义：不同用户修改互不相干的备注可能可合并，订单明细、金额和状态通常需要更谨慎。

#### 58.2 防止重复副作用

支付、审批、退款、发货等命令应有稳定的请求唯一标识或等价幂等机制：

```text
同一个业务意图 + 同一个请求ID
→ 多次到达仍只产生一次业务效果
```

幂等不等于吞掉所有重复请求。系统应能返回第一次执行的结果，或者明确说明仍在处理中。

#### 58.3 未知结果需要查询，不是盲目重试

客户端超时并不证明服务端失败。高风险动作应允许通过 `requestId` 或业务对象查询最终状态，避免重复扣款、重复审批和重复发货。

### 59. 失败隔离与恢复协议

页面组合多个来源后，失败边界应与任务关键性对齐：

```text
订单主体失败       → 详情任务无法继续，整页阻断
物流摘要失败       → 物流区块降级，订单主体仍可看
推荐信息失败       → 静默降级或稍后重试
权限服务不确定     → 对敏感能力默认拒绝
提交结果未知       → 查询状态，不直接重复命令
```

#### 59.1 错误模型应携带恢复信息

```text
errorCode      稳定错误分类
userMessage    面向用户的说明
fieldPath      可定位的字段或区块
retryable      是否适合重试
requestId      查询与支持追踪标识
nextActions    刷新、申请权限、重新登录、联系支持等
```

技术堆栈和敏感对象不应直接暴露给用户，运维侧仍应能用追踪标识找到完整链路。

### 60. 可观测性：观察一次解释是怎样形成的

动态 UI 除了记录请求成功率，还需要回答：

```text
页面使用了哪个 Schema、组件和规则版本？
当前用户为什么看见或看不见这个字段？
哪个数据源、权限或规则导致页面变慢？
一次字段变化触发了哪些派生值和查询？
动作被 UI 禁用还是被服务端拒绝？
```

建议关联：

```text
requestId, tenantId, userContextHash,
pageId, schemaVersion, runtimePlanHash,
objectId, objectVersion, actionId
```

#### 60.1 解释轨迹不是复制完整业务对象

记录匹配规则、版本、决策结果和耗时即可；敏感输入应脱敏或摘要化。可观测性不能成为第二条数据泄露通道。

#### 60.2 不同角色需要不同解释

- 用户需要知道发生了什么、怎样继续。
- 页面设计者需要知道规则、绑定和版本。
- 开发运维需要调用链、耗时和错误码。
- 安全审计需要谁在何时读取或执行了什么。

### 61. 测试模型：从结构到业务行为

#### 61.1 Schema 和静态检查

- 节点、字段和属性是否合法。
- 引用和稳定 ID 是否存在。
- 组件值契约是否匹配数据与命令输入。
- 依赖图是否存在循环。
- 敏感字段是否被不安全组件引用。

#### 61.2 映射单元测试

- 状态 code 是否映射正确文案和语义。
- 金额、单位、时区和空值是否正确转换。
- 派生字段是否使用权威口径。
- 有损映射是否被标为不可写。

#### 61.3 双向与属性测试

对于可逆映射验证：

```text
put(D, get(D)) = D
get(put(D, U新)) = normalize(U新)
```

对金额、日期区间、选择器等输入，可以生成大量边界值验证精度、时区、空值和非法输入。

#### 61.4 权限与状态决策表

| 角色 | 数据范围 | 对象状态 | 字段可见 | 字段可写 | 动作可执行 |
|---|---|---|---|---|---|
| 客服 | 所属客户 | 草稿 | 是 | 否 | 查看 |
| 财务 | 所属组织 | 草稿 | 是 | 是 | 调整 |
| 财务 | 所属组织 | 已支付 | 是 | 否 | 退款申请 |
| 仓库 | 所属门店 | 已支付 | 部分 | 否 | 发货 |

应测试允许路径和拒绝路径，也要测试深链接、搜索、导出和直接 API，而不只是菜单是否出现。

#### 61.5 契约与端到端测试

- 页面读取模型与 API 契约兼容。
- Command 输入与组件输出一致。
- 服务端拒绝越权、过期版本和非法状态。
- 用户从任务入口进入、执行动作并返回原上下文。
- 部分服务失败时按预期降级。

#### 61.6 视觉和可访问性测试

映射正确不等于视觉可用。还需要检查长文本、极值、空态、错误态、不同语言、缩放、键盘和屏幕阅读器语义。

### 62. 版本模型：哪些变化是兼容的

至少需要区分：

```text
数据 Schema 版本
业务语义或规则版本
接口契约版本
View Schema 版本
组件契约版本
插件版本
发布快照版本
```

#### 62.1 变更分类

| 变更 | 常见兼容性 | 主要动作 |
|---|---|---|
| 增加可选字段 | 通常向后兼容 | 旧页面忽略，新页面采用 |
| 改显示标签 | 结构兼容 | 更新文案和翻译 |
| 改稳定标识 | 高风险 | 建映射、扫描引用、迁移 |
| 改字段类型 | 高风险 | 迁移数据、组件和校验 |
| 删除字段 | 破坏性 | 先弃用、扫描依赖、分阶段删除 |
| 改金额口径 | 语义破坏性 | 新版本、回算与对账 |
| 改组件值形状 | 契约破坏性 | 主版本和迁移器 |
| 收紧权限 | 功能减少 | 影响报告、立即安全生效 |
| 放宽权限 | 数据暴露风险 | 单独安全审核 |

版本号本身不会带来兼容性。真正有价值的是变更分类、依赖扫描、迁移函数和兼容窗口。

### 63. 迁移、灰度与回滚

#### 63.1 迁移必须显式

```text
migrate(oldSchema, fromVersion, toVersion)
  → newSchema + diagnostics
```

迁移需要幂等、可审计，并能报告无法自动处理的配置。不要在运行时悄悄修改历史 Schema，否则同一发布版本在不同时间会产生不同页面。

#### 63.2 先验证存量，再切换生产

推荐流程：

```text
扫描存量页面与依赖
→ 离线迁移副本
→ 编译和契约测试
→ 代表性数据回放
→ 灰度用户或租户
→ 观察错误、性能和业务指标
→ 扩大范围
```

#### 63.3 回滚要区分表达和数据

页面布局回滚通常容易；如果新页面已经写入旧模型不认识的数据，回滚 UI 并不能恢复兼容。涉及数据和对外契约的变更，需要双读、双写、适配或反向迁移方案。

### 64. 影响分析：一个字段变化会波及哪里

大型映射系统应维护依赖图：

```text
字段
→ 语义类型
→ 读取模型
→ 页面节点
→ 公式和规则
→ 权限策略
→ 动作输入
→ 报表指标
→ 导出模板
```

删除或改名之前，先回答：

- 哪些页面读取它。
- 哪些公式和显隐规则依赖它。
- 哪些 Command 接收它。
- 哪些报表使用它作为维度或度量。
- 哪些历史版本仍然引用它。
- 哪些外部接口或自动化依赖它。

没有依赖图时，只能靠全局文本搜索和人工记忆，配置规模越大越不可靠。

### 65. 设计、发布与运行的职责边界

| 角色 | 主要责任 | 不应独自决定的内容 |
|---|---|---|
| 产品/业务 | 任务、信息优先级、口径和异常路径 | 服务端授权和并发策略 |
| 交互/页面设计 | 结构、组件、反馈和可访问性 | 改写业务不变量 |
| 平台团队 | Schema、组件契约、规则与发布系统 | 每个业务域的最终口径 |
| 领域团队 | 权威事实、Command、状态和不变量 | 任意控制所有页面布局 |
| 安全团队 | 数据范围、敏感等级和审计要求 | 用安全规则替代任务设计 |
| 运维/质量 | 门禁、监控、故障恢复 | 临时修改业务语义掩盖故障 |

重点不是组织名称，而是决策责任必须明确。一个规则如果没人拥有，就会在前端、后端和报表中各出现一份。

### 66. 质量指标与门禁

可以观察的指标包括：

```text
Schema 编译成功率
历史版本兼容通过率
规则冲突和循环依赖数量
页面查询数、P95 加载时间和局部重算时间
权限拒绝与异常放行审计
Command 重复率、冲突率和未知结果率
投影延迟和对账差异
页面错误恢复成功率
无障碍检查通过率
关键任务完成率和耗时
```

#### 66.1 不要把指标变成唯一目标

页面加载快不代表业务解释正确；配置项多不代表低代码能力成熟；自动生成率高也可能意味着页面同质化。质量门禁应同时覆盖正确性、安全、性能和任务效果。

#### 66.2 建议的发布门禁

```text
结构合法
→ 引用完整
→ 权限不放宽
→ 规则无循环和未决冲突
→ 历史配置可迁移
→ 关键契约与决策表通过
→ 性能预算不过线
→ 高风险变更完成人工评审
```

### 67. 安全、隐私与审计

数据最小化原则应贯穿映射链：

```text
查询时限制记录和字段
→ 传输时只发送所需数据
→ UI 中按任务最小展示
→ 日志和轨迹脱敏
→ 导出再次鉴权
→ 缓存按租户和权限隔离
```

#### 67.1 敏感数据分类

字段元数据可以声明：

```text
sensitivity       敏感等级
maskingPolicy     脱敏策略
exportPolicy      导出限制
retentionPolicy   保留期限
auditPolicy       访问是否审计
purposePolicy     允许使用目的
```

页面显示权限不自动等于导出权限；单条查看和批量下载的风险不同。

#### 67.2 审计记录业务意图

比起只记录 `status: PENDING → APPROVED`，审计更应记录：

```text
谁在什么租户和角色上下文
基于哪个对象版本和页面版本
执行了什么业务命令
服务端应用了哪些关键规则
结果和追踪标识是什么
```

### 68. 失败模式与预演

大型手册最后仍需要回到一个朴素问题：这套方案最可能怎样失败？

#### 68.1 万能实体泄露到所有页面

表现：接口返回完整实体，页面自行解释权限和状态。

后果：耦合、过度暴露、查询浪费和业务规则分散。

预防：按任务设计读取模型，服务端先收敛权限。

#### 68.2 万能 Schema 吞掉全部业务逻辑

表现：支付、审批、重试和补偿都塞进表达式或脚本。

后果：无法事务化、无法审计、难以测试和迁移。

预防：配置标准表达，Command 和领域服务守住高风险变化。

#### 68.3 同一概念多套口径

表现：列表、详情和报表分别计算金额和状态。

后果：用户看到互相冲突的系统。

预防：语义登记、权威来源、契约测试和对账监控。

#### 68.4 权限只做菜单和按钮

表现：入口隐藏，但搜索、接口、导出或选择器仍可访问。

后果：跨租户和敏感数据泄露。

预防：记录、字段、动作和数据源各层服务端鉴权。

#### 68.5 读取投影被错误当成写入模型

表现：直接提交格式化、组合或聚合后的页面对象。

后果：掩码写回、金额漂移、关联身份丢失。

预防：单独设计编辑模型和 Command，标注可逆性。

#### 68.6 动态平台无法解释结果

表现：只能看到最终组件，无法知道哪条规则生效。

后果：配置越多，排障和审计越困难。

预防：稳定版本、解析轨迹、依赖图和影响分析。

#### 68.7 为了“大而全”提前引入全部架构

表现：简单 CRUD 同时引入 BFF、CQRS、规则引擎和通用状态机。

后果：维护成本先于业务价值到来。

预防：从满足当前约束的最小模式开始，用页面差异、规模、风险和性能证据推动演进。

#### 68.8 三个月后失败的预演问题

在落地前主动回答：

```text
哪个业务概念最容易产生两套口径？
哪个权限入口最容易遗漏租户范围？
哪个组合页面会先出现 N+1 或部分失败？
哪个 Schema 变更最难迁移？
哪个派生字段最可能被误写回？
哪个高风险动作可能被重复执行？
如果平台团队离开，谁还能解释运行结果？
```

这些问题比增加更多抽象层更能提前暴露真实风险。

## 第八篇　完整案例：一张订单如何变成五种任务视图

这一篇把前面的概念放回一个端到端案例。目的不是提供可直接复制的订单系统设计，而是展示从业务事实、读取投影、UI 状态到写入命令的完整推理过程。

### 69. 第一步：识别事实、规则和上下文

#### 69.1 核心业务事实

```text
Order
├── orderId
├── tenantId
├── customerId
├── status
├── currency
├── paidAmount
├── version
├── createdAt
├── paidAt
└── items[]

OrderItem
├── productId
├── skuId
├── quantity
├── unitPrice
└── lineAmount
```

这里没有假定数据库必须按这个对象结构建表。它只是案例中需要持续追踪的业务事实集合。

#### 69.2 关键业务语义

```text
orderId       订单的稳定身份
customerId    订单所属客户的稳定身份
status        订单当前所处业务阶段
paidAmount    按统一金额口径得到的实付金额
version       用于识别并发修改的版本
items[]       决定订单内容和金额构成的明细
```

#### 69.3 映射上下文

```text
Context
├── task              查找 / 理解 / 编辑 / 审批 / 分析
├── user              当前用户
├── permissions       记录、字段和动作权限
├── workspace         当前租户、组织或门店
├── businessState     订单状态
├── device            桌面、移动或大屏
├── locale            语言、币种和时区
└── freshness         实时、快照或统计窗口
```

同一订单事实与不同上下文组合，产生五种任务视图。

### 70. 列表 UI：为“找”而投影

#### 70.1 页面问题—答案契约

```text
问题：我要处理的订单在哪里？
答案：用少量可比较字段展示一组订单，并提供筛选、排序和进入详情的路径。
```

#### 70.2 读取投影

```text
OrderListItem = π(
  orderId,
  customerDisplayName,
  itemCount,
  paidAmount,
  status,
  createdAt,
  availableActions
)
```

示例：

```json
{
  "orderId": "O202607130001",
  "customer": {
    "id": 1001,
    "displayName": "星海商贸"
  },
  "itemCount": 5,
  "paidAmount": {
    "minorUnits": 128800,
    "currency": "CNY"
  },
  "status": {
    "code": "PAID",
    "label": "已支付",
    "tone": "success"
  },
  "createdAt": "2026-07-13T10:15:00+08:00",
  "availableActions": ["VIEW", "SHIP"]
}
```

#### 70.3 为什么不返回完整订单

- 列表的任务是扫描和比较，不是理解全部明细。
- 完整明细增加传输、查询和渲染成本。
- 列表中不需要的敏感字段不应被返回。
- 每行携带大量关联对象容易造成 N+1 或过度组合。

#### 70.4 列表状态

```text
查询条件：门店、状态、时间范围
结果状态：加载、空、失败、部分刷新
导航状态：页码、排序、滚动位置、选中行
```

从列表进入详情再返回，应恢复这些上下文。

### 71. 详情 UI：为“看懂”而组合

#### 71.1 页面问题—答案契约

```text
问题：这张订单发生了什么，现在处于什么状态，我可以继续做什么？
答案：组合订单、客户、支付、物流和历史信息，按重要性分区，并给出合法下一步动作。
```

#### 71.2 读取组合

```text
OrderDetail = Compose(
  OrderSummary,
  CustomerSummary,
  OrderItems,
  PaymentSummary,
  ShipmentSummary,
  Timeline,
  AvailableActions
)
```

这里不是“加载所有实体”。每个区块仍然是面向详情任务的读取投影。

#### 71.3 局部失败策略

```text
订单主体成功 + 物流失败
→ 保留订单详情
→ 物流区块显示失败和重试
→ 不把整页替换成统一错误页
```

但如果订单主体本身不存在、越权或无法读取，则应停止展示依赖它的其余区块。

#### 71.4 动作计算

```text
详情页声明动作：取消、支付、发货、退款
订单状态允许：发货、退款
用户权限允许：发货
最终动作：发货
```

页面显示动作是服务端判断的提示或投影，不是最终授权凭证。

### 72. 编辑 UI：为“形成合法草稿”而映射

#### 72.1 页面问题—答案契约

```text
问题：当前有哪些内容可以修改，修改后是否构成一张可提交订单？
答案：只暴露当前状态允许编辑的字段，维护独立草稿并持续反馈校验结果。
```

#### 72.2 编辑模型

```json
{
  "orderId": "O202607130001",
  "baseVersion": 7,
  "customerId": 1001,
  "items": [
    {
      "itemId": "I001",
      "skuId": 2001,
      "quantity": 2
    }
  ],
  "remark": "工作日送货"
}
```

编辑模型没有直接接收 `paidAmount` 和任意 `status`，因为它们不是当前任务可以自由改写的事实。

#### 72.3 草稿与派生值

```text
W.items[].quantity  用户草稿
W.estimatedAmount   本地即时预估
D.authoritativeAmount 服务端最终计算
```

UI 可以立即给出金额预估，但提交后必须使用服务端商品价格、促销和精度规则重新计算。若最终金额不同，应按业务风险决定提示确认还是直接拒绝。

#### 72.4 并发冲突

```text
用户打开时 baseVersion = 7
提交时服务端 version = 8
→ 不能静默覆盖
→ 返回冲突字段或要求刷新
```

订单明细这类结构化集合通常不能只用“最后写入者获胜”解决。

### 73. 审批 UI：为“作出可追溯决策”而映射

#### 73.1 页面问题—答案契约

```text
问题：我依据哪些事实决定通过或驳回，决定会产生什么后果？
答案：突出决策所需证据、风险、历史和规则，并把审批表达成明确命令。
```

#### 73.2 决策快照

审批页面可能既需要当前事实，也需要提交审批时的快照：

```text
当前客户等级：VIP
提交审批时等级：普通
```

两者都可能正确。UI 必须标明时间语义，不能把历史快照伪装成当前值。

#### 73.3 审批命令

```json
{
  "command": "ApproveOrder",
  "orderId": "O202607130001",
  "approvalTaskId": "A9001",
  "decision": "APPROVE",
  "comment": "资料完整",
  "baseVersion": 8,
  "requestId": "approval-unique-id"
}
```

审批不是 `approvalStatus = APPROVED` 的普通字段更新。服务端还要验证审批任务归属、流程版本、订单状态、权限和重复提交。

### 74. 报表 UI：为“发现规律”而聚合

#### 74.1 页面问题—答案契约

```text
问题：一组订单在某个时间、组织和业务口径下呈现什么规律？
答案：使用明确维度、度量、过滤和统计窗口生成指标与图形。
```

#### 74.2 聚合模型

```text
SalesMetric = γ(
  dimension = storeId, businessDate,
  measures  = SUM(paidAmount), COUNT(orderId),
  filter    = status ∈ PaidStates
)
```

报表中的“销售额”必须明确：

- 使用下单时间、支付时间还是业务日期。
- 是否排除取消和全额退款。
- 部分退款如何计算。
- 跨币种如何折算。
- 数据刷新到什么时间点。

图表只是聚合结果的表现，指标口径才是核心模型。

### 75. 五种 UI 的完整映射矩阵

| 维度 | 列表 | 详情 | 编辑 | 审批 | 报表 |
|---|---|---|---|---|---|
| 核心任务 | 查找 | 理解 | 形成合法修改 | 作出决策 | 发现规律 |
| 输入基数 | 订单集合 | 一个订单及关联摘要 | 一个订单基线 | 订单 + 审批任务 + 快照 | 订单集合/投影 |
| 主要操作 | 选择、排序、筛选 | 连接、组合、解释 | 草稿、校验、命令 | 证据组织、命令 | 分组、聚合、下钻 |
| 数据新鲜度 | 较新 | 接近实时 | 基线 + 最新校验 | 快照与当前值并存 | 统计延迟可声明 |
| 可编辑性 | 通常无 | 通常无 | 受状态和权限约束 | 只编辑决策输入 | 通常无 |
| 写入方式 | 批量动作可选 | 上下文命令 | 更新草稿/提交订单 | 审批命令 | 保存视图或订阅 |
| 主要风险 | 过量查询、上下文丢失 | 跨服务部分失败 | 覆盖、半成品、派生值权威 | 快照混淆、重复审批 | 指标口径漂移、延迟 |
| 验证重点 | 查询和权限 | 组合与动作 | 双向规则和并发 | 状态/权限/审计 | 聚合口径和对账 |

### 76. 从案例得出的设计原则

1. 同一个业务对象可以拥有多个读取模型，不等于复制多套业务真相。
2. 每个页面先定义问题—答案契约，再选择数据和组件。
3. 详情组合多个模型，不代表它应该加载完整实体图。
4. 编辑 UI 操作的是草稿，服务端持有权威业务事实。
5. 审批需要明确当前值与决策快照的区别。
6. 报表首先是指标口径和聚合模型，其次才是图表。
7. 每种视图都需要声明权限、时间语义、失败策略和写入边界。

## 第九篇　深层问题库：继续追问，直到边界清楚

这些问题可以用于产品评审、架构设计、低代码平台能力规划和代码审查。答案给出判断原则，不替代具体项目证据。

本篇是速查入口。遇到需要落地的判断，应回到前八篇对应的模型、机制和案例，而不是只引用一段简答作为架构依据。

### 77. 本质与边界

#### 77.1 UI 是数据模型的一部分吗？

不是同一个模型，但 UI 会引用并解释数据模型中的业务概念。数据库模型决定可用事实，UI 模型决定当前任务如何组织这些事实。两者共享语义，不必共享结构。

#### 77.2 是否每个页面都要单独建立 ViewModel？

不需要。页面与接口结构接近、风险低、变化少时，复用 DTO 更简单。只有当数据形状、权限、组合、性能或演进需求产生实际差异时，专用 ViewModel 才有价值。

#### 77.3 一个字段应该只有一个 UI 组件吗？

不应该这样假设。同一个状态字段可以同时决定 Badge、步骤条、筛选项和动作可用性。组件由业务语义与场景共同决定，而不是字段永久绑定一个组件。

#### 77.4 一个页面能否组合多个领域的数据？

可以，工作台和详情页经常如此。但读取组合不等于写入归属改变。页面发出的命令仍应交给拥有相应业务规则的边界处理。

#### 77.5 UI 模型能否反过来决定数据库模型？

UI 可以暴露业务事实缺失和查询需求，但不应仅为了某个布局就把展示结构永久写进核心数据库。需要区分真正业务事实、读取优化投影和纯界面状态。

### 78. 语义与真值

#### 78.1 谁决定“实付金额”的含义？

应由明确的业务口径和权威服务决定，而不是由某个页面临时相加。所有 UI 和报表引用同一语义定义或可验证的等价实现。

#### 78.2 多个服务都能计算同一个值时，谁是真值来源？

要指定权威来源、计算版本和同步方式。其他副本是缓存或投影，不应在冲突时凭“更新时间较新”自动成为真值。

#### 78.3 显示值和身份值为什么要分开？

名称可重复、可修改、可本地化；稳定身份用于关联、深链接和写入。选择器显示名称但提交 ID，就是这一原则的具体表现。

#### 78.4 `null` 为什么不够？

因为空值可能表示未知、不存在、未加载、无权限、不适用、已清空或计算失败。这些状态对应不同文案、动作和写回语义。

#### 78.5 当前值和历史快照冲突时哪个正确？

两者可能都正确，只是时间语义不同。关键是明确页面任务需要当前事实还是决策当时的事实，并清楚标注。

### 79. 映射与可逆性

#### 79.1 为什么读取映射通常不是写入映射的逆函数？

因为读取会选择、组合、聚合、脱敏和格式化，常常丢失信息。写入必须单独表达用户意图、目标字段、基线版本和业务命令。

#### 79.2 如何判断一个派生字段能否编辑？

检查是否存在唯一、无歧义且符合业务规则的反向转换。如果没有，就应只读或提供编辑原始构成项的入口。

#### 79.3 修改完整地址为何有风险？

完整地址可能由结构化省市区和详细地址组合而成。自由文本无法可靠拆回结构化字段。应使用结构化编辑器或明确的解析与确认流程。

#### 79.4 格式化金额一定可逆吗？

不一定。还涉及币种、精度、舍入、千位分隔和地区格式。写回应解析为明确的最小单位或精确数值，并由服务端再次校验。

#### 79.5 脱敏值可以参与编辑吗？

通常不能直接把 `138****1234` 写回手机号。若允许修改，应要求输入完整新值；若不修改，提交协议必须区分“保持原值”和“把字段改成掩码字符串”。

### 80. 规则与冲突

#### 80.1 页面配置和字段权限冲突时谁优先？

权限优先。展示配置可以在允许范围内选择表达，不能扩大可读取或可修改范围。

#### 80.2 两条显隐规则冲突怎么办？

先明确它们属于安全约束还是展示偏好。安全约束通常取更严格结果；展示规则按特异性和显式优先级合并，并提供冲突诊断。

#### 80.3 “最后配置覆盖”为什么不够？

它无法表达拒绝优先、安全不可覆盖和多来源规则，也很难解释结果。平台需要区分配置类别，并记录解析轨迹。

#### 80.4 字段依赖形成循环怎么办？

默认应阻止发布并给出依赖路径。只有确实存在稳定点语义时才引入迭代求解，而且必须定义终止条件和不可收敛处理。

#### 80.5 租户能否覆盖平台默认组件？

可以在平台允许的扩展点和安全边界内覆盖。覆盖需要版本、兼容性和回滚策略，不能替换服务端业务规则。

### 81. 状态与写入

#### 81.1 页面上的值何时才成为业务事实？

当用户意图通过服务端权限、规则、并发和事务校验，并被权威数据源确认之后。输入框中的值只是草稿。

#### 81.2 自动保存是否总比显式保存好？

不是。自动保存适合低风险、可频繁合并的内容；对金额、库存和状态敏感单据，半成品持久化和未知结果可能增加风险。

#### 81.3 什么时候用 `PATCH`，什么时候用 Command？

局部、低风险、语义就是字段变化时优先 `PATCH`；涉及状态转换、跨对象不变量、审计或副作用时使用表达业务意图的 Command。

#### 81.4 UI 已隐藏按钮，服务端为什么还要鉴权？

因为请求可以绕开 UI，且权限可能在页面打开后变化。UI 隐藏改善体验，服务端鉴权保证安全。

#### 81.5 提交后网络断开，用户应该直接重试吗？

不能盲目重试。结果可能已经成功。高风险命令应使用请求唯一标识，并提供按请求或对象查询最终状态的方式。

### 82. 性能与一致性

#### 82.1 详情页是否应该一次返回全部数据？

取决于任务关键路径、数据规模和失败边界。主体信息可一次返回，低优先级或重数据区块可以独立加载；不能默认加载完整实体图。

#### 82.2 BFF 是否是复杂页面的必选项？

不是。单体服务、查询服务、GraphQL 或前端组合都可能合适。只有当终端适配、跨服务组合和治理收益大于新增层成本时才引入 BFF。

#### 82.3 报表为什么可以接受延迟，操作页却不一定可以？

报表回答一段时间内的规律，常能声明统计截止时间；操作页会基于当前状态发出命令，过旧数据可能导致错误决策。

#### 82.4 缓存的 UI 需要显示“更新时间”吗？

当数据新鲜度会影响用户判断时需要。例如库存、价格、风险和经营指标；纯静态字典则通常不必强调。

#### 82.5 如何避免列表 N+1？

建立面向列表的批量查询或投影，批量获取关联显示值，限制每行关联内容；不要逐行调用客户、商品和权限服务。

### 83. 测试与演化

#### 83.1 映射测试只测组件是否出现够吗？

不够。还要测业务语义、权限矩阵、状态动作、派生口径、可逆规则、并发冲突、时间语义和版本兼容。

#### 83.2 Schema 变更后历史页面怎么办？

需要 Schema 版本、迁移函数和兼容窗口。不可原地假设旧配置符合新语义；发布前应对存量配置进行批量验证。

#### 83.3 字段改名是 UI 小改动吗？

显示标签改名通常是双向门；字段标识或业务语义改名可能影响 API、公式、权限、报表和历史配置，是高成本变更。

#### 83.4 如何发现多个 UI 口径漂移？

集中登记语义和计算版本，用契约测试、对账指标和跨视图抽样比较发现差异；不要等用户截图举报。

#### 83.5 如何回滚一版 UI Schema？

发布物应不可变并带版本，运行时能选择上一稳定版本；若新版本伴随不可逆数据迁移，还需要兼容读取或明确反向迁移方案。

### 84. AI 动态生成 UI

#### 84.1 AI 可以根据数据模型直接生成生产 UI 吗？

可以生成初稿，但仅有数据模型缺少任务、权限、状态、口径和风险信息。没有这些上下文，生成结果最多是字段陈列，不应直接进入高风险生产流程。

#### 84.2 AI 最适合生成什么？

标准 CRUD 初稿、字段分组建议、组件候选、帮助文案、测试用例和 Schema 迁移建议。其输出应受组件白名单、权限边界和 Schema 校验约束。

#### 84.3 哪些内容不应交给 AI 自由决定？

服务端授权、金额与库存不变量、合法状态转换、跨租户范围、最终指标口径和高风险命令。AI 可以辅助解释和建议，不能成为未经治理的权威规则来源。

#### 84.4 如何验证 AI 生成的 UI？

```text
结构校验
→ 组件和属性白名单
→ 数据与权限契约校验
→ 状态/动作模型检查
→ 自动测试与视觉检查
→ 高风险场景人工评审
→ 受控发布和监控
```

#### 84.5 AI 个性化 UI 会破坏一致性吗？

会有这种风险。适合个性化的是排序、密度、推荐入口和非关键布局；稳定名称、对象身份、权限反馈、关键动作位置和业务口径应保持可预测。

#### 84.6 AI 动态 UI 的长期方向是什么？

不是让模型任意画页面，而是让模型在受约束的语义和组件系统中，针对任务生成可验证的视图。核心能力将从“生成像页面的代码”转向“理解任务、引用权威语义、给出映射解释并通过机器校验”。

## 第十篇　结论：从字段绑定走向任务解释系统

数据模型与 UI 映射可以分成五个成熟度层次：

```text
层次1  类型映射：string → Input
层次2  语义映射：money + edit → MoneyInput
层次3  场景投影：订单 + 审批任务 → 审批视图
层次4  交互闭环：读取投影 + 草稿 + Command + 反馈
层次5  治理系统：权限、时间、版本、测试、解释和演化
```

层次越高，不代表项目必须采用越复杂的架构。它表示设计者开始回答更多真实问题。简单 CRUD 可以停在前两层；核心订单、支付、审批和低代码平台需要根据风险逐步覆盖后续层次。

这本手册最终要守住的主线是：

> UI 不是数据的复制品，而是业务事实在任务上下文中的可交互投影；读取组织事实，写入表达意图，治理保证多种表达仍指向同一业务真相。

最后用三句话压缩：

```text
数据库回答：有哪些事实。
UI回答：谁在何时，为了什么任务，需要怎样理解和改变这些事实。
映射体系回答：如何让不同表达保持语义一致、行为正确，并能够安全演化。
```
