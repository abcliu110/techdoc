# 大型软件导航系统设计

## 文档概述

大型软件的导航系统是用户体验的骨架。本文档系统阐述导航的**模式分类**、**设计原则**、**实现机制**和**领域模型映射**，帮助理解从用户视角的「好导航」到工程实现的完整链路。

---

## 一、导航的本质问题

导航要解决三个核心问题：

1. **我在哪里**：当前位置感知
2. **我能去哪里**：可访问路径展示
3. **我怎么到达**：路径执行机制

这三点在不同场景下权重不同：
- 工具型软件（如 IDE、ERP）→ 重在「我能去哪里」和「怎么快速到达」
- 信息型软件（如 CMS、报表）→ 重在「我在哪里」和内容探索
- 交易型软件（如电商、CRM）→ 平衡探索与效率

### 1.1 导航的认知科学基础：Wayfinding 模型

人类导航行为的科学模型，最初源自城市规划与建筑环境研究（Kevin Lynch《城市意象》），后被交互设计广泛采用，包含三个核心能力：

**认知地图（Cognitive Map）**

用户在脑中构建的关于空间结构的整体印象。好的导航帮助用户建立准确的认知地图：
- 侧边栏的视觉层级 → 对应信息的层级关系
- 面包屑 → 认知地图的「锚点」
- 品牌 Logo 链接首页 → 全局参照物

**空间地标（Spatial Landmarks）**

用户用来判断位置的显著参照点。界面中的地标包括：
- 当前高亮的菜单项（告诉用户「你在哪里」）
- 页面标题（告诉用户「这是什么」）
- 页面路径标签（告诉用户「你从哪里来」）

**路径记忆（Path Memory）**

用户记住的到达路径。重复访问会强化路径记忆，但层级过深会导致回退困难。最近访问、最近搜索都是路径记忆的辅助工具。

### 1.2 导航的三种交互哲学

导航模式的选择，本质上是对「用户如何认知系统结构」这一问题的不同回答：

**空间隐喻（Space Metaphor）** — 将信息空间映射为物理空间，用户「走进」不同区域。

典型：Sidebar、Top Bar + 子菜单。用户需要学习系统的空间布局。
- 典型产品：Figma、Notion、飞书

**路径叙事（Path Narrative）** — 将信息空间理解为一条线性路径，用户沿路前进或折返。

典型：面包屑、步骤条。强调「你从哪来」，适合层级深的结构。
- 典型产品：电商后台、文档站点

**索引搜索（Index Search）** — 将系统内容理解为可被搜索的扁平化索引，用户通过关键词直达。

典型：Command Palette、全局搜索。绕过层级，最快但需要用户有明确目标。
- 典型产品：VS Code、Alfred、Linear

### 1.3 导航状态机：页面状态与跳转的数学描述

导航行为可以用状态机形式化描述。页面是状态，导航动作是状态转换：

```typescript
/* 导航状态机形式化定义 */
interface NavState {
  location: string;      // 当前路由路径
  context: object;       // 上下文数据（筛选条件、选中的实体 ID 等）
  history: string[];     // 浏览历史（用于后退）
}

/* 导航动作类型 */
type NavAction =
  | { type: 'PUSH', path: string, context?: object }      // 前进到新页面
  | { type: 'REPLACE', path: string, context?: object }   // 替换当前页面
  | { type: 'POP' }                                        // 后退
  | { type: 'RELOAD' }                                     // 刷新
  | { type: 'CROSS_CONTEXT', path: string, source: string }; // 跨上下文跳转（如从客户跳转订单）

/* 状态转换规则 */
const navReducer = (state: NavState, action: NavAction): NavState => {
  switch (action.type) {
    case 'PUSH':
      return {
        location: action.path,
        context: action.context || {},
        history: [...state.history, state.location],
      };
    case 'POP':
      return {
        location: state.history[state.history.length - 1] || '/',
        context: {},
        history: state.history.slice(0, -1),
      };
    case 'REPLACE':
      return {
        location: action.path,
        context: action.context || {},
        history: state.history,
      };
    default:
      return state;
  }
};
```

**为什么用状态机建模？** 它将「导航行为」从散乱的 `router.push()` 调用中抽象出来，提供了：
- 可预测的状态转换（POP 永远回到上一页，不会跳错）
- 可追踪的历史记录
- 可扩展的动作类型（例如新增 `CROSS_CONTEXT` 跨域跳转）

### 1.4 导航性能指标

评估导航系统有效性的量化指标：

| 指标 | 定义 | 优秀值 | 警告值 |
|------|------|--------|--------|
| **平均导航深度** | 用户完成任务所需的平均点击次数 | ≤ 3 跳 | > 5 跳 |
| **迷失率（Lostness Rate）** | 用户无法找到目标页面的比例 | < 10% | > 25% |
| **回退使用率** | 用户依赖「返回」操作的比例 | — | > 50%（说明入口设计差） |
| **搜索渗透率** | 用户通过搜索而非导航找到内容的比例 | > 30% | < 10% |
| **内容到交互耗时** | 页面加载完成到用户可执行操作的平均时间 | < 1.5s | > 3s |

**导航性能 = 路径深度 × 任务频率** — 高频任务应优先扁平化，低频任务允许更深的层级。

## 二、导航模式分类体系

### 2.1 按作用范围分类

```
导航系统
├── 全局导航（Global Navigation）
│   ├── 顶栏导航（Top Bar）
│   ├── 侧边栏导航（Sidebar）
│   └── 混合导航（Hamburger + Drawer）
├── 区域导航（Local Navigation）
│   ├── Tab 导航
│   ├── 面包屑（Breadcrumb）
│   └── 步骤条（Stepper）
├── 上下文导航（Contextual Navigation）
│   ├── 操作面板
│   ├── 快捷操作栏
│   └── 悬浮菜单
└── 辅助导航（Assisted Navigation）
    ├── 搜索（Search）
    ├── 命令面板（Command Palette）
    └── 最近访问（Recent / Favorites）
```

### 2.2 核心模式详解

#### 模式 A：顶栏导航（Top Bar）

**适用场景**：功能模块数量少（≤7 个）、需要最大化内容区域

**典型布局**：
```
┌────────────────────────────────────────────────────────┐
│ Logo │ 模块A │ 模块B │ 模块C │ 模块D │     搜索 │ 用户 │
└────────────────────────────────────────────────────────┘
                                    ↓ 点击模块D后
┌────────────────────────────────────────────────────────┐
│ Logo │ 模块A │ 模块B │ 模块C★│ 模块D★│     搜索 │ 用户 │
├────────────────────────────────────────────────────────┤
│ 侧边栏：                     │                         │
│  ▸ 子模块1                   │   主内容区               │
│  ▸ 子模块2  ← 当前            │                         │
│  ▸ 子模块3                   │                         │
└────────────────────────────────────────────────────────┘
```

**实现特征**：
- 顶栏通常固定，内容区可滚动
- 子模块通过侧边栏展开（常驻或折叠）
- 模块切换时清空或保留子模块选择状态

#### 模式 B：侧边栏导航（Sidebar）

**适用场景**：功能模块数量多（7-20 个）、需要快速切换

**变体**：
1. **图标+文字**（宽侧边栏）：桌面管理后台
2. **仅图标+悬浮文字**（窄侧边栏）：工具型软件
3. **可折叠侧边栏**：内容优先型界面

**分层设计**：
```
一级导航（侧边栏）  →  聚合根级别的模块
二级导航（Tab/子菜单）→  聚合根内的功能分区
三级导航（内嵌）     →  详情页内的切换
```

#### 模式 C：面包屑 + Tab 组合

> **名称溯源**：「面包屑」典出格林童话《糖果屋》：汉塞尔沿路撒下面包屑标记归途。互联网借喻用户在信息空间走过的路径 —— 它告诉用户「你从哪里来」，提供空间定位感和快速回溯能力。与导航菜单（告诉你「有哪些路可走」）互为补充。

**适用场景**：深层嵌套结构（3 层以上）

**典型场景**：电商管理后台
```
首页 / 商品管理 / 数码整机 / MacBook Pro 详情
     ──────── ─────────  ───────────
     一级    二级       三级（聚合根详情页）
```

**Tab 层级**：
```
┌────────────────────────────────────────────┐
│ 基本信息 │ 规格参数 │ 价格体系 │ 库存管理 │ 销售记录 │
├────────────────────────────────────────────┤
│                                            │
│         聚合根详情（Tab 内切换）            │
│                                            │
└────────────────────────────────────────────┘
```

#### 模式 D：命令面板（Command Palette）

**适用场景**：高频操作、键盘优先用户、专业工具

**设计思想**：将所有操作扁平化为「命令搜索」，绕过层级导航

**典型快捷键**：
- `Ctrl+K` / `Cmd+K`：打开命令面板
- `Ctrl+/`：`Alt` 标签页切换
- `G+I`：跳转 Inbox

**实现要点**：
- 模糊匹配（Fuzzy Search）
- 最近使用优先
- 操作历史
- 权限过滤（只显示有权限的命令）

#### 模式 E：渐进式导航（Progressive Disclosure）

**适用场景**：复杂表单、设置页面、配置向导

**核心思想**：分步骤展示，只在需要时显示更多选项

**示例**：
```
Step 1: 基础信息 ──────────────────
        名称：[        ]
        类型：[下拉选择 ]

Step 2: 高级选项（点击展开）───────
        [+] 显示更多选项
        ↓ 展开后
        有效期：[        ]
        优先级：[下拉选择 ]
        标签：[多选    ]
```

## 三、各模式优缺点拆解

为了在不同场景下做出合理选择，下表从多个维度对每种模式进行**横向对比**：

| 维度 | Top Bar | Sidebar | 面包屑+Tab | 命令面板 | 渐进式导航 |
|------|---------|---------|------------|----------|------------|
| **一级模块容量** | ≤7 个 | 7-20 个 | 不限 | 不限 | 不限 |
| **内容空间占用** | 高度 56-64px | 宽度 220-280px | 高度 28-32px | 无 | 视展开程度 |
| **深层定位能力** | ❌ 弱 | ⚠️ 中 | ✅ 强 | ⚠️ 中 | ✅ 强 |
| **键盘操作效率** | ⚠️ 中 | ⚠️ 中 | ❌ 低 | ✅ 极高 | ⚠️ 中 |
| **新用户学习成本** | ✅ 低 | ⚠️ 中 | ✅ 低 | ❌ 高 | ✅ 低 |
| **实现复杂度** | ✅ 低 | ⚠️ 中 | ⚠️ 中 | ❌ 高 | ⚠️ 中 |
| **移动端友好度** | ✅ 好 | ❌ 差 | ✅ 好 | ❌ 差 | ✅ 好 |
| **SEO 友好度** | ❌ 弱 | ✅ 好 | ✅ 好 | ❌ 差 | ❌ 弱 |

```
│  ▸ 子模块3                   │                         │
└────────────────────────────────────────────────────────┘
```

**实现特征**：
- 顶栏通常固定，内容区可滚动
- 子模块通过侧边栏展开（常驻或折叠）
- 模块切换时清空或保留子模块选择状态

**优点**：
- 水平空间最小化，顶栏固定不占内容高度
- 支持响应式平台自适应（桌面 ↔ 移动端顶栏）
- 学习成本最低，标签式心智模型符合用户直觉（Chrome、Excel）
- 快速切换一级模块，与搜索/消息等全局功能集成友好
- 框架原生组件支持完善（Ant Design、Element UI）

**缺点**：
- 顶栏横向宽度有限，一般只能容纳 ≤7 个一级模块
- 移动端需收起为抽屉或标签栏，需要二次设计
- 子模块需要额外侧边栏；切换主模块时如不保留状态容易迷路
- 深层页面 SEO 受限，导航强依赖二级导航展现

**最佳应用场景**：功能模块数量 ≤7、桌面端、对内容区域要求高的场景（ERP、BI 内容中台、低频模块切换）

### 模式 B：侧边栏导航（Sidebar）

**适用场景**：功能模块数量多（7-20 个）、需要快速切换

**变体**：
1. **图标+文字**（宽侧边栏）：桌面管理后台
2. **仅图标+悬浮文字**（窄侧边栏）：工具型软件
3. **可折叠侧边栏**：内容优先型界面

**分层设计**：
```
一级导航（侧边栏）  →  聚合根级别的模块
二级导航（Tab/子菜单）→  聚合根内的功能分区
三级导航（内嵌）     →  详情页内的切换
```

**优点**：
- 纵向列表不受横向宽度限制，理论上可无限添加二级导航
- 小鼠标运动距离短，适合频繁切换
- 二级导航可完全展开，深层链接可被索引（SEO 友好）
- 可变体适应不同密度需求（宽/窄/折叠三种形态）

**缺点**：
- 横向占用 220-280px，减少内容区可用宽度
- 侧边栏收起时隐藏导航，需要记忆/手势唤回
- 导航文字过多时换行或截断问题
- 移动端需要替代方案，触摸距离长
- 需要处理折叠展开动画、响应式变体、多级展开，实现成本较高

**变体优劣对比**：
| 变体 | 优点 | 缺点 |
|------|------|------|
| 图标+文字 | 认知成本低，可快速定位 | 占用空间大，模块数量受限 |
| 仅图标+悬浮文字 | 节省空间，可容纳更多模块 | 学习成本高，小屏幕难以触发悬浮 |
| 可折叠侧边栏 | 内容优先，凸显主内容区 | 需要额外手势唤回，视觉层次减少 |

**最佳应用场景**：模块横向 >7 的单一领域内后台（CRM、CMS）、桌面端频繁模块切换场景

**适用场景**：深层嵌套结构（3 层以上）

**典型场景**：电商管理后台
```
首页 / 商品管理 / 数码整机 / MacBook Pro 详情
     ──────── ─────────  ───────────
     一级    二级       三级（聚合根详情页）
```

**Tab 层级**：
```
┌────────────────────────────────────────────┐
│ 基本信息 │ 规格参数 │ 价格体系 │ 库存管理 │ 销售记录 │
├────────────────────────────────────────────┤
│                                            │
│         聚合根详情（Tab 内切换）            │
│                                            │
└────────────────────────────────────────────┘
```

**优点**：
- 网页端标准，用户识别度高（电商、管理后台）
- 告诉用户「你从哪里来」，提供精确的空间定位，减少迷路感
- 一键回溯顶层或某个中间级，提升效率
- 对搜索引擎友好，层级路径可直接索引
- 大部分组件库有现成组件

**缺点**：
- Tab 条本身占用高度（28-32px），且深层嵌套时面包屑过长会挤压内容空间
- 需要与 Tab 联动，保持状态同步
- 深度 ≥4 时面包屑需要截断/收起策略

**最佳应用场景**：深度 ≥3、线性信息流结构（电商商品分类、知识库目录、文档站点）

### 模式 D：命令面板（Command Palette）

**适用场景**：高频操作、键盘优先用户、专业工具

**设计思想**：将所有操作扁平化为「命令搜索」，绕过层级导航

**典型快捷键**：
- `Ctrl+K` / `Cmd+K`：打开命令面板
- `Ctrl+/`：`Alt` 标签页切换
- `G+I`：跳转 Inbox

**实现要点**：
- 模糊匹配（Fuzzy Search）
- 最近使用优先
- 操作历史
- 权限过滤（只显示有权限的命令）

**优点**：
- 将所有导航、操作、窗口聚合为文本搜索，完全绕过层级导航
- 键盘驱动，全键盘操作流畅
- 功能点 >30 时效率远超层级点击
- 一旦记住，可极快直接到达任意位置

**缺点**：
- 需要用户知道有此功能且知道快捷键，对新用户不友好
- 无法提供视觉上的空间结构认知（用户看不到整个系统轮廓）
- 中文输入法延迟、手眼协调要求高
- 深层链接隐藏在命令模糊匹配中，SEO 受限
- 需要实现命令路由、权限过滤、模糊匹配、最近使用、操作历史，实现复杂度高

**最佳应用场景**：功能点 >30、用户需要快速定位的场景（JetBrains IDE、VS Code、开发者工具）

**优点**：
- 把复杂表单/配置拆解，首次加载只显示必填，降低首次使用门槛
- 避免信息超载，对新手用户友好
- 移动端天然适配分步展示

**缺点**：
- 需要额外开发成本，分步提交需要状态/缓存管理
- 对熟练用户可能显得「笨重」、流程冗长
- 需要提供「返回上一步」机制、分步验证、暂存机制
- 深层表单对搜索引擎不友好

**最佳应用场景**：复杂表单/向导（设置、注册、配置向导、新手用户引导）

## 四、导航与领域模型的映射

### 3.1 导航层级 vs 聚合根层级

导航层级应与业务聚合根层级保持一致：

| 导航层级 | 对应领域概念 | 示例 |
|---------|-------------|------|
| 一级导航 | 限界上下文（Bounded Context） | 订单、库存、客户 |
| 二级导航 | 聚合根（Aggregate Root） | 订单详情下的 Tab |
| 三级导航 | 聚合根内实体操作 | 订单明细行操作 |

### 3.2 聚合根导航设计规则

**规则 1：聚合根是导航终点**

用户「进入」一个页面的语义终点 = 聚合根详情页

```
❌ 错误设计：
客户列表 → 客户卡片 → 联系人 Tab → 联系人详情

✓ 正确设计：
客户列表（搜索/过滤）→ 客户详情页（包含联系人 Tab）
```

**规则 2：聚合根内跨实体的操作入口应内聚**

```
订单详情页（聚合根）
├── 基本信息 Tab（Order 主信息）
├── 商品明细 Tab（OrderItem 列表）
├── 支付记录 Tab（Payment 列表）
└── 操作区（统一操作按钮）
    ├── 确认订单
    ├── 修改地址
    └── 取消订单
```

**规则 3：跨聚合根跳转需明确来源上下文**

```
从「客户详情」跳转「订单列表」时：
URL 应携带上下文：/customer/123/orders
而不是直接跳转：/orders（丢失客户上下文）

回退时应返回：/customer/123
```

### 3.3 导航路径的数据模型

```java
// 导航节点的领域模型
class NavigationNode {
    private String id;           // 节点唯一标识
    private String label;        // 显示文本
    private String path;         // 路由路径
    private String icon;         // 图标（可选）
    private Integer sortOrder;   // 排序
    private String parentId;     // 父节点（null = 一级）
    private NavigationType type; // 导航类型
    private Permission permission; // 权限约束
    private String aggregateRoot; // 关联的聚合根
}

// 导航树的组装逻辑
class NavigationService {
    // 1. 根据用户权限过滤可见节点
    // 2. 按父子关系组装成树
    // 3. 根据模块启用状态动态显示/隐藏
    // 4. 记录用户最近访问用于排序优化
}
```

## 五、导航设计的核心原则

### 4.1 层级克制原则（Hierarchy Control）

**核心规则**：单次导航层级差 ≤ 1

```
❌ 违反：
首页 → 一级导航 → 二级导航 → 三级导航 → 四级页面

✓ 正确：
首页 → 一级导航 → 二级导航 → 详情页
       （最多3跳到达目标）
```

**为什么重要**：
- 层级越深，用户越难「回去」
- 面包屑过长会挤压内容空间
- 深层页面通常是叶子节点，无需继续深入

### 4.2 上下文保留原则（Context Preservation）

**核心规则**：导航切换时保留合理的上下文

| 场景 | 应保留的上下文 | 不应保留的上下文 |
|-----|--------------|-----------------|
| 同模块内 Tab 切换 | 筛选条件、分页、详情 ID | 无 |
| 模块间切换 | 无 | 应清空（模块完全独立） |
| 详情页返回列表 | 筛选条件、页码 | 编辑状态 |

**实现方式**：
```javascript
// React Router 示例
<Routes>
  <Route path="/orders" element={<OrderList />} />
  <Route path="/orders/:id" element={<OrderDetail />} />
  <Route path="/orders/:id/items" element={<OrderItems />} />
</Routes>

// 返回时使用 replace 而非 push
navigate('/orders', { replace: true }); // 返回列表时
navigate(`/orders/${id}`);                // 进入详情时用 push
```

### 4.3 扁平优先原则（Flat-First）

**核心规则**：能用平级切换解决的，不用层级深入

**适用场景**：
- 多实体并列管理（如：商品、库存、评价）
- 列表页的批量操作
- 多窗口/多 Tab 并行工作

**反例**：
```
商品列表 → 商品详情 → 库存 Tab → 批次列表 → 批次详情
```

**正例**：
```
┌─────────────────────────────────────────────────┐
│  商品    库存    评价    设置                    │ ← 顶部 Tab
├─────────────────────────────────────────────────┤
│                                                 │
│  多视图切换（同级别）                              │
│  [列表视图] [看板视图] [图表视图]                  │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 4.4 一致性原则（Consistency）

**核心规则**：相同类型的操作应有相同的导航表现

| 操作类型 | 导航行为 | 示例 |
|---------|---------|-----|
| 列表 → 详情 | 进入（push） | 订单 → 订单详情 |
| 详情 → 列表 | 返回（back） | 订单详情 → 返回列表 |
| 新增/编辑 | 弹窗或内嵌 | 新增订单 → 表单弹窗 |
| 删除 | 确认后留在原处 | 删除后留在列表 |
| 跨模块跳转 | 保留面包屑 | 从客户跳转订单 |

### 4.5 渐进式暴露原则（Progressive Exposure）

**核心规则**：根据用户角色和使用频率，分层展示导航项

**分层策略**：
```
Level 1（默认展示）：核心高频功能
Level 2（折叠展开）：常用但非核心功能
Level 3（搜索/命令面板）：长尾功能
Level 4（管理后台可见）：管理员专属
```

**实现示例**：
```javascript
const navConfig = {
  level: 1,  // 默认展示
  expandable: true,  // 可折叠
  minRole: 'user',   // 最小权限
  frequency: 'high'  // 使用频率标记
};
```

## 六、导航的技术实现

### 5.1 路由层设计

**核心要求**：路由即状态，URL 是导航记忆的载体

```java
// RESTful 路由设计
GET    /api/orders              → 订单列表
GET    /api/orders/{id}         → 订单详情
POST   /api/orders               → 创建订单
PUT    /api/orders/{id}         → 更新订单
DELETE /api/orders/{id}         → 删除订单

// 带有上下文的路由
GET    /api/customers/{cid}/orders           → 某客户下的订单
GET    /api/orders/{id}/items                → 某订单下的商品
GET    /api/orders/{id}/payments/{pid}/refund → 退款详情

// 查询参数的导航状态
GET /api/orders?status=pending&page=2&sort=createdAt,desc
```

### 5.2 导航配置驱动化

**原则**：导航结构应从代码中抽离为配置，便于动态调整

```yaml
# navigation-config.yaml
navigation:
  - id: "customer"
    label: "客户管理"
    icon: "team"
    path: "/customer"
    children:
      - id: "customer-list"
        label: "客户列表"
        path: "/customer/list"
        aggregate: "Customer"
      - id: "customer-group"
        label: "客户分组"
        path: "/customer/group"
        aggregate: "CustomerGroup"
```

### 5.3 权限驱动的导航过滤

**流程**：
```
用户登录
  → 获取角色列表
  → 查询导航权限矩阵
  → 过滤导航树
  → 渲染可用导航
```

```java
class NavigationPermissionFilter {
    public List<NavigationNode> filterByPermission(
            List<NavigationNode> allNodes,
            UserRole role) {

        return allNodes.stream()
            .filter(node -> permissionService.hasAccess(role, node))
            .peek(node -> {
                // 递归过滤子节点
                if (node.hasChildren()) {
                    node.setChildren(filterByPermission(node.getChildren(), role));
                }
            })
            .collect(Collectors.toList());
    }
}
```

### 5.3 导航上下文传递机制

跨页面跳转时，上下文（筛选条件、选中实体、来源路径）的传递方式决定了用户体验的连贯性。

**URL 状态 vs 内存状态的选择**：

| 状态类型 | 存储方式 | 优点 | 缺点 | 典型场景 |
|---------|---------|------|------|---------|
| 路由参数 | URL path/query | 可分享、可刷新后恢复 | URL 过长、安全敏感数据 | 列表筛选条件、详情 ID |
| 路由状态 | Router store（内存） | 灵活、无限复杂度 | 刷新丢失、跨标签页不同步 | Tab 激活状态、展开折叠 |
| 持久状态 | LocalStorage / 后端 | 跨会话保留 | 同步复杂度、存储限制 | 用户偏好、收藏、最近访问 |
| 上下文对象 | 导航 API 传递 | 类型安全、无 URL 暴露 | 刷新丢失、调试困难 | 详情页的关联实体、临时计算结果 |

**上下文传递的四种模式**：

- **模式 A：Query String 传递** — 将上下文编码为 URL 参数，适合筛选条件、分页等可序列化的状态。
  - 示例：`/orders?status=pending&customerId=123&page=1`

- **模式 B：Router Store（内存）** — 将上下文存在路由管理器的内存 store 中，适合临时状态。刷新页面会丢失。
  - 示例：Vue Router `router.push({ path, query, state: { from: 'order-list' } })`

- **模式 C：Navigation Context API** — React Router / TanStack Router 等框架提供的上下文传递机制，类型安全且可调试。
  - 示例：`<Link to="/orders" state={{ customerId: 123 }}>`

- **模式 D：全局状态管理器** — 将上下文放在 Redux / Pinia / Zustand 等全局 store 中，适合跨多个页面共享的上下文。
  - 示例：Pinia `navigationStore.setContext('currentCustomer', customer)`

> **最佳实践**：优先使用 URL 状态（模式 A/C）传递可序列化的上下文，刷新后自动恢复，体验最接近用户预期。只在必要时使用内存状态，避免上下文丢失。

### 5.4 导航状态的持久化

**需要持久化的状态**：
- 最近访问的页面（Recent）
- 收藏的页面（Favorites）
- 侧边栏折叠状态
- Tab 切换位置
- 列表筛选条件（可选）

**存储策略**：
| 状态类型 | 存储位置 | 过期策略 |
|---------|---------|---------|
| 最近访问 | LocalStorage + 后端同步 | 保留 20 条 |
| 收藏页面 | 后端用户配置 | 永久 |
| UI 状态 | LocalStorage | 清缓存时丢失 |
| 列表状态 | URL 参数 | 分享链接时生效 |

### 5.5 主流 ERP 厂商导航设计对照

各 ERP 厂商的导航设计体现了不同的产品哲学和历史演进路径。下表从导航风格、一级入口、二级导航、特色四个维度进行对照：

| 厂商 | 导航风格 | 一级入口 | 二级导航 | 特色 |
|------|---------|---------|---------|------|
| **SAP S/4HANA** | 扁平化 + 命令优先 | 顶栏 + 全局搜索 (SAP Fiori) | Facet Filter 筛选侧边栏 | 角色首页（角色化配置）、搜索即导航、设计语言统一（Fiori） |
| **用友 NC/NCC** | 树形 + 菜单驱动 | 左侧功能树 | 右键菜单 + 弹出面板 | 按业务线分组、菜单树层级深、功能密度高、适合 power user |
| **金蝶云星空** | 桌面式 + 图标化 | 左侧图标模块（宽面板） | 展开子菜单 + Tab 页签 | 轻量化、按角色推荐入口、多端适配（桌面/移动）、云原生 |
| **Oracle EBS** | 经典菜单 + 可配置 | 顶栏超链接导航 | 标签页 + 表单嵌套 | 高度可配置、学习曲线陡、适合复杂流程定制、功能成熟稳定 |
| **鼎捷 / 管家婆** | 极简工具栏 | 顶部图标工具栏 | 下拉菜单 | 密集操作型（适合老用户）、轻量、部署简单、快速上手 |

> **设计哲学的分化**：
> - **命令优先型**（SAP、金蝶）：以搜索和角色首页为核心，降低菜单层级深度，适合不熟悉系统的用户快速定位功能。
> - **菜单树型**（用友、Oracle EBS）：层级深、功能全，适合 power user 和复杂业务流程，但初期学习成本高。
> - **工具栏型**（鼎捷/管家婆）：极简 UI，密集操作，适合业务单一、操作频繁的中小企业场景。

**原型 1：SAP S/4HANA — 扁平化 + 命令优先（Fiori 风格）**

- **顶栏**：白色背景卡片风格，蓝色 Logo 标识 + 胶囊式 Tab 导航
- **搜索框**：居中、圆角、灰色填充、放大镜图标 + 占位提示文字
- **角色首页**：浅灰背景 + 白色卡片 Tile（KPI 数字 + 图标 + 副标题），三列网格布局
- **最近访问**：白色卡片内嵌蓝色链接 + 时间戳
- **快捷操作**：蓝色主操作按钮 + 白色边框次级按钮

**原型 2：用友 NC/NCC — 树形 + 菜单驱动**

- **窗口框架**：Windows 风格标题栏（蓝底渐变 + 窗口控制按钮）
- **左侧树**：浅灰背景 + 目录/文件图标 + 选中高亮（蓝色左边框 + 浅蓝背景）
- **右侧内容**：深色下划线标题 + 工具栏按钮 + 斑马纹数据表格
- **风格关键词**：深蓝强调色、层级缩进、传统企业软件质感

**原型 3：金蝶云星空 — 桌面式 + 图标化**

- **左侧图标栏**：深蓝背景 + 白色图标圆角块，选中态有蓝色边框
- **二级菜单**：浅蓝背景 + 蓝色左边框标题 + 纯文字菜单项
- **Tab 页签**：下划线样式，激活态蓝色粗体
- **工具栏**：蓝色主按钮 + 白底边框次级按钮
- **数据区**：浅灰背景卡片

**原型 4：Oracle EBS — 经典菜单 + 可配置**

- **顶栏**：深蓝渐变背景 + 白色标题 + 蓝色职责标签
- **菜单栏**：深蓝背景 + 浅蓝文字，hover 变深蓝
- **工具按钮**：XP/Win32 风格（灰白渐变背景 + 立体边框 + 图标+文字）
- **表单区**：灰色边框 + 标签粗体 + 浅蓝表头 + 蓝底标题栏
- **风格关键词**：20年老牌 ERP、密集表单、Windows 原生控件风格

**原型 5：鼎捷 / 管家婆 — 极简工具栏**

- **顶部工具栏**：深灰背景 + 白色文字，当前模块蓝色高亮
- **快捷键标注**：右侧深灰小标签（F2/F3/F4），面向熟练操作员
- **筛选栏**：浅灰背景 + 紧凑的日期/下拉控件 + 蓝色查询按钮
- **数据表格**：无多余装饰、紧凑行高、状态徽章（绿/黄）、选中行浅蓝高亮
- **风格关键词**：密集操作、效率优先、工具栏即全部

## 七、典型场景导航设计

### 场景 1：SaaS 管理后台

**特征**：模块多、层级深、角色复杂

**导航架构**：
```
┌────────────────────────────────────────────────────────────┐
│ Logo │ 首页 │ 客户 │ 订单 │ 商品 │ 库存 │ 报表 │ 设置    │
├──────────┬─────────────────────────────────────────────────┤
│ 快捷入口  │                                                 │
│ 最近访问  │  内容区                                          │
│ ──────  │                                                 │
│ 客户列表  │                                                 │
│ 紧急待办  │                                                 │
└──────────┴─────────────────────────────────────────────────┘
```

**设计要点**：
- 一级导航 ≤ 7 个（遵循 7±2 法则）
- 二级导航通过侧边栏或 Tab 展开
- 右上角统一搜索覆盖全站
- 「首页」或「仪表盘」作为默认落地页

### 场景 2：业务流程型应用（CRM/ERP）

**特征**：以实体为中心，强调操作连贯性

**导航架构**：
```
以「客户」聚合根为中心：

客户列表 ←→ 客户详情
               ├── 基本信息 Tab
               ├── 跟进记录 Tab
               ├── 订单历史 Tab
               ├── 合同文档 Tab
               └── 操作面板（右侧抽屉）
```

**设计要点**：
- 详情页内 Tab 承载子实体
- 右侧抽屉承载即时操作
- 「新建」操作统一入口
- 列表页支持行内快捷操作

### 场景 3：数据可视化平台

**特征**：多视图切换，强调数据探索

**导航架构**：
```
┌────────────────────────────────────────────────────────┐
│ [仪表盘] [明细数据] [报表] [设置]                       │
├────────────────────────────────────────────────────────┤
│ 仪表盘切换 ▼ │ 时间范围 ▼ │ 刷新 ↻ │ 导出 ▼ │ 分享 🔗 │
├────────────────────────────────────────────────────────┤
│                                                        │
│   图表1    │    图表2    │    图表3                   │
│            │             │                            │
│   图表4    │    图表5    │    图表6                   │
│            │             │                            │
└────────────────────────────────────────────────────────┘
```

**设计要点**：
- 视图切换通过 Tab 或下拉
- 全局筛选器（时间、维度）固定在顶部
- 图表间支持钻取联动
- 支持全屏和自定义布局

### 场景 4：配置型系统

**特征**：树形层级、多级配置、分组管理

**导航架构**：
```
┌─────────────────────────────────────────────────────────┐
│  [返回]  系统配置                                       │
├───────────────┬─────────────────────────────────────────┤
│ ▾ 基础配置    │                                         │
│   ▸ 租户设置  │   配置项表单 / 表格                      │
│   ▸ 权限配置  │                                         │
│ ▾ 业务配置    │                                         │
│   ▸ 订单流程  │                                         │
│   ▸ 支付渠道  │                                         │
└───────────────┴─────────────────────────────────────────┘
        树形导航              内容区
```

**设计要点**：
- 左侧树形导航承载层级
- 右侧内容区承载配置表单
- 支持拖拽排序
- 配置变更需发布/生效流程

### 场景 5：大型 ERP 系统导航模式深度分析

ERP（Enterprise Resource Planning）系统是信息系统导航复杂度最高的应用类型之一——模块众多（20-100+）、层级深（3-5 层）、角色差异大（管理员/财务/仓库/销售）、数据关联复杂（上下游单据）。理解 ERP 的导航设计，是理解所有复杂信息系统导航的范式参考。

#### 5.1 ERP 导航复杂度来源

ERP 导航比普通 SaaS 复杂，根本原因在于**业务纵深与组织宽度同时存在**：

| 复杂度维度 | ERP 表现 | 普通 SaaS 对比 |
|-----------|---------|--------------|
| **模块数量** | 20-100+ 个功能模块 | 通常 ≤20 个 |
| **层级深度** | 3-5 层（系统→模块→单据类型→单据→操作） | 通常 ≤3 层 |
| **角色差异** | 10+ 种岗位角色，同一界面不同权限 | 通常 2-3 种角色 |
| **数据关联** | 上游单据→下游单据，树状/网状依赖 | 通常线性 |
| **操作密度** | 批处理、审核流、跨模块操作 | 通常单模块操作 |

#### 5.2 典型 ERP 导航架构

以用友 NC/SAP S/4HANA/金蝶云星空为参考，ERP 导航通常采用**混合模式**：

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：系统名称 │ 全局搜索 │ 消息 │ 切换组织/账套 │ 用户菜单  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ┌────────────┐  ┌──────────────────────────────────────┐  │
│  │            │  │ 面包屑：财务 → 总账 → 凭证管理 → 新增  │  │
│  │ 左侧模块树  │  ├──────────────────────────────────────┤  │
│  │            │  │ Tab：凭证列表 │ 凭证审核 │ 期末处理   │  │
│  │ ▸ 财务会计  │  ├──────────────────────────────────────┤  │
│  │   ▸ 总账    │  │                                      │  │
│  │   ▸ 应收    │  │  表单/列表内容区                     │  │
│  │   ▸ 应付    │  │                                      │  │
│  │ ▸ 供应链    │  │                                      │  │
│  │ ▸ 生产制造  │  │                                      │  │
│  │ ▸ 人力资源  │  ├──────────────────────────────────────┤  │
│  │ ▸ 客户关系  │  │ 底部：快捷操作栏（新增/保存/审批/打印）│  │
│  └────────────┘  └──────────────────────────────────────┘  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**五层导航体系**：

| 层级 | 导航组件 | 对应业务深度 |
|------|---------|------------|
| **一层（全局）** | 顶栏 | 系统级操作：切换组织、搜索、消息、用户 |
| **二层（领域）** | 左侧模块树 | 业务域：财务会计、供应链、生产制造 |
| **三层（单据）** | 树中展开的菜单 | 单据类型：总账→凭证、应收→应收单 |
| **四层（页面）** | Tab 切换 / 内嵌子导航 | 单据生命周期：列表/新增/审核 |
| **五层（操作）** | 快捷操作栏 + 工具栏 | 行级操作：编辑/删除/打印/审批 |

#### 5.3 主流 ERP 导航模式对比

| 厂商 | 导航风格 | 一级入口形态 | 二级导航 | 特色 |
|------|---------|------------|---------|------|
| **SAP S/4HANA** | 扁平化 + 命令优先 | 顶栏 + 全局搜索（SAP Fiori） | 左键菜单 + Facet Filter | 角色首页（Role-Based Launchpad）、智能搜索 |
| **用友 NC/NCC** | 树形 + 菜单 | 左侧功能树（可折叠） | 右键菜单 / 双击进入 | 传统树形导航，按业务线分组 |
| **金蝶云星空** | 桌面式 | 左侧图标模块（宽） | 展开子菜单 + Tab | 轻量化，按角色推荐入口 |
| **Oracle EBS** | 经典菜单 | 顶栏超链接菜单 | 标签页 + 表单 | 高度可配置，功能全面但学习曲线陡 |
| **鼎捷/管家婆** | 极简工具栏 | 顶部图标工具栏 | 下拉菜单 | 密集操作型，适合老用户 |

#### 5.4 ERP 导航的核心矛盾与解法

**矛盾一：模块多 vs 界面简洁**

ERP 动辄几十个模块，全部展示在一级导航不现实，但收起来又难以发现。

解法：
- **角色首页**（SAP Fiori Launchpad）：每个角色有专属首页，只显示与其相关的模块入口
- **渐进式发现**：搜索优先，通过全局搜索覆盖 80% 的导航需求
- **收藏/常用**：支持用户将高频功能加入快捷入口（如 ERP 首页仪表盘）

```
ERP 首页仪表盘：
┌────────────────────────────────────────────────────────┐
│  [我的工作台]                        🔔3  👤 张三 ▼  │
├────────────────────────────────────────────────────────┤
│                                                        │
│  ⭐ 快捷入口（用户自定义）                              │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐       │
│  │采购订单│ │付款申请│ │费用报销│ │合同审批│ │...   │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘       │
│                                                        │
│  📋 待办事项                                            │
│  · 待审核采购订单（3）                                  │
│  · 待付款费用单（1）                                    │
│  · 待签收入库单（5）                                    │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**矛盾二：层级深 vs 操作效率**

ERP 单据操作路径深：选模块 → 选单据类型 → 列表页 → 打开单据 → 编辑 → 保存。熟练用户抱怨效率低。

解法：
- **快捷键覆盖全流程**（参考 SAP GUI 快捷键体系）
- **快速创建**（Quick Create）：在任何页面通过 `Ctrl+N` 呼出上下文相关的创建表单
- **单据穿透**：双击列表行直接打开详情，不需要额外的「查看」按钮
- **批处理**：列表页支持批量选择、批量审核、批量打印

**矛盾三：权限复杂 vs 体验一致**

同一张单据，财务看到「记账」按钮，仓库看到「入库」按钮，销售看不到任何按钮。同一界面不同角色看到完全不同的功能。

解法：
- **功能级权限控制**：按钮级可见性控制（隐藏/禁用/只读）
- **Tab 级权限**：角色 A 看不到某个 Tab，角色 B 只能看不能编辑
- **权限引导**：无权限时显示占位符并提示「请联系管理员开通」，而非留白或报错

**矛盾四：数据关联深 vs 上下文丢失**

从采购订单点进去，关联到供应商、库存、财务凭证，跨了 3 个模块。用户在操作中切换模块后，容易忘记原始上下文。

解法：
- **父子单据链**：详情页顶部显示「上游单据 → 当前单据 → 下游单据」关联链
- **右侧抽屉（Side Panel）**：在不离开当前页面的情况下查看关联信息
- **多标签页**：新窗口打开关联单据，保留当前工作上下文

```
关联链示例（采购订单详情页）：
上游：供应商「华强电子」→ 采购申请单 #PR-2024-001
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
当前：采购订单 #PO-2024-089  【待审核】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
下游：入库单 #RK-2024-015（待入库）→ 应付单 #YF-2024-007（待生成）
```

#### 5.5 ERP 导航的技术实现要点

| 技术要点 | 说明 |
|---------|------|
| **路由设计** | ERP 路由通常携带多级上下文：`/finance/gl/voucher/:id/edit`，需要深层路由支持 |
| **权限中间件** | 每个路由/按钮注册权限点，菜单由权限数据动态渲染 |
| **状态持久化** | 列表页的筛选条件、分页状态应持久化到 URL 或 LocalStorage |
| **多标签页** | ERP 通常需要同时打开多个单据，需要 Tab 组管理（类似浏览器多 Tab） |
| **操作拦截** | 离开页面时检查表单是否修改，弹出确认提示 |
| **操作日志** | ERP 操作需审计，每个操作记录操作人、时间、操作内容、修改前后值 |

## 八、导航设计的常见反模式

### 反模式 1：迷宫导航

**问题**：层级过深，用户找不到回去的路

```
❌ 四级导航还在隐藏
设置 → 高级设置 → 开发者选项 → 调试模式 → 启用日志
```

### 反模式 2：标签云导航

**问题**：功能堆砌，没有层级，用户不知道从哪里开始

```
❌ 顶栏 20 个标签，无分组，无优先级
首页 | 功能A | 功能B | 功能C | ... | 功能Z
```

### 反模式 3：隐形导航

**问题**：重要功能藏在右键、悬浮、快捷键中，新用户完全看不到

### 反模式 4：双重地狱（Double Navigation）

**问题**：两套导航系统并存，用户不知道该用哪一套

```
❌ 侧边栏菜单 + 顶部 Tab 切换 + 页面内面包屑
三种导航指向不同层级，用户需要三套心智模型
```

### 反模式 5：上下文丢失

**问题**：跳转后丢失来源上下文，无法返回原状态

```
❌ 从列表点详情，编辑后保存返回，筛选条件和页码全丢了
```

## 九、导航评估 Checklist

### 评分体系说明

- **✅ 通过（绿色）**：满足标准，无需改进
- **❌ 不通过（红色）**：存在严重问题，需立即修复
- **⚠️ 需评估（橙色）**：具体情况具体分析，可能需要权衡利弊后决策

设计评审导航时，逐项检查：

| 检查项 | 阈值 | 问题 | 修复建议 | 优先级 |
|-------|------|-----|---------|--------|
| 一级导航项数量 | **≤ 7** | 过多导致认知过载 | 按业务域分组，核心功能提升到一级 | P0 |
| 最长导航路径深度 | **≤ 3 跳** | 过深难以返回、迷失率高 | 扁平化、三级以内功能并入抽屉或 Tab | P0 |
| 搜索功能覆盖率 | **≥ 80%** | 功能不可发现 | 补充搜索索引，覆盖核心实体和操作 | P1 |
| 导航项可发现率 | **≥ 90%** | 存在孤岛页面 | 检查导航树完整性，确保所有页面有入口 | P1 |
| 返回操作符合预期 | **100%** | 用户迷路、丢失上下文 | 验证浏览器后退 / 面包屑 / 导航菜单的一致性 | P0 |
| 权限过滤正确性 | **100%** | 未授权用户看到入口 | 前端菜单 + 后端路由双重鉴权，测试各角色权限 | P0 |
| 移动端适配合理 | **功能无缺失** | 功能不可用或体验差 | Bottom Tab / Drawer 替代侧边栏，核心操作保留 | P1 |
| 页面加载时间 | **≤ 1.5s** | 导航响应慢 | 懒加载非首屏菜单，骨架屏优化感知速度 | P1 |
| 导航状态可分享 | **核心页面** | 分享链接后状态丢失 | 列表筛选 / 排序条件编码进 URL | P2 |

**评分方法**：P0 项全部通过得 60% 基础分；每通过一个 P1 项 +8%，每通过一个 P2 项 +4%。总分 ≥ 80% 为合格，≥ 95% 为优秀。

## 十、导航设计体现了什么

导航设计的本质，是将**信息架构**、**用户心智模型**、**业务语义**三重约束投影到可见界面中的过程。

### 10.1 体现了信息架构

导航是对内容/功能的**分类体系**。它反映了设计者如何理解「这个系统中，什么和什么是同类的，什么和什么是不同的」。

- **分类即认知**：把订单和商品放在不同模块，说明它们是不同的领域概念
- **层级即包含关系**：Tab 是同一聚合根内的不同视角，侧边栏是一级业务域
- **分类的粒度就是系统的复杂度**：导航越深，说明系统认为这些功能是不同层级的

**导航是一张语义地图**，用户在导航中形成的印象，就是对整个产品结构的认知。

### 9.2 体现了用户心智模型

好的导航遵循用户的**已有认知**，而不是强迫用户学习新的分类体系。

| 设计选择 | 体现的心智假设 |
|---------|--------------|
| 把「报表」放在顶栏 | 用户认为报表是独立功能 |
| 把「报表」放在「订单」下 | 用户认为报表是订单分析的子功能 |
| 搜索框覆盖全站 | 用户习惯用搜索找东西 |
| 命令面板（Ctrl+K） | 用户习惯键盘操作 |

**导航是对用户心智的猜测和引导**。如果导航结构与用户预期不符，用户就会「迷路」——这不是用户的问题，是导航设计没有正确反映业务语义。

### 9.3 体现了权力与职责的分配

导航是**权限体系的可视化**。用户能看到什么入口，就代表他有什么权限。

```
├─ 客户管理          （销售可见）
├─ 报表分析          （经理可见）
├─ 系统设置          （管理员可见）
└─ 财务对账          （财务可见）
```

- 导航栏中不出现某个模块 = 用户无权访问（而非功能不存在）
- 导航栏中灰掉的选项 = 权限不足但功能存在
- 不同角色看到不同导航 = 系统在主动告知用户「你的职责范围在这里」

**导航是一张权限地图**，它无声地告诉用户：你在这个系统中的角色是什么。

### 9.4 体现了工作流与任务的抽象

导航的排列顺序和分组方式，反映了设计者对**用户完成任务路径**的理解。

**以电商后台为例**：
```
客户 → 下单 → 支付 → 发货 → 评价 → 统计
```

如果导航顺序是「客户 - 订单 - 物流 - 报表」，说明设计者认为用户的核心路径是：先处理客户相关事务，再处理交易流程，最后看数据。

如果顺序是「报表 - 订单 - 客户 - 物流」，说明设计者认为管理层的第一入口是数据，而不是事务。

**导航顺序是一种隐性的流程假设**。它告诉用户：「按这个顺序使用系统，是最顺畅的。」

### 9.5 体现了复杂度的分层管理

导航是**复杂度分层的可视化工具**。它用层级结构将大量功能压缩到可接受的认知范围内。

```
展示给用户的：7 ± 2 个一级入口
隐藏的复杂度：每个入口背后可能是几十个页面

顶栏：客户 | 订单 | 商品 | 库存 | 报表 | 设置
实际功能：
  客户 → 客户列表 | 客户分组 | 客户标签 | 客户导入 | 黑名单 | ...
  订单 → 待支付 | 待发货 | 已发货 | 已完成 | 已取消 | ...
```

- **导航层级 = 复杂度的分层策略**：每深入一层，系统复杂度就增加一个量级
- **折叠/展开 = 复杂度的按需暴露**：不在第一屏展示全部，只在需要时展开
- **搜索/命令面板 = 复杂度的扁平化索引**：用搜索绕过层级，直接定位功能

**导航设计是一种复杂度控制哲学**：不是把所有功能堆在用户面前，而是分层、按需、可探索地呈现。

### 9.6 体现了聚合根边界的空间表达

导航在空间上的组织方式，本质上是**领域模型的物理投影**。

```
侧边栏布局（常见的 SaaS 形态）：
┌────────────────────────────────────────────────┐
│ 业务域 A（侧边栏）                              │
│   ├─ 聚合根 A1（Tab 或子页面）                  │
│   └─ 聚合根 A2                                 │
│                                                │
│ 业务域 B                                        │
│   ├─ 聚合根 B1                                 │
│   └─ 聚合根 B2                                 │
└────────────────────────────────────────────────┘
```

- **同侧边栏内跳转**：同一业务域内的操作，保留上下文
- **跨侧边栏跳转**：跨业务域的操作，上下文切换
- **详情页 Tab**：同一聚合根内的不同视角，状态共享

**导航的空间布局，就是领域模型的空间布局**。当用户说「我找不到」时，往往是导航结构没有正确反映业务边界。

### 9.7 本质总结

| 本质 | 回答 |
|-----|------|
| 体现了信息架构 | 如何分类和分组信息 |
| 体现了心智模型 | 如何符合用户已有认知 |
| 体现了权限体系 | 谁能看到什么、能做什么 |
| 体现了工作流 | 什么顺序是最合理的 |
| 体现了复杂度策略 | 如何分层控制认知负担 |
| 体现了领域模型 | 业务边界如何在空间上表达 |

**最终，导航设计体现了设计者对「用户如何在复杂系统中完成任务」的理解深度。** 导航不是功能的索引表，而是业务语义和用户体验之间的翻译层。

## 十一、UI 是一棵聚合根树

### 10.1 核心认识

信息系统的 UI，本质上是一棵**随用户角色动态剪枝的聚合根树**。导航就是在这棵树上：

- **横向跳转**：同一层级的分支之间切换
- **纵向深入**：沿树干从根向叶节点深入

```
普通树 vs UI 树的区别：

普通树（静态、整齐）：
根
├── 节点 A
├── 节点 B
└── 节点 C

UI 树（动态、不均匀、有状态）：
根（仪表盘 / 客户列表 / 项目根）
├── 节点 A（客户管理）—— 大节点：50 个字段、10 个 Tab
│   ├── 客户列表
│   └── 客户分组
├── 节点 B（订单管理）—— 中节点
│   ├── 待支付
│   └── 已发货
└── 节点 C（系统设置）—— 某些用户看不到（剪枝）
```

### 10.2 两种运动的本质

```
横向跳转（同一层级）：
  客户列表 → 订单列表
  
  含义：用户换了一个业务域，脑子里需要重新建立上下文。
  成本：上下文切换的认知损耗。

纵向深入（沿树干）：
  订单列表 → 订单详情 → 订单明细
  
  含义：用户沿着一条线往下走，任务越来越具体。
  成本：层级越深，返回路径越长。
```

### 10.3 这棵树的三个特征

**特征 1：节点大小不一**

同一棵树上的节点，复杂度差异巨大：

| 节点 | 实际复杂度 |
|-----|----------|
| 开关切换 | 1 个字段，2 个选项 |
| 客户详情页 | 50+ 字段、10 个 Tab、5 个关联列表 |

**特征 2：节点类型不同**

| 类型 | 行为 |
|-----|-----|
| 叶子节点 | 执行具体操作（新建、删除、导出） |
| 容器节点 | 承载子级（列表页、详情页） |
| 聚合节点 | 汇总统计（仪表盘、数据面板） |

**特征 3：节点有状态**

- **当前节点**：高亮显示
- **路径节点**：记住来路
- **兄弟节点**：可跳转
- **剪枝节点**：权限过滤后隐藏

### 10.4 树的根是什么

不同系统的根不一样：

| 系统类型 | 根节点 | 设计含义 |
|---------|--------|---------|
| 电商后台 | 仪表盘 / 首页 | 数据驱动，先看全局 |
| CRM | 客户列表 | 资产优先，核心是客户 |
| ERP | 多根并行 | 财务根、供应链根、人力根并列 |
| IDE | 文件树 / 项目根 | 开发者视角，以文件为中心 |
| 操作系统 | 桌面 / 开始菜单 | 以应用为单位 |

**根 = 用户的第一入口 = 系统认为最重要的东西**

### 10.5 树的结构决定了什么

```
树的深度  →  用户完成任务需要多少步
树的广度  →  用户面对多少选择（认知负担）
分支的分组 →  用户对业务边界的理解
节点的一致性 → 用户能否预测操作结果
剪枝策略（权限）→ 用户感受到的角色边界
```

### 10.6 动态剪枝示例

同一棵树，在不同用户角色下，分支不同：

```
系统完整结构（设计者视角）：
根
├── 客户管理
│   ├── 客户列表
│   ├── 客户分组
│   ├── 客户标签
│   └── 黑名单
├── 订单管理
│   ├── 待支付
│   ├── 已发货
│   └── 已完成
├── 系统设置
└── ...

销售角色看到的树（剪枝后）：
根
├── 客户管理
│   ├── 客户列表
│   └── 客户标签
├── 订单管理
│   └── 待支付
（系统设置完全消失）
```

## 十二、总结

导航设计的核心思想：
1. **层级克制**：层级越浅越好，过深的层级是架构问题
2. **上下文感知**：导航行为应理解用户的当前位置和任务
3. **聚合根中心**：以业务实体为中心组织导航，而非以功能为中心
4. **配置驱动**：导航结构应与代码分离，支持动态调整
5. **权限一致**：导航展示与实际操作权限必须一致
6. **渐进暴露**：根据用户角色和场景逐步展示功能

最终，导航是用户体验的「脊椎」——用户通过导航理解产品结构，通过导航完成任务。好的导航让用户忘记导航的存在，专注于业务目标。

**一句话总结：信息系统的 UI，是一棵随用户角色动态剪枝的聚合根树，导航就是在这棵树上横向切换分支、纵向深入叶节点。**
