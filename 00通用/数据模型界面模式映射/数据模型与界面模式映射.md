# 数据模型与界面模式映射

## 文档概述

本文档系统阐述数据模型（Data Model）到用户界面（UI）的多层次映射关系。内容覆盖六个映射层次、领域驱动设计中的聚合根边界、命令查询职责分离（CQRS）模式、后端为前端服务（BFF）架构，以及这些概念如何共同指导界面设计决策。

映射的核心目标是：**建立从业务语义到界面表现的可追溯链路**，确保：
1. 界面呈现的数据有明确的模型来源
2. 用户操作能够映射到正确的领域行为
3. 读写路径分离，界面只暴露必要的复杂度

---

## 一、六个映射层次概览

数据模型到界面的映射并非一层直译，而是经历六个语义层次的理解与转换：

### 层次 1：结构映射（Structure Mapping）

**定义**：将数据模型的实体结构映射为界面的基本组织单元。

**映射关系**：
| 数据模型 | 界面表现 |
|---------|---------|
| 实体（Entity） | 卡片、列表项、详情页 |
| 值对象（Value Object） | 标签、徽章、格式化文本 |
| 实体属性 | 表单字段、详情行 |
| 关联关系 | 跳转链接、展开面板、Tab 切换 |

**示例**：CRM 系统中「客户」实体映射为客户列表页的卡片组件，每个卡片展示客户名称、行业等核心属性。

### 层次 2：交互映射（Interaction Mapping）

**定义**：将领域行为（命令操作）映射为用户可执行的界面动作。

**映射关系**：
| 领域行为 | 界面交互 |
|---------|---------|
| 创建实体 | 「新增」按钮 → 创建表单弹窗 |
| 修改属性 | 行内编辑 / 详情页编辑模式 |
| 删除实体 | 删除确认 → 列表项消失 |
| 状态流转 | 审批按钮、工作流状态选择器 |
| 聚合根内子实体操作 | 子列表的操作列、批量操作 |

**关键约束**：界面交互必须经过领域服务验证，UI 层不能自行决定业务规则的执行。

### 层次 3：聚合根映射（Aggregate Root Mapping）

**定义**：以聚合根为边界，决定界面的导航结构和事务范围。

**核心原则**：
- **聚合根 = 导航终点**：用户进入一个界面，通常对应到一个聚合根
- **聚合根 = 事务边界**：对聚合根内所有实体的修改，应在同一事务内完成
- **聚合根 = 加载单元**：界面数据按聚合根粒度加载，避免 N+1 查询

**示例**：
- 订单（Order）是聚合根 → 订单详情页展示订单主信息 + 订单明细列表 + 支付记录
- 客户（Customer）是聚合根 → 客户详情页展示客户档案 + 关联订单 + 跟进记录

### 层次 4：聚合映射（Aggregation Mapping）

**定义**：将领域模型中的聚合逻辑映射为界面的数据聚合展示。

**映射类型**：
1. **横向聚合**：同一层级多个实体的汇总展示
   - 客户列表的「客户总数」「高价值客户数」→ 聚合根级别的统计
   
2. **纵向聚合**：父子层级的数据钻取
   - 订单详情 → 订单明细 → 商品批次 → 批次详情
   
3. **时间聚合**：基于时间维度的数据切片
   - 销售报表 → 日/周/月/年切换 → 趋势图

### 层次 5：投影映射（Projection Mapping）

**定义**：同一数据模型的不同读模型（Projection/Read Model），根据界面场景选择最优展示方式。

**投影决策矩阵**：
| 场景 | 读模型选择 | 投影策略 |
|-----|-----------|---------|
| 列表页 | 扁平化 DTO | 去除关联，仅展示主字段 |
| 详情页 | 完整实体 | 保留所有关联，支持钻取 |
| 统计面板 | 聚合结果 | 预计算的计数/求和/平均值 |
| 导出场景 | 业务完整模型 | 包含所有业务字段 |

### 层次 6：权限映射（Permission Mapping）

**定义**：将数据模型的权限粒度映射为界面的可见性与可操作性。

**映射关系**：
| 权限模型 | 界面表现 |
|---------|---------|
| 字段级权限 | 表单项隐藏/只读/可编辑 |
| 记录级权限 | 整行/卡片隐藏 |
| 功能级权限 | 按钮/菜单项显示/隐藏 |
| 数据范围权限 | 列表数据过滤 |

## 二、聚合根边界的界面导航意义

### 2.1 聚合根作为导航单元

在领域驱动设计（DDD）中，**聚合根（Aggregate Root）** 是领域模型的核心组织单位。每个聚合根拥有独立的生命周期和一致性边界。

**界面导航的映射规则**：
- 聚合根 → 详情页（用户进入的最终页面）
- 聚合根内的实体 → 详情页的子区域（Tab、展开面板、关联列表）
- 聚合根之间的关系 → 页面间跳转（导航链接、返回操作）

### 2.2 典型聚合根导航示例

**订单聚合根**：
```
Order (聚合根)
├── OrderItem[] (子实体)
├── Payment[] (子实体)
└── Logistics (子实体)

界面导航：
订单列表页 → 订单详情页
            ├── 基本信息 Tab
            ├── 商品明细 Tab
            ├── 支付记录 Tab
            └── 物流信息 Tab
```

### 2.3 事务边界与界面提交

**规则**：对同一聚合根的多个修改，应在同一事务内提交；跨聚合根的修改，通过消息或补偿机制处理。

**界面体现**：
- 单个表单内的所有字段变更 → 一次性提交
- 跨 Tab 的修改 → 统一保存按钮，或分步保存后统一发布
- 跨聚合根的操作 → 提示用户分步执行（如：订单创建后自动触发库存扣减）

## 三、CQRS 模式与界面

### 3.1 CQRS 核心概念

**命令查询职责分离（Command Query Responsibility Segregation）** 是一种架构模式，将系统的读操作和写操作完全分离。

| 维度 | 命令（Command） | 查询（Query） |
|-----|----------------|---------------|
| 目的 | 改变系统状态 | 获取系统状态 |
| 返回 | 操作结果（成功/失败） | 数据模型 |
| 约束 | 可变、幂等性可选 | 幂等、不改变状态 |
| 优化 | 写入性能、校验逻辑 | 读取性能、缓存策略 |

### 3.2 CQRS 在界面层的应用

#### 读模型（Read Model）

界面展示的数据模型是 CQRS 中「查询」视角的产物：

1. **专用读模型**：根据界面场景定制的 DTO
   - 列表页用扁平化 DTO（避免关联查询）
   - 统计页用预聚合数据

2. **读写模型分离示例**：
   ```
   // 写模型（命令侧）
   class Order {
       private List<OrderItem> items;
       private Money totalAmount;
       private OrderStatus status;
       
       public void addItem(Product product, int quantity) { ... }
       public void confirm() { ... }
   }
   
   // 读模型（查询侧）
   class OrderListVO {
       private String orderNo;
       private String customerName;
       private String statusText;  // 状态的中文描述
       private String totalAmountFormatted;  // 格式化后的金额
       private int itemCount;  // 商品数量
   }
   ```

#### 命令侧与界面的交互

1. **表单提交**：用户的增删改操作 → Command（命令）
2. **命令验证**：前端做基础校验，后端做业务规则校验
3. **命令处理**：领域服务执行业务逻辑，变更聚合根状态
4. **结果反馈**：命令执行结果 → 界面提示（成功/失败/部分成功）

### 3.3 读写模型的对齐策略

**问题**：读写模型分离后，如何保持一致性？

**方案**：
1. **事件驱动同步**：命令执行后发布领域事件，读模型订阅事件更新
2. **读模型投影**：每次查询时动态组合数据（适用于简单场景）
3. **快照同步**：定时全量同步（适用于报表场景）

## 四、BFF 架构与界面服务

### 4.1 BFF 定义

**后端为前端服务（Backend for Frontend, BFF）** 是一种架构模式，为每种前端客户端（Web、移动端、小程序）构建专用的后端服务层。

**核心职责**：
- 聚合多个领域服务的数据，组装界面所需的数据结构
- 处理前端特定的数据裁剪、格式转换
- 管理会话、安全、权限验证
- 编排业务流程

### 4.2 BFF 与数据模型映射

BFF 是数据模型到界面的「最后一公里」：

```
┌─────────────────────────────────────────────────────────┐
│                     界面层 (UI)                          │
│  组件 A   组件 B   组件 C   组件 D                       │
└─────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│                      BFF 层                             │
│  • 数据组装（聚合多个服务返回）                            │
│  • 字段裁剪（只返回界面需要的字段）                         │
│  • 格式转换（枚举→文本、金额→¥xx.xx）                      │
│  • 缓存策略（读模型缓存）                                 │
└─────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│                    领域服务层                            │
│  OrderService   CustomerService   ProductService       │
└─────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│                    持久化层                              │
│  OrderRepository   CustomerRepository   ProductRepo    │
└─────────────────────────────────────────────────────────┘
```

### 4.3 BFF 中的映射决策

**数据裁剪示例**：
```java
// 领域服务的完整返回
class Order {
    private Long id;
    private String orderNo;
    private List<OrderItem> items;
    private List<Payment> payments;
    private List<Logistics> logistics;
    private BigDecimal costPrice;  // 成本价（敏感）
    private BigDecimal profitMargin;  // 利润率（敏感）
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
    private String createdBy;
    private String updatedBy;
    // ... 更多字段
}

// BFF 组装的界面 VO
class OrderDetailVO {
    private String orderNo;
    private String statusText;
    private List<OrderItemVO> items;
    private String totalAmountFormatted;
    private String paymentStatusText;
    private String logisticsStatus;
    private List<LocalDateTime> timeline;  // 时间线
    // 不包含：costPrice, profitMargin, createdBy 等
}
```

### 4.4 BFF 与 CQRS 的协同

BFF 是 CQRS 读模型的「组装车间」：

1. **命令路径**：界面 → BFF → 领域服务 → 聚合根 → 持久化
2. **查询路径**：界面 → BFF（缓存） → 读模型服务 → 持久化

## 五、综合映射示例：客户详情页

### 5.1 领域模型

```
Customer (聚合根)
├── CustomerBaseInfo (值对象：基本信息)
├── ContactInfo (值对象：联系方式)
├── FollowUpRecord[] (子实体：跟进记录)
├── Order[] (关联实体：订单)
└── Tag[] (关联实体：标签)
```

### 5.2 六个层次的映射

| 层次 | 映射内容 |
|-----|---------|
| 结构映射 | 客户实体 → 客户卡片/详情页；跟进记录 → 跟进列表组件 |
| 交互映射 | 添加跟进 → 跟进表单弹窗；编辑 → 编辑表单 |
| 聚合根映射 | 客户详情页为导航终点，包含所有关联数据 |
| 聚合映射 | 客户列表展示「客户总数」「本月新增」统计 |
| 投影映射 | 列表用客户列表 VO；详情页用客户完整 VO |
| 权限映射 | 销售只能看自己的客户；经理可看全部 |

### 5.3 CQRS 与 BFF 视角

**命令侧**：
- 新增客户（CreateCustomerCommand）
- 编辑客户（UpdateCustomerCommand）
- 添加跟进（AddFollowUpCommand）

**查询侧**：
- 客户列表查询（CustomerListQuery）→ 扁平化 VO
- 客户详情查询（CustomerDetailQuery）→ 完整 VO（含关联）
- 客户统计查询（CustomerStatsQuery）→ 聚合数据

## 六、映射规范建议

### 6.1 文档化要求

每个界面应文档化以下映射信息：
1. **数据来源**：对应的聚合根、读模型
2. **字段映射表**：UI 字段 → 数据模型字段
3. **操作映射**：界面动作 → 领域命令
4. **权限映射**：界面可见性 → 权限模型

### 6.2 一致性约束

1. **聚合根内一致性**：同一聚合根内的数据，应在同一事务内加载/保存
2. **读写模型一致性**：命令执行后，相关读模型应通过事件或同步机制保持一致
3. **界面与模型一致性**：界面展示的字段语义应与数据模型定义完全一致

### 6.3 性能考量

1. **加载粒度**：列表页避免加载完整聚合根
2. **关联加载**：使用延迟加载或显式指定加载策略
3. **缓存策略**：读模型应支持缓存，减少数据库访问

## 七、总结

数据模型到界面的映射是一个多层次的语义转换过程：

1. **结构映射**建立模型与 UI 组件的基本对应关系
2. **交互映射**将领域行为转化为用户操作
3. **聚合根映射**确定界面的导航边界和事务范围
4. **聚合映射**处理数据的多维度汇总展示
5. **投影映射**根据场景选择最优的数据展示形式
6. **权限映射**确保界面只暴露用户有权访问的数据

在实现层面，**CQRS** 分离读写职责，使界面展示更灵活；**BFF** 作为聚合层，负责数据裁剪和格式转换，使前端更简洁。两者结合，构成了现代 SaaS 应用的典型数据流架构。
