## 二、实现机制要点（协议/机制示例）

1. **元数据驱动**：财务单据结构、分录、按钮、权限全部来自元数据（BusinessInfo/FormMetadata），实例为 DynamicObject；插件代理按序扇出事件（历史实证）。
2. **单通道操作**：保存/提交/审核/过账/结账统一走操作框架，`timingPoint(Before/After)` 插桩插件逻辑——财务的大部分"业务语义"以插件与元数据形式存在，而非大段代码。
3. **服务门面分层**：FIN 提供 `*ServiceHelper` 作为业务服务门面（对账/核销/改期/凭证），复用平台 `BillOperateServiceHelper` 做单据操作编排。
4. **表结构候选**：见 DA5（快照无 Schema，U-DA0-1）。

## 三、设计决策记录（DEC 卡，D1-D5）

### DEC-001：为什么财务用"凭证-余额-期间"三段式结构（而非单一大表）
| 字段 | 内容 |
|---|---|
| 决策点 | 记账为何拆分"明细凭证 + 聚合余额 + 时间期间"三个对象 |
| 当时约束 | 需要同时支持"明细可审计、总额可汇总、历史不可变"三诉求；并发写余额要可控 |
| 可选方案 | 单一流水大表实时汇总；凭证+余额+期间三段；纯读模型物化 |
| 选择与理由 | 三段式：凭证=事件明细（审计），余额=按期间×科目的聚合（快速报表），期间=时间轴锁（防历史污染） |
| 成因分类 | 有意决策（会计理论与实践标准形态） |
| 当时合理性 | 合理（ERP 通用范式，性能与可审计平衡） |
| 当前合理性 | 仍合理（明细/聚合/时间轴三职责分离） |
| 影响面 | 结构变更会同时伤历史（凭证/余额/期间强耦合） |

### DEC-002：财务单据为何"零代码优先"（元数据+操作框架承载）
| 字段 | 内容 |
|---|---|
| 决策点 | 财务成百单据为什么几乎无手写业务类，只有少量插件 |
| 当时约束 | 单据类型多、字段/流程差异大；二次开发需要低门槛 |
| 可选方案 | 每单据写死类；元数据+插件；模板代码生成 |
| 选择与理由 | 元数据+插件：单据=配置，业务变化改元数据不改程序；插件只在特殊点介入 |
| 成因分类 | 有意决策（BOS 平台核心定位"可配置 ERP"） |
| 当时/当前合理性 | 合理 / 仍合理 |
| 影响面 | 改元数据影响新单据编辑，配错伤运行期（需权限+审计） |

### DEC-003：已结期间可"改期/反结"（锁期 ≠ 不可动）
| 字段 | 内容 |
|---|---|
| 决策点 | 结账已封闭期间，为何仍保留改期/反结通道 |
| 当时约束 | 业务现实：结账后仍可能发现错账、审计要求修正；同时历史数据必须受控 |
| 可选方案 | 期间硬锁定不可改（需数据库脚本）；可反结+留痕+权限；投影修正 |
| 选择与理由 | 受控反结：锁期保证默认安全，改期作为显式补偿通道，靠权限/留痕/审计兜底 |
| 成因分类 | 有意决策（平衡"防篡改"与"可纠错"） |
| 当时/当前合理性 | 合理 / 仍合理（但治理关键：监控改期频率与留痕） |
| 影响面 | 改期直接触碰"历史"——影响已固化余额与后续期间，需连同后续期间连锁重算 |

### DEC-004：核销为什么经"核销单"中间载体（而非发票直连收付款）
| 字段 | 内容 |
|---|---|
| 决策点 | 债权消灭为何要核销单桥接 |
| 当时约束 | 一张收付款可核多张发票、可部分核销、外币/折让有差异、需审计追溯 |
| 可选方案 | 发票↔收付款直连；核销单匹配；批量勾对标签 |
| 选择与理由 | 核销单承载匹配(先后/部分/合并)与差异额，支持反核销与审计 |
| 成因分类 | 有意决策（同 DA3 REL-04 间接路径论证） |
| 当时/当前合理性 | 合理 / 仍合理 |
| 影响面 | 换匹配载体伤历史核销——核销数据模型变更影响所有在途核销 |
