# 04 设计与实现 —— 机制与决策为什么这样

> 读者视角：不看代码也能懂"它靠什么跑起来、为什么这么设计"。证据与未知见 `05` 及过程附件。

## 一、机制层（怎么样）

### 1. 一句话架构
财务域 = **元数据驱动的单据** + **平台操作框架**（保存/审核/过账/结账统一通道）+ **FIN 服务门面**（对账/核销/改期/凭证生成/资金）。

### 2. 三层容器
| 层 | 承载什么 | 为什么 |
|---|---|---|
| 元数据 | 单据结构、分录、按钮、权限、报表口径 | 上百种财务单据"配置化"，改配置不改程序 |
| 操作框架 | 过账/结账/审核的公共执行（操作号+阶段点） | 一套"记账—锁期"能力被所有单据复用 |
| FIN 门面 | 凭证生成、核销、对账、改期、资金、账龄等业务服务 | 复杂财务规则以服务形式编排插件 |

### 3. 数据流（机制级）
```
业务单据(元数据实例) → 凭证生成(借=贷校验) → 过账(写分录驱动余额，防重)
  → 期间归并 → 结转 → 结账锁期(历史固化) → 报表/对账读取
```

### 4. 状态控制
凭证 SM-01（编制→提交→审核→过账/作废）、期间 SM-02（未结→已结→改期重开）、往来 SM-03（未核→部分/已核→反核销）——均带守卫与非法迁移拦截（见 DA4）。

## 二、决策层（为什么）— 4 张 DEC 卡（认知真源 D1-D5）

### DEC-001 凭证—余额—期间 三段式
- **决策点**：记账为何拆成"明细凭证 + 聚合余额 + 期间时间轴"？
- **当时约束**：要同时满足"明细可审计、余额可快速汇总、历史不可篡改"。
- **可选方案**：单一流水实时汇总 / 三段式 / 只物化读模型。
- **选择与理由**：三段式让"事件（凭证）、状态（余额）、时间（期间）"职责分离。
- **成因**：有意决策（会计标准范式）；当时合理，当前仍合理。
- **影响面**：三者强耦合，改结构伤历史。

### DEC-002 财务单据零代码（元数据优先）
- **决策点**：财务数百单据为何几乎不写业务类？
- **当时约束**：单据类型多、差异大、二次开发需低门槛。
- **可选方案**：每单据写死类 / 元数据+插件 / 模板代码生成。
- **选择与理由**：元数据+插件=单据由配置与少量事件插件承载。
- **成因**：有意决策（BOS"可配置 ERP"定位）；仍合理。
- **影响面**：改元数据影响编辑期与新单据，配错影响运行期。

### DEC-003 锁期可受控重开（反结/改期）
- **决策点**：已结期间为何保留反结/改期通道？
- **当时约束**：结账后仍会有审计纠错需求；历史必须默认受控。
- **可选方案**：硬锁不可改（仅库脚本） / 受控反结+留痕 / 只读投影修正。
- **选择与理由**：受控反结平衡"防篡改"与"可纠错"。（诚实边界：结账/反结**写入口在 FIN 快照未定位**，机制依据平台操作框架推断，见 U-DA0-5。）
- **成因**：有意决策；仍合理；治理要点=监控改期与留痕（强制程度待补证 U-DA4-2）。
- **影响面**：触碰历史，需连锁重算后续期间。

### DEC-004 核销经"核销单"中间载体
- **决策点**：债权消灭为何不把发票直连收付款？
- **当时约束**：一张收付款核多张发票、可部分核销、外币/折让有差异、需审计。
- **可选方案**：直连 / 核销单匹配 / 批量勾对标签。
- **选择与理由**：核销单承载匹配规则、差异额、反核销与审计。
- **成因**：有意决策（同 REL-04 间接路径论证）；仍合理。
- **影响面**：核销模型变更伤历史在途核销。
