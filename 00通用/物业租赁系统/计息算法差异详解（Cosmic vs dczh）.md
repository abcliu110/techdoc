# 计息算法差异详解：Cosmic 参考实现 vs dczh 当前实现

> 本文只讲**逐日计息这一块算法**，逐行对照代码，并用同一组数据把两侧的实际数字跑出来。
> 代码证据：`InterestDetailGenerator.java`（Cosmic，反编译源码）/ `RightOfUseCalcServiceImpl.java`（dczh）
**复算脚本**：`sim_trace.py`（忠实复刻两侧代码，可改参数重跑）
> 统一样例：**起租 2026-01-01、租期末 2027-01-01、季付 4 期 × 3 400 元、年折现率 6%（复利）**
> → 日利率 `r = 0.0001596536`、负债现值 `PV = 13 117.21`、付款合计 `13 600`、**未确认融资费用 `482.79`**（这个数就是"总利息目标"）

---

## 0. 一句话结论

两侧都能做到"**总利息 = Σ付款 − 负债现值**"（对账总额一致），但**每一天的利息、每个付款日归属的利息、每条明细行的闭合方式**都不一样。
差异来自 **2 个机制性分歧 + 2 个取整/封口分歧**，其中机制性分歧会把利息在时间轴上"搬家"，取整分歧会让账出现 1 分的口子。

| # | 分歧 | 性质 | 对样例的量化影响 |
|---|---|---|---|
| ① | 起租日**当天**收不收利息 | 机制（口径） | Cosmic 比 dczh 多收 **2.09 元** |
| ② | 付款日当天：**先扣款**还是**先计息** | 机制（口径） | dczh 每个付款日多收 **0.54 元**（3 个中间付款日 = 1.63） |
| ③ | 尾差封口的**落点与形态** | 机制（封口） | 只影响末期与最后一个月，但决定"总额怎么归零" |
| ④ | **取整时机**：逐日取整 vs 逐期取整 | 实现（精度） | Cosic 自然口径比目标多 0.03 元，靠封口拉回 |
| ⑤ | 明细行是否**内部自洽** | 实现（缺陷） | dczh 实测出现 **1 分**：`期初 + 利息 − 租金 ≠ 期末` |

## 1. 两侧算法骨架（先把"轨迹"看明白）

### Cosmic —— 明细表 **逐日一行**
```
InterestDetailGenerator.java:123-151
rowDate = detailBeginDate (=起租日，或存量场景的系统切换日)
beginBalance = 负债现值
while rowDate <= detailEndDate(≈最后付款日):
    leaseLiabPay = 当天的付款（无则 0）
    if rowDate == 最后付款日前一天:                      ← 尾差封口日
        int = 未确认融资费用 − 累计已提利息
    else:
        int = (beginBalance − leaseLiabPay) × 日利率      ← ★先扣款，再计息
    int = round2(int)                                   ← ★逐日就取 2 位
    endBalance = beginBalance − leaseLiabPay + int
    rowDate += 1 天
```
时间轴：

```
 起租日                    付款日                      最后付款日前一天   最后付款日
 ├──────────────────────────┼────────────…──────────────┼───────────────┼─────
 [计息 2.09]  …  [基数已扣款→计息 1.58]  …  [尾差封口 0.51]  [基数=0 → 利息 0]
 明细逐日一行；最后一天余额恒为 0
```

### dczh —— 明细表 **逐付款期一行**，内部先跑一遍逐日模拟
```
RightOfUseCalcServiceImpl.java:256-291（逐日）
起租日：      利息 = 0，仅冲减负债         balance = PV − 起租日付款      ← ★起租日不计息
起租日次日 → 最后付款日，每天：
    利息 = balance × 日利率                                             ← ★先计息
    balance = balance + 利息 − 当日付款                                  ← ★后扣款
（全程 10 位小数，不逐日取整）

RightOfUseCalcServiceImpl.java:314-394（聚合成行）
每行利息 = 「起租日次日 … 本行付款日(含)」区间的日利息累计 − 上一行累计
末期行：利息 = 本期付款 − 期初余额，期末余额强制 = 0.00
```
时间轴：

```
 起租日                      付款日                      最后付款日
 ├────────────────────────────┼────────────…──────────────┼─────
 [利息 0，仅冲减负债]  [次日起计息]  [基数未扣款→计息 2.12] … [末期行：利息=付款−期初]
 明细逐付款期一行；末期余额强制 0
```

**第一层差异已经可见**：Cosmic 是"逐日明细 + 尾差封口"，dczh 是"逐日模拟（内部）+ 逐期汇总（落库）"。
两者不是同一张表的两种写法，而是**两种不同的记账载体**——这决定了后面所有差异。

## 2. 分歧①：起租日当天，到底收不收利息

### 代码
| | 依据 | 行为 |
|---|---|---|
| Cosmic | `InterestDetailGenerator.java:123-137` | 循环**从 `detailBeginDate` 当天开始**，`int = (beginBalance − 付款) × r` → 起租日当天就计息 2.09 元（当天无付款时） |
| dczh | `RightOfUseCalcServiceImpl.java:264-272` | 注释明确写"**起租日不计息，但当天冲减负债，次日按扣款后的余额计息**"；循环从 `commencementDate.plusDays(1)` 开始 |

### 实测（同一份数据，逐日流水）
| 日期 | Cosmic 期初 | Cosmic 利息 | Cosmic 期末 | dczh 期初 | dczh 利息 | dczh 期末 |
|---|---:|---:|---:|---:|---:|---:|
| 2026-01-01（起租日） | 13117.21 | **2.09** | 13119.30 | 13117.21 | **0.0000** | 13117.2100 |
| 2026-01-02 | 13119.30 | 2.09 | 13121.39 | 13117.2100 | 2.0942 | 13119.3042 |
| 2026-01-03 | 13121.39 | 2.09 | 13123.48 | 13119.3042 | 2.0945 | 13121.3988 |

→ 起租日当天差 **2.09 元 = PV × r = 13 117.21 × 0.0001596536**，并且这条差会**顺延影响后续每一天的余额基数**（Cosmic 的负债基数一直比 dczh 高约 2 元）。
→ 反映到自然月：**2026-01 一个月差 2.10 元**。

### 为什么会这样 / 业务上怎么看
- 纯数学上，`PV` 是"起租日的负债现值"，只要起租日当天还没还钱，这一天就该产生利息 —— 这是 Cosmic 的逻辑（`int = (期初 − 当日付款) × r`，即**日初付款**假设）。
- dczh 的逻辑是"**租赁从起租日开始时点起，当天视为尚未开始计息**"。这条口径本身可以接受（属于会计政策选择），但要**在需求/说明书里写死**，因为它会永久改变每一期的利息分布。
- **关键**：它和 dczh 的折现口径是**自洽**的——dczh 对起租日付款取"折现 0 天"（`discountDays = DAYS.between(起租日, 付款日) = 0`），也就是把起租日付款当作"日初已付"，自然就不该再对这笔钱计息。Cosmic 则把它当"日初付款"但仍然对**当天**的日均余额计了息，两者对"同一天付款"的处理是两套假设。

## 3. 分歧②：付款日当天 —— 先扣款，还是先计息

### 代码
| | 公式 | 含义 |
|---|---|---|
| Cosmic `:133` | `int = (beginBalance − leaseLiabPay) × r` | **当天先把租金扣掉，再按剩余负债计息**（等价于"付款发生在当天日初"） |
| dczh `:279-282` | `int = balance × r; balance = balance + int − 付款` | **先按当天日初负债全额计息，再扣租金**（等价于"付款发生在当天日终"） |

### 实测（第 1 个付款日 2026-04-01）
| 日期 | Cosmic 期初 | 付款 | Cosmic 利息 | Cosmic 期末 | dczh 期初 | dczh 利息 | dczh 期末 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2026-03-31 | 13304.91 | 0 | 2.12 | 13307.03 | 13302.7862 | 2.1238 | 13304.9101 |
| **2026-04-01** | 13307.03 | **3400** | **1.58** | 9908.61 | 13304.9101 | **2.1242** | 9907.0342 |
| 2026-04-02 | 9908.61 | 0 | 1.58 | 9910.19 | 9907.0342 | 1.5817 | 9908.6159 |

→ 单日差 = `3 400 × 0.0001596536 = 0.54 元`，每次付款都会发生：**付款额越大，差越大**（年付 12 万的合同，单次差 19 元）。
→ 落在自然月上：4 月差 −0.54、7 月差 −0.55、10 月差 −0.44。

### 实测（末期 2026-12-31～2027-01-01）
| 日期 | Cosmic 期初 | 付款 | Cosmic 利息 | Cosmic 期末 | dczh 期初 | dczh 利息 | dczh 期末 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2026-12-30 | 3398.95 | 0 | 0.54 | 3399.49 | 3398.3688 | 0.5426 | 3398.9114 |
| 2026-12-31 | 3399.49 | 0 | **0.51**（尾差封口；自然值 0.54） | **3400.00** | 3398.9114 | 0.5426 | 3399.4541 |
| 2027-01-01（最后付款日） | 3400.00 | 3400 | **0.00** | 0.00 | 3399.4541 | 0.5427 | −0.0032 |

→ Cosmic 在最后付款日"正好还清"，当天利息为 0；dczh 当天照常计息 0.54，靠**末期行改写**归零。

### ⚠️ 一个需要指出的内部不一致（dczh 侧）
dczh 对"**起租日**的付款"按**日初**处理（先冲减负债、不计息），对"**其他付款日**的付款"按**日终**处理（先计息、后扣款）。
即：**同一天付款的日切假设，首日和后续日不同**。Cosmic 则统一按日初处理（`期初 − 当日付款`，首日与后续日一致）。
这不是算错，但属于会在审计/对账时被追问的口径不一致，建议二选一并写进测试基线。

## 4. 分歧③：尾差（封口）落在哪一天、以什么形态出现

### 两侧的封口机制
| | Cosmic | dczh |
|---|---|---|
| 落点 | **最后付款日的前一天**（`getDealTailDiffDate:251-266`，`dealTailDiffDate = addDay(lastPayDate, −1)`） | **末期行（最后付款日当行）** + 台账路径的**余额锚点当期**（`:388-394`、`:527-539`） |
| 公式 | `int = 未确认融资费用 − 累计已提利息`（封口当天利息被整体重写） | 明细：`利息 = 本期付款 − 期初`，`期末 = 0.00`；台账：单列 `settlement_adjustment`，`finance_expense = period_interest − adjustment` |
| 载体 | 就写在"那一天"的利息列 | 计划落库时**多出一列**「结算调整」（SQL12 注释：`期初负债+利息费用+调整−租金付款=期末负债`） |
| 为什么需要 | **逐日取 2 位**会累计误差（本例自然合计 482.82，多 0.03），必须封口拉回 482.79 | 逐日 10 位本就自然守恒（本例自然合计恰好 = 482.79），封口更像"形式动作"（本例只改动 −0.0032 → 0.00） |

### 图示

```
Cosmic：封口日 = 最后付款日 − 1 天
  … 12-30(0.54) │ 12-31 → 写成 0.51（= 482.79 − 累计） │ 01-01 付款日 基数已是 0 → 利息 0.00
                 ↑ 尾差在这里被"吃掉"，当天余额正好等于末期租金

dczh：封口在末期行 + 台账单列
  … 12-31(0.5426) │ 01-01 末期行：利息 = 3400 − 3350.43 = 49.57（= 该期自然利息），期末 = 0.00
                                    台账另出一列「结算调整」吸收 ±差额
```

### 影响
1. **报表按行取数会不一样**：Cosmic 的 12 月利息含 0.51 的封口值；dczh 的 12 月是自然值 0.5426×2 天，封口值跑到 1 月/末期行。
2. **dczh 的"结算调整"列是报表口径的额外项**：下游做"利息支出"科目取数时，若只取 `finance_expense` 而不含 `settlement_adjustment`，会与总额差一点点；必须明确口径。
3. 封口**方向可能为负**：`利息 = 付款 − 期初` 在大额负债、末期小额付款时会得到**负利息**（Cosmic 的 `未确认融资费用 − 累计` 形态也会为负，但金额量级完全不同）。建议加断言：`|末期利息| ≤ 当期自然利息 + 1 元` 之类的护栏，或直接用"未确认融资费用 − 累计利息"的守恒式。

## 5. 分歧④⑤：取整时机 —— 这一块能直接看出"差 1 分"的账

### 取整策略对比
| | Cosmic | dczh |
|---|---|---|
| 逐日利息 | **每天 round2** 后入余额链（`:134`，按币种 `amtprecision`） | 保留 **10 位**，链式累加（`:310-312`）|
| 明细行利息 | 就是逐日值，天然 2 位 | 期间汇总值再 round2（`:396-398`）|
| 期末余额 | `期初 − 付款 + 利息` 链式推导 → **恒等式永远成立** | 独立取"日终余额"的 round2（`:332-333, 381`）→ **可能不闭合** |

### 实测缺陷：dczh 明细行内恒等式不成立（1 分）
样例 A（6% 季付）——**4 行里 1 行不闭合**：

| 付款日 | 期初 | 行利息 | 租金 | 期初+利息−租金 | 落库期末 | 判定 |
|---|---:|---:|---:|---:|---:|---|
| 2026-04-01 | 13117.21 | 189.82 | 3400 | 9907.03 | 9907.03 | ✅ |
| **2026-07-01** | 9907.03 | 144.97 | 3400 | **6652.00** | **6652.01** | ❌ 差 0.01 |
| 2026-10-01 | 6652.01 | 98.42 | 3400 | 3350.43 | 3350.43 | ✅ |
| 2027-01-01 | 3350.43 | 49.57 | 3400 | 0.00 | 0.00 | ✅（末期强制）|
| **合计** | | **482.78** | **13600** | | | 与**未确认融资费用 482.79 差 0.01** |

样例 B（4.5% 月付 12 期）：**12 行里 1 行不闭合**（2026-09-01），Σ行利息 237.59 vs 未确认融资费用 237.60，同样差 1 分。
样例 C（8% 年付 3 期）、样例 D（0% 季付）：未复现，说明**是否出现取决于金额与日期组合**，不是必然但**一定会发生**。

**根因**：`beginBalance`、`periodInterest`、`endBalance` 三条数据**各自独立取 2 位**：
```
begin(row)  = round2(上一行期末, 10 位值)
interest(row)= round2(区间自然利息累计, 10 位值)
end(row)    = round2(日终余额, 10 位值)          ← 三者不再满足 期初+利息−租金=期末
```
**修法（三种，任选其一即可闭合）**：
1. 让期末由另两者推导：`end = round2(begin + interest − 租金)`（Cosmic 的做法，最省事、必然闭合）；
2. 让利息由另两者推导：`interest = 租金 + end − begin`（等价于末期行的现有写法，全行统一）；
3. 引入"行级尾差"列（类似 `settlement_adjustment`）显式吸收差额，并在报表口径中固定取"利息 + 调整"。

> 附带更正：上一版《租赁资产差异比对报告》第五节把 dczh 末期利息记为 0 并给出"合计 482.82 / 差 0.03"的月表——那是脚本贴错了格子。**以本文为准**：两侧自然口径逐日合计分别为 **Cosmic 482.82（需封口）**、**dczh 482.79（天然守恒）**，封口后都等于未确认融资费用 482.79。

## 7. 对业务的实际影响（为什么必须管）

| 受影响对象 | 具体表现 |
|---|---|
| 月度利润表 | 首月差 2.10 元（单合同，季付 3 400）；付款月差 0.5 元级；**合同越大/付款越集中，差异越大**（年付 12 万 → 单月差 19 元级） |
| 租赁负债余额表 | 起租日当天的负债余额差 2.09 元，且余额基数差会一直带着走 |
| 凭证/总账 | 若两侧混用（例如历史数据来自 Cosmic、新数据来自 dczh），同一年度出现两套利息节奏，**月度利息曲线不可比** |
| 明细对账 | dczh 行内 1 分不闭合 → 财务按"期初+利息−租金=期末"手工验算会报错；**建议尽快用第 5 节的修法 1 闭合** |
| 审计/税会 | 起租日、付款日日切假设必须有书面口径；差异 1 分/月/合同，1000 个合同就是 10 元级/月，量级不大但**性质是"账不闭合"**，审计会追问 |

## 8. 建议的对齐方案（三选一，先定口径再动代码）

**方案 A：dczh 向 Cosmic 对齐（推荐用于"要与参考软件对账"的场景）**
1. 起租日改为计息：把 `calculateDailyInterest` 的循环起点从 `commencementDate.plusDays(1)` 改为 `commencementDate`，并删掉"起租日只冲减负债"的特例；
2. 付款日改为"先扣款后计息"：把 `calculateDailyInterest(balance, rate)` 的入参改为 `(balance − 当日付款)`；
3. 封口改为"最后付款日前一天 + 守恒式"：末期行不再用 `付款 − 期初`，改用 `未确认融资费用 − 累计已提利息`；
4. 行内闭合：`end = round2(begin + interest − payment)`。
   ⚠️ 注意：这 4 条都会改变已落库的历史数据，需 **一次性重算 + 版本号（`calculationVersion`）迁移**，dczh 已有 `monthly-v6` 版本机制，正好用得上。

**方案 B：保持 dczh 现值口径，但"补齐说明 + 加测试护栏"（最快落地）**
1. 在需求说明中明确"**起租日不计息**"与"**付款日按日终处理**"，并在测算页面/导出报表上标注口径；
2. 修掉第 5 节的 1 分不闭合（改动最小、风险最低）；
3. 给末期行加护栏：`|末期利息| ≤ 该期自然利息 + 容差`，或在末期利息为负时改走守恒式；
4. 用本文第 6 节的表做**黄金样本回归**，锁死分布不再漂移。

**方案 C：统一到"日初付款 + 起租日计息"的行业惯例（我认为数值最自洽的一套）**
- 每日利息 = `(日初余额 − 当日付款) × r`，起租日同样适用；逐日 10 位、行级 round2、期末由恒等式推导。
- 好处：与复利现值口径**严格互为逆运算**（负债在末期精确归零，无需人为尾差）；且付款日日切假设全期一致。
- 代价：与 Cosmic 明细的逐日呈现不同（但总额与分布几乎一致），需要与财务确认。

## 9. 如何用脚本验证（可复现）

```bash
python3 sim_trace.py     # 输出逐日流水、行级对比、月度对比、归因
```
脚本里可改：`START / LEND / PAYS / annual`，建议至少跑这几个边界：
1. 起租日当天有付款（`PAYS[START] > 0`）→ 观察两侧首行差异是否变成"付款额×r + 首日利息"；
2. 最后付款日晚于租期末 → 观察 dczh 台账锚点回落到租期末（Cosmic 无对应行为）；

4. 同一天两笔付款 → Cosmic 逐日累加 / dczh `calculateLaterSameDayPayments` 加回；
5. 闰年 2 月、超长租期（10 年）→ 取整误差与封口量级。

## 10. 科目与报表视角：算法差异最终落在哪儿

> 概念讲清了，还要能落回账。**所有计息算法差异，最终只影响一个损益科目（财务费用—利息费用）及其对手方（租赁负债—未确认融资费用），其余科目不受影响。**
> 四层结构（概念 → 科目 → 报表 → 系统字段）的完整说明见《从租户角度的租金入表逻辑》§3.3.7～§3.3.8 与《使用权资产与租赁负债计算详解》§7.4.7。

### 10.1 差异 → 科目 → 报表 的映射

| 本文算法差异 | 影响的科目 | 影响方向 | 报表体现 |
|---|---|---|---|
| ① 起租日是否计息（第 2 节） | 财务费用—利息费用／租赁负债—未确认融资费用（借方余额） | Cosmic 多首日 1 天利息（＝负债现值 × 日利率） | 利润表首月财务费用、资负表净负债 |
| ② 付款日先扣款 vs 先计息（第 3 节） | 同上 | dczh 每个付款日多「付款额 × 日利率」 | 付款月财务费用 |
| ③ 尾差落点（第 4 节） | 同上级科目内部重分配 | 总额相同、逐期分布不同 | 各期财务费用与净负债 |
| ④ 逐日取整 vs 高精度（第 5 节） | 同上 ＋ 科目**残值** | 取整不当 → 期末备抵科目余额不为 0 | 科目余额表出现残值 |
| ⑤ dczh「结算调整」单列 | 财务费用（或单设明细） | 报表取数口径必须明确 | 摊销计划表「结算调整」列 |

**不受影响的科目**：使用权资产、使用权资产累计折旧（折旧按天直线法计提，与计息口径无关）、银行存款、应交税费。

### 10.2 三条复核红线（把算法差异变成可校验的账）

| # | 红线 | 判定方法 | 违反的后果 |
|---|---|---|---|
| 1 | **未确认融资费用期末余额必须为 0** | 租期结束／终止结清时，科目余额表上该科目期末余额 = 0 | 利息池残留 → 负债永不归零（第 5 节 1 分不闭合的直接后果：会残留 0.01） |
| 2 | **Σ 财务费用—利息费用 = 初始未确认融资费用** | 该科目累计发生额 vs 起租日计入备抵科目的金额 | 逐日取整误差未被封口吸收（如 Cosmic 自然口径的 0.03），差额沉淀在科目里 |
| 3 | **「结算调整」必须说明科目归属** | 明确报表取数公式：利息费用＝`finance_expense`（是否需要再加 `settlement_adjustment`） | 利润表与摊销计划表对不上，审计抽凭无法解释 |

### 10.3 系统字段 ↔ 科目（两侧通用）

| 概念 | 会计科目 | 系统字段（dczh 示例） |
|---|---|---|
| 付款总额（原值） | 租赁负债—租赁付款额（贷） | `lease_liab_ori` |
| 未确认融资费用 | 租赁负债—未确认融资费用（借） | `unconfirmed_cost`（＝ Σ租金 − Σ现值） |
| 负债现值（报表净额） | 租赁负债项目（净额列示） | `lease_liab` |
| 逐期摊销额 | 财务费用—利息费用 | 逐日利息累计 ＋ 尾差（末期归零／封口） |

### 10.4 一句话

> 算法差异不改变"总额与科目集合"，只改变**逐期金额在时间轴上的分布**。
> 因此对账盯三点即可：**备抵科目期末归零、Σ利息 ＝ 池子、逐期分布与已确认口径一致**。
