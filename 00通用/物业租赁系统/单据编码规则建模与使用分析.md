# 整个系统单据编码规则建模与使用分析

## 1. 分析范围

本文分析 `D:\cosmic-src` 整个源码工程中的编码规则能力，不以物业、租赁或任何单一业务域为中心。

源码工程是金蝶星瀚反编译多模块工程，主要目录如下：

| 目录 | 角色 | 编码规则相关内容 |
|---|---|---|
| `bos/bos-api` | 公共 API 与数据模型 | `CodeRuleInfo`、`CodeRuleEntryInfo`、`ConditionEntryInfo`、`ICodeRuleService` |
| `bos/bos-kddm-runtime` | 服务门面与运行时调用 | `CodeRuleServiceHelper`，对外提供取号、预读、批量、回收、规则查询等能力 |
| `bos/bos-kddm-core` | 核心编码规则接口 | 核心服务接口与平台抽象 |
| `bos/bos-svc-infra` | 平台实现 | `bos_coderule` 规则服务、缓存、流水号、表单插件、操作插件、唯一性校验和回收 |
| `bos/bos-nocode` | 无代码设计运行时 | 将无代码字段配置转换为前缀、系统时间、流水号规则项，并自动挂载插件 |
| `biz/*` | 业务领域模块 | 大量业务模块复用统一编码规则，也存在领域专用编号算法和扩展插件 |
| `lib`、`scripts` | 依赖与辅助目录 | 未发现编码规则主实现 |

本文基于反编译源码。源码中缺少部分依赖实现、运行时元数据实例和数据库 DDL，因此对数据库物理结构、锁粒度、生产参数和实际单据配置，单独标注“待运行环境确认”。

## 2. 总体结论

整个系统的编码并不是一套单一算法，而是三层模型：

```text
统一平台编码规则
    + 业务领域对统一服务的封装/扩展
    + 完全独立的领域专用编码器
```

其中：

1. **统一平台编码规则**以 `bos_coderule` 为核心模型，绑定业务对象，并按组织、条件和单据数据选择规则。
2. 统一规则项支持固定文本、业务属性、系统时间、流水号、格式化、补位、截取、分隔符、排序项和断号/最大流水管理。
3. `ICodeRuleService` 是公共服务契约，`CodeRuleServiceImp` 是平台实现，`CodeRuleServiceHelper` 是业务和脚本常用的服务门面。
4. 标准单据通常通过表单插件 `kd.bos.form.plugin.CodeRulePlugin` 和操作插件 `kd.bos.business.plugin.CodeRuleOp` 接入。
5. 无代码系统不直接手工编写规则对象，而是从字段配置生成规则项，并自动向表单和保存操作挂载插件。
6. 业务模块并非全部直接复用标准插件。源码发现资产卡片、员工号、HR、票务、批次码、凭证、生产/任务、销售订单等领域存在专用扩展或独立编码逻辑。
7. 因此排查任意单据编号时，必须先判断它属于哪一种路径：统一平台规则、统一服务的领域封装、标准插件的领域子类，还是完全自定义编号。

## 3. 统一平台模型

### 3.1 规则主对象

`bos/bos-svc-infra` 的 `CodeRuleConstant` 明确使用以下对象和逻辑键：

| 标识 | 含义 |
|---|---|
| `bos_coderule` | 编码规则主实体 |
| `t_cr_coderule` | 编码规则相关表常量 |
| `bos_coderule_maxserial` | 最大流水号/流水状态实体 |
| `bos_coderule_intermitno` | 间断号、断号相关实体 |
| `billno` | 单据编号逻辑键 |
| `codeRuleID` | 当前使用规则 ID 逻辑键 |
| `sortitemvalue` | 排序项值 |
| `serial` | 流水号值 |

源码没有给出完整数据库 DDL，但平台代码大量以动态实体方式读取和写入这些实体。

### 3.2 `CodeRuleInfo`

公共模型位于：

```text
bos/bos-api/src/main/java/kd/bos/coderule/api/CodeRuleInfo.java
```

主要字段可分为以下几组：

| 字段 | 含义 |
|---|---|
| `id`、`codeRuleNumber`、`name` | 规则标识、规则编号和名称 |
| `bizobjectId`、`entityId` | 绑定业务对象/数据实体 |
| `isdefault`、`savestate` | 默认规则和保存状态相关属性 |
| `isNonBreak` | 是否非断号规则，影响回收和断号处理 |
| `splitSign` | 全局分隔符 |
| `isAddView` | 新增页面是否预读并显示编号 |
| `appMode`、`ctrlMode` | 规则应用/控制模式 |
| `isModifiable` | 编号是否允许用户修改 |
| `updateRecover` | 组成属性变化后是否重生成并回收旧编号 |
| `enableCondition` | 序列化的启用过滤条件 |
| `checkNumber` | 是否校验手工编号格式 |
| `fillWithZero` | 是否补零 |
| `autoIncrLength` | 是否自动增长流水长度 |
| `useInterruption` | 使用断号的操作来源配置 |
| `updateMaxNumber` | 更新最大流水号的操作来源配置 |
| `ruleEntry` | 编码组成项集合 |
| `orgEntry` | 受控组织集合 |
| `conditionEntry` | 简单适用条件集合 |

### 3.3 `CodeRuleEntryInfo`

规则组成项位于：

```text
bos/bos-api/src/main/java/kd/bos/coderule/api/CodeRuleEntryInfo.java
```

其字段包括：

- `seq`：组成项顺序；
- `attributeType`：属性类型；
- `valueAtribute`：取值属性；
- `attUsingMode`：属性使用模式；
- `length`：长度；
- `cutstyle`：截取方式；
- `format`：格式或固定文本；
- `addchar`：补位字符；
- `addstyle`：补位方式；
- `initial`：初始流水值；
- `step`：流水步长；
- `isSortItem`：是否为排序项；
- `codeelement`：是否编码元素；
- `isSplitSign`、`splitSign`：分隔符配置；
- `isVisable`：是否可见。

因此统一规则的抽象表达是：

```text
最终编号 = 按 seq 排序的多个规则项拼接
规则项 = 固定文本 | 业务属性 | 系统时间 | 流水号 | 分隔符
```

### 3.4 `ConditionEntryInfo` 与启用条件

`ConditionEntryInfo` 只有两个核心字段：

```text
property
propertyValue
```

用于按单据属性值选择规则。除此之外，`CodeRuleInfo.enableCondition` 保存更复杂的过滤条件。`CodeRuleUtils` 会将 `filtercondition` 反序列化为 `FilterCondition`，再提取过滤字段，用于规则重复检查和修改重生成判断。

### 3.5 组织范围

`OrgEntryInfo` 对应规则受控组织。源码中明确读取：

```text
orgentry.orgid
orgentry.isincludesuborg
```

规则可以按组织区分，也可以包含下级组织。组织范围是编码规则匹配维度，不等同于租户隔离边界；不能仅凭组织字段推定系统租户模型。

## 4. 统一服务分层

### 4.1 公共接口：`ICodeRuleService`

位置：

```text
bos/bos-api/src/main/java/kd/bos/coderule/api/ICodeRuleService.java
```

核心能力包括：

| 能力 | 方法代表 |
|---|---|
| 规则查询 | `getCodeRule`、`getAllCodeRuleByEntity` |
| 单号生成 | `getNumber`、`getBatchNumber`、`getNumbers` |
| 单号预读 | `readNumber` |
| 批量注入 | `injectNumbers` |
| 编号回收 | `recycleNumber`、`recycleBatchNumber`、`autoRecycleNumber` |
| 编号格式校验 | `checkNumber` |
| 能力判断 | `isExist`、`isAddView`、`isModifiable`、`isUseIntermitNumber` |
| 断号处理 | `readIntermitNumber`、`consumeIntermitNumber`、`deleteBreakNumbers` |
| 最大流水更新 | `updateNumber` |
| 配置迁移 | `exportCodeRuleByEntityID`、`exportCodeRuleByAppID`、`exportCodeRuleByCoderuleID` |

这说明编码规则服务不只是“返回一个字符串”，还承担规则选择、预读与正式取号的区分、批量编号、断号、回收、格式校验和配置导出。

### 4.2 平台实现：`CodeRuleServiceImp`

位置：

```text
bos/bos-svc-infra/src/main/java/kd/bos/coderule/service/CodeRuleServiceImp.java
```

主要流程：

1. 根据实体 ID 从缓存获取该业务对象的全部规则；
2. 根据动态单据对象和组织 ID 选出可用规则；
3. 将 `CodeRuleInfo` 的规则项转换为编号组成；
4. 通过流水号/最大值/断号机制取得流水部分；
5. 按规则项格式化、补位、截取和拼接；
6. 区分预读编号和正式消耗流水号；
7. 根据操作成功结果更新最大流水或消费断号；
8. 在删除、失败或编号替换时执行回收。

实现类引入了 `DB`、`TX`、`DLock`、`CodeRuleSigner`、缓存和批量回收服务，说明正式取号涉及事务、并发控制、缓存和数据库状态协同。具体锁键和事务隔离级别需要运行时依赖源码或部署环境进一步确认。

### 4.3 服务门面：`CodeRuleServiceHelper`

位置：

```text
bos/bos-kddm-runtime/src/main/java/kd/bos/servicehelper/coderule/CodeRuleServiceHelper.java
```

该类通过 `ServiceFactory.getService(ICodeRuleService.class)` 获取实现，供 Java、脚本和业务模块调用。常见调用形式：

```text
CodeRuleServiceHelper.getCodeRule(entityId, dataInfo, orgId)
CodeRuleServiceHelper.getNumber(entityId, dataInfo, orgId)
CodeRuleServiceHelper.readNumber(entityId, dataInfo, orgId)
CodeRuleServiceHelper.getNumbers(entityId, dynamicObjects)
CodeRuleServiceHelper.recycleNumber(...)
CodeRuleServiceHelper.recycleBatchNumber(...)
CodeRuleServiceHelper.checkNumber(...)
```

## 5. 规则选择机制

规则选择的通用输入是：

```text
业务实体 ID + 当前单据动态对象 + 组织 ID
```

平台通过以下维度选择规则：

1. 业务对象/数据实体匹配；
2. 受控组织匹配；
3. 组织是否包含下级组织；
4. `conditionEntry` 的属性和属性值匹配；
5. `enableCondition` 的过滤条件匹配；
6. 规则是否启用；
7. 默认规则或规则优先级处理。

`CodeRuleUtils.isDuplicateCodeRule()` 会按业务对象、启用状态、受控组织和适用条件检查重叠规则，防止同一业务对象出现无法区分的规则。

规则缓存主要由：

```text
bos/bos-svc-infra/src/main/java/kd/bos/coderule/service/cache/CodeRuleCache.java
bos/bos-svc-infra/src/main/java/kd/bos/coderule/service/cache/CodeRuleCacheMrg.java
```

管理。规则变更或删除时，`CodeRuleUtils.clearCache()` 会清理实体元数据缓存、断号缓存、流水号缓存和最大流水缓存。

## 6. 标准单据使用链路

### 6.1 表单插件

标准表单插件：

```text
kd.bos.form.plugin.CodeRulePlugin
kd.bos.form.plugin.AbstractCodeRulePlugin
```

表单侧职责包括：

- 初始化单据动态对象和实体元数据；
- 通过 `DynamicObjUtil.getNumField(MainEntityType)` 找到编号字段；
- 查询当前单据适用的 `CodeRuleInfo`；
- 新增页面预读编号；
- 将预读编号写入页面；
- 监听规则组成字段变化；
- 按 `isUpdateRecover` 判断是否重新生成；
- 按 `isModifiable` 控制编号字段可编辑性；
- 按 `checkNumber` 校验用户手工修改的编号格式；
- 用 `BillNoChangeCache`、`RecycleCache`、`UseCodeRuleCache` 等缓存记录页面状态。

表单插件并不等于正式提交取号。预读主要用于页面展示和用户交互，正式消耗流水通常在保存/提交操作中完成。

### 6.2 操作插件

标准操作插件：

```text
kd.bos.business.plugin.CodeRuleOp
kd.bos.business.plugin.AbstractCodeRuleOp
```

`AbstractCodeRuleOp` 的主要流程：

```text
onAddValidators
    -> 恢复页面编号状态并准备编号校验

beginOperationTransaction
    -> 单条或批量生成编号
    -> 识别导入、OpenAPI、ISC、下推等来源
    -> 对重复编号重新生成

业务操作执行

onReturnOperation
    -> 仅对成功数据更新最大流水/消费断号
    -> 对失败或替换编号执行必要回收
```

只对 `save` 和 `submit` 等符合条件的操作生成或确认编号。

### 6.3 新增、修改与手工输入

新增单据：

- 没有编号时按当前规则生成；
- 有外部输入编号时按来源标记为用户输入或 Excel 输入；
- 启用了唯一校验时检查数据库重复；
- 重复时重新取号，最多循环 50 次。

修改单据：

- 若规则不允许修改，保持原编号；
- 若编号组成字段发生变化且 `updateRecover` 开启，则重新生成；
- 新编号操作成功后回收旧编号；
- 用户手工修改编号时，根据 `isModifiable` 和 `checkNumber` 决定是否允许及是否校验格式。

### 6.4 唯一性

`AbstractUniqueBillno` 和 `UniqueBillno` 支持两类唯一模型：

1. 仅按单据编号唯一；
2. 按 `GroupFieldUnique` 操作校验中配置的编号字段加其他字段组合唯一。

组合唯一的字段来自操作元数据，不应简单等同于编码规则组成项。例如一个业务对象可能允许不同组织拥有相同编号，也可能要求编号和项目、库存组织或其他字段联合唯一，具体以操作校验配置为准。

`UniqueBillno` 会按字段类型转换比较值：基础资料取主键，日期按时区格式化，枚举取名称，数值按精度格式化，多语言字段转文本。

### 6.5 删除与失败回收

`CodeRuleDeleteOp` 在删除操作中：

- 注入规则条件、规则组成和启用条件所需字段；
- 根据 `CODERULE_DELETE_OP_MOVE_RECYCLE` 决定删除前还是删除成功后回收；
- 调用 `CodeRuleServiceHelper.recycleBatchNumber(...)` 批量回收编号。

操作失败时，`CodeRuleOp` 会依据编号来源、是否已落库、是否已被其他数据占用、是否为非断号规则等条件决定是否回收。

## 7. 无代码编码规则

无代码模块存在独立的“配置转换链”，但最终仍可生成统一规则项并接入标准插件。

### 7.1 自动挂载标准插件

位置：

```text
bos/bos-nocode/src/main/java/kd/bos/nocode/coderule/utils/CodeRuleServiceUtils.java
```

源码提供：

- `setBusinessControl(formMetadata, value)`：设置业务控制中的编码号开关；
- `addCodeRulePlugin(formMetadata)`：挂载 `kd.bos.form.plugin.CodeRulePlugin`；
- `addCodeRuleOpPlugin(formMetadata)`：向 `save`、`saveandnew` 操作挂载 `kd.bos.business.plugin.CodeRuleOp`。

因此无代码设计的配置最终仍可落到统一表单插件和操作插件链路。

### 7.2 无代码规则项生成

`CodeRuleHandlerChain` 按固定顺序执行三个处理器：

```text
PrefixCodeRuleHandler
SystemTimeCodeRuleHandler
SerialNumberCodeRuleHandler
```

分别对应：

| 处理器 | 配置来源 | 生成的规则项 |
|---|---|---|
| `PrefixCodeRuleHandler` | `billNoPrefix` | 固定文本前缀 |
| `SystemTimeCodeRuleHandler` | YMD/HMS 开关 | `yyyyMMdd`、`HHmmss` 或 `yyyyMMddHHmmss` |
| `SerialNumberCodeRuleHandler` | `billNoRandomNum` | 指定长度的流水号 |

无代码配置可抽象为：

```text
编号 = 前缀 + 系统日期/时间 + 指定长度流水号
```

例如源码明确支持：

```text
yyyyMMdd
HHmmss
yyyyMMddHHmmss
```

以及初始值 `1`、步长 `1` 的流水项。注意：这只是无代码默认生成逻辑，不代表整个系统所有单据都采用这一格式。

## 8. 统一服务的业务领域封装

很多业务模块不直接操作平台内部实现，而是通过 `ICodeRuleService` 或 `CodeRuleServiceHelper` 封装领域语义。

### 8.1 物业管理示例

`biz/pmgt-pmbs` 中的：

```text
kd.pmgt.pmbs.common.utils.coderule.CodeRuleHelper
```

逻辑是：

1. 调用 `CodeRuleServiceHelper.isExist(entityId, dataInfo, orgID)` 判断是否存在规则；
2. 存在时调用 `CodeRuleServiceHelper.getNumber(...)`；
3. 返回业务单据编号。

这属于统一平台服务的轻量封装，不是物业模块自己实现编号算法。

### 8.2 财务卡片示例

`biz/fi-fa` 中的 `CodeRuleServiceImpl`：

- 通过 `ServiceFactory` 获取 `ICodeRuleService`；
- 构造时按实体、动态对象和组织取得 `CodeRuleInfo`；
- 提供 `getNumber()`、`readNumber()`、`isAddView()`、`isExistRule()`；
- 通过统一服务回收编号；
- 另有业务 DAO 查询业务数据是否重复。

它是“领域服务包装统一编码规则”的典型实现。

### 8.3 员工号示例

`biz/hrmp-hrpipro` 的 `EmployeeNumberCodeRuleOp` 继承标准 `CodeRuleOp`，只做两类定制：

- 在 `onPreparePropertys` 中补充员工号规则计算需要的字段；
- 重写 `getBillNoField`，将编号字段固定为 `number`。

这属于“标准操作插件子类化”，核心编号生成仍由平台完成。

## 9. 领域专用和自定义编码实现

全系统并非所有“编码”都由 `bos_coderule` 生成。扫描发现以下代表性类型。

### 9.1 AI 模板编码：完全自定义

`biz/ai-cvp` 的 `OcrCodeRulePlugin` 在新建数据后直接执行：

```text
number = "OCRTEMPLATE-" + new Date().getTime()
```

该逻辑没有调用统一编码规则服务，属于业务插件直接生成编码。

### 9.2 票务/运营领域编码扩展

以下模块存在领域自己的编码规则插件或操作插件：

- `biz/drp-dbd`：票务编码规则页面和操作插件；
- `biz/occ-ocdbd`：票务编码规则页面和操作插件；
- `biz/occ-ocbmall`、`biz/occ-ocepfp`：领域 `CodeRuleOp`、`AbstractCodeRuleOp`；
- `biz/occ-ocbsoc`：B2B 销售订单和退货单编码操作插件；
- `biz/occ-ocdbd`：条码编码插件；
- `biz/biz-bos-ext`：批次编码服务帮助类 `LotCodeRuleServiceHelper`。

这些类名不能单独证明其算法完全独立，需查看具体类是否继承平台插件或调用 `CodeRuleServiceHelper`。但它们明确构成了统一框架之外的领域扩展入口。

### 9.3 财务凭证编码

`biz/biz-bos-ext` 和 `biz/fi-gl` 中存在：

```text
VoucherCodeRuleEditPlugin
VoucherCodeRuleOp
GLCodeRuleServicesImpl
```

凭证编号通常有会计期间、账簿、凭证字和凭证号等领域约束，源码将其作为财务专用编码能力扩展，不能仅按普通单据编号分析。

### 9.4 资产实卡编码

`biz/fi-fa` 中存在一整套真实卡片编号相关实现：

```text
BaseRealCardCodeRuleOp
FaRealCardCodeRuleOp
FaRealCardCodeRulePlugin
FaRealCardCodeRuleServiceImpl
CodeRuleForRealCard
```

该链路既使用统一 `ICodeRuleService`，又引入资产卡片自己的服务、操作状态和表单插件，属于“平台规则 + 领域专用流程”的混合模型。

### 9.5 生产、任务和工程领域编码

扫描发现：

- `biz/mmc-fmm`：`TaskCodeRuleOp`、任务编码服务帮助类；
- `biz/mmc-pmts`：发布编码操作和表单插件；
- `biz/mmc-pom`：MRO 订单编码接口、实现和转换操作；
- `biz/swс-hsbp`、`biz/sit-sitbp`：各自的 `CodeRuleHelper`。

这些实现可能复用平台服务，也可能在领域流程中增加业务号、转换号或子单号。应以具体类的继承关系和调用链确认。

### 9.6 人力资源编码

除员工号标准插件外，HR 模块还存在：

- `hrmp-haos`、`hrmp-haospro`：组织、项目组等编码规则服务；
- `hrmp-hbp`、`hrmp-hbppro`：HR 编码操作；
- `hrmp-hrpi`：劳动关系、雇佣关系、部门员工、固定人员等泛型编码服务。

这些编号可能是基础资料编码，不一定是标准业务单据编号，但仍属于系统“编码规则”范畴，不能从单据编码分析中遗漏。

## 10. 标准路径与自定义路径判别

分析任意编码实现时，可按以下顺序判别：

### 路径 A：统一平台规则

特征：

- 使用 `CodeRuleInfo`；
- 调用 `CodeRuleServiceHelper` 或 `ICodeRuleService`；
- 使用 `bos_coderule` 规则数据；
- 挂载 `CodeRulePlugin`、`CodeRuleOp`；
- 通过实体、组织和动态对象选择规则。

### 路径 B：标准插件领域子类

特征：

- `extends CodeRuleOp` 或 `extends AbstractCodeRuleOp`；
- 通常只重写编号字段、预加载字段、领域校验或操作状态；
- 生成、唯一性和流水维护仍由平台父类完成。

代表：`EmployeeNumberCodeRuleOp`。

### 路径 C：统一服务领域封装

特征：

- 业务提供 `CodeRuleHelper`、`CodeRuleServiceImpl`；
- 内部调用 `ICodeRuleService`；
- 对外提供业务语义方法，例如 `getBillNo()`、`readNumber()`、`recycleNumber()`。

代表：`pmgt-pmbs`、`fi-fa`。

### 路径 D：领域专用混合实现

特征：

- 有独立 `CodeRuleService`、`CodeRuleOp`、`CodeRulePlugin`；
- 可能复用统一服务，但增加领域状态、重复检查、转换规则或特殊字段；
- 不能只看公共父类，需要追踪完整调用链。

代表：资产卡片、财务凭证、票务、MRO 订单。

### 路径 E：完全自定义编码

特征：

- 直接拼接固定前缀、时间戳、UUID 或业务字段；
- 不查询 `CodeRuleInfo`；
- 不调用 `ICodeRuleService`。

代表：`OcrCodeRulePlugin` 的 `OCRTEMPLATE-时间戳`。

## 11. 编号生命周期

统一平台路径的生命周期可抽象为：

```text
规则配置
    |
    v
规则缓存加载
    |
    v
按实体/组织/条件选择 CodeRuleInfo
    |
    +--> 表单预读：readNumber，不正式消耗或按缓存处理
    |
    +--> 保存/提交：getNumber / getNumbers
    |       |
    |       +--> 生成规则项
    |       +--> 获取流水/断号
    |       +--> 唯一性校验
    |       +--> 写回 billNo 字段
    |
    +--> 操作成功：更新最大流水、消费断号
    |
    +--> 操作失败：按状态决定回收
    |
    +--> 修改重生成：成功后回收旧编号
    |
    +--> 删除：按参数在删除前或成功后回收
```

需要注意：预读编号和正式编号不是同一个语义。表单上看到的编号可能来自预读、缓存、下推携带值或用户输入，不能仅凭页面显示值判断流水号是否已经提交。

## 14. 与业务对象的关系

统一编码规则依赖业务对象的元数据：

1. 业务对象必须能被平台实体元数据识别；
2. 单据实体需要有可识别的编号字段，通常由 `BillEntityType.getBillNo()` 或 `DynamicObjUtil.getNumField(...)` 得到；
3. 规则组成项引用的业务字段必须在操作数据中准备出来；
4. 规则条件字段、启用条件字段和组成字段变化时，操作插件需要能够读取这些字段；
5. 规则可能通过表单插件和保存操作插件接入，也可能由领域服务主动调用。

因此，“某张单据是否使用编码规则”不能只看是否存在 `billNo` 字段，还要检查：

- 业务对象是否存在规则；
- 表单是否挂载编码插件；
- 保存/提交操作是否挂载编码操作插件；
- 业务代码是否主动调用统一服务；
- 是否存在领域专用编码服务覆盖标准行为。

## 16. 分析和排查方法

遇到一个具体编码问题时，建议按以下顺序：

1. 确认单据实体 ID 和实际编号字段；
2. 搜索该实体是否存在 `bos_coderule` 规则；
3. 查看规则的受控组织、条件、启用条件和规则项；
4. 检查表单是否有 `CodeRulePlugin` 或领域子类；
5. 检查保存/提交操作是否有 `CodeRuleOp` 或领域子类；
6. 搜索业务代码是否调用 `CodeRuleServiceHelper`、`ICodeRuleService` 或领域 `CodeRuleHelper`；
7. 检查是否有同名领域专用 `CodeRuleService`、`CodeRulePlugin`、`CodeRuleOp`；
8. 判断编号是预读、正式取号、外部输入还是领域直接生成；
9. 检查唯一性校验和数据库重复记录；
10. 检查最大流水、断号、回收记录和相关系统参数；
11. 最后确认缓存是否已经清理。

## 18. 最终模型

整个系统的编码能力应理解为：

```text
编码需求
  |
  +--> 是否有 bos_coderule 规则？
  |       |
  |       +--> 是：统一平台规则路径
  |       |       业务对象 + 组织 + 条件
  |       |       -> CodeRuleInfo
  |       |       -> ruleEntry 组成
  |       |       -> 流水/断号/缓存
  |       |       -> 表单预读与保存提交正式取号
  |       |
  |       +--> 否：是否有领域 CodeRuleHelper/Service/Plugin/Op？
  |               |
  |               +--> 是：领域封装或领域专用路径
  |               |
  |               +--> 否：是否直接拼接时间、前缀、UUID 或业务字段？
  |                       |
  |                       +--> 是：完全自定义编码
```

因此，研究整个系统的单据编码规则，不能只研究物业模块，也不能只研究 `CodeRuleOp`。完整结论必须同时覆盖平台统一规则、无代码转换链、业务领域扩展以及完全自定义编码四类实现。

## 19. 关键算法源码级分析

本章只记录可以从当前反编译源码直接还原的算法。伪代码使用等价表达，不代表源码中存在同名方法。

### 19.1 规则匹配：当前组织、上级组织、默认规则三级决策

入口是 `CodeRuleServiceImp.getCodeRuleByEntityID()`，候选规则先由 `CodeRuleCache.getAllCodeRuleByEntity(entityId)` 提供，再交给 `CodeRuleInfoUtil.getUsableCodeRuleId()`。其决策顺序是：

```text
候选规则
  -> 当前组织直接命中
  -> 组织包含下级时，沿组织树查上级组织规则
  -> 无组织规则中匹配条件的规则
  -> 无组织且无条件的默认候选
```

等价伪代码：

```text
selectRule(rules, orgId, data):
    r = first direct-org rule whose conditions match(data)
    if r != null: return r

    r = first superior-org rule where includeSubOrg and conditions match(data)
    if r != null: return r

    fallback = null
    for r in rules:
        if r has org entries: continue
        if r has no simple condition and no filter condition:
            fallback = r
        else if matchConditions(r, data):
            return r
    return fallback
```

组织匹配中，直接组织命中优先于上级组织；上级关系按业务对象对应的组织职能查询，并使用集合避免重复计算。简单条件的源码行为是遍历 `conditionentry`，属性路径用点号分隔；只要有一条条件值相等即返回命中，空条件值且数据属性为空也视为命中。因此它不是“所有条件必须同时成立”的 AND 算法，而是当前实现中的 OR 式匹配。复杂 `filtercondition` 则交给 `SvcConditionMatcher`，其表达式组合语义由过滤器运行时解释。

无组织规则的“默认”不是无条件立即返回：遍历过程中会保留最后一个无组织、无条件候选；有条件规则一旦匹配则立即返回。这意味着同优先级规则的实际选择还受缓存返回顺序影响，配置管理端的重复检查和排序是重要前置约束。

### 19.2 编号组装：排序项先求值，流水段独立取号

`CodeRuleServiceImp.getNumber()` 按 `ruleEntry` 顺序扫描。每个组成项先计算原始值，再执行 `formatString()`，随后按可见标记拼入流水号前段或后段；属性 `isSortItem` 的格式化结果同时追加到排序项，并用 `_split_` 作为内部分隔符。

```text
before = ""; after = ""; sort = ""; seq = null
for entry in ruleEntry ordered by seq:
    value = evaluate(entry)
      FIX_TEXT       -> entry.format
      SYSTEM_TIME    -> now formatted by entry.format
      DATE_FIELD     -> bill date formatted by entry.format
      ITEM_FIELD     -> bill/base-data field value
      RANDOM         -> preview text or 8-char UUID-derived text
      SEQ            -> remember entry; switch output to after
      CHECK_CODE     -> mark check-code flag
    value = formatString(entry, value)
    if entry.visible: append delimiter and value to current output
    if entry.isSortItem: sort += value + "_split_"

sort = remove trailing "_split_"
serial = signer(rule, seqEntry, sort, isReadNumber)
result = before + (serial if seq visible) + after
if check-code: append EAN-style check digit
```

流水号前后的分界点不是固定位置，而是 `TYPE_SEQ` 规则项出现的位置。序列项本身不在第一次扫描中追加值，待取号后插入；因此序列项前的日期/前缀形成 `beforeSeqNumber`，序列项后的内容形成 `afterSeqNumber`。不可见的组成项不会拼入最终编号，但其值仍可能进入排序项，需结合配置确认。

排序项决定流水号分段。实际并发和最大值键至少包含 `codeRuleId + sortItem`；例如日期项或组织项标为排序项时，每个日期/组织形成独立流水序列。空排序项在部分数据库逻辑中规范化为空格或 `_split_`，不能把空字符串和缺省值随意视为同一配置语义。

### 19.3 规则项格式化：补位、截取和流水溢出

对业务属性项，`attUsingMode == "4"` 才进入截取/补位逻辑；固定文本、日期、流水、校验码、系统时间和随机码直接返回原值。长度处理可还原为：

```text
if actualLength < configuredLength:
    repeat addchar until configuredLength
    addstyle=true  -> 补在尾部
    addstyle=false -> 补在头部
if actualLength > configuredLength and addchar 非空:
    cutstyle=true  -> 取前 length 个字符
    cutstyle=false -> 取后 length 个字符
```

流水段使用 `addChar()`，其规则略有不同：长度不足且 `fillWithZero=true` 时按 `addchar` 补位，空白补位字符默认为 `0`；`addstyle=true` 表示前补，否则后补。流水长度超出配置长度时，若 `autoIncrLength=false` 直接抛出“流水号已用完”异常；开启后允许自然增长。因此“长度”既是显示格式约束，也是流水容量边界。

业务属性支持一至三段点号路径。基础资料字段可能直接从当前动态对象取值，也可能根据主键回载基础资料；多语言取当前语言，日期属性默认格式为 `yyyyMMdd`。超过三段的来源路径会报规则格式错误，取不到值通常转为空串或回退到当前时间（业务日期格式化异常时）。

### 19.4 流水号分配：按规则与排序段加锁、步长前进

默认数据库签名器是 `DBCodeRuleSigner`。它对 `bas/coderule/{codeRuleId + sortItem}` 建立 `DLock`，在锁内读取最大值缓存；缓存为空或标记为 `DATA_LOADED` 时读取 `T_CR_MaxSerial`，不存在则初始化最大值记录为 0。

设当前最大值为 `M`，初始值为 `I`，步长为 `S`，则源码的下一号计算为：

```text
if M < I: M = I - S
N = M + S
```

正式取号时先更新最大值缓存为 `N`，再核对缓存确实已经等于 `N`，最多等待重试两次，每次约 500ms；核对失败抛异常。随后更新 `T_CR_MaxSerial.FMaxSerial=N`。预读 `isReadNumber=true` 时仍在锁内计算 `N`，但跳过缓存持久化和最大值表更新，因此预读不应被当作已消费流水。

批量数据库取号从 `start` 位置开始，以 `M + S * (index-start+1)` 连续分配，最后将最大值推进 `M + S * count`。批量同样按规则和排序项共享锁，保证同一分段内不重复；不同排序项可以并行。

### 19.5 快速签名器与数据库签名器的边界

`CodeRuleSignerFactory` 根据规则配置选择签名器。`DBCodeRuleSigner` 的源码证据是分布式锁、缓存加数据库最大值表；`FastCodeRuleSigner` 还使用 `SEGMENTLENGTH=1000`、最大值 API 和缓存，属于号段/快速取号路径。当前反编译工程缺少部分 `MaxserialApi` 和缓存实现，不能把快速路径的预取、号段回收、Redis 一致性或故障转移细节写成确定事实。可以确定的是：两者共享 `AbstractCodeRuleSigner` 的断号优先和流水格式化流程，具体号段预占策略须结合部署参数和缺失依赖验证。

### 19.6 断号回收与重用：先读候选，再原子消费

只有 `isNonBreak=true` 的规则才进入断号回收/重用路径。编号回收时先由 `CodeRuleSerialNumUtil.getSerialNumberWithoutSplitSign()` 从完整编号拆出排序项、流水号前缀和后缀，再验证流水段：必须能解析为正整数，并满足配置长度、补零和自动增长规则；解析失败返回 `-1`，不写断号表。

成功回收前，`checkIntermitNumber()` 用规则 ID、序列段 ID、排序项和流水值查询 `bos_coderule_intermitno`；已存在则不重复插入，否则保存断号记录。取断号时：

```text
readNumber=true  -> SELECT TOP n ... ORDER BY FSerial，不删除
正式消费        -> 读候选；按规则选择乐观快速删除或 DLock 保护下删除
删除成功        -> 才把该断号交给编号组装
删除失败        -> 该号码不视为成功消费，继续由后续流程处理
```

批量取号先填充断号，不足部分再从最大流水连续分配。断号表的排序保证优先使用较小断号。`readIntermitNumber()` 与 `consumeIntermitNumber()` 的区别正是“只读”和“消费”。

### 19.7 编号冲突与 50 次重试

`AbstractCodeRuleOp.batchGenerateUniqueNumber()` 将待生成数据按当前编号组成映射，调用 `UniqueBillno` 查询数据库中已存在的重复编号；若发现冲突，只对冲突数据重新取号并再次查询，最多循环 50 次。这个循环同时处理数据库已有编号和同批数据组成的查询过滤，不应理解为数据库唯一索引异常后的无限重试。

单条路径也会根据 `isUnique` 和 `GroupFieldUnique` 配置执行唯一检查。组合唯一不是简单比较完整编号，而是按操作元数据指定的字段组装查询条件；基础资料通常比较主键，日期、枚举、多语言和数值会先转换为稳定的比较字符串。50 次后源码没有提供无限补偿机制，实际应由操作失败返回并检查规则容量、并发唯一索引和业务数据。

### 19.8 保存/提交生命周期：生成、成功确认、旧号回收

`AbstractCodeRuleOp.beginOperationTransaction()` 在业务操作事务开始阶段生成编号；`onReturnOperation()` 根据操作结果处理成功数据。对于修改单据，若编号组成属性变化且允许重生成，先生成新号，操作成功后根据 `BillNoChangeCache`/`RecycleCache` 找到旧号和旧规则，再按非断号配置回收旧号。操作失败或数据未成功落库时，不应把预读值、用户输入值和正式消耗号混为一谈。

批量路径将数据分为 `needGenerate` 和 `needUpdate`：可重用的下推/携带编号先尝试 `tryClaimCarriedNumber()`，认领失败才移入新号队列；新号生成后统一做唯一性冲突重试；未生成新号但需要推进手工编号最大值的数据，最后执行 `recordUpdateMaximum()`。该设计使“沿用外部携带编号”和“平台分配新编号”成为两条不同的流水状态路径。

### 19.9 EAN13 校验码

当规则项包含 `CHECK_CODE` 时，源码要求校验码前面恰好是 12 位数字。实现先在末尾追加 `0`，按源码的两段循环累加奇偶位，计算：

```text
check = (10 - ((sumEven * 3 + sumOdd) mod 10)) mod 10
```

最终将 `check` 追加到 12 位主体后形成 13 位编码。任何非数字或长度不为 12 的主体都会抛出规则校验异常。这里的位序必须以源码循环为准，不要仅依据“EAN13”名称自行替换算法。

### 19.10 算法边界与运行验证清单

源码可以确认上述控制流，但以下内容仍需运行环境验证：

- `FastCodeRuleSigner` 的 1000 号段如何预取、落库和失效；
- `DLock` 的实际实现、租约、超时和跨节点一致性；
- `T_CR_MaxSerial`、`T_CR_IntermitNO` 的完整索引、唯一约束和数据库类型；
- `SvcConditionMatcher` 对复杂过滤器的 AND/OR、空值和权限语义；
- 规则候选缓存的排序是否与管理端优先级一致；
- 生产参数对断号乐观消费、批量取号、预读和携带号认领的影响。

验证某个具体单据时，应记录：实体 ID、最终选中的规则 ID、组织和排序项、规则项快照、`isReadNumber`、签名器类型、最大流水记录、断号读/消费记录、唯一性查询结果和操作成功结果。日志与样例交付前必须脱敏，不能记录完整业务对象。

## 20. 这套编码规则设计解决了什么问题

### 20.1 解决业务代码硬编码编号的问题

最直接的问题是：如果每个业务模块都自己拼接“前缀 + 日期 + 流水号”，编号规则会散落在表单插件、保存服务、领域 Helper、SQL 和定时任务中。规则变更需要改代码、发版并重新验证，业务人员也无法自行维护。

统一 `CodeRuleInfo` / `CodeRuleEntryInfo` 模型把编号拆成可配置的规则项：固定文本、日期、系统时间、业务属性、流水号、随机码和校验码。这样做的实际收益是：

- 编号格式从代码逻辑中抽离为元数据；
- 前缀、日期格式、长度、补位字符、流水步长等常规变化可以通过配置完成；
- 平台服务、标准表单插件和操作插件可以复用同一套实现；
- 业务代码主要负责准备业务字段和选择调用时机，而不是重新实现取号算法。

它解决的是“规则变化导致代码变化”的耦合问题，但不意味着所有编码都能统一。员工号、凭证号、批次码等有特殊业务语义的编号仍可能保留领域扩展或独立算法。

### 20.2 解决同一业务对象在不同组织、场景下编号规则不同的问题

集团型系统中，同一单据实体可能因组织、业务类型、单据属性或过滤条件不同而使用不同编号格式。单纯在业务代码中写 `if/else` 会快速形成难以维护的分支树。

规则模型将这些差异显式建模为：

```text
业务对象
  + 组织范围
  + 是否包含下级组织
  + 简单条件
  + 复杂启用条件
  -> 可用编码规则
```

运行时先尝试当前组织规则，再尝试包含当前组织的上级规则，最后进入无组织的条件规则和默认规则。由此解决了：

- 总部规则向下级组织继承；
- 不同组织使用不同前缀或独立流水；
- 同一组织内按单据属性选择不同格式；
- 规则匹配逻辑集中管理，不在每个业务模块重复实现。

这里的关键价值不是“支持更多字段”，而是把规则选择从业务流程代码中独立出来，形成可以审计和排查的决策链。

### 20.3 解决并发创建单据时流水号重复的问题

在多节点服务、批量保存和高并发单据创建场景下，以下实现都不可靠：

```text
读取最大值 -> 最大值加一 -> 保存
```

两个线程可能读到同一个最大值，最终产生重复编号。平台通过“规则 ID + 排序项”确定流水分段，并结合分布式锁、最大流水记录、缓存校验和数据库更新分配下一个号码：

```text
同一规则、同一排序项 -> 同一并发控制范围 -> 串行推进流水
不同排序项           -> 可以拥有独立流水并行推进
```

因此它解决了三类问题：

1. 同一日期、组织或其他排序维度下的流水重复；
2. 多服务节点同时取号时的竞争；
3. 批量取号时逐条读取最大值造成的效率和一致性问题。

代价是取号依赖锁、缓存和最大流水存储的一致性。锁服务不可用、缓存与数据库状态不一致、数据库更新失败时，系统需要失败或重试，不能简单地把编号生成当作无状态字符串函数。

### 20.4 解决“预览编号”和“正式消耗编号”混淆的问题

新增页面通常需要提前显示编号，但用户可能取消保存、关闭页面或反复打开页面。如果预览就永久消耗流水，会造成大量无业务结果的断号；如果预览和正式取号使用同一更新逻辑，又可能造成重复或状态错乱。

服务接口明确区分 `readNumber`、正式 `getNumber`、批量取号和断号消费：

- 预读可以计算候选编号，但不应等同于正式推进最大流水；
- 正式保存/提交阶段才确认流水消费；
- 预读产生的临时编号不能作为已落库编号的凭据；
- 操作失败后是否回收，取决于规则的非断号配置和当前编号来源。

这解决的是编号生命周期问题：编号不再只有“生成”一个动作，而是区分“计算、预览、正式消耗、回收、重用”多个状态。

### 20.5 解决操作失败、修改重生成造成的断号浪费问题

单据保存失败、事务回滚、用户取消、修改了参与编号的字段，都会产生已经计算但未继续使用的编号。平台通过 `T_CR_IntermitNO` / `bos_coderule_intermitno` 保存可回收的间断号，并在 `isNonBreak` 规则下优先重用较小断号。

这使系统可以在“连续编号要求较高”的场景中：

- 将失败或取消产生的编号重新纳入候选池；
- 避免每次失败都永久推进最大流水；
- 修改编号组成属性时回收旧编号；
- 批量取号时优先消耗断号，不足部分再推进新流水。

但它不是无条件的“所有号码都必须连续”。是否回收、何时回收、是否允许断号，取决于 `isNonBreak`、操作来源、唯一性状态和事务结果。对于已经对外打印、发送或被其他单据引用的号码，盲目回收反而可能破坏外部可追溯性。

### 20.6 解决编号唯一性不能只靠流水算法的问题

流水号唯一只保证“平台本次分配的候选值不重复”，不能保证数据库中不存在同号历史数据，也不能覆盖手工输入、外部携带编号或跨流程下推编号。

因此操作层还提供：

- 单据编号唯一校验；
- 按编号字段组的组合唯一校验；
- 数据库冲突后的定向重新取号；
- 最多 50 次冲突重试；
- 下游操作对上游携带编号的认领检查。

这解决了“编号生成正确但落库仍冲突”的问题，并把手工编号、外部编号和平台自动编号纳入同一套校验边界。50 次上限也意味着系统不会无限重试；规则容量不足、唯一条件冲突或数据库约束异常最终必须显式失败。

### 20.7 解决编号在业务上“可读、可分组、可校验”的问题

编号不仅要唯一，还常被用于人工识别、按组织或日期检索、打印和外部传递。规则项支持前缀、日期、组织/业务字段、排序项、分隔符、补位和校验码，使编号可以承载有限的业务语义：

- 日期部分帮助人工判断业务发生时间；
- 组织或业务属性部分帮助分组和检索；
- 排序项让不同分组拥有独立流水；
- 固定长度和补位便于打印、排序和接口对接；
- EAN13 类校验码可以发现部分录入或传输错误。

这解决的是“编号可用性”问题，而不是只追求数据库层面的唯一。需要注意，编号中的日期、组织和业务字段是编码时的快照，不应被误当作实时业务事实；校验码也只能发现部分错误，不能替代数据库唯一约束和完整业务校验。

### 20.8 解决无代码、标准模块和领域扩展共存的问题

系统既有标准单据，也有无代码对象和特殊领域单据。若只有一条强制统一的实现路径，标准能力难以覆盖特殊规则；若完全允许各模块自定义，又会重新回到重复实现和运维困难。

当前设计采用分层兼容方式：

```text
常规单据 -> 统一规则服务 + 标准插件
无代码单据 -> 配置转换为统一规则项 + 自动挂载插件
特殊领域 -> 复用统一服务，并允许 Helper/Service/Plugin/Op 扩展
完全特殊 -> 保留独立编码器
```

这样解决了平台统一性和领域差异之间的冲突：公共取号、唯一校验、断号和缓存可以复用；特殊模块仍能加入员工号、凭证号、批次码等专有语义。

### 20.9 解决编号规则变更后的兼容与迁移问题

规则服务提供规则查询、导出、按实体或应用导出、缓存清理和能力判断等接口。这些能力使规则可以作为独立配置资产管理，而不是隐藏在业务代码中。规则变更后可围绕规则 ID、实体 ID、组织范围和规则项进行检查，并清理相关缓存。

它主要改善：

- 规则配置的迁移和部署；
- 多环境之间的配置同步；
- 规则变更后的缓存失效处理；
- 对“当前到底使用哪条规则”的排查能力。

但规则迁移并不自动解决历史编号兼容。修改前缀、日期组成、排序项或流水策略，可能影响查询、接口、打印、下游引用和旧数据回显，因此规则配置仍应视为对外契约管理。

### 20.10 总结：它建立的是编号基础设施，而不是单一编号函数

这套设计最终解决的是一组相互关联的问题：

| 问题 | 对应机制 |
|---|---|
| 规则散落、改格式要改代码 | `CodeRuleInfo` 和规则项元数据 |
| 多组织、多场景规则不同 | 组织范围、条件和默认规则匹配 |
| 并发取号重复 | 分布式锁、缓存、最大流水和排序分段 |
| 预览与正式保存混淆 | 预读、正式取号和操作生命周期分离 |
| 失败导致断号 | 间断号记录、回收和优先重用 |
| 手工/外部编号冲突 | 唯一校验、携带号认领和冲突重试 |
| 编号难以阅读和校验 | 格式化、补位、分隔符、业务字段和校验码 |
| 标准与特殊业务难以共存 | 平台统一能力加领域扩展层 |
| 规则变更难迁移和排查 | 规则导出、缓存清理和可追踪配置 |

所以，这个设计的本质是把“编号生成”提升为一个具有配置、匹配、并发控制、生命周期管理、唯一性保护和领域扩展能力的平台基础设施。它提高了复用性和一致性，同时也引入了配置复杂度、缓存/锁依赖和规则变更兼容成本。
