# 单据编码规则平台可靠性设计方案

## 1. 文档定位

本文用于设计一套面向物业租赁及其他业务域的新单据编码规则平台。设计以现有《单据编码规则建模与使用分析.md》为兼容基线，保留既有系统已经证明有业务价值的能力，同时重新划分配置、取号、唯一性、回收、审计和扩展边界。

本文不假设现有源码中的具体数据库表结构、锁实现或部署参数可以直接复用。凡是现有反编译源码无法确认的行为，均在“待确认项”中列出，不能在新系统中以隐含假设实现。

### 1.1 设计目标

1. 在多节点、高并发、批量导入和接口重试场景下，保证同一编号作用域内不重复。
2. 将“预览、申请、确认、释放、回收、作废”建模为可追踪的生命周期，而不是只有一个生成字符串的方法。
3. 规则配置可以按业务对象、组织、条件和版本管理，并能解释每次取号为什么选中某条规则。
4. 失败可重试、结果可核对、操作可审计，能够定位规则、流水段、请求和数据库状态之间的差异。
5. 保留标准单据、无代码对象和领域特殊编号的扩展能力，避免所有业务都被迫套用同一种算法。
6. 支持现有系统平滑迁移，历史编号可继续读取，旧调用方可以在兼容窗口内继续工作。

### 1.2 非目标

1. 不把所有业务编号都强制改造成统一格式。
2. 不通过回收机制改变已经对外发布、打印、发送或被其他单据引用的编号。
3. 不把租户隔离、组织权限或业务授权隐藏在编码服务内部猜测处理；这些边界由业务服务显式传入并校验。
4. 不在编码服务中承载业务单据保存、审批、会计处理或库存变更。

## 2. 兼容基线

现有系统的编码能力可归纳为四条路径：

| 路径 | 现有特征 | 新平台处理方式 |
|---|---|---|
| 统一平台规则 | `CodeRuleInfo`、规则项、组织/条件匹配、流水号服务 | 作为标准规则模型继续支持 |
| 标准插件子类 | 表单插件和保存/提交操作插件继承平台能力 | 通过适配器接入，业务字段准备仍由业务侧负责 |
| 领域服务封装 | `CodeRuleHelper`、领域 `CodeRuleService` 调用统一服务 | 保留领域门面，统一使用幂等申请接口 |
| 完全自定义编码 | 时间戳、UUID 或业务算法直接生成 | 作为受控扩展类型登记，不伪装成平台流水号 |

现有行为中需要保留的语义包括：

- 规则按业务对象、组织和单据条件选择；
- 直接组织规则优先于上级组织继承规则；
- 无代码场景可由前缀、系统时间和流水项组成；
- 预读编号不能直接视为正式消耗；
- 正式取号必须在业务操作成功边界内确认；
- 断号只在规则允许且编号尚未对外形成稳定引用时回收；
- 手工输入、外部携带编号和平台自动编号都必须进入唯一性检查；
- 规则变更必须清理缓存并保留可审计的版本信息。

## 3. 总体架构

### 3.1 分层

```text
业务单据服务
  ├─ 业务字段校验、授权、租户/组织范围校验
  ├─ 保存或提交事务
  └─ 调用编码平台适配器
          |
编码平台接入层
  ├─ 兼容旧接口
  ├─ 幂等请求处理
  ├─ 预览/申请/确认/释放 API
  └─ 领域扩展注册
          |
编码规则核心层
  ├─ 规则版本解析
  ├─ 规则匹配与解释
  ├─ 编号组装
  ├─ 唯一性校验
  └─ 生命周期状态机
          |
流水与持久化层
  ├─ 流水段分配
  ├─ 数据库唯一约束
  ├─ 请求与结果记录
  ├─ 断号/释放记录
  └─ 审计事件
```

编码平台只负责“根据已授权的业务输入，产生并管理编号状态”。组织、商户、租户和数据权限由调用方传入明确的作用域字段，平台不得根据同名字段自行推断租户隔离关系。

### 3.2 核心组件

| 组件 | 职责 | 可靠性要求 |
|---|---|---|
| `RuleCatalog` | 规则、版本、条件和组织范围管理 | 发布校验、版本不可变、配置审计 |
| `RuleMatcher` | 根据业务对象和作用域选择规则 | 决策可解释、无匹配明确报错 |
| `NumberRenderer` | 按规则项生成编号文本 | 纯函数、格式边界可测试 |
| `SerialAllocator` | 在流水作用域内分配序号 | 数据库唯一约束、并发安全 |
| `NumberLifecycle` | 管理预览、申请、确认、释放和作废 | 状态转移幂等、非法转移拒绝 |
| `NumberUniqueness` | 检查平台内、业务表和外部输入冲突 | 约束与应用校验双保险 |
| `RecoveryWorker` | 处理超时申请、补偿和差异核对 | 可重试、可暂停、告警不吞错 |
| `LegacyAdapter` | 兼容旧版 helper、插件和批量接口 | 保留旧返回语义并记录来源 |
| `AuditRecorder` | 记录规则、请求、结果和操作证据 | 摘要化、脱敏、不可篡改或追加写 |

## 4. 规则模型

### 4.1 规则主表

建议规则主表至少包含：

| 字段 | 含义 |
|---|---|
| `rule_id` | 规则稳定标识，不因版本发布改变 |
| `rule_version` | 规则版本，发布后不可原地修改 |
| `biz_object_id` | 业务对象或实体标识 |
| `scope_type` | 组织、门店、项目或其他业务作用域类型 |
| `scope_id` | 作用域值 |
| `include_children` | 是否包含下级组织 |
| `condition_expression` | 可解析的条件表达式 |
| `serial_scope_expression` | 决定流水是否分段的字段表达式 |
| `status` | 草稿、已发布、已停用、已归档 |
| `effective_from` / `effective_to` | 生效时间窗口 |
| `priority` | 明确的规则优先级 |
| `allow_preview` | 是否允许预览 |
| `allow_manual_input` | 是否允许手工输入 |
| `reuse_policy` | 不回收、仅事务失败回收、允许受控断号重用 |
| `created_by` / `published_by` | 配置审计信息 |

规则版本发布后不允许直接修改组成项、条件、流水初始值和步长。新配置必须生成新版本，避免同一编号在不同时间无法解释。

### 4.2 规则项

规则项支持以下类型：

- 固定文本；
- 系统时间或业务日期；
- 业务属性；
- 流水序号；
- 校验码；
- 分隔符。

每个规则项应明确：顺序、是否可见、长度、格式、截取方向、补位字符、补位方向、是否参与流水分段、是否参与唯一性组成。规则项解析失败时必须返回结构化错误，不得静默转为空串。

### 4.3 条件匹配优先级

规则选择采用确定性排序，不依赖缓存返回顺序：

1. 业务对象精确匹配；
2. 当前作用域精确匹配；
3. 直接组织规则优先于上级组织继承规则；
4. 条件具体度更高的规则优先；
5. 生效版本优先；
6. 显式 `priority` 数值更高者优先；
7. 仍然相同则判定为配置冲突，禁止随机选择。

配置发布前必须执行冲突检测，至少覆盖：同一业务对象、同一作用域、重叠生效时间、条件可能重叠、优先级相同的规则。发布失败时不影响当前已发布版本。

## 5. 编号生命周期

### 5.1 状态

```text
PREVIEWED -> REQUESTED -> CONFIRMED
                 |
                 +-> RELEASED
                 +-> EXPIRED
                 +-> VOIDED
```

- `PREVIEWED`：只计算候选值，不推进正式流水，不代表编号已占用。
- `REQUESTED`：已经申请并登记请求幂等键，编号暂时归属于一次业务请求。
- `CONFIRMED`：业务单据保存或提交成功，编号正式生效。
- `RELEASED`：申请未成功，编号按规则允许释放。
- `EXPIRED`：请求超过租约时间仍未确认，进入补偿流程；不能直接复用。
- `VOIDED`：编号已被确认但因业务原因作废，不再回收重用。

### 5.2 幂等键

正式申请必须由调用方提供稳定幂等键，例如：

```text
idempotency_key = 业务系统标识 + 业务单据临时主键 + 操作类型 + 业务版本
```

同一幂等键重复调用时，返回第一次成功申请的结果。请求参数摘要不一致时返回幂等键复用冲突，禁止覆盖原结果。

幂等记录至少保存：幂等键、业务对象、业务作用域、规则版本、结果编号、状态、请求摘要、创建时间和最后更新时间。敏感业务正文不进入编码平台日志。

### 5.3 确认边界

推荐由业务服务在同一数据库事务内完成：

1. 申请编号并写入编号申请记录；
2. 写入业务单据编号；
3. 执行业务表唯一约束校验；
4. 业务事务提交后将申请状态确认。

如果编码平台与业务库不在同一事务域，不能伪装成原子操作，应采用“申请记录 + 业务单据唯一约束 + 可重试确认 + 对账补偿”的最终一致方案，并明确业务方可以接受的中间状态。

## 6. 流水号可靠性设计

### 6.1 流水作用域

流水分段键由以下内容组成：

```text
规则版本 + 业务作用域 + serial_scope_expression 计算结果
```

例如按组织和业务日期分段时，组织或日期必须进入稳定的规范化键。分段键不得直接使用未经长度限制和字符规范化的外部文本，避免键膨胀、注入或不同表示形式产生重复分段。

### 6.2 分配策略

首选数据库原子更新加唯一约束：

```text
BEGIN
  读取并锁定 serial_scope
  next_value = current_value + step
  写回 current_value
  插入 number_reservation 唯一记录
COMMIT
```

当使用号段缓存优化吞吐时，号段必须先在数据库中原子预占，实例重启后未使用号码默认视为已占用或进入明确的作废状态，不得未经审计重新发放。高并发场景可以使用号段，但不能让内存缓存成为唯一事实来源。

### 6.3 数据库保护

至少设置以下唯一约束：

- `number_reservation(idempotency_key)`；
- `number_reservation(rule_version, serial_scope_key, serial_value)`；
- 业务单据表中按业务规定的编号唯一或组合唯一约束。

应用层重复检查用于提前返回友好错误，数据库唯一约束用于最终防线。两者不应互相替代。

### 6.4 预览语义

预览只读取规则和计算格式，不写入最大流水、正式申请或断号记录。若业务确实需要“占位预览”，必须调用单独的申请接口并展示租约过期时间，不能继续沿用 `readNumber` 的模糊语义。

## 7. 释放、回收和作废

### 7.1 默认原则

编号一旦进入 `CONFIRMED`，默认不可回收重用。已打印、已发送、已被下游引用或已进入财务凭证链路的编号，只能作废并保留原记录。

仅在以下条件同时成立时允许释放或回收：

- 业务操作未成功提交；
- 编号没有对外发布或被其他业务引用；
- 规则版本的 `reuse_policy` 明确允许；
- 释放动作可审计且幂等；
- 重新使用不会破坏历史查询和对账。

### 7.2 断号处理

断号记录应使用独立状态：`AVAILABLE`、`CLAIMED`、`CONSUMED`、`INVALIDATED`。读取候选和消费候选必须分开：

- 预览只读取，不改变状态；
- 正式消费通过条件更新将 `AVAILABLE` 改为 `CLAIMED`；
- 业务确认后改为 `CONSUMED`；
- 业务失败按规则释放或作废；
- 任何状态更新失败都必须可重试且不能重复消费。

## 8. 失败处理与补偿

### 8.1 错误分类

| 错误 | 处理 |
|---|---|
| 规则不存在 | 不自动降级到默认规则，返回可定位错误 |
| 多条规则冲突 | 发布阶段阻断；运行时保护性失败 |
| 规则字段缺失 | 业务请求失败，记录字段名和规则版本 |
| 流水存储不可用 | 有界重试，超过阈值告警并失败 |
| 唯一键冲突 | 重新申请仅限自动编号；手工编号直接返回冲突 |
| 幂等参数不一致 | 返回幂等键冲突，不覆盖原结果 |
| 业务提交后确认失败 | 对账任务补偿确认，不重复申请新编号 |
| 申请超时 | 标记 `EXPIRED`，由补偿任务决定释放或作废 |

### 8.2 对账任务

至少提供三类对账：

1. 编号申请记录与业务单据编号字段对账；
2. 流水最大值与已分配编号最大值对账；
3. 断号状态与业务实际引用对账。

对账只能生成差异清单和受控修复任务，不能默认批量改写业务数据。修复动作必须有范围、操作者、前后摘要、审批记录和可重复执行标识。

## 9. 接口设计

### 9.1 规则查询

```text
GET /api/numbering/rules/match
```

输入：业务对象、明确的业务作用域、规则匹配字段、调用方版本。

输出：规则 ID、规则版本、匹配原因摘要、流水作用域摘要、是否允许预览和手工输入。输出不返回完整业务对象。

### 9.2 预览

```text
POST /api/numbering/preview
```

预览接口无副作用，返回候选编号、规则版本、格式校验结果和解释信息。预览结果必须标记为不可直接作为正式编号使用。

### 9.3 申请

```text
POST /api/numbering/requests
```

输入包含幂等键、业务对象、业务作用域、规则匹配字段、编号来源和请求摘要。成功返回申请 ID、编号、规则版本、状态和确认期限。

### 9.4 确认、释放和作废

```text
POST /api/numbering/requests/{requestId}/confirm
POST /api/numbering/requests/{requestId}/release
POST /api/numbering/requests/{requestId}/void
```

所有动作必须幂等。确认已确认、释放已释放等重复动作返回当前状态；确认已释放、释放已确认等非法动作返回状态冲突。

### 9.5 兼容接口

旧版 `getNumber`、`readNumber`、批量取号和回收接口通过 `LegacyAdapter` 转换到新生命周期。兼容层必须记录旧调用来源、映射后的幂等键和规则版本。旧接口无法提供稳定幂等键时，默认只允许预览或要求调用方升级，不能在平台内部凭随机值伪造幂等保证。

## 10. 扩展机制

### 10.1 标准规则扩展

通过规则项类型和格式化器扩展，不允许业务模块直接修改流水分配器。新增规则项必须满足：

- 有纯函数计算逻辑；
- 明确输入字段、长度和字符集；
- 有边界测试和版本兼容说明；
- 不读取完整业务对象并写入日志；
- 不在渲染器中执行业务副作用。

### 10.2 领域专用编码

凭证号、资产卡片号、批次号等领域编号可以注册专用编码器，但必须声明：

- 是否复用平台流水；
- 是否复用平台唯一性；
- 是否允许回收；
- 业务作用域和租户/组织边界；
- 失败重试和对账方式；
- 与标准编号接口的兼容映射。

完全自定义编码器仍需登记编号来源、唯一性证明、审计字段和历史查询方式，不能以“插件自定义”为由绕过平台治理。

## 11. 缓存与配置发布

规则缓存只缓存已发布版本。缓存键必须包含业务对象、作用域和规则版本上下文；缓存失效采用版本切换优先，删除缓存作为辅助措施。

发布流程：

```text
草稿 -> 静态校验 -> 冲突检测 -> 影子匹配验证 -> 发布新版本
     -> 广播版本变更 -> 节点加载确认 -> 观察 -> 停用旧版本
```

旧版本在兼容窗口内保持可读取，以便历史单据回显和重试。停用规则不能删除历史规则版本，至少保留到所有引用和对账周期结束。

## 12. 可观测性与审计

### 12.1 指标

- 规则匹配成功率、无匹配率和冲突率；
- 预览、申请、确认、释放、作废数量；
- 幂等命中率和幂等参数冲突数；
- 流水分配耗时、锁等待、唯一键冲突和重试次数；
- 申请超时、确认补偿和对账差异数量；
- 每条规则版本的编号失败率。

### 12.2 日志

日志只保留：请求 ID、幂等键摘要、业务对象、规则 ID/版本、作用域摘要、编号摘要、状态转移和错误码。手机号、地址、证件、完整业务对象、token、支付信息和完整请求响应禁止写入日志。

审计记录需要回答：谁在什么时间发布了什么规则、哪个调用方以什么规则版本申请了什么编号、为什么释放或作废、谁执行了补偿。审计事件采用追加记录，不允许通过更新覆盖历史事实。

## 13. 测试策略

### 13.1 单元测试

覆盖：

- 规则匹配优先级和组织继承；
- 条件表达式边界、空值和类型转换；
- 前缀、日期、业务字段、补位、截取和分隔符；
- 流水初始值、步长、长度溢出和自动增长；
- 校验码和非法输入；
- 生命周期合法与非法状态转移。

### 13.2 集成测试

覆盖：

- 多线程和多节点并发申请不重复；
- 同一幂等键重试只得到同一结果；
- 不同作用域流水互不污染；
- 数据库唯一约束冲突时应用正确补偿；
- 业务事务失败后的释放或作废；
- 配置发布、缓存失效和旧版本读取；
- 断号预览不消费，正式消费不重复。

### 13.3 故障演练

至少演练：

- 流水数据库短暂不可用；
- 节点在申请后、确认前重启；
- 确认接口超时但业务事务已提交；
- 号段缓存节点失联；
- 配置发布广播丢失；
- 唯一索引冲突和重复回调；
- 对账任务中断后重跑。

验收不能只看接口返回成功，还要检查数据库状态、业务单据、唯一约束、审计事件和补偿结果。

## 14. 迁移方案

### 14.1 第一阶段：盘点与冻结事实

建立现有业务对象、规则、组织范围、编号样例、最大流水、断号记录、领域插件和外部接口清单。区分直接事实、推断和待确认项。对历史编号只读迁移，不改写既有编号。

### 14.2 第二阶段：影子匹配

新平台只执行规则匹配和编号渲染，不写入业务库、不推进流水、不发送消息。将新旧规则的规则 ID、版本、编号摘要和差异字段进行脱敏比对。差异达到上线阈值前不切换正式取号。

### 14.3 第三阶段：新单据灰度

按业务对象或组织启用新平台。旧接口通过适配层进入新平台，保留快速关闭开关。新写入编号必须能被旧查询和报表读取；旧规则版本继续保留，确保回滚后新数据不会无法读取。

### 14.4 第四阶段：扩展与收口

完成历史数据核对、外部接口验证、对账周期观察和故障演练后，再停用旧取号路径。旧路径停用前必须确认没有未处理申请、未完成补偿、未对账差异和隐藏调用方。

## 15. 回滚方案

- 规则匹配错误：停用新规则版本，恢复上一已发布版本。
- 新平台接口故障：关闭业务对象级开关，回到旧适配路径；已申请编号不得重复申请，需先按幂等记录核对。
- 数据库结构问题：保留旧字段和旧表，使用前向修复，不直接删除结构。
- 新平台已产生确认编号：不回收、不重编号，回滚后旧系统必须兼容读取这些编号。
- 对账差异：暂停自动修复，导出脱敏差异清单，由人工确认后执行幂等修复。

## 16. 待确认项

| 待确认项 | 已知证据 | 保守处理 |
|---|---|---|
| 生产环境分布式锁实现和租约 | 现有源码出现锁调用，但未完整提供依赖实现 | 新平台以数据库唯一约束为最终防线 |
| 现有最大流水和断号表索引 | 反编译源码未提供完整 DDL | 上线前必须取得 DDL 和索引证明 |
| 复杂过滤条件的 AND/OR 语义 | 由运行时条件组件解释 | 发布前用真实配置建立特征化测试 |
| 外部携带编号的所有来源 | 现有插件区分导入、OpenAPI、下推等来源 | 先按不可信外部输入校验，不自动认领 |
| 物业租赁单据的实际租户键 | 不能由组织字段或 `pid` 名称推断 | 由业务服务显式传入并验证实际租户/商户范围 |
| 对外已发布编号的判定 | 依赖打印、接口和下游单据链路 | 默认确认后不可回收，待业务补充引用状态 |

## 17. 结论

可靠的单据编码平台不是一个“拼接字符串并加一”的工具，而是由规则版本、确定性匹配、并发安全流水、生命周期状态、唯一性约束、失败补偿、审计和兼容适配共同组成的基础设施。

新平台应优先保证以下不变量：

1. 同一流水作用域内，正式确认编号不重复。
2. 同一幂等请求不会得到两个不同正式编号。
3. 预览不会被误认为正式消耗。
4. 已确认且可能被外部引用的编号不自动回收。
5. 规则冲突和字段缺失不会静默降级到不可解释的默认规则。
6. 失败、超时和确认异常都有可重试、可对账的记录。
7. 历史编号、旧调用方和领域扩展在迁移期间仍可被识别和读取。

该方案可以作为后续详细设计、数据库建模、接口契约和分阶段实施计划的共同基线。
