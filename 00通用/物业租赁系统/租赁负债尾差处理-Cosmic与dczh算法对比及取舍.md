# 租赁负债尾差处理：Cosmic 与 dczh 算法对比及取舍

> 对比对象：金蝶 Cosmic `biz/fi-fa`（`D:\cosmic-src` 反编译源码）与 dczh `yudao-module-dcfee` 的租赁资产初始单测算、租赁资产摊销计划。
> 路径约定：Cosmic 省略 `biz/fi-fa/src/main/java/kd/fi/fa/business/lease/`；dczh 省略 `yudao-module-dcfee/src/main/java/cn/iocoder/yudao/module/dcfee/`。
> 依据：直接阅读两边源码。没有用同一份合同在两边跑数值对比；文中的误差量级是理论推算。

## 1. 结论

- Cosmic 只有一套计算：先生成逐日利息明细 `fa_interest_detail`，租金结算和负债余额都从这张表汇总。
- 尾差的处理办法是先锁定总利息（负债原值 − 负债现值），在最后付款日的前一天，用"总利息 − 已确认利息"倒挤出当天的利息。负债余额一定归零，不设任何容差。
- dczh 的初始测算和测算页分期测算表已经是"全额吸收"的思路。摊销计划是另一套独立的计算，尾差超过 0.01 元就报错，这是已审核单据生成摊销计划失败的直接原因（缺陷 D2）。
- Cosmic 做法的好处是稳：一定能生成、一定平衡。代价是对数据错误不设防，差额再大也会被悄悄吸收。
- 对 dczh 的建议：借鉴总利息守恒和单一数据源，不照搬无上限吸收和"付款前一天"这两点。

## 2. Cosmic 如何处理尾差

### 2.1 锁定总利息，最后付款日前一天倒挤

位置：`InterestDetailGenerator.java:120-137`、`251-266`。

```java
notConfirmFinCost = leaseliabori - leaseliab;          // 总利息 = 负债原值 - 负债现值
dealTailDiffDate  = 最后付款日 - 1 天;
每天: leaseLiabInt = (尾差日) ? notConfirmFinCost - sumInterest
                             : (期初余额 - 当日付款) × 日利率;
      leaseLiabInt 按币种精度舍入（人民币 2 位）;
      期末余额 = 期初 - 当日付款 + 当日利息;
```

- 计息顺序是先扣当天付款，再按剩余余额计息。最后付款日当天余额正好等于当天付款，利息为 0，期末余额正好是 0。
- 期末归零靠恒等式保证：利息合计 = 总利息，付款合计 = 负债原值，所以期末余额 = 负债现值 + 利息合计 − 付款合计 = 0。
- 代码里没有尾差上限检查，尾差多大都会被这一天吸收。

### 2.2 每天的利息舍入到分，期间数据直接汇总

- 每一天的利息先舍入到币种精度（`InterestDetailGenerator.java:134`）。
- 租金结算（`RentSettleGenerator.java:119-153`）按会计期间把逐日的付款、利息直接相加，期末余额取期间最后一天的余额。
- 每一行本身就是精确到分的金额，汇总后天然对得上账。

### 2.3 实际日利率：在倒挤之前先缩小偏差

- 每天舍入到分，几年下来会累积出明显偏差。
- 两种情况下，Cosmic 用 `RealDailyIntRateCalculator` 反求日利率，让"每天舍入后的利息合计"尽量接近总利息：利息摊销选方案 B，或者合同不是新增合同。
- 做法：日利率反复乘 0.98 或 1.01，直到落在两个值之间，再做一次线性插值（`RealDailyIntRateCalculator.java:118-165`）。剩余差额仍由尾差日吸收。
- 新增合同走方案 A 时直接用名义日利率，不反求（`InterestDetailGenerator.java:244-248`）。

### 2.4 金额拆分时的尾差

方案 B 把一笔多月付款平均分到每个月，豁免合同按月均摊。这两种情况下，前面几份按"总额 ÷ 份数"舍入到分，最后一份 = 总额 − 前面几份之和（`InterestDetailGenerator.java:391-401`、`325-336`）。

### 2.5 现值逐笔舍入

`utils/LeaseUtil.java:434-440`：折现因子 `(1+日利率)^天数` 保留 10 位小数，每笔现值单独舍入到分，负债现值 = 各笔现值之和。dczh 也是这样做的。逐笔舍入是尾差的主要来源，Cosmic 靠 2.1 的倒挤消化掉。

## 3. dczh 现在的尾差处理

| 位置 | 做法 | 与 Cosmic 比较 |
|---|---|---|
| 测算明细 `service/roucalc/RightOfUseCalcServiceImpl#aggregatePeriodInterest`（初始单保存的付款明细） | 最后一期利息 = 付款 − 期初余额，期末强制为 0 | 结果相同：全额吸收、不设上限。差别是吸收在最后一次付款那一行，而不是付款前一天；也没有用总利息做控制目标 |
| 测算页分期测算表 `RightOfUseCalcServiceImpl#calculatePeriodLedgers` | 调整额 = (付款合计 − 负债现值) − 逐日利息合计，记在最后付款日所在期间 | 最接近 Cosmic：用总利息做目标，全额吸收，单独显示为结清调整 |
| 摊销计划 `service/rentamortization/RentAmortizationCalculator:88-102` | 每月利息先舍入到分，按显示金额推出期末负债；最后一个月尾差超过 0.01 元就报错 | 与 Cosmic 不一致：没有总利息目标，容差只有 0.01 元 |

实例：4 号单据（合同 3，60 期月付，年利率 5%，负债现值 924,260.35）。按摊销计划计算器逐月推算，最后一个月的期末负债为 0.02 元；按月累计的利息为 119,739.67 元，而"租金总额 − 负债现值"应为 119,739.65 元。尾差超过 0.01 元，生成摊销计划时报"摊销计划输入数据无效"。

另外，dczh 的测算和摊销计划是两套独立算法，各自计算一遍，同一份合同在两边可能差几分钱。Cosmic 只算一次逐日明细，结算和余额都从它派生，不存在这个问题。

## 4. 其他算法差异

| 环节 | Cosmic | dczh |
|---|---|---|
| 计息和折现起点 | 初始确认日 = max(免租开始日或租赁开始日, 首次执行日)；存量合同用系统切换日（`getDetailBeginDate`） | 合同起租日 |
| 计入负债的付款 | 付款项目核算分类为 A，且付款日不早于起点；金额取未付租金 | 付款计划全部期次的基础租金（抽成不计） |
| 日利率 | 复利 `(1+r)^(1/365)-1`，系统参数可切换为单利 `r/365` | 只有复利 |
| 每天的利息 | `(期初 − 当日付款) × 日利率`，从起点当天开始计，每天舍入到分 | `期初 × 日利率`，从起租次日开始计，保留 10 位小数，先计息后扣付款 |
| 计息截止 | max(租赁结束日, 最后付款日) | 测算到最后付款日；摊销计划到租赁结束日 |
| 期间归属 | 按会计日历查期间，找不到就报错；新增合同中早于入账期间的日期计入入账期间 | 测算表按配置的会计期间，没配置按自然月；摊销计划按自然月，期间名称读配置；没有"计入入账期间"的规则 |
| 期间利息 | 逐日利息直接相加 | 用"期末 − 期初 + 本期租金"反推 |
| 实际日利率、方案 B 付款拆分 | 有 | 没有 |
| 短期豁免 | 负债和资产置 0，只生成付款记录 | 没有 |
| 使用权资产 | 负债现值 + B 类付款，按增值税参数调整税额；过渡方案 A/C 另按租赁期开始日折现 | 负债现值 + 初始直接费用 + 预付租金 + 复原义务 − 租赁激励（固定字段） |
| 折旧 | 合同推送成固定资产卡片，由折旧引擎计提 | 摊销计划内按天直线法计提 |

关于计息顺序：Cosmic 先扣付款再计息、从第 0 天开始计；dczh 先计息再扣付款、从第 1 天开始计。两种写法和各自的现值公式都自洽，余额序列相同，只是每天的利息在 Cosmic 那边整体提前一天记录。因此月份交界处两边每月利息可能差几分钱，总利息不受影响。

## 5. Cosmic 做法的好处与缺点

### 5.1 逐日明细作为唯一数据源

好处：

- 口径一致：结算单、负债余额表、摊余成本报表都从同一份数据汇总，不会两边差几分钱。
- 可以审计：任意一天的期初余额、付款、利息、期末余额都查得到。
- 方便变更和终止：终止时从终止日起生成反向记录（`sourcetype B`）冲销后续数据，历史行保留不动。
- 期间配置改了不用重算：只需把逐日数据重新按会计期间汇总。

缺点：

- 数据量大：每份合同每天一行，10 年期约 3,650 行，一千份合同就有几百万行；合同变更要重写大段数据。
- 生成慢：每天都要格式化日期、查字符串 Map；`formatDate` 每次调用都新建 `SimpleDateFormat`（`InterestDetailGenerator.java:609-614`）。
- 算法升级要迁移数据：明细已存库，改算法时历史数据要么迁移，要么新旧口径并存。

### 5.2 锁定总利息、付款前一天倒挤

好处：

- 一定平衡：负债归零、未确认融资费用全部摊完，靠恒等式保证。
- 一定能生成：不会因为舍入误差拒绝生成。
- 规则简单：财务和审计人员容易理解。

缺点：

- 数据错误会被掩盖（最主要的缺点）：没有任何上限。付款计划改了但现值没重算、利率和现值口径不一致，差几百甚至几千元也会全部塞进一天，系统不报错。
- 可能出现负利息：主流程不检查倒挤利息是否为负（只有实际利率计算器在参数关闭时检查）。舍入累积多算时，这一天利息为负，当期利息费用出现异常跳动。
- 可能落到上一个期间：尾差日是"最后付款日前一天"。最后一笔付款在每月 1 号时，尾差记进上个月。
- 显示利率和实际利息对不上：倒挤那天的利息不是按利率算的，`realdailyrate` 仍显示名义利率。

### 5.3 每天的利息舍入到分

好处：每一行都是可以直接入账的金额，按期间相加不会出现分差，明细和凭证金额一致。

缺点：

- 舍入误差会累积：每天最多差 0.005 元；10 年约 3,650 天，正负抵消后一般在几毛钱以内，最坏情况能到十几元，最后全部压到尾差日。
- 因此才需要实际利率计算器来缩小倒挤金额。

### 5.4 实际日利率迭代

好处：

- 利息更平滑：倒挤金额变小，更接近实际利率法，更符合准则要求。
- 付款重新分配时必须用：方案 B 改变了现金流，名义利率与新现金流对不上，只能反求。

缺点：

- 不是精确解：按 0.98、1.01 倍数试探再线性插值，仍留差额，还得靠尾差日吸收。
- 计算量大：每试一次都要重算全部天数，计算量是"天数 × 迭代次数"。
- 用浮点数计算：每天 `Math.round` 舍入后累加，最后才转 BigDecimal，与其他金额计算的精度方式不一致。
- 限制多：年利率为 0 直接报错；利息合计为负也报错（受参数控制）。
- 业务上难解释：最终日利率与合同填写的折现率不同，需要向业务和审计说明。

### 5.5 先扣当天付款再计息、起点当天就计息

好处：

- 期初付款不用特殊处理：当天付的款当天不计息。
- 和折现公式一致：第 t 天的付款正好计 t 天利息，与 `P/(1+d)^t` 对得上。

缺点：

- 按月汇总时会差一点：每天的利息记在计息日的前一天，月末交界处两个月之间会差几分钱。
- 口径不同：与"先计息后扣款"的系统对账时，每天的数字对不上，需要先换算。

### 5.6 按会计日历归属期间

好处：

- 强制维护会计期间：查不到期间直接报错，数据不会落到无效期间。
- 不改已关账期间：早于入账期间的利息集中补记到入账期间。

缺点：

- 期间要提前维护：必须一直维护到租赁结束日，10 年期合同要提前建好 10 年期间，否则整份合同生成不了。
- 补记月份利息偏高：补记的利息集中在入账期间，这个月的利息费用明显偏大。

### 5.7 付款拆分时尾差放在最后一份

好处：写法简单，总额分毫不差。

缺点：最后一个月的金额和其他月份不一样，份数越多越明显，月报看起来不均匀。

## 6. 对 dczh 的取舍建议

| Cosmic 的做法 | 建议 | 理由 |
|---|---|---|
| 锁定总利息、倒挤尾差 | 借鉴 | 解决 D2 的核心，保证一定能生成、负债一定归零 |
| 不设尾差上限 | 不照搬，保留宽松上限（如期数 × 0.01 元） | 吸收正常舍入误差，同时拦下数据不一致等真实错误 |
| 尾差放在"最后付款日前一天" | 改为最后付款日所在期间 | 避免尾差落到上个月；dczh 测算页现在就是这样做的 |
| 单一数据源 | 借鉴 | 摊销计划复用测算页的期间数据，审核前后数字一致 |
| 逐日明细存入数据库 | 暂不做 | dczh 每次查询时重新计算，结果可复现；做合同变更和终止冲销时再考虑 |
| 实际日利率 | 暂不做 | dczh 目前只有新增合同，按 Cosmic 规则也用名义利率 |
| 每天舍入到分 | 不照搬 | dczh 逐日计算保留 10 位小数，只在期间汇总时舍入，累积误差更小、倒挤金额更小 |

据此，dczh 修复 D2 的方案（已实施）：

1. 总利息 = 付款合计 − 初始负债；逐日利息与总利息的差额全部计入最后付款日，期末负债为 0，差额记入结清调整 `settlementAdjustment`（`RightOfUseCalcServiceImpl#calculatePeriodLedgers`）。
2. 去掉 0.01 元的硬性容差，改为宽松上限"付款笔数 × 0.01 元"，超过报错 `RIGHT_OF_USE_CALC_TAIL_DIFF_EXCEEDED`。
3. 摊销计划直接复用测算页分期测算表（`RightOfUseCalcService#getSchedule`），不再用 `RentAmortizationCalculator` 单独计算；`CALCULATION_VERSION` 升级到 `monthly-v5`，已生成的计划下次生成时产生新版本，旧版本保留。

实施后用 4 号单据的实际数据复算：60 行，最后一期期末负债 0.00，结清调整 −0.04 元（在 60 × 0.01 = 0.60 元上限内），利息合计 119,739.65 元（等于付款合计 − 负债现值），折旧合计 924,260.35 元，末期资产余额 0.00，各期期初与上期期末衔接。

## 7. 未核实事项

- Cosmic `DateUtil.getDiffDays` 是否包含首尾两天。
- `LeaseUtil.irr` 具体在哪种租金结算方案中被调用。
- 实际日利率分支在 dczh 现有业务中是否会用到。目前 dczh 只有新增合同，按 Cosmic 规则走名义日利率，用不到。
- 两边没有用同一份合同做逐日数值对比。
