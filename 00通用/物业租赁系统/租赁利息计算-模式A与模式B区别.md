# 租赁利息计算：模式A与模式B的区别

## 一、概述

在租赁负债的利息分摊计算中，系统提供两种不同的日利率计算模式：

| 模式 | 名称 | 说明 |
|------|------|------|
| 模式A | 直接使用合同日折现率 | 简化计算，直接使用合同中设定的日利率 |
| 模式B | 迭代计算实际日利率 | 精确计算，通过迭代找到使利息总额精确匹配的日利率 |

---

## 二、为什么需要两种模式？

这是一个**简化 vs 精确**的设计权衡，核心原因是**首次确认与后续变更的业务本质不同**。

### 2.1 新增合同：简化处理足够

**场景分析**：
- 负债现值是**根据合同日利率计算出来**的
- 日利率和负债现值之间**数学上是一致的**
- 利息分摊只是把这个"已确定"的利息分配到每天

```
计算过程：
  第1期租金 ÷ (1+日利率)^天数 = 租金现值
  第2期租金 ÷ (1+日利率)^天数 = 租金现值
  ...
  Σ租金现值 = 负债现值

  负债现值已经"使用"了日利率来计算
  用同一个日利率来分摊利息，逻辑上自洽
```

**直接用合同日利率的误差来源**：
- 年利率转日利率时，复利法需要开365次方，有微小近似误差
- 但这个误差**非常小**（约0.2%），对于首次确认可以接受
- 而且首次确认时，还没有实际发生利息，用近似值是合理的

### 2.2 变更/续租：需要精确匹配

**场景分析**：
- 合同条款发生变化（租期延长、租金调整等）
- 负债原值和现值需要**重新计算**
- 利息分摊是**在已有基础上调整**，精度要求更高

```
变更场景示例：
  原合同：100万/2年，已执行1年，剩余负债现值45万
  变更：租期延长1年，新负债现值变为50万
  
  新增利息 = 50万 - 45万 = 5万
  
  如果用模式A（简化）：
  - 新增利息计算可能有误差
  - 累计误差会越来越大
  
  必须用模式B（精确）：
  - 确保新增利息 = 5万，精确无误
```

### 2.3 两种模式的业务逻辑对比

| 场景 | 业务本质 | 处理方式 | 选用模式 |
|------|----------|----------|----------|
| 新增合同首次确认 | 从零开始建立租赁关系 | 简化处理，快速完成 | 模式A |
| 租赁变更 | 在原基础上调整条款 | 重新精确计算 | 模式B |
| 续租 | 旧合同终止，新合同开始 | 视为新合同，但需要衔接 | 模式B |
| 初始存量租赁 | 系统切换前已存在的合同 | 需要追溯处理 | 模式B |

### 2.4 为什么不是"全用精确模式"？

既然模式B更精确，为什么不全部使用模式B？

| 原因 | 说明 |
|------|------|
| **性能考虑** | 迭代计算需要多次循环，性能开销约10-50倍 |
| **首次确认差异小** | 新增合同的误差仅0.2%，可接受 |
| **实务惯例** | 首次确认用合同利率是行业通行做法 |
| **减少复杂度** | 首次确认场景最多，简化处理覆盖大多数场景 |

### 2.5 为什么不是"全用简化模式"？

既然模式A更快，为什么还需要模式B？

| 原因 | 说明 |
|------|------|
| **变更需要精确** | 变更时如果不精确，会导致累计误差 |
| **财务一致性** | 确保利息分摊的数学一致性是财务合规要求 |
| **长期影响** | 变更/续租后继续用近似值，误差会累积 |
| **审计要求** | 审计时需要利息分摊的精确数据 |

### 2.6 核心设计思想

```
┌─────────────────────────────────────────────────────────────────┐
│                      两种模式并存的设计思想                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  首次确认 → 简化优先                                              │
│  ├─ 从零开始，数学上自洽                                          │
│  ├─ 误差微小（0.2%），业务可接受                                  │
│  └─ 性能最优，用户体验好                                          │
│                                                                  │
│  变更/续租 → 精确优先                                             │
│  ├─ 在已有基础上调整，不允许误差                                    │
│  ├─ 累计影响大，必须精确                                          │
│  └─ 财务合规要求                                                  │
│                                                                  │
│  核心思想：不同业务场景用不同的精度要求                            │
└─────────────────────────────────────────────────────────────────┘
```

### 2.7 触发条件分析（源码级）

> **重要发现**：根据星空金蝶源码分析，模式A与模式B的切换不是按"业务场景"区分，而是按**配置参数**和**数据来源**区分。

#### 源码证据

在 `InterestDetailGenerator.getDailyRate()` 中：

```java
protected BigDecimal getDailyRate(DynamicObject leaseContract, Map<String, BigDecimal> amountMap) {
    // 获取系统参数
    String interestAmortizeSchema = SystemParamHelper.getStringParam("interest_amortize_schema", ...);

    // 获取合同来源类型
    String sourceType = leaseContract.getString("sourcetype");

    // 判断条件：利息摊销模式 == A 且 来源类型 == A
    if (InterestAmortizeSchema.A.name().equals(interestAmortizeSchema)
        && LeaseContractSourceType.A.name().equals(sourceType)) {
        // 模式A：直接使用合同日折现率
        BigDecimal dailyDiscountRate = leaseContract.getBigDecimal("dailydiscountrate");
        return dailyDiscountRate.divide(FaBigDecimalUtil.HUNDRED, 10, ...);
    }

    // 否则：模式B - 迭代计算日利率
    return new RealDailyIntRateCalculator(leaseContract, ...).calculate();
}
```

#### 判断条件

| 条件组合 | 结果 | 说明 |
|---------|------|------|
| 利息摊销模式 = A **且** 来源类型 = A | **模式A** | 新增合同首次确认 |
| 利息摊销模式 = B | **模式B** | 无论什么来源类型都需要迭代 |
| 来源类型 = B 或 C | **模式B** | 变更单或续租单 |
| 其他情况 | **模式B** | 默认用模式B |

#### 简化记忆

```
只有【同时】满足以下两个条件，才用模式A：
  ✓ 利息摊销模式 = A
  ✓ 来源类型 = A（新增合同）

其他情况全部用模式B：
  ✗ 利息摊销模式 = B → 模式B
  ✗ 来源类型 = B/C → 模式B
```

#### 为什么不是"合同变更"场景？

之前推测星空迭代是因为"合同变更"，但源码分析表明：

1. **不是按业务场景区分**（新增/变更/续租）
2. **是按配置+数据属性区分**（利息摊销模式 + 来源类型）

可能的业务原因：

| 原因 | 说明 |
|------|------|
| **存量数据迁移** | 系统上线前已存在的合同，数据来源可能不是"A" |
| **手工调整** | 某些合同可能手工修改过日利率 |
| **配置差异** | 不同组织的配置可能不同 |

**本质**：星空的日折现率可能来自多个来源，不一定都是通过公式计算的，因此需要迭代来"反推"精确的日利率。

## 三、核心概念

### 2.1 关键术语

| 术语 | 英文 | 说明 | 示例 |
|------|------|------|------|
| 负债原值 | Lease Liab Original | 未来应付租金的累加值 | 100万 |
| 负债现值 | Lease Liab Present Value | 负债原值按日利率折现到初始确认日的价值 | 90万 |
| 未确认融资费用 | Unconfirmed Finance Cost | 负债原值与现值的差额，即总利息 | 10万 |
| 日折现率 | Daily Discount Rate | 年利率转换为日利率后的值 | 0.0137% |

### 2.2 基本公式

```
负债现值 = Σ [ 每期租金 ÷ (1 + 日利率)^天数 ]
未确认融资费用 = 负债原值 - 负债现值
```

## 三、日利率的计算

### 3.1 年利率转日利率

合同中的 `dailydiscountrate` 字段存储的是日折现率，其计算过程如下：

**第一步：年利率转小数**
```java
discountRate = 年折现率 ÷ 100
// 例如：5% → 0.05
```

**第二步：计算日利率**

系统参数 `dailydiscountrateformula` 控制计算方式：

| 公式 | 方法 | 公式 | 示例（年利率5%） |
|------|------|------|------------------|
| 复利法（默认） | `(1 + r)^(1/365) - 1` | `(1.05)^(1/365) - 1` | ≈ 0.00013377 |
| 单利法 | `r ÷ 365` | `0.05 ÷ 365` | ≈ 0.00013699 |

**复利法代码**（`LeaseContractCal.calDailyRateByCompoundInterest()`）：
```java
private static BigDecimal calDailyRateByCompoundInterest(BigDecimal discountRate) {
    BigDecimal number = BigDecimal.ONE.add(discountRate);  // 1 + r
    int n = 365;  // 固定365天（不考虑闰年）
    BigDecimal root = FaBigDecimalUtil.rooting(number, n, 10, 4);  // 10位精度，四舍五入
    return root.subtract(BigDecimal.ONE);  // (1+r)^(1/365) - 1
}
```

**第三步：存储为百分比形式**
```java
dailydiscountrate = 日利率 × 100  // 存储为 0.013377%
```

**精度说明**：
- 中间计算：10位小数
- 存储显示：8位小数
- 舍入方式：四舍五入（ROUND_HALF_UP）

### 4.2 计算逻辑

```java
// InterestDetailGenerator.getDailyRate() 第244-246行
if (利息摊销模式 == A && 来源类型 == A) {
    // 直接使用合同中的日折现率

```

### 4.3 计算公式

```
日利率 = 合同日折现率 ÷ 100
```

### 4.4 示例

假设：
- 年折现率 = 5%
- 负债现值 = 90万
- 租赁期 = 2年（730天）
- 日利率 = 0.013377%（复利法计算）

```
每日利息 = 90万 × 0.00013377 = 120.39元
2年利息总额 = 120.39 × 730 ≈ 87,885元
```

| 精度损失 | 利息总额可能 ≠ 未确认融资费用 |

### 5.4 源码解析

**迭代主方法**（`RealDailyIntRateCalculator.calculate()` 第98-168行）：

```java
public BigDecimal calculate() {
    // 1. 获取初始日利率
    double dailyRate = 合同日利率;
    
    // 2. 计算初始利息总额
    double notConfirmFinCost = 负债原值 - 负债现值;
    double interestTotal = calculateInterestTotal(dailyRate);
    double difference = interestTotal - notConfirmFinCost;
    
    // 3. 二分迭代
    if (difference > 0) {
        // 利息太多，减少日利率
        while (difference > 0) {
            dailyRate *= 0.98;
            difference = calculateInterestTotal(dailyRate) - notConfirmFinCost;
        }
    } else if (difference < 0) {
        // 利息太少，增加日利率
        while (difference < 0) {
            dailyRate *= 1.02;
            difference = calculateInterestTotal(dailyRate) - notConfirmFinCost;
        }
    }
    
    // 4. 线性插值
    double dailyRate = 线性插值计算;
    return new BigDecimal(dailyRate);
}
```

**利息总额计算**（`calculateInterestTotal()` 第170-192行）：

```java
private double calculateInterestTotal(double r) {
    double interestTotal = 0;
    double balance = 初始负债;  // 负债现值
    
    for (每天 until 最后付款日) {
        double intTemp = (balance - 当日支付) * r;  // 当日利息
        balance = balance - 当日支付 + intTemp;     // 更新余额
        interestTotal += intTemp;                    // 累加利息
    }
    
    return interestTotal;
}
```

### 5.5 具体示例

**假设条件**：
- 负债原值 = 100万
- 负债现值 = 90万
- 未确认融资费用 = 10万
- 租赁期 = 2年，每月1日支付，月租4.5万
- 合同日利率 = 0.013377%

**迭代过程**：

| 迭代次数 | 日利率 | 利息总额 | 与10万差额 | 调整方向 |
|----------|--------|----------|-----------|----------|
| 0 | 0.013377% | 110,500 | +10,500 | 减少 |
| 1 | 0.013109% | 108,290 | +8,290 | 减少 |
| 2 | 0.012847% | 106,124 | +6,124 | 减少 |
| ... | ... | ... | ... | ... |
| N | 0.012500% | **100,000** | **0** | 完成 |

**最终结果**：
- 实际日利率 = 0.012500%（迭代后）
- 利息总额 = 100,000元 = 未确认融资费用 ✓

## 七、两种模式的差异对比

### 7.1 计算流程对比

**模式A**：
```
合同日折现率 → 除以100 → 直接使用
```

**模式B**：
```
合同日折现率 → 迭代计算利息总额 → 与未确认融资费用比较 → 调整利率 → 重复直到匹配
```

### 7.2 结果差异对比

**假设条件**：
- 年折现率 = 5%
- 负债原值 = 100万
- 负债现值 = 90万
- 未确认融资费用 = 10万
- 租赁期 = 2年

| 对比项 | 模式A | 模式B |
|--------|-------|-------|
| 日利率 | 0.013377% | 0.012500% |
| 利息总额 | 97,853元 | 100,000元 |
| 与未确认融资费用差额 | -2,147元 | **0**（精确） |
| 差额比例 | -2.15% | 0% |

### 7.3 差异原因分析

模式A直接使用合同日利率计算，而该日利率是从年利率转换得到的近似值。这个近似转换本身就有微小误差，导致最终利息总额与未确认融资费用存在偏差。

模式B通过迭代"倒推"出准确的日利率，确保利息分摊的数学一致性。

### 7.4 实际影响

| 因素 | 影响程度 |
|------|----------|
| 租赁期限 | 期限越长，差异越大 |
| 利率高低 | 利率越高，差异越大 |
| 金额大小 | 金额越大，绝对差异越大，相对差异稳定 |
| 付款频率 | 频率越高，差异越小 |

**典型场景下的差异**：
- 100万/2年/月付：差异约2,000元（0.2%）
- 1000万/5年/月付：差异约20,000元（0.2%）

## 八、适用场景建议

### 8.1 建议使用模式A的场景

| 场景 | 原因 |
|------|------|
| 新增租赁合同首次确认 | 简化计算，性能最优 |
| 短期租赁 | 期限短，差异微小 |
| 对精度要求不高 | 可接受微小偏差 |
| 性能敏感场景 | 无迭代，计算快 |

### 8.2 建议使用模式B的场景

| 场景 | 原因 |
|------|------|
| 租赁变更后重新计算 | 需要精确匹配未确认融资费用 |
| 续租 | 确保利息分摊连续准确 |
| 长期租赁 | 期限长，差异累积明显 |
| 对账务精度要求高 | 确保利息分摊数学一致 |
| 审计/合规要求 | 需要精确的利息分摊记录 |

## 十、总结

### 10.1 核心区别

| 对比维度 | 模式A | 模式B |
|----------|--------|--------|
| 计算方式 | 直接取值 | 迭代计算 |
| 复杂度 | 简单 | 复杂 |
| 日利率来源 | 合同日折现率 | 计算得出的精确值 |
| 利息总额 | 可能 ≠ 未确认融资费用 | **精确 = 未确认融资费用** |
| 性能 | 最优 | 需多次迭代 |
| 适用场景 | 新增合同首次确认 | 变更/续租 |

### 10.2 选择建议

| 选择 | 建议 |
|------|------|
| **首次确认的新增合同** | 使用模式A（简化计算） |
| **租赁变更/续租** | 使用模式B（精确匹配） |
| **需要精确财务报告** | 使用模式B |
| **性能敏感场景** | 使用模式A |

### 10.3 本质理解

- **模式A**：把年利率直接当天利率用（简化处理）
- **模式B**：倒推出使利息精确匹配的日利率（精确处理）

两种模式都能正常工作，差异在于精度和适用场景的不同。企业可根据自身会计政策选择合适的模式。
