## 一、服务架构

### 1.1 核心服务

| 服务名 | 命名空间 | 职责 |
|---|---|---|
| CreditService | Core/.../App.BusinessService | 信用核心服务（调度） |
| CreditLimitService | BusinessPlugIn | 额度管理服务 |
| CreditCheckService | BusinessPlugIn | 信用检查服务 |
| CreditOccupancyService | BusinessPlugIn | 额度占用服务 |
| CreditWarningService | ServicePlugIn | 预警服务 |

### 1.2 服务交互关系

```
┌────────────────────────────────────────────────────────────────┐
│                    CreditService（核心调度）                     │

│  CreditCheckService   │  信用检查（交易前验证）                  │
│  CreditOccupancyService│  额度占用（占用/释放）                  │
```

## 四、信用检查流程

### 4.1 实时检查流程

```
开始
  │
  ▼
获取客户ID
  │
  ▼
检查客户是否存在有效额度
  │
  ├── 不存在 ──▶ 返回：无额度记录
  │
  ▼
检查额度状态
  │
  ├── 已冻结 ──▶ 返回：额度已冻结
  ├── 已失效 ──▶ 返回：额度已失效
  │
  ▼
计算已占用金额（SUM of CreditUsage WHERE 状态=占用中）
  │
  ▼
计算已冻结金额（SUM of CreditFreeze WHERE 状态=冻结中）
  │
  ▼
计算可用额度 = 总额度 - 已占用 - 已冻结
  │
  ▼
比较：可用额度 >= 交易金额？
  │
  ├── 是 ──▶ 返回：检查通过
  │
  ├── 否 ──▶ 检查是否启用超额审批
  │           │
  │           ├── 是 ──▶ 返回：需审批
  │           │
  │           └── 否 ──▶ 返回：额度不足
  │
结束
```

### 4.2 异步检查流程

```
开始
  │
  ▼
接收检查请求
  │
  ▼
放入检查队列
  │
  ▼
返回：检查中
  │
  ▼（后台线程）
  │
  ▼
执行检查逻辑（同实时检查）
  │
  ▼
更新检查结果
  │
  ▼
通知调用方（回调/事件）
  │
结束
```

## 五、DA6分析结论

**核心服务**：5个
- CreditService（调度）
- CreditLimitService（额度管理）
- CreditCheckService（信用检查）
- CreditOccupancyService（占用释放）
- CreditWarningService（预警）

**核心API**：12个
- 额度管理API：5个
- 信用检查API：3个
- 额度占用API：3个

**关键时序**：
- 销售订单信用检查（Sal→Credit）
- 出库触发额度占用（Sal→AR→Credit）
- 收款触发额度释放（AR→Credit）
