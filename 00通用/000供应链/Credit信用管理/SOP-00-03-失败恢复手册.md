# 失败恢复手册 — K3Cloud Credit信用管理

## 一、异常场景速查表

| 异常场景 | 紧急程度 | 影响范围 | 恢复方式 |
|---|---|---|---|
| 额度占用失败但出库成功 | 🔴 高 | 数据不一致 | 手动补偿占用 |
| 额度超占 | 🔴 高 | 额度透支 | 审批+调整 |
| 释放金额超过已占用 | 🔴 高 | 额度错误 | 拒绝释放 |
| 重复授信（同一客户两个额度） | 🟡 中 | 业务冲突 | 合并/作废 |
| 信用检查超时 | 🟡 中 | 订单延迟 | 降级为异步 |
| 冻结客户仍能下单 | 🔴 高 | 风控失效 | 反审核+冻结 |
| 预警未及时处理升级 | 🟡 中 | 风险累积 | 加速处理 |
| AR异常导致占用泄漏 | 🔴 高 | 额度不准 | 对账+补偿 |

## 二、场景一：额度占用失败但出库成功

### 2.1 问题描述
出库审核成功，但额度占用失败（系统异常或AR模块异常）。

### 2.2 系统行为
```
预期行为：出库审核 → AR生成 → 额度占用
实际行为：出库审核成功 → AR生成成功 → 额度占用失败 ❌
结果：客户额度未减少，但应收已生成，数据不一致
```

### 2.3 影响范围
```
├── 客户可用额度未减少
├── AR应收单已生成
├── 后续收款可能超额释放
└── 财务报表与额度数据不一致
```

### 2.4 恢复步骤

```
步骤1：识别问题
├── 检查T_CR_CREDITLIMITUSAGE是否有对应记录
├── 检查T_CR_CREDITLIMIT的FOCCUPIEDLIMIT是否正确
└── 如占用失败，会发现占用记录缺失或金额不对

步骤2：手动补偿占用
├── 查询出库单金额（含税金额）
├── 在Credit系统中手动创建占用记录
├── 更新客户额度（减少可用额度）
└── 记录补偿原因和操作人

步骤3：后续监控
├── 监控该客户额度使用情况
├── 检查后续收款是否正常触发释放
└── 验证AR与额度一致性
```

### 2.5 预防措施
```
建议：
1. 出库审核使用事务保证原子性
2. 引入消息队列异步处理，失败重试
3. 定时任务对账AR与额度占用
4. 建立异常告警机制
```

## 三、场景二：额度超占

### 3.1 问题描述
客户可用额度被超出，实际占用金额超过总额度。

### 3.2 系统行为
```
正常公式：可用额度 = 总额度 - 已占用 - 已冻结
异常情况：已占用 > 总额度，导致可用额度为负
```

### 3.3 恢复步骤

```
步骤1：确认超占原因
├── 原因A：并发出库导致竞态条件
│   └── 检查并发日志，确认时序问题
├── 原因B：释放计算错误
│   └── 检查释放记录，确认金额计算
└── 原因C：调整总额度时未同步处理占用
    └── 检查额度调整历史

步骤2：根据原因处理

原因A处理（并发）：
1. 回滚最近的占用操作
2. 重新执行正确的占用
3. 通知相关销售员重新下单

原因B处理（计算错误）：
1. 核实正确释放金额
2. 修正释放记录
3. 更新占用金额

原因C处理（调整未同步）：
1. 计算正确的占用比例
2. 调整总额度或占用记录
3. 发起审批流程确认

步骤3：事后分析
├── 分析超占根本原因
├── 修复并发控制或计算逻辑
└── 补充单元测试
```

## 四、场景三：释放金额超过已占用

### 4.1 问题描述
执行额度释放时，释放金额超过当前未释放金额。

### 4.2 系统行为
```
验证规则：BR-Cred-403 释放金额不能超过未释放金额
系统响应：拒绝释放，提示"释放金额超出已占用金额"
```

### 4.3 恢复步骤

```
步骤1：确认异常来源
├── 可能是收款金额与应收金额不一致
├── 可能是核销时选择了错误的应收单
└── 可能是历史数据错误

步骤2：核对AR数据
├── 确认应收单实际未核销金额
├── 确认收款单金额
└── 检查核销关系

步骤3：正确处理
├── 按正确的未释放金额执行释放
├── 如有多付部分，计入预收款
└── 或联系客户退款/抵账
```

## 五、场景四：重复授信

### 5.1 问题描述
同一客户同一币种存在两个生效额度。

### 5.2 系统行为
```
验证规则：BR-Cred-101 同一客户同一币种只能有一个生效额度
系统响应：保存时提示"该客户该币种已存在生效额度"
```

### 5.3 恢复步骤

```
步骤1：确认重复额度
├── 查询该客户所有额度记录
├── 确认哪个是正确的主额度
├── 确认哪个应该作废
└── 评估合并影响

步骤2：选择处理方式

方式A：作废多余额度
1. 确认主额度金额是否足够
2. 如足够：作废多余额度
3. 如不够：先增加主额度，再作废多余额度
4. 处理已占用金额的转移

方式B：合并额度
1. 计算合并后总金额
2. 作废原有两个额度
3. 创建新合并额度
4. 处理已占用金额合并

步骤3：审批确认
├── 提交额度合并/作废审批
├── 审批通过后执行操作
└── 记录操作原因
```

## 六、场景五：信用检查超时

### 6.1 问题描述
信用检查响应超时，导致订单创建缓慢或失败。

### 6.2 系统行为
```
配置项：信用检查模式（实时/异步）
实时检查：等待检查完成再返回
异步检查：先返回"检查中"，后台执行
```

### 6.3 恢复步骤

```
步骤1：确认超时原因
├── 原因A：数据库查询慢
│   └── 检查索引，添加缓存
├── 原因B：计算逻辑复杂
│   └── 简化计算，预聚合数据
└── 原因C：网络/服务不可用
    └── 检查依赖服务状态

步骤2：临时处理
├── 切换为异步检查模式
├── 或临时跳过检查（需审批）
└── 或使用缓存结果

步骤3：性能优化
├── 优化T_CR_CREDITLIMITUSAGE查询
├── 引入Redis缓存热点数据
├── 分离计算服务
└── 添加数据库索引
```

## 七、场景六：冻结客户仍能下单

### 7.1 问题描述
客户额度已被冻结，但销售订单仍然创建成功。

### 7.2 系统行为
```
验证规则：BR-Cred-204 冻结客户直接拒绝交易
预期结果：订单创建时检查额度状态，返回"额度已冻结"
实际结果：订单创建成功 ❌
```

### 7.3 恢复步骤

```
⚠️ 这是严重风控漏洞，需立即处理

步骤1：确认影响范围
├── 查询冻结后是否有新订单创建
├── 统计冻结后订单数量和金额
└── 评估风险敞口

步骤2：紧急处理
├── 立即反审核问题订单
├── 或冻结相关客户额度
└── 通知销售和风控

步骤3：修复问题
├── 检查信用检查插件是否正确执行
├── 检查冻结状态判断逻辑
├── 修复代码Bug
└── 补充测试用例

步骤4：事后分析
├── 分析为什么检查未生效
├── 审计其他检查点
└── 完善监控告警
```

## 八、场景七：AR异常导致占用泄漏

### 8.1 问题描述
AR应收单被删除或红冲，但对应的额度占用未释放。

### 8.2 系统行为
```
正常链路：AR应收 → 额度占用
         AR核销 → 额度释放
异常情况：AR应收删除/红冲 → 额度占用未释放 ❌
结果：额度被永久占用，无法恢复
```

### 8.3 恢复步骤

```
步骤1：识别泄漏
├── 定期执行AR与额度占用对账
├── 找出无对应AR的占用记录
└── 评估泄漏金额

步骤2：确认AR状态
├── 确认应收单是删除还是红冲
├── 确认应收单红字是否已生成
└── 确认这笔应收是否确实不再需要

步骤3：手动释放
├── 创建人工释放记录
├── 标注释放原因："AR异常释放"
├── 更新客户可用额度
└── 记录操作人和时间

步骤4：修复机制
├── 在AR删除/红冲时触发释放事件
├── 或定时对账任务自动检测
└── 引入跨模块事务保证
```

## 九、通用恢复原则

### 9.1 数据一致性优先
```
恢复操作必须保证：
├── 总额度 - 已占用 - 可用额度 = 0
├── 占用记录与AR应收一一对应
├── 冻结金额与冻结记录一致
└── 预警处理状态与实际操作同步
```

### 9.2 操作顺序原则
```
额度相关操作顺序：
冻结 → 解冻 → 调整 → 占用 → 释放
  ↑       ↓      ↓     ↓     ↓
 结束 ◀───恢复───┘     │     │
                    反操作  反操作
```

### 9.3 审批追溯
```
重要操作需保留审批记录：
├── 记录操作原因
├── 记录审批人
├── 记录审批时间
├── 保存相关附件
└── 记录对账结果
```

### 9.4 监控告警
```
必须监控的异常：
├── 额度为负（超占）
├── 占用无对应AR
├── 冻结客户仍能交易
├── 检查响应时间超限
└── 预警未处理超过时限
```

### 9.5 通知相关方
```
恢复操作后需通知：
├── 销售员：订单/额度变更
├── 风控专员：额度异常
├── 财务：AR与额度不一致
└── 信用管理员：额度调整
```
