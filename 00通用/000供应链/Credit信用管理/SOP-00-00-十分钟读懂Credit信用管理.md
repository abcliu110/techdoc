# 十分钟读懂Credit信用管理

> 快速理解K3Cloud信用管理模块的核心逻辑

## 一句话概括

**信用管理是辅助子域，核心链路"Sal销售→Credit检查→AR应收→CB收款"，围绕客户信用额度实现交易风险控制。**

---

## 核心发现（3个）

### 1. 信用管理嵌入销售流程
```
客户下单 ──▶ 信用检查 ──▶ 出库审核 ──▶ 额度占用 ──▶ AR记账
              │                            │
              ▼                            ▼
         通过/拒绝                      已占用额度
```

**每次销售订单创建必须通过信用检查，实时校验可用额度是否足够。**

### 2. 额度占用释放依赖AR模块
```
出库审核 ──▶ AR应收生成 ──▶ 额度占用
                              │
收款审核 ──▶ AR核销 ──▶ 额度释放
```

**额度占用/释放以AR应收为核心触发点，形成Credit↔AR紧密耦合。**

### 3. 预警机制保护额度安全
```
逾期天数 > N ──▶ 逾期预警
额度使用率 > M% ──▶ 额度预警
评级下调 > 2级 ──▶ 评级预警
```

## 核心流程

### 标准信用管理流程
```
销售员 ──▶ 创建订单 ──▶ 实时信用检查 ──▶ 检查通过 ──▶ 允许创建订单
                                                   │
                                          检查不通过 ──▶ 超额审批
                                                         │
                                                         ▼
仓库员 ──▶ 审核出库 ──▶ AR应收生成 ──▶ 额度占用 ──▶ 已占用额度
                                                         │
                                                         ▼
财务 ──▶ 收款审核 ──▶ AR核销 ──▶ 额度释放 ◀─── 已占用额度
```

## 核心数据表

| 表名 | 用途 |
|---|---|
| T_CR_CREDITLIMIT | 信用额度表头 |
| T_CR_CREDITLIMITUSAGE | 额度使用记录（占用/释放） |
| T_CR_CREDITLIMITFREEZE | 额度冻结记录 |
| T_CR_CREDITRATING | 客户信用评级 |
| T_CR_CREDITWARNING | 信用预警记录 |

---

## 额度计算公式

```
可用额度 = 总额度 - 已占用 - 已冻结

检查通过条件：可用额度 >= 订单含税金额
```

## 决策点（5个）

| 决策点 | 选项 | 选择 |
|---|---|---|
| 检查策略 | 实时检查 vs 异步检查 | 可配置 |
| 占用时机 | 出库审核时 vs AR记账时 | 出库审核时 |
| 释放时机 | 收款审核时 vs 核销时 | 收款+核销 |
| 额度不足处理 | 拒绝 vs 审批流程 | 审批流程 |
| 冻结策略 | 手动冻结 vs 自动冻结 | 手动+自动 |

---

## 风险项（1个高风险）

| 风险 | 等级 | 应对 |
|---|---|---|
| 额度占用与释放时序问题 | 高 | 原子操作+事务保证 |
| 跨模块数据一致性 | 中 | Sal/AR/Credit同步 |
| 信用检查性能影响 | 中 | 异步检查+缓存 |
| 巨型类CreditService维护困难 | 中 | 拆分服务 |
