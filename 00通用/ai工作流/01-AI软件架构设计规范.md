# AI软件架构设计规范

> 版本：1.0.1
> 状态：正式版
> 用途：在编码前形成可实现、可测试、可验证的系统设计。

## 1. 设计目标

架构设计不是目录规划，而是对业务规则、数据流、模块边界、失败行为和长期变更成本作出明确决策。编码 Agent 只能实现已批准的设计，不得自行发明业务规则、接口字段、页面状态或错误处理方式。

## 2. 设计输入

设计师和架构师必须先确认：

- 用户目标、角色和使用场景
- 正常、失败、取消、重试和恢复流程
- 业务规则、不变量、正例和反例
- 现有系统入口、依赖和兼容约束
- 数据敏感级别、权限和审计要求
- 性能、可靠性、可观测性和发布约束
- 明确不做的内容

需求不明确时必须记录问题并阻塞，不得让编码 Agent 通过猜测推进。

## 3. 必须产物

每个任务至少需要以下设计产物：

```yaml
design_package:
  metadata:
    task_id: MODULE-001
    feature_id: FEATURE-001
    feature_team_id: FEATURE-001-TEAM-001
    work_type: backend | frontend | fullstack
    version: 1.0.0
    input_revision: code-or-contract-revision
    design_revision: DESIGN-001
    artifact_hash: sha256:<digest>
    status: draft | approved
    owner: architect-agent-id
    approved_by: []
    approved_at: null
  user_goal: string
  acceptance_scenarios: []
  domain_rules: []
  invariants: []
  context_and_boundaries: docs/context.md
  module_design: docs/modules.md
  data_model: docs/schema.md
  api_or_events: docs/api.md
  state_model: docs/state.md
  error_model: docs/errors.md
  non_functional_constraints: docs/nfr.md
  testability_hooks: docs/testability.md
  adr: []
  threat_model: docs/threat-model.md
  data_lifecycle: docs/data-lifecycle.md
  capacity_assumptions: docs/capacity.md
  out_of_scope: []
```

不同任务类型按适用性裁剪产物：后端任务必须有数据、接口、错误和非功能设计；前端任务必须有页面状态、交互契约和测试抓手；全栈任务两者都必须有。无关字段必须标记 `not_applicable` 并说明原因，不能提交空文件充数。

## 4. 领域和业务建模

### 4.1 规则必须可验证

每条关键规则必须有唯一编号，并包含正例、反例和验证方式。

```yaml
rule_id: LEARNING-003
statement: 同一练习尝试只能产生一个有效提交结果
valid_examples:
  - 首次提交成功
invalid_examples:
  - 重复请求产生两条学习记录
verification:
  - api_contract_test
  - concurrent_integration_test
```

### 4.2 不变量

至少识别以下不变量（按领域裁剪）：

- 数据所有权不被越权破坏
- 状态只能沿允许的转换路径变化
- 已完成记录不能被重复计入
- 失败操作不能产生伪成功数据
- 事务边界内的数据保持一致
- 客户端展示状态与服务端结果一致

## 5. 模块和依赖设计

必须说明：

- 模块职责和公开接口
- 上层到下层的依赖方向
- 哪些逻辑属于领域层、应用层、基础设施层或展示层
- 哪些数据只能通过边界对象进入
- 循环依赖如何避免
- 哪些变化应该被隔离

禁止用“大而全的 service”“万能 util”“跨模块直接访问数据库”等模糊边界替代设计。

## 6. 后端架构规范

### 6.1 API 和 Schema

必须定义：

- 方法、路径、版本和认证要求
- 请求字段、类型、必填性、范围和默认值
- 响应结构、分页和空值语义
- 错误码、状态码、可重试性和用户可见信息
- 幂等键、并发行为和重复请求结果
- 向后兼容和弃用计划

Schema 必须版本化，非法数据不得进入领域逻辑、存储或渲染。

### 6.2 事务和外部依赖

架构必须明确事务边界、锁或并发策略、超时、重试、退避、部分失败和恢复方式。任何有副作用的重试都必须证明幂等性。

### 6.3 数据和迁移

数据结构变更必须说明旧客户端兼容、迁移顺序、回滚方式、回填校验和失败恢复。破坏性变更必须升版本并经过迁移演练。

同时必须定义数据生命周期：采集、使用、存储、访问、导出、保留期限、删除和备份恢复。涉及多用户或多租户时，必须明确租户隔离键、权限过滤和跨租户访问的阻断方式。

## 7. 前端架构规范

### 7.1 页面和状态

每个页面或交互场景必须定义：

```text
initial → loading → success
                 ├→ empty
                 └→ error → retrying → loading
```

同时说明状态所有者、状态流向、请求取消、竞态、重复提交、焦点、键盘和错误反馈。

### 7.2 测试抓手

优先使用用户可感知的 role、label 和文本；需要自定义抓手时使用稳定的 `data-testid` 和业务状态属性。

```tsx
<section data-testid={`question-card-${question.id}`} data-state={state}>
  <button data-testid="submit-answer" aria-label="提交答案" disabled={state !== 'ready'}>
    提交
  </button>
</section>
```

必须能观察初始、加载、成功、失败、空数据和重试状态。测试抓手表达真实状态，不能创建只供测试使用的假分支。

### 7.3 可访问性和国际化

设计必须考虑键盘路径、焦点可见性、可访问名称、错误提示、颜色独立表达、长文本、日期和数字格式。

## 8. 非功能设计

架构方案必须给出适用的预算、环境、测量工具、统计窗口和验证方式。以下只是模板，不是所有项目的默认阈值：

```yaml
performance_budget:
  api_p95_ms: 300
  initial_page_load_ms: 2500
  max_bundle_size_kb: 500
  measurement:
    environment: staging-like
    tool: project-selected-tool
    sample_window: project-defined
reliability:
  timeout_defined: true
  retry_defined: true
  recovery_defined: true
observability:
  request_id: required
  structured_error_code: required
```

同时说明认证授权、敏感数据、日志脱敏、告警、降级和恢复行为。生产任务必须有威胁模型、数据生命周期和容量增长假设；不适用时要留下明确的适用性判断。

## 9. ADR

重大架构选择必须记录：背景、决策、备选方案、选择理由、影响、迁移和验证方式。接口、数据库、状态模型或模块边界变化必须更新 ADR 并重新评审。

## 10. 设计评审清单

- 用户目标和验收场景无歧义
- 规则有正例、反例和编号
- 模块边界和依赖方向清晰
- API、Schema、状态和错误契约完整
- 正常、失败、取消、重试和恢复路径完整
- 安全、性能、可靠性和可观测性有方案
- 前端关键状态有稳定测试抓手
- 设计能被自动化测试和真实用户流程验证
- 明确不做的内容和已知风险
- Task Owner、架构师和设计师已批准
