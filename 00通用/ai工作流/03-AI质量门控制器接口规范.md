# AI质量门控制器接口规范

> 版本：1.0.0
> 状态：强制运行时规范
> 用途：把研发协议从提示文本变成可拒绝的文件写入、命令执行和状态推进接口。

## 1. 适用范围

`CLAUDE.md`、Markdown 和 YAML 只能告诉 Agent 应该怎么做，不能阻止 Agent 直接写文件或运行命令。本规范定义唯一允许执行研发操作的 `ai-quality-gate-controller` 接口。控制器不可用、状态无法验证、审计无法追加或返回结果无法验证时，任务必须保持 `blocked`。

直接使用 Shell、编辑器、文件 API、运行时脚本或后台进程修改项目，均不属于受控执行。Agent 只能向控制器提交请求；控制器拒绝请求时，Agent 不得换用其他工具重试或由主 Agent 接管。

## 2. 控制器必须维护的状态

控制器必须维护以下不可变或追加式产物：

```text
evidence/workflow-state.json
evidence/feature-progress.json
evidence/write-audit.jsonl
evidence/command-audit.jsonl
evidence/protocol-incident.json
```

状态至少包含 `task_id`、`feature_id`、`feature_team_id`、当前质量门、checkpoint、TDD 阶段、代码版本、允许路径、角色 Agent 身份和已通过门的证据哈希。

## 3. 必须提供的接口

```text
bootstrap(task_context)
assign_feature(feature_contract)
create_checkpoint(checkpoint_contract)
request_write(write_request)
register_command(command_definition)
run_gate(gate_id, command_ref)
submit_handoff(handoff)
advance_gate(gate_id, evidence)
freeze_feature(feature_id)
close_feature(feature_id)
authorize_next_feature(previous_feature_id, next_feature_id)
```

每个接口都必须校验当前状态、Agent 身份、`feature_id`、`feature_team_id`、输入版本、允许路径和对应质量门。接口失败必须返回阻塞原因和解除条件，并追加审计记录。

控制器加载 `ai研发质量门.yaml` 后，必须先按 `gate_schema` 校验每个门：必填字段、已声明的可选字段、字段类型、`required_pairs` 角色配对和 `applicability` 结果都必须可解析。未知字段、未解析的命令引用、未注册的角色配对、未明确的适用性或缺少对抗证据时，控制器必须拒绝该门并返回 `blocked`，不能把自然语言的 `pass_criteria` 当作结构化证据。

## 4. 写入策略

控制器拒绝默认执行以下规则：

| 阶段 | 允许写入 | 必须拒绝 |
|------|----------|----------|
| 启动门、设计门 | 任务契约、设计产物、证据 | 源码、测试、配置、数据库、依赖 |
| Red | 测试路径、证据路径 | 生产源码、生产配置、依赖清单、数据库、迁移 |
| Green | 批准范围内的最小生产实现 | 越界文件、无关重构、未注册依赖 |
| Refactor | 批准范围内的代码和注释 | 未经 Reviewer 允许的行为变更 |
| 验收后 | 证据冻结和功能关闭记录 | 当前功能关闭后继续修改其产物 |

进入 Red 前必须创建生产路径快照并记录哈希。Red 期间生产路径哈希发生变化，控制器必须拒绝 `tdd_red_phase_passed`。只有 Red 的测试版本、非零退出码、失败断言和快照哈希齐全，控制器才允许 Green 写入生产代码。

## 5. 命令策略

命令必须先注册到任务契约的 `task.commands`，注册字段至少包括命令、工作目录、环境、超时、预期退出码、报告路径、所有者 Agent 和角色。控制器拒绝未注册命令、所有者不匹配命令、当前门不允许命令、越界工作目录和缺少审计输出的命令。

安装依赖、启动服务、生成 Playwright 配置都只能作为已注册的环境准备命令执行，不能被记录为测试通过。真实测试必须产生退出码、报告以及适用的 trace、视频、截图或 API 交互证据。

所有 `review_gate_ids` 中的门必须提交 `reviewer_agent_id`、`reviewer_role`、`producer_agent_id`、`producer_role`、`review_revision`、`producer_output_revision`、`reviewer_is_independent`、`findings`、`disposition` 和 `regression_evidence`。控制器必须计算并拒绝自评、revision 不一致或未处理阻断/高严重性发现的证据。`feature_acceptance_passed` 还必须验证 Task Owner 与 Acceptance Challenger 是不同 Agent，并绑定同一批准 revision、真实命令、退出码、验收报告、trace/video 和缺陷登记状态。

## 6. 功能推进策略

同一时间只能存在一个活动 `feature_id`。当前功能必须按以下顺序关闭：

```text
feature_acceptance_passed
→ defect_registry_resolved
→ feature_evidence_frozen
→ feature_closed
→ next_feature_authorized
```

后端功能验收从真实 API、数据库和依赖链路运行；前端和全栈功能验收从真实浏览器入口运行，并覆盖成功、失败、重试、边界和持久化结果。Task Owner 和 Acceptance Challenger 必须以不同 Agent 身份独立验收同一版本。没有验收报告、退出码、trace/video、独立结论或缺陷关闭记录，控制器不得关闭功能，也不得授权下一个功能。

## 7. 违规处理

发现绕过控制器、生产代码先于 Red、删除证据、伪造退出码、修改测试制造通过或启动未授权功能时，控制器必须：

1. 拒绝后续写入和命令。
2. 追加 `evidence/protocol-incident.json`。
3. 将当前 checkpoint 标记为 `invalidated/unverified`。
4. 保留现场，不删除源码、测试或证据。
5. 固定回到协议规定的恢复门。

控制器不得提供“继续当前测试”或“重新 TDD”的流程选择；恢复路径由质量门配置决定。

## 8. 运行时适配要求

项目必须提供一个把 Agent 文件/命令工具调用接入本控制器的运行时适配器。适配器可以使用 IDE Hook、CLI 包装器、容器权限、CI Job 或其他等效机制，但必须证明：直接工具调用被拒绝、拒绝结果可追溯、受控请求能写入审计记录、门失败时无法推进状态。只有阅读本文件或在回复中声称“已通过控制器”不算 `agent_runtime_verified`。
