# AI研发执行协议

> 版本：1.4.0
> 状态：正式版
> 用途：作为所有 AI 软件研发任务的唯一执行入口。

## 1. 适用范围

凡由 AI Agent 参与需求分析、架构设计、交互设计、编码、测试、评审、发布或缺陷修复的任务，必须遵守本协议。

本协议负责协作和状态控制；专业设计、测试和代码质量要求分别见：

- [01-AI软件架构设计规范.md](./01-AI软件架构设计规范.md)
- [02-AI软件测试与代码质量规范.md](./02-AI软件测试与代码质量规范.md)
- [03-AI质量门控制器接口规范.md](./03-AI质量门控制器接口规范.md)

Agent 不得自行决定跳过、替换或降低这些规范中的质量门。

本项目的执行模式固定为 `strict_multi_agent`，模式不可协商、不可覆盖、不可按 MVP 或 Token 成本降级。禁止向用户询问 `strict/simple/single` 等模式选择；只能执行严格流程，或在能力不足时报告 `blocked`。

“新建项目”或“不参考现有文件”只改变任务范围和基线，不改变执行协议。禁止提供快速启动/严格模式等流程选项，禁止让用户选择下一步流程；仅在产品需求、业务规则、交互行为或验收条件不明确时提问。

首轮响应必须使用 `WORKFLOW_PREFLIGHT` 固定格式，列出 `mode`、规范加载状态、Agent 运行时状态、`feature_team` 状态、下一质量门和 `blocked` 原因。首轮禁止提供流程选项、快速启动方案或直接创建项目文件。启动门通过后必须自动进入下一门，不得再次询问流程选择。

任务启动时必须先读取项目级 `CLAUDE.md` 和上述规范文件，并记录版本、读取时间和内容指纹，完成 `workflow_bootstrap_verified` 后才能创建功能 Agent。路径不存在、读取失败、编码错误、版本无法确认、控制器适配器无法验证或规范未实际注入 Agent 上下文时，任务必须 `blocked`。

独立 Agent 的创建、调度或通信工具发生参数错误、超时、权限错误或结果无法验证时，必须记录原始错误和重试条件，进入 `blocked`；禁止由主 Agent 直接接管缺失角色，禁止继续编码、测试或声称流程完成。

发生任何协议违规时，先停止写入和运行命令，生成 `evidence/protocol-incident.json`，记录违规命令、Agent、阶段、代码版本、受影响路径和恢复条件。禁止 `rm -rf`、递归删除、`git reset --hard`、`git clean`、`git checkout` 或删除证据/源代码目录；未经 Task Owner 明确批准不得执行破坏性清理。恢复必须保留现场并在隔离 checkpoint、分支或工作区中继续。

### 文档不是执行器：质量门控制器是强制前提

Markdown 和 YAML 只能表达规则，不能阻止 Agent 直接调用 Shell、编辑器或文件 API。严格模式必须由 `ai-quality-gate-controller` 执行；所有文件写入和命令执行都必须经过控制器，并写入 `evidence/write-audit.jsonl`、`evidence/command-audit.jsonl`。控制器必须拒绝未注册命令、未通过质量门、越界路径、身份未验证和 TDD 阶段不匹配的请求。控制器不可用、返回结果无法验证或审计记录无法追加时，任务立即 `blocked`，不得由主 Agent 代替执行。

任务契约必须包含不可变的 `task.commands` 命令注册表。每个质量门的 `command_ref` 必须能解析到注册命令，且命令必须包含工作目录、环境、超时、预期退出码、报告路径、所有者 Agent 和角色。命令注册完成后，除非产生新版本并重跑受影响质量门，否则不得修改命令。

控制器按当前状态和 checkpoint 对写入路径分类：Red 阶段只允许测试和证据路径；Green 阶段才允许批准范围内的生产代码；Refactor 阶段只允许编码 Agent 在 Green 通过后修改代码，并要求 Clean Code Reviewer 和 Maintainability Adversary 复核。直接写入生产目录、`package.json`、锁文件、数据库或迁移文件都必须被拒绝并记录违规。

TDD 违规的恢复路径不可选择：若生产代码先于测试产生，当前 checkpoint 立即标记 `invalidated`，代码保留但标记 `unverified`，生成协议违规记录，然后自动回到 `checkpoint_submitted`，由 Automated Test Agent 先完成 Red，再执行 Green 和 Refactor。禁止继续当前“先写代码后测试”的路径，禁止询问用户选择继续或重启。

“若干 agents finished”、泛化名称 `Agent`、`0 tool uses`、绿色 Done 或 UI Agent 数量都不能证明角色已执行。每个子 Agent 必须生成持久化 `agent_handoff`，包含 `agent_id`、角色、`feature_id`、`feature_team_id`、输入版本、输出产物和结论；任一字段缺失时，`agent_runtime_verified` 失败并保持 `blocked`。

后台 Agent 正在运行、等待完成或自动通知不等于批次完成。每个 `parallel_plan` 批次必须等所有角色交接单到齐，并由 Orchestrator 校验输入版本、产物版本、结论和未决问题；批次未完成或存在未解决结论时，不得启动下一批次、测试策略、编码或评审，主 Agent 不得代替缺失交接单。

Skill 加载、workflow-authoring 技能、`/agents` 命令、后台 Shell、同一会话的角色切换、回复中的角色清单或界面上的 Agent 数量提示，都不是独立 Agent 创建证据。有效证据必须记录实际 Agent 工具名、调用或会话标识、独立 `agent_id`、输入版本、交付物路径和子 Agent 结论。

## 2. 强制执行原则

1. 设计先于实现，契约先于编码。
2. 一个任务只有一个 Task Owner，但设计、实现、测试和批准必须职责分离。
3. 每个 checkpoint 只完成一个可验证的逻辑单元。
4. 没有证据不能进入下一状态。
5. 失败、冲突或不确定必须阻塞，不得用假设继续推进。
6. 实现者不能批准自己的实现、测试或视觉结果。
7. 规范版本、代码版本、测试结果和评审结论必须可追溯。
8. 规范违规后的恢复必须保留现场，不得删除代码、证据或目录伪造干净起点。

一个 `feature_id` 是一个独立验收周期。系统同时只能有一个处于 `in_progress` 的功能；当前功能完成全部 checkpoint、TDD、评审和适用测试后，必须通过 `feature_acceptance_passed`、关闭阻断/高严重性缺陷并冻结证据，才能创建或启动下一个 `feature_id`。不得把多个功能合并到一次验收，也不得用项目最终验收代替功能级验收。

## 3. 角色

| 角色 | 职责 | 不得承担的职责 |
|------|------|----------------|
| Task Owner | 明确目标、批准范围、最终验收 | 代替专业评审 |
| Task Orchestrator | 拆分任务、注入规范、推进状态、阻塞违规任务 | 私自修改产物 |
| 领域专家 | 定义业务规则、不变量和反例 | 直接批准代码质量 |
| 架构师 | 定义模块、数据、接口、状态和非功能约束 | 跳过设计评审直接编码 |
| 产品/交互设计师 | 定义用户流程、页面状态、反馈和可访问性 | 用视觉偏好替代业务验收 |
| 编码 Agent | 按批准设计实现，并提交测试 | 自行发明业务规则或接口 |
| 自动化测试 Agent | 执行分层测试并保存证据 | 修改测试以制造通过 |
| Clean Code Reviewer | 检查结构、命名、复杂度、错误处理和注释 | 只看格式化结果 |
| 独立代码评审 Agent | 检查实现是否遵循设计和契约 | 批准自己编写的代码 |
| E2E/视觉验证 Agent | 真实操作浏览器并验证用户流程 | 只检查静态渲染 |

### 角色对抗矩阵

每个生产角色必须配一个独立的对抗角色。对抗角色必须寻找反例、边界、遗漏和错误假设，并可以返回 `changes_requested`。

| 生产角色 | 对抗角色 |
|----------|----------|
| Task Owner | Acceptance Challenger |
| Task Orchestrator | Workflow Auditor |
| Feature Orchestrator | Feature Process Auditor |
| 领域专家 | Domain Rule Challenger |
| 架构师 | Architecture Adversary |
| 架构评审者 | Architecture Review Auditor |
| 交互/视觉设计师 | Design Adversary |
| 编码 Agent | Implementation Adversary |
| 自动化测试 Agent | Test Adequacy Adversary |
| Clean Code Reviewer | Maintainability Adversary |
| 测试评审者 | Test Review Auditor |
| E2E/视觉验证 Agent | User Journey Adversary |
| 独立代码评审 Agent | Review Auditor |
| 安全/契约评审 Agent | Security/Contract Adversary |
| 发布验证者 | Release Risk Adversary |

对抗角色不再递归创建新的对抗角色。每一对角色必须有独立 `agent_id` 和持久化评审产物。

## 4. 规范注入

Orchestrator 创建任务时必须将以下内容注入每个 Agent 的任务上下文：

```yaml
task_context:
  task_id: MODULE-001
  feature_id: FEATURE-001
  feature_team_id: FEATURE-001-TEAM-001
  parallel_plan: []
  work_type: backend | frontend | fullstack
  architecture_spec: 01-AI软件架构设计规范@1.0.1
  testing_quality_spec: 02-AI软件测试与代码质量规范@1.2.0
  controller_spec: 03-AI质量门控制器接口规范@1.0.0
  policy: ai研发质量门@1.4.0
  commands: task.commands
  agent_mode: strict_multi_agent
  agent_assignments: []
  approved_design: docs/design/MODULE-001.md
  allowed_scope:
    - src/xxx.ts
  required_gates:
    - workflow_bootstrap_verified
    - agent_runtime_verified
    - agent_assignments_verified
    - design_approved
    - test_strategy_ready
    - clean_code_reviewed
    - automated_tested
```

Agent 不得仅凭记忆执行规范。每个阶段必须引用具体的规范版本和章节。

## 5. 状态机

在 `workflow_bootstrap_verified`、`agent_runtime_verified`、`agent_assignments_verified` 和 `test_strategy_ready` 全部通过前，只允许读取规范、项目结构和测试配置以生成任务契约；禁止修改源代码、测试代码或配置，禁止启动应用、安装运行时依赖、执行迁移或声称开始实现/测试。

前置门通过也不等于可以自由写入。进入每个 checkpoint 前，控制器必须创建生产代码快照并记录哈希。Red 阶段只能由 Automated Test Agent 写测试并执行失败测试；在 Red 命令退出前，生产代码、生产配置、依赖清单、数据库和迁移路径的哈希不得变化。没有快照哈希、测试版本、失败断言和非零退出码，`tdd_red_phase_passed` 不得通过。

```text
draft
  → workflow_bootstrap_verified
  → agent_runtime_verified
  → agent_assignments_verified
  → design_ready
  → task_contract_adversarial_reviewed
  → design_approved
  → design_adversarial_reviewed
  → feature_process_audit_passed
  → test_strategy_ready
  → in_progress
  → checkpoint_submitted
  → tdd_red_phase_passed
  → tdd_green_phase_passed
  → automated_tested
  → test_adversarial_reviewed
  → tdd_refactor_passed
  → clean_code_reviewed
  → clean_code_adversarial_reviewed
  → implementation_adversarial_reviewed
  → e2e_adversarial_reviewed（前端适用）
  → architecture_reviewed
  → architecture_review_adversarial_reviewed
  → test_reviewed
  → test_review_adversarial_reviewed
  → ready_for_independent_review
  → independent_review_adversarial_reviewed
  → security_contract_reviewed（条件适用）
  → security_contract_adversarial_reviewed（条件适用）
  → release_reviewed（条件适用）
  → release_adversarial_reviewed（条件适用）
  → feature_acceptance_passed
  → defect_registry_resolved
  → feature_evidence_frozen
  → feature_closed
  → next_feature_authorized（存在下一个功能时）
  → next_checkpoint 或 integrated
  → final_verification
  → closed
```

`next_checkpoint` 只有在 `checkpoint_index < total_checkpoints` 时成立；当 `checkpoint_index == total_checkpoints` 时，必须先完成当前 `feature_id` 的功能级验收，不能直接进入 `integrated`。`next_feature_authorized` 只有在前一个功能的验收、缺陷关闭和证据冻结全部通过后成立。

状态与质量门的映射必须满足：每个带有 `_adversarial_reviewed` 后缀的状态都对应质量门配置中的同名对抗门；`task_contract_adversarial_reviewed` 对应 `task_contract_adversarial_reviewed`；`design_adversarial_reviewed` 对应 `design_adversarial_reviews_passed`；`feature_process_audit_passed` 对应 `feature_process_audit_passed`；`implementation_adversarial_reviewed` 对应 `implementation_adversarial_reviews_passed`；`automated_tested` 表示当前任务适用的自动化测试门全部通过；`architecture_reviewed` 对应 `architecture_review_accepted`；`test_reviewed` 对应 `test_review_accepted`；条件状态分别对应同名的安全/契约和发布质量门；`final_verification` 对应 `final` 序列中的全部门。`scope_labels_verified`、基线、格式化、lint、类型检查和构建属于 checkpoint 的证据门，阻塞时回退到 `checkpoint_submitted`，不得伪造独立状态。任何一个适用门缺失证据，状态不得前进。

`agent_assignments_verified` 和 `test_strategy_ready` 分别对应质量门配置中的同名门；`tdd_red_phase_passed`、`tdd_green_phase_passed` 和 `tdd_refactor_passed` 分别对应质量门配置中的同名 TDD 门；任一门缺失证据，状态不得进入 `in_progress`。

`workflow_bootstrap_verified` 和 `agent_runtime_verified` 是所有任务的最早启动门；二者任一失败时只能修复启动环境并重新执行启动门，不能回退为主 Agent 单独开发。

失败或变更时：

```text
任何阶段 → changes_requested → in_progress
任何阶段 → blocked
契约变化 → design_revalidation → design_approved
blocked → evidence_pending → resume_to
blocked → design_revalidation → design_approved
feature_closed → next_feature_authorized（存在下一个功能时）→ next_checkpoint → in_progress
feature_closed → integrated（当前功能为最后一个功能时）
integrated → final_verification → closed
```

`architecture_reviewed` 和 `test_reviewed` 分别表示质量门配置中的 `architecture_review_accepted` 和 `test_review_accepted` 已通过；每个生产评审门后必须先通过对应 Auditor 对抗门；二者及独立评审的对抗门完成后才能进入 `ready_for_independent_review`。`final_verification` 表示 `final` 门序列全部通过。

禁止从 `in_progress` 直接跳到 `integrated` 或 `closed`。`changes_requested` 必须记录缺陷编号、受影响质量门和必须重跑的门；修复后不能只重跑编码者指定的单个测试。

禁止从 `feature_closed` 之前创建或启动下一个 `feature_id`。`feature_acceptance_passed` 必须引用当前功能的真实验收命令、最新批准代码版本、验收报告和 Task Owner/Acceptance Challenger 的独立结论；任一缺失都保持 `blocked`。

`blocked` 必须记录阻塞原因、责任人、解除条件和下一步状态。只有 Task Orchestrator 在证据补齐或设计重新批准后，才能解除阻塞。

`agent_assignments_verified` 或 `test_strategy_ready` 失败时，恢复点只能回到对应门或更早的设计状态，不能直接进入 `in_progress`。

TDD 阶段的失败必须按阶段恢复：Red 失败回到 `checkpoint_submitted`；Green 失败回到 `tdd_red_phase_passed`；Refactor 失败回到 `tdd_green_phase_passed`。这些状态必须加入 `resume_to` 白名单；不得跳过 Red、直接补测试或直接进入统一代码评审。

TDD 恢复状态白名单：`tdd_red_phase_passed`、`tdd_green_phase_passed`、`tdd_refactor_passed`。执行器必须把这些状态视为 `resume_to` 的合法值。

`resume_to` 只能取 `task_contract_adversarial_reviewed`、`design_approved`、`design_adversarial_reviewed`、`feature_process_audit_passed`、`checkpoint_submitted`、`clean_code_reviewed`、`clean_code_adversarial_reviewed`、`implementation_adversarial_reviewed`、`automated_tested`、`test_adversarial_reviewed`、`e2e_adversarial_reviewed`、`architecture_reviewed`、`architecture_review_adversarial_reviewed`、`test_reviewed`、`test_review_adversarial_reviewed`、`ready_for_independent_review`、`independent_review_adversarial_reviewed`、`security_contract_reviewed`、`security_contract_adversarial_reviewed`、`release_reviewed`、`release_adversarial_reviewed`、`feature_acceptance_passed`、`defect_registry_resolved`、`feature_evidence_frozen`、`feature_closed`、`next_feature_authorized` 或 `final_verification`。`scope_labels_verified`、基线、格式化、lint、类型检查和构建失败时使用 `checkpoint_submitted` 作为恢复点。解除阻塞必须产生记录：

```yaml
blocked_resolution:
  reason_id: BLOCK-001
  resolved_by: task-orchestrator-agent
  resume_to: test_adversarial_reviewed
  evidence: evidence/block-resolution.json
```

## 6. 设计前置门

进入 `in_progress` 前，必须根据 `work_type` 和变更标签生成适用的设计产物，并由 Task Owner、架构师和设计师（适用时）批准：

- 用户目标和验收场景
- 领域规则、不变量、正例和反例
- 架构方案和模块边界
- API/Schema/状态契约
- 前端交互状态和测试抓手（前端任务）
- 安全、性能、可靠性和可观测性约束
- 测试策略和证据计划
- 明确不在范围内的内容

缺少任一项，任务保持 `blocked` 或 `draft`。

静态前端任务可以将 API、持久化和网络状态标记为 `not_applicable`，但必须留下适用性判断和理由；不得用空文件代替设计。

## 7. Checkpoint 规则

每个 checkpoint 必须：

- 只实现一个业务行为或完整的小场景
- 说明修改文件和修改原因
- 说明未修改的范围
- 提交测试计划和预期证据；测试结果在后续质量门产生
- 通过后续 Clean Code、自动化测试和适用的浏览器验证门

单个 checkpoint 默认不得超过 5 个业务相关文件；超过时必须由 Task Owner 批准并记录拆分理由。

## 8. Agent 开始编码前的复述

编码 Agent 必须先提交：

```yaml
implementation_ack:
  understood_goal: true
  invariants:
    - 业务不变量
  design_refs:
    - ADR-001
    - schema@<approved-version>
  files_to_change:
    - src/xxx.ts
  files_out_of_scope:
    - src/yyy.ts
  tests_to_add_or_run:
   - npm test -- xxx
  unresolved_questions: []
  schema_ref: schema@<approved-version>
```

复述与设计契约不一致时，必须返回设计评审，不得自行补全。

## 9. 质量门顺序

```text
角色分配验证
  → 任务契约和对抗评审
  → 设计评审
  → 测试策略门
  → 每个 checkpoint 执行 TDD：Red → Green → Refactor
  → 编码
  → Red：测试 Agent 先提交失败测试及非零退出码
  → Green：编码 Agent 写最小实现，测试 Agent 执行并记录零退出码
  → Refactor：编码 Agent 重构，Clean Code Reviewer 复核并重新执行测试
  → 格式化、lint、类型检查、构建
  → 架构一致性和测试评审
  → 独立代码评审
  → 集成/API/安全/回归验证
  → 前端 E2E 和视觉验证
  → Task Owner 验收
```

后端任务不需要强制执行浏览器门，但必须执行适用的 API、集成和契约测试。前端任务必须执行真实浏览器 E2E；UI 变更必须执行桌面和移动视口验证。安装依赖、启动开发服务器、生成 Playwright 配置、静态渲染页面或存在测试文件都不算测试执行；必须有实际命令、退出码和报告、trace 或截图证据。前端 Agent 不得通过询问用户是否需要 E2E 来延期；环境缺失时必须 `blocked`。

质量门配置中的 `gate_sequences` 是唯一有效顺序。执行器必须按 `common → work_type → matching conditional → feature_closure → final` 合并，保持声明顺序、去除重复门；未知条件、未知变更标签或门定义缺失都必须阻塞。任务上下文中的 `required_gates` 只能由质量门配置生成，Agent 不得自行删减。`feature_closure` 不得被移到项目最终门之后，也不得早于适用的安全、契约、迁移和发布门。

`agent_assignments_verified` 是编码前阻塞门，必须验证所有必需生产角色及其对抗角色已经分配独立运行时 Agent，尤其是 `automated_test`、`test_adequacy_adversary`、`clean_code_reviewer` 和 `maintainability_adversary`。并发槽位不足时只能分阶段调度，但必须先登记完整分配表和不同 `agent_id`，不得先写代码再补登记。

`test_strategy_ready` 是编码前测试门。Automated Test Agent 必须提交需求到测试映射、实际命令、fixture/账号/数据库/浏览器重置方案、异常边界和回归计划；前端或全栈还必须提交真实浏览器 E2E、可访问性和视觉测试计划。没有该门证据，编码 Agent 只能保持 `blocked`。

测试环境准备必须通过已注册的控制器命令执行；允许安装测试依赖，但不能写入业务源代码。依赖清单、锁文件或生产配置发生变化时，必须回到设计评审并重新生成命令注册表。安装依赖、启动服务器、生成测试配置或创建测试文件仍然不算 Red、Green 或 E2E 测试。

### 功能级验收门

每个 `feature_id` 在进入下一个功能前必须通过 `feature_acceptance_passed`。验收命令必须从真实入口运行完整的批准场景：后端使用真实 API/集成链路，前端和全栈使用真实浏览器 E2E，并覆盖成功、失败、重试、边界和持久化结果。单元测试、组件测试、类型检查、构建通过或“代码已评审”都不能代替功能验收。

Task Owner 和 Acceptance Challenger 必须以不同 Agent 身份独立检查同一功能版本，并提交 `evidence/feature-acceptance.json`、报告和 trace/video。验收失败、证据缺失或存在高/阻断缺陷时，功能状态为 `blocked`；Feature Orchestrator 不得分配、启动或编码下一个功能。只有验收证据冻结、缺陷登记关闭且质量门控制器确认前一 `feature_id` 已通过，才允许创建下一个功能小组。

## 10. 评审独立性

评审者必须记录 `agent_id`、角色、评审版本和结论。以下组合禁止批准：

- 编码 Agent 批准自己的实现
- 测试 Agent 批准自己编写的测试
- 架构师批准自己未被其他架构师复核的重大架构决策
- 架构师担任自己任务的 `architecture_reviewer`
- 测试方案或测试代码作者担任该任务的 `test_reviewer`
- 设计师批准自己设计的最终视觉结果
- 同一 Agent 同时充当实现者和独立代码评审者

如果代理槽位不足，角色可以分阶段复用，但同一产物的实现和批准不能由同一 Agent 完成。

## 11. 证据要求

每个质量门必须记录：

- task_id、checkpoint_id 和产物版本
- 执行 Agent、时间、环境和代码版本
- 实际执行的命令
- 通过或失败日志
- 截图、视频、trace 或报告路径
- 失败时的复现步骤和缺陷编号

“已检查”“应该通过”“代码看起来没问题”不属于有效证据。

## 12. 强制阻塞条件

- 需求、接口、Schema 或交互状态存在冲突
- 设计尚未批准
- 基线测试失败且原因不明
- 任务超出批准范围
- 新增依赖、公共接口或数据迁移未经设计评审
- 测试无法独立、重复或从干净环境运行
- E2E 只依赖脆弱选择器或无法真实操作
- 有未解释的控制台、网络、安全或数据一致性错误
- 任一高严重性缺陷未关闭

## 13. 任务关闭

Task Owner 只有在以下条件全部满足后才能关闭任务：

- 设计产物和版本可定位
- 所有验收条件都有证据
- Clean Code、自动化测试和独立评审通过
- 前端任务的 E2E 和视觉验证通过
- 高严重性缺陷关闭
- 运行和回滚说明在存在发布目标、公共 API 或数据迁移时齐全
