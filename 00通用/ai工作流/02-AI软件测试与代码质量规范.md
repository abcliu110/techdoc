# AI软件测试与代码质量规范

> 版本：1.2.0
> 状态：正式版
> 用途：证明设计被正确实现，并保证代码可维护、可回归、可交付。

执行顺序、角色身份、质量门状态和控制器拒绝规则以同目录的 `00-AI研发执行协议.md`、`03-AI质量门控制器接口规范.md` 和 `ai研发质量门.yaml` 为准。本文件只定义测试与代码质量的专业判定标准，避免重复定义流程状态。

## 1. 总则

测试不是代码写完后的补救，也不是测试数量竞赛。测试必须从设计阶段开始，覆盖业务规则、状态转换、异常行为、边界条件和真实用户流程。

没有实际命令、日志、报告或运行证据的“通过”不成立。

## 2. 测试追踪

每个需求、规则和验收场景必须映射到测试：

```yaml
traceability:
  - requirement: LEARNING-003
    scenarios:
      - tests/api/duplicate-submit.spec.ts
      - tests/e2e/duplicate-submit.spec.ts
    negative_cases:
      - repeated_request
      - concurrent_request
```

覆盖率只能作为参考，不能替代行为、边界和风险覆盖。

## 2.1 测试驱动开发（TDD）

每个 checkpoint 和每个独立业务行为必须执行 Red-Green-Refactor，不得等全部代码完成后再统一补测试。TDD 的快照、写入审计和命令审计要求见 `03-AI质量门控制器接口规范.md`；单靠 Agent 的口头声明、提交顺序或报告不能证明阶段成立：

1. **Red**：自动化测试 Agent 根据批准的验收场景先编写测试。测试必须针对尚未实现的行为失败，记录实际命令、退出码、失败断言和测试版本。测试代码版本必须早于生产实现版本。
2. **Green**：编码 Agent 只实现让当前失败测试通过所需的最小代码。自动化测试 Agent 必须重新执行同一测试，并记录零退出码和回归结果。
3. **Refactor**：编码 Agent 在测试保护下改善结构、命名、边界和注释。Clean Code Reviewer 及 Maintainability Adversary 检查重构，测试 Agent 必须再次执行测试确认行为未改变。

禁止先完成生产代码再补测试；禁止删除、放宽断言、跳过测试或修改预期结果来制造 Red/Green；禁止把安装测试依赖、启动服务器或生成测试配置当作测试执行。任一阶段缺少失败/通过日志、代码版本、测试版本或交接单，当前 checkpoint 必须 `blocked`。

发现生产代码先于测试产生时，不得继续使用该代码证明 Green。当前 checkpoint 必须标记为 `invalidated/unverified`，保留代码用于审计，重新提交 checkpoint，由测试 Agent 先写出真实失败测试并从 Red 阶段开始；恢复路径由协议自动决定，不向用户提供“继续测试/重新 TDD”的选择。

## 3. 后端测试规范

| 层级 | 内容 | 必要证据 |
|------|------|----------|
| Schema | 合法、非法、缺失、极值和类型错误 | Schema 测试日志 |
| 单元 | 核心规则、分支、异常和边界 | 单元测试报告 |
| 集成 | 数据库、事务、队列和外部依赖 | 集成测试日志 |
| 契约 | 请求、响应、状态码、错误码和兼容性 | API 契约报告 |
| 安全 | 认证、授权、越权、敏感数据和输入攻击 | 安全检查记录 |
| 回归 | 受影响模块的原有行为 | 回归测试日志 |

必须覆盖空值、重复请求、并发、超时、依赖失败、事务回滚、未认证、无权限、资源不存在和错误信息脱敏。

## 4. 前端测试规范

### 4.1 组件测试

验证初始、输入、加载、成功、空数据、失败、重试、重复提交、键盘和可访问性基本行为。

### 4.2 E2E 测试

必须使用真实浏览器从真实入口执行：

1. 打开页面或路由
2. 通过用户可操作元素点击、输入或选择
3. 验证状态变化和关键请求结果
4. 覆盖成功、失败、重试和取消路径
5. 验证最终页面、下一步或持久化结果

```typescript
await page.goto('/practice');
await page.getByTestId('question-card-q1').click();
await page.getByRole('button', { name: '提交答案' }).click();
await expect(page.getByTestId('answer-result')).toHaveAttribute('data-state', 'success');
```

禁止只渲染组件、直接修改内部状态或只检查 URL 就声称 E2E 通过。

### 4.3 可视化验证

UI 变更必须在桌面和移动视口检查：非白屏、无溢出、无遮挡、文字完整、按钮可操作、错误和加载状态布局正常、弹层在视口内、无未解释的横向滚动。

截图必须记录视口、数据状态和代码版本。动态区域可以局部遮罩，但不能用大面积遮罩掩盖布局问题。

## 5. 测试环境和稳定性

- 测试可独立、重复、任意顺序运行
- 测试账号、数据库、浏览器状态和 fixture 可重置
- 时间、随机数、网络和外部服务可控制
- 测试结束清理临时数据、文件和进程
- 控制台错误、网络错误和页面异常必须收集
- Flaky Test 不能靠无限重试掩盖；持续不稳定必须建立缺陷并阻塞相关质量门

## 6. Clean Code 检查

TDD Green 阶段通过后、进入 Refactor 和回归确认时，`clean_code_reviewer` 必须检查：

- 命名表达业务含义
- 函数、组件和模块职责单一
- 控制流和条件复杂度可理解
- 重复逻辑有合理处理，没有过度抽象
- 依赖方向清晰，无循环依赖
- 错误不被吞掉，不返回假成功
- 没有死代码、注释掉的旧代码、魔法数字和无依据硬编码
- 格式化、lint、类型检查和构建通过

### 注释规范

代码结构应先表达“做什么”，注释解释代码无法表达的“为什么”：

- 公共 API、复杂算法、状态机、并发、事务和兼容性处理必须说明约束
- 业务规则注释必须引用规则编号或契约版本
- `TODO/FIXME` 必须说明原因、后续动作和任务编号
- 修改逻辑时同步维护注释
- 禁止用大段注释掩盖过长函数或糟糕设计
- 禁止保留整段被注释掉的旧代码

```typescript
// 规则 LEARNING-003：服务端要求幂等键，避免移动网络重试造成重复学习记录。
await submitAnswer(answer, { idempotencyKey: attemptId });
```

发现结构性问题时，必须重命名、拆分、调整边界或更新设计，不能只补注释。

Clean Code 检查必须提供工具输出和项目阈值。至少记录圈复杂度、函数长度、文件长度、重复率、死代码和注释一致性；超过阈值时必须有原因、负责人、到期时间和 Task Owner 批准。只写“代码整洁”“可维护”不能作为通过证据。

## 7. 评审角色

### Clean Code Reviewer

关注结构、可读性、复杂度、错误处理和注释，不能批准自己编写的代码。

### 架构一致性 Reviewer

关注实现是否遵守批准的模块边界、Schema、API、状态和 ADR。

### 测试 Reviewer

关注测试是否覆盖需求、异常、边界、回归和真实行为，是否存在修改测试制造通过。

### E2E/视觉 Reviewer

关注真实浏览器流程、抓手稳定性、控制台和网络错误、桌面/移动布局和关键状态。

任何高严重性问题都必须回到 `changes_requested`，修复后重新执行受影响的全部质量门。

## 8. 缺陷闭环

```markdown
问题编号：BUG-MOD-001
发现于：MODULE-001-C02
严重性：阻断/高/中/低
环境：运行时、浏览器、数据版本
复现步骤：
1.
2.
实际结果：
期望结果：
证据：日志/截图/视频/trace
根因：
修复文件：
回归测试：
状态：open → fixing → verifying → closed
```

关闭条件：根因已解释、增加回归测试、原失败用例通过、受影响模块通过、前端问题重新完成 E2E/视觉验证、独立验证者确认。

## 9. 发布和回滚验证

发布前必须执行干净构建、测试环境部署、迁移演练、核心流程冒烟、监控确认和发布后验证。涉及数据或公共接口的变更必须提供可执行回滚步骤和数据一致性检查。

## 10. 功能级验收

每个 `feature_id` 完成后必须单独验收，验收通过前不得开始下一个功能。验收不是把已有测试报告重新汇总，而是从真实入口运行批准的完整业务场景：后端使用真实 API、数据库和依赖链路；前端或全栈使用真实浏览器 E2E。至少覆盖成功、失败、重试、边界和持久化结果，并保存命令、退出码、报告、trace/video 和版本信息。

`feature_acceptance_passed` 必须由 Task Owner 和独立的 Acceptance Challenger 对同一版本分别提交结论。任何失败、未解释的控制台/网络错误、证据缺失或高/阻断缺陷都会阻止下一个功能启动。只有验收记录冻结且缺陷登记关闭，Feature Orchestrator 才能创建新的 `feature_team`。
