## 概念分组（按业务语义）

- **凭证管理组**：凭证、凭证分录、凭证字

- **时间管理组**：会计期间、期间状态
- **数据聚合组**：科目余额、凭证汇总
- **报表系统组**：总账、明细账、余额表、报表钻取

### GC-01：凭证

```
① 身份：
  凭证是GL总账的核心业务对象，是业务事件被转化为标准财务语言的"第一公民"。
  它不是简单的数据记录，而是一个包含时间、责任、金额、来源的完整"价值确认契约"。

② 结构：
  凭证由表头（GL_VOUCHER）+ 多条分录（GL_VOUCHERENTRY）组成。
  表头：凭证号、凭证日期、账簿、凭证字、制单人、审核人、附件张数
  分录：科目、借贷方向、金额、核算维度、摘要

③ 关系：
  ──属于──▶ 账簿（BD_AccountBook）：凭证归属的财务边界
  ──记录──▶ 业务凭证映射（BAS_BusinessVoucher）：业务来源追溯
  ──由多条──▶ 凭证分录（GL_VOUCHERENTRY）：借贷明细
  ──引用──▶ 会计科目（BD_Account）：核算分类
  ──发生于──▶ 会计期间（BD_FiscalPeriod）：时间归属

④ 行为：
  创建（手工/自动生成）→ 保存 → 审核 → 过账 → 结账后归档
  反方向：反过账 ← 反审核 ← 保存 ← 修改

⑤ 交互：
  业务单据审核事件 ──触发──▶ 凭证生成
  用户审核操作 ──触发──▶ 凭证状态变更
  报表查询请求 ──读取──▶ 凭证数据

⑥ 生命（时间线叙事）：
  一张凭证从"想法"开始：当业务人员在AP模块录入一张采购发票并审核，
  系统异步生成一张凭证。凭证在"保存"状态等待财务确认。
  财务审核后，凭证获得"已审核"状态，可以参与过账。
  过账后，凭证成为"历史档案"，不可再修改，只能查看和追溯。
  到了期末结账，这张凭证成为账簿历史的一部分，被永远归档。

⑦ 实现：
  表结构：GL_VOUCHER（凭证表头）、GL_VOUCHERENTRY（凭证分录）
  主键：FID（全局唯一标识）
  凭证号：FVoucherNo（全局自增，有业务语义如"GJ-2024-0032"）
  状态：FDocumentStatus（保存/已审核/已过账）
  E-SRC: 快速参考卡.md

⑧ 失败：
  - 借贷不平衡：凭证创建失败，提示借贷合计不相等
  - 科目不存在：分录保存失败，提示科目无效
  - 期间已关闭：凭证保存失败，提示当前期间不可录入
  - 凭证已审核：修改被拒绝，提示需先反审核
  - 凭证已过账：删除被拒绝，提示需先反过账

⑨ 证据：
  E-SRC: 快速参考卡.md（表结构）
  E-SRC: VoucherGenerateService.cs（生成逻辑）
  E-SRC: ViewGlVoucher.cs（联查逻辑）

⑩ 未知：
  U-04：多账簿场景下凭证的跨账簿查询逻辑未完全验证
```

### GC-02：凭证分录

```
① 身份：
  凭证分录是凭证的"价值原子"，每一条分录记录了"哪个科目收了多少钱"。
  凭证必须有借必有贷，借贷必相等——分录是这一规则的执行单元。

② 结构：
  凭证分录从属于凭证表头，包含：科目、借贷方向、金额、摘要、核算维度组合。
  一张凭证至少有两条分录（借方+贷方），也可能有多条（如多借多贷）。

③ 关系：
  ──从属于──▶ 凭证（GL_VOUCHER）：FK=FVoucherID
  ──引用──▶ 会计科目（BD_Account）：FK=FAccountID
  ──参与──▶ 业务凭证映射（BAS_BusinessVoucher）：分录与业务单据的精确对应

④ 行为：
  分录只能与凭证一起存在，不能单独创建或删除。
  分录的借贷金额汇总控制凭证的平衡状态。
  分录中的科目必须是账簿科目体系中的有效科目。

⑤ 交互：
  凭证创建时 ──逐条录入──▶ 分录明细
  过账时 ──逐条计算──▶ 科目余额更新

⑥ 生命（时间线叙事）：
  一条分录的生命从"用户输入科目和金额"开始。
  系统校验科目有效性和借贷平衡后，分录被保存。
  凭证审核后，分录进入"已确认"状态。
  凭证过账后，分录的金额被聚合到AccountBalance表中，
  成为报表数据的来源。分录本身不会被修改或删除，只会反过账后重新生成。

⑦ 实现：
  表结构：GL_VOUCHERENTRY
  主键：FID
  外键：FVoucherID（关联GL_VOUCHER）
  金额字段：FDebit（借方）、FCredit（贷方）
  E-SRC: 快速参考卡.md

⑧ 失败：
  - 借贷不平衡：凭证保存失败
  - 科目不在科目体系中：分录保存失败
  - 金额为负数：分录保存失败
  - 外键凭证不存在：分录无法保存

⑨ 证据：
  E-SRC: 快速参考卡.md（表结构）
  E-SRC: VoucherGenerateService.cs（生成逻辑）

⑩ 未知：
  U-06：核算维度的多层级组合逻辑未深入验证
```

### GC-03：业务凭证映射

```
① 身份：
  业务凭证映射（BAS_BusinessVoucher）是连接业务世界（AP/AR/CN/CB）
  和财务世界（GL）的"桥梁"。
  它解决了一个核心问题：一张业务单据可以生成多张凭证，
  一张凭证也可以对应多张业务单据——多对多关系需要一个独立的映射表。

② 结构：
  映射表包含：业务单据ID、业务单据类型、凭证ID、会计科目（分录级）。
  扩展后可增加：钩稽状态、确认人、确认时间。

③ 关系：
  ──连接──▶ 业务单据（各子系统）：FK=FSourceBillID
  ──连接──▶ 凭证（GL_VOUCHER）：FK=FVoucherID
  ──可选关联──▶ 凭证分录（GL_VOUCHERENTRY）：FK=FVoucherEntryID

④ 行为：
  业务单据审核时 ──自动创建──▶ 映射记录
  凭证联查时 ──通过映射──▶ 找到业务来源
  凭证作废时 ──更新映射──▶ 标记为已解除

⑤ 交互：
  凭证生成服务 ──写入──▶ BAS_BusinessVoucher
  业务单据联查 ──查询──▶ BAS_BusinessVoucher → GL_VOUCHER
  凭证联查 ──查询──▶ BAS_BusinessVoucher → 业务单据

⑥ 生命（时间线叙事）：
  当一张采购发票被审核，系统会创建一条映射记录，说"这张发票生成了那张凭证"。
  财务看到凭证后，可以追溯"这张凭证对应哪张发票"。
  如果发票需要调整，财务可能作废凭证，系统更新映射状态。
  如果重新生成凭证，映射表会增加新记录，形成完整的"钩稽历史"。

⑦ 实现：
  表结构：BAS_BusinessVoucher
  主键：FID
  核心字段：FSourceBillID（业务单据）、FSourceFormID（业务类型）、FVoucherID（凭证）
  E-SRC: ViewGlVoucher.cs:30（查询逻辑）

⑧ 失败：
  - 映射不存在：联查失败，用户看到"无关联凭证"
  - 凭证已删除但映射未清理：联查返回空，但映射记录仍存在（脏数据）
  - 多对多导致状态歧义：一张凭证钩稽多张单据，部分确认时状态不一致

⑨ 证据：
  E-SRC: ViewGlVoucher.cs:30-60（查询BAS_BusinessVoucher）
  E-SRC: GL总账进化实施规格.md §2（钩稽状态机设计）

⑩ 未知：
  U-07：多对多关系下的部分确认场景的具体实现
```

### GC-04：账簿

```
① 身份：
  账簿是GL总账的"财务户口本"，定义了财务核算的独立边界。
  一个组织（公司）可以有一个或多个账簿，每个账簿有自己独立的科目体系、
  会计期间、凭证编号体系。账簿是凭证的"归属容器"。

② 结构：
  账簿包含：账簿名称、所属组织、本位币、会计制度、凭证字集合。

③ 关系：
  ──拥有──▶ 凭证（GL_VOUCHER）：一对多
  ──关联──▶ 科目体系（BD_AccountSystem）：一对一
  ──包含──▶ 会计期间（BD_FiscalPeriod）：一对多
  ──使用──▶ 凭证字（凭证字配置）：一对多

④ 行为：
  创建账簿时 ──同时创建──▶ 默认科目体系
  凭证归属 ──由账簿决定──▶ 凭证的财务责任边界
  账簿结账 ──影响──▶ 该账簿下所有期间

⑤ 交互：
  凭证创建时 ──必须指定──▶ 归属账簿
  账簿管理员 ──管理──▶ 账簿下的科目、期间、凭证字
  财务主管 ──操作──▶ 账簿的结账/反结账

⑥ 生命（时间线叙事）：
  一个新公司成立时，账套管理员创建账簿。
  账簿被初始化后，会自动生成12个月份的会计期间。
  随着业务开展，凭证源源不断进入账簿。
  月末，财务主管关闭当月期间，账簿进入"已结账"状态。
  年末，整个账簿进入"已年结"状态，历史数据被归档。

⑦ 实现：
  表结构：BD_AccountBook（T_BD_ACCTBOOK）
  主键：FID
  关键字段：FName（账簿名称）、FCreateOrgId（所属组织）
  E-SRC: 快速参考卡.md

⑧ 失败：
  - 凭证账簿与业务单据组织不一致：凭证无法生成
  - 账簿科目体系与凭证科目不匹配：分录保存失败
  - 账簿已结账：无法新增凭证

⑨ 证据：
  E-SRC: 快速参考卡.md（表结构）
  E-SRC: GL总账进化实施规格.md §4（责任边界模型）

⑩ 未知：
  U-08：账簿移交（组织调整）时的凭证归属变更逻辑
```

### GC-05：会计科目

```
① 身份：
  会计科目是财务核算的"分类标签"，是"以业务语言描述的财务维度"。
  它定义了每一笔金额要归到哪一类——资产、负债、权益、收入、费用。
  科目不是简单的名字，而是一套有层级、有规则的分类体系。

② 结构：
  科目包含：科目编码、科目名称、科目类别（资产/负债等）、
  余额方向（借/贷）、核算维度集合、辅助核算标志。

③ 关系：
  ──归属──▶ 科目体系（BD_AccountSystem）：多对一
  ──被使用──▶ 凭证分录（GL_VOUCHERENTRY）：一对多
  ──累计──▶ 科目余额（AccountBalance）：一对多

④ 行为：
  凭证分录引用科目时 ──校验──▶ 科目有效性和辅助核算完整性
  过账时 ──按科目聚合──▶ 更新AccountBalance

⑤ 交互：
  凭证录入 ──选择──▶ 科目（来自当前账簿的科目体系）
  报表查询 ──按科目维度──▶ 聚合分录数据

⑥ 生命（时间线叙事）：
  新会计年度开始前，账套管理员维护科目体系，增加新科目或调整科目属性。
  全年中，凭证录入员日复一日地在凭证中引用这些科目。
  每一笔分录的金额，被归集到对应科目下。
  到了期末，科目余额表显示每个科目"累计收了多少钱、付了多少钱"。

⑦ 实现：
  表结构：BD_Account（T_BD_ACCOUNT）
  主键：FID
  关键字段：FNumber（编码）、FName（名称）、FAccountGroupID（科目类别）
  E-SRC: 快速参考卡.md

⑧ 失败：
  - 科目被禁用：凭证分录无法引用
  - 科目无辅助核算但分录提供了核算维度：校验失败
  - 科目体系版本切换：历史凭证引用的科目可能失效

⑨ 证据：
  E-SRC: 快速参考卡.md（表结构）

⑩ 未知：
  U-09：科目体系版本切换的具体实现机制
```

### GC-06：会计期间

```
① 身份：
  会计期间是财务核算的"时间盒子"，将连续的业务流切分为离散的时间段。
  每一个期间是一个独立的核算单元，有自己的"打开/关闭"状态。
  期间不可跨越，只能顺序处理——这体现了财务核算的严谨性。

② 结构：
  期间包含：年度、月份、开始日期、结束日期、状态（打开/关闭/结账）。

③ 关系：
  ──归属──▶ 账簿（BD_AccountBook）：多对一
  ──包含──▶ 凭证（GL_VOUCHER）：一对多
  ──产生──▶ 科目余额（AccountBalance）：按期间聚合

④ 行为：
  期初 ──打开──▶ 允许录入凭证
  期末 ──关闭──▶ 禁止新增/修改凭证
  年结 ──锁定──▶ 全年期间不可再调整

⑤ 交互：
  凭证保存时 ──检查──▶ 凭证日期是否在开放期间内
  期间结账时 ──检查──▶ 所有凭证是否已审核/过账
  报表查询时 ──传入──▶ 期间过滤参数

⑥ 生命（时间线叙事）：
  每月1日，新期间被自动打开（或手动打开）。
  全月中，凭证在开放的期间内自由流转。
  每月最后一天，财务人员进行期间结账。
  结账后，期间的"大门关闭"，历史凭证被永远锁定。
  如果发现错误，只能通过"反结账"重新打开，或者在后续期间调整。

⑦ 实现：
  表结构：BD_FiscalPeriod（期间表）
  主键：FID
  关键字段：FYear（年度）、FPeriod（月份）、FStatus（状态）
  E-SRC: 快速参考卡.md

⑧ 失败：
  - 凭证日期早于期间开始：凭证保存失败
  - 凭证日期晚于期间结束：凭证保存失败
  - 期间已关闭：凭证无法修改
  - 有未审核凭证：期间结账被阻止

⑨ 证据：
  E-SRC: 快速参考卡.md（表结构）

⑩ 未知：
  U-10：跨年期间的特殊处理逻辑（如12月跨年场景）
```

### GC-07：科目余额

```
① 身份：
  科目余额是凭证分录的"聚合缓存"，是GL总账的"预计算结果"。
  它不记录每一笔分录，而是记录每个科目在每个期间的累计发生额和余额。
  查询报表时直接读余额表，而不是每次都聚合全量凭证分录——这是性能优化的设计。

② 结构：
  余额记录包含：科目ID、期间ID、期初余额（借/贷）、本期发生额（借/贷）、期末余额（借/贷）。

③ 关系：
  ──由凭证分录累计──▶ 科目余额（GL_VOUCHERENTRY → AccountBalance）
  ──关联──▶ 会计科目（BD_Account）：FK=FACCOUNTID
  ──关联──▶ 会计期间（BD_FiscalPeriod）：FK=FPeriodID

④ 行为：
  凭证过账时 ──更新──▶ 科目余额（增加本期发生额，重新计算期末）
  凭证反过账时 ──回滚──▶ 科目余额（减少本期发生额）
  报表查询时 ──读取──▶ 科目余额（而非实时聚合凭证）

⑤ 交互：
  凭证过账服务 ──写入──▶ AccountBalance
  总账/余额表报表 ──读取──▶ AccountBalance

⑥ 生命（时间线叙事）：

⑦ 实现：

  关键字段：FDebitBalance、FCreditBalance（期初）、FPeriodDebit、FPeriodCredit（本期）、FEndBalance（期末）
  E-SRC: 快速参考卡.md

### GC-08：报表钻取路径

```
① 身份：
  报表钻取路径是用户从"总账→明细账→凭证"的导航轨迹。
  这个轨迹在K3Cloud中由"方案ID顺序状态机"管理——
  每一次钻取消耗一个方案ID，ID耗尽则钻取终止。
  方案ID是会话级隐式状态，关闭浏览器后丢失。

② 结构：
  钻取路径包含：起始报表、目标报表、过滤参数、方案ID。

③ 关系：
  ──存储在──▶ IUserParameterService（会话状态）
  ──读取──▶ 总账（GL_RPT_GeneralLedger）
  ──打开──▶ 明细账（GL_RPT_SubLedger）
  ──打开──▶ 凭证联查（ViewGlVoucher）

④ 行为：
  总账Cell点击 ──查询方案ID──▶ GetNextEntrySchemeId
  方案ID有效 ──打开明细账──▶ UpdateNextEntrySchemeId（消耗一个ID）
  方案ID耗尽（-1）──▶ 钻取终止

⑤ 交互：
  用户双击总账单元格 ──触发──▶ CellDbClick事件
  CellDbClick ──调用──▶ CheckViewDetailRight + GetNextEntrySchemeId
  方案ID更新 ──持久化──▶ IUserParameterService

⑥ 生命（时间线叙事）：
  用户打开总账，方案ID从0开始。
  双击某科目行，钻取到明细账，方案ID变成目标报表的ID（如"100"）。
  双击明细账某行，钻取到凭证，方案ID变成-1（耗尽）。
  用户关闭浏览器，再次打开时，方案ID状态已丢失。
  如果用户想从凭证返回明细账——对不起，路径已经断了。

⑦ 实现：
  服务：IUserParameterService
  方法：GetNextEntrySchemeId、UpdateNextEntrySchemeId
  存储：用户参数表（会话级）
  E-SRC: ReportFilterCommonFunction.cs:1023

  - 方案ID为-1：无法继续钻取
  - 权限不足：钻取被Cancel
  - 多Tab并发：不同Tab的状态互相覆盖

⑨ 证据：
  E-SRC: ReportFilterCommonFunction.cs:1023（GetNextEntrySchemeId）
  E-SRC: GeneralLedger.cs:30（CellDbClick）

### GC-09：确认契约（EVO-E-GL-001B）

```
① 身份：
  确认契约是"业务单据审核"与"GL凭证生成"之间的双向承诺协议。
  它解决的是异步两阶段模式下的双向盲区——
  业务端不知道凭证是否生成，财务端不知道业务单据是否审核。
  契约模式将"提议→确认"显式化，消除盲区。

② 结构：
  契约包含：契约ID、业务单据ID、凭证ID（null=待确认）、状态、提议时间、确认时间、过期时间、超时策略。

③ 关系：
  ──提议──▶ 业务单据审核事件
  ──确认──▶ 凭证生成完成事件
  ──级联──▶ 钩稽关系（BAS_BusinessVoucher）

④ 行为：
  业务单据审核 → 契约提议（Proposed）→ 异步凭证生成 → 契约确认（Confirmed）或超时取消（Cancelled）

⑤ 交互：
  业务子系统审核 → 发布ContractProposedEvent
  凭证生成服务 → 订阅事件 → 生成凭证 → 确认契约
  契约超时监控 → 超时未确认 → 自动取消契约

⑥ 生命（时间线叙事）：
  业务人员在AP模块审核一张发票。
  系统立即创建一个契约（状态=Proposed），并显示"确认中"给业务人员。
  后台异步生成凭证。如果30分钟内凭证生成成功，契约状态变为"Confirmed"，
  业务端看到"已确认"标记。如果超时，契约自动取消，通知相关人员。

⑦ 实现：
  表结构：GL_ConfirmationContract（新增）
  状态机：Proposed → Confirmed / Failed / Cancelled
  超时策略：Cancel / Notify / Escalate
  E-SRC: GL总账进化实施规格.md §1

⑧ 失败：
  - 契约重复提议：并发审核同一单据，数据库唯一约束防止
  - 凭证生成后契约已超时：动态超时计算
  - 事件总线消息丢失：事件溯源 + 补偿机制

⑨ 证据：
  E-SRC: GL总账进化实施规格.md §1（完整Schema和状态机）

⑩ 未知：
  无
```

### GC-10：钩稽关系状态（EVO-E-GL-002A）

```
① 身份：
  钩稽关系状态将BAS_BusinessVoucher从"简单的关联表"升级为"有状态的生命周期实体"。
  钩稽不仅是"是否关联"，还要表达"关联的质量"——
  待确认、已确认、已拒绝、已解除。

② 结构：
  钩稽状态扩展字段：FHookStatus、确认人、确认时间、拒绝/解除原因。

③ 关系：
  ──由确认契约触发──▶ PENDING_CONFIRMATION
  ──由财务确认──▶ CONFIRMED
  ──由凭证作废──▶ BROKEN
  ──由重新生成──▶ 回到PENDING_CONFIRMATION

④ 行为：
  钩稽待确认 → 财务检查金额/科目匹配 → 确认/拒绝/解除
  钩稽已确认 → 凭证作废 → 自动解除关联
  钩稽已解除 → 重新生成凭证 → 新的钩稽待确认

⑤ 交互：
  财务人员 → 确认钩稽 → 更新FHookStatus=Confirmed
  凭证作废事件 → 自动触发钩稽状态变更
  报表查询 → 按钩稽状态过滤

⑥ 生命（时间线叙事）：
  发票审核后，系统创建一个"待确认"的钩稽记录。
  财务人员看到凭证后，检查业务单据与凭证的金额是否一致。
  如果一致，点击"确认钩稽"，钩稽进入"已确认"状态。
  如果金额不匹配，财务拒绝钩稽，并记录原因。
  如果后续凭证被作废，钩稽自动进入"已解除"状态。

⑦ 实现：
  表结构变更：BAS_BusinessVoucher增加FHookStatus等字段
  新增历史表：BAS_BusinessVoucherHistory
  E-SRC: GL总账进化实施规格.md §2

⑧ 失败：
  - 并发确认同一钩稽：乐观锁防止
  - 凭证删除后钩稽悬空：软删除凭证，级联变更钩稽状态
  - 多对多关系部分确认：引入"部分确认"状态

⑨ 证据：
  E-SRC: GL总账进化实施规格.md §2（完整状态机和服务接口）

⑩ 未知：
  无
```
