### DEC-001：凭证表头与分录行分离设计

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么凭证要分为表头（GL_VOUCHER）和分录（GL_VOUCHERENTRY）两张表，而不是一张表？ |
| 当时约束 | 一张凭证可能有多条分录（多借多贷），每条分录的借贷方向和金额不同 |
| 可选方案 | 方案A：表头分录分离（当前方案）；方案B：单表设计，分录用JSON存储；方案C：单表设计，每条分录一行但冗余表头字段 |
| 选择与理由 | 选择方案A。分离设计保证数据规范化：表头信息不重复存储；分录数量灵活（1-N条）；支持按分录级别查询和钩稽；外键关联清晰，数据完整性有保障。方案B的JSON字段无法建立外键约束，方案C的冗余字段难以维护一致性。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：符合数据库规范化原则，支持灵活的分录数量 |
| 当前合理性 | 仍合理：仍然是最佳实践，支持业务灵活性 |
| 影响面 | 伤历史（已有数据需迁移）/ 只伤未来（不影响历史数据） |

### DEC-002：凭证联查两级权限降级

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么凭证联查要实现两级权限降级（GL子系统权限→子系统独立权限）？ |
| 当时约束 | 业务单据（如AP发票）由业务子系统管理，凭证由GL子系统管理。业务人员有业务单据权限，但可能没有GL凭证权限。 |
| 可选方案 | 方案A：两级降级（当前方案）；方案B：强制要求GL凭证权限；方案C：完全信任业务权限 |
| 选择与理由 | 选择方案A。业务人员审核发票后，需要能联查生成的凭证。但业务人员通常没有被授予GL凭证权限（这是财务权限）。两级降级实现了"业务优先，财务兜底"的权限模型：优先检查GL凭证权限，如果无权限，再降级检查业务单据来源权限。方案B会导致业务人员无法联查凭证；方案C会让业务人员看到所有凭证（安全性问题）。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：平衡了业务便利性和财务安全性 |
| 当前合理性 | 仍合理：但可进一步优化为"责任边界显式化"模型（EVO-E-GL-004） |
| 影响面 | 伤历史（需兼容旧权限体系）/ 只伤未来（不影响历史凭证） |

### DEC-003：报表钻取依赖方案ID状态机

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么报表钻取要依赖IUserParameterService管理的方案ID状态机，而不是用URL参数传递？ |
| 当时约束 | 报表钻取需要知道"从哪个报表的哪一行钻取"，这个上下文需要跨请求保持。钻取过程中还需要权限检查（CheckViewDetailRight）。 |
| 可选方案 | 方案A：方案ID状态机（当前方案）；方案B：URL参数传递；方案C：数据库会话表 |
| 选择与理由 | 选择方案A。方案ID状态机比URL参数更安全：用户无法篡改参数；比数据库会话轻量：无需额外的表操作。方案ID顺序机制还支持"返回"操作。方案B的问题是用户可以手动修改URL；方案C的问题是性能开销。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：性能和安全性的权衡 |
| 当前合理性 | 已过期：会话丢失后无法恢复，用户体验差。建议迁移到服务器端会话持久化（EVO-E-GL-003） |
| 影响面 | 伤历史（需迁移现有会话逻辑）/ 伤未来（影响所有钻取功能） |

### DEC-004：BAS_BusinessVoucher多对多映射设计

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么业务单据与凭证的关联要设计为多对多关系，而不是一对多？ |
| 当时约束 | 实际业务中，一张发票可能生成多张凭证（如价税分离：一张发票生成"进项税额"凭证和"物资采购"凭证）；也可能多张发票合并生成一张凭证（如多张采购发票合并付款）。 |
| 可选方案 | 方案A：多对多映射表（当前方案）；方案B：一对多，外键放在业务单据表；方案C：一对多，外键放在凭证表 |
| 选择与理由 | 选择方案A。多对多映射表支持最灵活的业务场景：一张单据对应多张凭证、多张单据对应一张凭证、多对多。方案B无法支持"多单据对一凭证"；方案C无法支持"单单据对多凭证"。映射表还支持关联到分录级别（FVoucherEntryID），实现精确钩稽。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：支持所有实际业务场景 |
| 当前合理性 | 仍合理：但缺少钩稽状态管理，建议扩展（EVO-E-GL-002A） |
| 影响面 | 伤历史（已有映射数据需迁移）/ 伤未来（不影响历史映射） |

### DEC-005：凭证生成采用异步Floating窗口模式

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么凭证生成要使用异步Floating窗口，而不是同步等待？ |
| 当时约束 | 业务单据审核是高频操作，用户不希望等待凭证生成完成。凭证生成可能涉及复杂的科目映射计算、多币种折算等。 |
| 可选方案 | 方案A：异步Floating窗口（当前方案）；方案B：同步等待；方案C：后台任务+通知 |
| 选择与理由 | 选择方案A。Floating窗口实现了"异步非阻塞"：用户点击审核后立即返回，后台生成凭证，用户可继续其他操作。方案B会导致审核操作变慢；方案C的实时性不如Floating窗口。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：优化了用户体验 |
| 当前合理性 | 已过期：异步模式导致双向盲区（用户不知道凭证是否生成），建议迁移到确认契约模式（EVO-E-GL-001B） |
| 影响面 | 伤历史（需迁移生成逻辑）/ 伤未来（影响所有凭证生成场景） |

### DEC-006：科目余额表作为预计算聚合缓存

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么要有独立的AccountBalance表，而不是每次查询时实时聚合GL_VOUCHERENTRY？ |
| 当时约束 | 企业可能有数万张凭证，每月报表查询需要聚合全量数据。实时聚合性能无法接受。 |
| 可选方案 | 方案A：预计算余额表（当前方案）；方案B：实时聚合凭证分录；方案C：数据库视图 |
| 选择与理由 | 选择方案A。预计算余额表是性能和准确性的最佳平衡：查询性能高（直接读余额，无需聚合）；过账时更新余额（实时性）；支持多维度余额（按核算维度分层）。方案B性能差；方案C维护困难。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：性能优化和数据准确性的权衡 |
| 当前合理性 | 仍合理：仍然是最佳实践 |
| 影响面 | 伤历史（已有余额数据需迁移）/ 伤未来（不影响历史数据） |

### DEC-007：凭证号全局自增且有业务语义

| 字段 | 内容 |
|---|---|
| 决策点 | 为什么凭证号要设计为全局自增且包含业务语义（凭证字+年份+序号），而不是UUID？ |
| 当时约束 | 财务人员需要通过凭证号快速定位凭证；凭证号需要连续性以满足审计要求；凭证号需要按业务类型分组（凭证字）。 |
| 可选方案 | 方案A：业务语义凭证号（当前方案）；方案B：UUID；方案C：数据库自增ID |
| 选择与理由 | 选择方案A。业务语义凭证号满足财务人员的业务需求： GJ-2024-0032 表示"记字凭证、2024年度、第32号"。凭证字分组满足按业务类型汇总的需求；年份前缀满足按年度归档的需求；序号连续性满足审计追溯需求。方案B无法满足业务需求；方案C无业务语义。 |
| 成因分类 | 有意决策 |
| 当时合理性 | 合理：满足财务业务需求 |
| 当前合理性 | 仍合理：财务凭证号的设计原则未变 |
| 影响面 | 伤历史（历史凭证号不可改）/ 只伤未来（新凭证号需遵循规则） |
