# 十分钟读懂GL总账 — K3Cloud财务域价值确认枢纽

> **阅读时间**：约10分钟
> **目标读者**：接手GL总账模块的产品经理、开发工程师、测试工程师

---

## 一、系统为何存在

**一句话定位**：GL总账是K3Cloud财务域的价值确认枢纽，将业务系统产生的经济事件（如采购、入库、销售、收款）转化为标准的财务语言（凭证），为管理者提供真实、及时、可追溯的财务决策支持。

**业务价值**：
- 将分散在AP（应付）、AR（应收）、INV（库存）等业务子系统的经济事件统一转化为标准财务凭证
- 提供总账、明细账、余额表、凭证汇总表等财务报表，支撑经营分析和合规审计
- 通过账簿、科目、期间三维体系实现财务核算的规范化管理

---

## 二、系统拥有什么

| 核心能力 | 说明 |
|---|---|
| **凭证管理** | 凭证的创建、审核、过账、反审核、反过账、作废 |
| **账簿管理** | 账簿创建、科目体系绑定、凭证字配置 |
| **科目管理** | 会计科目维护、级次管理、辅助核算维度 |
| **期间管理** | 会计期间打开、结账、反结账控制 |
| **报表查询** | 总账、明细账、余额表、凭证汇总表 |
| **报表钻取** | 从报表追溯到明细凭证，支持多级钻取 |
| **业务钩稽** | 业务单据与财务凭证的关联追溯 |

---

## 三、系统不拥有什么

| 边界 | 说明 |
|---|---|
| **业务单据所有权** | AP发票、AR发票由各自子系统管理，GL只记录关联的财务结果 |
| **业务单据审核** | 由AP/AR等业务子系统触发，GL被动接收审核事件 |
| **资金收付** | 由出纳模块（CB）管理 |
| **库存核算** | 由存货模块（INV）管理 |
| **外部报表** | 税务报表、法定报表由其他系统或手工处理 |

## 四、核心业务对象

### 凭证（Voucher）
- **是什么**：财务确认的原子单元，记录一笔经济业务的借贷双方
- **结构**：表头（凭证号、日期、凭证字、附件数）+ 多条分录（科目、借贷方向、金额、摘要）
- **状态**：保存 → 已审核 → 已过账（可反向操作）
- **生命周期**：录入员创建 → 审核员审核 → 过账员过账 → 归档

### 账簿（AccountBook）
- **是什么**：财务核算的独立边界，一个核算组织对应一个账簿
- **组成**：账簿名称、本位币、科目体系、凭证字集合、会计期间
- **隔离性**：不同账簿的数据完全隔离，凭证归属账簿

### 会计科目（Account）
- **是什么**：对经济业务进行分类的标签
- **结构**：科目编码（如1001-银行存款）、科目名称、余额方向（借/贷）
- **核算维度**：科目可关联多个辅助核算维度（部门、项目、供应商、客户等）

### 科目余额（AccountBalance）
- **是什么**：每个科目在每个期间、每个核算维度组合下的预计算余额
- **用途**：报表查询时直接读取余额表，避免实时聚合全量凭证
- **更新时机**：凭证过账时同步更新

### 业务凭证映射（BusinessVoucher）
- **是什么**：业务单据与财务凭证的多对多关联表
- **为什么需要**：一张发票可生成多张凭证（价税分离），多张发票可合并一张凭证（合并开票）

## 五、典型业务故事

### 故事一：采购入库生成凭证（成功）

```
1. 仓库管理员在INV模块审核采购入库单
2. 审核事件触发Floating窗口，异步生成凭证：
   借：原材料  1000元
   贷：应付账款  1000元
3. 用户看到Floating窗口显示"凭证生成成功"，继续其他操作
4. 财务人员在GL模块可以联查这张凭证
```

**为什么这样设计**：Floating窗口实现"异步非阻塞"，业务人员审核时不等待凭证生成完成，提升操作效率。

### 故事二：凭证联查权限

```
场景：业务人员A审核了采购发票，需要查看生成的凭证

1. A在发票页面点击"联查凭证"
2. 系统检查A是否有GL凭证权限
   - 如果有：直接展示凭证
   - 如果没有：降级检查A是否有AP发票权限
     - 如果有：展示凭证（降级成功）
     - 如果没有：提示"无权限查看"
```

**为什么这样设计**：业务人员和财务人员的权限边界不同，两级降级实现"业务优先，财务兜底"。

### 故事三：报表钻取

```
1. 财务主管打开总账报表，查看"银行存款"科目1月发生额
2. 鼠标双击某行，系统记录当前方案ID=0
3. 钻取到明细账，方案ID=1
4. 再双击某条分录，钻取到凭证，方案ID=-1（耗尽）
5. 用户点击"返回"，系统使用方案ID=0重新打开总账
```

**为什么这样设计**：方案ID状态机记录钻取路径，支持"返回"操作。关闭浏览器后会话丢失，需重新开始钻取。

## 六、主要失败场景

| 场景 | 失败表现 | 检测方式 | 恢复动作 |
|---|---|---|---|
| 凭证借贷不平衡 | 保存失败，提示"借贷不平衡" | 服务端校验 | 修改分录金额 |
| 凭证日期超出期间 | 保存失败，提示"期间已结账" | 服务端校验 | 调整日期或申请反结账 |
| 凭证生成失败 | Floating窗口显示错误 | 异常捕获 | 用户手动重试 |
| 凭证已被其他用户锁定 | 保存失败，提示"已被锁定" | 行锁检测 | 等待或联系锁定用户 |
| 钻取方案ID耗尽 | 无法继续钻取 | 状态检测 | 重新打开报表 |
| 无GL凭证权限 | 无法查看凭证 | 两级权限检查 | 申请权限或联系管理员 |

## 七、进化方向（EVO）

基于当前设计，以下场景存在改进空间：

| EVO编号 | 问题 | 改进方案 | 收益 |
|---|---|---|---|
| EVO-E-GL-001B | 异步生成后用户不知道是否成功 | 确认契约模式：提议→确认→超时状态机 | 消除双向盲区 |
| EVO-E-GL-002A | 多对多映射关系缺少状态 | 钩稽状态机：待确认→已确认/已拒绝/已解除 | 表达关联质量 |
| EVO-E-GL-003 | 钻取会话关闭浏览器后丢失 | 服务器端会话持久化 | 支持会话恢复 |
| EVO-E-GL-004 | 两级权限降级隐式表达 | 财务责任边界显式化 | 权限模型可预测 |

## 八、关键结论速查

| 问题 | 结论 |
|---|---|
| 凭证为什么分为表头和分录？ | 支持1-N条借贷分录，按分录级别钩稽 |
| 为什么需要多对多映射表？ | 支持价税分离（单单据→多凭证）和合并开票（多单据→一凭证） |
| 为什么要单独存储科目余额？ | 预计算聚合缓存，报表查询性能优化 |
| 报表钻取为什么用方案ID？ | 比URL参数更安全，防止用户篡改 |
| 两级权限降级解决什么问题？ | 业务人员有业务单据权限但可能没有GL凭证权限 |
