## 一、DQ 闭环矩阵

### 核心设计问题（DQ）与答案

| DQ | 问题 | 当前结论 | 关键证据 | 反证/未知项 | 状态 |
|---|---|---|---|---|---|
| DQ-01 | 凭证生成的异步模式为什么导致双向盲区？ | 异步Floating窗口模式：用户审核后立即返回，不等待凭证生成完成。业务端不知道凭证是否生成，财务端不知道业务单据是否已审核触发生成。 | E-SRC: VoucherGenerateService.cs:88（Floating窗口） | 无 | ✅ 已闭环 |
| DQ-02 | 为什么凭证联查需要两级权限降级？ | 业务单据由业务子系统管理，凭证由GL子系统管理。业务人员有业务单据权限，但可能没有GL凭证权限。两级降级实现了"业务优先，财务兜底"。 | E-SRC: ViewGlVoucher.cs:37-50（两级权限检查） | 无 | ✅ 已闭环 |
| DQ-03 | 为什么报表钻取依赖方案ID状态机？ | 钻取上下文需要跨请求保持，方案ID由IUserParameterService管理会话状态。GetNextEntrySchemeId获取下一级方案ID，UpdateNextEntrySchemeId更新为-1表示耗尽。 | E-SRC: ReportFilterCommonFunction.cs:1023 | U-15：状态丢失后的恢复机制未验证 | ✅ 已闭环（存在U-*） |
| DQ-04 | 为什么BAS_BusinessVoucher是多对多关系？ | 支持最灵活的业务场景：一张发票可生成多张凭证（价税分离），多张发票可合并为一张凭证（合并开票）。映射表还支持关联到分录级别。 | E-SRC: ViewGlVoucher.cs | 无 | ✅ 已闭环 |
| DQ-05 | 钩稽关系为什么需要独立的状态管理？ | 钩稽不仅是"是否关联"，还要表达"关联的质量"。待确认、已确认、已拒绝、已解除四种状态对应不同的业务语义和操作权限。 | E-SRC: GL总账进化实施规格.md §2 | 无 | ✅ 已闭环（EVO-E-GL-002A） |
| DQ-06 | 财务责任边界为什么不重合？ | 业务单据所有权（业务子系统）与凭证所有权（GL子系统）不在同一责任边界内。凭证归属账簿，业务单据归属组织，两者是不同的维度。 | E-SRC: ViewGlVoucher.cs（两级降级逻辑） | 无 | ✅ 已闭环（EVO-E-GL-004） |
| DQ-07 | 为什么凭证表头和分录要分离？ | 支持灵活的分录数量（1-N条借贷）；分录可单独关联业务单据（FVoucherEntryID）；支持按分录级别查询和钩稽。 | E-SRC: GL_VOUCHER + GL_VOUCHERENTRY分离设计 | 无 | ✅ 已闭环 |
| DQ-08 | 为什么科目余额要单独存储？ | 预计算聚合缓存：每次查询报表时直接读余额表，避免实时聚合全量凭证分录。性能优化设计。 | E-SRC: AccountBalance表设计 | U-03：余额计算触发时机未完整验证 | ✅ 已闭环（存在U-*） |
| DQ-09 | 确认契约模式如何消除双向盲区？ | 契约在业务审核时提议（Proposed），在凭证生成成功时确认（Confirmed）。两端都能看到契约状态，消除盲区。超时机制防止永久悬空。 | E-SRC: GL总账进化实施规格.md §1 | 无 | ✅ 已闭环（EVO-E-GL-001B） |
| DQ-10 | 会话状态显式化如何实现钻取路径恢复？ | 将会话状态从隐式（IUserParameterService）迁移到显式（GL_ReportSessionState表），支持会话持久化和恢复。 | E-SRC: GL总账进化实施规格.md §3 | 无 | ✅ 已闭环（EVO-E-GL-003） |

## 六、进化方案与元规范发现

### 已采纳的进化方案（EVO-E）

| EVO-E | 方案名称 | 源问题 | 进化目标 |
|---|---|---|---|
| EVO-E-GL-001B | 确认契约模式 | 异步Floating窗口导致双向盲区 | 契约提议→确认→超时状态机，消除盲区 |
| EVO-E-GL-002A | 钩稽关系状态机 | BAS_BusinessVoucher缺少状态管理 | 钩稽状态：Pending→Confirmed/Rejected/Broken |
| EVO-E-GL-003 | 会话状态显式化 | 方案ID状态隐式，浏览器关闭后丢失 | 服务器端会话持久化，支持恢复 |
| EVO-E-GL-004 | 财务责任边界显式化 | 两级权限降级隐式表达责任分离 | 凭证归属规则显式化，权限模型可预测 |

### 元规范发现（5个惊讶事实）

| S编号 | 惊讶点 | 业务本质提炼 |
|---|---|---|
| S1 | 凭证生成异步两阶段，用户不等待 | 财务确认延迟，契约语义缺失 |
| S2 | 业务单据与GL凭证多对多，需要独立映射表 | 钩稽关系是独立实体，不是简单关联 |
| S3 | 凭证联查权限需要两级降级 | 责任边界不重合，需要跨边界追溯 |
| S4 | 报表钻取依赖方案ID顺序状态机 | 报表是有限状态机，钻取是状态转换 |
| S5 | 凭证表头+分录行分离，凭证号全局自增 | 凭证号有业务语义，是审计追溯依据 |

### 进化洞察（EVO-T）

| EVO-T | 洞察内容 |
|---|---|
| EVO-T-GL-001 | 财务确认从"时点"到"区间" |
| EVO-T-GL-002 | 钩稽关系作为第一公民 |
| EVO-T-GL-003 | 报表即状态机 |
