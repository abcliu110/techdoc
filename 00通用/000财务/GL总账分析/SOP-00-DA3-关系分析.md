## 一、业务对象识别

### 1.1 核心业务对象清单

| 对象编号 | 对象名称 | 业务定义 | 生命周期 | 边界 |
|---|---|---|---|---|
| BO-01 | 凭证 | 财务确认业务的标准化"价值确认契约"，是业务事件转化为财务语言的原子单元 | 创建→保存→审核→过账→归档 | 按账簿隔离 |
| BO-02 | 凭证分录 | 凭证中记录借贷方向的"价值原子"，定义哪个科目收多少钱 | 从属于凭证，不可单独存在 | 唯一外键：FVoucherID |

| BO-04 | 账簿 | 财务核算的"独立边界"，凭证归属的"财务户口本" | 创建→使用→结账→归档 | 按组织隔离 |
| BO-05 | 会计科目 | 财务核算的"分类标签"，定义金额的归属类别 | 科目体系维护时创建，按年度使用 | 按科目体系隔离 |
| BO-06 | 会计期间 | 财务核算的"时间盒子"，将业务流切分为离散时间片 | 打开→录入→结账→锁定 | 按账簿隔离 |
| BO-07 | 科目余额 | 凭证分录的"聚合缓存"，预计算的性能优化设计 | 期初结转→本期累计→期末锁定 | 按科目+期间唯一 |

### 2.3 间接路径分析要点

#### BP-01：业务单据 → 确认契约 → 业务凭证映射 → 凭证（3跳）

**为什么要经过中间对象：**

1. **确认契约的职责**：业务单据审核是"业务事件"，而凭证生成是"财务确认"。契约作为中间层，将这两个异步操作显式化。用户审核发票时，契约立即创建（Proposed），告诉业务端"财务正在确认中"。凭证生成完成后，契约确认（Confirmed），告诉两端"已完成"。

2. **业务凭证映射的职责**：契约解决"是否完成"的问题，映射解决"如何关联"的问题。一张发票可能生成多张凭证（如价税分离），或者多张发票对应一张凭证（如合并开票）。映射表记录这种多对多关系，并关联到具体的凭证分录级别。

3. **如果直接关联（业务单据→凭证）会怎样**：
   - 无法表达"正在生成中"的状态（双向盲区）
   - 无法处理多对多场景（一张票→多张凭证）
   - 无法追踪钩稽质量（金额是否匹配）

**中间对象业务语义：**
- 确认契约：时间承诺协议，定义"审核后多久凭证应该生成"
- 业务凭证映射：空间关联表，定义"这张票的哪部分金额对应哪张凭证的哪个分录"

**级联行为：**
- 删除业务单据 → 契约取消 + 映射解除
- 凭证生成失败 → 契约失败 + 映射回滚
- 凭证作废 → 映射状态变更 + 契约取消

---

#### BP-03：凭证 → 凭证分录 → 会计科目 → 科目余额（3跳）

**为什么要经过中间对象：**

1. **凭证分录的职责**：凭证是"一堆借贷的容器"，分录是"每一笔借贷的具体内容"。分录定义了"哪个科目、多少钱、借还是贷"。没有分录，凭证只是一张空白纸。

2. **会计科目的职责**：科目是"分类标签"，分录必须引用一个有效的科目。科目决定了金额的"去处"——是进资产类科目，还是负债类科目。没有科目，分录只知道金额，不知道归属。

3. **科目余额的职责**：余额表是"聚合缓存"。如果每次查报表都要聚合全量分录，性能无法承受。余额表预计算了每个科目在每个期间的累计发生额，查询报表时直接读取余额，而不是重新聚合。

4. **如果直接关联（凭证→科目余额）会怎样**：
   - 丢失借贷方向信息（借/贷混淆）
   - 丢失核算维度信息（无法按项目/部门查询）
   - 报表性能严重下降

**中间对象业务语义：**
- 凭证分录：价值原子，定义"这笔记账的借/贷、金额、科目、维度"
- 会计科目：分类维度，定义"金额归到哪一类"
- 科目余额：聚合结果，定义"这个科目累计了多少"

**级联行为：**
- 删除凭证分录 → 科目余额回滚（反向计算）
- 修改科目属性 → 不影响历史余额
- 期间结账 → 余额表冻结，历史数据不可变

---

#### BP-08：明细账 → 凭证 → 业务凭证映射 → 业务单据（3跳）

**为什么要经过中间对象：**

1. **凭证的职责**：明细账的每一行数据都来自凭证分录。凭证是"原始记录"，明细账是"按科目前缀展示的视图"。钻取到凭证，用户才能看到完整的表头信息（凭证字、凭证号、审核人等）。

2. **业务凭证映射的职责**：凭证本身只记录财务信息，不记录业务出身。映射表提供了"追溯链"——通过FVoucherID找到映射记录，再通过FSourceBillID找到业务单据。没有映射，财务无法追溯业务源头。

3. **如果直接关联（明细账→业务单据）会怎样**：
   - 丢失财务上下文（凭证号、审核状态等）
   - 无法处理自制凭证（没有业务来源）
   - 无法区分多对多场景中的具体映射

**中间对象业务语义：**
- 凭证：原始记录，包含时间、责任、业务等多维度信息
- 业务凭证映射：追溯链，连接财务世界与业务世界

**级联行为：**
- 凭证作废 → 映射状态变更 → 明细账显示"已作废"
- 映射记录缺失 → 明细账显示"无业务来源"
- 多映射存在 → 明细账可选择任一业务单据联查

### REL-08：凭证 ↔ 业务凭证映射（间接关联，2跳）

```
┌─────────────────────────────────────────────────────────────────┐
│ REL-08: 凭证 ↔ 业务凭证映射（间接关联，2跳）                      │
├─────────────────────────────────────────────────────────────────┤
│ 【关系定义】                                                    │
│   类型：1:N（一张凭证对应多条映射）                             │
│   关联路径：间接（2跳）                                         │
│                                                                 │
│ 【关联路径】                                                    │
│   凭证 → BAS_BusinessVoucher.FVoucherID（找到所有映射）         │
│     → BAS_BusinessVoucher.FSourceBillID（找到业务单据）         │
│                                                                 │
│ 【为什么要经过中间对象】（业务原因，至少2条）                     │
│   1. 多对多关系：一张凭证可能钩稽多张业务单据（如多张发票合并开票），│
│      也可能一张业务单据生成多张凭证（如价税分离）。              │
│      直接关联无法表达这种灵活的多对多关系。                      │
│   2. 精确钩稽：映射表关联到分录级别（FVoucherEntryID），         │
│      可以说"这张发票的100元对应凭证第3行的银行存款科目"。        │
│      如果凭证直接关联单据，只能知道"有关联"，无法知道"哪部分金额有关联"。│
│   3. 状态独立：映射关系有自己的生命周期（待确认/已确认/已解除），  │
│      与凭证状态独立。一张凭证作废了，映射可以保留历史。          │
│                                                                 │
│ 【如果直接关联（凭证→业务单据）会怎样】                          │
│   无法表达多对多关系                                            │
│   无法关联到分录级别                                            │
│   无法独立管理钩稽状态                                           │
│                                                                 │
│ 【中间对象职责】                                                │
│   BAS_BusinessVoucher：多对多关联表 + 钩稽状态载体                │
│                                                                 │
│ 【级联行为】                                                    │
│   删除凭证 → 映射状态变更（IsActive=false）                      │
│   删除业务单据 → 映射状态变更（IsActive=false）                  │
│   凭证过账 → 不影响映射状态                                      │
│                                                                 │
│ 【异常场景】                                                    │
│   场景1：映射记录存在但凭证已删除 → 联查返回空，映射为脏数据      │
│   场景2：多对多映射，部分确认 → 状态不一致（建议引入"部分确认"状态）│
│   场景3：凭证分录删除但映射未更新 → 映射引用失效分录             │
│                                                                 │
│ 【代码位置】                                                    │
│   后端：ViewGlVoucher.cs:30-60                                  │
│   映射查询：BAS_BusinessVoucher.SelectByVoucherID()              │
│                                                                 │
│ 【证据】                                                        │
│   E-SRC: ViewGlVoucher.cs:30-60                                 │
│   E-SRC: BAS_BusinessVoucher表结构定义                          │
└─────────────────────────────────────────────────────────────────┘
```

### REL-12：总账报表 ↔ 明细账报表（间接关联，2跳）

```
┌─────────────────────────────────────────────────────────────────┐
│ REL-12: 总账报表 ↔ 明细账报表（间接关联，2跳）                    │
├─────────────────────────────────────────────────────────────────┤
│ 【关系定义】                                                    │
│   类型：N:1（多行汇总钻取到一行明细）                            │
│   关联路径：间接（2跳）                                         │
│                                                                 │
│ 【关联路径】                                                    │
│   总账Cell点击 → IUserParameterService.GetNextEntrySchemeId()   │
│     → 明细账报表 → 传入过滤参数（科目、期间范围）                │
│     → GetNextEntrySchemeId获取下一级方案ID                      │
│     → 凭证联查                                                  │
│                                                                 │
│ 【为什么要经过中间对象】（业务原因，至少2条）                     │
│   1. 钻取上下文传递：总账的一行可能是"1月-12月的汇总"，          │
│      明细账需要知道这个汇总的范围才能正确过滤。                   │
│      方案ID携带了过滤参数的语义（起始期间、结束期间、科目范围）。 │
│   2. 权限分层控制：总账→明细账需要检查明细账权限，               │
│      明细账→凭证需要检查凭证权限。                               │
│      如果直接关联，权限检查逻辑无法分层。                        │
│   3. 钻取路径可追溯：方案ID状态机记录了钻取历史，                │
│      用户可以从明细账返回总账。                                  │
│      如果直接关联，返回路径无法确定。                            │
│                                                                 │
│ 【如果直接关联（总账→凭证）会怎样】                               │
│   无法传递过滤上下文（不知道从哪个科目范围钻取）                  │
│   无法分层权限控制                                                │
│   无法支持返回操作                                                │
│                                                                 │
│ 【中间对象职责】                                                │
│   IUserParameterService：方案ID状态管理器，                       │
│      维护钻取路径的上下文和权限链                                 │
│                                                                 │
│ 【级联行为】                                                    │
│   总账刷新 → 不影响已打开的明细账                                │
│   明细账关闭 → 不影响总账                                        │
│   浏览器关闭 → 方案ID状态丢失，钻取路径断裂                       │
│                                                                 │
│ 【异常场景】                                                    │
│   场景1：方案ID为-1（已耗尽） → 钻取终止，无法继续钻取           │
│   场景2：无明细账权限 → CheckViewDetailRight返回false，钻取取消 │
│   场景3：数据刷新后钻取 → 过滤参数可能失效（数据范围变化）        │
│   场景4：多Tab钻取 → 不同Tab的状态互相覆盖（Session竞争）        │
│                                                                 │
│ 【代码位置】                                                    │
│   后端：GeneralLedger.cs CellDbClick()                          │
│   工具类：ReportFilterCommonFunction.cs                         │
│                                                                 │
│ 【证据】                                                        │
│   E-SRC: GeneralLedger.cs:30（CellDbClick）                    │
│   E-SRC: ReportFilterCommonFunction.cs:1023（方案ID管理）       │
└─────────────────────────────────────────────────────────────────┘
```
