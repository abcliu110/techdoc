> 文档编号：23-方法论

> 更新日期：2026-08-06

## 0. 一页总结（TL;DR）

- **库存思维**回答"哪里有什么、有多少、够不够、被谁占用了"，主计量单位是**数量**，红线是**账实一致**。
- **财务思维**回答"这一切值多少钱、价值属于哪个期间、账平不平均可审计"，主计量单位是**金额**，红线是**借贷平衡 + 期间不错配**。
- **两者不是二选一，而是同一业务事实的两个投影**：物理世界用库存模型管"数量真相"，价值世界用财务模型管"价值真相"，二者只靠**业务事件**串联，严禁用一个模型同时承载两种语义。
- **SaaS 特有规律**：纯软件没有实体仓库时，"库存思维"转移到**额度/配额/余额/积分/券**这类"金额或次数型资源池"上（虚拟库存），"财务思维"则集中在**递延收入、收入确认、对账关账、资金台账**上。
- **判断工具**：一个模块问三个问题——有没有"数量"？有没有"价值归属/期间/平衡"？数据允许被直接覆盖还是只能冲正？

## 1. 文档目的与适用范围

用于指导 SaaS 产品的数据建模、服务拆分、流程设计，明确"哪些部分应该套用财务知识、财务模型，哪些部分应该套用库存知识、库存模型，交界处如何衔接"。

适用对象：业务架构师、数据模型设计者、后端开发、需要评审既有系统账务与库存设计的工程师。

适用场景：
- 新功能设计前判断"这一块该用余额流水还是库存台账"；
- 评审既有系统时识别"用错思维"的表结构与流程（如把出库当收入确认、把收款当收入）；
- 设计 SaaS 计费、钱包、仓储、配额、券、积分这类功能时对照落地。

## 2. 两种思维的本质差异

| 维度 | 库存思维（Inventory Thinking） | 财务思维（Financial Thinking） |
|---|---|---|
| 核心对象 | 实物/资源/额度（商品、配件、配额、余额、券） | 钱、价值、权益、义务 |
| 主计量单位 | 数量（个、件、次、份） | 金额（元、USD） |
| 关心量 | 存量为主（时点：可用/锁定/在库/在途） | 流量为主（时期：收入、成本、期间利润）+ 存量（资产负债表） |
| 时间观 | "现在这一刻有没有" | "现金流（收付实现）+ 利润（权责发生）"两条时间轴 |
| 核心动作 | 入库、出库、盘点、调拨、预留、扣减、冻结、释放 | 记账、结账、结转、结算、对账、开票、核销、关账、冲红 |
| 质量红线 | 账实一致（账面数量 = 实物/实际数量） | 借贷平衡、权责发生、可审计、可追溯、只可冲正不可篡改 |
| 天然允许 | 短暂负库存、盘点冲平、近似值 | 不允许近似、不允许直接覆盖，只能反向凭证 |
| 典型承载结构 | 库存台账（存量 + 出入库流水） | 资金/账务台账（账户 + 前后余额 + 变动类型 + 冲红标志） |

核心区别一句话：**库存对不上是"缺货/超卖/盘亏"，是经营问题；财务对不上是"账不平/错期/做假账"，是诚信与合规问题。** 所以财务模型在系统里的约束强度永远高于库存模型。

## 3. 财务理论基础（被 SaaS 复用的部分）

### 3.1 权责发生制 vs 收付实现制
- 收付实现制（Cash Basis）：钱进钱出即记账。只适用于极简个人记账。
- 权责发生制（Accrual Basis）：**"义务履行时确认收入，价值消耗时确认成本"**。SaaS 必须用权责发生制，因为订阅/充值高度符合"先收钱、后履约"。

### 3.2 复式记账（Double-Entry）
每一笔价值变动至少同时影响两个科目，全局永远平衡。这是系统强校验力的来源，也是"业务流 + 账务流"分离后，账务层自洽自证的根基。

### 3.3 三大报表 = 财务思维的三种视角
| 报表 | 回答的问题 | 时间形态 |
|---|---|---|
| 利润表 | 这个期间赚没赚 | 时期流量 |
| 资产负债表 | 现在拥有什么、欠什么 | 时点存量 |
| 现金流量表 | 钱实际怎么进出 | 时期流量 |

结论：财务分析必须三张表一起看，"利润高但没现金"（应收多、垫资重）是 SaaS 常见陷阱。

## 4. 财务模型在 SaaS 中的应用

### 4.1 递延收入（Deferred / Unearned Revenue）
**SaaS 财务第一课。**
一次性收一年订阅费/大额储值，钱当天到账，但**收入必须按履约进度分期确认**；到账全额记为资产负债表负债（预收/递延），每月结转进利润表收入。

> 反模式：年费全额计在收款当月 → 当月利润虚高、后续月份"亏空"，看报表误判经营。

### 4.2 收入确认与履约义务（ASC 606 / IFRS 15 思路）
- 收入认领匹配**义务完成**而非收款；
- 充值送赠金：钱不全为收入，赠金实质是折扣，按消费比例摊进每次消费；
- 组合套餐（软件+实施+培训打包价）：按各义务独立售价分摊；
- 退款/退订：冲销已确认收入或当期确认，不是简单"冲减现金"。

### 4.3 经常性收入模型（经营层）
- MRR / ARR：月度/年度经常性收入，成长型 SaaS 的核心度量；
- 流失（Churn）与留存（Retention）：流失是收入的负增长，是最贵的"成本";
- LTV / CAC：客户终身价值与获客成本之比，决定获客投入是否该花；
- 单位经济模型（Unit Economics）：单客户毛利 = 应摊收入 − 履约成本（服务器/支持/客服均摊）。

### 4.4 资金事件化记账模型
见 §7，这是财务思维在工程上的核心落地：**凭证 + 幂等 + 可回滚 + 操作留痕**。
- 不直接裸 UPDATE 余额字段；
- 每个操作带 `voucherId`（凭证 ID）防重、`srcAccountId`（源账户）、`rollback` 与延时回滚检查；
- 每笔成败都落流水，账实可追溯。

### 4.5 对账、关账与审计模型
- 三方对账：**业务流水 ↔ 资金流水 ↔ 银行流水**；
- 会计期间关账：关账后不可改历史，只允许调整/红冲凭证；
- 四个"只"：只追加、只冲正、只留痕、只审计。

### 4.6 财务模型应用对照表（模块 → 用哪个财务概念/模型）
| SaaS 模块 | 财务概念/模型 | 落地要点 |
|---|---|---|
| 计费与订阅 | 递延收入、分摊(proration)、MRR/ARR | 年费递延、升级降级按剩余天数分摊 |
| 支付/钱包/余额 | 资产负债、应收应付、冻结/可用 | 余额是负债，充值不确认收入 |
| 发票与税务 | 价税分离、税区、净价/含税价 | 含税/不含税双字段，开票状态机 |
| 总账/账务核心 | 复式记账、科目、凭证、关账、对账 | 业务事件统一入账、只可冲正 |
| 采购/应付 | 应付账款、核销、账期 | 采购→立账→到期核销 |
| 客户信用 | 应收、信用额度、账龄、坏账计提 | CRM 授信与账龄管理 |
| 经营报表 | 三报表、毛利=确认收入−履约成本、LTV/CAC | 报表按"确认口径"而非"流水口径" |

## 5. 库存理论基础（被 SaaS 复用的部分）

### 5.1 存量与流量
- 存量（Stock）：某个时点的持有量；
- 流量（Flow）：某个期间的收/发量；
- 不变量：`期末存量 = 期初存量 + 期间流入 − 期间流出`。

### 5.2 三态模型（可用/锁定/在途）
- 可用（Available）：可承诺售卖的数量；
- 锁定（Locked/Reserved）：被订单占用、未出库的数量（已下单未支付）；
- 在途（In-transit）：已发出未入库/未签收的数量；
- 超卖防护：承诺量不能超过可用量；锁定量与扣减量必须原子操作。

### 5.3 批次、库位、效期
- 批次（Batch/Lot）：追溯来源与流向；
- 库位（Location）：空间定位；
- 效期（Expiry）：先进先出推荐、效期预警、过期报废。

### 5.4 账实一致与盘点模型
- 账面数量 vs 实物数量，周期盘点，差异用**盘点调整单**冲平（允许直接调整，这是库存与财务的本质差异之一）；
- 库存允许"临时负库存 + 事后冲平"，财务不允许。

### 5.5 计价/成本结转模型（库存→财务的桥）
- 移动加权平均（Moving Weighted Average）；
- 先进先出（FIFO）；
- 后进先出（LIFO，多税率区不可用）；
- 每次出库 = "库存数量减少"（库存链）+ "结转营业成本、库存资产减少"（财务链）同时触发。

## 6. 库存模型在 SaaS 中的应用（含虚拟库存）

### 6.1 实物库存（WMS）
标准 WMS 模型：入库单/出库单、库位、批次、效期、盘点、调拨、损耗，全部以数量记账。

### 6.2 虚拟库存（SaaS 特有，重点）
纯 SaaS 没有实体仓库，但"库存思维"在以下对象上依然成立，且建模方式与实物一致：

| 虚拟库存对象 | 相当于"入库" | 相当于"出库" | 相当于"盘点/调整" |
|---|---|---|---|
| 订阅席位数/许可证 | 扩容/续费增加 | 占用/过期回收 | 后台调整 |
| API 调用额度 / 短信/邮件次数 | 套餐发放 | 每次调用扣减 | 后台补发/扣回 |
| 会员余额（本金+赠送） | 充值入库 | 消费出库 | 调整/冲正 |
| 积分 | 消费赠分/任务发放 | 兑换消耗 | 调整 |
| 券（面额/有效期） | 发券入库 | 核销出库 | 撤销/作废 |

关键规律：**"金额式资源池"（余额、积分、券额度）用库存模型的"存量 + 流水 + 前后值镜像"管理，但真正的账务增减必须由财务/资金服务原子记账。** 即：**管理表现用库存模型，资金真相用财务模型。**

### 6.3 锁定-扣减-释放的通用流程
```
可用 →（下单/预约）→ 锁定 →（支付/履约）→ 扣减
                              ↘（取消/超时）→ 释放
```
适用对象：实物 SKU、库存、配送时段、预约座位、并发额度、优惠券。

## 7. 交界区：两套模型如何共存

| 交界点 | 库存侧 | 财务侧 | 关键设计 |
|---|---|---|---|
| 订单/交易 | 明细履行量（下单数、上菜数、作废数） | 订单头价值（应收、折扣、税、实收） | **履行层 + 价值层拆开**，或至少用不变量约束两者 |
| 发货/货权转移 | 在库 → 在途 → 已签收 | 风险报酬转移 → 收入确认触发点 | 实物出库 ≠ 收入确认 |
| 成本核算 | 批次/计价法决定流出顺序与金额 | 结转营业成本、库存资产减少 | 靠同一业务事件双写两条链 |
| 促销/赠品 | 赠品预占库存 | 赠品成本、营销费用、收入让渡 | 同活动两条链各记一笔 |
| 退款/撤单 | 数量回流（释放/回库） | 冲销收入或冲红包含义务 | 撤销同类"反向事件"而非覆盖记录 |

## 8. 表结构落地模式对比

### 8.1 财务/资金台账模式（账户 + 流水 + 冲红）
```
账户表（可并入流水或独立）：  account_id, 当前余额, 结转日期
流水表：
  id, account_id, 变动类型(type), 变动金额,
  balance_before, balance_after,      -- 前后余额镜像
  voucher_id, src_account_id,         -- 凭证/源账户（幂等）
  refflag(是否冲红), ref_id(冲正来源), -- 只可冲正
  other_bill_id(关联业务单据), created_by, comment
```
特征：**只追加、只冲正、前后值可复算、可追溯**。

### 8.2 库存台账模式（存量 + 出入库流水）
```
库存主档： sku_id, location, batch_no, 可用/锁定/在途, 账面数
出入库流水： sku_id, 单据号, 方向(+/-), 数量, 批次, 发生时间
盘点调整单： 盈亏数量（直接调整允许）
```
特征：**可盘点冲平、可短暂负库存、以数量为不变量**。

> 两者都有"流水"，但一个是**金额 + 冲红**，一个是**数量 + 可调平**。混用（一个表里既写金额又当凭证）是最常见的错误。

## 9. 真实代码落地样例（本工作区 `nms4cloud`）

以下基于 `nms4cloud` 顾客点餐 → 下单 → 结账 → 撤单业务线的真实表结构与服务契约。

### 9.1 价值链：订单三表
| 表 | 实体 | 角色 | 关键字段 |
|---|---|---|---|
| `order_bill` | `OrderBill.java` | 价值/应收头 | `food_amount` / `discount_amount` / `service_charge_amount` / `promotion_amount` / `paid_amount` / `cancel_amount` / `send_amount` / `refund_amount` / `order_status`(初/已结/已撤) / `refund_state` |
| `order_food` | `OrderFood.java` | 明细行（数量=履行链 + 金额=价值链组件） | 数量：`food_number`/`send_number`/`cancel_number`；金额：`food_org_price`/`food_pro_price`/`food_amount`/`paid_amount`；券结算：`platform_price`/`platform_paid_amount` |
| `order_pay` | `OrderPay.java` | 收付链 + 储值卡台账镜像 | `pay_amount`/`amount`(实收)/`exchange_amount`(找零)/`is_real_income`/`give_amount`/`points` + `card_balance_before/after`×本金/赠送/积分 |

`order_food` 是典型**交界行**：一行同时管数量真相与价值组成，靠 `send_number`/`cancel_number` 等可覆盖字段维持数量链，靠 `refund_state` 控制回滚——这是"履行层 + 价值层挤一表"的现实代价，建模时可评估是否拆行。

### 9.2 财务核心：独立资金服务契约（`yd4cloud.capital`）
- `BalanceDealInterface`：`recharge`(充值) / `consume`(消费) / `addByAdmin`(蓝补) / `subByAdmin`(红冲) / `undoRecharge`(撤销充值) / `undoConsume`(撤销消费)；
- `DealTypeEnum`：1充值 / 2消费 / 3撤销充值 / 4撤销消费 / 5蓝补 / 6红冲——六个交易类型呈"正向/反向"成对出现，即"只可冲正"的工程表达；
- 请求基类 `CapBalanceOpBaseRequest`：`voucherId`(凭证ID，幂等)、`srcAccountId`(源账户)、`rollback` + `redisKeyForRollback` + 延时回滚检查、`createdBy`/`comment`(留痕)。

### 9.3 财务台账表：`sc_inst_finance_bill`（`ScInstFinanceBill.java`）
复式记账式台账范式：
```
balance_before → balance(变动额) → balance_after
principal_before/principal + gift_balance        -- 本金/赠送分账
powerbank_balance / share_balance                -- 多收益分账
type_(变动类型) + year/month/day(关账维度) + status_(状态)
refflag(是否冲红) + otherbillid(关联单据)
```

### 9.4 会员卡操作接口（`CrmCardOpServiceFeign`）
`cardConsumeInner`(消费扣款) / `cardCashBackInner`(返现) / `grantConsumePointsInner`(补积分) / `revokeConsumeInner`(撤销消费) / `revokeConsumePointsInner`(撤销赠分) / `adjustBalanceInner`(调余额) / `adjustPointsInner`(调积分)——**增减一律走操作接口，不允许裸 UPDATE 余额**。

### 9.5 虚拟库存：券的三态状态机
券字段 `product_coupon_business_type`(WP会员券/MP平台券/DP平台券) + `platform_certificate_id` / `platform_write_off_id` / `write_off_channel` 承载"未用→已核销→已撤销"，与库存三态"可用→锁定→扣减"同构。

### 9.6 事件串联时序
```
点餐下单 crt_order
  → 写 order_bill(初始) + order_food(数量+金额+券核销落证)
  → 结账 pay()：组装 order_pay；校验 Σpay_amount ≥ 订单应付（财务强校验）
  → 按支付方式分流：
      会员卡 → crmCardOpServiceFeign.cardConsumeInner（资金域原子扣款，带凭证）
             → 返回余额 before/after → 镜像落 order_pay.card_balance_before/after
             → grantConsumePointsInner 补积分
      微信   → wechat 支付
      券     → 核销/撤销
  → 成功 → order_bill.order_status=已结账 → 发券/分享/评价等后置
撤单 cancel()
  → order_status=已撤销 → revokeConsumeInner 撤销卡消费 → revokeConsumePointsInner 撤销赠分
```
设计亮点：**业务侧（order_pay）只存账户余额快照镜像，真正的增减由资金服务原子记账**——业务表与资金账分离，靠凭证/镜像对账，正是"两链独立、事件串联"的正例。

## 10. 判断一把尺：一个模块先问三个问题

1. **它有没有"数量/可用性/占用"**？——有 → 至少要有库存/资源模型层（存量 + 流水 + 锁定/扣减）。
2. **它有没有"价值归属/期间/平衡"**？——预收、分摊、退款、跨期 → 必须有财务/账务层（账户 + 前后值 + 凭证 + 冲红）。
3. **数据允许被直接覆盖吗**？——盘点可调平 → 偏库存；**资金不可覆盖只能冲正** → 偏财务。

> 两条都有"是" = 交界区，必须拆两层模型、用事件串联、定期对账。

---

## 11. 设计红线与反模式清单

### 红线
1. 资金/账务数据**只追加、只冲正、可审计**，绝不覆盖历史；
2. 收款 ≠ 收入确认；出库 ≠ 成本发生；一切以权责发生制与义务履行为准；
3. 业务流与账务流分离，用**凭证/事件**衔接，禁止在业务表上直接改余额；
4. 数量真相与价值真相分表归口，靠不变量与对账保证一致；
5. 多租户下，账务与库存按租户隔离，币种/税区/计价法不全局共享。

### 反模式
- 把"出库"当收入确认、把"回款"当收入确认（收付实现误用）；
- 年费/大额储值全额计当月收入（漏递延收入）；
- 余额裸 UPDATE，无流水无凭证（不可审计）；
- 一个表同时当"库存流水"和"凭证"用；
- 金额与数量分开维护，两边漂移；
- 负库存长期存在且无对账冲平机制；
- 促销/赠品只记库存链或只记财务链，导致两套报表对不上。

## 12. SaaS 模块 × 知识体系映射总表（速查）

| SaaS 模块 | 主要知识体系 | 核心模型 |
|---|---|---|
| 计费与订阅 | 财务 | 递延收入、proration、MRR/ARR |
| 支付/钱包/余额 | 财务（表现可用库存模型） | 资金台账、凭证、冲正 |
| 发票与税务 | 财务 | 价税分离、开票状态机 |
| 总账/审计 | 财务 | 复式记账、科目、关账、对账 |
| 应收/信用 | 财务 | 账期、账龄、坏账计提 |
| 实物仓储/供应链 | 库存 | 出入库、批次、效期、盘点、计价 |
| 订单履行 | 库存 + 财务（交界） | 履行量三态 + 应收头，事件串联 |
| 配额/席位/API额度 | 库存（虚拟） | 总量/已用/剩余、锁定扣减 |
| 余额/积分/券 | 库存(表现) + 财务(账务) | 存量台账 + 资金原子记账 |
| 成本核算 | 库存 + 财务（交界） | 计价法 + 成本结转分录 |
| 经营报表/BI | 财务为主 | 三报表、毛利=确认收入−履约成本 |

## 13. 收尾结论

- 用**库存思维**保证"不缺货、不超卖、账实一致、承诺量不超可用量"；
- 用**财务思维**保证"不错账、不错期、不虚增收入、只可冲正、永远可审计"；
- 二者由**事件/凭证**串联，由**对账**兜底；
- **成本结转（数量 → 金额）和货权转移（履约 → 收入）是它们必须握手的地方**，也是设计中最容易出错的交界区。

## 14. 业务概念向财务/库存领域概念的对齐（速查表 + 本源与双投影）

### 14.1 一个定论：业务概念"可以对应"财务，但"不应归并"财务

- **可以对应（理论成立）**：复式记账是完备的经济刻画系统，一张资产负债表 + 一张损益表能收纳企业一切与经济相关的业务（库存有成本、交货有毛利、发券有让渡、拉新有费用）。任何业务事件**都能被赋值为财务事件**——所以财务视图永远能作为对账兜底层从业务事件推导出来。
- **不应归并（实践禁忌）**：财务是"投影"不是"本源"。
  - 时序不同：库存/下单要秒级、高并发、面向承诺（锁定/抢占/防超卖）；财务是低频、事后、面向期间（记账/结转/关账）。用记账抢库存，性能与语义全错。
  - 大量概念无处安放：口味、时刻表、排队、评价、路由、权限等无"价值/权责"语义，财务科目是分类汇总视图，不是状态载体。
  - 防超卖靠数量守恒，不靠现金守恒——实物/资源视图是正确操作的前提。
- 正确表述：**所有业务事件都要能投影到财务（对账兜底），但只有"涉及价值/权责/期间"的才显式建模为财务概念，只有"涉及资源存量/占用"的才显式建模为库存概念。**

### 14.2 业务概念 → 财务领域概念对齐速查表

| SaaS 业务概念 | 对齐的财务概念 | 对齐后自动获得的约束 |
|---|---|---|
| 用户/商户充值、余额、储值金 | 预收账款 / 递延负债 | 余额是负债非收入；充值 ≠ 收入确认 |
| 消费扣款、结账支付 | 营业收入确认 | 义务履行才计收入 |
| 先货后款/赊销 | 应收账款 + 账期 | 挂应收、到期核销、账龄管理 |
| 取消/退款/撤销 | 冲销 + 红字冲正 | 不改历史、只冲正、可回溯 |
| 优惠券/满减/折扣/赠品/返现 | 收入让渡 / 销售费用 | 面额 ≠ 真实收入 |
| 充值赠金（充100送20） | 递延/折扣分摊 + 本金/赠送分账 | 按消费比例摊，科目分开 |
| 商家提现/分账/佣金/续费分成 | 应付账款 + 分账台账 | 分账路径、结算周期、对账 |
| 开票/税务 | 价税分离、税务科目 | 含税/不含税双字段 |
| 积分发放/消耗/过期 | 递延负债（积分负债） | 积分是未来履约义务 |
| 会员信用/授信 | 应收、账龄、坏账准备 | 超期计提坏账 |
| 订阅年付/试用/自动续费 | 合同 + 递延收入 + 分摊 | 分期确认、prorate |
| 欠费停服/违约金 | 应收 + 预计坏账 | 催收节奏 |
| 履约成本（服务器/支持） | 营业成本/费用归集 | 期间匹配、毛利口径 |
| 拉新补贴/活动返利 | 销售费用 + 单位经济(CAC/LTV) | 算清获客回本 |
| 结算对账/账单流水 | 银行流水 + 三方对账 | 业务↔资金↔银行逐笔核对 |

### 14.3 业务概念 → 库存领域概念对齐速查表

| SaaS 业务概念 | 对齐的库存概念 | 对齐后自动获得的约束 |
|---|---|---|
| 可售数量/菜品/SKU | 可用库存 | 承诺量 ≤ 可用量，防超卖 |
| 下单占位（未付/未确认） | 锁定库存（Reserved） | 锁定量原子占用 |
| 支付成功正式成交 | 扣减出库（Issue） | 扣减与流水成对 |
| 取消/超时未付 | 释放库存（Release） | 释放与锁定成对 |
| 已发货/在途/待收货 | 在途库存（In-transit） | 在途独立口径 |
| 多门店/多仓/多餐段 | 多仓/安全库存 | 分仓可用量、调拨 |
| 原材料批次/效期/临期促销 | 批次 + 效期 + FIFO | 效期预警、先进先出 |
| 损耗/报损/盘点 | 盘点调整单 | 差异调平、账实核对 |
| 预售/预约/排队/座位/限额 | 预订占用模型 | 占用不超 capacity |
| 套餐席位/API 次数/短信条数/并发 | 虚拟库存（总量/已用/剩余） | 配额占用与释放 |
| 会员余额/积分/券的"可用"显示 | 虚拟库存池（可用/冻结/已核销） | 三态呈现与操作成对 |
| 卖多补多/采购建议 | 再订货点 / 安全库存模型 | 阈值补货预警 |
| 菜品估清/售罄 | 可用量=0 → 售罄状态 | 由量推导状态 |

### 14.4 同一业务概念跨两域对齐（分层，最容易做错的点）

| 业务概念 | 对齐库存层（表现/履约） | 对齐财务层（价值/真相） |
|---|---|---|
| 订单 | 明细履行量：sku/数量/锁定/扣减 | 订单头价值：应收/折扣/税费/实收 |
| 发货/货权转移 | 在库→在途→签收 | 风险报酬转移=收入确认触发点 |
| 退款 | 数量回流：释放/回库 | 冲销收入/冲红包含义务 |
| 余额消费 | 余额池扣减（视角上"出库"） | 资金服务原子记账 + 凭证 |
| 成本 | 批次/计价法决定流出金额 | 结转营业成本、库存资产减少 |

### 14.5 本源与双投影关系模型

```
                业务主模型（领域/事件，真相源）
                订单、菜品、状态机、券、履约
                       │ 事件驱动
        ┌──────────────┴──────────────┐
   库存视图（资源投影）            财务视图（经济投影）
   可用/锁定/在途、批次/效期        收入/成本/应收、递延/账龄
   不变量：数量守恒、账实一致        不变量：借贷平衡、期间不错配
                               │ 同一事件 ID + 对账
                               └──────── 关联
```

- **对应** = 投影层的对应：每个有经济影响的业务事件，在财务视图都有一笔可对账；每个有资源含义的事件，在库存视图都有一笔可对账。
- **归并** = 禁止：三个视图各守各的不变量，靠事件 ID + 对账关联，不做进一个表。

### 14.6 判断一把尺（补充 §10）

| 概念它有没有…… | 决定 |
|---|---|
| 数量/可用性/占用 语义 | → 向库存领域对齐（存量 + 占用/释放成对） |
| 价值/权责/期间/平衡 语义 | → 向财务领域对齐（账户 + 前后值 + 只可冲正） |
| 两者都没有（纯运营/体验/平台属性） | → 留在业务主模型，不对齐任何领域 |

> 印证（本工作区代码）：`order_bill/order_food/order_pay` 留在业务主模型管发生与状态；`BalanceDealInterface` / `ScInstFinanceBill` 承担财务投影；余额镜像与券核销三态承担库存投影——正是"本源 + 双投影"格局，无需改造成"一切皆记账"。
