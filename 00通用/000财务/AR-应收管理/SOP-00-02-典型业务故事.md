## 故事一：销售应收的暂收与核销

### 故事背景

华新公司向深圳科技公司销售了一批服务器，合同金额10万元。货物于3月1日出库，但发票3月15日才开具给客户。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 销售员 | 小王 | 负责与客户对接销售业务 |
| 应收会计 | 小李 | 负责发票审核和核销 |
| 财务主管 | 老张 | 负责复核和审批 |

### 业务时间线

```
3月1日 ──────────────────────────────────────────────────────────────
│
├─ 事件1：销售出库
│   角色：小王
│   操作：仓库发出服务器，在系统中审核销售出库单
│   系统响应：
│     - SA模块出库单审核
│     - AR模块生成暂收应收单（FSetAccountType=暂收=2）
│     - 生成暂收凭证：借：应收账款-暂收 100,000 / 贷：主营业务收入 100,000
│   结果：AR_RECEIVABLE.FSetAccountType=暂收，未核销金额=100,000
│
3月15日 ──────────────────────────────────────────────────────────────
│
├─ 事件2：开具发票
│   角色：小李
│   操作：开具销售发票给客户
│   系统响应：
│     - AR模块新增财务应收单（FSetAccountType待判断）
│
├─ 事件3：发票审核
│   角色：小李
│   操作：审核销售发票
│   系统响应：
│     - SetAccountType()判断：发票已开，更新FSetAccountType=财务=3
│     - 生成发票确认凭证：借：应收账款-客户 / 贷：应收账款-暂收 / 贷：应交税费-销项税
│     - 创建BAS_BusinessVoucher映射
│   结果：AR_RECEIVABLE.FSetAccountType=财务
│
├─ 事件4：钩稽确认
│   角色：小李
│   操作：对暂收单和财务单执行钩稽确认
│   系统响应：
│     - VerificationServiceHelper.Verify()
│     - 创建AR_VERIFICATION记录
│     - 建立暂收↔财务的钩稽关系
│   结果：两单据建立钩稽关联
│
├─ 事件5：核销匹配
│   角色：小李
│   操作：执行核销匹配
│   系统响应：
│     - ARFinMatch.FinMatchProcess()
│     - 校验行数限制（method=73，1:1组合）
│     - 计算未核销金额
│     - 创建AR_WRITEOFFRECORD
│     - 生成核销凭证
│     - 更新AR_RECEIVABLE.FUnWriteOffAmt=0，FWriteOffStatus=已核销
│   结果：应收单核销完成，债权清零
│
└─ 事件6：核销复核
    角色：老张
    操作：复核核销记录
    系统响应：
      - 查询AR_WRITEOFFRECORD
      - 验证核销金额、单据对应关系
    结果：核销复核通过
```

### 系统状态变化

| 时间 | 单据 | 核算类型 | 未核销金额 | 核销状态 |
|---|---|---|---|---|
| 3月1日 | 暂收应收单 | 暂收(2) | 100,000 | 未核销 |
| 3月15日 | 财务应收单 | 财务(3) | 100,000 | 未核销 |
| 3月15日 | 钩稽后 | 暂收↔财务 | - | 钩稽已确认 |
| 3月15日 | 核销后 | 财务 | 0 | 已核销 |

### 关键业务规则

| 规则 | 描述 |
|---|---|
| BR-AR-003 | SA销售采用SA核算逻辑 |
| BR-AR-002 | 特殊核销method=73，行数1:1 |
| BR-AR-004 | 核销金额≤双方未核销金额 |
| BR-AR-021 | 暂收→财务转换通过钩稽确认触发 |

## 故事二：客户付款认领

### 故事背景

华新公司客户深圳科技公司支付了一笔款项15万元，但未注明对应哪笔订单。应收会计小李需要在系统中进行认领匹配。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 应收会计 | 小李 | 执行收付款认领 |
| 财务主管 | 老张 | 复核认领结果 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：客户付款到账
│   角色：系统/出纳
│   操作：收到银行收款通知，款项到账
│   系统响应：
│     - CB现金模块记录收款
│     - CM资金模块更新可用余额
│   结果：收款记录已创建
│
├─ 事件2：查看客户应收情况
│   角色：小李
│   操作：打开BillRecReport，选择客户"深圳科技公司"
│   系统响应：
│     - 查询该客户所有未核销的应收单据
│     - 显示：应收单A（10万）、应收单B（5万），合计15万
│   结果：待认领应收单据清单
│
├─ 事件3：自动匹配认领
│   角色：小李
│   操作：执行自动匹配
│   系统响应：
│     - BillRecReport自动匹配算法执行
│     - 按到期日期、单据金额进行匹配
│     - 应收单A（10万）+ 应收单B（5万）= 15万
│     - 确认认领金额15万
│   结果：匹配结果已生成
│
├─ 事件4：执行认领
│   角色：小李
│   操作：确认认领，执行认领操作
│   系统响应：
│     - 更新应收单A.FUnWriteOffAmt=0，FWriteOffStatus=已核销
│     - 更新应收单B.FUnWriteOffAmt=0，FWriteOffStatus=已核销
│     - 更新收款记录已认领金额
│   结果：两笔应收单核销完成
│
└─ 事件5：认领复核
    角色：老张
    操作：复核认领记录
    结果：认领复核通过
```

### 认领与核销的关系

| 维度 | 认领（Claim） | 核销（Match） |
|---|---|---|
| 触发时机 | 客户付款到账后 | 人工选择单据执行 |
| 匹配方式 | 自动匹配算法 | 人工选择 |
| AR位置 | AR独有（BillRecReport） | AR/AP均有 |
| 凭证生成 | 可选 | 必须 |
| 用途 | 客户对账确认 | 账务核销 |

## 故事三：反核销与补偿

### 故事背景

小李发现上周执行的一笔核销有误，核销金额多算了1,000元，需要反核销后重新处理。

### 业务角色

| 角色 | 姓名 | 权限 |
|---|---|---|
| 财务主管 | 老张 | 拥有"反清理"权限 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：发现核销错误
│   角色：老张
│   发现：核销金额多了1,000元
│
├─ 事件2：执行反核销
│   角色：老张
│   操作：打开核销记录，执行反核销
│   系统响应：
│     - ARFinMatch校验权限（检查"反清理"权限）
│     - 调用VerificationServiceHelper.UnVerify()
│     - 返回UnVerifyResultAction
│   结果：UnVerifyResultAction.NeedCompensationVoucher=true
│
├─ 事件3：生成补偿凭证
│   角色：系统
│   操作：自动生成补偿凭证
│   系统响应：
│     - VoucherGenerateServiceHelper.Generate(补偿凭证)
│     - 借贷方向相反，冲销原核销凭证
│     - 创建BAS_BusinessVoucher映射（补偿标记）
│   结果：补偿凭证已生成
│
├─ 事件4：恢复核销状态
│   角色：系统
│   操作：恢复单据原状态
│   系统响应：
│     - 更新AR_RECEIVABLE.FWriteOffStatus=部分核销
│     - 更新AR_RECEIVABLE.FUnWriteOffAmt=1,000
│     - AR_WRITEOFFRECORD.FStatus=已反核销
│   结果：单据恢复到反核销前状态（保留1,000未核销）
│
└─ 事件5：重新核销
    角色：小李
    操作：执行正确金额的核销
    系统响应：
      - ARFinMatch.FinMatchProcess(正确金额)
      - 更新未核销金额=0
    结果：核销正确完成
```

### 为什么需要补偿凭证？

```
原核销凭证：                    补偿凭证：
借：应收账款 10,000        借：应收账款 10,000（红字）
贷：银行存款 10,000        贷：银行存款 10,000（红字）
                                  +
                            借：应收账款 9,000（正确）
                            贷：银行存款 9,000（正确）

净效果：借：应收账款 9,000 / 贷：银行存款 9,000（正确金额）
```

## 故事四：内部应收核销

### 故事背景

华新公司集团内有两个责任中心：A部门（销售部门）和B部门（生产部门）。A部门向B部门销售了一批半成品，内部应收应付需要核销。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 财务主管 | 老张 | 执行内部核销 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：录入内部应收单
│   角色：老张
│   操作：A部门录入对B部门的内部应收单
│   系统响应：
│     - 创建AR_InnerIVRecord（A部门内部应收）
│     - FInnerOrgID=B部门ID
│     - FAmount=50,000
│   结果：AR_InnerIVRecord已创建
│
├─ 事件2：录入内部应付单（AR侧记录）
│   角色：老张
│   操作：B部门录入对A部门的内部应付单
│   系统响应：
│     - 创建AR_InnerAPRecord（B部门内部应付）
│     - FInnerOrgID=A部门ID
│     - FAmount=50,000
│   结果：AR_InnerAPRecord已创建
│
├─ 事件3：执行内部应收核销
│   角色：老张
│   操作：对内部应收和内部应付执行内部核销
│   系统响应：
│     - ARInnerIVSpecialMatchEdit.InnerIVProcess()
│     - 校验组织关系（同体系）
│     - 创建AR_InnerClearRecord
│     - 生成内部抵消凭证：借：内部应收 50,000 / 贷：内部应付 50,000
│     - 更新双方余额为0
│   结果：组织间往来清零
│
└─ 事件4：核销复核
    角色：老张
    操作：复核内部核销记录
    结果：内部核销复核通过
```

### 内部应收核销与普通核销的区别

| 维度 | 普通核销 | 内部核销 |
|---|---|---|
| 参与方 | 企业↔外部客户 | 组织A↔组织B（同集团） |
| 核销对象 | AR_RECEIVABLE | AR_InnerIVRecord / AR_InnerAPRecord |
| 凭证类型 | 标准核销凭证 | 内部抵消凭证 |
| 组织要求 | 同组织 | 同体系组织 |
| 科目 | 应收账款 | 内部往来科目 |

## 故事五：账龄分析与收款决策

### 故事背景

华新公司财务部需要在月末制定收款计划，通过账龄分析确定催收优先级。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 财务主管 | 老张 | 查看账龄分析报表 |
| 应收会计 | 小李 | 执行催收 |

### 业务时间线

```
月末 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：查看应收余额明细
│   角色：老张
│   操作：打开ReceivableBillBalRpt报表
│   系统响应：
│     - 查询AR_RECEIVABLE.FUnWriteOffAmt>0的记录
│     - 按客户、组织维度汇总
│   结果：应收余额明细报表
│
├─ 事件2：查看账龄分析
│   角色：老张
│   操作：打开ReceivableBillReport报表
│   系统响应：
│     - 按FDueDate计算逾期天数
│     - 按区间分组：0-30天、31-60天、61-90天、90天以上
│     - 按FUnWriteOffAmt汇总
│   结果：账龄分析报表
│
├─ 事件3：识别高风险客户
│   角色：老张
│   发现：
│     - 深圳科技：90+天，金额80,000（逾期严重）
│     - 顺丰客户：61-90天，金额5,000（即将逾期）
│   决策：优先催收给深圳科技
│
├─ 事件4：制定催收计划
│   角色：小李
│   操作：制定催收计划，联系客户
│   系统响应：
│     - 创建催收记录
│   结果：催收计划已制定
│
└─ 事件5：部分收款
    角色：小李
    操作：收到深圳科技部分款项3万元，执行认领
    系统响应：
      - BillRecReport执行部分认领
      - 更新未核销金额=50,000
    结果：部分收款已认领
```

### 账龄分析计算逻辑

```
逾期天数 = 当前日期 - 到期日期（FDueDate）

账龄区间判定：
├─ 0-30天：逾期天数 ≤ 30 → 正常
├─ 31-60天：30 < 逾期天数 ≤ 60 → 关注
├─ 61-90天：60 < 逾期天数 ≤ 90 → 警告
└─ 90+天：逾期天数 > 90 → 高风险
```

## 故事六：其他业务类型应收

### 故事背景

华新公司收到一笔押金2,000元，这是一笔"其他应收"业务，不涉及销售出库。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 应收会计 | 小李 | 录入其他应收单 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：收到押金
│   角色：小李
│   操作：录入"其他应收"单据（业务类型=其他）
│   系统响应：
│     - AR_RECEIVABLE.FBillType=其他
│     - FSetAccountType=财务（其他业务直接计入，无需暂收）
│   结果：应收单已创建
│
├─ 事件2：审核应收单
│   角色：小李
│   操作：审核其他应收单
│   系统响应：
│     - SetAccountType()执行"其他"业务逻辑（非SA，跳过暂收判断）
│     - 直接FSetAccountType=财务=3
│     - 生成凭证：借：其他应收款-押金 / 贷：相关科目
│   结果：凭证已生成
│
└─ 事件3：押金退还核销
    角色：小李
    操作：押金退还，执行核销
    系统响应：
      - 核销匹配
      - 更新未核销金额=0
    结果：押金核销完成
```

### SA销售与其他业务的关键区别

| 维度 | SA销售 | 其他业务 |
|---|---|---|
| 核算类型 | 暂收→财务（两阶段） | 直接财务（单阶段） |
| 暂收凭证 | 有（出库时生成） | 无 |
| 收入确认时点 | 出库时暂收，发票时确认 | 发生时直接计入 |
| 钩稽关系 | 有（暂收↔财务） | 无 |
| 税务处理 | 销项税确认（发票时） | 发生时确认 |
