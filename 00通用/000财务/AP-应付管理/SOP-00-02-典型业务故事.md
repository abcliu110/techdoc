## 故事一：采购发票的暂估与核销

### 故事背景

华新公司向深圳电子采购了一批服务器，合同金额10万元。货物于3月1日到货入库，但供应商发票3月15日才到达。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 采购员 | 小王 | 负责与供应商对接 |
| 应付会计 | 小李 | 负责发票审核和核销 |
| 财务主管 | 老张 | 负责复核和审批 |

### 业务时间线

```
3月1日 ──────────────────────────────────────────────────────────────
│
├─ 事件1：采购入库
│   角色：小王
│   操作：仓库收到服务器，在系统中审核采购入库单
│   系统响应：
│     - PM模块入库单审核
│     - AP模块生成暂估应付单（FSetAccountType=暂估=2）
│     - 生成暂估凭证：借：库存商品 100,000 / 贷：应付账款-暂估 100,000
│   结果：AP_PAYABLE.FSetAccountType=暂估，未核销金额=100,000
│
3月15日 ──────────────────────────────────────────────────────────────
│
├─ 事件2：发票到达
│   角色：小李
│   操作：收到供应商发票，录入采购发票
│   系统响应：
│     - AP模块新增财务应付单（FSetAccountType待判断）
│
├─ 事件3：发票审核
│   角色：小李
│   操作：审核采购发票
│   系统响应：
│     - SetAccountType()判断：发票已到，更新FSetAccountType=财务=3
│     - 生成发票校验凭证：借：库存商品 / 应交税费-进项税 / 贷：应付账款-供应商
│     - 创建BAS_BusinessVoucher映射
│   结果：AP_PAYABLE.FSetAccountType=财务
│
├─ 事件4：钩稽确认
│   角色：小李
│   操作：对暂估单和财务单执行钩稽确认
│   系统响应：
│     - VerificationServiceHelper.Verify()
│     - 创建AP_VERIFICATION记录
│     - 建立暂估↔财务的钩稽关系
│   结果：两单据建立钩稽关联
│
├─ 事件5：核销匹配
│   角色：小李
│   操作：执行核销匹配
│   系统响应：
│     - FinMatch.FinMatchProcess()
│     - 校验行数限制（method=73，1:1组合）
│     - 计算未核销金额
│     - 创建AP_WRITEOFFRECORD
│     - 生成核销凭证
│     - 更新AP_PAYABLE.FUnWriteOffAmt=0，FWriteOffStatus=已核销
│   结果：应付单核销完成，债务清零
│
└─ 事件6：核销复核
    角色：老张
    操作：复核核销记录
    系统响应：
      - 查询AP_WRITEOFFRECORD
      - 验证核销金额、单据对应关系
    结果：核销复核通过
```

### 系统状态变化

| 时间 | 单据 | 核算类型 | 未核销金额 | 核销状态 |
|---|---|---|---|---|
| 3月1日 | 暂估应付单 | 暂估(2) | 100,000 | 未核销 |
| 3月15日 | 财务应付单 | 财务(3) | 100,000 | 未核销 |
| 3月15日 | 钩稽后 | 暂估↔财务 | - | 钩稽已确认 |
| 3月15日 | 核销后 | 财务 | 0 | 已核销 |

### 关键业务规则

| 规则 | 描述 |
|---|---|
| BR-AP-003 | CG采购采用CG核算逻辑 |
| BR-AP-002 | 特殊核销method=73，行数1:1 |
| BR-AP-004 | 核销金额≤双方未核销金额 |
| BR-AP-008 | 钩稽确认后才能核销 |

## 故事二：员工费用报销

### 故事背景

华新公司员工张总出差回来报销差旅费，总金额5,000元（不含税），税额450元，价税合计5,450元。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 员工 | 张总 | 提交费用报销单 |
| 应付会计 | 小李 | 审核费用单据 |
| 财务主管 | 老张 | 审批付款 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：提交费用报销
│   角色：张总
│   操作：在系统中录入差旅费报销单
│   系统响应：
│     - 创建费用应付单（业务类型=FY）
│     - FSetAccountType=财务（费用直接计入损益，无需暂估）
│   结果：AP_PAYABLE.FBillType=FY，FSetAccountType=财务
│
├─ 事件2：费用单审核
│   角色：小李
│   操作：审核差旅费报销单
│   系统响应：
│     - SetAccountType()执行FY逻辑（非CG，跳过暂估判断）
│     - 生成费用凭证：借：管理费用-差旅费 5,000 / 应交税费-进项税 450 / 贷：其他应付款 5,450
│     - 创建BAS_BusinessVoucher映射
│   结果：费用凭证已生成
│
├─ 事件3：付款核销
│   角色：小李
│   操作：对费用单执行核销
│   系统响应：
│     - FinMatch.FinMatchProcess()
│     - 创建AP_WRITEOFFRECORD
│     - 生成付款凭证
│     - 更新未核销金额=0
│   结果：费用单核销完成
│
└─ 事件4：付款审批
    角色：老张
    操作：审批付款
    系统响应：
      - CM模块执行付款
      - AP模块更新FRelateHadPayAmount
    结果：付款完成
```

### FY与CG的关键区别

| 维度 | CG采购 | FY费用 |
|---|---|---|
| 核算类型 | 暂估→财务（两阶段） | 直接财务（单阶段） |
| 暂估凭证 | 有（入库时生成） | 无 |
| 成本确认时点 | 入库时暂估，发票时调整 | 费用发生时直接计入 |
| 税务处理 | 进项税抵扣（发票校验后） | 进项税抵扣（费用发生时） |

## 故事三：反核销与补偿

### 故事背景

小李发现上周执行的一笔核销有误，核销金额多算了1,000元，需要反核销后重新处理。

### 业务角色

| 角色 | 姓名 | 权限 |
|---|---|---|
| 财务主管 | 老张 | 拥有"反清理"权限 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：发现核销错误
│   角色：老张
│   发现：核销金额多了1,000元
│
├─ 事件2：执行反核销
│   角色：老张
│   操作：打开核销记录，执行反核销
│   系统响应：
│     - FinMatch校验权限（检查"反清理"权限）
│     - InnerClearRecordEdit.CheckPermission()
│     - 调用VerificationServiceHelper.UnVerify()
│     - 返回UnVerifyResultAction
│   结果：UnVerifyResultAction.NeedCompensationVoucher=true
│
├─ 事件3：生成补偿凭证
│   角色：系统
│   操作：自动生成补偿凭证
│   系统响应：
│     - VoucherGenerateServiceHelper.Generate(补偿凭证)
│     - 借贷方向相反，冲销原核销凭证
│     - 创建BAS_BusinessVoucher映射（补偿标记）
│   结果：补偿凭证已生成
│
├─ 事件4：恢复核销状态
│   角色：系统
│   操作：恢复单据原状态
│   系统响应：
│     - 更新AP_PAYABLE.FWriteOffStatus=部分核销
│     - 更新AP_PAYABLE.FUnWriteOffAmt=1,000
│     - AP_WRITEOFFRECORD.FStatus=已反核销
│   结果：单据恢复到反核销前状态（保留1,000未核销）
│
└─ 事件5：重新核销
    角色：小李
    操作：执行正确金额的核销
    系统响应：
      - FinMatch.FinMatchProcess(正确金额)
      - 更新未核销金额=0
    结果：核销正确完成
```

### 为什么需要补偿凭证？

```
原核销凭证：                    补偿凭证：
借：应付账款 10,000        借：应付账款 10,000（红字）
贷：银行存款 10,000        贷：银行存款 10,000（红字）
                                  +
                            借：应付账款 9,000（正确）
                            贷：银行存款 9,000（正确）

净效果：借：应付账款 9,000 / 贷：银行存款 9,000（正确金额）
```

## 故事四：内部核销

### 故事背景

华新公司集团内有两个责任中心：A部门（销售部门）和B部门（生产部门）。A部门向B部门销售了一批半成品，内部应收应付需要核销。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 财务主管 | 老张 | 执行内部核销 |

### 业务时间线

```
T日 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：录入内部应收单
│   角色：老张
│   操作：A部门录入对B部门的内部应收单
│   系统响应：
│     - 创建AP_InnerIVRecord（A部门内部应收）
│     - FInnerOrgID=B部门ID
│     - FAmount=50,000
│   结果：AP_InnerIVRecord已创建
│
├─ 事件2：录入内部应付单
│   角色：老张
│   操作：B部门录入对A部门的内部应付单
│   系统响应：
│     - 创建AP_InnerPayRecord（B部门内部应付）
│     - FInnerOrgID=A部门ID
│     - FAmount=50,000
│   结果：AP_InnerPayRecord已创建
│
├─ 事件3：执行内部核销
│   角色：老张
│   操作：对内部应收和内部应付执行内部核销
│   系统响应：
│     - InnerClearRecordEdit.InnerClearProcess()
│     - 校验组织关系（同体系）
│     - 创建AP_InnerClearRecord
│     - 生成内部抵消凭证：借：内部应付 50,000 / 贷：内部应收 50,000
│     - 更新双方余额为0
│   结果：组织间往来清零
│
└─ 事件4：核销复核
    角色：老张
    操作：复核内部核销记录
    结果：内部核销复核通过
```

### 内部核销与普通核销的区别

| 维度 | 普通核销 | 内部核销 |
|---|---|---|
| 参与方 | 企业↔外部供应商 | 组织A↔组织B（同集团） |
| 核销对象 | AP_PAYABLE | AP_InnerIVRecord / AP_InnerPayRecord |
| 凭证类型 | 标准核销凭证 | 内部抵消凭证 |
| 组织要求 | 同组织 | 同体系组织 |
| 科目 | 应付账款 | 内部往来科目 |

## 故事五：账龄分析与付款决策

### 故事背景

华新公司财务部需要在月末制定付款计划，通过账龄分析确定付款优先级。

### 业务角色

| 角色 | 姓名 | 操作 |
|---|---|---|
| 财务主管 | 老张 | 查看账龄分析报表 |

### 业务时间线

```
月末 ──────────────────────────────────────────────────────────────────
│
├─ 事件1：查看应付余额明细
│   角色：老张
│   操作：打开PayableOpenDetail报表
│   系统响应：
│     - 查询AP_PAYABLE.FUnWriteOffAmt>0的记录
│     - 按供应商、组织维度汇总
│   结果：应付余额明细报表
│
├─ 事件2：查看账龄分析
│   角色：老张
│   操作：打开AgingAnalysis报表
│   系统响应：
│     - 按FDueDate计算逾期天数
│     - 按区间分组：0-30天、31-60天、61-90天、90天以上
│     - 按FUnWriteOffAmt汇总
│   结果：账龄分析报表
│
├─ 事件3：识别高风险付款
│   角色：老张
│   发现：
│     - 深圳电子：90+天，金额80,000（逾期严重）
│     - 顺丰快递：61-90天，金额5,000（即将逾期）
│   决策：优先付款给深圳电子
│
└─ 事件4：制定付款计划
    角色：老张
    操作：导出账龄报告，制定付款计划
    系统响应：
      - 导出报表数据
      - 创建付款申请单
    结果：付款计划已制定
```

### 账龄分析计算逻辑

```
逾期天数 = 当前日期 - 到期日期（FDueDate）

账龄区间判定：
├─ 0-30天：逾期天数 ≤ 30 → 正常
├─ 31-60天：30 < 逾期天数 ≤ 60 → 关注
├─ 61-90天：60 < 逾期天数 ≤ 90 → 警告
└─ 90+天：逾期天数 > 90 → 高风险
```
