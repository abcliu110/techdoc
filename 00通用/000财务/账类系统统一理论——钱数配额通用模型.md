# 账类系统统一理论 —— 从财务/库存到一切"余额"业务

> **定位**：元理论层。把"财务""库存"归并为同一类系统的特例，提炼可迁移到**预算、配额、积分、库存券、仓位、时段、工位、额度和一切有余量的业务**的统一模型。
> **实证基础**：K3Cloud 财务（《财务系统高维抽象理论.md》）+ 库存（《库存系统高维抽象理论.md》）两次逆向实例化。
> **一句话**：**凡是"某个对象在某类账户下，随时间流入流出、可被承诺、需守恒、要按期固化"的业务，都是一本"账"，可用同一套骨架建模。**

---

## 1. 什么是账类系统 —— 判定四问

判断一个业务是不是"账"，问四句（全 "是" 则按账类系统建模，收益最大）：

| # | 判据 | 通俗问法 |
|---|---|---|
| 1 | **有存量** | 是否有一个可数的"存量"，今天和明天会不同？ |
| 2 | **有方向流动** | 存量是否因"流入/流出/冻结/调整"而变化？ |
| 3 | **有归属对象** | 存量是否分属某对象（物料、客户、科目、用户、券池）？ |
| 4 | **需守恒** | 攒到月末，是否必须"期初+入-出=期末"对得上？ |

**命中即适配**：
- 命中 1+2+4（不强调归属）→ 最简单的"总账式"单池账；
- 命中 3 → 需"分户账"（对象 × 账户）；
- 还需"承诺/占用" → 加"承诺层"（可用量/可用额度/可分配）。

**反例对照**：纯行为日志（无存量）、纯流程审批（无守恒约束）不是账。

**第 5 问（进阶 · 对象三查）**：它声称测的是 A，数据/报表实际落在哪一侧（应收/应付、成本/损益、生产/库存）？核心实现在源码内还是外部？——对抗性验证最频发的一类错误就是**对象错位**（账龄=应付款非应收；"结转五步链"核心在外部 DLL；"调汇"实为期间查询）。建模/分析前先对齐"声称对象"与"实际对象"。（详见 `13-方法卡-账类业务机制的对抗性验证` §1）

## 2. 统一五要素 —— `对象 × 分类 × 度量 + 事件 + 时间轴`

任何账类系统 = 五个抽象，各自在具体领域里"换词不换骨架"：

| 抽象要素 | 财务 | 库存 | 预算 | 积分 | 库存券/配额 |
|---|---|---|---|---|---|
| **① 对象 Object** | 核算组织 | 物料 | 预算责任中心 | 用户 | 券池/名额 |
| **② 账户分类 Category** | 科目 | 仓/批次/状态 | 预算科目 | 积分类型 | 券类型/时段 |
| **③ 度量 Measure** | 金额(币别) | 数量(三单位) | 金额/数量 | 积分值 | 张数/名额 |
| **④ 事件 Event** | 凭证/核销 | 过账/盘点 | 预算调整/占用 | 发放/兑换 | 发放/核销 |
| **⑤ 时间轴 Timeline** | 期间/结账 | 期初/关账 | 预算年度/期间 | (可选)结算期 | 有效期/时段 |

> 建模起点：**先回答三件事——本系统"①谁对谁、②在哪个分类、③用什么度量记账"，再回答"④哪些事件改账、⑤何时固化"。** 五问定完，骨架就出来了。

## 3. 守恒律 —— 统一不变量

### 统一方程
对每一"对象 × 分类"组合，任意时点成立：

```
存量 = 期初 + Σ流入 - Σ流出 + Σ调整     （对每个度量均成立）
```

### 三层守恒（层层从松到严）
1. **流量守恒**：每一笔变动恰好把一份量从"源"搬到"目标"（不凭空产生）；
2. **可出性守恒**：出库/扣减不得超过"可用量"（现存量扣承诺后）——库存的**负库存检查**、预算的**超支拦截**、积分的**负积分防空**、券的**超发防堵**都是它；
3. **总额守恒**：月末/期末聚合后，账实一致——试算平衡、库存对账、预算执行分析全同构。

> ⚠️ **行为期望 ≠ 产品承诺**：守恒常是**可被配置豁免**的——库存"允许负库存"、会计"月末暂估+期初冲回"、结账"忽略负库存检查"、未审核单"改期继续结账"，都是"为现实开放的可控豁免"。因此写"这个系统会守恒/会被拦"之前，先查它是否提供"忽略/绕过/改期/继续"出口；"应该收敛"须用代码或运行数据证实，否则只是期望，不是产品保证。（13-方法卡 §2/§5）

### 普适启示
> **先定义"本系统的守恒方程"，把违规情形枚举成校验规则**（哪些情形允许负、哪些必须拦截）。验证器（见第9章）是账类系统的"质检员"，缺了它账就是"看起来对"。

## 4. 事件溯源 × 投影 —— 可重算是可靠性的终极判据

### 统一分层
```
事件层(只追加流水)  →  投影层(存量/余额,可多份)  →  视图层(报表/查询)
```
- **事件**：不可变，记录"谁、何时、从哪、到哪、多少、哪个单据、哪个操作"；
- **投影**：按维度聚合出的存量，**任何时刻可由事件重算**；
- **视图**：报表永远查投影，不扫事件。

### 普适启示（最值钱的一条）
> 给任何账类系统配两件"救生索"：
> 1. **重算工具**：从流水重建任何时点的存量 → 任何 dirty data、任何反审核/回滚都可自愈；
> 2. **对账报表**：投影 vs 事件的重放结果对比（K3：`STKBALRESULT/OCCURLOG`、现金调节表）→ 发现"看似正确实则差一分钱"的问题。
> 这也决定了"删数据"的纪律：**改存量不删流水，反操作（冲销/反审核）永远优先于删除**。

## 5. 维度空间 —— 存量的坐标

### 统一思想
存量不是单一标量，而是存在于**多维坐标**上的**稀疏点集**：
```
维度 = 归属(对象) ∪ 分类(账户) ∪ 分组(批次/时段/项目/来源) 
存量 = 落在每个坐标点(维度组合)上的值      ← 用"组合键"标识唯一坐标
```
- **报表** = 沿某几个维聚合（roll-up）、沿细节维下沉（drill-down）、固定某维（slice）；
- **新增维度** = 加一个坐标轴，属于**元数据扩展**，不应改成套代码（K3 财务"辅助核算"、库存"15维"均如此）。

### 普适启示
> "把一切存量做成坐标点 + 组合键"让**报表与明细天然统一**：明细是坐标点本身，汇总就是按坐标归并。这直接消解"报表得另写取数"这类常见返工。

## 6. 承诺/占用机制 —— 存量与可用量分离

### 统一思想（全理论最高杠杆的一条）
```
现存量      = 已经在账的存量
承诺/占用   = 已被"未来事项"预定、但尚未实际发生的量
可用量      = 现存量 - 承诺量        ← 业务真正能用的，往往是可用量
```
**铁律：承诺量不要单独维护成计数器，而是从"承诺明细"实时聚合**：
```
承诺明细: (占用对象, 占用的是哪一行存量, 占多少, 何时到期, 状态)
锁定量 = SUM(承诺明细.数量) where 该存量行 & 未释放
```

### 为什么如此
承诺的生命周期（占用→核销/释放/到期自动解）与业务单据挂钩；把它物化为明细，**释放、反审核、到期自动解锁、超期回收都自动一致**，无需多套计数器靠"补丁"同步。多计数器的崩溃剧本：占用单反审核了、锁定量没减回去 → 账实永远对不上。

### 领域落地
| 领域 | 现存量 | 承诺量 | 承诺明细 |
|---|---|---|---|
| 库存 | 即时库存 | 锁定量/预留 | 预留单→库存行 |
| 财务往来 | 往来余额 | 未核销可勾稽额 | 勾稽/核销明细 |
| 预算 | 预算已批 | 已占用未报账 | 预算占用单 |
| 积分 | 积分余额 | 冻结积分 | 冻结/兑换明细 |
| 券/配额 | 券池存量 | 已预约名额 | 预约/派发明细 |

## 7. 时间轴状态机 —— 存量在时间上的固化

### 统一生命周期
```
启用/开账 → 期初入账 → 日常流动(期间内开放) → 期末动作(盘点/调汇/结账/年结) → 固化 → (必要时)反固化
```
- **固化 = 权限与一致性的边界**：固化前可写，固化后只读，余额滚到下一期间；
- **反固化 = 需级联重算**（反结账要重开、重算、并对齐所有下游投影）；
- 跨系统时间轴需**对齐**（库存结账 → 成本 → 财务结账），这本质是分布式一致性的领域形态。

### 普适启示
> 只要账跨"期"就要时间轴。**把"某期间是否可写"做成唯一的判定函数**（而不是在各处写死），并把"反固化"实现为"级联 + 可重算"而非"直接改历史"。这是账类系统最容易被低估、也最常出事的部分。

## 8. 翻译器 —— 业务世界与账务世界的解耦

### 统一思想
业务单据（发生了什么）与账务事实（如何入账）是**两个世界**，中间必须隔一层**配置化的翻译器**：
```
业务单据(自然语言) ──翻译器(模板/规则)──▶ 账务事实(代数语言: 科目×方向×金额 / 库×批次×数量)
```
- 翻译器 = 规则数据（凭证模板、过账点+数量乘数、预算映射、积分规则），**改规则不改内核**；
- 收益：业务域可独立演进，账务内核稳定；新单据接入 = 配一套规则，不写代码。

### 普适启示
> 反过来说：**只要发现某业务需要"记账"，就不要让业务代码直接改存量**。改为"业务发事件 → 翻译器 → 过账"，存量只被过账引擎触碰。这是防止"每个功能都偷偷扣两下余额"的根本隔离。

## 9. 验证器体系 —— 给每个不变量配一个质检员

账类系统可靠的工程配方 = **把守恒律落成可运行的验证器**：

| 层级 | 验证器 | 用途 |
|---|---|---|
| 事件级 | 事件必填/方向合法/度量一致（三单位或双币别同步） | 防脏数据入账 |
| 过账级 | 借贷平衡 / 数量守恒 / 可出性检查（负库存/超支/超发） | 防即时事故 |
| 期间级 | 试算平衡 / 库存对账 / 预算执行差异 / 现金调节表 | 防账实差异 |
| 溯源级 | 流水重算 == 存量投影 | 防"看起来对其实错" |

> 设计账类系统时，**"每层配验证器"和"建模"同等重要**。很多系统的崩溃不是"模型错了"，是"没在入账点拦住、也没在期末发现"。

> ⚠️ 三条反证教训（13-方法卡 §3/§7）：
> ① **"分析报表"≠"决策工具"**——只有驱动自动化（拦截/计提/审批/信用）的才算决策工具，才值得做博弈防御；只是"给人看的"分组展示，别按"会被博弈"过度设计（账龄教训）。
> ② **"未见"≠"没有"**——本地源码没有某机制≠产品没有；"缺X"是待证缺口，先明确证据面再断言（分配标准"缺审计"教训）。
> ③ **补监控几乎总是优于加强制裁**——对"可能被滥用"的机制，加"超期/异常暴露+告警"零误伤、可落地；"强制拦截"常制造新事故（预留"僵尸占用"教训：监控首选、强制到期释放否决）。

## 10. 从理论到实现 —— 账类系统内核骨架

任何一个账类系统的**最小可运行内核**（少一个就不完整）：

```
┌──────────────────────────────────────────────────────────┐
│ 入口: 业务单据/规则 → 1.翻译器(模板/乘数)                    │
│   → 2.事件日志(只追加,带事务号)                              │
│   → 3.过账器(原子MERGE/UPDATE,集合式,并发锁) → 4.存量投影    │
│   → 5.承诺明细聚合(锁定量实时)                               │
│   → 6.时间轴(期间状态/固化/反固化+级联重算)                  │
│   → 7.验证器(4层质检)                                       │
│   → 8.视图/报表(查投影)                                     │
└──────────────────────────────────────────────────────────┘
  9.维度元数据(可扩展坐标)  ✕  3/4/6为并发与可靠性的"钢"点
```

**技术要点**：
- 事务号 + 幂等：过账整批原子，重试安全；
- 维度组合键：定位存量行的"地址"；
- 集合式 SQL：批量原子合并，避免逐行循环的并发破洞；
- 一律用"冲销/反审核"表达回退，禁止 delete 存量行。

## 11. 业务机制层：账类系统的五类陷阱与博弈

> 本章来自对 K3Cloud 财务"业务机制"的溯因分析（元规范 L1 执行业务分析）：**不做功能罗列，只讲"业务会怎样被正确地做坏"**。每条均带 `S-M0-Δ-H-P-F` 与竞争解释；应用于任何账类系统。
> ⏳ **验证状态**：本层五条均已闭环（每条含 `独立 Reviewer 反证` 标注与补证清单，汇总见附3）；实证方法见《13-方法卡-账类业务机制的对抗性验证》。

### 11.1 五条业务机制陷阱

**① 义务时点 ≠ 金额时点：暂估双单的真实主因（成本归属期 + 报表结构）**
- `S`：货到票未到先记暂估应付；票到后不改原单，而是冲暂估、重记正式应付（"月末暂估应付单"+期初冲回）。
- H(原解释,⚠️已削弱为副产品)：曾主张主因是"义务时点≠金额时点、保留审计轨迹"——独立 Reviewer 反证(2026-08)：审计轨迹真实但**仅数量维度**（FinMatch 按数量勾稽、金额由数量派生、**核销不校验金额差额** `FinMatch.cs:86-137`），非主动机。
- **主动机(已转正)**：`H''` 成本归属期——暂估**月末集中批量**生成 + **期初自动冲回**(`FHOOKTYPE=1`、日期=endDate+1、开关 `AP_FHookAPReturn`、连续法) + **结账前置校验**(期内采购入库未下推应付则结账失败 `ClosedAccountCommonFunction:25-31`) = 保"本期成本完整 + SCM入库暂估成本与FIN暂估应付结账级对齐"。`H''''` 报表/对账结构：暂估须以独立明细类型(`FDetailType=8`)进入往来对账并在期初清零，与正式往来永不混淆。`H'''`:红字冲销会计惯例为其形态载体。
- **真实缺口(坐实)**：暂估-正式**金额差额缺自动对账/预警**——核销不校验金额差额、FIN 无差异报表、SCM 采购跟踪仅并列两列靠人眼(`POOrderTraceService.cs:203-214`)。
- `P`：月末暂估、期初冲回、结账校正均为 K3 现行行为；票到冲销按数量勾稽而非金额对账。
- `F`：若某组织"暂估被静默消除、正式差额无处可查"却从未出错 → 缺口被削弱；若存在我未见的差额对账 → 缺口缩小。
- 应用：凡"双单(冲销+新建)"必须配**"原值 vs 重估值"差异对账**，否则"义务轨迹保留"只是纸面；"改历史"设为反模式。
- ⚠️ 验证状态：**增强待补证**（H 副产物/H''+H'''' 主动机）。补证：结账冲回算法(DLL)、凭证模板(FHOOKTYPE 1/2 借贷与专设暂估科目)、票到自动触发勾稽、金额差额对账是否存在。

**② 结账的"改期归位"：受控通道成立，意图更接近"跨期承接"而非"防造假"**
- `S`：期末结账遇"期内落错期间的未审单"，系统提供"将单据业务日期调整到期末+1天后结账"，并保留"结账但不调整/取消"三选一(`UnAuditBillInfoFormPlugIn`)。
- 机制层(成立,独立 Reviewer 反证 2026-08)：改期是**显式确认**的非静默受控通道——可编辑建议值、有"不早于结束日"校验、返回空则结账中止；`H'''`(静默偷懒) **否证**。
- 意图层(存疑,倾向 H'''')：无改期专项留痕(仅结账汇总日志，不含被改单号/改前后日期)、无独立改期权限(仅挂结账权限 `CloseAccountCommonFunction.cs:170-177`)、改期规则机械(只校验晚于结束日、**无上界**、预填 end+1 `SetAdjustBillDateFormPlugIn.cs:38-66`) → 更支持 **H''''**：改期是"**结账检查绕过阀 + 跨期承接工具**"（把单据 `FDATE` 挤出本期区间、绕开范围检查，自动纳入下期结账），而非"归位到精确正确期间"的防造假闸口。
- 我的"业务日期 vs 入账期间"两字段拆分提案：**当前 AR/AP 数据模型无第二期间字段可拆**（检查与改期同一 `FDATE` 锚点 `CloseAccountCommonFunction.cs:27/57`），为 GL 式设计建议，可行性与不可见元数据相关。
- `P`：改期默认拒绝 + 用户显式选择 + 结账权限门；但**改期明细级留痕/独立权限缺位**。
- `F`：若发现改期"无痕静默自动" → 退回 H'''（已被显式确认否证）；若 DLL 内逐单更新连 `FPERIOD` 一起改 → 更支持"绕过阀"。

### 11.3 进化建议（EVO-E-B1）：把"先冲哪笔"从隐式规则升级为可审计决策记录

- **当前机制**：自动核销的"先冲哪笔"由撮合字段规则决定，用户无感，坏账责任隐性分配。
- **目标机制**：每次自动撮合生成一条**带决策理由与归属的"冲账决策记录"**（为何先冲这单），允许人工覆盖并留痕。
- **因果链**：风险的隐性分配 → 显式分配 → 可争议、可复查、可考核。
- **受损角色**：操作员失去"无痕裁量"，会抵触（需显式识别与激励配套）。
- **博弈检查**：仅记录不考核仍会被"按对自己有利的方向覆盖"→ 需配套"覆盖率 vs 坏账率"对照指标，不看单一完成率。
- **边界**：属策略/决策点调整，不命中 `K1-K5`，保持核心抽象内进化。

## 12. 库存业务机制层：实物世界的五类陷阱与博弈

> 承上章，对 K3Cloud 库存"业务机制"做同规格溯因分析。库存与财务的最大差别：**库存的账是对着"物理世界"记的**——规则再对，如果翻译不成可执行的物理操作，就只是报表劝告。四条为深度溯因、一条简短。
> ⏳ **验证状态**：**§12 五条已全部闭环**（附3），引用前请查各条 ⚠️ 状态与补证清单。实证方法见《13-方法卡-账类业务机制的对抗性验证》。

### 12.1 五条库存业务机制陷阱

**① 负库存开关：守恒的"受控豁免"，而非"合法缺口"**
- `S`：系统把"允许负库存"做成布尔开关（仓库表 `T_BD_STOCK.FALLOWMINUSQTY`，默认关闭、opt-in），开启后负向过账降级放行。
- `H`：负库存是**时间错位的受控豁免**——制造业实物先动、单据后补（先领料/先发货后开单）使守恒短期被突破，靠补单收敛。但开关是博弈点：长期开启会把"补单流程失效"掩盖成"允许负库存"，使负库存成为流程退化的缓存。
- 分型修正：按 L0 定位为**有意设计（受控豁免）→ 保护**，而非缺陷；真正的缺陷是**缺负库存时长监控**（可靠性缺陷 → 修复）。证据（独立 Reviewer 反证 2026-08 确认）：负库存走 `errType=1`（可忽略）而非静默直通——交互确认表单 + 锁量冲突**无条件硬拦** + 基本/辅单位一正一负默认硬拦 + 序列号物料**强制禁负** 的多层受控架构。故"允许负"≠"允许任意负"。
- 竞争解释（未证实，动机无法从代码判定）：H'' = 开关是"**转化松弛变量**"（放行超卖/超投，降低单据转化阻抗，与时间错位无关）。
- `P`（修订）：允许负库存的组织，其负库存行"平均存续时长/补单及时率"显著劣于禁止组；若长期负库存却补单及时，H 被削弱。
- `F`：出现"允许负 + 关账勾选'忽略负库存检查'→ 同一物料连续 ≥2 期常驻为负、无补单/盘盈处置"的物料行，则"靠补单+期末收敛"的 H 被否证。
- 应用：**把"允许负库存"从布尔开关升级为"负库存时长 + 频次 + 责任"的分级监管**——允许短时错位，监控长期积压（见 12.3）。
- ⚠️ 验证状态：**增强待补证**（独立 Reviewer 判定），补证需：负库存行生命周期数据、关停动因访谈、禁止组账实偏差基线。

**② 预留"僵尸占用"：承诺生命周期已内建，缺口收窄为"条件性不适配"**
- `S`：销售可出量=现存量 − 锁定量（预留明细实时聚合）；K3 **已内建**生命周期机制——`FRESERVEDATE/FRELEASEDAYS/FRELEASEDATE`、到期自动解锁调度(`UnLockStockByDateBGService`)、手动解锁、订单关闭/反审核清除预留。
- H(原解释,✅收窄)：轻量版曾断言"不设生命周期→僵尸占用缺口普遍"——⚠️ 独立 Reviewer 反证(2026-08)：机制已内建但**默认触发面窄**，缺口收窄为条件命题：**销售订单锁库(`FLINKTYPE='4'`，默认计入可用量)×未设 `FRELEASEDATE`×后续无出库/未关闭/未反审核×长账期业务域** 下，僵尸占用持续架空**他人**可用量且无自动对账。
- 补充关键事实：①到期自动解锁**未按 FLINKTYPE 过滤**、仅覆盖 `FSUPPLYFORMID='STK_Inventory'`(`UnLockStockByDateBGService.cs:54`)；②"出库核销释放"主路径落点 `StockLockService.AutoUnLock` 为**空方法(`:1839-1841`)**——真正主路径在本仓库是黑盒，存疑；③自身订单出库可用量=现存+自身锁库(`CheckSalAvailableOutQtyService.cs:1248`)——**占用不阻塞自身发货，只架空他人**。
- 现行视角 **H''''(适配域错位)**：产品默认保守(`FRELEASEDATE` 可空、不填不触发释放)是**有意的两难权衡**——强制到期释放会误伤长账期有效订单；"僵尸占用"是模型不适配"长账期/按单/跨期"业务域的结果，而非能力缺陷。
- 最小改进(明确方向，非"强制释放")：**超期预留监控告警**——只暴露"占用时长超阈值"清单(补"超期暴露"形态)，零误伤；**不建议**"所有类型强制到期释放"(会在长账期域制造批量误释放→可用量虚高→"可卖但无货"新事故)。
- `P`：僵尸占用按业务/行业维二分类(快周转≈无缺口；长账期/按单≈高发)；占用时长分布可分割数据验证。
- `F`：若已规范填写 `FRELEASEDATE` 的企业仍频繁出现僵尸占用 → H 增强(缺口不止适配域)；若调度默认注册且释放可期 → 缺口进一步缩小。
- 应用：承诺型机制(预留/配额/预算占用)先确认"生命周期是否已内建、默认面多窄"，再谈缺口——**"补监控告警"几乎总是优于"加强制裁"**(零误伤+暴露)。
- ⚠️ 验证状态：**增强待补证(缺口条件化)**。补证：调度是否默认注册(`T_BAS_SCHEDULE`)、`FRELEASEDATE` 实际填写率、客户占用时长分布。

**③ 效期/批次出库：约束 vs 建议——"账外物理"的真相**
- `S`：批次+效期管理（`FISEXPPARTOFLOT` 效期并入批次主档、保质期预警报表），出库有 FEFO(先到期先出)选项可按 `FEXPIRYDATE ASC` 排序。

### 12.3 进化建议（EVO-E-B2）：把"负库存"从布尔开关升级为"分级监管"

- **当前机制**：`允许负库存` 是 0/1 开关，开启即放行一切。
- **目标机制**：三级——①禁止（零容忍）；②有限缓冲（允许短错位，配"负库存时长上限+自动预警"）；③监管放行（开后仍对"负库存的时长/频次/责任组织"作持续评分与暴露）。
- **因果链**：布尔开关放行一切 → 分级+度量 → 流程失效被显式暴露，补单效率成为受监督变量而非被掩盖。
- **受益/受损**：仓储/采购决策受益；"用负库存消化流程问题"的操作方失去缓冲（受损角色明确）。
- **博弈检查**：若监控只看"有无负库存"，会诱导刷零掩盖；须同时看"负库存时长/重建单据及时率"。
- **边界**：策略/监控点调整，不命中 `K1-K5`，保持核心抽象内进化。

## 13. 成本核算业务机制层：分摊的博弈与守恒

> 承上两章，对成本核算做同规格溯因。成本是库存与财务之上的"第三层账"：既守恒（投入=结转+在产），又多了一个新难题——**共同成本如何"分摊"给各成本对象**。分摊 = 全系统规则密度最高、也最容易被"合法做坏"的地方。
> ⏳ **验证状态**：**§13 五条已全部闭环**（附3），引用前请查各条 ⚠️ 状态与补证清单。实证方法见《13-方法卡-账类业务机制的对抗性验证》。

### 13.1 五条成本核算业务机制陷阱

### 13.3 进化建议（EVO-E-B3）：把"分配标准变更"升级为"重大口径事件"

- **当前机制**：分配标准(工时/机时/约当等)是普通参数，可在月末随手改。
- **目标机制**：标准变更视为 **口径变更事件**——记录"谁、何时、从何改为何、影响哪些成本对象、变更前后成本差异"，并支持"按两套标准对比重算"；在考核敏感期给涉事角色显式提示。
- **因果链**：政治性分配被静默物化 → 显式化 + 可对比 → 分配决策透明、可问责、可复盘。
- **受益/受损**：财务/成本治理受益；"静默改标准调成本"的操作方失去暗箱（受损角色明确）。
- **博弈检查**：若只管"记录"不管"对比/告警"，仍会流于形式——须让"影响面"可量化可见。
- **边界**：策略/治理点调整，不命中 `K1-K5`，保持核心抽象内进化。

## 14. 预算与配额业务机制层（⚠️ CA-* 探索记录 · 非已实证结论）：申报博弈与额度分配

> ⚠️ **实证性质声明**：本章不对应 K3 源码实证（源码树中无预算主模块，仅平台存在预算控制校验点），合规标注为**理论推演 + 通用业务观察**，全部为**假设候选，待补证**——与前 §11-§13 的源码锚定性质不同。补证计划见 §14.5。

> 预算/配额是"额度类账"（钱、量、名额的额度）：比库存少"物理"、比财务少"义务"，但多出两类独有博弈——**申报对抗** 与 **分配竞争**。

### 14.1 五条预算/配额业务机制陷阱

**① 申报博弈：报高动机与"软硬"之痛**
- `S`：部门预算申报常系统性夸大；而系统若**硬拦**(超支拒绝)则急单被误伤、若**软提示**则预算形同虚设。
- `H`：预算申报是"信息不对称博弈"——使用方比审批方更清楚真实需求，于是报高以留安全垫；系统的"软/硬"只在约束使用者，而申报端的"夸大"由**审批流程与考核参照**决定，不由系统金额拦截决定。因此单加"硬拦截"解决不了虚报，只会把博弈前移到申报。
- `P`：按"增量预算(上年+%)"考核的组织，其预算申报膨胀系数比"零基预算"显著更高；可在申报数据上直接观测。
- `F`：若存在零基预算却膨胀系数同样高的反例，H 需修正（则根因在信息不对称本身而非预算方法）。
- 应用：预算治理的杠杆在"申报参照系+审批留痕"，不在金额拦截的软硬。

**② 期末突击：'用不完被砍'的经典博弈**
- `S`：按"年底未用预算被回收/削减次年基数"规则的组织，年末出现突击消费与抢购。
- `H`：预算是"留用途=留资源"的信号资源；当"执行率<100% 会伤害明年基数"成为共识，理性行为人会把剩余额度在期末耗掉。"年末突击"不是浪费，而是**对考核规则的理性响应**——代理指标(执行率)被制度性博弈。
- `P`：凡采用"未用即砍/基数联动"规则，其组织 12 月的预算执行/采购占比显著高于其他月份；改用"余额留用/基数钝化"后该峰值下降。可测。
- `F`：若"未用即砍"组织无 12 月峰值，H 需修正。
- 应用：设计预算指标时，把"执行率"与"突击行为"捆绑监测——治理的是指标，不是消费。

**③ 占用而不兑现：预算的"僵尸额度"**
- `S`：预算可用额 = 预算 − 已占用(PO占) − 已报账(实耗)；占用可由单据产生但迟迟不报账。
- `H`：同库存 §12-② 的承诺生命周期问题——预算占用若无"占用期+到期释放+超期警示"，会产生僵尸额度：额度被锁、实际未花、别处却因"无额度"被拒。**预算的三态(申报/占用/实耗)必须各自有生命周期**。
- `P`：设"占用到期自动释放+警示"的预算系统，其额度利用/误拒率优于不设者。
- `F`：反例即修正。
- 应用：复用 §6 承诺模型，预算占用同样要"预留天数+释放+告警"三件套（K3 预留/锁定已有同款机制可类比）。

**④ 配额分配：先到先得 vs 均分的机制选择**
- `S`：配额(限量/名额/门票)要么先到先得(FCFS)要么抽签均分；两者都有"不够分"的争议。
- `H`：FCFS 实际是在"按响应速度分配"，奖励有准备者、惩罚慢者；均分/抽签"按运气分配"，奖励均匀但不认效率。选哪种本质是**把"稀缺资源"交给谁的标准**——若资源可被转卖牟利，FCFS 会催生"抢购-转卖"套利，均分则催生"抽中-转售"。
- `P`：高转卖价值的配额(限量品/入场券/稀缺运力)，FCFS 系统的"批量抢购/多账户"特征显著；可观测。
- `F`：若高价值配额在 FCFS 下无套利特征，需修正。
- 应用：配额建模先回答"资源能否转售 + 谁该优先"，再选分配机制；并给 FCFS 配"防批量"策略。

**⑤ 口径漂移：'看似超标实则达标'**
- `S`：预算对比常在"含税/不含税、是否资本化、是否含调拨"等口径上游移，导致同一笔支出时而算预算时而不算。
- `H`：口径是预算的"度量单位"；口径漂移=度量漂移，它让"超支/达标"变成可协商而非可判定。口径一致性是预算的守恒/验证器（呼应 §3/§9）——失去它会面子(报表)与里子(事实)脱节。
- `P`：口径规则模糊的预算系统，"超支争议→升级审批"的比例显著高于口径锁死者。
- `F`：反例即修正。
- 应用：把"口径"建成受控元数据（谁改过、何时、影响面），而非可随手切换的显示选项。

### 14.2 机制韧性检查表（预算/配额）

| 机制 | 代理指标风险 | 博弈/套利 | 反馈时滞 | 风险外溢 |
|---|---|---|---|---|
| 申报博弈 | 预算执行率≠预算精准 | 报高留安全垫 | 年度才考核 → 一年期时滞 | 虚报→资源错配→真需求被挤 |
| 期末突击 | 年底执行率100%≠用得值 | 未用即砍→突击消费 | 只在年末暴露 | 浪费+次年基数失真 |

### 14.3 进化建议（EVO-E-B4）：预算软硬约束 → "分级闸门 + 例外留痕"

- **当前机制**：预算要么硬拦(全拒)要么软提示(全放)。
- **目标机制**：按"额度缺口 + 支出类型 + 发起人信用"分级——小额可自动过闸、大额/越权强制走"例外审批 + 理由留痕"，并把"超预算出多少次、差额多少"回馈给预算持有人。
- **因果链**：单一软硬 → 分级闸门 + 反馈 → 既不僵化误伤、也不虚设失控，且"突破预算"成为有记录的显式行为而非悄悄放行。
- **受益/受损**：审批链（快速放行小额）与财务治理（大额可见）双受益；"无痕超支"空间被压缩。
- **博弈检查**：若分级阈值被钻空（拆单规避大额审批），需"同供应商/同期间聚合"检测。
- **边界**：策略/治理点调整，不命中 `K1-K5`，保持核心抽象内进化（但预算模块本身若设计为自言自语且无源码依托，实装前仍应视为未验证候选）。

## 附 2 · 账类系统识别与建模四问（落地清单）

拿到一个新业务，按序回答：

1. **它是账吗？** 用第1章四问判定；不是 → 别过度设计，是 → 继续。
2. **五要素是啥？** 对象/分类/度量 三个词；事件有哪些（流入/流出/调整/冻结）；何时固化。
3. **守恒怎么守？** 写方程 → 枚举"可出性/负向"规则 → 排验证器位置。
4. **要不要承诺层？** 业务里是否出现"未来才兑现、现在要预留" → 建"承诺明细"而非计数器。

> 这四问对**买菜系统的小余额**和**跨国集团的全面预算**同样有效，只是规模与维度数量不同。

**四轮闭环沉淀的通用教训**（比任何单条更值钱）：
1. **先分型再出方案**：同一现象"陷阱"vs"有意设计(受控豁免)+补监控/补审计"行动方向不同（§12①/§13①）。
2. **"未见"≠"没有"**：本地快照没有≠产品没有；"缺X"类论断必须等证据（§13① F'-b 教训）。
3. **类能不能替代证据**：负库存"缺监控"有证，不能类推到分配标准"缺审计"（§13①）。
4. **约束 vs 建议**：账类系统只对单据字段记账，物/对侧规则没连"审核/锁库"就只是建议（§12③ H''''、§11④ 单边快照）。
5. **行为期望 ≠ 产品承诺**：守恒收敛、闭环存在等"应该如此"须用代码或数据证实再写（§11④/§12③）。
