### 阶段顺序强制约束

1. **G0 = Level 0 系统总览层**。
2. **G1 = Level 1 业务域汇总层**，是 G2 的硬性前置，必须先生成并验收 Level 1。
3. **G2 = Level 2 上下文分析层**，只能读取已通过 G1 门禁的业务域划分和上下文清单。
4. 未通过 G1 时，禁止从 Level 0 直接进入 Level 2；“先分析 Level 2、后补 Level 1”不符合本 SOP。
5. 执行者在每个 Phase 开始时必须记录当前 Gate、输入产物、输出目录和门禁结论。

## 0. 执行前置

### 0.0 产物完整性保障（防漏建 / 防误删）

> **强制约束**：本节规则在 `0.1 任务识别` 之前生效。下列三条不满足时，禁止进入任何阶段门禁；任何“后续补建 Level 1”或“先分析 Level 2、再回写 Level 1”的做法均视为破坏 SOP。

1. **业务域清单是唯一来源**
   - 在 G0 完成时必须形成 `系统分析产出/Level 0/02-模块分级.md` 中明确列出的业务域清单（含编号、标识、中文名、对应上下文列表）。
   - 该清单是后续 Level 1 / Level 2 目录、文件名、索引、检查点和门禁脚本的**唯一事实来源**；任何新增、拆分、合并都必须先回到 Level 0 留痕。
2. **骨架预创建（在 G0 门禁通过后立即执行，不可推迟到 G2）**
   - G0 门禁通过后立即按业务域清单生成 `Level 1-业务域层/业务域<NN>-<name>(<domain>)` 目录，并为每个业务域同时创建三份占位文件：`01-业务域概览.md`、`02-上下文清单.md`、`03-业务域总结.md`（内容可暂为空模板，但文件必须存在）。
   - 占位文件顶部必须包含固定标记 `<!-- skeleton: do not delete -->`，供门禁脚本识别“被故意清空但未删除”的情况。
   - 三份文件未同时存在，视为 G1 不可启动；Level 2 任何任务禁止在没有对应 Level 1 骨架的业务域下被创建。
   - **骨架预创建只生成带 skeleton 标记的空模板；G1 任务是"填满模板"而非"创建模板"**。skeleton 标记之后必须有非"-"或非"待补充"的实质分析内容，否则视为 G1 未完成。
3. **门禁脚本强制校验（必须可重跑）**
   - 在仓库根提供 `check-level1-skeleton.ps1`（Windows）与 `check-level1-skeleton.sh`（POSIX）两个脚本，固定退出码：
     - `0`：所有业务域的三份骨架齐全且含 skeleton 标记，且每个文件至少有一行实质分析内容（非纯模板占位符），可继续 G2。
     - `2`：存在 Level 1 目录但骨架缺失或被误删，必须先重建骨架，禁止进入 G2。
     - `3`：存在 Level 2 任务，但其所属业务域在 Level 0 业务域清单中不存在或未生成 Level 1 骨架，禁止继续。
     - `4`：业务域清单与 Level 1 目录不一致（漏建、错号、错名、错中文名），禁止继续。
     - `5`：Level 1 文件存在且含 skeleton 标记，但内容全为模板占位符（如"待补充""待分析""-"等），视为 G1 未完成，禁止进入 G2。
   - G1 门禁、G2 启动、G6 验收三个节点必须显式调用该脚本并把退出码写入检查点；任何非 0 退出码都阻断后续阶段。
   - 脚本实现要点（必须照做，**禁止简化为只校验文件存在**）：
     - 读 `Level 0/02-模块分级.md` 中的业务域表格，得到 `业务域<NN>-<name>(<domain>)` 的全集。
     - 对每个业务域校验目录存在、三份文件存在且非空、文件首行包含 `<!-- skeleton: do not delete -->`。
     - 校验 `Level 2/` 下任何子目录的所属业务域都在 Level 0 业务域清单中、并且其上级业务域的 Level 1 骨架齐全。
     - 校验业务域编号连续且不重复；编号与中文名一致；不允许出现两份 `01-业务域概览.md` 在不同业务域使用同一编号。

## 0.8 增量式执行策略

> **理论依据**：理论框架章节 0.6.8

### 0.8.1 索引文件维护

大型系统分析需要维护索引文件，记录每个分析对象的产出位置：

```markdown
# 系统分析产出/索引.md

## 阶段索引

| 阶段 | 业务域/上下文 | 产出目录 | 状态 | 完成时间 | 门禁记录 |
|------|--------------|---------|------|---------|---------|
| Level 1 | 支付(pay) | Level 1-业务域层/业务域02-pay支付/ | ✅已完成/⏳待生成 | - | G1-支付 |
| Level 2 | order-订单 | Level 2/上下文order-订单/ | ✅已完成 | 2026-09-04 | G2-order |
| Level 2 | goods-商品 | Level 2/上下文goods-商品/ | 🔄分析中 | - | G2-goods |
| Level 2 | pay-支付 | Level 2/上下文pay-支付/ | ⏳待分析 | - | G2-pay |

> **说明**：
> 1. Level 1 业务域索引是必填项，必须先于该业务域下的 Level 2 上下文登记。只有 G1 门禁通过后，才允许将对应上下文写入 Level 2 索引。
> 2. **索引表必须包含 Level 0 业务域清单中的所有业务域**；任何业务域漏登记视为索引不完整。
> 3. G0 完成后立即创建索引.md，初始状态所有业务域 = "⏳待生成"；G1 完成后更新对应业务域状态为"✅已完成"。
```

### 0.8.2 检查点执行流程

每个阶段完成后，记录检查点。**Level 1 必须单独记录检查点，不能只记录其后的 Level 2 位置**：

```markdown
# 检查点.md

## 最后检查点
- 时间：2026-09-04 10:00
- Gate：G1 / G2 / G3 / G4 / G5 / G6
- 阶段：Level 1 业务域汇总 / Level 2 上下文分析
- 位置：Level 1-业务域层/业务域X/ 或 Level 2/上下文X/
- Level 1 已完成：
- Level 1 未完成：
- Level 2 已完成：
- Level 2 未完成：
- 当前门禁结论：通过 / 不通过
- 门禁脚本退出码：check-level1-skeleton.ps1 = 0 / 2 / 3 / 4 / 5
- 阻断原因或证据位置：

> **说明**：每个 Gate 完成后必须追加一条检查点记录；无检查点记录视为该 Gate 未启动。G2 启动前必须确认 G1 检查点存在且门禁结论 = "通过"且脚本退出码 = 0。
```

### 0.8.3 断点续传操作

**中断恢复步骤**：
1. 读取检查点.md，获取最后位置
2. 读取索引.md，获取已分析对象列表
3. 从检查点位置继续分析
4. 分析完成后更新检查点

### 0.8.4 执行原则

| 原则 | 说明 |
|------|------|
| **阶段独立** | 每个阶段只依赖已完成的阶段 |
| **产出即时** | 分析完成立即写入文件 |
| **索引更新** | 每完成一个业务域或上下文立即更新对应阶段索引；Level 1 业务域必须先登记，Level 2 上下文不得先于所属业务域登记 |
| **检查点记录** | 每阶段完成后记录检查点 |
| **不依赖内存** | 读取时不依赖其他上下文的内存状态 |
| **批次控制** | 单批次分析对象数量受上下文限制 |

### 0.8.5 批次管理策略

> 单次AI调用的上下文窗口有限，需要批次管理。

**批次大小控制**：

| 系统规模 | 每批次对象数 | 每批次实体数 | 说明 |
|---------|-------------|-------------|------|
| 小型（<10模块）| 5-8个模板 | 10-15个实体 | 可一次性分析 |
| 中型（10-30模块）| 3-5个模板 | 5-10个实体 | 需要分批 |
| 大型（>30模块）| 2-3个模板 | 3-5个实体 | 严格分批 |

**批次内原则**：
- 单批次分析"有多少写多少"
- 批次间通过文件隔离上下文
- 批次完成后立即写入文件，不在内存积累

**批次执行流程**：

```
批次1：分析对象1-5 → 写入文件A → 更新索引
批次2：分析对象6-10 → 写入文件A → 更新索引
批次3：分析对象11-15 → 写入文件A → 更新索引
...
批次N：完成 → 更新检查点
```

**上下文隔离**：
- 每个批次只读取当前批次需要的文件
- 不读取其他批次已分析的内容（除非必要）
- 通过索引文件追踪已完成的分析

### 0.8.6 增量式执行示例

> **注**：Phase 编号对应 G0–G6 阶段门禁，便于理解执行顺序。**Level 1 不再是可选项；G1(Phase 2) 必须在 Phase 3 / G2 之前通过门禁，否则禁止进入 Level 2**。

```
Phase 1（G0 = Level 0 系统总览）
├─ 分析系统总览
├─ 写入：Level 0/00-执行总结.md
└─ 更新：索引.md
        ↓ [G0 门禁通过]

Phase 2（G1 = Level 1 业务域汇总）【必经、禁止跳过、禁止与 Phase 3 并行执行】
├─ 读取：Level 0 的上下文划分
├─ 按业务域并行产出业务域概览 / 上下文清单 / 业务域总结（业务域间可并行，但必须先完成所有 Level 1 再进入任一 Level 2）
├─ 写入：Level 1/业务域X/{01-业务域概览,02-上下文清单,03-业务域总结}.md
└─ 更新：索引.md
        ↓ [G1 门禁通过：所有 Level 0 划分的业务域均生成 3 个文件、且跨上下文一致性矩阵有实质内容、且 check-level1-skeleton.ps1 退出码 = 0]

Phase 3（G2 = Level 2 上下文分析，叶子节点）【在 G1 完成后可并行】
├─ 上下文A分析 → 写入 → 更新索引
├─ 上下文B分析 → 写入 → 更新索引
└─ ...

Phase 4（G3 集成层）
├─ 读取：Level 1 + Level 2 产出
├─ 综合：全局视图
└─ 写入：集成层/

Phase 5（G5 设计层）
├─ 读取：G3 集成层与 G4 评价层产出

Phase 6（G6 验收层）
├─ 读取：集成层产出
├─ 验证：覆盖度、质量
└─ 写入：验收层/
```

## 1. G1 阶段：Level 1 业务域汇总

> **说明**：Level 1 在 Level 0 之后执行，汇总 Level 0 划分的业务域。

### 产出要求

每个业务域必须产出以下文件：

| 产出文件 | 内容要求 |
|---------|---------|
| **01-业务域概览.md** | 域名称、优先级、包含上下文列表、核心概念汇总 |
| **02-上下文清单.md** | 上下文名称、状态、核心发现 |
| **03-业务域总结.md** | 跨上下文一致性分析、规则统一、对象关系 |

### 执行要求

1. **扫描要求**
   - 必须扫描 Level 0 的上下文划分
   - 必须确认每个业务域包含的上下文
   - 必须汇总核心概念

2. **生成步骤（不可跳过，且与 0.0 节骨架预创建配套）**
   - 从 Level 0 的业务域/上下文全集建立 Level 1 待生成清单。
   - 复用 `0.0` 节已生成的业务域目录与三份占位文件，**禁止在 G1 阶段才临时创建**。
   - 先填写 `02-上下文清单.md` 完成 Level 0 → Level 1 的全量映射，再填写概览和总结；没有对应 Level 1 目录的业务域不得创建其 Level 2 分析任务。
   - 三份文件完成后执行 `check-level1-skeleton.ps1` 并把退出码写入检查点；只有退出码 = 0 才释放 G2 任务。

3. **输出要求**
   - 每个业务域必须有产出文件
   - 上下文清单必须包含所有上下文
   - 业务域总结必须分析跨上下文的一致性

## 模板：Level 2 业务对象建模（静态建模）

## 执行前准备

### 必须完成的扫描

1. **扫描DAO层**：查找所有 `*Dao.java` 和 `*DaoImpl.java`
2. **扫描Entity层**：查找所有实体类
3. **扫描Service层**：查找业务服务类，找到业务方法
4. **扫描枚举类**：查找枚举定义，找到状态和类型

### 执行原则

- DAO、Entity、DTO、Service、Handler、Selector、Mapper 和枚举都是候选对象，必须先按理论框架的分类契约归类，不能要求技术对象数量等于业务实体数量。
- **候选对象以扫描范围为全集**：对已纳入范围的代码包、数据库表、接口契约、任务、消息、配置和文档进行穷举登记；不得只选“核心5个”或按上下文长度任意截断。无法完成穷举时，必须列出未扫描范围和原因，产出状态为“不通过”。
- **必须输出对象树**：至少按“上下文 → 聚合根候选 → 实体/值对象 → 命令/结果/领域事件 → 应用/领域服务 → 技术组件”展开；每个节点标明来源、类型、父节点/归属、状态（已确认/候选/排除/未知）和去向。
- 业务实体必须建立“实体识别卡”：业务身份、技术标识、生命周期、读写动作、状态、关系、不变式、证据层级和待确认项。
- **聚合根逐一判定**：所有聚合根候选必须列出判定结果和理由；不能因为没有事件、没有方法或事件少于2个就排除，也不能因为类名或请求入口就认定为聚合根。
- 属性必须与代码/数据库字段或接口字段有证据；无法确认的字段标为未知，不能编造。
- 方法只能在能证明业务动作时归入业务行为；Service/Handler 方法默认记录为应用编排或技术调用。
- 必须区分业务实体关系图、用例调用链、业务信息流和状态转换图，禁止用一张ER图承载全部关系。
- 每个对象、关系、状态转换和规则都必须能追溯到证据；无法确认时保留候选或未知状态。

```
| **关系/关联** | 分别输出实体关系、调用链、信息流和状态转换 | 每条关系有类型、数量、时序和证据 |
| **约束** | 核心不变式和约束全部列出，未知项形成缺口 | 不设每聚合约束数量下限 |

**门禁**：对象扫描范围完整、对象树无漏登、聚合根候选全部判定、分类和证据账本完整，且无P0缺口，才可进入下一个上下文分析。对象、属性、方法、事件和约束的数量不得作为单独通过条件。
```

|------|------|
| ★★★★★ | 新增规则无需改代码，只需配置 |

| ★★★ | 新增规则需改10-30%代码 |
| ★★ | 新增规则需改30-50%代码 |
| ★ | 任何扩展需重构 |

**扩展性总分计算**：
```
总分 = (规则扩展性×0.3 + 概念扩展性×0.25 + 流程扩展性×0.25 + 集成扩展性×0.2) × 20
```
