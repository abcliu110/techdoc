# 遗留系统拆解理论

> **文档版本**：v0.1（初稿，待评审）
> **定位**：遗留系统分析方法论目录的**顶层理论**，回答"为什么这样拆解"。
> **与执行 SOP 的关系**：本理论是 SOP 的上位依据，SOP 执行者必须先理解本理论再读 SOP。
> **不包含**：执行步骤、模板、check 脚本（这些属于 SOP 层）

---

## 0. 理论目标

### 0.1 一句话目标

**建立一套可操作的认知框架，使任何人都能通过结构化拆解，深入理解任意信息系统的业务本质和架构逻辑，并基于理解指导新系统开发。**

### 0.2 拆解的认知前提

任何信息系统都是**人类意图的物质化**——业务人员的需求、管理者的决策、历史包袱的妥协、技术债务的积累，在代码、数据库、接口、配置里都能找到痕迹。

拆解不是"读代码"。代码是实现结果的载体，不是业务意图本身。同一个业务意图可以用 10 种代码写法实现；同样一段代码在不同上下文里可能承载不同业务意图。

因此，拆解的本质是**逆向还原意图**：

```
信息系统 ← 解构 ← 业务意图 + 历史约束 + 技术选择 + 偶然因素
```

### 0.3 拆解理论的三个核心命题

**命题一：拆解必须分层**
系统的复杂性来自纵深，不是来自广度。一个有 50 张表的系统，每个业务域有 5 张表、每个表 10 个字段——这个复杂度是纵深的，不是横向的。
拆解必须先分清层次，再在每一层建立结构。混淆层次是拆解失败的第一原因。

**命题二：拆解必须追溯因果**
系统里任何可见的结构（表、类、接口、状态值）都是某个因果链的产物。不追溯因果，就只能得到结构清单，不能得到理解。
因果链有三种：
- **业务因果**：为什么需要这个功能？解决了什么问题？
- **历史因果**：为什么是这个实现方式？当时有什么约束？
- **技术因果**：这个技术选型在当时是否合理？现在是否仍然合理？

**命题三：拆解必须区分三层结论**
从代码事实到最终理解，中间有三层结论，必须区分清楚：

| 结论层 | 定义 | 示例 | 可信度 |
|--------|------|------|--------|
| 代码事实 | 代码中明确存在的行为 | `OrderMasterDO.pay()` 方法存在 | 高（但只证明存在） |
| 业务推断 | 对代码事实的业务解释 | "pay() 方法说明订单需要支付" | 中（推断） |
| 历史解释 | 对业务推断的进一步追问 | "为什么要单独写 pay() 方法而不放在支付服务里？" | 低（需要访谈或文档） |

**拆解报告里不能把三层结论混写**——读者必须能区分"代码说了什么"和"我们推测什么"。

## 1. 拆解的维度：拆解什么？

### 1.1 四维拆解框架

任何信息系统都可以从四个维度拆解，每个维度回答不同的问题：

```
维度一：业务逻辑
  回答：系统支持的"人"和"人的意图"是什么？
         哪些角色能做哪些事？
         做事的流程和规则是什么？
         失败和异常怎么处理？

维度二：数据模型
  回答：系统维护了哪些"事实"？
         这些事实之间是什么关系？
         事实如何产生、如何变化、如何消亡？
         事实的权威存储在哪里？

维度三：架构设计
  回答：系统由哪些组件构成？
         组件之间怎么通信？
         为什么是这些组件而不是别的？
         组件的边界在哪里、为什么这样划？

维度四：运行行为
  回答：系统实际怎么工作？
         部署在哪里、依赖什么基础设施？
         定时任务和后台处理是什么？
         故障模式是什么？
```

### 1.2 维度之间的关系

四个维度不是并列的，**数据模型是业务逻辑的投影，架构设计是数据模型和业务逻辑的实现约束，运行行为是架构设计的实际表现**。

```
业务逻辑（意图层）
    ↓ 投影到
数据模型（结构层）
    ↓ 实现约束
架构设计（实现层）
    ↓ 部署运行
运行行为（事实层）
```

理解一个系统，必须从业务逻辑出发（"做什么"），经过数据模型（"存什么"）和架构设计（"怎么做"），落地到运行行为（"实际怎样"）。

**拆解时禁止逆向**：不能从代码结构倒推业务逻辑（那会得到技术清单，不是业务理解）。

## 2. 拆解的层次：拆解到什么粒度？

### 2.1 四层拆解结构

拆解不是一次完成，是从粗到细逐层深入的：

```
第一层：系统级
  回答：这个系统是什么？服务谁？在更大系统里扮演什么角色？
  产出：系统边界定义、核心能力地图、上下文关系图

第二层：域级
  回答：这个系统里有哪些相对独立的业务领域？领域之间的关系是什么？
  产出：业务域划分、跨域流程、域间契约

第三层：上下文级（最厚的层）
  回答：每个业务域内部由哪些业务场景构成？场景之间的因果是什么？
  产出：业务切片（含正常流程 + 异常流程 + 失败恢复）、
        业务对象（含状态机、不变式、生命周期）、
        业务规则（含触发条件、执行顺序、冲突关系）

第四层：实现锚点
  回答：每个业务场景在代码里具体怎么实现的？关键路径是什么？
  产出：实现映射（业务语义 → 代码位置）、
        关键决策记录（为什么要这样做）
```

### 2.2 每一层的"够用"标准

| 层次 | 够用标准 | 不够用的信号 |
|------|---------|-------------|
| 第一层 | 能向非技术人员用 3 句话说清系统是什么 | 只能说"它是一个 XX 系统" |
| 第二层 | 能说出 5 个以内核心业务域的名称和边界，能画出域间关系 | 每个域都说不清边界 |
| 第三层 | 能讲清每个核心场景的"谁在什么条件下做什么得到什么"，包括失败路径 | 只有 happy path，没有失败场景 |
| 第四层 | 能从业务语义追溯到代码位置，代码变更能预判业务影响 | 代码改了不知道影响什么 |

**停止拆解的条件**：当某一层的"够用标准"已达到，且继续深入不会改变对上一层的理解时停止。不追求第四层的全量覆盖。

## 3. 抽象归纳：从拆解到理解

### 3.1 抽象的三级跳

拆解得到的是"具体"，抽象得到的是"本质"。从具体到本质要跳三级：

```
第一跳：从具体代码到业务语义
  → 把类名、方法名、字段名翻译成业务含义
  → 核心技能：区分"技术对象"和"业务对象"

第二跳：从业务语义到业务模式
  → 在多个相似业务场景中识别共同结构
  → 核心技能：找到"变化的部分"和"不变的部分"

第三跳：从业务模式到领域模型
  → 把业务模式归入更大的领域框架
  → 核心技能：识别"核心业务"和"支撑业务"
```

### 3.2 抽象的操作路径

**第一跳的操作**：代码对象 → 业务对象

```
Step 1：列清单——把代码中所有候选对象列出来（类、接口、表、字段）
Step 2：分类——按"技术组件 / 命令对象 / 结果对象 / 业务实体 / 值对象"分类
Step 3：追问——对每个业务实体追问：
         ① 这个对象的生命周期由谁控制？
         ② 这个对象的状态变化是否有业务意义？
         ③ 这个对象是否被其他组件引用？
Step 4：判定——同时满足①+②+③ → 聚合根
                    满足② → 实体
                    都不满足 → 值对象或技术组件
```

**第二跳的操作**：多个相似场景 → 业务模式

```
Step 1：找相似——列出所有业务场景
Step 2：画矩阵——横轴是场景，纵轴是特征，填入每个场景的特征值
Step 3：找不变——同一列（特征）上，所有场景的值是否相同？
         相同 → 这个特征是"不变部分"
         不同 → 这个特征是"变化部分"
Step 4：命名——为"不变部分"命名，这就是业务模式
         为"变化部分"标注变体点
```

**第三跳的操作**：业务模式 → 领域模型

```
Step 1：画核心度——哪些模式是这个系统存在的根本原因？
         删除哪个模式会导致系统失去价值？
Step 2：画依赖度——哪些模式依赖其他模式存在？
Step 3：画边界——核心度高且依赖度低 → 核心域
         核心度低且被依赖高 → 支撑域
         核心度低且依赖度低 → 通用域
Step 4：定关系——核心域的变更不能影响支撑域；支撑域可以依赖核心域
```

## 4. 进化方向：从理解到决策

### 4.1 进化的前提：矛盾识别

进化不是"把所有旧的换成新的"。进化的前提是**准确识别矛盾**：系统当前的结构和它应该服务的业务之间存在什么张力？

矛盾有三类：

| 矛盾类型 | 定义 | 示例 | 发现方式 |
|---------|------|------|---------|
| **业务矛盾** | 业务规则之间相互冲突或无法同时满足 | "优惠券和折扣不能叠加"但"会员价本身就是折扣" | 从规则账本里找互斥关系 |
| **结构矛盾** | 系统结构无法自然表达业务概念 | 订单和商品在不同上下文里用同一张表关联 | 从关系图里找多跳关联 |
| **演化矛盾** | 历史设计在当前业务规模下失效 | 单体架构在日均 10 万订单下性能下降 | 从运行行为里找性能拐点 |

### 4.2 进化的决策框架

在识别矛盾之后，进化有三个方向，必须按顺序考虑：

```
方向一：保留
  什么情况下保留？
    → 这个设计在当前业务约束下仍然是最优解
    → 改变它的成本远大于收益
    → 它服务的是核心业务，不能动

方向二：优化
  什么情况下优化？
    → 局部改进可以缓解矛盾，不需要整体重构
    → 优化成本低、风险小、收益明确

方向三：替换
  什么情况下替换？
    → 矛盾是结构性的，无法通过局部优化解决
    → 替换的成本可以被未来收益覆盖
    → 有足够的迁移窗口期
```

**禁止跳步**：不能从"发现问题"直接跳到"替换方案"。必须先问"能不能保留"，再问"能不能优化"，最后才是"要不要替换"。

### 4.3 进化的决策链

```
识别矛盾
    ↓
评估矛盾的影响范围（核心域/支撑域/通用域）
    ↓
评估矛盾的历史深度（历史包袱/设计失误/规模变化）
    ↓
判断进化方向（保留/优化/替换）
    ↓
选择进化模式
    ↓
规划演进路径（保留哪些、改造哪些、替换哪些、顺序是什么）
    ↓
输出 ADR（架构决策记录）
```

## 5. 质量标准：怎么判断拆解到位了？

### 5.1 拆解质量的三层验证

**第一层：结构完整性**
每个维度、每个层次是否都有产出？有没有明显缺失的维度或层次？

**第二层：因果追溯性**
每个结论是否能追溯到证据？三层结论是否区分清楚？

**第三层：读者可理解性**
一个不了解这个系统的人，能否仅通过拆解报告理解核心业务逻辑？

### 5.2 禁止行为清单

拆解过程中，以下行为**禁止**：

1. ❌ 把"类名"直接当"业务概念"——类名是技术事实，业务概念需要翻译
2. ❌ 把"表结构"直接当"数据模型"——表是存储实现，数据模型是业务语义
3. ❌ 把"接口路径"直接当"业务能力"——接口是技术契约，业务能力需要从调用方意图理解
4. ❌ 把"枚举值"直接当"状态机"——枚举只证明状态存在，不证明状态转换
5. ❌ 把"高并发"直接当"性能问题"——性能问题的根因可能是业务逻辑复杂度，而非技术指标
6. ❌ 把"代码改了"直接当"业务影响"——必须先追溯到业务语义，再判断影响
7. ❌ 把"多系统"直接当"微服务"——微服务是架构选择，不是系统数量的必然结果
8. ❌ 把"历史包袱"直接当"需要重构"——历史包袱可能是核心业务的沉淀，需要先理解再决策

## 6. 拆解理论与 SOP 的关系

### 6.1 理论是 SOP 的上位依据

本理论回答"为什么这样拆解"，SOP 回答"怎么执行拆解"。两者是"知"与"行"的关系：

| 维度 | 理论层（本文） | SOP 层 |
|------|---------------|--------|
| 回答的问题 | 为什么要这样拆解？ | 具体怎么执行拆解？ |
| 粒度 | 概念、原则、方法路径 | 步骤、模板、check 清单 |
| 稳定性 | 高（不随项目变化） | 中（随方法论迭代更新） |
| 读者 | 理论学习者、SOP 编写者 | 执行者（人或 AI） |

### 6.2 SOP 必须引用本文

任何 SOP 在执行拆解前，必须先确认执行者理解本文的以下章节：

- §0.3 三个核心命题（尤其是三层结论的区分）
- §1.1 四维拆解框架（尤其是"禁止逆向"的约束）
- §2.1 四层拆解结构（尤其是每层的"够用标准"和停止条件）
- §3.1 抽象的三级跳（尤其是"技术对象"和"业务对象"的区分）
- §4.2 进化的决策框架（尤其是"禁止跳步"的约束）
- §5.2 禁止行为清单（8 条）

### A. 术语表

| 术语 | 定义 |
|------|------|
| 拆解 | 从信息系统的可见结构逆向还原业务意图和架构逻辑的过程 |
| 抽象 | 从具体实现中提取共同结构、去除细节、形成更高层次认知的过程 |
| 归纳 | 从多个具体实例中发现共同规律、形成通用模式的过程 |
| 进化 | 在理解现状的基础上，规划从当前结构向目标结构演进的方向和路径 |
| 业务语义 | 代码、数据、配置在业务层面的含义，而非技术层面的含义 |
| 技术对象 | 代码中的类、接口、模块，不直接对应业务概念 |
| 业务对象 | 业务层面有意义的实体，有生命周期和状态变化 |
| 不变量 | 在指定范围内始终成立的业务约束 |
| 矛盾 | 系统当前结构与应该服务的业务之间存在的张力 |
