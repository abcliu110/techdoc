# 遗留系统分析方法论

> **版本**：V2.7
>
> **目的**：通过系统化的分析方法，从遗留系统中提取业务知识，进行抽象升华，评价业务规则的扩展性和适应性，最终指导设计出更优的新系统。
>
> **适用范围**：任何需要从遗留系统改造或重建的信息系统。

---

## 0. 理论基础与设计原则

### 0.1 理论基础

本方法论整合以下业界先进理论与实践：

| 理论/实践 | 核心贡献 | 在本方法论中的位置 |
|-----------|----------|-------------------|
| **DDD（领域驱动设计）** | 限界上下文、聚合、实体、值对象、领域事件 | 分析层的核心语言 |
| **Event Storming** | 业务流程的事件化建模 | 业务流程分析方法 |
| **CQRS（命令查询职责分离）** | 读写分离、命令与查询分离 | 业务规则评价维度 |
| **六边形架构（Hexagonal）** | 端口与适配器、内外解耦 | 架构设计指导 |
| **整洁架构（Clean Architecture）** | 依赖倒置、分层职责 | 架构设计指导 |
| **STRangler Fig模式** | 渐进式迁移策略 | 改造策略 |
| **业务建模（ArchiMate）** | 业务架构多视角建模 | 业务抽象方法 |
| **溯因推理（Abductive Reasoning）** | 从结果追溯原因的推理方式 | 深层因果分析方法 |

**融合原则**：
1. **DDD为骨架**：DDD的战略设计（限界上下文、聚合、领域事件）贯穿整个分析层
2. **Event Storming为血肉**：业务流程通过事件风暴方法进行可视化建模
3. **量化评估为依据**：可扩展性和适应性通过量化评分矩阵进行评价
4. **六边形为架构模板**：架构设计以六边形架构为核心，同时借鉴整洁架构
5. **溯因推理为深度**：深层因果分析借鉴溯因推理，从结果追溯原因

### 0.2 设计原则

| 原则 | 含义 |
|------|------|
| **业务完整性优先** | 老系统的业务必须100%继承，不遗漏任何功能 |
| **抽象层次递进** | 从具体到抽象、从业务到模式，层层升华 |
| **评价驱动设计** | 评价结论直接指导架构设计决策 |
| **可验证性** | 每个分析结论必须有可验证的标准 |
| **实践导向** | 理论必须转化为可操作的步骤和模板 |

### 0.4 迭代策略（非线性执行）

本方法论在实际项目中采用**渐进式迭代**而非线性执行：

| 阶段 | 迭代模式 | 说明 |
|------|---------|------|
| **分析层** | 快速扫描 → 重点深入 → 补充完善 | 先整体了解，再聚焦核心，最后补充边缘 |
| **评价层** | 边分析边评价 | 分析到一定程度即可开始评价，不必等100%完成 |
| **设计层** | 分析-评价-设计螺旋迭代 | 每完成一个模块的分析和评价，立即开始设计 |
| **验证层** | 持续验证 | 新功能开发完成即验证，不必等全部完成 |

**关键原则**：不追求一次性完美，而是追求持续逼近真相。

**层级说明**：

| 层级 | 粒度 | 分析深度 | 并行能力 |
|------|------|---------|---------|
| **Level 0** | 系统级 | 概览 | 1人 |
| **Level 1** | 业务域级 | 中度 | 可并行 |
| **Level 2** | 上下文级 | 深度 | 可并行 |
| **Level 3** | 子系统级 | 视需求 | 可并行 |
| **Level N** | 细粒度 | 按需 | 按需 |
| **集成层** | 全局 | 综合 | 串行 |

**分析顺序原则**：

```
分析顺序：Level 0 → Level 1 → Level 2 → Level 3 → 集成层
         ↑
         └── 从根到叶，广度优先

并行原则：同层级可以并行，不同层级按依赖顺序
         例：Level 2的所有上下文可以并行分析

产出原则：叶子节点的产出向上汇总，父节点整合子节点产出
```

**大型系统的产出规模预估**：

| 系统规模 | 上下文数 | 预计产出文件数 |
|---------|---------|--------------|
| 小型（<10模块）| 3-5个 | 30-50个 |
| 中型（10-30模块）| 5-15个 | 50-150个 |

#### 0.6.1 大型系统的特征识别

| 特征 | 阈值 | 影响 |
|------|------|------|
| 模块数量 | > 50个 | 无法单次完成全量分析 |
| 数据表数量 | > 1000张 | 数据库分析耗时过长 |
| 代码规模 | > 50万行 | 代码扫描无法人工逐一审查 |
| 团队规模 | > 20人 | 协作复杂度上升 |
| 业务域数量 | > 5个 | 限界上下文划分困难 |

> **判定方法**：满足任意3项即为大型系统，需采用专项处理。

#### 0.6.3 大型系统的限界上下文划分策略

**策略1：核心域优先策略**

```
分析顺序：
1. 先识别核心域（最核心的业务价值）
2. 再识别支撑域（为核心域提供服务）
3. 最后识别通用域（跨业务复用）

划分原则：
- 核心域：深入分析，建立完整模型
- 支撑域：概要分析，关注接口契约
- 通用域：复用分析，避免重复建设
```

**策略2：团队边界映射策略**

```
划分原则：
- 限界上下文边界 ≈ 团队边界
- 避免跨团队协作在同一个上下文内

验证方法：
- 检查每个上下文的变更频率
- 变更频率高且跨团队 → 需要拆分
```

**策略3：数据一致性边界策略**

```
划分原则：
- 强一致性数据 → 同一个上下文
- 弱一致性数据 → 可以跨上下文

验证方法：
- 检查模块间的数据库表依赖
- 共享同一数据库的事务 → 同一个上下文
```

#### 0.6.4 大型系统的模块分级策略

**分级方法**：

| 级别 | 定义 | 分析深度 | 分析优先级 |
|------|------|---------|-----------|
| **P0 核心模块** | 核心业务价值，必须准确 | 深度分析 | 最高 |
| **P1 重要模块** | 支撑核心业务，影响较大 | 中度分析 | 高 |
| **P2 一般模块** | 支撑性功能，影响可控 | 概要分析 | 中 |
| **P3 边缘模块** | 历史遗留，无人维护 | 地图扫描 | 低 |

**分级标准**：

| 标准 | P0 | P1 | P2 | P3 |
|------|----|----|----|-----|
| 核心业务相关 | ✓ | 部分 | 间接 | 无 |
| 日均调用量 | >1万 | >1千 | >1百 | <1百 |
| 代码变更频率 | 高 | 中 | 低 | 无 |
| 涉及金额 | 高 | 中 | 低 | 无 |
| 故障影响 | 全系统 | 部分 | 有限 | 无 |

#### 0.6.5 大型系统的上下文依赖管理

> 大型系统的上下文不是真正的"树"，而是**DAG（有向无环图）**，因为上下文之间存在依赖关系。

**上下文依赖类型**：

| 依赖类型 | 含义 | 示例 | 处理方式 |
|---------|------|------|---------|
| **数据依赖** | 上下文A的数据被上下文B使用 | 订单上下文依赖客户上下文 | 通过接口查询，不共享数据库 |
| **流程依赖** | 上下文A的流程触发上下文B的流程 | 支付成功触发订单完成 | 通过领域事件异步通知 |
| **语义依赖** | 上下文A的概念被上下文B引用 | 订单上下文使用商品上下文的价格 | 建立共享概念映射 |
| **技术依赖** | 上下文A的技术组件被上下文B使用 | 通用工具上下文 | 建立共享基础设施 |

**上下文分级**：

| 级别 | 定义 | 分析顺序 | 并行能力 |
|------|------|---------|---------|
| **根上下文** | 无依赖其他上下文 | 最先分析 | 可并行 |
| **叶上下文** | 不被其他上下文依赖 | 最后分析 | 可并行 |
| **中间上下文** | 既有依赖也有被依赖 | 等待依赖完成后分析 | 受限并行 |

**依赖分析步骤**：

1. **识别上下文**：通过全局扫描识别所有上下文候选，标注核心业务职责

2. **识别依赖关系**：
   - 数据流分析：谁产生数据，谁消费数据
   - 调用链分析：谁调用谁的接口
   - 事件流分析：谁发布事件，谁订阅事件

3. **构建依赖图**：
   - 节点：上下文
   - 边：依赖关系（有向边，从依赖方指向被依赖方）
   - 检查：是否存在循环依赖

4. **分析级联影响**：修改某个上下文的接口，会影响哪些上下文

**依赖图示例**：

```
┌─────────────┐
│   客户上下文   │ ← 根上下文（无依赖）
└───────┬─────┘
        │ 依赖
        ▼
┌─────────────┐
│   商品上下文   │
└───────┬─────┘
        │ 依赖
        ▼
┌─────────────┐
│   订单上下文   │
└───────┬─────┘
        │ 依赖
        ▼
┌─────────────┐
│   支付上下文   │ ← 叶上下文（无被依赖）
└─────────────┘
```

**分析顺序推导**：

```
从根到叶的拓扑排序：
1. 客户上下文（最先分析）
2. 商品上下文（等待客户上下文）
3. 订单上下文（等待商品上下文）
4. 支付上下文（等待订单上下文）

并行能力：
- 步骤1：只有客户上下文 → 不能并行
- 步骤2：只有商品上下文 → 不能并行
- 步骤3：只有订单上下文 → 不能并行
- 步骤4：只有支付上下文 → 不能并行

结论：这个例子是严格串行的。但如果加入仓储上下文、物流上下文，可以实现部分并行。
```

**依赖冲突检测**：

| 检测项 | 检测方法 | 发现问题 |
|-------|---------|---------|
| 循环依赖 | 检查依赖图中是否存在环 | 上下文边界划分错误 |
| 单点依赖 | 检查是否有多个上下文依赖同一个上下文 | 单点瓶颈 |
| 依赖深度 | 检查最长依赖链长度 | 分析周期过长 |
| 依赖复杂度 | 检查每个上下文的平均依赖数 | 上下文边界可能不合理 |

#### 0.6.6 大型系统的并行分析策略

**并行分析的前提条件**：

| 条件 | 说明 |
|------|------|
| 限界上下文已划分 | 每个上下文独立分析 |
| 模块分级已完成 | 按优先级分配资源 |
| 接口契约已明确 | 上下文间依赖清晰 |
| 团队配置到位 | 每个上下文有负责人 |

**并行分析方法**：

```
Phase 1：全局概览（串行，1周）
    │
    ▼
Phase 2：P0模块深度分析（并行，4-6周）
    ├─ Context A 分析 ──→ 业务模型
    ├─ Context B 分析 ──→ 业务模型
    └─ Context C 分析 ──→ 业务模型
    │
    ▼
Phase 3：P1模块分析（并行，4-6周）
    │
    ▼
Phase 4：P2/P3模块扫描（并行，2-4周）
    │
    ▼
Phase 5：上下文集成验证（串行，2周）
```

**并行分析的协调机制**：

| 机制 | 频率 | 内容 |
|------|------|------|
| 日站会 | 每日 | 进度同步、问题升级 |
| 周评审 | 每周 | 阶段性评审、问题汇总 |
| 上下文对齐会 | 双周 | 接口契约确认、模型一致性检查 |
| 问题升级会 | 按需 | 跨上下文问题处理 |

#### 0.6.7 大型系统的上下文集成策略

**问题**：并行分析后，上下文之间可能存在冲突或不一致。

**集成验证清单**：

| 检查项 | 检查内容 | 发现问题 |
|-------|---------|---------|
| 接口一致性 | 同一接口在不同上下文中定义是否一致？ | 接口定义冲突 |
| 术语一致性 | 同一术语在不同上下文中是否含义相同？ | 术语歧义 |
| 数据归属 | 同一数据是否只在一个上下文中作为聚合根？ | 数据归属不清 |
| 调用关系 | 调用链是否形成循环依赖？ | 循环依赖 |
| 事件契约 | 领域事件在不同上下文中的定义是否匹配？ | 事件契约不匹配 |

**冲突解决策略**：

| 冲突类型 | 解决策略 | 负责人 |
|---------|---------|--------|
| 接口定义冲突 | 主持控场，以核心上下文为准 | 架构师 |
| 术语歧义 | 业务方裁决，建立统一术语表 | 业务分析师 |
| 数据归属不清 | 技术方评估，以业务内聚为准 | 技术架构师 |
| 循环依赖 | 重构边界，打破循环 | 技术架构师 |
| 事件契约不匹配 | 对齐事件格式，建立事件规范 | 技术架构师 |

#### 0.6.8 大型系统的上下文管理策略

> 大型系统的分析受限于AI的上下文窗口，需要特殊的上下文管理策略。

**问题背景**：

| 问题 | 表现 | 影响 |
|------|------|------|
| **上下文溢出** | AI上下文窗口有限，无法一次性分析完整个系统 | 分析结果不完整 |
| **遗忘** | 分析后半部分忘记前半部分细节 | 重复分析或遗漏 |
| **浅尝辄止** | 不敢深入分析（怕上下文溢出）| 分析深度不足 |
| **无法综合** | 分析完所有域后，难以综合出全局视图 | 产出碎片化 |

**上下文溢出阈值估算**（经验估算，需实践验证）：

| 系统规模 | 代码规模 | 上下文压力 | 处理策略 |
|---------|---------|-----------|---------|
| 小型（<10模块）| <10万行 | 轻松 | 可一次性分析 |
| 中型（10-30模块）| 10-50万行 | 中等 | 按模块分批 |
| 大型（30-50模块）| 50-100万行 | 紧张 | 按上下文分批 |
| 超大型（>50模块）| >100万行 | 溢出 | 必须增量式 |

**增量式分析方法论**：

| 原则 | 说明 | 实现方式 |
|------|------|---------|
| **阶段独立** | 每个阶段只依赖已完成的阶段，不依赖未完成的上下文 | 写入文件，读取时不依赖内存 |
| **产出即时** | 分析完成立即写入文件，不在内存中积累 | 每个上下文完成后立即写文件 |
| **索引维护** | 维护索引文件，记录每个对象的产出位置 | 索引文件按需加载 |
| **断点可续** | 中断后可从最后检查点恢复 | 检查点记录最后位置 |

**检查点机制原则**：

| 机制 | 内容 | 目的 |
|------|------|------|
| **检查点文件** | 最后分析位置、已完成项、未完成项 | 支持断点续传 |
| **索引文件** | 对象名称 → 产出文件位置的映射 | 按需加载 |
| **交付清单** | 每个阶段完成的产出文件列表 | 追踪进度 |

**增量式执行原则**：

```
分析顺序：
Level 0（系统总览）→ 写入文件 → 更新索引
    ↓
Level 2（上下文分析）→ 每个上下文独立分析 → 各自写入文件 → 更新索引
    ↓
Level 1（业务域汇总）→ 读取Level 2产出 → 汇总写入文件 → 更新索引
    ↓
集成层 → 读取Level 1产出 → 综合写入文件
```

**上下文隔离原则**：

| 问题 | 解决方案 |
|------|---------|
| 重复分析同一对象 | 索引文件记录已分析对象的位置 |
| 上下文遗忘 | 每个上下文独立文件，不依赖其他上下文内存 |
| 产出碎片化 | 统一的树形产出结构 + 索引文件 |
| 断点难续 | 检查点文件记录最后位置 |

#### 0.6.9 大型系统的分析质量保障

**问题**：并行分析可能导致质量不一致。

**质量保障机制**：

| 机制 | 说明 |
|------|------|
| 分析模板统一 | 所有上下文使用统一的分析模板 |
| 分析规范培训 | 分析前统一培训，确保方法一致 |
| 中间产物评审 | 每个上下文有阶段性评审 |
| 最终集成评审 | 所有上下文完成后统一评审 |
| 问题追溯机制 | 问题可追溯到具体的分析结论 |

**质量评分公式**：

```
整体质量分 = Σ(上下文质量分 × 上下文权重) / Σ上下文权重

上下文权重：
- P0上下文：权重 = 5
- P1上下文：权重 = 3
- P2上下文：权重 = 1
- P3上下文：权重 = 0.5
```

## 1. 分析层

### 1.1 业务理解（Business Comprehension）

#### 1.1.1 目标

从遗留系统中提取完整的业务语义，包括：
- 业务概念与术语
- 业务实体与关系
- 业务流程与规则
- 业务约束与边界

#### 1.1.2 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | 遗留系统（代码、数据库、文档、访谈） |
| **输出** | 业务概念模型、业务流程图、业务规则清单 |

#### 1.1.3 分析维度

采用DDD战略设计的**7要素提取法**：

| 要素 | 定义 | 分析问题 | 示例（POS系统）|
|------|------|---------|---------------|
| **主体（Who）** | 业务的参与者 | 谁使用这个系统？有哪些角色？ | 顾客、服务员、收银员、厨师、店长 |
| **目标（What）** | 参与者想达成的结果 | 用户使用系统想达成什么？ | 顾客想点餐结账、厨师想接收订单 |
| **规则（Rules）** | 业务必须遵守的约束 | 业务有哪些硬性规则？ | 满100才能用券、退菜必须填原因 |
| **协作（Collaboration）** | 主体之间的配合方式 | 各角色之间如何协作？ | 顾客→服务员→收银员→厨师 |
| **时序（Timing）** | 业务的时间维度 | 业务有有效期/时段/版本吗？ | 营业日00:00-24:00、班次早/中/晚 |
| **资源（Resource）** | 业务操作的实体对象 | 哪些实体被创建、消耗或转移？ | 桌台、打印机、库存、原材料 |
| **信息（Information）** | 业务传递的数据 | 哪些数据被创建、传递或存储？ | 订单数据、报表、流水、状态 |

> **说明**：增加"资源"和"信息"两个要素的原因：
> - **资源**与"实体"不同：实体是业务参与者（能动），资源是业务操作的对象（被动）
> - **信息**与"数据"不同：数据是技术存储形式，信息是业务语义载体

#### 1.1.3.1 7要素的互斥边界

> **借鉴自新方法论Q1的严谨性要求**：每个业务事实只能归入1个要素，不能同时属于多个。

| 要素 | 互斥边界（不属于本要素的事实举例） |
|------|----------------------------------|
| **主体** | 不包括"主体想做什么"（→目标）、"主体按什么规则做"（→规则） |
| **目标** | 不包括"实现目标的路径"（→协作+时序）、"目标必须满足的约束"（→规则） |
| **规则** | 不包括"违反规则的后果"（→协作中的处理流）、"规则何时生效"（→时序） |
| **协作** | 不包括"协作的节奏"（→时序）、"协作中谁主导"（→主体+视角） |
| **时序** | 不包括"时序中谁在先"（→协作+主体）、"时序是否过期"（→规则） |
| **资源** | 不包括"资源的归属"（→主体）、"资源的状态变化"（→规则） |
| **信息** | 不包括"信息的存储位置"（→技术）、"信息的生产者"（→主体） |

> **反证方法**：如果能把一个业务事实归入两个要素，说明要么是要素定义有重叠，要么是拆解不正确。每个事实只能属于一个要素。

#### 1.1.3.2 7要素的依赖关系

> **借鉴自新方法论Q1的依赖关系**：7要素不是平行的，它们有强依赖关系。

```
主体 ─→ 目标 ─→ 规则
              │
              ↓
            协作 ─→ 时序
              │
              ↓
           资源 ─→ 信息
```

| 依赖关系 | 说明 |
|---------|------|
| **没有主体就没有目标** | 谁都没确定，谈不上要做什么 |
| **没有目标就没有规则** | 不知道要做什么，谈不上要守什么规矩 |
| **没有规则就没有协作** | 没规矩的协作是混乱，不是业务 |
| **没有协作就没有时序** | 不与他人交互的事，没有"先后"的语义 |
| **没有时序就没有资源** | 没有时间锚点，资源状态变化无法追踪 |
| **没有资源就没有信息** | 信息是资源的状态和变化的记录 |

> **分析顺序原则**：按依赖关系的从上游到下游顺序分析。先分析主体，再分析目标，以此类推。

#### 1.1.3.3 可证伪条件

> **借鉴自新方法论Q1的可证伪性**：本框架在以下情况下失效。

本框架在以下情况下失效（说明系统不属于本框架的分析范围）：

1. **业务无法识别任何主体**（例如纯自动化的数据处理系统，无人参与）
2. **业务无法识别任何时序**（例如纯瞬时反应系统，无时间维度）
3. **业务无法识别任何规则**（例如纯创意类工作，无约束）
4. **业务的7个要素无法穷尽其所有事实**（必须能穷尽）

如果遇到上述情况，本框架**明确不适用**，应使用其他分析框架。

> **关键原则**：7要素缺一不可。任何业务都可以拆解为这7个要素的具体取值。

#### 1.1.3.4 业务概念与技术对象的分类契约

> **强制原则**：代码中出现的类、接口、表、字段和方法，首先是技术证据，不是业务概念。必须先分类，再翻译为业务语义；禁止由类名、DTO字段或枚举值直接推断实体、聚合根或完整状态机。

**对象分类**：

| 分类 | 判定条件 | 常见例子 | 是否可直接作为业务实体 |
|------|----------|----------|------------------------|
| **业务实体** | 有业务身份、生命周期，且其变化具有业务意义 | 订单、支付单、退款单 | 是，须有证据 |
| **值对象** | 无独立业务身份，以整体值描述业务特征 | 金额、渠道信息、时间范围 | 否 |
| **命令/请求** | 表达“希望执行什么动作” | PayRequest、CancelRequest | 否 |
| **结果/视图/事件** | 表达处理结果、查询结果或已发生事实 | PayResponse、PaymentSucceeded | 否，事件需单独建模 |
| **应用/领域服务** | 编排用例或承载跨实体规则 | PayCancelService | 否 |
| **技术组件** | 处理传输、路由、持久化、并发或框架生命周期 | Handler、Selector、Mapper、Lock、Interceptor | 否 |

**实体判定必须同时回答**：

1. 业务身份是什么，是否与技术主键区分？
2. 何时创建、何时结束，生命周期由谁控制？
3. 哪些业务动作会读取或改变它？
4. 哪些状态变化可以由代码、数据、文档或访谈证明？
5. 它与其他概念的数量、一致性和时序关系是什么？

无法回答时只能列为“实体候选”或“待确认概念”，不得列为确定实体或聚合根。

**证据与结论分层**：

| 层级 | 含义 | 最低证据要求 | 允许的表述 |
|------|------|--------------|------------|
| **L1 代码事实** | 可定位且无歧义的代码行为或对象存在 | 文件、类/方法、行号或可重复搜索 | “代码中存在/调用/写入” |
| **L2 代码推断** | 由多个事实组合得出的实现结论 | 完整调用链、分支或数据流 | “推断为，待跨路径验证” |
| **L3 业务语义** | 对代码事实的业务解释 | 代码 + 文档/访谈中的至少一项语义依据 | “业务上可能表示” |
| **L4 业务推断** | 未被业务来源确认的假设 | 明确假设、反例和待确认问题 | “假设/待确认” |
| **L5 未知项** | 当前证据不足或来源冲突 | 记录已尝试的验证方式 | “无法确认，不得补写结论” |

“高置信度”不能只表示代码存在；实体、关系、规则和状态转换必须分别记录证据层级、来源、反例和待确认项。

#### 1.1.4 分析方法

##### 方法1：代码逆向分析

**适用场景**：有源代码的遗留系统

**代码分析模式清单**：

| 模式 | 识别特征 | 提取方法 |
|------|---------|---------|
| **Entity类** | `@Entity`、`@Document`、`@Data`、`继承BaseEntity` | 类名 → 业务概念名 |
| **Domain类** | `Domain`、`Aggregate`、`Root`关键词 | 聚合根识别 |
| **Service类** | `Service`、`Manager`、`Handler` | 方法名 → 业务动词 |
| **Repository类** | `Repository`、`Dao`、`Mapper` | 接口方法 → 数据操作 |
| **Controller类** | `Controller`、`Api`、`RestController` | URL路径 → 业务功能 |

**方法名→业务动词映射表**：

| 方法名模式 | 业务含义 | 示例 |
|-----------|---------|------|
| `create*` | 创建 | `createOrder` → 创建订单 |
| `update*` | 更新 | `updateStatus` → 更新状态 |
| `delete*` | 删除 | `deleteMember` → 删除会员 |
| `process*` | 处理 | `processPayment` → 处理支付 |
| `check*` | 校验 | `checkInventory` → 校验库存 |
| `apply*` | 应用 | `applyDiscount` → 应用折扣 |
| `confirm*` | 确认 | `confirmOrder` → 确认订单 |
| `cancel*` | 取消 | `cancelReservation` → 取消预订 |
| `calculate*` | 计算 | `calculatePrice` → 计算价格 |
| `generate*` | 生成 | `generateReport` → 生成报表 |

**代码逆向分析详细步骤**：

1. **第一步：识别核心实体类**
   - 查找所有带有 `@Entity`、`@Table`、`@Document` 注解的类
   - 查找继承自 `BaseEntity`、`DomainObject` 的类
   - 查找以 `Entity`、`DO`、`Domain` 结尾的类
   - 输出：实体类清单 + 表名/集合名

2. **第二步：提取业务方法**
   - 扫描所有 Service/Manager 类
   - 识别业务动词方法名（create/update/process/apply/confirm/cancel等）
   - 分析方法签名：参数 → 输入概念，返回值 → 输出概念
   - 输出：业务方法清单 + 输入输出概念

3. **第三步：重构业务规则**
   - 在业务方法内部查找条件判断 `if/else/switch`
   - 提取判断条件中的业务规则
   - 查找常量定义位置的规则
   - 输出：业务规则清单

4. **第四步：还原业务流程**
   - 追踪方法调用链（从Controller到Service到Repository）
   - 识别状态字段的取值和转换逻辑
   - 识别事件发布/订阅（如果有）
   - 输出：业务流程图 + 状态机

5. **第五步：识别业务组合效应**
   - 识别多个方法调用的组合场景
   - 分析组合后的涌现行为（非线性效果）
   - 识别潜在的规则冲突点
   - 输出：组合效应清单

> **关键原则**：代码反推只能得到实现层面的概念，必须经过业务术语翻译。例如：`OrderDO` → `订单`（数据对象 → 业务实体）

##### 方法2：数据库逆向分析

**适用场景**：有数据库的遗留系统

**步骤：**

1. **表结构分析**
   - 识别核心表（业务主表、事务表）
   - 分析表关系（外键、一对一、一对多、多对多）

2. **字段语义分析**
   - 从字段名推断业务含义
   - 分析字段类型、长度、约束（NOT NULL、默认值）

3. **数据语义分析**
   - 抽样查看数据，理解字段取值含义
   - 识别状态字段的枚举值及其业务含义

4. **业务规则推断**
   - 从唯一约束推断业务规则
   - 从触发器、存储过程中提取业务规则

##### 方法3：文档与访谈

**适用场景**：有历史文档或可访谈业务人员

**步骤：**

1. **收集文档**
   - 需求文档、用户手册、运维手册
   - 会议纪要、变更记录

2. **结构化访谈**
   - 核心问题清单（见下表）

| 问题类型 | 示例问题 |
|---------|---------|
| 主体 | "谁会使用这个系统？有哪些角色？" |
| 目标 | "用户使用这个系统想达成什么？" |
| 规则 | "做这件事有什么硬性要求？" |
| 协作 | "这件事需要哪些角色配合？" |
| 时序 | "这件事有时间要求吗？什么时候可以做？" |
| 资源 | "操作哪些对象？对象的状态如何变化？" |
| 信息 | "传递哪些数据？数据的来源和去向是什么？" |

3. **三角验证**
   - 对同一业务问题，访谈多个来源
   - 代码、文档、访谈三者交叉验证

##### 方法4：业务对象分析方法（静态建模）

> **目的**：从7要素提取的静态概念，进一步深入到对象的完整建模。

**分析维度清单**：

| 序号 | 维度 | 必须填 | 适用对象 | 说明 |
|------|------|-------|---------|------|
| 1 | 属性/字段 | ✓ | 业务概念/实体/值对象 | 业务属性；命令、结果和技术组件只记录相关输入输出 |
| 2 | 方法/操作 | △ | 业务实体、领域服务、应用服务 | 记录已证实的业务动作；不能把 Service 方法自动归为实体方法 |
| 3 | 事件/状态变化 | △ | 有状态实体、领域事件 | 有状态对象必须分析状态变化；没有事件机制时明确记录“未发现” |
| 4 | 关系/关联 | ✓ | 业务概念 | 关系类型、数量、一致性/时序和证据 |
| 5 | 生命周期 | ✓ | 实体、聚合、领域事件 | 创建、使用、结束边界；非生命周期对象标记“不适用” |
| 6 | 状态机 | △ | 有状态实体/流程 | 只有存在状态证据时填写；枚举值本身不能替代状态转换证据 |
| 7 | 不变式/约束 | ✓ | 实体、聚合、业务规则 | 记录业务约束；无法确认时标记未知，不得虚构 |
| 8 | 类型判定 | ✓ | 全部候选对象 | 实体/值对象/命令/结果/事件/服务/技术组件 |
| 9 | 聚合边界 | △ | 聚合候选 | 必须有不变式、生命周期和事务边界证据 |
| 10 | 权限/可见性 | △ | 涉及授权的概念/用例 | 只有发现权限约束时填写，否则记录未分析或不适用 |
| 11 | 并发控制 | △ | 涉及并发的实体/用例 | 区分业务并发不变式与锁等技术实现 |
| 12 | 持久化策略 | △ | 持久化对象 | 记录表、字段、读写路径；不能由类名推断 |
| 13 | 缓存策略 | △ | 发现缓存证据的对象 | 没有缓存证据时标记未发现，不作为业务实体判定条件 |
| 14 | 版本/历史 | △ | 有审计/版本需求的对象 | 记录历史来源和保留要求 |

> **说明**：✓ = 对适用对象必须填，△ = 发现适用证据时必须填；“不适用”“未发现”“未知”必须写明原因，不能留空。

**与7要素的对应关系**：

| 7要素 | 对象分析维度 | 说明 |
|-------|-------------|------|
| 资源 | 属性/字段 | 对象持有的数据 |
| 主体 | 权限/可见性 | 谁可以操作对象 |
| 目标 | 方法/操作 | 对象能做什么 |
| 规则 | 不变式/约束 | 对象必须遵守的规则 |
| 协作 | 关系/关联 | 对象之间的关系 |
| 时序 | 生命周期、状态机 | 对象的时间维度 |
| 信息 | 事件/状态变化 | 对象发布的事件 |

**类型判定标准**：

| 类型 | 判定标准 | 示例 |
|------|---------|------|
| 实体 | 有业务身份和生命周期，状态变化具有业务意义 | Order, Member |
| 值对象 | 无独立业务身份，按整体值比较，通常不可变 | Money, Address |
| 聚合根 | 聚合内唯一对外身份、控制内部对象生命周期并维护聚合不变式的实体 | Order（可能包含OrderDetail）|

> **纠正**：聚合根不是“实体的子集”或“请求入口”，而是实体的一种角色。是否为聚合根必须由身份、生命周期、不变式、引用方式和事务边界的证据共同判定。

**对象分析方法执行步骤**：

1. **识别候选对象**：从代码、数据库、接口、文档和访谈识别对象，并先按对象分类契约归类。
2. **建立实体识别卡**：为每个核心实体记录业务身份、技术标识、生命周期、读写动作、状态和证据。
3. **类型判定**：判断实体、值对象、命令、结果/事件、服务或技术组件，无法确认的标为候选或未知。
4. **分析关系**：分别记录归属、引用、生命周期、数量、一致性和时序关系，不把服务调用图当作实体关系图。
5. **聚合划分**：根据不变式维护者、生命周期控制者和事务边界识别聚合根；没有证据不得强行划分。
6. **绘制分离模型**：至少分别输出业务实体关系图、用例调用链、业务信息流和状态转换图。

**实体关系记录格式**：

| 关系双方 | 关系类型 | 数量 | 一致性/时序 | 证据 | 确定性 | 待确认问题 |
|---------|---------|------|-------------|------|--------|------------|
| 概念A → 概念B | 归属/引用/生命周期/流程/技术 | 1:1、1:N或未知 | 同事务/异步/未知 | 文件:行号、表、接口或访谈 | L1-L5 | 问题 |

> `A调用B` 只能证明调用关系，不能直接证明 `A是B的实体`、`A拥有B` 或 `A与B在同一聚合`。

##### 方法5：业务逻辑分析方法（动态建模）

> **目的**：分析业务的动态行为，回答"业务是怎么运作的"。

**分析维度清单**：

| 序号 | 维度 | 必须填 | 说明 |
|------|------|-------|------|
| 1 | 业务流程分析 | ✓ | 主流程、分支、异常、补偿 |
| 2 | 业务规则分析 | ✓ | 显性规则、隐性规则、规则依赖 |
| 3 | 决策分析 | ✓ | 决策点、决策条件、决策分支 |
| 4 | 场景分析 | ✓ | 正常、边界、异常、特殊场景 |
| 5 | 协作分析 | ✓ | 同步、异步、事件驱动 |
| 6 | 异常处理 | ✓ | 异常类型、捕获、恢复；没有异常分支也必须记录“未发现” |
| 7 | 补偿/回滚 | ✓ | 补偿链、幂等性、超时处理；无补偿机制时必须记录缺口和风险 |
| 8 | 权限控制 | △ | 权限点、校验、绕过风险；不适用时说明原因 |

**决策分析示例**：

```markdown
## 优惠决策矩阵

| 用户等级 | 消费金额 | 可用优惠 |
|---------|---------|---------|
| 普通 | <100 | 无 |
| 普通 | 100-500 | 满100减10 |
| 普通 | >500 | 满100减15 |
| 银卡 | 任意 | 额外9.5折 |
| 金卡 | 任意 | 额外9折 |

决策规则：
- 优先级：会员折扣 > 满减优惠
- 互斥：优惠券与折扣二选一
```

**场景矩阵示例**：

```markdown
## 退款场景矩阵

| 场景 | 订单状态 | 可退金额 | 手续费 | 处理方式 |
|------|----------|----------|--------|----------|
| 正常 | 已结账 | 100% | 0% | 原路返回 |
| 部分 | 已结账 | 按商品 | 0% | 原路返回 |
| 超时 | 已结账7天后 | 90% | 10% | 退至账户 |
| 风控 | 已结账 | 待定 | - | 人工审核 |
```

**补偿事务分析示例**：

```markdown
## 订单取消补偿链

1. 释放库存（补偿：恢复库存）
2. 返还优惠（补偿：重新发放）
3. 退款支付（补偿：追款）
4. 发送通知（无补偿）

补偿原则：
- 按逆序执行
- 补偿失败告警
- 补偿次数限制（3次）
- 补偿幂等保证
```

**业务逻辑分析方法执行步骤**：

1. **用例清单化**：从所有已识别入口、Handler、接口、任务、消息和批处理动作建立用例清单；P0上下文不得用“核心场景”替代未分析入口。
2. **逐用例追踪**：从入口追踪到应用服务、领域对象、仓储/数据库、外部系统和事件，记录每一步的输入、输出和副作用。
3. **决策点识别**：识别流程中的判断节点，并为每个分支记录条件、执行者、状态变化、外部调用、事件和返回结果。
4. **场景枚举**：至少覆盖正常、边界、拒绝、失败、超时、重复、并发、未知结果和恢复/补偿场景；“未找到实现”也必须作为缺口记录。
5. **规则提取**：只把业务目的和业务约束写成业务规则；锁、拦截器、重试框架等先记录为技术机制，再说明它们实现或未实现的业务约束。
6. **状态机验证**：枚举值只能证明状态存在，不能证明状态转换。每条转换必须关联实际写入/校验路径、触发用例、前置条件、后置条件和失败分支。
7. **补偿与幂等分析**：识别跨系统副作用、重复请求、超时和部分成功场景，记录补偿动作、幂等键、重试边界和无法补偿的风险。

**每个用例的最低产出**：

```markdown
## 用例：<业务动作>
- 入口与触发者：
- 输入与前置条件：
- 涉及实体/值对象：
- 主流程：
- 决策分支及每个分支的副作用：
- 状态变化及证据：
- 异常、超时、重复和未知结果：
- 补偿、幂等和重试：
- 后置条件与对外结果：
- 代码/数据/文档/访谈证据：
- 未确认项：
```

#### 1.1.5 产出标准

**业务概念模型**：

| 属性 | 说明 |
|------|------|
| **概念名称** | 业务术语；技术名称只能作为候选别名 |
| **概念类型** | 实体 / 值对象 / 命令 / 结果 / 领域事件 / 服务 / 技术组件 |
| **业务身份** | 业务标识及其与技术主键的区别 |
| **定义** | 一句话说明这个概念是什么 |
| **生命周期** | 创建、使用、结束的边界和控制者 |
| **状态** | 已确认的状态值；未确认的状态不能补写 |
| **关系** | 关系类型、数量、一致性/时序和证据；不能只写1:1、1:N |
| **证据与确定性** | 代码事实、代码推断、业务语义、业务推断或未知 |
| **待确认项** | 证据不足、来源冲突和下一步验证方式 |

**业务规则清单**：

| 属性 | 说明 |
|------|------|
| **规则编号** | 全部分析文档共享的唯一编号 |
| **规则类型** | 业务不变式 / 准入 / 决策 / 状态 / 幂等 / 并发 / 异常 / 补偿；技术机制单独标注 |
| **规则表述** | 用“触发条件—判断—动作—结果”表述，不把实现手段当规则 |
| **触发用例/事件** | 哪个业务动作或事件触发 |
| **关联实体/状态** | 受影响的概念和状态变化 |
| **正向与负向结果** | 成功、拒绝、失败、超时、重复和未知结果 |
| **证据来源** | 代码文件/类/方法/行号、数据、文档、访谈；至少能追溯一种来源 |
| **确定性层级** | L1-L5；必须与证据强度一致 |
| **待确认项** | 尚未证实的假设、冲突和验证方式 |

> **规则与技术机制分离**：例如“同一支付对象不得被并发重复处理”是业务约束；“使用 LockUtil.lock(billNo)”是实现证据。两者必须分别记录。

**隐性规则置信度分级**：

| 置信度 | 定义 | 风险 | 处理方式 |
|--------|------|------|---------|
| **高** | 代码、文档、访谈三者一致 | 低 | 可直接采用 |
| **中** | 两个来源一致 | 中 | 需进一步验证 |
| **低** | 仅单一来源或推断 | 高 | 需多源验证或标记待确认 |

> **置信度使用原则**：
> - 置信度低的规则在设计阶段需要特别标注
> - 置信度低的区域是后续业务访谈的重点
> - 验收阶段必须对低置信度规则进行业务确认

#### 1.1.5 规则依赖图

> **借鉴自新方法论L2的规则依赖分析**：规则之间不是孤立的，而是有依赖关系的。

**规则依赖类型**：

| 依赖类型 | 含义 | 示例 |
|---------|------|------|
| **强依赖** | 规则A必须先于规则B校验 | "满100元才能用券"强依赖"订单总价计算" |
| **弱依赖** | 规则A和规则B都校验，但顺序无关 | "退款必须在7天内"和"退款必须填原因" |
| **互斥依赖** | 规则A和规则B不能同时成立 | "满减券与折扣互斥" |
| **条件依赖** | 规则A在某条件下依赖规则B | "会员卡余额支付"条件依赖"会员卡余额充足" |

**规则依赖图示例**：

```
R002 满100元可用券 ──强依赖──→ R001 订单总价计算
R003 满减券与折扣互斥 ──互斥依赖──→ 折扣规则
R004 会员卡余额支付不能超过订单总价 ──强依赖──→ R001 + 会员卡余额查询
```

**规则依赖图的作用**：

| 作用 | 说明 |
|------|------|
| **执行顺序推导** | 只有有代码或运行证据的强依赖才能推导执行顺序；接口/拦截器先后不等于业务规则强依赖 |
| **冲突检测** | 互斥依赖规则在同一业务对象和场景下不能同时生效；未生成互斥矩阵时必须标记“待检测”，不能写“无冲突” |
| **影响范围分析** | 修改一条规则时，必须找出所有依赖它的规则、用例、实体和外部副作用 |
| **缺口暴露** | 规则没有实现、实现位置未知或来源冲突时，必须形成缺口，不得用推断补齐 |

**规则依赖的建模边界**：

- 参数必填、认证和拦截器属于准入/技术处理；除非证据表明它决定了业务规则顺序，否则不能作为业务强依赖的根节点。
- 加锁、事务、重试和日志是技术机制；它们只有在能证明对应业务不变式时，才作为规则的实现证据。
- 规则依赖图必须区分业务依赖、状态依赖、数据依赖、技术前置和未知关系，并在边上标注证据。
- 状态枚举只证明状态存在；状态转换必须追踪实际写入、校验、事件或外部回调路径。

**规则冲突解原则**：

| 方法 | 适用场景 |
|------|---------|
| **优先级法** | 给规则设优先级，高优先级覆盖低优先级 |
| **互斥矩阵法** | 列出所有规则的两两互斥关系 |
| **规则分层法** | 把规则分成"通用层+特殊层"，特殊层覆盖通用层 |

### 1.2 业务抽象（Business Abstraction）

#### 1.2.1 目标

从具体的业务实现中，归纳出通用的业务模式：
- 识别重复的业务模式
- 提取业务变体的抽象基类
- 构建可复用的业务组件模型

#### 1.2.2 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | 业务理解阶段的产出（概念模型、规则清单、流程图） |
| **输出** | 业务模式清单、业务组件模型、抽象层级定义 |

#### 1.2.3 抽象的层次（业务升华的前置）

> 本节描述从具体到抽象的层次，帮助理解1.2业务抽象和1.3业务升华的关系。

业务抽象分为3个递进层次：

```
层次3：通用领域模式（Cross-Domain Patterns）
  └─ 跨行业的通用模式
  └─ 示例：订单处理模式、支付模式、客户管理模式

层次2：行业通用模型（Industry Patterns）
  └─ 同行业的通用模式
  └─ 示例：零售行业模型、餐饮行业模型、金融行业模型

层次1：具体业务实现（Concrete Implementation）
  └─ 具体的业务逻辑实现
  └─ 示例：某餐厅的POS点餐系统
```

**层次关系**：

- 1.2业务抽象：从层次1到层次2
- 1.3业务升华：从层次2到层次3

#### 1.2.4 分析方法

##### 方法1：模式识别

**步骤：**

1. **列举所有业务场景**
   - 列出业务规则清单中的所有场景
   - 列出业务流程图中的所有路径

2. **寻找重复模式**
   - 识别相似的业务流程
   - 识别相似的规则结构
   - 识别相似的数据结构

3. **提取抽象模式**
   - 将重复的具体实现抽象为模式
   - 定义模式的接口/契约
   - 识别模式的变化点

**模式识别检查表：**

| 检查项 | 问题 |
|-------|------|
| 流程模式 | 是否有多个流程遵循相似的结构？ |
| 规则模式 | 是否有多个规则遵循相似的条件结构？ |
| 数据模式 | 是否有多个实体遵循相似的结构？ |
| 协作模式 | 是否有多个协作遵循相似的交互结构？ |

##### 方法2：变体抽象

**步骤：**

1. **识别业务变体**
   - 识别规则清单中的条件分支
   - 识别流程图中的条件路径

2. **分析变体维度**
   - 是什么导致变体？（场景/时段/角色/地区）
   - 变体之间有什么共同点？

3. **构建抽象模型**
   - 定义变体的抽象基类
   - 定义变体维度的配置化方案
   - 识别哪些变体应该配置化，哪些应该代码化

**变体抽象决策表：**

| 变体特征 | 推荐方案 |
|---------|---------|
| 变体值固定不变 | 枚举硬编码 |
| 变体值可能增加 | 配置化 + 枚举兜底 |
| 变体逻辑复杂 | 策略模式 + 工厂模式 |
| 变体需要运行时切换 | 规则引擎 |
| 变体需要外部系统提供 | 适配器模式 |

##### 方法3：组件边界划分

**步骤：**

1. **识别内聚性**
   - 高内聚：同一组件内的业务概念是否紧密相关？
   - 低内聚：是否有关注点混杂？

2. **识别耦合性**
   - 直接耦合：组件之间是否直接引用？
   - 间接耦合：组件之间是否通过接口交互？

3. **划分限界上下文**
   - 根据业务内聚性划分上下文边界
   - 定义上下文之间的接口契约

**限界上下文划分原则：**

| 原则 | 说明 |
|------|------|
| **语义内聚** | 同一上下文内的概念有统一的业务语义 |
| **自主演化** | 每个上下文可以独立演进 |
| **明确边界** | 跨上下文交互有明确的接口定义 |
| **最小耦合** | 上下文之间的依赖关系最少化 |

#### 1.2.5 产出标准

**业务模式清单**：

| 属性 | 说明 |
|------|------|
| **模式名称** | 模式的标准名称 |
| **模式类型** | 流程模式 / 规则模式 / 数据模式 / 协作模式 |
| **抽象层次** | 层次1（具体）/ 层次2（行业通用）/ 层次3（通用模式）|
| **模式描述** | 模式的核心逻辑 |
| **适用场景** | 哪些业务可以用这个模式 |
| **变体点** | 模式的可变部分 |

#### 1.2.5.1 组合效应分析

> 组合效应是遗留系统复杂性的重要来源：当多个规则、流程、组件叠加时，整体行为往往不是部分之和。

**组合效应的类型**：

| 类型 | 定义 | 示例 | 风险 |
|------|------|------|------|
| **规则叠加** | 多条规则同时作用于同一对象 | 优惠券+折扣+积分同时生效 | 金额计算错误 |
| **流程交叉** | 多个业务流程共享资源 | 点餐流程和结账流程共享桌台 | 状态冲突 |
| **状态连锁** | 一个状态变化触发多个状态变化 | 订单取消 → 库存释放 → 积分扣减 → 通知发送 | 事务不一致 |
| **事件风暴** | 一个事件触发多个处理逻辑 | 支付成功 → 更新订单 → 发货 → 通知 → 统计 | 性能瓶颈 |

**组合效应分析步骤**：

1. **识别核心业务场景组合（基于帕累托法则）**
   - 识别占据80%业务量的20%核心场景组合
   - 识别高频触发的场景组合（如点餐+结账）
   > **说明**：枚举"所有"组合在实践中不可行，采用核心场景优先策略

2. **分析组合后的涌现行为**
   - 组合后的行为是否等于各部分之和？
   - 是否存在非线性效果（放大或缩小）？

3. **识别冲突点和一致性问题**
   - 规则之间是否存在冲突？
   - 数据是否可能不一致？

4. **制定冲突解决策略**
   - 优先级策略（高优先级规则覆盖低优先级）
   - 互斥策略（某些规则不能同时生效）
   - 累加策略（规则效果叠加）

**组合爆炸的应对策略**：

| 策略 | 适用场景 | 方法 |
|------|---------|------|
| **分层分析** | 复杂系统 | 按限界上下文分别分析，再分析跨上下文组合 |
| **场景优先级** | 资源有限 | 先分析高频场景，延后低频场景 |
| **异常优先** | 已知问题 | 先分析已知异常场景，再分析正常场景 |
| **规则引擎** | 规则复杂 | 用规则引擎管理组合逻辑，便于分析 |

#### 1.2.5.2 7要素与DDD概念的映射

> 7要素是分析维度，DDD概念是建模结果，两者不是一一对应，而是多对多关系。

| 7要素 | DDD概念 | 映射关系 |
|-------|---------|---------|
| 主体 | 聚合根、领域事件发布者 | 主体是DDD聚合根的主要来源 |
| 资源 | 实体、聚合 | 资源是有生命周期和唯一标识的业务对象 |
| 信息 | 值对象、领域事件 | 信息是描述性、不可变的业务数据 |
| 规则 | 领域服务、规约 | 规则是独立于实体的业务约束 |
| 协作 | 应用服务、限界上下文交互 | 协作是跨上下文或跨服务的交互 |
| 时序 | 状态机、领域事件时序 | 时序由状态转换和事件序列表达 |

**业务组件模型**：

| 属性 | 说明 |
|------|------|
| **组件名称** | 组件的业务名称 |
| **组件职责** | 组件负责什么业务 |
| **依赖组件** | 依赖哪些其他组件 |
| **暴露接口** | 向外部暴露什么接口 |
| **内部实现** | 如何实现（抽象程度） |

### 1.3 业务升华（Business Generalization）

#### 1.3.1 目标

将业务模型从特定领域**跨行业泛化**到通用领域：
- 构建跨行业的通用业务模型
- 提取业务的核心本质（去除行业特征）
- 建立业务的元模型（最抽象的表达）

> **与1.2业务抽象的区别**：
> - 业务抽象：从"具体实现"到"行业通用模型"（同行业跨系统）
> - 业务升华：从"行业通用模型"到"跨行业通用模型/元模型"（跨行业）

#### 1.3.2 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | 业务抽象阶段的产出（层次2：行业通用模型） |
| **输出** | 层次3：跨行业通用模型、业务元模型、领域特定语言（DSL） |

#### 1.3.3 升华的层次

```
具体业务系统（层次1的产出）
    ↓ 抽象（1.2业务抽象）
行业通用模型（层次2）
    ├─ 零售行业模型（零售POS、电商ERP）
    ├─ 餐饮行业模型（快餐POS、餐饮ERP）
    └─ 金融行业模型（银行核心、保险核心）
    ↓ 升华（1.3业务升华）
跨行业通用模型（层次3）
    ├─ 订单管理通用模型（所有行业）
    ├─ 客户管理通用模型（所有行业）
    ├─ 支付结算通用模型（所有行业）
    └─ 报表统计通用模型（所有行业）
    ↓ 升华（1.3业务升华的终极目标）
业务元模型（最抽象的表达）
    └─ 主体、目标、规则、协作、时序、资源、信息
```

#### 1.3.4 分析方法

##### 方法1：本质提取

**步骤：**

1. **去除行业特征**
   - 去掉业务术语中的行业特定词汇
   - 用通用词汇替换

2. **识别核心要素**
   - 什么是一切业务都有的？（主体、目标、规则、协作）
   - 什么是特定业务特有的？

3. **构建元模型**
   - 定义最抽象的业务概念
   - 定义概念之间的关系

**本质提取示例：**

| 特定业务 | 抽象后 |
|---------|-------|
| POS餐饮"点餐" | "下单" |
| 电商"购物车" | "订单暂存" |
| 银行"开户" | "注册" |
| 医疗"挂号" | "预约" |

##### 方法2：模式泛化

**步骤：**

1. **跨业务域对比**
   - 对比不同业务域的同一类型模式
   - 识别模式的核心共性

2. **构建通用模式**
   - 定义模式的通用接口
   - 为特定实现留出扩展点

**模式泛化示例：**

| 特定模式 | 通用模式 |
|---------|---------|
| 餐饮"菜品分类" | 商品分类 |
| 电商"商品SKU" | 商品规格 |
| 银行"账户类型" | 实体类型 |
| 通用名称 | **实体分类体系** |

##### 方法3：DSL设计

**步骤：**

1. **识别业务语言**
   - 从业务术语中提取DSL词汇
   - 定义DSL的语法结构

2. **定义DSL语义**
   - 为DSL词汇赋予语义
   - 定义DSL的求值规则

3. **构建DSL引擎**
   - 实现DSL解析器
   - 实现DSL执行器

**DSL设计示例：**

```
业务规则DSL示例：
RULE "满100减10" 
  WHEN order.total >= 100
  THEN order.discount = 10
  APPLY_TO POS_RESTAURANT

RULE "满200免运费"
  WHEN order.total >= 200 AND order.type = "DELIVERY"
  THEN order.shipping_fee = 0
  APPLY_TO ECOMMERCE
```

#### 1.3.5 产出标准

**通用业务模型**：

| 属性 | 说明 |
|------|------|
| **模型名称** | 跨行业的通用模型名称 |
| **核心概念** | 模型包含的核心概念 |
| **通用规则** | 所有业务域都适用的规则 |
| **扩展点** | 特定业务域可以扩展的部分 |

**业务元模型**：

| 属性 | 说明 |
|------|------|
| **元概念** | 最抽象的业务概念定义 |
| **元关系** | 概念之间的最抽象关系 |
| **元约束** | 所有业务必须满足的约束 |
| **实例化规则** | 如何从元模型派生出具体模型 |

## 2. 评价层

### 2.1 可扩展性评价（Extensibility Evaluation）

#### 2.1.1 目标

评价业务规则的扩展性，即：
- 当业务需求变化时，规则能否快速适应？
- 新增规则是否需要修改现有代码？
- 扩展是否引入系统不稳定性？

#### 2.1.2 扩展性维度

| 维度 | 定义 | 评价指标 |
|------|------|---------|
| **规则扩展性** | 新增业务规则的成本 | 代码改动量、测试范围 |
| **概念扩展性** | 新增业务概念的成本 | 数据模型改动、接口改动 |
| **流程扩展性** | 新增业务流程的成本 | 流程编排改动、状态机改动 |
| **集成扩展性** | 新增外部系统的成本 | 适配器开发量、接口兼容性 |
| **安全扩展性** | 新增安全策略的成本 | 安全组件解耦程度、策略可配置性 |

> **安全扩展性说明**：遗留系统往往安全策略硬编码，新增安全需求（如GDPR、数据脱敏）需要大量改动。评价时需关注安全组件是否独立、安全策略是否可配置。

#### 2.1.2.1 安全分析方法（遗留系统专项）

> 遗留系统的安全性分析是改造前的重要环节，以下提供系统性的安全分析方法。

**安全分析维度**：

| 维度 | 分析内容 | 分析方法 |
|------|---------|---------|
| **认证安全** | 用户身份认证机制 | 代码审计、渗透测试 |
| **授权安全** | 权限控制机制 | 权限矩阵分析、越权测试 |
| **数据安全** | 敏感数据保护 | 数据分类、加密审计 |
| **传输安全** | 数据传输加密 | 协议分析、证书审计 |
| **审计安全** | 操作日志记录 | 日志完整性分析 |
| **合规安全** | 法规合规性 | 对标检查（GDPR/等保）|

**安全分析执行步骤**：

1. **安全需求收集**
   - 收集安全合规要求（等保、GDPR等）
   - 收集业务安全需求（敏感数据保护等）
   - 收集历史安全事件

2. **安全现状分析**
   - 代码安全审计（SQL注入、XSS等）
   - 认证授权机制分析
   - 数据加密情况审计

3. **安全风险评估**
   - 识别安全漏洞
   - 评估风险等级
   - 制定整改计划

**安全风险评估矩阵**：

| 风险等级 | 定义 | 整改时限 | 改造要求 |
|---------|------|---------|---------|
| **严重** | 可导致数据泄露或系统瘫痪 | 立即整改 | P0，改造前置条件 |
| **高** | 可导致业务受损 | 1个月内 | P1，Phase1必须解决 |
| **中** | 可能被利用 | 3个月内 | P2，Phase2必须解决 |
| **低** | 风险可控 | 6个月内 | P3，延期处理 |

#### 2.1.3 扩展性评估方法

##### 方法1：变化点分析

**步骤：**

1. **识别业务变化点**
   - 从业务抽象阶段识别所有可能的变化维度
   - 分析每个变化点的变化频率预期

2. **评估当前实现**
   - 现有实现是否预留了扩展点？
   - 扩展是否需要修改核心代码？

3. **计算扩展成本**
   - 估算每种扩展需要的改动量
   - 评估扩展对系统稳定性的影响

**变化点评估表：**

| 变化点 | 变化频率 | 当前扩展成本 | 目标扩展成本 | 差距 |
|-------|---------|-------------|-------------|------|
| 新增支付渠道 | 高 | 高（改核心代码）| 低（配置化）| 大 |
| 新增会员等级 | 中 | 中（改数据库）| 低（配置化）| 中 |
| 新增促销规则 | 极高 | 高（改代码）| 低（规则引擎）| 大 |

##### 方法2：扩展性评分

**评分标准（五星制）**：

| 评分 | 条件（必须全部满足） |
|------|---------------------|
| ★★★★★ | ① 新增规则无需修改代码，只需配置；② 配置项有类型校验；③ 配置生效无需重启 |
| ★★★★ | ① 新增规则只需改少量代码(<10%)；② 有扩展点预留；③ 扩展不影响现有功能 |
| ★★★ | ① 新增规则需要改中等量代码(10-30%)；② 需要测试相关模块；③ 扩展有一定风险 |
| ★★ | ① 新增规则需要改大量代码(30-50%)；② 需要回归测试；③ 扩展风险较高 |
| ★ | ① 任何扩展都需要重构代码(>50%)；② 扩展可能导致系统不稳定；③ 无扩展点预留 |

**客观判定方法**：

| 评估指标 | 量化方法 |
|---------|---------|
| 代码改动量 | 新增功能导致的代码改动行数 / 系统总代码行数 |
| 测试范围 | 需要回归测试的模块数 / 总模块数 |
| 扩展点数量 | 预留的扩展点数量 / 理论需要的扩展点数量 |
| 配置化率 | 可配置项数量 / 总业务参数数量 |

**评估维度权重：**

| 维度 | 权重 | 理由 |
|------|------|------|
| 规则扩展性 | 30% | 业务规则是系统最频繁变化的部分 |
| 概念扩展性 | 25% | 数据模型变化成本高 |
| 流程扩展性 | 25% | 业务流程变化频率高 |
| 集成扩展性 | 20% | 外部集成变化相对少 |

**扩展性总分计算公式**：

```
总分 = (规则扩展性×0.3 + 概念扩展性×0.25 + 流程扩展性×0.25 + 集成扩展性×0.2) × 20

例：四维度分别为 ★★★★、★★★、★★★★、★★
总分 = (4×0.3 + 3×0.25 + 4×0.25 + 2×0.2) × 20 = 3.35 × 20 = 67分（百分制）
```

##### 方法3：扩展性反模式识别

| 反模式 | 表现 | 修复建议 |
|-------|------|---------|
| **硬编码魔法值** | 业务规则中的数值/字符串硬编码 | 配置化 |
| **条件分支爆炸** | if-else/switch 嵌套过深 | 策略模式/规则引擎 |
| **重复代码** | 相似逻辑多处实现 | 抽象为公共方法 |
| **循环依赖** | 模块之间相互依赖 | 依赖倒置/中介者 |
| **上帝类** | 一个类承担过多职责 | 拆分为多个类 |
| **过拟合** | 过度适配当前需求 | 延迟设计/预留扩展点 |

#### 2.1.4 产出标准

**扩展性评估报告**：

| 属性 | 说明 |
|------|------|
| **评估对象** | 被评估的业务模块/组件 |
| **各维度评分** | 规则/概念/流程/集成扩展性评分 |
| **总分** | 加权总分 |
| **主要瓶颈** | 扩展性最差的方面 |
| **改进建议** | 如何提升扩展性 |

### 2.2 适应性评价（Adaptability Evaluation）

#### 2.2.1 目标

评价业务规则的适应性，即：
- 同一套规则能否适应不同的业务场景？
- 规则能否通过配置适应不同的客户/租户？
- 规则能否适应不同的运行环境？

#### 2.2.2 适应性维度

| 维度 | 定义 | 评价指标 |
|------|------|---------|
| **场景适应性** | 规则能否适应不同业务场景 | 配置化程度、参数化程度 |
| **多租户适应性** | 规则能否适应不同租户 | 租户隔离、租户配置 |
| **多环境适应性** | 规则能否适应不同环境 | 环境配置、外部依赖抽象 |
| **多语言适应性** | 规则能否支持多语言 | i18n支持、文字配置化 |

#### 2.2.3 适应性评估方法

##### 方法1：配置化程度评估

**评估步骤：**

1. **枚举所有业务常量**
   - 从代码中提取所有硬编码的值
   - 区分技术常量和业务常量

2. **评估配置化可行性**
   - 每个常量是否可以配置化？
   - 配置化的性能/复杂度代价是什么？

3. **计算配置化率**
   - 配置化率 = 可配置项 / 总业务常量

**配置化评估表：**

| 常量类型 | 示例 | 配置化难度 | 建议 |
|---------|------|----------|------|
| 业务规则参数 | 满减门槛100元 | 低 | 必须配置化 |
| 业务规则逻辑 | 满减计算方式 | 中 | 优先配置化 |
| 业务术语 | 菜品/商品/货品 | 高 | 按需配置化 |
| 技术参数 | 超时时间30s | 低 | 应该配置化 |

##### 方法2：多租户适应性评估

**评估步骤：**

1. **识别租户相关字段**
   - 代码中是否所有数据都有租户标识？
   - 租户隔离是否完整？

2. **评估租户配置能力**
   - 租户能否自定义业务规则？
   - 租户规则是否与平台规则冲突？

3. **评估租户隔离性**
   - 数据隔离是否完整？
   - 配置隔离是否完整？

**多租户适应性评分：**

| 评分 | 标准 |
|------|------|
| ★★★★★ | 完全多租户，所有规则可租户级配置 |
| ★★★★ | 主要规则可配置，核心规则平台统一 |
| ★★★ | 部分规则可配置，但配置能力有限 |
| ★★ | 租户隔离较弱，存在数据泄露风险 |
| ★ | 不支持多租户 |

##### 方法3：适应性反模式识别

| 反模式 | 表现 | 修复建议 |
|-------|------|---------|
| **硬编码租户ID** | 代码中直接判断租户类型 | 租户配置化 |
| **环境假设** | 假设特定的运行环境 | 环境抽象 |
| **单语言硬编码** | 所有文字硬编码在代码中 | i18n框架 |
| **时区硬编码** | 假设特定的时区 | 时区抽象 |
| **货币硬编码** | 只支持单一货币 | 多币种支持 |
| **业务场景耦合** | 特定业务场景与代码强耦合 | 业务场景抽象 |

#### 2.2.4 产出标准

**适应性评估报告**：

| 属性 | 说明 |
|------|------|
| **评估对象** | 被评估的业务模块/组件 |
| **配置化率** | 可配置项占比 |
| **租户适应性** | 多租户支持程度 |
| **环境适应性** | 多环境支持程度 |
| **主要瓶颈** | 适应性最差的方面 |
| **改进建议** | 如何提升适应性 |

## 3. 设计层

### 3.1 架构设计（Architecture Design）

#### 3.1.1 目标

基于分析层和评价层的产出，设计新的系统架构：
- 采用先进的架构模式
- 解决评价中发现的扩展性和适应性问题
- 确保架构能够支撑未来的业务演进

#### 3.1.2 设计原则

| 原则 | 含义 | 应用 |
|------|------|------|
| **领域驱动设计** | 以业务领域为核心组织系统 | 限界上下文划分 |
| **六边形架构** | 业务逻辑与外部依赖解耦 | 端口与适配器设计 |
| **CQRS** | 命令与查询分离 | 读写分离设计 |
| **事件驱动** | 通过事件解耦和异步通信 | 领域事件设计 |
| **整洁架构** | 依赖方向从外向内 | 分层架构设计 |
| **微服务** | 独立部署和演进的服务 | 服务边界划分 |

#### 3.1.3 设计步骤

##### 步骤1：从业务模型到限界上下文

**映射规则：**

| 业务模型要素 | 限界上下文映射 |
|-------------|---------------|
| 高内聚业务概念 | 一个限界上下文 |
| 低内聚业务概念 | 多个限界上下文 |
| 跨上下文业务流程 | 上下文间交互 |

##### 步骤2：从业务规则到策略模式/规则引擎

**映射规则：**

| 规则特征 | 设计模式 |
|---------|---------|
| 规则逻辑简单，值可配置 | 配置化 + 工厂模式 |
| 规则逻辑复杂但固定 | 策略模式 |
| 规则逻辑需要动态组合 | 规则引擎 |
| 规则需要运行时切换 | 策略模式 + 配置中心 |

##### 步骤3：从业务流程到状态机/流程引擎

**映射规则：**

| 流程特征 | 技术方案 |
|---------|---------|
| 状态机明确，状态有限 | 状态模式 + 状态机框架 |
| 流程可变，需要可视化编排 | 流程引擎（BPMN）|
| 流程需要补偿/回滚 | SAGA模式 |
| 流程需要异步执行 | 消息队列 + 状态机 |

##### 步骤4：从可扩展性评价到架构决策

| 扩展性问题 | 架构决策 | 实施方法 |
|-----------|---------|---------|
| 硬编码魔法值 | 引入配置中心 | Apollo/Nacos + 配置刷新 |
| 条件分支爆炸 | 引入策略模式或规则引擎 | 策略工厂 + 规则引擎（如Drools）|
| 循环依赖 | 引入依赖倒置或中介者 | 接口抽象 + 事件解耦 |
| 上帝类 | 拆分为多个微服务或领域对象 | 按职责拆分 + 职责链模式 |
| 过拟合 | 预留扩展点，延迟设计 | 插件机制 + 扩展点接口 |

#### 3.1.4 可观测性与CI/CD设计

> 遗留系统改造过程中和改造完成后，可观测性和持续交付是运维的关键支撑。

**可观测性三要素**：

| 要素 | 说明 | 实施工具 |
|------|------|---------|
| **日志（Logging）** | 记录系统运行事件 | ELK/Loki |
| **监控（Metrics）** | 采集系统性能指标 | Prometheus/Grafana |
| **追踪（Tracing）** | 追踪请求全链路 | Jaeger/Zipkin |

**CI/CD策略**：

| 阶段 | 重点 | 工具 |
|------|------|------|
| 开发 | 单元测试、代码质量 | SonarQube |
| 集成 | 接口测试、集成测试 | Postman |
| 部署 | 蓝绿/灰度发布 | ArgoCD |
| 监控 | 线上验证 | Prometheus |

#### 3.1.5 架构设计模式映射

> 以下提供具体的设计模式选择指南，基于业务特征选择合适的架构模式。

**业务特征 → 设计模式映射表**：

| 业务特征 | 推荐设计模式 | 理由 |
|---------|-------------|------|
| 规则频繁变化 | 规则引擎 | 规则与代码解耦 |
| 状态转换复杂 | 状态机框架 | 状态转换可视化、减少错误 |
| 多支付渠道 | 策略模式 + 适配器 | 新渠道新增策略，不改核心 |
| 多租户隔离 | 租户字段隔离 + 配置隔离 | 数据层隔离，配置层按需 |
| 异步处理 | 消息队列 + 事件驱动 | 解耦、提升性能 |
| 补偿事务 | SAGA模式 | 分布式事务的替代方案 |
| 读写分离 | CQRS | 读模型和写模型分离优化 |

#### 3.1.6 ROI分析与阶段性价值交付

> 遗留系统改造是大额投入，必须回答"值不值"和"怎么交付价值"两个问题。

##### ROI分析框架

**改造收益量化**：

| 收益类型 | 量化方法 | 单位 |
|---------|---------|------|
| **运维成本降低** | 故障率下降 × 平均故障损失 | 万元/年 |
| **开发效率提升** | 新功能开发时间减少 × 人力成本 | 万元/年 |
| **业务损失避免** | 避免系统崩溃导致的业务损失 | 万元/年 |
| **技术风险降低** | 避免技术债务利息 × 债务总额 | 万元/年 |
| **业务创新能力** | 新功能带来的收入增长 | 万元/年 |

**改造投入量化**：

| 投入类型 | 量化方法 | 单位 |
|---------|---------|------|
| **直接人力成本** | 团队人数 × 改造周期 × 人均成本 | 万元 |
| **基础设施成本** | 新架构基础设施投入 | 万元 |
| **培训成本** | 团队学习新技术的成本 | 万元 |
| **过渡期成本** | 双轨运营期的额外成本 | 万元 |
| **风险成本** | 改造失败的可能性 × 损失 | 万元 |

**ROI公式**：

```
ROI = (年度总收益 - 年度总成本) / 总投入 × 100%

例：
- 年度总收益 = 200万（运维+效率+风险避免）
- 年度总成本 = 50万（基础设施+培训）
- 总投入 = 500万（人力成本）
- ROI = (200 - 50) / 500 × 100% = 30%
```

> 改造周期长，必须在过程中持续交付业务价值，让利益相关方看到进展。

| 自动化测试覆盖 | 回归测试时间减少80% |

**Phase 3：全面迁移（第7-12个月）**

### 3.2 改造策略（Transformation Strategy）

#### 3.2.1 目标

制定从老系统到新系统的改造策略：
- 确定改造的优先级和顺序
- 选择合适的改造模式
- 确保业务连续性

#### 3.2.2 改造模式

| 模式 | 适用场景 | 风险 | 成本 |
|------|---------|------|------|
| **Big Bang（一次切换）** | 小型系统、业务可停机 | 高 | 低 |
| **Strangler Fig（绞杀者）** | 大型系统、需要平滑迁移 | 中 | 中 |
| **Parallel Run（双轨并行）** | 关键业务、需要充分验证 | 低 | 高 |
| **Feature Toggle（功能开关）** | 新旧功能需要渐进切换 | 低 | 中 |
| **抽象锚点** | 需要逐步替换内部实现 | 中 | 中 |

#### 3.2.3 改造策略制定步骤

##### 步骤1：改造范围分析

基于评价阶段的产出：

## 4. 验证层（Validation）

### 4.0 验证层概述

> 验证层是确保改造质量的关键环节，包含三重验证和两轮评审。

**验证层结构**：

```
验证层
├── 4.1 覆盖度验证（功能/规则/数据三重验证）
├── 4.2 质量验证（分析质量/架构质量/重构质量）
├── 4.3 安全验证（安全分析/安全整改/安全确认）
├── 4.4 性能验证（性能基线/性能测试/性能验收）
└── 4.5 验收交付（交付检查/签字验收/问题关闭）
```

### 4.1 覆盖度验证（Coverage Validation）

#### 4.1.1 目标

验证新系统是否完整覆盖了老系统的全部业务：
- 功能覆盖度
- 数据覆盖度
- 规则覆盖度

#### 4.1.2 验证方法

##### 方法1：功能清单对比

**步骤：**

1. **生成老系统功能清单**
   - 从分析阶段产出功能清单
   - 每个功能标注优先级

2. **生成新系统功能清单**
   - 从设计阶段产出功能清单
   - 每个功能标注实现状态

3. **对比分析**
   - 标记覆盖的功能
   - 标记未覆盖的功能
   - 标记新增的功能

**功能覆盖度矩阵：**

| 功能ID | 功能名称 | 老系统 | 新系统 | 覆盖状态 | 优先级 |
|-------|---------|-------|-------|---------|--------|
| F001 | 用户登录 | ✓ | ✓ | 已覆盖 | P0 |
| F002 | 订单创建 | ✓ | ✓ | 已覆盖 | P0 |
| F003 | 会员积分 | ✓ | - | 未覆盖 | P1 |

**覆盖率 = 已覆盖功能数 / 老系统功能总数 × 100%**

##### 方法2：业务规则对比

**步骤：**

1. **生成老系统规则清单**
   - 从分析阶段产出规则清单
   - 每个规则标注重要程度

2. **生成新系统规则清单**
   - 从设计阶段产出规则清单
   - 每个规则标注实现方式

3. **对比分析**
   - 标记完全一致的规则
   - 标记语义一致但实现不同的规则
   - 标记不一致的规则

**规则覆盖度矩阵：**

| 规则ID | 规则描述 | 老系统 | 新系统 | 一致性 |
|-------|---------|-------|-------|--------|
| R001 | 满100可用券 | ✓ | ✓ | 完全一致 |
| R002 | 会员9折 | ✓ | ✓ | 完全一致 |
| R003 | 退款7天 | ✓ | ✓ | 语义一致 |

**覆盖率 = 语义一致规则数 / 老系统规则总数 × 100%**

##### 方法3：数据覆盖度验证

**步骤：**

1. **对比数据结构**
   - 老系统表结构 vs 新系统表结构
   - 字段语义是否一致

2. **对比数据迁移**
   - 验证数据迁移脚本
   - 抽样验证迁移结果

3. **对比查询结果**
   - 相同查询条件，老系统和新系统结果是否一致

**数据覆盖度报告：**

| 检查项 | 状态 | 说明 |
|-------|------|------|
| 表结构对比 | ✓ | 全部字段映射完成 |
| 字段语义对比 | ✓ | 语义一致 |
| 数据迁移验证 | ✓ | 抽样一致率99.9% |
| 查询结果对比 | ✓ | 核心查询一致 |

#### 4.1.3 产出标准

**覆盖度验证报告**：

| 指标 | 值 | 标准 |
|------|---|------|
| 功能覆盖度 | 98% | ≥95% |
| 规则覆盖度 | 100% | =100% |

| 整体评估 | 通过 | 全部达标 |

### 5.4 分析质量验证

#### 5.4.1 业务提炼的质量保证

> **核心问题**：如何保证业务提炼的完整性？

**业务提炼的完整性判定标准**：

| 判定维度 | 判定方法 | 通过标准 |
|---------|---------|---------|
| **主体覆盖** | 对比系统用户角色与实际使用者 | 覆盖 ≥ 90% |
| **规则覆盖** | 代码路径覆盖率 | 覆盖率 ≥ 95% |
| **流程覆盖** | 核心业务流程图完整性 | 核心流程100%覆盖 |
| **边界覆盖** | 限界上下文边界清晰度 | 无模糊边界 |
| **隐性规则发现** | 异常案例分析法 | 发现率 ≥ 80% |

**隐性规则发现率提升方法**：

| 方法 | 适用场景 | 提升效果 |
|------|---------|---------|
| 异常案例收集 | 有工单/故障记录的系统 | +20%发现率 |
| 资深员工访谈 | 有经验丰富的员工 | +30%发现率 |
| 对比竞品 | 有竞品可参考 | +15%发现率 |
| 跨部门访谈 | 涉及多部门的业务 | +25%发现率 |

> **关键认知**：业务提炼的"完整"是相对概念，不是绝对概念。实践中的策略是：追求高覆盖率达到业务可接受阈值，而非追求100%覆盖。

#### 5.4.2 业务归纳的正确性验证

> **核心问题**：如何验证归纳结果的正确性？

**归纳正确性的验证方法**：

| 验证方法 | 说明 | 适用场景 |
|---------|------|---------|
| **反推法** | 从归纳结果反推，看能否推导出原始业务现象 | 模式归纳 |
| **边界法** | 验证归纳结果在边界情况下是否仍然成立 | 规则归纳 |
| **对比法** | 多个人独立归纳，对比结果一致性 | 复杂业务 |
| **反例法** | 主动寻找归纳结果的反例 | 假设归纳 |

**归纳一致性评分**：

```
一致性 = 相同结论数 / 总结论数 × 100%

评分标准：
- ≥90%：归纳结果可信
- 70-90%：需要进一步验证
- <70%：归纳方法有问题，需要重新分析
```

**归纳的置信度分级**：

| 置信度 | 判定依据 | 风险等级 |
|--------|---------|---------|
| **高** | 多证据支持 + 反推验证通过 | 低 |
| **中** | 单证据支持 + 边界验证通过 | 中 |
| **低** | 推断得出 + 无验证 | 高 |

> **关键认知**：业务归纳没有"绝对正确"，只有"高置信度"。目标是提高置信度，而非追求绝对正确。

#### 5.4.3 设计先进性的保证

> **核心问题**：如何保证设计是"先进"的？

**先进性的定义标准**：

| 维度 | 定义 | 衡量指标 |
|------|------|---------|
| **业务适配性** | 设计与业务需求的匹配度 | 需求覆盖率、变更成本 |
| **技术领先性** | 采用的技术栈是否当代先进 | 技术栈评级、版本新度 |
| **架构优雅性** | 架构的简洁性和可维护性 | 圈复杂度、耦合度 |
| **扩展便利性** | 应对未来变化的成本 | 扩展点数量、配置化率 |
| **团队适配性** | 团队能力与技术的匹配度 | 学习曲线、技术储备 |

**先进性评估矩阵**：

| 技术/模式 | 业务适配性 | 技术领先性 | 架构优雅性 | 扩展便利性 | 团队适配性 | 综合得分 |
|-----------|-----------|-----------|-----------|-----------|-----------|---------|
| 单体架构 | ★★★★★ | ★★ | ★★★ | ★ | ★★★★★ | 3.0 |
| 模块化单体 | ★★★★★ | ★★★ | ★★★★ | ★★ | ★★★★ | 3.6 |
| 微服务 | ★★★ | ★★★★★ | ★★★★ | ★★★★★ | ★★★ | 4.0 |
| 六边形架构 | ★★★★★ | ★★★★ | ★★★★★ | ★★★★★ | ★★★ | 4.4 |
| CQRS | ★★★★ | ★★★★ | ★★★★ | ★★★★★ | ★★ | 3.8 |
| 事件驱动 | ★★★★ | ★★★★★ | ★★★★ | ★★★★★ | ★★ | 3.8 |

> **先进性选择原则**：
> 1. **业务适配性优先**：先进技术不适合业务 = 落后
> 2. **团队适配性底线**：团队驾驭不了 = 风险
> 3. **综合得分最大化**：选择综合得分最高的方案

**架构决策框架**：

```
                    ┌─────────────────────────┐
                    │     业务需求约束        │
                    │   （功能、性能、成本）    │
                    └───────────┬─────────────┘
                                │
                                ▼
        ┌───────────────────────────────────────┐
        │        技术选型评估                    │
        │  ┌─────────────────────────────────┐ │
        │  │ 1. 业务适配性（必须 ≥ 4★）       │ │
        │  │ 2. 综合得分（必须排名前3）       │ │
        │  │ 3. 团队适配性（必须可培养）      │ │
        │  └─────────────────────────────────┘ │
        └───────────────┬───────────────────────┘
                        │
                        ▼
        ┌───────────────────────────────────────┐
        │        架构决策记录（ADR）              │
        │  记录选择依据、替代方案、未选原因       │
        └───────────────────────────────────────┘
```

#### 5.4.4 重构先进性的保证

> **核心问题**：如何保证重构是"先进"的？

**重构质量评价体系**：

| 评价维度 | 评价指标 | 目标值 |
|---------|---------|-------|
| **业务保真度** | 功能覆盖度 | ≥99% |
| **业务保真度** | 规则一致性 | =100% |
| **业务保真度** | 数据完整性 | ≥99.9% |
| **架构质量** | 圈复杂度下降 | ≥30% |
| **架构质量** | 耦合度下降 | ≥40% |
| **架构质量** | 扩展点增加 | ≥50% |
| **交付效率** | 交付周期缩短 | ≥30% |
| **交付效率** | 缺陷密度下降 | ≥50% |
| **风险控制** | 线上故障数 | 0 |
| **风险控制** | 回滚次数 | 0 |

**重构成熟度模型**：

| 成熟度等级 | 特征 | 适用场景 |
|-----------|------|---------|
| **L1：基础级** | 有测试用例，有文档，有code review | 小型重构 |
| **L2：规范级** | 有CI/CD，有自动化测试，有代码规范 | 中型重构 |
| **L3：量化级** | 有质量度量，有性能基线，有监控告警 | 大型重构 |
| **L4：卓越级** | 有A/B测试，有灰度发布，有快速回滚 | 核心系统重构 |

**重构前的必做检查项**：

| 检查项 | 检查方法 | 通过标准 |
|-------|---------|---------|
| 业务覆盖分析 | 功能清单对比 | ≥99% |
| 回归测试用例 | 测试用例覆盖率 | ≥80% |
| 数据迁移验证 | 数据一致性校验 | 100%一致 |
| 应急预案 | 回滚方案评审 | 通过 |
| 风险评估 | 风险矩阵分析 | 风险可接受 |

**重构过程中的质量保障**：

| 阶段 | 质量保障活动 |
|------|-------------|
| 开发阶段 | 单元测试、代码审查、持续集成 |
| 测试阶段 | 自动化回归、对比测试、压力测试 |
| 部署阶段 | 灰度发布、监控告警、快速回滚 |
| 验收阶段 | 业务验收、数据核对、用户确认 |

> **重构先进性的本质**：不是技术多先进，而是"用更小的风险、达成更好的架构质量"。先进性 = 风险可控 + 质量提升 + 效率提高

#### 5.4.5 分析质量综合验证

**分析完整性的检验标准**：

| 检验项 | 检验方法 | 通过标准 |
|-------|---------|---------|
| **用例完整性** | 入口、Handler、接口、任务、消息与用例清单对照 | P0入口覆盖率 = 100%；每个入口都有正常、拒绝、失败或未知结果说明 |
| **实体完整性** | 候选对象与实体识别卡对照 | 每个核心实体都有业务身份、生命周期、读写动作和证据；技术对象不得冒充实体 |
| **关系完整性** | 关系矩阵与调用链、表结构、事件对照 | 核心关系都有关系类型、数量、一致性/时序、证据；未知关系不能默认为已确认 |
| **状态完整性** | 状态值与实际写入、校验、回调路径对照 | 每条核心状态转换都有触发用例、前后置条件、执行者、失败分支和证据 |
| **规则完整性** | 从用例决策点、分支和副作用反查规则 | P0规则证据覆盖率 = 100%；覆盖正常、拒绝、失败、超时、重复、并发、未知和补偿缺口 |
| **双向可追溯性** | 规则→用例/实体/代码，代码路径→规则/用例 | P0结论全部可双向追踪；每个未确认项都有验证计划 |
| **术语一致性** | 同一术语在不同文档中逐项对照 | 规则编号、实体名称、状态名称和跨文档引用无冲突 |
| **依赖完整性** | 限界上下文、业务依赖、技术依赖分别检查 | 无未声明的跨上下文调用；业务依赖与技术依赖不能混画 |

**不可用作单独通过条件的指标**：对象数量、每个对象固定属性数量、每个对象固定方法数量、每个聚合根固定事件数量、星级或百分比估算。没有分子、分母、样本范围和证据位置的评分只能作为待评估项，不能作为验收结论。

**分析失败的识别信号**：

| 信号类型 | 具体表现 | 可能原因 |
|---------|---------|---------|
| **概念跳跃** | 分析结论与代码实现差距大 | 分析浮于表面 |
| **规则遗漏** | 代码中有未记录的规则 | 逆向分析不彻底 |
| **术语混乱** | 同一概念有多种名称 | 没有统一术语表 |
| **流程缺失** | 代码路径在流程图中找不到 | 流程分析不完整 |
| **规则冲突** | 不同来源的规则相互矛盾 | 没有三角验证 |
| **置信度偏低** | 高置信度规则占比 < 50% | 分析深度不足 |

**分析质量评分公式**：

```
质量分 = (概念完整率×0.2 + 规则完整率×0.3 + 流程完整率×0.2 + 术语一致率×0.15 + 依赖完整率×0.15) × 100
```

**分析质量改进循环**：

```
分析执行 → 质量检验 → 问题识别 → 分析改进 → 再检验
     ↑                                              ↓
     └──────────────────────────────────────────────┘
```

**改进策略**：

| 质量问题 | 改进方法 |
|---------|---------|
| 概念跳跃 | 增加代码阅读深度，逐方法追踪 |
| 规则遗漏 | 补充业务访谈，重点关注异常场景 |
| 术语混乱 | 建立术语表，逐项对齐 |
| 流程缺失 | 补充状态机分析和事件追踪 |
| 规则冲突 | 多角色访谈，三角验证 |
| 置信度低 | 增加证据来源，提高验证轮次 |

#### 5.4.6 分析失败处理流程

> 当分析过程中发现问题时，按以下流程处理。

**分析失败的识别信号**：

| 信号类型 | 具体表现 | 可能原因 |
|---------|---------|---------|
| **概念跳跃** | 分析结论与代码实现差距大 | 分析浮于表面 |
| **规则遗漏** | 代码中有未记录的规则 | 逆向分析不彻底 |

| **置信度偏低** | 高置信度规则占比 < 50% | 分析深度不足 |

**分析失败处理流程**：

```
    │                     ▼

    ├─ P2（一般）
```

| P3 | 记录在案 | 无特殊要求 |

#### 5.4.7.5 恢复验证清单

**恢复验证清单**：

```
- 0.90-0.95：恢复质量良好
- 0.80-0.90：需要补充验证
- <0.80：需要重新分析
```

## 6. 与其他方法论的关系

### 6.1 与"业务维度卷"的关系

| 业务维度卷 | 本方法论 |
|-----------|---------|
| L1-L5分析层 | 对应第1阶段"分析层"，但本方法论更强调可扩展性/适应性评价 |
| 缺少评价维度 | 本方法论新增第2阶段"评价层" |
| 缺少设计指导 | 本方法论新增第3阶段"设计层" |
| 缺少验证方法 | 本方法论新增第4阶段"验证层" |

**关系**：本方法论是业务维度卷的**扩展和深化**，两者可以结合使用：
- 用业务维度卷做深度分析（L1-L5）
- 用本方法论做评价、设计和验证

### 6.2 与现有SOP的关系

| 现有SOP | 本方法论 |
|---------|---------|
| SOP-00业务系统分析SOP | 补充理论框架 |
