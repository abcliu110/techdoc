**一句话**：从业务场景和运行证据出发，用 DA0-DA8 螺旋流程重建可解释、可验证、可追溯的领域模型。

## 0. 定位与使用契约

### 0.1 文档定位

本文是 `SOP-00` 在已有系统领域理解方向上的专项 SOP，用于从业务场景和领域语义出发，结合页面、接口、数据、代码、配置、任务、消息与运行证据，重建足以解释系统行为的领域模型。

本文不替代其他专项 SOP：

| 需要深入的对象 | 路由文档 |
|---|---|
| 前端入口、页面状态、交互和请求链 | `SOP-01-前端整体分析.md` |
| 后端模块、事务、依赖和运行机制 | `SOP-02-后端整体分析.md` |
| 端到端流程、状态机、规则与不变量 | `SOP-03-核心业务流程分析.md` |
| 单个功能的端到端深挖 | `SOP-04-功能点深度分析.md` |
| API、消息、错误和兼容契约 | `SOP-05-前后端对接分析.md` |
| 数据语义、权威源、血缘与生命周期 | `SOP-06-数据模型分析.md` |
| 综合结论、风险和行动建议 | `SOP-07-综合评估与报告.md` |
| 候选架构与设计启发 | `SOP-08-架构与业务设计启发式评审.md` |
| 目标业务设计合理性 | `SOP-09-业务设计合理性评审.md` |
| 多实现归一、迁移与退役 | `SOP-10-业务演进多实现归一与重构迁移.md` |

### 0.2 适用与不适用

适用于：

- 接手、维护或重构前理解已有系统；
- 从分散实现中还原领域语言、业务规则和真实边界；
- 解释页面、接口、表、代码、消息和任务为何共同形成当前行为；
- 发现文档、设计意图、代码、配置、数据和运行行为之间的矛盾；
- 为兼容治理、架构评审、迁移或业务演进建立事实模型。

不适用于：

- 只需定位一个明确代码问题的窄范围排障；
- 没有既有实现、需要从零设计的新系统；
- 未经授权的生产写入、压测、故障注入、数据导出或外部副作用操作；
- 试图一次性穷举整个大型系统，而没有证据派生的分析问题、明确决策问题或关键业务切片。

### 0.3 分析目标

本 SOP 不以“列完功能、读完代码、画完 ER 图”为完成标准，而要回答：

1. 系统服务哪些角色，在什么上下文中完成什么业务结果？
2. 领域中有哪些核心概念，概念之间存在什么稳定关系？
3. 哪些规则、不变量和状态转换决定系统行为？
4. 这些语义分别由实体、值对象、聚合、策略、事件、流程或读模型承载？
5. 人、领域对象、服务和外部系统如何协作，失败后如何恢复？
6. 页面、接口、数据、代码和运行行为是否支持同一解释？
7. 哪些是事实、推断、假设、历史兼容或仍未解释的矛盾？

### 0.4 强制边界

- 继承 `SOP-00` 的 G0 任务书、证据类型、确定性、验证状态、安全和脱敏规则。
- 分析现状默认只读；任何有副作用的验证必须另行获得明确授权。
- `As-Is` 事实、设计意图、部署配置、运行行为和 `To-Be` 建议必须分开记录。
- 已有合法可观察行为默认视为兼容候选；未确认调用方和历史数据影响前，不得直接建议删除。
- 已确认的越权、跨作用域访问、注入、凭据泄露或资金完整性错误不因历史存在而成为必须保留的兼容基线。

### 0.5 双层交付契约

分析产物分为两个层次，不能用其中一层替代另一层：

| 层次 | 目标读者 | 主要内容 | 判断标准 |
|---|---|---|---|
| 理解层 | 接手者、业务人员、架构师和决策者 | 一句话本质、一页模型、真实业务切片、概念关系、状态、不变量、失败恢复和主要结论 | 不阅读源码也能建立正确的系统心智模型 |
| 复核层 | 开发、测试、运维、数据、安全和验证者 | 证据台账、MAP 矩阵、源码/配置/数据/运行定位、矛盾、未知项和复现步骤 | 能从结论定位原始证据，并从实现反查业务语义 |

理解层不得堆放大段源码来代替解释；复核层不得用概括性描述代替精确证据。二者通过稳定 ID 关联，不复制成两套互相漂移的事实。

认知重建默认必须形成独立的理解层主文档。DA0-DA8 是分析工作底稿和复核附件，不能代替按业务问题重新综合的读者文档；只有 DA0-DA8 时，任务不得宣告交付完成。

面向理解的内容必须支持四级压缩：

```text
一句话：系统的业务本质和核心张力
一页：角色、边界、核心概念关系、不变量、主切片和主要风险
十分钟：用一个真实切片解释如何工作、如何失败和如何恢复
完整报告：模型、证据、差异、未知项、方案和复验触发
```

## 1. 核心分析模型

### 1.1 核心命题

> 已有系统分析的本质，是从可观察行为和实现证据中，重建系统正在执行的业务决策、维护的业务事实、保护的不变量，以及这些语义形成当前边界的历史条件。

因此，系统不能只表示为“实体集合”，应表示为：

```text
系统理解 = 上下文与角色
         + 场景与业务结果
         + 概念及其关系
         + 规则、不变量与状态机
         + 领域模型元素与责任边界
         + 用例、事件与交互
         + 实现、数据与运行证据
         + 失败、恢复、兼容与演进约束
```

### 1.2 三条同时执行的分析方向

```text
正向语义链：业务目标 → 场景 → 概念/关系 → 规则/状态 → 模型 → 交互 → 实现

反向证据链：页面/API/表/代码/配置/任务/消息/运行数据
                                      → 行为 → 规则 → 状态 → 领域语义

失败反推链：异常结果 → 被破坏的不变量 → 错误状态/责任边界
                                    → 隐含规则 → 设计或实现缺口
```

三条链必须在同一业务切片上汇合。只走正向链会得到理想模型；只走反向链会得到实现清单；只看成功路径会遗漏真实边界。

### 1.3 五类事实不得混写

| 层次 | 说明 | 典型证据 |
|---|---|---|---|
| 业务认知 | 业务人员、用户或文档认为系统应如何工作 | `HUM`、`DOC` |
| 设计意图 | 架构、需求、ADR、注释表达的原始目的 | `DOC`、`SRC` |
| 实现能力 | 某版本代码理论上能够如何运行 | `SRC`、测试 |
| 部署与运行事实 | 特定环境、配置、数据和时间窗口内实际如何运行 | `CFG`、`DAT`、`RUN`、`CON` |
| 目标建议 | 分析后建议未来如何演进 | 决策记录，不是现状证据 |

当五者不一致时，建立矛盾项，不得选择最符合预期的一层覆盖其他层。

### 1.4 分析单位

默认分析单位是“业务切片”，不是页面、接口、类或表。

```text
业务切片 = 角色 + 触发条件 + 业务目标 + 主路径 + 异常路径
         + 规则/状态 + 数据变化 + 外部副作用 + 业务结果
```

页面、接口、类和表是业务切片在不同实现层的投影。只有贯穿至少一个切片，才能判断它们的业务含义。

每个 P0/P1 业务切片除场景卡、图和矩阵外，还必须形成一段因果叙事：

```text
谁在什么条件下发起什么业务意图；
为什么需要这个业务结果；
哪些事实、规则和状态决定结果；
哪些对象和权威数据发生变化；
产生哪些外部副作用；
在哪里确认成功、失败或结果未知；
重复、并发、超时和部分失败如何处理；
谁负责检测、补偿、对账或人工恢复。
```

只有调用链、时序箭头、表格或代码片段，没有上述因果解释，不得判为“业务切片已贯通”。

### 1.5 先判断分析对象的业务位置

在发现实体、状态或交互前，先判断分析对象在业务中的位置：

| 类型 | 判据 | 分析重点 |
|---|---|---|---|
| 核心业务域 | 拥有核心业务事实，并作出直接影响业务结果的决策 | 业务身份、规则、不变量、状态和权威数据 |
| 支撑业务能力 | 加工、传递、编排或执行其他领域已经形成的业务事实 | 上游事实、交付义务、时效、路由、失败和恢复 |
| 技术平台能力 | 向多个业务域提供通用技术机制，本身不解释上游业务事实 | 服务契约、隔离、容量、可用性和接入边界 |
| 混合类型 | 同时包含上述多类责任 | 按子边界分别建模，禁止用一个中心实体覆盖全部语义 |

定位必须回答：接收什么上游业务事实；该事实由谁权威解释；本对象自身拥有什么事实和规则；向谁交付什么结果；不负责决定什么；失败会破坏哪个业务结果。没有这些回答，不得直接以持久化对象或任务对象作为领域中心。

对于支撑能力，优先建立业务交付义务：

```text
上游业务事实 + 权威来源
  -> 需要交付的产物/结果
  -> 接收角色及其后续动作
  -> 有效时点与成功判据
  -> 遗漏/错误/重复/延迟/结果未知的业务后果
```

## 2. 建模语法

### 2.1 概念不等于实体

领域概念是业务语言中的语义单位；实体只是其中一种系统表达。

| 判断问题 | 候选表达 |
|---|---|
| 属性变化后，业务仍需识别为同一个对象？ | 实体 |
| 只由属性值定义相等性，可整体替换？ | 值对象 |
| 描述资格、额度、计算或决策？ | 规则、策略或决策表 |
| 描述生命周期和合法转换？ | 状态机 |
| 描述已经发生且值得传播或审计的事实？ | 领域事件或集成事件 |
| 协调多个对象、步骤或外部参与方？ | 应用用例、领域服务或流程管理器 |
| 只服务查询、报表或派生展示？ | 读模型、指标或投影 |
| 在声明范围和观察点必须持续成立？ | 不变量 |

持久化、数据库表、ORM、DTO 和页面控件是实现选择，不能反向作为实体判据。

### 2.2 概念关系是分析骨架

每条重要关系使用“主体—谓词—客体”表达，并补充基数、方向、条件、时间和权威来源。

| 关系类型 | 核心问题 | 示例 |
|---|---|---|---|
| 分类关系 | A 是否是 B 的一种？ | 会员客户 `is-a` 客户角色 |
| 构成关系 | A 是否是 B 的组成部分？生命周期是否从属？ | 订单项 `part-of` 订单 |
| 角色关系 | 同一主体在什么上下文扮演什么角色？ | 企业在采购域是供应商，在销售域是客户 |
| 责任关系 | 谁拥有修改权、裁决权或数据权威？ | 支付服务拥有支付结果 |
| 依赖关系 | A 成立或执行前依赖什么？ | 发货依赖可履约订单 |
| 决定关系 | 哪些输入、规则决定结果？ | 订单项和价格规则决定应付金额 |
| 时间/因果关系 | 什么先发生，什么由什么触发？ | 支付确认触发待履约状态 |
| 作用域关系 | 规则、身份或数据在哪个范围有效？ | 价格在门店和时间段内有效 |
| 映射关系 | 同一语义如何投影到实现？ | 订单状态映射字段、枚举、事件和页面标签 |

关系默认不具有对称性、传递性或反身性。查询可导航性、对象引用、数据库外键和业务关系是四个不同问题。

### 2.3 关系规格

```text
REL-{序号}
主体：
谓词：
客体：
业务含义：
方向与基数：
成立条件/失效条件：
时间语义：
权威来源与修改者：
关联规则/不变量/状态：
实现投影：
证据与适用范围：
反例/未知项：
```

### 2.4 规则、不变量和状态必须分开

| 对象 | 定义 | 示例 |
|---|---|---|---|
| 业务规则 `BR` | 在条件下允许、禁止、计算或触发某结果 | 大额订单需要审批 |
| 不变量 `INV` | 所有合法路径在声明观察点都必须保持的事实 | 已确认支付金额不得小于已入账金额 |
| 状态机 `SM` | 对象生命周期、合法状态及迁移条件 | 待支付 → 已支付 → 待履约 |
| 实现机制 | 保护规则、不变量或状态的技术手段 | 唯一约束、事务、锁、幂等键、对账 |

不得用技术机制代替业务定义，也不得把“代码里有校验”直接写成不变量已被完整保护。

### 2.5 交互不是实体互调清单

交互至少包含：

```text
发起者 + 目标 + 命令/查询/事件 + 前置条件 + 状态变化
      + 数据与副作用 + 一致性时限 + 超时/重复/乱序 + 恢复责任
```

同步/异步、编排/编舞、事务/补偿都是约束下的实现选择，不是天然优劣关系。

### 2.6 业务概念与实现术语隔离

以下对象默认属于实现投影，不得仅因名称重要就登记为业务概念：

- Controller、Service、Manager、Worker、Util、DTO、VO、Mapper；
- 数据库表、字段、缓存键、队列名和配置项；
- 框架枚举、异常类、设计模式和部署单元。

它们只有在能够回答“哪个角色为什么需要这个语义、它影响什么业务判断、与哪些概念存在什么关系”后，才能映射到 `BC/REL/DM`。无法上溯时登记为技术机制、历史遗留或 `U-*`，不得通过中文翻译把技术名词包装成领域概念。

## 3. 统一产物与追溯协议

### 3.1 稳定 ID

| 对象 | ID 前缀 | 最小内容 |
|---|---|---|---|
| 分析/决策问题 | `DQ-` | 来源证据、业务问题、重要性、状态和演进理由 |
| 业务切片 | `SC-` | 角色、触发、目标、主/异常路径、结果 |
| 业务概念 | `BC-` | 定义、上下文、边界、同义/歧义 |
| 概念关系 | `REL-` | 主体、谓词、客体、条件、证据 |
| 业务规则 | `BR-` | 条件、判断、结果、优先级、执行点 |
| 不变量 | `INV-` | 适用范围、观察点、破坏后果、保护机制 |
| 状态机 | `SM-` | 状态、迁移、守卫、终态、异常与恢复 |
| 领域模型元素 | `DM-` | 类型、身份、职责、边界、权威源 |
| 交互 | `IX-` | 参与方、契约、时序、失败与恢复 |
| 实现映射 | `MAP-` | 语义到页面/API/数据/代码/运行位置 |
| 实现谱系 | `IMPL-` | 同一业务能力的多入口、多版本、多历史实现；各自记录 REL/证据，归一并经 SOP-10 裁决前不合并 |
| 矛盾项 | `X-` | 冲突证据、适用版本、候选解释 |
| 未知项 | `U-` | 缺口、影响、补证动作、责任人 |
| 结论 | `C-` | 命题、证据、范围、确定性、反证 |

证据继续使用 `SOP-00` 的 `E-SRC/E-CFG/E-DAT/E-RUN/E-CON/E-DOC/E-HUM`。

### 3.2 端到端追溯主链

```text
原始目标 + G0-B 保留的分析/决策问题
  → SC 场景
  → BC 概念 + REL 关系
  → BR 规则 + INV 不变量 + SM 状态
  → DM 领域模型元素
  → IX 交互
  → MAP 实现与运行投影
  → 验证用例/监控/审计
  → C 结论、X 矛盾、U 未知项
```

双向检查：

- 从业务目标向下，应能定位承载行为的实现和验证证据；
- 从页面、接口、字段、类、消息或任务向上，应能解释其业务语义或明确标记为技术/历史遗留；
- 无法双向追溯的对象不能直接删除，应先登记为未知项或兼容候选。

### 3.3 证据真实性护栏

正式证据必须满足 `SOP-00` 的精确定位要求，并执行以下检查：

1. 文件、符号、接口、表、消息或配置确实存在于声明基线；
2. 行号或定位信息有效，引用内容与原始证据一致；
3. 枚举、状态、方法签名和字段取值不得凭经验补全；
4. 同一 ID 在任务内全局唯一，不在每份文档重新定义不同的 `E01`；
5. 代码能力、部署启用和运行事实分别记录，不能由源码直接跨越到运行结论；
6. 无法取得的证据进入 `U-*`，不得用伪代码、示例 JSON 或常见做法填补。

发现项目产物包含不存在的方法、越界行号、占位路径或与源码不符的枚举/状态时，立即停止结论收敛并转入文档 21 的 V6/V7 失败处理。

## 5. 分阶段执行

### 5.1 DA0：从原始目标到问题基线

**输入**：用户原始提示、`SOP-00` G0-A 启动契约、可访问证据和已有资料。认知重建不要求用户预先提供 DQ、领域概念或业务切片。

#### DA0-A：解析原始目标与安全边界

1. 保留用户原话，识别分析对象、证据范围、输出位置和任务模式。
2. 明确允许的只读动作、禁止动作、脱敏/留存要求和需要另行授权的动作。
3. 记录旧文档处理方式、范围内/外和当前未知边界。
4. 决策支持提取决策意图；变更实施提取需求、验收和授权。认知重建只需明确希望建立哪一对象的系统认知。

**产物**：G0-A 启动契约。满足认知重建最小输入后立即进入 DA0-B，不向用户索要只能由取证产生的问题清单。

#### DA0-B：有限只读证据侦察

侦察的目的不是完成全量分析，而是先建立业务广度，再找到边界和高信息量切片。分两步执行：

**第一步：业务结果族广度扫描。** 从用户入口、业务写入口、消息/任务、输出类型、配置和调用方中，按“相同业务结果或交付义务”聚类，形成候选全景：

| 业务结果族/能力 | 上游触发事实 | 交付物/输出 | 接收角色 | 成功义务 | 失败后果 | 入口证据 | 覆盖状态 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  | 候选/已覆盖/部分覆盖/未覆盖 |

**第二步：代表切片证据侦察。** 至少执行：

- 固定每个仓库的路径、分支、提交、工作区状态和适用项目入口规则；
- 检索用户可见入口、API/消息/任务、核心写入、状态/错误、配置开关和外部依赖；
- 识别跨仓库同名词、调用方向、生产者/消费者和可能的权威数据；
- 登记源码、契约、配置、文档和运行证据的可用性，不把缺失的部署/运行证据补写为事实；
- 只记录能精确定位的 `E-SRC/E-CON/E-CFG/E-DOC/...`，AI 经验只作为搜索启发。

侦察必须设置停止条件。最低停止条件是：候选业务结果族已经形成可解释的样本框；每个已发现的主要结果族至少有一个入口或输出证据；已发现一个用户/外部入口、一个业务写入口、一个结果状态、一个失败信号和一条跨边界链路；未覆盖结果族及影响已登记。达到条件即转入 DA0-C，禁止先遍历全部目录再思考业务问题，也禁止只发现一条链路就代表整个分析对象。

#### DA0-C：从证据派生候选 DQ

围绕侦察到的角色、触发、结果、状态、失败和恢复提出可被证据回答的问题：

| DQ | 来源证据 | 为什么重要 | 状态 |
|---|---|---|---|
| `DQ-*` | `E-SRC/E-CON/E-CFG/...` | 影响哪项系统理解、维护或后续决定 | 候选/保留/合并/已反证 |

候选 DQ 按以下顺序派生；前一层不能回答时，后一层技术问题不得成为主叙事：

1. `DQ-BIZ`：该能力为什么存在，支持什么业务结果？
2. `DQ-ACTOR`：谁发起，谁依赖结果继续工作？
3. `DQ-FACT`：什么业务事实被创建、判断、加工或交付，权威来源是谁？
4. `DQ-OBLIGATION`：向谁、何时、以什么产物或结果交付才算完成？
5. `DQ-RISK`：遗漏、错误、重复、延迟和结果未知分别造成什么业务后果？
6. `DQ-OWNERSHIP`：事实、规则、状态和恢复责任分别由谁拥有？
7. `DQ-MECHANISM`：系统通过什么模型、交互和技术机制实现以上义务？

候选 DQ 还应覆盖跨边界副作用如何一致和恢复，以及哪些实现差异可能代表业务变体或历史兼容。不得把“分析某目录/类/表”写成 DQ，也不得先以状态机、缓存、负载均衡、协议或框架问题替代业务问题。

#### DA0-D：候选业务切片

**重要约束**：所有候选业务切片都必须深度分析，不得选择性放弃。

从候选 DQ 反推能提供最高区分度的业务切片，按以下顺序评估分析优先级：

1. 能贯穿用户/外部角色、入口、核心决策、状态变化和业务结果；
2. 跨越多个仓库、服务或前后端边界，能解释主要概念关系；
3. 包含失败、重复、超时、并发或恢复信号；
4. 业务影响、不确定性和信息增益较高，同时可安全只读取证。

**全量分析原则**：所有候选切片都是分析范围内必须覆盖的内容，不存在"优先放弃"的选项。未选择区域必须登记为**未覆盖**并在后续补充分析。

#### DA0-E：建立可演进的分析问题基线

形成 G0-B：分析对象业务位置、业务结果族全景、初始角色/事件/结果、候选概念/关系、DQ 台账、首批切片、证据台账、U/X 台账和停止条件。维护以下追溯：

```text
用户原始目标
  -> DA0-B 证据侦察
  -> DA0-C 候选 DQ
  -> DA0-D 候选切片
  -> 后续 DA 阶段保留/合并/反证 DQ
  -> DA8 条件化结论
```

**退出条件**：G0-A 已通过；任务模式未被 AI 擅自升级；分析对象业务位置和候选结果族已建立；候选 DQ 有来源证据且先表达业务问题；首批切片能回答至少一个高信息量 DQ；未选结果族、范围、仓库基线、权限、证据缺口和停止条件已记录。认知重建无需决策负责人或风险接受人即可进入 DA1；需要正式建议、变更或风险接受时，再补齐相应负责人和授权。

### 5.2 DA1：业务切片与黑箱观察

先观察用户和外部系统看到的输入、输出和失败，不先用代码结构解释业务。

```text
SC-{序号} 场景卡
名称与业务目标：
角色与权限/作用域：
触发条件与前置事实：
上游业务事实及权威来源：
需交付的业务产物/结果：
接收角色及其后续动作：
有效时点与成功义务：
主路径：
边界/异常/撤销/补偿路径：
输入与业务结果：
遗漏/错误/重复/延迟/结果未知的业务后果：
本能力拥有/不拥有的事实：
资金、库存、权益或敏感数据影响：
成功、失败和结果未知的判据：
业务指标/审计：
证据、版本与覆盖缺口：
```

**必须覆盖**：至少一个正常样本、一个边界样本、一个失败或结果未知样本；高风险写操作还要覆盖重复、并发和超时重试。

**理解层输出**：为每个 P0/P1 切片写出完整因果叙事，并选择一个真实、可复核的样本，逐步说明每一步的业务目的、判断依据、状态变化、数据变化和失败后果。不得用方法逐行转述代替；删除类名、方法名、表名和接口名后叙事仍必须成立。

**正面示例（合格的业务因果叙事）**：
```text
用户提交订单并完成支付后，系统自动触发库存扣减流程。
→ 系统先根据订单类型确定需要扣减的库存项：商品 SKU、数量和仓库位置。
→ 系统检查各仓库的实时库存，如果库存不足则提示用户。
→ 库存扣减操作被记录到库存流水表，用于后续追溯和审计。
→ 扣减成功后，系统发布库存变更事件。
→ 事件订阅方（财务、报表、物流）异步接收事件并各自处理。
→ 如果主仓库扣减失败，系统自动切换到备用仓库；
   如果所有仓库都失败，订单进入异常队列，需人工处理。
```

**反面示例（不合格的实现转述）**：
```text
用户提交订单 → OrderController.submitOrder()
  → OrderService.submit()
    → ProductService.checkStock()
    → OrderMapper.insert()
    → InventoryService.decrease()
```
删除类名和方法名后，只剩"→ → → → →"，没有任何业务含义。
不得用这种"代码调用链"冒充因果叙事。

**退出条件**：关键切片的业务结果可判定，主路径和主要异常路径有证据，未覆盖范围已显式记录。

### 5.3 DA2：上下文与概念建模

**概念来源**：业务语言、页面任务、接口语义、状态值、规则、报表口径、数据库读写、代码命名、消息和运行记录。任何单一来源只能产生候选概念。

```text
BC-{序号} 概念卡
名称与一句话定义：
所属上下文：
业务价值与使用者：
包含/不包含：
身份或相等性判据：
生命周期：
同义词/近义词/歧义词：
与其他上下文的翻译：
证据与适用版本：
未知项：
```

**分析动作**：

- 合并同义词之前检查上下文、生命周期、规则、权限和权威源是否相同；
- 同名词在不同上下文含义不同时分别建模，通过翻译关系连接；
- 区分主体、角色、过程、结果、策略、计量和实现术语；
- 概念依赖其他概念不意味着它应降级为字段。

**退出条件**：关键场景使用的术语可判定，歧义有裁决或未知项，概念没有被数据库表名机械替代。

### 5.4 DA3：概念关系与责任建模

> **与 SOP-00 §9.5.4 的对齐（强制）**：DA3 模板由本节与 SOP-00 §9.5.4 共同构成，执行顺序为：
> 1. 先按 SOP-00 §9.5.4 识别**业务对象（BO-*）**——从业务对象出发，不从数据表出发（一个数据表可能承载多个业务对象）；
> 2. 再分析**关键业务路径（BP-*）**——必须至少包含 1 条 3 跳及以上的业务路径，含中间对象职责、"为什么经过中间对象"（至少 2 条业务原因）、级联行为；深度参照 SOP-00 §9.5.4a 合格范例；
> 3. 最后按本节 9 维契约展开每个核心 REL（维度清单见 §5.4.1：关系定义、建立与维护机制、字段连接、关联路径、约束条件、使用方式、修改影响、级联行为、实现证据）。

> **模板文件**：生成 DA3 文档时，以独立文件 `SOP-00-DA3-模板.md`（与 SOP-00 同目录）为准，并在 DA3 文档开头输出"模板加载记录"、末尾输出"模板字段对照表"（见 SOP-00 §0 执行前置第 1/3/6 条）。本节与 SOP-00 §9.5 全文内容仅作历史参考。

#### 5.4.0 事实关系分类框架（REL-*）

> **⚠️ 本节分类已废弃（v3.x 起）**：REL-CONTAIN/ATTRIBUTE/SEQUENCE/ROUTING 为旧版遗留分类，**不得在新产物中作为正式分类使用**（见 SOP-00 §3.10 禁止行为）。正式分类使用 SOP-00 §3.6 的 L1 三类关系（结构/轨迹/归因）。本节仅保留作历史参考，不再维护。

在开始逐项建模之前，先用REL-*框架对关系进行分类。事实实体（业务事件）之间的关系通常表现为**4种基础模式**：

| 关系模式 | 标识 | 语义描述 | 典型问句 |
|----------|------|----------|----------|
| 父子包含 | `REL-CONTAIN` | 上级实体"包含"下级实体，生命周期绑定 | "A 的生命周期是否包含在 B 内？" |
| 事务归因 | `REL-ATTRIBUTE` | 业务事件"指向"某个配置或维度 | "A 是否是 B 的执行实例或结果？" |
| 事务链 | `REL-SEQUENCE` | 同一业务主体上的操作序列 | "A 和 B 是否作用于同一主体？" |
| 资源分配 | `REL-ROUTING` | 资源或产品路由到多个目标 | "A 是否需要路由到多个 B？" |

**关系分类三步法**：

```
关系标定问句（按顺序尝试）：

1. "A 的生命周期是否包含在 B 内？"
   → 是 → REL-CONTAIN（包含关系）
   → 否 → 继续下一个问句

2. "A 是否是 B 的执行实例或结果？"
   → 是 → REL-ATTRIBUTE（归因关系）
   → 否 → 继续下一个问句

3. "A 和 B 是否作用于同一业务主体？"
   → 是 → REL-SEQUENCE（链式关系）
   → 否 → 继续下一个问句

4. "A 是否需要路由到多个 B？"
   → 是 → REL-ROUTING（分配关系）
   → 否 → 需要重新审视 A 和 B 的定义
```

**关系分析检查表**（每个核心REL必须完成）：

| 检查项 | 检查内容 | 标记符号 |
|---|---|---|---|
| 关系类型 | 属于哪种基础模式？ | REL-CONTAIN / REL-ATTRIBUTE / REL-SEQUENCE / REL-ROUTING |
| 基数 | 一端有多少实例？ | 1 或 N |
| 方向 | 谁指向谁？ | A → B 或 B → A |
| 建立时机 | 配置时还是运行时？ | 设计时 / 初始化 / 配置维护 / 交易执行 |
| 变更影响 | 修改后对历史数据的影响？ | 热生效 / 追溯历史 / 解绑处理 |
| 业务语义 | 一句话说明这个关系"是什么" | 纯业务语言，不含技术术语 |

**打印系统示例**：

```
事实识别：
- 创建打印任务（CreatePrintJob）
- 分发打印任务（DispatchPrintJob）
- 完成打印任务（CompletePrintJob）

              CreatePrintJob  DispatchPrintJob  CompletePrintJob
CreatePrintJob       —            REL-ATTR          REL-ATTR
DispatchPrintJob     —              —               REL-ATTR
CompletePrintJob     —              —                 —

关系解读：

- DispatchPrintJob → 打印机：任务"归因"到打印机配置（运行时建立）
```

对关键概念逐项提问：

1. 它由什么构成，是否共享生命周期？
2. 它依赖什么事实或规则才成立？
3. 谁创建、修改、确认、撤销和审计它？
4. 哪个系统或对象是权威源，其他位置是副本、快照还是投影？
5. 关系是否带角色、作用域、时间、版本或条件？
6. A→B→C 是否真的允许推出 A→C？

**必要产物**：关系规格（含完整关系契约格式）、概念关系图（含直接/间接路径）、责任/权威源矩阵。

基础资料之间的关系，经证据确认后可描述为**配置型静态关系**。“静态”表示关系实例通常作为业务交易的前置资料或配置被读取，而不是在每次交易中临时计算；它不表示不可修改。完整表达分为四层：

```text
业务关系定义：A 是否允许关联 B，角色、方向、基数、作用域和有效期是什么
关系实例维护：谁通过哪个 UI/API/导入入口执行绑定、换绑、解绑或停用
关系事实存储：关联字段、中间表或版本化配置在哪里，约束和权威源是什么
运行时使用：哪个业务动作在何时读取该关系，变更何时生效，历史对象是否沿用旧关系
```

因此不能只写“A 与 B 是 N:1”，也不能只写“在某页面设置”。前者缺少关系实例如何形成，后者缺少业务语义、服务端约束、数据落点和运行效果。

#### 5.4.1 关系契约格式（每个核心 REL 必须建卡）

下列维度必须逐项判定，但不要求每个关系都存在字段连接、UI、间接路径或级联。不存在或不适用时填写“无/不适用”，并附证据、理由和对关系结论的影响；证据不足时填写“证据不足”并登记 `U-*`，不得生成看似合理的字段、接口或业务原因。

```markdown
### REL-{序号}：{主体} ↔ {客体}

#### 关系定义
- **关系类型**：[构成/依赖/分配/路由/引用/同步/...]
- **业务含义**：这个关系解决什么业务问题？
- **定义与实例**：关系定义允许哪些对象按什么规则关联？当前关系实例具体连接了谁与谁？
- **相对交易角色**：[配置型/交易型/派生型/混合型]；配置型仅表示相对交易是前置配置，不表示运行期不可修改
- **建立时机**：什么业务操作或维护入口会创建这个关系？
- **变更时机与影响**：配置维护期/交易期如何变更；是否热生效；是否追溯历史
- **失效时机**：什么业务操作或条件会解除这个关系？

#### 建立与维护机制
- **维护入口**：[UI 配置/API/导入/脚本/消息同步/规则派生/系统内置/无/证据不足]
- **操作者与权限**：谁能建立、修改、解除，作用域和授权依据是什么？
- **输入与可选范围**：候选对象从何处加载，如何过滤无权、失效或不兼容对象？
- **校验与冲突处理**：必填、唯一性、基数、状态、作用域、时间有效性和并发冲突如何处理？
- **持久化与生效**：请求写入什么权威字段/关联表/配置，何时被业务读取并生效？
- **审计与历史**：是否记录操作者、时间、前后值；修改是否影响历史对象？
- **解除与恢复**：如何解绑、停用、回滚或修复错误关系？

仅当维护入口包含 UI 时，按以下链路描述并逐段引用证据；维护入口为 API/导入/消息/派生/内置时，改用对应链路，不适用段填“无/不适用”+理由：

```text
用户任务/页面控件
  -> 候选基础资料查询及权限/作用域过滤
  -> 保存请求字段和 API 契约
  -> 服务端业务校验与并发控制
  -> 权威字段/关联表/版本化配置

  -> 审计、历史兼容、解绑/停用
```

页面存在选择器只能证明“存在一个候选维护入口”；只有请求、校验、持久化和读取证据闭合后，才能断言关系可配置且已按该机制生效。

#### 5.4.4 DA3 机械真实性门禁

在关系模型进入 G2 前执行以下检查：

1. REL 中出现的字段、类、方法、API、消息、表、配置键和测试名称，必须在任务声明的源码/Schema/契约基线中逐一解析；无法解析的关键标识使 DA3 不通过，非关键标识标为“证据不足”并登记 `U-*`。
2. 字段连接必须核对字段归属、类型、空值语义和真实读写点；跨层命名差异必须有映射证据，不能从相似命名推导不存在的连接。
3. 基数和可选性必须引用数据库约束、模型声明、查询/写入逻辑或有边界说明的数据样本；证据只能覆盖样本时，结论必须限定为样本观察。
4. 删除、修改和级联行为必须核对 Schema、持久化配置、服务逻辑及软删除/历史保留路径；未搜索到代码不能证明“不级联”。
5. 仅当维护入口包含 UI 时，必须至少验证页面控件、请求字段/API、服务端校验、持久化载体和生效读取点；任一关键段缺失时，只能报告已证实的局部链路，不得对非 UI 关系强行补齐 UI 段。
6. 发现同一能力存在多个入口、版本或历史实现时，为每个实现建立独立 `IMPL-*`，分别记录 REL 和证据；未经 SOP-10 完成语义对齐、适用域分析和冲突裁决，不得合并。

门禁结果必须输出“通过/不通过/证据不足”及失败项清单，不能以模板填写完整代替真实性检查。

### 5.6 DA5：领域模型元素与数据所有权

#### 5.6.0 维度关系分析框架（DR-*）

在维度建模中，当一个维度表引用另一个维度表时，被引用的维度称为**Outrigger Dimension（引援维度）**。维度之间的关系通常表现为**4种基础模式**：

| 类型 | 标识 | 语义描述 | 典型示例 |
|------|------|----------|----------|
| 层级关系 | `DR-HIER` | 同一维度内的上下级归属 | 菜品大类 → 菜品小类 |
| 引用关系 | `DR-REFI` | A维度引用B维度，B是A的配置上下文 | 打印队列引用打印机 |
| 多值关系 | `DR-MULT` | A维度对应多个B维度实例 | 一台打印机属于多个队列 |
| 归属关系 | `DR-OWNS` | A维度"拥有"B维度实例的生命周期 | 门店拥有打印机 |

**基数判定矩阵**：

| 基数 | 判定问句 | 关系标记 |
|---|---|---|---|
| 1:1 | "B 只能唯一属于 A 吗？" | `1:1` |
| 1:N | "B 可以同时属于多个 A 吗？"（否 → 1:N）| `1:N` |
| N:1 | "A 只能对应一个 B 吗？"（否 → N:1）| `N:1` |
| N:N | "A 和 B 都是多对多吗？" | `N:N` |

**SCD变更特性**（Slowly Changing Dimension）：

| 类型 | 代码 | 变更行为 | 对历史数据的影响 | 示例 |
|------|------|----------|----------------|------|
| Type 1 | `SCD-T1` | 覆盖旧值 | 历史不一致 | 打印机名称修改 |
| Type 2 | `SCD-T2` | 新增一行 | 保留历史轨迹 | 打印机归属变更 |
| Type 3 | `SCD-T3` | 新增列保存旧值 | 有限历史 | 保留变更前后两个值 |

**维度关系分析检查表**（每个维度关系必须完成）：

| 检查项 | 检查内容 | 标记符号 |
|---|---|---|---|
| 关系类型 | 属于哪种维度关系？ | DR-HIER / DR-REFI / DR-MULT / DR-OWNS |
| 基数 | 两端的基数分别是？ | `1:1` / `1:N` / `N:1` / `N:N` |
| 引用结构 | 星型还是雪花型？ | STAR / SNOWFLAKE |
| SCD类型 | 变更时如何处理历史？ | SCD-T1 / SCD-T2 / SCD-T3 |
| 后台菜单配置 | 在哪个菜单页签、通过什么字段建立关系？ | 见下方详细规范 |
| 变更频率 | 变更的频繁程度？ | 高 / 中 / 低 |

**后台菜单配置规范**（每条维度→维度关系必填）：

对每个维度关系，必须说明建立/修改该关系的**后台配置路径**，包含以下要素：

| 配置要素 | 填写内容 | 示例 |
|---|---|---|---|
| 菜单路径 | 从哪个一级菜单进入，经过哪些二级菜单 | 设备管理 → 打印机 → 绑定队列 |
| 关系建立方式 | 声明式（建时就指定）还是运行时绑定？ | 声明式：在打印机新增页关联队列 |
| 关系字段 | 源维度表上哪个字段承载这个关系 | `queue_lid`：逗号分隔的队列ID列表 |
| 存储形式 | 字段列/JOIN表/外键/SQL计算？ | 逗号分隔字段（nms_printer.queue_lid） |
| UI交互 | 勾选/下拉/弹窗/导入？ | 多选下拉框，逗号分隔存储 |
| 校验规则 | 建立关系时有什么校验？ | 同一队列不能同时绑定主备打印机 |
| 自动/手动 | 关系变更由人工操作还是系统自动维护？ | 人工：管理员在页面手动绑定 |

**打印系统示例**：

```
维度关系矩阵（含后台配置）：
| 源维度 | 目标维度 | DR类型 | 基数 | SCD | 菜单路径 | 关系字段 | 存储形式 |
|--------|----------|--------|------|-----|----------|----------|----------|

#### 5.6.0b 维度链式传递分析（A→B→C）

当一个维度通过中间维度间接关联另一个维度时，形成维度链。分析维度链需要回答五个核心问题：

一、链的起点判定
  - 起点是事实表：链类型为"事实链"，关注事实聚合粒度的膨胀/收缩
  - 起点是维度表：链类型为"维度链"，关注查询路径和语义独立性

二、基数传播规则
  | A→B 基数 | B→C 基数 | 传递后 A→C 基数 | 行为描述 |
  |---------|---------|----------------|----------|
  | 1:N     | N:1     | N:1（前提：A 的多个 B 映射到同一 C 才收缩；否则退化为 N:N） | 链收缩（每 A 只到一个 C，但多个 A 可共享同一 C，故非 1:1） |
  | 1:N     | N:N     | N:N            | 膨胀，需要物化或保留JOIN |
  | N:N     | N:1     | N:1（前提：A 的多个 B 映射到同一 C 才收缩；否则退化为 N:N） | 链收缩（与第 1 行同法：B→C 收敛为一主值时可收缩） |
  | N:1     | 1:N     | N:N            | 膨胀 |
  | 1:N     | 1:N     | 1:N（树状传递：每个 C 经唯一 B 回到唯一 A，故 C 侧保持唯一） | 链式传递，A 的基数不变（示例见下"菜品→菜品小类→菜品大类"） |

三、SCD 级联影响矩阵
  - B 变T1 × C 变T1：覆盖传播，A通过B间接感知C的新值
  - B 变T2 × C 变T1：影子行包含旧的B引用，B的新行指向C的新值
  - B 变T1 × C 变T2：C变更新增一行，A查询结果"漂移"
  - B 变T2 × C 变T2：最复杂，需追踪B历史版本对应的C版本

四、物化决策树
  ```
  查询频率高 且 B→C稳定？
    → 是 → 冗余C属性到A（星型），查询快但变更传播复杂
    → 否 ↓
  B是独立分析实体？
    → 是 → 必须保留B（雪花型），不能折叠
    → 否 ↓
  查询稀少 且 C高频变更？
    → 是 → 保留JOIN路径，不物化
    → 否 → 评估折叠代价后决定
  ```

五、禁止行为
  - 未分析基数就写JOIN（可能导致笛卡尔积膨胀）
  - 把雪花型链当作星型处理（忽略中间实体的独立语义）
  - 忽略SCD级联传递对历史数据一致性的影响
  - 在未确认B是独立实体前删除B
  - 把传递链当作等价于冗余字段

**打印系统示例**：

```
维度链分析矩阵：
| 维度链 | A→B 基数 | B→C 基数 | 传递后基数 | 物化决策 |
|--------|---------|---------|-----------|----------|
| 收银交易→门店→城市 | N:1 | N:1 | N:1（收缩） | 冗余 city_id（查询频繁） |
| 菜品→菜品小类→菜品大类 | 1:N | 1:N | 1:N（传递） | 保留B独立管理单元 |
| 打印队列→打印机→厂商 | N:N | N:1 | N:N（膨胀，属于"N:N×N:1 发散前提"的分支，见基数传播规则第 3 行的前提） | 保留JOIN，不冗余 |
```

#### 5.6.0c 维度关系合理性评估与进化分析

一、必要性判定（每个P0/P1维度必答）
  1. 删除这个维度，什么业务场景无法支持？（如果无 → 标记为冗余候选）
  2. 这个维度是否只服务于展示/统计，不参与任何业务规则？
     （如果是 → 标记为统计维度候选，与业务维度分离）
  3. 它是否可以合并到另一个维度而不损失语义？
     （如果可以 → 合并的收益 vs 失去独立管理入口的代价）

二、正确性验证
  1. 维度粒度是否与使用它的业务粒度匹配？（过粗→统计失真，过细→维度爆炸）
  2. 基数判定是否有运行数据佐证？（不只是代码推断，要看实际数据分布）
  3. SCD选择是否与历史数据的保留需求一致？（变更频率+历史查询需求决定）

三、代价评估
  1. 引入这个维度后，每次查询多了几跳JOIN？
  2. 维度变更的传播路径是否清晰？影响范围有多大？
  3. 如果是雪花型：是否值得为规范化牺牲查询性能？
  4. 如果是事实表维度：是否造成维度爆炸？

四、进化路径分析（每个P0/P1维度必填）
  1. 最初引入它是为了解决什么问题？证据是什么？
  2. 历史上它的形态发生过什么变化？经历了哪些版本？
  3. 什么业务变化/技术变化触发了这些变化？
  4. 当前是终态还是过渡态？依据是什么？
  5. 什么条件出现时，这个维度应该被拆分/合并/删除？

五、反模式检测矩阵
  | 反模式 | 在这个维度上是否存在？ | 证据/依据 |
  |--------|----------------------|----------|
  | 维度爆炸 | 维度数量是否失控？ | |
  | 雪花反模式 | 规范化程度 vs 查询性能是否失衡？ | |
  | 过度反规范化 | 是否把应该独立的维度直接冗余到事实表？ | |
  | 角色扮演陷阱 | 同一实体是否被多个维度表重复建模？ | |
  | SCD策略混乱 | 同一维度的不同属性是否使用了不同的SCD策略？ | |

六、物化决策（综合 §5.6.0b 的链式分析）
  1. 雪花→星型折叠的收益/成本对比是否完成？
  2. 折叠后是否引入新的更新异常？
  3. 中间实体是否承担了独立的业务职责（不能折叠的判断依据）？

#### 5.6.8 DDD 类型条件说明

DDD 类型是条件化解释，不是必填标签。只有同时存在稳定业务身份、明确生命周期、需要原子维护的不变量、对外行为边界，并且项目设计或可观察行为支持该语义时，才能标记为聚合；缺一项时记录为候选或使用更中性的模型类型。只有表达已经发生、对业务角色或消费者有独立意义的事实时，才能标记为领域事件或集成事件。持久化、有状态、有队列或被多个服务调用，均不能单独证明聚合或领域事件成立。

聚合边界只围绕一次业务操作需要原子维护的不变量划分。跨聚合关系应说明一致性时限、状态机、幂等、补偿或对账，不以”微服务”名称代替边界依据。

④ 行为
   状态机摘要：引用 SM-*，列出关键迁移路径
   关键规则摘要：引用 BR-*，列出核心判断逻辑

⑥ 生命（时间线叙事）

   - 谁在什么条件下创建它
   - 经历哪些关键事件，状态如何变化
   - 产生哪些外部副作用（消息、通知、对账）

   **正面示例（以"配送单"对象为例）**：

   ```
   删除类名、方法名后，叙事仍完整表达对象的生命周期。

   **反面示例（不合格）**：
   ```text
   配送单创建 → PENDING → ASSIGNED → DELIVERING → COMPLETED/FAILED
   超时 7 天 → CANCELLED
   ```
   这只是状态枚举变化，没有业务因果，无法回答"为什么创建"、"谁触发"、"失败后怎么办"。

### 5.7 DA6：用例、事件、交互和恢复

从场景中的业务命令开始还原交互：

```text

  → 认证、授权与作用域检查
  → 读取权威事实
  → 执行规则并校验不变量
  → 状态和数据变化
  → 产生领域事实/响应/外部副作用
  → 消费者处理、通知、对账和审计
```

| IX | 发起者→接收者 | 命令/查询/事件 | 前置与状态变化 | 一致性时限 | 超时/重复/乱序 | 恢复责任 | 证据 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

对支付、订单、库存、余额、权益和消息消费等可重复写操作，必须定位幂等键、唯一约束、事务边界、并发控制、结果确认、补偿和对账。超时只能说明调用方未及时获知结果，不能直接等同业务失败。

**退出条件**：关键交互的成功、失败和结果未知状态可解释；外部副作用、部分失败和恢复责任明确。

### 5.8 DA7：实现映射与运行反查

对每个关键语义建立实现映射：

| MAP | 业务语义 | 页面/入口 | API/消息/任务 | 代码/配置 | 数据/缓存 | 运行/审计 | 版本/范围 | 差异 |
|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |

执行顺序：

1. 黑箱：观察任务、输入、输出、错误和权限表现；
2. 灰箱：追踪 API、消息、任务、数据写入、外部依赖和运行链路；
3. 白箱：解释代码、配置、事务、并发和恢复机制；
4. 反查：从关键表、枚举、接口、消息和任务向上寻找业务语义；
5. 互证：比较源码、部署、配置、数据、日志、Trace 和调用方契约。

代码只能证明某版本可能如何运行；数据库字段名只能产生语义假设；单次日志只能证明观测窗口内发生过该路径。

**退出条件**：关键结论至少有直接证据，重要决策有独立证据互证；强反证和无法解释的实现进入 X/U 台账。

|---|---|---|---|---|---|---|

#### DA8-B：业务综合

```text

#### DA8-C：复核封装

**退出条件**：关键场景可从业务目标双向追溯到实现和运行证据；理解层五类职责均有承载文件且通过十分钟理解测试；跨文档规范事实无未解释冲突；证据不足项未被写成事实。认知重建可以准确披露未修复 P0/P1 后完成报告，但不得宣称系统风险已接受或可以上线；决策支持或变更实施仍按 SOP-00 的负责人和风险门禁处理。

### 6.1 设计评价的诚实边界

> 本节说明分析能力可以到达和不可到达的边界。超出边界的评价是过度承诺，比没有分析更危险。

█ 本 SOP 支持的评价

| 评价类型 | 说明 |
|----------|------|
| 消除已识别的反模式 | 发现并记录设计中明确违背最佳实践的模式 |
| 约束集内代价评估 | 在已明确的约束下，评估候选方案的代价并选择最小者 |
| 目标一致性判断 | 判断当前设计是否满足其声称要解决的业务问题 |
| 进化合理性 | 识别设计的进化路径，判断当前是终态还是过渡态 |
| 必要性判定 | 判断维度/实体/关系是否存在冗余或缺失 |

█ 本 SOP 不支持的评价

| 评价类型 | 原因 |
|----------|------|
| 证明某个设计"最优" | 没有完整约束集和运行数据，无法证明，只能比较已知方案 |
| 声称性能改进 | 性能结论需要运行数据，没有数据时只能记录为假设 |
| 跨约束集比较 | 分析范围外的约束（人员/迁移/商业合同）不在评价范围内 |
| 发现范围外约束 | 分析只能识别已暴露的约束，无法发现未暴露的 |

█ "更好设计"的来源

| 来源 | 分析能做什么 | 分析不能做什么 |
|---|---|---|---|
| 约束集内代价最小化 | ✅ 可以做到：消除反模式后选择已知方案中代价最小的 | |
| 约束集的重新定义 | ❌ 无法做到：需要业务/技术决策者拍板 | ✅ 输出是"DQ-约束重新定义" |
| 发现新范式 | ❌ 无法做到：分析只能消除错误，不能主动构造 | |

█ 分析到更好的正确路径

```
分析现有设计
    │
    ▼ 消除已识别的反模式
消除明显的错误（在现有约束内）
    │
    ▼
识别多个候选改进方案
    │
    ▼ 评估每个方案的代价
权衡分析（诚实记录假设和未知项）
    │
    ▼
输出："在已知约束下，建议A方案，原因是X"
      ↓
不是"A更好"，而是"在已知约束下A的代价更小"
      ↓
超出已知约束的判断 → 登记为DQ，转交决策负责人
```

█ 横切检查项（§6 必须回答的设计评价问题）

| 问题 | 评价维度 |
|------|----------|
| 这个维度/关系是否真的必要？ | 必要性 |
| 基数/SCD是否有运行数据支撑？ | 正确性 |
| 引入它付出的代价是否与解决的问题对等？ | 代价 |
| 当前形态是终态还是过渡态？ | 进化 |
| 是否存在已知的反模式？ | 反模式 |

## 7. 纯方法示例：订单提交切片

> 本节只演示产物之间如何连接，不描述任何目标项目。执行者不得复制其中的概念、状态、技术机制或失败策略到项目文档；必须重新从目标项目证据建立模型。示例与项目事实相似时，仍需逐项验证。

### 7.1 语义链

```text
SC-ORDER-01 客户提交购物车形成订单
  → BC-CART / BC-ORDER / BC-ORDER-ITEM / BC-PRICE / BC-INVENTORY
  → REL-01 订单由订单项构成
  → REL-02 成交金额由订单项价格快照和计价规则决定
  → BR-01 只有活动购物车可提交
  → INV-01 订单至少包含一个正数量订单项
  → SM-ORDER 草稿 → 已提交 → 库存处理中 → 待支付/库存失败
  → DM-ORDER 订单聚合；DM-MONEY 金额值对象；库存为独立权威边界
  → IX-RESERVE 库存预留交互
  → MAP-01 页面按钮/API/订单表/Outbox/库存消息/Trace
```

### 7.2 必须追问的失败语义

- 订单保存成功但库存请求未可靠发送怎么办？
- 库存已预留但调用方超时，重复提交是否产生第二张订单或重复预留？
- 商品改价是否覆盖已提交订单的价格快照？
- 库存失败、消息积压、补偿失败和人工修复分别进入什么状态？
- 哪个系统拥有订单状态、支付结果和库存结果，副本如何纠偏？

这个示例说明：只有概念、关系、规则、状态、模型、交互和证据同时闭环，才能解释系统，而不仅是知道 `orders` 与 `order_items` 的外键关系。

## 8. 常见反模式

| 反模式 | 问题 | 修正动作 |
|---|---|---|---|
| 从菜单开始列功能 | 得到页面目录，得不到业务机制 | 先选业务切片和结果 |
| 概念直接映射表/实体 | 把存储实现误当领域模型 | 先判断规则、状态、身份和责任 |
| 只画静态 ER 图 | 无法解释行为、失败和恢复 | 加入状态机、交互和不变量 |
| 只看正常路径 | 看不到真实边界 | 注入边界、失败、重复和并发问题 |
| 代码即真相 | 忽略部署、配置、数据和旁路 | 用 CFG/DAT/RUN/CON 互证 |
| 访谈即真相 | 把角色认知写成运行事实 | 标为 HUM，寻找独立证据 |
| 追求全量后再总结 | 成本失控且没有决策焦点 | 风险驱动选择切片，螺旋扩展 |
| 发现不同就建议统一 | 可能删除合法业务变体或兼容契约 | 先区分缺陷、变体、历史兼容和未知项 |
| 为解耦而事件化 | 引入延迟、重复和恢复复杂度 | 按一致性时限和失败成本选择交互 |
| 报告混写现状与建议 | 目标模型伪装为系统事实 | 分开 As-Is、差异、To-Be 与迁移 |

### 9.2 停止条件

达到支持当前决策所需的证据充分度即可停止，不以穷举整个系统为目标。以下情况应暂停确定性结论并升级：

- 关键部署/数据版本无法与源码对齐；
- 核心业务语义无人有权裁决；
- 权限、租户或敏感数据边界不明确；
- 需要生产写入、压测、故障注入或外部协调但尚未授权；
- 高影响结论只有单一低质量证据或存在未解释强反证。
