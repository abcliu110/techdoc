## 1. 目的与定位

本 SOP 处理长期维护系统中的一类特殊问题：同一业务能力为满足不同客户、渠道、区域、时期或经营模式，逐步产生修改版、扩展版、定制版、重写版和兼容版。多个实现可能适用域重叠、竞争同一业务事实、维护不同状态机或重复产生外部副作用；开发新版本时，又需要把这些历史实现重新提炼为可持续演进的统一业务能力。

本 SOP 不把“合并代码”作为目标，而完成：

```text
历史实现考古
→ 业务语义对齐
→ 共性、变体、分叉、兼容和缺陷分类
→ 适用域重叠与交互冲突分析
→ 稳定核心、显式变化和统一裁决设计
→ 旧新语义映射、迁移、验证和旧实现退役
```

一句话标准：

> 新系统不是旧实现的代码并集，而是对多个历史实现背后的业务事实、共同不变量、真实变化维度和冲突关系重新建模。

## 2. 适用范围与边界

### 2.1 适用

- 同一业务能力存在多个客户版、渠道版、区域版、时期版或重写版。
- 新需求持续叠加，出现客户判断、版本判断、模式判断和兼容分支。
- 新旧实现可能同时命中、双写、重复产生副作用或对状态有不同解释。
- 新版本需要整合多个历史实现并形成统一产品能力。
- 需要迁移历史数据、进行中流程、旧接口和人工制度。

### 2.2 不适用或可裁剪

- 纯技术实现替换且已证明业务语义、输入输出和副作用等价，可按普通技术迁移处理。
- 单一、稳定且无历史变体的 CRUD 功能，不必机械执行完整流程。
- 仅修复局部缺陷且不改变规则、状态、数据语义或适用范围时，执行对应缺陷修复流程。

裁剪必须说明依据；“代码看起来相似”不能证明业务语义等价。
## 3. 核心概念与判断模型

### 3.1 五个对象必须分离

| 对象 | 定义 | 常见混淆 |
|---|---|---|
| 业务能力 | 对外提供的稳定业务结果，如定价、退款、结算 | 被误认为某个页面、服务或接口 |
| 业务模式 | 对象、责任、不变量或生命周期具有结构性差异的经营方式 | 被误压缩为一个开关 |
| 业务变体 | 在共同语义下，因政策、渠道、区域等形成的受控差异 | 被实现成客户专属流程副本 |
| 技术实现 | 完成既定语义的算法、组件或集成方式 | 技术不同被误判为业务不同 |
| 兼容实现 | 为旧接口、旧数据、存量流程或过渡期保留的行为 | 临时兼容永久进入核心模型 |

### 3.2 多实现不自动等于冲突

设业务能力为 `B`，实现为 `I1...In`。实现 `Ii` 对业务对象 `x`、时间 `t`、上下文 `c` 的适用性为 `Eligible(Ii,x,t,c)`。

只有同时满足下列条件，才形成需要裁决的多实现冲突：

```text
存在 x、t、c：
Eligible(Ii,x,t,c) = true
且 Eligible(Ij,x,t,c) = true
且二者的决策、写入、状态变化或副作用不可安全合并
```

因此必须分别证明：

1. 适用域是否重叠。
2. 重叠后属于等价、互斥、择优、有序组合、可交换组合、依赖还是非法组合。
3. 是否已有一个权威机制完成裁决。

### 3.3 业务演进类型

| 类型 | 判断特征 | 默认处理方向 |
|---|---|---|
| 原实现修订 | 语义和不变量不变，仅修正缺陷或算法 | 修改原实现并回归兼容 |
| 原语义扩展 | 增加同一模型可自然表达的规则 | 扩展现有模型，显式版本化 |
| 业务变体 | 核心语义相同，适用条件或政策不同 | 参数、规则、策略或受控流程变体 |
| 语义分叉 | 对象、状态机、不变量、责任或结果发生结构变化 | 独立业务模式或版本，不伪装成普通分支 |
| 替代实现 | 新实现目标是取代旧实现 | 双轨验证、迁移、停止新流量、退役旧实现 |
| 历史兼容 | 只服务旧数据、旧契约或存量流程 | 隔离到兼容层并设置退出条件 |

## 5. 历史实现考古

### 5.1 业务能力边界

先以业务结果而不是代码位置命名能力。例如使用“订单最终定价”而不是“PriceService”，使用“退款责任与资金返还”而不是“RefundController”。明确：

- 服务对象、触发场景和成功结果。
- 核心业务事实和不变量。
- 正向、逆向、异常和人工路径。
- 业务、数据、运行和损失承担者。
- 哪些客户、渠道、区域、时间版本和存量数据在范围内。

### 5.2 实现谱系卡

每个实现建立独立记录，禁止先假定它们等价。进入语义归一前，每个实现必须在文档 20 中分别形成可追溯的场景、REL、规则、状态、数据和实现映射，并通过文档 21 的适用门禁；不能先把多个实现拼成一份 DA3/DA5，再用合并后的模型反证它们相同：

| 字段 | 内容 |
|---|---|
| 实现 ID/名称 | `IMPL-___` / ___ |
| 来源与时间线 | 初始需求、客户需求、事故修复、迁移或临时补丁 |
| 当前适用域 | 客户、渠道、区域、产品、时间、状态、版本 |
| 业务目标与结果 | 解决什么问题，什么叫成功 |
| 入口与路由 | 页面、API、消息、任务、脚本、人工入口及选择条件 |
| 规则与优先级 | `BR-___`、来源、覆盖和冲突关系 |
| 状态与不变量 | `SM-___`、`INV-___` |
| 数据与权威源 | 读取、写入、所有者、历史解释和副本 |
| 外部副作用 | 支付、库存、权益、消息、结算、审计等 |
| 逆向与恢复 | 取消、退款、冲正、补偿、对账、人工处理 |
| 使用证据 | 真实流量、数据、客户、配置和运行版本 |
| 生命周期 | 主实现/变体/过渡/兼容/待退役/未知 |

### 5.3 决策考古

对每个差异追问：

1. 当时为什么新增而不是修改原实现？
2. 它解决的是业务差异、组织边界、交付压力还是技术限制？
3. 当时约束现在是否仍存在？
4. 哪些客户、历史数据、报表、脚本或人工流程仍依赖它？
5. 如果删除，最小可观察反例是什么？

不得因为注释写“临时”就判定可删除，也不得因为运行多年就判定其语义正确。

## 6. 语义对齐与差异归类

### 6.1 语义三角

对同名或相似概念同时比较：

```text
声明语义：需求、合同、文档和人员如何解释。
实现语义：代码、状态转换、SQL 和配置如何处理。
运行语义：真实数据、日志、报表和用户行为呈现什么。
```

例如不同实现中的“完成”“已确认”“已结算”可能是同义词、不同阶段、不同业务事实，也可能是错误映射。未对齐前不得合并状态或数据。

### 6.3 每项差异的五种目标归宿

| 归宿 | 条件 | 目标处理 |
|---|---|---|
| 统一核心 | 语义、不变量和生命周期相同 | 合并为一个权威模型 |
| 参数配置 | 只有阈值、开关、范围等数据差异 | 类型化、校验、版本化配置 |
| 规则/策略变体 | 输入输出语义相同，决策算法或政策不同 | 受控策略、决策表或政策对象 |
| 独立业务模式 | 对象、状态机、不变量、责任或资金边界不同 | 保持独立模型，定义共享与交互边界 |
| 兼容/退役 | 过期定制、实现偶然、旧契约或历史缺陷 | 兼容层、迁移或显式淘汰 |

不允许用“某客户需要”代替差异性质。客户身份可以选择业务配置，但不能成为核心模型中的业务语义。

## 7. 重叠与冲突分析

### 7.1 实现交互矩阵

| 实现对 | 适用域交集 | 结果关系 | 写入冲突 | 状态冲突 | 副作用冲突 | 版本/逆向冲突 | 当前裁决 | 目标处理 |
|---|---|---|---|---|---|---|---|---|
| A × B |  | 等价/互斥/择优/有序组合/可交换/依赖/非法/未知 |  |  |  |  |  |  |

对每个非空交集必须建立最小合法反例。“未知”不得默认按调用顺序、代码位置或后写覆盖处理。

### 7.2 八类冲突

1. **资格冲突**：多个实现同时认为自己适用。
2. **优先级冲突**：都可适用，但缺少谁覆盖谁的业务规则。
3. **组合冲突**：缺少是否叠加、组合顺序、择优或拒绝规则。
4. **状态冲突**：同一对象被多个状态机推进或对同一状态解释不同。
5. **数据权威冲突**：多个实现都能写同一业务事实。
6. **副作用冲突**：重复扣款、扣库存、发权益、退款、结算或通知。
7. **时间版本冲突**：对象生命周期中被不同版本重新解释。
8. **逆向冲突**：正向采用新规则，退款、撤销、冲正或对账仍使用旧规则。

### 7.3 裁决关系必须显式

允许的关系包括：

```text
等价：可替换或用于影子比较。
互斥：一次决策只能选择一个。
择优：多个候选计算后按声明规则选一个。
有序组合：允许共同作用，但顺序属于业务语义。
可交换组合：顺序不影响结果，需用性质测试证明。
依赖/蕴含：启用 A 要求 B 存在或同时启用。
冲突拒绝：组合非法，应在配置发布或请求进入时拒绝。
```

> **说明**：本节裁决关系是多实现组合/归一语境下的派生裁决分类，**不替代** L1 的三类关系（结构/轨迹/归因）；L1 三类关系用于描述业务内容之间的连接，本节分类用于裁定多个实现之间的组合与冲突。无法归入本节任一类时登记 U-* 或"弱相关，不建模"，禁止硬贴标签。

## 8. 目标业务模型设计

### 8.1 设计原则

多实现可以存在，但对一次具体业务决策必须产生唯一、可解释、可追溯的权威结果。目标模型至少分离：

```text
稳定核心：核心对象、业务事实、基础生命周期和跨变体不变量。
变化模型：业务模式、政策、区域、渠道、客户合同和外部能力差异。
资格判断：哪些变体在当前上下文有资格参与。
统一裁决：互斥、优先、择优、组合、依赖和冲突拒绝。
结果守卫：金额、额度、权限、合规和其他不变量。
外部适配：客户系统、渠道、协议和技术集成差异。
版本快照：模式、规则版本、命中规则、执行顺序、中间值和最终结果。
兼容迁移：旧接口、旧状态、旧数据和存量流程的隔离处理。
```

这是一组职责，不强制对应某种框架、类结构、规则引擎或微服务。

### 8.2 禁止简单求并集

旧实现能力分别为 `I1={A,B,C}`、`I2={A,B,D}`、`I3={A,E,F}` 时，不得直接令目标能力 `T={A,B,C,D,E,F}`。必须确认：

- C 与 D 是否互斥。
- E 是否属于独立业务模式。
- F 是否只是历史缺陷或兼容行为。
- 组合后是否产生旧系统从未允许的新状态。
- 新增自由度是否有真实场景、明确语义和测试证据。

目标系统应覆盖被确认保留的业务场景，而不是保存所有历史行为。

### 8.3 修改、变体、独立模式和替代的选择

| 选择 | 更适合的条件 | 不适合的信号 |
|---|---|---|
| 修改原实现 | 核心对象、不变量、状态和权威源不变；现有模型可自然表达 | 大量字段和分支仅在某模式有效 |
| 参数/规则变体 | 输入输出语义一致，差异可声明、校验和版本化 | 参数组合改变对象含义或生命周期 |
| 独立业务模式 | 状态机、责任、资金、信任或交易边界发生结构变化 | 仅算法不同却复制完整流程 |
| 替代实现 | 新旧目标语义一致且新实现最终接管 | 没有迁移终态和旧实现退出计划 |

### 8.4 防止过度通用化

只抽象被多个真实场景证明的稳定变化维度：

```text
已证明共性 → 稳定核心
已证明差异 → 显式变化点
仅一次定制 → 先隔离并观察，不急于抽象
无法解释 → 保持未知并补证
假想未来需求 → 不据此建设重量级机制
```

“所有字段可配置、任意状态可流转、任意脚本可执行”通常只是把代码复杂度转移为配置、测试和运营复杂度。

## 9. 目标模型正确性条件

设保留的历史合法场景集合为 `S`，目标模型为 `T`：

1. **覆盖性**：每个 `s∈S` 在 T 中都有声明的业务归宿。
2. **确定性**：相同上下文、规则版本和输入产生唯一声明结果。
3. **不变量保持**：任意合法变体及合法组合都不破坏核心不变量。
4. **非法组合封闭**：未声明或冲突组合在发布期或执行前被拒绝。
5. **权威唯一**：每个业务事实和状态转换有唯一权威写入路径。
6. **历史可解释**：历史对象可追溯到创建时模式、规则版本和决策快照。
7. **逆向完整**：退款、撤销、冲正、补偿和对账与正向决策对应。
8. **可退役**：兼容和过渡实现具备停止新流量、清空存量和移除条件。

不能证明上述性质时，只能标为待验证目标模型，不能宣称“完成统一”。
## 10. 旧新映射、迁移与退役

### 10.1 旧新映射表

| 旧实现/场景 | 目标核心/模式/变体 | 保留语义 | 修正/废弃语义 | 数据转换 | 存量流程处理 | 兼容窗口 | 退役条件 |
|---|---|---|---|---|---|---|---|
| IMPL-___ |  |  |  |  |  |  |  |

每个旧实现必须有归宿。不得仅设计新流量而遗漏历史数据、进行中流程、旧客户端、异步消息、定时任务、报表、脚本和人工操作。

### 10.2 对象迁移分类

按业务对象当前状态分别处理：

- 未开始对象：可直接进入新模型。
- 进行中对象：继续旧流程、状态映射后迁移或受控接管，必须逐类决定。
- 已完成对象：原则上保持历史事实和原版本解释，不用新规则重算。
- 失败/结果未知对象：先确认权威事实，再决定补偿、迁移或人工接管。
- 脏数据/未知版本对象：隔离、补证或人工裁决，不得静默猜测。

### 10.3 双轨与影子验证

高风险替代优先采用：

```text
旧实现继续产生正式结果
+ 新实现无副作用并行计算
+ 按稳定业务键比较结果和中间决策
+ 差异分类与业务确认
+ 分批灰度切换
+ 保留观测和快速回退
```

差异必须分类为：新实现缺陷、旧实现缺陷修正、产品规则改变、历史兼容、数据质量、配置差异、时序差异或证据不足。不能用总体一致率掩盖资金、状态和权限类少量高影响差异。

### 10.4 旧实现退役状态机

```text
活跃
→ 禁止新增客户/配置
→ 停止新业务对象进入
→ 只处理存量对象和逆向流程
→ 存量清零并完成对账
→ 关闭入口和写权限
→ 观察期
→ 删除代码/配置/任务/数据兼容
```

每次迁移必须定义退出终态。没有退役计划的“双轨”默认视为新增永久复杂度。

## 11. 验证方法

### 11.1 历史样本与差分测试

- 从每个实现、客户、渠道、状态和历史时期分层采样。
- 同时比较最终结果、中间决策、状态变化、数据写入和外部副作用。
- 对差异引用业务规则和决策记录，不把旧结果自动当成正确答案。

### 11.2 组合与性质测试

对变化维度生成合法及非法组合，重点验证：

- 互斥配置不能同时发布或生效。
- 优先级变化符合声明规则。
- 有序组合严格保持执行顺序。
- 声称可交换的组合改变顺序后结果不变。
- 增加无关变体不会改变当前结果。
- 同一规则版本和输入重复计算结果一致。
- 正向决策与退款、撤销、冲正和对账保持守恒关系。
- 任意合法组合均满足资金、状态、权限和审计不变量。

### 11.3 最小反例

固定追问：

```text
哪个最小客户/渠道/版本组合能同时命中两个实现？
哪个最小状态会被两个流程同时推进？
哪个最小失败点会导致两个实现都产生副作用？
哪个最小历史对象无法映射到目标模型？
哪个最小配置组合能绕过业务不变量？
```

## 13. AI 执行算法

```text
INPUT：重构目标、历史实现集合、客户/渠道/版本范围、现有证据和权限边界

1. 以业务结果定义能力边界，不按服务、页面或客户命名能力。
2. 建立全部实现谱系；没有运行证据时不得断言实现已废弃。
3. 对齐术语、对象、状态、规则、数据、责任和正逆向语义。
4. 将差异标为业务本质、政策规则、流程控制、外部集成、历史兼容、实现偶然、缺陷或未知。
5. 为每项差异选择统一核心、参数、策略变体、独立模式或退役归宿。
6. 计算实现适用域交集，建立两两及高风险多方交互矩阵。
7. 用最小反例检查资格、优先、组合、状态、写入、副作用、版本和逆向冲突。
8. 构造多个目标候选，包括最小归一、结构性重构和保守兼容方案。
9. 设计稳定核心、显式变化、统一裁决、权威写入、版本快照和非法组合封闭。
10. 为所有保留场景、历史数据和存量流程建立旧新映射。
11. 设计差分、性质、组合、影子、对账、灰度、回滚和退役验证。
12. 将目标候选交由 SOP-09 评审；未经业务责任人裁决，不自行合并冲突语义。
```

AI 必须输出支持与反对归一化的证据、无法统一的真实边界和可能被错误抽象的差异，不得为了得到整洁模型而删除历史事实。

## 14. 常见反模式

- 把多个旧实现的代码直接复制到新系统，再增加客户判断。
- 把所有旧字段、状态和流程求并集，制造万能对象。
- 看到重复代码就认定业务语义相同。
- 用租户 ID、客户名称或渠道编码代替真实业务模式。
- 每个变化点单独使用策略，却不分析策略之间的交互。
- 允许任意配置组合，但没有发布校验和非法组合封闭。
- 只重构正向流程，遗漏退款、撤销、对账和历史解释。
- 用当前规则重算历史对象，破坏原始交易事实。
- 新实现上线后永久保留旧实现，没有停止新流量和退役终态。
- 以“更通用”为理由引入规则引擎、工作流或插件体系，却没有真实变化证据。
- 把旧新结果不一致全部判为新系统缺陷，或全部判为旧系统错误。
