## 0. 演示目的

通过三个典型场景的完整规则映射，演示：
1. 如何从业务流框架出发，识别场景涉及的流

4. 如何识别跨流不变量和对账规则

## 场景一：O2C 全链路（订单到收款）

### 1.1 场景概述

```text
客户下单 → 支付 → 商家发货 → 客户签收 → 确认收货 → 完成

涉及业务流：
- 商流：报价、订单、促销
- 物流：库存、出库、配送
- 资金流：支付、收款、结算
- 会计流：应收、确认收入
- 票税流：开票
- 信息流：通知、单据
```

### 1.3 关键规则详细设计

#### 1.3.1 价格计算（商流）

```text
OrderPricingPipeline

Step 1: 基础价格（Strategy）
├─ RetailPriceStrategy
│   └─ 根据商品目录价计算
├─ MemberPriceStrategy
│   ├─ 判断客户是否会员（Specification）
│   └─ 根据会员等级应用折扣
└─ ContractPriceStrategy
    ├─ 判断是否有合同价（Specification）
    └─ 应用合同价格

Step 2: 商品级优惠（Pipeline + Quota）
├─ 商品满减
│   ├─ 判断是否满足满减条件（Specification）
│   └─ 计算优惠金额
├─ 商品折扣
│   └─ 应用折扣率
└─ 促销名额预占
    └─ Quota: 促销名额 - 已使用 <= 剩余名额

Step 3: 订单级优惠（Pipeline + Quota）
├─ 订单满减
│   └─ 判断是否满足满减条件（Specification）
├─ 优惠券
│   ├─ 判断优惠券是否可用（Specification）
│   ├─ 权益检查（Agreement-Policy-Entitlement）
│   └─ 核销记录（Ledger）
└─ 优惠券额度预占
    └─ Reservation: 使用时预占，核销时确认

Step 4: 平台补贴（Policy + Quota）
├─ 判断是否满足补贴条件（Specification）
└─ 补贴预算控制（Quota）

Step 5: 税费计算（Calculation）
├─ 按商品税率分别计算
└─ 汇总税额

Step 6: 金额分摊（Calculation）
├─ 将订单级优惠分摊到各明细
└─ 将税费分摊到各明细

Step 7: 不变量校验（Invariant）
├─ 订单应付 >= 0
├─ 明细应付之和 = 订单应付
├─ 优惠分摊之和 = 优惠总额
└─ 税费分摊之和 = 税费总额
```

**实现模型选择理由**：
- Strategy：因为零售价、会员价、合同价是相同输入输出但不同算法
- Pipeline：因为计算有稳定阶段（价格→优惠→税费→分摊）
- Quota/Reservation：因为促销名额和优惠券需要预占
- Invariant：因为应付非负和分摊守恒是底线

#### 1.3.2 库存预占（物流）

```text
InventoryReservationFlow

Step 1: 资格判断（Specification）
├─ 商品在售
├─ 仓库支持配送区域
├─ 购买数量在限购范围内
└─ 商品未被锁定

Step 2: 可用库存计算（Specification）
├─ 可用 = 总库存 - 冻结 - 已预占
└─ 需要考虑批次和效期（可选）

Step 3: 预占执行（Reservation）
├─ 预占键: orderId + skuId + warehouseId
├─ 预占数量: 下单数量
├─ 预占过期: 15分钟（未支付自动释放）
├─ 预占状态: AVAILABLE → RESERVED
└─ 幂等键防止重复预占

Step 4: 不变量校验（Invariant）
├─ 已使用 + 已预占 <= 可支配库存
├─ 批次追溯不被破坏
└─ 库位可用性不被破坏

Step 5: 出库确认（State Machine Transition）
├─ 支付成功后: RESERVED → COMMITTED
├─ 预占过期: RESERVED → RELEASED
└─ 取消订单: RESERVED → RELEASED

Step 6: 库存账更新（Ledger）
├─ 预占时: 记录预占分录
├─ 确认时: 预占分录转为使用分录
└─ 释放时: 释放预占分录
```

**实现模型选择理由**：
- Specification：因为资格判断是布尔结果
- Reservation：因为需要预占-确认-释放语义
- Invariant：因为库存底线不可破坏
- State Machine：因为预占有生命周期
- Ledger：因为库存变化需要可追溯

#### 1.3.3 支付执行（资金流）

```text
PaymentExecutionSaga

State Machine:
PENDING → AUTHORIZED → CAPTURED
              ↓              ↓
          FAILED         REFUNDING → REFUNDED
              ↓
          RESULT_UNKNOWN → 查询对账 → CAPTURED / FAILED

Step 1: 支付准备（Specification）
├─ 订单状态允许支付
├─ 支付金额 > 0
├─ 支付方式可用
└─ 账户余额充足（针对余额支付）

Step 2: 支付授权（State Machine）
├─ 状态: PENDING → AUTHORIZED
└─ 生成支付流水号（幂等键）

Step 3: 调用支付渠道（Saga）
├─ 发起支付请求
├─ 设置超时时间（30秒）
└─ 处理响应

Step 4: 支付结果处理（State Machine）
├─ 成功: → CAPTURED
│   ├─ 更新订单状态
│   ├─ 确认库存预占
│   ├─ 发送支付成功事件
│   └─ 生成收款凭证
│
├─ 失败: → FAILED
│   ├─ 释放库存预占
│   ├─ 发送支付失败事件
│   └─ 解冻优惠券（可选）
│
└─ 超时/未知: → RESULT_UNKNOWN
    ├─ 禁止重复支付（同幂等键）
    ├─ 延迟查询（1分钟、5分钟、30分钟）
    ├─ 对账任务兜底
    └─ 转人工处理（24小时无结果）

Step 5: 收款账务（Ledger）
├─ 借: 银行存款 / 应收账款（待结算）
└─ 贷: 主营业务收入 / 应交税费
```

**实现模型选择理由**：
- Saga：因为支付是外部系统调用，结果不确定
- State Machine：因为支付有明确生命周期
- Invariant：因为不能重复支付
- Ledger：因为收款需要会计分录

#### 1.3.4 跨流不变量

```text
O2C跨流不变量清单

INV-O2C-001: 订单应付 = 明细应付之和
├─ 涉及流: 商流
├─ 校验时机: 订单创建、修改
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-O2C-002: 预占数量 <= 可用库存
├─ 涉及流: 物流
├─ 校验时机: 预占时
├─ 实现: Invariant + 数据库约束
└─ 破坏处理: 拒绝

INV-O2C-003: 支付金额 = 订单应付
├─ 涉及流: 商流 + 资金流
├─ 校验时机: 支付时
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-O2C-004: 出库数量 <= 预占数量
├─ 涉及流: 物流
├─ 校验时机: 出库时
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-O2C-005: 签收数量 <= 出库数量
├─ 涉及流: 物流
├─ 校验时机: 签收时
├─ 实现: Invariant
└─ 破坏处理: 记录差异 + 人工处理

INV-O2C-006: 发票金额 <= 订单实付金额
├─ 涉及流: 商流 + 票税流
├─ 校验时机: 开票时
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-O2C-007: 结算金额 = 订单应付 - 已退款金额
├─ 涉及流: 商流 + 资金流
├─ 校验时机: 结算时
├─ 实现: Ledger + 对账
└─ 破坏处理: 差异告警 + 人工处理
```

### 1.4 异常收敛设计

| 异常场景 | 检测方式 | 收敛策略 | 责任人 |
|---|---|---|---|
| 支付超时 | 定时任务查询 | 对账确认+转人工 | 财务 |
| 库存预占失败 | 实时返回 | 提示客户重试 | 客服 |
| 发货失败 | 状态监控 | 重试+告警 | 运营 |
| 物流轨迹丢失 | 物流接口轮询 | 主动联系物流 | 客服 |
| 签收异常 | 客户反馈/对账 | 人工处理 | 客服 |
| 发票开具失败 | 重试+告警 | 人工处理 | 财务 |
| 结算金额差异 | 对账任务 | 差异排查+调整 | 财务 |

## 场景二：P2P 全链路（采购到付款）

### 2.1 场景概述

```text
采购申请 → 审批 → 下达订单 → 供应商发货 → 收货检验 → 入库 → 发票处理 → 付款 → 核销

涉及业务流：
- 商流：采购申请、供应商管理、合同、订单
- 物流：收货、检验、入库
- 资金流：付款、结算
- 成本流：入库成本、成本归集
- 票税流：发票、认证
- 会计流：应付、凭证
- 质量流：来料检验
```

### 2.3 关键规则详细设计

#### 2.3.1 三单匹配（商流+票税流+资金流）

```text
ThreeWayMatchingPolicy

输入：
├─ 采购订单（PO）
│   ├─ 供应商
│   ├─ 物料
│   ├─ 数量
│   ├─ 单价
│   └─ 金额
├─ 收货单（GR）
│   ├─ 供应商
│   ├─ 物料
│   ├─ 收货数量
│   └─ 收货日期
└─ 供应商发票（Invoice）
    ├─ 供应商
    ├─ 物料
    ├─ 数量
    ├─ 单价
    ├─ 税率
    └─ 金额

匹配规则（Decision Table）：

| 供应商 | 物料 | 数量差异 | 单价差异 | 金额差异 | 决策 |
|---|---|---|---|---|---|
| 匹配 | 匹配 | 无 | 无 | 无 | 通过 |
| 匹配 | 匹配 | ≤容差 | 无 | ≤容差 | 通过（记录差异） |
| 匹配 | 匹配 | >容差 | 任意 | 任意 | 拒绝（需审批） |
| 匹配 | 匹配 | 任意 | >容差 | 任意 | 拒绝（需审批） |
| 匹配 | 不匹配 | 任意 | 任意 | 任意 | 拒绝（需审批） |
| 不匹配 | 任意 | 任意 | 任意 | 任意 | 拒绝 |

> 决策口径说明（防止误读为矛盾）：`供应商不匹配 → 直接拒绝`，因为主体不一致属于硬性不符（收到的货可能来自未授权供应商），不允许通过审批补洞；`物料不匹配 → 拒绝（需审批）`，因为物料不一致常见于"可用等价/替代物料或工程变更"场景，可经采购/技术审批后放行。本质差异是**主体不符不可修复，物料不符可裁决修复**。

匹配结果（DecisionResult）：
├─ status: PASS / PASS_WITH_DIFFERENCE / REJECT
├─ matchedFields: [...]
├─ differences: [...]
├─ allowedActions: ["APPROVE", "REJECT", "REQUEST_CORRECTION"]
└─ reasonCode: [...]

容差政策（Policy）：
├─ 数量容差: ±2%
├─ 单价容差: ±0.01元
└─ 金额容差: ±10元
```

#### 2.3.2 来料检验（质量流）

```text
IncomingInspectionPolicy

Step 1: 确定检验方案（Specification）
├─ 全检条件：金额>10万 / 高风险物料 / 新供应商
├─ 抽检条件：常规物料 / 老供应商
└─ 免检条件：认证供应商 / 历史合格率>99%

Step 2: 执行检验（State Machine）
├─ 待检 → 检验中 → 已判定
│                 ↓
│           合格 / 不合格 / 让步接受

Step 3: 不合格处理（Policy）
├─ 退货：供应商承担运费
├─ 返工：供应商负责返工后重新送货
├─ 让步接受：需采购总监审批，价格扣减5%
└─ 降级使用：需技术和质量部门审批

Step 4: 检验记录（Ledger）
├─ 检验批次
├─ 抽样数量
├─ 不合格数量
├─ 判定结果
└─ 处理方式

不变量（Invariant）：
├─ 合格数量 <= 收货数量
├─ 让步接受记录有审批
└─ 退货数量 <= 不合格数量
```

#### 2.3.3 付款执行（资金流）

```text
PaymentExecutionSaga（采购侧）

State Machine:
PENDING → APPROVED → PROCESSING → COMPLETED
              ↓              ↓
          REJECTED      FAILED → COMPENSATING → COMPENSATED

Step 1: 付款申请（Specification）
├─ 入库已完成
├─ 发票已接收
├─ 三单匹配通过
└─ 付款金额 <= 应付金额

Step 2: 付款审批（Decision Table + RBAC）
├─ ≤ 5万 → 财务经理
├─ 5-50万 → 财务经理 + 财务总监
└─ > 50万 → 财务经理 + 财务总监 + CFO

Step 3: 执行付款（Saga）
├─ 生成付款单
├─ 发起银行转账
├─ 等待银行回执
└─ 更新付款状态

Step 4: 付款成功处理
├─ 更新付款单状态
├─ 核销应付账款（Ledger）
├─ 记录付款凭证
└─ 发送付款成功通知

Step 5: 付款失败处理
├─ 标记失败
├─ 重新发起（限3次）
└─ 转人工处理

不变量（Invariant）：
├─ 付款金额 <= 应付金额
├─ 累计付款 <= 应付总额
└─ 付款对象 = 合同供应商
```

### 2.4 跨流不变量

```text
P2P跨流不变量清单

INV-P2P-001: 采购订单金额 = 收货单金额（允许合理差异）
├─ 涉及流: 商流 + 物流
├─ 校验时机: 收货时
├─ 实现: Decision Table（容差内通过）
└─ 破坏处理: 差异告警 + 审批

INV-P2P-002: 收货单金额 = 发票金额（允许合理差异）
├─ 涉及流: 物流 + 票税流
├─ 校验时机: 发票接收时
├─ 实现: Decision Table（三单匹配）
└─ 破坏处理: 拒绝 + 需修正

INV-P2P-003: 入库成本 = 采购订单价格 + 合理费用
├─ 涉及流: 物流 + 成本流
├─ 校验时机: 入库时
├─ 实现: Calculation + Policy
└─ 破坏处理: 成本差异分析

INV-P2P-004: 付款金额 <= 应付金额
├─ 涉及流: 资金流 + 会计流
├─ 校验时机: 付款时
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-P2P-005: 应付核销金额 = 付款金额
├─ 涉及流: 资金流 + 会计流
├─ 校验时机: 核销时
├─ 实现: Ledger
└─ 破坏处理: 差异告警

INV-P2P-006: 库存金额 = 采购入库金额
├─ 涉及流: 物流 + 成本流 + 会计流
├─ 校验时机: 入库时、对账时
├─ 实现: Ledger + 对账
└─ 破坏处理: 差异排查
```

### 3.3 关键规则详细设计

#### 3.3.1 会员权益模型（Agreement-Policy-Entitlement）

```text
会员权益三层模型

Layer 1: Agreement（协议层）
├─ 会员等级：普通、银卡、金卡、钻石
├─ 有效期：2026-01-01 至 2026-12-31
├─ 权益套餐：基础套餐 / 高级套餐 / 尊享套餐
└─ 来源：注册赠送 / 购买升级 / 活动赠送

Layer 2: Policy（政策层）
├─ 每月发放：2张优惠券 / 1次保洁服务 / 0积分
├─ 发放条件：会员等级 + 活跃度
├─ 使用限制：限指定商品 / 限指定门店 / 不可叠加
├─ 有效期限：发放后30天内 / 每月1-5号可用
└─ 版本管理：政策可变更，历史权益按原政策

Layer 3: Entitlement（权益层）
├─ EntitlementId: ENT-2026-XXXXX
├─ Type: 优惠券 / 服务 / 积分
├─ Source: 权益套餐 + 发放批次
├─ Quota: 剩余次数/金额
├─ ValidFrom: 2026-07-01
├─ ValidTo: 2026-07-31
├─ Status: AVAILABLE / RESERVED / USED / EXPIRED / CANCELLED
└─ History: 发放记录、使用记录

关系：
Agreement
  ├─ 1:N Policy（不同等级有不同政策）
  └─ 1:N Entitlement（具体权益实例）
```

#### 3.3.2 权益使用流程

```text
EntitlementUsageFlow

Step 1: 资格判断（Specification）
├─ 会员状态有效
├─ 权益未过期
├─ 权益状态 = AVAILABLE
├─ 权益剩余次数 > 0
└─ 满足使用条件（如订单金额门槛）

Step 2: 权益预占（Reservation）
├─ 预占键: entitlementId + orderId
├─ 预占数量: 使用1次 / 抵扣X元
├─ 预占过期: 订单超时未支付自动释放
└─ 状态: AVAILABLE → RESERVED

Step 3: 履约执行（视权益类型）
├─ 优惠券：订单金额扣减
├─ 服务：派单到服务商
└─ 积分：积分扣减

Step 4: 核销确认（Ledger）
├─ 权益使用记录
├─ 权益剩余次数扣减
├─ 订单优惠记录
└─ 状态: RESERVED → USED

Step 5: 异常处理
├─ 订单取消：释放预占 RESERVED → AVAILABLE
├─ 服务取消：释放预占 + 退换权益
└─ 超时：定时任务释放预占

不变量（Invariant）：
├─ 使用次数 <= 权益总次数
├─ 抵扣金额 <= 权益额度
├─ 权益状态转换合法
└─ 权益不能超发
```

### 3.4 跨流不变量

```text
会员权益跨流不变量清单

INV-MBR-001: 权益使用次数 <= 权益总次数
├─ 涉及流: 商流
├─ 校验时机: 使用时
├─ 实现: Invariant + Quota
└─ 破坏处理: 拒绝

INV-MBR-002: 权益抵扣金额 <= 订单优惠金额
├─ 涉及流: 商流（订单）
├─ 校验时机: 核销时
├─ 实现: Invariant
└─ 破坏处理: 拒绝

INV-MBR-003: 权益退款后恢复原权益状态
├─ 涉及流: 商流 + 资金流
├─ 校验时机: 退款时
├─ 实现: Ledger + 逆向逻辑
└─ 破坏处理: 权益异常 + 告警

INV-MBR-004: 过期权益不可使用
├─ 涉及流: 商流
├─ 校验时机: 使用时
├─ 实现: Specification
└─ 破坏处理: 拒绝
```

## 总结

### 场景对比

| 维度 | O2C | P2P | 会员权益 |
|---|---|---|---|
| 核心流 | 商+物流+资金+会计+票税 | 商+物流+资金+成本+票税+会计 | 商+物流/履约+资金 |
| 主要模型 | Pipeline+Reservation+Saga | Policy+DecisionTable+Saga | A-P-E+Quota+Ledger |
| 跨流复杂度 | 高 | 高 | 中 |
| 不变量数量 | 7 | 6 | 4 |
| Saga数量 | 2 | 2 | 1 |

### 模型选择规律

1. **计算型规则** → Pipeline + Strategy
2. **资格判断** → Specification
3. **裁决决策** → Decision Table
4. **资源预占** → Quota + Reservation
5. **外部调用** → Saga
6. **生命周期** → State Machine
7. **价值追溯** → Ledger
8. **政策组合** → Policy Object
9. **权益管理** → Agreement-Policy-Entitlement
10. **底线校验** → Invariant
