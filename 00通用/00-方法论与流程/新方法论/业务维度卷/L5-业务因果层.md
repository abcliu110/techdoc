# L5 业务因果层

> **分析层次 5**：深入到业务决策背后的"为什么"——业务动因、组织塑形、历史路径依赖。

---

## 1. 层级目标

**在 L5，分析者要回答以下问题：**

- 业务决策背后的**业务原因**是什么（非技术原因）？
- **组织结构**如何塑形业务？
- **历史路径依赖**如何影响当前业务？
- 业务的**隐性约束**是什么（业务方自己都没意识到的约束）？
- 业务的**真实目标**是什么（业务方嘴上说的 vs 实际想要的）？

---

## 2. 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | L1-L4 所有产出 + Q2 三类成分的深度分析 + 组织背景 + 历史背景 |
| **输出** | 业务因果链 + 组织塑形分析 + 路径依赖图 + 隐性约束清单 + 真实目标识别 |

---

## 3. 核心操作 1：业务因果链分析

### 3.1 因果链的基本结构

```
业务结果（What）
    ↑
业务动因（Why）
    ↑
业务背景（Context）
    ↑
历史路径（Path）
```

### 3.2 因果链的层级

#### 表层因果
**定义：** 业务方明确表达的原因。
**示例：** "我们设置这个规则是因为监管要求。"
**特点：** 容易识别，但可能不是真实原因。

#### 中层因果
**定义：** 业务方不完全表达但实际起作用的原因。
**示例：** "监管要求是表面原因，真实原因是老板担心被监管处罚。"
**特点：** 需要深入访谈才能识别。

#### 深层因果
**定义：** 业务方自己都没意识到的原因。
**示例：** "老板担心被处罚，是因为过去的某次处罚让他失去了重要客户。"
**特点：** 需要历史访谈、组织分析才能识别。

### 3.3 因果链分析方法

#### 方法 1：5 Why 分析法

**步骤：** 对每个业务决策，连续追问 5 个"为什么"。

**示例（POS 餐饮为什么设置"满 100 元才能用券"？）**

| 层级 | 问题 | 回答 |
|------|------|------|
| Why 1 | 为什么设置满 100 元门槛？ | 为了控制优惠成本 |
| Why 2 | 为什么控制优惠成本？ | 因为利润率不高，优惠太多会亏损 |
| Why 3 | 为什么利润率不高？ | 因为原材料成本上涨，但菜品价格不能涨 |
| Why 4 | 为什么菜品价格不能涨？ | 因为周边竞品价格低，涨价会流失顾客 |
| Why 5 | 为什么周边竞品价格低？ | 因为新开的店在做价格战，我们被动了 |

**深层因果：** 设置满 100 元门槛的真实原因是**被动应对竞品价格战**。

#### 方法 2：因果图法（鱼骨图）

**结构：** 业务结果 → 多条业务动因 → 业务背景 → 历史路径

**示例（POS 餐饮订单错误率高的因果图）**

```
订单错误率高
    │
    ├─ 原因 1：服务员操作不熟练
    │       │
    │       └─ 背景：服务员培训时间短
    │              │
    │              └─ 历史：人手不足，无法系统培训
    │
    ├─ 原因 2：系统交互不友好
    │       │
    │       └─ 背景：界面设计复杂
    │              │
    │              └─ 历史：早期系统设计粗糙，未迭代
    │
    ├─ 原因 3：菜单信息不一致
    │       │
    │       └─ 背景：菜单变更频繁
    │              │
    │              └─ 历史：菜品更新机制不完善
    │
    └─ 原因 4：顾客临时改单
            │
            └─ 背景：顾客犹豫不决
                   │
                   └─ 历史：餐厅氛围匆忙，顾客来不及决定
```

#### 方法 3：反事实分析法

**步骤：** 对每个业务决策，问"如果不这样，会怎样？"

**示例（POS 餐饮为什么要设计成"服务员代为下单"而不是"顾客自助下单"？）**

- 反事实 1：不这样（顾客自助下单）→ 节省人力
- 反事实 2：不这样（顾客自助下单）→ 顾客点错率高
- 反事实 3：不这样（顾客自助下单）→ 失去服务员推荐高利润菜品的机会

**深层因果：** 设计为"服务员代为下单"的真实原因是**希望通过服务员推荐提升客单价**。

## 4. 核心操作 2：组织塑形分析

### 4.1 组织塑形的含义

**组织塑形：** 业务的形态、流程、规则很大程度上是由**组织结构**决定的，而不是由业务本身决定的。

**核心观点：** 组织结构是业务形态的"塑形者"，业务分析必须理解组织。

### 4.2 组织塑形的具体表现

| 组织特征 | 业务塑形表现 |
|---------|------------|
| **层级数** | 业务审批层级数 = 组织层级数 |
| **部门划分** | 业务模块划分 ≈ 部门划分 |
| **汇报关系** | 业务决策权 ≈ 汇报关系 |
| **绩效考核** | 业务指标 ≈ 绩效考核指标 |
| **历史包袱** | 业务规则 ≈ 组织历史包袱 |
| **人事变更** | 业务变更 ≈ 人事变更 |

### 4.3 组织塑形的分析维度

#### 维度 1：组织架构映射

**步骤：**
1. 画出组织架构图
2. 识别业务审批层级
3. 对比组织架构与业务审批层级

**示例（POS 餐饮连锁组织架构）：**

```
集团总部
    │
    ├── 区域经理（A 区域）
    │       │
    │       ├── 店长（门店 1）
    │       │       │
    │       │       ├── 服务员
    │       │       ├── 收银员
    │       │       └── 厨师
    │       │
    │       └── 店长（门店 2）
    │               │
    │               └── ...
    │
    └── 区域经理（B 区域）
            │
            └── ...
```

**业务审批层级：** 顾客 → 服务员 → 收银员 → 店长 → 区域经理 → 总部

**问题：** 业务审批层级是否与组织层级一致？如果不一致，说明组织塑形出现问题。

#### 维度 2：部门边界映射

**步骤：**
1. 识别业务子系统边界
2. 识别部门边界
3. 对比两者

**示例：**
- 业务子系统：订单、库存、财务、人事
- 部门划分：运营部、仓储部、财务部、人事部
- 一致性：高（每个子系统对应一个部门）

**问题：** 业务子系统与部门是否对齐？如果不对齐，业务协作会出现跨部门问题。

#### 维度 3：绩效映射

**步骤：**
1. 识别业务关键指标（KPI）
2. 识别部门绩效指标
3. 对比两者

**示例：**
- 业务指标：订单完成率、客单价、退款率
- 部门绩效：服务员（订单完成率）、收银员（客单价）、店长（综合）
- 一致性：基本一致

**问题：** 业务指标与部门绩效是否对齐？如果不对齐，会出现"指标冲突"——业务想做 A，部门想做 B。

### 4.4 组织塑形的反模式

#### 反模式 1：组织调整不匹配业务调整
- **表现：** 组织重组了，但业务系统没有调整
- **后果：** 业务效率下降、沟通成本上升

#### 反模式 2：业务调整不匹配组织能力
- **表现：** 业务系统设计很先进，但组织跟不上
- **后果：** 业务系统用不起来，组织抵触

#### 反模式 3：组织塑形过度
- **表现：** 业务完全按照组织设计，没有考虑业务本身的逻辑
- **后果：** 业务效率低下，但组织协调顺畅

## 5. 核心操作 3：路径依赖分析

### 5.1 路径依赖的含义

**路径依赖：** 业务当前的状态很大程度上由**过去的关键决策**决定，即使这些决策在当时看来是合理的。

**核心观点：** 业务的现状是历史的累积，不能简单评判"对错"。

### 5.2 路径依赖的识别

#### 识别方法 1：历史追溯法

**步骤：** 追溯每个业务规则的产生历史。

**示例（POS 餐饮菜品字段"是否主推"）**
- 历史：2019 年店长要求增加此字段，用于运营推荐
- 当下：字段还在使用，但很少用
- 路径依赖：保留字段是为了不破坏现有数据

#### 识别方法 2：决策点反推法

**步骤：** 识别业务的关键决策点，反推决策的影响。

**示例（POS 餐饮会员系统设计决策点）**
- 2018 年决策：会员等级只用积分，不引入成长值
- 影响：现在想引入成长值，必须重构会员表
- 路径依赖：会员等级规则受到 2018 年决策的约束

### 5.3 路径依赖的强度

| 强度 | 描述 | 改造成本 |
|------|------|---------|
| **极强** | 涉及核心数据、核心接口、核心流程 | 极高（必须迁移数据）|
| **强** | 涉及重要规则、重要角色 | 高（必须改规则）|
| **中** | 涉及次要数据、次要规则 | 中（局部改造）|
| **弱** | 涉及临时规则、临时角色 | 低（可直接改）|

### 5.4 路径依赖的应对

| 路径依赖 | 应对策略 |
|---------|---------|
| **极强** | 必须保留兼容，新功能用新接口 |
| **强** | 谨慎改造，先做兼容层 |
| **中** | 局部改造，渐进替换 |
| **弱** | 直接改造 |

## 6. 核心操作 4：隐性约束识别

### 6.1 隐性约束的特征

- 业务方不会主动提到
- 违反约束业务方会强烈反应
- 约束本身没有被明文记录

### 6.2 隐性约束的来源

| 来源 | 描述 |
|------|------|
| **行业惯例** | 行业内默认的规则 |
| **组织文化** | 组织内部约定俗成的规则 |
| **政治因素** | 受组织内部人际关系影响的规则 |
| **历史教训** | 曾经的失败经验形成的规则 |
| **隐性目标** | 业务方没说但实际想要的 |

### 6.3 隐性约束的识别方法

#### 方法 1：异常反应观察法

**步骤：** 观察业务方对异常情况的反应，识别隐性约束。

**示例：** 业务方强烈反对删除某个字段 → 可能是隐性约束（虽然没用，但不能删）。

#### 方法 2：跨场景对比法

**步骤：** 对比业务方在不同场景下的反应，识别隐性约束。

**示例：** 业务方对 A 类型错误宽容，对 B 类型错误严厉 → B 类型错误背后可能有隐性约束。

#### 方法 3：第三方访谈法

**步骤：** 访谈业务方的同事、上级、下级，识别业务方自己都没意识到的约束。

**示例：** 访谈店长的上级，发现店长设置某个规则是为了完成上级的考核。

### 6.4 隐性约束的处理原则

- **不暴露：** 隐性约束通常不适合暴露在文档里
- **不绕过：** 绕过隐性约束会带来不可预期的后果
- **不强化：** 不要把隐性约束变成显性约束
- **记录在案：** 把隐性约束记录在内部文档里，供团队参考

## 7. 核心操作 5：真实目标识别

### 7.1 真实目标的层级

#### 层级 1：表面目标
**定义：** 业务方明确表达的目标。
**示例：** "我们做会员系统是为了提升顾客粘性。"

#### 层级 2：业务目标
**定义：** 业务方想达成的业务结果。
**示例：** "提升顾客粘性是为了让顾客复购，减少拉新成本。"

#### 层级 3：组织目标
**定义：** 业务方所在的组织想达成的目标。
**示例：** "减少拉新成本是为了让今年的利润达标。"

#### 层级 4：个人目标
**定义：** 业务方个人想达成什么（晋升、奖金、稳定）。
**示例：** "利润达标是为了让老板拿到今年的奖金。"

### 7.2 真实目标的识别方法

#### 方法 1：层层追问法

**步骤：** 从表面目标开始，连续追问"这个目标是为了什么？"

#### 方法 2：决策反推法

**步骤：** 观察业务方在资源有限时的优先级，反推真实目标。

**示例：** 业务方对某些功能积极投入资源，对其他功能消极 → 投入资源的功能才是真实目标。

#### 方法 3：考核指标法

**步骤：** 业务方的考核指标往往反映真实目标。

### 7.3 真实目标与业务设计的关系

- **表面目标：** 用于业务宣传
- **业务目标：** 用于业务设计
- **组织目标：** 用于架构决策
- **个人目标：** 用于沟通协调

**关键原则：** 业务设计必须满足**业务目标**，满足其他目标但违背业务目标的设计是无意义的。

## 11. L5 的特殊地位

L5 是**5 个分析层次中最深的一层**，也是**最难被业务方接受的一层**。

| L5 的难点 | 描述 |
|----------|------|
| **隐性内容多** | 大量内容是业务方自己都没意识到的 |
| **触及敏感** | 可能触及组织内部的政治问题 |
| **主观性强** | 缺乏客观证据，多基于访谈推断 |
| **风险大** | 如果分析错误，可能损害团队信任 |

**关键原则：** L5 的分析必须谨慎使用，只在内部讨论，不轻易外传。
