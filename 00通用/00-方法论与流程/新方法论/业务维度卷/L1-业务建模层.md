# L1 业务建模层

> **分析层次 1**：识别业务的 6 个核心要素，并建立业务概念模型。

---

## 1. 层级目标

**在 L1，分析者要回答以下问题：**

- 业务由哪些**核心概念**构成？
- 这些概念之间的**关系**是什么？
- 哪些概念是**核心实体**（有独立生命周期）？
- 哪些概念是**值对象**（无独立生命周期）？
- 哪些概念是**领域事件**（业务状态变化的通知）？
- 业务边界在哪里？**限界上下文**是什么？

---

## 2. 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | Q1 的 6 要素（主体、目标、规则、协作、时序、视角）|
| **输出** | 业务概念模型（实体、值对象、聚合、限界上下文）|

---

## 3. 核心操作：6 要素提取

### 3.1 提取主体（Who）

**目标：** 识别业务中所有参与角色。

**步骤：**
1. 列出所有直接参与者（人、组织、系统）
2. 列出所有间接参与者（监管、审计、第三方）
3. 识别参与者的**角色标签**（不是具体的人，是角色）

**典型主体提取：**

| 业务类型 | 典型主体 |
|---------|---------|
| POS 餐饮 | 顾客、服务员、收银员、厨师、店长 |
| 电商订单 | 买家、卖家、物流商、平台运营、客服 |
| 银行存取款 | 客户、柜员、风控、合规、监管 |
| ERP 采购 | 采购员、供应商、财务、仓库管理员 |
| BI 报表 | 决策者、分析师、数据工程师、运营 |
| SaaS 多租户 | 租户管理员、普通用户、平台运营、审计 |

**常见错误：**
- 把具体的人当主体（"张三"）而不是角色（"收银员"）
- 遗漏间接参与者（只看到直接操作者，忽略监管/审计）
- 把主体和角色混用（"顾客"和"买家"是不同角色）

### 3.2 提取目标（What）

**目标：** 识别每个主体想达成什么结果。

**步骤：**
1. 对每个主体，问："这个主体参与这个业务，想得到什么？"
2. 区分**主要目标**（核心价值）和**次要目标**（辅助价值）
3. 识别目标之间的**冲突**（主体 A 的目标和主体 B 的目标矛盾）

**典型目标提取：**

| 主体 | 主要目标 | 次要目标 |
|------|---------|---------|
| 顾客（餐饮）| 完成点餐和结账 | 快速出品、发票获取 |
| 服务员（餐饮）| 完成服务任务 | 减少差错、获得好评 |
| 店长（餐饮）| 门店正常运营 | 成本控制、员工管理 |
| 买家（电商）| 收到商品 | 省钱、快速配送 |
| 卖家（电商）| 收到货款 | 减少退款、获得好评 |
| 客户（银行）| 完成存取款 | 安全、隐私 |

### 3.3 提取规则（Rules）

**目标：** 识别业务必须遵守的约束。

**步骤：**
1. 列出所有**强制规则**（不遵守业务无法进行）
2. 列出所有**建议规则**（不遵守业务可以进行但有风险）
3. 区分**显性规则**（明文规定）和**隐性规则**（行业惯例/潜规则）

**典型规则提取：**

| 业务类型 | 典型显性规则 | 典型隐性规则 |
|---------|------------|------------|
| 餐饮 POS | 满 100 元才能用券 | 熟客可以赊账 |
| 电商订单 | 7 天无理由退货 | 超时未付款自动取消 |
| 银行存取 | 反洗钱核查 | 大额存款需要提前预约 |
| ERP 采购 | 三级审批 | 供应商优先选择关系好的 |

### 3.4 提取协作（Collaboration）

**目标：** 识别主体之间如何配合。

**步骤：**
1. 识别**直接协作**（主体之间有直接交互）
2. 识别**间接协作**（主体之间通过系统/中间件交互）
3. 识别协作的**发起方**和**响应方**
4. 识别协作的**频率**（一次性/周期性/实时）

**典型协作提取：**

| 业务类型 | 典型协作 |
|---------|---------|
| 餐饮 POS | 顾客→服务员（点餐）→收银员（结账）→厨师（制作） |
| 电商订单 | 买家→卖家（下单）→物流商（配送）→买家（签收） |
| 银行存取 | 客户→柜员（操作）→风控（审核）→系统（记录） |
| ERP 采购 | 采购员→供应商（询价）→财务（审批）→仓库（收货） |

### 3.5 提取时序（Timing）

**目标：** 识别业务的时间维度。

**步骤：**
1. 识别**有效期**（业务规则/数据的生效和失效时间）
2. 识别**时段**（业务在不同时间段的规则不同）
3. 识别**版本**（业务规则/数据的版本迭代）
4. 识别**节奏**（业务的执行频率和周期）

**典型时序提取：**

| 业务类型 | 典型时序 |
|---------|---------|
| 餐饮 POS | 营业日（00:00-24:00）、班次（早/中/晚）、节假日特殊规则 |
| 电商订单 | 大促期间规则（双十一）、日常规则、商品上下架时间 |
| 银行存取 | 工作时间（09:00-17:00）、节假日、年度结息日 |
| ERP 采购 | 月度采购计划、季度评审、年度合同 |
| SaaS | 合同有效期（年）、试用期（30 天）、计费周期（自然月） |

### 3.6 提取视角（Viewpoint）

**目标：** 识别谁在观察这个业务。

**步骤：**
1. 识别**直接用户**（直接操作系统的人）
2. 识别**间接用户**（不直接操作但受业务影响的人）
3. 识别**监管视角**（监管机构/审计人员的观察角度）
4. 识别**管理视角**（管理层的观察角度）

**典型视角提取：**

| 业务类型 | 典型视角 |
|---------|---------|
| 餐饮 POS | 收银员视角（操作）、店长视角（管理）、顾客视角（体验）、老板视角（盈利） |
| 电商订单 | 买家视角（购物）、卖家视角（销售）、平台视角（治理）、监管视角（合规） |
| 银行存取 | 柜员视角（操作）、客户视角（服务）、风控视角（合规）、监管视角（审计） |
| ERP 采购 | 采购员视角（执行）、财务视角（成本）、管理者视角（效率）、审计视角（合规） |

## 4. 核心操作：建立业务概念模型

### 4.1 概念分类

从 6 要素中提取的概念，必须分类为：

| 概念类型 | 定义 | 判定标准 |
|---------|------|---------|
| **实体** | 有独立生命周期，需要持久化 | 有唯一标识（ID），生命周期跨越多个业务操作 |
| **值对象** | 无独立生命周期，描述实体的特征 | 无唯一标识，随实体存在 |
| **聚合** | 一组相关实体和值对象的组合 | 有统一的根实体，内部一致性强 |
| **领域事件** | 业务状态变化的通知 | 描述"发生了什么"，不描述"要做什么" |
| **限界上下文** | 业务边界的划分 | 概念在边界内有统一语义，跨边界语义可能变化 |

### 4.2 典型业务的概念模型

#### POS 餐饮概念模型

```
聚合：订单
  实体：订单（OrderId）
  值对象：菜品明细、价格、桌台号
  领域事件：OrderCreated、OrderPaid、OrderRefunded

聚合：桌台
  实体：桌台（TableId）
  值对象：桌台状态（空闲/占用/清理中）、容纳人数
  领域事件：TableOccupied、TableCleared

聚合：会员
  实体：会员（MemberId）
  值对象：等级、积分、余额
  领域事件：MemberRegistered、PointsEarned、BalanceRecharged

限界上下文：
  点餐上下文：订单、菜品
  桌台上下文：桌台、区域
  会员上下文：会员、积分、等级
  收银上下文：支付、退款、优惠
```

#### 电商订单概念模型

```
聚合：订单
  实体：订单（OrderId）
  值对象：商品明细、收货地址、发票信息
  领域事件：OrderCreated、OrderPaid、OrderShipped、OrderCompleted、OrderCancelled

聚合：商品
  实体：商品（ProductId）、SKU（SKUid）
  值对象：价格、库存、规格
  领域事件：ProductCreated、PriceChanged、StockReserved、StockReleased

聚合：会员
  实体：会员（MemberId）
  值对象：等级、成长值、优惠券
  领域事件：MemberRegistered、MemberUpgraded

限界上下文：
  商品上下文：商品、SKU、库存、价格
  交易上下文：订单、支付、优惠券
  会员上下文：会员、等级、积分
  物流上下文：配送、物流跟踪
```

## 5. 分析方法

### 5.1 访谈法

**适用场景：** 有明确的业务负责人，可以直接访谈。

**访谈问题清单：**

| 问题类型 | 示例问题 |
|---------|---------|
| 主体 | "谁会使用这个系统？" |
| 目标 | "用户使用这个系统想达成什么？" |
| 规则 | "做这件事有什么硬性要求？" |
| 协作 | "这件事需要哪些角色配合？" |
| 时序 | "这件事有时间要求吗？什么时候可以做？" |
| 视角 | "谁会关心这件事的结果？" |

### 5.2 代码反推法

**适用场景：** 无法直接访谈，需要从遗留系统代码反推业务模型。

**步骤：**
1. 识别核心实体类（带 Domain/Entity 注解的类）
2. 识别核心方法（业务动词，如 createOrder、payOrder）
3. 从方法参数反推输入/输出概念
4. 从方法内部逻辑反推业务规则
5. 从数据库表名反推实体和关系

**关键原则：** 代码反推只能得到**实现层面的概念模型**，不能直接得到**业务层面的概念模型**。必须经过业务术语翻译。

### 5.3 文档分析法

**适用场景：** 有历史文档（需求文档、用户手册、操作手册）。

**分析步骤：**
1. 提取文档中的**名词**（候选概念）
2. 提取文档中的**动词**（候选操作/事件）
3. 提取文档中的**形容词/副词**（候选规则/约束）
4. 识别名词之间的关系（has-a, is-a）
5. 识别动词的发起方和接收方（协作关系）

## 6. 典型错误与修正

### 错误 1：把技术实现当业务概念

| 错误 | 修正 |
|------|------|
| "OrderDO"（数据对象）| "订单"（业务实体）|
| "userId"（技术标识）| "顾客"（业务主体）|
| "status"（通用字段）| "订单状态"（具体业务状态）|

### 错误 2：把 UI 交互当业务概念

| 错误 | 修正 |
|------|------|
| "点击按钮"（UI 交互）| "提交订单"（业务操作）|
| "弹出框"（UI 形态）| "收款确认"（业务事件）|
| "页面跳转"（UI 行为）| "进入结账流程"（业务流程）|

### 错误 3：遗漏间接参与者和视角

| 遗漏 | 补充 |
|------|------|
| 只看到操作者 | 补充监管者、审计者 |
| 只看到前台视角 | 补充后台管理视角 |
| 只看到直接用户 | 补充间接受影响者 |

## 7. L1 的产出标准

### 7.1 概念清单

每个业务概念必须包含：

| 属性 | 说明 |
|------|------|
| **名称** | 业务术语，不是技术术语 |
| **类型** | 实体 / 值对象 / 聚合 / 领域事件 |
| **定义** | 一句话说明这个概念是什么 |
| **生命周期** | 创建、使用、销毁的边界 |
| **关系** | 与其他概念的关系（1:1, 1:N, N:N）|

### 7.2 限界上下文清单

每个限界上下文必须包含：

| 属性 | 说明 |
|------|------|
| **名称** | 业务术语 |
| **边界** | 包含哪些概念 |
| **输入** | 从其他上下文接收什么 |
| **输出** | 向其他上下文发送什么 |
| **核心概念** | 上下文内最重要的 1-3 个概念 |

### 7.3 概念关系图

用 UML 类图的简化版表示概念之间的关系：

- 实线箭头：关联（has-a）
- 三角箭头：泛化（is-a）
- 虚线箭头：依赖（uses-a）

## 8. 与其他层次的关系

| 层次 | 从 L1 得到什么 | 向 L1 反馈什么 |
|------|--------------|--------------|
| **L2 业务规则层** | L1 识别的概念是 L2 规则的载体 | L2 规则约束 L1 概念的关系 |
| **L3 业务流程层** | L1 识别的概念和协作是 L3 流程的节点 | L3 流程变化可能影响 L1 概念 |
| **L4 业务演化层** | L1 识别的概念是 Q2 历史分析的起点 | L4 发现的概念演化反哺 L1 |
| **L5 业务因果层** | L1 识别的概念是 L5 因果分析的载体 | L5 发现的概念原因反哺 L1 |

## 10. 业务对象分析方法（静态建模）

> **目的**：从业务概念模型进一步深入到对象的完整建模，回答"对象的具体特征是什么"。

### 10.1 分析维度清单

| 序号 | 维度 | 必须填 | 适用对象 | 说明 |
|------|------|-------|---------|------|
| 1 | 属性/字段 | ✓ | 全部 | 对象的数据 |
| 2 | 方法/操作 | ✓ | 全部 | 对象的行为 |
| 3 | 事件/状态变化 | ✓ | 全部 | 状态变化的发布 |
| 4 | 关系/关联 | ✓ | 全部 | 对象之间的关系 |
| 5 | 生命周期 | ✓ | 全部 | 创建→使用→销毁 |
| 6 | 状态机 | ✓ | 有状态的对象 | 状态转换规则 |
| 7 | 不变式/约束 | ✓ | 全部 | 业务约束 |
| 8 | 类型判定 | ✓ | 全部 | 实体/值对象/聚合根 |
| 9 | 聚合边界 | △ | 聚合根 | 事务边界 |
| 10 | 权限/可见性 | △ | 核心实体 | 谁能操作 |
| 11 | 并发控制 | △ | 核心实体 | 锁机制 |
| 12 | 持久化策略 | △ | 全部 | 存储方式 |
| 13 | 缓存策略 | △ | 核心实体 | 缓存机制 |
| 14 | 版本/历史 | △ | 核心实体 | 审计需求 |

> **说明**：✓ = 必须填，△ = 按需填

### 10.2 与6要素的对应关系

| 6要素 | 对象分析维度 | 说明 |
|-------|-------------|------|
| 资源 | 属性/字段 | 对象持有的数据 |
| 主体 | 权限/可见性 | 谁可以操作对象 |
| 目标 | 方法/操作 | 对象能做什么 |
| 规则 | 不变式/约束 | 对象必须遵守的规则 |
| 协作 | 关系/关联 | 对象之间的关系 |
| 时序 | 生命周期、状态机 | 对象的时间维度 |
| 信息 | 事件/状态变化 | 对象发布的事件 |

### 10.3 类型判定标准

| 类型 | 判定标准 | 示例 |
|------|---------|------|
| 实体 | 有唯一标识，有生命周期 | Order, Member, Product |
| 值对象 | 无唯一标识，不可变 | Money, Address, Color |
| 聚合根 | 实体的子集，作为事务边界 | Order（包含OrderDetail）|

### 10.4 对象分析方法执行步骤

1. **识别对象**：从代码/数据库/文档中识别所有业务对象
2. **类型判定**：判断每个对象是实体、值对象还是聚合根
3. **维度分析**：按维度逐一分析对象
4. **聚合划分**：识别聚合根和聚合边界
5. **关系建模**：绘制对象关系图

### 10.5 对象分析模板

```markdown
## Order（订单聚合根）

### 类型判定
| 判定项 | 结论 | 依据 |
|---------|------|------|
| 实体/值对象 | 实体 | 有唯一标识billNo |
| 聚合根/成员 | 聚合根 | 外部通过billNo引用 |

### 属性/字段
| 属性 | 类型 | 说明 | 约束 |
|------|------|------|------|
| billNo | String | 订单号 | PK，唯一 |
| status | OrderStatus | 状态 | 非空 |
| totalAmount | BigDecimal | 总额 | >= 0 |

### 方法/操作
| 方法 | 输入 | 输出 | 业务含义 |
|------|------|------|----------|
| create() | items[] | Order | 创建订单 |
| settle() | payment | void | 结账 |
| refund() | items[] | void | 退款 |

### 状态机
```
待结账 ──支付──► 已结账 ──退款──► 已退款
```

### 不变式/约束
| 约束 | 表达式 |
|------|--------|
| 实付不超过应付 | paidAmount <= totalAmount |

### 领域事件
| 事件 | 触发 | 数据 |
|------|------|------|
| OrderCreated | 创建成功 | {billNo, items} |
| OrderPaid | 结账成功 | {billNo, payment} |

### 关系/关联
| 类型 | 对象 | 说明 |
|------|------|------|
| has-many | OrderDetail | 订单明细 |
| has-one | Payment | 支付记录 |
```

## 11. 业务逻辑分析方法（动态建模）

> **目的**：分析业务的动态行为，回答"业务是怎么运作的"。

### 11.1 分析维度清单

| 序号 | 维度 | 必须填 | 说明 |
|------|------|-------|------|

### 11.2 决策分析示例

```markdown
## 优惠决策矩阵

| 用户等级 | 消费金额 | 可用优惠 |
|---------|---------|---------|
| 普通 | <100 | 无 |
| 普通 | 100-500 | 满100减10 |
| 普通 | >500 | 满100减15 |
| 银卡 | 任意 | 额外9.5折 |
| 金卡 | 任意 | 额外9折 |

决策规则：
- 优先级：会员折扣 > 满减优惠
- 互斥：优惠券与折扣二选一
```

### 11.3 场景矩阵示例

```markdown
## 退款场景矩阵

| 场景 | 订单状态 | 可退金额 | 手续费 | 处理方式 |
|------|----------|----------|--------|----------|
| 正常 | 已结账 | 100% | 0% | 原路返回 |
| 部分 | 已结账 | 按商品 | 0% | 原路返回 |
| 超时 | 已结账7天后 | 90% | 10% | 退至账户 |
| 风控 | 已结账 | 待定 | - | 人工审核 |
```

### 11.4 补偿事务分析示例

```markdown
## 订单取消补偿链

1. 释放库存（补偿：恢复库存）
2. 返还优惠（补偿：重新发放）
3. 退款支付（补偿：追款）
4. 发送通知（无补偿）

补偿原则：
- 按逆序执行
- 补偿失败告警
- 补偿次数限制（3次）
- 补偿幂等保证
```

### 11.5 业务逻辑分析方法执行步骤

1. **业务流程梳理**：从入口点开始，梳理所有可能路径
2. **决策点识别**：识别流程中的判断节点
3. **场景枚举**：列出正常场景和异常场景
4. **规则提取**：从流程中提取业务规则
5. **补偿链设计**：识别需要补偿的操作
