# L3 业务流程层

> **分析层次 3**：识别业务的全部执行路径，并建立流程模型。

---

## 1. 层级目标

**在 L3，分析者要回答以下问题：**

- 业务有哪几条**主流程**（正常路径）？
- 每个主流程有哪些**变体流**（分支路径）？
- 每个流程有哪些**异常流**（出错路径）？
- 每个流程有哪些**补偿流**（回滚路径）？
- 不同流程之间如何**对账**（数据一致性）？
- 流程之间的**时序关系**是什么？

---

## 2. 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | L1 的概念 + L2 的规则 + Q3 的流程复杂度 + Q4 的一致性/可观测性 |
| **输出** | 流程清单 + 流程图 + 变体表 + 异常处理表 + 补偿流表 + 对账流表 |

---

## 3. 流程的 5 类路径

### 3.1 主流程（Happy Path）
**定义：** 一切正常情况下的业务执行路径。

**特征：**
- 概率高（70%+ 业务走这条路径）
- 所有规则都校验通过
- 没有异常发生
- 没有人为中断

**示例（POS 餐饮主流程）：**
```
点餐 → 下单 → 厨房制作 → 出品 → 结账 → 收款 → 完成
```

### 3.2 变体流（Variant Path）
**定义：** 在不同业务变体下的执行路径。

**常见变体：**
- **场景变体**：新客 vs 老客、堂食 vs 外卖
- **时段变体**：平日 vs 节假日、大促 vs 日常
- **组织变体**：直营 vs 加盟、批发 vs 零售
- **状态变体**：首次下单 vs 复购、退款 vs 换货

**示例（POS 餐饮变体流）：**
- 堂食变体：点餐 → 下单 → 出品 → 结账 → 完成
- 外卖变体：点餐 → 下单 → 厨房制作 → 配送 → 完成
- 包间变体：预订 → 到店 → 点餐 → 下单 → 出品 → 结账 → 完成

### 3.3 异常流（Exception Path）
**定义：** 业务执行出错时的处理路径。

**异常类型：**
- **系统异常**：网络故障、服务宕机、超时
- **业务异常**：库存不足、余额不足、规则冲突
- **用户异常**：取消操作、修改订单、退出流程
- **外部异常**：支付失败、第三方接口超时、物流异常

**示例（POS 餐饮异常流）：**
- 支付失败：选择其他支付方式 → 重新支付
- 库存不足：菜品估清 → 引导顾客换菜
- 厨房缺货：通知服务员 → 引导顾客换菜或退款
- 网络故障：离线模式 → 恢复后补传

### 3.4 补偿流（Compensation Path）
**定义：** 已经执行的步骤需要回滚的处理路径。

**补偿类型：**
- **全量补偿**：整个业务完全回滚（如取消订单、退款）
- **部分补偿**：部分步骤回滚（如部分退款、个别菜品退菜）
- **状态补偿**：状态从 A → B → A 恢复（如订单取消、支付撤销）
- **资源补偿**：释放已占用的资源（如库存释放、座位释放）

**示例（POS 餐饮补偿流）：**
- 整单退款：所有菜品 → 已退 → 释放桌台 → 释放库存（如果占用）
- 部分退款：指定菜品 → 已退 → 其他菜品继续
- 反结账：恢复订单到未结账状态 → 重新结账
- 库存回滚：订单取消 → 释放预占库存

### 3.5 对账流（Reconciliation Path）
**定义：** 确保多系统、多方数据一致性的处理路径。

**对账类型：**
- **实时对账**：每笔交易立即核对（如支付成功后立即核对订单）
- **定时对账**：定时（如每日）批量核对（如日结对账）
- **差异处理**：发现不一致时的处理流程
- **追平机制**：数据追平的规则和优先级

**示例（POS 餐饮对账流）：**
- 订单支付 → 实时核对：金额、状态、支付方式
- 班次结束 → 班结对账：现金、银行卡、移动支付
- 日结结束 → 日结对账：所有订单、所有支付
- 月底对账：营业额、退款额、优惠额、税额

## 5. 关键流程的详细分析

### 5.1 关键流程的判定

不是所有流程都需要详细分析。判定标准：

| 判定因素 | 描述 |
|---------|------|
| **业务价值** | 流程涉及的业务价值大小（金额、用户数）|
| **发生频率** | 流程被执行的频率（每日、每周、每月）|
| **复杂度** | 流程本身的复杂度（步骤数、变体数）|
| **风险程度** | 流程出错的影响（金额、合规）|

**关键流程的特征：** 业务价值高 + 发生频率高 + 复杂度高 + 风险高。

### 5.2 关键流程的详细分析模板

| 字段 | 内容 |
|------|------|
| **流程名称** | 业务术语 |
| **流程目标** | 流程要达成什么 |
| **触发条件** | 什么情况下启动流程 |
| **前置条件** | 流程启动前必须满足的条件 |
| **主流程步骤** | 步骤 1, 步骤 2, 步骤 3... |
| **每个步骤的角色** | 谁负责这个步骤 |
| **每个步骤的输入** | 进入步骤的数据 |
| **每个步骤的输出** | 步骤产生的数据 |
| **每个步骤的规则** | 必须遵守的规则（引用 L2 规则编号）|
| **变体表** | 不同场景下的变体步骤 |
| **异常表** | 可能发生的异常和处理方法 |
| **补偿流** | 回滚的方法 |
| **对账流** | 数据一致性的保证 |
| **可观测点** | 监控/日志的关键节点 |

### 5.3 关键流程示例（POS 餐饮点餐流程）

| 字段 | 内容 |
|------|------|
| **流程名称** | 顾客点餐 |
| **流程目标** | 顾客成功下单，菜品进入厨房制作 |
| **触发条件** | 顾客就座后，服务员询问点餐 |
| **前置条件** | 桌台状态为空闲（已开台）|
| **主流程步骤** | 1. 服务员询问点餐 → 2. 顾客选择菜品 → 3. 服务员录入系统 → 4. 系统校验库存和估清 → 5. 订单提交 → 6. 订单送厨房 → 7. 厨房确认接收 |
| **角色** | 服务员（步骤 1-3）、系统（步骤 4-6）、厨房（步骤 7）|
| **变体** | - 新客：服务员引导注册会员<br>- VIP：服务员提示可用优惠券<br>- 大桌：服务员分批下单 |
| **异常** | - 估清：服务员引导换菜<br>- 系统故障：服务员手写下单<br>- 顾客改菜：服务员修改订单 |
| **补偿** | - 顾客取消菜品：服务员删除订单项<br>- 整单取消：服务员取消订单，释放桌台 |
| **对账** | - 订单与厨房显示一致<br>- 订单与桌台绑定一致 |
| **可观测点** | - 下单耗时（步骤 1-5）<br>- 厨房接收耗时（步骤 5-7）<br>- 估清发生频率 |

## 6. 流程复杂度评估

### 6.1 复杂度评估维度

| 维度 | 评估指标 |
|------|---------|
| **步骤数** | 主流程有多少个步骤 |
| **变体数** | 有多少种变体流 |
| **异常数** | 有多少种异常流 |
| **补偿路径数** | 有多少种补偿方式 |
| **角色数** | 涉及多少个角色 |
| **外部系统数** | 与多少外部系统交互 |

### 6.2 复杂度评分

| 评分 | 标准 |
|------|------|
| ★★★★★ | 步骤 > 20，变体 > 10，异常 > 10，多角色，多外部系统 |
| ★★★★ | 步骤 10-20，变体 5-10，异常 5-10 |
| ★★★ | 步骤 5-10，变体 2-5，异常 2-5 |
| ★★ | 步骤 < 5，变体 1-2，异常 1-2 |
| ★ | 单一线性流程 |

## 7. 流程分析的反模式

### 反模式 1：流程图只画主流程
- **表现**：只画 happy path，遗漏变体、异常、补偿
- **修正**：强制要求每条流程都要画出 5 类路径

### 反模式 2：流程与规则混杂
- **表现**：流程图中嵌入大量规则判断，流程和规则难以分离
- **修正**：流程图只描述"做什么"，规则引用 L2 的规则编号

### 反模式 3：流程图过细或过粗
- **表现**：流程图要么步骤过多（每个按钮一次），要么过粗（一句话描述整个流程）
- **修正**：流程粒度按"业务动作"划分，每个步骤是一个可观测的业务动作

### 反模式 4：补偿流缺失
- **表现**：只考虑正向流程，不考虑如何回滚
- **修正**：每条关键流程必须分析"如果中途出错怎么办"

## 8. 流程的可观测性

### 8.1 可观测性的 4 个层次

| 层次 | 描述 | 实现方式 |
|------|------|---------|
| **日志** | 关键步骤的日志记录 | 业务日志框架 |
| **监控** | 关键指标的实时监控 | 监控系统（如 Prometheus）|
| **追踪** | 单次业务请求的全链路追踪 | 分布式追踪（如 Jaeger）|
| **告警** | 异常情况的告警通知 | 告警系统（如 Alertmanager）|

### 8.2 流程的可观测点设计

每个关键流程必须有：

| 可观测点 | 说明 |
|---------|------|
| **入口埋点** | 流程开始的埋点 |
| **关键节点埋点** | 流程关键步骤的埋点 |
| **出口埋点** | 流程结束的埋点 |
| **异常埋点** | 流程异常的埋点 |
| **耗时埋点** | 关键步骤耗时的埋点 |
| **结果埋点** | 流程结果的埋点 |

### 8.3 可观测点的设计原则

- **不漏关键节点**：关键业务动作必须有埋点
- **不过度埋点**：每个动作都埋会导致性能问题和日志爆炸
- **埋点即业务**：埋点字段应该反映业务语义
- **可聚合**：埋点数据应该可以按维度聚合分析

## 10. 与其他层次的关系

| 层次 | 从 L3 得到什么 | 向 L3 反馈什么 |
|------|--------------|--------------|
| **L1 业务建模层** | L1 的概念是 L3 流程的节点 | L3 流程变化影响 L1 概念的关系 |
| **L2 业务规则层** | L2 规则是 L3 流程的约束 | L3 流程变化引入新规则 |
| **L4 业务演化层** | L3 流程是 L4 演化的载体 | L4 演化揭示流程的历史变化 |
| **L5 业务因果层** | L3 流程是 L5 因果的对象 | L5 因果解释流程的产生背景 |
