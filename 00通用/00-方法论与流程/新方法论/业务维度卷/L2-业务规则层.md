# L2 业务规则层

> **分析层次 2**：识别业务必须遵守的全部规则，并建立规则依赖图。

---

## 1. 层级目标

**在 L2，分析者要回答以下问题：**

- 业务必须遵守哪些**显性规则**？
- 业务隐含哪些**隐性规则**？
- 规则之间有哪些**依赖关系**？
- 规则之间存在哪些**冲突**？冲突如何解？
- 规则在不同业务场景下如何**变体**？

---

## 2. 输入与输出

| 项目 | 内容 |
|------|------|
| **输入** | L1 的概念清单 + Q3 的规则复杂度维度 + Q4 的完整性/一致性评价 |
| **输出** | 规则清单 + 规则依赖图 + 规则冲突解 + 规则变体矩阵 |

---

## 3. 核心操作 1：显性规则提取

### 3.1 显性规则的特征
- **明文存在**：写在文档、合同、法规、流程图里
- **可枚举**：可以被业务方口头列举出来
- **强约束**：违反规则会导致业务失败、合规问题、财务损失

### 3.2 提取步骤

| 步骤 | 描述 |
|------|------|
| 1. 收集文档 | 收集所有业务文档（需求文档、合同模板、SOP）|
| 2. 提取规则句 | 提取所有"必须、不能、应当、不应"的句式 |
| 3. 规则编号 | 给每条规则编号 |
| 4. 分类标签 | 给每条规则打分类标签（计费/库存/审批/合规等）|
| 5. 关联概念 | 关联到 L1 的概念 |

### 3.3 典型显性规则（POS 餐饮为例）

| 编号 | 规则 | 关联概念 |
|------|------|---------|
| R001 | 订单总价 = 所有菜品明细价格之和 | 订单、菜品 |
| R002 | 单笔订单满 100 元可使用满减券 | 订单、优惠券 |
| R003 | 满减券与折扣互斥，不可叠加 | 优惠券、折扣 |
| R004 | 会员卡余额支付不能超过订单总价 | 会员卡、订单 |
| R005 | 退菜必须填写原因（必填项）| 订单、退菜 |
| R006 | 整单退款必须在 7 天内 | 订单、退款 |
| R007 | 桌台未结账前不能重复开台 | 桌台、订单 |
| R008 | 班次交接必须清点现金 | 班次、现金 |

## 4. 核心操作 2：隐性规则提取

### 4.1 隐性规则的特征
- **不存在于文档**：没有明文，但实际业务中必须遵守
- **不可枚举**：业务方"知道"但说不出来
- **经验式约束**：违反规则不会立即报错，但会导致后续问题

### 4.2 提取方法

| 方法 | 描述 | 适用场景 |
|------|------|---------|
| **对比法** | 对比文档规则和实际行为，找差异 | 有完整文档的业务 |
| **专家访谈** | 找资深员工（操作员、班长）聊 | 有运营人员的业务 |
| **异常案例法** | 收集异常处理案例，反推规则 | 有工单/日志的业务 |
| **历史修复法** | 看历史 bug 修复记录，反推规则 | 有 bug 跟踪系统的业务 |

### 4.3 典型隐性规则（POS 餐饮为例）

| 编号 | 隐性规则 | 来源 |
|------|---------|------|
| I001 | 熟客可以赊账，记录在小黑本上 | 店员经验 |
| I002 | 厨房忙的时候，凉菜优先出 | 厨师经验 |
| I003 | 顾客投诉时，免费送饮料 | 店长经验 |
| I004 | 周末单量翻倍，需要提前备料 | 运营经验 |
| I005 | 收银员交接时，抹零头需要两人签字 | 财务经验 |
| I006 | 网络故障时，先记单后录入系统 | 应急预案 |

## 5. 核心操作 3：建立规则依赖图

### 5.1 依赖关系类型

| 依赖类型 | 含义 | 示例 |
|---------|------|------|
| **强依赖** | 规则 A 必须先于规则 B 校验 | "满 100 元才能用券" 强依赖 "订单总价计算" |
| **弱依赖** | 规则 A 和规则 B 都校验，但顺序无关 | "退款必须在 7 天内" 和 "退款必须填原因" |
| **互斥依赖** | 规则 A 和规则 B 不能同时成立 | "满减券与折扣互斥" |
| **条件依赖** | 规则 A 在某条件下依赖规则 B | "会员卡余额支付" 条件依赖 "会员卡余额充足" |

### 5.2 依赖图示例（POS 餐饮优惠券规则）

```
R002 满 100 元可用券 ──强依赖──→ R001 订单总价计算
R003 满减券与折扣互斥 ──互斥依赖──→ 折扣规则
R004 会员卡余额支付不能超过订单总价 ──强依赖──→ R001 + 会员卡余额查询
```

### 5.3 依赖图的作用

- **执行顺序推导**：强依赖规则必须按顺序执行
- **冲突检测**：互斥依赖规则在同一订单上不能同时生效
- **影响范围分析**：修改一条规则时，必须找出所有依赖它的规则

## 6. 核心操作 4：规则冲突解

### 6.1 冲突类型

| 冲突类型 | 含义 | 示例 |
|---------|------|------|
| **直接冲突** | 两条规则直接矛盾 | "满减券与折扣互斥"（明确禁止） |
| **隐式冲突** | 两条规则在特定场景下矛盾 | "7 天无理由退货" 与 "已使用的券不退" |
| **范围冲突** | 两条规则覆盖范围不一致 | "所有商品满减" 与 "生鲜不参与满减" |
| **时序冲突** | 两条规则在不同时间下矛盾 | "促销价" 与 "会员价" 在不同促销期间 |

### 6.2 冲突解原则

按 Q4 的评价维度优先级矩阵：

1. **完整性优先**：确保所有场景都有规则覆盖
2. **一致性优先**：确保同一场景下规则行为一致
3. **可执行性优先**：确保规则能被技术精确实现

### 6.3 冲突解方法

| 方法 | 描述 | 适用场景 |
|------|------|---------|
| **优先级法** | 给规则设优先级，高优先级覆盖低优先级 | 互斥规则，明确主次 |
| **互斥矩阵法** | 列出所有规则的两两互斥关系 | 多规则互斥 |
| **优先级 + 互斥矩阵组合** | 优先级用于直接冲突，互斥矩阵用于范围冲突 | 复杂规则集 |
| **规则分层法** | 把规则分成"通用层 + 特殊层"，特殊层覆盖通用层 | 大规模规则集 |

### 6.4 冲突解示例（POS 餐饮优惠券规则）

**场景：** 顾客同时有满减券、折扣、会员折扣，应该用哪个？

**冲突：** 三种优惠可能同时适用，但实际只能选一种或有限叠加。

**解：**
- 优先级：会员折扣 > 满减券 > 折扣
- 互斥矩阵：满减券与折扣互斥；会员折扣可以叠加满减券
- 规则分层：基础规则（互斥规则） + 特殊规则（叠加规则）

## 7. 核心操作 5：规则变体矩阵

### 7.1 变体的来源

- **时段变体**：不同时间（节假日、平日、大促）规则不同
- **场景变体**：不同场景（新客、老客、VIP、异常）规则不同
- **地区变体**：不同地区（北上广深、内地、港澳台、海外）规则不同
- **组织变体**：不同组织（直营、加盟、代理）规则不同
- **版本变体**：不同版本（V1、V2）规则不同

### 7.2 变体矩阵示例（POS 餐饮）

| 规则 | 平日 | 节假日 | 大促 | 新客 | 老客 | VIP |
|------|------|--------|------|------|------|-----|
| 满减门槛 | 100 元 | 100 元 | 200 元 | 50 元 | 100 元 | 100 元 |
| 折扣范围 | 全单 | 全单 | 指定菜品 | 指定菜品 | 全单 | 全单 |
| 会员折扣 | 9 折 | 9 折 | 9.5 折 | 9.5 折 | 9 折 | 8.5 折 |
| 退款期限 | 7 天 | 7 天 | 7 天 | 3 天 | 7 天 | 30 天 |

### 7.3 变体的核心思想
- **基础规则 + 变体规则**：先有基础规则，再叠加变体
- **变体优先级**：变体规则的优先级通常高于基础规则
- **变体记录**：变体规则必须显式记录，不能"埋"在代码里

## 8. 规则的完整度评估

### 8.1 完整度评估方法

| 评估方法 | 描述 |
|---------|------|
| **场景穷举** | 列出所有业务场景，验证每个场景都有规则 |
| **角色穷举** | 列出所有角色，验证每个角色的规则都已识别 |
| **时序穷举** | 列出所有时段，验证每个时段的规则都已识别 |
| **变体穷举** | 列出所有变体，验证每个变体的规则都已识别 |

### 8.2 完整度评分

| 评分 | 标准 |
|------|------|
| ★★★★★ | 所有变体、所有时段、所有角色、所有场景的规则都已识别 |
| ★★★★ | 80%+ 场景有规则，遗漏主要是边缘情况 |
| ★★★ | 60%+ 场景有规则，主要场景覆盖完整 |
| ★★ | 40%+ 场景有规则，主要场景有遗漏 |
| ★ | < 40% 场景有规则，需要大幅补充 |

## 9. 规则分析的反模式

### 反模式 1：规则爆炸
- **表现**：规则数量爆炸，几百上千条规则
- **根因**：缺乏规则分层、变体抽象
- **修正**：抽象出基础规则和变体规则，避免每种组合都列一条规则

### 反模式 2：规则僵化
- **表现**：所有规则固定，无法适应业务变化
- **根因**：规则硬编码在代码里，不支持配置化
- **修正**：规则配置化、规则引擎化

### 反模式 3：规则冲突隐蔽化
- **表现**：规则冲突只在特定场景下出现，难以排查
- **根因**：规则分散在多个模块，没有统一的冲突管理
- **修正**：集中规则管理、建立规则依赖图

### 反模式 4：规则与代码混杂
- **表现**：业务规则写在代码里，难以识别
- **根因**：规则没有显式抽取
- **修正**：规则从代码中抽取出来，独立管理

## 10. L2 的产出标准

### 10.1 规则清单

| 字段 | 说明 |
|------|------|
| **规则编号** | 唯一标识 |
| **规则类型** | 显性 / 隐性 |
| **规则分类** | 计费 / 库存 / 审批 / 合规 / 等 |
| **规则表述** | 自然语言描述 |
| **触发条件** | 什么场景下触发 |
| **关联概念** | 关联到 L1 的概念 |
| **依赖规则** | 依赖的其他规则编号 |
| **变体矩阵** | 在不同变体下的取值 |

### 10.2 规则依赖图

用有向图表示：

- 节点：规则
- 实线：强依赖
- 虚线：弱依赖
- 双线：互斥依赖
- 条件线：条件依赖

### 10.3 规则冲突解文档

每个冲突点必须有：

- 冲突描述
- 冲突类型
- 冲突解方法
- 优先级排序
- 适用范围

## 11. 与其他层次的关系

| 层次 | 从 L2 得到什么 | 向 L2 反馈什么 |
|------|--------------|--------------|
| **L1 业务建模层** | L1 的概念是 L2 规则的载体 | L1 概念变化可能影响 L2 规则结构 |
| **L3 业务流程层** | L2 规则是 L3 流程的约束 | L3 流程变化可能引入新规则 |
| **L4 业务演化层** | L2 规则是 L4 演化的载体 | L4 演化揭示规则的产生原因 |
| **L5 业务因果层** | L2 规则是 L5 因果的对象 | L5 因果解释规则的产生背景 |
