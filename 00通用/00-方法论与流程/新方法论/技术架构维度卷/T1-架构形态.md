# T1 架构形态

> **架构维度 1**：业务系统的整体组织形式——单体、分层、分布式、微服务、事件驱动。

---

## 1. 维度目标

**在 T1，分析者要回答以下问题：**

- 业务系统的**整体形态**是什么？
- 业务的**复杂度分布**如何映射到架构形态？
- **何时**选择哪种架构形态？
- 不同架构形态的**业务适配性**如何？
- 架构形态的**演化路径**是什么？

---

## 2. 5 种核心架构形态

### 形态 1：单体架构（Monolith）
**定义：** 所有功能集中在一个代码库、一个部署单元中。

**业务适配场景：**
- 业务规模小（用户 < 10 万）
- 业务规则少（规则数 < 50）
- 业务变体少（变体数 < 5）
- 组织规模小（团队 < 10 人）
- 业务复杂度集中在 1-2 个维度

**优势：**
- 开发简单（一个代码库）
- 部署简单（一个部署单元）
- 测试简单（端到端测试）
- 调试简单（调用链清晰）

**劣势：**
- 扩展性差（只能整体扩展）
- 维护性差（代码库越来越大）
- 技术债积累快（所有改动耦合）
- 可用性差（一个 bug 影响全部）

**典型业务：** 导入期的 SaaS、小型电商、个人记账、小型 POS

### 形态 2：分层架构（Layered）
**定义：** 按技术分层组织（表示层、业务层、数据层），功能集中。

**业务适配场景：**
- 业务规模中等（用户 10-100 万）
- 业务流程复杂但稳定
- 需要清晰的分层职责
- 团队规模中等（10-50 人）

**优势：**
- 职责清晰（每层负责一类功能）
- 易于测试（可以分层测试）
- 易于替换（可以替换某层实现）
- 标准化（业界共识强）

**劣势：**
- 上层调用下层，灵活度受限
- 容易出现"贫血模型"（业务逻辑都在 Service）
- 跨层修改影响大
- 仍然有单体的问题

**典型业务：** 中小型 ERP、中型 POS 连锁、传统行业系统

### 形态 3：分布式架构（Distributed）
**定义：** 多个独立部署的服务协同完成业务。

**业务适配场景：**
- 业务规模大（用户 > 100 万）
- 业务流程复杂，跨多个业务域
- 部分模块需要独立扩展
- 团队规模大（50-200 人）

**优势：**
- 可独立扩展（按模块扩展）
- 可独立部署（不影响其他模块）
- 故障隔离（一个模块故障不影响全部）
- 技术异构（不同模块可用不同技术栈）

**劣势：**
- 分布式复杂度（网络、序列化、一致性）
- 调试复杂（跨服务调用）
- 测试复杂（需要集成测试）
- 运维复杂（多服务管理）

**典型业务：** 大型电商、大型 ERP、大型 SaaS、互联网平台

### 形态 4：微服务架构（Microservices）
**定义：** 分布式架构的细分版本，强调"小而专"的服务拆分。

**业务适配场景：**
- 业务规模极大（用户 > 1000 万）
- 业务域清晰，可独立演进
- 团队规模极大（200+ 人）
- 业务演化快，需要快速迭代

**优势：**
- 服务边界清晰（按业务域划分）
- 独立演进（每个服务可独立升级）
- 组织对齐（康威定律）
- 故障隔离（服务级隔离）

**劣势：**
- 拆分标准争议大（粒度、边界）
- 分布式事务复杂
- 服务治理复杂（注册发现、熔断降级）
- 数据一致性挑战

**典型业务：** 大型互联网平台、超大型 SaaS、跨国业务系统

### 形态 5：事件驱动架构（Event-Driven）
**定义：** 以事件为中心，业务流程通过事件传递完成。

**业务适配场景：**
- 业务流程跨多个业务域
- 业务实时性要求高
- 业务流程有显著的"反应"模式
- 业务需要解耦发布方和订阅方

**优势：**
- 高度解耦（发布方不知道订阅方）
- 实时性强（事件立即传递）
- 可扩展（新增订阅方不影响发布方）
- 异步处理（不阻塞主流程）

**劣势：**
- 调试复杂（事件链路难追踪）
- 一致性挑战（最终一致性）
- 事件设计难（事件契约、版本管理）
- 运维复杂（事件总线、消息队列）

**典型业务：** 实时风控、实时推荐、实时库存、订单履约系统

### 3.2 选择原则

**核心原则：架构形态必须服务于业务复杂度，而不是反过来。**

| 原则 | 描述 |
|------|------|
| **不要过度架构** | 业务规模小不要用微服务，业务简单不要用事件驱动 |
| **不要过度单体** | 业务规模大不要坚持单体，业务复杂不要坚持分层 |
| **匹配业务演化** | 架构必须能跟随业务演化 |
| **匹配组织能力** | 团队能力必须能支撑架构复杂度 |
| **匹配运维能力** | 运维能力必须能支撑架构复杂度 |

## 4. 架构形态的演化路径

### 4.1 典型演化路径

```
单体 → 分层 → 分布式 → 微服务 → 事件驱动（部分模块）
```

**示例（POS 餐饮的架构演化）：**

| 阶段 | 时间 | 业务规模 | 架构形态 |
|------|------|---------|---------|
| 导入期 | 2018 | 1 个门店 | 单体 |
| 成长期 | 2019-2020 | 5-10 个门店 | 分层 + 数据库分库 |
| 扩张期 | 2021-2022 | 20-50 个门店 | 分布式（订单、会员、库存 3 个服务）|
| 成熟期 | 2023+ | 100+ 个门店 | 微服务 + 部分事件驱动 |

### 4.2 演化路径的反模式

#### 反模式 1：过早微服务化
- **表现：** 业务还在导入期就用微服务
- **后果：** 团队负担过重，开发效率低
- **修正：** 先用单体 + 模块化，业务规模到了再拆分

#### 反模式 2：过晚微服务化
- **表现：** 业务规模很大了还在单体
- **后果：** 维护性差，扩展性差
- **修正：** 在临界点之前完成微服务化

#### 反模式 3：拆分标准混乱
- **表现：** 微服务拆分没有明确标准
- **后果：** 服务边界混乱，依赖复杂
- **修正：** 按业务域（限界上下文）拆分

## 5. 架构形态的评价

### 5.1 评价维度

| 评价维度 | 描述 |
|---------|------|
| **业务适配性** | 是否匹配业务特征 |
| **团队适配性** | 是否匹配团队能力 |
| **可演进性** | 是否容易演化 |
| **可维护性** | 是否容易维护 |
| **可观测性** | 是否容易观测 |
| **运维成本** | 运维负担大小 |

### 5.2 评价的反模式

- **盲目崇拜微服务**：认为微服务就是先进，单体就是落后
- **盲目崇拜单体**：认为单体就是简单，微服务就是复杂
- **技术驱动而非业务驱动**：脱离业务谈架构选择

**关键原则：** 架构的好坏是**业务匹配度**，不是技术先进性。

## 6. 架构形态与业务维度卷的对应

| 架构形态 | 对应的业务层 | 映射方式 |
|---------|------------|---------|
| **单体** | L1 概念少 + L2 规则少 + L3 流程简单 | 一个代码库覆盖所有业务 |
| **分层** | L1 概念中等 + L2 规则中等 + L3 流程中等 | 按业务层/数据层/表示层分层 |
| **分布式** | L1 概念多 + L2 规则多 + L3 流程复杂 | 按业务域拆分服务 |
| **微服务** | L1 概念极多 + 多个业务域 | 按限界上下文精细拆分 |
| **事件驱动** | L3 流程高实时 + 多业务域协同 | 业务流程通过事件传递 |
