# T2 模块化

> **架构维度 2**：业务系统的模块组织方式——内聚、耦合、边界、依赖。

---

## 1. 维度目标

**在 T2，分析者要回答以下问题：**

- 业务系统如何**划分模块**？
- 模块之间的**依赖关系**是什么？
- 模块的**内聚度**如何？
- 模块之间的**耦合度**如何？
- 模块**边界**如何设计？
- 模块的**依赖方向**是什么？

---

## 2. 模块化的 4 个核心原则

### 原则 1：高内聚
**含义：** 模块内部的功能应该紧密相关。

**判定：**
- 模块内部的类/函数应该围绕同一个业务概念
- 模块内部的修改应该是局部的，不需要频繁跨模块
- 模块应该有清晰的单一职责

**反例：**
- 一个"工具类"模块包含了订单、会员、支付的所有工具方法（低内聚）

### 原则 2：低耦合
**含义：** 模块之间的依赖应该尽量少、尽量弱。

**判定：**
- 模块之间应该通过清晰的接口通信
- 模块之间不应该有循环依赖
- 模块之间不应该共享内部状态
- 一个模块的变化不应该频繁影响其他模块

**反例：**
- 订单模块直接调用会员模块的内部方法（强耦合）
- 模块 A 调用模块 B，模块 B 又调用模块 A（循环依赖）

### 原则 3：清晰边界
**含义：** 模块的边界应该清晰，对外只暴露必要的接口。

**判定：**
- 模块有明确的对外接口
- 模块内部实现对外不可见
- 模块边界与业务边界对齐

**反例：**
- 模块 A 直接访问模块 B 的数据库表（边界不清）
- 模块边界与技术分层对齐而非业务边界（边界错位）

### 原则 4：单向依赖
**含义：** 模块之间的依赖方向应该是单向的，不应该有循环。

**判定：**
- 依赖关系可以画成一个有向无环图（DAG）
- 上层模块依赖下层模块，下层模块不依赖上层
- 业务模块依赖基础设施，基础设施不依赖业务模块

**反例：**
- 模块 A 依赖 B，B 依赖 C，C 又依赖 A（循环依赖）

## 3. 模块边界的设计方法

### 3.1 按业务域划分（最常用）

**原则：** 模块边界 = 限界上下文边界。

**步骤：**
1. 从 L1 的限界上下文出发
2. 每个限界上下文对应一个模块（或微服务）
3. 限界上下文之间的依赖关系 = 模块之间的依赖关系

**示例（POS 餐饮）：**
- 模块：点餐、桌台、会员、收银、库存、报表
- 每个模块对应一个限界上下文

### 3.2 按技术分层划分

**原则：** 模块边界 = 技术层边界。

**步骤：**
1. 分为表示层、业务层、数据层、基础设施层
2. 上层调用下层，下层不调用上层
3. 业务层内部按业务子域再划分

**示例：**
```
com.pos.controller（表示层）
com.pos.service（业务层）
    ├── com.pos.service.order
    ├── com.pos.service.member
    └── ...
com.pos.dao（数据层）
com.pos.infrastructure（基础设施层）
```

### 3.3 按团队划分

**原则：** 模块边界 = 团队边界（康威定律）。

**步骤：**
1. 识别团队结构和分工
2. 每个团队负责一个或多个模块
3. 团队之间的协作边界 = 模块之间的依赖关系

**说明：** 团队结构应该服务于业务结构，而不是反过来。

## 4. 模块依赖的设计原则

### 4.1 依赖方向

**单向依赖原则：**
```
UI 层 → 业务层 → 数据层 → 基础设施层
         ↓
    公共服务层
```

**禁止的反模式：**
- 下层调用上层
- 业务层调用 UI 层
- 数据层调用业务层
- 基础设施层调用业务层

### 4.2 依赖方式

| 依赖方式 | 描述 | 适用场景 |
|---------|------|---------|
| **直接调用** | 直接调用目标模块的接口 | 强依赖、性能敏感 |
| **依赖注入** | 通过容器注入依赖 | 依赖可替换 |
| **事件发布** | 通过事件总线发布事件 | 松耦合、异步 |
| **消息队列** | 通过 MQ 传递消息 | 跨服务、异步 |
| **共享数据库** | 通过数据库表共享 | 反模式（尽量避免）|

### 4.3 循环依赖的检测

**检测方法：**
- 工具：依赖分析工具（如 jdeps、NDepend）
- 手动：画模块依赖图，检查是否有环

**循环依赖的处理：**
- 提取公共依赖：把循环依赖的内容提取到公共模块
- 引入事件机制：用事件解耦
- 合并模块：如果两个模块循环依赖，考虑合并

## 5. 模块的粒度

### 5.1 模块粒度的判断

| 模块类型 | 粒度 | 数量建议 | 适用规模 |
|---------|------|---------|---------|
| **包（Package）** | 细 | 数十到数百 | 小型系统 |
| **模块（Module）** | 中 | 数个到数十个 | 中型系统 |
| **微服务（Microservice）** | 粗 | 数个到十数个 | 大型系统 |
| **子系统（Subsystem）** | 极粗 | 数个 | 超大型系统 |

### 5.2 模块粒度的判定原则

- **业务域大小**：业务域大 → 模块大，业务域小 → 模块小
- **变更频率**：变更频繁的模块单独拆分
- **复用频率**：被多处复用的模块单独拆分
- **团队规模**：团队规模大 → 模块粒度细，团队规模小 → 模块粒度粗

### 5.3 模块粒度的反模式

#### 反模式 1：粒度过细
- **表现：** 几十个微服务，每个服务只有几个类
- **后果：** 分布式复杂度远大于业务复杂度
- **修正：** 合并相关微服务，按业务域拆分

#### 反模式 2：粒度过粗
- **表现：** 一个模块包含多个业务域
- **后果：** 模块内部耦合严重
- **修正：** 按业务域拆分模块

#### 反模式 3：粒度不均
- **表现：** 有的模块几十个类，有的模块只有 1 个类
- **后果：** 管理混乱
- **修正：** 重新评估边界，按业务域对齐

## 6. 模块的可测试性

### 6.1 可测试模块的特征

| 特征 | 描述 |
|------|------|
| **接口清晰** | 模块对外接口明确 |
| **依赖可替换** | 依赖可以通过 mock 替换 |
| **状态可隔离** | 模块状态可以独立测试 |
| **输入可控制** | 测试输入可以精确控制 |
| **输出可验证** | 测试输出可以精确验证 |

### 6.2 模块的可测试设计

- **依赖注入**：通过 DI 注入依赖，便于替换
- **接口抽象**：核心依赖通过接口抽象，便于 mock
- **避免静态状态**：避免静态变量、全局状态
- **避免时间耦合**：避免代码依赖特定执行时间

---

## 7. 模块的可演进性

### 7.1 可演进模块的特征

| 特征 | 描述 |
|------|------|
| **边界稳定** | 模块边界不容易变化 |
| **接口稳定** | 对外接口向后兼容 |
| **实现可替换** | 模块内部实现可以独立升级 |
| **依赖清晰** | 依赖关系简单清晰 |

### 7.2 模块的可演进设计

- **接口先行**：先定义接口，再实现
- **抽象稳定**：核心抽象保持稳定
- **实现可替换**：通过抽象层隔离实现
- **依赖单向**：保持单向依赖

## 8. 模块的评价

### 8.1 评价指标

| 指标 | 描述 | 计算方式 |
|------|------|---------|
| **内聚度** | 模块内部功能的紧密程度 | 模块内部方法的相互调用频率 |
| **耦合度** | 模块之间的依赖强度 | 模块之间的调用频率、依赖数量 |
| **稳定性** | 模块对外接口的变化频率 | 单位时间内接口变更次数 |
| **可测试性** | 模块测试的难易程度 | 测试代码与产品代码的比例 |
| **可演进性** | 模块升级的难易程度 | 升级所需修改的模块数 |

### 8.2 模块评分标准

| 评分 | 内聚度 | 耦合度 |
|------|--------|--------|
| ★★★★★ | 极高（单一职责）| 极低（无循环依赖）|
| ★★★★ | 高 | 低 |
| ★★★ | 中 | 中 |
| ★★ | 低 | 高 |
| ★ | 极低（杂项模块）| 极高（强耦合）|

## 9. 模块的反模式

### 反模式 1：循环依赖
- **表现：** 模块 A 依赖 B，B 依赖 C，C 依赖 A
- **后果：** 修改牵一发动全身
- **修正：** 提取公共模块，引入事件机制

### 反模式 2：核心模块依赖外围模块
- **表现：** 核心业务模块依赖工具类、基础设施
- **后果：** 核心模块难以独立部署
- **修正：** 依赖倒置（核心模块定义接口，外围模块实现）

### 反模式 3：上帝模块
- **表现：** 一个模块包含太多功能
- **后果：** 模块臃肿，难以维护
- **修正：** 按业务域拆分

### 反模式 4：贫血模块
- **表现：** 模块只有数据没有行为
- **后果：** 业务逻辑分散在调用方
- **修正：** 把业务逻辑下沉到模块内部

### 反模式 5：共享数据库
- **表现：** 多个模块共享同一个数据库表
- **后果：** 边界不清，耦合严重
- **修正：** 每个模块独立的数据表，通过 API 共享数据

## 10. T2 的产出标准

### 10.1 模块清单

每个模块包含：

| 字段 | 说明 |
|------|------|
| **模块 ID** | 唯一标识 |
| **模块名称** | 业务术语 |
| **模块职责** | 模块的核心职责（一句话）|
| **对外接口** | 模块对外提供的接口 |
| **依赖模块** | 模块依赖的其他模块 |
| **被依赖模块** | 哪些模块依赖本模块 |
| **业务域归属** | 属于哪个业务域 |
| **团队归属** | 属于哪个团队 |

### 10.2 模块依赖图

用有向图表示模块之间的依赖关系，包括：
- 节点：模块
- 边：依赖关系
- 边的粗细：依赖强度

### 10.3 模块评价报告

按内聚度、耦合度、稳定性、可测试性、可演进性分别评分。
