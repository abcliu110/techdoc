# T6 技术债务

> **架构维度 6**：业务系统的技术债务识别与评估——腐化识别、债务评估、改造决策。

---

## 1. 维度目标

**在 T6，分析者要回答以下问题：**

- 业务系统存在哪些**技术债务**？
- 技术债务的**严重程度**如何？
- 技术债务的**改造成本**如何？
- 技术债务的**改造优先级**如何？
- **何时**应该还债？
- **如何**制定还债计划？

---

## 2. 技术债务的定义

### 2.1 什么是技术债务

**技术债务 = 为了短期目标而做出的技术妥协，这些妥协会增加未来的开发成本。**

| 要素 | 描述 |
|------|------|
| **债务本金** | 技术妥协本身（差的代码、差的架构）|
| **债务利息** | 技术妥协带来的额外开发成本（维护困难、修改风险）|
| **还款期限** | 技术债必须偿还的时间点 |
| **债主** | 承担技术债后果的人（通常是后来的开发者）|

### 2.2 技术债务的来源

| 来源 | 描述 | 示例 |
|------|------|------|
| **时间压力** | 为了赶工期而做的妥协 | 复制粘贴代码 |
| **认知不足** | 当时不理解更好的方案 | 错误的抽象 |
| **业务变更** | 业务变化导致原有设计失效 | 旧功能未清理 |
| **人员变动** | 人员离开导致知识丢失 | 无人能改的代码 |
| **技术演进** | 新技术出现后旧技术变债务 | jQuery → React |
| **架构腐化** | 代码长期无序演化导致腐化 | 循环依赖、硬编码 |

### 2.3 技术债务的类型

| 类型 | 描述 | 示例 |
|------|------|------|
| **代码债务** | 代码质量问题 | 重复代码、命名混乱、过长方法 |
| **设计债务** | 架构设计问题 | 紧耦合、低内聚、错误抽象 |
| **测试债务** | 测试覆盖不足 | 没有单元测试、没有集成测试 |
| **文档债务** | 文档缺失或过时 | 没有文档、文档与代码不一致 |
| **数据债务** | 数据质量问题 | 数据不一致、数据缺失 |
| **安全债务** | 安全问题 | 硬编码密码、SQL 注入漏洞 |
| **性能债务** | 性能问题 | N+1 查询、全表扫描 |

## 3. 技术债务的识别

### 3.1 识别方法

#### 方法 1：代码扫描
- 静态分析工具（SonarQube、PMD、CheckStyle）
- 复杂度分析
- 重复代码检测

#### 方法 2：架构评审
- 架构图与实际代码对比
- 模块依赖分析
- 架构腐化指标

#### 方法 3：代码审查
- 历史 PR 的问题累积
- 代码审查的重复问题
- 难改动的代码特征

#### 方法 4：业务反馈
- 需求实现周期
- Bug 修复周期
- 生产事故分析

### 3.2 识别指标

| 指标 | 描述 | 阈值建议 |
|------|------|---------|
| **圈复杂度** | 方法的分支数 | > 10 需要重构 |
| **重复代码** | 重复代码比例 | > 5% 需要重构 |
| **过长方法** | 方法行数 | > 50 行建议拆分 |
| **过长类** | 类的行数 | > 500 行建议拆分 |
| **循环依赖** | 依赖环数 | 0 为理想 |
| **接口暴露** | 对外暴露的字段数 | 越少越好 |
| **硬编码** | 硬编码数量 | 0 为理想 |
| **单元测试覆盖率** | 测试覆盖率 | < 70% 需要补充 |

### 3.3 技术债务清单模板

| 字段 | 描述 |
|------|------|
| **债务 ID** | 唯一标识 |
| **债务名称** | 债务的简短描述 |
| **债务类型** | 代码/设计/测试/文档/数据/安全/性能 |
| **严重程度** | 高/中/低 |
| **影响范围** | 影响的模块、功能 |
| **改造成本** | 预估人天 |
| **产生时间** | 债务产生的时间 |
| **产生原因** | 为什么产生债务 |
| **偿还方案** | 如何偿还债务 |
| **偿还优先级** | 优先级排序 |

## 4. 技术债务的评估

### 4.1 严重程度评估

| 严重程度 | 描述 | 判定标准 |
|---------|------|---------|
| **高** | 严重影响开发效率 | Bug 频发、需求周期 > 正常 3 倍 |
| **中** | 中度影响开发效率 | 修改一处影响多处、维护成本高 |
| **低** | 轻度影响开发效率 | 代码不优雅但不影响功能 |

### 4.2 影响范围评估

| 影响范围 | 描述 |
|---------|------|
| **全局** | 影响整个系统 |
| **子系统** | 影响某个子系统 |
| **模块** | 影响某个模块 |
| **功能** | 影响某个功能 |

### 4.3 改造成本评估

| 改造成本 | 描述 |
|---------|------|
| **极高** | > 10 人月 |
| **高** | 3-10 人月 |
| **中** | 1-3 人月 |
| **低** | < 1 人月 |

### 4.4 偿还优先级矩阵

| 严重程度 × 影响范围 | 高严重程度 | 中严重程度 | 低严重程度 |
|--------------------|-----------|-----------|-----------|
| **全局影响** | P0（立即还）| P1（尽快还）| P2（计划还）|
| **子系统影响** | P1（尽快还）| P2（计划还）| P3（有空还）|
| **模块影响** | P2（计划还）| P3（有空还）| P4（可以不还）|
| **功能影响** | P2（计划还）| P3（有空还）| P4（可以不还）|

## 5. 技术债务与业务的关系

### 5.1 业务债务映射

技术债务背后往往有业务原因：

| 业务原因 | 技术债务表现 | 典型案例 |
|---------|------------|---------|
| **时间压力** | 复制粘贴代码 | 为了赶工，复制了类似功能 |
| **需求变更** | 大量 if-else | 需求变了多次，每次加 if-else |
| **人员变动** | 无人能改的代码 | 核心开发离职，留下神秘代码 |
| **业务下线** | 废弃代码未清理 | 旧功能下线，代码还在 |
| **组织调整** | 不匹配的模块边界 | 部门调整，模块边界没调整 |

### 5.2 业务价值与债务偿还

| 偿还策略 | 描述 | 适用场景 |
|---------|------|---------|
| **立即偿还** | 不计成本，立即偿还 | 安全漏洞、高频 Bug |
| **计划偿还** | 纳入迭代计划，逐步偿还 | 中等债务、有明确改造收益 |
| **延迟偿还** | 业务稳定后再偿还 | 低严重程度、近期有大需求 |
| **不偿还** | 不值得偿还，考虑替代方案 | 改造成本 > 收益、即将废弃 |

### 5.3 债务与业务迭代的平衡

| 原则 | 描述 |
|------|------|
| **不增新债** | 新代码必须是无债的 |
| **控制存量** | 存量债务必须控制在可接受范围 |
| **持续偿还** | 每个迭代必须有债务偿还时间 |
| **价值驱动** | 偿还债务必须有明确的业务价值 |

## 6. 技术债务的偿还策略

### 6.1 偿还模式

#### 模式 1：大爆炸模式
- **描述：** 集中一段时间大量偿还债务
- **优点：** 一次性解决
- **缺点：** 影响业务进度，风险高
- **适用：** 债务极多，系统难以维护

#### 模式 2：持续偿还模式
- **描述：** 每个迭代都分配时间偿还债务
- **优点：** 稳定可控
- **缺点：** 偿还速度慢
- **适用：** 债务可控，系统可维护

#### 模式 3：修缮模式
- **描述：** 在开发新功能时顺便偿还相关债务
- **优点：** 债务偿还与业务开发结合
- **缺点：** 可能不完整
- **适用：** 债务与新功能相关

#### 模式 4：替换模式
- **描述：** 用新系统/新模块替换旧系统/旧模块
- **优点：** 彻底解决
- **缺点：** 成本高、风险大
- **适用：** 系统级债务、无法局部改造

### 6.2 偿还原则

| 原则 | 描述 |
|------|------|
| **先止血** | 先防止债务继续增加 |
| **后还债** | 止血后再逐步偿还 |
| **小步快跑** | 每次偿还一小部分，降低风险 |
| **测试覆盖** | 偿还债务必须补充测试 |
| **持续集成** | 偿还债务必须持续集成 |

## 8. 技术债务的反模式

### 反模式 1：忽视债务
- **表现：** 认为债务不重要，先做业务
- **后果：** 债务累积，系统难以维护
- **修正：** 建立债务意识和债务管理机制

### 反模式 2：过度还债
- **表现：** 追求完美，不断重构
- **后果：** 影响业务进度
- **修正：** 债务偿还必须有明确的业务价值

### 反模式 3：只借不还
- **表现：** 持续产生新债务，从不偿还
- **后果：** 债务累积，系统崩溃
- **修正：** 每个迭代必须有债务偿还

### 反模式 4：新债还旧债
- **表现：** 用新的债务偿还旧的债务（如用微服务重构偿还代码债务）
- **后果：** 债务转移，问题可能更大
- **修正：** 债务偿还必须实际解决问题
