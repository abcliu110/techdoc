# T3 数据与状态

> **架构维度 3**：业务实体的数据建模与状态管理——持久化、状态机、一致性、并发。

---

## 1. 维度目标

**在 T3，分析者要回答以下问题：**

- 业务实体如何**映射到数据模型**？
- 业务实体的**状态机**是什么？
- 业务规则如何**约束数据**？
- 多方数据如何保证**一致性**？
- 并发场景下如何保证**数据正确性**？
- 数据的**生命周期**是什么？

## 2. 数据与业务实体的映射

### 2.1 映射的基本原则

| 业务实体类型 | 数据模型映射 | 示例 |
|------------|------------|------|
| **实体** | 一张或多张数据库表 + 主键 | 订单（order_id）、会员（member_id）|
| **值对象** | 嵌入主表或独立的表（无主键）| 地址（嵌入订单表）、金额（值对象）|
| **聚合** | 主表 + 从表 | 订单聚合（订单主表 + 订单明细表）|
| **领域事件** | 事件表或消息队列 | OrderCreated、OrderPaid |

### 2.2 映射的具体方法

#### 方法 1：贫血映射
- 实体 = 数据（只有 getter/setter）
- 业务逻辑在 Service 层
- 适用于简单 CRUD 操作

#### 方法 2：充血映射
- 实体 = 数据 + 行为
- 业务逻辑在 Entity/聚合根
- 适用于复杂业务逻辑

#### 方法 3：DDD 映射
- 聚合根 + 实体 + 值对象
- 仓库（Repository）负责持久化
- 领域事件负责状态变化通知

### 2.3 映射的反模式

| 反模式 | 表现 | 修正 |
|--------|------|------|
| **贫血模型** | 实体只有 getter/setter，所有逻辑在 Service | 充血化，把逻辑下沉到实体 |
| **上帝表** | 一张表包含几十个字段，对应多个业务概念 | 拆分成多个表，按业务概念分离 |
| **泛化表** | 用 key-value 表代替结构化表 | 结构化表，保留业务语义 |
| **跨表引用** | 实体 A 直接引用实体 B 的内部数据 | 通过接口/聚合根访问 |

## 3. 状态机设计

### 3.1 状态机的基本结构

**状态机 = 状态 + 事件 + 转换规则**

| 元素 | 描述 | 示例（订单）|
|------|------|-----------|
| **状态** | 实体的稳定状态 | 待支付、已支付、已发货、已完成、已取消 |
| **事件** | 触发状态变化的操作 | 下单、支付、发货、确认收货、取消 |
| **转换规则** | 在某状态下收到某事件后的转换规则 | 待支付 + 支付 → 已支付 |

### 3.2 状态机的表示

#### 状态图表示法
```
[待支付] --支付--> [已支付] --发货--> [已发货] --确认收货--> [已完成]
     |                      |
     └─────取消──────────────┘
```

#### 转换表表示法

| 当前状态 | 事件 | 目标状态 | 转换条件 |
|---------|------|---------|---------|
| 待支付 | 支付 | 已支付 | 支付成功 |
| 待支付 | 取消 | 已取消 | 无条件 |
| 已支付 | 发货 | 已发货 | 物流已发出 |
| 已发货 | 确认收货 | 已完成 | 顾客确认 |
| 已支付 | 取消 | 已取消 | 退款成功 |

### 3.3 状态机的设计原则

| 原则 | 描述 |
|------|------|
| **状态有限** | 状态数量应该有限且可枚举 |
| **转换明确** | 每个状态的转换规则应该明确 |
| **条件可验证** | 转换条件应该可以被验证 |
| **可追溯** | 状态变化应该被记录（领域事件）|
| **无环路** | 避免死循环状态 |

### 3.4 状态机的反模式

| 反模式 | 表现 | 修正 |
|--------|------|------|
| **状态爆炸** | 状态数量过多（如布尔字段叠加）| 状态抽象，用枚举表示 |
| **隐式状态** | 状态由多个字段组合判断 | 显式状态字段 |
| **无状态** | 没有状态机，状态由业务逻辑判断 | 引入状态机 |
| **状态分散** | 状态分散在多个表中 | 状态集中在主表 |

### 3.5 典型状态机设计

#### 订单状态机（POS 餐饮）

```
[草稿] --提交--> [待结账] --结账--> [已完成] --退款--> [已退款]
     |                                                        |
     └────────────────────取消───────────────────────────────┘
```

#### 会员状态机

```
[待激活] --激活--> [正常] --冻结--> [已冻结] --解冻--> [正常]
                    |                  |
                    └────注销──────────┘
```

#### 桌台状态机

```
[空闲] --开台--> [占用] --加菜--> [占用] --结账--> [清理中] --清台--> [空闲]
```

## 4. 数据约束

### 4.1 约束的类型

| 约束类型 | 描述 | 实现方式 |
|---------|------|---------|
| **类型约束** | 字段类型正确 | 数据库类型、Java 类型 |
| **范围约束** | 字段值在有效范围内 | CHECK 约束、枚举 |
| **唯一约束** | 字段值唯一 | UNIQUE 索引 |
| **外键约束** | 引用完整性 | FOREIGN KEY |
| **业务约束** | 业务规则约束 | 触发器、存储过程、应用层校验 |

### 4.2 约束的层级

| 层级 | 约束位置 | 描述 |
|------|---------|------|
| **数据库层** | 数据库约束 | 类型、范围、唯一、外键 |
| **应用层** | Service/Entity | 业务规则校验 |
| **接口层** | Controller/DTO | 输入校验 |
| **前端层** | 前端校验 | 用户体验优化 |

### 4.3 约束的设计原则

| 原则 | 描述 |
|------|------|
| **约束下沉** | 约束尽量在数据库层实现 |
| **约束一致** | 各层约束保持一致 |
| **约束可验证** | 约束应该可以被验证 |
| **约束可追溯** | 约束违反应该被记录 |

## 5. 数据一致性

### 5.1 一致性的类型

| 一致性类型 | 描述 | 适用场景 |
|-----------|------|---------|
| **强一致性** | 写入后立即可读 | 金融、库存扣减 |
| **最终一致性** | 写入后延迟可读 | 日志、统计、通知 |
| **会话一致性** | 同一会话内一致 | 用户体验优化 |
| **因果一致性** | 有因果关系的操作一致 | 协同编辑 |

### 5.2 一致性的实现方式

#### 强一致性实现

| 实现方式 | 描述 | 适用场景 |
|---------|------|---------|
| **分布式事务** | XA 协议、两阶段提交 | 跨库事务 |
| **Saga** | 编排式 / 协同式 Saga | 微服务事务 |
| **本地消息表** | 本地表 + 消息队列 | 最终一致 |
| **TCC** | Try-Confirm-Cancel | 资源预留 |

#### 最终一致性实现

| 实现方式 | 描述 | 适用场景 |
|---------|------|---------|
| **消息队列** | 异步消息驱动 | 松耦合 |
| **定时任务** | 定时对账、补偿 | 批处理 |
| **CDC** | 变更数据捕获 | 数据同步 |

### 5.3 一致性的选择原则

| 业务需求 | 一致性选择 |
|---------|-----------|
| 金额相关 | 强一致性（分布式事务、Saga）|
| 库存扣减 | 强一致性 + 幂等 |
| 订单状态 | 最终一致性 + 补偿 |
| 通知消息 | 最终一致性 |
| 日志记录 | 最终一致性 |

## 6. 并发控制

### 6.1 并发问题的类型

| 问题类型 | 描述 | 示例 |
|---------|------|------|
| **脏读** | 读取了未提交的数据 | 事务 A 修改了，事务 B 读取了，但事务 A 回滚了 |
| **不可重复读** | 同一数据两次读取结果不同 | 事务 A 读取了，事务 B 修改并提交了，事务 A 再读结果不同 |
| **幻读** | 同一查询两次结果集不同 | 事务 A 读取了 N 条记录，事务 B 插入了一条，事务 A 再读变成了 N+1 条 |

### 6.2 并发控制的实现方式

#### 数据库层并发控制

| 方式 | 描述 | 适用场景 |
|------|------|---------|
| **乐观锁** | 版本号 / CAS | 冲突少、低并发 |
| **悲观锁** | 排他锁 / 共享锁 | 冲突多、高并发 |
| **串行化** | 事务串行执行 | 数据一致性要求极高 |

#### 应用层并发控制

| 方式 | 描述 | 适用场景 |
|------|------|---------|
| **分布式锁** | Redis/ZooKeeper 锁 | 跨服务并发 |
| **幂等设计** | 重复请求幂等处理 | 消息幂等、接口幂等 |
| **唯一约束** | 数据库唯一索引 | 防止重复插入 |

### 6.3 幂等设计

**幂等性：** 同一操作执行一次和执行多次的结果相同。

| 幂等实现 | 描述 | 适用场景 |
|---------|------|---------|
| **唯一键** | 数据库唯一索引 | 插入幂等 |
| **状态机** | 状态转换幂等 | 状态变更幂等 |
| **去重表** | 消息去重表 | 消息幂等 |
| **Token** | 业务 Token | 表单提交幂等 |

## 7. 数据生命周期

### 7.1 数据生命周期的阶段

| 阶段 | 描述 | 处理方式 |
|------|------|---------|
| **创建** | 数据首次写入 | 校验默认值 |
| **使用** | 数据被读写 | 缓存、索引 |
| **变更** | 数据被修改 | 版本记录、变更日志 |
| **归档** | 数据不再活跃使用 | 归档到历史表 |
| **销毁** | 数据生命周期结束 | 脱敏、删除 |

### 7.2 数据生命周期的设计原则

| 原则 | 描述 |
|------|------|
| **明确生命周期** | 每类数据有明确的生命周期定义 |
| **分离冷热数据** | 活跃数据和历史数据分离存储 |
| **归档策略** | 数据达到一定时间后自动归档 |
| **销毁策略** | 数据超过保留期后销毁（合规要求）|
