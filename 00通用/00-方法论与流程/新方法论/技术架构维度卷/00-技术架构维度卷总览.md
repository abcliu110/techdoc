# 技术架构维度卷

> 从 T1 到 T6 共 6 个分析维度，完整覆盖技术架构的所有关键面。
>
> 本卷是**业务与技术的桥梁**——把业务维度卷（L1-L5）的业务结构映射到技术架构。
>
> 适用场景：业务系统技术评审、技术方案设计、技术债务识别、架构改造决策。

---

## 写作背景与前置假设

### 本卷的定位
- **元理论卷**回答"为什么"（5 个根本性问题）
- **业务维度卷**回答"业务的'是什么'"（L1-L5）
- **本卷**回答"业务的'怎么实现'"（T1-T6 的架构原理）
- **综合视角卷**回答"综合应用"（价值 + 演化 + 对比）

### 本卷的核心立场

**架构不是业务的对立面，而是业务的载体。** 每个架构决策都必须回答"它服务于业务的什么需求"。脱离业务谈架构是无意义的。

### 本卷的前置假设
1. 业务已经被 L1-L5 完整分析
2. 业务有明确的当前需求和未来预期
3. 技术实现服务于业务目标，而不是反过来

---

## T1-T6 的核心关系

```
T1 架构形态    ──┐
T2 模块化      ──┼─→ 这些是"结构"维度（系统怎么组织）
T3 数据与状态  ──┘

T4 接口与契约  ──┐
T5 运行时特性  ──┼─→ 这些是"行为"维度（系统怎么运转）
T6 技术债务    ──┘
```

- T1-T3 描述系统的**结构**
- T4-T6 描述系统的**行为**

---

## T1-T6 与业务维度卷的对应

| 架构维度 | 服务于业务层 | 核心映射 |
|---------|------------|---------|
| **T1 架构形态** | L1（业务建模）| 限界上下文 → 微服务 / 模块 / 单体 |
| **T2 模块化** | L1 + L3 | 实体聚合 → 模块边界，流程协作 → 模块依赖 |
| **T3 数据与状态** | L1 + L2 | 业务实体 → 数据模型，业务规则 → 数据约束 |
| **T4 接口与契约** | L1 + L4 | 业务概念 → API 设计，业务演化 → 接口演化 |
| **T5 运行时特性** | L3 + L4 | 业务流程 → 性能需求，业务演化 → 容量规划 |
| **T6 技术债务** | L4 + L5 | 业务历史包袱 → 技术债，组织惯性 → 架构惯性 |
