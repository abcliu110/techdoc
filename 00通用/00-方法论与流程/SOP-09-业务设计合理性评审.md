## TL;DR

**一句话**：评判业务设计是否"让正确的事容易发生、错误的事难以发生"，输出红线门槛结论和候选方案比较。

**核心输入**：SOP-03 业务流程模型、SOP-04 功能切片证据

**核心输出**：业务设计门槛结论、候选方案比较、质量维度评价、成立条件

**关键约束**：不依赖行业最佳实践做判断；必须用场景和证据支撑；好设计必须可验证可回滚

## 1. 目的与定位

本 SOP 用于评判信息系统中具体业务设计的好坏，包括业务流程、角色责任、规则、状态机、权限、数据语义、异常处理、人工运营和演进方案。

它不以“是否符合行业最佳实践”“是否使用先进架构”或“综合得分高低”作为结论，而判断设计是否：

```text
业务结果正确
+ 核心风险受控
+ 异常能够收敛
+ 用户完成任务高效
+ 变化能够承受
- 引入的成本与复杂度
```

一句话标准：

> 好的业务设计，让正确的事情容易发生，让错误的事情难以发生，让异常能够被发现，让失败能够恢复，让变化尽量局部化。

## 3. 核心评判逻辑

### 3.1 先门槛，后比较

评判分为三层，顺序不可颠倒：

```text
第一层 正确性底线：业务事实、不变量、权限、资金、数据、安全、合规是否正确。
第二层 运行质量：正常、边界、失败、重复、并发和人工路径是否能够收敛。
第三层 长期适配：用户效率、可运营、可演进、兼容迁移和成本是否合理。
```

任何红线门槛不通过，不能靠用户体验、可维护性或综合评分抵消。

### 3.2 先还原问题，再评价方案

同时维护三个空间：

| 空间 | 内容 | 防止的错误 |
|---|---|---|
| 问题空间 | 用户目标、业务结果、约束、不变量和失败后果 | 把现有页面和流程当成问题本身 |
| 方案空间 | 当前、最小改进、结构性改进、不处理方案 | 只论证单一偏好方案 |
| 证据空间 | 支持或反对模型和方案的事实 | 用经验或行业口号冒充系统事实 |

执行顺序：`定义问题 → 建立业务模型 → 展开候选方案 → 用证据筛选`。

### 3.3 条件化结论

不得只写“设计 A 更好”。结论必须包含：

```text
推荐方案：___
成立条件：___
不适用条件：___
被优先保护的不变量/目标：___
主要牺牲与代价承担者：___
最可能推翻结论的事实：___
验证、灰度和回滚：___
```

## 4. 准入输入与评审基线

### 4.1 最小输入

评审先声明模式：**评现状**（只读，对已有系统当前设计做合理性判断）或 **评方案**（对目标设计做取舍决策）。评现状模式不要求决策负责人或风险接受人签署，评审结论为条件化判断；评方案模式必须补齐决策负责人、风险接受人和停止条件，否则结论只能停留在"输入不足→待验证假设"。

- [ ] 决策问题、评审范围；决策负责人仅在评方案模式必需（评现状模式可登记为未知）
- [ ] 业务目标、用户任务和可观察结果
- [ ] 角色责任、系统边界和上下游
- [ ] 当前业务流程及正常/异常路径

## 5. 第一层：红线门槛

任一适用项不通过，结论原则上为“不通过”或“有条件通过并先止损”：

| 门槛 | 必须证明 | 典型反例 |
|---|---|---|
| 真实问题 | 设计解决真实用户/业务问题，而非只美化现有实现 | 为减少页面点击破坏必要复核 |
| 业务正确 | 业务事实、金额、数量、状态和口径正确 | 累计退款超过可退金额 |
| 不变量 | 任意合法及关键失败路径不破坏核心不变量 | 重试导致重复入账 |
| 权限与隔离 | 功能、对象、行级权限和租户作用域成立 | 替换对象 ID 可跨门店查询 |
| 安全与合规 | 满足隐私、财务、审计和监管要求 | 调账覆盖原记录、无法追溯 |
| 可恢复 | 不产生无法发现或无法恢复的高影响错误 | 部分成功后既无补偿也无人工入口 |
| 可审计 | 关键命令、审批、状态、金额和人工操作可追踪 | 管理员可直接改结果且无留痕 |

门槛结论必须引用规则、不变量、契约和证据 ID，不能仅凭评审者判断。
## 6. 第二、三层：质量评价维度

### 6.1 业务价值与目标匹配

- 谁在什么情境下完成什么任务，最终结果是什么？
- 设计解决根本问题，还是把成本转移给其他角色？
- 业务结果能否被观察、度量和验收？
- 当前组织分工和页面形式是否被误当成永久业务本质？

### 6.2 业务模型真实性

- 核心对象、关系、标识和生命周期是否符合现实业务？
- 同一术语在不同上下文是否有不同含义？
- 记录的是原始业务事实，还是派生展示结果？
- 权威来源、数据所有者和修改责任是否明确？

### 6.3 流程与状态完整性

至少覆盖：正常、边界、失败、重复、并发、超时/结果未知、取消、撤销/冲正、补偿、历史数据、跨日/时区和人工介入。

状态机必须说明状态语义、进入条件、操作者、前置条件、副作用、失败后状态、恢复路径、终态和非法转换。

### 6.4 角色、责任与控制

- 谁发起、批准、执行、复核、承担损失、处理异常并接受审计？
- 高风险操作是否需要职责分离、额度和双人复核？
- 人工补单、调账、改状态是否有授权、留痕和撤销机制？
- 系统异常是否有明确 Owner，而不是默认“找开发改库”？

### 6.5 异常收敛与韧性

- 能否区分成功、失败、处理中和结果未知？
- 重试是否安全，补偿是否完整，补偿失败如何处理？
- 是否存在对账、死信、差异修复和人工接管？
- 故障能否被发现、定位、止损、恢复和复盘？

### 6.6 数据语义与一致性

- 谁是业务事实的权威来源，哪些只是缓存、索引、报表或副本？
- 副本如何同步、去重、纠错和重建？
- 迟到、乱序、重放和历史数据如何解释？
- 一致性窗口、事务边界、幂等键和最终收敛证明是什么？

### 6.7 用户任务效率

不要只计算点击次数，应比较：

```text
任务完成时间 + 认知负担 + 出错概率 + 等待成本 + 返工成本
```

检查重复录入、无意义审批、系统内部概念暴露、默认值、批量操作、错误提示、结果未知提示和系统外绕行。

### 6.8 可观测、可运营与可审计

- 是否有业务指标、关联 ID、状态积压、重复率和差异告警？
- 客服、运维、财务能否查询并解释业务结果？
- 告警是否有责任人、处理动作和关闭条件？
- 人工处理入口是否安全、可审计、可撤销？

### 6.9 可演进性

- 易变规则是否与稳定事实分离并集中维护？
- 新角色、渠道、状态、策略或规则变化会影响多少无关模块？
- 契约和数据是否支持版本化，历史数据能否继续解释？
- 能否渐进迁移，而非只能一次性重写？

可演进不等于预先引入抽象。稳定的少量分支不一定需要策略模式；业务边界不清时拆微服务只会放大问题。

### 6.10 兼容与迁移

检查旧接口、消息、数据库直连、缓存键、任务产物、脚本、报表、历史状态、人工约定和混部节点。评价新旧规则并存、数据迁移、灰度、双轨/影子验证、监控和回退能力。

### 6.11 成本与复杂度匹配

成本包括开发、测试、迁移、用户学习、运营、运维、跨团队协作、故障恢复、长期认知和退出成本。好设计不是功能最多或技术最新，而是以与价值和风险匹配的复杂度解决问题。

## 7. 强制场景与压力测试

对每个候选方案执行：

```text
如果请求重复两次会怎样？
如果两个角色并发操作会怎样？
如果依赖成功但本地超时会怎样？
如果流程执行一半失败会怎样？
如果没有人工补单，系统能否自行收敛？
如果历史数据进入新流程会怎样？
如果规则明年变化会怎样？
如果规模扩大 10 倍，哪个约束先失效？
如果取消某个控制步骤，损失由谁承担？
```

寻找能够破坏设计的最小合法反例。只解释正常路径的设计不得评为“良好”。

## 9. 执行流程

```text
S09-G0 定义决策、对象、范围、证据和停止条件
  → S09-G1 还原目标、角色、对象、流程、状态、规则和不变量
  → S09-G2 检查红线门槛，失败则先止损或补证
  → S09-G3 枚举候选方案并执行全场景、反事实和最小反例测试
  → S09-G4 比较收益、代价、兼容、可逆性和证据强度
  → S09-G5 输出条件化结论、验证、灰度、回滚和复审触发器
```

### 9.1 竞争假设与信息增益

对存在争议的设计至少保留两个解释或方案，记录支持证据、反证和区分性验证。优先执行低成本、能改变方案排序的验证；只增加细节、不能改变决策的动作延后。

### 9.2 约束传播

沿以下链路检查设计变化影响：

```text
规则 → 状态/不变量 → API/消息/错误码 → 数据/历史/副本
→ 缓存/搜索/报表/指标 → 任务/对账/补偿/审计
→ 权限/租户/合规 → 测试/发布/监控/回滚
→ 调用方/客服/运维/人工制度
```

### 9.3 设计模式护栏

微服务、独立数据库、事件驱动、策略模式、规则引擎、状态机、TCC/Saga、缓存和分库分表都只是候选方案。采用前必须回答：

1. 当前真实问题和触发条件是什么？
2. 模式通过什么机制解决问题？
3. 新增哪些分布式、运维、认知、测试和数据成本？
4. 什么规模、团队和变化频率下它反而更差？
5. 能否先通过小切片、适配层或影子模式验证？
6. 效果不达标如何退出并保留旧契约？

## 10. 结论等级

| 结论 | 含义 | 后续动作 |
|---|---|---|
| 不通过 | 红线门槛失败或存在未隔离的不可接受风险 | 先止损、补证或重新设计，不进入实施 |
| 有条件通过 | 门槛基本满足，但关键未知项或保护措施尚未关闭 | 明确条件、Owner、期限和超期复审 |
| 通过 | 在声明范围内有足够证据支持，风险和代价可接受 | 进入验证、灰度或实施决策 |
| 优化候选 | 当前合理，替代方案可能有收益但证据不足或收益不确定 | 作为可逆实验，不升级为缺陷 |

每条业务结论必须同时标注确定性级别（直接事实/交叉验证结论/经验判断/推断/假设，对应 L1 第 6 章）和关键证据 ID；确定性为"推断"或"假设"的结论不得写成最终建议措辞。

“通过”不表示全局最优，只表示在当前目标、范围、约束和证据下合理。

## 13. AI 辅助评审约束

1. 不把当前实现、行业惯例或某种设计模式直接判为正确或错误。
2. 不以类名、表名、字段名和文档意图代替业务事实和运行证据。
3. 不只生成支持推荐方案的理由，必须主动输出反证和替代方案。
4. 不虚构用户痛点、运行数据、损失概率、成本、调用方和历史约束。
5. 不用流畅措辞掩盖未知项，不用总分抵消红线问题。
6. 推荐方案必须说明机制、代价承担者、成立条件、失效边界、验证和退出方式。
7. 高影响结论必须由具备业务责任的人和可复现实验证据复核；AI 不能担任风险接受人。
