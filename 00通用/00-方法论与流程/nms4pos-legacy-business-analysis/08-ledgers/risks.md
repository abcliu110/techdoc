## 2. P0 级风险（必须立即处理）

### 2.1 P0-R001: 优惠叠加规则未明确定义

**风险描述**：
不同文档对优惠叠加顺序描述不一致，代码实现可能与业务预期不符，导致结算金额错误。

**来源证据**：
- CT002：SLICE-001 与 business-rules.md 描述不一致
- I002：优惠叠加按固定优先级（置信度：中）

**影响分析**：
- 财务损失：优惠多算或少算直接导致营收偏差
- 客诉风险：会员权益无法保障
- 合规风险：可能违反价格法规

**发生概率**：中（已有矛盾证据）

**影响程度**：极高（直接涉及财务）

**缓解措施**：
1. 产品确认优惠叠加规则（C002）
2. 代码审查 CalcOrderService.calc() 实际顺序
3. 增加优惠计算的自动化测试用例
4. 制定优惠叠加规则文档并同步给开发和测试

**残余风险**：低（确认规则后可消除）

**决策要求**：
- 产品必须参与
- 财务确认
- 测试覆盖验证

---

### 2.2 P0-R002: 账单金额计算逻辑分散

**风险描述**：
CalcOrderService 承担核心计算，但调用链路长，涉及多个模块，变更风险高。

**来源证据**：
- C006：账单金额计算通过 CalcOrderService
- C002：核心业务在 pos2plugin 模块

**影响分析**：
- 重构风险：任何变更可能影响结账核心流程
- 测试难度：金额计算需要完整集成测试环境
- 回滚成本：高，账单数据已写入

**发生概率**：高（系统复杂度决定）

**影响程度**：高（直接影响收银）

**缓解措施**：
1. 绘制完整的金额计算调用链路图
2. 建立金额计算的单元测试和集成测试
3. 变更采用功能开关和影子模式
4. 保留旧逻辑兼容路径

**残余风险**：中（通过充分测试可降低）

**决策要求**：
- 技术评审必须覆盖
- 金额计算变更需要专项测试

## 3. P1 级风险（需要关注）

### 3.1 P1-R001: 离线同步冲突解决策略不明确

**风险描述**：
离线模式下，云端和门店数据可能产生冲突，现有实现策略不明确。

**来源证据**：
- C005：离线模式通过 sync_queue 实现
- I003：同步冲突以云端时间戳为准（推断）
- CT003：离线能力与文档描述有差距

**影响分析**：
- 数据一致性：极端场景可能导致数据不一致
- 业务中断：长时离线后同步失败
- 客诉风险：订单数据丢失或重复

**发生概率**：中（网络不稳定场景）

**影响程度**：高（数据完整性）

**缓解措施**：
1. 测试极端场景（长时离线、大量数据）
2. 明确 sync_queue 的冲突处理策略
3. 增加同步状态监控和告警
4. 制定离线数据丢失的补偿机制

**残余风险**：中

**决策要求**：
- 技术负责人确认冲突解决策略
- 测试极端场景

---

### 3.2 P1-R002: 核心业务逻辑分散在多个模块

**风险描述**：
pos2plugin、pos3boot、pos4cloud 等模块都有业务逻辑，职责边界不完全清晰。

**来源证据**：
- C002：核心业务在 pos2plugin 模块
- CT001：打印服务职责不清
- R001：历史遗留代码可能存在

**影响分析**：
- 维护困难：修改时需要了解多个模块
- 重构风险：拆分或重构时影响范围难以评估
- 学习成本：新成员上手困难

**发生概率**：中（架构演进结果）

**影响程度**：中（不影响功能但影响效率）

**缓解措施**：
1. 完成模块职责梳理文档
2. 绘制模块间依赖关系图
3. 制定重构计划，明确边界
4. 增加模块间接口测试

**残余风险**：低

**决策要求**：
- 技术负责人参与架构讨论
- 制定中长期重构规划

---

### 3.3 P1-R003: 历史遗留代码可能未被清理

**风险描述**：
pos3boot 中的打印代码、部分旧接口可能已废弃但未被清理。

**来源证据**：
- CT001：pos3boot 中有打印相关代码
- DC001-DC003：废弃候选登记
- E001：CLAUDE.md 描述与实际不符

**影响分析**：
- 维护负担：维护不必要的代码
- 安全风险：旧代码可能有漏洞
- 混淆：新成员可能被误导

**发生概率**：中（有证据支持）

**影响程度**：中（不影响功能但增加负担）

**缓解措施**：
1. 执行废弃候选评估
2. 检查代码调用情况
3. 制定废弃时间表
4. 必要时保留兼容入口

**残余风险**：低

**决策要求**：
- 运维确认无流量后可废弃
- 需要向后兼容时间窗口

## 4. P2 级风险（可接受）

**风险描述**：
mid/sid 隔离机制依赖代码规范，边界不够明确。

**缓解措施**：

2. 增加租户隔离的自动化测试
3. 使用 ORM 层的租户插件

**残余风险**：低

## 5. 风险应对策略总结

| 优先级 | 策略 | 资源需求 | 时间框架 |
|--------|------|----------|----------|
| P0 | 立即处理，产品参与决策 | 高 | 1-2周 |

## 6. 风险监控机制

### 6.1 定期检查

- P0 风险：每日检查状态
- P1 风险：每周检查状态
- P2 风险：每月检查状态

### 6.2 触发条件

- 财务异常时立即评估
- 客诉增加时重新评估
- 系统变更后重新评估
