# 业务与业务规则设计模式方法论

> 版本：v1.0  
> 适用对象：业务建模、规则重构、多客户产品、既有系统分析和新系统设计  
> 关联方法：`11-方法论-业务多实现统一建模与冲突治理.md`  
> 设计评审：`SOP-09-业务设计合理性评审.md`

## 0. AI 执行入口

### 0.1 最小输入

- 业务目标、用户任务、角色责任和可观察结果。
- 核心对象、业务事实、状态、数据权威源和外部副作用。
- 规则来源、适用范围、客户/渠道/区域/时间及历史版本。
- 正常、边界、失败、重复、并发、撤销和人工介入场景。
- 业务负责人、规则负责人、数据负责人和风险接受人。

信息不足时，AI 只能输出候选规则模型、竞争解释和最小验证动作，不能自行决定合同、资金、合规或风险接受语义。

### 0.2 核心输出

```text
业务事实与规范词汇
+ 核心不变量
+ 规则分类与来源
+ Policy/Decision/Process/State 模型
+ 规则关系和冲突裁决
+ 版本、生效期与决策快照
+ 执行、副作用和审计边界
+ 测试性质与生命周期治理
```

### 0.3 核心原则

> 稳定事实与不变量进入核心模型；易变经营政策成为版本化 Policy；资格、选择和冲突使用显式决策模型；流程和状态使用各自适合的模型；规则先形成决策，副作用由唯一执行计划统一实施。

## 1. 基础概念必须分离

| 概念 | 含义 | 示例 |
|---|---|---|
| 业务事实 Fact | 已经发生或客观存在、不能因当前政策被改写的内容 | 支付已完成、合同已签署 |
| 不变量 Invariant | 任意合法路径都必须成立的底线 | 累计退款不超过原有效支付 |
| 业务政策 Policy | 企业选择怎样经营，可按时间或范围变化 | 合同价是否允许叠加优惠 |
| 业务规则 Rule | 将事实和政策转换成判断、计算或约束 | 满足合同有效期时产生合同价候选 |
| 参数 Parameter | 阈值、比例、额度和时间窗 | 审批阈值 500 元 |
| 决策 Decision | 在给定上下文和版本下得到的业务结论 | 本单采用促销价 |
| 流程 Process | 谁在何时完成哪些协作步骤 | 申请、审核、执行、对账 |
| 状态 State | 业务对象生命周期阶段 | 待审核、执行中、已完成 |
| 执行计划 Plan | 根据决策形成的受控动作集合 | 写入价格、分摊、发送结算事件 |
| 决策快照 Snapshot | 冻结本次规则版本、依据、过程和结果 | 命中规则、排除原因、中间值 |
## 2. 规则分类与优先模式

不同规则不应全部实现为 `if/else`、策略或规则引擎。

| 规则类型 | 核心问题 | 优先模式 | 关键风险 |
|---|---|---|---|
| 不变量 | 什么绝不能被破坏 | 领域守卫、数据库约束、条件更新 | 被配置或旁路入口绕过 |
| 资格 | 当前主体是否有资格 | Specification、决策表、ABAC | 条件散落、语义不清 |
| 分类/选择 | 应选择哪个业务结果 | Decision Table、DMN、Policy | 重叠、遗漏、多结果 |
| 计算 | 金额、数量、比例如何形成 | Formula、Strategy、Pipeline | 基准、精度、顺序、分摊不清 |
| 状态转换 | 能否进入下一状态 | State Machine、Guard | 非法跃迁、并发覆盖 |
| 流程协作 | 谁何时做什么 | BPMN、Workflow、Process Manager | 把短流程过度平台化 |
| 时间 | 何时生效、历史如何解释 | Effective Dating、Versioned Policy | 用当前规则重算历史 |
| 权限/责任 | 谁可做、谁批准、谁承担 | RBAC/ABAC、SoD、Policy | 只控制按钮、不控制对象 |
| 额度/资源 | 如何预占、使用和释放 | Quota、Reservation、Allocation | 超占、重复扣减、无法回收 |
| 异常覆盖 | 谁可突破普通政策 | Explicit Override、Approval | 无理由、无审计、不可撤销 |

## 3. 不变量与领域守卫

不变量比具体规则稳定，应优先识别并在所有写入口统一保护：

```text
资金：资产不能无来源增加或无去向消失。
退款：累计有效退款不超过原有效支付。
库存：可用、预占、扣减和释放满足定义的守恒关系。
订单：一次业务意图不能因重试产生多个不可撤销结果。
权限：读写必须落在主体授权的数据作用域内。
审计：冲正、退款和调账不能覆盖原始事实。
状态：对象只能沿合法路径演进。
```

推荐多层防护：

```text
领域模型语义校验
+ 应用服务统一入口
+ 数据库唯一/检查/条件更新约束
+ 对账和业务指标
+ 属性测试与最小反例
```

不变量不应作为普通客户开关。若某业务模式确实采用不同不变量，应先证明它是独立业务模式，而不是降低公共底线。

## 4. Specification Pattern：资格与业务谓词

将资格条件封装为有业务名称的规格：

```text
有效会员
可退款订单
可参与促销商品
满足账期资格的客户
```

组合示例：

```text
EligibleForMemberPrice =
  有效会员
  AND 商品支持会员价
  AND 门店启用会员政策
  AND 当前时间在政策有效期
```

优点：语义明确、可复用、可测试、可组合。边界：条件很少且稳定时，具名方法比规格框架更简单；大量微小规格任意组合会形成难以理解的布尔网络，应重新封装为业务级规格。

## 5. Policy Object：完整业务政策

Policy 不只是一个计算函数，应承载一组完整经营语义：

```text
PromotionCombinationPolicy
- businessMeaning
- scope/applicability
- eligibility
- exclusions
- priority
- compositionOrder
- limits
- fundingResponsibility
- effectivePeriod
- version
- overridePolicy
- auditRequirement
```

Policy 适用于客户合同、价格组合、审批、结算、风险和权益政策。它应回答为什么适用、与其他政策如何相处、谁批准、何时生效、如何解释和如何逆向。

## 6. Strategy Pattern：相同语义下的算法变化

适用条件：

```text
输入语义相同
输出语义相同
维护的不变量相同
只有算法或技术实现不同
```

例如运费、税费或评分算法。Strategy 只负责“怎么算”，不能独立解决资格、优先级、组合、冲突和历史版本。

若两个实现的对象、状态机、责任或资金边界不同，它们不是普通策略，而是不同业务模式。

## 7. 决策表与 DMN

### 7.1 决策表

用于有限条件组合和明确结果：

| 会员 | 促销商品 | 合同客户 | 决策 |
|---|---|---|---|
| 否 | 否 | 否 | 零售价 |
| 是 | 否 | 否 | 会员价 |
| 是 | 是 | 否 | 会员价与促销价择优 |
| 任意 | 任意 | 是 | 合同政策裁决 |

必须声明命中策略：唯一命中、优先级命中、收集全部或择优。谨慎使用“首条命中”，因为表格顺序容易意外成为业务语义。

### 7.2 DMN

用于复杂决策依赖：

```text
最终定价
├─ 基础价格选择
├─ 权益资格判断
├─ 组合合法性判断
├─ 优惠计算
├─ 商业底线校验
└─ 资金分摊
```

DMN 擅长业务决策，不负责长流程、分布式事务、状态生命周期和副作用一致性。

## 8. Pipeline：阶段化计算与决策

适合具有稳定处理阶段的业务：

```text
构造业务上下文
→ 资格筛选
→ 候选生成
→ 调整计算
→ 冲突裁决
→ 不变量校验
→ 分摊
→ 决策快照
```

每个阶段必须声明输入、输出、失败语义和不变量。执行顺序若影响业务结果，就必须成为显式业务政策，不能依赖处理器注册顺序。

## 9. State Machine：状态与合法转换

状态转换至少包含：

```text
当前状态
命令/事件
操作者
Guard 前置条件
目标状态
业务副作用
失败后状态
逆向路径
审计信息
```

状态机负责合法转换，不应承载所有金额计算、外部集成和流程编排。多个客户状态不同，先判断是命名差异、可选步骤还是不同业务模式；禁止直接求状态并集。
## 10. BPMN、Workflow 与 Process Manager

适合表达角色协作、审批、等待、超时、消息交互、补偿和人工任务：

```text
退款申请
→ 资格与金额判断
→ 必要时审核
→ 调用支付机构
→ 等待结果
→ 更新退款状态
→ 对账和差异处理
```

固定短流程不一定需要工作流引擎。只有步骤、角色或路由确实频繁变化，且具备版本、发布、监控和迁移治理时，工作流平台才可能带来净收益。

## 11. Agreement–Policy–Rule

多客户系统应区分：

```text
Agreement：与客户或合作方达成的约定。
Policy：组织批准的经营政策。
Rule：将政策转化为可执行判断或计算。
```

示例：

```text
Agreement：客户 A 在合同有效期享受协议价格。
Policy：协议价优先于会员价，但不能叠加商家优惠。
Rule：合同、商品和时间满足条件时产生协议价候选并排除冲突优惠。
```

该模式避免把客户 ID 直接写入核心规则。

## 12. Entitlement–Eligibility–Benefit

适用于会员、优惠券、权限、补贴和服务权益：

```text
Entitlement：主体拥有什么权利。
Eligibility：当前场景是否满足使用资格。
Benefit：本次实际获得什么结果。
Consumption：权益是否被消耗以及消耗多少。
```

“拥有权益”不等于“当前可使用”，也不等于“已经享受权益”。分离这几个概念可以减少重复发放、错误核销和退款恢复问题。

## 13. Limit–Quota–Reservation–Usage

适用于额度、预算、次数、库存和产能：

```text
Limit：总体上限
Quota：分配额度
Reservation：预占
Usage：正式使用
Release：释放
Adjustment：调整
```

典型不变量：

```text
已使用 + 已预占 <= 可用额度
```

是否允许临时超限、跨周期结转或负库存属于政策，不能由技术默认决定。

## 14. Account–Ledger–Transaction

适用于资金、积分、储值、信用额度和库存账：

```text
Account：业务账户
Transaction：业务交易
Entry：不可覆盖的增减分录
Ledger：账簿
Balance：由分录派生或校验的余额
Reversal：冲正或逆向交易
```

账本模式提高审计、冲正和对账能力，但简单、低风险、无需历史追溯的数据不必全部账本化。

## 15. Effective Dating 与 Versioned Policy

时间规则至少区分：

```text
业务发生时间
规则生效时间
系统处理时间
数据记录时间
```

规则版本应包含有效期、发布状态、来源、负责人和兼容关系。历史业务对象原则上绑定创建时的业务模式和规则版本；退款、撤销和审计使用原决策快照，而非当前最新政策。

## 16. 权限、责任与例外模式

### 16.1 RBAC、ABAC 与职责分离

- RBAC：角色权限较稳定。
- ABAC：权限取决于主体、对象、租户、门店、金额和环境属性。
- Separation of Duties：发起、批准、执行和复核不能由不相容角色同时承担。

权限必须在服务端校验对象和数据范围，前端隐藏按钮不构成授权证据。

### 16.2 Explicit Override

业务例外必须显式建模：

```text
适用条件
授权主体
额度和时效
理由
审批/复核
审计
影响
撤销或复审方式
```

管理员直接改状态或改库不是合格的例外机制。

## 17. Rule Engine / BRMS 使用边界

规则引擎适用于规则数量多、更新频繁、组合复杂、需要集中模拟发布且业务人员参与维护的场景。引入前必须具备：

- 稳定业务词汇和规则类型。
- 版本、有效期和审批发布。
- 冲突、依赖和非法组合检测。
- 历史回放、模拟、差异分析和回滚。
- 审计、性能、故障和权限治理。

以下场景不宜引入：

- 只有少量稳定规则。
- 业务语义和边界尚未澄清。
- 只是为了消除几个 `if/else`。
- 缺少规则所有者和发布治理。
- 规则会直接执行不可逆副作用。

规则引擎不能替代业务建模，只会更快执行已经表达清楚或表达混乱的规则。

## 18. 规则关系与冲突治理

规则之间必须声明关系：

| 关系 | 含义 | 治理 |
|---|---|---|
| Equivalent | 语义等价 | 合并或影子比较 |
| Exclusive | 互斥 | 同时命中时选择或拒绝 |
| Priority | 优先覆盖 | 明确优先级并防止成环 |
| Best-of | 多候选择优 | 声明比较指标和边界 |
| Ordered Composition | 有序组合 | 固化顺序和中间契约 |
| Commutative | 可交换组合 | 用性质测试证明 |
| Requires | 依赖 | 发布期校验 |
| Implies | 蕴含 | 自动补齐或拒绝 |
| Forbidden | 禁止组合 | 发布期和运行期阻断 |
| Undefined | 尚无业务答案 | 补证或人工裁决 |

### 18.1 三级治理

```text
设计期：决定语义、边界、责任、合同和政策。
发布期：检查互斥、依赖、优先级环、有效期和非法组合。
运行期：只执行已批准裁决；未知组合拒绝、挂起或转人工。
```

禁止使用调用顺序、后写覆盖、最新版本或客户特殊代码作为未声明的默认优先级。
## 19. 推荐运行架构

```text
业务事实 Fact
→ 构造业务上下文 Context
→ 选择业务模式 BusinessMode
→ 加载有效政策版本 PolicyVersion
→ 资格判断 Eligibility
→ 规则评估 Evaluation
→ 冲突裁决 Resolution
→ 生成业务决策 Decision
→ 校验不变量 InvariantGuard
→ 生成执行计划 ExecutionPlan
→ 统一产生副作用
→ 保存决策快照和审计
```

关键边界：

1. **规则评估尽量纯化**：相同事实、上下文和版本产生相同候选决策。
2. **决策与执行分离**：规则不直接扣款、扣库存、发券、退款或发送消息。
3. **副作用单一编排**：只有最终执行计划可以驱动不可逆动作。
4. **不变量独立守卫**：即使规则配置错误，也不能绕过资金、权限和状态底线。
5. **决策可快照**：必须能解释选择了什么、排除了什么以及为什么。

### 19.1 决策结果模型

```text
DecisionResult
- decisionId
- businessContext
- policyVersion
- matchedRules
- rejectedRulesAndReasons
- selectedOutcome
- intermediateValues
- invariantResults
- executionPlan
- reversePlan
- decidedAt
```

决策结果不是日志附属信息，而是退款、对账、审计、客服解释和历史重放的业务依据。

## 20. 业务规则元数据模型

完整业务规则至少包含：

```text
BusinessRule
- ruleId
- businessName
- businessMeaning
- ruleType
- source
- owner
- scope
- applicability
- condition
- decision/effect
- priority
- relations
- effectiveFrom/effectiveTo
- version
- overridePolicy
- auditRequirement
- lifecycleStatus
- testCases
```

### 20.1 来源和责任

规则来源可能是法律法规、客户合同、公司政策、产品决策、风险控制、运营配置或历史兼容。不同来源不能自动相互覆盖，必须定义适用边界和裁决权。

### 20.2 作用域

至少说明客户、租户、渠道、区域、产品、对象状态、业务模式和时间范围。未声明作用域的规则容易意外影响全部业务。

### 20.3 生命周期

```text
草稿
→ 待评审
→ 已批准
→ 待生效
→ 生效中
→ 已停止新业务使用
→ 仅服务历史对象
→ 已退役
```

规则删除不等于历史语义消失。只要历史对象仍需解释，规则版本或决策快照就必须可访问。

## 21. 规则设计与发布流程

```text
提出规则需求
→ 明确业务问题、来源和责任人
→ 分类为不变量/资格/决策/计算/状态/流程/权限等
→ 明确适用域和版本
→ 建立与现有规则的关系
→ 设计正例、反例、边界和冲突场景
→ 业务、财务、风险或合规评审
→ 模拟历史数据和组合空间
→ 发布前冲突校验
→ 灰度生效
→ 监控结果、差异和异常
→ 停止、回滚或退役
```

高影响规则不能由配置修改后立即全量生效。至少应具备审批、预览、模拟、影响范围、灰度、告警和回滚。

## 22. 测试与验证模式

### 22.1 决策表覆盖

检查每种有效条件组合是否有唯一声明结果，并发现：

- 条件遗漏。
- 重复规则。
- 多结果冲突。
- 不可达规则。
- 没有默认处理的场景。

### 22.2 边界测试

覆盖等于、小于和大于阈值，以及零、负数、最大值、空值、精度、舍入、跨日、有效期首尾和时区边界。

### 22.3 组合测试

对规则关系执行：

- 互斥组合拒绝。
- 依赖缺失拒绝。
- 优先级无环。
- 有序组合保持顺序。
- 非法组合不能发布。
- 未声明组合不能静默执行。

### 22.4 属性测试

不只枚举案例，还验证一般性质：

```text
任意合法退款序列：累计退款 <= 原有效支付。
任意合法优惠组合：客户应付 >= 0。
任意重复请求：不可逆副作用最多发生一次。
任意合法状态序列：不会越过禁止状态。
任意跨租户输入：不产生其他租户数据结果。
```

### 22.5 蜕变测试

验证输入变化与输出关系：

- 增加无关规则不应改变当前决策。
- 声称可交换的规则改变顺序后结果不变。
- 提高优惠额度不应在无其他约束时增加客户应付。
- 相同规则版本和输入重复计算结果一致。
- 增加限制条件不应扩大资格集合。

### 22.6 差分与影子测试

旧规则产生正式结果，新规则无副作用计算。差异必须分类为新缺陷、旧缺陷修正、政策改变、历史兼容、数据质量、配置差异或证据不足，不能自动以旧结果为正确答案。

## 23. 模式选择表

| 业务问题 | 首选模式 | 适用条件 | 不适用信号 |
|---|---|---|---|
| 少量稳定条件 | 具名方法/简单决策表 | 条件少、变化低 | 不要为形式统一上规则引擎 |
| 复杂资格判断 | Specification | 条件可组合且有稳定语义 | 大量匿名微规格 |
| 多因素决策 | Decision Table/DMN | 条件、结果和依赖可声明 | 决策实际依赖长事务 |
| 相同语义不同算法 | Strategy | 输入输出和不变量相同 | 状态或责任边界不同 |
| 完整可变政策 | Policy Object | 有范围、版本和负责人 | 只有一个简单公式 |
| 稳定处理阶段 | Pipeline | 阶段输入输出清晰 | 顺序隐式且任意插入处理器 |
| 生命周期 | State Machine | 状态有限、转换重要 | 只是展示标签 |
| 审批、等待、人工协作 | BPMN/Workflow | 流程确实频繁变化 | 短小固定同步流程 |
| 多客户合同 | Agreement–Policy–Rule | 合同、政策、规则可分离 | 直接按客户 ID 编程 |
| 会员、券和补贴 | Entitlement 模型 | 拥有、资格、享用需分离 | 简单永久权限 |
| 库存、预算和额度 | Reservation/Quota | 存在预占与竞争 | 只记录静态上限 |
| 资金、储值和积分 | Ledger | 需审计、冲正和对账 | 低风险无历史需求数据 |
| 外部模型差异 | Adapter/ACL | 外部语义不能污染核心 | 内外模型本来完全一致 |
| 大量动态规则 | Rule Engine/BRMS | 规则治理体系成熟 | 规则少或语义未澄清 |
| 历史业务解释 | Versioned Policy/Snapshot | 规则会变化且历史需重放 | 纯瞬时无历史影响判断 |

## 24. 常见反模式

- 把业务事实、经营政策、参数和技术配置混在一个规则中。
- 用客户 ID、租户 ID 或渠道编码直接代表业务模式。
- 规则命名只有技术条件，没有业务含义。
- 每个入口复制一份相似规则，形成多个权威版本。
- 用 `if/else` 顺序、规则表顺序或最后写入决定优先级。
- 规则执行时直接产生不可逆副作用。
- 把所有变化都做成策略，却没有资格和冲突裁决。
- 把所有参数都开放配置，允许未设计组合进入生产。
- 使用当前最新规则重新计算历史订单、退款和结算。
- 只测试单条规则，不测试规则交集和组合顺序。
- 以规则引擎替代不清晰的业务模型和责任划分。
- 规则下线但不保存历史版本和决策依据。
- 人工例外依靠改库、改状态且无授权审计。

## 26. AI 执行算法

```text
INPUT：业务目标、事实、规则、流程、历史版本、证据和决策边界

1. 分离事实、不变量、政策、规则、参数、流程、状态和技术机制。
2. 为每条规则确定类型、来源、Owner、适用域、版本和业务含义。
3. 优先提取不变量，并检查所有写入口能否绕过。
4. 资格使用具名谓词/Specification；多因素选择使用决策表或 DMN。
5. 计算规则分离基准、公式、顺序、精度、上下限和分摊。
6. 生命周期使用状态机；角色协作和等待使用流程模型。
7. 将客户合同、组织政策和执行规则分离。
8. 建立规则等价、互斥、优先、择优、组合、依赖和禁止关系。
9. 设计期解决语义冲突，发布期阻断非法组合，运行期只执行已批准裁决。
10. 让规则先产生决策，再由唯一执行计划实施副作用。
11. 建立规则版本、有效期、决策快照、正逆向和历史解释。
12. 使用边界、组合、属性、蜕变和差分测试验证。
13. 比较简单实现、结构化模式、规则平台和不处理方案的净收益。
14. 将高影响方案交由 SOP-09 评审并记录剩余未知项。
```

AI 不得把常见模式直接判为最佳方案；每次推荐必须说明适用条件、新增成本、反例边界、验证和退出方式。
