## 读者引导

### TL;DR

稳定不是“服务进程没有宕机”，也不是“接口大多数时候返回 200”。稳定的业务系统必须同时保证：

```text
业务结果正确
+ 关键能力在目标时间内可用
+ 数据不丢、不重、不串、不被旧版本覆盖
+ 负载和依赖异常时影响受控
+ 故障能够发现、止血、恢复和验证
+ 变更能够灰度、回退或前向修复
+ 用户、运营和工程人员看到适合其职责的真实状态
```

稳定性设计的主线是：

```text
关键用户旅程
-> 业务不变量和失败后果
-> SLI / SLO / RTO / RPO
-> 依赖与故障模型
-> 预防、隔离、降级和恢复机制
-> 可观测、告警和运行手册
-> 压测、故障演练和恢复证据
-> 事故学习与持续演进
```

本文不允许 AI 直接从故障名称跳到熔断、重试、扩容或多活。标准及高风险设计必须执行 §1A 的创造性稳定性分析：重构业务承诺，比较竞争解释，发现隐藏的共同故障、替代履约方式和业务能力进化机会，再选择工程机制。

## 0. 定位与使用契约

### 0.1 文档定位

本文是业务系统设计总纲中的稳定性专项方法论，负责把业务正确性、可靠性目标、故障治理、数据收敛、可观测、变更安全、事故响应和恢复验证连成闭环。

本文不替代：

- 业务目标、规则、状态、数据所有权和权限边界设计；
- 针对具体系统的容量测试、灾备方案和运行手册；
- 安全威胁建模和合规评估；
- 既有系统事实分析和兼容性盘点。

如果业务语义、不变量和数据所有权尚未明确，不能直接通过增加副本、重试和告警解决“稳定性”。错误逻辑被更稳定地执行，只会更稳定地产生错误结果。

既有系统补充稳定性治理时，必须先经过 `研发方法/元规范-既有业务系统评估、进化与重构规范.md` 路由。只补可靠性机制且不改变核心抽象时走路径 A；RCA 发现错误业务状态、主关系、不变量、责任或一致性边界时升级路径 B。本文产生的候选必须回到统一 L1 完成兼容、验证和迁移收敛。

### 0.2 适用与不适用

适用于：

- 核心业务链路的新系统设计；
- 对现有系统补充稳定性治理；
- 跨服务、消息、定时任务和同步链路设计；
- 资金、订单、库存、数据同步等高完整性场景；
- SLO、容灾、变更和事故响应体系建设；
- 上线前稳定性评审和演练。

不适用于：

- 用通用模式替代具体业务事实；
- 未经授权在生产环境压测或注入故障；
- 只凭一次成功测试宣称系统可靠；
- 只提高技术可用性，却不验证业务结果和数据正确性。

### 0.3 稳定性不是单一属性

```text
稳定性 =
  正确性
  + 可用性
  + 可靠性
  + 韧性
  + 数据持久性
  + 可恢复性
  + 可预测性
  + 可运营性
```

这些属性有联系但不能互相替代。例如：

- 服务可用但返回错误价格，业务仍不稳定；
- 数据最终能恢复但恢复需要三天，不满足业务恢复目标；
- 有三个副本但位于同一故障域，不构成有效容灾；
- 自动重试成功率很高但造成重复扣款，不是韧性；
- 告警很多但无人知道如何处理，不是可运营性。

### 0.4 风险驱动深度

稳定性设计深度由以下因素决定：

- 失败是否影响资金、库存、权限、合规或客户承诺；
- 影响范围和爆炸半径；
- 失败是否可逆；
- 数据是否能够重建或对账；
- 业务能够容忍的中断和数据丢失；
- 依赖、部署和组织复杂度；
- 变更频率和恢复能力。

低风险、可逆的内部工具不需要照搬金融核心系统的容灾成本；高风险核心链路也不能用“系统不大”省略正确性和恢复设计。

### 0.5 完成定义

满足以下条件才算完成稳定性设计：

- 关键用户旅程及其业务结果明确；
- 正确性底线与可预算的可靠性目标分开；
- SLI、SLO、统计窗口、RTO 和 RPO 可计算；
- 依赖、故障域、部分失败和恢复路径已建模；
- 超时、重试、限流、背压、隔离和降级形成组合，而非孤立配置；
- 重复、并发、乱序、消息丢失和数据差异能够收敛；
- 告警可行动，运行手册和责任人明确；
- 变更、回滚、前向修复和恢复演练可执行；
- 关键结论已有测试、观测或演练证据；
- 标准及高风险设计已经完成创造性稳定性分析，形成竞争解释、替代履约候选和区分性验证，或给出收敛到简单机制的证据；
- 已判断稳定性缺陷只是实现问题，还是暴露了业务义务、状态、权威、反馈或运营能力缺失；
- 未覆盖风险和复验触发条件已经记录。

## 1. 稳定性基础模型

### 1.1 核心术语

| 术语 | 定义 | 典型问题 |
|---|---|---|
| Correctness 正确性 | 系统结果满足业务规则和不变量 | 是否算对、写对、作用于正确对象？ |
| Availability 可用性 | 在约定观察口径下能够提供合格服务的比例 | 用户是否能完成关键任务？ |
| Reliability 可靠性 | 在一段时间内持续产生正确结果的能力 | 是否反复出错或行为不可预测？ |
| Resilience 韧性 | 发生扰动后限制影响并维持或恢复关键能力 | 依赖失败时能否降级和恢复？ |
| Durability 持久性 | 已确认成功的数据在承诺范围内不丢失 | 确认后的订单会不会消失？ |
| Recoverability 可恢复性 | 在目标时间和数据损失范围内恢复 | RTO、RPO 是否达标？ |
| Safety 安全性 | 不产生不可接受的危险或错误结果 | 是否会错扣款、串租户、卖出非法库存？ |
| Operability 可运营性 | 人能够理解、控制和修复系统 | 是否能发现、止血、重试和审计？ |

### 1.2 Fault、Error、Failure

```text
Fault 故障原因
  -> Error 内部错误状态
     -> Failure 对外未满足承诺
```

示例：

```text
数据库连接泄漏（Fault）
-> 连接池耗尽（Error）
-> 用户无法提交订单（Failure）
```

稳定性治理可以作用于不同位置：消除故障原因、阻止错误状态传播，或在发生对外失败后快速恢复。不能把用户看到的症状直接写成根因。

### 1.3 关键用户旅程

稳定性目标应围绕业务旅程，而不是围绕服务器进程：

```text
关键用户旅程 =
  <角色,
   业务意图,
   前置条件,
   核心路径,
   成功结果,
   正确性不变量,
   允许的降级,
   失败后果>
```

例如：

- 顾客完成支付并只生成一次入账结果；
- 门店在断网时完成可离线销售的最小业务；
- 总部价格按授权范围发布到目标门店；
- 退款在约定时间内完成并可追溯；
- 库存扣减不突破业务允许的下限。

CPU、内存和进程状态是支持信号，不是最终稳定性目标。

### 1.4 正确性底线与错误预算分开

有些目标可以按比例管理，例如 99.9% 的合格请求在目标延迟内完成。有些底线不能用错误预算合理化，例如：

- 跨租户或跨门店数据访问；
- 重复扣款或重复入账；
- 退款超过原支付；
- 未授权价格发布；
- 已确认成功的数据静默丢失。

这类不变量应通过预防、检测、拒绝、审计和恢复机制保护，不能解释成“每月允许错几次”。

### 1.5 可用性计算的边界

在简化、稳定故障率和可修复系统假设下，可以写：

```text
Availability = MTBF / (MTBF + MTTR)
```

这只是一个长期近似模型。真实系统还可能存在部分降级、灰色故障、计划维护、不同用户受影响程度和数据错误，因此不能仅靠 MTBF/MTTR 推导业务可用性，也不能笼统断言降低 MTTR 永远比提高 MTBF 更重要。

## 1A. AI 创造性稳定性分析与业务进化协议

### 1A.1 稳定性创造力解决什么问题

常规稳定性分析从组件故障出发，容易得到固定答案：加超时、重试、熔断、限流、副本和告警。创造性稳定性分析必须进一步追问：

- 组件失败时，用户真正需要的业务结果是否仍能通过其他方式完成；
- 当前“失败”是否只是系统没有建模的合法业务状态；
- 多个故障是否来自同一个错误业务抽象、共同依赖或控制点；
- 是否把技术确认误当成业务履约证明；
- 恢复是否只是恢复进程，还是恢复业务事实和用户信任；
- 稳定性缺陷是否暴露了值得产品化的新运营、自治、对账或补救能力。

目标不是发明更多基础设施，而是发现跨故障条件仍然成立的业务承诺，并选择最小、可验证的实现。

### 1A.2 继承总纲 CA0-CA8

本文强制继承 `22-方法论-系统设计原理与实践.md` §1A 的三空间隔离、CA0-CA8、十二个业务重构视角、创造性分析卡和 CG1-CG6。稳定性专项在此基础上增加 RCA0-RCA7；两套流程可以合并记录，不能互相替代。

本文不复制 CA 通用卡和通用门禁。稳定性报告只记录 RCA 增量以及它对既有 CA 结论的修正；如果 RCA 推翻业务本质或目标设计，必须返回 22A 和统一 L1 更新上游结论，不能只改稳定性附件。

### 1A.3 RCA0-RCA7 稳定性创造循环

`RCA` 表示 Reliability Creative Analysis。

| 阶段 | AI 必须执行的动作 | 最小产物 |
|---|---|---|
| RCA0 重写承诺 | 用业务语言定义成功、失败、允许降级和不可预算底线 | 业务承诺和失败后果 |
| RCA1 寻找悖论 | 找出“技术成功但业务失败”“进程恢复但数据未恢复”等矛盾 | 稳定性悖论清单 |
| RCA2 竞争解释 | 区分实现缺陷、错误失败语义、共同依赖、业务状态缺失和错误抽象 | 假设、预测和区分证据 |
| RCA3 共享命运分析 | 发现副本、区域、租户、控制面和人工操作的隐藏共同故障 | 共享命运和爆炸半径 |
| RCA4 替代履约 | 探索延迟履约、异步受理、只读、最后有效值、人工接管和替代渠道 | 业务级降级/替代路径 |
| RCA5 能力提炼 | 将重试、对账、回执、恢复、例外处理提炼成可复用业务能力 | 候选稳定性业务能力 |
| RCA6 进化推演 | 推演十倍规模、长时间离线、规则变化和灾难恢复后的业务形态 | 进化候选及失效条件 |
| RCA7 区分验证 | 用故障实验、数据对账或行为预测淘汰解释并收敛 | 验证结果和条件化决策 |

### 1A.4 十个稳定性重构视角

| 视角 | 创造性追问 |
|---|---|
| 承诺 | 系统承诺的是接收请求、完成处理，还是最终业务结果？ |
| 结果未知 | 超时后是真的失败，还是缺少查询最终结果的能力？ |
| 业务状态 | 离线、待履约、部分完成、待核对是否被错误归为技术异常？ |
| 替代履约 | 原路径失败时，能否延迟、异步、只读、人工或通过其他渠道完成？ |
| 最后有效事实 | 依赖不可用时，哪些经过验证的旧事实可以安全继续使用？ |
| 权威与核对 | 多方状态冲突时以谁为准，怎样证明最终一致？ |
| 共享命运 | 看似独立的副本、服务和团队是否依赖同一控制面、数据或操作？ |
| 恢复负载 | 系统恢复后积压、补传、重试和缓存回源是否造成第二次故障？ |
| 人机协作 | 自动恢复失败后，业务人员能否在受控权限下安全处理？ |
| 学习进化 | 事故是否揭示了新的业务能力、服务承诺或自治边界？ |

### 1A.5 六种创造性转换

稳定性洞察经常来自以下转换，但只能在项目事实命中时使用：

```text
技术异常 -> 明确的业务中间态
发送动作 -> 有期限、有对象、有证明的履约义务
盲目重试 -> 幂等结果查询 + 受控重试 + 对账
备用资源 -> 经过演练的业务恢复能力
监控告警 -> 能改变系统或人的控制反馈环
事故记录 -> 业务能力和边界演进信号
```

例如，门店离线不一定是“消息失败”。它可能是“目标门店尚未履约、在恢复连接后有补传义务”的业务状态。这个重构会自然推导出期限、版本水位、最后有效值、回执、逾期和人工补救，而不仅是增加重试次数。

### 1A.6 稳定性进化候选光谱

对非简单问题至少扫描：

| 层级 | 候选方向 |
|---|---|
| R-E0 接受 | 保留现状，明确风险、损失和触发条件 |
| R-E1 技术修复 | 修复单一缺陷，不改变业务语义 |
| R-E2 可靠性机制 | 超时、幂等、背压、隔离、对账、恢复等机制治理 |
| R-E3 运营能力 | 将观察、重试、补偿、核对和人工处理产品化 |
| R-E4 替代履约 | 为依赖失败、离线或过载设计可接受的业务完成路径 |
| R-E5 业务承诺进化 | 重新定义服务等级、责任、自治、回执和例外处理 |
| R-E6 核心抽象进化 | 改变对象、生命周期、主关系、不变量或能力边界，升级设计评估与重构 |

最终可以选择 R-E1，但必须证明 R-E2 至 R-E5 没有更高决策价值，而不是从未探索。

### 1A.8 创造性稳定性门禁

#### RCG1：从业务承诺出发

- 没有直接从 CPU、数据库、消息或网络故障跳到方案；
- 能说明故障破坏了哪个用户旅程、业务义务或不变量。

#### RCG2：存在竞争解释

- 已区分实现故障、失败语义缺失、业务状态缺失、共同依赖和错误抽象；
- 高影响结论具有不同预测及区分性验证。

#### RCG3：探索替代履约

- 至少评估一种业务级降级、延迟履约、人工接管或替代路径；
- 不适用时说明业务或安全原因。

#### RCG4：提炼业务能力

- 检查稳定性机制是否应形成用户或运营可直接使用的回执、核对、恢复和例外处理能力；
- 没有把所有问题都封装成内部技术组件。

#### RCG5：形成可证伪进化候选

- 至少扫描 R-E0 至 R-E6；
- 候选写明成立、失效、成本、兼容和验证条件。

#### RCG6：安全收敛

- 创造性假设没有降低正确性、安全、隔离、兼容和恢复底线；
- 命中核心抽象变化时升级，不在可靠性补丁中偷改业务模型。

标准及高风险稳定性设计必须同时通过总纲 CG1-CG6 和本节 RCG1-RCG6。低风险局部修复可以精简记录，但不得因改动小而跳过业务承诺和失败后果判断。

### 1A.9 独立审查问题

Reviewer 必须额外追问：

- 方案是否只是把常见稳定性模式逐项套上去？
- 哪个技术成功与业务失败的悖论被识别？
- 哪些故障由同一个业务义务、状态或权威缺失解释？
- 原路径不可用时是否存在更安全的业务完成方式？
- 恢复后如何证明业务而非进程已经恢复？
- 这项治理能否成为业务人员可使用的能力？
- 什么事实会推翻当前稳定性抽象？

无法回答时，文档可能完整，但尚未达到创造性稳定性分析要求。

## 2. 可靠性目标：SLI、SLO、错误预算、RTO 和 RPO

### 2.1 从旅程定义 SLI

SLI 是服务水平指标，必须明确：

- 测量对象；
- 有效事件或有效时间；
- 合格事件或合格时间；
- 数据来源；
- 聚合方式；
- 排除条件；
- 数据延迟和缺失处理。

请求型 SLI 的常见表达：

```text
SLI = 合格事件数 / 有效事件数
```

“有效”和“合格”必须由业务定义，不能直接把所有 HTTP 2xx 当作成功。

### 2.2 SLI 类型

| 类型 | 示例 |
|---|---|
| 可用性 | 有效提交中成功产生业务结果的比例 |
| 延迟 | 合格结果在目标时间内完成的比例 |
| 正确性 | 抽样或对账结果中满足业务不变量的比例 |
| 新鲜度 | 数据在允许延迟内更新的比例 |
| 完整性 | 预期记录、消息或明细实际到达的比例 |
| 持久性 | 已确认数据在观察窗口内仍可读取且校验一致的比例 |
| 恢复性 | 故障演练中在 RTO/RPO 内恢复的比例 |

### 2.3 SLO 规格

```text
SLO =
  <关键旅程,
   SLI 定义,
   目标值,
   统计窗口,
   统计方法,
   排除条件,
   数据源,
   责任人,
   违反后的策略>
```

示例：

```text
旅程：在线门店应用已批准价格版本
SLI：计划生效后五分钟内成功应用且版本正确的在线目标项 / 在线有效目标项
目标：30 天滚动窗口 >= 99.5%
数据源：发布明细、门店确认和版本对账
排除：在整个目标窗口内被确认离线的门店，但离线识别本身必须可靠
违反策略：冻结高风险发布变更，优先处理可靠性缺口
```

目标值必须基于业务损失和成本决定，不应无条件追求更多的“9”。

### 2.4 错误预算

```text
允许错误比例 = 1 - SLO 目标

错误预算事件数 = 有效事件数 * 允许错误比例
```

若 30 天内有 1,000,000 个有效事件，SLO 为 99.9%，则该窗口错误预算为 1,000 个不合格事件。它用于平衡功能变更和可靠性投入，不表示业务不变量可以被破坏。

### 2.5 燃烧率

```text
Burn Rate = 实际错误率 / SLO 允许错误率
```

燃烧率大于 1 表示以当前速度持续下去会耗尽预算。告警应结合短窗口和长窗口：短窗口发现快速事故，长窗口发现持续退化。具体阈值应根据 SLO 窗口、值班能力和误报成本设计，不能机械复制固定数字。

### 2.6 错误预算策略

错误预算策略应由业务、研发和运维共同确认：

| 状态 | 可选策略 |
|---|---|
| 预算充足 | 正常迭代，持续观察护栏指标 |
| 消耗加快 | 降低变更频率，优先修复主要消耗源 |
| 即将耗尽 | 暂停非必要高风险发布，执行稳定性专项 |
| 已耗尽 | 由风险负责人决定恢复策略和例外，不自动继续变更 |

### 2.7 RTO 和 RPO

| 指标 | 回答的问题 |
|---|---|
| RTO | 从中断开始，业务能力最迟多久恢复？ |
| RPO | 恢复后最多允许丢失多长时间范围的数据？ |

RTO/RPO 必须按业务能力和数据分类定义，不应只给整个系统一个数字。例如查询可在五分钟内恢复，支付写入可能要求更严格；可重建报表数据和不可重建交易事实的 RPO 也不同。

### 2.8 MTTD、MTTA、MTTR

| 指标 | 含义 |
|---|---|
| MTTD | 从故障开始到被检测的平均时间 |
| MTTA | 从告警产生到有人接手的平均时间 |
| MTTR | 从故障开始或确认到业务恢复的平均时间，必须声明口径 |

平均值可能掩盖长尾，应同时观察分位数、最大值和按故障类型分组的分布。

### 2.9 依赖目标不能简单相加

关键旅程依赖多个组件时，整体可靠性受串并联关系、共同故障和降级能力影响。不能把各依赖的 SLA 直接相加或默认独立。需要通过运行时依赖图、故障域和用户旅程实测整体 SLI。

## 3. 依赖、故障域和失败建模

### 3.1 运行时依赖图

对每条关键旅程画出：

```text
入口
-> 网关/身份
-> 核心服务
-> 数据库/缓存/消息
-> 外部服务
-> 异步消费者/任务
-> 最终业务结果
```

每条边记录：

- 是否关键依赖；
- 同步或异步；
- 超时和 deadline；
- 重试位置；
- 降级行为；
- 数据和权限作用域；
- 失败时影响的用户旅程；
- 负责人和运行手册。

### 3.2 故障域

常见故障域包括：

- 进程和线程池；
- 容器、虚拟机和物理机；
- 可用区、机房和区域；
- 数据库主从或分片；
- 消息分区；
- 网络、DNS、证书和时间服务；
- 配置中心和控制面；
- 第三方供应商；
- 租户、商户和大客户流量；
- 发布批次和功能开关范围。

多个副本只有在关键故障域上足够独立，才形成有效冗余。

### 3.3 爆炸半径

设计时必须问：

- 一个坏请求最多影响多少用户；
- 一个大租户能否耗尽共享资源；
- 一个错误配置影响单实例、单租户还是全局；
- 一条毒消息能否阻塞整个分区；
- 一个错误版本能否一次发布到所有门店；
- 一个数据库故障会影响哪些业务能力；
- 运维操作是否有范围限制和二次确认。

稳定性不是只降低故障概率，也包括把不可避免的故障限制在较小范围。

### 3.4 失败不是只有“成功/失败”

至少区分：

| 类型 | 特征 |
|---|---|
| 明确失败 | 已知未产生业务结果，可以安全重试或提示 |
| 结果未知 | 调用超时，但远端可能已经产生结果 |
| 部分成功 | 多对象或多步骤中只有一部分完成 |
| 延迟成功 | 当前未完成，但后台仍可能收敛 |
| 错误成功 | 技术返回成功，业务结果错误 |
| 灰色故障 | 部分请求、实例、用户或数据异常，整体探活仍正常 |
| 静默失败 | 无错误信号，但数据遗漏或状态未推进 |

不同失败类型的重试、反馈和恢复策略不同。

### 3.5 相关性故障

不要默认故障独立。常见相关性来源：

- 多副本共享同一数据库、网络或证书；
- 主备使用同一错误配置；
- 所有消费者处理同一毒数据；
- 多区域依赖同一控制面或第三方；
- 自动重试同时放大下游压力；
- 故障切换把流量转移到容量不足的备用环境。

### 3.6 失败模式分析卡

```markdown
### FM-XXX：失败模式

- 关键旅程：
- 触发条件：
- 局部错误状态：
- 用户可见失败：
- 受影响不变量：
- 爆炸半径：
- 当前预防：
- 检测信号：
- 自动处置：
- 人工处置：
- 恢复和验证：
- 未覆盖风险：
```

常见失败模式可路由到 `03-方法论-系统级失败模式与设计约束清单.md` 和 `04-清单-通用系统级失败模式与设计约束.md`，本文负责把它们映射到具体用户旅程和恢复闭环。

### 3.7 优先级

不要平均处理所有故障。可按以下因素排序：

```text
优先级约等于
  业务后果
  * 发生可能性
  * 影响范围
  * 不可逆程度
  * 难以检测程度
```

资金、权限、跨作用域和数据静默损坏即使概率较低，也可能具有更高优先级。

## 4. 超时、重试、过载、隔离和降级

### 4.1 机制必须组合设计

孤立使用稳定性模式容易产生反效果：

- 只有超时，没有取消和结果查询，会制造结果未知；
- 只有重试，没有退避和预算，会放大故障；
- 只有熔断，没有降级和恢复探测，会把暂时故障变成长时间不可用；
- 只有队列，没有边界和背压，会把故障变成积压；
- 只有副本，没有故障域独立和切换验证，会形成伪冗余；
- 只有降级，没有业务边界，会返回错误或危险结果。

### 4.2 Deadline 和超时预算

端到端请求应携带剩余 deadline，下游调用根据剩余预算设置超时：

```text
总预算 >=
  排队时间
  + 各处理阶段时间
  + 外部调用时间
  + 允许的重试与退避
  + 返回和渲染时间
```

设计原则：

- 连接、单次读取和业务总 deadline 分开；
- 下游超时小于上游剩余时间；
- 超时后尽可能取消无意义工作；
- 对不可取消写操作提供结果查询和幂等语义；
- 根据延迟分布和业务预算设置，不复制固定三秒；
- 长任务异步化并暴露任务状态，而不是无限延长请求超时。

### 4.3 重试

只有同时满足以下条件才考虑自动重试：

- 错误具有瞬时性；
- 操作天然幂等或已有可靠幂等保护；
- 重试仍在业务 deadline 内；
- 下游没有持续过载；
- 重试层级和责任唯一；
- 有最大次数、退避、随机抖动和重试预算；
- 能观察首次请求和重试的整体结果。

禁止对参数错误、权限错误、明确业务拒绝和不可幂等副作用盲目重试。

重试放大示例：三层调用各重试三次，最坏可能把底层调用放大到 `3 * 3 * 3 = 27` 次。因此通常应在最了解业务语义的一层重试，而不是每层都重试。

### 4.4 熔断

熔断器应定义：

- 统计窗口和最小样本；
- 哪些错误计入失败；
- 打开阈值；
- 打开后的降级或拒绝行为；
- 半开探测的并发和频率；
- 恢复判据；
- 状态指标和人工干预边界。

熔断保护调用方和下游资源，不保证业务结果完成。被熔断的工作仍需明确返回、排队、补偿或人工处理。

### 4.5 限流和准入控制

限流应回答：

- 保护的资源是什么；
- 按全局、租户、用户、门店、接口还是优先级限流；
- 瞬时突发容量；
- 被拒绝请求如何反馈和重试；
- 是否为关键业务保留容量；
- 大租户能否耗尽共享资源；
- 限流配置错误时怎样回退。

只设置全局 QPS 可能导致大客户或批量任务挤占所有资源，需要结合公平性和作用域设计。

### 4.6 有界队列、背压和负载丢弃

队列不是无限缓冲。必须定义：

- 最大长度或最大等待时间；
- 生产速率和消费能力；
- 积压后的业务过期语义；
- 谁向上游传播背压；
- 哪些低优先级工作可以丢弃；
- 哪些关键工作必须持久化；
- 恢复时怎样避免瞬时洪峰；
- 积压是否会导致旧事件覆盖新状态。

### 4.7 隔离

隔离维度可以包括：

- 线程池和连接池；
- 租户和大客户；
- 在线与批处理；
- 读与写；
- 核心与非核心业务；
- 消息主题和分区；
- 故障域和发布批次；
- 高风险功能开关。

隔离的目标是限制资源竞争和爆炸半径，但会增加容量碎片和运营复杂度，需要用风险证明。

### 4.8 降级

降级必须由业务明确允许：

| 类型 | 示例 | 必须避免 |
|---|---|---|
| 功能降级 | 暂停推荐，保留下单 | 把非核心失败扩大到核心链路 |
| 数据降级 | 展示有时间戳的旧数据 | 把过期数据伪装成实时事实 |
| 精度降级 | 使用预计算近似值 | 在资金和合规计算中静默近似 |
| 交互降级 | 任务转异步，稍后查看结果 | 让用户重复提交产生副作用 |
| 只读降级 | 暂停写入，保留查询 | 在不能保证一致时继续危险写入 |

降级结果必须标明数据时间、能力限制和下一步动作。

### 4.9 冗余、选主和防脑裂

冗余设计至少说明：

- 副本是否跨关键故障域；
- 数据复制是同步还是异步；
- 选主和仲裁条件；
- 网络分区时哪一侧允许写；
- 旧主恢复后如何防止继续写入；
- 是否使用租约、任期或 fencing token；
- 切换期间的 RTO/RPO；
- 切换和回切是否演练。

负载均衡不等于高可用，多副本也不自动解决共享数据库和共同配置故障。

## 5. 数据正确性、幂等、消息和对账

### 5.1 业务稳定性的底座是不变量

以下问题必须先于重试和副本设计：

- 什么业务事实绝不能被破坏；
- 不变量在哪个作用域成立；
- 哪个写入点负责原子保护；
- 跨系统期间允许什么中间态；
- 怎样发现静默损坏；
- 自动恢复失败后怎样对账和人工修复。

详细不变量方法路由到 `18-方法论-统一不变量体系设计.md`。

### 5.2 幂等请求模型

完整幂等记录至少包含：

```text
作用域
+ 幂等键
+ 请求摘要
+ 处理状态
+ 业务结果引用
+ 创建和过期时间
```

处理流程：

1. 在真实业务作用域内原子声明幂等键；
2. 相同键但请求摘要不同，应拒绝而不是返回旧结果；
3. 首次处理中时返回明确的“处理中”或查询入口；
4. 首次成功后重放同一业务结果；
5. 业务写入和幂等结果尽量处于同一事务边界；
6. 记录过期时间必须长于业务可能重试和消息重放窗口；
7. 外部不可回滚副作用需要单独的业务标识和结果查询。

“插入前查询”存在并发窗口，必须以数据库唯一约束、条件更新或同等原子机制作为最终保护。分布式锁可以减少竞争，但锁过期和所有权变化使它不能单独证明幂等。

### 5.3 状态机和条件更新

关键状态迁移应表达为：

```text
仅当 当前状态 = 允许源状态 且 版本 = 预期版本
才执行 业务写入 + 状态迁移 + 审计/事件记录
```

受影响行数为零时，必须区分：已处理、版本冲突、对象不存在、作用域错误和非法状态，不能一律当成成功。

### 5.4 Outbox 和 Inbox

Transactional Outbox 用于保证本地业务事实和待发布事件在同一事务中提交，后台发布器负责可靠投递。Inbox 或消费记录用于识别重复事件。

它们仍需要设计：

- 发布失败和积压；
- 消费幂等；
- 事件版本和兼容；
- 顺序要求；
- 清理和归档；
- 监控和重放；
- 业务对账。

Outbox 不等于端到端“恰好一次”。跨系统通常通过至少一次投递、幂等处理和可验证收敛获得业务上的唯一结果。

### 5.5 消息重复、乱序和毒消息

| 问题 | 典型机制 |
|---|---|
| 重复 | 业务幂等键、消费记录、结果重放 |
| 乱序 | 版本号、序列号、状态守卫、按键分区 |
| 丢失怀疑 | Outbox、水位、完整性对账 |
| 毒消息 | 有界重试、死信隔离、人工修复后重放 |
| 积压 | 背压、扩容、优先级、过期策略 |
| 重放 | 明确范围、幂等验证、副作用保护和审计 |

死信队列不是终点。必须有人负责、可定位、可修复、可重放，并防止同一消息无限往返。

### 5.6 Saga 和补偿

跨系统长事务可使用 Saga 思路，但补偿不等于物理撤销：

- 补偿动作本身可能失败；
- 有些外部事实不可逆，只能业务冲正；
- 补偿必须幂等；
- 中间态需要对用户和运营可见；
- 需要超时、人工介入和最终核对；
- 补偿后仍需保留原始历史和审计链。

### 5.7 对账是独立保护层

实时流程成功不能证明长期数据一致。对账应独立回答：

- 以哪个权威事实为基准；
- 比较的业务键和时间窗口；
- 容忍差异和等待时间；
- 如何处理迟到数据；
- 差异怎样分类；
- 哪些可自动修复；
- 哪些需要双人复核；
- 修复后怎样复验和审计。

### 5.8 时间和版本

稳定性设计要区分：事件发生时间、系统接收时间、处理时间和业务生效时间。涉及版本覆盖时应使用可比较的业务版本或顺序语义，不能仅依赖不同机器的本地时间戳。

### 5.9 备份不能代替一致性保护

备份用于灾难恢复，不负责实时阻止重复扣款、乱序覆盖和跨租户写入。正确性保护、在线对账和备份恢复是不同层次，必须同时按风险设计。

## 6. 变更可靠性

### 6.1 变更是主要风险来源之一

变更不仅包括代码发布，还包括：

- 配置和功能开关；
- 数据库结构、索引和数据回填；
- 消息和 API 契约；
- 依赖版本和证书；
- 基础设施、网络和权限；
- 批处理、同步范围和调度频率；
- 运营批量操作。

### 6.2 变更风险分级

| 因素 | 风险上升信号 |
|---|---|
| 影响范围 | 全局、全租户、全部门店 |
| 可逆性 | 数据或外部副作用难以回滚 |
| 新颖性 | 新技术、新路径、缺少生产证据 |
| 复杂度 | 多服务、多阶段、多团队协同 |
| 检测性 | 错误结果难以及时观察 |
| 恢复性 | 回滚慢、数据需要人工修复 |
| 时机 | 高峰、大促、无人值守窗口 |

高风险变更需要更小灰度、更强护栏、更长观察和更明确的决策责任。

### 6.3 发布前门禁

- 业务目标、不变量和影响范围明确；
- 兼容调用方、数据、配置、任务和消息已盘点；
- 容量和故障假设有验证；
- 数据迁移可重入、可暂停、可观察；
- 灰度单位和样本合理；
- 护栏指标、停止条件和负责人明确；
- 回滚后新数据仍可被旧版本读取，或已有前向修复；
- 运行手册和值班安排就绪。

### 6.4 渐进式发布

灰度不是固定百分比流程。应根据业务边界选择：

- 内部主体；
- 白名单租户或门店；
- 单实例或单可用区；
- 按数据范围；
- 按功能开关；
- 按可逆的影子计算；
- 按逐步扩大的流量比例。

写入、扣款、扣库存、发券和发送外部消息等有副作用操作不能为了比较而无保护双跑。影子验证只适合无副作用、结果可比较的计算，并且线上结果仍由旧路径决定。

### 6.5 护栏指标

灰度必须同时观察：

- 关键业务结果和正确性；
- SLI 和错误预算燃烧；
- 新旧结果差异摘要；
- 数据作用域和审计异常；
- 延迟、错误、积压和资源水位；
- 人工工单和用户反馈；
- 回滚或关闭开关是否真实可用。

### 6.6 配置变更

配置键、默认值、单位、作用范围和优先级都是契约。需要：

- 结构和范围校验；
- 版本、审批、审计和原因；
- 灰度发布和实例生效状态；
- 错误值的安全边界；
- 回滚值和恢复路径；
- 敏感配置脱敏；
- 临时配置到期和清理。

“动态配置”不代表可以无门禁全局即时生效。

### 6.7 数据库变更

采用：

```text
Expand -> Backfill/Migrate -> Verify -> Contract
```

重点检查：

- 大表锁和资源影响；
- 新旧应用滚动期间的读写兼容；
- 回填批次、游标、重跑和失败处理；
- NULL、默认值和历史语义；
- 索引建立和查询计划变化；
- 报表、导出、同步和外部读取；
- 回滚或前向修复；
- 收紧约束和删除旧字段前的无依赖证据。

### 6.8 功能开关

开关必须有：名称、默认值、作用域、负责人、启用条件、观测指标、关闭方式、下线日期和旧路径删除条件。长期存在的开关会形成组合爆炸和不可测试状态，应纳入清理治理。

### 6.9 回滚并非总是安全

以下场景可能无法简单回滚版本：

- 新版本已写入旧版本不认识的数据；
- 已发送不可撤回的消息或第三方请求；
- 数据结构已收紧或删除；
- 批量操作已产生业务结果；
- 新旧版本对同一状态有不同解释。

此时需要兼容读取、业务补偿、数据修复或前向修复方案。

## 7. 可观测、告警和面向人的透明度

### 7.1 可观测性服务于问题回答

日志、指标和链路不是目的。可观测系统应帮助回答：

- 哪个用户旅程失败；
- 影响哪些租户、门店或业务对象；
- 从什么时候开始；
- 最近发生了什么变更；
- 故障位于哪个依赖或故障域；
- 数据是否错误、延迟、遗漏或重复；
- 自动恢复是否有效；
- 当前应该执行什么安全动作。

### 7.2 信号层次

| 层次 | 示例 |
|---|---|
| 业务结果 | 支付成功率、价格按时生效率、退款完成率 |
| 用户旅程 SLI | 合格事件比例、延迟、新鲜度、正确性 |
| 服务信号 | Rate、Errors、Duration、Saturation |
| 资源信号 | CPU、内存、连接、磁盘、队列和线程池 |
| 变更信号 | 版本、配置、开关、迁移批次和操作者 |

资源信号解释原因，业务和旅程信号判断影响。告警优先围绕症状和错误预算，资源阈值作为诊断或早期预警。

### 7.3 结构化日志

日志至少考虑：

- 时间和级别；
- 服务、实例和版本；
- trace/request/correlation 标识；
- 脱敏后的业务关联标识；
- 事件类型、阶段和结果；
- 错误分类和可重试性；
- 必要的依赖和耗时信息。

禁止记录密钥、token、支付凭据、完整请求响应、完整业务对象和未经脱敏的个人信息。堆栈只应在受控工程日志中记录，不向最终用户返回。

### 7.4 指标设计

每个指标应明确：

- 业务含义；
- 类型和单位；
- 标签及其基数边界；
- 聚合方式；
- 数据延迟；
- 负责人；
- 对应的运行手册。

不要把用户 ID、订单号等高基数字段直接作为时序指标标签。

### 7.5 链路和关联

链路追踪应覆盖同步和异步边界。异步场景需要传播关联标识和业务事件标识，并保留重试次数、原始事件和当前处理阶段。采样策略应保证错误、长尾和高风险旅程有足够证据。

### 7.6 告警质量

一个可行动告警至少包含：

- 受影响旅程和范围；
- 当前值、目标值和持续时间；
- 关联变更；
- 初步诊断入口；
- 运行手册；
- 严重度和响应责任；
- 抑制、聚合和恢复条件。

告警严重度应按用户影响、数据风险和时间紧迫性确定，不按某个 CPU 阈值机械分级。

### 7.7 用户、运营、工程和审计看到不同信息

| 对象 | 应看到什么 |
|---|---|
| 最终用户 | 当前状态、结果、失败原因、系统是否重试、下一步动作 |
| 业务运营 | 范围、进度、失败明细、来源、差异和安全处理入口 |
| 工程人员 | 旅程、依赖、日志、指标、链路、版本和资源 |
| 审计人员 | 操作者、授权、审批、前后变化和时间线 |

信息透明不是把系统知道的一切公开给所有人。展示内容必须符合最小权限、隐私、安全和认知负担要求。

### 7.8 业务血缘和版本

对同步、发布和派生数据，应能够回答：

- 来源系统和来源版本；
- 处理批次、任务或事件；
- 目标系统和应用结果；
- 当前数据是否新鲜；
- 发生差异时以谁为准；
- 如何重放、回滚或修复。

血缘、版本和审计是业务可追溯性，不能替代运行指标；运行指标也不能代替单条业务事实追踪。

## 8. 事故响应与学习闭环

### 8.1 事故处理阶段

```text
发现
-> 确认业务影响
-> 分级和接管
-> 限制爆炸半径
-> 止血和恢复
-> 验证业务结果与数据
-> 持续沟通
-> 根因分析
-> 改进和复验
```

恢复业务优先于在事故现场完成根因分析，但不能通过隐瞒错误、吞掉异常或关闭必要校验制造“恢复”。

### 8.2 角色

| 角色 | 责任 |
|---|---|
| 事故指挥 | 统一优先级、授权和决策节奏 |
| 技术处置 | 诊断、止血、恢复和验证 |
| 业务代表 | 判断业务影响、降级和补偿边界 |
| 沟通负责人 | 对内外更新事实、影响和预计动作 |
| 记录员 | 保存时间线、证据、命令和决策 |

同一个小团队可以兼任角色，但责任不能消失。

### 8.3 事故分级

分级依据至少包括：

- 影响用户和业务范围；
- 核心旅程是否不可用；
- 是否涉及错误资金、库存、权限或数据泄露；
- 数据是否可能不可逆；
- 影响持续时间；
- 是否仍在扩大；
- 是否有安全降级方案。

响应时限应根据组织值班能力制定，不应把固定 P0/P1 分钟数写成普遍标准。

### 8.4 止血原则

优先选择可逆、范围明确、验证快速的动作：

- 关闭高风险功能开关；
- 停止继续产生错误数据；
- 缩小流量或租户范围；
- 切换只读或安全降级；
- 回滚最近变更；
- 隔离毒消息或异常批次；
- 暂停不可控的自动补偿和重试。

任何生产操作都应记录目标、范围、执行者、时间、预期、实际和恢复方式。

### 8.5 恢复验证

进程恢复和告警消失不等于业务恢复。必须检查：

- 关键旅程 SLI 是否恢复；
- 积压是否正在可控速度消化；
- 数据是否完整、唯一和作用域正确；
- 重试是否造成重复副作用；
- 降级状态是否正确退出；
- 用户和运营是否看到正确状态；
- 备份或切换后数据是否满足 RPO。

### 8.6 证据链和根因

根因结论至少包含：

```text
触发事件
-> 直接技术原因
-> 错误如何传播
-> 哪些防线缺失或失效
-> 为什么未提前发现
-> 为什么恢复耗时
-> 哪些组织或流程条件允许问题发生
```

“代码有 bug”“人员误操作”或“流量过大”通常只是起点，不是足够根因。

### 8.7 复盘改进项

高质量改进项应：

- 对应明确失败机制；
- 有负责人和期限；
- 有验证方式；
- 能降低发生概率、爆炸半径、检测时间或恢复时间；
- 区分立即止损、近期修复和结构性治理；
- 横向检查同类系统；
- 完成后复验，而不是只关闭工单。

## 9. 容灾、备份、恢复和回切

### 9.1 从业务能力定义灾备

灾备设计从业务影响分析开始：

- 哪些能力必须优先恢复；
- 最长中断时间；
- 最大可接受数据丢失；
- 恢复时的最低容量；
- 外部依赖是否也具备灾备；
- 降级期间哪些操作必须禁止；
- 恢复后怎样核对业务数据。

### 9.2 容灾级别是条件化选择

| 方式 | 特征 | 主要风险 |
|---|---|---|
| 本地备份 | 成本低，恢复较慢 | 同故障域损坏、恢复时间长 |
| 异地备份 | 抵御站点级数据损失 | 数据传输和恢复演练不足 |
| 冷备/温备 | 备用资源部分预置 | 启动、配置和容量不确定 |
| 主备 | 可较快切换 | 复制延迟、脑裂、回切风险 |
| 多活 | 低 RTO 潜力 | 一致性、流量路由和运营复杂度高 |

不能仅按名词推断 RTO/RPO，必须以演练证据为准。

### 9.3 备份策略

备份设计至少包含：

- 备份对象和数据分类；
- 全量、增量和日志策略；
- 加密、访问和保留；
- 跨故障域存储；
- 备份完整性校验；
- 定期恢复到隔离环境；
- 恢复后的业务不变量和数据质量验证；
- 删除和合规要求；
- 负责人和最近一次成功演练证据。

“备份任务成功”不证明备份可恢复。

### 9.4 切换和回切

切换方案必须明确：

- 触发者和授权人；
- 如何阻止双主写入；
- DNS、流量和连接如何收敛；
- 数据复制进度和 RPO 判断；
- 备用环境容量；
- 外部依赖和密钥是否可用；
- 切换后的业务验证；
- 原环境恢复后的数据合并和回切步骤。

回切通常比切换更容易被忽略，也可能再次造成中断或数据冲突，必须纳入演练。

### 9.5 恢复顺序

恢复应按依赖和业务优先级排序，例如：

```text
身份与基础数据
-> 核心写入和交易事实
-> 查询和运营能力
-> 异步任务和积压处理
-> 报表、推荐和非核心能力
```

真实顺序由具体系统依赖决定，不能机械套用。

## 10. 稳定性验证与演练

### 10.1 验证不是一次压测

| 验证类型 | 目标 |
|---|---|
| 基准测试 | 建立单请求和单组件性能基线 |
| 负载测试 | 验证目标工作负载下的 SLO 和资源水位 |
| 压力测试 | 找到容量拐点、失败方式和保护机制 |
| 突发测试 | 验证快速流量变化和弹性 |
| 浸泡测试 | 发现泄漏、累积误差和长期积压 |
| 容量恢复测试 | 验证故障后积压能否在目标时间内消化 |
| 并发与重复测试 | 验证幂等、不变量和状态条件更新 |
| 故障注入 | 验证超时、隔离、降级和恢复 |
| 灾备演练 | 验证 RTO、RPO、切换和回切 |
| 备份恢复 | 验证备份可读取且业务数据正确 |
| 运营演练 | 验证告警、运行手册和人工处理能力 |

### 10.2 工作负载真实性

测试模型至少覆盖：

- 峰值与突发；
- 读写比例；
- 热点租户、门店和商品；
- 大对象和长尾请求；
- 批处理、重试和消息重放；
- 离线恢复后的集中补传；
- 依赖延迟和部分错误；
- 接近真实的数据分布和索引选择性。

平均均匀流量很容易掩盖真实热点和资源竞争。

### 10.3 故障注入前提

生产故障注入必须满足：

- 有明确授权和范围；
- 稳态假设和通过标准明确；
- 爆炸半径受控；
- 停止条件和立即恢复动作明确；
- 监控和值守到位；
- 不触碰不可逆资金、库存和外部副作用；
- 数据和日志符合安全要求；
- 先在低风险环境验证工具本身。

### 10.4 场景矩阵

| 场景 | 预期保护 | 业务通过标准 |
|---|---|---|
| 下游延迟升高 | deadline、隔离、限流 | 核心旅程仍在目标范围或明确降级 |
| 消息重复 | 幂等、唯一约束 | 只产生一个业务结果 |
| 消息乱序 | 版本和状态守卫 | 旧状态不覆盖新状态 |
| 单实例故障 | 副本和负载摘除 | 用户影响在 SLO 内 |
| 数据库主节点故障 | 切换和写保护 | 无双主写，RTO/RPO 达标 |
| 大租户突发 | 作用域限流和隔离 | 其他租户关键旅程不受不可接受影响 |
| 错误配置 | 校验、灰度和回滚 | 影响受限且能快速恢复 |
| 长期离线恢复 | 有界补传和背压 | 不重复处理，积压按目标消化 |

### 10.5 演练证据


## 11. 贯穿案例：总部价格发布到门店的稳定性设计

> 本案例使用演示假设，不代表任何现有项目事实。实际设计必须用项目证据替换规模和目标。

### 11.1 关键用户旅程

```text
总部定价员创建价格版本
-> 审批人批准范围和生效时间
-> 发布服务形成不可变版本
-> 目标门店接收并应用
-> 云端汇聚结果并对账
-> 用户看到真实生效状态
```

业务成功定义：经授权的正确价格版本在正确门店和生效时间被应用，重复、乱序、离线和部分失败不会产生错误价格，并且未生效项可以被发现和恢复。

### 11.2 RCA：从“让消息可靠”到“让业务义务可恢复”

常规分析会把问题定义为“怎样提高消息投递成功率”。创造性稳定性分析先寻找悖论：

- 消息成功到达，不代表门店价格已经应用；
- 门店离线时，继续快速重试不会提高履约能力；
- 云端恢复不代表离线期间的积压已经收敛；
- 多副本发布服务无法解决错误版本、错误门店范围和本地权威冲突；
- 只有技术告警时，业务人员仍无法判断哪些门店正在使用错误价格。

竞争解释：

| 假设 | 预测 |
|---|---|
| H1 投递实现不可靠 | 修复消息丢失后，大部分业务差异应消失 |
| H2 成功语义错误 | 即使零消息丢失，仍存在“收到但未应用”和“应用后未核对” |
| H3 离线未被建模为业务状态 | 系统会对离线门店无限重试或过早判失败，恢复后产生补传洪峰 |
| H4 缺少可恢复的履约义务 | 无法回答谁尚未完成、何时逾期、使用什么替代路径和怎样证明恢复 |

创造性重构后的稳定性问题是：

> 当目标门店、网络或发布链路处于不同故障条件时，系统如何持续保存价格发布义务，保护最后有效价格，选择安全履约路径，并在恢复后用版本和实际结果证明业务已经收敛？

由此产生的业务级进化候选包括：

- 把“离线”建模为待履约状态，而不是简单失败；
- 将最后经过验证的有效价格及其适用边界显式化；
- 门店通过版本水位主动补齐，形成消息通知之外的替代履约路径；
- 将回执、逾期、对账和人工例外处理提炼为运营能力；
- 为总部强制价格和门店自治价格定义冲突、升级与审计政策；
- 用逐门店业务义务的完成比例衡量可靠性，而不是仅看消息中间件成功率。

最小反例：如果所有门店始终在线、业务只承诺尽力通知且本地价格无任何客户或合规后果，则完整履约模型可能成本过高。真实设计必须用离线比例、错价损失、运营责任和恢复要求验证。

### 11.3 正确性底线

- 不得跨商户或门店作用域发布；
- 旧版本不得覆盖新版本；
- 同一发布项重复处理只产生一个结果；
- 未审批版本不得生效；
- 总体完成状态必须由门店明细状态推导；
- 回滚通过新版本表达，历史审批和生效事实不可静默覆盖。

这些底线不使用错误预算。

### 11.4 演示 SLO

| 旅程 | SLI | 演示目标 |
|---|---|---|
| 提交发布 | 合法发布请求在 2 秒内被可靠受理的比例 | 30 天 >= 99.9% |
| 在线门店生效 | 计划时间后 5 分钟内版本正确的在线目标项比例 | 30 天 >= 99.5% |
| 状态新鲜度 | 门店结果产生后 1 分钟内云端可见的比例 | 30 天 >= 99.0% |
| 故障恢复 | 演练中发布链路恢复时间 | RTO <= 30 分钟 |
| 数据恢复 | 已确认发布版本允许的数据损失 | RPO = 0；实现需通过持久化和恢复验证证明 |

目标是否合理，需要由业务损失、门店离线特征、成本和实际基线共同决定。

### 11.5 依赖和故障域

```text
总部页面
-> 身份与权限
-> 价格/审批服务
-> 发布数据库 + Outbox
-> 消息或版本通知
-> 门店接收端
-> 门店业务库
-> 结果回报
-> 云端状态汇聚和对账
```

故障域包括：总部发布批次、消息分区、单门店、区域网络、云端数据库、门店本地数据库、版本配置和运营重试操作。

### 11.6 失败场景和机制

| 失败场景 | 风险 | 设计机制 |
|---|---|---|
| 发布事务成功但事件未发出 | 门店永远收不到 | Outbox、积压监控和完整性对账 |
| 同一事件重复五次 | 重复副作用 | 门店作用域幂等键和原结果重放 |
| 版本 11 先于版本 10 到达 | 旧价覆盖新价 | 单调版本和条件更新 |
| 门店离线七天 | 长期未生效、恢复洪峰 | 版本水位拉取、有界补传、背压和新鲜度状态 |
| 一条坏数据持续失败 | 阻塞分区 | 有界重试、死信隔离、人工修复后重放 |
| 云端结果回报丢失 | 总部误判未生效 | 门店版本水位和周期对账 |
| 运营人员全量重试 | 形成流量洪峰 | 范围预览、限流、审批和分批重试 |
| 错误门店范围 | 跨作用域错价 | 审批时范围摘要、契约作用域校验和审计 |

### 11.7 Deadline、重试和背压

- 总部提交只等待“可靠受理”，不等待所有门店最终生效；
- 门店应用结果通过任务状态查询和结果回报观察；
- 投递重试使用指数退避、随机抖动、最大次数和整体重试预算；
- 业务拒绝、作用域错误和旧版本不自动重试；
- 门店恢复时按水位分批拉取，避免所有积压同时冲击云端和本地数据库；
- 已过业务有效期的中间版本按规则跳过或合并，但必须保留审计和最终版本正确性。

### 11.8 幂等和原子性

门店在一个本地事务中：

1. 校验门店作用域；
2. 声明 `store_id + publication_item_id` 唯一处理记录；
3. 校验请求摘要和版本；
4. 条件写入价格；
5. 写入应用结果和审计；
6. 提交后异步回报云端。

回报失败不回滚已经正确生效的本地价格，而由重试和对账补齐状态。

### 11.9 可观测和业务透明度

业务面板展示：

- 目标项总数；
- 待投递、已投递、已接收、已应用、拒绝、待重试、长期离线；
- 当前版本与目标版本；
- 计划和实际生效时间；
- 失败分类及安全操作；
- 发布范围、审批人和回滚版本。

工程信号包括：

- 发布旅程 SLI 和预算燃烧；
- Outbox 年龄、消息积压和消费延迟；
- 幂等命中、版本冲突和作用域拒绝；
- 门店在线率和补传吞吐；
- 对账差异数量和最长未收敛时间；
- 关联版本、配置和发布批次。

### 11.10 告警和运行手册

示例告警：

```text
现象：计划生效 15 分钟后，在线目标门店仍有 3% 未应用
影响：价格发布旅程新鲜度 SLO 快速燃烧
范围：发布版本 P-XXX，涉及若干门店，明细受权限控制
首查：消息积压、门店在线率、版本拒绝、最近发布和配置
自动动作：停止扩大当前发布批次，不自动回滚价格
人工动作：确认数据正确性后选择分批重试、暂停或发布回滚版本
恢复验证：门店版本对账一致，积压消化，SLI 恢复
```

### 11.11 验证矩阵

| 目标 | 场景 | 通过标准 |
|---|---|---|
| 幂等 | 同一项并发投递 20 次并在处理中重启 | 只产生一个生效结果，所有重放返回一致结论 |
| 版本单调 | 11、10、12 乱序到达 | 最终为 12，10 不覆盖 11 |
| 作用域安全 | 构造错误商户/门店组合 | 原子拒绝，无数据变化且审计安全 |
| 部分失败 | 10% 门店离线 | 在线门店继续，离线项状态明确并可补传 |
| 过载保护 | 大量门店同时恢复 | 队列有界，核心业务不被拖垮，积压按目标消化 |
| 对账恢复 | 丢弃部分结果回报 | 周期对账发现并修正云端状态 |
| 灾难恢复 | 云端主库故障 | RTO/RPO 达标，无双主写和版本倒退 |
| 用户透明 | 混合成功、失败和离线 | 页面不把“已发送”显示成“已生效” |

## 12. 稳定性设计执行流程

### 12.1 R0-R8 总览

| 阶段 | 核心问题 | 主要产物 | 退出条件 |
|---|---|---|---|
| R0 准入 | 业务边界和正确性是否明确？ | 任务卡、不变量、责任人 | 无关键语义缺口 |
| R1 旅程与创造性重构 | 哪些业务结果最关键，故障是否暴露了错误承诺或缺失状态？ | 关键用户旅程、RCA0-RCA2 | 成功、失败和竞争解释可区分 |
| R2 目标 | 稳定性承诺是什么？ | SLI、SLO、RTO、RPO | 可计算且责任明确 |
| R3 失败模型与共享命运 | 系统怎样失败和传播，哪些表面独立项实际共同失效？ | 依赖图、故障域、FM 卡、RCA3 | 高风险及竞争故障解释已覆盖 |
| R4 保护与替代履约 | 如何预防、隔离、降级并通过其他路径完成业务？ | 机制组合、数据收敛、RCA4-RCA5 | 不变量与爆炸半径受控；替代路径已评估 |
| R5 观察与运行 | 怎样发现和处置？ | 信号、告警、运行手册 | 告警可行动 |
| R6 变更 | 怎样安全发布和回退？ | 风险分级、灰度和恢复 | 停止条件可执行 |
| R7 验证 | 怎样证明机制有效？ | 测试、演练和证据 | 目标场景通过 |
| R8 学习与业务进化 | 怎样从运行和事故提炼可复用能力并推动业务进化？ | 预算策略、复盘、RCA6-RCA7、进化候选 | RCG1-RCG6 通过；改进闭环运行 |

### 12.4 评审门禁

- [ ] 关键旅程、成功结果和不变量明确；
- [ ] 权限、租户、资金、库存和数据底线没有红线缺口。

#### RG1A：创造性稳定性分析

- [ ] 已执行总纲 CA0-CA8 和本文 RCA0-RCA7，未从组件故障直接跳到模式清单；

- [ ] 至少评估一种业务级替代履约路径，不适用时已有理由；
- [ ] 已判断稳定性治理是否应提炼为用户或运营可使用的业务能力；
- [ ] RCG1-RCG6 全部通过，核心抽象变化已升级处理。

#### RG2：目标可测量

- [ ] SLI 的有效和合格口径明确；
- [ ] SLO、窗口、错误预算、RTO/RPO 和责任人明确。

#### RG3：故障可控

- [ ] 关键依赖、故障域、相关性故障和爆炸半径已建模；
- [ ] 结果未知、部分成功、灰色故障和静默错误已有处理。

#### RG4：数据可收敛

- [ ] 幂等、并发、乱序、消息、补偿和对账形成闭环；
- [ ] 不依赖吞异常或人工改库维持表面成功。

#### RG5：运行可处置

- [ ] 告警指向用户旅程和可执行运行手册；
- [ ] 自动和人工恢复均有范围、权限、审计和验证。

#### RG6：变更可控

- [ ] 灰度、护栏、停止条件、回滚或前向修复可执行；
- [ ] 新旧版本和数据在兼容窗口内能够共同运行。

#### RG7：证据充分

- [ ] 关键机制经过目标负载、故障和恢复验证；
- [ ] 结论、剩余风险和复验条件有记录。

## 13. 常见反模式

### 13.1 进程存活等于业务可用

探活成功可能同时存在错误价格、重复入账、数据延迟和部分用户失败。应围绕关键旅程定义 SLI。

### 13.2 固定“99.9%”但没有口径

没有有效事件、合格事件、窗口、数据源和违反策略的 99.9% 无法执行和验收。

### 13.3 所有错误都重试

会放大过载、重复副作用和业务拒绝。只对可恢复瞬时错误，在幂等和 deadline 保护下重试。

### 13.4 依赖分布式锁保证幂等

锁过期、暂停、选主变化和网络分区会破坏互斥假设。应以业务键、唯一约束、状态条件更新和结果记录作为正确性基础。

### 13.5 Catch 后返回 null

把依赖故障伪装成“数据不存在”，上层无法正确降级、告警和恢复。应区分业务空结果、可重试依赖错误和未知系统错误。

### 13.6 无限队列吸收流量

积压只是在延后失败，并可能使任务过期、内存耗尽和恢复洪峰更严重。队列必须有界，并有背压、过期和清理策略。

### 13.7 多副本等于容灾

共享数据库、网络、证书、配置和控制面会形成共同故障。需要故障域独立、切换控制和演练证据。

### 13.8 最终一致等于无需负责

没有收敛时限、检测、对账、修复和人工责任的最终一致，是长期不一致。

### 13.9 告警越多越安全

不可行动的告警会造成疲劳并延长真正事故的响应。告警应围绕用户影响、错误预算和明确处置动作。

### 13.10 备份成功等于可恢复

只有实际恢复并验证业务不变量、完整性和 RTO/RPO，才能证明备份有效。

### 13.11 回滚版本解决所有变更

新数据、外部副作用和不兼容结构可能无法回滚。必须设计数据兼容、业务补偿或前向修复。

### 13.12 把内部细节全部展示给用户

透明度应可行动、分角色并受权限保护。内部堆栈、敏感数据和安全策略不应暴露。

### 15.1 业务和目标

- [ ] 关键用户旅程及成功结果明确；

- [ ] 已从业务承诺、结果未知、合法中间态、替代履约和恢复证明重新定义问题；

- [ ] 已扫描 R-E0 至 R-E6，简单修复是证据收敛结果而非默认答案；
- [ ] 已识别可产品化的回执、对账、恢复、例外处理或自治能力；

### 15.2 故障和保护

- [ ] 依赖图、故障域、爆炸半径和相关性故障已分析；
- [ ] 超时、重试、限流、背压、隔离和降级组合合理；
- [ ] 冗余跨越关键故障域，并有防脑裂和切换验证；

- [ ] 未覆盖风险、负责人和复验日期明确。

## 16. 最终原则

```text
稳定不是永不失败。

稳定是：
业务结果有清晰承诺，
正确性底线不会被错误预算稀释，
故障发生时影响被限制，
错误不会通过重试和异步链路无限放大，
数据最终能够被验证地收敛，
用户和运营人员看到真实且可行动的状态，
系统能够在目标时间和数据损失范围内恢复，
AI 能从故障中发现隐藏的业务承诺、共享命运和新的履约方式，而不只套用稳定性模式，
每次变更和事故都会产生下一轮改进证据。
```
