# 重建 vs 优化决策分析报告

## 一、核心判断

**结论：不是"重建"，也不是简单的"优化"，而是"补全翻译层"**

### 现有理论的现状

你的`00-遗留系统分析方法论框架.md`（V2.8）实际上已经拥有**扎实的理论根基**：

| 理论维度 | 现状评估 | 评分 |
|---------|---------|------|
| **世界观/哲学层** | ✅ 完整：7要素提取法、证据分层(L1-L5)、置信度体系 | 85/100 |
| **认知框架层** | ✅ 完整：事实→维度→规则三元模型、组合效应分析 | 80/100 |
| **方法论层** | ✅ 完整：分析→抽象→升华三层递进、可扩展性/适应性评价 | 85/100 |
| **实践指导层** | ❌ 薄弱：缺少"操作分解"、"判定树"、"批次协议" | 30/100 |
| **执行控制层** | ❌ 薄弱：门禁只管形式不管内容、缺少实质验收标准 | 25/100 |

### 问题的本质

**现有理论像一座"理论大厦"，但缺少"楼梯"和"电梯"——人知道要上去，但不知道怎么爬楼梯。**

```
理论层（丰富）
    ↓ [缺失：如何从理论推导出操作步骤]
    ↓ [缺失：如何在具体场景中判定应用哪个理论]
    ↓ [缺失：如何控制执行质量和进度]
执行层（空洞）
    → 产出骨架占位符（3行表格）
```

## 二、现有理论的优势（必须保留）

### 2.1 世界观层：7要素提取法 ✅

```
7要素框架：
├── 主体（Who）- 业务参与者
├── 目标（What）- 业务意图
├── 规则（Rules）- 业务约束
├── 协作（Collaboration）- 角色配合
├── 时序（Timing）- 时间维度
├── 资源（Resource）- 业务对象
└── 信息（Information）- 数据流转
```

**优势：**
- 互斥边界清晰（每个事实只能归入1个要素）
- 依赖关系明确（主体→目标→规则→协作→时序→资源→信息）
- 可证伪条件完整

**保留理由：** 这是分析的业务语言系统，是所有产出的"词汇表"，必须保留。

---

### 2.2 认知框架层：证据分层体系 ✅

```
证据层级：
├── L1 代码事实（文件:行号，可定位）
├── L2 代码推断（完整调用链，可追溯）
├── L3 业务语义（代码+文档/访谈，至少1项）
├── L4 业务推断（明确假设+反例+待确认）
└── L5 未知项（记录已尝试的验证方式）
```

**优势：**
- 每条结论必须关联证据层级
- "高置信度"不能只表示代码存在
- 防止虚构和臆测

**保留理由：** 这是分析的质量保障体系，确保结论可验证。

---

### 2.3 方法论层：三层递进结构 ✅

```
第一层：分析（Analysis）
├── 1.1 业务理解 → 7要素提取
├── 1.2 业务抽象 → 模式识别、变体抽象
└── 1.3 业务升华 → 跨行业通用模型

第二层：评价（Evaluation）
├── 2.1 可扩展性评价
└── 2.2 适应性评价

第三层：设计（Design）
├── 3.1 架构设计
└── 3.2 改造策略
```

**优势：**
- 分析→抽象→升华的递进关系清晰
- 评价维度明确（可扩展性/适应性）
- 设计层直接指导开发

**保留理由：** 这是方法论的"骨架"，是不可动摇的核心结构。

---

### 2.4 理论融合层：DDD + Event Storming + 六边形 ✅

```
融合架构：
├── DDD战略设计 → 限界上下文、聚合、领域事件
├── Event Storming → 业务流程可视化
├── CQRS → 读写分离评价维度
├── 六边形架构 → 架构设计模板
└── STRangler Fig → 改造策略
```

**保留理由：** 这些都是业界验证过的方法，整合方式合理。

## 三、现有理论的缺口（必须补全）

### 3.1 操作分解层缺失

**问题：** 理论说"用7要素提取法分析业务"，但没说"具体怎么提取"。

**缺失内容：**

| 理论要求 | 缺失的操作步骤 |
|---------|--------------|
| "识别业务主体" | 1. 扫描哪些代码入口？2. 如何区分系统角色和外部角色？3. 如何避免遗漏？ |
| "提取业务规则" | 1. 从代码哪里提取？2. 如何区分业务规则和技术实现？3. 如何处理隐式规则？ |
| "建立实体识别卡" | 1. DAO类如何映射到业务对象？2. 聚合根如何判定？3. 关系如何命名？ |

---

### 3.2 判定树层缺失

**问题：** 理论说"仅UI维护入口适用某清单"，但没说"如何判定UI维护入口"。

**缺失内容：**

| 判定场景 | 缺失的判定规则 |
|---------|---------------|
| "这是实体还是值对象？" | 判定标准 + 常见误判示例 |
| "这是聚合根吗？" | 判定决策树 |
| "这是UI配置关系吗？" | 入口类型识别流程 |
| "这是结构关系还是轨迹关系？" | 关系类型判定流程 |

---

### 3.3 批次协议层缺失

**问题：** 理论说"增量式执行"，但没说"批次间如何保持一致性"。

**缺失内容：**

| 问题 | 缺失的协议 |
|-----|-----------|
| ID分配 | 批次1用了REL-001，批次2如何知道？ |
| 关系传递 | 批次1分析A→B，批次2分析B→C，如何合并A→B→C？ |
| 概念复用 | 批次1定义了"Order"，批次2如何知道？ |
| 证据索引 | 批次1的证据E-001，批次2从E-002还是E-001继续？ |

---

### 3.4 门禁实质化缺失

**问题：** G1门禁说"至少1行实质内容"，但`✅ 一致`三个字就能通过。

**缺失内容：**

| 门禁项 | 当前标准 | 缺失的实质要求 |
|--------|---------|--------------|
| 实质内容 | "至少1行非'待补充'" | 必须包含证据ID |
| 一致性结论 | "✅ 一致" | 必须说明一致的原因和证据 |
| 关系分析 | "REL-001: A↔B" | 必须说明业务语义 |

## 六、总结

| 选项 | 选择 | 理由 |
|------|------|------|
| 重建整套理论 | ❌ 否 | 现有理论基础扎实（世界观/认知框架/方法论三层完整） |
