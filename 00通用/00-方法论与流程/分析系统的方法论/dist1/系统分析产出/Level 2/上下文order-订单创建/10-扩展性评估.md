# 10-扩展性评估

## 1. 当前扩展性评估

| 维度 | 当前评分 | 说明 |
|------|---------|------|
| 新增支付方式 | ★★ | 需要修改OrderMasterDO的pay()方法 |
| 新增优惠类型 | ★★ | 需要修改apportionAmount()分摊逻辑 |
| 新增订单类型 | ★★★ | 通过bizType枚举扩展 |
| 新增第三方对接 | ★★ | 需要新增Service和Handler |

## 2. 扩展性约束

### 2.1 硬约束
| 约束 | 影响 |
|------|------|
| billNo唯一性 | 不能修改生成算法 |
| OrderStatusEnum | 状态流转固定，修改需谨慎 |
| PayMutexShare锁 | 保证并发安全，修改需考虑兼容性 |

### 2.2 软约束
| 约束 | 影响 |
|------|------|
| OrderMasterDO聚合边界 | 当前包含所有订单相关对象 |
| 优惠分摊算法 | 按金额比例，可扩展为策略模式 |

## 3. 扩展建议

### 3.1 短期（降低耦合）
- 提取支付策略接口，支持更多支付方式
- 提取优惠计算接口，支持更多优惠类型

### 3.2 长期（架构升级）
- 引入领域事件，实现支付/优惠的插件化
- 引入规则引擎，配置化管理业务规则

## 4. 重构风险

| 风险点 | 影响程度 | 缓解措施 |
|--------|---------|----------|
| 聚合根过大 | 高 | 拆分非核心值对象到独立服务 |
| 支付逻辑分散 | 中 | 抽取支付策略类 |
| 优惠规则耦合 | 高 | 引入规则引擎 |
