# 产物空洞根因分析报告

## 一、问题现状

### 1.1 典型空洞产物示例

**实际产出（Level 2/上下文base-员工/03-业务对象建模.md）：**
```markdown
# 03-业务对象建模
## 员工对象
| 属性 | 说明 |
| employeeId | 员工ID |
| employeeNo | 工号 |
| role | 角色 |
```

**SOP要求应包含的内容（10大维度）：**
1. 类型判定（实体/值对象/聚合根/成员）
2. 完整属性/字段（类型+约束+业务含义）
3. 方法/操作（业务含义）
4. 生命周期
5. 状态机
6. 不变式/约束
7. 领域事件
8. 关系/关联
9. 权限/可见性
10. 并发控制

**实际覆盖率：10%（仅有简化版属性列表）**

---

## 二、根本原因（核心3点）

### 2.1 理论过载 vs 执行真空

**问题：** SOP-00有1790行理论，但缺少"最小可执行单元"

**具体表现：**
- ✅ 有200+个模板字段定义
- ❌ 没有"哪些字段必填/可选/条件适用"的判定规则
- ❌ 没有"从空白到填满一个DA3"的分步操作手册
- ❌ 没有"DAO类如何转换为业务对象"的映射规则

**AI执行困境：**
```
AI看到模板 → 包含12个字段 → 不知道哪些必填 
→ 保守策略：只填必填项 
→ 但不知道哪些是必填项 
→ 最终只输出3行表格避免出错
```

---

### 2.2 模板字段未分级

**问题：** 所有字段平铺，未区分必填/可选/条件

**DA3关系契约框的12个字段：**
```markdown
1. 关系定义（类型/方向/路径）
2. 字段连接
3. 建立时机
4. 约束条件
5. 使用方式
6. 为什么经过中间对象 ← 唯一标注"仅间接关系必填"
7. 修改影响
8. 异常场景
9. 级联行为
10. 代码位置
11. 证据
12. (其他扩展字段)
```

**AI无法判断：**
- "约束条件"是所有关系都要填吗？
- "异常场景"必须3个吗？
- "级联行为"哪些关系适用？

**导致：** AI只能"战略性放弃"，产出最简内容

---

### 2.3 门禁检查与内容质量脱节

**遗留系统SOP V3.14的G1门禁：**
```markdown
检查项：Level 1文件完整性
通过标准：每个业务域同时存在01/02/03三个文件
实质内容要求：至少1行非"待补充"或"-"的内容
```

**实际产出：**
```markdown
| 上下文 | 状态定义 | 一致性 |
| order-订单支付 | 支付完成触发状态变更 | ✅ 一致 |
```

**问题：**
- ✅ 文件存在
- ✅ 有1行内容
- ✅ 不是"-"或"待补充"
- ❌ 但"✅ 一致"三个字没有证据、分析或推理过程

**门禁只检查形式，不检查质量**

---

## 三、核心改进建议（可立即落地）

### 3.1 引入"三级模板"机制

**Level 1 最小必填（4字段）：**
```markdown
| REL-ID | 关系名称 | 两端对象 | 关系类型 | 证据 |
| REL-001 | 订单包含明细 | Order-OrderDetail | 结构:1:N | E-SRC-001 |
```

**Level 2 标准模板（+4字段）：**
```markdown
+ 基数 | 建立时机 | 业务语义 | 代码位置
```

**Level 3 完整模板（+4字段）：**
```markdown
+ 为什么经过中间对象 | 异常场景 | 级联行为 | 变更影响
```

**执行规则：**
1. AI必须先完成Level 1（所有关系）
2. 再选择性填充Level 2（重要关系）
3. 最后只对间接关系填充Level 3

**效果：** 确保至少有"最小有效内容"

---

### 3.2 强化"实质内容"标准

**当前问题：** `✅ 一致` 三个字可以通过门禁

**改进方案：**

**不合格示例：**
```markdown
❌ | order-订单支付 | order-订单退款 | ✅ 一致 |
```

**合格示例：**
```markdown
✅ | order-订单支付 | order-订单退款 | 一致：两者共享OrderMasterDO聚合根(E-SRC-012)，状态枚举定义在OrderStatus，支付后状态=20(E-SRC-015)，退款后状态=30(E-SRC-018) |
```

**验收标准：**
1. 每个结论必须引用≥1个证据ID（E-SRC-XXX格式）
2. 不一致结论必须说明冲突点
3. 未知项必须说明验证计划

**脚本检查（新增退出码6）：**
- 扫描一致性矩阵的每行
- 检查是否包含`E-[A-Z]{3}-\d{3}`格式的证据ID
- 无证据行数>50% → 退出码6（内容不足）

---

### 3.3 补充"字段适用性判定树"

**当前问题：** "仅UI维护入口适用"，但未定义如何判定

**改进方案：**

```markdown
## UI配置关系适用性判定流程

1. 关系实例是否由用户在UI中手动建立/修改？
   - 是 → 继续第2步
   - 否 → 跳过本清单，标注"非UI入口：{类型}"

2. 是否存在非UI入口（API/导入/消息）？
   - 否 → 适用完整清单（7项）
   - 是 → 混合入口，只填UI相关4项：
         入口路径/数据结构/写入链路/约束校验
```

**效果：** AI能快速判定，避免"无法判定→跳过整个清单"

## 四、SOP参考价值评估

### 4.1 SOP-00（业务系统分析总览）

**高价值（建议保留）：**

- §0.8 批次管理（无ID分配/依赖解析协议） — **执行价值25分**

**总体：理论价值高（70分），执行指导价值低（30分）**

## 五、结论

### 核心问题
产物空洞的根本原因是**"理论与执行的翻译层缺失"**：

1. **理论层（SOP-00）**：完整的认知框架、证据协议、门禁体系
2. **❌ 缺失的翻译层**：字段分级、判定树、操作分解、批次协议
3. **执行层（AI生成）**：无法从理论推导出操作步骤 → 产出骨架占位符

### 立即可行的改进
1. **三级模板**：Level 1最小必填 → Level 2标准 → Level 3完整
2. **实质内容标准**：每个结论必须引用证据ID，脚本自动检查
3. **判定树**：为"条件适用"字段补充判定流程图

### SOP参考价值
- ✅ **保留**：理论框架、证据协议、门禁体系、骨架机制
- ❌ **重构**：DA模板分级、AI提示词操作化、批次协议补全
