## TL;DR

**一句话**：在明确版本/环境基线的前提下，枚举全入口、追踪关键业务切片、分析一致性与韧性，输出可复核的后端整体认知。

**核心输入**：分析任务书、仓库地址、部署清单、配置中心、环境权限

**核心输出**：系统地图、入口/出口清单、关键业务切片追踪矩阵、事务/幂等/补偿分析、配置/开关清单

**关键约束**：不得只枚举 Controller；不得把"未找到"写成"不存在"；多实现必须先建立 IMPL-* 谱系

## 目的

对后端系统建立可复核的整体认知：在明确版本、环境和部署基线的前提下，识别技术栈、模块与服务边界、数据和外部依赖、所有权、真实入口、关键业务切片、横切控制及运行恢复能力，为后续业务、接口、数据与综合评估提供证据。

本 SOP 受 `SOP-00-业务系统分析SOP总览.md` v3.7、`研发方法/业务系统分析-认知真源.md` v2.0、文档 20 和 `10-方法论-复杂既有系统拆解与架构分析.md` 约束。若简化检查项与上位约束冲突，以 L1 认知理论和 SOP-00 为准。

## 适用范围与原则

适用于单体、模块化单体、微服务和事件驱动后端，包括 Java、Python、Go、Node.js 等技术栈。执行深度由分析任务书、业务风险和证据缺口决定，不要求平均阅读全部代码。

强制原则：

1. **先基线后结论**：未对齐代码、制品、配置、数据库和部署版本，不输出确定性现状结论。
2. **入口不等于 Controller**：HTTP/RPC、MQ、任务、脚本、监听器、批处理、运维命令和数据库触发机制均可能改变业务状态。
3. **业务切片贯穿**：模块清单不能替代端到端切片；关键切片必须连接入口、规则、数据、副作用、故障和恢复。
4. **静态与运行互证**：源码说明“可能如何运行”，运行和部署证据说明特定环境“实际如何运行”。
5. **正常与失败并重**：必须覆盖重复、并发、超时、部分失败、补偿、对账和人工介入。
6. **现状与评价分离**：先记录事实，再按业务影响和质量属性场景评价；不得机械以类长、方法长、覆盖率或模块数量判优劣。
7. **未知显式化**：未找到不等于不存在；隐藏入口、隐式调用方和历史契约无法确认时，登记未知项并降低结论确定性。
8. **多实现先分谱系**：同一能力出现多个入口、版本、开关分支、任务、脚本或历史模块时，分别建立 `IMPL-*` 和证据链；未经 SOP-10 语义对齐与冲突裁决，不得按类名相似或“最新实现”直接合并。


### 1.2 分析动作

- 读取 Maven/Gradle、requirements/pyproject、go.mod、package/lock 等构建描述，导出解析后的依赖树。
- 识别父 BOM、插件、私服、镜像基础层、原生库、驱动和运行时注入组件；确认同包多版本、排除规则和依赖冲突。
- 检查构建是否可复现：固定版本、锁文件、制品来源、构建参数、生成代码、测试跳过条件和环境依赖。
- 使用获批准的漏洞与许可证扫描结果；确认漏洞是否进入运行制品、是否可达、暴露面和补丁兼容性。
- EOL 或存在新版本只是风险信号，不直接推出升级方案；升级建议必须说明业务影响、兼容契约、迁移验证和回滚。
- 安装依赖或执行构建前确认脚本副作用和网络访问范围，不向未经批准的服务上传代码、数据或凭据。

### 1.3 项目结构与代码质量

记录源码、测试、配置、迁移、脚本、部署清单及生成目录，识别按层/按业务聚合、跨层调用、循环依赖、共享库和插件扩展点。目录命名只能作为候选职责，必须用调用、数据和运行证据验证。

类/方法长度、圈复杂度、重复率、覆盖率、模块数等仅用于筛选候选点。风险判断应联合：业务关键性、变化/事故历史、影响半径、运行暴露、测试缺口、所有权和兼容成本。生成代码、声明式配置、算法与普通 CRUD 使用不同语境，不设通用“一刀切”阈值。

重点核对：

- 代码模块与实际部署单元是否一致，是否存在同包异版、共享进程或条件装配。

分层、DDD、模块化或微服务不是天然优劣标签。评价应回答：边界是否承载稳定业务职责，变更是否局部化，数据所有权是否清晰，能否独立测试/部署/回滚，故障能否隔离。Controller 直调 DAO、循环依赖或共享库等是调查信号，需结合真实影响后定性。

## 3. 全入口、出口与契约清单

### 3.1 入口枚举

不得只枚举 Controller。至少检查以下入口，并记录启用条件和部署环境：

| 入口类型 | 典型形态 | 重点检查 |
|---|---|---|
| HTTP/WebSocket | Controller、Route、Filter、Webhook | 网关路由、版本、认证、参数/错误契约、幂等 |
| RPC | Feign/gRPC/Dubbo/内部协议 provider | 服务发现、超时、调用方、兼容版本 |
| MQ/事件 | Consumer/Listener/订阅、死信回放 | Topic/Queue、Schema、消费组、顺序、重投、幂等 |
| 定时/批处理 | Cron、Scheduler、XXL-Job、Batch | 时区、错过策略、并发实例、补跑、租户遍历 |
| 文件/脚本 | CLI、Shell、SQL、迁移、导入导出 | 执行权限、参数、重复执行、审计、回滚 |
| 监听器/回调 | 启动、领域、数据库、配置、文件监听器 | 触发顺序、事务阶段、异常处理、隐藏副作用 |
| 管理/运维 | Actuator、Admin、JMX、内部修复接口 | 暴露面、授权、危险动作、审计 |
| 数据触发 | Trigger、存储过程、CDC/Canal、外部直写 | 隐式状态变化、顺序、重复和所有权 |

搜索注解或命名只能发现候选入口；还要结合框架注册、配置开关、部署清单、调度平台、MQ 控制台、网关路由和运行记录确认是否生效。

#### 3.1.1 定时任务/批处理分析规范

**适用范围**：Cron 定时任务、延迟任务、批处理作业、调度平台（XXL-Job/Elastic-Job）、补偿/对账任务、数据导入导出任务、离线计算任务。

**分析目的**：回答"这个定时任务/批处理解决了什么业务问题、它的调度规则是什么、失败后如何恢复、重复执行是否安全"，而非"有哪些定时任务"。定时任务和批处理是信息系统自动执行业务逻辑的重要入口，其调度规则、数据范围、失败处理直接反映业务对时效性、一致性、容错性的要求。

**分析维度**（每个核心定时任务/批处理必须回答）：

| # | 问题 | 说明 |
|---|------|------|
| ① | 任务解决的业务问题是什么？ | 这个任务解决什么业务需求？为什么要用定时/批处理而不是实时触发？ |
| ② | 调度规则与数据范围是什么？ | Cron 表达式、时区、错过策略、数据范围（全量/增量/租户遍历）、并发实例限制 |
| ③ | 幂等性与重复执行安全吗？ | 重复执行是否产生重复数据？是否支持补跑？补跑时如何处理已处理数据？ |
| ④ | 失败检测与恢复机制是什么？ | 失败如何检测？自动重试还是人工介入？重试次数和间隔？部分失败如何处理？ |
| ⑤ | 任务产物的消费者是谁？ | 任务产出被谁消费？下游任务是否依赖本任务的成功？任务间依赖关系是什么？ |

**分析模板**：

```text
## {任务名称} 定时任务/批处理分析

**业务问题**：解决什么业务需求
**为什么用定时/批处理**：实时触发不行吗？

**调度规则**：
- 调度表达式：0 0 3 * * ?（每天凌晨3点）
- 时区：Asia/Shanghai
- 错过策略：错过执行后立即补跑
- 数据范围：全量租户遍历
- 并发实例：单实例（禁止并发）

**幂等性**：
- 重复执行是否安全：是（任务有幂等键）
- 补跑支持：支持，通过 {参数} 指定补跑日期
- 补跑时已处理数据：跳过（检查 {状态字段}）

**失败处理**：
- 失败检测：任务执行超时（{N} 分钟）自动标记失败

**任务依赖**：
- 前置任务：{任务A} 完成后触发
- 后置任务：本任务完成后触发 {任务B}
```

**禁止行为**：

- ❌ 不分析部分失败处理（批量任务部分失败不等于全部失败）

**退出条件**：每个核心定时任务都有"业务问题"和"调度规则"描述；幂等性和失败恢复机制已明确；任务间依赖关系已记录。

保留 URL、HTTP 方法、接口粒度、版本和统一错误格式检查，但 REST 风格不是唯一判据。优先检查业务语义、鉴权、幂等、分页/排序稳定性、金额/时间/枚举格式、空值语义、错误码、兼容演进和调用方依赖。历史上非 REST 的稳定契约不得仅因风格不统一判为缺陷。

## 4. 关键业务切片：静态追踪与运行追踪

### 4.1 选择和场景覆盖

关键切片优先覆盖资金、订单、库存、权限、租户、不可逆数据、高频或事故多发流程。每个切片按适用性检查：正常、边界、失败、重复、并发、超时、撤销/冲正、跨日/时区、历史数据、人工补偿；不适用项写明理由。

#### 4.1.1 同一业务多实现主动发现

不得默认“一个业务切片只有一个实现”。应以相同业务目标、结果和核心事实为聚类键，交叉检查：

- 不同 API/RPC/MQ/任务/脚本是否完成相同业务结果；
- `v1/v2`、`old/new/legacy`、客户/渠道/区域包、复制 Service、条件装配和功能开关是否路由到不同实现；
- 同一关键写方法、状态字段、业务表或外部副作用是否存在多条入口链；
- 配置、租户、环境、灰度、数据版本和历史状态是否改变实际处理分支；
- 新旧实现是否同时活跃，还是分别属于影子、兼容、存量处理或待退役状态。

代码相似度只能发现候选；代码不同也可能表达同一业务。必须用业务目标、规则、状态、不变量、权威数据和运行结果确认。每个候选实现形成 `IMPL-*` 记录，并输出：

| 业务能力 | 实现 ID | 入口/路由条件 | 客户/渠道/版本/时间适用域 | 规则/状态 | 写入与副作用 | 运行证据 | 生命周期 | 重叠/未知项 |
|---|---|---|---|---|---|---|---|---|
| ___ | IMPL-___ | EP-___ | ___ | BR/SM-___ | ___ | E-___ | 活跃/过渡/兼容/待退役/未知 | ___ |

发现两个以上实现或无法排除适用域重叠时，必须转入 SOP-10；不得只选择当前最常见入口继续分析。

**G2 通过条件**：选定的高价值/高风险切片已建立“业务目标→入口→规则/状态→数据→副作用→运行信号→证据”链；关键静态边至少有一种运行证据校验，无法校验者已降级为推断并登记未知项。

## 5. 事务、一致性、幂等、并发、补偿与对账

### 5.1 事务与一致性边界

对切片逐节点标注本地事务、跨数据源、跨服务、MQ、缓存和外部副作用边界，不能因存在 `@Transactional` 就推断全链路原子。确认代理是否生效、传播级别、隔离级别、回滚异常类型、提交后回调、长事务和锁范围。

| 节点 | 读/写/副作用 | 事务边界 | 一致性模型 | 失败回滚范围 | 提交后风险 | 证据 |
|---|---|---|---|---|---|---|
| | | | 本地强一致/最终一致/无补偿 | | | E-* |

### 5.2 可重复写与幂等

枚举 HTTP/RPC 写接口、Webhook、MQ 消费、任务补跑、脚本、监听器和补偿操作。对每项记录幂等语义、键来源/作用域/有效期、原子落点、重复中的并发竞争、结果重放和过期后行为。

可接受机制可能包括业务唯一键+数据库约束、条件更新/状态机、幂等记录、原子令牌、Inbox/Outbox、版本号或受约束的锁。仅有“先查再写”、进程内锁或上游“保证只调用一次”通常不能单独证明幂等。

| 写操作 | 重复来源 | 幂等键/作用域 | 原子机制 | 重复/并发结果 | 过期/重放窗口 | 缺口 | 证据 |
|---|---|---|---|---|---|---|---|
| | 超时重试/MQ 重投/补跑 | | | | | | E-* |

### 5.3 并发控制

分析同一业务对象和跨对象并发：数据库隔离/锁、乐观版本、条件更新、分布式锁、队列串行、线程安全及锁续期/释放。验证竞争窗口、锁粒度和顺序、死锁、丢失更新、重复扣减、超卖、锁失效以及重试放大；不得看到锁 API 就认定安全。

### 5.4 补偿与对账

| 机制 | 检查内容 |
|---|---|
| 同步补偿/TCC/Saga | 正向步骤与 Confirm/Cancel/Undo 是否完整、幂等、可重试 |
| 异步可靠消息 | Outbox/本地消息、投递确认、消费幂等、DLQ、重放和顺序 |
| 定时对账 | 双方权威源、口径、容忍窗口、差异分类、自动/人工修复、复核 |
| 人工补偿 | 权限分离、工单、前置校验、审计、可逆性和二次确认 |

重点检查“写库+发消息”“写库+外部调用”“写库+缓存/搜索更新”“跨库写入”的部分成功。补偿动作本身也必须防重复、防越权并可观测。对账存在不等于能恢复：需验证发现时延、积压、责任人、修复成功率和业务闭环。

### 5.5 一致性错配

对比业务宣称与实际机制，识别“宣称强一致但边界外无保障”“最终一致但无重试/幂等/补偿”“有补偿但无检测触发”等错配。每个缺口关联受破坏的不变量、触发条件、影响半径和契约影响。

## 6. 认证授权、租户隔离与敏感数据

### 6.1 身份与权限链

|---|---|---|---|---|---|---|

### 6.3 敏感数据与秘密

建立敏感数据清单和流向：采集目的、最小化、传输/存储保护、密钥管理、日志/Trace/错误信息脱敏、缓存/消息/备份/导出、留存与删除。密码应使用适当的不可逆哈希；Token、密钥、证书和支付凭证不得硬编码或进入报告。

```text
**兼容性**：
- 关闭后旧数据是否受影响：是/否（{说明}）
- 关闭后旧消息是否受影响：是/否（{说明}）
- 关闭后旁路入口是否消失：是/否（{说明}）

**生命周期**：
- 创建日期：{日期}
- 到期日期：{日期}
- 清理条件：{条件}
- 灰度规则：{灰度方案}
- 观测指标：{指标}
```

**禁止行为**：
- ❌ 只列出开关名称和默认值，不解释业务行为
- ❌ 不检查关闭后的兼容性（开关关闭不等于旧数据消失）
- ❌ 不分析生效方式（配置了但未生效可能导致困惑）
- ❌ 忽略开关的到期清理（废弃开关长期不清理增加维护成本）

**退出条件**：每个核心功能开关都有"业务行为"和"作用域"描述；开关关闭的兼容性已检查；生效方式和生命周期已明确。

**分析结论的流向**：功能开关分析输出应输入到 §7.1 配置地图（登记为配置条目），以及 §4.4 运行追踪（验证开关切换的实际行为）。发现开关关闭后仍有旧数据或旁路入口时，应联动 §4.5 静态—运行差异。

### 7.3 环境差异

对开发、测试、预发、生产及区域/租户比较：制品版本、配置、开关、拓扑、数据规模、外部沙箱、证书、时区、资源限制、网关/MQ/数据库参数和观测能力。区分“刻意差异”和“漂移”，说明差异是否使测试结论不能外推生产。

## 8. 运行韧性、容量与故障传播

### 8.1 依赖调用预算

对关键同步/异步边记录端到端时延预算、连接/读取/总超时、重试主体、次数/退避/抖动、可重试条件、幂等前提、熔断/限流/隔离和降级语义。禁止只检查“是否配置超时”；要验证嵌套调用预算是否单调收敛，重试是否跨层叠加和放大负载。

| 调用边 | 协议 | 超时预算 | 重试主体/策略 | 幂等前提 | 限流/熔断/降级 | 失败返回/补偿 | 证据 |
|---|---|---|---|---|---|---|---|
| | | | | | | | E-* |

### 8.2 线程池、连接池与队列

盘点 Web/RPC、异步、调度、MQ 消费、数据库、Redis、HTTP 客户端等池和队列：大小、队列、获取/执行超时、拒绝策略、隔离、生命周期、上下文传播和监控。结合并发模型、请求耗时、下游容量、实例数与峰值证据评估，不复制通用线程数公式。

关注无界队列、CallerRuns 引起的级联阻塞、池间相互等待、连接泄漏、慢依赖占满资源、任务静默丢失、上下文污染及优雅停机期间未完成工作。

### 8.3 限流、熔断、隔离与降级

确认控制点、维度（用户/租户/接口/依赖）、配额来源、突发容量、集群一致性、拒绝语义、恢复探测和业务可接受性。降级必须明确保持哪些不变量、允许哪些数据陈旧、何时恢复和如何补偿；“返回成功但未处理”通常是危险的静默降级。

### 8.4 缓存、MQ 与存储运行风险

保留原有缓存穿透/击穿/雪崩、Key/TTL、一致性检查，以及 MQ 持久化、确认、顺序、积压和 DLQ 检查；进一步关联业务切片：缓存失效是否回源压垮数据库，消息积压是否越过业务时效，重放是否破坏幂等，主从延迟/分片路由/搜索索引滞后是否造成错误决策。

数据库表数、慢查询秒数等不采用通用阈值。以业务时延预算、数据量/分布、执行计划、锁等待、峰值容量和历史基线评价索引、查询、连接池及分页策略。

### 8.5 故障传播图

对关键切片选择慢依赖、不可用、超时、连接耗尽、线程池耗尽、MQ 积压、缓存雪崩、配置中心故障、实例重启等刺激，记录：触发条件→传播路径→受影响租户/业务→检测信号→隔离/降级→恢复/补偿。识别共享数据库、缓存、配置、DNS、证书、时钟和网络出口等共同失效点。

质量目标必须写成场景（刺激源+刺激+环境+对象+系统响应+可度量标准），目标来自业务损失、合同/合规、历史基线和成本约束，不照抄行业数字。

## 9. 测试、可观测性、发布、回滚与恢复

### 9.1 测试与持续校验

按风险和契约评估测试充分性，而非仅看覆盖率。关键切片应按适用性具备：

- 领域规则、状态机、不变量、金额/时间/精度的单元或性质测试；
- 数据库、缓存、MQ、任务、事务提交时序的集成测试；
- API/RPC、消息 Schema、错误码、历史数据的契约/兼容测试；
- 认证授权、租户隔离、敏感数据和管理入口的负向测试；
- 重复、并发、超时、重试、部分失败、补偿、对账和重放测试；
- 关键质量属性的容量、故障和恢复验证；
- 模块边界、禁止依赖、Schema 兼容等架构适应度函数。

| 切片/契约 | 主要风险 | 已有测试 | 未覆盖场景 | 环境真实性 | 失败可诊断性 | 建议校验 |
|---|---|---|---|---|---|---|
| SC-* | | | | | | |

覆盖率只表示被执行的代码比例，不能证明断言质量、场景充分或业务正确。高覆盖但缺少失败/并发/契约断言仍可能是高风险；低覆盖也应先补业务关键且高变化区域。

### 9.2 可观测性与可运营性

保留日志、指标、Trace、健康检查和告警分析，但以“能否发现、定位、止损、恢复并验证业务结果”为标准：

| 信号 | 检查内容 |
|---|---|
| 日志 | 结构化、关联 ID、业务对象/结果、错误堆栈、采样/保留、脱敏；不记录密钥和完整敏感载荷 |
| 指标 | 流量、错误、延迟、饱和度，以及订单/金额/库存/MQ/对账等业务结果和积压 |
| Trace | 跨 HTTP/RPC/MQ/异步线程传播，采样策略，关键标签脱敏，断链情况 |
| 健康检查 | 存活/就绪/启动语义，依赖故障是否导致错误摘除或假健康 |
| 告警 | 用户影响、阈值依据、去重升级、负责人、Runbook、静默风险和事后闭环 |
| 审计/对账 | 谁在何时对什么对象执行何动作，差异发现、修复及复核可追溯 |

用历史事故或演练验证告警，不以“已有监控组件”判定充分。记录 MTTD/定位/恢复证据及盲区，不机械要求生产只输出 WARN/ERROR；日志级别应兼顾诊断、成本、隐私和动态调整能力。

### 9.3 发布与回滚

记录构建到部署链：制品不可变性、签名/哈希、配置/Schema 变更顺序、审批、灰度/蓝绿、开关、健康门禁、监控窗口、自动/人工停止条件、优雅停机和 MQ/任务交接。

每类变更确认回滚能力：仅代码回滚、代码+配置回滚、数据库前向修复、消息/数据兼容、旧实例与新 Schema 共存。不可逆数据迁移不得笼统写“回滚版本”，应有备份、双写/回填、校验、切换和前向修复方案。

### 9.4 备份、容灾与业务恢复

| 对象/切片 | 权威源 | 备份/副本 | RPO/RTO 目标及依据 | 恢复步骤 | 依赖/权限 | 最近验证 | 业务校验/对账 | 缺口 |
|---|---|---|---|---|---|---|---|---|
| | | | | | | | | |

“有备份”不等于可恢复。检查备份完整性、加密、保留、异地性、恢复权限、密钥/配置/消息等非数据库状态；用获授权的恢复演练验证耗时和步骤，并通过业务不变量及对账证明恢复结果，而非只看数据库启动成功。

## 10. 证据、未知项与问题闭环

### 10.1 证据模型

证据类型沿用总览，详见 `SOP-00 §5.1`。每份关键证据登记：

```text
证据 ID：E-{类型}-{序号}
位置/获取方式：文件+行号、查询、看板或复现步骤
版本/环境/配置：对应提交、制品、实例和配置版本
采集时间/观测窗口：
质量：直接性、时效性、覆盖度、可复现性、独立性
脱敏/权限状态：
适用范围与不能外推范围：
```

结论使用稳定 ID 和确定性：直接事实、交叉验证结论、经验判断、推断、假设；记录验证状态“未验证→部分验证→交叉验证→已反证”。示例：`C-012（交叉验证结论）← E-SRC-017 + E-RUN-008`。已反证项保留反证原因，避免重复误判。

### 10.2 台账

| 台账 | ID | 最小字段 |
|---|---|---|
| 未知项 | U-* | 未知内容、为何未知、决策影响、最小验证动作、负责人/期限 |
| 假设 | H-* | 观察、候选解释、支持/反对证据、区分性验证、状态 |
| 矛盾 | X-* | 冲突证据、版本/环境、可能解释、解决动作、结论影响 |
| 结论 | C-* | 内容、确定性、范围、证据、反证、复核人 |
| 问题/风险 | I-* / R-* | 类型、触发、影响、不变量/契约、证据、根因、处置 |

### 10.3 问题与建议闭环

区分缺陷、风险、技术债、改进机会和未知项。本文件的 P0-P3 指缺陷/问题严重度（SEV-P0~P3），不直接等同固定修复时限，且与 L1 的 SC-P* 切片深度分级无关（SC-P* 是分析深度配额，禁止混用）。排序同时考虑业务影响、发生可能性、暴露面、可检测性、可逆性、证据强度、实施成本和依赖关系，不制造伪精确总分。

每条高影响问题至少包含：现象与触发条件、被破坏的不变量/契约、版本/环境/范围、证据与确定性、影响对象/半径、可能性/暴露/检测/可逆性、直接/机制/系统性根因、临时缓解、候选方案（含不处理）、兼容/迁移/数据影响、验证标准、回滚、负责人、状态和复查日期。

建议不得从“常见最佳实践”直接跳到重写。先说明现状证据和目标质量属性，再比较保留、隔离、包装、开关、版本化、并行验证、小步替换等候选方案；明确调用方、数据迁移、发布、观测和回滚。

**G3 通过条件**：安全、租户、一致性、幂等、兼容、配置、韧性、可观测和恢复等适用横切项已分析；跳过项有理由和影响说明。

**G4 通过条件**：高影响问题有证据、业务影响和根因层级；建议有替代方案、兼容/迁移影响、验证标准和回滚。

## 12. 完成判据

本轮后端整体分析以“足以支持决策”为停止条件，不以读完全部代码、画完所有表或达到通用分数为完成。全部满足或明确豁免后通过 G5：

- [ ] 任务书、范围内/外、权限和停止条件明确，决策负责人可确认用途
- [ ] 源码、制品、配置、Schema、部署和运行窗口基线可复现，差异已解释或登记
- [ ] 模块、服务、数据、外部依赖、所有权和信任边界地图已建立
- [ ] HTTP/RPC、MQ、任务、脚本、监听器、管理和数据触发等适用入口已枚举
- [ ] 高价值/高风险切片已贯通业务目标、入口、规则、数据、副作用、运行和恢复
- [ ] 关键静态调用边有运行证据校验；无法校验项已降低确定性
- [ ] 事务边界、幂等、并发、补偿、对账和一致性错配已分析
- [ ] 认证授权、租户/数据作用域和敏感数据路径覆盖所有适用入口及异步边界
- [ ] 配置优先级、功能开关生命周期和环境差异已识别
- [ ] 超时/重试预算、资源池、限流/熔断/降级及主要故障传播已分析
- [ ] 显式/隐式调用方和兼容契约已登记；“未找到”未被写成“不存在”
- [ ] 关键规则、失败场景和契约的测试缺口已明确，可观测信号能支持发现和恢复
- [ ] 发布、回滚、备份和恢复方案已基于当前环境验证或明确证据缺口
- [ ] 关键结论均有关联证据、适用范围、确定性和反证状态
- [ ] 未知项、假设和矛盾有决策影响、最小验证动作、负责人和期限
- [ ] 高影响建议有候选方案、兼容/迁移影响、验证标准和回滚方案
- [ ] 未解释的强反证为零；另一名分析者能按证据索引复核关键结论
- [ ] 新增分析的预期信息价值低于继续投入的时间和风险成本

## 13. AI 辅助执行约束

1. 不以类名、包名、表名、字段名或注释直接断言业务语义；只能形成候选解释，并寻找数据、运行、契约或人员证据。
2. 不把本地源码、默认配置或文档意图写成生产事实；先核对部署、配置和运行时间窗口。
3. 不只搜索 Controller；必须覆盖 RPC、MQ、任务、脚本、监听器、管理入口、数据触发和反向调用。
4. 不因静态搜索无结果就断言“无人调用、没有重试、没有租户隔离”；优先提出能区分候选解释的最小验证动作。
5. 不机械以类长、方法长、圈复杂度、覆盖率、模块数、表数、慢查询固定秒数或是否 RESTful 判定优劣；这些仅是筛选信号。
6. 不把框架注解或组件存在等同机制生效；验证代理、配置、部署、调用路径和运行结果。
7. 不把“常见做法”写成本系统事实或唯一方案；质量目标必须有业务、合规、历史或容量依据。
8. 不生成大而全但无人使用的清单；优先高价值、高风险、高变化和高证据缺口切片。
9. 不直接建议重写或删除疑似旧逻辑；未知依赖默认按存在处理，先识别契约、历史数据、开关、迁移、并行验证和回滚。
10. 不自行执行生产写操作、故障注入、消息重放、任务补跑、数据修复或高开销扫描；需要明确授权和停止/回滚方案。
11. 输出时区分现状事实、推断模型、目标建议；所有关键结论同时给出证据 ID、范围、确定性和未知项。
12. 涉及凭据、个人信息、支付或跨租户数据时只保留最小脱敏证据，不向未经批准的外部服务传输项目内容。
