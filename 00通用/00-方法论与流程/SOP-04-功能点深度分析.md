## TL;DR

**一句话**：从业务目的出发，贯通单个功能/切片的入口、规则、状态、数据、副作用和测试，形成可复核的深度分析结论。

**核心输入**：分析任务书、切片标识、版本/环境基线、权限边界

**核心输出**：功能定义卡、入口/出口追踪矩阵、状态机与规则、事务/幂等分析、测试矩阵

**关键约束**：必须贯通"业务目的→入口→规则→状态→数据→副作用"全链路；多实现必须先执行 SOP-10

## 1. 目的与适用范围

本 SOP 用于贯通单个功能或业务切片的业务目的、用户交互、接口、后端机制、状态与规则、数据、外部副作用、运行证据和测试，形成可复核、可复现、可支持决策的深度分析结论。

适用于核心或问题功能排查、新功能设计前的现状基线、重构/迁移/兼容评估、事故复盘及高风险变更分析。简单静态页面可按适用性裁剪，但所有跳过项都必须说明理由和决策影响。

**不是完成标志**：页面截图齐全、接口或代码文件清单齐全、Controller/Service/Mapper 顺序读完、数据库表结构抄完、成功路径可运行，均不等于完成深度分析。

## 2. 核心原则与分析单位

1. **一个切片，贯通到底**：切片应以业务结果命名，如“会员储值入账”，而非“储值页面”或“某 Controller”。
2. **业务语义是锚点**：先回答服务谁、解决什么问题、成功意味着什么，再解释技术实现。
3. **黑箱、灰箱、白箱往返验证**：先观察用户行为和输入输出，再追踪请求、消息、数据与运行链路，最后用代码、配置和事务机制解释。
4. **正常与失败同等重要**：必须分析边界、失败、重复、并发、超时、撤销/冲正、历史数据和人工恢复；不适用时给出依据。
5. **静态与动态互证**：源码只能说明可能行为，部署配置、日志、指标、Trace、数据和可复现实验才说明特定环境中的实际行为。
6. **现状事实与合理性分离**：现有行为不自动等于正确设计，行业惯例也不自动等于本系统事实。
7. **允许未知，不允许伪确定**：证据空白、矛盾和无法验证项必须进入台账。

端到端追踪链：

```text
业务目的 → 用户/角色 → 场景、前置条件与成功标准
         → 前端交互/页面/API/消息/任务/回调/人工入口
         → 接口契约 → 后端编排与领域规则 → 状态机与不变量
         → 数据读写、权威源与历史数据 → 外部副作用
         → 事务、一致性、幂等、重试、补偿与对账
         → 指标、日志、Trace、审计与告警
         → 动态证据、测试、问题/风险/未知项与建议
```
## 3. 准入、执行流程与门禁

### 3.1 S04-G0：任务书与范围基线

开始分析前记录：

| 字段 | 必须回答 |
|---|---|
| 任务模式与分析/决策问题 | 认知重建说明要理解什么；只有决策支持或变更实施才填写决定、负责人和风险接受要求。AI 不得自行升级任务模式 |
| 切片标识 | `SL-xxx`、名称、所属模块、业务关键等级 |
| 分析对象业务位置 | 核心业务域/支撑业务能力/技术平台能力/混合类型；本切片拥有与不拥有什么事实 |
| 版本基线 | 仓库分支/提交、部署版本、配置版本、数据库版本 |
| 环境与时间窗口 | 开发/测试/预发/生产，以及证据采集区间 |
| 范围内 | 本轮覆盖的角色、渠道、入口、状态、数据和上下游 |
| 范围外 | 明确不覆盖的内容、理由及可能影响 |
| 权限与安全边界 | 可访问资源、允许动作、只读要求、脱敏与禁止事项 |
| 预期产物 | 报告、追踪矩阵、状态图、证据索引、测试矩阵、台账 |
| 风险容忍度 | 哪些错误结论不可接受，哪些可通过可逆实验纠正 |
| 停止条件 | 哪些证据足以支持决策，何时停止继续分析 |

**准入条件**：任务书已书面化；SOP-00 G1 所需的系统边界、主要依赖、数据存储、所有权和信任边界可用。未满足时只能输出探索性发现，不得给出确定性根因或不可逆改造建议。

### 3.2 执行流程

1. 定义功能目的、业务位置、角色、范围、前置条件、上游事实、交付义务与成功标准。
2. 黑箱复现正常路径，记录用户可见行为、请求、结果和副作用。
3. 枚举全部入口和调用方，建立初始端到端追踪矩阵。
4. 灰箱追踪接口、消息、任务、缓存、数据库、外部系统和运行观测。
5. 白箱解释前端状态、后端编排、规则、状态机、事务和数据机制。
6. 建立正常、边界和失败场景矩阵，执行最小风险的区分性验证。
7. 校验权限租户、安全隐私、一致性幂等、兼容和可运营性。
8. 建立测试矩阵、证据/结论/矛盾/未知项台账。
9. 必须主动以相同业务目标、结果和核心事实聚类入口、服务、规则、状态、数据写入、配置、版本及人工路径，确认是否存在多个客户版、渠道版、时期版、重写版或兼容版；不得因当前切片只命中一个入口就断言只有一个实现。发现多个实现或无法排除适用域重叠时，执行 `SOP-10-业务演进多实现归一与重构迁移.md`，建立实现谱系、语义差异、适用域交集、冲突关系和旧新映射。
10. 若分析结果将用于选择、改造或批准业务设计，执行 `SOP-09-业务设计合理性评审.md`，校验红线门槛并比较当前、不处理、最小改进和结构性方案；SOP-10 形成的目标模型同样必须经过该评审。
11. 形成问题、风险、候选方案、验证和回滚闭环，执行完成判据。

### 3.3 门禁

| 门禁 | 最小通过条件 |
|---|---|
| S04-G1 边界与入口 | 功能边界、入口（页面/API/MQ/任务/脚本）和业务位置已确认；由 §3.1 S04-G0 完成后在追踪环节衔接，本文档不设独立 S04-G1 小节 |
| S04-G2 切片贯通 | 业务目标到指标/审计、测试和证据的链路完整；空白项已登记未知项 |
| S04-G3 横切校验 | 权限租户、安全隐私、一致性幂等、兼容、运行恢复等适用项有证据；跳过项有理由 |
| S04-G4 建议闭环 | 高影响发现具备证据、影响、根因层级、替代方案、兼容影响、验证与回滚 |
| S04-G5 交付验收 | 关键结论可复现，强反证已解释，范围限制与未知项明确，独立复核可执行 |

门禁允许回退：例如并发验证发现状态越迁，应回到规则、事务和数据追踪，而不是只在报告末尾增加一句“建议加锁”。
## 4. 功能语义与业务边界

### 4.1 功能定义卡

| 维度 | 分析要求 |
|---|---|
| 功能目的 | 解决的业务问题、创造/保护的价值；不用技术动作代替业务目的 |
| 业务位置 | 核心业务域/支撑业务能力/技术平台能力/混合类型；不得默认把任务或持久化对象当成业务中心 |
| 用户与角色 | 发起者、审批者、受益者、运营/客服/审计、系统账号及责任主体 |
| 触发与场景 | 用户操作、API、回调、消息、定时任务、批处理、脚本、人工修复 |
| 上游业务事实 | 触发本功能的事实、权威解释者、版本/时点及本功能是否只保存快照 |
| 交付义务 | 需交付的产物/结果、接收角色及后续动作、有效时点和成功判据 |
| 范围内/外 | 对象、渠道、租户、地域、时间、状态、上下游及明确排除项 |
| 前置条件 | 身份、权限、对象状态、依赖数据、配置开关、额度/库存/时间窗 |
| 输入与输出 | 字段语义、单位、精度、时区、枚举、默认值、可空性及展示语义 |
| 成功标准 | 用户可见结果、持久化事实、状态变化、外部副作用、指标/审计可见性 |
| 失败语义 | 可重试/不可重试、结果确定/未知、用户提示、恢复责任和时限 |
| 失败业务后果 | 遗漏、错误、重复、延迟和结果未知分别破坏什么业务结果 |
| 事实所有权边界 | 本功能拥有、不拥有以及仅复制/缓存/执行的事实 |
| 所有权 | 业务、代码、数据、运行、外部依赖和故障处置负责人 |

“接口返回成功”不是充分的成功标准。必须确认权威数据已形成、必要副作用已达成或进入可追踪的最终一致流程，且用户不会因假成功继续执行错误操作。

### 4.2 关联与影响

记录前置功能、后置功能、共享数据、共用规则、被动消费者、报表/对账、客服工具、定时任务和人工流程。未搜索到调用方不得写成“无人使用”；无法确认时登记 `U-xxx`，默认存在兼容风险。

## 5. 端到端实现追踪

### 5.1 追踪矩阵

| 切片/场景 ID | 核心概念 | 业务目的与角色 | 入口/交互 | 接口/消息/任务 | 服务/规则/状态 | 数据/权威源 | 外部副作用 | 指标/审计 | 测试/证据 | 未知项 |
|---|---|---|---|---|---|---|---|---|---|---|
| SL-001/S-01 | CONCEPT-xxx |  |  |  |  |  |  |  |  |  |

每个格子应写稳定 ID 或可定位引用，不复制大段代码。空白必须转为未知项并说明是否阻断决策。

### 5.2 概念语义与作用校验（强制）

**目的**：每个功能切片必须验证其涉及的核心概念是否被正确理解，防止将枚举名/类名/样式名误当成业务概念。

**概念定义卡（按切片维度）**：

| 字段 | 必须回答 |
|---|---|
| 概念 ID | `CONCEPT-xxx`，在追踪矩阵中引用 |
| 概念名称 | 源码枚举/字段/类名，或业务术语 |
| 业务语义 | 这个概念解决什么问题，表达什么业务事实 |
| 在业务设计中的作用 | 在此切片中触发什么动作/决策/路由 |
| 正交/组合关系 | 与本切片其他概念的关系：用途维度 × 样式维度？谁能替代？ |
| 语义三角校验 | 声明语义（文档注释）、实现语义（代码逻辑）、运行语义（实际行为）是否一致 |
| 证据与确定性 | 源码位置/测试/运行证据；直接事实/交叉验证/推断/假设 |

**常见概念混淆检查**：

| 混淆类型 | 示例 | 检查方法 |
|---|---|---|
| 用途维度 × 样式维度混淆 | `PrnJobPurposeEnum`（给谁用）与 `PrnStyleTypeEnum`（打印什么单据）被混用 | 检查枚举的所有枚举值，确认每个值是否属于用途或样式维度 |
| 同名不同义 | 不同模块中的 `status` 字段含义不同 | 检查源码出处和字段注释 |
| 同义不同名 | 同一业务概念有多个命名 | 检查业务语义是否相同 |
| 隐式概念 | 概念未在文档/注释中声明，读者需自行推断 | 检查是否所有核心概念都有明确定义 |

**输出要求**：每个功能切片至少包含一张概念定义卡；不允许出现"概念未定义"或"读者需自行推断业务语义"的情况。

### 5.3 前端与用户交互

保留原 SOP 对页面结构、组件职责、表单字段、校验、联动、页面状态和 API 调用的分析，并补齐：

- 每个角色能看到、能操作和被禁止的内容；前端隐藏按钮不能证明后端授权。
- 初始、加载、空、只读、编辑、提交中、成功、失败、结果未知、过期和冲突状态。
- 连点、重复提交、返回/刷新、跨页、断网重连、超时后重试、并发编辑的交互语义。
- 前端校验与服务端校验是否一致；金额、精度、时区、枚举、空值和默认值是否被转换。
- 错误提示是否可行动，是否泄露内部结构或敏感数据；成功提示是否早于真实业务成功。
- 本地缓存、全局状态、草稿、离线队列和刷新策略是否造成陈旧数据或跨租户残留。

输出用户操作序列，而不是仅附截图：`前置状态 → 操作 → 请求/事件 → UI 状态 → 业务结果 → 可恢复动作`。

### 5.4 接口与契约

逐个记录 HTTP/RPC/消息/回调/批任务：方法或主题、调用方、认证主体、租户来源、请求/响应 Schema、业务错误、超时、重试、幂等键、版本策略和废弃计划。校验：

- 必填、范围、格式、精度、时区、排序/分页、枚举未知值、额外字段和空值语义。
- HTTP 状态与业务码是否稳定；超时或连接断开时能否确认服务端结果。
- 消息顺序、重复、延迟、丢失、死信、重放和 Schema 演进。
- 调用方是否依赖未声明字段、错误文本、字段顺序、默认值或“错误但稳定”的历史行为。
### 5.5 后端执行链与运行机制

从入口追踪到应用服务、领域逻辑、数据访问、消息生产/消费、任务、缓存和外部适配器。记录实际调用顺序、同步/异步边界、配置或功能开关、异常转换、超时与资源限制。Controller/Service/Mapper 文件清单只作为定位索引，不是分析结论。

重点回答：

1. 业务校验发生在哪里，是否能被其他入口绕过；前置查询与写入之间是否存在竞态。
2. 事务代理是否实际生效，回滚范围包含哪些数据，不包含哪些消息、缓存和外部调用。
3. 重试由谁触发，对哪些错误生效，是否有退避、上限、熔断、限流和结果确认。
4. 线程池、连接池、锁、批量大小、超时和降级如何影响此切片，故障如何向上下游传播。
5. 关键日志、指标、Trace、审计和告警能否关联同一业务对象并定位失败阶段。

## 6. 横切强制分析

### 6.1 身份、权限、租户、安全与隐私

逐入口建立矩阵：

| 入口/动作 | 认证主体 | 功能权限 | 对象/行级权限 | 租户来源与隔离 | 允许用例 | 拒绝用例 | 审计 | 证据 |
|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |

必须检查：

- 服务端是否校验权限和数据作用域；对象 ID、租户 ID、门店/组织 ID 能否被替换越权。
- 平台、商户、门店、用户、系统账号和异步任务的租户上下文是否明确且贯穿查询、缓存、消息和日志。
- 创建、审批、撤销、退款、导出、数据修复等高风险动作是否职责分离并可审计。
- 输入校验、注入、XSS、文件、SSRF、批量赋值、重放和错误信息泄露风险。
- 敏感字段分类、最小采集、传输/存储保护、日志/Trace 脱敏、导出、保留、删除和跨境/跨租户边界。
- 密钥和 token 的来源、使用与轮换；报告不得落盘完整凭据或个人敏感信息。

至少验证一个允许和一个拒绝场景；多租户功能还应验证跨租户拒绝。不得用前端隐藏、携带 token、出现 401/403 或 SQL 中偶见租户条件替代端到端隔离证据。

### 6.2 事务、一致性、幂等与补偿

绘制提交与副作用时序，并记录：

| 项目 | 必须回答 |
|---|---|
| 事务边界 | 本地/跨库/跨服务边界、隔离级别、提交顺序、回滚范围 |
| 一致性目标 | 强一致/最终一致；允许的不一致窗口及业务影响 |
| 并发控制 | 唯一约束、条件更新、版本号、锁粒度、冲突结果与死锁处理 |
| 幂等机制 | 幂等键来源、作用域、绑定请求、有效期、结果复用和原子落库 |
| 消息可靠性 | 事务消息/Outbox、投递与消费语义、去重、顺序、死信和重放 |
| 重试 | 可重试错误、发起方、次数/退避/抖动、结果确认和重试风暴防护 |
| 补偿与对账 | 触发条件、逆操作、不可逆项、补偿幂等、人工入口、差异闭环 |

仅发现 `@Transactional`、分布式锁、防重 token 或重试注解，不足以证明端到端原子性、并发安全或幂等。尤其验证“事务内调用外部系统/发消息”“响应丢失但服务端已提交”“补偿自身失败”三类结果未知场景。

### 6.3 接口、历史与隐式依赖兼容

建立兼容清单：API/OpenAPI、RPC、消息 Schema、错误码、配置键、功能开关、缓存键、数据库表/视图/直连、文件和任务产物、脚本、反射入口、报表、历史数据及人工操作约定。

对每项记录生产者、已知/未知消费者、当前契约、历史异常行为、变更影响、版本策略、兼容窗口、数据迁移、灰度/双写/影子验证、监控和回滚。验证旧客户端、旧消息、历史枚举/空值/精度/时区、迁移前数据和新旧节点混部；无法穷举消费者时采用保守方案，不得直接删除、改义或重写。

### 9.1 测试矩阵

## 10. 问题、风险、未知项与建议闭环

不得混淆：缺陷（已违反要求/不变量）、风险（存在触发条件和损失暴露）、技术债（增加理解/变更/运营成本）、改进机会（有明确收益）、未知项（证据不足且可能改变结论）。

### 10.1 记录模板

| 字段 | 内容 |
|---|---|
| ID/类型/严重度 | `I-xxx`（缺陷/风险/技术债/改进机会）；P0-P3 仅表示业务严重度 |

| 根因层级 | 直接原因、机制原因、系统性原因；证据不足不得写确定根因 |

| 治理 | 负责人、状态、目标/复查日期和决策记录 |

处置顺序应综合业务影响、可能性、暴露面、可检测性、可逆性、证据强度、实施成本和依赖，不使用简单总分制造伪精确。高影响建议未包含替代方案、兼容影响、验证和回滚时，不得进入实施决策。

## 13. AI 辅助分析约束

使用 AI 执行本 SOP 时，除遵守 SOP-00 v3.7、`研发方法/业务系统分析-认知真源.md` v2.0、文档 20 和文档 21 外，还必须：

1. **字段名真实性门禁**：文档中引用的所有字段名必须与源码（Entity/POJO/DTO/VO/枚举/数据库Schema）中的实际字段名逐字段核对；跨层允许 API/DTO/DB/前端命名差异，但必须有可解析映射证据；禁止无映射猜测名。核对须记录层别、符号、出处和版本基线
2. 不以页面名、类名、方法名、表名、字段名或注释直接断言业务语义；推断须标注并寻找运行、数据、契约或人员证据。
3. 不把示例技术栈、常见做法或行业标杆写成本系统事实，也不把目标建议画成现状。
4. 不因未搜索到调用方而断言无人使用；反射、配置、消息、任务、脚本、报表、缓存和数据库直连均可能形成隐式依赖。
5. 每个关键结论同时输出证据 ID、版本/环境/范围、确定性、反证和关键未知项；证据不足时提出最小区分性验证动作。
6. 不机械扩展“大而全”清单；优先验证高业务价值、高损失、高频、高变化、事故多发和证据缺口大的场景。
7. 不把 `@Transactional`、锁、token、重试、唯一查询、前端隐藏按钮等名称当作机制成立的证明。
7. 不直接建议重写、上分布式锁、引入新中间件或大规模重构；先列不处理、最小改动和替代方案，再评估兼容、迁移、观测和回滚。
8. 不虚构动态证据、测试结果、性能数据、调用方或历史行为；未执行必须明确写“未验证”。
9. 不在报告、提示词或外部工具中暴露代码、凭据、完整日志或敏感数据；未经授权不得上传项目材料。
10. AI 生成的图、矩阵和结论必须由人或可复现实验校验；高影响决策不得只依据 AI 推断。
11. 未满足稳定业务身份、明确生命周期、原子不变量和行为边界时，不得把实现对象标记为聚合根；没有独立业务事实语义时，不得标记为领域事件。

## 14. 常见反模式

- 按页面、Controller、Service、Mapper、表结构逐层抄录，却没有业务结果和失败语义。
- 只走“提交成功→刷新列表”，未核对权威数据、异步副作用、审计和结果未知。
- 用截图、代码搜索结果或静态调用图替代运行证据。
- 用“加锁、加事务、加重试、上缓存/搜索引擎”等名词替代触发条件、机制、代价和验证。
- 把前置 `exists` 查询当作并发唯一性，把前置检查当作并发删除安全。
- 把未观察到当作不存在，把历史脏数据当作可直接清理，把当前错误行为当作可任意修正。
- 问题只记录“问题、位置、建议”，没有证据、影响、替代方案、兼容、验证和回滚。
- 用综合总分掩盖单个 P0 风险，或把 P0-P3 直接等同固定修复时限。
