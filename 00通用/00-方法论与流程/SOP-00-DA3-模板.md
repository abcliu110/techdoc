## 模板正文

```markdown
# DA3 关系分析 — {分析对象}

> **分析视角**：从业务对象出发，不是从数据表出发
> **核心洞察**：最有价值的是对象之间的间接路径（3-4跳），而非表之间的直接引用（0跳）

## 一、业务对象识别

> **目的**：先识别业务对象，再分析对象之间的关系
> **注意**：业务对象 ≠ 数据表，一个数据表可能承载多个业务对象

### 1.1 核心业务对象清单

| 对象编号 | 对象名称 | 业务定义 | 生命周期 | 边界 |
|----------|----------|----------|----------|------|
| BO-01 | {对象名} | {一句话说明这个对象是做什么的} | 创建→使用→消亡 | {边界说明} |
| BO-02 | ... | ... | ... | ... |

### 1.2 业务对象之间的关系

| 关系编号 | 对象A | 对象B | 关联类型 | 业务意义 |
|----------|-------|-------|---------|---------|
| OR-01 | {对象A} | {对象B} | 结构/轨迹/归因 | {描述业务关系的存在原因} |
| OR-02 | ... | ... | ... | ... |

## 二、关键业务路径

> **目的**：分析业务对象之间的间接路径，发现多跳关联的业务价值
> **强制要求**：从核心业务对象出发，追踪所有可达路径，每一跳都要写清楚，直到没有新的有意义的关系为止。不是"凑够N跳"，而是"有多少跳就写多少跳"

### 2.1 核心业务路径图（从核心业务对象出发，追踪所有可达路径）

```
{业务对象A} ──{关系}──▶ {业务对象B} ──{关系}──▶ {业务对象C} ──{关系}──▶ {业务对象D}
     │                                                          │
     │                    业务起点/触发事件                      │
     └──────────────────────────────────────────────────────────┘
```

> **强制要求**：必须覆盖所有从核心对象出发的可达路径，每一跳都要标注业务语义

### 2.2 路径与业务场景映射

| 路径编号 | 路径（对象→对象→...） | 跳数 | 关键业务场景 | 为什么需要这条路径 |
|----------|----------------------|------|-------------|-------------------|
| BP-01 | {A}→{B}→{C}→{D} | 3跳 | {业务场景} | {间接关联的业务价值} |
| BP-02 | {A}→{B}→{C} | 2跳 | {业务场景} | {为什么不能直接A→C} |
| BP-03 | ... | ... | ... | ... |

### 2.3 间接路径分析要点

对于每条间接路径，必须回答：
1. **为什么需要经过中间对象**：中间对象承担了什么职责（路由/分组/边界/生命周期）
2. **如果直接关联会怎样**：直接关联会导致什么问题（耦合/重复/难以维护）
3. **中间对象的业务语义**：这个中间对象在业务上代表什么概念

## 合格范例（强制参照）

以下范例演示"3 跳间接关系"契约的完整深度。每个核心间接关系（N跳）必须达到此深度；只写"A 关联 B，N:1"不算完成。

```
┌─────────────────────────────────────────────────────────────────┐
│ REL-04: 菜品 ↔ 打印机（间接关联，3 跳）                          │
├─────────────────────────────────────────────────────────────────┤
│ 【关系定义】                                                    │
│   类型：N:1（通过中间对象间接关联，运行时动态路由）              │
│   关联路径：直接（0跳）不存在，必须经过 3 跳                     │
│                                                                 │
│ 【关联路径】（共 3 跳）                                          │
│   菜品 → 出品部门（菜品归属哪个部门制作）                        │
│     → 打印队列（部门关联哪个队列出单）                           │
│     → 打印机（队列选择哪台健康打印机）                           │
│                                                                 │
│ 【为什么需要经过中间对象】（业务原因，至少 2 条）                │
│   1. 简化配置：只需为每个出品部门配置一个队列，而不是为每道菜    │
│      单独配置打印机；新菜只选部门即可，无需配打印机              │
│   2. 自然分组：同一部门的菜自动合打一张单，厨师按部门收单；      │
│      如果菜品直接绑打印机，跨部门合单、换打印机都要改所有菜      │
│   3. 故障转移：队列层可以配主/备打印机；若菜品直连打印机，       │
│      打印机故障时无法自动切换                                    │
│                                                                 │
│ 【如果直接关联（菜品→打印机）会怎样】                            │
│   新增/更换打印机需修改所有关联菜品配置；无法按部门合单；        │
│   打印机故障时无备机可切                                         │
│                                                                 │
│ 【中间对象职责】                                                │
│   出品部门：业务分组边界（什么菜归谁做）                         │
│   打印队列：路由与容错（主/备打印机、负载均衡）                  │
│                                                                 │
│ 【级联行为】                                                    │
│   删除菜品 → 不影响部门/队列/打印机                              │
│   删除部门配置 → 该部门菜品无法路由，需重新配置                  │
│   删除队列 → 关联部门菜品无法打印                                │
│   删除打印机 → 队列自动切换到备用                                │
│                                                                 │
│ 【异常场景】                                                    │
│   场景1：菜品未配置部门 → 无法路由，任务创建失败或跳过           │
│   场景2：部门未配置队列 → 分发失败，日志记录                     │
│   场景3：队列主备全故障 → 延迟重试（2秒），超时（45分钟）放弃    │
└─────────────────────────────────────────────────────────────────┘
```

> 使用方式：AI 生成 DA3 时，对最重要的 1 条间接路径（如上述 3 跳路径）按范例深度展开；其余关系可适当精简，但"为什么经过中间对象"和"级联行为"不允许省略。
