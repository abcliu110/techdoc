## 0. 文档目的

统一提炼不变量（Invariant）的设计原则、分类体系、实现模式和验证方法，作为业务流-规则统一建模方法论的补充。

## 1. 不变量基础

### 1.1 什么是业务不变量

业务不变量是业务系统在任何合法操作路径上都必须保持成立的条件。它回答的问题是：

> "在什么情况下，即使业务人员、管理员甚至系统故障，都**绝对不能**发生的事情是什么？"

### 1.2 不变量与业务规则的区别

| 维度 | 业务规则 | 不变量 |
|---|---|---|
| 性质 | 可配置、可变更 | 不可破坏、不可协商 |
| 来源 | 经营政策、产品决策 | 法规、财务、逻辑底线 |
| 例外 | 可以有授权例外 | 原则上不允许例外 |
| 变化频率 | 经常变化 | 很少变化 |
| 违反处理 | 提示、审批、拒绝 | 直接拒绝 + 告警 |
| 示例 | 满500免运费 | 退款不超过原支付 |

### 1.3 为什么需要不变量

1. **安全底线**：防止数据腐败、系统漏洞或人为错误导致不可接受的后果
2. **业务可信**：保证财务报表、对账单、库存数据的可信度
3. **风险控制**：保护资金、库存、权限等关键资产
4. **合规要求**：满足财务、税务、审计的硬性要求

### 1.4 不变量元模型

```text
Invariant =
  <invariantId,
   description,
   category,
   scope,
   formula,
   enforcementPoints,
   verificationMethods,
   violationHandling,
   relatedBusinessFlows,
   relatedRules,
   evidence>
```

| 字段 | 含义 |
|---|---|
| invariantId | 不变量唯一标识 |
| description | 不变量描述（业务语言） |
| category | 分类：资金/库存/数量/权限/状态/跨流 |
| scope | 适用范围：全局/租户/门店/商品 |
| formula | 数学或逻辑表达式 |
| enforcementPoints | 校验时机：创建/更新/删除/对账 |
| verificationMethods | 验证方式：实时/异步/人工 |
| violationHandling | 违反处理：拒绝/告警/修复 |
| relatedBusinessFlows | 涉及的业务流 |
| relatedRules | 相关业务规则 |
| evidence | 设计依据：法规/合同/逻辑 |

## 2. 不变量分类体系

### 2.1 一级分类：按业务领域

```
业务不变量
├── 资金类（Money）
├── 库存类（Inventory）
├── 数量类（Quantity）
├── 权限类（Authorization）
├── 状态类（State）
├── 时间类（Temporal）
├── 跨流类（Cross-Flow）
└── 合规类（Compliance）
```

### 2.2 二级分类：按破坏后果

```
资金类
├── 绝对底线：余额不能为负、资金不能凭空产生
├── 业务底线：退款不超过支付、付款不超过应付
└── 审计底线：所有变化必须有分录

库存类
├── 绝对底线：库存不能为负
├── 业务底线：出库不超过预占、预占不超过可用
└── 追溯底线：批次追溯不可丢失

数量类
├── 守恒底线：投入=产出+损耗
├── 边界底线：订单数量不能为负
└── 分摊底线：分摊合计等于总额

权限类
├── 绝对底线：不能访问未授权数据
├── 业务底线：不相容职责不能同一人承担
└── 审计底线：所有操作有操作人

状态类
├── 合法转换：状态机只允许合法转换
├── 互斥状态：对象不能同时处于互斥状态
└── 终结状态：进入终结状态后不可变更

时间类
├── 有效期：只在有效期内有效
├── 顺序性：某些事件必须按顺序发生
└── 幂等性：重复请求不产生重复结果

跨流类
├── 一致性：多流之间的金额/数量一致
├── 派生关系：一个流的金额由另一个派生
└── 依赖关系：一个流的状态依赖另一个流

合规类
├── 财务合规：借贷必相等
├── 税务合规：税额计算正确
└── 审计合规：所有关键操作留痕
```

## 3. 不变量识别方法

### 3.1 从法规和合同识别

```text
问题清单：
├─ 哪些法规要求必须满足？（如财务、税务、劳动法）
├─ 哪些合同条款是硬性约束？
├─ 哪些行业标准必须遵守？
└─ 哪些内部制度不可突破？

典型发现：
├─ 《票据法》：发票金额与实际交易金额一致
├─ 《劳动合同法》：工资不能低于最低工资标准
├─ 供应商合同：付款不能超过合同金额
└─ 行业规范：食品安全追溯必须完整
```

### 3.2 从业务逻辑识别

```text
问题清单：
├─ 哪些条件一旦破坏会导致业务无法继续？
├─ 哪些数据矛盾会让报表失真？
├─ 哪些操作会让对账永远无法平衡？
└─ 哪些假设被代码隐式依赖？

典型发现：
├─ 退款金额不能超过支付金额（否则财务无法解释）
├─ 库存为负会让采购计划失效
├─ 订单明细之和必须等于订单总额（否则分摊无法计算）
└─ 预占数量不能超过可用数量（否则超卖）
```

### 3.3 从反模式识别

```text
问题清单：
├─ 现有代码中有哪些 "should always" 的假设？
├─ 哪些 if-else 是在保护边界条件？
├─ 哪些异常是在防止不合理状态？
└─ 哪些测试用例在测试 "不应该发生" 的场景？

典型发现：
├─ if (balance < amount) throw InsufficientBalance
├─ if (refundedAmount > paidAmount) throw Error
└─ if (shippedQty > orderQty) throw Error
```

### 3.4 从跨流关联识别

```text
问题清单：
├─ 哪些业务流之间有金额/数量关系？
├─ 哪些状态变化会触发其他流的变化？
├─ 哪些数据需要跨系统对账？
└─ 哪些场景需要 Saga 补偿？

典型发现：
├─ 订单金额 = 支付金额 + 退款金额
├─ 预占数量 = 出库数量 + 释放数量
├─ 发票金额 = 订单实付 - 已退款
└─ 应收金额 = 付款金额 + 核销金额
```

## 4. 不变量设计原则

### 原则1：识别核心不变量优先

```text
第一优先级（绝对底线）：
├─ 资金不能凭空产生或消失
├─ 库存不能为负
├─ 权限边界不可突破
└─ 历史记录不可覆盖

第二优先级（业务底线）：
├─ 业务量守恒
├─ 状态转换合法
└─ 依赖关系正确

第三优先级（跨流一致）：
├─ 多流金额一致
├─ 多流数量一致
└─ 派生关系正确
```

### 原则2：不变量必须可表达

```text
好的不变量（可验证）：
├─ 累计退款金额 <= 原支付金额
├─ 订单应付 = 明细应付之和
└─ 库存可用 = 总库存 - 已预占 - 已冻结

不好的不变量（模糊）：
├─ "金额要合理"
├─ "库存要够用"
└─ "操作要合规"
```

### 原则3：不变量必须有明确校验时机

```text
校验时机分类：
├─ 事务内：单操作原子性校验
├─ 应用层：跨聚合操作校验
├─ Saga边界：跨系统操作校验
├─ 定时任务：异步对账校验
└─ 人工巡检：定期完整性校验

示例：
├─ 订单创建时：校验应付 = 明细之和（事务内）
├─ 退款申请时：校验累计退款 <= 支付（应用层）
├─ 支付回调时：校验金额一致性（Saga边界）
├─ 日终对账：校验订单金额 = 支付金额（定时任务）
└─ 月末盘点：校验账面库存 = 实际库存（人工巡检）
```

### 原则4：不变量必须有破坏检测

```text
检测方式：
├─ 实时检测：内存中即时校验
├─ 异步检测：后台任务检测
├─ 监控告警：指标异常检测
└─ 人工检测：定期巡检

示例：
├─ 实时：if (balance < 0) throw
├─ 异步：每日对账任务检测金额不一致
├─ 监控：库存为负时发送告警
└─ 人工：每月库存盘点
```

### 原则5：不变量必须有恢复机制

```text
恢复方式：
├─ 自动修复：幂等重试、状态回滚
├─ 人工修复：审批后调整
├─ 补偿修复：反向操作
└─ 数据修复：历史数据修正

示例：
├─ 预占过期：自动释放
├─ 支付失败：自动重试（3次）
├─ 金额差异：人工审批后调整
└─ 历史错误：数据修复工单
```

## 5. 不变量实现模式

### 5.1 模式一：Invariant Guard（不变量守卫）

```text
适用场景：方法入口处的快速校验

实现方式：
function transfer(account, amount) {
  // Invariant Guard
  assert(account.balance >= amount, "余额不足");
  
  // 主逻辑
  account.balance -= amount;
  targetAccount.balance += amount;
}

特点：
├─ 轻量级、无状态
├─ 失败直接抛出异常
├─ 适合单对象、单操作的底线校验
└─ 典型应用：余额检查、权限检查
```

### 5.2 模式二：Precondition Check（前置条件）

```text
适用场景：命令执行前的状态校验

实现方式：
class Order {
  void cancel() {
    // Precondition
    if (this.status != OrderStatus.PENDING) {
      throw new IllegalStateException("只有待处理订单可取消");
    }
    
    // 主逻辑
    this.status = OrderStatus.CANCELLED;
  }
}

特点：
├─ 与领域对象紧密绑定
├─ 校验对象当前状态是否允许某操作
└─ 典型应用：状态机转换校验
```

### 5.3 模式三：Database Constraint（数据库约束）

```text
适用场景：并发环境下的最后防线

实现方式：
-- 余额非负
ALTER TABLE account ADD CONSTRAINT chk_balance 
  CHECK (balance >= 0);

-- 唯一约束防止重复
ALTER TABLE payment ADD CONSTRAINT uk_payment_idempotency 
  UNIQUE (idempotency_key);

-- 外键约束
ALTER TABLE refund ADD CONSTRAINT fk_refund_payment 
  FOREIGN KEY (payment_id) REFERENCES payment(id);

特点：
├─ 数据库层面的硬性保证
├─ 即使应用层bug也能保护
├─ 高并发下可能有性能影响
└─ 典型应用：余额非负、唯一键、外键
```

### 5.4 模式四：Event Sourcing（事件溯源）

```text
适用场景：需要完整审计和重建的状态

实现方式：
class Account {
  List<LedgerEntry> entries = [];
  
  void debit(Money amount) {
    // 计算当前余额
    Money balance = entries.stream()
      .map(LedgerEntry::amount)
      .reduce(Money.ZERO, Money::add);
    
    // 不变量校验
    if (balance.compareTo(amount) < 0) {
      throw new InsufficientBalanceException();
    }
    
    // 追加分录（不可变）
    entries.add(new LedgerEntry(
      LedgerEntryType.DEBIT, 
      amount, 
      LocalDateTime.now()
    ));
  }
  
  Money getBalance() {
    return entries.stream()
      .map(LedgerEntry::amount)
      .reduce(Money.ZERO, Money::add);
  }
}

特点：
├─ 余额由分录计算，不可直接修改
├─ 完整审计日志
├─ 可重建任意时刻状态
└─ 典型应用：资金账、库存账
```

### 5.5 模式五：Optimistic Lock（乐观锁）

```text
适用场景：并发更新时的版本校验

实现方式：
class Inventory {
  @Version
  Long version;
  Integer quantity;
  
  void reserve(Integer amount) {
    // 读取时记录版本
    Inventory snapshot = this.clone();
    
    // 校验不变量
    if (snapshot.quantity < amount) {
      throw new InsufficientInventoryException();
    }
    
    // 尝试更新（版本变化则失败）
    this.quantity -= amount;
    this.version++;
    
    // 数据库校验版本
    int updated = jdbc.update(
      "UPDATE inventory SET quantity=?, version=? WHERE id=? AND version=?",
      this.quantity, this.version, this.id, snapshot.version
    );
    
    if (updated == 0) {
      throw new OptimisticLockException();
    }
  }
}

特点：
├─ 高并发下性能优于悲观锁
├─ 需要重试机制
└─ 典型应用：库存预占、余额扣减
```

### 5.6 模式六：Reservation Pattern（预占模式）

```text
适用场景：资源有限、需要预留的场景

实现方式：
class InventoryReservation {
  Integer totalStock;
  Integer reservedQuantity;
  Integer usedQuantity;
  
  // 不变量
  Integer getAvailable() {
    return totalStock - reservedQuantity - usedQuantity;
  }
  
  void reserve(Integer amount) {
    // 不变量校验
    if (getAvailable() < amount) {
      throw new InsufficientInventoryException();
    }
    
    reservedQuantity += amount;
  }
  
  void confirm(Integer amount) {
    reservedQuantity -= amount;
    usedQuantity += amount;
  }
  
  void release(Integer amount) {
    reservedQuantity -= amount;
  }
}

特点：
├─ 将资源分为：已用、预占、可用
├─ 支持超时自动释放
├─ 典型应用：库存预占、优惠名额
```

### 5.7 模式七：Double Entry（复式记账）

```text
适用场景：需要严格借贷平衡的场景

实现方式：
class DoubleEntryLedger {
  void record(Account debitAccount, Account creditAccount, Money amount) {
    // 借方分录
    ledgerEntries.add(new LedgerEntry(
      LedgerEntryType.DEBIT,
      debitAccount,
      amount
    ));
    
    // 贷方分录
    ledgerEntries.add(new LedgerEntry(
      LedgerEntryType.CREDIT,
      creditAccount,
      amount
    ));
  }
  
  // 不变量：所有借方 = 所有贷方
  boolean isBalanced() {
    Money totalDebit = ledgerEntries.stream()
      .filter(e -> e.type == DEBIT)
      .map(LedgerEntry::amount)
      .reduce(Money.ZERO, Money::add);
      
    Money totalCredit = ledgerEntries.stream()
      .filter(e -> e.type == CREDIT)
      .map(LedgerEntry::amount)
      .reduce(Money.ZERO, Money::add);
      
    return totalDebit.equals(totalCredit);
  }
}

特点：
├─ 每笔交易都有借方和贷方
├─ 自动校验借贷平衡
└─ 典型应用：财务会计、资金流水
```

## 6. 不变量验证体系

### 6.1 单元测试

```text
测试类型：
├─ 正向测试：合法操作通过
├─ 边界测试：临界值校验
├─ 负向测试：非法操作被拒绝
└─ 异常测试：异常情况处理

示例：
@Test
void refundMustNotExceedOriginalPayment() {
  // 准备
  Payment payment = createPayment(1000);
  
  // 操作：尝试退款1200
  assertThrows(RefundExceedsPaymentException.class, () -> {
    refundService.refund(payment, 1200);
  });
}

@Test
void inventoryCannotBeNegative() {
  // 准备
  Inventory inventory = createInventory(10);
  
  // 操作：尝试预占15
  assertThrows(InsufficientInventoryException.class, () -> {
    inventory.reserve(15);
  });
}
```

### 6.2 属性测试（Property-Based Testing）

```text
测试不变量在所有输入下都成立：

示例：
@Test
void orderTotalAlwaysEqualsLineItemsSum() {
  // 生成随机订单
  for (int i = 0; i < 1000; i++) {
    Order order = OrderGenerator.random();
    
    Money lineItemsSum = order.getLineItems().stream()
      .map(LineItem::getSubtotal)
      .reduce(Money.ZERO, Money::add);
    
    assertEquals(lineItemsSum, order.getTotal());
  }
}

@Test
void inventoryAlwaysNonNegative() {
  // 生成随机操作序列
  for (int i = 0; i < 1000; i++) {
    List<InventoryOperation> ops = OperationGenerator.randomSequence();
    Inventory inventory = new Inventory(100);
    
    for (InventoryOperation op : ops) {
      op.execute(inventory);
    }
    
    assertTrue(inventory.getQuantity() >= 0);
  }
}
```

### 6.3 并发测试

```text
测试不变量在高并发下不被破坏：

示例：
@Test
void concurrentReservationsMaintainInventoryInvariant() 
    throws InterruptedException {
  Inventory inventory = new Inventory(100);
  int threadCount = 100;
  int reservationsPerThread = 5;
  
  ExecutorService executor = Executors.newFixedThreadPool(threadCount);
  CountDownLatch latch = new CountDownLatch(threadCount);
  
  for (int i = 0; i < threadCount; i++) {
    executor.submit(() -> {
      try {
        for (int j = 0; j < reservationsPerThread; j++) {
          inventory.reserve(1);
        }
      } finally {
        latch.countDown();
      }
    });
  }
  
  latch.await();
  
  // 验证：库存不能为负
  assertTrue(inventory.getQuantity() >= 0);
  // 验证：预占+已用不超过总量
  assertTrue(
    inventory.getReserved() + inventory.getUsed() <= 100
  );
}
```

### 6.4 对账测试

```text
测试跨流不变量通过对账验证：

示例：
@Test
void orderAmountMatchesPaymentAmount() {
  // 准备测试数据
  Order order = createOrder(1000);
  Payment payment = createPayment(order, 1000);
  
  // 执行操作
  orderService.confirm(order);
  paymentService.capture(payment);
  
  // 对账验证
  ReconciliationResult result = reconciliationService.reconcile(order);
  
  assertEquals(ReconciliationStatus.BALANCED, result.getStatus());
  assertEquals(order.getTotal(), payment.getAmount());
}

@Test
void inventoryMatchesLedger() {
  // 执行一系列库存操作
  inventoryService.reserve(product, 10);
  inventoryService.ship(product, 8);
  inventoryService.release(product, 2);
  
  // 对账验证
  InventoryBalance physicalBalance = inventoryService.getBalance(product);
  LedgerBalance ledgerBalance = ledgerService.getBalance(product);
  
  assertEquals(physicalBalance.getQuantity(), 
               ledgerBalance.getQuantity());
}
```

### 6.5 蜕变测试（Metamorphic Testing）

```text
测试增加无关操作不改变不变量：

示例：
@Test
void addingUnrelatedItemDoesNotChangeTotal() {
  Money originalTotal = order.getTotal();
  
  // 添加无关操作
  order.updateNotes("Some notes");
  order.updateShippingAddress(address);
  order.attachDocument(doc);
  
  // 验证总额不变
  assertEquals(originalTotal, order.getTotal());
}

@Test
void increasingDiscountDoesNotDecreaseTotal() {
  Money originalTotal = order.getTotal();
  
  // 增加优惠额度
  order.increaseDiscount(Money.of(50));
  
  // 验证：应付不能增加
  assertTrue(order.getTotal().compareTo(originalTotal) <= 0);
}
```

## 7. 常见不变量反模式

### 反模式1：把业务规则当作不变量

```text
错误示例：
// 把"满500免运费"当作不变量
if (orderTotal < 500 && shippingFee > 0) {
  throw new InvariantViolation("满500才能免运费");
}

问题：
├─ 这只是经营政策，可以随时调整
├─ 管理员应该有权限例外
└─ 不需要严格的告警和恢复机制

正确做法：
// 作为业务规则，可配置、可例外
if (!policy.isFreeShippingApplicable(order)) {
  throw new ShippingFeeRequiredException();
}
```

### 反模式2：不变量只在测试中验证

```text
错误示例：
// 测试中验证
@Test
void orderTotalMustMatchLineItems() {
  assertEquals(order.getTotal(), 
               order.getLineItems().stream()
                 .map(LineItem::getSubtotal)
                 .reduce(Money.ZERO, Money::add));
}

// 但代码中没有校验！
void addLineItem(Order order, LineItem item) {
  order.getLineItems().add(item);
  // 没有更新 order.total
}

问题：
├─ 测试不能防止运行时破坏
├─ 如果其他代码直接修改total，测试测不到
└─ 边界情况可能被绕过

正确做法：
// 在运行时有Invariant Guard
class Order {
  void addLineItem(LineItem item) {
    this.lineItems.add(item);
    recalculateTotal(); // 自动维护
  }
  
  private void recalculateTotal() {
    this.total = lineItems.stream()
      .map(LineItem::getSubtotal)
      .reduce(Money.ZERO, Money::add);
  }
}
```

### 反模式3：复杂不变量跨越多个系统

```text
错误示例：
// 想维护一个跨5个系统的全局不变量
// "订单金额 = 支付金额 + 退款金额 = 发票金额 = 会计应收"

问题：
├─ 每个系统都可能失败
├─ 网络延迟导致短暂不一致
├─ 分布式事务成本极高
└─ 几乎不可能实时保证

正确做法：
├─ 每个系统维护自己的局部不变量
├─ 通过对账检测全局不一致
├─ 设计合理的容差
└─ 建立差异处理流程
```

### 反模式4：不变量校验在错误时机

```text
错误示例：
// 先查后写，并发下会破坏不变量
Inventory inventory = inventoryRepo.findById(id);
if (inventory.quantity >= amount) {
  // 这个窗口内，其他请求可能已经预占
  inventory.quantity -= amount;
  inventoryRepo.save(inventory);
}

问题：
├─ 并发时两个请求都通过检查
├─ 最终库存可能变成负数
└─ 先查后写是典型的竞态条件

正确做法：
// 数据库条件更新
int updated = jdbc.update(
  "UPDATE inventory SET quantity = quantity - ? 
   WHERE id = ? AND quantity >= ?",
  amount, id, amount
);
if (updated == 0) {
  throw new InsufficientInventoryException();
}
```

### 反模式5：把显示状态当作不变量

```text
错误示例：
// 认为"页面显示正常"意味着数据正确
// 或者用页面状态判断业务状态

问题：
├─ 页面可能缓存了旧数据
├─ 页面可能没刷新
├─ 前端状态可以伪造
└─ 不变量的权威来源应该是领域模型

正确做法：
├─ 业务不变量由领域模型维护
├─ 页面只是领域状态的投影
├─ 服务端才是权威
└─ 不信任客户端输入
```

### 反模式6：不变量过于宽松

```text
错误示例：
// 不变量定义太模糊
invariant "订单金额要合理"
invariant "库存要够用"

问题：
├─ 无法自动化验证
├─ 不同人有不同理解
├─ 无法检测边界情况
└─ 本质上不是不变量

正确做法：
// 精确定义
invariant "订单应付 = 明细应付之和 ± 0.01"
invariant "可用库存 = 总库存 - 已预占 - 已冻结 >= 0"
```
