## 1. 接口契约分析

### 1.1 接口文档分析

**分析方法**：

```
分析步骤：
1. 查看是否有接口文档
2. 核对文档与代码是否一致
3. 检查文档完整性
4. 评估文档可用性
```

**分析维度**：

| 检查项 | 说明 | 良好实践 |
|--------|------|---------|
| 文档存在 | 是否有接口文档 | 必须有 |
| 文档更新 | 文档是否与代码同步 | 变更时更新 |
| 文档格式 | 是否使用 Swagger/OpenAPI | 自动生成 |
| 文档内容 | 是否包含所有必要信息 | 字段说明必须完整 |

**输出模板**：

```
### 接口文档情况

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 文档存在 | ✅/❌ | |
| 文档格式 | Swagger/手工/Markdown | |
| 文档更新 | 同步/滞后/废弃 | |
| 字段说明 | 完整/部分/无 | |
```

### 1.2 URL 规范分析

**分析方法**：

```bash
# 查看后端 Controller 定义
grep -r "@RequestMapping\|@GetMapping\|@PostMapping" src/ --include="*.java"

# 查看前端 API 调用
grep -r "request\.(get\|post\|put\|delete)" src/ --include="*.ts"
```

**分析维度**：

| 检查项 | 说明 | RESTful 规范 |
|--------|------|-------------|
| URL 命名 | 名词复数 | /users, /orders |
| 版本控制 | 是否包含版本 | /v1/users, /v2/users |
| 路径参数 | RESTful 风格 | /users/{id} |
| 查询参数 | GET 参数 | ?page=1&size=10 |

> **REST 规范参考**：新接口建议遵循 REST 规范，已存在接口须结合 §6 综合判定。详细规范见附录 A。

### 1.3 HTTP 方法分析

**分析方法**：

```
检查点：
1. 查询操作是否使用 GET
2. 新增操作是否使用 POST
3. 更新操作是否使用 PUT
4. 删除操作是否使用 DELETE
```

**REST 方法说明（新接口参考，已存在接口须结合 §6 综合判定）**：

```
理想规范（新接口建议遵循）：
GET    /orders        → 查询订单列表
POST   /orders        → 创建订单
PUT    /orders/{id}   → 更新订单
DELETE /orders/{id}   → 删除订单

⚠️ 实际项目可能存在 POST 做查询、GET 做删除等情况，
若已形成调用方约定，不得仅因不符合语义就标记为缺陷，
应按 §6 要求确认消费者依赖、历史兼容和迁移成本。
```

> **详细 REST 规范**：HTTP 方法与资源映射规范见附录 A。

### 1.4 请求参数分析

**分析方法**：

```
分析步骤：
1. 查看前端发送的参数
2. 查看后端接收的参数
3. 对比是否一致
4. 检查必填/可选是否对齐
```

**分析维度**：

| 检查项 | 说明 | 问题示例 |
|--------|------|---------|
| 参数名一致性 | 前后端字段名是否一致 | userId vs user_id |
| 参数类型一致性 | 类型是否匹配 | string vs number |
| 必填一致性 | 必填项是否对齐 | 前端可选，后端必填 |
| 默认值一致性 | 默认值是否一致 | 前端默认0，后端默认null |

**检查清单**：

```
□ 前端传的字段名 = 后端接收的字段名？
□ 参数类型是否一致？（字符串/数字/布尔）
□ 枚举值是否一致？（前端用字符串，后端用数字）
□ 必填项是否一致？
□ 日期格式是否一致？（YYYY-MM-DD vs YYYY-MM-DD HH:mm:ss）
□ 金额单位是否一致？（元 vs 分）
```

### 1.5 响应数据格式分析

**分析方法**：

```
分析步骤：
1. 查看前端如何解析响应
2. 查看后端返回的数据结构
3. 对比是否一致
4. 检查是否有统一格式
```

**分析维度**：

| 检查项 | 说明 | 良好实践 |
|--------|------|---------|
| 统一格式 | 是否有统一响应格式 | Result<T> 包装 |
| 错误码 | 是否有明确的错误码 | 统一的错误码定义 |
| 错误信息 | 错误信息是否友好 | 不暴露内部信息 |
| 分页格式 | 分页数据格式是否统一 | page/rows/total |

**统一响应格式示例**：

```json
// 成功响应
{
  "code": 0,
  "message": "success",
  "data": {
    // 业务数据
  }
}

// 分页响应
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "pagination": {
      "page": 1,
      "pageSize": 10,
      "total": 100
    }
  }
}

// 错误响应
{
  "code": 40001,
  "message": "参数校验失败：用户名不能为空",
  "data": null
}
```

## 2. 数据一致性分析

### 2.1 字段命名一致性

**分析方法**：

```
检查步骤：
1. 列出前端使用的字段名
2. 列出后端使用的字段名
3. 对比是否一致
4. 识别不一致的字段
```

**常见不一致模式**：

```
┌─────────────────────────────────────────────────────────────┐
│                    常见不一致模式                            │
├─────────────────┬───────────────────┬─────────────────────┤
│   驼峰 vs 下划线  │   缩写不一致        │   语义不一致          │
├─────────────────┼───────────────────┼─────────────────────┤
│ userId/user_id  │ orderNo/order_num  │ status vs state     │
│ createTime/ct   │ maxCount/max_num  │ flag vs enable      │
└─────────────────┴───────────────────┴─────────────────────┘

解决方案：
1. 统一规范（全项目使用驼峰或下划线）
2. 序列化配置（JSON序列化时转换）
```

**不一致检查脚本**：

```
前端字段（response.ts）：
interface User {
  userId: string;
  userName: string;
  createTime: string;
}

后端字段（UserVO）：
- userId: string   ✅ 一致
- userName: string  ✅ 一致
- createTime: string  ✅ 一致
```

### 2.2 枚举值一致性

**分析方法**：

```
检查步骤：
1. 查看前端枚举定义
2. 查看后端枚举定义
3. 对比枚举值是否一致
4. 检查枚举描述是否一致
```

**常见枚举不一致**：

```
前端定义：
const StatusEnum = {
  PENDING: '0',
  APPROVED: '1',
  REJECTED: '2'
}

后端定义：
public enum StatusEnum {
  PENDING("1"),      // ❌ 不一致！
  APPROVED("2"),
  REJECTED("3")
}
```

**枚举一致性检查表**：

```
| 枚举名称 | 前端值 | 后端值 | 是否一致 |
|---------|-------|-------|---------|
| 状态-status | '0'=待处理 | 0=待处理 | ✅ |
| 状态-status | '1'=已完成 | 1=处理中 | ❌ 语义不一致 |
| 性别-gender | 1=男 | 1=男 | ✅ |
```

### 2.3 类型一致性

**分析方法**：

```
检查步骤：
1. 查看前端字段类型
2. 查看后端字段类型
3. 对比是否一致
4. 检查 JSON 序列化是否正确
```

**常见类型不一致**：

```
┌─────────────────────────────────────────────────────────────┐
│                    常见类型不一致                              │
├─────────────────┬───────────────────┬─────────────────────┤
│   数字精度问题    │   布尔值问题       │   日期格式问题        │
├─────────────────┼───────────────────┼─────────────────────┤
│ 后端: 0.1       │ 前端: "true"      │ 后端: Date对象       │
│ 前端: 0.1000001 │ 后端: true        │ 前端: "2024-01-01"   │
│ 问题: 显示精度   │ 问题: 解析失败     │ 问题: 格式不一致      │
├─────────────────┴───────────────────┴─────────────────────┤
│ 解决方案：                                                   │
│ - 金额用整数（分）传输，前端展示时转换                         │
│ - 统一布尔值：都用 true/false (JSON原生)                    │
│ - 统一日期格式：ISO 8601 或 YYYY-MM-DD HH:mm:ss             │
└─────────────────────────────────────────────────────────────┘
```

### 2.4 状态同步一致性

**分析方法**：

```
状态同步检查：
1. 操作后状态是否更新？
2. 页面刷新后状态是否正确？
3. 多端登录状态是否同步？
4. 状态变更是否有消息通知？
```

**状态同步检查表**：

```
| 操作 | 预期状态变化 | 前端更新 | 后端更新 | 是否同步 |
|------|------------|---------|---------|---------|
| 创建 | 草稿 | ✅ 更新 | ✅ 更新 | ✅ |
| 提交 | 待审核 | ✅ 更新 | ✅ 更新 | ✅ |
| 审核通过 | 已通过 | ✅ 更新 | ⚠️ 延迟 | ⚠️ |
| 删除 | 已删除 | ❌ 未更新 | ✅ 更新 | ❌ |
```

### 2.5 概念语义一致性分析（强制）

**目的**：防止将枚举名/样式名误当成业务概念，确保前后端对同一字段的业务语义理解一致。

**概念混淆检查表**：

| 字段名 | 前端理解 | 后端实现 | 实际业务语义 | 是否一致 |
|--------|----------|----------|--------------|---------|
| `type` | 类型X | 枚举值A | 用途维度？样式维度？ | ❌/✅ |
| `purpose` | 用途 | PrnJobPurposeEnum | 给谁用 | ✅ |

**语义三角校验**：

| 概念 | 文档语义 | 前端语义 | 后端语义 | 一致性 |
|------|----------|----------|----------|--------|
| CONCEPT-xxx | 声明的业务含义 | 前端对字段的理解 | 后端枚举/逻辑的实际含义 | ✅/❌ |

**常见概念混淆类型**：

| 混淆类型 | 示例 | 后果 |
|----------|------|------|
| 用途维度 × 样式维度 | 将"备注"当成用途而非样式 | 无法表达"加急备注"组合 |
| 状态 × 类型 | 将状态枚举值当成类型 | 无法区分"待处理"和"处理类型" |
| 主键 × 业务分类 | 将 `lid` 当成业务分类字段 | 数据关联错误 |

**分析步骤**：

1. 枚举接口中所有枚举/类型字段
2. 确认每个字段在前端和后端分别代表什么业务概念
3. 追溯源码确认枚举的实际语义
4. 填写概念混淆检查表
5. 识别不一致项并评估影响

## 3. 异常处理一致性分析

### 3.1 HTTP 状态码一致性

**分析方法**：

```
检查点：
1. 前端是否根据 HTTP 状态码做不同处理
2. 后端是否返回正确的 HTTP 状态码
3. 状态码语义是否正确
```

**HTTP 状态码规范**：

```
正确使用：
200 OK                    → 成功
201 Created              → 资源创建成功
204 No Content           → 删除成功（无返回内容）
400 Bad Request          → 参数错误
401 Unauthorized         → 未认证
403 Forbidden            → 无权限
404 Not Found            → 资源不存在
409 Conflict             → 资源冲突（如重复创建）
422 Unprocessable Entity → 业务校验失败
500 Internal Server Error → 服务器错误
```

**常见问题**：

```
❌ 问题示例：
- 所有错误都返回 200 + code=500 → ❌ 违反 HTTP 语义
- 参数错误返回 500 → ❌ 应返回 400
- 未认证返回 200 + code=401 → ❌ 应返回 401

✅ 正确示例：
return ResponseEntity.ok(Result.success());     // 200
return ResponseEntity.status(201).body(id);     // 201
return ResponseEntity.badRequest(Result.fail()); // 400
return ResponseEntity.status(401).build();       // 401
```

### 3.2 错误码体系一致性

**分析目的**：回答"错误码反映什么业务边界、错误码变更如何影响消费者、错误码的业务语义是否一致"，而非"前后端错误码是否对得上"。错误码是系统业务边界的直接表达——每个错误码背后都有一个业务约束。

**分析维度**（每个核心错误码必须回答）：

| # | 问题 | 说明 |
|---|------|------|
| ① | 错误码对应的业务约束是什么？ | 这个错误码反映了什么业务规则被违反？如"库存不足"反映库存约束、"余额不足"反映资金约束 |
| ② | 错误码的消费者有哪些？ | 前端如何展示？是否触发重试？是否触发降级？是否触发补偿流程？ |
| ③ | 错误码变更的兼容性如何？ | 新增/废弃/重命名错误码是否影响前端判断、消息消费、对账脚本？ |
| ④ | 相同错误码在不同上下文中语义是否一致？ | 同一个 code 在不同模块中是否表示相同业务含义？ |
| ⑤ | 错误码是否有统一文档和维护入口？ | 错误码定义在哪里？谁负责维护？变更是否有审批流程？ |

**错误码分析模板**：

```text
## {错误码} 错误码分析

**业务约束**：{错误码} 对应的业务规则
- 触发条件：{什么情况下返回这个错误码}
- 业务含义：{这个错误码反映什么业务边界}

**消费者行为**：
| 消费者 | 行为 | 证据 |
|--------|------|------|
| 前端 | 展示提示："{提示文本}" | {源码位置} |
| 前端 | 触发重试 / 不触发重试 | {源码位置} |
| 前端 | 触发降级 / 不触发降级 | {源码位置} |
| 对账脚本 | 标记为 {对账状态} | {脚本位置} |

**变更记录**：
- v1.0：初始定义
- v2.0：新增 {错误码}
- v2.1：废弃 {错误码}（不再返回，但前端仍保留处理逻辑）

**跨模块一致性**：
| 模块 | 错误码 | 业务含义 | 是否一致 |
|------|--------|---------|---------|
| 用户模块 | 1001001 | 用户不存在 | ✅ |
| 订单模块 | 1001001 | 用户不存在 | ❌ 订单模块应使用自己的错误码前缀 |
```

**错误码体系设计**：

```
推荐格式：模块(2位) + 错误类型(2位) + 序号(3位)

示例：
1001xxx - 用户模块
├── 1001001 - 用户不存在
├── 1001002 - 用户已存在
├── 1002001 - 密码错误
├── 1002002 - Token 过期
└── 1002003 - Token 无效

2001xxx - 订单模块
├── 2001001 - 订单不存在
├── 2001002 - 订单状态不允许操作
└── 2001003 - 库存不足
```

**错误码一致性检查表**：

```
| 错误场景 | 前端判断 | 后端返回 | 是否一致 |
|---------|---------|---------|---------|
| 用户不存在 | code === 1001001 | code = 1001001 | ✅ |
| 订单不存在 | code === 2001001 | code = 2001001 | ✅ |
| 库存不足 | message 包含 "库存" | message = "库存不足" | ⚠️ |
```

**禁止行为**：
- ❌ 只检查前后端错误码是否对得上，不分析错误码对应的业务约束
- ❌ 忽略错误码变更对消费者的影响（前端可能因错误码变化而判断错误）
- ❌ 把不同模块中同名错误码直接当作同一语义
- ❌ 不记录错误码的业务含义（只看数字无法判断业务约束）

**退出条件**：每个核心错误码都有"业务约束"和"消费者行为"描述；跨模块不一致项已登记；错误码变更的兼容性已检查。

**分析结论的流向**：错误码分析输出应输入到 §3.3 错误提示一致性（验证前端提示是否准确反映业务约束），以及 §3.4 重试机制一致性（验证错误码是否触发正确的重试行为）。发现错误码反映的业务约束与前端提示不一致时，应联动 §2.5 概念语义一致性分析。

### 3.3 错误提示一致性

**分析方法**：

```
检查步骤：
1. 查看前端错误提示
2. 查看后端错误提示
3. 对比是否一致
4. 检查是否友好
```

|------|---------|---------|---------|

| 库存不足 | "库存不足" | ✅ 友好 | |
| 系统错误 | "Internal Server Error" | ❌ 技术错误 | 需优化：友好提示 |

### 5.1 问题分类

```
问题分类：

接口契约问题：

异常处理问题：
├── [ ] HTTP 状态码不正确

├── [ ] 异常信息泄露
└── [ ] 重试机制不一致

性能问题：
├── [ ] 请求超时配置不一致
├── [ ] 分页实现不一致
├── [ ] 缓存策略不一致
└── [ ] 数据量未限制
```

### 5.2 问题优先级

```
P0 问题（必须修复）：
├── [ ] 接口不通（功能完全不可用）
├── [ ] 严重数据不一致（导致业务错误）
├── [ ] 安全漏洞（权限绕过、数据泄露）
└── [ ] 接口文档缺失（严重影响对接）

P1 问题（尽快修复）：
├── [ ] 参数校验不一致（容易出 bug）
├── [ ] 错误码不完整（难以排查问题）
├── [ ] HTTP 状态码错误（违反规范）
└── [ ] 响应格式不统一（解析困难）

P2 问题（计划修复）：
├── [ ] 错误提示不友好（影响排查但可降级使用）
├── [ ] 冗余字段或过时字段未清理（增大维护成本）
├── [ ] 文档与实现轻微不同步（有默认行为兜底）
└── [ ] 性能/容量隐患（大数据量下响应变慢）

> **关于 REST 规范问题**：URL/方法不符合 REST 风格（如 POST 做查询）是否需要修复，必须按 §6 要求先确认调用方依赖、网关行为、历史兼容和迁移成本。已形成稳定约定的接口不应仅因不符合 REST 语义就标记为缺陷。
```

> **关于优先级符号**：本节 P0/P1/P2 指问题修复优先级（等同 SEV-P0~P2），与 L1 的 SC-P* 切片深度分级无关；修复顺序还应结合影响面、暴露频率、可检测性、可逆性和迁移成本综合判断，不机械按上述示例归类。

## 6. SOP-00 v3.0 强制执行门禁

> 本章是对前述基础检查项的增量补强。执行时以 SOP-00 v3.7、`研发方法/业务系统分析-认知真源.md` v2.0、文档 20 和文档 21 的“问题驱动、业务切片、螺旋验证、证据闭环”为总约束；若前述 REST 示例、字段对照或经验建议与项目既有规范、历史兼容契约或本章冲突，以事实证据和上位约束为准。不得因 URL 不够“标准”、查询使用 POST 或成功响应统一为 200 就直接判定为缺陷，必须先确认文档约定、调用方依赖、网关行为、安全要求和迁移成本。

### 6.1 分析任务书与基线

开始分析前至少记录：决策问题、范围内/范围外、关键业务切片、前后端仓库及提交、部署版本、网关与配置版本、环境、采样时间窗口、客户端版本范围、租户/组织范围、证据访问权限、脱敏要求、停止条件。未建立版本和环境基线时，只能输出探索性发现，不能宣称“前后端一致”或“生产不存在该问题”。

优先选择资金、库存、订单状态、权限、租户隔离、文件导出、不可逆操作、调用频繁、事故多发或近期将变更的接口；长尾接口可分层采样，但要说明样本框与覆盖缺口。

### 6.2 三层契约必须分开分析

| 契约层 | 回答的问题 | 典型证据 | 常见误区 |
|---|---|---|---|
| 文档契约 | 团队和外部消费者被承诺了什么 | OpenAPI/Swagger、JSON Schema、接口文档、SDK 文档、ADR、变更公告 | 把过期文档当成当前事实 |
| 代码契约 | 当前源码允许、校验、序列化和消费什么 | 前端类型与调用封装、网关规则、Controller、DTO/VO、校验器、序列化配置、异常映射、测试 | 只比较 DTO 字段名，忽略消费逻辑和运行配置 |
| 运行契约 | 特定版本、环境和流量中实际发生什么 | 抓包、脱敏日志、Trace、网关指标、实际响应样本、客户端版本分布、可复现实验 | 用单个成功样本外推全部接口和全部客户端 |

三层一致不能靠单一来源证明。发现文档、代码、运行行为不一致时，建立矛盾项，先核对部署提交、灰度范围、功能开关、网关改写、序列化配置、历史客户端和旁路入口；不得自行选一层覆盖其他证据。每个结论标注证据 ID、版本/环境、采集时间、适用范围、确定性和验证状态。

### 6.3 接口清单与契约矩阵

每个关键接口建立稳定 `API-ID`，同一业务动作的预检、提交、查询、撤销、导入导出、回调和轮询应关联到同一业务切片。最小契约矩阵如下：

| API-ID | 场景/消费点 | URL/方法/媒体类型 | 成功及失败状态码 | 认证/授权 | 租户/组织上下文 | 请求 Schema | 响应 Schema | 幂等/并发 | 版本/客户端 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|
| API-001 | 页面/组件/事件/任务 | 含网关前缀 | HTTP + 业务码 | 身份与权限点 | 来源、透传、校验 | 字段语义而非仅名称 | 包装、分页、错误体 | 键、版本号 | 当前/历史/灰度 | E-CON/E-SRC/E-RUN |

检查 URL 时同时覆盖域名与环境、网关/反向代理前缀、baseURL 拼接、路径参数编码、尾斜杠、大小写、版本前缀和重定向。检查方法时关注安全性、幂等性、缓存、预检、请求体及网关支持，不机械套用 REST。检查状态码时列出成功、校验失败、未认证、无权、跨租户、资源不存在、冲突、限流、超时、上游失败和服务异常，确认前端拦截器不会把业务失败当成功或把可恢复错误统一跳转登录。

### 6.4 从消费点贯通到数据与副作用

不得从 Controller 和 DTO 开始后就停止。每个关键切片至少追踪：

```text
用户/角色与业务目标
  → 页面、组件、路由守卫、事件处理器、请求封装、状态管理/缓存
  → CDN/BFF/网关/鉴权过滤器/路由与协议转换
  → Controller/Resolver/消息或下载入口
  → 参数绑定、校验、授权、租户与组织作用域
  → 应用服务、领域规则、事务与状态机
  → 数据库/缓存/搜索索引/对象存储的读写与权威源
  → MQ、第三方、通知、审计、对账等外部副作用
  → 响应组装、前端解析、缓存更新、页面状态和用户反馈
  → 日志、Trace、指标、告警与补偿入口
```

追踪时记录静态调用链和实际运行链。静态搜索不到调用方不能证明“无人使用”；还需检查动态路由、反射、配置化 URL、共享 SDK、脚本、定时任务、移动端、小程序、外部客户和历史安装包。副作用必须分析成功、失败、部分成功、重复和超时后的可见结果。

## 7. 字段之外的完整契约语义

### 7.1 请求与响应 Schema

对照对象层级、字段路径、JSON 类型、格式、长度/范围、正则、集合元素、唯一性、互斥/联动条件、只读/只写字段、未知字段策略、默认值、序列化命名、数字字符串、大整数精度和错误定位。前端 TypeScript 类型只能证明编译期意图，不能替代运行校验；后端 DTO 也不能代表网关、转换层、数据库和实际响应。

必须区分以下语义，不得混为一谈：

| 输入/输出形态 | 可能语义 | 必查项 |
|---|---|---|
| 字段缺省 | 未修改、采用默认、客户端版本过旧 | 创建与更新是否不同；反序列化后能否保留“未提供”信息 |
| `null` | 显式清空、未知、不适用、无值 | 后端是否允许；是否会覆盖旧值；响应是否稳定保留 |
| 空字符串 `""` | 用户清空、无内容、非法占位 | 是否 trim；是否转 null；校验和数据库约束是否一致 |
| 空集合 `[]`/`{}` | 明确清空集合、当前无结果 | 与缺省、null 的更新语义是否不同 |
| 可选字段 | 可不传但传入时受约束 | 文档、前端表单、后端校验、存储约束是否一致 |
| 默认值 | 客户端、服务端或数据库补值 | 谁是权威补值方；旧客户端是否得到相同行为 |

更新接口特别检查全量替换、部分更新、表单脏字段和后端复制工具，避免缺省字段被误清空，或显式 null 无法清空。

### 7.2 专项语义矩阵

| 专项 | 必须确认 | 典型验证 |
|---|---|---|
| 金额与比例 | 币种、元/分等单位、含税/未税、精度、舍入模式、负数、上限、序列化是否用字符串或整数最小单位 | 边界金额、累计误差、前后端各自计算与数据库落值对账；禁止用二进制浮点推断精确金额 |
| 时间与时区 | 时间点/本地日期/营业日/时长的语义，格式、精度、时区、夏令时、服务端和数据库时区 | 跨日、月末、闰日、夏令时、客户端时区变化、历史数据无时区样本 |
| 枚举 | API 和数据库传稳定 `code`，不得依赖展示文案或常量名；未知 code、废弃 code、组合值如何处理 | 当前、未知、废弃、灰度新增 code；旧客户端应可降级而非崩溃或误判 |
| 布尔与开关 | true/false、0/1、字符串及 null 的含义，三态开关是否存在 | 序列化、表单控件、数据库默认值和旧数据样本 |
| ID 与数字 | 长整型是否超过 JavaScript 安全整数，前导零是否有意义，ID 能否被当数值运算 | 大 ID、字符串 ID、路径与 JSON 双通道 |
| 分页 | 页码起点、page/size/cursor、默认与最大值、total 含义、空页和数据变化 | 首尾页、越界页、游标过期、并发插入/删除 |
| 排序 | 字段白名单、升降序、null 顺序、稳定次排序、区域规则 | 重复主排序值、非法字段、分页跨页重复/遗漏 |
| 过滤/搜索 | 操作符、大小写、模糊规则、空值、时区边界、组合条件、权限过滤顺序 | 空条件、非法操作符、跨租户条件注入、前后端编码差异 |
| 文件上传 | multipart 字段名、单个/多个、大小、类型、扩展名与内容检测、摘要、断点续传、病毒扫描、对象级授权 | 空文件、超限、伪装类型、同名、重复、部分上传、取消和重试 |
| 文件下载 | Content-Type、Content-Disposition、UTF-8 文件名、长度、流式/范围请求、错误体与二进制区分、授权和审计 | 中文名、大文件、断流、过期链接、跨租户对象、错误 JSON 被保存成文件 |

### 7.3 认证、授权、租户与组织上下文

逐项追踪 token/cookie/session/API key 的获取、存储、刷新、注销和失效；区分 `401 未认证`、`403 已认证但无权` 与业务对象不可见。不能只验证菜单/按钮隐藏，后端必须在对象和数据查询层执行授权。

租户、组织、门店、项目、数据域等上下文需确认：来源是身份声明、服务端会话、可信网关头还是请求参数；在哪一层校验和透传；异步任务、导入导出、缓存键、对象存储路径、日志和消息是否携带；客户端传入的 tenant/org ID 能否覆盖可信上下文。至少验证同租户不同组织、不同租户同 ID、越权读取/修改/删除/下载、批量接口漏检和推测 ID 等反例。任何跨租户动态验证必须获得授权并使用隔离测试数据。

### 7.4 错误码、重试与恢复语义

HTTP 状态、业务错误码、机器可读详情、用户提示和 Trace/Request ID 分层记录。前端不得依赖错误 message 文本分支；后端不得暴露堆栈、SQL、内部地址或敏感字段。明确哪些错误可重试、由哪一层重试、最大次数、退避与抖动、总超时预算、`Retry-After`、熔断和取消传播。

查询重试也要考虑负载与一致性；写请求只有在幂等契约成立时才能自动重试。防止浏览器、请求库、网关、服务和消息消费者叠加重试形成放大。验证超时但服务端已成功、客户端取消但副作用继续、部分副作用成功和补偿失败等不确定结果。

### 7.5 幂等键、并发更新与缓存一致性

| 主题 | 必须确认 | 失败模式/验证 |
|---|---|---|
| 幂等键 | 生成方、作用域、唯一性、请求摘要绑定、保存位置、TTL、成功/失败响应复用、并发首请求 | 同键同请求、同键不同请求、并发重复、超时重放、TTL 后重放；仅“先查再写”通常有竞态 |
| 并发更新 | 乐观锁版本/ETag、条件更新、悲观锁、状态机前置条件、冲突码和前端合并/刷新策略 | 两端同时编辑、重复点击、乱序响应、审核与撤销竞争；禁止静默覆盖未知新版本 |
| 缓存一致性 | 数据权威源、前端/Service Worker/CDN/网关/后端缓存键、租户维度、TTL、失效/更新顺序、读写一致性 | 更新后读旧值、负缓存、并发回填、删除后复活、灰度版本混用、敏感响应被共享缓存 |

缓存命中快不代表数据正确。写后刷新、失效消息或版本化缓存必须有失败处理；页面局部乐观更新失败时要能回滚，并避免旧请求晚到覆盖新状态。

## 8. 版本化与兼容性分析

### 8.1 兼容方向

- **向后兼容**：新服务能否继续服务旧 Web 包、移动端、POS、小程序、外部集成和长期离线客户端。
- **向前兼容**：旧服务或旧客户端遇到新字段、新枚举、新消息形态时能否忽略、降级或明确失败，而不是误解释。
- **数据兼容**：新代码能否读取历史缺省/null/旧枚举/旧时区数据；回滚后的旧代码能否读取新版本写入的数据。

新增可选字段通常比删除、重命名、改类型安全，但仍要验证默认语义、未知字段策略、签名摘要和旧客户端反序列化行为。响应字段删除、可选改必填、精度/单位改变、枚举 code 复用、排序默认值改变、错误码语义改变和认证上下文改变均视为潜在破坏性变更。

### 8.2 版本与灰度矩阵

| 服务端版本/灰度组 | 客户端版本 | 契约版本 | 功能开关 | 预期行为 | 实测证据 | 回滚可读性 |
|---|---|---|---|---|---|---|
| 新/旧 | Web/移动/POS/外部 | URL/Header/媒体类型 | 开/关 | 成功/降级/拒绝 | E-RUN-* | 是/否/未知 |

检查 URL、Header、媒体类型、能力协商或字段级版本策略；版本规则应可观测、可弃用并有生命周期。灰度期间同时验证“新前端→新后端、新前端→旧后端、旧前端→新后端、旧前端→旧后端”中实际可能出现的组合。统计历史客户端活跃分布和关键调用，不以“已经发布新前端”推断旧客户端消失。

发布计划应包含兼容窗口、双读/双写或适配层、流量比例、监控指标、停止条件、数据迁移顺序、回滚触发器。数据库或缓存一旦写入旧版本不可理解的形态，代码回滚不等于业务可回滚。

## 9. OpenAPI、契约测试与实际流量互证

### 9.1 静态契约验证

1. 对 OpenAPI/JSON Schema 执行语法和引用校验，识别遗漏接口、宽泛 `object`、错误 required/nullable、无约束枚举和未声明错误响应。
2. 将文档与网关路由、后端入口、序列化/校验配置、前端类型及消费代码比较；生成代码只能作为证据，不能替代消费逻辑核对。
3. 建立消费者驱动或提供方契约测试，覆盖成功与错误响应、认证/授权、租户上下文、null/缺省、金额、时间、枚举、分页、文件、幂等和并发冲突。
4. 契约 diff 纳入变更检查，破坏性变化必须有显式审批、版本策略、迁移和回滚方案。

### 9.2 动态互证

在授权环境使用脱敏抓包、网关日志、Trace 和可复现实验，按客户端版本、租户/组织、接口、状态码和时间窗口分层采样。关键切片至少按适用性覆盖：正常、边界、失败、重复、并发、超时、撤销/补偿、跨日/时区、历史数据、灰度和旧客户端。

| 对照结果 | 处理方式 |
|---|---|
| 文档、代码、流量一致 | 记录适用版本、环境、窗口和覆盖度，仍不外推未采样场景 |
| 文档与代码一致、流量不同 | 优先排查部署版本、网关改写、功能开关、旁路服务和灰度 |
| 代码与流量一致、文档不同 | 记录文档债务及对外承诺风险，不能直接修改文档掩盖兼容问题 |
| 文档与流量一致、代码不同 | 排查当前仓库/分支是否为部署源、生成代码和运行时增强 |
| 无实际流量 | 只能说明观测窗口未出现；查客户端清单、历史日志和业务周期，不能断言无人调用 |

流量样本必须最小化采集并脱敏，禁止保存 token、cookie、密钥、完整身份证件、银行卡、支付凭证和不必要的跨租户数据。生产原则上只读观察；写入、并发、重试、越权和故障实验必须在隔离环境或获得明确授权后执行。

## 10. 敏感数据与越权专项

- 建立字段级敏感数据清单，检查请求、响应、URL、Referer、埋点、日志、Trace、缓存、导出文件、错误消息和第三方调用中的暴露与保留周期。
- 检查传输加密、凭据存储、刷新 token 轮换、CSRF/CORS、下载签名 URL、响应缓存头和前端持久化；不得把长期凭据或高敏数据无必要写入 localStorage。
- 验证功能权限、对象级权限、字段级权限和数据范围权限，尤其是详情、批量、导出、搜索、自动补全、统计、文件和异步任务。
- 防止前端提交只读字段或批量赋值改变 owner、tenant、org、role、price、status 等受控属性；后端应使用允许列表和服务端可信上下文。
- 错误场景也要脱敏，并确认 `404`/`403` 策略不会泄露对象是否存在。安全证据保留最小复现，不在共享报告写可直接滥用的细节。

## 12. 完成判据与 AI 约束

### 12.1 完成判据

- [ ] 已明确决策问题、范围、版本/环境、客户端与采样窗口。
- [ ] P0/P1 业务切片已从前端消费点贯通到后端入口、数据读写、外部副作用和运行观测。
- [ ] 文档、代码、运行三层契约已分别取证；未解释的强矛盾为零。
- [ ] URL/方法/状态码、认证授权、租户/组织、Schema 与 null/缺省语义均已检查。
- [ ] 金额、时间时区、枚举 code、分页排序过滤、文件、错误重试、幂等、并发和缓存等适用专项已检查；跳过项有理由。
- [ ] 当前、灰度和历史客户端的向后/向前兼容已形成矩阵，迁移与回滚可执行。
- [ ] OpenAPI/Schema、契约测试、源码和实际流量已互证；无法取得运行证据的结论已降级并登记未知项。
- [ ] 敏感数据、对象级越权、租户隔离和批量/导出旁路已验证或明确限制。
- [ ] 高影响问题有证据、根因层级、替代方案、验证标准、观测指标和回滚方案。
- [ ] 另一位分析者可依据证据索引与复现步骤复核关键结论；新增分析的信息价值已低于成本。

### 12.2 AI 辅助分析约束

1. 不得只比较 DTO/VO/TypeScript 字段名后宣称契约一致；必须分析业务语义、校验、序列化、消费分支、权限、数据与运行行为。
2. 不因类名、字段名、注释、OpenAPI 或“常见 REST 做法”直接推断事实；区分现状事实、规范建议和目标设计。
3. 不因静态搜索无结果或采样窗口无流量就断言无人使用；动态路由、配置、SDK、脚本、任务、外部系统和历史客户端均可能形成依赖。
4. 不伪造抓包、日志、Trace、客户端分布或测试结果。无法访问时标记证据缺口，并提出最小、可区分候选解释的验证动作。
5. 不自行执行生产写操作、并发压测、越权探测、故障注入或敏感数据导出；生产默认只读、最小权限和最小采集。
6. 不为追求“规范化”直接破坏既有 URL、POST 约定、状态码包装、枚举 code 或错误码；先识别消费者、兼容窗口、适配层、灰度和回滚。
7. 输出结论必须携带范围、版本/环境、证据 ID、确定性、反证和未知项；建议必须给出替代方案及不处理后果。

## 附录 A：RESTful API 设计规范参考

> **⚠️ 重要性质说明**：本附录仅为新接口设计提供参考规范。**已存在接口是否符合 REST 风格，必须按 §6 要求综合判定**，不得仅因不符合本附录就标记为缺陷。

### A.1 核心原则

| 原则 | 说明 |
|------|------|
| 资源导向 | URL 表示资源（名词），用 HTTP 方法表达动作 |
| 无状态 | 每个请求自带所有必要信息 |
| 统一接口 | GET 查、POST 创、PUT 全量改、PATCH 部分改、DELETE 删 |
| 分层系统 | 客户端不需知道后端架构细节 |

### A.2 常用状态码

| 状态码 | 含义 | 典型场景 |
|--------|------|----------|
| 200 | 成功 | 正常响应 |
| 201 | 创建成功 | POST 创建资源 |
| 204 | 无内容 | DELETE 成功无返回 |
| 400 | 参数错误 | 校验失败 |
| 401/403 | 未认证/无权限 | 鉴权问题 |
| 404 | 资源不存在 | ID 不存在 |
| 409 | 资源冲突 | 重复创建 |
| 422 | 业务校验失败 | 规则校验不通过 |
| 429 | 限流 | 请求过多 |
| 500 | 服务器错误 | 非业务异常 |

### A.3 详细规范

完整规范（URL 命名、HTTP 方法映射、版本控制、错误响应格式、分页格式、兼容性注意事项）参考团队内部 REST API 设计规范文档（若未提供，按 §6.2 三层契约分析实际约定，不以外部模板代替项目事实）。
