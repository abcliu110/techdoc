## 0. 文档概述

### 0.1 目的

本方法论指导如何对复杂既有系统（Legacy System）进行系统性拆解与架构分析。涵盖业务维度、技术维度、架构维度的完整分析框架，帮助团队在接手遗留系统、重构改造、技术迁移等场景中建立全面认知，避免盲人摸象式的局部理解。

### 0.2 适用范围

| 适用场景 | 不适用场景 |
|---|---|
| 新团队接手遗留系统 | 全新系统从零设计 |
| 微服务化改造前期分析 | 系统边界已完全清晰 |
| 技术栈升级/迁移评估 | 技术选型尚未确定 |
| 系统重构可行性分析 | 只需要局部功能理解 |
| 并购系统整合评估 | 单一模块小改动 |

### 0.3 最小输入

| 输入类型 | 说明 |
|---|---|
| 系统访问权限 | 代码仓库、数据库、监控、日志、文档 |
| 知情人访谈机会 | 老员工、运维、业务方 |
| 足够的时间窗口 | 中型系统至少 2 周深入分析 |

### 0.4 启动位置

阅读第 1 章先定义本次分析要支持的决策、边界、风险容忍度和停止条件。执行时不要把第 2-5 章机械地串成一次性瀑布流程，而应选择少量关键业务切片，在业务、代码、数据、运行时和部署视图之间往返验证；第 4A 章用于所有涉及跨库、跨服务、消息或外部副作用的切片。最后在第 6 章汇总结论、未知项、候选方案和决策建议。

> 维度对应：第 2 章业务维度、第 3 章代码与技术框架、第 4 章技术栈、第 4A 章一致性专项、第 5 章架构视图。业务语义是技术分析的锚点，但业务理解本身也必须接受代码、数据和运行行为的反向校验。

### 0.5 证据、结论与置信度模型（贯穿全文）

证据来源、证据质量、结论确定性和验证状态是四个不同维度，不得再用一套 `L1-L5` 同时表示“来源”和“可信度”。每条重要结论先登记证据，再记录推理链和反证情况。

#### 0.5.1 证据类型

| 代码 | 类型 | 典型来源 | 主要局限 |
|---|---|---|---|
| SRC | 源码与测试 | 代码、SQL、测试、构建描述 | 可能未部署、未被执行或已失效 |
| CFG | 配置与部署 | 配置中心、环境变量、部署清单 | 环境之间可能不同 |
| DAT | 数据事实 | Schema、脱敏样本、历史分布、审计记录 | 样本可能有偏，字段名不等于业务语义 |
| RUN | 运行行为 | 日志、指标、Trace、抓包、可复现实验 | 只代表观测窗口和实际流量 |
| CON | 调用方与契约 | OpenAPI、消息 Schema、消费者代码、外部查询 | 调用方清单可能不完整 |
| DOC | 文档与决策记录 | PRD、手册、ADR、事故报告 | 可能过时或只表达设计意图 |
| HUM | 人员知识 | 业务、开发、运维、客服访谈 | 受记忆、角色和局部视角影响 |

#### 0.5.2 证据质量属性

每份关键证据至少评价以下属性，使用“高/中/低/未知”，不计算没有统计意义的平均分：

| 属性 | 判断问题 |
|---|---|
| 直接性 | 它直接观察到结论，还是经过多层推导？ |
| 时效性 | 它是否对应当前版本、当前环境和有效业务周期？ |
| 覆盖度 | 是全量、分层样本，还是单个偶发案例？ |
| 可复现性 | 另一位分析者能否按步骤得到相同结果？ |
| 独立性 | 多份证据是否真正独立，而非都引用同一来源？ |

#### 0.5.3 结论确定性

| 标记 | 定义 | 可否直接支持决策 |
|---|---|---|
| 直接事实 | 源码、数据、当前配置、运行观测或可复现实验直接表明 | 可，但必须写明适用范围和时间窗口 |
| 交叉验证结论 | 至少两类独立证据相互印证，且不存在未解释的强反证 | 可 |
| 经验判断 | 依据常见实践或专家经验，结论依赖场景 | 不可单独支持高影响决策 |
| 推断 | 由已知证据推出，推理链明确但仍有缺口 | 只能支持下一步调查或可逆实验 |
| 假设 | 尚未获得足够证据的待验证解释 | 不可作为事实、根因或最终建议 |

#### 0.5.4 验证状态

`未验证 → 部分验证 → 交叉验证 → 已反证`。被反证的结论不得删除，应保留在假设台账中并记录反证，防止团队重复走同一条错误路径。

**强制要求**：

- 关键结论使用稳定 ID，并关联证据 ID，例如：`C-012（交叉验证结论）← E-RUN-08 + E-SRC-17`。
- 证据必须带版本/环境、采集时间、查询或复现步骤、脱敏状态和适用范围。
- 访谈可以直接证明“某角色持有该认知”，不能单独证明系统实际行为或兼容契约。
- 风险、ADR 和不可逆决策必须具有直接事实或交叉验证结论；证据不足时只能形成待验证项或可逆实验。
- 代码不是天然最高事实：源码、部署版本、配置、数据和运行行为不一致时，先登记矛盾并查明原因。

### 0.6 知识脱敏与访问边界

分析过程中产生的日志、响应、报告、截图、差异样本在落盘或交付前必须完成脱敏，并遵守访问边界与保留要求：

- 敏感字段（手机号、身份证、银行卡、支付凭证、token、密钥）须脱敏为保留前 3 后 4 的掩码或哈希摘要。
- 禁止序列化完整请求/响应对象到分析产物；如需保留样本，须替换为脱敏后的最小必要片段。
- 产出的数据样本、ER 图、差异数据须按知情人授权范围留存，不得越权带离租户或项目工作区。
- 分析报告交付外部（如审计、并购方）前，须经知情人或安全负责人确认脱敏充分性。

## 1. 分析准备

### 1.1 前置 Checklist

在开始实质性分析前，逐项确认以下条件：

```
□ 获得代码仓库只读访问
□ 获得数据库只读访问（Schema 分析用）
□ 获得生产/测试环境日志访问
□ 获得监控/链路追踪系统访问（如有）
□ 识别关键知情人：原架构师、核心开发、运维、业务负责人
□ 明确分析目标：是为了重构？迁移？接手维护？找问题根因？
```

### 1.2 分析目标对齐

与利益相关方（Stakeholder）对齐分析范围和产出期望：

| 关键问题 | 需要回答 |
|---|---|
| 分析目的 | 重构？迁移？接手维护？找根因？ |
| 分析边界 | 全系统还是特定模块？ |
| 深度要求 | 概要了解还是需要可执行的设计决策？ |
| 时间约束 | 何时需要产出？ |
| 决策影响 | 分析结论将影响哪些重大决策？ |
| 决策时点 | 何时必须作出决定？哪些信息可以延后获得？ |
| 风险容忍度 | 哪些错误结论不可接受？哪些可以通过可逆实验纠正？ |
| 成功与停止条件 | 什么证据足以支持当前决策？何时停止继续分析？ |

形成一页“分析任务书”，至少包含：决策问题、决策负责人、范围内/范围外、关键业务切片、可用证据、重要未知项、风险容忍度、交付时间和停止条件。

**完成判据**：以上内容有书面记录；真正承担决策后果的负责人确认，而不是笼统要求“所有干系人一致”。

### 1.4 分析方法论总览

本方法论采用“决策驱动 + 业务切片 + 黑箱/灰箱/白箱 + 假设检验”的螺旋式逆向工程：

```text
决策问题
  → 初步系统地图与证据盘点
  → 假设、矛盾和未知项台账
  → 选择高价值/高风险业务切片
  → 黑箱观察输入输出与角色任务
  → 灰箱追踪运行链路、数据和依赖
  → 白箱解释代码、配置与事务机制
  → 领域语义、不变量和失败模式建模
  → 反例、历史样本和知情人交叉验证
  → 风险、候选方案和决策建议
  → 仍不充分则选择下一切片继续迭代
```

每个业务切片必须尽量形成端到端追踪链：

```text
业务目标 → 角色任务 → 用例/场景 → API/页面/消息/任务
         → 应用服务 → 领域规则/状态 → 数据读写
         → 外部副作用 → 指标/审计/对账 → 测试与证据
```

#### 1.4.1 三种观察模式

| 模式 | 首要问题 | 典型动作 | 防止的偏差 |
|---|---|---|---|
| 黑箱 | 使用者看到什么行为和结果？ | 试用、抓包、观察角色任务和异常提示 | 被代码结构误导业务理解 |
| 灰箱 | 请求、事件和数据实际如何流动？ | Trace、日志关联、SQL/MQ/任务追踪 | 只看静态调用图 |
| 白箱 | 机制为何产生该行为？ | 阅读代码、配置、事务和部署实现 | 把相关性误当因果 |

#### 1.4.2 假设与矛盾台账

| 字段 | 说明 |
|---|---|
| 假设/矛盾 ID | 稳定编号，便于报告引用 |
| 观察 | 不掺解释的原始事实 |
| 当前解释 | 推断或候选原因，不得伪装成事实 |
| 支持/反对证据 | 关联证据 ID |
| 区分性验证 | 能区分候选解释的最小验证动作 |
| 状态 | 未验证/部分验证/交叉验证/已反证 |
| 决策影响 | 若不验证，会影响什么决定 |

#### 1.4.3 风险驱动的切片与采样

不追求平均地阅读所有代码。按业务关键性、调用频率、金额/数据影响、变化频率、事故历史、合规要求和证据缺口选择切片。样本至少覆盖正常、边界、失败、重复、并发、撤销/冲正、跨日/时区、历史数据和人工补偿；不适用项须说明原因。

对长尾功能采用分层采样，并明确总体、样本框和覆盖缺口。核心营收、资金、权限、租户、库存和不可逆数据操作不得仅依赖抽样结论。

#### 1.4.4 分析停止条件

满足以下条件时可停止本轮，而不是以“读完全部代码”为标准：

- 决策问题已有足够直接事实或交叉验证结论支撑。
- 关键业务切片的语义、机制、不变量、主要失败模式和依赖已经贯通。
- 未知项已登记，且不会改变当前决策，或已有隔离、回滚、监控和验证计划。
- 新增分析的预期信息价值低于时间成本；继续分析不会明显改变方案排序。
- 最可能挑战当前结论的反例已经检查，未解释的强反证为零。

## 2. 业务维度分析

### 2.1 分析目标

建立对系统“为何存在、为谁创造什么结果、通过什么语义与控制机制实现”的认知。业务分析不能停留在菜单、接口、表和功能清单，必须覆盖价值、角色、领域语义、对象生命周期、规则、不变量、异常补偿、指标口径和责任边界。

#### 2.1.1 业务分析基础结构

下图表达业务分析对象之间的静态关系；第 1.4 节表达分析工作的动态执行流程。两者用途不同，应同时保留：

```text
                           ┌─────────────────┐
                           │   业务能力地图   │  ← 顶层抽象
                           └────────┬────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
     ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
     │    核心流程    │    │    数据实体    │    │    业务规则    │
     │  （任务-状态） │    │  （对象-关系） │    │  （约束-校验） │
     └────────────────┘    └────────────────┘    └────────────────┘
              │                     │                     │
              └─────────────────────┼─────────────────────┘
                                    ▼
                           ┌─────────────────┐
                           │   系统功能清单   │  ← 可验证基准
                           └─────────────────┘
```

该图是最小骨架，不是业务分析的全部。价值与结果、角色责任、领域语义、不变量、异常补偿、指标口径和兼容契约作为纵向约束贯穿能力、流程、实体、规则和系统实现，后续小节分别展开。

### 2.2 核心问题清单

在开始分析前，必须回答以下核心问题：

| # | 核心问题 | 回答来源 | 重要性 |
|---|---|---|---|
| 1 | 系统的核心价值是什么？谁在为什么场景使用系统？ | 业务方访谈、产品文档 | P0 |
| 2 | 系统的边界在哪里？哪些是核心能力，哪些只是当前实现或辅助功能？ | 用户任务、组织职责、上下游契约 | P0 |
| 3 | 系统的核心流程有哪些？哪些流程是不可中断的？ | 业务分析、日志分析 | P0 |
| 4 | 系统中的核心数据实体是什么？它们之间的关系如何？ | 数据库分析、代码分析 | P0 |
| 5 | 系统中嵌入了哪些业务规则？哪些规则是硬编码的？ | 代码审查、业务测试 | P1 |
| 6 | 系统有哪些对外暴露的契约？哪些契约是隐式的？ | 接口分析、日志分析 | P0 |
| 7 | 系统有哪些历史包袱？哪些代码是"没人敢动"的？ | 老员工访谈、代码注释 | P1 |
| 8 | 系统的核心风险点在哪里？哪些场景曾经出过事故？ | 故障报告、老员工访谈 | P0 |
| 9 | 谁发起、批准、执行、承担损失、处理异常并接受审计？ | 组织制度、权限配置、操作日志 | P0 |
| 10 | 哪些业务事实在任何时候都必须成立？谁负责维护？ | 规则、数据、对账、事故样本 | P0 |
| 11 | 业务指标如何计算、何时截点、能否重算、不同报表是否同口径？ | SQL、报表、指标文档、财务对账 | P0/P1 |
| 12 | 正常路径以外，超时、重复、撤销、冲正和人工干预如何处理？ | 日志、客服/运维流程、补偿任务 | P0 |

### 2.3 分析步骤

#### 步骤 2.3.1：业务能力识别

通过多源证据交叉验证，识别系统提供的业务能力：

| 证据来源 | 提取方法 | 产出 |
|---|---|---|
| 前端菜单/导航 | 截图或抓包分析 URL | 功能模块列表 |
| 接口文档/OpenAPI | Swagger/RAML 或抓包 | API 能力清单 |
| 数据库表名/视图名 | 逆向工程 | 数据存储能力 |
| 定时任务/批处理 | 代码扫描 | 后台处理能力 |
| 报表/导出功能 | 功能试用 | 数据输出能力 |

**执行动作**：

1. 收集所有证据源的原始清单
2. 按功能域（Domain）对能力分组
3. 识别能力之间的主从关系
4. 标注能力之间的依赖关系

**优先级判定标准**：

| 优先级 | 判定依据（满足任一即可） | 典型示例 |
|---|---|---|
| P0 | 核心营收链路、合规必需、故障直接影响核心业务 | 下单、支付、出库、对账 |
| P1 | 重要支撑能力强关联 P0、影响主流程稳定性风控 | 库存校验、会员权益、消息通知 |
| P2 | 增值能力、辅助功能、可短期降级 | 营销活动、报表导出、消息中心 |
| P3 | 边缘功能、低频、可考虑外包或下线 | 历史活动、调研、弃用模块 |

> 优先级须结合调用频率监控、业务方访谈、营收占比三源证据交叉确认，单一来源不得单独定级。

**产出**：`02-business/业务能力地图.md`

#### 步骤 2.3.1A：价值、结果与角色责任分析

先回答“业务为何存在”，再判断现有功能是否核心。菜单使用频率高不等于业务价值高，历史功能多也不等于未来必须保留。

| 分析对象 | 核心问题 | 推荐产物 |
|---|---|---|
| 用户/客户任务 | 用户在什么情境下试图完成什么进展？现有绕行方案是什么？ | JTBD/用户任务清单 |
| 价值交换 | 谁付出时间、资金、库存或风险，谁获得什么结果？ | 价值链/价值流 |
| 业务结果 | 什么指标代表业务成功，哪些只是过程指标？ | Outcome/KPI 树 |
| 角色责任 | 谁发起、批准、执行、知会、承担损失、处理异常？ | RACI 与责任矩阵 |
| 控制职责 | 谁能操作、谁能复核、谁能越权批准、谁被审计？ | 职责分离矩阵 |

执行时区分三类内容：

- `业务本质`：不依赖当前页面和技术仍然成立的任务、规则和结果。
- `组织策略`：因当前组织分工、风险偏好或运营方式形成，可随制度演化。
- `现有实现`：页面、字段、审批层级、批处理时间等具体实现，不自动升级为新系统需求。

**产出**：`02-business/价值结果与角色责任.md`

#### 步骤 2.3.2：核心流程还原

识别系统支持的核心业务流程，包括正常路径和分支路径：

| 流程类型 | 分析方法 |
|---|---|
| 用户交互流程 | 试用系统、跟踪前端请求 |
| 数据处理流程 | 分析后端逻辑链路 |
| 异步处理流程 | 分析消息队列、任务调度 |
| 跨系统集成流程 | 分析接口调用、事件触发 |

**关键技巧**：

- 从高频/核心场景入手：如订单创建、支付完成、会员注册
- 识别流程中的状态机：订单状态、会员状态、库存状态
- 标注外部依赖：第三方支付、短信服务、微信/支付宝

**产出**：`02-business/核心流程还原.md`

#### 步骤 2.3.2A：异常、补偿与人工流程还原

正常路径只说明系统“能工作”，异常路径才揭示业务真实边界。每条 P0/P1 流程至少分析：

| 场景 | 必须回答 |
|---|---|
| 超时/部分失败 | 系统如何判断未知结果，谁重试，何时转人工？ |
| 重复到达 | 如何识别同一业务操作，重复执行的副作用是什么？ |
| 撤销/冲正 | 是删除、反向分录、补偿单还是新状态？原记录是否可审计？ |
| 并发冲突 | 两个角色或请求同时操作时，哪个业务不变量决定胜负？ |
| 跨日/时区 | 营业日、自然日、账期和时区如何定义？ |
| 历史数据 | 旧字段、旧状态和旧规则如何解释，能否重新处理？ |
| 人工介入 | 谁能补单、改状态或调账，授权、复核和审计如何保证？ |

使用 BPMN 或服务蓝图同时表达用户、人工岗位、系统、外部机构和等待时间；不要把人工补偿隐藏在“系统外处理”一句话中。

**产出**：`02-business/异常补偿与人工流程.md`

#### 步骤 2.3.3：数据实体与关系

逆向提取核心数据模型，理解数据结构和业务语义：

| 方法 | 适用场景 | 工具 |
|---|---|---|
| 数据库逆向工程 | 有数据库访问权限 | PowerDesigner, ER/Studio, DBeaver |
| 代码分析 | 无法直连数据库 | 分析 Entity/Model 类 |
| API 响应分析 | 只有运行系统 | 抓包分析 JSON 结构 |

**关注点**：

- 核心实体的定义和属性
- 实体之间的关系（1:1, 1:N, N:N）
- 关键字段的业务含义（状态、类型、金额）
- 数据生命周期（创建、修改、归档、删除）

**产出**：`02-business/数据实体模型.md`

#### 步骤 2.3.3A：领域语义与边界识别

数据库表不是领域模型，Entity 类也不天然等于业务对象。通过事件风暴、术语对照、接口与数据样本识别：

- 核心业务对象、值对象、业务事件和负责作出决策的主体。
- 同一术语在销售、仓储、支付、财务等上下文中的不同含义。
- 同一现实对象使用多个 ID、编码或映射表的原因及权威来源。
- 对象由谁创建、谁拥有、谁可修改、何时失效、如何归档和能否重建。
- 上下文之间通过共享库表、API、消息、文件还是人工流程交换语义。

输出限界上下文图和上下文映射，标明上下游、共享内核、开放主机服务、防腐层或事实上的数据库耦合。DDD 术语只用于解释已观察到的语义边界，不得为了套方法论虚构聚合或领域事件。

**产出**：`02-business/领域术语与上下文地图.md`

#### 步骤 2.3.4：业务规则提取

识别嵌入在代码中的业务规则和约束：

| 规则类型 | 示例 | 分析位置 |
|---|---|---|
| 输入校验 | 金额必须大于0、手机号格式 | Controller/Service 校验逻辑 |
| 流程约束 | 订单未支付不能发货 | 状态机转换逻辑 |
| 业务计算 | 折扣计算、积分计算 | 业务计算方法 |
| 权限控制 | 只有管理员能查看报表 | 权限校验注解 |
| 数据一致性 | 库存不能为负 | 库存扣减逻辑 |

**关键技巧**：

- 搜索常见规则关键词：`if (amount < 0)`、`validate`、`check`、`must`
- 分析 Service 层的核心业务方法
- 注意异常处理中的业务逻辑

规则提取不能只搜索 `if/validate/check`。还要检查 SQL 条件、唯一键、默认值、配置、规则表、模板、脚本、前端校验、报表 SQL、人工制度和外部系统。对每条重要规则记录：

| 字段 | 内容 |
|---|---|
| 规则 ID 与自然语言 | 用业务语言表达，不直接复制代码 |
| 触发条件与适用范围 | 角色、渠道、租户/门店、时间、产品、版本 |
| 输入、输出与优先级 | 冲突规则如何裁决，缺省值是什么 |
| 所有者与变更依据 | 谁批准，依据什么政策、合同或经营策略 |
| 实现位置 | 前端、服务、SQL、配置、任务、人工或外部系统 |
| 例外与反例 | 哪些情况规则不成立，历史数据如何处理 |
| 证据与测试 | 证据 ID、正例、边界例和反例 |

复杂判断优先使用决策表或 DMN 表达，流程状态使用状态机表达；不要把判断条件、状态变化和副作用混成一张流程图。

#### 步骤 2.3.4A：状态机与业务不变量

为核心对象建立显式状态模型：状态定义、允许转换、触发命令、前置条件、执行角色、副作用、失败后的状态、终态和非法转换。数据库中的状态值只是候选证据，还须结合实际数据分布、代码路径和运行日志验证是否可达。

不变量是任何合法路径都必须保持的业务事实，不等于简单字段校验。例如：

- 一笔支付只产生一次有效入账，但可以有多次支付尝试和回调。
- 库存可用量、占用量和实物量的关系必须满足项目实际定义的守恒规则。
- 调账、退款、冲正必须可追溯到原业务事实，不得通过覆盖历史消除审计链。
- 租户、商户、门店、组织等作用域必须依据项目真实授权模型确定，不凭字段同名猜测。

对每条不变量记录维护者、强制点、并发策略、破坏后果、检测信号、修复/对账机制和验证用例。

**产出**：`02-business/状态机与不变量目录.md`

#### 步骤 2.3.5：兼容契约与隐式依赖识别

遗留系统分析的关键产出之一是被调用方、历史数据、配置、定时任务、消息或对外契约已经依赖的"可观察行为契约"。这些契约不在文档中显式声明，却是后续重构与演进的硬约束。

| 契约来源 | 识别方法 | 典型契约 |
|---|---|---|
| 对外 API | 抓包、调用方代码扫描、日志中的调用方 IP/UA | 字段名、字段顺序、错误码语义、幂等键 |
| 消息 MQ | 分析 Topic/Queue 的生产者与消费者清单、消息体样本 | 消息 schema、分区规则、消费顺序假设 |
| 数据库被外部查询 | 抓取直连 DB 的应用清单、报表工具、BI 取数脚本 | 表结构、视图、字段语义、统计口径 |
| 定时任务产出 | 分析任务清单与下游消费者 | 产出文件路径、命名、生成时刻、数据口径 |
| 配置被外部引用 | 分析配置中心、环境变量被外部读取的记录 | 配置 key、默认值、变更通知机制 |
| 前端缓存依赖 | 分析前端 localStorage/SessionStorage、CDN 缓存 key | 缓存 key 命名、过期策略、版本字段 |

**契约风险分级**：

| 分级 | 特征 | 处置原则 |
|---|---|---|
| 显式契约 | 有文档、有版本号、有调用方对接记录 | 变更需走正常版本协商，提供兼容期 |
| 隐式契约 | 无文档但被外部稳定调用，调用方依赖字段名/顺序 | 变更前必须先补充契约文档并通知调用方 |
| 灰色地带 | 偶发调用、调用方不明 | 通过日志埋点确认调用方后再决策 |
| 已废弃 | 经确认无调用方 | 可安全变更，但需保留一个版本的灰度退路 |

> 注意区分"内部实现"与"契约"：内部实现细节（如私有方法、内部表结构）不属于必须保留的兼容基线；但已对外暴露的可观察行为属于契约。已确认的越权、注入、凭据泄露等安全缺陷不属于必须保留的兼容基线，修复时仍须评估调用方与数据迁移影响。

**产出**：`02-business/兼容契约清单.md`

#### 步骤 2.3.6：指标口径与业务数据血缘

指标是业务规则的另一种外显形式。对营收、订单、库存、会员、履约、结算等关键指标建立口径卡：

| 字段 | 必须说明 |
|---|---|
| 业务定义 | 指标回答什么问题，不能回答什么问题 |
| 事实粒度 | 每行代表订单、明细、支付尝试、日快照还是其他事实 |
| 公式与过滤 | 分子、分母、状态范围、去重键和排除条件 |
| 时间语义 | 事件时间、入库时间、营业日、账期、时区和截点 |
| 数据来源 | 权威源、同步链路、转换 SQL、聚合层和报表出口 |
| 修订机制 | 迟到数据、退款、冲正和历史重算如何反映 |
| 责任与对账 | 口径所有者、审批人、对账对象和差异容忍度 |

对相同名称不同口径、不同名称相同口径、直接读业务库、离线与在线不一致等情况建立“口径冲突台账”。

**产出**：`02-business/指标字典与数据血缘.md`

把业务认知和技术证据绑定，避免业务文档与代码分析再次分离：

| 目标 | 场景 | 规则/不变量 | 接口/消息/任务 | 代码入口 | 数据 | 指标/审计 | 测试与证据 |

### 2.3.8 行业对标与合理性评价

分析遗留系统不仅要回答"系统是什么"，还要回答"合理吗"和"行业标杆是什么"。缺乏对标分析会导致两种错误：把行业标准当圣经（忽视业务上下文）或把历史实现当最优解（丧失改进机会）。

#### 2.3.8.1 对标分析框架

```
遗留系统现状 ──→ 行业做法 ──→ 差距分析 ──→ 风险与建议
     │               │              │
     ▼               ▼              ▼
  当前实现        行业标准       实现 vs 行业
  业务上下文      最佳实践       业务适配性
  约束条件        监管要求       改进优先级
```

#### 2.3.8.2 评价维度

| 维度 | 评价问题 | 典型对标来源 |
|---|---|---|
| **业务模型合理性** | 领域模型是否符合业务本质？状态机是否完整？ | 同行业头部产品、行业标准数据模型 |
| **流程效率** | 核心流程步骤是否必要？等待/审批节点是否合理？ | 行业平均处理时长、最佳实践流程 |
| **规则复杂度** | 业务规则是否过度复杂或过度简化？规则是否可配置？ | 行业规则复杂度基准、合规要求 |
| **数据模型** | 表结构是否符合范式？字段设计是否冗余或缺失？ | 行业标准 ER 图、数据治理规范 |
| **接口设计** | API 契约是否合理？是否支持扩展？幂等/版本化如何处理？ | RESTful 最佳实践、行业 API 标准 |
| **异常处理** | 失败场景是否全覆盖？补偿机制是否完整？ | 行业可靠性标准、SLA 要求 |
| **合规性** | 是否满足行业监管要求？数据安全是否达标？ | 行业法规、等保/ISO 标准 |

#### 2.3.8.3 合理性判定规则

| 现状特征 | 行业做法 | 判定 | 说明 |
|---|---|---|---|
| 订单状态仅 5 种 | 行业标准 8-12 种 | **可能不合理** | 缺少"部分退款""部分发货"等细分状态 |
| 支付回调无幂等 | 行业必须幂等 | **不合理** | 重试导致重复记账风险 |
| 库存扣减无事务 | 强一致或可靠消息 | **不合理** | 超卖风险 |
| 用户密码明文存储 | 哈希+盐 | **不合理** | 安全合规违规 |
| 无操作审计日志 | 必须有审计 | **不合理** | 合规风险 |
| 定时任务无补偿 | 消息+补偿+告警 | **可能不合理** | 需评估业务影响 |
| 表结构无索引 | 应有索引覆盖高频查询 | **可能不合理** | 需分析查询性能 |
| 跨库无补偿 | 最终一致+对账 | **可能合理** | 评估业务容忍度 |

> **注意**：合理性判定必须结合业务上下文。同行业头部做法未必适合当前系统规模、团队能力和业务阶段。"不合理"的判定仅表示存在差距，是否需要改进需结合业务价值、改进成本和风险评估综合决策。

#### 2.3.8.4 知识库对标方法

使用知识库中的行业最佳实践进行对标：

1. **从知识库提取对标基准**：查阅 `../01-知识库/` 中对应业务域的"行业做法"和"设计决策输入包"

2. **多源交叉验证**：
   - 知识库最佳实践（综合多家竞品提炼）
   - 行业标准/监管文档
   - 头部产品实际实现（通过逆向或公开资料）

3. **差距量化**：
   ```
   差距分 = Σ(差距项 × 业务影响权重 × 修复难度系数)
   
   差距项：0=无差距, 1=轻微, 2=明显, 3=严重
   业务影响：1=边缘, 2=重要, 3=核心
   修复难度：1=简单, 2=中等, 3=复杂
   ```

### 2.4 业务分析方法选择

| 方法 | 最适合解决的问题 | 主要产物 | 不适用或注意点 |
|---|---|---|---|
| Event Storming | 发现事件、命令、角色、策略、热点和语义边界 | 事件时间线、候选上下文 | 研讨结论仍需运行和代码证据验证 |
| JTBD/Outcome Mapping | 区分用户真正目标与现有功能 | 用户任务、结果树 | 不替代规则与控制分析 |
| 业务能力地图/价值流 | 识别稳定能力与端到端价值产生过程 | 能力地图、价值流 | 能力层级须保持一致，不能混入页面功能 |
| BPMN/服务蓝图 | 表达跨角色、人工和系统流程 | 协作图、等待与失败点 | 避免把所有代码调用画进业务流程 |
| 状态机 | 表达对象生命周期和合法转换 | 状态转换表/图 | 不要用状态机承载复杂决策规则 |
| 决策表/DMN | 显式化条件组合、优先级和结果 | 可审查规则表 | 规则动态性低时无需引入规则引擎 |
| DDD Context Mapping | 识别语义边界和上下游关系 | 上下文地图、术语表 | 不得从表结构机械推导聚合 |
| 不变量分析/反例驱动 | 验证业务规则边界和失败条件 | 不变量、最小反例、测试 | 反例须使用合法且脱敏的数据 |

#### 步骤 3.3.4：代码质量评估

**复杂度信号**：

| 指标 | 计算方法 | 正确用法 |
|---|---|---|
| 类/方法长度 | 有效代码行数与职责数量 | 用于筛选需人工检查的候选点，不以固定行数直接定债务 |
| 圈复杂度/认知复杂度 | 分支、循环、异常和嵌套 | 与变更频率、测试和缺陷记录联合判断 |
| 依赖与扇入扇出 | 静态依赖、运行调用和数据依赖 | 区分稳定公共能力与无意耦合 |
| 继承深度 | 继承层级与覆盖行为 | 关注行为可预测性，而非机械限制层数 |
| 重复与克隆 | 语法或语义相似片段 | 先判断是否会共同变化，再决定是否抽取 |

任何通用阈值都只能作为团队可调整的预警线，不能直接证明代码质量差。框架生成代码、声明式配置、核心算法和普通 CRUD 应使用不同基线。

**技术债识别**：

| 类型 | 典型表现 | 风险判定依据 |
|---|---|---|
| 硬编码 | Magic Number、散落规则值 | 是否表达可变化业务规则、是否多处不一致 |
| 重复代码 | Copy-Paste 代码段 | 是否共同变化、是否已造成缺陷分叉 |
| 复杂职责 | 过长方法/大类/高认知复杂度 | 是否位于高变更、高故障的核心切片 |
| 结构耦合 | 循环依赖、跨层调用、共享数据库 | 影响范围、发布耦合和故障传播范围 |
| 废弃代码 | 注释代码、疑似未调用入口 | 是否存在反射、配置、任务或外部隐式调用 |
| 不安全实践 | SQL 拼接、明文凭据、越权路径 | 可利用性、影响和暴露面；安全缺陷优先单独处置 |

#### 步骤 3.3.5：技术债量化

使用 SonarQube 或类似工具进行系统性扫描，但扫描结果只是候选问题，不等于业务风险或重构优先级：

```bash
# SonarQube 扫描
sonar-scanner -Dsonar.projectKey=legacy-system
mvn sonar:sonar

# 生成技术债报告
mvn com.github.veithen.maven:qulice-maven-plugin:check
mvn com.github.spotbugs:spotbugs-maven-plugin:check
```

**技术风险优先级模型**：

```text
优先级依据 = 业务关键性 × 变更/故障暴露 × 影响半径 × 证据强度
处置收益   = 风险降低 + 交付效率提升 + 认知成本降低
实施约束   = 工作量 + 回归难度 + 兼容/迁移成本 + 不可逆性
```

不要机械相乘得到伪精确总分。使用评分只是为了排序和暴露分歧，最终保留各维度、证据和判断理由：

| 候选点 | 业务关键性 | 变更热点 | 故障/安全暴露 | 耦合范围 | 测试缺口 | 建议 |
|---|---|---|---|---|---|---|
| ... | 高/中/低 | 提交/作者/近期变更 | 事故或扫描证据 | ... | ... | 保留/隔离/测试/重构 |

工作量必须给出估算范围、假设和置信度；扫描工具生成的“技术债分钟数”不得直接作为项目排期。

#### 步骤 3.3.6：幂等性与可重复写校验

遗留系统中，支付、订单、库存、MQ 消费等可重复写操作若未做幂等，在重试、补偿、消息重投场景下会产生脏数据与资金风险。

**幂等机制识别清单**：

| 机制类型 | 识别方法 | 代码特征 |
|---|---|---|
| 唯一键约束 | 数据库唯一索引、`INSERT ... ON DUPLICATE KEY` | DDL 中的 UNIQUE KEY、`uk_` 前缀索引 |
| 状态机校验 | 更新前 `where status = ?` 条件判断 | Service 层 `updateXxx where status=待支付` |
| 幂等表/防重表 | 独立的 `idempotent_record` / `req_log` 表 | 表名含 `idempotent`/`dedup`/`req_log` |
| 分布式锁 | Redis `SETNX`、ZK 锁、Redisson | `tryLock`、`SETNX`、`RLock` |
| token 防重 | 前端获取一次性 token，后端校验消费 | `token` 字段、redis `del` 返回 0 表已消费 |
| 业务唯一键 | 业务流水号 + 来源去重 | `out_trade_no`、`biz_no` + 唯一索引 |

**分析命令**：

```bash
# 搜索幂等/jq相关关键字
grep -rn "idempotent\|幂等\|防重\|dedup\|onceToken\|SETNX\|tryLock" --include="*.java" | head -30

# 搜索状态机条件更新
grep -rn "where.*status\s*=" --include="*.xml" --include="*.java" | head -20

# 识别幂等表
grep -rin "idempotent\|req_log\|dedup" --include="*.sql" --include="*.xml"
```

**风险评估矩阵**：

| 写操作 | 幂等机制 | 覆盖完整度 | 重投/重试后果 | 风险 |
|---|---|---|---|---|
| 支付回调 | 唯一键 `out_trade_no` | 全量 | 重复回调安全 | 低 |
| 订单创建 | 无 | - | 重复下单 | 高 |
| 库存扣减 | 状态机 + 流水 | 部分 | 超扣 | 中 |
| MQ 消费 | 无幂等表 | - | 重复消费致重复发放 | 高 |

> 幂等性缺口在遗留系统中属高风险，但修复受调用方契约约束：补幂等通常会改变接口或表结构，须与 2.3.5 兼容契约清单联动评估影响面。

## 4A. 数据一致性边界与事务模式专项

> 本章插入于第 4 章与第 5 章之间，作为业务/技术分析通向架构分析的桥梁。遗留系统中数据一致性边界与事务模式是架构演进的硬约束，跨库、跨服务、异步链路的一致性假设常被隐藏在"看起来正常"的代码里，必须在架构决策前显式抽取。

### 4A.1 分析目标

显式标注系统中每条关键业务链路的一致性模型、事务边界与补偿路径，识别"看起来强一致实则最终一致"与"假设最终一致实则无补偿"两类高风险错配。

### 4A.2 一致性模型分类

| 一致性模型 | 典型实现 | 适用场景 | 风险特征 |
|---|---|---|---|
| 强一致（本地事务） | 单库 `@Transactional` | 单库内多表写入 | 实现简单，边界外不可靠 |
| 两阶段提交/XA | 分布式事务协调器 | 跨库强一致 | 性能差，遗留系统中多为摆设 |
| 最终一致-同步补偿 | TCC、Saga | 跨服务核心链路 | 需 Confirm/Cancel 完整 |
| 最终一致-异步消息 | 本地消息表 + MQ | 跨域解耦 | 依赖消费幂等与重投 |
| 最终一致-定时对账 | 对账任务 + 差异修复 | 资金、库存 | 修复滞后需容忍窗口 |
| 无补偿 | 跨库写后无任何机制 | - | 高风险，仅靠"不会失败"假设 |

### 4A.3 分析步骤

#### 步骤 4A.3.1：事务边界抽取

```bash
# 搜索事务注解与显式边界
grep -rn "@Transactional" --include="*.java" | head -40
grep -rn "TransactionTemplate\|TransactionStatus\|commit()\|rollback()" --include="*.java"
```

**事务边界标注表**：

| 链路节点 | 事务边界 | 跨度 | 一致性模型 | 失败回滚范围 |
|---|---|---|---|---|
| 订单创建 | OrderService.create 内 | 单库 | 强一致 | 仅订单库 |
| 库存扣减 | InventoryService 单独事务 | 单库 | 强一致 | 与订单非同事务 |
| 支付回调 | 更新订单 + 发 MQ | 跨库+MQ | 最终一致 | 无补偿 |

#### 步骤 4A.3.2：跨库/跨服务写入识别

| 识别点 | 方法 | 关注问题 |
|---|---|---|
| 跨库写入 | 代码中不同 DataSource 切换 | 是否在同一事务内 |
| 写库 + 发 MQ | `transactionTemplate` 后 `producer.send` | 发送失败是否回滚、MQ 是否本地消息表 |
| 写库 + 调外部接口 | DB 写入后 HTTP/RPC 调用 | 调用失败是否回滚或幂等重试 |
| 写库 + 缓存更新 | DB 更新后 redis `set` | 失败是否容忍脏缓存 |

#### 步骤 4A.3.3：补偿与对账机制识别

| 机制 | 识别方法 | 缺口风险 |
|---|---|---|
| TCC Confirm/Cancel | 搜索 `confirm`/`cancel`/`tcc` | 缺 Cancel 致资源悬挂 |
| Saga 补偿动作 | 搜索 `compensate`/`rollback`/`undo` | 补偿不完整致脏状态 |
| 对账任务 | 定时任务清单含"对账"/"reconcile" | 修复滞后窗口容忍度 |
| 死信队列处理 | MQ DLQ 与人工补单流程 | DLQ 是否有人处理 |

#### 步骤 4A.3.4：一致性错配判定

对每个核心链路，核对其"宣称一致性"与"实际机制"是否匹配：

| 链路 | 宣称一致性 | 实际机制 | 是否错配 | 风险 |
|---|---|---|---|---|
| 订单+库存 | 强一致 | 跨库非同事务，无补偿 | 是 | 中/高并发下超卖 |
| 支付+积分 | 最终一致 | MQ 无幂等消费 | 是 | 重复发放积分 |

## 5. 架构层面深入分析

### 5.1 分析目标

在业务和技术理解的基础上，深入分析架构层面的设计决策、质量属性和风险敞口。

### 5.2 架构分析框架

使用七个互相校验的视图，避免用一张“总架构图”混合不同尺度和语义：

| 视图 | 核心问题 | 主要产物 |
|---|---|---|
| 1. 系统上下文 | 谁使用、谁拥有、依赖哪些外部系统、信任边界在哪？ | C4 Context、系统清单、所有权矩阵 |
| 2. 业务与领域 | 能力、价值流、上下文、规则和不变量如何划分？ | 能力/上下文地图、关键切片 |
| 3. 应用与代码 | 部署单元、模块、职责和依赖是否与业务边界一致？ | C4 Container/Component、依赖图、热点图 |
| 4. 数据 | 权威源、所有权、血缘、生命周期、口径和一致性是什么？ | 数据流/血缘、CRUD/所有权矩阵 |
| 5. 运行时 | 同步/异步链路、状态变化、重试、超时和故障如何传播？ | 动态图、序列图、故障传播图 |
| 6. 部署与运维 | 拓扑、容量、发布、观测、备份和恢复如何实现？ | 部署图、SLO/告警/恢复矩阵 |
| 7. 演进与治理 | 隐式契约、历史决策、团队边界和迁移约束是什么？ | 决策考古、ADR、演进路线、适应度函数 |

七视图不是要求画七张大图。仅为当前决策和关键业务切片创建必要视图，每张图标明范围、层级、版本/环境、证据来源和更新时间。

#### 5.2.1 跨视图一致性检查

- 业务能力所有者与代码/服务所有者是否错位。
- 领域对象权威源与实际写入者是否一致，是否存在多主或绕过服务直写。
- 静态依赖与真实运行调用是否一致，是否存在反射、配置、任务和消息形成的隐藏边。
- 部署冗余是否真正消除共享数据库、缓存、网络、配置中心等共同失效点。
- 对外承诺的 SLA/SLO 是否有容量、超时、降级、恢复和观测机制支撑。
- 团队边界是否导致跨团队高频协作、共享发布或模型语义冲突。

#### 步骤 5.3.1：静态架构分析

**模块结构分析**：

cat pom.xml | grep -A 200 "<modules>"

# 包结构分析
find . -path "*/src/main/java" -type d | \

# 使用 Maven Enforcer 插件

#### 步骤 5.3.2：动态架构分析

**调用链路追踪**：

| 追踪方法 | 适用场景 | 工具 |
|---|---|---|
| 代码静态分析 | 链路复杂但可离线分析 | IDE Call Hierarchy |
| 运行时追踪 | 需要真实数据验证 | Skywalking/Jaeger |
| 日志分析 | 已有的调用记录 | ELK/Graylog |

**核心链路识别**：

```
## 订单创建调用链路

/gateway/order/create
    │
    ▼
[OrderController.create] ──> 20ms
    │
    ▼
[OrderService.create] ──> 50ms
    │
    ├──► [InventoryService.check] ──> 30ms  ← 外部依赖
    │
    ├──► [PriceService.calculate] ──> 10ms

```

调用链只描述“发生了什么”，还应标注：同步/异步边界、超时预算、重试主体、幂等键、事务边界、数据所有权、线程/租户上下文、降级行为、补偿/对账、可观测信号和故障传播方向。静态调用图必须用至少一份运行证据校验关键边。

#### 步骤 5.3.3：质量属性评估

质量属性必须使用场景而非通用阈值评价。每个场景采用：

```text
刺激源 + 刺激 + 环境 + 受影响对象 + 系统响应 + 可度量标准
```

示例：

| 属性 | 质量属性场景 |
|---|---|
| 性能 | 大促峰值 3000 TPS 时，支付回调 99.9% 在 2 秒内完成，重复回调不产生重复记账 |
| 可用性 | 主库节点不可用时，核心查询 60 秒内恢复；写入按已批准策略拒绝或切换，不能静默丢失 |
| 安全 | 普通门店用户枚举其他门店 ID 时，所有入口均拒绝且产生脱敏审计事件 |
| 可修改性 | 新增一种支付渠道时，修改范围限定于指定扩展点，既有渠道契约测试不变 |
| 可恢复性 | 删除/损坏关键数据后，在 RPO/RTO 目标内从备份恢复并通过业务对账验证 |

质量属性场景的目标值来自业务损失、合同/合规、历史基线、容量和成本约束，不能照抄行业模板。分析步骤：

1. 从关键业务切片和事故历史提取最重要的质量属性场景。
2. 识别架构敏感点、取舍点和风险点，可用轻量 ATAM 研讨形成候选项。
3. 用运行指标、压测、故障演练、配置或代码证据验证当前响应。
4. 对关键失败模式使用 FMEA 或故障树记录触发条件、影响、检测、隔离和恢复。
5. 把需要长期保持的属性转成架构适应度函数或持续校验。

**质量属性场景模板**：

| 场景 ID | 业务切片 | 属性 | 刺激/环境 | 当前响应 | 目标/依据 | 敏感点/取舍 | 证据 | 缺口 |
|---|---|---|---|---|---|---|---|---|
| QA-... | ... | ... | ... | ... | ... | ... | E-... | ... |

#### 步骤 5.3.4：架构决策记录 (ADR)

识别关键架构决策及其上下文。已有正式 ADR 才称为 ADR；从现状逆向推测的历史选择应称为“决策考古记录”，不能虚构当年的理由：

```markdown
## ADR-001: 选用 MySQL 作为主数据库

### 背景
2018 年系统设计时，需要选择主数据存储。

### 决策
选择 MySQL 5.7 作为主数据库。

### 已确认理由
- 仅记录能够由当时文档、提交记录或参与者交叉验证的理由

### 待验证解释
- 对无法确认的历史约束明确标注推断和验证路径

### 后果
- 正面：开发效率高，运维成本低
- 负面：水平扩展受限，分库分表复杂度高

### 当前状态与重新决策触发器
- 记录何种业务、风险或供应商条件变化时需要重新评估；不得仅凭 EOL 直接跳到具体迁移方案
```

对于新的重大决策，ADR 至少包含：决策问题、事实与约束、质量属性场景、候选方案、比较判据、选择、正负后果、受影响契约、迁移/回滚、验证方式和重新评估触发器。核心数据模型、状态机、对外契约和不可逆迁移属于单向门，必须比可逆的参数或界面决策具有更强证据。

#### 步骤 5.3.5：租户隔离与安全不变量

**租户隔离分析**：

| 检查项 | 方法 | 关注点 |
|---|---|---|
| 作用域模型 | 识别项目实际定义的租户、商户、组织、门店和全局数据 | 不凭 `lid`、`pid` 等字段名猜测含义 |
| 隔离条件完整性 | 沿入口、线程、查询、缓存、搜索、消息和任务追踪上下文 | 作用域是否丢失、污染或被绕过 |
| 跨租户越权风险 | 分析用户权限模型与数据访问路径 | 是否存在水平越权 |

字段搜索只能用于发现候选实现，必须先从项目入口规则、权限模型、权威文档和实际数据访问链确认作用域语义，再评估隔离是否完整。全局表、租户独占存储和共享表采用不同检查方式。

**安全不变量检查**：

| 不变量类型 | 检查方法 | 风险 |
|---|---|---|
| 金额不为负 | `amount >= 0` 校验 | 负数金额可被利用 |
| 库存不为负 | 扣减前校验 | 超卖漏洞 |
| 订单状态合法 | 状态机校验 | 非法状态流转 |
| 权限校验完整 | 接口鉴权覆盖 | 未授权访问 |

#### 步骤 5.3.6：变更热点、组织耦合与演进能力

把静态复杂度与版本历史结合，识别真正昂贵的变化点：

- 文件/模块变更频率、共同变更关系、缺陷修复频率和回滚记录。
- 同一热点涉及的作者/团队数量、跨团队等待和共享发布频率。
- 业务规则变化是否集中在稳定扩展点，还是散落在前端、服务、SQL、任务和报表。
- 架构边界是否支持独立测试、部署、回滚和数据迁移。

高复杂度但长期稳定的代码未必优先重构；高变更、高关键性、高耦合且测试薄弱的区域通常优先。提交次数不是价值指标，必须结合业务事件和仓库历史窗口解释。

#### 步骤 5.3.7：架构适应度函数

将关键架构特性转成可重复执行的验证，示例包括：

- 模块依赖和禁止跨层调用的 ArchUnit/依赖规则。
- API、消息和数据 Schema 的兼容性检测。
- 状态机合法转换、幂等、租户隔离和权限边界测试。
- 核心质量属性的性能预算、SLO、恢复演练和告警覆盖。
- 指标口径一致性、对账差异和数据质量规则。

适应度函数必须关联业务风险和失败后处置；不要为了“架构治理”创建大量无人响应的检查项。

## 5A. 业务实现合理性与行业对标评价

> 本章插入于第 5 章与第 6 章之间。前三章（业务/技术/架构）回答"系统是什么、怎么做的、做得稳不稳"，本章回答前几章未独立回答的关键问题：**这个业务实现本身合理吗？相对行业做法偏差有多大？** 遗留系统重构决策经常失败，根因不是没有看清技术债，而是没看清业务模型与行业基线的偏差——把"历史合理但需演进"误判为"一开始就错了"，或反之。

### 5A.1 分析目标

对每个被识别出的核心业务实现，建立**双尺度合理性判定**：历史合理性（在当时的约束下是否合理）与当下合理性（在当前约束下是否仍可接受），并以行业对标给出符合度结论。结论直接驱动第 6 章风险登记册与重构优先级。

### 5A.2 评价的尺度原则

评价遗留系统的业务实现必须用双尺度，单一尺度会得出无效结论：

| 尺度 | 回答的问题 | 用途 |
|---|---|---|
| 历史合理性 | 在当时的技术/业务/团阘认知约束下，这个实现是否是合理解？ | 区分"历史合理需演进"与"起点错误" |
| 当下合理性 | 在当前约束下，这个实现是否还能接受？ | 决定是否要重构、何时重构 |

> 反模式：拿当前业界最优解否定过去。这样会得出"什么都不合理"的结论，对重构决策没有价值，且会让团队对评价结论失去信任。

### 5A.3 业务对象的四层分解

"业务实现"是模糊词，必须先拆成可单独评价的对象，否则评价落空：

| 层 | 评价对象 | 例子 | 对标尺度侧重 |
|---|---|---|---|
| L1 业务模型层 | 实体抽象、状态机、领域边界是否合理 | 订单状态机是否漏了挂起态、库存是否按门店-SKU 建模 | 行业模型 |
| L2 业务流程层 | 主流程、分支、异常路径是否符合业务现实 | 支付失败是否退库存、积分发放是否幂等 | 行业流程范式 |
| L3 业务规则层 | 校验、计算、约束是否正确可演进 | 折扣硬编码 vs 规则引擎、金额单位用分还是元 | 可演进性 |
| L4 技术承载层 | 用什么技术实现业务 | 同步 RPC vs MQ、本地事务跨库 | 当下技术合理性 |

> L1-L3 的"合理"主要对标行业业务做法；L4 的"合理"主要对标当下技术做法。混淆这两类对标会得出无效结论（例如用电商推荐做法否定零售 POS 做法）。

### 5A.4 行业对标来源的可信度

"行业做法"不是单一答案，对标前必须分清来源并标注可信度：

| 来源 | 可信度 | 风险 |
|---|---|---|
| 同行业成熟标杆（头部 SaaS/开源） | 高 | 头部方案常为大规模优化，未必适配中小系统 |
| 行业通用范式（订单四态、支付幂等） | 高 | 稳定共识，可作为基准 |
| 主流框架默认实践 | 中 | 框架默认适合常见场景，特殊场景需偏离 |
| 个人经验/口口相传 | 低，须升级 | 易带偏见，必须落到 L1/L2 证据 |
| 本企业其他系统的做法 | 仅参考 | 不是"行业做法"，只是"本企业做法" |

**三条不可违反的对标原则**：

1. **行业做法 ≠ 最优做法**。行业惯例常是"够用且稳定"的折中，未必是性能/架构最优。评价遗留系统时若只对标"最优解"，会误判为不合理。
2. **同行业才有对标意义**。电商订单 ≠ POS 订单 ≠ SaaS 多租户。对标前必须先确认行业归属。
3. **规模量级决定做法差异**。日百单与日百万单的订单模型合理做法不同，跨量级对标会误判。

### 5A.5 评价五步法

这是本章核心方法论，可推广至任意业务实现对标，不局限于附录清单所列案例：

| 步 | 问题 | 产出 |
|---|---|---|
| ① 识别业务对象与阶段 | 这个实现背后映射什么业务对象？有几个推进阶段？几条轨道？ | 对象阶段图 |
| ② 找行业标准约束 | 行业共性约束是什么？（幂等必须、单调推进、物理隔离、对账口径、并发范围…） | 约束清单 |
| ③ 对照实现的偏离点 | 实现相对标准的偏离有哪些？每条偏离是技术实现差异还是模型缺陷？ | 偏离清单 |
| ④ 判定偏离性质 | 每条偏离：可解释偏离(业务差异导致)/实现风格(不影响语义)/真缺陷(确有缺口) | 性质判定 |
| ⑤ 给出双尺度结论 | 历史合理性 + 当下合理性 + 行业对标符合度（带证据等级与对标来源） | 评价结论 |

### 5A.6 三条判定范式（可跨案例复用）

这三条范式是五步法第④步"判定偏离性质"反复使用的判断内核，比具体清单更值得沉淀：

| 范式 | 含义 | 典型例子 |
|---|---|---|
| **"存在 ≠ 生效"范式** | 字段/约束存在不等于它真在起作用，必须验证强制执行路径 | DDL 有 `store_id` 但查询语句没带；有唯一索引但没有状态前置条件 |
| **"外部不可作不变量"范式** | 不能把不可控的外部行为当作系统安全基线 | 把支付渠道"只通知一次"承诺当作幂等防护 |
| **"业务对象粒度对齐"范式** | 同一业务链路上多个对象的建模最小粒度应当一致，否则必然存在跨粒度缺口 | 订单按门店而库存按全局 |

### 5A.7 评价产出结构

每个被评价的业务实现最小结论应包含以下字段，缺一项即判定为评价不完整：

```
业务对象：库存扣减
对标依据：零售多门店通用范式（同行业头部 SaaS + 主流库存开源实践）—— 对标来源：行业通用范式
实现的合理部分：扣减走状态机 + 流水
偏离点：①扣减粒度按 SKU 不按门店-SKU；②缺超卖兜底
偏离性质判定：① 真缺陷(多门店业务下不合理)；② 真缺陷
历史合理性：部分合理（单店阶段可接受）
当下合理性：不合理（已多门店，超卖风险）
行业对标符合度：部分符合
证据等级：L1（代码 + 生产超卖事故记录）
联动：纳入风险登记册 R-xxx；与 3.3.6 幂等缺口、4A 一致性错配联动
行动建议：纳入重构，需联动订单迁移、跨店调拨流程
```

### 5A.8 评价结论与重构决策的衔接

评价的价值落点是重构决策，不是评价本身。评价结论按以下矩阵映射为行动：

| 评价结论 | 历史合理性 | 当下合理性 | 行动建议 |
|---|---|---|---|
| 合理 | 是 | 是 | 保留，纳入演进监测 |
| 历史合理需演进 | 是 | 部分 | 规划重构，非紧急 |
| 起点错误 | 否 | 否 | 高优先级重构，须评估契约影响 |
| 历史合理但当下不可接受 | 是 | 否 | 如硬编码密码——历史普遍做法，当下必须修，且不属兼容基线 |

**与既有章节的衔接点**：

- 评价的"风险敞口"维度直接进第 6 章风险登记册（须带证据等级）。
- "历史合理性"用于第 5 章 ADR/决策考古，判断原决策是否仍成立。
- "当下合理性"对接第 3 章技术债与第 5 章质量属性。
- "行业对标符合度"是本章新增视角，是当前文档其他章节未覆盖的。

### 5A.9 完成判据

- [ ] 核心业务实现已按 L1-L4 四层分解识别评价对象
- [ ] 每个对象已执行五步法（对象与阶段→行业约束→偏离点→偏离性质→双尺度结论）
- [ ] 至少使用一条判定范式（存在≠生效 / 外部不可作不变量 / 粒度对齐）支撑偏离性质判定
- [ ] 每条评价结论含历史合理性、当下合理性、行业对标符合度、证据等级、对标来源
- [ ] 评价结论已联动风险登记册与 3.3.6/4A/5.3.5 缺口
- [ ] 对标来源已标注可信度，未用本企业做法或个人经验冒充行业基准

## 6. 综合分析与报告

### 6.1 分析报告结构

按决策问题汇总各维度，不按工具输出简单拼接报告：

```
# 复杂既有系统架构分析报告

## 执行摘要
## 1. 分析背景与范围
   1.1 决策问题、决策负责人和停止条件
   1.2 范围、关键切片、证据窗口和限制
## 2. 业务维度分析
   2.1 价值、角色、能力、领域语义与流程
   2.2 规则、状态机、不变量、异常补偿与指标口径
   2.3 兼容契约和业务到实现追踪矩阵
## 3. 技术框架分析
   3.1 架构/框架/设计模式
   3.2 幂等与可重复写校验
## 4. 技术栈分析
## 4A. 数据一致性边界与事务模式专项
## 5. 架构维度分析
   5.1 七视图与跨视图一致性
   5.2 质量属性场景与失败模式
   5.3 安全、作用域、不变量与适应度函数
## 5A. 业务实现合理性与行业对标评价
   5A.1 双尺度合理性判定（历史合理性/当下合理性）
   5A.2 四层分解与五步法
   5A.3 行业对标符合度结论
## 6. 关键结论、矛盾与未知项
## 7. 风险、候选方案与决策建议
## 8. 分阶段验证和演进计划
## 附录（证据索引、假设/矛盾台账、复现方法）
```

### 6.1.1 证据与结论标注规范（强制）

报告全文遵循第 0.5 节四维模型：

- **证据**：使用 `E-SRC-xxx/E-RUN-xxx` 等 ID，记录类型、质量属性、版本/环境、采集窗口和复现方式。
- **结论**：使用 `C-xxx`，标注“直接事实/交叉验证结论/经验判断/推断/假设”、验证状态和适用范围。
- **推理链**：结论必须关联支持证据与反对证据，关键结论记录从观察到结论的推理步骤。
- **风险/ADR**：关联结论 ID，不得用工具告警或单次访谈直接替代结论。
- **附录索引**：列明结论、证据文件、脱敏状态、查询/复现脚本和保留期限。

### 6.1.2 风险登记册联动机制

各章节产出的风险项须汇聚至统一风险登记册，并标注来源与联动关系：

| 风险条目 | 来源/联动章节 | 业务影响与范围 | 触发条件/可能性 | 现有检测与恢复 | 结论/证据 ID | 是否兼容基线 | 优先级理由 |
|---|---|---|---|---|---|---|---|
| 支付缺幂等 | 3.3.6、4A、5.3.5 | 重复记账/指定渠道 | 重复回调 | 对账滞后 | C-.../E-... | 否（缺陷） | 资金完整性 |
| 订单+库存跨边界无补偿 | 4A、3.3.6 | 订单与库存不一致 | 部分失败 | 人工修复 | C-.../E-... | 否 | 频率、损失和恢复成本 |

**联动规则**：

- 同一风险被多个章节识别时，登记册只保留一条，但须在"联动章节"列登记所有识别点，避免重复计数或漏评估。
- 兼容契约（2.3.5）、幂等缺口（3.3.6）、一致性错配（4A）、安全不变量（5.3.5）四类风险互相联动时，任一章节的修复建议须在登记册注明对其他章节的影响。
- 推断和假设可以进入“待验证风险线索”，但不得伪装成已确认风险，也不得单独支撑不可逆决策。

### 6.2 综合评估矩阵

| 决策维度 | 当前判断 | 判据/目标 | 关键结论 ID | 证据覆盖与限制 | 是否改变决策 |
|---|---|---|---|---|---|
| 业务适配与完整性 | ... | ... | C-... | ... | 是/否/未知 |
| 可靠性与数据完整性 | ... | ... | C-... | ... | ... |
| 安全与作用域隔离 | ... | ... | C-... | ... | ... |
| 可维护性与演进成本 | ... | ... | C-... | ... | ... |
| 技术与供应链健康度 | ... | ... | C-... | ... | ... |

> 不对有序类别或不同证据类型求平均分。综合判断必须保留分项、判据、证据覆盖和未知项，以便决策者看见分歧而不是被总分掩盖。

### 6.3 优先级建议

基于风险、信息价值和可逆性安排，不把”微服务化、升级框架”等方案预先绑定到固定阶段：

| 类型 | 选择条件 | 典型动作 |
|---|---|---|
| 立即控制 | 已确认且暴露中的安全、资金、合规或数据完整性风险 | 限流/隔离/开关/权限收紧/监控与应急流程 |
| 先补证据 | 可能影响决策但证据不足 | 埋点、契约测试、数据采样、Spike/POC、故障演练 |
| 降低风险 | 价值明确、范围可控、可逐步验证 | 特征化测试、封装边界、补偿/对账、热点治理 |
| 结构演进 | 当前边界持续阻碍业务且替代方案收益经验证 | 渐进迁移、双写/影子流量、Strangler、数据迁移 |
| 接受/观察 | 风险低于处置成本或触发条件尚未出现 | 明确所有者、触发器、监控和复审时间 |

#### 6.3.1 典型决策场景判定矩阵

| 场景 | 关键问题 | 判定条件 | 推荐行动 |
|---|---|---|---|
| Spring Boot 2→3 升级 | 破坏性变更范围？测试覆盖度？ | 依赖全部兼容且测试覆盖>60% | 分阶段升级 |
| 微服务化改造 | 服务边界是否清晰？数据一致性可接受？ | 领域边界稳定且最终一致可接受 | 渐进拆分 |
| 接受现状 | 业务关键性与变更频率？ | P2 以下且低变更、低风险 | 持续观察 |
| 局部重构 | 变更热点是否集中？测试是否充分？ | 高频变更且有特征化测试 | 优先重构热点 |
| 技术债偿还 | 投入产出比是否合理？ | 技术债影响业务交付且修复成本<重构成本 | 按优先级偿还 |

每项建议必须说明”不行动的损失、行动收益、前置条件、影响契约、验证、回滚/前向修复和重新评估触发器”。

### 6.4 决策支持

分析报告应能回答以下关键决策问题：

| 决策问题 | 报告中的答案位置 |

## 8. 常见陷阱与应对

### 8.1 分析阶段常见问题

| 陷阱 | 表现 | 应对 |
|---|---|---|
| 过度分析 | 分析报告写得很详细但产出无法落地 | 聚焦核心问题，与干系人确认优先级 |
| 忽视知情人 | 只看代码，不与老员工交流 | 将知情人访谈作为必经环节 |
| 局部最优 | 只分析某个模块，不看全局 | 从顶向下，先建立全局视图 |
| 假设验证 | 基于假设而非证据做结论 | 每个结论必须有证据支撑 |

### 8.2 遗留系统特有挑战

| 挑战 | 描述 | 应对策略 |
|---|---|---|
| 隐式知识 | 关键逻辑只在老员工脑中 | 通过访谈、代码注释逆向提取 |
| 文档过时 | 文档与实际不符 | 以代码为准，文档仅供参考 |
| 测试缺失 | 难以安全修改 | 补充关键路径的测试 |
| 依赖黑盒 | 外部系统依赖不清楚 | 补充接口文档，分析调用日志 |

### C.2 业务分析方法论体系

业务分析不是单一方法的简单应用，而是需要多方法协同，形成交叉验证的证据网络。

#### C.2.1 逆向工程法（主要方法）

从系统产出物反推业务语义，适用于遗留系统——文档缺失或过时的场景。

**逆向工程的证据层次**：

```
Level 1: 直接证据（最高置信度）
├── 代码：Controller/Service/DAO 的业务逻辑
├── 数据库：表结构、视图、存储过程、触发器
├── 配置文件：业务规则配置、业务参数
└── 测试代码：单元测试/集成测试中隐含的业务假设

Level 2: 运行证据
├── 接口请求/响应：Swagger/OpenAPI、日志
├── 消息队列：Topic、Queue、消息体样本
├── 前端页面：URL、表单、按钮交互
└── 报表/导出：数据口径、计算公式

Level 3: 外部证据
├── 第三方调用方：接口调用方代码、文档
├── 监控系统：调用频率、错误率、耗时
└── 日志系统：业务日志、审计日志

Level 4: 人的证据（需交叉验证）
├── 老员工口述：架构背景、业务规则
├── 业务方访谈：流程、规则、异常场景
└── 代码提交记录：谁改的、为什么改
```

#### C.2.2 事件风暴法（补充方法）

使用事件驱动的方式还原业务流程，特别适合复杂的状态机和异步流程分析。

**事件风暴的执行步骤**：

1. **识别领域事件**：从代码和日志中提取业务事件

```bash

grep -rn "log\|info\|event" --include="*.java" \
  | grep -i "order\|pay\|status\|complete\|fail" \
  | head -50
```

2. **识别命令和查询**：从 Controller 和 Service 中提取用户操作

3. **识别聚合根**：找出管理核心状态的对象

4. **识别限界上下文**：划分业务边界

**数据库分析命令**：

```bash
# MySQL: 提取表结构
mysql -u user -p -e "SHOW CREATE TABLE table_name\G"

# 提取所有表和注释
SELECT TABLE_NAME, TABLE_COMMENT
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'your_database';

# 提取外键关系
SELECT
    tc.table_name,
    kcu.column_name,
    ccu.table_name AS foreign_table,
    ccu.column_name AS foreign_column
FROM information_schema.table_constraints AS tc
JOIN information_schema.key_column_usage AS kcu ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage AS ccu ON ccu.constraint_name = tc.constraint_name
WHERE constraint_type = 'FOREIGN KEY';
```

## 附录 H-1：行业基准做法参考清单

> 本附录为第 5A 章"业务实现合理性与行业对标评价"的对标参考。所列案例是行业通用范式（高可信度对标来源），不是"最优解"。对标时仍须遵守 5A.4 的三条原则：行业做法 ≠ 最优做法、同行业才有对标意义、规模量级决定做法差异。每个案例均给出"标准做法—背后约束—遗留系统常见偏离与判定—可推广的方法论启发"，便于套用五步法。

### H-1.1 订单四态模型（L1 业务模型层对标）

**标准做法**：四个核心状态 + 两条取消轨道。

```
[待支付] --支付成功--> [已支付] --发货--> [已发货] --确认收货--> [已完成]
    │                      │
    └─超时取消─→ [已取消]    └─退款取消─→ [已取消]
```

**背后约束**：

| 约束 | 体现 |
|---|---|
| 状态单调推进 | 只能向前，不能回退到前一态（除非显式取消分支） |
| 每态对应明确后续可执行动作 | 待支付才能支付；已支付才能发货；已发货才能确认 |
| 取消是显式第二轨道 | 不允许"已支付"直接变回"待支付"重走，必须走取消分支 |
| 状态迁移触发下游副作用 | 状态变更触发库存、积分、通知等副作用 |

**遗留系统常见偏离与判定**：

| 偏离 | 是否一定不合理 | 判定依据 |
|---|---|---|
| 缺发货态（已支付直接到已完成） | 不一定 | 实物电商必须有；虚拟商品/服务类可退化，属可解释偏离 |
| 状态字段用 int 不用枚举名 | 技术实现风格 | 评价"可维护性差"而非"业务不合理" |
| 退款被实现为"状态回退到已支付"再走一遍 | 通常不合理 | 违反单调性，致重发积分、重复发货 |
| 缺挂起态（如等风控审核） | 须看业务 | 业务有审核环节却没建模，判定为缺失而非多建 |

**可推广的方法论启发**：

1. **"单调推进 + 显式回滚轨道"是普适范式**，适用于任何多阶段推进的业务对象（订单、审批、出库单、退款单、对账单）。
2. **判断"建模缺态"必须从"业务是否真的需要这个阶段"反推**，不能只从代码清单"看到没这个字段"就判缺。
3. **回滚轨道与正向轨道必须同等待遇**：单独问一句"这个态能不能合法地不走了"，常能暴露缺口。

### H-1.2 支付幂等（L2 业务流程层对标）

**标准做法**：业务唯一键（`out_trade_no`）+ 状态机条件更新，双重防护。

```sql
UPDATE payment_record
SET status = 'paid', paid_at = now()
WHERE out_trade_no = ? AND status = 'unpaid';
```

- 唯一键约束防同一笔重复入库
- `AND status = 'unpaid'` 保证只有第一次成功回调生效，后续重复回调影响行数为 0

**背后约束**：

| 约束 | 体现 |
|---|---|
| 支付渠道必然重试 | 网络抖动、对账补偿，回调可能来多次 |
| 重投边界不可控 | 不能假设"下游只通知一次" |
| 资金一致性 > 性能 | 允许多花一次查询，绝不允许重复入账 |
| 状态前置条件 | 已支付态不能再变支付态，缺失前置则不构成幂等 |

**遗留系统常见偏离与判定**：

| 偏离 | 是否一定不合理 | 判定依据 |
|---|---|---|
| 只用唯一索引不用状态前置 | 部分防护 | 防重复入库但不防"已退款被回调改回已支付" |
| `if (status==unpaid) then update` 两步分离 | 不合理 | 非原子，并发下仍可双更新 |
| 只查 DB 不查缓存状态 | 不一定错 | 缓存非权威可接受；若缓存驱动下游动作须保证 DB 与缓存一致 |
| 依赖渠道"只通知一次"承诺 | 不合理 | 第三方契约不可当安全基线 |

**可推广的方法论启发**：

1. **幂等判定范式 = "业务唯一键 + 前置状态条件 + 原子操作"三元组**，适用于订单创建、库存扣减、积分发放、消息消费等所有可重复写操作。
2. **多步幂等是伪幂等**：先查询再更新不是幂等，只有原子条件更新才是。
3. **不可把外部承诺当作安全基线**：评价时要识别"系统是否把不可控的外部行为当作不变量"——这正是 5A.6 三条范式之一"外部不可作不变量"。

### H-1.3 库存按门店-SKU 建模（L1 业务模型层对标）

**标准做法**：多门店系统库存粒度为 `(store_id, sku_id)` 联合主键，不是 `(sku_id)` 单键。

```
inventory 表
─────────────────────────────
store_id   | sku_id | qty | locked
─────────────────────────────
1          | A1001  | 50  | 2
2          | A1001  | 30  | 0     ← 同一商品，不同门店独立库存
─────────────────────────────
```

**背后约束**：

| 约束 | 体现 |
|---|---|
| 库存物理隔离 | 各门店库存不能互相挪用，跨店调拨是显式动作 |
| 单据归属门店 | 销售、退货、调拨单都挂门店，库存须同粒度 |
| 财务对账粒度 | 盘点、成本、毛利按门店核算 |
| 并发范围收窄 | 同 SKU 在不同门店可独立扣减，避免全局热点锁 |

**遗留系统常见偏离与判定**：

| 偏离 | 是否一定不合理 | 判定依据 |
|---|---|---|
| 只按 SKU 存总库存 | 多门店场景下不合理 | 跨店销售会乱扣；单店系统可接受 |
| 有 `store_id` 字段但查询不带 | 严重不合理 | 字段存在不等于隔离生效（"存在 ≠ 生效"范式） |
| `store_id` 字段叫 `pid` | 须查实际语义 | 不得凭字段名判，pid 在某些系统是门店而非租户 |
| 用"虚拟仓"代替门店 | 技术实现等价 | 虚拟仓与门店一一对应且查询强制带，不判为不合理 |

**可推广的方法论启发**：

1. **"建模粒度"判定范式 = 对齐业务单据与核算的最小单元**。订单粒度、库存粒度、核算粒度不一致，就是建模缺口信号——这正是 5A.6 "业务对象粒度对齐"范式。
2. **字段存在 ≠ 隔离生效**：DDL 有 `tenant_id`/`store_id` 不代表查询里都带了。必须验证**强制带**而非**有这个字段**——"存在 ≠ 生效"范式的典型体现。
3. **物理独立性优先于全统能力**："统计想要全局视图"与"业务上各单元独立"冲突时，标准做法是物理隔离 + 聚合视图，而不是物理合并。
4. **粒度选择受并发量驱动**：评价时须问"当前并发量级别下，这个粒度的代价是否可接受"。

### H-1.4 使用本附录的方式

对每个被评价的业务实现：

1. 从 H-1.1/H-1.2/H-1.3 中找最接近的行业范式作为对标基线；
2. 按 5A.5 五步法执行，偏离点对照"常见偏离与判定"表初步分类；
3. 偏离性质判定须至少引用一条 5A.6 范式作为依据；
4. 对标来源标注为"行业通用范式（附录 H-1.x）"，可信度记为高。

> 本清单只列三个高共识案例。其他业务对象（如对账、积分、促销、风控）的行业基准应在本方法论使用过程中逐步沉淀补充，新增时须附"背后约束 + 常见偏离判定 + 方法论启发"三段，保持与现有案例同构。

## 附录 I：高阶分析方法与工具箱

> 本附录收录在主文各章基础上更深入、更偏实战的分析方法与技术工具。
> 适用场景：系统规模大、文档缺失严重、团队认知碎片化、需要快速建立高置信度全景图。

### I.1 代码考古与变更动力学

当文档不可信、知情人记忆模糊时，**代码本身的变更历史**就是最诚实的叙事来源。
变更动力学不看单个提交写了什么，而是看**谁在什么频率改动什么**，从中反推模块边界、知识归属、风险集中区和隐性耦合。

#### I.1.1 变更热点分析

**原理**：一个文件/模块被修改的频率越高，要么是核心业务频繁迭代，要么是质量差一直在救火。
结合缺陷提交（带 bug/fix 关键字）可以进一步分离"增长型变更"和"还债型变更"。

**分析步骤**：

1. 导出近 12 个月的提交记录
2. 按文件聚合修改次数
3. 按模块/包维度汇总
4. 标记高频修改且高缺陷率的区域 = 风险热区
5. 与模块负责人交叉验证：热区是否对应已知痛点

**工具命令**：

```bash
# Git 变更热点 Top 30
git log --pretty=format: --name-only --since="12 months ago" \
  | sort | uniq -c | sort -rn | head -30

# 按目录聚合变更量（Java 项目）
git log --pretty=format: --name-only --since="12 months ago" -- "*.java" \
  | awk -F/ '{print $1"/"$2"/"$3}' | sort | uniq -c | sort -rn

# 缺陷提交关联文件（假设提交信息含 fix/bug/缺陷）
git log --all --oneline --grep="fix\|bug\|缺陷\|hotfix" --name-only --since="12 months ago" \
  | grep -v "^[a-f0-9]" | sort | uniq -c | sort -rn | head -20
```

**产出物**：变更热点热力图、风险模块清单（变更频率 × 缺陷密度）。

#### I.1.2 知识归属与巴士因子

**巴士因子**：一个模块最少被几个人同时撞到，项目就没人能维护了。

**分析方法**：

- 按文件/模块计算主要贡献者（贡献 > 20% 代码的人数）
- 识别"单人模块"：90% 以上代码由同一人提交
- 识别"关键人"：手握 3 个以上核心模块的人
- 交叉验证：与团队访谈对比，看非正式知识枢纽是否与提交数据一致

```bash
# 单文件贡献者分布
git shortlog -sn -- path/to/file.java

# 按模块统计主要贡献者数量（需要脚本聚合）
# 输出格式：模块名 | 贡献者数 | Top1 占比 | 巴士因子
```

**低巴士因子模块 = 人员风险 + 交接盲区**，是接手遗留系统时必须优先做知识萃取的对象。

#### I.1.3 共同变更网络（隐性耦合探测）

**原理**：两个从来没有互相 import 的文件，如果每次提交都一起被改，它们之间存在**隐性耦合**。
这种耦合在静态分析里完全看不到，但重构时一动全崩。

**分析方法**：

- 取近 N 个月所有提交，每个提交的文件集合构成一条事务
- 计算文件对的共同变更频率（支持度 + 置信度）
- 输出高置信度的"隐形依赖对"
- 人工复核：这些文件为什么总是一起改？是业务规则散落、还是缺少抽象层？

**工具推荐**：`code-maat`、`git-of-theseus`、自研关联规则脚本。

> **实战经验**：在一个 50 万行的遗留系统里，共同变更网络通常能挖出 20%~30% 静态分析看不到的耦合。
> 这些耦合往往就是"为什么改 A 总是 B 出问题"的答案。

### I.2 运行时逆向与流量考古

静态代码分析只能告诉你"代码写了什么"，运行时分析才能告诉你"系统实际在做什么"。
对于遗留系统，两者不一致是常态——死代码、废弃分支、灰度开关、旁路逻辑比比皆是。

#### I.2.1 真实接口清单与调用拓扑

**目标**：从生产流量反推**实际被调用的**接口清单、调用方、调用频率。

**方法层级**：

| 层级 | 数据来源 | 能回答的问题 | 证据等级 |
|---|---|---|---|
| L1 网关/Nginx 日志 | 访问日志 | 哪些接口有人调、频率多少、来自哪里 | RUN-高 |
| L2 APM / 链路追踪 | SkyWalking / Pinpoint / Jaeger | 全链路调用关系、耗时分布、错误率 | RUN-高 |
| L3 应用日志 | 业务日志、方法级埋点 | 业务语义、内部流程 | RUN-中 |
| L4 抓包 / eBPF | tcpdump、bpftrace、sidecar | 最细粒度的实际行为 | RUN-最高 |

**关键动作**：

1. **拉一份 7 天内被调用过的接口清单**，与 Swagger/代码声明的接口对比
   - 声明了但没被调用的 = 候选废弃接口
   - 调用了但没在文档里的 = 隐式接口 / 历史兼容入口
2. **绘制调用拓扑**：入口 → 服务 → 下游服务 → 数据库/第三方
3. **标记关键路径**：按调用量 × 业务重要性排序，Top 10 路径必须做到可追踪、可解释

#### I.2.2 代码覆盖率考古（生产侧）

**目标**：回答"这段代码到底有没有人在用"——比单元测试覆盖率更有价值的是**生产覆盖率**。

**实现方式**：

- Java：`JaCoCo` agent 挂载到测试/预发环境跑真实流量
- Go：`-cover` 编译 + 测试流量
- 动态语言：线上采样 + 日志埋点

**输出**：

- 死代码候选区（生产环境 30 天从未执行到的代码块）
- 冷代码区（低频执行，可能是异常分支或边缘场景）
- 热代码区（必须保证质量和性能的核心路径）

> **注意**：死代码≠可以删。有些低频代码可能是年终结算、季度报表、灾备切换、合规审计等周期性触发逻辑。
> 删除前必须查变更历史、问知情人、查配置开关。

#### I.2.3 特征标记与差异实验

当你怀疑"代码 A 和代码 B 做的是同一件事"或者"这个分支已经废弃了"，
最可靠的验证方式不是读代码，而是**埋点观测**。

**方法**：在怀疑的位置加一条低开销的特征日志（带唯一标识），观测一个完整业务周期后看是否有命中。

```java
// 低开销特征埋点示例（只打计数，不打内容）
if (logger.isDebugEnabled()) {
    logger.debug("LEGACY_FEATURE: order_discount_path_v2_hit");
}
```

**适用场景**：

- 验证某段代码是否还在执行
- 验证某个调用方是否还存在
- 验证某个异常分支是否真的会发生
- 区分"文档说废弃"和"实际没人用"

**伦理与安全**：埋点不得记录敏感数据；只记特征 ID 和计数；观测期结束后移除。

### I.3 数据考古与语义反推

遗留系统里，**数据库才是最诚实的真相来源**。代码可以重构、服务可以替换，
但数据模型的演化轨迹记录了系统真实的业务变迁。

#### I.3.1 表年龄与字段考古

**方法**：

1. 按表的创建时间 / 最早数据时间排序
2. 每个字段看：最早出现的版本、注释变化、是否可空、默认值变化
3. 识别"补丁字段"：某张表突然多了一堆 `ext_`、`remark`、`temp_` 字段 = 业务快速迭代期的应急方案

**能揭示的信息**：

- 系统的业务演化路径（先有什么、后加什么）
- 哪些模块是"亲生的"、哪些是后来拼接的
- 字段语义漂移：同一个 `status` 字段在不同时期含义可能不一样

#### I.3.2 数据分布探针

看表结构只能知道"字段叫什么"，看数据分布才能知道"字段实际存了什么、有几种取值、空值率多少"。

**必查指标**：

- 每个枚举/状态字段的取值分布和占比
- 关键字段的空值率（空值率高 = 该字段可能已废弃或非强制）
- 时间字段的分布（最早/最晚数据、数据增长趋势）
- 关联表的 join 命中率（不是所有外键逻辑都有外键约束）

**示例 SQL**：

```sql
-- 状态字段分布探针
SELECT order_status, COUNT(*) as cnt,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) as pct
FROM t_order
GROUP BY order_status
ORDER BY cnt DESC;

-- 空值率探针
SELECT
  SUM(CASE WHEN pay_time IS NULL THEN 1 ELSE 0 END) * 100.0 / COUNT(*) as pay_time_null_pct,
  SUM(CASE WHEN refund_time IS NULL THEN 1 ELSE 0 END) * 100.0 / COUNT(*) as refund_time_null_pct
FROM t_order;
```

#### I.3.3 数据血缘与派生链路

当系统报表口径对不上、或者你想知道"这个数字从哪来"时，需要追溯数据血缘。

**追溯方法**：

1. 从报表/接口输出字段出发，反向找 SQL / Service 计算逻辑
2. 追踪每一步的转换、聚合、过滤规则
3. 标记"口径节点"：哪些地方做了业务规则过滤、哪些地方是纯技术转换
4. 输出完整血缘链：源表 → 中间表/视图 → 计算层 → 输出字段

**常见坑**：

- 同一指标在不同模块口径不一致（"订单金额"是含优惠还是不含？含税还是不含？）
- 报表有手工调整/冲正，与原始数据不可对账
- 异步计算有延迟，实时数和离线数对不上是正常的，但差值应有界

### I.4 高级代码分析技术

#### I.4.1 符号执行与路径探索

对于关键但复杂的业务逻辑（如定价、计费、权限判定），人工逐条读分支容易漏。
**符号执行**可以系统地探索所有可达路径，找出隐藏的边界条件。

**适用场景**：

- 复杂状态机的全状态验证
- 金额计算逻辑的边界条件发现
- 权限判定逻辑的越权路径探测

**工具**：

- Java：`Symbolic PathFinder`、`KLEE`（C 系）、`JPF`
- Python：`angr`（二进制级）、`CrossHair`
- 轻量级替代：基于 AST 的分支路径穷举 + 约束求解

**注意**：符号执行有路径爆炸问题，实战中只用于**核心且高风险**的小范围代码。

#### I.4.2 程序切片（Program Slicing）

**程序切片**回答一个问题："如果我想理解变量 X 在第 N 行的值，哪些代码是相关的？"
它从一个关注点出发，反向/正向追踪数据流和控制流，剪掉不相关的代码。

**为什么对遗留系统有用**：遗留系统的典型痛点是"一个方法 500 行，我只关心其中一小段逻辑"。
程序切片能自动帮你把不相关的部分剥离。

**工具**：

- Java：`Indus`、`Joana`、`Soot` 框架
- 轻量级：IDE 的"查找引用"+ 手动追踪（效果差但随时可用）
- LLM 辅助：给模型完整方法 + 明确关注点，让它做切片并标注每条语句的相关性

#### I.4.3 架构衰退检测（Architecture Fitness Function）

如果你打算在分析后做持续治理，而不是一次性报告，可以建立**架构适应度函数**——
把架构约束变成可自动检测的规则，每次构建都跑一遍。

**可检测的约束示例**：

- 模块 A 不得直接依赖模块 B（只能通过接口）
- Controller 层不得出现 DAO 直接调用（必须经 Service）
- 循环依赖不允许出现
- 新写的公共方法必须有单元测试
- 数据库表的 schema 迁移必须有回滚脚本

**工具**：

- Java：`ArchUnit`、`jQAssistant`、`Structure101`
- .NET：`NetArchTest`
- Node：`dependency-cruiser`
- 通用：定制化脚本 + CI 门禁

> **价值**：一次性分析报告 3 个月后就过期。适应度函数把分析结论沉淀为持续约束，
> 让架构质量不会随着时间自然衰退。

### I.5 AI 增强分析方法

#### I.5.1 LLM 辅助的代码理解工作流

直接把整仓库代码扔给大模型效果不好（上下文不够、噪声多、容易幻觉）。
正确的姿势是**先做结构化筛选，再做语义理解**：

**推荐工作流**：

```
1. 粗定位（传统工具）
   ├── 用 grep/rg 搜关键字，定位相关文件
   ├── 用知识图谱找调用链、依赖关系
   └── 用变更历史找热点模块

2. 精读取（按需切片）
   ├── 取目标方法 + 其直接依赖的类型和方法
   ├── 取相关 DTO / 实体定义
   └── 取相关测试用例（如果有）

3. 语义理解（LLM）
   ├── 解释这段代码做了什么
   ├── 还原业务规则
   ├── 识别隐含假设和边界条件
   └── 生成流程图 / 状态机

4. 交叉验证（回到代码和运行时）
   ├── LLM 的结论哪些有代码直接证据
   ├── 哪些是推断，需要用日志/数据验证
   └── 哪些是幻觉，直接排除
```

**关键原则**：LLM 输出的一切都当作**假设**，必须经过代码或运行时验证才能升级为结论。

#### I.5.2 对话式知识库构建

把分析过程本身变成对话式知识库，比写一份静态报告有价值得多。

**做法**：

- 每个重要发现都用问答形式记录（Q：订单状态有哪些？A：... 证据：...）
- 按照"业务问题 → 技术实现 → 证据来源"三层结构组织
- 新团队成员可以通过问答快速上手，而不用啃几百页文档

**工具形态**：

- 轻量：Markdown 文件 + 目录索引
- 中等：Obsidian / Notion 双向链接
- 高级：RAG 系统 + 代码嵌入 + 自然语言查询

#### I.5.3 自动化差异分析

当你需要对比两个版本、两个环境、两个相似模块的差异时，LLM 可以大幅提升效率：

| 场景 | 传统方式 | AI 增强 |
|---|---|---|
| 版本间行为差异 | 读 diff + 手动分析 | 让 LLM 总结语义级差异（不是行级 diff） |
| 重复代码识别 | 复制粘贴检测工具 | 让 LLM 判断两段代码是否"做同一件事"（语义级去重） |
| 接口兼容性判断 | 逐字段对比 | 让 LLM 识别破坏性变更 + 兼容变更 + 语义漂移 |
| 测试用例补全 | 手动写 | 基于代码逻辑生成边界测试场景 |

**风险提醒**：AI 做差异分析容易漏掉它不理解的隐含依赖。
涉及金额、权限、状态机的关键差异，必须人工复核。

### I.7 快速上手路径推荐

根据你的时间和目标，选择不同深度的分析路径：

**1 天快速摸底**（适用于：初步评估、面试准备、方案预研）

1. 跑变更热点 + 项目结构扫描（30 min）
2. 拉接口清单 + 数据库表清单（30 min）
3. 找 2-3 个核心业务流程，追踪端到端调用链（2 h）
4. 输出：一页架构概览 + 10 条关键发现 + 风险等级初判

**1 周深度分析**（适用于：技术选型、重构决策、接手准备）

1. 第 1 天：全局扫描 + 业务维度粗分析
2. 第 2-3 天：核心流程深度拆解（代码 + 数据 + 运行时三视角）
3. 第 4 天：技术债量化 + 一致性专项
4. 第 5 天：交叉验证 + 报告撰写 + 风险排序

**1 个月系统治理**（适用于：大型重构、微服务化、技术现代化）

1. 第 1 周：全维度分析 + 建立基线
2. 第 2 周：建立架构适应度函数 + 自动化检测
3. 第 3 周：试点治理（选一个模块做完整改造）
4. 第 4 周：总结方法论 + 制定分阶段路线图

## 附录 J：阶段化执行 SOP（来源：10B 方法论整合）

> 本附录整合自 10B-方法论-遗留系统业务分析，提供标准化的阶段化执行流程。
> 适用于需要明确执行里程碑、断点续跑和阶段门禁的深度分析场景。

### J.1 阶段总览

```text
B0 任务对齐与证据盘点
→ B1 系统上下文与角色识别
→ B2 业务能力地图与术语表
→ B3 关键业务切片选择
→ B4 端到端流程还原
→ B5 对象、状态、规则与不变量建模
→ B6 数据语义、血缘与指标口径分析
→ B7 契约、作用域、人工流程与外部依赖分析
→ B8 交叉验证、反例和风险评估
→ B9 报告、评审与知识沉淀
```

### J.2 执行状态机

统一使用以下状态流转：

```text
not_started → in_progress → passed
                           ├→ blocked（缺少权限/输入/外部条件）
                           ├→ awaiting_human（到达必须人工决策点）
                           └→ failed（阶段门禁未通过，可修正后重跑）

passed → superseded（输入基线变化，旧结论被替代）
blocked / awaiting_human / failed → in_progress
```

### J.3 各阶段说明

#### B0：任务对齐与证据盘点

**动作等级**：自动执行；任务边界和高影响决策目标须人工确认。

**输出**：`00-state/analysis-charter.md`、`00-state/execution-state.yaml`、`07-evidence/evidence-register.md`、`08-ledgers/open-items.md`

**完成判据**：决策问题可验证；输入基线有版本；关键缺口已登记；不存在把"全面了解系统"作为唯一目标的情况。

---

#### B1：系统上下文与角色识别

**动作等级**：自动执行，产物执行后送审。

**输出**：`01-context/system-context.md`、`01-context/actor-goal-matrix.md`、`01-context/external-systems.md`

**完成判据**：核心业务结果可以关联到责任角色；关键外部系统有方向和交换内容；未知调用方已显式登记。

---

#### B2：业务能力地图与术语表

**动作等级**：自动执行，产物执行后送审。

**能力卡模板**：

```markdown
## CAP-001 [能力名称]
- 业务域：
- 业务结果：
- 使用角色：
- 触发入口：
- 核心对象：
- 上游/下游：
- 重要性：核心/支撑/边缘
- 当前证据：
- 已知变体：
- 未知项：
```

**输出**：`02-capabilities/capability-map.md`、`02-capabilities/glossary.md`、`02-capabilities/capability-evidence-matrix.md`

**完成判据**：核心能力不依赖菜单层级解释；同义和歧义术语有记录；每项核心能力至少关联一份证据。

---

#### B3：关键业务切片选择

**动作等级**：AI 自动排序，最终范围须责任人确认。

**推荐评分**：

```text
优先级 = 业务关键性 + 风险影响 + 变化/事故强度 + 证据缺口
```

**完成判据**：首轮切片覆盖至少一个核心成功路径和一个关键失败/补偿路径；每条切片有选择理由和停止条件。

---

#### B4：端到端流程还原

**动作等级**：自动执行，产物执行后送审。

**业务切片模板**：

```markdown
# SLICE-001 [切片名称]

## 业务目标与范围
- 触发角色：
- 起点：
- 终点：
- 成功结果：
- 范围外：

## 主流程
| 步骤 | 角色/系统 | 输入 | 动作 | 状态/数据变化 | 外部副作用 | 证据 |
|---|---|---|---|---|---|---|

## 失败与补偿
| 失败点 | 可观察现象 | 重试 | 幂等 | 补偿/冲正 | 人工处理 | 证据 |
|---|---|---|---|---|---|---|

## 未知项和强反证
```

**完成判据**：流程贯通到最终业务结果；数据和外部副作用没有停在"调用某服务"；关键失败点有恢复方式或明确缺口；存在可复现案例。

---

#### B5：对象、状态、规则与不变量建模

**动作等级**：自动执行，产物执行后送审；业务不变量最终确认属于人工决策。

**状态转换模板**：

| 对象 | 当前状态 | 触发命令/事件 | 守卫条件 | 目标状态 | 副作用 | 可逆性 | 证据 |
|---|---|---|---|---|---|---|---|

**不变量示例**：

- 同一支付回调重复到达不得重复入账
- 成功退款总额不得超过有效实付金额
- 订单取消与库存释放最终必须可对账

**输出**：`04-models/core-objects.md`、`04-models/state-machines.md`、`04-models/business-rules.md`、`04-models/invariants.md`

**完成判据**：关键状态均有进入和退出解释；历史数据中的未知状态已登记；复杂规则有决策表；不变量具有验证方式。

### J.4 执行模式

| 模式 | 适用场景 | 最低范围 |
|---|---|---|
| 快速摸底 | 1-2 天内建立初步认知 | B0-B3 完整 + 1 条核心切片 + 1 条失败切片 + 初版能力地图和风险 Top 10 |
| 标准分析 | 1-3 周接手/重构准备 | B0-B9 全部 + 3-5 条高价值切片 + 完整评审记录 |
| 高风险专项 | 支付/订单/库存/金额/权限/租户/合规/迁移/下线 | 在标准模式上加严：不依赖平均抽样；核心不变量必须有可重复验证或对账方法 |

### J.5 常见失败模式

| 失败模式 | 表现 | 纠正方式 |
|---|---|---|
| 菜单即业务 | 按页面目录复制功能清单 | 用角色目标和业务结果重新归类能力 |
| 表名即语义 | 根据字段名直接定义业务概念 | 检查数据分布、代码使用和运行案例 |
| 代码即事实 | 读到实现就断言生产行为 | 核对部署版本、配置、日志和数据 |
| 访谈即事实 | 老员工说法直接进入报告 | 标记 HUM 证据并做独立交叉验证 |
| 只画正常流程 | 报告看起来整齐但无法解释事故 | 强制覆盖失败、重试、补偿和人工处理 |
| 忽略系统外流程 | 把 Excel、脚本和电话确认视为"非系统问题" | 纳入服务蓝图和责任边界 |
| 把无流量当废弃 | 观察短窗口后建议删除 | 检查业务周期、任务、历史调用方和配置开关 |
| 平均阅读全部代码 | 时间耗尽仍没有完整业务链路 | 风险排序后按切片纵向追踪 |
| 评分代替判断 | 用总分掩盖财务或安全单点风险 | P0 风险单列并设置阻断门禁 |
| 报告没有证据索引 | 结论无法复现或更新 | 结论 ID 关联证据、范围、时间和步骤 |

### J.6 最终自检清单

**入口与边界**：

```text
□ 决策问题、范围、环境、版本和时间窗口明确
□ 适用/不适用范围明确
□ 所有写操作和外部副作用均有授权
□ 系统内和系统外业务步骤均纳入分析
```

**业务完整性**：

```text
□ 角色、目标、能力、切片和核心对象可以互相追踪
□ 至少一条核心切片贯通到最终业务结果
□ 状态机包含守卫条件、失败行为和非法转换
□ 规则、例外和不变量分别记录
□ 正常、边界、重复、并发、超时、撤销和补偿已按适用性检查
□ 人工流程、离线脚本、周期性任务和历史数据没有静默遗漏
```

**证据与风险**：

```text
□ 关键结论有稳定 ID 和证据引用
□ 事实、推断、假设、建议和人工决策分离
□ 至少检查一个反例、边界或失败样本
□ 强反证已解释，证据冲突已登记
□ 风险接受和契约废弃没有由 AI 擅自决定
□ 日志、样本、截图和报告已脱敏
```

**可复现与维护**：

```text
□ 输入基线、执行状态和阶段产物已落盘
□ 验证步骤、时间、环境和结果可复现
□ 未覆盖风险和未知项已报告
□ 断点恢复位置明确
□ 文档保鲜条件和重新分析触发器明确
```

> 任一硬门禁不满足时，状态只能是 `blocked`、`failed`、`awaiting_human` 或 `draft`，不得声明业务分析完成。

### J.7 变更与保鲜机制

出现以下任一情况，应评估重跑受影响阶段：

- 核心业务规则、状态、权限或作用域发生变化
- 新增或废弃外部调用方、消息消费者、任务或数据接口
- 系统版本、部署拓扑、配置或数据库 Schema 发生重大变化
- 出现与当前模型不一致的事故、审计问题或数据异常
- 关键知情人离开团队且知识尚未完成交接
- 证据超过约定保鲜期，或观测窗口不能覆盖当前业务周期

更新时不得覆盖历史结论。将旧结论标记为 `superseded`，保留变化原因、影响范围、新证据和迁移关系。
