## 0. 定位与验证契约

### 0.1 文档定位

本文不是第二套系统分析 SOP，而是对文档 20 产物执行独立挑战、反证和验收的验证协议。

```text
文档 20：生成场景、概念、关系、规则、状态、模型、交互和实现映射
    ↓
文档 21：尝试用独立证据、最小反例、竞争解释和失败场景推翻这些结论
    ↓
通过/条件通过/不通过/不适用/证据不足
```

没有发现反例，只能说明结论在已声明范围、版本、时间窗口和证据强度内暂未被推翻，不等于证明模型绝对正确。

### 0.2 验证目标

反向验证必须回答：

1. 分析对象、版本、环境和覆盖范围是否固定？
2. 结论是否来自证据，而不是建模者自己的术语循环？
3. 是否存在能解释同一现象的更简单或更强竞争解释？
4. 模型能否正确预测未用于建模的边界、失败或历史样本？
5. 业务语义、实现和运行行为是否互相支持，矛盾是否被解释？
6. 安全、权限、租户、资金、库存、并发、兼容和恢复红线是否成立？
7. 修正后是否重跑原失败证据及受影响链路，而不是只修改文档？

### 0.3 验证前置输入

开始前至少具备：

- `SOP-00` G0-A 启动契约、G0-B 问题基线和任务模式；决策负责人/风险接受人只在决策支持、变更实施或风险接受时必需；
- 文档 20 的 DA0-DA8 适用产物，或缺失产物及影响说明；
- 证据索引、版本/环境/时间窗口和脱敏状态；
- 关键业务切片、规则、不变量、状态机和实现映射；
- 已知矛盾、未知项、假设、兼容候选和停止条件；
- 验证允许执行的只读动作及需要另行授权的动态实验。

缺少关键输入时，状态只能是“证据不足”，不得用“通过”或“不适用”掩盖。

### 0.4 独立性要求

- 高影响或不可逆决策应由未参与原建模的人复核；无法独立复核时，至少安排显式反方评审。
- 多份证据必须检查是否真正独立；多个文档共同引用同一代码或同一访谈不算交叉验证。
- 业务、开发、数据、运维和安全视角分别取证后再汇合，避免先共享一个解释而形成确认偏差。
- 建模者的理由可以作为待检验假设，不能作为该结论自己的验证证据。

### 0.5 安全边界

验证默认只读、最小权限、最小影响。生产写入、压测、故障注入、跨租户抽样、数据导出、缓存清理、消息重放和外部调用必须另行授权，并明确停止、回滚或清理条件。无法安全执行的实验应改用隔离环境、脱敏快照、历史证据或静态反例。

## 1. 验证的四层状态模型

### 1.1 证据质量

沿用 `SOP-00` 的证据类型 `SRC/CFG/DAT/RUN/CON/DOC/HUM`。每份关键证据至少评价：

| 属性 | 判断问题 |
|---|---|
| 直接性 | 是否直接观察结论，还是经过多层解释？ |
| 时效性 | 是否对应目标版本、环境和有效业务周期？ |
| 覆盖度 | 是全量、分层样本还是单个个例？ |
| 可复现性 | 另一位验证者能否按步骤得到相同结果？ |
| 独立性 | 是否与其他证据共享同一原始来源？ |

不计算没有统计基础的证据平均分。

### 1.2 结论确定性

| 标记 | 含义 | 决策用途 |
|---|---|---|---|
| 直接事实 | 指定范围内由源码、数据、配置、契约、运行或实验直接观察 | 可支持决策，但不得无条件外推 |
| 交叉验证结论 | 至少两类独立证据相互印证，且强反证已解释 | 可支持决策 |
| 经验判断 | 基于实践经验，依赖具体场景 | 只能辅助判断 |
| 推断 | 推理链明确但仍有证据缺口 | 用于设计下一验证动作 |
| 假设 | 尚未获得足够证据的候选解释 | 不得作为事实、根因或最终建议 |

### 1.3 结论验证状态

验证状态描述一条结论的证据进展，沿用 `SOP-00`：

```text
未验证 → 部分验证 → 交叉验证
                    ↘ 已反证
```

已反证内容不得删除，应保留原假设、反证证据和影响，防止团队重复走同一错误路径。

### 1.4 门禁结论

门禁结论描述某一阶段是否可以继续，与结论验证状态不是一回事。

| 门禁结论 | 含义 | 最低记录要求 |
|---|---|---|---|
| 通过 | 关键产物有充分证据，适用反证未推翻，阻断问题关闭 | 范围、证据、验证案例、复核人、复验触发 |
| 条件通过 | 仅在明确前提、护栏和有效期内可继续 | 前提、失效信号、责任人、到期时间 |
| 不通过 | 已发现可复现冲突、遗漏或不可接受风险 | 失败证据、影响、严重度、处置与复验 |
| 不适用 | 该检查对当前对象确实无意义 | 理由、范围和批准人 |
| 证据不足 | 目前无法作出判断 | 缺口、补证动作、责任人、期限 |

关键不变量、安全边界或兼容契约存在证据不足时，综合门禁不得判为“通过”。

### 1.5 问题严重度

P0-P3 只表示实际业务影响，不预绑定 D 编号，也不等同固定处理时限：

| 等级 | 典型判据 |
|---|---|
| P0 | 已发生或极可能造成越权、跨作用域访问、资金/库存不可逆错误、重大数据损坏、法规事故或核心系统不可恢复 |
| P1 | 核心场景错误、关键契约破坏、高影响风险缺少护栏或没有可靠恢复路径 |
| P2 | 有绕行、补偿或监控的一般缺陷，短期不破坏关键不变量 |
| P3 | 低影响表达、维护性或优化问题 |

评定必须记录影响范围、发生可能性、暴露面、可检测性、可恢复性、证据强度和受影响不变量。

### 1.6 机械完整性与事实真实性预检

进入语义反证前，先执行可机械检查的预检。预检不是深度验证，但预检失败足以阻止 G5：

| 检查 | 失败判据 | 门禁处理 |
|---|---|---|---|
| 基线可复现 | 只写“最新版本”，没有仓库提交、部署版本或环境窗口 | V0 证据不足 |
| 证据位置 | 正式证据含 `xxx`、省略路径、文件不存在、符号不存在或行号越界 | V6 不通过 |
| 内容一致 | 引用的枚举、状态、字段、方法签名或代码片段与基线原文不一致 | V6 不通过，并登记 X-* |
| 关系技术事实 | REL 中的字段、类、方法、API、消息、表、配置键无法在声明基线解析，或基数、空值、删除/级联行为没有对应约束、读写逻辑或限定样本 | V2 不通过；非关键缺口可判证据不足并登记 U-* |
| ID 唯一 | 多份文档重复使用同一证据/结论 ID 指向不同对象 | V7 不通过 |
| DQ 闭环 | 后续产物没有逐项引用和回答 G0-B 状态为“保留”的分析/决策问题 | V7 不通过 |
| 覆盖口径 | 声明百分比但没有总体、样本框、已覆盖、未覆盖和选择方法 | 删除百分比，V7 证据不足 |
| 评分口径 | 架构分数、星级、风险值或人日没有量表、样本、推导和责任人 | 不得作为结论，V7 不通过 |
| 事实分层 | 只有 SRC，却声称某环境实际高可用、性能达标或恢复有效 | 降级为实现能力，V6 证据不足 |
| 复核独立性 | 原分析者自行确认“证据准确、结论合理”，无独立复核或反方协议 | G5 不得通过 |
| 文档状态 | 上游仍是草稿/初稿，或决策支持/变更实施所需关键负责人待定，G5 却宣布正式完成 | G5 不通过 |
| 理解层交付 | 认知重建只有 DA/G/V 过程产物，缺少 SOP-00 §8 定义的理解层职责 | V7 不通过 |
| 业务广度 | 没有业务结果族样本框，仅以少量代码入口或切片代表整个分析对象，且未披露未覆盖范围 | V1/V7 不通过 |
| 跨文档规范事实 | 状态、枚举、文件格式、接口、消息、类/符号、配置、超时/重试或恢复声明相互矛盾 | V6/V7 不通过，并登记 X-* |

预检必须保留失败清单。修正文档文字不能代替核对原始证据；发现疑似虚构机制时，应从对应源码、配置、数据和运行入口重新取证。

## 2. 反证方法

### 2.1 从可验证命题开始

“模型合理”“架构清晰”不可直接验证。先把结论改写成单一、带范围、可被推翻的命题：

```text
弱命题：订单号是唯一的。

可验证命题：在生产集群 A 的新订单链路中，2026-07-01 之后创建的订单号
在租户作用域内唯一；历史导入、归档库和离线单据暂不在结论范围内。
```

### 2.2 建立竞争解释

对重要现象至少列出一个替代解释。例如“订单重复”可能来自：

- 创建接口缺少幂等；
- 上游生成了两个不同业务请求；
- 消息重复消费；
- 历史导入重复；
- 查询联表或同步副本造成展示重复。

优先执行能最大区分竞争解释、风险最低的验证动作，而不是不断收集只支持原假设的证据。

### 2.3 使用最小反例

最小反例是能以最少前提推翻命题的输入或状态。常用构造：

| 模型对象 | 最小反例方向 |
|---|---|
| 概念边界 | 一个对象同时满足两个本应互斥的概念，或两者无法判别 |
| 关系 | 方向、基数、条件、时间或权威源不成立的单个实例 |
| 规则 | 同一输入同时命中冲突规则，或缺少裁决顺序 |
| 不变量 | 一条合法操作路径即可破坏必须成立的事实 |
| 状态机 | 不可达状态、非法跃迁、死状态或多条路径产生不一致结果 |
| 聚合边界 | 一个业务原子操作必须跨边界才能守住不变量 |
| 交互 | 超时、重复、乱序或部分成功产生不可解释状态 |
| 实现映射 | 一个运行入口、写入者或消费者无法回到任何业务语义 |

### 2.4 使用保留样本和预测

模型建立时不要用尽所有样本。保留未参与建模的历史、失败、边界或不同租户/渠道样本，让模型先预测结果，再与实际行为比较。只能解释训练样本、不能预测保留样本的模型，不足以支持高影响决策。

### 2.5 反事实与删除测试

对每个模型元素提问：

- 删除它后，哪个场景、规则、状态、数据或调用方无法解释？
- 合并它与另一个概念后，是否丢失生命周期、权限、权威源或历史口径？
- 反转关系方向或改变基数后，会出现什么业务矛盾？
- 如果外部依赖成功但本地失败，模型还能解释结果吗？
- 如果系统扩大 10 倍、规则变化或调用方升级，哪个约束先失效？

## 4. 分门禁验证

### 4.1 V0：启动与问题基线准入

V0 分两次执行。V0-A 在证据侦察前验证安全启动条件；V0-B 在 DA0-B/DA0-C 后验证问题质量。不得因为认知重建的用户没有预先提供 DQ 而判定 V0 失败。

#### V0-A：启动契约

**挑战问题**：

- 原始提示、任务模式、分析对象、证据范围和输出位置是否明确？
- 只读动作、禁止动作、旧文档处理和另行授权边界是否记录？
- 本地仓库基线能否取得；暂缺的部署、配置、数据库、环境和时间窗口是否登记为未知？
- 当前动作是否在授权范围内，样本和报告是否满足脱敏与留存要求？
- 是否误把请求者当成业务裁决人、风险接受人或变更授权人？

**最小反证**：发现下一步计划包含生产写入、外部调用或覆盖旧文档，但启动契约没有相应授权。

**通过条件**：认知重建的对象、可访问证据、输出位置和只读边界明确；决策支持或变更实施还满足对应模式的最低输入。未知部署/运行基线只限制结论层级，不阻止源码范围的只读侦察。

#### V0-B：候选问题质量

**挑战问题**：

- 每个候选 DQ 是否能追溯到 `E-SRC/E-CON/E-CFG/E-DOC/...`，而不是来自 AI 想象或模板？
- DQ 是否描述角色、意图、结果、规则、状态、失败或恢复等业务问题，而不是目录、类、表或接口清单？
- 候选问题是否覆盖初始角色、业务结果、关键状态、主要失败和恢复信号？
- 候选切片是否能区分至少一个重要 DQ 的竞争解释，并具备较高信息增益？
- 新证据出现后，DQ 是否允许增加、合并、改写或反证，并保留演进理由？
- 行业经验和 AI 常识是否仅用于搜索和提出假设，没有写成项目事实？

**最小反证**：随机抽取一个候选 DQ，无法找到来源证据，或删除技术名词后没有任何可判定的业务问题。

**通过条件**：G0-B 中至少一个高信息量 DQ 有可复核来源并关联首批业务切片；问题覆盖与未覆盖范围明确；关键版本冲突已解释或登记 U/X。认知重建无需业务裁决人批准候选 DQ 即可进入 DA1。

### 4.2 V1：场景、上下文与概念

**挑战问题**：

- 是否先判断分析对象属于核心业务域、支撑业务能力、技术平台能力还是混合类型，并说明它拥有与不拥有的事实？
- 是否先形成业务结果族/能力样本框，再选择代表切片；未覆盖结果族及影响是否披露？
- 场景是否写清角色、触发、目标、成功、失败和结果未知？
- 支撑能力是否说明上游事实、权威来源、交付物/结果、接收角色、有效时点和业务后果？
- 页面功能是否被误当成业务场景？
- 概念是否来自至少一个场景，并能解释其业务价值？
- 同名词在不同上下文是否被错误合并？同义词是否被重复建模？
- 概念边界能否用包含/排除条件判断？
- 主路径之外，撤销、冲正、补偿、人工修复和历史场景是否覆盖？

**反证方法**：交叉角色访谈、入口/输出反查结果族、保留样本预测、概念删除测试、边界对象测试、不同版本术语对照；随机抽取未入选入口，检查是否落入已有结果族或暴露新结果族。

**通过条件**：分析对象业务位置有依据；结果族样本框和代表切片选择可解释；高价值/高风险场景可判定；核心概念有上下文、边界和证据；歧义有裁决或未知项。

### 4.3 V2：概念关系与责任

**挑战问题**：

- 每条关系是否有明确业务谓词，而不只是“关联”？
- 方向、基数、可选性、时间和成立条件是否来自证据？
- 关系是否错误假设对称或传递？
- 业务关系、对象引用、数据库外键和查询导航是否混淆？
- 创建者、修改者、确认者和权威源是否明确？
- 是否存在两个系统都能独立修改同一权威事实？
- 循环是否是无害查询关系，还是所有权/状态推进死锁？

**反证方法**：反转方向、改变基数、构造跨上下文角色、查询写入者、追踪删除/修改语义、寻找第二权威源。

**通过条件**：关键关系有语义、条件、责任和证据；权威源唯一或冲突协调机制明确。

#### V2-扩展：关系契约质量与真实性门槛（DA3 v2.9+）

> 本扩展用于验证 DA3 产物是否满足 SOP-00 v3.11 的关系契约适用性、UI 配置链路和机械真实性门槛。

**挑战问题**：

- 每个核心 REL 是否逐项判定关系定义、建立与维护机制、字段连接、关联路径、约束、使用、修改影响、级联和实现证据？
- 标为“无/不适用”的维度是否有直接证据、理由和影响，而不是为了过门禁随意填写？
- 关系定义与具体关系实例是否分开，直接路径（1-hop）与间接路径（2-hop 及以上）是否分开？
- 间接路径中的每个中间对象是否有来自项目证据的职责，是否错误套用了与本系统无关的通用原因？
- 是否把“配置型/静态”误写成“运行时不可改变”，而忽略配置维护期的授权变更证据？
- 声称基础资料关系由 UI 配置时，是否先确认维护入口确实包含 UI，并验证了页面控件、权限/候选范围、请求契约、服务端校验、持久化载体、生效读取点和审计/历史处理？非 UI 入口是否错误套用了 UI 全量清单？
- 是否发现同一能力的多个实现却直接合并，遗漏独立 `IMPL-*` 谱系和 SOP-10 裁决？

**关系契约完整性检查表**：

| 检查项 | 要求 | 验证方法 |
|---|---|---|---|
| 适用性判定 | 每个核心 REL 的各维度均明确为有事实/无/不适用/证据不足 | 逐 REL 核对依据；空白或无依据的“无/不适用”使 V2 不通过 |
| 标识可解析 | 字段、类、方法、API、消息、表和配置键存在于声明基线 | 重新定位声明与引用；关键标识任一无法解析即 V2 不通过 |
| 字段真实性 | 字段归属、类型、空值、关联和写入方式与实现一致；跨层别名有映射证据 | 对照 Schema、模型、契约、映射与真实读写点 |
| 基数/可选性 | 结论有约束、模型声明、查询/写入逻辑或限定样本支持 | 改变基数并构造边界样本；只有样本时限制结论范围 |
| 删除/级联 | 删除、修改、软删除、拒绝和历史保留行为有实现证据 | 追踪 Schema、持久化配置、服务逻辑和测试；未搜索到不等于“无” |
| UI 配置链路 | 仅当入口含 UI 时要求页面到持久化/生效读取点闭合；非 UI 入口不强制 UI 段 | 先核维护入口类型，再逐段核对适用证据 |
| 路径与职责 | 直接为 1-hop，间接为 2-hop 及以上；中间对象职责来自项目事实 | 删除中间对象或尝试直连，检查业务规则、作用域、生命周期或权威性是否改变 |
| 3跳路径配额（强制） | DA3 必须至少存在 1 条 3 跳及以上业务路径契约（BP-*），含中间对象职责、"为什么经过中间对象"（至少 2 条业务原因）、级联行为 | 对照 SOP-00 §9.5.4 与 §9.5.4a 合格范例逐项核对；缺失或深度不足（只写"A 关联 B，N:1"）即 V2 不通过 |
| 模板加载记录（强制） | 每个 DA 文档开头必须包含"模板加载记录"（读取了哪个独立模板文件 `SOP-00-DA{n}-模板.md`、门禁检查结果） | 无加载记录即视为未执行 SOP-00 §0 执行前置第 1/6 条，V 验证不通过 |
| 多实现隔离 | 每个实现有独立 `IMPL-*` 和证据，合并前经过 SOP-10（`IMPL-*` 定义与注册见文档 20 §3.1 稳定 ID 表） | 反查入口、配置、版本和运行路由，寻找遗漏实现 |
| 关系路径总图 | 只呈现已证实的直接、间接及主备/冗余路径 | 图中每条边反查 REL 和证据；无证据边删除或标未知 |

**最小反证**：

- 随机抽取一个 REL，将字段、API、类、表和配置键逐一在声明基线重新解析
- 对一个 UI 配置关系，从页面选择动作反追到权威存储，再从业务读取点正向验证是否实际生效
- 改变一个关系的基数、空值或删除方式，检查模型声称的约束是否仍成立
- 对一个间接关系移除中间对象，检查证据是否真的证明不能直接关联；无证据时降级为未知，不补写理由
- 从路由、开关、版本目录或历史入口寻找第二实现，检查是否被错误合并

**通过条件**：所有核心 REL 的适用维度有可解析证据或有依据的“无/不适用”；关键字段、符号、API、基数和删除/级联行为真实；对 UI 维护入口的关系链路在声明范围内闭合；配置型关系未被误标为运行期不可变更；多实现已分谱系；关系图只包含可回溯边；**DA3 至少存在 1 条 3 跳及以上业务路径契约且达到 SOP-00 §9.5.4a 范例深度**。任一关键标识无法解析、关键链路由猜测补齐、3 跳路径缺失、或原分析者仅以自检替代独立复核时，V2 不通过；非关键证据缺口明确限制结论时可判“证据不足”。

V2 的关系真实性抽检应由未编写该 REL 的复核者执行；人员受限时，必须使用显式反方协议，重新定位原始证据并主动寻找第二实现、反向基数和删除反例。原分析者勾选自己的模板不构成复核证据。**按 SOP-00 §0 执行前置第 5 条，V2 及全部 V 验证必须由未参与 DA 生成的独立 agent 执行，禁止生成者自检，验证记录必须输出到验证附件。**

### 4.4 V3：规则、不变量与状态机

**挑战问题**：

- 规则是否有来源、适用条件、生效版本、执行点和冲突优先级？
- 派生结果是否使用正确时点和权威输入？
- 不变量是否把业务事实和保护机制分开？
- 所有合法入口，包括任务、消息、批量、人工和数据修复，是否都保护不变量？
- 状态是否业务可判定，还是页面标签和技术处理阶段混杂？
- 是否存在不可达状态、非法跃迁、死状态、缺失终态或补偿后悬空状态？
- 并发、重复、超时、部分失败和历史非法数据是否进入模型？

**反证方法**：决策表冲突测试、状态遍历、属性/性质测试、并发交错、历史数据扫描、失败点枚举。

**通过条件**：关键规则可判定；状态迁移完整；关键不变量在所有已知写入口有保护、检测和恢复证据。

### 4.5 V4：领域模型与数据所有权

**挑战问题**：

- 概念是否被机械映射为实体或数据库表？
- 项目未采用相应 DDD 语义时，是否仍为实现对象强贴聚合根、值对象或领域事件标签？
- 实体身份是否稳定，是否错误使用可变邮箱、手机号或名称作为身份？
- 值对象是否按属性相等，历史快照是否在正确时点固定？
- 聚合边界是否来自原子维护的不变量，而不是服务数量或对象个数？
- 跨聚合规则是否有一致性时限、状态机、补偿或对账？
- 数据权威源、副本、缓存、索引、报表和历史快照是否区分？
- 业务标识的租户/组织/时间作用域是否准确？
- **每个核心实体是否有"为什么这样设计"的业务解释？**（设计动机、业务不变性、替代方案）
- **每个关系是否有业务语义说明？**（为什么是 N:1 而不是 1:1？这个关系解决什么业务问题？）
- **每个聚合根是否有边界决策依据？**（什么不变量必须原子维护？跨聚合一致性策略是什么？）
- **每个领域服务是否有"为什么需要它"的解释？**（为什么不放在实体内部？跨聚合协调/复杂查询/基础设施封装？）
- **每个外部依赖是否有业务意义和一致性策略？**（如何处理外部系统故障/超时/数据不一致？）
- **每个跨限界上下文边界是否有集成方式和数据权威说明？**（哪个上下文是权威源？跨上下文事务如何处理？）
- **P0/P1 核心实体是否有完整对象全景卡（8 维度）？**（身份/结构/关系/行为/交互/生命/失败/实现；缺失维度是否显式登记 U-* 及理由？生命周期时间线叙事是否可复核？失败维度是否覆盖检测、恢复和人工介入？）

**反证方法**：删除 DDD 标签后检查业务解释是否仍成立、身份变更测试、聚合拆分/合并测试、跨边界事务失败、历史快照对比、双写权威冲突、数据血缘反查。

**通过条件**：模型类型、身份、边界、所有权和数据生命周期有业务与实现证据；DDD 类型满足条件化门槛，证据不足时使用中性类型；不存在未解释的多权威写入；**每个实体、关系、聚合根、领域服务、外部依赖和跨限界上下文边界都有"为什么这样设计"的业务解释，缺失则 V4 阻断**；**P0/P1 核心实体对象全景卡 8 维度完整（生命周期叙事可复核、失败维度覆盖检测/恢复/人工介入），缺失则 V4 阻断**。

### 4.6 V5：行为、事件、交互和恢复

**挑战问题**：

- 行为是否有业务目的、前置条件、后置条件和拒绝语义？
- 外部副作用是否与领域决策、数据提交和消息发布形成可靠边界？
- 事件是否表达已发生的重要事实，而不是 CRUD 日志？
- 领域事件与面向消费者的集成契约是否分离并可版本化？
- 重复投递、并发消费、处理成功但确认失败时是否重复业务结果？
- 同步/异步选择是否符合结果确认需求、一致性时限和恢复成本？
- 超时是否被误写成失败？结果未知如何查询、重试、对账或人工接管？
- 失败、补偿失败和恢复顺序是否可演练？

**反证方法**：重复提交、重复消息、乱序、并发、慢依赖、远端成功本地失败、消息发送前后崩溃、恢复中再次失败。

**通过条件**：成功、失败和结果未知均有状态；资金、库存、权益和消息写入具备可验证的幂等、原子、补偿或对账策略。

### 4.7 V6：实现与运行映射

**挑战问题**：

- 每个关键业务语义是否能定位到页面/入口、契约、代码、数据和运行证据？
- 每个关键写入口、消息消费者、任务和人工脚本能否回到业务场景和不变量？
- 源码是否部署，配置/开关是否使路径生效，数据是否显示实际使用？
- 是否存在数据库直连、动态 SQL、反射、脚本、批任务、灰度、旧消费者或旁路入口？
- 文档、代码、配置、数据和运行冲突是否按版本/环境解释？
- 日志、Trace 和报告是否最小化并脱敏？

**反证方法**：调用方反查、生产者/消费者搜索、配置变体对照、运行采样、数据写入者追踪、死代码/隐藏入口检查。

**通过条件**：关键追溯链无未解释断点；静态和运行差异进入 X/U 台账；结论没有超出证据覆盖范围。

### 4.8 V7：综合收敛与交付

**挑战问题**：

- 端到端追溯是否从原始目标和保留的分析/决策问题到监控/审计双向成立？
- 重要结论是否只有支持证据而没有反证记录？
- `As-Is`、合理性判断、`To-Be` 和迁移建议是否分开？
- 兼容候选、历史数据、调用方和隐性行为是否在建议中被考虑？
- 认知重建是否披露阻断问题和证据不足；决策/变更模式的条件通过和风险接受是否有责任人及期限？
- 修正后是否重跑原失败用例和受影响链路？
- 报告是否回答 G0-B 保留的分析/决策问题，而不是汇总所有发现？
- 每个 DQ 是否在闭环矩阵中给出结论、证据、反证/未知项、可选行动和成立条件？
- 是否存在可直接导航的阅读入口，以及业务全景、业务故事、失败恢复、实现证据五类理解职责？
- 面向理解的主文档是否按业务结果和因果重新综合，而不是改名、拼接 DA 文档或重复源码和表格？
- 主文档是否能用一个真实切片解释业务因果，并说明上游事实、交付义务、接收者、有效时点和失败后果？
- 删除类名、方法名、接口名和表名后，业务叙事是否仍然成立？
- 不看源码和过程附件，读者能否在十分钟内回答：系统为何存在、谁依赖它、交付或维护哪些业务事实、代表故事如何成功/失败、系统拥有什么与不拥有什么？
- 跨文档规范事实表是否已核对状态、枚举、文件格式、接口、消息、类/符号、配置、超时/重试和恢复声明？
- 证据附件是否通过 §1.6 的机械完整性与事实真实性预检？

**反证方法**：随机抽取结论反查证据、随机抽取实现上溯语义、十分钟盲读复述、删除技术标识后复述、跨角色复核、跨文档事实抽样、保留切片预测、最挑剔评审者审查。

**通过条件**：理解层与复核层同时存在；十分钟理解测试全部可回答；业务广度、代表深度和未覆盖范围明确；跨文档规范事实无未解释冲突；关键结论经交叉验证，复验触发和范围限制明确。认知重建中，未修复 P0/P1 必须显著披露且不得被写成系统已安全、可上线或风险已接受，但其存在不自动导致分析报告 G5 失败；决策支持或变更实施若要批准相关行动，则适用 P0 必须关闭，P1 必须关闭或由具备权限的风险责任人限时接受。关键不变量证据不足时，不得对其作确定性保证。

## 5. 验证执行协议

### 5.1 风险驱动选取

验证不机械从 D1 跑到 D43。先按以下因素选择：

- 业务影响：资金、库存、权益、权限、隐私、核心流程；
- 不确定性：证据冲突、单一来源、动态配置、历史分叉；
- 变更不可逆性：数据、契约、状态机和外部依赖；
- 暴露面：调用方、租户、用户、消息消费者和数据规模；
- 可恢复性：能否回滚、冲正、补偿、对账或人工修复。

### 5.2 七步验证循环

```text
1. 固定对象、范围、版本和原结论
2. 把结论改写为可证伪命题
3. 列竞争解释和最小反例
4. 选择最小、最安全、区分度最高的验证动作
5. 执行并记录原始证据、环境、步骤和限制
6. 更新结论状态、问题、矛盾和未知项
7. 修正后重跑原反例及受影响链路，再作门禁判断
```

连续多次动作没有减少关键不确定性时，应暂停并重新检查问题定义、证据独立性和竞争解释。

### 5.3 验证案例模板

```text
VCASE-{序号}
关联门禁/D项：
被验证对象与版本：
原结论/假设：
可证伪命题：
竞争解释：
最小反例或预测：
验证方法与授权边界：
输入/样本/环境/时间窗口：
预期区分结果：
实际结果与原始证据：
证据质量与覆盖限制：
结论状态变化：
影响与严重度：
修正、责任人和复验触发：
```

### 5.4 修正闭环

问题关闭必须同时满足：

- 原失败证据不再出现；
- 相关不变量和合法历史行为仍成立；
- 受影响的调用方、数据、契约、任务、消息和运行链路已回归；
- 未通过删除测试、放宽断言、绕过错误或改变验收标准制造通过；
- 结论、证据、范围、残余风险和复验触发已更新。

## 6. D1-D43 检查库

D1-D43 是可选检查工具，不是固定评分表。执行时记录选用理由；未选用不等于“不适用”。

### 6.1 D1-D5：场景与概念

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D1 | 概念语义必要性 | 删除该概念后，哪个业务判断或沟通会失真？ |
| D2 | 概念边界 | 包含、排除和灰区对象能否判别？ |
| D3 | 依赖与上下文 | 它依赖什么、在哪个上下文成立、是主体还是角色/视图？ |
| D4 | 场景和生命周期覆盖 | 正常、边界、失败、撤销和历史阶段是否覆盖？ |
| D5 | 语义一致与版本 | 文档、角色、代码和报表中的定义是否按版本对齐？ |

### 6.2 D6-D10：关系与责任

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D6 | 关系证据 | 关系是否来自真实业务事实，而不是画图便利？ |
| D7 | 方向与可导航性 | 所有权、主引用、反向查询和业务方向是否混淆？ |
| D8 | 关系语义性质 | 对称、传递、反身等性质是否被错误假设？ |
| D9 | 基数、条件与时间 | 可选性、上限、作用域、生效和失效条件是否完整？ |
| D10 | 循环与权威冲突 | 循环是查询关系还是形成所有权、状态或依赖死锁？ |

### 6.3 D11-D15：领域模型元素

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D11 | 模型元素必要性 | 它是否承载独立身份、规则、生命周期或责任？ |
| D12 | 身份稳定性 | 标识是否稳定，唯一范围是否准确？ |
| D13 | 内聚性 | 行为是否围绕同一身份、生命周期和不变量？ |
| D14 | 聚合边界 | 边界是否对应一次操作需原子维护的不变量？ |
| D15 | 引用与所有权 | 对象引用、ID、快照、外键和读模型是否选择正确？ |

### 6.4 D16-D19：属性与数据语义

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D16 | 属性必要性 | 属性是否服务规则、状态、查询、审计或兼容？ |
| D17 | 来源与权威 | 谁产生、修改和解释该值，能否实际获取？ |
| D18 | 派生与快照 | 公式、输入、舍入、时点和历史快照是否正确？ |
| D19 | 约束完整性 | 类型、范围、空值、唯一、作用域和跨字段约束是否一致？ |

### 6.5 D20-D24：行为

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D20 | 行为必要性 | 行为对应什么业务命令、目标或规则？ |
| D21 | 行为粒度 | 是否既能表达一个业务意图，又未隐藏关键步骤？ |
| D22 | 前置条件 | 权限、状态、输入和依赖事实是否完整？ |
| D23 | 后置与结果未知 | 成功、拒绝、失败和未知结果分别是什么状态？ |
| D24 | 副作用边界 | 数据写入、外部调用、消息、通知和审计如何原子或恢复？ |

### 6.6 D25-D28：事件

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D25 | 事件业务意义 | 是否表达已发生的重要业务事实，而非 CRUD 噪音？ |
| D26 | 事件覆盖与版本 | 必要事实、Schema、生产者/消费者和兼容窗口是否完整？ |
| D27 | 因果、审计与重放声明 | 因果链可追踪吗；若承诺重放/重建，恢复证据成立吗？ |
| D28 | 重复处理安全 | 重复、并发和确认失败时是否产生重复业务结果？ |

事件本身不承担“幂等”；需要验证的是命令和消费者的重复处理安全。普通状态存储系统不要求从事件重建全部状态，只有明确采用事件溯源或承诺重放时才验证该能力。

| D32 | 契约完整性 | 输入、输出、错误、权限、幂等、版本和废弃是否明确？ |
| D33 | 时序与重试 | 顺序、超时、重试、乱序、积压和恢复时序是否正确？ |

### 6.8 D34-D37：规则、约束与状态

| ID | 检查主题 | 核心问题 |
|---|---|---|---|
| D34 | 不变量覆盖 | 所有写入口和恢复路径是否保护关键不变量？ |
| D35 | 规则冲突与优先级 | 同时命中时谁优先，裁决依据是什么？ |
| D36 | 跨边界传播 | 规则和约束跨聚合/系统后如何检测、协调和纠偏？ |
| D37 | 边界与异常 | 空值、极值、时间、并发、失败、历史和人工路径是否覆盖？ |

| D43 | 容量、SLO 与降级 | 峰值和数量级增长下哪个约束先失效，如何安全降级和恢复？ |

## 7. 红线门禁

以下问题一经证实，必须按实际影响阻断门禁，不能因历史存在而标为“兼容行为”：

- 未授权访问、越权或跨租户/组织/门店作用域访问；
- SQL/命令注入、任意资源访问、硬编码或泄露密钥/token/支付凭证；
- 支付、订单、库存、余额、权益或 MQ 可重复写缺少可验证幂等和并发保护；
- 状态或数量更新非原子，能够产生资金、库存或账务完整性错误；
- 敏感请求/响应完整落日志、报告、截图或分析样本未脱敏；
- 破坏已有调用方、历史数据或外部契约，却没有迁移、兼容、回滚或前向修复路径；
- 为制造通过而删除失败用例、放宽断言、绕过错误或改变验收标准。
- 生成目标仓库中不存在的类、方法、接口、消息、状态、表、配置或恢复机制，并将其标记为已验证事实；
- 使用无效证据位置、占位行号或与原始证据不一致的代码片段支撑关键结论。

红线修复仍需评估调用方、历史数据、迁移、审计、恢复和残余风险。

## 9. 示例：订单提交反向验证

### 9.1 待验证结论

```text
C-ORDER-01（推断）
命题：相同租户、客户和购物车版本的重复提交只会产生一个有效订单，
且最多产生一次有效库存预留。
```

### 9.2 竞争解释

- API 使用购物车版本作为业务幂等键；
- 只有前端防重复点击，后端并不幂等；
- 订单创建幂等，但库存预留不是；
- 数据库唯一约束只覆盖新链路，旧链路或任务入口可绕过；
- 两个订单均创建，查询层只展示一个。

### 9.3 最小区分性验证

| 验证动作 | 预期区分 | 安全边界 |
|---|---|---|---|
| 查找所有订单创建入口及幂等键 | 区分前端防重与后端保证 | 静态只读 |
| 检查唯一约束、事务和 Outbox/消息发送边界 | 判断订单与库存请求是否共同可靠 | Schema/代码只读 |
| 使用隔离环境并发提交同一业务键 | 验证竞态与重复结果 | 需测试授权和隔离数据 |
| 对照订单、Outbox、库存处理和 Trace | 判断副作用是否重复 | 脱敏、限定样本 |

### 9.4 门禁判断示例

若发现订单唯一约束有效，但库存消费者用非原子的缓存 TTL 去重，则：

- D39、D28：不通过；
- 原命题 `C-ORDER-01`：已反证；
- V5：不通过；
- 严重度按重复库存预留的实际业务影响评定，不因属于 D28 固定为某级；
- 修正后重跑同一并发/重复样本，并验证消息确认失败、缓存丢失和历史消费者路径。

## 10. 完成与复验

### 10.1 完成判据

- [ ] V0-V7 适用门禁均有结论、证据和复核人；
- [ ] 高风险结论被改写为可证伪命题，并执行了反例或竞争解释验证；
- [ ] 关键结论达到直接事实或交叉验证，强反证已解释；
- [ ] D1-D43 按风险选用，未选项不伪装为不适用；
- [ ] 安全、租户、权限、资金、库存、并发、兼容和恢复红线已检查；
- [ ] 失败证据、已反证假设、矛盾和未知项未被删除；
- [ ] 修正后重跑原反例及受影响链路；
- [ ] 门禁结论不依赖伪精确总分；
- [ ] 条件通过有护栏、责任人、失效信号和到期时间；
- [ ] 综合结论明确范围限制、残余风险和复验触发。
- [ ] 已通过 §1.6 机械完整性与事实真实性预检；占位路径、越界行号和源码不一致项为零。
- [ ] 每个 G0-B 保留的分析/决策问题均在 DQ 闭环矩阵中获得条件化回答，候选/合并/已反证状态可追溯。
- [ ] 认知重建没有因用户未预先提供 DQ 或业务负责人而失败；正式决策、变更和风险接受仍有具备权限的负责人。
- [ ] G5 由独立复核人或显式反方协议完成，没有由原分析者自我确认质量。
- [ ] 认知重建已交付 SOP-00 §8 的理解层职责；只有 DA/G/V 过程产物时未判定完成。
- [ ] 已执行十分钟理解测试和删除技术标识后的业务叙事测试，结果可复核。
- [ ] 已建立业务结果族样本框并披露未覆盖范围，没有用少量入口冒充完整业务全景。
- [ ] 已核对跨文档规范事实，状态、枚举、文件格式、接口、消息、类、配置和恢复声明无未解释冲突。
- [ ] P0/P1 核心实体对象全景卡 8 维度完整，生命周期叙事可复核，失败维度覆盖检测/恢复/人工介入，缺失维度已登记 U-* 及理由。

### 10.2 复验触发

以下变化至少重跑受影响门禁：

- 业务规则、状态机、权限或租户作用域变化；
- API、消息 Schema、调用方或消费者变化；
- 数据迁移、历史修复、分库分表或权威源变化；
- 部署版本、配置、功能开关或灰度范围变化；
- 发生事故、对账差异、重复写、越权或恢复失败；
- 原条件通过前提失效、到期或关键未知项获得新证据。
