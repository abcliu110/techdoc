# 业务多实现统一建模与冲突治理方法论

> 版本：v1.0  
> 适用对象：长期演进系统、客户定制系统、产品线、新旧系统重构与迁移  
> 理论定位：解释业务提炼、统一建模和冲突治理的经典模型及组合方法  
> 执行流程：`SOP-10-业务演进多实现归一与重构迁移.md`  
> 目标评审：`SOP-09-业务设计合理性评审.md`

## 0. AI 执行入口

### 0.1 最小输入

- 需要提炼的业务能力、分析目的和范围。
- 已知历史实现、客户/渠道/区域/版本及当前使用状态。
- 各实现的流程、规则、状态、数据、副作用和运行证据。
- 明确继续支持、允许改变和必须兼容的业务约束。
- 具备业务裁决权、数据责任和迁移责任的负责人。

输入不足时，AI 只能输出候选模型、竞争解释和补证动作，不能自行决定冲突业务语义。

### 0.2 核心输出

```text
业务能力边界
+ 历史实现谱系
+ 规范术语与业务事实
+ 稳定核心和不变量
+ 业务模式与变化点
+ 变体关系和冲突矩阵
+ 候选目标模型
+ 旧新映射、验证与退役方案
```

### 0.3 核心原则

> 统一建模不是消灭差异，而是让真实差异具有明确语义、适用边界、组合规则和生命周期；冲突治理不是增加更多分支，而是在副作用发生前形成唯一、合法、可解释的业务决策。

## 1. 问题定义

长期维护系统通常按单次需求局部扩展：原实现不能满足新客户时，修改原逻辑、复制一套流程、增加客户分支或重写新版本。每次变更可能局部正确，但长期形成多个实现竞争同一业务事实。

```text
同一业务能力
├─ 原始实现
├─ 客户定制实现
├─ 渠道/区域实现
├─ 新版本实现
├─ 历史兼容实现
└─ 存量或逆向流程实现
```

新系统的目标不是求历史实现代码并集，而是回答：

1. 哪些是所有场景稳定成立的业务事实和不变量？
2. 哪些差异是真实业务模式、政策或集成差异？
3. 哪些只是重复实现、历史补丁、过期兼容或旧缺陷？
4. 多个变体同时适用时，如何互斥、优先、择优、组合或拒绝？
5. 如何保持历史可解释、正逆向一致并逐步退役旧实现？
## 2. 经典模型全景

没有一个经典模型能独立完成业务提炼。不同模型解决不同问题：

| 方法/模式 | 核心用途 | 本问题中的作用 | 不能单独解决什么 |
|---|---|---|---|
| 业务能力地图 | 按业务结果组织能力 | 将不同模块、客户和版本聚类到同一能力 | 不表达详细规则、状态和冲突 |
| Event Storming | 从事件、命令、政策发现业务事实 | 还原多个实现实际怎样决策和演进 | 不是最终数据或目标模型 |
| DDD 战略设计 | 划分子域、限界上下文和统一语言 | 判断是同一模型变体还是语义分叉 | 不擅长大量产品组合约束 |
| 共性与变异分析 CVA | 提取稳定共性和真实变化 | 区分核心、参数、策略、模式和兼容 | 不表达复杂流程和事务 |
| FODA 特征模型 | 表达必选、可选、互斥、依赖 | 封闭客户产品组合空间 | 不表达时序、状态和资金守恒 |
| 软件产品线 SPL | 领域工程与客户产品组装 | 将反复出现的差异产品化 | 少量一次性定制可能过度设计 |
| 决策表/DMN | 表达资格、规则和决策依赖 | 发现重叠、遗漏并统一裁决 | 不管理长流程和副作用一致性 |
| BPMN/流程变体 | 表达角色、审批、等待、补偿 | 提取公共流程骨架和可选步骤 | 不证明数据和业务不变量 |
| 状态机/Statecharts | 表达生命周期和合法转换 | 对齐状态并限制非法跃迁 | 状态并集可能造成状态爆炸 |
| Canonical Model | 建立跨实现交换语义 | 形成旧新映射和规范概念 | 企业级万能模型容易膨胀 |
| Anti-Corruption Layer | 隔离旧语义和外部模型 | 防止旧字段、状态污染新模型 | 无退出计划会成为永久翻译债 |
| Strangler Fig | 渐进接管旧能力 | 支持灰度迁移与退役 | 不决定目标业务语义 |
| Shadow/Parallel Run | 无副作用比较旧新结果 | 验证等价、口径和历史兼容 | 总体一致率不能替代高风险审查 |

推荐组合主干：

```text
业务能力地图负责聚类
+ Event Storming 负责发现事实
+ DDD 负责语义和边界
+ CVA/FODA/SPL 负责共性与变化
+ DMN/决策表负责冲突裁决
+ 状态机/BPMN 负责生命周期和流程
+ Canonical Model/防腐层负责旧新映射
+ Strangler/Shadow 负责迁移验证
```

## 3. 三个必须分离的分析空间

### 3.1 问题空间

记录业务目标、用户结果、现实约束、不变量和失败后果。不得把现有页面、表、服务和客户分支直接当作业务本质。

### 3.2 历史实现空间

记录每个实现实际适用范围、规则、状态、数据、技术机制和副作用。它用于还原事实，不自动代表目标设计。

### 3.3 目标模型空间

形成多个候选模型，包括保守归一、结构性重构、独立业务模式和不处理方案。目标模型由证据筛选，并由 SOP-09 正式评审。

禁止从“发现代码重复”直接跳到“建立统一策略框架”。

## 4. 统一建模元模型

可使用下列元模型组织提炼结果：

```text
BusinessCapability
  ├─ StableCore
  │   ├─ CanonicalConcept
  │   ├─ BusinessFact
  │   ├─ Invariant
  │   └─ Authority
  │
  ├─ BusinessMode
  │   ├─ Applicability
  │   ├─ StateMachine
  │   └─ ResponsibilityBoundary
  │
  ├─ VariationPoint
  │   ├─ Parameter
  │   ├─ Policy
  │   ├─ Strategy
  │   ├─ ProcessVariant
  │   └─ Adapter
  │
  ├─ Constraint
  │   ├─ Requires
  │   ├─ Excludes
  │   ├─ Priority
  │   ├─ OrderedComposition
  │   └─ InvalidCombination
  │
  ├─ DecisionModel
  │   ├─ Eligibility
  │   ├─ Arbitration
  │   └─ ExecutionPlan
  │
  ├─ VersionAndDecisionSnapshot
  └─ LegacyMappingAndRetirement
```

### 4.1 业务能力 BusinessCapability

按稳定业务结果命名，例如“形成订单最终定价”“完成退款责任与资金返还”，而非 `PriceService` 或退款页面。能力契约至少定义输入语义、输出结果、权威事实、成功/失败语义和核心不变量。

### 4.2 稳定核心 StableCore

只纳入跨合法场景稳定成立的内容：

- 规范业务概念和事实。
- 核心对象、标识和权威数据。
- 跨变体不变量。
- 基本审计和历史解释要求。
- 正向与逆向业务的守恒关系。

稳定核心不是“各实现都恰好写了什么”，而是经业务和证据确认必须长期成立的语义。

### 4.3 业务模式 BusinessMode

当对象、状态机、不变量、责任主体、资金方、信任或交易边界发生结构变化时，建模为独立业务模式，不压缩成普通参数。

例如即时零售与账期赊销可能共享商品和订单概念，但授信、责任、结算和状态生命周期不同，应先选择业务模式，再在模式内选择政策。

### 4.4 变化点 VariationPoint

| 差异 | 建模方式 |
|---|---|
| 阈值、额度、时间窗、开关 | 类型化参数 |
| 相同输入输出语义下的政策不同 | Policy/决策表 |
| 算法不同但语义等价 | Strategy |
| 中间控制步骤不同 | 受控 ProcessVariant |
| 外部协议或系统不同 | Adapter |
| 旧接口、旧状态、历史数据 | Compatibility/ACL |

客户身份只能选择业务画像和配置，不能代替业务语义。

### 4.5 变体描述 Variant

每个变体至少包含：

```text
变体 ID、业务含义、适用谓词、所需上下文
输入/输出语义、维护的不变量、状态转换
副作用、逆向政策、规则版本、优先级和生命周期
```

只有实现类而没有业务描述的“策略”，无法支持冲突治理和历史解释。
## 5. 从历史实现提炼统一模型

### 5.1 以能力聚类，而非以代码归档

使用相同业务目标、业务结果和核心事实为聚类键，交叉查找不同 API、消息、任务、脚本、客户包、版本包、配置分支、表写入者和人工路径。代码相似不证明语义相同，代码不同也不证明业务不同。

### 5.2 分别还原各实现

每个实现独立记录：

| 维度 | 必须回答 |
|---|---|
| 业务目标 | 为谁解决什么问题，成功结果是什么 |
| 适用域 | 客户、渠道、区域、产品、时间、状态和版本 |
| 业务语义 | 对象、术语、规则、状态和不变量 |
| 权威关系 | 谁决定、谁写入、谁承担责任和损失 |
| 副作用 | 支付、库存、权益、结算、消息和审计 |
| 逆向路径 | 取消、退款、冲正、补偿和对账 |
| 生命周期 | 活跃、过渡、兼容、存量处理、待退役或未知 |
| 证据 | 源码、配置、数据、运行、契约、文档和人员证据 |

### 5.3 语义三角对齐

```text
声明语义：合同、需求、文档和人员说它是什么。
实现语义：代码、SQL、状态转换和配置如何处理。
运行语义：真实数据、日志、报表和用户行为呈现什么。
```

三者冲突时登记矛盾，不得自行选择最整洁的一份作为真相。

### 5.4 共性与变化矩阵

| 业务元素 | IMPL-A | IMPL-B | IMPL-C | 差异性质 | 目标归宿 | 证据/未知 |
|---|---|---|---|---|---|---|
| 业务目标 |  |  |  |  |  |  |
| 对象与关系 |  |  |  |  |  |  |
| 不变量 |  |  |  |  |  |  |
| 资格条件 |  |  |  |  |  |  |
| 规则/优先级 |  |  |  |  |  |  |
| 状态机 |  |  |  |  |  |  |
| 角色/责任 |  |  |  |  |  |  |
| 数据权威 |  |  |  |  |  |  |
| 副作用/逆向 |  |  |  |  |  |  |

每项差异只能进入下列目标归宿之一：

1. 统一到稳定核心。
2. 建模为类型化参数。
3. 建模为规则、策略或流程变体。
4. 保持为独立业务模式。
5. 隔离到兼容迁移层或退役。
6. 保留为未知项并补证。

### 5.5 不做历史能力并集

如果 `I1={A,B,C}`、`I2={A,B,D}`、`I3={A,E,F}`，不得直接令目标模型 `T={A,B,C,D,E,F}`。必须确认 C/D 是否互斥、E 是否属于独立模式、F 是否是旧缺陷，以及并集是否创造历史上从未允许的新状态。

## 6. 经典业务领域原型

领域原型不是现成答案，而是用于识别稳定概念、责任和不变量的参考结构。

### 6.1 Party–Role–Relationship

```text
Party：个人、组织或机构
Role：客户、供应商、付款方、收款方、审批人
Relationship：隶属、代理、合作、授权或结算关系
```

适用于同一主体具有多个业务身份、客户与供应商模型重复、权限和责任混入用户类型的场景。

### 6.2 Product–Offer–Price–Benefit

```text
Product：提供什么商品或服务
Offer：向谁、在什么条件下提供
Price：如何形成基准和成交价格
Benefit：优惠、补贴或权益
Agreement：客户合同或特别约定
```

适用于商品、报价、价格、促销和客户协议被压缩在同一字段或同一计算过程的场景。

### 6.3 Agreement–Policy–Rule

```text
Agreement：与客户或合作方达成的约定
Policy：组织批准的业务政策
Rule：可执行的资格、计算和裁决逻辑
```

适合把客户合同、公共政策和技术判断分离，避免把单一客户代码直接写入核心逻辑。

### 6.4 Resource–Reservation–Allocation

```text
Resource → Availability → Reservation → Allocation
         → Consumption/Release/Adjustment
```

适用于库存、额度、资金、席位和产能。它能对齐不同实现中的预占、冻结、扣减、确认和释放语义。

### 6.5 Account–Ledger–Transaction

```text
Account：业务账户
Transaction：业务交易
Entry：不可覆盖的分录
Ledger：账簿
Balance：由交易或分录派生的余额
Reversal：冲正或逆向交易
```

适用于资金、积分、储值、信用额度和库存账，避免多个实现直接竞争更新余额而失去审计依据。

### 6.6 State–Transition–Event

```text
Command：业务意图
Event：已经发生的业务事实
State：当前生命周期阶段
Guard：转换前置条件
Transition：合法状态变化
Action：状态变化产生的副作用
```

适合统一状态码和生命周期，但不得把所有旧状态求并集。先区分真实阶段、展示状态、技术处理中状态、异常状态和历史兼容状态。

### 6.7 Observation–Measurement 与 Quantity–Unit

用于检测、质检、设备、指标、金额、数量、单位、精度、舍入和换算。很多表面业务差异实际是单位、精度、测量方法或时间口径不同。

## 7. 特征模型与产品线

### 7.1 特征关系

```text
Mandatory：必须具备
Optional：可选
Alternative：一组中只能选择一个
Or：一组中可以选择多个
Requires：A 要求 B
Excludes：A 与 B 冲突
```

示例：

```text
订单能力
├─ 定价（必选）
│  ├─ 零售价
│  ├─ 会员价
│  └─ 合同价
├─ 优惠（可选）
├─ 支付模式（即时/账期二选一）
└─ 审批（可选）

账期支付 requires 授信管理
合同独占价 excludes 商家优惠
跨境模式 requires 税务与报关
```

### 7.2 使用边界

FODA/SPL 适合差异反复出现、客户数量较多、变化维度相对稳定且需要持续产品化的系统。若只有一次性定制或业务语义尚未稳定，先隔离和观察，不立即建设重量级产品线平台。

特征模型只说明允许哪些能力组合，不能替代流程时序、状态、不变量和副作用分析。
## 8. 冲突模型与统一裁决

### 8.1 冲突成立条件

设上下文为 `C`，变体 `Vi` 的适用性为 `Eligible(Vi,C)`：

```text
E(C) = { Vi | Eligible(Vi,C) }

若 E(C) 中多个变体同时适用，
且其结果、状态、写入或副作用不可安全合并，
则必须执行显式业务裁决。
```

多实现不自动等于冲突。适用域不重叠或已证明业务等价的实现可以安全共存或迁移。

### 8.2 关系类型

| 关系 | 含义 | 治理方式 |
|---|---|---|
| 等价 | 语义、结果和副作用相同 | 合并、替换或影子验证 |
| 适用域互斥 | 不会同时命中 | 按业务模式/上下文路由 |
| 业务互斥 | 可能同时命中但只允许一个 | 明确选择规则或拒绝 |
| 优先覆盖 | 高优先级覆盖低优先级 | 声明优先级并防止循环 |
| 择优 | 多个候选均合法 | 按已批准指标选择 |
| 有序组合 | 可以共同执行但顺序有语义 | 固化执行顺序和中间契约 |
| 可交换组合 | 顺序不影响结果 | 用性质测试证明 |
| 依赖/蕴含 | A 需要或必然带出 B | 发布期校验或补齐 |
| 冲突禁止 | 组合本身非法 | 发布期和运行期拒绝 |
| 独立业务模式 | 不应进入同一裁决空间 | 上层先选择模式 |
| 未定义 | 当前没有合法业务答案 | 阻断、补证或人工裁决 |

### 8.3 三阶段治理

#### 设计期

决定概念、边界、业务模式和政策。法律、合同、资金责任、对象语义和状态生命周期冲突必须由具备业务责任的人裁决，技术不能自行选择“最新实现”。

#### 配置发布期

检查：

- 互斥变体是否同时启用。
- 依赖是否缺失。
- 优先级或执行顺序是否成环。
- 有效期是否产生未裁决重叠。
- 资金/责任承担是否完整。
- 配置组合是否属于已声明、已测试空间。

能在发布期发现的问题不得拖到交易运行时。

#### 运行期

运行期只执行已批准的裁决：计算资格、应用互斥/优先/择优/组合、生成执行计划、校验不变量并保存决策快照。未知组合必须拒绝、挂起或转人工，不得按代码顺序静默处理。

### 8.4 统一决策模型

```text
业务上下文 C
→ 确定业务模式 M
→ 加载规则版本 V
→ 计算候选集合 E(C)
→ 校验依赖、互斥和非法组合
→ 应用优先、择优和组合政策
→ 生成唯一执行计划 P
→ 执行得到结果 O
→ 校验 Invariant(O)
→ 保存结果和 DecisionSnapshot
```

决策器输出的不是一个实现类，而是一份可解释执行计划：

```text
selectedVariants
excludedVariantsAndReasons
executionOrder
inputBaseline
combinationPolicy
expectedSideEffects
invariantGuards
reversePlan
```

### 8.5 权威与副作用

多个变体可以计算候选结果，但最终业务事实、状态转换和不可逆副作用必须有唯一权威路径。策略不得各自扣款、扣库存、发权益或退款后再尝试合并。

```text
先裁决
→ 再生成执行计划
→ 单一权威编排副作用
→ 使用业务幂等键
→ 记录状态、对账和补偿
```

## 9. 决策表、DMN、BPMN 与状态机的组合

### 9.1 决策表

适合穷举有限条件组合，发现条件重叠、遗漏、不可达规则和多结果冲突。

| 会员 | 促销商品 | 合同客户 | 结果 |
|---|---|---|---|
| 否 | 否 | 否 | 零售价 |
| 是 | 否 | 否 | 会员价 |
| 是 | 是 | 否 | 会员价与促销价择优 |
| 任意 | 任意 | 是 | 合同政策裁决 |

### 9.2 DMN

适合把复杂决策拆成依赖图：

```text
最终定价
├─ 基础价格选择
├─ 权益资格判断
├─ 组合合法性判断
├─ 优惠计算
├─ 商业底线校验
└─ 资金分摊
```

DMN 不负责长事务、状态生命周期和外部副作用。

### 9.3 BPMN/流程变体

用于提取公共流程骨架、可选控制步骤和模式专属子流程。不要建立包含所有客户节点和判断的超级流程。

### 9.4 状态机/Statecharts

用于合法状态转换、层次状态和并行区域。若不同实现的终态、不变量和责任主体均不同，应拆成独立模式，而不是继续增加层级状态。

## 10. 历史版本与决策快照

每次业务决策至少冻结：

- 业务模式和上下文。
- 规则/配置版本及有效期。
- 候选变体和命中资格。
- 被排除变体及原因。
- 冲突裁决和执行顺序。
- 中间结果、最终结果和责任分摊。
- 不变量校验结果。
- 对应逆向计划。

退款、撤销、冲正、补偿和审计原则上基于原决策快照，不能使用当前最新政策重新解释历史交易。

## 11. 迁移模式

### 11.1 Canonical Model 与防腐层

按业务能力或限界上下文建立规范交换语义，并通过防腐层翻译旧状态、旧字段、旧接口和外部系统模型。禁止建设试图覆盖全企业全部语义的万能模型。

### 11.2 Branch by Abstraction

先建立稳定业务能力入口，让旧实现和新实现受控共存。该抽象必须代表业务能力和契约，而不是仅隐藏两个 Service。

### 11.3 Strangler Fig

逐步让新模型接管客户、渠道、业务模式或状态范围；停止旧实现接收新流量后，再处理存量和逆向流程并最终退役。

### 11.4 Shadow/Parallel Run

旧实现产生正式结果，新模型无副作用计算；按稳定业务键比较最终结果、中间决策、数据写入和预期副作用。差异分类为新缺陷、旧缺陷修正、产品政策变化、历史兼容、数据质量、配置或时序问题。

## 12. 正确性性质与验证

目标模型至少满足：

1. **覆盖性**：所有确认继续支持的合法场景都有目标归宿。
2. **确定性**：相同上下文、版本和输入产生唯一声明结果。
3. **封闭性**：合法组合有明确集合，未知组合不能静默执行。
4. **不变量保持**：任意合法变体和组合均满足核心不变量。
5. **权威唯一**：最终事实、状态和副作用只有一个权威路径。
6. **可解释性**：能够解释选择、排除、顺序和最终结果。
7. **版本稳定性**：历史对象绑定原业务模式和规则版本。
8. **正逆向完整性**：正向与退款、冲正、补偿、对账语义对应。
9. **可迁移退役**：旧实现、存量流程和历史数据都有归宿及退出条件。

推荐验证：

- 历史样本分层回放。
- 旧新差分和影子计算。
- 资格、互斥、依赖和优先级组合测试。
- 不变量属性测试。
- 可交换性、单调性、幂等性等蜕变测试。
- 正向与逆向守恒测试。
- 非法配置发布测试。
- 存量流程、混部、灰度、对账和回滚演练。

总体一致率不能掩盖少量资金、权限、状态和审计类高影响差异。
## 13. 模式选择决策树

```text
多个实现是否表达相同业务结果？
├─ 否 → 分开定义业务能力或限界上下文
└─ 是
   ↓
核心对象、不变量、状态生命周期和责任边界是否相同？
├─ 否 → 建立独立业务模式
└─ 是
   ↓
差异是否只是阈值、范围或开关？
├─ 是 → 类型化参数
└─ 否
   ↓
差异是否为同一输入输出语义下的政策或算法？
├─ 是 → Policy/决策表/Strategy
└─ 否
   ↓
差异是否为中间控制步骤？
├─ 是 → 受控流程变体
└─ 否
   ↓
差异是否只来自外部协议或系统？
├─ 是 → Adapter/防腐层
└─ 否
   ↓
是否只服务旧接口、旧数据或存量流程？
├─ 是 → 兼容迁移层并定义退役条件
└─ 否 → 保持未知，补充证据，不强行抽象
```

## 14. 常见反模式

- 按客户复制整套流程，再用客户 ID 路由。
- 把所有旧字段、状态和功能求并集形成万能对象。
- 看到代码重复就断言业务语义相同。
- 用策略模式拆开计算，却不建模策略交互。
- 所有开关可任意组合，没有合法组合封闭。
- 用调用顺序或后写覆盖代替业务优先级。
- 规则版本未绑定业务对象，用当前政策重算历史交易。
- 只统一正向流程，遗漏退款、撤销、冲正和对账。
- 多个实现同时写最终事实或直接产生副作用。
- 为一次性定制建立重量级规则引擎或产品线平台。
- 防腐层、双写和双轨没有退出条件。
- 为得到整洁模型而删除证据不足的历史行为。

## 16. AI 执行算法

```text
INPUT：业务能力、历史实现集合、客户/渠道/版本范围、证据和决策边界

1. 用业务结果定义能力边界，不按代码和客户命名能力。
2. 建立全部实现谱系，标明适用域、入口和生命周期。
3. 使用 Event Storming 和语义三角对齐事件、命令、政策、状态和事实。
4. 使用 DDD 判断同一变体空间与独立业务模式边界。
5. 使用 CVA 将差异归为核心、参数、政策、流程、适配、兼容或未知。
6. 使用 FODA/SPL 表达必选、可选、互斥、依赖和产品组合。
7. 使用决策表/DMN 建立资格和裁决；使用状态机/BPMN 表达生命周期和流程。
8. 枚举变体适用域交集，建立等价、互斥、优先、择优、组合、依赖和禁止关系。
9. 形成至少两个目标候选，不把历史实现直接求并集。
10. 检查覆盖、确定、封闭、不变量、权威、解释、版本、逆向和退役性质。
11. 使用 Canonical Model/防腐层建立旧新映射，设计 Strangler/Shadow 迁移。
12. 将目标候选交由 SOP-09 评审；冲突业务语义交由有权负责人裁决。
```

AI 禁止：

- 用行业惯例替代当前业务事实。
- 以客户名称或代码结构直接定义业务模式。
- 为追求统一而抹除真实责任、合同、监管和资金边界。
- 把未解释差异自动变成配置项。
- 自行决定合同、资金、合规和风险接受冲突。
- 把目标模型画成当前系统事实。

## 17. 完成判据

- [ ] 声明、实现和运行语义已经对齐，矛盾与未知项被保留。
- [ ] 每项差异已进入核心、参数、政策、流程、模式、适配、兼容或未知归宿。
- [ ] 真实业务模式与普通配置差异已分离。
- [ ] 特征组合、依赖、互斥和非法组合已明确。
- [ ] 适用域交集和高风险多方组合已分析。
- [ ] 目标模型不是历史功能并集，至少比较两个候选和不处理方案。

- [ ] 正向、逆向、异常、人工和历史路径均可解释。
