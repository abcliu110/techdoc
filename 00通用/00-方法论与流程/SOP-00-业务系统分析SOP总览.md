## 0. 执行前置（AI 必须遵守）

用户仅说"按 SOP-00 分析 {对象}"（未复制 §12.1 提示词模板）时，AI 执行本 SOP 及下位 SOP 前，必须：

1. **生成 DA{n} 前先读取独立模板文件 `SOP-00-DA{n}-模板.md`**（从 §9.5 拆出，共 9 个，**以独立文件为准**，全文中的模板仅作历史参考），并在 DA 文档开头输出"模板加载记录"（读取了哪个独立模板文件、门禁检查结果）；禁止凭记忆简化模板；
2. **§12.1 提示词模板对 AI 是执行规范，不是仅供用户复制的可选项**：即使输入框未复制该模板，AI 也必须自行按其中全部执行要求（证据 ID、U-*/X-*、DEC 卡、八关、叙事模板等）执行；
3. **每个 DA 文档生成后输出"模板字段对照表"**：对照独立模板文件逐字段核对，模板要求字段缺失必须补齐或登记 U-*，对照表附在 DA 文档末尾；
4. **DA3 关系分析必须分析所有可达的业务路径**：从核心业务对象出发，追踪每一条可达路径直到终点，每一跳都要写清楚；不是"凑够N跳"，而是"有多少跳就写多少跳"，间接路径必须包含"为什么经过中间对象"（至少2条业务原因）和级联行为；
5. **V 验证（文档 21）必须由未参与 DA 生成的独立 agent 执行**，禁止生成者自检；验证记录必须输出到验证附件；
6. **门禁前置**：每个独立 DA 模板开头含"门禁检查（生成前必填）"，生成 DA 文档前必须先逐项通过该检查，未全部通过禁止继续生成，先补齐；
7. **修订前置（SOP 维护者必须遵守）**：修订本 SOP 或任何下位 SOP（SOP-01~10）、文档 20/21、DA 模板前，必须先读取 `研发方法/元规范-业务系统分析SOP编写规范.md` 并通过附录自查卡（A-F 组逐项 ✅），输出"自查卡通过记录"；修订后版本号必须变更、修订记录必须新增一行（未做视为未执行本前置，V 验证 P1 检查）。

## 1. 定位与边界

### 1.1 本文负责什么

本文只负责四件事：

1. 判断本次分析是什么任务、要形成什么认知或支持什么决定；
2. 把任务路由到正确的主流程和专项 SOP；
3. 定义所有分析共同遵守的证据、结论和阶段门禁；
4. 判断产物是否足以支持决策、是否可以交付。

本文不是领域分析教程，不承载具体项目事实，也不替代专项取证。已有系统的领域反向分析方法统一由文档 20 承担，产物反证和验收统一由文档 21 承担。

### 1.2 本文不负责什么

- 不按代码目录、页面菜单、表或接口生成全量清单；
- 不在没有业务场景和证据时预设领域概念、聚合、状态机或架构模式；
- 不以文档数量、篇幅、图表数量、代码行数或模板填写率证明分析完成；
- 不把本文中的字段名、流程名或抽象模板当成目标项目事实；
- 不替代项目入口规则、PRD、已批准 ADR、契约、实际代码、配置、数据和运行行为。

### 1.3 完成标准

业务系统分析的完成标准是：

```text
分析问题或决策问题获得足够证据
+ 关键业务切片可以解释
+ 业务语义与实现能够双向追溯
+ 失败、恢复和关键未知项可管理
+ 重要结论经独立挑战仍成立
```

“读完代码”“生成所有文档”“所有检查项打勾”均不是完成标准。

### 2.2 任务模式与最小输入

先识别任务模式，再判断最小输入。不得把三种模式的前置条件混用：

| 任务模式 | 典型目的 | 用户最小输入 | DQ 来源 |
|---|---|---|---|
| 认知重建 | 接手、理解、解释已有系统如何工作 | 分析对象、证据/代码范围、输出位置 | AI 在有限只读取证后派生，用户无需预先给出 |
| 决策支持 | 为选型、取舍、迁移、治理或优先级提供依据 | 决策意图、对象和范围 | 用户意图 + AI 分解 |
| 变更实施 | 修改代码、配置、数据、契约或运行行为 | 需求、范围、验收标准和实施授权 | 显式需求 + AI 分解 |

用户只要求“根据本 SOP 分析已有系统/模块并把文档输出到指定位置”，且没有要求实施变更时，自动归类为“认知重建”，动作等级默认为只读。此时请求者是分析结果接收人，不自动等同于业务语义裁决人、决策负责人或风险接受人。

任务模式一经 G0-A 确认即锁定。AI 不得因为分析过程中发现风险、改进机会或技术问题，自行把“认知重建”升级为“决策支持”或“变更实施”；只有用户新增了明确的决策意图、变更目标或实施授权，才能变更模式，并记录变更来源、时间和新增门禁。认知重建中的 DQ 只用于解释系统，不自动生成推荐方案、实施排期、决策负责人或风险接受人。

## 3. 理论基础

### 3.1 认知真源引用

**执行前置（AI 必须遵守）**：AI 执行本 SOP（及全部下位 SOP-01 至 SOP-10）前，**必须先读取** `研发方法/业务系统分析-认知真源.md` v2.0 的全部内容，并将其作为执行依据。认知真源中的定义、八关标准、OP/R/D 程序与本 SOP 的对应引用产生冲突时，以认知真源为准。

本 SOP 只做执行层适配说明，不复制、不替代、不重新解释真源定义。

**认知真源**：`研发方法/业务系统分析-认知真源.md` v2.0

**冲突裁决**：凡对象定义、分析顺序、主文档终点、深度标准、关系分类、证据与结论级别，以 L1 为准。

### 3.2 核心概念速查（执行层视角）

L1 定义八个核心对象，分为两组：

| 分组 | 对象 | 执行层含义 |
|---|---|---|---|
| **业务内容三元** | 事实（Fact） | 业务事件与状态变化，回答"发生了什么" |
| | 维度（Dim） | 在多个事实中重复出现的实体/角色/配置，回答"关于谁/什么" |
| | 规则（Rule / INV） | 约束、许可、计算口径、不变量，回答"必须/不得/按什么计算" |
| **分析装置** | 分析问题（DQ） | 本次分析要回答的问题 |
| | 业务切片（SC） | 有边界的业务场景单元，是分析的基本单位 |
| | 关系（Rel） | 结构归属/轨迹先后/事实对维度的归因 |
| | 证据（E-*） | 观察依据及其局限 |
| | 结论（Claim） | 带级别与范围的断言 |

**关键约束**：维度从事实派生，不得在零事实时先验"领域模型完成"。关系不是第四种业务内容，而是内容之间的连接方式。切片不是第四元，而是三元内容的组合单元。

### 3.3 分析顺序

```
1. 声明分析问题类型与完成线
2. 识别切片候选，做深度分级与配额
3. 对 SC-P0 提取事实轨迹
4. 从事实派生维度
5. 抽出规则与不变量
6. 标定关系（结构/轨迹/归因）
7. 挂接证据，定级结论；登记竞争解释与未知
8. 仅在需要追溯时补实现锚点
9. 收敛为主文档
```

**禁止逆序**：先全量结构模型后补业务故事；先优化建议后补事实；先全量清单后发现没有切片。

### 3.4 切片分级与配额

L1 定义切片深度级 SC-P* 为**分析深度配额**，不是缺陷严重度：

| 级别 | 含义 | 主文档要求 |
|---|---|---|---|
| **SC-P0** | 本任务必须讲透的核心切片 | 过深度八关；占主要篇幅 |
| **SC-P1** | 高频或重要，但非本任务第一焦点 | 叙事 + 关键规则 + 主要失败；关系可减负 |
| **SC-P2** | 边缘/低频 | 地图中点名 + 简述，可进未覆盖 |
| **SC-P3** | 异常/补偿场景 | 若支撑 P0/P1，写入失败关；否则可附录 |

**分级靠排序与名额**：

```
候选分 = 不可替代性(0-5)
        + 失败不可恢复或资金/库存/合规冲击(0-5)
        + 频率或变更率(0-3)
        + 跨边界耦合或多实现纠缠(0-3)

默认 SC-P0 名额：2（复杂域最多 3，且必须在主文档 §0 写破例理由）
取分最高者进入名额；其余降为 SC-P1/P2
```

### 3.5 深度八关（主文档验收）

对每个 SC-P0，必须同时满足：

| 关 | 名称 | 合格标准 |
|---|---|---|---|
| 1 | 价值关 | 说清该切片对经营/履约/风控的不可替代性或核心贡献 |
| 2 | 叙事关 | 去技术名后叙事完整可读 |
| 3 | 轨迹关 | 有事件/状态变化，而非名词并列 |
| 4 | 规则关 | 有必须/不得/口径，不只 happy path |
| 5 | 失败关 | 失败如何被发现、如何恢复、是否人工介入 |
| 6 | 影响关 | 关键变更伤历史还是只伤未来，谁受影响 |
| 7 | 证据关 | 关键断言有证据类型、范围；假设不冒充事实 |
| 8 | 反例关 | 至少 1 个竞争解释，或显式未知与待验 |

少任一关：该切片未深写；若全部 SC-P0 未过关：主文档不合格。

### 3.6 关系分析

L1 定义三类关系，禁止使用其他分类体系：

| 类型 | 含义 | 主要出现在 |
|---|---|---|---|
| **结构关系** | 归属、拥有、层级、配置引用、多值关联 | 维度↔维度 |
| **轨迹关系** | 触发、先后、分支、补偿、重做 | 事实↔事实 |
| **归因链接** | 事实实例指向其执行所用的维度/配置 | 事实→维度 |

**判定顺序**：
1. 两端首先是事实还是维度？
2. 若两端皆事实 → 只尝试轨迹关系
3. 若两端皆维度 → 只尝试结构关系
4. 若事实指向维度/配置 → 归因链接
5. 仍不成立 → U-（未知关系）或"弱相关，不建模"

**关系最小字段**（SC-P0 关键关系必答）：
- 类型：结构/轨迹/归因
- 方向与基数：谁指向谁，1/N
- 建立时机：设计时/初始化/配置维护/交易执行
- 变更影响：热生效/不追溯历史/需处理在途或历史/禁止
- 业务语义：一句不含技术词的说明

存储形态、级联、桥接、历史版本策略等为**条件扩展**，仅变更风险高或任务需要时展开。

### 3.8 时间盒执行规范

#### 3.8.1 推荐时间分配

| 阶段 | 精简路径 | 标准路径 | 完整路径 |
|------|---------|---------|---------|
| G0侦察 | 10min | 15min | 30min |

#### 3.8.2 停止条件

**可以停止**：
- P0切片全部达到深度分析标准
- P1切片达到标准分析标准

3. 说明"下次分析优先覆盖..."

**禁止**：
- 继续做直到完美（超出时间）
- 草草收尾不标记缺口

#### 3.9.1 分次执行的优势

## 4. 不可降级的分析原则

1. **问题驱动**：认知重建由证据派生待解释问题；决策支持和变更实施先明确要决定或改变什么，以及哪些事实会改变决定。
2. **业务切片驱动**：分析单位是角色完成业务结果的场景，不是类、表、接口或页面。
3. **切片分级与配额**：所有候选业务切片必须显式分级（SC-P0 深写、SC-P1 标准、SC-P2/P3 简述或未覆盖），按 §3.4 的评分排序与名额机制执行，不允许假性全覆盖。未分析区域必须显式标记为"未覆盖"并登记 U-*，后续按优先级补充。**禁止**"所有切片都做了但都不深入"（对应 L1 公理 7"深度靠配额：全覆盖且平均浅，等于失败"）。
4. **业务语义先于实现**：先建立场景、概念、关系、规则和状态，再映射技术元素。
5. **关系先于实体**：先回答谁与谁存在什么业务关系，再判断如何表达为实体、值对象、规则、事件或流程。
6. **事实分层**：业务认知、设计意图、代码能力、部署配置、运行事实和目标建议不得混写。
7. **静态与动态分离**：源码只能证明某版本可能如何运行；配置、数据和运行观测才能证明指定环境实际如何运行。
8. **失败与结果未知优先**：成功路径之外，必须解释拒绝、超时、重复、并发、部分失败、补偿失败和人工恢复。
9. **未知显式化**：证据不足可以得到“未知”或“证据不足”，不得得到确定性事实。
10. **主动寻找反证**：重要结论至少有一个竞争解释、最小反例或失效条件。
11. **安全只读**：生产环境默认只读、最小权限、最小影响和脱敏；有副作用的验证另行授权。

## 5. G0 任务与证据准入

G0 分成两个连续门禁。`G0-A` 判断能否安全启动；`G0-B` 在有限证据侦察后建立可演进的问题基线。认知重建不得要求用户在取证前回答只有分析者看过系统后才可能提出的问题。

### 5.1 G0-A：启动契约

开始读取目标证据前，先从用户原始提示和工作区规则形成启动契约：

| 字段 | 最低要求 |
|---|---|
| 原始目标 | 保留用户原话，并写明希望形成的认知、决定或变更结果 |
| 任务模式 | 认知重建 / 决策支持 / 变更实施 |
| 分析对象 | 系统、模块、业务域或问题对象 |
| 证据范围 | 仓库、文档、配置、数据或运行环境；暂缺项登记未知 |
| 输出与读者 | 输出位置、主要读者和预期交付形式 |
| 动作边界 | 允许的只读动作、禁止动作，以及需另行授权的动作 |
| 旧文档处理 | 默认只读作为候选证据；新产物不覆盖同名旧文件，除非用户明确要求重写或覆盖 |
| 初始范围内/外 | 已知边界和需要通过侦察确认的边界 |
| 初始基线 | 可从本地仓库自动取得分支/提交；部署、配置、数据版本未知时如实登记 |

认知重建只要分析对象、可访问证据范围、输出位置和只读边界明确，即可通过 `G0-A` 开始侦察。部署环境或业务裁决人未知，不阻止源码范围内的只读分析，但所有结论必须限定为相应证据层级。

### 5.2 G0-B：问题基线

执行文档 20 的 DA0 只读证据侦察后，AI 建立并持续修订：

- 初始角色、触发事件、业务结果、状态和失败信号；
- 分析对象在业务中的位置：核心业务域、支撑业务能力、技术平台能力或混合类型；
- 业务结果族全景，以及每类结果对应的触发事实、交付物/输出、接收角色和业务后果；
- 候选概念、概念关系、系统边界和权威源；
- 候选 `DQ-*`、业务切片及其选择理由；
- 版本/环境差异、未知项、矛盾项和下一步最小取证动作；
- 当前停止条件：哪些问题得到何种证据后足以形成声明范围内的解释。

候选 DQ 至少记录：

| DQ | 来源证据 | 为什么重要 | 状态 |
|---|---|---|---|
| `DQ-*` | `E-SRC/E-CON/E-CFG/...` | 影响哪项系统理解、维护或决策 | 候选/保留/合并/已反证 |

DQ 必须表达业务问题，例如“谁在什么条件下请求打印，系统以什么结果确认完成”；不得只是“分析某目录、类或接口”。新证据可以增加、合并、改写或反证 DQ，变更时保留来源和理由。

### 5.3 负责人和人工确认语义

- 认知重建：请求者是结果接收人；业务裁决人可以未知。AI 可交付带证据边界的事实模型和未知项，但无权批准业务取舍、实施变更或接受残余风险。
- 决策支持：作出正式推荐或接受高影响风险前，必须明确决策负责人和风险接受人。
- 变更实施：开始修改前必须具备需求、验收、实施授权，并按风险明确业务/技术负责人和回滚责任。

只有以下情况才向用户追问；其余可从本地证据取得的信息由 AI 自行侦察并登记来源：

1. 对分析范围存在会产生实质不同产物的多种解释；
2. 下一步需要新增授权、生产动作、外部协调或其他副作用；
3. 多个竞争业务解释无法用本地证据区分，且会改变核心结论；
4. 需要正式批准变更、验收结论或接受残余风险。

### 5.4 G0 门禁结论

`G0-A` 和 `G0-B` 分别使用以下结论：

| 结论 | 含义 |
|---|---|
| 通过 | 当前模式所需的启动条件或问题基线明确 |
| 条件通过 | 可在明确缺口和证据边界内继续，不能输出超出条件的结论 |
| 证据不足 | 关键范围、授权或区分性证据缺失，当前结论无法成立 |
| 不通过 | 目标、范围、权限或安全边界存在不可接受冲突 |

以下情况不得判为通过：

- 所有模式：分析对象、证据范围或输出位置无法确定；
- 所有模式：仓库基线只写“最新版本”，且 AI 未获取实际提交标识；
- 所有模式：生产访问、敏感数据或外部副作用边界不明确却准备执行相关动作；
- 所有模式：没有停止条件，却计划一次性穷举整个系统；
- 认知重建：侦察后仍没有来自证据的候选 DQ 或业务切片，只准备按目录生成清单；
- 决策支持：决策意图仍不可判定，或正式交付时决策负责人/风险接受人待定；
- 变更实施：需求、验收标准、实施范围或变更授权缺失。

“用户没有预先给出 DQ”“业务裁决人未知”“部署环境未知”本身不构成只读认知重建的失败；它们决定证据层级、结论范围和未知项。`G0-A` 未通过时不得取证；`G0-B` 未通过时后续产物标记为“探索性”，不得给出架构评级、确定性根因、实施排期或不可逆改造建议。

## 6. 统一证据与结论协议

### 6.1 证据类型

| 前缀 | 类型 | 可证明什么 | 不能单独证明什么 |
|---|---|---|---|
| `E-SRC` | 源码与测试 | 指定提交的实现能力 | 已部署、已执行或覆盖所有入口 |
| `E-CFG` | 配置与部署 | 指定环境的启用条件和拓扑 | 业务行为一定发生 |
| `E-DAT` | 数据与 Schema | 指定样本或总体中的事实和约束 | 字段名对应的完整业务语义 |
| `E-RUN` | 日志、指标、Trace、实验 | 指定窗口内的实际运行行为 | 未观测窗口内不存在其他行为 |
| `E-CON` | API、消息和调用方契约 | 对外或内部可观察约定 | 所有调用方都已发现 |
| `E-DOC` | PRD、ADR、手册和事故记录 | 声明需求、设计意图或历史背景 | 当前实现和运行事实 |
| `E-HUM` | 访谈与人员知识 | 角色认知、业务解释和人工流程 | 无需验证的系统事实 |

### 6.2 证据最小字段

每条证据必须记录：

```text
证据 ID：
类型：
精确位置：仓库相对路径 + 符号/有效行号，或查询/日志/Trace/文档定位
版本、环境和时间窗口：
采集或复现步骤：
原始观察：
覆盖范围与局限：
脱敏状态：
```

禁止在正式产物中使用 `xxx`、省略路径、无法定位的“某服务”、超出文件范围的行号或没有环境/时间窗口的运行截图作为关键证据。

### 6.3 结论确定性

| 类型 | 定义 | 决策用途 |
|---|---|---|---|
| 直接事实 | 在声明范围内直接观察到 | 可支持局部判断，不得无条件外推 |
| 交叉验证结论 | 至少两类真正独立的证据互证，强反证已解释 | 可支持高影响决定 |
| 经验判断 | 基于实践、依赖场景 | 只辅助比较 |
| 推断 | 推理链明确但仍有证据缺口 | 用于安排下一验证动作 |
| 假设 | 尚未验证的候选解释 | 不得写成事实、根因或最终建议 |

### 6.4 稳定 ID 与双向追溯

```text
DQ-*   分析问题/决策问题
SC-*   业务切片（深度分级用 SC-P0/P1/P2/P3，见 §3.4）
SEV-* 缺陷/问题严重度（SEV-P0/P1/P2/P3；与 SC-P* 切片深度配额无关，禁止混用）
BC-*   业务概念
CONCEPT-*  概念定义卡（用于 SOP-04/SOP-08 的语义三角校验）
REL-*  概念关系
BR-*   业务规则
INV-*  不变量
SM-*   状态机
DM-*   领域模型元素（含对象全景卡，是 DM-* 的强制聚合形态，维度引用 BC/REL/BR/SM/IX/MAP，不新增 ID 类型）
IX-*   交互
MAP-*  实现映射
C-*    结论
H-*    假设
U-*    未知项
X-*    矛盾项
I-*    缺陷/风险/技术债/机会
R-*    风险（与 I-* 并列的记录类型，用于单独跟踪风险；缺陷/技术债/机会仍用 I-*）
```

**严重度与切片深度禁止混用**：`SC-P*`（切片深度配额）与 `SEV-*`（缺陷严重度）是两套独立符号。专项 SOP 中若出现"P0-P3 表示业务严重度"的表述，均指 `SEV-P0~P3`，与 L1 的切片深度分级无关；任何把"缺陷优先级"写成"SC-P0"或把"切片深度"当作缺陷严重度的做法均属违规。

ID 在同一分析任务内全局唯一，不能在每份文档中重新从 `E01` 开始而不带命名空间。

必须能够执行两种追溯：

```text
原始目标 -> 证据侦察 -> 候选 DQ -> 保留/合并/已反证 DQ
  -> SC -> BC/REL -> BR/INV/SM -> DM/IX -> MAP -> E -> C

页面/接口/字段/类/配置/消息/任务
  -> MAP -> 业务语义或 U/X/兼容候选
```

## 7. G1-G5 阶段门禁

| 门禁 | 核心任务 | 必需产物 | 退出条件 | 对应验证 |
|---|---|---|---|---|
| G1 | 建立业务位置、结果全景、场景、上下文、概念和关系 | 分析对象定位、业务能力/结果族地图、场景卡、术语表、概念卡、关系规格、责任/权威源表 | 先有全景再选择代表切片；关键术语和关系可判定，技术名词未冒充领域概念 | V1-V2 |
| G2 | 建立规则、状态、责任、交互和恢复 | BR/INV/SM、领域责任、交互与失败恢复矩阵、对象全景卡（核心实体） | 正常、失败和结果未知均可解释 | V3-V5 |
| G3 | 映射实现并做运行反查和横切检查 | MAP 矩阵、静态/部署/运行差异、横切风险 | 关键链路无未解释断点，证据范围明确 | V6 |
| G4 | 收敛模型并回答分析/决策问题 | DQ 闭环矩阵、结论卡；按模式提供解释或方案/风险/行动 | 每个保留 DQ 有证据化回答；建议另有条件、验证、兼容和退出方式 | V7 预审 |
| G5 | 独立交付验收 | 门禁汇总、失败证据、范围限制、复验触发 | 认知重建的报告真实可复核；决策/变更门禁的阻断项已关闭或有权接受 | V7 正式结论 |

### 7.1 DQ 闭环矩阵

G4 和 G5 必须逐项回答 G0-B 中每个状态为“保留”的 DQ，并保留已合并、已反证 DQ 的演进记录：

| DQ | 来源与状态 | 当前结论 | 关键证据 | 反证/未知项 | 可选行动/下一验证 | 确认要求 |
|---|---|---|---|---|---|---|
|  | 候选/保留/合并/已反证 |  |  |  |  | 认知重建可写“不需决策确认” |

后续文档未引用某个 DQ，表示该问题尚未闭环，不能因为已生成报告而视为完成。

认知重建的闭环是“原始目标 -> 证据侦察 -> 候选 DQ -> 稳定或反证 -> 条件化结论”；它不要求用户在分析前认可 DQ，也不要求业务负责人对只读知识文档签署风险接受。决策支持和变更实施仍必须完成相应负责人确认。

### 7.2 回退规则

- V1/V2 失败：回到场景、概念和关系，不继续构造领域实体；
- V3 失败：修正规则、不变量或状态，不在风险报告中只写一句“建议完善”；
- V4/V5 失败：修正责任边界、交互或恢复语义；
- V6 失败：修正实现映射、证据范围或部署/运行解释；
- V7 失败：不得签署 G5，不得用文档完整率替代修正。

## 9. 面向理解与面向复核的双层交付

### 9.1 面向读者的主文档

认知重建默认必须同时交付理解层主文档和复核层附件。除非用户明确只要求过程工作表，否则只有 G0、DA0-DA8、门禁记录、代码清单或证据台账时，任务仍处于“分析过程完成、读者交付未完成”状态，不得进入 G5 通过结论。

理解层主文档使用以下默认结构；可按领域改名或合并，但五类职责均必须保留并可从阅读入口直接导航：

```text
00-阅读入口-十分钟读懂
01-业务全景与能力地图
02-典型业务故事与关键规则
03-失败恢复与运行机制
04-实现映射、证据与未知项

过程附件/
  DA0-启动契约与问题基线
  ...
  DA8-模型收敛
```

`00-阅读入口-十分钟读懂` 至少包含：一句话业务本质（**比喻式**，如"输出神经""出票工厂"，禁止定义式罗列）、分析对象的业务位置、范围与边界、角色和责任、业务结果族/能力地图、一个主故事（**必须有可代入的具体人物+情境**，如"服务员小王在中午高峰给 3 号桌点菜"）、主要失败后果、系统拥有与不拥有的事实、证据边界、**快速问答表（末尾必填，至少 5 问：数据存哪/失败怎么办/如何新增/卡住怎么办/支持哪些设备）**和阅读顺序。它不是文件目录或执行摘要，不得以 DA 阶段完成情况作为主体。形式参照 §9.4.2 叙事合格范例。

`01-业务全景与能力地图` 至少包含：业务结果族全景（含触发事实、交付物、接收角色、成功义务和失败后果）、**业务分类表（按业务语义分组如收银/后厨/报表/会员，禁止枚举罗列）**、**触发时机图（业务事件→输出的映射图，如"点餐完成→厨房联"）**、角色与权限、核心概念关系（引用 REL-* 规格，不得只用文字描述"有关联"）、设计决策记录（至少包含 3 个以上"为什么这样设计"的取舍记录，含被放弃的方案和原因；**按 L1 §3.6 D1-D5 程序产出 DEC 卡**——决策点/当时约束/可选方案/理由/成因分类/当时与当前合理性，禁止无证据地把"现状"写成"有意设计"）。仅有角色列表、业务流程图和规则表，没有显式关系规格和设计决策记录，不得判定"业务全景完整"。

**关系规格的最低质量门槛**（DA3 执行标准，对齐 L1 三类关系）：

每个核心 REL 必须完成以下检查（L1 定义的关系最小字段，SC-P0 关键关系必答）：

| 字段 | 内容 | 适用说明 |
|---|---|---|---|
| 类型 | 结构/轨迹/归因 | 按 L1 判定顺序确定 |
| 方向与基数 | 谁指向谁，1/N | 两端皆事实→轨迹关系；两端皆维度→结构关系；事实→维度→归因链接 |
| 建立时机 | 设计时/初始化/配置维护/交易执行 | 配置型关系仍可在运行期通过授权入口变更 |
| 变更影响 | 热生效/不追溯历史/需处理在途或历史/禁止 | 修改后对历史业务数据的影响 |
| 业务语义 | 一句不含技术词的说明 | 纯业务语言，不含表名、字段名、API 路径 |

**条件四问**（仅变更风险高或任务需要时展开）：
- 存储形态与字段连接：外键/JSON/关联表/M2M，跨层字段映射证据
- 级联行为：删除/修改上级时的连锁反应
- 全部使用方：谁在什么场景下使用这个关系
- 约束规则：唯一性、基数上限、业务规则校验

**关系定义与关系实例必须分开**：前者说明允许何种关联及其业务规则，后者说明某两个具体对象何时、由谁、通过何种入口建立、变更和解除。

**维护入口证据链（条件适用）**：先判定关系实例的维护入口类型（UI / API / 导入或脚本 / 消息同步 / 规则派生 / 系统内置 / 证据不足）。仅当维护入口包含 UI 时，启用下列 UI 配置关系取证清单；其他入口使用对应链路模板，不适用段填写“无/不适用”并说明理由。不得对非 UI 关系强行填满 UI 清单。

**UI 配置关系取证清单**（仅 UI 维护入口适用；适用项必须有源码或契约证据）：

1. **配置入口路径**：哪个菜单/页面 → 哪个功能模块 → 哪个具体操作触发关系建立/变更/解除；入口路径的路由规则和权限校验
2. **配置数据结构**：配置数据存储的具体表名、字段名、字段类型；关联关系在哪个字段体现（外键字段/JSON字段/关联表/M2M表）
3. **配置写入链路**：前端请求的 API 路径 → DTO/VO 字段映射 → Service 层校验逻辑 → 最终持久化的表和字段；跨层字段名须有映射证据
4. **配置约束与校验**：唯一性约束（单对象唯一/组合唯一/租户内唯一）、基数约束（1:1/1:N/N:M 上限）、业务规则校验（哪些字段不能为空/互斥/级联）
5. **配置生效读取链路**：业务操作时从哪个表/字段读取配置；读取路径是否经过缓存、是否有延迟
6. **配置变更与解除语义**：配置修改后是否影响已产生的业务数据；解除关系时历史业务数据如何处理（保留/级联删除/置空）
7. **配置审计与历史**：谁在何时因何操作变更了配置；变更前后的值；操作日志或历史表记录。无审计实现时填“无/不适用”或“证据不足”，不得虚构审计表
8. **边界情况处理**：未配置时的默认行为；配置冲突时的优先级规则；配置数据与实际业务数据不一致时的处理

**禁止事项**：
- 不得仅凭页面控件存在就断言关系已建立
- 不得仅凭未找到 FK 就断言关系不存在
- 不得仅凭代码中使用了某字段名就断言该字段就是关系字段
- 不得假设 UI 保存后关系立即生效（可能存在缓存/异步/定时刷新延迟）
- 关系路径必须区分直接路径（1-hop）和间接路径（多跳）；只有实际存在间接路径时，才依据项目证据说明中间对象承担的身份、作用域、生命周期、规则或路由职责，不得套用通用原因
- 业务关系、关系实例、UI 维护入口、对象引用、数据库关系和查询导航是不同问题，不得混为一谈
- DA3 提到的字段、类、方法、API、消息、表、配置键、基数和删除/级联行为必须在声明的版本基线中可解析并有证据；关键标识无法解析时，G2 不通过或结论标为”证据不足”，不得用合理猜测补齐
- 发现同一业务能力存在多个实现时，必须先为每个实现建立独立 `IMPL-*` 谱系并分别取证；未经 SOP-10 的语义对齐与冲突裁决，不得合并为单一 REL 或事实模型
- **字段名真实性门禁**：文档中的字段名必须能回溯到声明基线中的实际符号。跨层允许 API 字段、DTO 属性、DB 列、前端表单名存在差异，但必须给出可解析的映射证据；禁止使用无映射的猜测名、无出处缩写或仅凭业务口语发明的字段名。核对结果须记录层别、符号、出处和版本基线
- **关系建立时机与可变性分类**：每个核心 REL 必须分别判定下列属性，禁止把“静态”写成“运行时不可修改”：
  1. **相对交易的角色**：配置型（交易前作为前置资料/规则被读取）/ 交易型（在业务交易中创建或变更）/ 派生型（由其他事实计算得出）
  2. **建立与变更时机**：设计时 / 初始化或导入 / 配置维护期 / 交易执行期；配置型关系的实例通常仍可在配置维护期通过授权入口变更
  3. **变更影响**：是否热生效、是否追溯历史业务、解绑后历史数据如何处理
  “配置型静态关系”中的“静态”仅表示相对业务交易是前置配置，不表示部署后或运行期不可改变

`02-典型业务故事与关键规则` 至少包含：每个 P0/P1 切片的业务因果叙事（§9.2 定义）、关键规则和状态迁移、所涉及核心对象的全景卡引用。仅有代码调用链、时序图或表格，没有因果叙事，不得判定"故事已贯通"。

`03-失败恢复与运行机制` 至少包含：每个核心对象的失败维度摘要（引用对象全景卡 §5.6.10 ⑧）、检测/恢复/人工介入矩阵、监控指标和告警配置、**故障恢复手册（对至少 3 个高频失败场景输出"场景N：{失败} → 1.{步骤} 2.{步骤}..."可操作步骤清单，如打印机离线/任务丢失/大量失败，禁止只有矩阵没有可执行步骤）**。仅有失败类型列表，没有恢复路径和人工介入点，不得判定"失败恢复可解释"。

`04-实现映射、证据与未知项` 至少包含：每个核心对象的实现映射（引用对象全景卡 §5.6.10 ⑦）、证据索引、矛盾/未知项台账、DQ 闭环矩阵。仅有代码位置清单，没有与业务语义的映射关系，不得判定"实现映射完整"。

DA 阶段产物是形成主文档的工作底稿，不是默认最终阅读结构。不得把同一份 DA 文档简单改名或拼接后冒充理解层；主文档必须按业务问题重新综合和解释。

主文档必须支持四级压缩：

```text
一句话：系统的业务本质和核心张力
一页：角色、边界、关键概念关系、不变量、主切片和主要风险
十分钟：用一个真实切片解释如何工作、如何失败、如何恢复
完整报告：模型、证据、矛盾、未知项、方案、验证和复验触发
```

### 9.2 每个业务切片的因果叙事

除图表和矩阵外，每个 P0/P1 切片必须用连贯文字回答以下问题（对齐 L1 叙事关）：

```text
谁在什么条件下发起什么业务意图；
为什么需要这个结果；
哪些事实、规则和状态决定结果；
哪些对象和权威数据发生变化；
产生什么外部副作用；
系统在哪里确认成功、失败或结果未知；
重复、并发、超时和部分失败如何处理；
谁负责检测、补偿、对账或人工恢复。
```

每个切片还必须明确其业务交付义务：上游业务事实及权威来源、需交付的业务产物或结果、接收角色及其后续动作、有效时点，以及遗漏、错误、重复、延迟和结果未知的业务后果。

只有箭头、代码块和表格，没有因果解释，不得判定”易理解”。删除类名、方法名、表名和接口名后叙事无法成立，说明内容仍是实现转述，也不得判定”业务切片已贯通”。

**正面示例（合格的业务因果叙事）**：
```text
{角色}提交{业务对象}后，系统自动触发{处理流程}。
→ 系统先根据{对象类型}找到对应的处理规则（{规则1}、{规则2}、{规则3}）。
→ 业务规则引擎按优先级依次执行各项规则，生成最终{结果}。
→ {对象}状态更新后，系统发布{事件类型}事件。
→ 事件订阅方（{下游服务1}、{下游服务2}、{下游服务3}）异步接收事件并各自处理。
→ {角色}收到{结果通知}；如果{失败场景}，系统自动触发{补偿动作}并通知{角色}。
```
删除具体服务名、方法名后，上述叙事仍完整表达业务过程。

**反面示例（不合格的实现转述）**：
```text
{角色}提交{对象} → {控制器}.{方法}()
  → {服务}.{方法}()
    → {领域服务}.{方法}()
    → {支付服务}.{方法}()
    → {持久层}.{方法}()
    → {库存服务}.{方法}()
```
删除类名和方法名后，只剩”→ → → → →”，没有任何业务含义。
不得用这种”代码调用链”冒充因果叙事。

C-* 结论命题：

### 9.4 交付物规范

#### 9.4.1 文档分级与数量基准

| 级别 | 触发条件 | 文档数量 | 说明 |
|---|---|---|---|

#### 9.4.2 叙事质量门槛（适用于全部交付文档）

所有交付文档（理解层 00-05 + 过程附件 DA0-DA8 + 验证附件 V0-V7）的产出必须同时满足结构完整性和叙事可读性。结构覆盖度不等于可读性——人类需要读完所有文档才能深入理解系统，枚举和检查表不是阅读体验。

**叙事质量门槛（全部文档适用）**：

| 门槛项 | 要求 | 不合格示例 | 合格示例 |
|--------|------|-----------|----------|
| 一句话定义 | 每个核心概念/模块有一句人类可理解的本质定义 | "{对象}是{枚举/字段列表}" | "{对象}是{一句话本质}，用于{业务目的}，不{常见误解}" |
| 原因解释 | 每个设计/规则/行为有"为什么这样"的解释 | "使用{技术选型}" | "使用{技术选型}，因为{约束1}；{效果1}，{效果2}" |
| 具体情境 | 异常/失败场景有可代入的人物+情境，不只是错误码枚举 | "{设备/系统}离线 → {动作}" | "{具体角色}在{具体情境}时遇到{具体问题}，导致{后果}，需要{响应}" |
| 可转述性 | 读者读完能向同事转述核心内容，不带额外上下文 | 字段列表 + 枚举值 | 业务本质 + 设计原因 + 关键场景 |
| 可读性优先 | 理解层文档（00-05）优先用叙事解决，叙事解决不了再用列表 | 冗长的多级列表 | 自然段落 + 必要表格，表格服务于叙事而非代替叙事 |

**深度级文档（DA0-DA8）的额外叙事要求**：
- ⑥生命时间线：去技术名，必须可独立阅读（示例：{角色}完成{操作}后，系统自动创建{对象}，状态为"{状态1}"→{对象}被{动作}→...）
- §2.6 P0强制形态：每个对象的 P0 形态必须能向非技术人员解释清楚
- DA4 规则分析：每个规则的"违反后果"必须有具体场景，不只是"MUST"

**理解层文档（00-05）的叙事比重要求**：
- 00-十分钟读懂：叙事 > 60%，结构化内容作为补充
- 02-典型故事：100% 叙事，禁止列表冒充故事
- 03-失败恢复：叙事 + 场景化，人工介入必须有具体角色和动作

**叙事合格范例（形式参照，内容必须真实）**：

以下范例展示"可读性形式"的达标标准。**形式可参照，占位符内容必须由真实证据（E-SRC）填充，禁止沿用示例中的具体类名/字段/参数**。

1. **一句话本质（比喻式，禁止定义式罗列）**：
   - ❌ "打印子系统是管理打印任务、打印样式、打印队列的系统"（定义式，无记忆点）
   - ✅ "打印子系统是{核心系统}的{输出神经}——把{点菜、结账、划菜}转化为{物理小票}，确保{厨房按单做菜、顾客拿到凭证}"（比喻 + 输入→转化→受益者三要素）

2. **快速问答表（00 文档末尾必填，至少 5 问）**：
   - 问题必须是"新人接手最常问的"：数据存在哪 / 失败怎么办 / 如何新增某类 / 卡住怎么办 / 支持哪些设备
   - 答案必须是"一句话可操作"，不是章节引用
   ```
   | 问题 | 答案 |
   |------|------|
   | {XX}存在哪里？ | {一句话答案} |
   | {XX}离线怎么办？ | {自动恢复机制} + {人工介入动作} |
   ```

3. **人物故事（02 典型故事必填）**：
   - 必须有可代入的具体人物（"服务员小王""收银员小张"）+ 具体情境（"中午 12 点，3 号桌 4 位客人"）
   - 故事必须走完"触发→系统处理→输出→失败怎么办"完整闭环
   - ❌ "用户提交订单后系统处理并返回结果"（抽象）
   - ✅ "{人物}在{情境}时{操作}，系统{行为}，{结果}；如果{失败}，{恢复/人工介入}"（具体）

4. **业务分类表 + 触发时机图（01 文档必填）**：
   - 业务分类按业务语义分组（如收银/后厨/报表/会员），禁止枚举罗列
   - 触发时机图为"业务事件→输出"映射图，一目了然
   ```
   点餐完成 ──→ 厨房联（后厨打印机）
   结账完成 ──→ 顾客联（前台打印机）
   ```

5. **故障恢复手册（03 文档必填，至少 3 个高频场景）**：
   - 输出"场景N：{失败} → 1.{步骤} 2.{步骤}..."可操作步骤清单
   - 禁止只有矩阵没有可执行步骤
   ```
   场景一：{打印机离线}
   1. {检查电源/网络}
   2. {确认状态检测结果}
   3. {自动恢复机制（切备机/重试）}
   4. {人工介入动作（修复后重打）}
   ```

#### 9.5.4a 合格范例：间接关系契约必须达到的深度（强制参照）

以下范例演示"3 跳间接关系"契约的完整深度。每个核心间接关系（N跳）必须达到此深度；只写"A 关联 B，N:1"不算完成。

```
┌─────────────────────────────────────────────────────────────────┐
│ REL-04: 菜品 ↔ 打印机（间接关联，3 跳）                          │
├─────────────────────────────────────────────────────────────────┤
│ 【关系定义】                                                    │
│   类型：N:1（通过中间对象间接关联，运行时动态路由）              │
│   关联路径：直接（0跳）不存在，必须经过 3 跳                     │
│                                                                 │
│ 【关联路径】（共 3 跳）                                          │
│   菜品 → 出品部门（菜品归属哪个部门制作）                        │
│     → 打印队列（部门关联哪个队列出单）                           │
│     → 打印机（队列选择哪台健康打印机）                           │
│                                                                 │
│ 【为什么需要经过中间对象】（业务原因，至少 2 条）                │
│   1. 简化配置：只需为每个出品部门配置一个队列，而不是为每道菜    │
│      单独配置打印机；新菜只选部门即可，无需配打印机              │
│   2. 自然分组：同一部门的菜自动合打一张单，厨师按部门收单；      │
│      如果菜品直接绑打印机，跨部门合单、换打印机都要改所有菜      │
│   3. 故障转移：队列层可以配主/备打印机；若菜品直连打印机，       │
│      打印机故障时无法自动切换                                    │
│                                                                 │
│ 【如果直接关联（菜品→打印机）会怎样】                            │
│   新增/更换打印机需修改所有关联菜品配置；无法按部门合单；        │
│   打印机故障时无备机可切                                         │
│                                                                 │
│ 【中间对象职责】                                                │
│   出品部门：业务分组边界（什么菜归谁做）                         │
│   打印队列：路由与容错（主/备打印机、负载均衡）                  │
│                                                                 │
│ 【级联行为】                                                    │
│   删除菜品 → 不影响部门/队列/打印机                              │
│   删除部门配置 → 该部门菜品无法路由，需重新配置                  │
│   删除队列 → 关联部门菜品无法打印                                │
│   删除打印机 → 队列自动切换到备用                                │
│                                                                 │
│ 【异常场景】                                                    │
│   场景1：菜品未配置部门 → 无法路由，任务创建失败或跳过           │
│   场景2：部门未配置队列 → 分发失败，日志记录                     │
│   场景3：队列主备全故障 → 延迟重试（2秒），超时（45分钟）放弃    │
└─────────────────────────────────────────────────────────────────┘
```

> 使用方式：AI 生成 DA3 时，对最重要的 1 条间接路径（如上述 3 跳路径）按范例深度展开；其余关系可适当精简，但"为什么经过中间对象"和"级联行为"不允许省略。

## 10. G5 阻断式交付验收

### 10.1 门禁状态

G5 只使用：`通过 / 条件通过 / 不通过 / 证据不足 / 不适用`。

不得使用没有分母的“完成度 100%”“代码覆盖率 100%”“证据完整率 100%”。覆盖结论必须同时给出总体或样本框、已覆盖、未覆盖、选择方法和缺口影响。

G5 验收对象是分析交付物，不自动等同于“被分析系统可以上线”。认知重建准确发现未修复 P0/P1、缺陷或未知项时，报告仍可通过，但必须显著披露证据、影响和范围，且不得给出安全、上线或风险接受结论。决策支持和变更实施若要批准相关行动，适用阻断项必须关闭或由有权者限时接受。

### 10.2 自动阻断条件

以下任一情况存在时，不得判为通过：

- G0-A 未通过，或 G0-B 没有形成可追溯的问题基线；决策支持/变更实施的决策负责人、风险接受人或关键基线仍待定；
- 关键证据包含占位符、省略路径、无效符号或越界行号；
- 文档中的枚举、状态、接口、字段或方法与对应基线源码不一致；
- 重要结论没有关联保留 DQ，或保留 DQ 没有在 G4/G5 逐项回答；
- 只有源码证据，却声明指定环境的高可用、性能、故障恢复或实际运行结果；
- 评分、星级、风险值、覆盖率或工作量没有口径、样本、计算依据和责任人；
- 未知项、矛盾项和反证为空，但没有证明其确实经过查找和验证；
- 同一分析者自我确认“证据准确、结论合理”，且没有独立复核或显式反方协议；
- G1-G4 的文档状态仍为初稿，却在 G5 宣布正式通过；
- 通过数量、篇幅、图表或代码引用数替代业务语义和证据充分性。
- 认知重建只有 DA/G/V 过程产物，没有 §9.1 定义的理解层主文档；
- 没有业务结果族全景就直接以少量代码入口代表整个分析对象，或未披露未覆盖结果族；
- 阅读入口无法在不查阅源码和过程附件的情况下回答业务本质、角色、主要结果、代表故事、失败后果及事实所有权；
- 跨文档中的状态集合、枚举值、文件格式、接口、消息、类、配置或恢复机制相互矛盾，或者没有与基线证据一致。
- 理解层主文档的 01-04 不满足 §9.1 的最低质量门槛：01 缺少 REL 引用或设计决策记录，02 故事为代码调用链而非业务因果叙事，03 缺少恢复路径和人工介入点，04 缺少业务语义映射。
- 任一 SC-P0 切片未通过 L1 深度八关（价值/叙事/轨迹/规则/失败/影响/证据/反例），或 SC-P0 数量超出 §3.4 名额且未在 §0 写破例理由；
- 认知重建未以 §9.1 理解层主文档为唯一交付终点，仅以 DA/G/V 过程附件冒充完成。
- 交付文档（00-05 + DA0-DA8 + V0-V7）不满足 §9.4.2 叙事质量门槛：读者不带源码和过程附件仍无法读懂核心内容；或叙事比重低于门槛（理解层叙事比重 < 60%，02-典型故事非 100% 叙事）。

### 10.3 验收最小动作

1. 校验所有关键证据位置存在且与原文一致；
2. 从 DQ 随机抽取结论向下追到证据；
3. 从关键写入口、消息、任务和数据反向追到业务语义；
4. 对关键结论执行最小反例或竞争解释验证；
5. 检查静态、部署、配置、数据和运行证据是否混写；
6. 检查失败、结果未知、恢复和人工责任是否可判定；
7. 执行十分钟理解测试：不看源码和过程附件，回答系统为何存在、谁依赖它、交付/维护哪些业务事实、代表故事如何成功或失败、系统拥有什么和不拥有什么；
8. 执行跨文档事实一致性检查，核对状态、枚举、接口、消息、文件格式、配置和恢复声明；
9. 记录未通过项、责任人、修正阶段和复验触发。

G5 不负责替原分析者补写缺失内容。发现缺口后必须回退到相应 DA 阶段。

## 11. 横切安全与兼容底线

以下维度按场景贯穿 DA0-DA8，不在最终报告中临时补写：

| 维度 | 必答问题 |
|---|---|
| 身份、权限与作用域 | 谁能对哪个租户、组织、门店或主体的数据做什么，依据和审计是什么 |
| 资金、库存、数量和状态 | 精度、守恒、原子性、并发和对账如何成立 |
| 重复与结果未知 | 双击、重试、重复消息、远端成功本地超时是否产生重复结果 |
| 契约与兼容 | 调用方、消费者、历史数据、配置、任务、文件和人工流程如何依赖 |
| 安全与隐私 | 输入校验、参数化查询、密钥保护、最小数据和脱敏是否成立 |
| 失败与恢复 | 部分成功、补偿失败、人工接管、恢复顺序和最终权威事实是什么 |
| 可观测与审计 | 能否发现、关联、定位、审计和恢复关键失败 |
| 容量与降级 | 峰值和数量级增长时哪个约束先失效，如何安全降级和恢复 |

生产分析默认只读。日志、响应、SQL 样本、截图和报告落盘前必须脱敏；不得记录密钥、token、支付凭据或完整敏感请求/响应。

## 12. AI 执行约束

1. 先读取目标项目入口规则、版本基线和真实源码，再使用本 SOP。
2. 稀疏提示满足认知重建最小输入时，自动形成 G0-A、执行 DA0 只读侦察并建立 G0-B；不得反问用户“请先提供领域概念、业务切片或 DQ”。
3. 类名、字段名、枚举名、注释和常见行业做法只能产生候选假设，不能直接产生业务事实。
4. 通用 SOP 中的示例与模板只说明格式；复制到项目产物前必须用项目证据逐字段重建。
5. 不得为了填满 BR、INV、SM、CON 等栏目而虚构规则、状态或契约；证据不足时留空并登记 U-*。
6. 不得生成并引用目标仓库不存在的方法、实体、接口、消息、队列、表或恢复机制。
7. 引用代码前必须确认文件存在、符号存在、行号有效，并记录提交基线。
8. 未执行运行验证时，统一使用“源码显示可能”“尚未验证部署是否启用”等条件表述。
9. 设计模式只能作为候选解释或方案，必须说明触发条件、机制、代价和反例。
10. 未获得业务、运行或独立证据时，不得给出架构总分、星级、成熟度百分比或实施人日。
11. 只有 §5.3 的四类情况可以中断并追问用户；可由仓库、文档、配置或只读工具确定的事实必须先自行取证。
12. 认知重建不得把 AI 设为业务裁决人、决策负责人或风险接受人；无法裁决的语义登记为 U-* 并说明对结论的影响。
13. 生成 G5 前必须调用文档 21，不得由“文件已经生成”推导“分析已经通过”。
14. 有叙事/模板要求时，必须按 L1 §2.8 对象全景卡模板和 §7.2 切片叙事模板填写，不得自创格式或用调用链冒充叙事。
15. 每条断言必须标注证据 ID（E-* + 文件:行号）或"推断"或 U-*；**无证据的断言、无 U-* 的文档、无竞争解释的关键结论**均视为未完成。
16. 产出必须满足 §9.4.2 叙事质量门槛：所有文档（00-05 + DA0-DA8 + V0-V7）的人类可读性不低于"读者不带背景知识可读懂核心内容"；叙事比重低于门槛的文档视为未完成，不得宣告分析结束。

### 12.1 AI 执行提示词模板（可直接复制使用）

**背景**：仅说"根据 SOP-00 分析"是不够的——AI 只会执行提示词中明确写出的指令。**本模板对 AI 是执行规范，不是仅供用户复制的可选项**：用户仅说"按 SOP-00 分析"且未复制本模板时，AI 必须自行按本模板的全部执行要求执行（等同本模板自动生效，见 §0 执行前置）。以下模板内嵌了全部执行约束（证据 ID、U-*、候选事实、八关、主文档、DEC 卡、叙事模板），用户只需补充分析对象、仓库路径、输出目录和**深度级别**。

```text
任务：对 {分析对象} 做深入业务分析（认知重建模式）。

范围：
- 相关仓库：{仓库1}、{仓库2}
- 输出目录：{目录路径}
- 深度级别：{精简级/标准级/深度级}（按 SOP-00 §9.4.1 执行）

执行要求（必须全部遵守）：

1. 【主文档与文档结构】按 {深度级别} 的文档清单执行（见 §9.4.1）：
   - 精简级（3 个）：五类职责合并，按 §9.4.1 精简级清单
   - 标准级（16 个）：理解层 5 + 过程附件 11（G0-A/G0-B + DA0-DA8）
   - 深度级（26 个）：标准级 16 + 验证附件 8（V0-V7）+ 业务理解 2
   理解层用读者视角文件名（00-十分钟读懂/01-业务全景/02-典型故事/03-失败恢复/04-设计与实现/05-证据与未知），
   过程附件用分析者视角文件名（G0-A/G0-B/DA0-DA8），验证附件用 V0-V7。
   过程附件与理解层之间的证据 ID 必须一致，不得各写一套。

2. 【叙事模板】因果叙事必须按 L1 §7.2 切片叙事模板写：
   "谁在什么条件下发起什么动作 → 系统如何响应 → 涉及哪些对象
    → 成功长什么样 → 失败如何收场 → 变更影响谁"，
   删除类名/方法名/表名后必须仍成立；禁止用调用链冒充叙事。

3. 【对象全景卡】核心对象按 L1 §2.8 对象全景卡模板填写，
   其中⑥生命时间线必须可去技术名（示例：{角色}完成{操作}后，
   系统自动创建{对象}，状态为"{状态1}"→{对象}被{动作}→...）。

4. 【证据纪律】每条断言必须标注证据：E-SRC/E-CFG/E-DAT/E-RUN/
   E-CON/E-DOC/E-HUM + 文件:行号；无法标注的写"推断"或登记 U-*。
   指标数字（成功率、耗时、阈值、周期、超时）必须有出处，同一数字全文档一致。

5. 【证据受限】无运行证据（E-RUN）时，禁止陈述"实际性能/故障表现"，
   一律登记 U-* 或写"源码显示可能"。

6. 【未知/矛盾/竞争解释】未知登记 U-*，矛盾登记 X-*；
   每个关键结论至少一个竞争解释（中强度以上）或显式未知。

7. 【设计决策】设计怪点（为什么用 X 不用 Y：文件存储、逗号分隔、
   固定超时等）走 L1 §3.6 D1-D5 程序，产出 DEC 卡
   （决策点/当时约束/可选方案/理由/成因分类/当时与当前合理性）。

8. 【反向程序】从代码痕迹提取候选事实（R2），标注验证状态（R3）——
   交叉验证/直接事实/推断/未知，禁止痕迹直译。

9. 【深度八关】完成后按价值/叙事/轨迹/规则/失败/影响/证据/反例
   八关逐关自检，输出自检表；任一关不过则标记为"未完成"并说明缺口，
   不得宣告完成。

10. 【诚实收尾】时间/证据不足时交付"未完成分析报告"（逐关标记
    过/不过/未及），禁止把过程附件冒充主文档。

11. 【叙事质量门槛】所有文档必须满足 §9.4.2 叙事质量门槛：
    - 每句话以"人"能理解的方式写，不是以"系统"的方式写
    - 每个设计/规则/行为解释"为什么"，不只写"是什么"
    - 异常场景用具体人物+情境，不用错误码枚举
    - 读者读完能向同事转述，不带额外上下文
    - 理解层文档（00-05）叙事比重 > 60%，02-典型故事 100% 叙事
    - DA 层文档同样必须可读，不允许纯检查表格式
```

## 13. 停止、升级与复验

### 13.1 可以停止

- 每个保留 DQ 已有足够直接事实、交叉验证结论或明确的证据边界；
- P0/P1 切片已覆盖正常、边界、失败和结果未知；
- 关键规则、不变量、状态、交互和实现可双向追溯；
- 最可能推翻结论的反例已验证；
- 未知项和矛盾项不会在未声明的情况下改变当前决定；
- 继续分析的预期信息增益低于时间、成本和风险。

### 13.2 必须暂停或升级

- 关键部署、配置、数据和源码版本无法对齐；
- 竞争业务解释无法由本地证据区分且会改变核心结论；认知重建中的一般语义未知只登记 U-*，不自动暂停；
- 权限、租户或敏感数据边界不明确；
- 需要生产写入、压测、故障注入或外部协调但未授权；
- 高影响结论只有单一低质量证据或存在未解释强反证。

### 13.3 复验触发

业务规则、状态机、权限作用域、API/消息契约、调用方、数据权威源、部署版本、配置开关、历史迁移或关键假设变化时，至少重跑受影响的 DA/V 阶段。
