01 / 理论底座

UI 是业务规则约束下的任务工作面

同一条规则对顾客、操作员、审批人和审计人员会产生不同的界面责任；同一个界面也会组合多条规则。理论的作用，是在选择控件之前先把责任和权威说清楚。

A

活动与任务

规则必须落到“谁为了什么结果执行什么任务”。数据库字段和页面菜单都不是业务目标。

B

行动与评价闭环

既要让用户发现合法动作，也要让用户理解系统发生了什么、为什么，以及下一步怎么办。

C

状态与命令

按钮不是权限清单，而是当前状态、资格、数据范围和风险控制共同求交后的合法命令。

D

决策权

事实输入、用户选择、系统裁决和审批决定必须分离，避免把系统结论伪装成用户选择。

E

控制与恢复

提交不是终点。异步和高风险业务必须形成“操作—反馈—判断—修正”的闭环。

F

渐进披露

重要后果必须提前展示；复杂依据可以按需展开；审计细节只向承担相应责任的角色开放。

02 / 五级映射

从规则语义到具体界面，中间经过五次转换

任何一步被跳过，都会出现“按钮为什么禁用说不清”“前后端规则漂移”“用户只看到失败却不知道如何恢复”等问题。

Level 1规范规则语义

区分事实、不变量、资格、计算、状态、权限、时间和例外。

Level 2定位角色任务

谁提供事实、谁选择、谁审批、谁承担错误结果。

Level 3推导交互义务

规则要求界面收集、告知、约束、解释还是恢复。

Level 4合成交互契约

形成字段策略、允许命令、决策投影和失败语义。

Level 5选择 UI 表现

再选择页面、表单、按钮、状态、时间线和消息。

04 / 双向追踪

每一个 UI 约束都能反查业务依据

规则到 UI 的映射不是设计师个人判断，而是一条可验证、可回归、可审计的证据链。

BR-*

业务规则

含义、来源、作用域、版本与关系。

IO-*

交互义务

收集、告知、约束、解释与恢复。

IC-*

交互契约

角色、任务、命令、字段和反馈。

UI-*

页面状态

可见、只读、阻断、审批和未知。

API/GUARD-*

权威守卫

服务端裁决、状态转换和不变量。

TEST-*

场景验证

正常、边界、冲突、并发和恢复。

06 / 使用护栏

理论不是把每条规则都做成复杂界面

UI 预检 ≠ 最终裁决

即时反馈提升体验，但动态政策、权限、并发资源和高风险结果必须由服务端重新判断。

适用
格式、局部依赖、低成本预估
边界
金额、库存、状态、权限和不可逆副作用
反例
两个终端同时看到“库存 1”并各自在前端扣减

解释 ≠ 暴露内部代码

解释应来自实际决策结果，使用规范业务词汇，并根据角色分层展示。

适用
高影响、易质疑或需恢复的决策
边界
敏感风控只给最低必要解释和申诉路径
反例
向顾客展示类名、SQL 或内部风险阈值

禁用 ≠ 隐藏 ≠ 只读

三者表达完全不同的业务语义，必须先定义用户是否需要发现能力、理解原因和查看事实。

适用
状态、资格和权限共同影响动作
边界
安全信息不能因“解释”而过度泄露
反例
优惠券消失，用户无法区分过期、无资格或系统故障

复杂度必须与风险匹配

低风险、即时可逆的操作可以轻量表达；资金、权限和长流程需要状态、解释和恢复闭环。

适用
按影响、可逆性和失败成本分级
边界
不是所有规则都需要规则平台
反例
标签重命名也要求完整审批和决策快照
