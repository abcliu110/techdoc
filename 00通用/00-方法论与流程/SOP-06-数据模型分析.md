## TL;DR

**一句话**：围绕业务决策问题，分析数据的业务语义、Schema 设计、读写路径、约束一致性和安全演进，输出可支持数据变更决策的证据与结论。

**核心输入**：决策问题、库/表/Schema 范围、代码/部署基线、权限边界

**核心输出**：数据血缘图、Schema 分析、约束与不变量、查询分析、迁移方案

**关键约束**：不得用字段名猜测业务语义；不得把"未找到外键"判为设计错误；生产操作必须先获授权

## 目的

围绕本次决策问题，分析数据如何表达业务事实、由谁负责、如何流动、如何维持约束与一致性，以及如何安全演进和恢复。输出应支持风险判断、问题闭环和可执行的数据变更决策，而不是仅生成表清单、ER 图或规范评分。

## 适用范围

- 关系数据库、分库分表、主从/多副本及其 Schema
- 缓存、搜索索引、消息、对象存储、数仓、数据湖和报表数据集
- 外部系统直连、CDC/ETL/同步任务、批处理和人工导入导出
- 领域模型、持久化模型、API/消息模型之间的映射
- 数据质量、安全、生命周期、迁移、备份恢复和历史兼容

不适用项必须说明原因。数据库不可访问时仍可基于 DDL、代码、配置、迁移脚本和脱敏样本开展静态分析，但不得把静态推断表述为实际生产事实。

## 核心原则

1. **数据库表不等于领域模型**：表是某一存储实现；领域对象、聚合、业务事件和口径可能跨表、跨库、跨服务，也可能一表承载多个历史语义。
2. **Schema 不等于实际数据**：DDL 表达声明约束，代码、数据分布和运行链路表达实际行为；三者冲突时登记矛盾项，不自行选择其中一方覆盖其他证据。
3. **字段名、注释不等于业务语义**：字段名只能产生待验证假设，必须结合写入者、读取者、状态流转、样本分布、文档和知情人验证。
4. **外键缺失不等于关系不存在或设计错误**：关系可能由应用、事件、路由键或外部标识维护；是否需要数据库外键取决于所有权、写入路径、删除语义、性能和故障模式。
5. **范式、反范式没有脱离场景的优劣**：必须结合读写模式、一致性要求、数据规模、变更频率、恢复能力和组织边界评价。
6. **索引不能按字段机械推荐**：索引结论必须关联真实查询、参数分布、数据选择性、排序/分页、写放大和执行计划。
7. **生产只读、最小权限、最小影响**：未经授权不得执行 DDL、DML、锁表、高开销全表扫描、真实数据导出或带执行效果的计划分析。
8. **“未观察到”不等于“不存在”**：外部直连、动态 SQL、脚本、报表、定时任务、消息和人工操作都可能形成隐藏依赖。

## 1. 证据、采样与语义验证

### 1.1 证据登记

沿用 SOP-00 的 `SRC/CFG/DAT/RUN/CON/DOC/HUM` 类型，详见 `SOP-00 §5.1`。关键证据使用稳定 ID：`E-{类型}-{序号}`。

| 证据 ID | 来源与定位 | 版本/环境 | 采集时间/窗口 | 查询或复现步骤 | 覆盖度 | 脱敏状态 | 质量与限制 |
|---|---|---|---|---|---|---|---|
| E-DAT-001 |  |  |  |  | 全量/分层/个例 |  | 直接性、时效性、可复现性、独立性 |

关键结论使用稳定 ID 并关联证据，例如：

```text
C-DATA-012（交叉验证结论）
结论：订单号在租户内唯一，而非全局唯一。
证据：E-DAT-008 + E-SRC-017 + E-RUN-004
范围：生产集群 A，2026-07-01 至 2026-07-31，新链路；历史导入数据除外。
反证/限制：归档库尚未验证，关联 U-DATA-006。
```

### 1.2 分层采样

采样必须记录总体、样本框、选择方法、时间窗口和覆盖缺口。根据切片按适用性覆盖：

- 正常、边界、失败、重复、并发和部分成功数据
- 当前与历史版本、迁移前后、灰度组和不同业务周期
- 不同租户、区域、渠道、数据规模和热点分区
- 撤销/冲正、补偿、人工修复、归档和恢复后的数据
- 空值、极值、非法枚举、孤儿关系、重复标识和时间异常

资金、库存、权限、租户隔离和不可逆操作不能仅凭少量随机样本下结论。抽不到生产样本时降低确定性，不得用测试数据替代生产事实。

### 1.3 安全数据探针示例

以下仅为模板，执行前必须按产品语法、索引、分区、租户范围和影响预算改写：

```sql
-- 先限定租户与时间窗口，再观察状态分布；禁止直接套用到大表全量扫描。
SELECT status, COUNT(*) AS cnt
FROM target_table
WHERE tenant_id = :tenant_id
  AND created_at >= :window_start
  AND created_at < :window_end
GROUP BY status
ORDER BY cnt DESC;

-- 检查业务标识在声明粒度内是否重复。
SELECT tenant_id, business_no, COUNT(*) AS cnt
FROM target_table
WHERE created_at >= :window_start
  AND created_at < :window_end
GROUP BY tenant_id, business_no
HAVING COUNT(*) > 1;

-- 检查应用声明关系的未命中情况；先验证两侧过滤条件与索引。
SELECT COUNT(*) AS unmatched_cnt
FROM child_table c
LEFT JOIN parent_table p
  ON p.tenant_id = c.tenant_id
 AND p.id = c.parent_id
WHERE c.tenant_id = :tenant_id
  AND c.created_at >= :window_start
  AND p.id IS NULL;
```

探针结果必须保留查询文本/哈希、参数范围、执行环境、时间、行数、耗时和计划证据；“空值率高”“关联未命中”是观察，不自动等于字段废弃或数据错误。

## 2. 领域语义、所有权、粒度与血缘

### 2.1 数据库表与领域模型分离建模

对每个关键业务切片分别回答：

```text
业务事实/事件
  → 领域对象、聚合与不变量
  → 应用命令/查询、API/消息契约
  → 持久化模型（表、文档、缓存、索引）
  → 数仓事实表/维表、报表口径
```

必须识别：

- 一个领域对象是否拆到多表、多库或多个服务；
- 一张表是否混合多个生命周期、租户、业务类型或历史版本；
- 快照、流水、当前态、事件、汇总和派生字段的区别；
- ORM Entity、DTO、VO、消息和数据库行是否存在语义或精度转换；
- 反范式字段是权威事实、性能副本、历史快照还是展示缓存；
- 删除、撤销、冲正是否改变原事实，还是追加新的反向事实。
- 配置表、关联表、中间表、映射表等非事实存储表，还需额外完成动机分析（见 §2.1.2），回答"为什么需要这张表"而非"这张表有哪些字段"。

	#### 2.1.1 从数据反向发现同一业务多实现

数据视图必须用于反证“只有一个实现”的假设。对核心业务事实反向枚举全部写入者、状态推进者、计算口径和版本来源，重点检查：

- 同一表/字段是否被不同服务、任务、脚本、存储过程、CDC 或人工工具写入；
- 相同业务事实是否分散在客户表、渠道表、旧新表、分片表或版本表中；
- 同一金额、状态、资格或指标是否存在多套计算字段和报表口径；
- 数据行中的类型、来源、版本、租户、渠道、时间和历史默认值是否隐式选择不同实现；
- 新旧实现是否双写、互相覆盖，或分别拥有正向与逆向数据；
- 同一对象是否缺少实现/规则版本，导致历史数据被当前逻辑重新解释。

输出数据侧实现证据：

| 业务事实/对象 | 写入者/实现 ID | 表/字段/事件 | 适用与版本线索 | 权威性 | 口径/状态差异 | 冲突或未知 | 证据 |
|---|---|---|---|---|---|---|---|
| ___ | IMPL-___ | ___ | ___ | 权威/副本/旁路/未知 | ___ | X-/U-___ | E-___ |

发现多写者、多口径或无法确认权威源时，不得自行选取”最新表”或”主服务”为标准，也不得把多个实现的字段和关系合并成一张事实模型。应先为每个实现建立独立 `IMPL-*`、REL 和数据证据，与 SOP-02/03/04 的入口和流程证据汇合，再按 SOP-10 建立实现谱系、语义对齐和旧新映射。

#### 2.1.2 非事实表动机分析

**适用范围**：配置表、关联表、中间表、映射表、关系表等非业务事实存储表（非事务记录表）。这类表不记录业务事件或数值度量，只记录对象之间的关联关系、配置参数或映射规则。

**分析目的**：回答”为什么需要这张表”，而非”这张表有哪些字段”。非事实表的业务语义在表结构层面不可读——字段全是外键或配置值，只看表名和字段无法判断其存在的业务理由。必须通过动机分析还原其业务意义。

**分析维度**（每个非事实表必须回答）：

| # | 问题 | 说明 |
|---|------|------|
| ① | 解决的业务问题是什么？ | 这张表对应的是什么业务复杂度？否则会导致什么问题？ |
| ② | 对应哪个问题域/业务能力？ | 属于权限管理？打印配置？支付渠道？促销规则？储值方案？ |
| ③ | 解决了什么问题域的什么问题？ | 权限矩阵？多对多关联？动态配置？版本化管理？映射转换？ |
| ④ | 不存在这张表会怎样？ | 反面场景：缺失的替代方案是什么？代价有多大？ |
| ⑤ | 表的维护入口是什么？ | 谁在何时通过什么方式维护数据？系统初始化/配置页面/定时同步？ |
| ⑥ | 表的数据权威源是谁？ | 谁是主数据的来源？其他系统是否需要同步？ |

**分析模板**：

```text
## {表名} 非事实表分析

**表用途**：解决什么问题
**问题域**：XX 管理 / YY 配置 / ZZ 关联
**核心价值**：
1. 解决了 XX 问题域的 YY 问题（如：解决了”一个用户可以有多个角色”的多对多关系表达问题）
2. 避免了 ZZ 风险（如：避免了角色权限硬编码导致的维护灾难）

**反面场景**（不存在这张表会）：
- 场景1：...
- 场景2：...

**维护入口**：
- 入口1：系统初始化
- 入口2：管理员配置页面
- 入口3：定时任务同步

**数据权威源**：
- 主数据源：XX 系统
- 同步目标：YY 系统、ZZ 服务
```

**禁止行为**：
- ❌ 只描述字段结构，不解释业务目的
- ❌ 只写”这张表用于存储 XX 配置”，不说明为什么要单独建表
- ❌ 把所有配置表/关联表放在一起，不区分问题域
- ❌ 不标注数据权威源和同步方向

**退出条件**：每个非事实表都有”问题域归属”和”核心价值”描述；反证场景说明这张表确实必要而非过度设计。

**分析结论的流向**：非事实表动机分析的输出（问题域归属、核心价值、维护入口）应输入到 §2.2 数据资产最小语义卡（登记业务含义和权威源）和 §2.4 数据血缘（补充配置链路的血缘关系）。发现多张非事实表属于同一问题域时，应联动 §2.1.1 检查是否存在多实现问题。

#### 2.1.3 枚举分析规范

**适用范围**：Java/Kotlin 枚举类、数据库枚举字段（`tinyint`/`varchar` 存枚举值）、前端枚举常量、API 契约中的枚举参数、状态机中的状态值。

**分析目的**：回答"这个枚举值代表什么业务概念、为什么取这些值、值之间的业务关系是什么"，而非"枚举有哪些常量"。枚举是业务概念最直接的代码化表达，其取值集合、命名和注释直接反映业务语义。

**分析维度**（每个核心枚举必须回答）：

| # | 问题 | 说明 |
|---|------|------|
| ① | 枚举的业务含义与上下文是什么？ | 这个枚举描述的是哪个业务概念？在什么业务场景下使用？ |
| ② | 每个枚举值的业务语义是什么？ | 值名称、code、注释是否准确反映业务语义？是否存在历史遗留命名？ |
| ③ | 枚举的变更与兼容性如何？ | 新增/废弃/重命名枚举值是否影响历史数据、消息、API 消费者？ |
| ④ | 枚举的跨系统映射是否一致？ | 前端、后端、数据库、消息、报表中的枚举值集合和 code 是否一致？ |
| ⑤ | 枚举的代码定义与实际数据分布是否一致？ | 数据库中是否存在代码中未定义的枚举值？代码定义的值是否从未在数据中出现？ |

**分析模板**：

```text
## {枚举类名} 枚举分析

**业务概念**：描述什么业务概念
**使用场景**：在哪些业务切片中使用

**枚举值清单**：

| code | 名称 | 业务语义 | 历史备注 | 数据分布（样本） |
|------|------|---------|---------|----------------|
| 0 | PENDING | 待处理 | 旧系统曾用名 INIT | 占比 65% |
| 1 | ACTIVE | 已激活 | | 占比 30% |
| 2 | DISABLED | 已禁用 | v2.0 新增 | 占比 5% |

**变更记录**：
- v1.0：初始定义 PENDING(0), ACTIVE(1)
- v2.0：新增 DISABLED(2)，历史数据 ACTIVE 保持不变
- v2.1：废弃 PENDING（不再新建，历史数据保留）

**跨系统一致性**：
| 位置 | 定义 | 是否一致 |
|------|------|---------|
| Java 枚举 | ✅ | 一致 |
| 数据库 | 0,1,2 均有分布 | 一致 |
| 前端常量 | 缺少 DISABLED | ❌ 不一致 |
| API 文档 | 未更新 | ❌ 不一致 |

**数据-代码差异**：
- 数据库中存在的 code 值：0, 1, 2, 99（99 在代码中未定义，需确认是否为历史遗留）
```

**禁止行为**：
- ❌ 只列出枚举常量名称，不解释业务语义
- ❌ 只检查代码定义，不验证实际数据分布
- ❌ 忽略枚举值变更对历史数据、消息、API 消费者的影响
- ❌ 把不同上下文中同名枚举直接当作同一概念

**退出条件**：每个核心枚举都有"业务概念"和"枚举值语义"描述；代码定义与实际数据分布已互证；跨系统不一致项已登记。

**分析结论的流向**：枚举分析输出应输入到 §2.2 数据资产最小语义卡（登记业务含义）、§2.3 标识与映射（跨系统枚举映射），以及 §3.3 约束、不变量和状态机（状态枚举与状态机的对应关系）。发现代码定义与实际数据分布不一致时，应联动 §3.4 声明与实际分布互证。

#### 2.1.4 值对象分析规范

**适用范围**：金额、百分比、比率、日期范围、时间段、地址、电话号码、邮箱、坐标、度量单位等无独立业务身份、只由属性值定义相等性的概念。

**分析目的**：回答"这个值对象封装了什么业务概念、它的精度/单位/格式是什么、相等性如何判断、是否可变更"，而非"这个类有哪些字段"。值对象是业务概念最精细的表达层次——金额的精度、百分比的范围、地址的层级结构都直接反映业务语义和约束。

**分析维度**（每个核心值对象必须回答）：

| # | 问题 | 说明 |
|---|------|------|
| ① | 值对象的业务身份是什么？ | 封装了什么业务概念？在什么业务场景中使用？ |
| ② | 相等性判据与不可变性如何？ | 哪些字段决定相等性？是否为不可变？修改是创建新实例还是原地修改？ |
| ③ | 精度/单位/格式是什么？ | 金额精度（分/厘）、百分比范围（0-100/0-1）、日期格式（含时区）、度量单位 |
| ④ | 序列化与兼容性如何？ | JSON/数据库/消息序列化方式？历史版本兼容？精度损失风险？ |
| ⑤ | 值对象与实体的边界在哪里？ | 为什么这个概念是值对象而不是实体？什么条件下它可能升级为实体？ |

**分析模板**：

```text
## {值对象名} 值对象分析

**业务概念**：封装什么业务概念
**使用场景**：在哪些实体/服务中使用

**属性清单**：

| 属性 | 类型 | 精度/单位/格式 | 相等性判据 | 业务约束 |
|------|------|---------------|-----------|---------|
| amount | BigDecimal | 分（2位小数） | 是 | >= 0 |
| currency | String | ISO 4217 三字母 | 是 | 必填 |
| scale | int | 小数位数 | 否 | 默认2 |

**不可变性**：是/否。修改方式：创建新实例 / 原地修改
**相等性判据**：所有属性全部相等 / 部分属性（列出）

**序列化**：
- JSON：{"amount": 1000, "currency": "CNY"}
- 数据库：amount 字段存储分值整数
- 历史兼容：v1.0 使用元为单位（2位小数），v2.0 改为分（0位小数）

**与实体的边界**：
- 为什么不是实体：没有独立业务身份，金额100分和另一个100分没有区别
- 升级条件：如果需要追踪"这笔金额是谁审批的"，则需升级为实体
```

**禁止行为**：
- ❌ 把值对象当作实体分析（赋予独立身份、生命周期）
- ❌ 忽略精度和单位（如金额元/分混淆导致严重错误）
- ❌ 不检查序列化兼容性（历史数据可能因格式变化而无法解析）
- ❌ 把不同上下文中同名但精度/单位不同的值对象当作同一概念

**退出条件**：每个核心值对象都有"业务概念"和"相等性判据"描述；精度/单位/格式已明确；序列化兼容性已检查。

**分析结论的流向**：值对象分析输出应输入到 §2.2 数据资产最小语义卡（登记业务含义和精度约束），以及 §3.1 Schema 盘点（验证数据库字段类型与值对象精度是否匹配）。发现精度/单位不一致时，应联动 §3.4 声明与实际分布互证，并登记到 §8.1 数据质量规则。

### 2.2 数据资产最小语义卡

每个进入主文档的核心数据资产（表/集合/文档/事件流/缓存键）必须登记一张最小语义卡：

| 字段 | 内容 |
|---|---|
| 资产 ID 与名称 | 使用业务语言命名（如"门店收款流水"），不使用裸表名代替 |
| 业务含义 | 一句话说明该资产在业务中代表什么、由哪些事实产生/更新 |
| 权威源 | 谁是该资产的权威写入方；多个来源时声明权威源与副本关系 |
| 粒度（Grain） | 一行/一文档/一事件究竟代表什么，唯一性必须在该粒度下定义 |
| 时间语义 | 至少区分业务发生时间、系统处理时间、有效起止时间、入仓时间及时区 |
| 生命周期 | 创建/更新/归档/删除路径，是否物理删除或逻辑删除 |
| 关联资产 | 引用其他资产的 ID 及关系类型（结构/轨迹/归因） |
| 证据 | 对应表/字段/代码位置与版本基线 |

**约束**：语义卡必须在事实轨迹和维度分析之后填写（L1"维度从事实派生"），不得在零事实时先验建立"领域模型完成"结论；无法确定语义的字段登记 U-* 而非猜测。

### 2.3 标识与映射

逐项核对：

- 技术主键、业务标识、租户内标识、全局标识、外部机构标识和幂等键；
- 标识作用域、生成方、稳定性、是否复用、大小写/前导零/格式化规则；
- 合并、拆分、重建、跨系统同步时旧 ID 与新 ID 的映射表；
- 映射是一对一、一对多、多对一还是按有效期变化；
- 映射失败、重复、延迟和人工修复如何发现与追溯。

## 3. Schema、关系、约束、状态与实际分布互证

### 3.1 Schema 盘点

至少采集：表/视图/物化视图、列类型与精度、默认值、生成列、主键/唯一/CHECK/外键、索引、分区、触发器、存储过程、序列、字符集/排序规则、时区、表空间以及迁移历史。

评价字段类型、NULL、默认值、主键、UUID/自增/雪花 ID、JSON、扩展表、分区或 EAV 时，不使用“一律禁止/推荐”。必须结合业务粒度、写入模式、排序局部性、跨库生成、兼容契约、查询能力和数据库版本说明取舍。

### 3.2 关系与完整性

数据库外键、应用关联和业务关系分别记录。所有关系必须判定相对交易角色、建立/变更时机与变更影响；禁止把配置型关系写成“运行时不可改变”：

- **配置型（相对交易）**：关系实例通常作为业务交易的前置资料/规则被读取，而不是在每次交易中临时计算；实例仍可在配置维护期经授权入口变更，不得写成“运行时不可改变”
- **交易型**：在业务交易执行过程中创建、变更或解除
- **派生型**：由其他已证实事实计算得出，无独立维护入口或仅有只读投影
- **混合型**：同时包含配置部分与交易/派生部分时，必须分别说明边界、变更权限和历史影响

**字段名真实性门禁**：关系文档中引用的所有字段名（来源对象字段、目标对象字段、外键字段、关联字段）必须与源码（Entity/POJO/DTO/VO/枚举/数据库Schema）中的实际字段名逐字段核对；跨层允许 API/DTO/DB/前端命名差异，但必须有可解析映射证据；禁止无映射猜测名。核对须记录层别、符号、出处和版本基线

| 关系 ID | 业务关系 | 建立时机 | 来源对象 | 目标对象 | 声明约束 | 应用维护机制 | 删除/归档语义 | 数据命中率 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|
| REL-001 | 1:1/1:N/N:M/层级/时态 | 配置型/交易型/派生型/混合型 |  |  | FK/唯一/无 |  |  |  |  |

判断关系质量时必须验证：类型和作用域是否一致、租户键是否参与关联、历史/逻辑删除是否影响命中、级联是否符合业务保留要求，以及并发写入和部分失败是否产生孤儿或重复。缺少 FK 只能登记为“完整性由何处保证”的问题，不能直接定性为缺陷。

配置式关系（由 UI 配置建立）若由 UI 配置，数据侧必须继续核对保存请求最终写入的权威字段/关联表、唯一性与基数约束、生效读取点、修改/解绑语义和审计历史。页面控件存在不等于关系已经持久化；未找到 FK 或级联代码也不等于”不存在关系”或”无级联”。

**维护入口证据链（条件适用）**：先判定维护入口类型；仅当入口包含 UI 时启用下列清单，其他入口用对应链路，不适用段填“无/不适用”+理由。**UI 配置关系取证清单**（仅 UI 入口适用；适用项须有源码或契约证据）：

1. **配置入口路径**：哪个菜单/页面 → 哪个功能模块 → 哪个具体操作触发关系建立/变更/解除
2. **配置数据结构**：配置数据存储的具体表名、字段名、字段类型；关联关系在哪个字段体现（外键字段/JSON字段/关联表/M2M表）
3. **配置写入链路**：前端请求的 API 路径 → DTO/VO 字段映射 → Service 层校验逻辑 → 最终持久化的表和字段；字段名必须与源码逐字段核对
4. **配置约束与校验**：唯一性约束（单对象唯一/组合唯一/租户内唯一）、基数约束（1:1/1:N/N:M 上限）、业务规则校验
5. **配置生效读取链路**：业务操作时从哪个表/字段读取配置；读取路径是否经过缓存、是否有延迟
6. **配置变更与解除语义**：配置修改后是否影响已产生的业务数据；解除关系时历史业务数据如何处理
7. **配置审计与历史**：谁在何时因何操作变更了配置；变更前后的值
8. **边界情况处理**：未配置时的默认行为；配置冲突时的优先级规则；配置数据与业务数据不一致时的处理

### 3.3 约束、不变量和状态机

约束分三层记录：

1. **Schema 约束**：NOT NULL、UNIQUE、CHECK、FK、触发器等；
2. **应用约束**：校验、条件更新、锁、事务、状态转换；
3. **业务不变量**：任何合法路径下都必须成立的事实，例如“同一幂等键只能产生一笔有效入账”。

| 规则 ID | 对象/粒度 | 规则或不变量 | 实现位置 | 并发保护 | 失败/补偿 | 数据验证 | 证据 | 状态 |
|---|---|---|---|---|---|---|---|---|
| INV-001 |  |  | DB/服务/事件/人工 |  |  | 反例数/样本 |  | 未验证/交叉验证/已反证 |

状态字段分析必须同时检查：枚举定义、合法迁移、触发者、前置条件、终态、撤销/冲正、并发条件更新、历史状态记录和实际值分布。不能因发现未定义值就立即判错；先核对版本、灰度、导入、历史语义和旁路写入。

### 3.4 声明与实际分布互证

至少按风险选择以下分布：总量与增长、空值、基数、重复、极值、长度、时间、状态、租户、分区、热点、孤儿、跨字段组合和历史漂移。

| 对象/字段 | 声明语义 | Schema/代码约束 | 实际分布与窗口 | 反例 | 解释 | 结论/未知项 | 证据 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

禁止以下机械判断：

- 空值率高 ⇒ 字段废弃；
- 无外键 ⇒ 数据一定不一致；
- 有外键 ⇒ 业务关系一定正确；
- 低基数字段 ⇒ 索引一定无效；
- 不满足第三范式 ⇒ 设计错误；
- 表很宽/很大 ⇒ 必须拆表分库；
- 字段长度、索引数量超过固定阈值 ⇒ 必然有问题。

上述观察只能触发进一步验证。

## 4. 租户、权限、敏感数据与生命周期

### 4.1 租户隔离

- 租户标识在哪一层注入，是否进入主键/唯一键/关联键/分片键和缓存键；
- API、后台任务、消息消费、报表、导出、搜索、缓存、归档和恢复是否保持同一租户边界；
- 超级管理员、平台运营、跨租户聚合和代运营是否有明确授权、审计和最小范围；
- 缺失租户条件、默认租户、上下文丢失、跨租户 ID 猜测、共享缓存键和恢复到错误租户的失败模式；
- 租户迁移、合并、拆分和销户如何处理标识、历史和外部映射。

核心租户结论必须使用代码/配置与脱敏数据或运行证据交叉验证；不得通过越权读取其他租户数据来“验证隔离”。

### 4.2 权限与审计

识别数据库账号、服务账号、BI/报表账号、运维和人工脚本权限，验证最小权限、读写分离、职责分离、授权审批、轮换、审计留痕及紧急账号回收。应用层“有权限按钮”不能证明数据层不存在绕过路径。

### 4.3 敏感数据

| 数据分类 | 字段/对象 | 敏感等级 | 收集目的与合法性 | 存储/传输保护 | 脱敏/令牌化 | 访问与审计 | 保留期限 |
|---|---|---|---|---|---|---|---|
| 个人/支付/凭证/商业敏感 |  |  |  |  |  |  |  |

检查副本、缓存、搜索、日志、消息死信、备份、测试数据、导出文件和数仓是否复制了敏感数据。哈希不自动等于匿名化；可关联、可枚举或保留映射时仍按敏感数据管理。

### 4.4 保留、归档、删除与法律保全

为每类数据记录：保留依据、起算点、在线期限、归档格式与可读性、删除方式、备份中的到期处理、法律保全例外、恢复后再删除机制和证明材料。

逻辑删除不是生命周期终点；归档也不等于可安全删除。删除必须考虑关联数据、派生数据、搜索/缓存/数仓副本、外部接收方、审计要求和业务撤销/冲正需求。

## 5. 查询、索引、容量与执行计划

### 5.1 从真实工作负载出发

优先收集慢查询、查询统计、Trace、ORM 生成 SQL、报表 SQL、任务 SQL 和用户场景。每条关键查询关联：调用方、业务目的、频率/峰值、参数分布、返回量、延迟目标、一致性要求、超时/重试和版本环境。

| 查询 ID | 业务切片/调用方 | SQL 指纹 | 频率与峰值 | 参数/返回分布 | SLO | 当前计划 | 风险 | 证据 |
|---|---|---|---|---|---|---|---|---|
| Q-001 |  |  |  |  |  |  |  |  |

### 5.2 索引与计划验证

索引分析同时检查：过滤、连接、排序、分组、分页、覆盖性、最左匹配、表达式/隐式转换、统计信息、分区裁剪、回表、热点、锁与写放大。复合索引顺序不能只按“区分度高的在前”，应以真实谓词、排序、范围条件和复用价值验证。

建议新增/删除/调整索引前必须提供：

1. 目标查询和代表性参数；
2. 当前与候选执行计划；
3. 数据量、选择性和热点分布；
4. 读收益与写入、存储、维护、DDL 风险；
5. 在类生产数据上的基准或可解释估算；
6. 上线观测、失效判据和回滚方法。

不得仅凭 SQL 文本断言“索引失效”，也不得因两个索引前缀相似就直接删除其中一个；需检查覆盖查询、排序、唯一性、计划稳定性和隐藏调用方。

### 5.3 容量与热点

按业务增长和保留策略估算行数、字节、索引、分区、事务日志、备份窗口和恢复时间。识别大租户、热点键、时间热点、单调 ID 写热点、跨分片聚合、深分页和批任务争用。固定行数阈值不能替代对数据库版本、硬件、SLO 和变更方式的评估。

## 6. 分布式存储、派生系统与隐式依赖

### 6.1 分库分表

验证分片键来源与稳定性、路由完整性、跨片查询/事务、扩容再平衡、全局唯一性、广播表、热点分片、分页排序、归档、备份恢复和租户迁移。逻辑表、物理表及中间件规则必须对应到同一版本基线。

### 6.2 复制与读写分离

记录复制模式、拓扑、延迟分布、故障切换、只读路由和一致性需求。重点验证写后读、会话一致性、复制中断、重复/乱序、脑裂防护、提升旧副本及切换回退。不能只凭“主从正常”截图证明业务一致性。

### 6.3 缓存

识别缓存键（含租户边界）、值 Schema/版本、TTL、填充/失效、穿透/击穿/雪崩、防脏写和回源策略。明确缓存是可丢失派生副本还是承载不可重建事实；后者必须按权威存储风险处理。

### 6.4 搜索

核对索引文档粒度、映射、分词、刷新延迟、重建来源、增量顺序、删除传播、权限过滤和重建期间服务策略。搜索命中不等于权威事实；业务写入不可仅以搜索结果确认成功。

### 6.5 数仓、报表与指标口径

记录事实表粒度、维度变化策略、事件时间/处理时间、迟到数据、重跑覆盖、去重、口径版本和回溯能力。报表数字必须能追溯到权威源和转换规则；同名指标口径不一致应登记为矛盾项。

### 6.6 外部直连与旁路写入

检查数据库账号、连接审计、视图、报表工具、脚本、存储过程、定时任务、CDC 和外部系统。未搜到代码调用方不能断言无人使用。任何 Schema/索引/字段语义变更前，必须把外部直连和旁路写入列入兼容性调查。

## 7. 事务、一致性、并发、幂等与对账

### 7.1 事务边界

对关键业务切片绘制而非猜测事务边界：

```text
入口/命令 → 本地读写集 → 锁与隔离级别 → 提交点
          → 消息/缓存/搜索/外部副作用 → 重试/补偿 → 对账
```

核对事务传播、隔离级别、条件更新、锁顺序、长事务、异常吞没、提交后回调和连接中断。方法上的事务注解不等于运行时事务生效，需结合代理方式、调用路径、配置和运行证据验证。

### 7.2 一致性模型

为每条数据链路明确强一致、会话一致、单调读、最终一致或无保证，并记录可接受不一致窗口。跨服务/跨库方案可采用本地事务加可靠消息、Outbox、Saga/TCC、CDC 等，但不得脱离故障模式机械指定方案。

### 7.3 并发与幂等

必须覆盖重复请求、并发更新、消息重投、乱序、超时后结果未知、任务重跑和人工补偿：

| 场景 | 幂等作用域/键 | 原子性机制 | 重复结果 | 并发冲突策略 | 过期/清理 | 证据 |
|---|---|---|---|---|---|---|
| 支付回调/入库/发券等 |  | 唯一约束/条件更新/锁 |  | 拒绝/合并/重试 |  |  |

幂等不能只检查“是否有幂等表”，还要验证键粒度、保留时间、原业务结果复用、失败占位、并发窗口和多租户作用域。

### 7.4 对账与修复

对账定义双方/多方权威源、业务粒度、时间窗口、容差、迟到数据、差异分类、告警、自动/人工修复、复核和审计。修复脚本必须可预览、限范围、幂等、留痕、可停止并有回滚或反向操作；不得把“数量相等”当作完整一致性证明。

## 9. 迁移、DDL、回填、双写、校验、回滚与恢复

### 9.1 变更分类与兼容性

识别 Schema DDL、数据修复、标识迁移、拆库合库、引擎迁移、历史回填和生命周期清理。任何变更先盘点生产者、消费者、外部直连、缓存/搜索/数仓副本及历史数据兼容。

优先采用可逆、分阶段的扩展—迁移—收缩流程：

```text
建立基线与备份/恢复保障
→ 增量兼容变更（expand）
→ 新旧读写兼容或影子比对
→ 限速、可续跑回填
→ 增量追平/双写观察
→ 按粒度校验与业务验收
→ 灰度切读/切写
→ 稳定观察
→ 停旧写并确认无隐藏依赖
→ 延迟收缩（contract）
```

### 9.2 DDL 与回填

- 基于数据库版本、表规模、锁/日志/复制影响和磁盘余量选择原生在线 DDL、影子表或专用工具；固定行数阈值只能预警，不能直接决定方案。
- 在类生产环境演练并记录耗时、锁等待、日志增长、复制延迟和取消行为。
- 回填按稳定游标/分片执行，限速、可暂停、可续跑、幂等；避免大事务、深分页和与在线流量争抢热点。
- 明确回填期间新增/更新/删除数据如何追平，以及失败批次如何重试和审计。

### 9.3 双写

双写不是天然的一致性方案。必须说明写入顺序、原子性缺口、部分失败、重试、乱序、删除、幂等键、差异检测、修复、停写条件和退出计划。若采用 CDC/Outbox 等替代，也要验证延迟、重放和 Schema 演进。

### 9.4 校验

迁移校验至少包含：

- 行数/分区数等完整性基线；
- 主键或业务粒度的存在性、唯一性；
- 关键字段、聚合和业务不变量；
- 分层校验和/哈希及差异明细；
- 源端持续变化时的同一截止点或水位；
- API、任务、报表、对账和性能验收；
- 异常样本、阈值、负责人和关闭状态。

仅比较总行数或总金额不足以证明迁移正确。

### 9.5 回滚与前滚

DDL、数据语义和新写入可能不可简单回滚。方案必须区分：应用回滚、流量切回、读写开关、数据反向同步、备份恢复和修复性前滚。明确回滚触发阈值、最后安全点、数据丢失窗口、决策人和演练结果。

### 9.6 备份恢复

备份“成功”不等于可恢复。必须验证：

- RPO/RTO 与业务要求一致，覆盖全量、增量、日志和配置/密钥依赖；
- 备份加密、隔离、不可变、防勒索、保留和删除策略；
- 分片/多库/对象存储/搜索等组件在一致时间点的恢复顺序；
- 定期恢复演练、校验、应用启动、租户隔离和外部副作用抑制；
- 恢复后追平、对账、重复消息处理和到期数据再次删除。

## 10. 问题、未知项与闭环

### 10.1 不混淆记录类型

沿用 SOP-00：缺陷、风险、技术债、改进机会、未知项分别登记。命名不规范、未建外键、反范式或索引数量本身通常只是观察，只有违反明确要求/不变量并有证据时才能定为缺陷。

### 10.2 未知项与矛盾项

| ID | 类型 | 观察/未知问题 | 候选解释 | 支持/反对证据 | 最小区分性验证 | 决策影响 | 负责人 | 状态/期限 |
|---|---|---|---|---|---|---|---|---|
| U-DATA-001 | 未知/矛盾 |  |  |  |  |  |  |  |

高影响未知项在关闭前不得被省略；暂时无法关闭时，必须给出限制、保守假设、隔离措施和触发复查条件。

### 10.3 问题记录

| 字段 | 内容 |
|---|---|
| 问题 ID / 类型 | 缺陷、风险、技术债、改进机会或未知项 |
| 现象与触发条件 | 不掺杂未经验证的根因 |
| 违反的规则 | 契约、INV、DQ、安全或恢复要求 |
| 范围与基线 | 版本、环境、租户、时间窗口、业务切片 |
| 证据与确定性 | 证据 ID；直接事实/交叉验证/推断/假设 |
| 影响 | 对象、半径、频率、可检测性、可逆性 |
| 根因层级 | 直接、机制、系统性；证据不足时标假设 |
| 候选方案 | 包含不处理方案、成本、兼容和迁移影响 |
| 验证与回滚 | 可测验收标准、观测、停止和回滚/前滚 |
| 闭环 | 负责人、状态、期限、复查日期、关闭证据 |

P0-P3 仅表示业务严重度（等同 SEV-P0~P3），不替代发生可能性、暴露面、证据强度和处置时限，且与 L1 的 SC-P* 切片深度分级无关。

```text
G0 数据任务书、版本/环境/权限基线
```

6. 一致性、幂等、对账、迁移和恢复矩阵；
7. 证据索引、结论、矛盾、未知项和问题闭环台账。

- [ ] 核心数据的所有者、权威源、粒度、标识映射、时间语义和血缘已明确
- [ ] 关键 Schema 约束、应用约束、状态机、不变量与实际数据分布已互证
- [ ] 租户隔离、权限、敏感数据及保留/归档/删除适用项已检查

- [ ] 事务、一致性、并发、幂等、重试、补偿和对账的主要失败模式已覆盖
- [ ] 数据质量规则、异常样本、豁免、责任人和处置状态可追踪
- [ ] 迁移方案覆盖 DDL、回填、双写/同步、校验、切换、回滚/前滚和兼容退出
- [ ] 备份恢复具有实际演练或证据；无证据时已标为未知或风险
- [ ] 每条关键结论有证据 ID、确定性、适用范围、反证和限制
- [ ] 高影响未知项、矛盾项和问题已有负责人、验证动作、期限和关闭证据
- [ ] 不存在仅凭字段名、外键缺失、范式或固定阈值得出的好坏结论
- [ ] 未解释的强反证为零，另一名分析者可按证据和步骤复核关键结论

## 13. AI 辅助分析约束

1. 不以表名、字段名、注释、ORM 类名直接定义业务语义；只能生成假设，并给出最小区分性验证。
2. 不把数据库表机械映射为领域实体、聚合边界或权威源。
3. 不因缺少外键、未满足某种范式、使用 UUID/JSON/逻辑删除或索引数量较多就判定设计错误。
4. 不生成未经核对数据库产品/版本、索引、分区和影响预算的生产探针；默认只读、限范围、脱敏。
5. 不臆造数据量、分布、执行计划、调用频率、复制延迟、RPO/RTO 或恢复成功事实。
6. 不以“未搜索到引用”断言字段/表无人使用；必须考虑动态 SQL、配置、脚本、任务、报表、CDC 和外部直连。
7. 不把测试环境、单租户、单时段或单个样本外推为全量生产结论。
8. 不推荐删除字段、索引、表、历史数据或关闭旧链路，除非消费者、保留要求、迁移、验证和回滚均有证据。
9. 不把常见实践写成唯一方案；建议必须列出场景前提、替代方案、兼容影响、验证和回滚。
10. 对证据冲突先登记矛盾；不得静默选取最符合预期的一份证据。
11. 输出必须区分直接事实、交叉验证结论、推断和假设，并同时列证据 ID、范围与未知项。
12. 不在提示词、第三方服务或分析产物中泄露生产数据、凭据、连接串或跨租户敏感信息。
13. 不得虚构证据 ID、文件位置、行号、版本、数据量、分布、执行计划、调用方或历史行为；无法取得的信息填写"未知/待确认"，未执行的动作必须明确写"未验证"。
