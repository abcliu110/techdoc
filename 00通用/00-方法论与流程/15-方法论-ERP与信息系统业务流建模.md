## 0. AI 执行入口

### 0.1 本文解决的问题

本文用于回答：

1. ERP 和企业信息系统中有哪些重要的“流”。
2. 商流、物流、资金流、信息流分别是什么，如何区分。
3. 计划流、生产流、质量流、成本流、会计流和票税流如何扩展经典四流。
4. 业务流、端到端流程、状态机、账本和技术数据流有什么区别。
5. 如何为每条流建立对象、状态、权威系统、正逆向和对账关系。
6. 如何避免用一个订单状态代替整个企业业务运行状态。

核心结论：

> ERP 的本质不是把所有业务放进一个软件，而是让多条独立业务流在统一业务语义下协同运行，同时保持各自的对象、状态、账簿、时间、责任和权威边界。

### 0.2 最小输入

- 企业类型：贸易、制造、零售、平台、服务或混合经营。
- 客户、供应商、组织、仓库、工厂、门店和结算主体。
- 商品、物料、服务、资产和权益。
- 采购、生产、库存、销售、履约、收付款、成本和会计过程。
- 业务单据、状态、事件、消息和接口。
- 正向、取消、退货、退款、红冲、返工、补偿和对账场景。
- 各系统的数据所有权、时间口径和历史兼容约束。

输入不足时，AI 只能输出候选业务流地图和待确认项，不能根据行业惯例自行决定收入确认、所有权转移、税务、资金或库存口径。

### 0.3 核心输出

```text
业务流分类与范围
+ 各流对象、状态和权威系统
+ 端到端流程—业务流矩阵
+ 正向与逆向流
+ 跨流关系和对账规则
+ 数据、事件与单据追踪
+ 异常、补偿和人工收敛
+ 风险、测试和完成判据
```
## 1. “流”到底是什么

### 1.1 业务流的判定标准

一个概念要作为独立业务流分析，通常至少具有：

```text
流动或转换对象
+ 起点和终点
+ 参与主体
+ 状态变化
+ 数量、金额或责任变化
+ 权威记录
+ 正向和逆向路径
+ 可验证的业务结果
```

例如物流的流动对象是货物和保管责任；资金流的流动对象是资金、债权和债务；信息流的流动对象是单据、事件和业务事实表示。

不是所有被称为“流”的内容都处在同一抽象层。分析前应区分：

| 概念 | 关注点 | 示例 |
|---|---|---|
| 业务流 | 业务对象、价值或责任如何移动 | 商流、物流、资金流 |
| 端到端流程 | 为完成客户结果需要哪些活动 | O2C、P2P、R2R |
| 状态机 | 单个对象允许怎样变化 | 订单、支付、发票状态 |
| 账本 | 数量或价值变化如何不可覆盖地记录 | 资金账、库存账、积分账 |
| 工作流 | 人和系统任务如何协调 | 采购审批、退款审批 |
| 数据流 | 数据如何生成、转换和传输 | API、MQ、ETL、报表 |
| 控制流 | 程序或规则如何选择执行路径 | 条件、分支、异常 |

### 1.2 三种常见口径

#### 供应链经典三流

```text
物流 + 资金流 + 信息流
```

#### 电子商务和现代供应链四流

```text
商流 + 物流 + 资金流 + 信息流
```

#### 财税合规四流

```text
合同流 + 货物流 + 资金流 + 发票流
```

三种口径服务于不同目的，不能因为名称相似就互相替代。

### 1.3 本文采用的分层

```text
L1 企业核心流：商流、物流/履约流、资金流、信息流
L2 ERP 专业流：计划、生产、质量、成本、会计、票税、任务、资产、人力
L3 端到端流程：O2C、P2P、Plan-to-Produce、R2R 等
L4 技术运行流：数据、事件、消息、状态、控制、配置版本和审计证据
```

## 2. 核心流一：商流

### 2.1 定义

商流描述交易关系、价格条件、权利义务和商业责任如何形成、变更和终止。

```text
需求/商机
→ 报价
→ 合同
→ 订单
→ 订单确认
→ 变更
→ 完成/取消/退货终止
```

### 2.2 关键对象

- 客户、供应商、商户和合作方。
- 商品、服务、套餐和权益。
- 报价、合同、销售订单和采购订单。
- 价格、折扣、税务条件、交付条件和支付条件。
- 所有权、使用权、风险和履约责任。

### 2.3 关键问题

```text
谁与谁交易？
交易什么、多少、什么价格？
何时成立、变更和结束？
谁拥有选择、批准和取消权？
何时转移所有权、风险或服务权利？
```

### 2.4 边界

- 商流成立不等于货物已经交付。
- 订单确认不等于已经收款。
- 合同生效不等于已经确认收入。
- 订单取消可能需要分别触发库存释放、退款和发票红冲。

## 3. 核心流二：物流、物料流与履约流

### 3.1 实物业务

制造和供应链中，物流也可称为物料流：

```text
供应商发货
→ 收货
→ 检验
→ 入库
→ 库存
→ 预占
→ 领料/拣货
→ 出库
→ 运输
→ 签收
```

### 3.2 关键对象

- 物料、商品、批次和序列号。
- 仓库、库区、库位和库存状态。
- 收货、入库、移库、领料、出库和盘点单。
- 包裹、运输任务、承运商和签收证明。
- 可用、冻结、预占、在途、待检和不合格数量。

### 3.3 服务业务

没有明显实物的业务，应使用“服务履约流”：

```text
预约
→ 受理
→ 派工
→ 到场/开始服务
→ 服务执行
→ 验收
→ 售后
```

### 3.4 核心约束

```text
实物数量和保管责任可追溯
库存预占、扣减和释放有明确语义
批次、序列号和质量状态不能丢失
出库、运输和签收不是同一个状态
```

### 3.5 边界

物流状态不应代替商流和资金流状态。货物已经签收，不自动证明：

- 订单商业条件全部满足。
- 客户已经付款。
- 收入已经确认。
- 发票已经开具。
- 商户已经完成结算。

## 4. 核心流三：资金流

### 4.1 定义

资金流描述货币、债权和债务在参与方之间如何形成、冻结、支付、清算、结算、退款和核销。

销售侧：

```text
形成应收
→ 支付授权
→ 支付受理
→ 到账
→ 清算/分账
→ 结算
→ 应收核销
```

采购侧：

```text
形成应付
→ 付款申请
→ 审批
→ 银行支付
→ 对方到账
→ 应付核销
```

逆向：

```text
退款申请
→ 审批
→ 退款受理
→ 退款成功/未知/失败
→ 冲正和核销调整
```

### 4.2 关键对象

- 应收、应付、预收和预付。
- 支付单、退款单、收付款单。
- 银行流水、支付渠道流水。
- 分账单、结算单和核销单。
- 资金账户、冻结金额和可用余额。

### 4.3 必须分离的概念

```text
支付成功 ≠ 清算完成
清算完成 ≠ 商户结算到账
银行扣款 ≠ 应付核销
退款受理 ≠ 退款到账
资金到账 ≠ 收入确认
```

## 5. 核心流四：信息流

### 5.1 定义

信息流描述业务事实如何以数据、单据、事件、消息和凭证形式生成、传播、同步、解释和审计。

```text
订单数据
→ 库存预占事件
→ 支付通知
→ 发货事件
→ 签收信息
→ 开票信息
→ 结算与对账信息
```

### 5.2 主要载体

- 业务单据和电子凭证。
- API、文件和批量接口。
- MQ 消息和领域事件。
- 主数据、规则版本和配置。
- 决策快照、日志和审计记录。
- 报表、指标和数据仓库。

### 5.3 信息到达不等于业务完成

```text
收到支付成功消息
```

只代表信息到达，仍需验证消息真实性、幂等、金额、主体、支付状态、订单状态以及后续分账结算。信息流是其他流的表示和协调机制，不是其他流本身。
## 6. ERP 专业流一：计划流

### 6.1 定义

计划流把市场需求、库存、产能、提前期和供应策略转换成可执行建议：

```text
销售预测
→ 需求计划
→ S&OP
→ 主生产计划 MPS
→ 物料需求计划 MRP
→ 采购/生产/调拨建议
→ 已批准执行计划
```

### 6.2 必须区分

```text
销售预测 ≠ 销售订单
采购建议 ≠ 采购订单
生产计划 ≠ 生产工单
计划需求 ≠ 实际库存扣减
```

计划流可以被重新计算；正式订单和实际执行则产生新的业务事实。计划覆盖执行事实会破坏追溯。

## 7. ERP 专业流二：生产流

```text
生产计划
→ 生产工单
→ 工序排程
→ 领料
→ 开工
→ 工序报工
→ 在制品转移
→ 完工
→ 检验
→ 成品入库
```

关键对象：BOM、工艺路线、工作中心、工单、工序任务、领退料、报工、在制品和完工品。

生产流同时牵动：

```text
物料流：原料、在制品和成品变化
成本流：材料、人工和制造费用归集
质量流：检验、返工和报废
信息流：工单、设备数据和报工事件
```

生产状态不能由单一“完成百分比”代替；物料齐套、工序进度、质量放行和成本结转可能处于不同阶段。

## 8. ERP 专业流三：质量流

```text
质量标准
→ 检验计划
→ 来料/过程/完工检验
→ 合格放行或不合格隔离
→ 返工/让步/退货/报废
→ 原因分析
→ 纠正预防措施 CAPA
→ 关闭和追溯
```

关键对象：检验标准、检验批、抽样方案、检测结果、不合格品、质量事故、返工单和 CAPA。

质量状态会影响库存可用性、生产投料、成品出库和供应商评价，但不应直接篡改原库存、生产或采购事实。

## 9. ERP 专业流四：成本流与价值流

### 9.1 成本流

```text
采购成本
→ 入库成本
→ 材料成本
→ 人工与制造费用
→ 在制品成本
→ 完工产品成本
→ 销售成本
```

关键对象：成本中心、成本对象、成本要素、标准成本、实际成本、作业成本、分摊和差异。

### 9.2 与资金流的区别

```text
采购入库：可能形成库存价值，但尚未付款。
赊销发货：可能形成收入和应收，但尚未收到资金。
计提折旧：发生成本和会计变化，但没有外部资金流。
```

成本流回答“价值如何归集和转移”，资金流回答“钱是否实际流动”。

## 10. ERP 专业流五：财务会计流

```text
业务事实
→ 会计事件
→ 会计规则
→ 会计分录
→ 凭证
→ 明细账
→ 总账
→ 财务报表
```

主要内容：

- 应收、应付和固定资产会计。
- 收入确认和销售成本结转。
- 费用计提、摊销和折旧。
- 存货核算和成本差异。
- 期间结账和财务报表。

必须区分：

| 流 | 核心问题 |
|---|---|
| 资金流 | 钱是否实际流入或流出 |
| 成本流 | 价值如何归集、转移和分摊 |
| 会计流 | 业务如何按会计政策形成分录和报表 |

会计凭证应来源于可追溯业务事件；人工凭证不能成为掩盖业务链断裂的默认补丁。

## 11. ERP 专业流六：发票流和税务流

```text
开票申请
→ 开具蓝字发票
→ 交付/收取发票
→ 认证与抵扣
→ 红冲/作废/换票
→ 税务申报
```

关键对象：发票抬头、发票明细、税率、税额、蓝票、红票、进项、销项和申报记录。

必须区分：

```text
已经开票 ≠ 已经收款
已经付款 ≠ 已收到合法采购发票
发生退款 ≠ 已经完成发票红冲
订单金额 ≠ 在任何场景下都等于开票金额
```

分批交付、部分开票、折扣分摊、价外费用、税差和红冲都需要明确口径。

## 12. ERP 专业流七：单据流

销售单据链：

```text
报价单
→ 合同
→ 销售订单
→ 发货通知
→ 出库单
→ 运输/签收单
→ 应收单
→ 发票
→ 收款单
```

采购单据链：

```text
采购申请
→ 采购订单
→ 收货单
→ 检验单
→ 入库单
→ 应付单
→ 采购发票
→ 付款单
```

单据转换应记录：来源单、目标单、上游数量、已转换数量、剩余数量、版本、取消和冲销关系。不要只用备注文本描述来源。

单据是业务事实的载体，不是事实本身。删除单据不能让已经发生的收货、付款和会计事实消失。

## 13. ERP 专业流八：审批流和任务流

```text
提交
→ 业务审批
→ 财务/风险审批
→ 执行
→ 复核
→ 归档
```

关键对象：审批实例、节点、任务、审批人、意见、委托、会签、或签、超时、升级、撤回和驳回。

审批通过只表示获得执行授权，不表示执行已经完成。例如采购申请审批通过不等于采购订单已下达、货物已入库或供应商已付款。

## 14. ERP 专业流九：资产流

```text
采购
→ 验收
→ 资产建卡
→ 领用
→ 转移
→ 折旧
→ 维修
→ 盘点
→ 减值
→ 处置/报废
```

资产流同时关联：

- 实物位置和责任人。
- 原值、累计折旧和净值。
- 维修和停机记录。
- 会计分录和处置损益。

资产实物状态、使用状态和会计状态应分别建模。

## 15. ERP 专业流十：人力资源流

```text
招聘需求
→ 候选人
→ 录用
→ 入职
→ 试用
→ 转正
→ 调岗/调薪
→ 培训/绩效
→ 离职
```

薪资相关链路：

```text
排班与考勤
→ 薪资计算
→ 社保个税
→ 工资发放
→ 成本分摊
→ 会计入账
```

人力资源流适用于 HCM/HRM。员工生命周期、组织任职、薪资资金流和人工成本流不能压缩成一个员工状态。

## 16. 场景化扩展流

### 16.1 人流或客流

适用于门店、商场、餐饮和线下服务：

```text
到店 → 行走/停留 → 排队 → 服务 → 转化 → 离店/复访
```

到店未购买只产生人流，没有形成商流。

### 16.2 权利流或所有权流

适用于租赁、寄售、供应链金融、数字权益和许可证业务。发货、签收、付款和所有权转移可能发生在不同时间，应由合同明确。

### 16.3 服务流

适用于医疗、维修、咨询、SaaS 和专业服务；服务交付、验收、计费和续费通常替代传统实物物流。
## 17. 企业端到端流程不是另一组同义业务流

端到端流程以客户或企业结果为边界，通常横跨多条业务流：

| 缩写 | 流程 | 业务结果 |
|---|---|---|
| L2C | Lead-to-Cash | 从线索到收入和收款 |
| O2C | Order-to-Cash | 从销售订单到收款核销 |
| P2P | Procure-to-Pay | 从采购需求到供应商付款 |
| Plan-to-Produce | 计划到生产 | 从需求计划到完工入库 |
| R2R | Record-to-Report | 从会计记录到财务报告 |
| H2R | Hire-to-Retire | 从招聘到员工离职 |
| A2R | Acquire-to-Retire | 从资产取得到报废处置 |

不要把 O2C 当成与物流、资金流并列的单一流。O2C 是贯穿商流、物流、资金、会计、发票和信息流的端到端过程。

## 18. O2C：销售到收款的多流贯通

```text
报价/合同/销售订单          商流
→ 可承诺量和需求计划         计划流
→ 库存预占                  物流
→ 拣货、出库、运输、签收     物流/履约流
→ 质量放行                  质量流
→ 形成应收和收入条件判断     会计流
→ 开具销售发票              票税流
→ 客户支付和银行到账         资金流
→ 清算、分账、结算和核销     资金/会计流
→ 消息、单据和报表同步       信息流
```

### 18.1 阶段矩阵

| 阶段 | 商流 | 物流/履约 | 资金 | 会计/成本 | 发票 | 信息 |
|---|---|---|---|---|---|---|
| 下单 | 订单成立 | 预占候选 | 可能预授权 | 暂未确认 | 暂无 | 下单事件 |
| 支付 | 交易确认 | 等待履约 | 支付/预收 | 形成相应会计事件 | 满足条件后可开 | 支付通知 |
| 发货 | 履约执行 | 出库、在途 | 可能待结算 | 按政策判断收入/成本 | 可部分开票 | 发货事件 |
| 签收 | 商业履约确认 | 完成交付 | 进入结算条件 | 收入、应收、成本 | 可申请或完成开票 | 签收事件 |
| 退款 | 交易部分/全部解除 | 退货或无需退货 | 退款、冲正 | 应收和收入调整 | 红冲/调整 | 退款事件 |

具体企业的收入确认、所有权转移和开票时点必须依据合同、会计和税务政策确认，不能直接采用本表作为最终规则。

## 19. P2P：采购到付款的多流贯通

```text
采购申请和寻源             商流/任务流
→ 采购订单                 商流
→ 供应商发货和企业收货      物流
→ 来料检验                 质量流
→ 入库                     物流/成本流
→ 供应商发票               票税流
→ 订单、收货、发票匹配      控制/信息流
→ 形成应付                 会计流
→ 付款审批和支付            任务/资金流
→ 应付核销                 会计流
```

经典三单匹配：

```text
采购订单
+ 收货/入库记录
+ 供应商发票
```

匹配的不只是单号，还包括主体、商品、数量、单价、税率、金额、币种和时间。合理差异必须有容差政策、审批和审计，不能直接以“最新单据为准”。

## 20. Plan-to-Produce：计划到生产

```text
需求预测和订单              商流/计划流
→ MPS/MRP                  计划流
→ 采购、调拨和备料          商流/物流
→ 生产工单                 生产流
→ 领料和在制品              物料流
→ 工序报工和检验            生产/质量流
→ 完工入库                 物流
→ 成本归集和差异分摊        成本流
→ 会计凭证                 会计流
```

关键对账包括计划量、工单量、领料量、投产量、合格量、不合格量、报废量、完工入库量和成本归集量。

## 21. 信息系统技术运行流

### 21.1 数据流

```text
输入/采集
→ API/文件
→ 应用服务
→ 业务数据库
→ 事件/MQ
→ 数据仓库
→ 指标和报表
```

关注数据来源、所有权、血缘、转换、主数据、一致性、质量和生命周期。

### 21.2 事件流和消息流

```text
业务事实形成
→ 发布领域事件
→ 消费者接收
→ 幂等处理
→ 形成新事实或任务
→ 发布后续事件
```

关注生产者、消费者、顺序、重复、重试、死信、版本和最终一致性。

### 21.3 状态流

每个重要对象都应有自己的状态机：

```text
订单状态
履约状态
库存预占状态
支付状态
结算状态
发票状态
审批状态
售后状态
```

状态之间可以有约束，但不能合并为一个万能状态字段。

### 21.4 控制流

控制流描述程序、规则或流程如何选择路径：条件、分支、循环、异常、回退和补偿。它偏实现机制，不能代替业务语义。

### 21.5 配置和规则版本流

```text
草稿
→ 模拟
→ 评审
→ 批准
→ 待生效
→ 灰度
→ 生效
→ 停止新业务使用
→ 仅服务历史对象
→ 退役
```

适用于价格、税率、审批、会计、结算和权限政策。

### 21.6 审计证据链

审计链回答：

```text
谁在什么时间
基于什么事实和规则版本
作出什么决定
执行什么动作
形成什么结果
是否被撤销、冲正或覆盖
```

审计日志不能代替领域事实，但必须能够连接各流的权威记录。

## 22. 每条流的标准建模模板

```text
FlowDefinition
- flowId/name
- businessPurpose
- movingObject
- source/target
- actorsAndResponsibilities
- commands/events
- statesAndTransitions
- quantityOrAmount
- ownershipAndCustody
- authoritativeSystem
- businessTime/processingTime/recordedTime
- upstream/downstreamFlows
- forwardPath
- reversePath
- invariants
- reconciliationRules
- evidenceAndAudit
- failureAndRecovery
```

### 22.1 对象

明确流动的是订单权利、物料、资金、价值、单据还是信息。对象不明确时，流程图容易只剩动作名称。

### 22.2 状态

状态必须表示稳定、可观察的业务事实，而不是页面步骤或临时技术动作。

### 22.3 权威系统

明确哪个系统对哪个事实有最终解释权。例如：

| 事实 | 候选权威系统 |
|---|---|
| 合同和订单商业条件 | 合同/订单系统 |
| 库存数量和批次 | WMS/库存系统 |
| 运输轨迹 | TMS/承运平台 |
| 支付渠道结果 | 支付系统并与渠道对账 |
| 会计余额 | 财务总账/明细账 |
| 发票状态 | 发票/税务系统 |

真实项目必须按组织职责和系统边界确认，不能只按系统名称推断。

### 22.4 时间

至少区分：

```text
业务发生时间
规则生效时间
系统处理时间
外部机构确认时间
数据记录时间
对账确认时间
```

不同时间口径是跨系统差异的重要来源。
## 23. 跨流关联模型

### 23.1 统一业务关联键，不统一所有生命周期

```text
businessTransactionId
├─ contractId
├─ salesOrderId / purchaseOrderId
├─ fulfillmentOrderId
├─ inventoryReservationId
├─ shipmentId
├─ paymentOrderId
├─ settlementOrderId
├─ accountingDocumentId
├─ invoiceId
└─ afterSaleId
```

这些对象通过业务关联键追踪，但保留各自标识、状态和版本。强迫所有对象共用一个 ID、状态或数据表会制造隐式耦合。

### 23.2 关系类型

```text
一对一：一个付款对应一个订单
一对多：一个订单拆成多个发货单
多对一：多个订单合并结算
多对多：多次支付覆盖多个订单或发票
部分关系：部分发货、部分开票、部分退款
派生关系：会计分录由多个业务事件汇总产生
逆向关系：退款关联原支付，红票关联原蓝票
```

数据模型和对账算法必须支持真实关系，不能预设全部一对一。

## 24. 不要使用一个状态表示所有流

错误模型：

```text
order.status = COMPLETED
```

它无法回答：

- 商业订单是否仍可售后。
- 是否全部发货和签收。
- 是否全部收款、退款或结算。
- 是否全部开票和红冲。
- 会计是否完成确认和核销。

推荐分离：

```text
CommercialState
FulfillmentState
LogisticsState
InventoryState
PaymentState
SettlementState
InvoiceState
AccountingState
AfterSaleState
```

可以建立聚合视图，例如“订单总览状态”，但它只能是可解释的派生结果，不能反向覆盖各专业状态。

## 25. 正向流、逆向流和调整流

| 正向业务 | 逆向/调整业务 |
|---|---|
| 下单 | 取消、变更 |
| 库存预占 | 释放预占 |
| 出库 | 退货入库 |
| 生产领料 | 退料、补料 |
| 完工 | 返工、报废 |
| 支付 | 退款、冲正 |
| 收入确认 | 收入调整 |
| 开票 | 红冲、作废、换票 |
| 权益发放 | 撤销、返还 |
| 资产入账 | 处置、报废、减值 |

逆向不是删除或把状态直接改回去，而是新的业务事实：

```text
原事实保持不可覆盖
+ 新逆向单据
+ 与原业务关联
+ 独立审批和状态
+ 对应账本分录
+ 对账和审计
```

## 26. 跨流不变量和对账

### 26.1 数量对账

```text
订单数量
↔ 预占数量
↔ 出库数量
↔ 签收数量
↔ 退货数量
```

### 26.2 金额对账

```text
订单应付
↔ 支付
↔ 退款
↔ 分账
↔ 结算
↔ 应收核销
```

### 26.3 成本和会计对账

```text
入库价值
↔ 存货余额
↔ 生产耗用
↔ 完工成本
↔ 销售成本
↔ 总账余额
```

### 26.4 票税对账

```text
合同/订单主体与内容
↔ 实际交付
↔ 收付款
↔ 发票主体、数量、金额和税额
```

### 26.5 不应机械要求简单相等

拆单、部分交付、手续费、平台补贴、汇率、税差、舍入、预收、退款和红冲会造成合理差异。每条对账规则必须声明：

```text
比较对象
统计范围
时间窗口
币种和汇率
含税/未税口径
容差
合法差异原因
差异责任人
修复或调整方式
```

## 27. 一致性与异常收敛

跨流通常是异步的，不可能依赖一个数据库事务覆盖所有系统。推荐：

- 每条流在自身权威系统内维护局部一致性。
- 使用业务幂等键防止重复不可逆结果。
- 使用 Outbox/Inbox 或可靠消息传递事实。
- 明确“已接受、处理中、成功、失败、结果未知”。
- 使用状态查询、重试、补偿和对账收敛。
- 对不能自动裁决的差异建立人工任务和责任时限。

错误做法：

```text
外部支付超时
→ 直接标记支付失败
→ 允许再次支付
```

正确做法：

```text
外部支付超时
→ 标记 RESULT_UNKNOWN
→ 禁止同业务意图重复支付
→ 使用原幂等键查询
→ 对账或转人工
```

## 29. AI 分析算法

```text
INPUT：企业范围、系统地图、单据、接口、状态、账簿和业务样例

1. 确定行业和经营模式，冻结分析范围。
2. 从客户或企业结果识别 O2C、P2P、生产、R2R 等端到端流程。
3. 对每个流程分别识别商流、物流/履约、资金流和信息流。
4. 按场景补充计划、生产、质量、成本、会计、票税、任务、资产和人力流。
5. 为每条流识别流动对象、主体、状态、命令、事件和权威系统。
6. 区分计划、承诺、执行和最终确认，禁止混用状态。
7. 建立业务主键和专业对象 ID 之间的一对一、一对多和多对多关系。
8. 绘制正向、逆向、调整和补偿路径。
9. 识别跨流不变量、时间口径和对账规则。
10. 识别 API、消息、文件、批任务和人工操作等信息通道。
11. 检查重复、乱序、超时、部分成功和结果未知如何收敛。
12. 区分直接事实、推断、假设和未知项，记录证据来源。
13. 形成业务流地图、状态矩阵、跨流追踪矩阵和差异清单。
14. 关键设计进入 SOP-09；多历史实现进入 SOP-10。
```

AI 不得仅根据模块名推断权威系统，不得把页面显示状态当成领域事实，也不得自行决定所有权、收入确认、税务和会计口径。

## 31. 常见反模式

1. 只画一个业务流程图，不区分商流、物流、资金和信息流。
2. 使用一个 `orderStatus` 表达订单、履约、支付、结算、发票和售后。
3. 把计划建议当成正式订单或实际执行事实。
4. 把资金到账、收入确认和会计入账视为同一事件。
5. 把发货、签收、所有权转移和收入确认视为同一时点。
6. 只设计正向流程，不设计取消、退货、退款、红冲和冲正。
7. 使用删除或覆盖原记录实现逆向业务。
8. 假设订单、发货、支付、发票和会计凭证永远一对一。
9. 仅按单号对账，不校验主体、数量、金额、币种、税额和时间。
10. 把消息发送成功当成下游业务完成。
11. 把页面状态或报表字段当成权威业务事实。
12. 多系统同时修改同一专业事实，没有明确数据 Owner。
13. 使用当前规则和当前主数据重新解释历史交易。
14. 把所有差异都自动修正，没有合法差异、审批和审计。
15. 只记录技术错误，没有结果未知、人工任务和收敛责任人。

## 32. 适用范围与简化边界

### 32.1 适用

- ERP、供应链、制造、零售、平台和企业服务系统。
- 采购、生产、库存、销售、财务和税务一体化。
- 多系统之间的业务边界、数据所有权和对账设计。
- 遗留系统分析、ERP 重构、系统整合和数据治理。
- 退款、退货、红冲、补偿和历史业务解释。

### 32.2 可以简化

- 单体、低风险、业务链很短的内部工具。
- 没有实物、资金、税务和跨系统副作用的简单查询系统。
- 只需分析某个局部状态机而非完整企业链路的任务。

简化不等于混淆。即使不建立独立模块，也应明确关键事实属于哪条流、谁拥有权威解释权。
