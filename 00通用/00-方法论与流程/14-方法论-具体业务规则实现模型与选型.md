## 0. AI 执行入口

### 0.1 本文解决的问题

本文不再回答“业务规则是什么”，而是回答：

1. 一条具体业务规则应使用哪种实现模型。
2. 多种规则模型如何组合，而不是堆进一个规则引擎。
3. 规则、决策、状态、流程和副作用如何分层。
4. 如何让规则结果可解释、可测试、可版本化和可回放。
5. 如何从散落的 `if/else` 安全迁移到结构化模型。

核心结论：

> 不存在适合所有业务规则的单一最佳模型。最佳实现取决于规则约束的对象、变化轴、决策权、时间语义、并发风险和副作用边界。应先识别规则性质，再选择最小充分模型。

### 0.2 最小输入

- 规则原文、业务含义、来源和 Owner。
- 角色、任务、业务对象、当前状态和目标结果。
- 所需事实、事实权威源及数据新鲜度。
- 适用客户、租户、渠道、区域、产品、时间和业务模式。
- 正例、反例、边界、冲突、重复、并发和历史场景。
- 是否涉及资金、库存、权限、合同、合规或外部副作用。
- 当前实现入口、调用方、历史数据和兼容约束。

输入不足时，AI 只能输出候选模型、竞争解释和待确认项，不得自动补全资金、合同、权限、合规和风险接受语义。

### 0.3 核心输出

```text
规则分类与证据
+ 实现模型选择及理由
+ 规则组合与执行顺序
+ 决策结果契约
+ 状态/流程/副作用边界
+ 版本、快照和历史解释
+ 测试性质与最小反例
+ 迁移、灰度和回滚方案
```
## 1. 先建立统一规则执行模型

### 1.1 规则元模型

一条可实施规则至少应表示为：

```text
BusinessRule =
  <RuleId, Meaning, Type, Source, Owner,
   Scope, RequiredFacts, Applicability,
   Condition, Decision, Relations,
   EffectivePeriod, Version,
   Authority, Override, ReasonCode,
   AuditRequirement, LifecycleStatus>
```

字段含义：

| 字段 | 回答的问题 |
|---|---|
| Meaning | 规则真正保护或实现的业务目的是什么 |
| Type | 它是不变量、资格、决策、计算、状态、流程、权限还是其他类型 |
| Source | 来自法规、合同、组织政策、产品决策还是历史兼容 |
| Scope | 对哪些主体、对象、模式、渠道、区域和时间有效 |
| RequiredFacts | 决策需要哪些权威事实 |
| Applicability | 当前规则是否进入候选集合 |
| Condition | 在什么条件下命中 |
| Decision | 命中后形成什么业务结论 |
| Relations | 与其他规则互斥、优先、依赖、组合还是禁止 |
| EffectivePeriod | 何时开始和停止服务新业务 |
| Version | 本次决策使用哪个不可变版本 |
| Authority | 系统、用户、审批人或外部机构谁有最终决定权 |
| Override | 是否允许例外，由谁批准，不能突破什么底线 |
| ReasonCode | 如何稳定解释命中、拒绝和恢复 |
| AuditRequirement | 哪些事实、版本、人员和结果必须留痕 |

### 1.2 标准执行链

```text
采集权威事实 Fact
→ 选择业务模式 BusinessMode
→ 选择有效政策版本 PolicyVersion
→ 判断适用范围 Applicability
→ 检查资格 Eligibility
→ 生成合法候选 Candidates
→ 执行裁决/计算 Decision
→ 校验不变量 Invariant
→ 校验状态转换 Transition
→ 生成执行计划 ExecutionPlan
→ 单一入口执行副作用
→ 保存决策快照、账本和审计证据
```

这是一条参考链，不是所有简单规则都必须建立全部层次。少量稳定条件可以压缩为具名方法；只有真实存在对应复杂度时才引入独立模型。

### 1.3 决策与执行必须分离

推荐：

```text
规则评估：相同事实 + 上下文 + 版本 → 相同决策
执行计划：根据最终决策生成待执行动作
副作用执行：持久化、扣减、支付、发券、消息发送
```

不推荐：

```text
规则命中
→ 在规则对象内部直接修改数据库
→ 调支付接口
→ 发送消息
```

适用条件：规则结果需要重放、解释、比较、模拟或可能触发不可逆动作。  
边界：一个无副作用、低风险、局部校验方法不必机械增加 `ExecutionPlan`。  
反例：优惠规则评估时直接核销优惠券，后续另一条规则判定组合非法，导致无法安全撤销。  
已有机制：应用服务、事务脚本和 Saga 可以执行副作用；规则模型只负责形成明确决策。

## 2. 模型一：Invariant——不可破坏的业务底线

### 2.1 解决的问题

Invariant 用于表达任意合法路径都必须成立的性质：

```text
累计退款 <= 原有效支付
客户应付金额 >= 0
资金分摊合计 = 订单实付
库存已使用 + 已预占 <= 可支配库存
同一业务意图最多产生一个不可逆结果
主体只能访问其授权数据范围
```

### 2.2 推荐实现

```text
InvariantResult
- passed
- invariantId
- reasonCode
- authoritativeFacts
- evaluatedAt
```

伪代码：

```java
InvariantResult checkRefundLimit(RefundContext context) {
  Money total = context.refundedAmount().add(context.requestAmount());
  return total.lessThanOrEqual(context.paidAmount())
      ? InvariantResult.pass("REFUND_LIMIT")
      : InvariantResult.reject("REFUND_EXCEEDS_PAID_AMOUNT");
}
```

高并发写入还需要数据库条件更新、唯一约束、锁、账本或幂等键，不能只在内存中先查再写。

### 2.3 适用条件、边界和验证

- **适用：**资金、库存、状态、权限、唯一性和审计底线。
- **边界：**经营政策可以配置；核心不变量通常不能作为普通客户开关。
- **反例：**“满 500 元需要店长审批”是可变政策，不是核心不变量。
- **验证：**属性测试、并发测试、旁路入口测试、数据库约束测试和对账。

## 3. 模型二：Specification——资格与业务谓词

### 3.1 解决的问题

Specification 判断一个主体或对象是否满足具名业务条件：

```text
有效会员
可退款订单
可参加促销商品
有账期资格的客户
可审批当前门店退款的员工
```

组合形式：

```text
EligibleForMemberPrice =
  ActiveMember
  AND ProductSupportsMemberPrice
  AND StorePolicyEnabled
  AND PolicyWithinEffectivePeriod
```

### 3.2 推荐结果

不要只返回 `boolean`：

```json
{
  "eligible": false,
  "reasonCode": "REFUND_PERIOD_EXPIRED",
  "missingFacts": [],
  "recoverable": false,
  "suggestedCommands": ["CONTACT_SUPPORT"]
}
```

### 3.3 适用条件、边界和验证

- **适用：**资格、过滤、命令前置条件、数据作用域和可组合谓词。
- **边界：**只有一两个稳定条件时，具名方法通常比规格框架更简单。
- **反例：**用数十个匿名微规格任意组合，形成无法解释的布尔网络。
- **验证：**正例、反例、缺失事实、组合短路和拒绝原因测试。

## 4. 模型三：Decision Table / DMN——多条件裁决

### 4.1 解决的问题

适合多个输入条件共同决定一个离散结果，例如审批路由、费率、风险等级、物流方式和价格候选选择。

| 退款金额 | 风险 | 主体类型 | 决策 |
|---|---|---|---|
| ≤ 500 | 低 | 普通员工 | 自动批准 |
| > 500 | 低 | 普通员工 | 店长审批 |
| 任意 | 高 | 任意 | 财务审批 |
| 任意 | 黑名单 | 任意 | 拒绝 |

### 4.2 必须声明命中策略

```text
UNIQUE：只能命中一条
FIRST：按已批准顺序选择第一条
PRIORITY：按业务优先关系裁决
COLLECT：收集全部合法结果
BEST_OF：按明确比较函数择优
```

“表格顺序”不能在未声明时偷偷成为业务优先级。

### 4.3 推荐结果

```json
{
  "decision": "SUBMIT_FOR_APPROVAL",
  "nextActor": "STORE_MANAGER",
  "reasonCode": "REFUND_EXCEEDS_AUTO_APPROVAL_LIMIT",
  "matchedRuleIds": ["REFUND-APPROVAL-003"],
  "policyVersion": "refund-policy-v7"
}
```

### 4.4 适用条件、边界和验证

- **适用：**输入维度有限、条件与结果可以结构化声明的决策。
- **边界：**DMN 负责决策依赖，不负责长事务、等待、状态生命周期和副作用一致性。
- **反例：**把支付回调、超时重试和人工对账全部塞进决策表。
- **验证：**完整性、重叠、不可达行、命中策略、边界值和默认分支检查。
## 5. 模型四：Policy Object——完整、可版本化的经营政策

### 5.1 解决的问题

Policy 表达组织选择如何经营的一组完整语义，而不只是一个判断函数：

```text
RefundPolicy
PricingPolicy
PromotionCombinationPolicy
CreditPolicy
InventoryAllocationPolicy
```

建议包含：

```text
businessMeaning
scope/applicability
eligibility
candidateRules
exclusions
priority/composition
limits
fundingResponsibility
effectivePeriod/version
overridePolicy
auditRequirement
```

### 5.2 推荐接口

```java
interface RefundApprovalPolicy {
  RefundApprovalDecision decide(RefundContext context);
}

record RefundApprovalDecision(
    ApprovalMode mode,
    ApproverRole nextApprover,
    String reasonCode,
    String policyVersion
) {}
```

### 5.3 适用条件、边界和验证

- **适用：**规则按合同、地区、渠道、时间或业务模式变化，且需要历史解释。
- **边界：**只有一个简单公式时不必创建庞大的 Policy 聚合。
- **反例：**把参数、流程状态、外部调用和所有客户差异都塞进一个万能 Policy。
- **验证：**作用域、有效期、版本选择、历史快照和政策切换差分测试。

## 6. 模型五：Strategy——相同业务语义下的算法替换

### 6.1 识别标准

只有同时满足以下条件，两个实现才适合作为 Strategy：

```text
输入语义相同
输出语义相同
维护的不变量相同
责任与状态边界相同
只有算法或技术实现不同
```

例如普通定价、合同定价、会员定价可以分别生成统一的 `PriceCandidate`。

```java
interface PricingStrategy {
  boolean supports(PricingContext context);
  PriceCandidate calculate(PricingContext context);
}
```

### 6.2 Policy 与 Strategy 的区别

```text
Policy：决定哪种经营规则适用、候选如何相处
Strategy：执行某一种具体算法
```

常见组合：

```text
Policy 选择合法 Strategy
→ Strategy 生成候选
→ Decision Table 裁决候选
```

### 6.3 适用条件、边界和验证

- **适用：**运费、税费、评分、定价等算法变化。
- **边界：**对象、责任、状态机或资金含义不同，通常是不同业务模式，不是普通 Strategy。
- **反例：**按客户 ID 选择完全不同的订单生命周期，却命名为“客户策略”。
- **验证：**统一输入输出契约、共同不变量、策略替换和交叉实现测试。

## 7. 模型六：Calculation Pipeline——阶段化计算与决策

### 7.1 解决的问题

适用于存在稳定业务阶段的计算：

```text
基础价
→ 价格候选
→ 商品优惠
→ 订单优惠
→ 平台补贴
→ 税费
→ 舍入
→ 分摊
→ 不变量校验
```

每一步应声明：

```text
输入契约
输出契约
适用条件
金额或状态变化
原因码
失败语义
维护的不变量
```

### 7.2 推荐接口

```java
interface PricingStep {
  PricingResult apply(PricingContext context, PricingResult current);
}
```

每一步产生可解释痕迹：

```json
{
  "step": "PLATFORM_SUBSIDY",
  "before": 80.00,
  "after": 75.00,
  "matchedRuleId": "SUBSIDY-007",
  "reasonCode": "PLATFORM_QUOTA_AVAILABLE"
}
```

### 7.3 适用条件、边界和验证

- **适用：**计算顺序具有稳定业务含义，且需要中间值、解释或差分。
- **边界：**处理器注册顺序不能未经声明就成为政策；动态插拔会扩大未设计组合空间。
- **反例：**任意调整 Pipeline 顺序导致税费和优惠结果变化，却没有版本和审批。
- **验证：**阶段契约、顺序、舍入、分摊、组合和蜕变性质测试。

## 8. 模型七：State Machine——生命周期与合法命令

### 8.1 解决的问题

状态机用于回答：

```text
对象现在处于什么业务状态
当前角色可以发出什么命令
命令需要满足哪些 Guard
执行后进入什么目标状态
失败、撤销和逆向如何表达
```

示例：

```text
DRAFT
→ PENDING_APPROVAL
→ APPROVED
→ PROCESSING
→ SUCCEEDED

PENDING_APPROVAL → REJECTED
PROCESSING → RESULT_UNKNOWN → SUCCEEDED / FAILED / MANUAL_REVIEW
```

一个转换至少包含：

```text
FromState + Command + Actor + Guard
→ ToState + DomainEvents + Audit
```

### 8.2 推荐命令模型

不推荐：

```java
refund.setStatus(request.getStatus());
```

推荐：

```java
refund.approve(approver, approvalReason);
refund.reject(approver, rejectionReason);
refund.markGatewayResultUnknown(requestId);
```

### 8.3 适用条件、边界和验证

- **适用：**对象生命周期有限、转换有业务意义、非法跃迁会造成风险。
- **边界：**状态机不替代金额计算、流程编排或外部副作用协调。
- **反例：**把所有页面展示标签都建成领域状态，造成状态爆炸。
- **验证：**合法/非法转换、并发版本、终止状态、撤销、重复命令和状态性质测试。

## 9. 模型八：Workflow / BPMN——多角色协作与等待

### 9.1 解决的问题

适用于：

```text
多级审批
跨角色任务
等待外部回调
超时升级
驳回与重新提交
人工补偿
```

工作流应表达：

```text
任务 + 责任人 + 输入 + 截止时间
+ 路由条件 + 等待事件 + 超时
+ 升级 + 补偿 + 版本
```

### 9.2 与状态机的分工

| 模型 | 负责什么 |
|---|---|
| State Machine | 单个业务对象是否合法转换 |
| Workflow | 多参与者、任务和等待如何协调 |

推荐组合：

```text
Workflow 分派和推进审批任务
→ Domain State Machine 验证并改变退款状态
```

### 9.3 适用条件、边界和验证

- **适用：**角色、步骤、等待或路由确实复杂且可能变化。
- **边界：**短小、同步、固定流程通常由应用服务编排更简单。
- **反例：**为两个固定步骤引入完整工作流平台，却没有版本迁移和运维能力。
- **验证：**正常、驳回、撤回、超时、升级、重复事件、流程版本和人工恢复测试。
## 10. 模型九：Agreement–Policy–Entitlement——合同、套餐与权益

### 10.1 三层分离

```text
Agreement：主体与组织约定了什么
Policy：在什么条件下如何解释约定
Entitlement：主体当前实际拥有并可使用什么权益
```

例如：

```text
Agreement：客户在合同期内享受协议价格
Policy：合同、商品、门店和时间同时有效时才适用
Entitlement：客户当前可对 SKU-001 使用合同价 80 元
```

权益结果建议包含来源、作用域、有效期和版本，而不是只存 `isVip=true`。

### 10.2 适用条件、边界和验证

- **适用：**会员、合同客户、套餐、优惠券、服务等级和渠道合作。
- **边界：**拥有权益不等于当前有资格，也不等于权益已被消费。
- **反例：**客户 ID 直接触发特殊价格，无法解释合同来源和有效期。
- **验证：**协议版本、资格、范围、消费、恢复、到期和历史订单测试。

## 11. 模型十：Limit–Quota–Reservation——额度和竞争资源

### 11.1 模型分工

```text
Limit：总体业务上限
Quota：向主体或范围分配的额度
Reservation：正式使用前的预占
Usage：已确认使用
Release：释放预占
Adjustment：经授权调整
```

典型关系：

```text
已使用 + 已预占 <= 可支配额度
```

适用于库存、预算、次数、信用、优惠补贴、席位和产能。

### 11.2 Reservation 生命周期

```text
AVAILABLE → RESERVED → CONFIRMED
                     ↘ RELEASED / EXPIRED
```

预占必须具有业务键、过期时间、确认与释放的幂等语义。

### 11.3 适用条件、边界和验证

- **适用：**存在并发竞争、先占后用或失败后释放。
- **边界：**无并发、无预占的静态上限可以简化为普通校验。
- **反例：**两个终端同时读取“库存 1”，各自在前端减一后提交。
- **验证：**并发预占、重复确认、过期释放、补偿失败和额度守恒测试。

## 12. 模型十一：Account–Ledger–Transaction——可追溯价值变化

### 12.1 核心模型

```text
Account：业务账户
Transaction：业务交易
Entry：不可覆盖的增减分录
Ledger：账簿
Balance：由分录派生或校验的余额
Reversal：冲正或逆向交易
```

适用于资金、储值、积分、信用、库存账和预算使用。

关键原则：

```text
不静默覆盖历史分录
调整通过新分录完成
余额必须能够由权威流水解释
正向与逆向交易建立明确关联
```

### 12.2 适用条件、边界和验证

- **适用：**需要审计、对账、退款、冲正和历史追溯的价值变化。
- **边界：**简单、低风险、无历史需求的数据不必全部账本化。
- **反例：**直接修改储值余额，无法解释变化来源和责任人。
- **验证：**借贷/增减守恒、重复交易、冲正、跨日对账和余额重建测试。

## 13. 模型十二：Effective Dating + Versioned Policy + Snapshot

### 13.1 解决的问题

时间规则至少区分：

```text
业务发生时间
规则生效时间
系统处理时间
数据记录时间
当前查看时间
```

规则版本至少包含：

```text
version
validFrom / validTo
publishedAt
lifecycleStatus
scope
approvedBy
```

业务决策形成时保存快照：

```json
{
  "policyVersion": "refund-policy-v7",
  "facts": {"refundAmount": 680},
  "matchedRuleIds": ["REFUND-APPROVAL-003"],
  "decision": "STORE_MANAGER_APPROVAL",
  "decidedAt": "2026-07-31T10:00:00+08:00"
}
```

### 13.2 适用条件、边界和验证

- **适用：**价格、合同、权益、审批和流程规则会变化，历史业务仍需解释。
- **边界：**瞬时、无历史影响的临时筛选不必建立完整版本治理。
- **反例：**政策升级后使用当前规则重算并解释历史订单。
- **验证：**有效期首尾、时区、版本切换、历史回放和原快照不变性测试。

## 14. 模型十三：RBAC + ABAC + SoD——权限、范围与职责分离

### 14.1 分层授权

```text
RBAC：主体角色允许哪些能力
ABAC：主体、对象、租户、门店、金额、状态和环境是否匹配
SoD：不相容职责不能由同一主体承担
```

完整授权通常是：

```text
角色能力
∩ 数据作用域
∩ 对象状态
∩ 业务资格
∩ 职责分离
∩ 风险政策
```

例如：

```text
门店经理可以审批退款
AND 退款属于其管理门店
AND 退款处于待审批状态
AND 审批人不是申请人
```

### 14.2 适用条件、边界和验证

- **适用：**权限随对象、范围、状态或责任关系变化。
- **边界：**前端隐藏、禁用和只读只是投影，不是权威授权。
- **反例：**按钮被隐藏，但调用 API 仍能审批其他门店退款。
- **验证：**角色矩阵、跨租户/跨门店、直接 API、自审和权限变化测试。

## 15. 模型十四：Explicit Override——受控业务例外

### 15.1 例外不是管理员万能通道

```text
OverrideRequest
- overrideType
- targetRule
- scope
- requestedBy
- reason/evidence
- authorizedBy
- validPeriod
- impactPreview
- result
- review/revoke
```

必须区分：

```text
可覆盖的普通政策
不可覆盖的资金、权限、安全、合规和核心不变量
```

### 15.2 适用条件、边界和验证

- **适用：**组织明确允许经授权突破普通政策。
- **边界：**不是所有拒绝都应提供例外；例外能力本身需要额度和审计。
- **反例：**管理员直接改数据库状态或跳过审批。
- **验证：**授权主体、范围、时效、理由、二次审批、撤销和审计测试。

## 16. 模型十五：Saga / Process Manager——异步副作用与结果收敛

### 16.1 状态模型

```text
未提交
→ 已接受
→ 处理中
→ 等待外部结果
→ 成功 / 明确失败 / 结果未知
→ 查询、对账、补偿或人工处理
```

必须明确：

```text
请求已接受 ≠ 业务已完成
外部超时 ≠ 业务失败
数据库回滚 ≠ 外部副作用已撤销
补偿动作是新的业务动作
```

关键机制：幂等键、Outbox、回调去重、状态查询、补偿计划、对账和人工升级。

### 16.2 适用条件、边界和验证

- **适用：**支付、退款、发券、履约及跨服务最终一致业务。
- **边界：**单数据库内的简单原子修改不需要 Saga。
- **反例：**支付超时后标记失败并允许再次支付，首笔实际上可能已经成功。
- **验证：**重复请求、乱序回调、超时、未知、部分成功、补偿失败和人工收敛测试。

## 17. Rule Engine / BRMS 的正确边界

规则引擎适合：

- 规则数量多且更新频繁。
- 条件、结果和关系可以结构化表达。
- 需要集中模拟、审批、发布、灰度和回滚。
- 业务人员确实参与维护。
- 已有稳定词汇、Owner、版本和测试治理。

不适合：

- 只有少量稳定条件。
- 业务语义尚未澄清。
- 只是为了消除几个 `if/else`。
- 规则需要直接执行长流程或不可逆副作用。
- 没有冲突检测、发布审批和历史版本能力。

规则引擎不是第十六种业务语义模型，而是承载部分 Specification、Decision Table、Policy 和 Formula 的运行平台。它不能替代状态机、工作流、账本、资源预占和 Saga。
## 18. 模型选择决策表

| 业务问题 | 首选模型 | 选择信号 | 不适用信号 |
|---|---|---|---|
| 任意路径都不能违反 | Invariant | 资金、库存、状态、权限底线 | 可按经营策略变化 |
| 是否满足条件 | Specification | 资格可具名、可组合 | 需要从多个结果中裁决 |
| 多条件决定离散结果 | Decision Table / DMN | 条件与结果可枚举 | 实际是长流程或事务 |
| 一组规则形成政策 | Policy Object | 有范围、版本和 Owner | 只有一个简单条件 |
| 相同语义不同算法 | Strategy | 输入输出和不变量相同 | 对象、状态或责任不同 |
| 计算存在稳定阶段 | Pipeline | 顺序和中间值有业务意义 | 顺序只是技术偶然 |
| 对象生命周期 | State Machine | 合法命令和转换重要 | 只是展示标签 |
| 多角色、等待、审批 | Workflow / BPMN | 协作、超时和人工任务 | 短小固定同步流程 |
| 合同、套餐、会员权益 | Agreement–Policy–Entitlement | 拥有、资格、享用需分离 | 简单永久权限 |
| 库存、预算、额度 | Quota / Reservation | 预占和并发竞争 | 静态无竞争上限 |
| 资金、储值、积分 | Ledger | 审计、冲正、对账 | 低风险无历史要求 |
| 历史规则解释 | Versioned Policy / Snapshot | 规则会变化、历史需重放 | 纯瞬时判断 |
| 对象和数据范围授权 | RBAC + ABAC | 权限依赖主体与对象 | 单一静态角色足够 |
| 不相容职责 | SoD | 申请、审批、执行需分离 | 不存在责任冲突 |
| 授权突破普通政策 | Explicit Override | 有合法例外和批准人 | 核心底线不可覆盖 |
| 异步、跨系统、补偿 | Saga / Process Manager | 外部结果和最终一致 | 单事务原子更新 |

## 19. 模型组合蓝图

### 19.1 退款规则

```text
Specification
  判断订单、支付和时间是否允许退款

Invariant
  累计退款不得超过有效支付

Decision Table
  按金额、风险和主体决定自动退款或审批层级

RBAC + ABAC + SoD
  判断谁能审批、作用范围及禁止自审

State Machine
  控制申请、审批、处理中、成功、失败和未知

Workflow
  协调店长、区域经理、财务和补充材料

Saga
  协调支付机构请求、查询、对账和补偿

Ledger
  记录退款、冲正和资金分录

Versioned Policy + Snapshot
  保存申请时政策版本和决策依据
```

这里不存在一个应包办全部职责的 `RefundRuleEngine`。每个模型只承担其擅长的语义。

### 19.2 价格与优惠

```text
Agreement / Entitlement
  确定合同、会员和优惠权益

Specification
  判断每个候选是否适用

Strategy
  生成零售价、会员价、合同价和渠道价候选

Decision Table / Policy
  裁决优先、择优、互斥和组合

Calculation Pipeline
  依次完成价格、优惠、税费、舍入和分摊

Quota / Reservation
  保护补贴预算和优惠额度

Invariant / Ledger
  保证应付非负和资金分摊守恒

Versioned Policy + Snapshot
  冻结订单采用和排除的规则
```

### 19.3 会员权益

```text
Agreement / Entitlement：拥有什么权益
Specification：当前场景能否使用
Quota：剩余次数或额度
Reservation：提交期间预占
State Machine：未激活、可用、冻结、耗尽、过期
Ledger：权益发放、使用、返还和调整
Versioned Policy：按原规则处理退款与返还
```

### 19.4 跨系统履约

```text
Policy：选择履约模式
State Machine：维护订单合法状态
Workflow：组织仓库、配送和客服任务
Saga：协调库存、支付、配送和补偿
Outbox/Inbox：可靠发布与幂等消费
Snapshot/Audit：记录每次决策和外部结果
```

## 20. 推荐运行架构

```text
Controller / Consumer / Scheduler
              ↓
Application Service
  身份、幂等、事务和用例编排
              ↓
Fact Provider
  采集权威事实并标记时间与来源
              ↓
Business Mode + Policy Version Selector
              ↓
Specification / Decision Table / Strategy / Pipeline
  形成候选和业务决策
              ↓
Invariant Guard + State Machine + Authorization
  执行底线、状态和权限校验
              ↓
DecisionResult + ExecutionPlan
              ↓
Repository / Adapter / Saga / Outbox
  统一执行持久化和外部副作用
              ↓
Snapshot / Ledger / Audit / Metrics
```

### 20.1 各层责任

| 层 | 主要责任 | 不应承担 |
|---|---|---|
| 接口层 | 协议转换、基础格式、身份入口 | 核心规则裁决 |
| 应用层 | 用例、幂等、事务、编排 | 隐式复制领域规则 |
| 事实层 | 读取权威事实、来源和新鲜度 | 替业务负责人决定语义 |
| 规则/政策层 | 纯化评估、候选、决策和解释 | 直接执行不可逆副作用 |
| 领域层 | 不变量、状态、具名命令 | 编排所有外部系统 |
| 执行层 | 持久化、消息、外部适配、补偿 | 重新决定业务政策 |
| 证据层 | 快照、账本、审计、监控 | 用日志代替业务事实 |

## 21. 决策结果契约

不要只返回 `true/false`。推荐：

```text
DecisionResult
- decisionId
- status
- selectedOutcome
- allowedCommands
- reasonCode/reasonParams
- matchedRules
- rejectedCandidatesAndReasons
- intermediateValues
- policyVersion
- effectiveAt/evaluatedAt
- confidence/ambiguities
- invariantResults
- executionPlan
- reversePlan
- auditRequirements
```

示例：

```json
{
  "status": "APPROVAL_REQUIRED",
  "selectedOutcome": "SUBMIT_FOR_APPROVAL",
  "allowedCommands": ["SUBMIT_FOR_APPROVAL"],
  "reasonCode": "REFUND_EXCEEDS_AUTO_APPROVAL_LIMIT",
  "reasonParams": {"threshold": 500, "currency": "CNY"},
  "nextActor": "STORE_MANAGER",
  "policyVersion": "refund-policy-v7",
  "matchedRules": ["REFUND-APPROVAL-003"],
  "rejectedCandidatesAndReasons": [],
  "ambiguities": [],
  "evaluatedAt": "2026-07-31T10:00:00+08:00"
}
```

原因码是前后端和历史解释的稳定契约；展示文本由交互层本地化，不能让前端根据结果值猜测原因。
## 22. 从散落条件安全迁移

### 22.1 不要直接重写

既有系统中的重复和不合理分支可能已成为兼容契约。推荐顺序：

```text
盘点入口、调用方、历史数据、配置、任务和消息
→ 建立旧行为特征样例
→ 提取规则清单和差异
→ 区分事实、不变量、政策、参数和技术补丁
→ 选择最小模型
→ 新模型无副作用计算
→ Shadow 比较旧新决策
→ 分类差异并取得业务裁决
→ 灰度切换
→ 保留可执行回滚
→ 满足删除条件后再退役旧路径
```

有副作用的支付、扣库存、发券和消息发送不能双跑。Shadow Mode 只能比较纯决策结果，正式副作用继续由旧路径唯一产生。

### 22.2 差异分类

```text
新模型缺陷
旧实现缺陷修正
明确政策变化
历史兼容差异
数据质量问题
配置差异
证据不足
```

旧结果不是天然正确答案，新模型也不能因“结构更好”自动成为正确答案。

## 23. 验证体系

### 23.1 示例与边界测试

- 正常命中与不命中。
- 阈值小于、等于和大于。
- 零、负数、最大值、空值、精度和舍入。
- 生效期开始、结束、跨日和时区。
- 权限、租户、门店和对象范围。

### 23.2 决策表测试

- 条件组合完整。
- 没有意外多命中。
- 不存在不可达规则。
- 命中策略与业务定义一致。
- 默认分支有明确语义。

### 23.3 组合与冲突测试

- 互斥规则不能同时生效。
- 依赖缺失不能发布。
- 优先关系不能成环。
- 有序组合保持规定顺序。
- 未定义组合不得按加载顺序静默执行。

### 23.4 性质测试

```text
任意合法退款序列：累计退款 <= 原有效支付。
任意合法优惠组合：客户应付 >= 0。
任意重复业务意图：不可逆副作用最多发生一次。
任意合法状态序列：不会越过禁止状态。
任意跨租户输入：不产生其他租户的数据结果。
相同事实、上下文和版本：得到一致决策与解释。
```

### 23.5 蜕变测试

- 增加无关规则不应改变当前决策。
- 声称可交换的步骤改变顺序后结果不变。
- 在没有其他约束时，提高优惠额度不应增加客户应付。
- 增加限制条件不应扩大资格集合。
- 政策版本变化不应改变已冻结历史对象的解释。

### 23.6 故障与恢复测试

- 重复请求和重复回调。
- 外部超时和结果未知。
- 部分成功和补偿失败。
- 并发状态变化。
- 规则服务不可用。
- 人工升级、撤回和恢复。

## 24. 常见反模式

1. 所有业务规则都实现成一个巨大 `if/else`。
2. 所有变化都套 Strategy，却没有资格、冲突和状态模型。
3. 把所有规则都放进通用规则引擎。
4. 规则评估时直接扣款、发券、扣库存或发消息。
5. 使用客户 ID、门店 ID 或租户 ID 代表隐式业务模式。
6. 用数字优先级、表格顺序或最后写入掩盖语义冲突。
7. 只返回 `true/false`，没有原因码、版本和恢复动作。
8. 用当前规则重新解释历史订单、审批和退款。
9. 用前端隐藏或禁用按钮代替服务端授权和守卫。
10. 用“管理员”提供不受控万能绕过。
11. 状态机直接接收任意目标状态，而不是具名命令。
12. Workflow 同时承载规则、领域状态和全部外部副作用。
13. 余额字段可直接修改，缺少交易、分录、冲正和对账。
14. 预占失败、过期或补偿后没有明确资源释放语义。
15. 为少量稳定规则建设复杂平台，却没有 Owner 和发布治理。

## 25. AI 模型选型算法

```text
INPUT：规则原文、事实、作用域、状态、流程、历史实现和证据

1. 规范化规则业务含义；区分事实、参数、政策和技术机制。
2. 判断是否为任意路径都必须成立的底线；是则优先 Invariant。
3. 判断是否只回答“是否满足条件”；是则选择具名方法或 Specification。
4. 判断是否由有限条件组合决定离散结果；是则选择 Decision Table/DMN。
5. 判断是否为完整、可变、可版本化经营政策；是则使用 Policy Object。
6. 判断多个实现是否具有相同输入、输出、不变量和责任边界；是才使用 Strategy。
7. 判断计算是否存在稳定阶段和有意义中间值；是则使用 Pipeline。
8. 判断业务对象是否存在合法命令和生命周期；是则建立 State Machine。
9. 判断是否存在多角色、等待、超时和人工任务；是则补充 Workflow。
10. 判断是否存在合同、套餐或权益；使用 Agreement–Policy–Entitlement。
11. 判断是否存在竞争资源、预占和释放；使用 Quota/Reservation。
12. 判断是否需要审计、冲正和对账；使用 Ledger。
13. 判断规则是否随时间变化且历史需解释；使用 Versioned Policy/Snapshot。
14. 判断权限是否依赖对象、范围和职责；使用 RBAC/ABAC/SoD。
15. 判断是否允许合法例外；使用 Explicit Override，并列出不可覆盖底线。
16. 判断是否存在跨系统异步副作用；使用 Saga/Process Manager。
17. 建立模型之间的输入、输出和权威边界，避免职责重叠。
18. 生成 DecisionResult、ExecutionPlan、测试性质、迁移和回滚方案。
19. 对高影响规则执行 SOP-09；证据不足时结论为 EVIDENCE_INSUFFICIENT。
```

AI 每次推荐模型必须同时说明：

```text
为什么适用
为什么不用更简单模型
模型新增成本
不适用边界和反例
权威数据与决策人
验证方式
迁移和退出条件
```
