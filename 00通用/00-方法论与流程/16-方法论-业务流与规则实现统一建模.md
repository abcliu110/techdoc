**整合的价值**：
```

    ↓ 每条规则选择什么实现模型
规则实现（微观）
    ↓ 组合运行形成完整业务能力
```

### 0.2 核心结论

> 业务流是规则的容器，规则是业务流的内核。流确定边界，规则确定行为。不懂流，规则会相互侵入；不懂规则，流只是空壳。

## 1. 业务流框架回顾

### 1.1 四层业务流体系

```text
L1 企业核心流
├── 商流：交易关系、价格条件、权利义务
├── 物流/履约流：实物或服务交付
├── 资金流：货币、债权、债务变化
└── 信息流：数据、单据、事件传播

L2 ERP专业流
├── 计划流：需求转执行建议
├── 生产流：工序、物料、在制品
├── 质量流：检验、返工、CAPA
├── 成本流：价值归集和转移
├── 会计流：分录、凭证、报表
├── 票税流：发票、申报、红冲
├── 任务流：审批、人工任务
├── 资产流：采购到报废
└── 人力流：招聘到离职

L3 端到端流程
├── O2C：订单到收款
├── P2P：采购到付款
├── Plan-to-Produce：计划到生产
└── R2R：记录到报告

L4 技术运行流
├── 数据流、事件流、状态流
├── 配置版本流、审计证据流
└── 控制流
```

### 1.2 业务流判定标准

一个概念要作为独立业务流，需同时具备：

```text
流动对象 ✓
起点和终点 ✓
参与主体 ✓
状态变化 ✓
数量/金额/责任变化 ✓
权威记录 ✓
正向和逆向路径 ✓
可验证的业务结果 ✓
```

### 1.3 业务流与端到端流程的区别

| 维度 | 业务流 | 端到端流程 |
|---|---|---|
| 视角 | 单一价值转移 | 客户/企业结果 |
| 边界 | 同一类对象的变化 | 横跨多条业务流 |
| 典型 | 物流、资金流 | O2C、P2P |
| 分析时机 | 先识别流 | 后确定端到端 |

## 2. 规则实现模型回顾

### 2.1 15种模型分类

| 类别 | 模型 | 回答的问题 |
|---|---|---|
| 底线 | Invariant | 任意路径都不能违反什么 |
| 资格 | Specification | 主体是否满足条件 |
| 裁决 | Decision Table/DMN | 多条件如何决定结果 |
| 政策 | Policy Object | 一组规则如何组合 |
| 算法 | Strategy | 相同语义下算法替换 |
| 计算 | Calculation Pipeline | 分阶段计算如何执行 |
| 生命周期 | State Machine | 对象如何合法变化 |
| 协作 | Workflow/BPMN | 多角色任务如何协调 |
| 权益 | Agreement-Policy-Entitlement | 拥有、资格、享用分离 |
| 额度 | Quota/Reservation | 资源如何预占和释放 |
| 价值 | Ledger | 变化如何不可覆盖记录 |
| 时间 | Effective Dating/Snapshot | 历史如何解释 |
| 权限 | RBAC+ABAC+SoD | 谁能做什么 |
| 例外 | Explicit Override | 何时可突破政策 |
| 异步 | Saga/Process Manager | 外部结果如何收敛 |

### 2.2 模型选择决策表（精简）

| 业务问题 | 首选模型 | 典型场景 |
|---|---|---|
| 资金/库存底线 | Invariant | 退款不超过支付、库存不超可支配 |
| 资格判断 | Specification | 有效会员、可退款订单 |
| 多条件裁决 | Decision Table | 审批路由、费率、风险等级 |
| 规则组合政策 | Policy | 退款政策、促销政策、信用政策 |
| 算法变体 | Strategy | 普通定价、会员定价、合同定价 |
| 分阶段计算 | Pipeline | 价格→优惠→税费→分摊 |
| 对象生命周期 | State Machine | 订单、支付、审批状态 |
| 多角色协作 | Workflow | 多级审批、跨部门任务 |
| 合同权益 | A-P-E | 会员权益、合同价格 |
| 资源预占 | Quota/Reservation | 库存预占、优惠额度 |
| 价值追溯 | Ledger | 资金账、积分账 |
| 历史规则解释 | Snapshot | 订单绑定当时政策版本 |
| 权限控制 | RBAC+ABAC | 门店范围、金额范围 |
| 合法例外 | Override | 特殊审批、促销豁免 |
| 跨系统异步 | Saga | 支付、退款、外部履约 |

### 2.3 规则执行标准链

```text
采集权威事实 Fact
→ 选择业务模式 BusinessMode
→ 选择有效政策版本 PolicyVersion
→ 判断适用范围 Applicability
→ 检查资格 Eligibility
→ 生成合法候选 Candidates
→ 执行裁决/计算 Decision
→ 校验不变量 Invariant
→ 校验状态转换 Transition
→ 生成执行计划 ExecutionPlan
→ 单一入口执行副作用
→ 保存决策快照、账本和审计证据
```

## 3. 流-规则映射框架

### 3.1 为什么需要映射

业务流回答"有哪些独立的业务能力在运行"，规则模型回答"每种能力内部如何实现"。没有映射会导致：

- 流边界内的规则相互侵入
- 跨流规则重复或冲突
- 对账规则找不到对应的实现模型
- 状态机不知道属于哪条业务流

### 3.2 映射矩阵

```
           Invariant | Spec | Decision | Policy | State | Ledger | Saga | ...
商流       ✓         ✓     ✓         ✓       ✓      ✗      ✗
物流       ✓         ✓     ✓         ✓       ✓      ✓      ✓
资金流     ✓         ✓     ✓         ✓       ✓      ✓      ✓
计划流     ✓         ✓     ✓         ✓       ✓      ✗      ✗
生产流     ✓         ✓     ✓         ✓       ✓      ✓      ✓
...
```

### 3.3 映射原则

**原则1：每条流至少有一个核心 Invariant**

```text
商流不变量：订单应付 = 商品总价 - 优惠 + 税费
物流不变量：出库数量 ≤ 预占数量 ≤ 可用库存
资金流不变量：累计退款 ≤ 原有效支付
信息流不变量：状态变更必须可追溯
```

**原则2：每条流至少有一个权威 State Machine**

```text
商流状态：订单状态（DRAFT→CONFIRMED→COMPLETED/CANCELLED）
物流状态：履约状态（ALLOCATED→PICKING→SHIPPED→SIGNED）
资金流状态：支付状态（AUTHORIZED→CAPTURED→REFUNDED）
```

> 说明：以上仅为"每流至少一个状态机"的简化示意，状态命名以文档19 §5.1/§5.2 的权威状态机为准（商流订单对应 DRAFT→PENDING→PAID→PROCESSING→DELIVERED→COMPLETED，逆向走 REFUNDING/RETURNING）。

**原则3：跨流操作需要 Saga 或补偿机制**

```text
订单取消 → 库存释放 + 退款 + 发票红冲 + 账务调整
                         ↓
              任何一步失败都需要补偿其他步骤
```

**原则4：跨流对账需要 Ledger 支持**

```text
订单金额 ↔ 支付金额 ↔ 应收金额 ↔ 发票金额 ↔ 会计凭证金额
     ↓           ↓           ↓           ↓           ↓
   商流Ledger   资金流Ledger 资金流Ledger  票税Ledger  会计Ledger
```

## 4. 业务流内的规则建模步骤

### 4.1 步骤概览

```
Step 1：识别业务流范围和边界
Step 2：确定流动对象、状态和权威系统
Step 3：识别流内业务能力和规则
Step 4：为每条规则选择实现模型
Step 5：建立流内不变量和约束
Step 6：设计流内正逆向路径
Step 7：建立流内规则组合和执行顺序
Step 8：与相邻流建立跨流关联
Step 9：识别跨流不变量和对账规则
Step 10：设计异常收敛和补偿机制
```

### 4.2 Step 3 详细：识别流内业务能力

以商流为例：

```text
商流业务能力
├── 报价管理
│   ├── 报价资格判断（Specification）
│   ├── 报价规则计算（Pipeline/Calculation）
│   ├── 价格策略应用（Policy + Strategy）
│   └── 报价有效期管理（Effective Dating）
├── 合同管理
│   ├── 合同条款规则（Policy）
│   ├── 合同状态机（State Machine）
│   └── 合同不变量（Invariant）
├── 订单管理
│   ├── 订单资格判断（Specification）
│   ├── 订单金额计算（Pipeline）
│   ├── 订单审批规则（Decision Table）
│   ├── 订单状态机（State Machine）
│   ├── 订单不变量（Invariant）
│   └── 订单变更规则（Policy）
├── 促销管理
│   ├── 促销资格判断（Specification）
│   ├── 促销互斥规则（Policy）
│   ├── 优惠计算（Pipeline）
│   ├── 促销额度控制（Quota/Reservation）
│   └── 促销状态机（State Machine）
└── 权益管理
    ├── 权益发放（Agreement-Policy-Entitlement）
    ├── 权益使用资格（Specification）
    ├── 权益额度（Quota/Reservation）
    └── 权益账本（Ledger）
```

### 4.3 Step 4 详细：流内规则模型选择

**商流规则模型选择树**：

```text
规则性质识别
    │
    ├─ 是否是不可破坏的底线？
    │   └─ 是 → Invariant
    │       例：订单应付 = 明细合计 + 税费 - 优惠
    │
    ├─ 是否是资格/条件判断？
    │   └─ 是 → Specification
    │       例：是否允许对当前客户报价
    │
    ├─ 是否是多条件裁决？
    │   └─ 是 → Decision Table/DMN
    │       例：大额订单需要几级审批
    │
    ├─ 是否是一组规则的组合政策？
    │   └─ 是 → Policy Object
    │       例：促销组合规则、订单变更政策
    │
    ├─ 是否需要分阶段计算？
    │   └─ 是 → Calculation Pipeline
    │       例：订单金额 = 商品合计 → 优惠 → 税费 → 分摊
    │
    ├─ 是否有生命周期和合法命令？
    │   └─ 是 → State Machine
    │       例：报价 → 确认 → 完成/过期/拒绝
    │
    ├─ 是否涉及额度/预占/释放？
    │   └─ 是 → Quota/Reservation
    │       例：促销名额、权益次数
    │
    ├─ 是否需要价值追溯？
    │   └─ 是 → Ledger
    │       例：优惠核销记录、权益使用记录
    │
    └─ 是否有历史解释需求？
        └─ 是 → Versioned Policy + Snapshot
            例：订单采用当时的促销规则
```

## 5. 跨流规则协作模式

### 5.1 跨流触发模式

```text
流A规则执行
    ↓
流A状态变化
    ↓
触发流B规则
    ↓
流B状态变化
    ↓
...级联触发
```

**典型案例：订单支付成功**

```text
商流：订单状态 CONFIRMED
    ↓ 触发
资金流：支付状态 CAPTURED
    ↓ 触发
物流流：库存预占确认 → 出库
    ↓ 触发
信息流：发送通知、生成单据
    ↓ 触发
会计流：生成应收凭证
```

### 5.2 跨流状态依赖模式

```text
操作X允许条件
= 流A处于状态S1
AND 流B处于状态S2
AND 流C处于状态S3
```

**典型案例：订单发货**

```text
发货允许条件
= 商流订单状态 = CONFIRMED
AND 物流库存状态 = ALLOCATED
AND 资金流支付状态 = CAPTURED
AND 会计流应收状态 = CONFIRMED
```

### 5.3 跨流不变量校验模式

```text
跨流不变量：商流金额 = 物流数量 × 单价 = 资金流应收

校验时机：
- 订单创建时
- 支付成功时
- 发货确认时
- 对账周期
```

### 5.4 跨流Saga编排模式

```text
跨流业务操作
    │
    ├─ Step 1：流A执行并记录
    ├─ Step 2：流B执行并记录
    ├─ Step 3：流C执行并记录
    │
    ├─ 全部成功 → 提交
    │
    └─ 任意失败
        ├─ 补偿流C
        ├─ 补偿流B
        └─ 补偿流A
```

**典型案例：退款**

```text
RefundSaga
    ├─ Step 1：商流退款单创建
    ├─ Step 2：资金流退款执行
    ├─ Step 3：物流退货入库（可选）
    ├─ Step 4：票税流发票红冲
    ├─ Step 5：会计流应收调整
    │
    ├─ 全部成功 → 完成
    │
    └─ 任意失败 → 补偿已执行步骤
```

## 6. 流内规则组合与执行

### 6.1 商流规则组合示例

以订单金额计算为例：

```text
OrderPricingPipeline
    │
    ├─ Step 1：基础价格（Strategy）
    │   ├─ RetailPriceStrategy
    │   ├─ MemberPriceStrategy
    │   └─ ContractPriceStrategy
    │
    ├─ Step 2：商品级优惠（Pipeline + Quota）
    │   ├─ 商品满减（Specification + Calculation）
    │   ├─ 商品折扣（Specification + Calculation）
    │   └─ 促销名额预占（Reservation）
    │
    ├─ Step 3：订单级优惠（Pipeline + Quota）
    │   ├─ 订单满减（Specification + Calculation）
    │   ├─ 优惠券（Specification + Ledger）
    │   └─ 优惠券额度预占（Reservation）
    │
    ├─ Step 4：平台补贴（Policy + Quota）
    │   └─ 补贴预算控制（Quota）
    │
    ├─ Step 5：税费计算（Calculation）
    │   └─ 按税率规则计算
    │
    ├─ Step 6：金额分摊（Calculation）
    │   └─ 优惠分摊到明细
    │
    └─ Step 7：不变量校验（Invariant）
        ├─ 订单应付 >= 0
        └─ 分摊合计 = 优惠总额
```

### 6.2 物流规则组合示例

以库存预占为例：

```text
InventoryReservationFlow
    │
    ├─ Step 1：资格判断（Specification）
    │   ├─ 商品是否在售
    │   ├─ 仓库是否支持配送
    │   └─ 数量是否满足
    │
    ├─ Step 2：可用库存查询（Specification）
    │   └─ 可用 = 库存 - 冻结 - 已预占
    │
    ├─ Step 3：库存预占（Reservation）
    │   ├─ 预占状态：AVAILABLE → RESERVED
    │   ├─ 预占键：orderId + skuId
    │   └─ 过期时间：15分钟
    │
    ├─ Step 4：库存不变量校验（Invariant）
    │   ├─ 已使用 + 已预占 <= 可支配库存
    │   └─ 批次追溯不被破坏
    │
    └─ Step 5：出库确认（State Machine Transition）
        └─ 预占状态：RESERVED → COMMITTED
```

### 6.3 资金流规则组合示例

以支付执行为例：

```text
PaymentExecutionFlow
    │
    ├─ Step 1：支付资格判断（Specification）
    │   ├─ 订单状态允许支付
    │   ├─ 支付金额 > 0
    │   └─ 支付方式可用
    │
    ├─ Step 2：支付限额检查（Invariant + Quota）
    │   ├─ 单笔限额
    │   └─ 渠道日限额
    │
    ├─ Step 3：支付授权（State Machine）
    │   └─ 状态：AWAITING_PAYMENT → AUTHORIZED
    │
    ├─ Step 4：调用支付渠道（Saga）
    │   ├─ 发起支付
    │   ├─ 等待回调
    │   └─ 处理结果：成功/失败/未知
    │
    ├─ Step 5：支付结果处理（State Machine）
    │   ├─ 成功：→ CAPTURED
    │   ├─ 失败：→ FAILED
    │   └─ 未知：→ RESULT_UNKNOWN → 查询对账
    │
    ├─ Step 6：资金分账（Ledger + Policy）
    │   ├─ 平台分账
    │   ├─ 商户分账
    │   └─ 手续费扣除
    │
    └─ Step 7：账务凭证（Ledger）
        ├─ 应收分录
        └─ 资金到账分录
```

## 7. 端到端场景：O2C退款全链路规则映射

### 7.1 场景描述

客户对已签收订单申请退款，需要：
1. 判断是否在退款期限内
2. 判断退款金额是否合规
3. 确定审批层级
4. 执行退款
5. 处理退货或无需退货
6. 红冲发票
7. 调整账务

### 7.2 业务流-规则模型完整映射

#### 7.2.1 商流层

```text
退款资格判断（Specification）
├─ 订单已签收
├─ 在退款期限内（订单签收后7天内）
├─ 未超过最大退款次数
└─ 订单未被风控拦截

退款金额规则（Calculation Pipeline）
├─ Step 1：可退金额 = 订单实付 - 已退金额
├─ Step 2：扣除优惠（按比例）
├─ Step 3：扣除运费（可选）
├─ Step 4：校验不变量：可退金额 >= 0
└─ Step 5：返回可退金额

退款审批规则（Decision Table）
├─ ≤ 500元 + 低风险 → 自动批准
├─ > 500元 + 低风险 → 店长审批
├─ 任意 + 高风险 → 财务审批
└─ 黑名单 → 拒绝

审批权限规则（RBAC + ABAC + SoD）
├─ 店长：审批其管辖门店
├─ 财务：审批大额或高风险
└─ 禁止：申请人审批自己的退款

退款政策（Policy Object）
├─ 退款期限政策
├─ 退款金额政策
├─ 审批层级政策
└─ 退货政策
```

#### 7.2.2 物流层

```text
退货资格判断（Specification）
├─ 商品支持退货
├─ 商品未被使用/损坏
└─ 在退货期限内

退货入库规则（State Machine）
├─ PENDING_RETURN → SHIPPED → RECEIVED → INSPECTED
├─ INSPECTED → PASS（入库）/ FAIL（拒绝）

库存释放规则（Reservation + Ledger）
├─ 预占释放
└─ 库存账记录
```

#### 7.2.3 资金流层

```text
退款执行（Saga）
├─ Step 1：创建退款单（商流）
├─ Step 2：调用支付渠道退款
├─ Step 3：等待退款结果
├─ Step 4：更新退款状态
└─ 失败 → 补偿 + 重试 + 转人工

├─ 原支付分录
├─ 退款分录（逆向）
├─ 优惠返还分录（可选）
└─ 余额可追溯
```

```text
红冲执行（State Machine + Saga）
```

```text
├─ 退款冲减分录
└─ 凭证可追溯
```

#### 7.2.6 信息流层

```text
├─ 退款成功事件
```

## 9. 统一不变量体系

### 9.1 不变量定义

不变量（Invariant）是业务系统在任何合法路径上都必须保持成立的条件。

**与业务规则的区别**：
- 业务规则：可以配置、可以例外、可以变更
- 不变量：不可破坏的底线、任何例外都需要特殊审批

### 9.2 不变量分类

#### 9.2.1 核心不变量（绝对不可破坏）

```text
资金类
├─ 累计退款 <= 原有效支付
├─ 累计付款 <= 应付总额
├─ 账户余额 >= 0（资产类账户）
└─ 资金分摊合计 = 订单实付

库存类
├─ 已使用 + 已预占 <= 可支配库存
├─ 出库数量 <= 预占数量
└─ 批次追溯不可丢失

数量类
├─ 订单数量 = 明细数量之和
├─ 出库数量 <= 订单数量
└─ 退货数量 <= 原发货数量

权限类
├─ 主体只能访问其授权数据范围
├─ 不相容职责不能由同一主体承担
└─ 审批人 ≠ 申请人

审计类
├─ 所有业务变化必须有可追溯记录
└─ 历史记录不可覆盖
```

#### 9.2.2 业务不变量（通常不可破坏，除非特殊审批）

```text
订单类
├─ 订单应付 >= 0
├─ 优惠分摊合计 = 优惠总额
└─ 明细合计 = 订单金额

库存类
├─ 库存冻结数量 <= 可用库存
├─ 预占过期自动释放
└─ 批次先进先出（按策略）

权益类
├─ 权益使用次数 <= 权益总次数
├─ 权益有效期有效
└─ 优惠核销金额 <= 优惠额度

合同类
├─ 合同金额 >= 已执行金额
├─ 合同有效期有效
└─ 合同条款不可单方面修改
```

#### 9.2.3 跨流不变量（涉及多条业务流）

```text
O2C不变量
├─ 订单金额 = 支付金额 + 退款金额（支付金额 = 已收未退的净实付；毛支付 - 已退 = 净实付，等价表述见文档18 §8.6）
├─ 发货数量 <= 订单数量
├─ 开票金额 <= 订单实付金额
└─ 会计应收 = 订单应付 - 已收款

P2P不变量
├─ 采购订单 = 收货单 = 发票（允许合理差异）
├─ 入库金额 = 应付金额
├─ 付款金额 = 发票金额 - 已付金额
└─ 库存金额 = 采购入库金额

生产不变量
├─ BOM用量 = 投料数量 + 损耗
├─ 完工数量 <= 投料数量 × 成品率
└─ 在制品成本 = 材料 + 人工 + 制造费用
```

### 9.3 不变量设计原则

**原则1：识别核心不变量优先**

```text
第一步：识别资金、库存、安全相关的不变量
第二步：识别业务量级相关的不变量
第三步：识别跨流一致性不变量
```

**原则2：不变量必须可验证**

```text
不变量必须能够被测试验证
├─ 单元测试：正常路径
├─ 边界测试：临界值
├─ 并发测试：竞态条件
└─ 异常测试：故障恢复
```

**原则3：不变量校验必须有时机**

```text
Invariant校验时机
├─ 事务边界内：单操作原子性
├─ 应用服务层：跨聚合操作
├─ Saga补偿前：跨系统操作
└─ 对账周期：异步最终一致
```

**原则4：不变量破坏必须可发现**

```text
检测机制
├─ 实时校验：内存中检查
├─ 异步检测：对账任务
├─ 监控告警：指标异常
└─ 人工巡检：定期检查
```

**原则5：不变量破坏必须可修复**

```text
修复路径
├─ 自动修复：幂等重试
├─ 人工修复：审批后调整
├─ 补偿修复：反向操作
└─ 数据修复：历史数据修正
```

### 9.4 不变量与规则模型对应

| 不变量类型 | 推荐实现模型 | 典型验证方式 |
|---|---|---|
| 资金底线 | Invariant + Ledger | 并发测试、对账 |
| 库存底线 | Invariant + Quota/Reservation | 并发测试、库存快照 |
| 数量守恒 | Invariant | 边界测试、蜕变测试 |
| 权限底线 | RBAC + ABAC + SoD | 跨租户测试 |
| 状态合法性 | State Machine | 合法/非法转换测试 |
| 跨流一致性 | Ledger + 对账 | 定期对账、差异告警 |
| 历史不可覆盖 | Versioned Policy + Snapshot | 历史回放测试 |

### 9.5 不变量反模式

```text
反模式1：把业务规则当作不变量
├─ 错误："满500免运费"是不可变量
└─ 正确：这只是可配置政策

反模式2：不变量只在测试中验证
├─ 错误：代码中没有校验，只靠测试保证
└─ 正确：运行时有Invariant Guard

反模式3：复杂不变量跨多个系统
├─ 错误：跨5个系统的全局不变量
└─ 正确：每个系统维护局部不变量，通过对账保证全局

反模式4：不变量校验在错误时机
├─ 错误：先查后写导致并发破坏
└─ 正确：数据库条件更新、乐观锁、幂等键

反模式5：把显示状态当作不变量
├─ 错误："页面显示正常"意味着数据正确
└─ 正确：业务领域模型才是权威
```
