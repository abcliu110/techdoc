# 11-方法卡-设计评分与重新选型

> **层级**：L2 方法卡  
> **用途**：补充统一 L1 路径 B 的五维评分锚点、组合判定和 `RST-*` 重新选型方法  
> **原则**：评分暴露判断，不替代证据；重新选型由业务本质与约束触发，不由技术潮流触发  
> **版本**：v1.0 | **日期**：2026-08-05

---

## 1. 评分单位与准备

评分对象应是能独立承担业务责任或结构责任的对象，如模块、核心服务、业务边界、关键关系或跨模块流程。不要把整个系统只打一个平均分，也不要把每个小方法都评分。

评分前记录：对象范围、原设计意图、当时约束、当前约束、直接证据、推断状态。缺少意图证据时不得用低分惩罚历史未知。

---

## 2. 五维评分锚点

### 2.1 职责分配

| 分数 | 锚点 |
|---:|---|
| 1 | 多个不相关变化原因集中，任何变化都影响核心路径 |
| 2 | 职责明显扩散，边界主要靠约定维持 |
| 3 | 主职责可识别，但存在少量跨界逻辑 |
| 4 | 职责内聚，跨界行为有明确接口或协作点 |
| 5 | 职责与变化原因稳定对应，边界可验证且易演进 |

### 2.2 抽象层次

| 分数 | 锚点 |
|---:|---|
| 1 | 业务语义完全依赖技术表示，无法独立表达 |
| 2 | 关键业务判断泄漏大量存储、协议或部署细节 |
| 3 | 主抽象成立，但部分核心规则仍被实现细节绑架 |
| 4 | 业务概念清晰，技术细节主要留在适配边界 |
| 5 | 业务语义可独立验证，技术替换不改变核心模型 |

### 2.3 关注点分离

| 分数 | 锚点 |
|---:|---|
| 1 | 业务、配置、基础设施和副作用混在同一路径 |
| 2 | 分层名义存在，但依赖方向反复穿透 |
| 3 | 主路径分离，少数横切关注点仍散落 |
| 4 | 依赖方向清晰，策略与基础设施有稳定边界 |
| 5 | 关注点可独立测试、替换和发布，协作契约明确 |

### 2.4 一致性

| 分数 | 锚点 |
|---:|---|
| 1 | 同一概念多义、状态冲突，不变量无单一维护点 |
| 2 | 多实现频繁分叉，需要人工同步语义 |
| 3 | 核心语义基本一致，边缘状态或规则存在漂移 |
| 4 | 概念、状态和规则有集中契约，差异明确建模 |
| 5 | 不变量、状态和跨边界一致性均可自动验证 |

### 2.5 演进能力

| 分数 | 锚点 |
|---:|---|
| 1 | 常见变化必须修改核心抽象或一次性全量切换 |
| 2 | 变化范围大、回归难、关键选择不可逆 |
| 3 | 局部变化可控，但高频演化轴仍穿透核心路径 |
| 4 | 主要变化点有扩展位置，可灰度、兼容和回退 |
| 5 | 高频变化局部化，替换路径和演进契约经过验证 |

---

## 3. 组合判定

- 任一核心维度为 1：整体不能判“设计健康”，必须说明结构性阻断；
- 两个及以上维度为 2：至少进入重构候选评估；
- 平均分不能抵消不变式、一致性或安全边界上的低分；
- 高分也不能证明无需改变，必须结合约束是否已变化；
- 分数差异超过 1 分的评审者必须回到证据和评分对象范围，不用投票掩盖分歧。

建议输出：

| 对象 | 职责 | 抽象 | 分离 | 一致性 | 演进 | 关键证据 | 原因 | 置信度 |
|---|---:|---:|---:|---:|---:|---|---|---|

## 4. 反模式信号

| 信号 | 主要影响维度 | 不可直接推出的结论 |
|---|---|---|
| 工具类承载业务规则 | 职责、抽象 | 必须引入 DDD |
| Service 直接处理协议/序列化 | 抽象、分离 | 必须拆微服务 |
| 同一状态多套定义 | 一致性 | 必须统一成单一枚举 |
| 新类型不断修改核心 switch | 演进、职责 | 必须引入插件平台 |
| 多值字符串承载结构关系 | 抽象、一致性 | 必须立即迁表 |
| 跨模块共享数据库表 | 边界、演进 | 必须服务化拆库 |

反模式只是调查信号。必须结合业务规模、历史兼容、变化频率和替代成本判断。

---

## 5. 重新选型触发条件

仅在以下证据成立时进入 `RST-*`：

1. 现有技术或架构选择无法表达 ESS 的关键对象、关系或不变式；
2. 现有选择使高频演化轴持续修改核心路径；
3. 可靠性、容量、合规或生命周期要求已突破原约束；
4. 在现有选择上继续补丁的总迁移风险和长期成本高于替换；
5. 存在可分阶段兼容迁移的现实路径。

“技术旧”“业界流行”“团队想学”不能单独触发重新选型。

---

## 6. `RST-*` 四步法

### 6.1 从 ESS 定义能力需求

先写业务需要什么：语义表达、状态/一致性、时效、容量、扩展、可观测、合规和迁移要求。不得先写候选产品名。

### 6.2 评估现有选择的承载上限

区分：可通过配置解决、可通过局部封装解决、需要结构扩展、根本无法承载。记录证据、代价和原假设的突破点。

### 6.3 比较真实候选

| 字段 | 要求 |
|---|---|
| 候选 | 保留现状必须作为基线候选 |
| 业务匹配 | 如何承载 ESS 与不变式 |
| 兼容迁移 | 数据、接口、消息、任务、配置影响 |
| 运行代价 | 性能、容量、运维、可观测和故障模式 |
| 组织代价 | 技能、交付周期、供应商和锁定风险 |
| 退出成本 | 失败后如何回退或替换 |
| 证据状态 | 已验证、推断、假设、未知 |

### 6.4 形成决策与触发条件

`RST-*` 至少包含：目标 ESS、现状上限、候选对比、推荐及放弃理由、代价、约束、失效条件、验证计划、与 MIG 的接口、决策状态。

RST 是提议，不自动成为 ADR；人工或既有治理流程批准后才能标“已批准”。

---

## 7. 旧技术改进与重新选型的边界

| 情况 | 默认路径 |
|---|---|
| 业务语义可表达，只是可靠性或封装不足 | 路径 A 修复或局部进化 |
| 核心模型成立，但高频变化点缺扩展位置 | 路径 B 目标重构，技术可保持 |
| 技术选择扭曲对象、关系或不变式 | 进入 RST 候选评估 |
| 替换收益成立但无安全迁移路径 | 保留为目标/观察项，不得实施 |

重新选型不能替代目标设计。先有 ESS/TGT，再判断技术；选了新技术仍必须有 MIG。

---

## 8. 评分与选型失效模式

- 给整个系统一个平均分，掩盖核心边界的低分；
- 分数没有证据或评分对象范围不一致；
- 将无 DEC 自动判为设计错误；
- 从反模式名称直接跳到框架选型；
- 候选表只有新方案，没有保留现状；
- 只比功能，不比迁移、运行和退出成本；
- 把 RST 提议写成已批准决策；
- 用新技术重现旧错误抽象。

---

## 9. 与 L1 路径 B 的接口

统一 L1 的路径 B 主文保留五维结论、业务机制、RST 决策和证据；本卡只提供评分锚点与比较方法。方法细节不能越权首次产出 `REV/ESS/BIZ/TGT/RST/MIG` 主结论，也不能把评分差异冒充 `CA-*` 创造性洞察。
