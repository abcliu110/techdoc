一、应用壳类型分类

按核心导航模型和信息架构划分为 7 种，每种壳解决不同的业务场景和用户心智模型

🏢
企业业务壳
应用 → 对象/模块 → 列表 → 记录详情
以业务实体为中心，支持多应用切换。角色首页聚合待办，详情抽屉保持上下文，底部固定工具栏存放高频工具。
Salesforce Lightning SAP Fiori ServiceNow Workday
✅
任务协作壳
工作区 → 团队 → 项目/视图 → 任务详情
极度克制的左侧窄边栏，多视图切换（列表/看板/时间线），Split 面板保留列表上下文。命令面板是导航核心。
Linear Jira Plane Asana
📊
数据应用壳
空间 → Base → 表 → 视图 → 记录侧栏
顶部 Table Tab + 左侧 View 列表 + 主数据网格三区结构。同一份数据可多视图展示。Record Side Panel 不离开当前视图展开详情。
Airtable Teable NocoDB Baserow
📝
知识空间壳
工作区 → Teamspace → 页面树 → 内容画布
左侧树即导航结构，整理内容=整理导航。Hub-and-Spoke 最佳实践：5~8 个 Hub，三跳内可达任意内容。
Notion AFFiNE Outline Confluence
⌨️
开发者工具壳
Activity Bar → 侧边栏 → 编辑区 → 底部面板 → 状态栏
多区域并列、可拖拽重组。不是层级导航，而是区域型布局。Tab 式多文件，分割窗格，状态栏实时信息。
VS Code GitHub Vercel GitLab
🖥️
后台管理壳
顶部导航 → 左侧菜单树 → 面包屑 → 主内容（表格/表单/图表）
最通用的企业后台模式。RBAC 权限菜单驱动，统计卡片+数据表格为主视图，支持多标签页保留工作上下文。

低代码设计壳
页面列表 + 组件树 → 画布 → 属性面板 → 数据/查询面板
IDE 式四区布局：左侧实体树、中央画布、右侧属性、底部数据。设计态/运行态双态切换是核心能力。
Retool Appsmith NocoBase ToolJet
📋
服务队列壳
角色工作台 → 队列 → 工单 → 客户上下文面板
三栏结构：左队列列表、中工单详情、右客户上下文。不离开当前工单可查看关联信息（SLA、知识库、历史记录）。

二、导航模式详解

5 种核心导航模式，每种有明确的适用场景和设计权衡

模式 A：顶栏导航 + 左侧二级导航
顶栏承载全局操作（Logo、应用切换、搜索、通知、用户），左侧边栏承载当前应用内的模块导航。Salesforce、SAP Fiori、金蝶的核心布局。
优点
应用切换与模块导航职责分离
顶栏固定，内容区空间最大
跨应用一致的全局操作位置
缺点
顶栏 Tab 超过 7 个需折叠
双层导航学习成本较高
移动端需二次设计
SalesforceSAP FioriServiceNow金蝶云星空
模式 B：左侧边栏主导（两栏）
侧边栏承载所有导航层级（工作区 → 模块 → 子视图），顶部仅保留搜索/用户等全局操作。Linear、Notion、Vercel 的选择。适合深层级快速切换。
优点
导航层级统一在一个位置
支持无限纵向扩展
可折叠释放内容区宽度
缺点
占用 220-280px 宽度
深层嵌套时文字被截断
移动端体验差
LinearNotionVercelOutline
模式 C：Activity Bar + 多区域并列（VS Code 式）
最左侧 48px Activity Bar（仅图标）切换 Primary Sidebar 内容；中央 Editor 区多 Tab；底部 Panel 区（Terminal/日志）；底部状态栏。所有区域可拖拽重组。
优点
多任务并行效率极高
扩展可向所有区域注入内容
区域可拖拽重组适配个人习惯
缺点
新用户学习成本最高
不适合普通业务用户
移动端完全不适用
VS CodeJetBrainsZed
模式 D：IDE 四区布局（低代码设计壳）
顶部工具栏（应用名、设备切换、预览/发布）+ 左侧实体树（组件/页面/数据源）+ 中央画布 + 右侧属性面板 + 底部查询面板。设计态专属。
优点
所见即所得，信息密度高
组件树与画布强联动
设计/运行双态明确分离
缺点
仅适用于构建者，非使用者
小屏幕体验极差
实现复杂度最高
RetoolAppsmithToolJetBudibase
模式 E：三栏结构（服务队列 / 企业记录详情）
左栏：队列/列表（导航），中栏：工单/记录详情（主内容），右栏：上下文信息（客户资料、SLA、知识库推荐）。ServiceNow Agent Workspace 的核心模式。
优点
同时可见列表、内容、上下文
客服、审批场景效率极高
无需页面跳转
缺点
需要至少 1280px 宽度
三栏宽度比例需精心设计
中栏内容密度难以控制
ServiceNowZammadSalesforce Console
三、布局区域定义

企业应用壳的标准区域划分，各区域有明确的职责和作用域

┌──────────────────────────────────────────────────────────────────┐ │ GLOBAL SHELL BAR (48-56px) ← 全局作用域：跨所有应用持久化 │ Logo | App Launcher | Nav Tabs | Search | Notifications | User ├────────────┬─────────────────────────────────────────────────────┤ │ APP NAV │ BREADCRUMB / PAGE TITLE ← 应用作用域 │ SIDEBAR │ ─────────────────────────────────────────────── │ │ (220px) │ TOOLBAR: [New] [Import] [Filter] 🔍 Search │ │ │ ─────────────────────────────────────────────── │ │ Module A │ │ │ Module B● │ MAIN CONTENT AREA │ │ Module C │ (List / Dashboard / Form / Canvas) │ │ Module D │ ┌─────────┤ │ ──────── │ │ DETAIL │ │ Settings │ │ DRAWER │ │ │ │(380px) │ ├────────────┴──────────────────────────────────────────┴─────────┤ │ UTILITY BAR (40px, 可选) ← Salesforce 模式：常驻工具托盘 │ [📞 软电话] [📝 笔记] [⏱ 计时器] [📋 最近访问] └──────────────────────────────────────────────────────────────────┘
🌐全局层
跨所有应用持久化。包含：品牌 Logo、App Launcher/应用切换器、全局搜索（跨 App）、通知中心、用户菜单、租户切换。

关键约束：全局层内容不随 App 切换而改变。
📱应用层
当前应用内持久化。包含：应用内模块导航（侧边栏/顶部 Tab）、角色首页/工作台、待办聚合、应用级设置入口。

关键约束：切换应用时，应用层内容重置。
📄页面层
当前页面/视图专属。包含：面包屑、页面工具栏（筛选/排序/新建）、视图切换（列表/看板/日历）、分页、列表/表格/图表。

关键约束：跳转时状态可通过 URL 保留。
🔍详情层
记录详情，3 种展开方式。侧边抽屉（保留列表上下文）、Split 面板（列表+详情并排）、整页跳转（URL 稳定可书签）。

选择依据：操作深度 vs 上下文保留需求。
四、记录详情展开方式

从列表到详情的过渡是应用壳最核心的交互决策之一

侧边抽屉（Side Drawer）
列表不消失，右侧滑入详情
适用：快速预览、轻量编辑
优点：保留列表上下文，可返回
典型：Airtable、Jira、Salesforce
分屏面板（Split View）
列表左，详情右，同时可见
适用：高频切换、深度编辑
优点：最高信息密度，无跳转损耗
典型：Linear（Detail Level 1-3）、Outlook
整页跳转（Full Page）
独立 URL，面包屑标记来路
/
适用：深度编辑、可分享、SEO
优点：URL 稳定、专注内容
典型：GitHub、Metabase、Frappe
五、关键功能模块分析

应用壳的可组合功能单元，每个功能有明确的采用产品和设计规范

⌨️ 命令面板（Command Palette）
高价值功能
作为"第 5 层导航"：绕过所有层级，直接键盘跳转到任意位置或执行任意操作。触发：Cmd+K（Linear、Notion）或 Ctrl+Shift+P（VS Code）。
核心设计要点：① Fuzzy Search 容错匹配 ② 操作范围感知（当前上下文决定显示哪些命令）③ 子菜单式下钻 ④ 面板内显示快捷键提示 ⑤ 权限过滤（只显示有权限的命令）⑥ 最近使用优先排序。
Linear ⌘K VS Code ⇧⌘P Notion ⌘P GitHub (搜索代替)
🚀 App Launcher / 应用切换器
企业壳必备
解决多 App 平台的切换问题。Salesforce 用九宫格图标网格 + 搜索框，点击左上角图标展开全屏覆盖层。SAP Fiori 用瓦片磁贴首页作为 App 入口（Launchpad）。Vercel 用左侧顶部 Team Switcher（类 Slack 工作区切换）。
关键数据：App 数量 ≤ 7 用顶部 Tab；8-20 用下拉菜单或 Grid；＞20 必须加搜索。
Salesforce App Grid SAP Fiori Launchpad Notion Workspace Linear Workspace
🔔 通知中心
场景依赖
设计关键点：① 铃铛图标 + 数字 badge（超过 99 显示 99+）② 点击展开下拉列表（不跳转页面）③ 通知分类（@我、任务、系统、审批）④ 支持单条/全部已读 ⑤ 点击跳转到通知来源记录（带上下文回跳）。
SAP Fiori 通知支持按业务对象分组显示，Linear 的 Inbox 作为独立页面处理通知而非下拉。
SAP Fiori 分组通知 Linear Inbox Jira 通知下拉 GitHub 通知列表
🏠 角色工作台首页（Role-Based Home）
企业壳差异化
核心理念：不同角色看到不同的首页内容（销售看机会、服务看工单、财务看审批）。SAP Fiori 用"磁贴即应用入口"，每个 Tile 内嵌实时 KPI 数值，既是导航又是摘要。Salesforce 的仪表盘组件支持基于角色的动态配置。
设计要点：待办聚合、快捷操作、关键指标卡片、最近访问。
SAP Fiori Launchpad Salesforce Home Page ServiceNow Workspace Jira "For You"
🏷️ 多标签页（Multi-Tab / Workspace Tab）
复杂场景适用
解决问题：同时处理多条记录时避免反复跳转。Salesforce Console Navigation 把每条记录作为顶部 Sub-Tab，像浏览器标签管理工作上下文。用友 NC/金蝶 ERP 用 Tab 页签保留多个打开的功能页面。
注意：Tab 数量超过 8 条时用户认知负担急剧增加，需要提供"关闭所有"、Tab 排序等管理功能。
Salesforce Console 金蝶 Tab 页签 用友 NC VS Code Editor Tabs
🔗 底部工具栏（Utility Bar）
Salesforce 独有模式
Salesforce 独创：固定在页面最底部，宽度与视口同宽，类似 macOS Dock。存放高频辅助工具（软电话 CTI、快速笔记、计时器、最近访问）。点击按钮弹出向上的浮动面板（Docked Panel），不离开当前页面。
适用场景：需要在不离开主内容的情况下访问工具，特别适合呼叫中心、销售场景。
Salesforce Utility Bar

七、选型决策框架

根据业务场景快速定位应用壳类型和导航模式

问题 1：这个系统的核心用户任务是什么？
→ 处理业务实体（客户/订单/合同/工单）
企业业务壳
有多个业务对象（客户、订单、产品）且需要跨对象导航 → 顶栏 Tab + 侧边栏模块
服务队列壳
以工单/队列为核心，需同时查看上下文 → 三栏结构
→ 管理任务/项目进度
任务协作壳
团队协作、Sprint 管理、路线图 → 左侧窄边栏 + 多视图切换
命令面板是否必需：高频用户强烈推荐
→ 管理/分析结构化数据
数据应用壳
多视图、多维表格 → 顶 Tab + 左 View 列表 + 数据网格
需要 Record Side Panel 保留视图上下文
→ 创作知识/文档内容
知识空间壳
内容创作为主 → 左侧页面树 + 内容画布
Hub 数量控制在 5-8 个，树深度 ≤ 3
通用后台管理壳（菜单 → 路由 → 页面）适用于以上所有场景的最低成本实现，是功能导向的权限系统的默认选择。当业务实体未被明确识别、或团队没有专属设计资源时，优先选择此壳 + 标准组件库（Ant Design Pro / Vue Vben Admin）。
八、核心设计原则

从 14 款产品中提炼的共同规律，可作为向导框架的评分标准

原则 01
层级克制：3 跳原则
用户到达任何内容不超过 3 次点击。一级导航 ≤ 7 项（7±2 法则）。层级每加一层，回退成本加一倍。
✓ 首页 → 客户列表 → 客户详情（2跳）
✗ 首页 → 模块 → 子模块 → 列表 → 详情（4跳）
原则 02
上下文保留：不让用户迷路
跳转时保留来路（面包屑、返回按钮、列表状态）。列表筛选条件编码进 URL，刷新后可恢复。详情弹出时背景列表不消失。
✓ URL: /customers?status=active&page=2
✗ 点详情后返回，筛选和页码全丢了
原则 03
全局 vs 局部作用域明确分离
全局层（跨所有 App 持久）与应用层（当前 App 内持久）必须有视觉和行为上的明确边界。Retool 的 Global Frame vs Page Frame 是范本。
全局：顶部 ShellBar、通知、用户头像
局部：侧边栏菜单、面包屑、工具栏
原则 04
导航即权限地图
用户看到哪些菜单项 = 有哪些权限。不可访问的功能应直接隐藏，而非显示后报"无权限"。前端菜单过滤 + 后端路由鉴权双重保障。
✓ 销售只看到"客户""商机""活动"
✗ 显示所有菜单但点了报错
原则 05
渐进式暴露复杂度
高频功能在一级，低频功能折叠，长尾功能进命令面板。随着用户熟练度提升，逐渐开放快捷键和高级功能，而非一开始就全部展示。
Level 1: 按钮点击 → Level 2: 右键菜单
Level 3: 键盘快捷键 → Level 4: 命令面板
原则 06
配置驱动，与代码分离
导航结构从代码中抽离为配置（YAML/JSON/数据库），支持按角色动态渲染、运营配置、A/B 测试，不需要重新部署。SAP Fiori Launchpad 自定义是典型实现。
navigation.yaml → 角色过滤 → 动态菜单
而非 if(role==='admin') showMenu()
反模式警示：
① 迷宫导航：层级 ≥ 4，用户找不到回去的路   ② 标签云导航：顶栏 20 个项目，无分组无优先级   ③ 双重地狱：侧边栏 + 顶部 Tab + 面包屑 三套导航并存，用户需要三套心智模型   ④ 权限误导：显示无权限的菜单项，点击后报错   ⑤ 上下文丢失：跳转详情后返回，筛选和页码全丢
