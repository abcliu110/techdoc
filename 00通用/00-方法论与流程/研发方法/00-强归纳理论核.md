## 0. 六句硬共识

1. **归纳的产品是骨架，不是清单**
2. **冲突是高价值信号，必须升级**
3. **无分型，不出方案**
4. **一页压不出来 = 归纳未完成**
5. **先允许假设跳跃，再要求证据收敛**
6. **创造从当前解释失败处开始，不从“请创新”开始**

---

## 1. 主轴

业务知识在实现中被压进代码、表、配置、异常分支和历史妥协。

- **分析**：可验证解压
- **归纳**：把解压结果压成高密度主结构
- **进化**：在不改核心抽象内改善
- **重构**：在本质重映射后迁移
- **实施**：只在可验证边界内改动

归纳不是翻译代码，也不是堆清单。  
归纳是：**从分散事实生成更少、更硬、可回指、可决策的业务结构。**

强归纳包含两种不同工作：

- **恢复性归纳**：把已经压进实现的业务语义还原出来，回答“这个系统实际上如何运转”；
- **生成性归纳**：对同一批事实提出多个可区分解释，发现隐性关系、缺席能力和失效假设，回答“还可以怎样理解，它还能推导出什么”。

只有恢复性归纳，容易得到正确但平庸的复述；只有生成性归纳，容易得到漂亮但无证据的故事。两者必须按“先发散、后收敛”组合使用。

## 2. 三压缩 / 三解压

| 压缩 | 表现 | 解压目标 |
|------|------|----------|
| 表示压缩 | 业务含义被技术表示替换 | 还原业务概念、时效、能力 |
| 层级压缩 | 不变式 → 规则 → 分支 → 状态值 | 还原规则、策略、不变式 |
| 语境压缩 | 完整语义被拆到多文件/多跳/DEC | 还原关系、流程、边界、聚合 |

**法则**：按压缩类型定向解压；无信号不强开全方法。方法细则属 L2，不在本核展开。

## 3. 强归纳最小骨架（完成必须造形）

造骨架前，先把零散事实装配成一个能运行的**业务活模型**：

```text
服务对象与业务结果
  -> 角色在什么条件下作出什么决定或承诺
  -> 对哪些对象执行什么动作或交换
  -> 形成什么状态、权利、义务和结果
  -> 失败如何恢复，结果如何反馈并改变下一次行为
```

活模型是等待检验的解释，不是项目事实。它必须标明证据、推断和未知；其用途是让反事实、跨事实组合和视角切换有一个可以推演的对象。

一次有效归纳，必须给出以下骨架，而不是只给条目：

1. **核心对象**：少了它就不再是该系统
2. **关键关系**：尤其 2 跳以上隐性约束
3. **不变式**：改了就换系统
4. **边界**：一起变、一起一致、一起失败的范围
5. **能力**：系统对外真正提供的业务能力
6. **演化轴**：高变、高价值、高痛的变化方向
7. **分型**：保护 / 修复 / 演进 / 重绘

**先造形，后编目。** 清单只是原料，骨架才是产物。

## 4. 四律

### 律 1：先造形，后编目

不能停留在概念表、规则表、问题表。  
若压不成骨架，归纳未完成。

### 律 2：三级上升，不许跳级

- **L1 事实**：代码 / 表 / 配置 / 路径 / DEC 的直接证据
- **L2 结构**：对象、关系、规则、策略、异常、时效
- **L3 判断**：不变式、有意设计、缺陷、反模式、是否动核心抽象

从 L1 直接跳到“应微服务/事件驱动”= 虚构。  
停在 L2 不出 L3 = 只有分析，没有归纳。

### 律 3：冲突必须升级

同名异义、结构与流程不一致、DEC 与现状张力、规则与数据冲突，不得只并排列出。  
冲突要升成更高判断：语义分裂、边界错放、有意设计过期、隐性规则、演化轴暴露。

### 律 4：按决策相关性终压

每条保留结论至少服务一个决策：  
保护什么、修什么、演进什么、是否重绘、兼容如何保、迁移如何做。  
不影响决策的“正确百科”，删除或降为附录。

## 5. 四对象分型

| 类型 | 定义 | 默认动作 |
|------|------|----------|
| 业务不变式 | 系统存续期几乎不可破的约束 | 保护 |
| 有意设计 | 有代价意识的历史选择 | 保留，直到触发条件出现 |
| 可靠性缺陷 | 能力存在但脆弱 | 架构内修复 |
| 错误抽象 / 建模反模式 | 能跑，但理解与扩展代价过高 | 评估演进或重构 |

**无分型，不得出方案。**  
有意设计不得因为“不优雅”被误杀。

### 5.1 有意设计的确认与推断

**已确认有意设计**（优先）：

- 存在 DEC 卡，或等价的明确设计决策记录
- 记录了当时约束、代价或取舍

**推断有意设计**（无 DEC 时）：须**同时**满足以下三条，且必须标注为“推断”，不得写成已确认：

1. 存在长期稳定的代码/配置路径（非偶发分支）
2. 能说明当时约束或代价（性能、工期、兼容、技术栈等）
3. 当前运行未明显突破原假设（规模、复杂度、扩展方式仍大致成立）

三条缺一：不得判有意设计；默认进入可靠性缺陷或错误抽象的评估。

## 6. 生成主链

```text
理解循环（CA0-CA5）：
恢复阶段（CA0-CA1，不另称循环）
  事实样本
    -> 定向解压
    -> 装配业务活模型
    -> 形成当前解释 M0 与初始对象/关系/不变式/边界/能力/演化轴
创造阶段（CA2-CA5，不另称循环）
  当前解释 M0 无法自然解释的惊讶事实 S
    -> 固定解释缺口 Δ
    -> 反事实 / 期望违例 / 跨事实组合 / 重新框定 / 结构类比 / 假设反转 / 因果回路与博弈
    -> 形成让 S 变得可预期的竞争解释 H
    -> 比较解释增量，并形成实施前可观察、可能为错的冒险预测 P
    -> 用独立反证、保留样本和区分性验证淘汰、降级或转正
    -> 收敛为可证伪的业务骨架与分型

重设计循环（CA6-CA8）：
已收敛的本质、待解决矛盾和现实约束
  -> 核对真实结果与代理指标
  -> 保持不变量，改变角色责任、决策点、控制点、反馈、激励或协作机制
  -> 形成不同因果机制的业务候选
  -> 用博弈、反馈时滞、外部性、失败预演、最小实验、兼容和迁移约束收敛
  -> 再交给目标系统设计
```

`CA3 -> CA4` 完成一次“解释竞争轮”。执行前必须按同一决策问题和路径纪元记录轮次预算，默认最多 **3 轮**。出现以下任一结果即结束当前迭代：① 已形成至少两个因果结构和预测不同的解释，并确定能改变排序的下一项区分证据，进入独立验证；② 对非平凡任务已执行至少 2 轮、使用至少 2 类不同认知动作，Reviewer 仍确认后一轮没有新增因果结构或区分预测，按当前解释空间收敛；③ 达到预算仍不能区分。命中③时只能保留竞争解释、未知项和补证计划，不得强行转正本质。超过默认预算必须由 Referee 或人工责任人批准新增轮数、理由和停止点；验证失败或新证据到达可开启新轮次，但继续累计同一决策问题和路径纪元的轮数，不得改名、拆文档或重开任务来清零，也不得抹去既有轮次与失败预测。

创造性跳跃不是事实结论。发散阶段允许无证据假设，但必须标记来源和操作；收敛阶段只有经项目事实支持、能说明反例与失效条件的候选，才可进入正式 `EVO-T/ESS/BIZ` 结论。

高影响结论至少保留两个**预测不同**的解释，或给出答案唯一的区分性证据。多个同义改写不算竞争解释；证据缺席不等于业务能力不存在；外部类比只能产生候选，不能替代项目事实。

方法卡（概念净化、策略识别、创造性跳跃、多实现归一等）只在信号命中时加载，不默认全开，也不强制最后得到新奇答案。

## 7. 两路径判据

- **路径 A：核心抽象内进化**：`K1-K5` 均不改变且不需要重评原设计；地图仍可用，修路况与局部代价
- **路径 B：设计评估与重构**：需要评价原设计是否仍成立，或 `K1-K5` 任一项必须改变；先重估地图，再决定保留、重映射或重构

### 7.1 核心抽象的操作定义

触及以下**任一**，即视为“动核心抽象”，应走评估重构路径（或从进化升级）：

1. `K1` 核心对象的身份或生命周期语义
2. `K2` 对象间主关系（尤其 2 跳以上的路由/归属/一致性关系）
3. `K3` 关键不变式
4. `K4` 一致性边界（一起成功、一起失败、一起过期、一起回溯的范围）
5. `K5` 对外业务能力语义（输入/输出/前置条件的业务含义）

**不算**动核心抽象（默认仍可走进化）：

- 仅改实现手段（存储、中间件、线程模型等），业务语义不变
- 仅补可靠性（超时、重试、幂等、监控）
- 仅调局部策略参数，且不改变对外能力语义与不变式

### 7.2 路径切换防循环

路径可以随证据或经确认的推理纠错而变化，但不能随叙述摇摆。任务身份由“决策对象 + 事实基线 + `K1-K5` 判定对象”确定，不能靠改文件名、拆报告或重开 Prompt 清零。每个任务必须维护一个**路径纪元**，至少记录：当前路径、适用事实基线、`K1-K5` 逐项结论、支持与反方证据、切换次数、上次切换原因和审批人。

- 只有以下两种触发才允许切换：① 新增或新验证的证据改变 `K1-K5` 至少一项结论；② Reviewer/Referee 定位出原判定的具体推理、范围或证据引用错误，并记录“原结论为什么不再成立”。同一事实基线和同一组证据不得在没有上述纠错记录时同时作为相反方向的切换理由。
- `A -> B` 必须指出命中的 `K1-K5` 项；`B -> A` 必须由 `REV-*` 证明 `K1-K5` 均不改变，并经未参与原判定的 Reviewer 确认。
- 同一任务允许自动切换一次。发生第二次及后续切换时，停止产出正式 `EVO-E/BIZ/TGT/MIG`，由 Referee 或人工责任人裁决路径、证据缺口和下一次重开条件。
- 裁决后对当前事实基线锁定路径。只有改变 `K1-K5` 判断的新证据，或新发现且经独立确认的原判定错误，才能开启下一路径纪元；新纪元继续引用旧证据、编号和切换历史，不得清零重做以规避次数限制。

### 7.3 四禁止

- 无证据判断
- 无分型行动
- 无验证方案
- 无迁移重构（无迁移 = 重写，不是重构）

## 8. 完成定义（五关 + 创造性五关）

1. **可逆**：能从结论回指证据
2. **区分**：能说明这不是另一个系统
3. **稳定**：多读相近材料不整体改口
4. **最小**：再少一条就丢关键结构
5. **可决策**：能支撑保护/修复/演进/重绘之一

五关不过，不得称“已归纳完成”。

路径 B、正式或高影响的归纳还必须通过创造性五关：

6. **溯因**：明确惊讶事实 `S`、当前解释 `M0` 和解释缺口 `Δ`；没有解释失败，不凭空制造新抽象；
7. **解释增量**：核心抽象比 `M0` 多解释事实、少使用补丁假设，新增概念成本与剩余事实透明；
8. **竞争**：关键判断与至少一个因果结构不同的解释比较过，或已有区分性证据证明解释空间唯一；
9. **冒险与可证伪**：给出实施前可观察、可能为错、能区分解释的新预测，以及削弱或放弃结论的最小事实；
10. **机制韧性**：业务候选没有把代理指标冒充真实结果，并检查适用的角色激励、套利/规避、反馈时滞和风险外溢。

五关要求的是探索质量，不是“必须创新”。充分探索后，最简单的原解释仍可能是正确答案。

## 9. 一页残酷小样（压测工具）

| 项 | 上限 | 要求 |
|----|------|------|
| 惊讶与解释 | 1 条主矛盾 | 写清 `S-M0-Δ` 和最可能推翻胜出解释的事实 |
| 业务活模型 | 1 条主链 | 能说明服务对象、结果、决定/承诺、动作/交换、反馈/恢复 |
| 核心对象 | ≤ 5 | 每个有证据 |
| 不变式 | ≤ 5 | 区分于可变规则 |
| 关键隐性关系 | ≤ 3 | 优先 2 跳+ |
| 演化轴 | ≤ 2 | 高变/高价值/高痛 |
| 路径判断 | 1 | 进化或评估重构，给判据 |
| 分型动作 | 若干 | 保护/修复/演进/重绘，不混写 |

**用法**：

- 小样是归纳力压测与开工前自检工具，不是每次正式长文的唯一交付格式
- 正式进化/评估报告可以更长，但**必须能压回这一页**；压不回 = 归纳未完成或终压不足
- 当前打印系统小样实践可后置，不阻塞本核生效

- 当前目录、路径路由和产物接口以统一 L1 正文为准，不再引用重构讨论稿

### 10.5 强制术语表（防跨文档漂移）

同一概念在 L0/L1/22A/Profile 中必须使用同一用词，禁止另造同义词或缩写。新增术语必须登记于此。

| 概念 | 唯一用词 | 禁用词/例示 |
|---|---|---|
| 归纳中从惊讶到解释的推理链 | `S-M0-Δ-H-P-F` 溯因链 | 不要只写"溯因"或"解释推理" |
| 反向+增量+反直觉的增强溯因链 | `S-M0-Δ-H-P-F-ΔH-CI` 增强溯因链：ΔH=解释增量、CI=反直觉洞察；架构版以 `CI(A)` 后缀（真源：业务版 10-方法卡 §8.3、架构版 16-方法论 §1.3.1） | ❌ 溯因增强 / 增强推理 / 升级溯因 |
| 对比当前解释 `M0` 与候选 `H` 的信息收益 | **解释增量** | 禁止同义改写："解释覆盖度/信息增益" |
| 候选业务机制没有把代理指标冒充真实结果 | **机制韧性** | 术语漂移警告：L1 §7.1 曾用"机制真实性"，已统一回本词 ❌ 机制真实性 / 机制健全性 |
| 用保留样本或未见领域检验 AI 能力 | **迁移压测** | ❌ 能力测试 / 泛化测试 |
| 两个独立演进方向 | **路径 A / 路径 B** | ❌ 方案一 / 方案二 |
| 业务机制重设计产物 | **`BIZ-*`** | ❌ 业务重构（与"重绘"混用） |
| 探索记录产品 | **`CA-*`** | ❌ 灵感 / 想法 / 草案 |
| 压测：从已验证 `EVO-T/ESS` 形成因果机制不同的候选 | **机制生成** | ❌ 机制候选生成 / 业务重设计方案生成 |
| 压测：揭示保留样本后对照已冻结 `P/F` 按证据比例更新解释 | **证据更新** | ❌ 改口 / 事后修正 / 无条件迎合 |
| 从事实恢复到经独立验证的业务本质 | **理解循环（CA0-CA5）** | ❌ 恢复循环 / 创造循环 / 归纳循环 |
| 从已验证本质生成并收敛业务机制候选 | **重设计循环（CA6-CA8）** | ❌ 业务重设计循环 / 进化循环 |
| 判断路径 A/B 的五项唯一判据 | **核心抽象判据 `K1-K5`** | 禁止在下游另写缩略判据作为新定义 |

| 架构在核心约束内增加新能力的演进 | **增强型进化**：风险低、成本低、保持核心架构不变；类比路径 A | ❌ 架构增强 / 架构优化 |
| 架构调整以适应新需求的演进 | **适应型进化**：风险中、成本中、部分改变核心架构 | ❌ 架构调整 |
| 架构根本性改变架构模式的演进 | **转型型进化**：风险高、成本高、改变核心约束；类比路径 B | ❌ 架构重构 / 架构迁移 |

# 附录 D：复杂系统思维与元框架

> 本附录将复杂系统思维、第一性原理、批判性思维和系统性设计思维纳入 L0 框架，为分析遗留系统和业务重构提供更底层的认知工具。

## D.1 为什么需要复杂系统思维

遗留系统是复杂适应系统，不是设计出来的机器。理解这一点是归纳成功的前提。

**复杂系统的特征**：

```text
1. 涌现性
   - 系统整体行为不能从部件行为推导
   - 代码行数多不等于理解成本高
   - 模块边界清晰不等于业务边界清晰

2. 非线性
   - 小改动可能引发大影响
   - 大改动可能平安无事
   - 因果关系不是简单的一一对应

3. 路径依赖
   - 当前状态由历史决策决定
   - 看似不合理的设计往往有合理的历史原因
   - 改变现状的代价取决于历史路径

4. 自组织
   - 没有中央控制但有秩序
   - 开发者按局部最优行动，结果可能全局次优
   - 代码结构是熵增与熵减的动态平衡

5. 反馈回路
   - 正反馈：成功导致更多成功
   - 负反馈：偏差导致纠正
   - 延迟反馈：后果滞后于行动
```

**对归纳工作的启示**：

| 复杂系统特征 | 在遗留系统中表现 | 归纳时应对 |
|---|---|---|
| 涌现性 | 整体行为不可预测 | 避免从局部推断整体，从整体解释局部 |
| 非线性 | 改一点可能崩一片 | 识别关键杠杆点，评估连锁反应 |
| 路径依赖 | 历史决策限制现在 | 用决策考古法，理解”为什么当时必须这样” |
| 自组织 | 没有设计但有秩序 | 识别实际的组织逻辑，不强加外部框架 |
| 反馈回路 | 修复引发新问题 | 评估干预的长期效果，不只看短期结果 |

## D.2 第一性原理方法论

第一性原理（First Principles Thinking）是从最基本的不可分割的真理出发进行推理的思维方法。

### D.2.1 第一性原理 vs 类比思维

| 思维类型 | 本质 | 优点 | 风险 |
|---|---|---|---|
| 类比思维 | “别人这样做，我也这样做” | 快速、安全、有先例可循 | 受限于现有模式，难以突破 |
| 第一性原理 | “从最基本的真理出发” | 可能发现全新解法 | 需要更多时间，可能过于理想化 |

### D.2.2 第一性原理操作方法

```text
分解：把问题分解到最基本的、不可再分的事实

问题 X
  -> 分解为子问题 A, B, C
    -> 子问题 A 分解为 a1, a2
    -> 子问题 B 分解为 b1, b2, b3

追问：对每个基本事实追问”为什么”
  -> “为什么 a1 是真的？”
  -> “a1 的反面是什么？”
  -> “如果 a1 不成立，X 会怎样？”

重建：从基本真理重建解决方案
  -> 如果 a1, b2, c1 为真
  -> 那么 X 应该是什么样子？
  -> 这个样子与当前实现有什么差距？
```

### D.2.3 第一性原理在归纳中的应用

**应用场景 1：追问核心抽象的必要性**

```text
问题：这个系统的”订单”为什么要建模为一个独立实体？

第一性原理追问：
1. “订单”的最基本功能是什么？
   -> 记录”谁在什么时候承诺了什么”

2. 这个功能能否由其他更基本的概念组合而成？
   -> 承诺 + 支付 + 物流 = 订单？
   -> 或者是：承诺 = 订单？

3. 当前”订单”实体是否混合了多个概念？
   -> 商业承诺 vs 履约记录 vs 对账凭证

4. 如果重新设计，是否需要保留”订单”这个实体？
   -> 还是应该拆分为更原子的概念？
```

**应用场景 2：追问约束的必要性**

```text
问题：为什么系统要求”订单必须在 24 小时内支付”？

第一性原理追问：
1. 这条规则的原始目的是什么？
   -> 可能是：防止库存锁定太久 / 防止欺诈 / 简化对账

2. 这个目的是否仍然成立？
   -> 现在库存是否紧张？
   -> 是否有其他防欺诈手段？
   -> 对账周期是否仍是 24 小时？

3. 如果取消这条规则，最坏会发生什么？
   -> 量化最坏情况的成本

4. 有没有更轻量的方式实现相同目的？
   -> 动态超时 / 分级超时 / 信用评估
```

## D.3 批判性思维框架

批判性思维不是”批评”，而是”系统性地审视 thinking about thinking”。

### D.3.1 批判性思维要素

| 要素 | 定义 | 在归纳中的表现 |
|---|---|---|
| 清晰性 | 能用简单语言解释吗？ | 能否向非技术人员解释业务逻辑 |
| 准确性 | 有证据支持吗？ | 推断是否有代码/配置/接口证据 |
| 精确性 | 粒度够细吗？ | 不变量是否区分于规则和策略 |
| 相关性 | 与问题真正相关吗？ | 结论是否影响决策 |
| 深度 | 触及根本原因了吗？ | 是否停在表层解释 |
| 广度 | 考虑其他视角了吗？ | 是否有竞争解释 |
| 逻辑性 | 因果链成立吗？ | 从事实到结论的推理是否有效 |
| 重要性 | 关注最重要的了吗？ | 是否被细枝末节分散注意力 |
| 公正性 | 是否受偏见影响？ | 是否只为迎合预设结论 |

### D.3.2 批判性思维在归纳中的应用

**应用场景 1：审视归纳结论**

```text
结论：系统的核心问题是”缺乏统一的状态管理”

批判性思维检验：
1. 清晰性：什么是”统一”？什么是”状态”？
   -> 需要明确定义，不能用模糊术语

2. 准确性：结论有证据支持吗？
   -> 哪些代码/设计证明了”缺乏统一”？
   -> 是否只是因为代码分散就认为”不统一”？

3. 深度：这是根本原因还是症状？
   -> “缺乏统一状态管理”是原因还是表现？
   -> 如果是表现，真正的原因是什么？

4. 广度：其他解释是否同样合理？
   -> “缺乏统一状态管理” vs “业务边界与模块边界不一致”
   -> 哪个解释更能产生可操作的改进？
```

**应用场景 2：识别认知偏见**

| 认知偏见 | 定义 | 在归纳中的表现 | 应对方法 |
|---|---|---|---|
| 确认偏见 | 只寻找支持已有假设的证据 | 看到符合预期的事实，忽略反例 | 主动寻找反例，假设自己是错的 |
| 锚定效应 | 过度依赖第一个信息 | 被代码中最先看到的部分主导 | 先广泛采样，再形成假设 |
| 幸存者偏差 | 只分析成功的案例 | 只看”正常”代码，忽略废弃代码 | 也要分析错误处理、异常路径 |
| 知识诅咒 | 假设别人与自己知识相同 | 用技术术语代替业务解释 | 用业务语言重述技术发现 |
| 过度自信 | 高估自己的判断准确性 | “这个设计明显是错的” | 记录不确定性，定期检验假设 |

### D.3.3 批判性思维检验清单

```text
在得出任何重要结论前，必须逐项检验：

□ 结论是否有证据支持？证据等级是什么？
□ 结论的反面是什么？有证据支持反面吗？
□ 是否考虑了其他合理解释？
□ 因果链是否完整？有遗漏的中间环节吗？
□ 结论是否可证伪？什么事实会推翻它？
□ 是否混淆了相关性因果性？
□ 样本是否具有代表性？是否存在选择偏差？
□ 结论是否过于笼统或过于具体？
□ 结论是否被利益相关方影响？
□ 是否被时间压力或认知捷径影响？
```

## D.4 系统性设计思维

系统性设计思维（Systems Thinking）关注整体而非部分，关注关系而非对象，关注模式而非事件。

### D.4.1 系统性思维的核心概念

| 概念 | 定义 | 在遗留系统中的体现 |
|---|---|---|
| 因果回路 | 原因和结果形成闭环 | 修复引发新问题，问题引发新修复 |
| 增强回路 | 正反馈循环，强者更强 | 成功案例被复制，导致更多同类实现 |
| 平衡回路 | 负反馈循环，目标导向 | 业务规则层层加码直到崩溃边界 |
| 延迟 | 行动与结果之间的时间差 | 技术债长期积累后才显现问题 |
| 边界 | 系统的内外之分 | 模块边界 vs 业务边界 vs 组织边界 |
| 涌现 | 整体大于部分之和 | 代码量与复杂度不成正比 |

### D.4.2 因果回路图简化版

```text
增强回路（正反馈）示例：
  技术债增加
    -> 开发速度下降
      -> 时间压力增加
        -> 更多临时方案
          -> 技术债进一步增加

平衡回路（负反馈）示例：
  业务需求变化
    -> 系统复杂度增加
      -> 维护成本上升
        -> 引发重构投入
          -> 复杂度得到控制（如果成功）
```

### D.4.3 系统性思维检验清单

```text
在分析遗留系统时，用系统性思维检验：

□ 是否识别了系统的关键反馈回路？
  - 哪些是正反馈？哪些是负反馈？
  - 正反馈是否导致问题累积？

□ 是否识别了关键延迟？
  - 行动与结果之间有什么延迟？
  - 延迟是否导致问题难以追溯？

□ 是否识别了系统的边界？
  - 当前分析的边界是什么？
  - 边界外有什么因素在影响系统？

□ 是否考虑了涌现效应？
  - 局部最优是否导致全局次优？
  - 如何利用涌现而非对抗？

□ 是否考虑了二阶效应？
  - 干预会产生什么新问题？
  - 受益方和受损方是谁？
```

## D.5 整合框架

四个框架不是独立的，而是互补的：

```text
复杂系统思维：理解”系统是什么样子”
  -> 帮助识别涌现、反馈、延迟等系统特征

第一性原理：追问”最基本的真理是什么”
  -> 帮助穿透表象，找到不可动摇的基础

批判性思维：检验”推理是否有效”
  -> 帮助识别认知偏见和逻辑谬误

系统性思维：理解”系统如何运作”
  -> 帮助识别反馈回路和干预杠杆点
```

**应用顺序建议**：

```text
1. 用复杂系统思维建立对系统的基本理解
2. 用第一性原理追问核心假设
3. 用批判性思维检验归纳结论
4. 用系统性思维评估干预方案
```

# 附录 E：溯因验证的实验设计方法

> 本附录为溯因链中的冒险预测提供实验设计方法，确保解释可以被有效验证。

## E.1 好的验证特征

```text
1. 可观察：在实施前就能看到结果
2. 可能失败：结果可能与预测不符
3. 区分性：能区分 H 和竞争解释 H'
4. 可重复：其他人在类似条件下也能验证
```

## E.2 溯因验证实验设计方法

### E.2.1 自然实验法

利用已有事实构建”天然实验”：

```text
适用场景：存在自然发生的对比组

操作方法：
1. 识别 H 预测的差异化结果应该出现在什么条件下
2. 在已有数据/代码/配置中寻找满足/不满足该条件的案例
3. 比较两组的实际结果是否与预测一致

示例：
H：系统的状态同步问题源于”没有事务性消息”
P：在有消息重试机制的模块，状态同步应该更可靠
验证：在代码中找到两类实现（有消息重试 / 无消息重试），对比状态一致性
```

### E.2.2 最小实验法

设计最小可执行的实验来验证预测：

```text
适用场景：需要主动验证而非被动寻找证据

操作方法：
1. 将预测转化为最小可执行的测试场景
2. 识别触发预测结果所需的最小条件
3. 执行实验并观察结果

示例：
H：用户权限判断在并发时存在竞态条件
P：当两个请求同时修改权限时，可能出现不一致
验证：编写并发测试脚本，同时发起两个冲突的权限修改请求，检查结果
```

### E.2.3 反事实验证法

利用反事实推理验证预测：

```text
适用场景：无法直接验证，但可以验证反事实

操作方法：
1. 如果 H 为真，那么”非 H”会导致什么不同结果？
2. 寻找”非 H”已经发生的案例
3. 验证结果是否与预期一致

示例：
H：系统的延迟问题源于单点数据库查询
P：如果使用缓存，延迟会显著下降
验证：找一个已经使用缓存的类似场景，对比延迟数据
```

### E.2.4 区分性证据搜索法

有目的地寻找能够区分解释的证据：

```text
适用场景：存在多个竞争解释，需要找到区分性证据

操作方法：
1. 列出竞争解释 H1, H2, H3...
2. 对每对解释，找到它们预测不同结果的场景
3. 优先寻找该场景的证据

示例：
H1：状态不一致源于并发控制不足
H2：状态不一致源于数据模型设计缺陷

区分性预测：
- H1 预测：在低并发场景问题应该消失
- H2 预测：无论并发高低，问题都应该存在

验证：在低并发时间段监控问题发生率
```

## E.3 溯因验证质量评估

| 评估维度 | 问题 | 评估标准 |
|---|---|---|
| 可验证性 | 预测是否可以被观察到？ | 可以在实施前验证得高分 |
| 区分性 | 预测是否能区分竞争解释？ | 能区分多个解释得高分 |
| 可重复性 | 验证是否可重复？ | 其他人在类似条件可重复得高分 |
| 成本 | 验证的成本是什么？ | 低成本高价值得高分 |
| 风险 | 如果预测失败意味着什么？ | 失败能明确否定解释得高分 |

## E.4 溯因验证记录模板

```markdown

区分的解释（如果有）：

验证方法：[自然实验 / 最小实验 / 反事实 / 区分性证据搜索]

验证执行：
- 时间：
- 方法：
- 观察到的结果：

结论：
- [ ] 预测得到验证
- [ ] 预测被否定
- [ ] 证据不足，需要进一步验证

对解释 H 的影响：
- 强化 / 削弱 / 否证 / 需要修正
```

# 附录 F：架构债务量化方法

> 本附录为架构归纳提供量化工具，将架构债务从定性描述转化为可度量的指标。

## F.1 架构债务的组成

```text
1. 设计债务
   - 过时的架构假设
   - 不再适用的设计决策
   - 未实现的架构改进

2. 代码债务
   - 重复代码
   - 过长函数
   - 复杂条件逻辑
   - 硬编码值

3. 技术债务
   - 过时的依赖
   - 安全漏洞
   - 性能问题

4. 测试债务
   - 低测试覆盖率
   - 缺少集成测试
   - 测试维护成本高
```

## F.2 架构债务量化方法

### F.2.1 影响范围法

量化债务影响的范围：

```text
指标：
- 受影响模块数量
- 受影响代码行数
- 受影响功能点数量
- 受影响接口数量

计算公式：
影响范围得分 = 受影响模块数 × 0.3 + 受影响代码行数/总代码行数 × 0.3 + 受影响功能点数/总功能点数 × 0.2 + 受影响接口数/总接口数 × 0.2
```

### F.2.2 修复成本法

量化偿还债务所需的工作量：

```text
指标：
- 预估修复工时
- 需要的测试工时
- 需要的回归测试工时
- 需要的文档更新工时

估算方法：
- 基准：类似问题的历史修复工时
- 调整因子：代码复杂度、测试覆盖率、依赖关系
- 风险因子：不确定性、可能的连锁影响
```

### F.2.3 业务影响法

量化债务对业务的影响：

```text
指标：
- 缺陷密度（缺陷数/代码行数）
- 变更前置时间（从需求到上线）
- 故障恢复时间
- 技术债导致的业务损失
```

### F.2.4 演进阻力法

量化债务对架构演进的影响：

```text
指标：
- 新功能开发成本增幅
- 架构修改的影响范围
- 技术选型的限制程度
- 团队学习曲线

计算公式：
演进阻力得分 = (当前开发成本 - 基准开发成本) / 基准开发成本 × 0.3 + 架构修改影响范围系数 × 0.3 + 技术选型限制程度 × 0.2 + 团队学习曲线 × 0.2
```

## F.3 架构债务综合评估

```text
综合得分 = 影响范围得分 × 0.25 + 修复成本得分 × 0.25 + 业务影响得分 × 0.25 + 演进阻力得分 × 0.25

债务等级：
- 低（0-25分）：债务可控，可按计划偿还
- 中（26-50分）：债务需要关注，建议近期偿还
- 高（51-75分）：债务严重，需要优先偿还
- 极高（76-100分）：债务危机，需要立即处理
```

# 附录 H：Event Sourcing / CQRS / Saga 深度分析

> 本附录为架构归纳提供常见分布式架构模式的深度分析框架。

## H.1 Event Sourcing 架构模式

### H.1.1 模式定义

**Event Sourcing（事件溯源）**：将业务状态的所有变更存储为不可变的事件序列，通过重放事件来重建状态。

```text
核心概念：
- 事件（Event）：表示已发生的事实，不可变
- 聚合（Aggregate）：处理命令、生成事件
- 事件存储（Event Store）：持久化事件序列
- 投影（Projection）：从事件生成读模型

与 CRUD 对比：
CRUD：当前状态 ← 操作 ← 新状态
ES：事件序列 → 重放 → 当前状态
```

### H.1.2 Event Sourcing 的架构特征

```text
识别信号（在代码中）：
1. 存在事件类/事件总线
2. 聚合通过 apply(event) 方法更新状态
3. 没有 update 语句，只有 insert（事件）
4. 存在从事件重建状态的逻辑
5. 存在快照机制（优化重放性能）

代码模式：
class Order {
    private OrderState state;  // 从事件重建

    public void apply(OrderCreatedEvent event) {
        this.state = new OrderState(event.getDetails());
    }

    public void apply(OrderPaidEvent event) {
        this.state.markPaid(event.getPaymentId());
    }
}
```

### H.1.3 Event Sourcing 的架构约束

```text
硬约束：
1. 事件不可变
   - 不能修改已发生的事实
   - 修正只能通过补偿事件

2. 事件顺序重要
   - 聚合的事件必须按顺序重放
   - 并发控制必须保证事件顺序

3. 幂等性
   - 投影必须能处理重复事件
   - 事件处理器必须幂等

软约束：
1. 事件大小
2. 投影一致性
3. 版本兼容性
```

### H.1.4 Event Sourcing 的架构债务

```text
常见债务类型：
1. 事件版本混乱
   - 早期事件没有版本号
   - 事件格式变更没有迁移策略

2. 投影不一致
   - 投影代码与聚合代码不同步
   - 事件处理器有 bug 导致投影错误

3. 性能问题
   - 聚合太重，重放耗时
   - 事件太多，查询慢
   - 缺少快照机制

4. 事件泄露
   - 事件包含不应该暴露的内部细节
   - 事件与业务契约耦合
```

## H.2 CQRS（命令查询责任分离）

### H.2.1 模式定义

**CQRS（Command Query Responsibility Segregation）**：将读操作和写操作分离，使用不同的模型处理。

```text
核心概念：
- 命令（Command）：改变状态的写操作
- 查询（Query）：只读状态
- 写模型（Write Model）：优化写操作
- 读模型（Read Model）：优化读操作

与 CRUD 对比：
CRUD：同一个模型处理读写
CQRS：分离模型，专门的写模型和读模型
```

### H.2.2 CQRS 的架构特征

```text
识别信号（在代码中）：
1. 存在两个不同的数据模型
2. 命令处理和查询处理使用不同代码
3. 存在同步机制将写模型同步到读模型
4. 读模型可能是非规范化的
5. 存在读写分离的 API

代码模式：
// 写模型
class OrderService {
    public void createOrder(CreateOrderCommand cmd) {
        Order order = new Order(cmd.getDetails());
        orderRepository.save(order);
        eventBus.publish(new OrderCreatedEvent(order));
    }
}

// 读模型
class OrderQueryService {
    public OrderSummaryDTO getOrderSummary(Long orderId) {
        return orderSummaryRepository.findById(orderId);
    }
}
```

### H.2.3 CQRS 的架构约束

```text
硬约束：
1. 命令与查询必须分离
   - 命令不返回数据（或返回有限数据）
   - 查询不改变状态

2. 数据一致性边界
   - 写模型与读模型之间是最终一致
   - 必须处理不一致窗口

软约束：
1. 读模型设计
2. 同步机制
```

### H.2.4 CQRS 的架构债务

```text
常见债务类型：
1. 读模型过时
   - 同步延迟导致读模型数据过时
   - 同步失败导致读模型不一致

2. 读写模型不一致
   - 业务规则变更时只更新了写模型
   - 读模型投影代码有 bug

3. 复杂度失控
   - CQRS 过度使用
   - 不需要分离的场景也用了 CQRS

4. 迁移成本高
   - 从 CRUD 迁移到 CQRS 成本高
   - 读模型重建耗时长
```

## H.3 Saga 模式

### H.3.1 模式定义

**Saga**：通过一系列本地事务和补偿事务实现跨服务的分布式事务。

```text
核心概念：
- 本地事务（Local Transaction）：单个服务内的事务
- 补偿事务（Compensating Transaction）：撤销本地事务的操作
- 协调者（Coordinator）：管理 saga 执行和补偿

Saga 类型：
1. 编排 saga（Choreography）：通过事件驱动，无中心协调者
2. 编排 saga（Orchestration）：有中心协调者控制 saga 流程
```

### H.3.2 Saga 的架构特征

```text
识别信号（在代码中）：
1. 存在 saga 编排器/协调者类
2. 存在补偿操作的实现
3. 存在 saga 状态的持久化
4. 存在重试和幂等处理
5. 跨服务的调用有补偿逻辑

代码模式：
class OrderSaga {
    public void execute(Order order) {
        try {
            // Step 1: 预留库存
            inventoryService.reserve(order.getItems());

            // Step 2: 扣款
            paymentService.charge(order.getCustomer(), order.getTotal());

            // Step 3: 创建订单
            orderService.confirm(order);

        } catch (PaymentFailedException e) {
            // 补偿：释放库存
            inventoryService.release(order.getItems());
            throw e;
        }
    }
}
```

### H.3.3 Saga 的架构约束

```text
硬约束：
1. 补偿必须存在
   - 每个写操作必须有对应的补偿操作
   - 补偿必须能处理部分成功的情况

2. 幂等性
   - 所有操作必须幂等
   - 补偿操作也必须幂等

3. 隔离性缺失
   - Saga 不提供 ACID 隔离
   - 必须处理并发冲突

软约束：
1. 补偿顺序
2. 超时处理
3. 状态可见性
```

### H.3.4 Saga 的架构债务

```text
常见债务类型：
1. 补偿逻辑缺失
   - 早期实现没有补偿
   - 新增步骤忘记补偿

2. 补偿逻辑错误
   - 补偿逻辑与主逻辑不一致
   - 补偿顺序错误

3. 补偿不可靠
   - 补偿操作失败没有重试
   - 补偿状态没有持久化

4. 测试不足
   - Saga 测试覆盖不足
   - 异常场景没有充分测试
```

## H.4 三种模式的组合分析

### H.4.1 Event Sourcing + CQRS

```text
组合优势：
- 写模型通过事件构建，读模型通过投影生成
- 天然的事件驱动架构
- 可以重放任意历史状态

组合挑战：
- 两套一致性模型需要协调
- 投影的一致性延迟
- 事件版本管理

识别信号：
- 既有事件存储，又有读模型同步
- 投影是从事件流生成
- 存在快照和重放机制
```

### H.4.2 Saga + Event Sourcing

```text
组合优势：
- Saga 的每一步都是事件
- 天然支持重放和审计
- 补偿逻辑可以是事件

组合挑战：
- Saga 状态也需要作为事件存储
- 补偿事件的处理顺序

识别信号：
- Saga 步骤通过事件触发
- 存在 SagaStarted、SagaCompleted、SagaCompensated 事件
```

### H.4.3 CQRS + Saga

```text
组合优势：
- 命令端发起 saga，读模型展示 saga 状态
- 写模型处理复杂事务，读模型展示最终结果

组合挑战：
- Saga 的中间状态在读模型中可见
- 需要处理最终一致性

识别信号：
- 命令端有 saga 编排器
- 读模型有 saga 状态展示
- 存在 saga 状态变更事件
```

## H.5 与架构归纳的接口

- L4 模式识别识别系统是否使用了 ES/CQRS/Saga
- L5 本质归纳判断这些模式是核心架构还是偶然架构
- 架构债务量化评估模式相关的债务
- 架构进化评估是否需要迁移到/移出这些模式

| **整洁架构** | 依赖方向如何控制 | 内层不依赖外层、依赖反转 | 依赖方向错误、跨界依赖 |
| **CQRS** | 读写如何分离 | 两个模型、两套API | 读写不一致、同步延迟 |
| **ES** | 状态如何存储 | 只insert事件、apply()方法 | 版本混乱、投影不一致 |
| **Saga** | 分布式事务如何处理 | 补偿逻辑、重试幂等 | 补偿缺失、补偿错误 |

## J.2 反先入为主验证树

**用途**：不是"找模式"，是"检测是否在套模式"。任何回答"是"都意味着可能存在先入为主。

```text
Q1: 结论是否以模式名开头？
   └─ 是 → **STOP**：先归纳结构，后命名模式。模式名是结论，不是起点。

Q2: 是否跳过了 L1-L3 直接到 L4？
   └─ 是 → **STOP**：必须先回答技术清单→结构关系→约束决策，才能到模式识别。

Q3: 模式是否能回答"为什么这个结构是这样"？
   └─ 否 → 该模式候选无效。模式必须解释因果，不是贴标签。

Q4: 模式是否与代码具体特征矛盾？
   └─ 是 → 该模式候选被否证。选择其他候选或承认"未识别模式"。

Q5: 是否只有一个模式候选？
   └─ 是 → 强制要求至少两个候选解释，或明确说明为何只有一个合理候选。

Q6: 模式候选能否推导该模式的典型失效？
   └─ 否 → 该模式候选缺乏解释力，不应作为结论。

通过 Q1-Q6 且未触发 STOP → 模式候选有效
触发 STOP 或任何"是"（除Q5外）→ 重新归纳，回到 L1
```

**运行时 Go/No-Go**：L4 模式识别必须通过本验证树才能算完成。J.1 速查表仅作参考，不是检查清单。

## J.3 模式适用性评估

| 评估维度 | 问题 | 评估标准 |
|---|---|---|
| 结构匹配度 | 代码结构是否满足模式的核心约束？ | 满足得3分，部分满足得1分，不满足得0分 |
| 问题匹配度 | 当前问题是否适合用该模式解决？ | 高度匹配得3分，中度得1分，不匹配得0分 |
| 团队能力 | 团队是否有能力实现和维护该模式？ | 有经验得3分，可学习得1分，缺乏得0分 |
| 迁移成本 | 从当前架构迁移到该模式需要多少成本？ | 低成本得3分，中等得1分，高成本得0分 |

**总分 ≥ 8**：推荐使用该模式
**总分 5-7**：谨慎评估后决定
**总分 < 5**：不推荐使用该模式

## J.4 禁先入为主套模式检查清单

在识别架构模式前，必须先完成以下检查：

```text
□ 是否先回答了"这个结构解决了什么问题"？
□ 模式候选是否解释了"为什么"而非仅仅"是什么"？
□ 模式候选是否能推导出代码中的具体特征？
□ 模式候选是否能识别出该模式的典型失效？
□ 是否允许"未识别模式"作为结论？
□ 是否有多个模式候选可供比较？
```

## J.5 与 16-方法论的接口

- 16-方法论 §1.3.0 禁先入为主套模式规则与本附录 J.2/J.4 一致
- L4 模式识别前，必须先通过 J.2 反先入为主验证树
- J.1 速查表仅作候选参考，不是检查清单
- J.3 评估方法用于多候选比较，不是准入门槛
- 模式识别结论必须包含典型失效模式检查（通过 J.4）

# 附录 I：架构反模式深度分析

> 本附录为架构归纳提供常见架构反模式的识别和评估框架。

## I.1 常见架构反模式

### I.1.1 意大利面条式架构（Spaghetti Architecture）

```text
定义：组件之间关系混乱，没有清晰的结构

识别特征：
- 模块之间相互依赖，形成复杂的依赖网络
- 没有清晰的层次划分
- 修改一个模块可能影响多个不相关的模块
- 代码难以理解和维护

诊断方法：
- 画出模块依赖图，观察是否有循环依赖
- 计算模块之间的耦合度
- 检查是否有跨层直接依赖

影响评估：
- 修改成本高
- Bug 难以定位
- 新功能难以加入
```

### I.1.2 上帝对象（God Object）

```text
定义：一个类或模块承担了太多职责

识别特征：
- 单个类代码行数超过 1000 行
- 单个类依赖大量其他类
- 单个类包含多种不相关的功能
- 修改该类时风险很高

诊断方法：
- 统计类的代码行数、方法数、依赖数
- 检查类是否符合单一职责原则
- 检查类的公开方法是否相关

影响评估：
- 代码难以理解
- 测试困难
- 复用困难
- 维护风险高
```

### I.1.3 循环依赖（Circular Dependency）

```text
定义：模块 A 依赖 B，B 依赖 C，C 又依赖 A

识别特征：
- 编译错误：类循环依赖
- 模块无法独立测试
- 修改一个模块影响多个模块
- 部署顺序敏感

诊断方法：
- 使用依赖分析工具检测循环
- 检查包/模块之间的 import
- 检查服务之间的调用关系

影响评估：
- 编译和构建复杂
- 测试困难
- 部署风险高
- 难以拆分
```

### I.1.4 银弹综合症（Silver Bullet Syndrome）

```text
定义：过度依赖某种技术或方法来解决所有问题

常见表现：
- 引入微服务解决所有问题，但实际不需要
- 过度使用设计模式
- 过度抽象，导致复杂度爆炸
- 盲目追求新技术

识别特征：
- 新技术引入后问题没有解决
- 团队对新技术过度热情
- 存在”技术债务是因为没用 X”的观点
- 解决方案比问题更复杂

影响评估：
- 技术债务没有减少，反而增加
- 团队学习成本高
- 维护复杂度增加
```

### I.1.5 提前优化（Premature Optimization）

```text
定义：在没有证据的情况下进行性能优化

识别特征：
- 存在大量”可能需要”的优化代码
- 优化代码比正常代码更复杂
- 优化代码难以理解和维护
- 没有性能问题就做了优化

诊断方法：
- 是否有性能基准测试？
- 优化是否有量化依据？
- 优化代码是否比原来更复杂？

影响评估：
- 增加代码复杂度
- 可能引入 bug
- 维护成本增加
```

### I.1.6 供应商锁定（Vendor Lock-in）

```text
定义：过度依赖某个供应商的技术或服务

识别特征：
- 业务逻辑与供应商 API 紧密耦合
- 大量使用供应商特定功能
- 没有抽象层或适配器
- 迁移到其他供应商成本极高

诊断方法：
- 如果供应商服务不可用，系统能否工作？
- 替换供应商需要多少改动？
- 是否存在抽象层？

影响评估：
- 议价能力降低
- 供应商风险无法控制
- 技术演进受限
```

## I.2 架构反模式评估框架

| 反模式 | 识别难度 | 修复成本 | 业务影响 | 优先级 |
|---|---|---|---|---|
| 意大利面条 | 中 | 高 | 高 | 高 |
| 上帝对象 | 低 | 中 | 中 | 中 |
| 循环依赖 | 低 | 高 | 高 | 高 |
| 银弹综合症 | 中 | 低 | 中 | 中 |
| 提前优化 | 低 | 低 | 低 | 低 |
| 供应商锁定 | 中 | 高 | 中 | 中 |

## I.3 与架构归纳的接口

- L4 模式识别识别系统中的反模式
- L5 本质归纳判断反模式是核心问题还是次要问题
- 架构债务量化评估反模式的修复优先级
- 架构进化规划反模式的修复路径

# 附录 A：架构归纳五层次

> 本附录将架构归纳纳入 L0 框架，明确架构归纳的层次结构和完成标准。

## A.1 架构归纳的定义

架构归纳是从复杂、混乱的代码和系统中识别核心架构模式、约束决策和本质结构的过程。

与业务归纳的关系：

- **业务归纳**回答：”系统支持什么业务？业务本质是什么？”
- **架构归纳**回答：”系统如何实现这些业务？架构约束是什么？本质架构是什么？”

两者必须结合：业务归纳的输出（ESS/BIZ）是架构归纳的输入；架构归纳的输出（架构本质/约束）是系统设计的约束。

## A.2 架构归纳的五个层次

| 层次 | 问什么问题 | 产出什么 | 类比业务归纳 |
|---|---|---|---|
| L1 技术清单 | 系统用了什么技术组件？ | 技术组件清单、版本、依赖关系 | L1 事实 |
| L2 结构关系 | 技术组件之间是什么关系？ | 架构图、模块边界、数据流 | L2 结构 |
| L3 约束决策 | 什么约束或决策导致了这个结构？ | 约束列表、设计决策记录、权衡分析 | L2 结构 |
| L4 模式与反模式 | 这个结构反映了什么架构模式？ | 模式名称、反模式识别、设计意图 | L3 判断 |
| L5 本质与偶然 | 什么是核心架构？什么是偶然架构？ | 架构不变量、可演进部分、迁移路径 | L3 判断 |

**强制要求**：L5 是架构归纳的终点。只停在 L1-L4 是分析，不是归纳。

## A.3 架构归纳的约束分类

与业务归纳的四对象分型对应，架构归纳也要区分约束类型：

| 架构约束类型 | 定义 | 默认动作 | 类比业务分型 |
|---|---|---|---|
| 架构不变量 | 改变后系统无法保持同一性的约束 | 保护 | 业务不变式 |
| 架构有意设计 | 有代价意识的历史架构决策 | 保留，直到触发条件出现 | 有意设计 |
| 架构技术债 | 为了速度或兼容性接受的架构权衡 | 评估修复成本和收益 | 可靠性缺陷 |
| 架构偶然选择 | 可以无代价改变的架构选择 | 标记为可演进 | 错误抽象 |

## A.4 架构归纳的信号

在分析代码时，以下信号指示需要深入架构归纳：

```text
1. 重复模式
   - 多个模块有相似的代码结构
   - 多个地方有相似的错误处理模式

2. 约束痕迹
   - 代码中有明显的”不得已”的设计
   - 有 hack、workaround 或临时方案

3. 决策印记
   - 有明显的”当时选择 A 而非 B”的痕迹
   - 有 TODO、FIXME、DEPRECATED 注释

4. 边界异常
   - 模块边界与业务边界不一致
   - 跨模块的隐式依赖

5. 演化层叠
   - 代码中有多个时间层的叠加
   - 有”新酒装旧瓶”或”旧瓶装新酒”的情况
```

## A.5 架构归纳的操作框架

```text
技术清单（L1）
  ↓
结构关系（L2）
  ↓
约束决策（L3）
  ↓
模式识别（L4）
  ↓
本质归纳（L5）
  ↓
架构骨架（类比业务骨架）
  - 架构核心对象（核心组件、核心数据）
  - 架构关键关系（组件间依赖、数据流）
  - 架构不变量（一致性、事务、安全边界）
  - 架构边界（部署边界、一致性边界）
  - 架构能力（系统对外提供的能力）
  - 架构演化轴（架构变更的高频方向）
  - 架构分型（保护/修复/演进/重绘）
```

## A.6 架构归纳完成标准

架构归纳必须通过以下门禁：

| 门禁 | 要求 | 修正说明 |
|---|---|---|
| G1 完整性 | 必须完成 L1-L5 所有层次 | - |
| G2 约束分类 | 必须将约束分为不变量/有意设计/技术债/偶然选择 | - |
| G3 模式识别 | **尝试识别候选模式，允许"未识别模式"作为结论** | 原"必须识别至少一种"过于刚性 |
| G4 本质回指 | **L5 核心架构必须回指业务机制与一致性边界** | 运行时 Go/No-Go：不是模式名字，是业务约束 |
| G5 可决策 | 归纳结论必须能支撑架构演进决策 | - |
| G6 证据追溯 | 归纳结论必须可追溯到代码证据 | - |

# 附录 B：架构想象力

> 本附录定义架构想象力的能力维度，并提供训练方法。

## B.1 架构想象力的定义

架构想象力不是”想到更多技术方案”，而是：

1. **可能性识别**：识别当前架构之外的可能性
2. **约束理解**：理解为什么当前架构是现在这个样子
3. **演进预演**：预演架构随需求和技术演进的路径
4. **权衡评估**：评估不同架构选择的权衡

## B.2 架构想象力的四个维度

| 维度 | 核心问题 | 训练方法 |
|---|---|---|
| 可能性识别 | 当前架构之外还有什么可能？ | 架构重构想象、架构模式组合 |
| 约束理解 | 什么约束导致了当前架构？ | 决策考古、架构历史想象 |
| 演进预演 | 架构如何随时间演进？ | 架构极端假设、架构进化路径 |
| 权衡评估 | 不同选择有什么权衡？ | 权衡矩阵、成本收益分析 |

## B.3 架构想象力训练方法

### B.3.1 架构重构想象

**问题**：如果今天重新设计这个系统，没有任何约束，会怎么设计？

**操作**：

```text
1. 从零开始想象
   - 用什么架构模式？
   - 如何划分模块？
   - 如何处理数据？

2. 对比当前架构
   - 主要差异是什么？
   - 什么约束导致了这些差异？

3. 设计演进路径
   - 如何从当前演进到理想？
   - 每步的风险和收益？
```

### B.3.2 架构极端假设

**问题**：挑战当前架构的假设，探索极限情况。

**操作**：

```text
10x 假设：
- 如果规模是现在的 10 倍，架构会怎么变化？
- 如果用户数是现在的 10 倍呢？

归零假设：
- 如果某个关键组件消失，架构会怎样？
- 如果数据库不可用了呢？

反转假设：
- 如果原来是集中的，变成去中心化会怎样？
- 如果原来是同步的，变成异步会怎样？
```

### B.3.3 架构模式组合

**问题**：如何结合多个架构模式的优点？

**操作**：

```text
1. 列出相关架构模式
2. 识别每个模式的优势
3. 尝试组合
4. 设计边界
```

### B.3.4 架构历史想象

**问题**：架构为什么是现在这个样子？

**操作**：

```text
1. 重建架构时间线
   - 系统最初是什么样的？
   - 每次重大变更是什么？
   - 变更的动机是什么？

2. 理解演化压力
   - 什么需求推动了架构演进？
   - 什么技术变化影响了架构？

3. 预演未来
   - 未来会有什么变化压力？
   - 当前架构如何应对？
```

## B.4 架构想象力评估

| 维度 | 问题 | 评估标准 |
|---|---|---|
| 可能性识别 | 是否识别了当前架构之外的可能性？ | 识别多种可能性得高分 |
| 约束理解 | 是否理解了导致当前架构的约束？ | 能解释约束来源得高分 |
| 权衡评估 | 是否评估了不同架构选择的权衡？ | 权衡分析平衡得高分 |
| 演进路径 | 是否设计了可行的演进路径？ | 演进路径具体可行得高分 |
| 风险识别 | 是否识别了架构变更的风险？ | 风险识别全面得高分 |

# 附录 C：架构进化

> 本附录定义架构进化的类型、触发信号和路径选择。

## C.1 架构进化的定义

架构进化是架构随时间和需求变化的过程。架构进化不是随意的变更，而是有方向、有约束的演进。

## C.2 架构进化的三种类型

| 类型 | 定义 | 风险 | 成本 | 适用条件 |
|---|---|---|---|---|
| **增强型进化** | 在现有架构上增加新能力，保持核心架构不变 | 低 | 低 | 现有架构能满足大部分需求 |
| **适应型进化** | 调整架构以适应新的需求，部分改变核心架构 | 中 | 中 | 架构需要调整但核心有效 |
| **转型型进化** | 根本性地改变架构模式，改变核心约束 | 高 | 高 | 架构根本性不匹配需求 |

**类型判断**：与路径 A/B 的关系

- 增强型进化 ≈ 路径 A（核心抽象内进化）
- 适应型进化 ≈ 路径 A→B 的过渡
- 转型型进化 ≈ 路径 B（设计评估与重构）

## C.3 架构进化触发信号

### 功能信号

```text
- 新功能难以加入
- 功能需要跨多个模块修改
- 边界情况处理复杂
```

### 性能信号

```text
- 性能目标无法达成
- 扩展性受限
- 资源消耗异常
```

### 质量信号

```text
- Bug 难以定位和修复
- 测试覆盖率低
- 代码理解成本高
```

### 维护信号

```text
- 部署复杂度高
- 依赖管理困难
- 技术债累积
```

### 业务信号

```text
- 业务需求变化频繁
- 新业务难以接入
- 业务实验成本高
```

## C.4 架构进化路径

### 渐进式演进（Strangler Fig Pattern）

适用于需要改变核心架构，但不能一次性重构的场景。

```text
阶段 1：隔离
- 识别需要变更的核心组件
- 将其与周边隔离
- 建立清晰的边界

阶段 2：新建
- 在隔离区域新建目标架构
- 保持与旧架构的兼容
- 逐步迁移功能

阶段 3：切换
- 逐步将流量切换到新架构
- 保持旧架构作为回退
- 监控和验证

阶段 4：退役
- 旧架构流量降为 0
- 清理旧代码
```

### 特性开关演进（Feature Toggle Evolution）

适用于需要同时维护新旧架构，进行 A/B 测试的场景。

```text
1. 设计开关
   - 定义开关的维度（用户、租户、时间、百分比）
   - 确保开关可以细粒度控制

2. 并行运行
   - 新旧架构同时运行
   - 验证结果一致性
   - 收集性能数据

3. 渐进切换
   - 从小比例开始切换
   - 逐步扩大范围
   - 保持可回退能力

4. 清理
   - 删除旧代码路径
   - 删除开关
```

### 领域拆分演进（Domain Split Evolution）

适用于单体架构需要拆分为服务架构的场景。

```text
1. 领域建模
   - 识别核心领域
   - 定义领域边界
   - 识别领域依赖

2. 识别粘合剂
   - 跨领域的数据依赖
   - 跨领域的事务需求
   - 跨领域的查询需求

3. 渐进拆分
   - 从低依赖领域开始
   - 建立领域间契约
   - 迁移数据和逻辑

4. 处理粘合剂
   - 异步化强耦合
   - 引入事件机制
   - 接受最终一致
```

## C.5 架构进化决策矩阵

| 进化类型 | 触发信号数 | 风险承受度 | 成本承受度 | 推荐路径 |
|---|---|---|---|---|
| 增强型 | 1-2 | 低 | 低 | 局部优化 |
| 适应型 | 3-4 | 中 | 中 | 渐进演进 |
| 转型型 | ≥5 | 高 | 高 | 特性开关或渐进拆分 |

## C.6 架构进化质量门禁

| 门禁 | 要求 |
|---|---|
| G1 渐进性 | 必须提供渐进式演进路径 |
| G2 可回退 | 必须保证可回退能力 |
| G3 风险评估 | 必须评估每步风险 |
| G4 验证计划 | 必须有验证方案 |
| G5 影响评估 | 必须评估对现有功能的影响 |
