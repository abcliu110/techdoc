## §0 公理：本文推理的起点

以下公理是业务系统分析的**不可动摇的约束**，后续所有概念、程序、验收标准都从这里导出。

1. **主文档终点**：无合格理解层主文档，则分析未完成。
2. **事实先于维度**：无事件轨迹，不得建立稳定领域模型结论。
3. **切片是分析单位**：类、表、接口、菜单、目录默认不是分析单位。
4. **叙事可去技术名**：删除类名、方法名、表名、接口名后不成立，则未完成业务理解。
5. **证据有类型局限**：单类证据不得支撑高影响结论。
6. **结论级别不可跃迁**：假设不得写成根因；推断不得写成已证实规律。
7. **深度靠配额**：全覆盖且平均浅，等于失败。
8. **缺口必须显式**：未覆盖写成已覆盖，属于过程造假。
9. **竞争解释必须可淘汰**：对核心切片，至少保留主解释与一个可被证据淘汰的替代解释（强度为中/强），或明确登记 U-*；纯推测（无机制描述）不计入反例关。
10. **认知不自动授权变更**：除非任务模式升级，分析结论不自动变成实施指令。
11. **间接路径必须闭合**：声称 A 与 B 间接关联时，必须还原全部有效中间对象与路径，不得压缩成无语义的直连。
12. **图是认知产物**：影响核心理解的复杂关系图与活动图是主文档组成部分，不是附件装饰。

## §1 分析问题类型：先定问题，再定模型

### 1.1 五类问题

不同类型的分析问题，主对象、主证据与"完成"定义不同。未声明问题类型，不得开始深挖。

| 类型 | 典型意图 | 主对象 | 主证据偏向 | 主文档完成定义 |
|---|---|---|---|---|
| 认知重建 | 接手、讲解、建立共同语言 | 切片因果、规则、失败 | 源码/配置/契约 + 必要运行 | SC-P0 过深度八关，可独立讲述 |
| 故障定位 | 解释异常、缩小根因 | 失败轨迹、假设集 | 运行证据优先，源码次之 | 根因候选可证伪，排除项有据 |
| 迁移/重构决策 | 替换、归一、兼容 | 契约、多实现、变更影响 | 多类互证 | 差异可裁决，风险可排序 |
| 设计合理性评审 | 评现状或评方案 | 目标约束 + 已有事实模型 | 已验证事实卡，而非感想 | 条件化结论，红线与权衡分开 |
| 数据治理/语义对齐 | 口径、血缘、约束 | 维度语义、约束、分布 | Schema + 样本 + 写入路径 | 业务语义与存储语义对齐或显式裂隙 |

**规则**：一次任务只允许一个主类型；若中途发现应升级类型，必须显式记录变更原因，不得静默漂移。

### 1.2 证据可得性建模

每个任务类型在启动时声明其**预期证据集**与**最小证据集**；实际证据集低于最小证据集时，按"缺失推进"规则执行，不停止、不伪造：

| 类型 | 预期证据集 | 最小证据集 | 缺失时的推进规则 |
|---|---|---|---|
| 认知重建 | SRC+CFG+CON+DAT+RUN | SRC（或 DAT） | 按 §4.2 R7 受限定级；无运行证据时"实际发生"类结论禁止，登记 U-* |
| 故障定位 | RUN 优先 + SRC | RUN 或 SRC 之一 | 只有 SRC：假设集可缩小但不得宣布根因（公理 6）；必须运行验证后升结论 |
| 迁移/重构决策 | SRC+CON+DAT 多类互证 | SRC+CON 或 SRC+DAT | 单类证据时结论降为"推断"，不得支持高影响决定 |
| 设计合理性评审 | 已验证事实卡 | 事实模型（任意类型） | 事实模型未建立时只输出"待验证假设"，不评设计 |
| 数据治理/语义对齐 | DAT+SRC | DAT 或 SRC 之一 | 语义对齐问题分两类：①**计算影响型**——口径差异直接影响业务计算结果（如金额/库存/配额），此类必须登记 U-* 并优先验证；②**展示型**——口径差异仅影响展示/报表，不影响核心计算，此类可降级为推断或登记 U-* 备注；两类区分标准：改动口径定义是否导致已确认的业务数值变化 |

**禁止**：实际证据集低于最小证据集时仍宣布完成（属于公理 8 缺口隐藏）；也不得因证据不足而放弃分析（推进规则保证合法路径存在）。

---

**类型漂移检测**：任务执行中若出现以下信号，必须显式记录类型是否需要升级，不得静默漂移：
- 认知重建中途发现关键缺陷或安全风险 → 触发设计合理性评审类型
- 迁移决策中发现历史行为与文档严重不符 → 降级为故障定位或认知重建
- 任何类型变更须记录原因、旧类型、新类型和决策人

## §2 最小概念集：业务分析需要哪些最小对象

### 2.0 业务内容三元：为什么需要三层

本节回答：在"对已有业务系统做可验证理解"这件事上，**最少需要几个内容层**才能回答完整的业务问题。

三层常见写法是"事件 + 实体"。它能描述发生与参与者，但**无法稳定安放约束**：

| 只保留两层时 | 规则被塞去哪里 | 失败模式 |
|---|---|---|
| 规则并进事件 | "提交订单"与"金额必须 ≥ 0"混为一谈 | 把约束误当成又一次发生 |
| 规则并进实体 | "订单必须有明细"变成订单的静态属性 | 属性与义务不分，变更影响说不清 |
| 规则不建模 | 只讲流程与对象 | 主文档缺"必须/不得"，深度八关的规则关必然失败 |

因此：在"发生了什么 / 关于谁与什么 / 必须怎样"三问上，**第三层不可消掉**。不是因为"三"这个数字神圣，而是因为业务理解至少要同时回答：

1. **发生**（动态变化）
2. **指称**（稳定可指的参与者与资源）
3. **约束**（许可、禁止、口径、不变量）

缺任一问，主文档都无法独立支撑接手、排障或迁移判断。

#### 为什么不是四个

四层常见加法是"事件 + 实体 + 规则 + 目标/意图/价值"。**不把目标升为第四业务内容层**，理由：

| 候选第四层 | L1 安放位置 | 原因 |
|---|---|---|
| 目标 / 价值 / 意图 | **分析问题（DQ）**与主文档 §6.1 价值关 | 目标首先是"本次分析要解释/服务什么"，属于任务与评价，不是系统内与事实同级的存在物 |
| 指标 / KPI | 规则中的计算口径，或结论中的观察断言 | 指标是度量规则或运行观察，不是独立本体层 |
| 界面 / 交互 | 事实的触发方式，或实现锚点 | 交互是进入事实轨迹的入口，不是第四内容层 |
| 数据模型 / 表 | 维度与关系的存储投影 | 属于实现锚点，不得反客为主 |

#### 完备性主张

| 主张 | L1 是否主张 | 含义 |
|---|---|---|
| **分析完备（弱）** | 是 | 对任一进入主文档的业务说法，应能归入三元之一，或标为关系/未知/实现锚点；不得长期以"说不清类别"的概念支撑高影响结论 |
| **世界完备（强）** | **否** | 不声称现实中一切商业与组织现象只有这三类 |

遇到暂时无法归类的概念，正确动作是登记 `U-*` 或降为实现细节，而不是硬贴标签，也不是立刻发明第五层。

#### 三层正交性

| 测试 | 问法 | 结果 |
|---|---|---|
| 消去测试 | 删去该层后，主文档是否仍能回答对应业务问 | 删事实→不知发生；删维度→不知对谁；删规则→不知可否 |
| 变换测试 | 固定另外两层，只改该层，业务含义是否明显变化 | 只改规则（如是否允许负库存）可改系统合法性，故规则独立 |
| 证据测试 | 该层主要靠什么被观察 | 事实偏轨迹/日志；维度偏主数据/配置；规则偏分支、校验、口径与不变量陈述 |

#### 边界判定程序

同一句话里常混有三元。分析时**拆句归类**，不整句单贴一个标签。

**步骤 1：先找变化**
若描述的是"从一状态到另一状态 / 一次发生 / 一次结果"，核心是**事实**。

**步骤 2：再找可跨事实指称者**
若名词在多个事实中重复出现、可被指认、可配置或可持久，核心是**维度**。

**步骤 3：最后找义务与口径**
若去掉情态与约束词（必须、不得、仅当、按…计算）句子不再成立，核心是**规则**。

**仍双属时，用主问题裁决**：

| 双属现象 | 默认归属 | 说明 |
|---|---|---|
| "状态"既像事实又像维度 | 状态**值的变化**→事实；状态**机定义/枚举集合**→维度或规则依附 | 一次"已审批"是事实；"审批状态可取值"是维度属性或规则约束的对象 |
| "配置"既像维度又像规则 | 配置**项本身**→维度；配置**被解释成必须怎样**→规则 | "折扣策略 A"是维度；"策略 A 下满 100 减 20"是规则 |
| "创建订单"既是事实又含规则 | 创建这一发生→事实；创建前置条件→规则 | 事实回答发生与否；规则回答可否发生 |
| "金额" | 某单金额数值的产生/变更→事实或事实结果；计价口径→规则；金额字段作为对象属性→维度属性 | 拆成"值的变化 / 口径 / 属性" |
| "权限" | 授权关系与角色→维度；"仅经理可驳回"→规则；"驳回已发生"→事实 | 三角拆开写 |

**边界判定示例**：

> "订单金额 = 商品单价 × 数量 - 优惠券金额"

- **步骤1（找变化）** → "订单金额从A变为B" → **事实**候选
- **步骤2（找指称者）** → "订单""商品""优惠券"在多次交易中重复出现 → **维度**候选
- **步骤3（找义务/口径）** → "金额 = 单价 × 数量 - 优惠券" → 计算口径 → **规则**；"订单金额 ≥ 0" → 完整性约束 → **规则**；"优惠券只能使用一次" → 不变量 → **规则**
- **双属处理**：同一"金额" → "金额变化"→事实；"计价口径"→规则；"金额作为订单属性"→维度

**禁止**：因为某个词在代码里是一个类/一张表，就把整类概念永久钉死在单一层。

#### 边界自检

| 表述 | 错误归类 | 正确拆分 |
|---|---|---|
| 订单必须有至少一行明细 | 事实 | 规则（完整性）+ 维度（订单、明细行） |
| 库存从 10 变为 8 | 规则 | 事实（数量变化）+ 维度（SKU/仓） |
| 客户等级为金卡 | 事实 | 维度属性；若"因升级而变为金卡"则另有升级事实 |
| 超时自动取消 | 纯维度 | 规则（时序/触发）+ 取消事实（若已发生或可发生） |
| 表 order 有字段 status | 业务事实 | 实现锚点；业务上仍要还原为状态事实或维度属性 |

### 2.1 八对象定义

只保留八个核心对象。更多标签若不能还原到这八类，不得进入 L1 强制层。

八对象按角色分为两组：

| 组 | 成员 | 角色 |
|---|---|---|
| **业务内容三元** | 事实、维度、规则 | 被分析的业务世界里"有什么内容" |
| **分析装置** | 分析问题、切片、关系、证据、结论 | 分析者用来组织、连接、证明内容的工具 |

**切片（SC）**是一次有界讲述中，三元内容的组合单元。公式：

```text
SC ≈ 选定边界内的（事实轨迹 × 参与维度 × 生效规则）
     + 必要关系说明
     + 证据与定级结论
```

下表给出每个对象的识别要点：

| 对象 | 符号 | 一句话 |
|---|---|---|
| 分析问题 | DQ / 问题类型 | 本次要回答什么、完成线在哪 |
| 业务切片 | SC | 有边界的业务场景单元 |
| 事实 | Fact（事件/动作/状态变化） | 发生了什么 |
| 维度 | Dim（参与者、对象、配置、资源） | 谁/什么在场景中扮演稳定角色 |
| 规则 | Rule / INV | 必须满足什么、什么不变 |
| 关系 | Rel（结构/轨迹/归因） | 内容之间的连接方式（归属、先后、归因） |
| 证据 | E-* | 观察依据及其局限 |
| 结论 | Claim | 带级别与范围的断言 |

### 2.2 业务切片（SC）

**定义**：在明确触发、参与角色、业务结果与边界条件的情况下，可被单独讲述的业务场景单元。

**是切片**：有可叙述的触发与结果（"当…则…"）；能指出成功与失败的业务含义；可以独立作为分析与验证单位。

**不是切片**：单个菜单项/按钮文案；单个类/表/API；"整个模块""全部功能列表"。

**识别问句**：
1. 谁在什么业务意图下启动？
2. 业务上成功长什么样？
3. 失败时经营侧看到什么？
4. 边界外哪些相关事故意不纳入本次 SC？

**否证**：若只能列出页面或接口名称，无法叙述触发到结果，则它不是 SC，只是入口线索。

**有效切片判定标准**：候选切片 X 是有效 SC，当且仅当同时满足：

```
□ 能用"当[触发]，则[结果]"句式完整描述
□ 能区分成功与失败的业务含义（各至少一条）
□ 能说出本切片与相邻切片的边界（共享什么/不共享什么）
□ 不属于"只有类名/表名/菜单名"（公理3）
```

若以上任一为"否"：
- 若只有名称但能补全四问 → 可作为 SC 入口线索，深入后升级
- 若始终无法回答 → 降为实现锚点，登记 U-*

**切片卡必填字段（SC-P0/P1 强制）**：

| 字段 | 内容 |
|---|---|
| 业务层 | 平台层 / 业务层 / 渠道层（平台型系统必须标注；单一业务系统可填"业务层"） |
| 共享资产声明 | 本切片依赖的共享维度/规则/证据（多人并行分析时明确负责切片，共享资产单独声明负责人） |
| 触发/结果/成功/失败 | 对应识别问句四项 |
| 边界外声明 | 明确不纳入本切片的相关事实 |

**共享资产规则**：切片之间共享的维度、规则、不变量、权威数据源，由首次引用它的切片声明并登记；并行分析时共享资产由指定负责人维护，其他切片只引用不重复定义。**禁止**：每个切片各自复制一份共享维度定义。

### 2.3 事实（Fact）

**定义**：业务上可观察的事件、动作或状态变化，回答"发生了什么"。

**是事实**：单据已提交/作废；额度已预占/释放；审批已通过/驳回；任务已创建/完成/超时；款项已收取/退回。

**不是事实**：实体静态属性（多属维度）；纯技术步骤（除非本身是业务承诺，否则只作实现锚点）。

**业务承诺判定**（区分"纯技术步骤"与"业务承诺"）：对任何一个疑似事实的表述，依次问：
1. 去掉技术词后，是否仍是**外部可观察的行为**？
2. 是否**影响角色决策**？
3. 是否产生**业务后果**（钱/货/状态/合规）？

任一为"是" → 业务承诺，可作事实；全否 → 纯技术步骤，只作实现锚点。

**识别问句**：用动词与结果问，不用"有哪些东西"问。

| 问法 | 通常得到 |
|---|---|
| 发生了什么？产生了什么结果？ | 事实 |
| 谁做的？对什么做的？依据什么配置？ | 维度 |
| 是否允许？失败是否必须补偿？ | 规则 |

**否证**：去掉所有程序符号后，若不再存在可被业务理解的变化，则原表述只是实现转述。

**候选事实（反向分析）**：在只有实现痕迹可观察时，事实是从痕迹推断出的**候选事实**——定级为"推断"，必须经验证升级后才能进入主文档事实层。**禁止**把实现痕迹直接写成事实（公理 6 + 公理 8）。

### 2.4 维度（Dim）

**定义**：在多个事实中重复出现、可被指称的业务实体、角色、资源或配置对象。

**关键约束**：维度从事实中派生，**不能**在零事实时先验"领域模型完成"。

**是维度**：客户、组织节点、账期、价目、仓库、审批角色、通道、模板、策略配置等。

**不是维度**：一次请求的临时局部变量、仅实现细节的传输对象字段堆。

**否证**：若某概念从未出现在任何 SC 的事实轨迹中，不得写入主文档核心概念层。

### 2.5 规则（Rule / INV）

**定义**：对事实与维度施加的约束、许可、计算口径或不变量。

**类型（通用，不强制用完）**：许可；完整性；计算；时序；不变量 INV。

**否证**：只描述"代码里分支很多"，给不出业务必须/不得，则尚未抽出规则。

### 2.6 对象最小可验证形态（P0 强制）

八对象的自由文本不足以支撑验收。对 **SC-P0** 的核心对象，强制以下最小形态：

| 对象 | 最小可验证形态 | 可检查什么 |
|---|---|---|
| 规则 BR | 前提-动作-后置三元组（When…Then…Ensure…） | 与代码分支/校验一一对应 |
| 不变量 INV | 可检查断言（数据库约束/代码校验/测试用例之一） | 断言是否真实存在且生效 |
| 状态机 SM | 状态集合 + 合法迁移表 + 非法迁移清单 | 非法迁移是否被代码阻止；注：SM 是时序规则的具体实现形态，归入规则类型的时序子类型 |
| 关系 Rel | 六要素卡（类型/方向/基数/建立时机/变更影响/业务语义） | 六要素是否都有证据 |
| 事实 Fact | 候选事实卡（痕迹位置/推断链/置信度）或观察记录 | 是否能回溯到痕迹或观察 |
| 维度 Dim | 可回溯声明（回溯到哪个候选事实） | 维度是否违反"从事实派生"约束 |
| 结论 Claim | 级别 + 证据 ID + 反证/未知（见 §5） | 级别是否与证据匹配 |

**作用**：验收从"人读判断"升级为"结构可查"；无法给出最小形态的对象，该切片不得判定深写完成。

## §3 关系理论：对象之间如何连接

L1 只承认三类关系。更多细分是派生技法，不得上升为强制分类。

### 3.1 三类关系

| 类型 | 含义 | 主要出现在 | 典型问句 |
|---|---|---|---|
| **结构关系** | 归属、拥有、层级、配置引用、多值关联 | 维度↔维度 | A 是否拥有/包含/引用 B？生命周期是否绑定？ |
| **轨迹关系** | 触发、先后、分支、补偿、重做 | 事实↔事实 | A 是否导致/先于/补偿 B？是否同一业务主体上的序列？ |
| **归因链接** | 事实实例指向其执行所用的维度/配置 | 事实→维度 | 这次发生是否落在某配置、通道、策略上？ |

不能归入三类时：**登记未知**，禁止硬贴标签。

### 3.2 判定顺序

```text
1. 两端首先是事实还是维度？
2. 若两端皆事实 → 只尝试轨迹关系
3. 若两端皆维度 → 只尝试结构关系
4. 若事实指向维度/配置 → 归因链接
5. 仍不成立 → U-（未知）或"弱相关，不建模"
```

### 3.3 关系最小字段

| 字段 | 内容 |
|---|---|
| 类型 | 结构 / 轨迹 / 归因 |
| 方向与基数 | 谁指向谁，1/N |
| 建立时机 | 设计时 / 初始化 / 配置维护 / 交易执行 |
| 变更影响 | 热生效 / 不追溯历史 / 需处理在途或历史 / 禁止 |
| 业务语义 | 一句不含技术词的说明 |

### 3.4 核心四问 vs 条件四问

SC-P0 关键关系必答：是什么；何时建立/变更；如何被找到；变更影响历史还是未来。

条件四问（级联、约束、全部使用方、存储细节）仅在删除、迁移、数量承诺、多实现冲突等触发时展开。

### 3.5 间接关系路径闭合

如果结论声称对象 A 与对象 B 存在间接引用，不得把真实路径压缩成无语义的 `A → B`。必须还原完整有效路径。

**中间对象纳入判据**（三问，任一"是"则必须纳入路径节点）：
1. 删除该对象后，A 是否仍能以相同条件、相同语义找到 B？
2. 删除后，最终业务结果、适用范围或历史解释是否变化？
3. 该对象是否承担桥接、路由、资格判断、规则解释、版本选择或权威映射职责？

不改变业务语义的纯实现细节，不进入读者关系主图。

**多路径时**：必须列出所有已知有效路径及其适用条件、优先级，不得只选最容易解释的一条。动态路由/配置/反射使路径无法穷尽时，区分"已发现路径"与"尚未排除路径"，登记 `U-*`。

**路径未闭合时**：不得对 A 与 B 的完整基数、级联行为、权威性和变更影响作确定性结论。

### 3.6 非事实表与复杂结构关系

**非事实表**：不直接记录核心业务事件，但承载主数据、配置、规则、字典、关联、路由、快照、版本或运行控制的存储结构。它不是新的业务本体，而是维度、规则、结构关系或控制机制在存储层的投影。

**识别与处理原则**：
1. 不根据表名直接推断业务语义；
2. 先说明它解释、约束或连接了哪些业务事实；
3. 再判断它属于主数据、配置、规则、字典、桥接、快照、版本还是运行控制；
4. 影响核心业务活动的非事实表必须进入理解层关系展示；
5. 间接引用必须遵守 §3.5 路径闭合；
6. 星型、雪花型、SCD 等数仓术语仅在数据仓库、历史口径或迁移任务触发时使用，不得作为通用强制本体。

## §4 分析程序：如何建立认知

### 4.1 正向认知顺序（主文档组织顺序）

```text
1. 声明分析问题类型与完成线
2. 识别切片候选，并做深度分级与配额
3. 对 SC-P0（及必要的 SC-P1）提取事实轨迹
4. 从事实派生维度
5. 抽出规则与不变量
6. 标定关系（结构 / 轨迹 / 归因）
7. 挂接证据，定级结论；登记竞争解释与未知
8. 仅在需要追溯时补实现锚点
9. 收敛为主文档
```

**禁止逆序**：先全量结构模型后补业务故事；先优化建议后补事实；先全量清单后发现没有切片。

**顺序的性质**：§4.1 是**产物组织顺序**（主文档的叙事/论证顺序），不是取证顺序。既有系统分析的取证路径是从实现痕迹出发的反向路径，按 §4.2 执行。产物按 §4.1 组织，取证按 §4.2 执行，二者不冲突。

### 4.2 反向分析操作程序（R1-R7）

**适用场景**：既有系统认知重建、迁移/重构决策中的事实建模——分析者面对代码、配置、Schema、运行日志，业务语义需要重构而非观察。

**核心立场**：反向分析不改变八对象与三类关系，只改变**对象如何被发现与验证**：反向路径中产生的所有"事实/维度/规则/关系"都是**候选**，必须经验证升级后才能进入主文档。

**实现痕迹（代码/配置/Schema/日志）是反向分析的线索源，不是终点锚点。**

#### R1 实现痕迹盘点

从可观察入口出发盘点痕迹，输出**候选线索清单**：
- 入口痕迹：Controller/消息监听/定时任务/Shell/脚本/报表入口
- 数据痕迹：核心表/字段/枚举/Schema 约束/数据分布
- 配置痕迹：配置项/开关/路由/外部依赖配置
- 运行痕迹（如有）：日志/指标/Trace/失败记录

**禁止**：把痕迹清单写成业务结论；痕迹清单是候选线索，不是主文档内容。

#### R2 候选事实生成

从**写痕迹**反推候选事实：

| 痕迹模式 | 候选事实 | 示例 |
|---|---|---|
| 写入口（insert/update/状态变更） | "某业务对象被创建/修改" | 业务任务创建 |
| 状态流转代码 | "某状态发生迁移" | 待处理→处理中 |
| 消息发送/订阅 | "某事件被发布/消费" | 点菜事件发布 |
| 定时任务执行 | "某周期业务被触发" | 交班汇总生成 |
| 外部副作用（HTTP/文件/命令） | "某外部动作发生" | 向外部系统发送指令 |

每个候选事实必须标注：痕迹位置（E-SRC）、推断链、当前置信度（推断）。

#### R3 候选事实验证与升级/降级

| 条件 | 升级/降级 |
|---|---|
| 两类独立痕迹互证（如源码 + Schema + 配置，生成链不共享环节） | 升级为**交叉验证结论**，可进入主文档事实层 |
| 单一源码痕迹且语义明确（写入口 + 无歧义业务含义，无须推断） | 升级为**直接事实**（限定在声明范围内） |
| 只有单一源码痕迹但语义需要推断 | 保持**推断**，不得进入事实层 |
| 与运行/数据/人员证据矛盾 | 降级或登记 X-* |
| 无法验证 | 登记 U-*，不得写入事实层 |

"直接事实"与"交叉验证结论"的区别：前者只有一类痕迹但语义无歧义，后者有两类以上独立痕迹。两者都不得冒充"实际发生过"——无运行证据时，结论必须限定在"系统具备该能力"的范围内。

#### R4 维度候选派生

从候选事实中的名词（参与者/对象/配置/资源）提取**维度候选**。维度候选必须回溯到至少一个候选事实；未出现在任何候选事实中的代码实体 → 实现锚点或未知，不得进入维度层。

#### R5 规则候选与关系候选

- 规则候选：从分支/校验/断言/状态机/配置口径代码提取"可能存在的业务规则"，标注推断
- 关系候选：按 R6 映射表从技术关系提取候选业务关系，标注推断
- 规则/关系候选同样按 R3 的验证程序升级/降级

#### R6 技术关系 → 业务关系映射表

| 技术关系模式 | 候选业务关系 | 验证线索 |
|---|---|---|
| 调用（A 调用 B） | 轨迹关系候选（A 触发 B） | 是否构成业务叙事的先后/分支 |
| 消息发送/订阅 | 轨迹关系候选（跨系统） | 消息语义与消费行为 |
| 配置引用（A 读取 B 的配置） | 归因链接候选（A 归因到 B） | 改 B 配置是否改变 A 的行为 |
| 外键/关联表/冗余字段 | 结构关系候选 | 生命周期是否绑定 |
| 继承/接口实现 | 结构关系候选（变体）或未知 | 业务语义是否真不同 |
| 状态流转代码 | 轨迹关系候选 + 规则候选 | 状态机是否业务承诺 |

映射规则：①映射产出的是候选，进入主文档前必须满足 §3 的验证（六要素）；②套不上三类关系时登记 U-*，**禁止硬贴**；③数据模型/表本身的存储形态是条件扩展信息，不改变关系候选的类型判定。

#### R7 证据受限的推进策略

当无法取得运行证据（E-RUN 不可得）时，推进不停止，但结论级别受限：

| 想陈述的内容 | 只有源码时合法级别 |
|---|---|
| "系统支持某能力" | 直接事实（E-SRC 范围） |
| "某业务事件可能发生/可能如此流转" | 推断（必须标注） |
| "某业务事件实际发生/实际如此运行" | **禁止**（登记 U-* 或降级为推断） |
| "性能/容量/故障实际表现" | **禁止**（登记 U-*） |

**反向分析的停止条件**：候选事实已收敛、关键候选已验证或登记 U-*、继续取证的预期信息增益低于成本。

**反向分析的自检**：产物主文档仍按 §4.1 正向顺序组织；若主文档中事实层出现无法回溯到候选事实清单的"事实"，视为造假（公理 6 + 公理 8）。

### 4.3 正向执行操作程序（OP1-OP6）

**适用场景**：无既有代码可读时（如新建系统设计评审、业务方访谈调研、纯文档分析）；或需要从业务方视角重建事实模型的场景。

**核心立场**：正向执行不改变八对象与三类关系，只改变**对象如何从业务方描述中提取与验证**。正向路径中产生的所有"事实/维度/规则"在进入主文档前仍需经过证据定级——访谈/文档声明 ≠ 直接事实，除非经过 §5 证据规则验证。

#### OP1 利益相关者与证据源盘点

```
步骤：
1. 列出所有相关角色及其能观察到的业务现象
2. 列出可获得的文档类型（需求/合同/手册/报表/制度）
3. 列出可观察的系统输出（界面/消息/报表/日志）
4. 标注每类证据的可信度层级：直接观察 > 书面记录 > 当事人陈述
5. 标注每类证据的局限（谁会说谎、什么会被美化）
```

输出：**证据源地图**（角色/文档/系统输出 × 可信度 × 主要覆盖内容）

#### OP2 切片候选枚举与筛选

```
步骤：
1. 从证据源中枚举所有业务活动候选
2. 对每个候选回答四问（§2.2）：触发/结果/成功/失败
3. 用有效切片判定标准（四条）筛选
4. 对每个通过筛选的候选评估深度分级（§8）
5. 输出切片候选清单（含筛选理由与分级）
```

筛选工具——"触发→结果"二象限矩阵：

|  | 有可叙述业务结果 | 无明确业务结果 |
|---|---|---|
| **有明确业务触发** | ✅ 有效切片候选 | ⚠️ 需补充结果定义 |
| **无明确触发** | ⚠️ 需补充触发定义 | ❌ 不是有效切片 |

#### OP3 事实提取操作

```
步骤：
1. 从业务描述中提取"谁在什么情况下对什么做了什么"的句式
2. 用§2.3业务承诺判定三问验证每个候选：
   - 去掉技术词后是否仍外部可观察？
   - 是否影响角色决策？
   - 是否产生业务后果（钱/货/状态/合规）？
   任一"是" → 业务承诺候选
   全"否" → 实现锚点
3. 对每个候选事实标注：证据来源、推断级别、验证缺口
4. 验证后升级/降级（§5）
```

**常见陷阱**：
- 访谈者说"订单被创建"→ 需要确认"创建"是业务承诺还是内部技术步骤
- 用"系统会…"代替"业务上要求…"→ 需区分系统能力与业务规则

#### OP4 维度派生操作

```
步骤：
1. 从已确认事实轨迹中的名词提取维度候选
2. 验证：维度是否在至少两个不同事实中重复出现？
   - 是 → 维度候选
   - 否 → 可能是临时变量或实现细节，降为实现锚点
3. 验证：维度是否能独立指称（可配置/可持久/可命名）？
4. 输出维度清单（含来源事实ID列表）
```

**注意**：维度从事实派生，不得在零事实时先建立"领域模型"（公理2）。

#### OP5 规则提取操作

```
步骤：
1. 从业务描述中提取"必须/不得/仅当/按…计算/每次…必须…"的约束表达
2. 用§2.5规则类型分类：许可 / 完整性 / 计算 / 时序 / 不变量
3. 对每条规则识别：成功场景 + 失败场景
   - 找不出失败场景 → 规则定义不完整，补充边界条件
4. 标注每条规则的触发条件、违反后果、证据来源
```

**规则提取检查问句**：
- "如果违反这条规则，系统会怎么做？"
- "这个规则在什么条件下不适用？"
- "这条规则是系统强制的，还是业务习惯？"

#### OP6 关系标定操作

```
步骤：
1. 按§3.2判定顺序（事实vs维度→关系类型）逐对分析对象
2. 对每条候选关系填写六要素卡（§3.3）
3. 检验间接路径是否闭合（§3.5三问）
4. 检验多路径是否穷尽（§3.5多路径规则）
5. 无法归入三类 → 登记 U-*
```

**关系六要素填写示例**（订单→客户的结构关系）：
```
类型：结构关系
方向：订单 → 客户（N:1）
基数：每个订单归属于一个客户；一个客户可有零到多个订单
建立时机：订单创建时（交易执行）
变更影响：不追溯历史；热生效
业务语义：订单归属客户，归属关系在订单生命周期内一般不变
```

#### 正向执行与反向分析的协同

| 场景 | 主路径 | 补路径 |
|---|---|---|
| 有代码、无业务方 | §4.2 反向为主，OP1-OP6 用于访谈补证 | 正向补访谈/文档验证假设 |
| 有业务方、无代码 | OP1-OP6 正向为主 | 反向用 §4.2 检验描述是否与实现一致 |
| 两者皆有 | 先反向验证代码事实，再正向补业务意图 | 交叉验证，矛盾处登记 X-* |

**正向执行的自检**：产物主文档仍按 §4.1 正向顺序组织；若主文档中出现无法回溯到 OP1-OP6 证据源盘的"事实"，视为造假（公理 6 + 公理 8）。

## §5 证据与结论

### 5.1 证据类型

| 类型 | 可支持 | 单独不能证明 |
|---|---|---|
| E-SRC 源码与测试 | 某版本具备的实现能力 | 已部署、已被执行、覆盖所有入口 |
| E-CFG 配置与部署 | 某环境启用条件与拓扑 | 业务一定按此发生 |
| E-DAT 数据与 Schema | 样本/总体中的结构与约束迹象 | 字段名的完整业务语义 |
| E-RUN 日志/指标/追踪 | 某时间窗实际行为 | 窗外不存在其他行为 |
| E-CON 契约 | 可观察约定 | 所有调用方均已发现 |
| E-DOC 需求/设计/手册 | 意图与历史声明 | 当前实现与运行事实 |
| E-HUM 访谈与操作知识 | 角色认知与人工流程 | 无需核验的系统事实 |

### 5.2 证据最小字段

证据 ID；类型；精确定位；版本/环境/时间窗；采集或复现步骤；原始观察；覆盖范围与局限；脱敏状态。

### 5.3 结论级别

| 级别 | 定义 | 允许用途 |
|---|---|---|
| 直接事实 | 声明范围内直接观察到 | 局部判断；不可无条件外推 |
| 交叉验证结论 | 至少两类独立证据互证 | 可支持高影响判断 |
| 经验判断 | 基于实践惯例 | 只辅助比较 |
| 推断 | 推理链清楚但有缺口 | 只用于安排下一验证 |
| 假设 | 未验证候选 | 不得写为根因/规律/最终建议措辞 |

### 5.4 冲突、未知与竞争解释

- 冲突登记 X-*，不得私自挑一份证据覆盖其余。
- 未知登记 U-*，写清阻塞理解、决策还是实施。
- SC-P0 关键机制至少：主解释、竞争解释、可淘汰证据；不可淘汰则保持开放并写入 U-*。

## §6 验收门禁：怎么判定分析是否达标

### 6.1 深度八关（主文档验收）

对每个 **SC-P0**，必须同时满足：

| 关 | 名称 | 合格标准 | 检查问句 |
|---|---|---|---|
| 1 | 价值关 | 说清该切片对经营/履约/风控的不可替代性或核心贡献；**遗留系统允许合法出口**："价值不明/正在退役/历史继承"，前提是给出证据（无当前调用方、功能被替代、无业务 owner），不得编造价值 | "如果这个功能消失，经营/履约/风控会受到什么影响？有没有替代手段？" |
| 2 | 叙事关 | 去技术名后叙事完整可读；SC-P0 具备正常活动图。叙事结构：谁在什么业务意图下发起 → 系统如何响应 → 涉及哪些对象 → 成功长什么样 → 失败如何收场 → 变更影响伤及谁 | "删去所有类名/方法名/表名/字段名后，叙事是否仍可读？业务人员能理解吗？" |
| 3 | 轨迹关 | 有事件/状态变化，而非名词并列；反向分析中允许"候选事实→验证"标注来源 | "这份叙事是否描述了变化（从X变为Y），而不是只列举了名词？" |
| 4 | 规则关 | 有必须/不得/口径，不只 happy path | "能否找出至少一个违反规则时的业务失败场景？规则在什么条件下失效？" |
| 5 | 失败关 | 失败如何被发现、如何恢复、是否人工介入；SC-P0 具备失败恢复活动图 | "当系统失败时，是否说清了：谁会发现、如何发现、是否自动恢复、是否需要人工介入、人工介入的权限和审计如何？" |
| 6 | 影响关 | 关键变更伤历史还是只伤未来，谁受影响 | "修改这个对象/规则/流程，会影响已经发生的业务实例吗？影响哪些角色？" |
| 7 | 证据关 | 关键断言有证据类型、范围；假设不冒充事实；**只有源码时按 §4.2 R7 的受限级别定级，不得伪造运行证据** | "每个关键结论是否标注了证据类型和级别？'推断'和'假设'级结论是否未冒充事实？" |
| 8 | 反例关 | 至少 1 个**中强度以上**竞争解释，或显式未知与待验 | "对核心机制，是否能说出一个合乎逻辑但与主解释不同的替代方案？替代方案是否有机制描述（而非纯推测）？" |

少任一关：该切片未深写；若全部 SC-P0 未过关：主文档不合格。

**竞争解释三强度**（反例关的最低门槛 = 中强度）：
- **强**：有独立代码/数据/运行支持，替代机制可运行，仅结论被主解释覆盖
- **中**：替代机制机制上可运行（能说清如何发生），但暂无直接证据
- **弱**：纯推测，无机制描述——**不计入反例关**

### 6.2 主文档骨架

主交付**有且仅有一篇**主文档（附件另计）。推荐骨架：

```text
《{分析对象} 业务分析》理解层

0. 阅读入口 / 十分钟结论
   - 业务价值与存在理由
   - 核心切片（通常 2–3 个）
   - 最大风险 / 最大未知
   - 问题类型、深度范围、明确不覆盖项

1. 业务全景与复杂关系
   - 切片地图与分级理由
   - 切片如何组成经营过程
   - 影响核心业务的对象关系

2. 核心切片深写（正文主体，应占主要篇幅）
   每个 SC-P0：
   2.1 因果叙事（可去技术名）
   2.2 正常活动图与事实轨迹
   2.3 参与维度与关键非事实表
   2.4 规则与不变量
   2.5 失败恢复活动图、补偿、人工介入
   2.6 关键关系与间接路径
   2.7 证据与结论定级
   2.8 竞争解释与未决项
   2.9 设计决策（DEC 卡，按 §6.3 D1-D5）

3. 横切约束（仅写实际碰到的）
4. 设计与实现（机制 + 决策，深度按任务类型）
   - 机制层（怎么样）：分层、并发模型、数据流、部署拓扑
   - 决策层（为什么）：DEC 卡汇总
5. 风险、未知、冲突、下一步
```

理解层可按阅读需要拆成多篇，但 §0 必须是唯一入口，且上述职责不得因拆分而丢失。

**设计分析要求**：主文档不得停留在"业务如何运转"——对每个 SC-P0 必须回答**机制如何设计**（§4 机制层）与**为何如此选择**（§2.9 DEC 卡，按 §6.3 D1-D5 程序）。只有业务叙事没有机制与决策的主文档，视为未完成。

### 6.3 设计意图与决策分析（D1-D5）

主文档不仅要回答"系统如何运转"，还要回答"机制如何设计"（怎么样）与"为何如此选择"（为什么）。设计决策是**解释性结论（Claim）**，不是新对象——必须按 §5 定级，并区分四类成因。**适用深度按任务类型**：认知重建默认中（每个 SC-P0 至少 1 张 DEC 卡）、迁移/重构决策默认深（全部核心决策点）、故障定位默认浅（仅影响根因的决策点）。

#### D1 决策点识别

怪点 = 代码中不寻常、不直观、或代价明显偏高的选择：
- 这里为什么不用更简单的做法？
- 为什么是这个结构？
- 为什么是这个参数？
- 为什么是这里？

识别不出决策点本身是信号——要么系统过于直白，要么分析没有深入机制层。

#### D2 四类成因分类

| 成因 | 含义 | 识别线索 |
|---|---|---|
| **有意决策** | 当时有人权衡过 | 设计文档/ADR/评审记录/注释/当事人访谈 |
| **历史遗留** | 当时环境如此，无记录、当事人不可追溯 | 无任何意图证据，只能按当时上下文推断 |
| **偶然事故** | 由 bug 修复/临时方案演化成正式行为 | 提交历史显示先"临时绕过"后"转正" |
| **兼容约束** | 为兼容老数据/老调用方/老设备不得不如此 | 存在历史数据兼容代码、废弃字段保留、双版本接口 |

无法分类时登记 U-*，不得默认"有意决策"。

#### D3 决策证据收集

| 证据源 | 能证明什么 | 不能证明什么 |
|---|---|---|
| git blame/log | 何时引入、相邻提交、当时代码状态 | 为什么引入 |
| 引入时 diff | 引入时的规模/可选项/上下文 | 决策时的权衡过程 |
| E-DOC | 当时声明的意图 | 意图是否真的被执行 |
| E-HUM | 当时的权衡与约束 | 记忆是否可靠（需交叉验证） |
| 代码注释 | 决策现场留下的"为什么" | 注释是否过时 |
| 替代方案推断 | 当时技术栈中可用的其他选项 | 是否真的考虑过 |

git 只证明"何时引入"，意图必须由 DOC/HUM/注释/上下文推断；单一意图证据 = 推断级别，两类独立证据 = 交叉验证结论。

#### D4 决策逻辑重建（当时合理性）

还原**当时约束集**：当时规模、框架版本、业务需求、可用技术、团队上下文。判断在当时的约束下，该选择是否合理？**禁止**：用今天的视角审判历史决策。

#### D5 决策现状评估（当前合理性）

检查约束是否变化：规模×10？框架升级？新需求出现？协议生态变化？输出**历史合理性 vs 当前合理性分离**。当前不合理 → 形成 I-*（技术债）或 R-*（风险），**不自动变成实施指令**（公理 10）。

#### DEC 卡（产出形态）

```text
DEC-xxx 决策点：当时问的问题
当时约束：规模/框架/业务/团队上下文（含证据）
可选方案：当时考虑过的替代 / 可推断的替代
选择与理由：证据（git/DOC/HUM/注释 + 定级）
成因分类：有意决策 / 历史遗留 / 偶然事故 / 兼容约束
当时合理性：合理 / 勉强 / 不合理（按当时约束）
当前合理性：仍合理 / 已过期（约束变化）
影响面：伤历史还是只伤未来（对应八关影响关）
```

**禁止**：无证据地把"现状"写成"有意设计"（决策神化）；用今天标准审判历史（历史审判）；把 DEC 卡当验收装饰品。

### 6.4 自检清单（分优先级）

**【P0 阻断项】任一不过则主文档不合格**：

```text
□ 存在一篇主文档，而非只有过程附件
□ SC-P0 数量有配额与理由
□ 每个 SC-P0 通过深度八关（逐关检查）
□ 叙事可去技术名（叙事关）
□ 关键结论有级别与证据；假设未冒充事实（证据关）
□ 维度均能回溯到事实（公理2）
□ 未完成时交付了"未完成分析报告"（逐关标记状态），未冒充完成
```

**【P1 重要项】影响主文档质量但不阻断交付**：

```text
□ 叙事关检查问句通过（去技术名后业务人员可读）
□ 规则关检查问句通过（有失败场景）
□ 失败关检查问句通过（发现/恢复/人工介入/审计四问）
□ 竞争解释已显式，中强度以上（反例关）
□ 间接关系路径已闭合，中间对象纳入有判据依据
□ 每个 SC-P0 有设计决策（DEC 卡），走 D1-D5
□ DEC卡D2不默认"有意决策"，无法分类时登记U-*
□ D3单一意图证据未冒充交叉验证结论
□ D4当时合理性按当时约束，非今天视角
□ 主文档含机制层，深度与任务类型匹配
□ 关系只使用结构/轨迹/归因，或显式未知
□ U-/X- 与竞争解释已显式
□ 反向分析：事实层均能回溯到候选事实清单，无"痕迹直译"
□ 反向分析：技术关系→业务关系经 R6 映射并验证，无"静态硬贴"
□ 反向分析：只有源码时结论级别符合 R7，未伪造运行证据
□ SC-P0 核心对象具备 §2.6 最小可验证形态；切片卡含业务层与共享资产声明
□ 多实现/演进场景按 §9 谱系优先处理，无硬合并
□ 问题类型与完成线已声明，未静默漂移
□ 类型漂移信号已识别并显式记录（见 §1.1 类型漂移检测）
□ 认知重建未冒充实施授权
□ 未把清单、枚举、调用链当作深入本身
□ 横切仅在命中时出现
```

**【P2 增强项】提升完整性，非质量门槛**：

```text
□ 反模式与八关已建立映射（见 §7）
□ 术语速查含章节锚点（见 §12）
□ SC-P0 具备正常活动图与失败恢复活动图
□ 影响关检查问句通过（伤历史还是只伤未来）
□ 轨迹关检查问句通过（叙事描述变化而非列举名词）
```

## §7 反模式库：常见失败与纠正

### 7.1 反模式清单

| 反模式 | 表现 | 主要导致哪关失败 | 纠正 |
|---|---|---|---|
| 清单完成主义 | 表多、项全即完成 | 叙事关、价值关 | 回到主文档八关 |
| 实现转述 | 调用链当故事 | 叙事关、轨迹关 | 去技术名重写 |
| 先验领域模型 | 先概念后事实 | 叙事关、维度违反"从事实派生" | 从 SC 事实反推 |
| 假覆盖 | 全标已分析但都浅 | 价值关、八关有缺口 | 配额 + 显式未覆盖 |
| 级别跃迁 | 假设当根因 | 证据关 | 降级并验证 |
| 单证独断 | 一份源码定全局 | 证据关 | 补独立证据或降级 |
| 关系硬贴 | 套不上也要套 | 影响关（关系未经验证） | U- 或弱相关不建模 |
| 主文档空洞 | 附件重正文空 | 叙事关、规则关 | 附件只供料 |
| 类型漂移 | 摸底变改造方案 | 价值关、影响关 | 冻结或显式升级 |
| 严重度混淆 | 缺陷优先级当切片深度 | 价值关、八关有缺口 | SC-P* 与 SEV-* 分离 |
| 痕迹直译 | 代码痕迹直接当业务事实 | 轨迹关（候选事实未验证） | 候选事实→验证→升级（§4.2 R2/R3） |
| 静态硬贴 | 技术关系直接当业务关系 | 影响关（关系未经验证） | R6 映射 + 验证；套不上登记 U-* |
| 决策神化 | "现状如此"写成"当初有意设计" | DEC卡D2阶段失败 | 走 D1-D5，区分四类成因 |
| 历史审判 | 用今天约束审判历史决策 | DEC卡D4阶段失败 | 当时合理性按当时约束判断 |
| 规则缺失 | 只描述 happy path | 规则关、失败关 | 补边界条件与违反场景 |
| 维度先验 | 零事实时先建领域模型 | 叙事关、维度违反公理2 | 从事实轨迹派生维度 |
| 关系未闭合 | A→B声称但中间路径未还原 | 影响关 | §3.5路径闭合三问 |

### 7.2 自学习闭环
1. 记录到当次分析的 U-*/X-* 台账及 SOP-07 报告
2. 复盘时由负责人评估是否进入本文——新增条目须满足：在至少一个真实任务中观察到、有可复现表现、有明确纠正动作
3. 本文版本号 +1 并记录来源案例

**禁止**：把单次任务的个人偏好直接写成反模式；把尚未复现的失败写进强制层。

## §8 深度分级：哪些需要深写

### 8.1 切片深度级（SC-P*）

| 级别 | 含义 | 主文档要求 |
|---|---|---|
| **SC-P0** | 本任务必须讲透的核心切片 | 过深度八关；占主要篇幅；含正常与失败恢复活动图 |
| **SC-P1** | 重要但非本任务第一焦点 | 叙事 + 关键规则 + 主要失败；关系可减负 |
| **SC-P2** | 边缘/低频 | 地图中点名 + 简述，可进未覆盖 |
| **SC-P3** | 本次只浅覆盖的边缘切片 | 可附录或登记未覆盖；不得因场景是异常就自动归入 P3 |

SC-P* 是**分析深度配额**，不是缺陷严重度，也不是"正常/异常"场景类型。失败、补偿和恢复是核心切片内部场景，默认跟随 SC-P0/P1 深写，不因异常而自动降级。

### 8.2 分级靠排序与名额

```text
候选分 = 不可替代性(0-5)
        + 失败不可恢复或资金/库存/合规冲击(0-5)
        + 频率、变更率或事故率(0-3)
        + 跨边界耦合或多实现纠缠(0-3)

取分最高者进入名额；其余降为 SC-P1/P2/P3
```

频率只是输入之一，不得使用固定日调用阈值作为通用 P0 标准。

**名额 = f(任务类型, 切片总数, 证据可得性)**：

| 任务类型 | 候选切片总数 | SC-P0 名额 |
|---|---|---|
| 认知重建/迁移决策 | > 15（大系统） | 3-5 |
| 认知重建/迁移决策 | 5-15（中系统） | 2-3 |
| 认知重建/迁移决策 | < 5（小系统/单功能） | 1-2 |
| 故障定位 | 不限 | 1 |
| 数据治理/语义对齐 | 不限 | 1-2 |

超出上限必须在主文档 §0 写破例理由。

### 8.3 信息增益停止原则

若下一步取证不能提升关键结论级别，也不能减少关键未知对完成线的阻塞，则停止加深，缺口写入主文档 §5。

## §9 演进与兼容：多实现、多版本如何处理

### 9.1 谱系优先原则

面对多实现或多版本时，**先分谱系，后谈合并**：
- 入口不同 → 不同谱系
- 规则不同 → 不同谱系
- 状态机不同 → 不同谱系
- 副作用不同 → 不同谱系

不因命名相似就认为属于同一谱系，也不因技术实现不同就认为必然分离。

### 9.2 变体与冲突的判定

| 关系 | 判定 |
|---|---|
| 适用域不重叠 | **变体**，各自成立，无需裁决 |
| 适用域重叠且争用同一业务事实 | **冲突**，必须有明确的仲裁规则 |
| 适用域重叠但不争用同一业务事实 | **变体**，可共存 |

### 9.3 历史行为的处理

- **历史合法行为默认受保护**：标为兼容关注点（COMPAT-*）
- 是否允许破坏由任务授权与工程规则决定
- 兼容关注点进入影响关（伤历史还是只伤未来）
- 修复影响仍进影响关，不得以"修复"为由绕过兼容性评估

### 9.4 缺陷的定位

- **缺陷不是兼容义务**：已证实的越权、错账、数据污染等不升格为应保留规则
- 修复影响按正常变更处理，进入影响关
- 不得以"历史存在"为由拒绝修复有明确业务危害的缺陷

### 9.5 配置变更的评估框架

每次配置变更必须评估三个维度：

| 维度 | 问法 |
|---|---|
| 在途 | 变更是否影响已在处理中的业务实例？ |
| 历史可解释性 | 变更后能否解释历史数据的产生逻辑？ |
| 未来新语义 | 变更是否引入新的业务语义需要文档化？ |

### 9.6 版本化策略的判定

如果系统存在版本化需求，在分析时必须明确：
- 哪个版本是当前权威版本
- 历史版本的退出路径
- 版本切换的触发条件与影响范围
- 版本间的不兼容点

## 附录：唯一终点（理解层主文档的人类阅读测试）

业务系统分析的终点不是"方法走完"或"附件齐全"，而是：

> **产出可独立阅读的理解层主文档**，使读者在不打开代码的情况下，能理解关键业务如何运转、对象如何关联、受何约束、失败如何收场、变更会伤及何处，以及哪些结论仍不确定。

**人类阅读测试**（理解层验收的最低标准）：不阅读源码，仅通过理解层文档及其关系图、活动图，读者应能回答：
1. 系统解决什么业务问题？
2. 最重要的业务活动如何运行？
3. 核心对象与影响业务的非事实表如何关联？
4. 关键规则与状态变化是什么？
5. 失败后如何发现、恢复和人工处理？
6. 改变一个关键关系、配置或流程会影响什么？
7. 哪些是事实，哪些仍是推断或未知？

**未完成分析报告（合法产物，不是失败）**：时间盒到期或必须停止时，交付**未完成分析报告**——逐切片标记状态（已完成/部分/未开始），对每个 SC-P0 逐关标记（过/不过/未及），明确缺口（U-* 清单、未验证候选事实、未覆盖结果族），给出继续路径。

**明确禁止**：把未完成报告包装成"已完成"（公理 8）；把未完成报告当最终交付而不声明状态。
