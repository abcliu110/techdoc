## 1. 使用方式

先识别压缩信号，再选方法。恢复性归纳负责还原已经存在的业务语义；生成性归纳负责提出竞争解释和新预测；业务重设计负责在不编造目标的前提下改变业务机制。三者不得混成一次"填表"。

```text
事实信号 -> 当前解释 M0 -> 惊讶事实 S 与解释缺口 Δ
        -> 选择解压卡 -> 装配活模型
        -> 溯因与创造性跳跃 -> 竞争假设 -> 冒险预测 -> 区分性验证
        -> L0 骨架 / ESS -> 业务机制候选 BIZ -> 目标系统设计
```

每次使用记录：触发信号、输入证据、所用方法、形成的骨架字段、反证结果和决策影响。

以下任务必须执行完整的**理解循环与重设计循环**：路径 B 的业务本质与业务重设计、正式或高影响结论、存在多个合理解释，或命中 L0 §10.5 的反复修补信号。答案明确且可逆的局部缺陷可以精简，但必须写明为什么不存在需要区分的结构性解释。

### 3.2 溯因增强方法

#### 3.2.1 多层次溯因（Multi-Level Abduction）

**适用信号**：表面解释无法预测关键现象，或问题反复出现但原因不明。

**核心思想**：每种现象都有表层原因、深层机制和元层假设三层解释。真正的洞察来自深入到更深层次。

**操作方法**：

```text
表层（L1）：直接可观察的事件序列
  -> 为什么？
深层（L2）：产生表层的因果机制或约束
  -> 为什么？
元层（L3）：使深层机制成立的基本假设或世界观
```

**示例**：

```text
问题：门店频繁上报"价格不一致"投诉

L1（表层）：门店看到的价格与总部发布的价格不同
L2（深层）：存在多版本价格数据源，且发布时间窗口存在重叠
L3（元层）：系统假设"只有一个价格权威"，但实际业务存在"总部定价权"与"门店本地调价权"的二元权威

洞察：真正问题是"价格权威的边界没有在系统层面建模"
```

**产出要求**：

- 每层必须独立回答"为什么"，不能简单重复
- 至少深入到 L2 才能形成有价值的洞察
- 元层假设要显式标记，因为它可能被后续证据推翻

#### 3.2.2 溯因质量评估（Abduction Quality Assessment）

**适用信号**：生成了多个候选解释，需要评估哪个更值得深入。

**核心思想**：不是所有溯因都一样有价值。高质量溯因具有更强的解释力、可验证性和启发性。

**评估维度**：

| 维度 | 问题 | 权重 |
|---|---|---|
| 解释力 | 该解释能同时解释正常案例和异常案例吗？ | 高 |
| 可验证性 | 存在可以削弱或否证该解释的最小事实吗？ | 高 |
| 简洁性 | 它比竞争解释使用更少的新假设吗？ | 中 |
| 生成力 | 它能推导出尚未观察到的预测吗？ | 中 |
| 深度 | 它深入到因果机制还是只停留在表面？ | 高 |
| 意外性 | 它是否揭示了不显而易见的关系？ | 中 |

**操作方法**：

```text
1. 列出所有候选解释 H1, H2, H3...
2. 对每个 H 在五个维度上打分（1-5分）
3. 计算加权总分
4. 优先深入最高分，但保留次高分作为竞争项
5. 如果最高分的意外性得分很低，考虑是否只是泛化常识
```

#### 3.2.3 元层溯因（Meta-Level Abduction）

**适用信号**：当前分析框架本身可能有问题，需要审视分析前提。

**核心思想**：不仅对业务现象进行溯因，还对"我们为什么会这样理解这个现象"进行溯因。

**操作方法**：

```text
观察：当前对 X 的解释 M0
      ↓
元层问题：为什么我会用这个框架来理解 X？
      ↓
元层答案：假设 A（来自专业背景）、假设 B（来自经验）、假设 C（来自类比）
      ↓
元层溯因：如果假设 A/B/C 不成立，M0 会怎样？
      ↓
新的可能解释：基于不同假设的解释 H'
```

**示例**：

```text
观察：系统采用"集中式"架构
M0 解释：因为业务需要强一致性
元层假设：我用"一致性需求 → 架构选择"这个框架理解
新的可能：换一个框架"控制成本 → 技术债务 → 架构演进路径"，解释变成：
  不是"需要一致性所以集中"，而是"最初成本限制只能集中，后来架构惯性导致延续"
```

#### 3.2.4 溯因到溯因（Abduction to Abduction）

**适用信号**：一个解释本身需要进一步溯因才能找到真正的根因。

**核心思想**：溯因的结果本身可能还需要进一步溯因，形成溯因链。

**操作方法**：

```text
观察 O → 溯因得到 H1
H1 本身需要解释 → 溯因得到 H1.1, H1.2
哪个 H1.x 更可能 → 选择 H1.2
H1.2 本身需要解释 → 溯因得到 H1.2.1
...继续直到找到满意深度
```

**停止条件**：

- 达到 L3 元层假设
- 找到"因为这是行业惯例/最佳实践"这类需要追溯历史或文化的根因
- 继续深入不产生新的可验证预测

### 3.3 想象力训练方法

#### 3.3.1 假设链构建（Hypothesis Chain Construction）

**适用信号**：需要生成多个有内在逻辑的候选解释，而非孤立的猜测。

**核心思想**：好解释不是孤立的，而是一个可以向后追溯、向前预测的链条的一部分。

**操作方法**：

```text
从观察 O 开始：
1. "如果 O 是真的，那么 X 应该发生"（前向预测）
2. "要使 O 成立，需要满足什么条件 C？"（后向条件）
3. "C 本身需要什么条件 C'？"（条件链）
4. "是否存在使 C' 不成立的场景？"（反事实分支）

构建一个假设链：
H0: 观察 O
  -> H1: O 的直接原因（条件 C）
    -> H2: C 的原因（条件链）
      -> H3: 条件链的终点（元假设）

检查假设链的每个节点：
- 是否有直接证据支持？
- 是否有反证？
- 哪个节点最脆弱？
```

**示例**：

```text
观察 O：用户频繁放弃购物车
假设链：
H0: 用户放弃购物车
  -> H1: 价格太高
    -> H2: 用户没有看到足够的价值
      -> H3: 产品展示无法传达差异化价值
        -> H4: 竞品更有力的价值主张

或另一条假设链：
H0: 用户放弃购物车
  -> H1: 结账流程太复杂
    -> H2: 需要多步骤验证
      -> H3: 历史欺诈损失导致的风控策略
        -> H4: 风控与用户体验的权衡策略

两个假设链指向不同的干预方向，需要区分性验证。
```

#### 3.3.2 反直觉洞察生成（Counter-Intuitive Insight Generation）

**适用信号**：当前分析只有符合直觉的结论，需要突破性洞察。

**核心思想**：最有价值的洞察往往是与直觉相反的。通过系统性地挑战直觉假设来生成反直觉解释。

**操作方法**：

```text
1. 列出当前理解中的直觉假设（"大家都这样认为"）
2. 对每个直觉假设进行反转：
   - "如果相反是真的呢？"
   - "如果这个假设不成立呢？"
3. 沿着反转方向推演：
   - 会导致什么不同的观察？
   - 什么证据可以验证反转？
4. 评估反转假设的解释力：
   - 是否能同样好地解释现有观察？
   - 是否能解释之前被忽略的现象？
   - 是否产生新的可验证预测？
```

**直觉假设类型及反转策略**：

| 直觉类型 | 反转策略 |
|---|---|
| "更多功能 → 更好体验" | "减少功能 → 更聚焦价值" |
| "用户需要更多选择" | "选择疲劳 → 减少选项" |
| "集中控制 → 更安全" | "去中心化 → 更强韧性" |
| "实时同步 → 更准确" | "最终一致 → 更高可用性" |
| "人工审批 → 更安全" | "自动化 → 消除人为错误" |
| "大团队 → 快速度" | "小团队 → 减少沟通开销" |

#### 3.3.3 认知突破识别（Cognitive Breakthrough Identification）

**适用信号**：分析过程遇到瓶颈，需要识别是否已经发生认知突破。

**核心思想**：认知突破不是灵光一现，而是有可识别的信号和结构。

**突破信号**：

```text
1. 框架转换
   - 从"问题 X"转换为"问题 Y"（不是同一问题的不同表述）
   - 发现 X 和 Y 本质上是同一结构

2. 约束重构
   - 意识到之前认为的约束其实是可选的
   - 发现之前没意识到的真正约束

3. 视角融合
   - 两个之前分离的视角合并成一个更宏观的视角
   - 发现表面不同的现象有共同根因

4. 简化压缩
   - 多个复杂现象可以用一个简单机制解释
   - 之前认为必要的复杂性其实是多余的

5. 反直觉发现
   - 某个与直觉相反的解释比直觉解释更有力
```

**操作方法**：

```text
定期检查：
1. 我的分析框架在过去一小时有变化吗？
2. 我是否发现了不同现象之间的共同结构？
3. 我是否意识到某个之前认为必须的假设其实不必须？
4. 我的核心结论是否比开始时更简单但更有力？

如果任何一个问题的答案是"是"，很可能已经发生认知突破。
记录突破的内容、触发因素和它对结论的影响。
```

### 3.4 类比增强方法

#### 3.4.1 跨领域类比（Cross-Domain Analogy）

**适用信号**：当前领域的问题与其他领域有相似结构，可以借用其他领域的解决方案。

**核心思想**：类比不是复制表面特征，而是映射深层结构。

**操作方法**：

```text
源领域选择：
1. 选择一个你深入理解的领域（不一定是技术领域）
2. 选择一个与当前问题有某种结构相似性的领域

结构映射：
源领域 A    ->  当前领域 B
角色/参与者   ->  ?
核心机制     ->  ?
关键约束     ->  ?
失败模式     ->  ?
成功条件     ->  ?

必须回答的问题：
- 什么相似？什么不同？
- 可以迁移什么？不能迁移什么？
- 迁移需要什么适配？
- 用什么项目事实验证类比的有效性？
```

**值得探索的类比源**：

```text
自然系统：蜂群、蚁群、生态系统、免疫系统
物理系统：流体、热力学、弹簧、杠杆
社会系统：市场、民主、市场监管、合同
生物系统：细胞、器官、进化、适应
经济系统：供需、期货、保险、仲裁
法律系统：合同、判决、执行、上诉
军事系统：战略、战术、情报、后勤
```

#### 3.4.2 多重类比融合（Multiple Analogy Fusion）

**适用信号**：单一类比不够全面，需要结合多个类比形成更完整的理解。

**核心思想**：不同类比捕捉同一现象的不同维度，融合后形成更丰富的理解。

**操作方法**：

```text
1. 收集多个相关类比 A1, A2, A3...
2. 对每个类比分析：
   - 它捕捉了什么维度？
   - 它遗漏了什么？
3. 寻找类比之间的互补性：
   - A1 的强项是否补充 A2 的弱项？
   - 是否有冲突需要解决？
4. 构建融合理解：
   - 综合多个类比的核心洞察
   - 识别共同结构
   - 形成新的整体视图
```

**示例**：

```text
问题：如何理解系统的韧性设计？

类比1：人体免疫系统
- 强项：多层次防御、自愈能力、记忆与学习
- 弱项：不考虑经济成本

类比2：生态系统
- 强项：物种多样性、冗余、动态平衡
- 弱项：演化是随机的，不是有目的的

类比3：航空系统
- 强项：冗余设计、故障隔离、安全边界
- 弱项：过度保守，缺乏灵活性

融合理解：
- 多层次韧性 = 免疫系统 + 航空冗余
- 动态适应 = 生态系统演化机制
- 约束平衡 = 需要考虑经济/性能/安全的权衡
```

#### 3.4.3 类比质量评估（Analogy Quality Assessment）

**适用信号**：生成了多个类比，需要评估哪个更有价值。

**评估维度**：

| 维度 | 问题 | 评估标准 |
|---|---|---|
| 结构相似性 | 核心结构是否相似，而非表面特征？ | 高相似性得高分 |
| 解释力 | 类比是否能解释当前现象的多个方面？ | 能解释更多得高分 |
| 可迁移性 | 迁移的洞察是否经过验证？ | 有验证得高分 |
| 启发性 | 类比是否产生新的洞察或预测？ | 产生新洞察得高分 |
| 边界清晰 | 类比的适用边界是否明确？ | 边界清晰得高分 |

**操作方法**：

```text
1. 对每个类比在五个维度打分（1-5分）
2. 识别类比的核心洞察
3. 明确类比的不适用场景
4. 综合评估：优先使用结构相似性高且启发性强的类比
5. 在报告中显式说明类比的局限性和适用边界
```

### 3.5 组合创新方法

#### 3.5.1 概念组合（Concept Combination）

**适用信号**：需要生成新的解决方案，组合现有概念。

**核心思想**：创新常常来自看似不相关概念的意外组合。

**操作方法**：

```text
1. 列出当前问题域的核心概念 C1, C2, C3...
2. 列出其他领域或系统的核心概念 D1, D2, D3...
3. 尝试组合：
   - C1 + D1：产生什么新理解？
   - C2 + D2：产生什么新理解？
   - 意外组合：什么组合看起来不相关但可能有价值？
4. 对每个组合追问：
   - 为什么这个组合有价值？
   - 它解决什么之前无法解决的问题？
   - 它的风险和局限是什么？
```

**组合类型**：

```text
交叉组合：把一个领域的方法应用到另一个领域
  例：区块链 + 供应链 = 供应链溯源

层次组合：把不同抽象层次的机制组合
  例：市场机制 + 技术协议 = 代币经济

约束组合：把看似矛盾的约束组合在一起
  例：去中心化 + 高性能 + 低成本 = 需要新的架构范式

功能组合：把不同功能组合成新能力
  例：缓存 + 消息队列 + 事务 = 可靠消息模式
```

#### 3.5.2 约束组合（Constraint Combination）

**适用信号**：需要找到满足多个约束的解决方案，或理解约束之间的权衡。

**核心思想**：约束不是简单的"满足/不满足"，而是需要理解约束之间的关系和权衡。

**操作方法**：

```text
1. 列出所有相关约束 C1, C2, C3...
2. 识别约束之间的关系：
   - 协同：满足 C1 自动满足 C2
   - 冲突：满足 C1 难以满足 C2
   - 独立：满足 C1 与 C2 无关
3. 对冲突约束进行权衡分析：
   - 每个约束的相对重要性是什么？
   - 能否通过重新表述约束找到双赢？
   - 能否在满足核心约束的同时放宽次要约束？
4. 生成满足约束的方案：
   - 必须满足：不可妥协的约束
   - 尽量满足：重要但不必须的约束
   - 可以放松：低优先级或假设性的约束
```

#### 3.5.3 意外组合（Serendipitous Combination）

**适用信号**：需要突破性创新，常规组合无法产生足够新颖的方案。

**核心思想**：最有价值的创新往往来自"不应该"但实际上有效的组合。

**操作方法**：

```text
1. 识别当前问题的"必须"约束和"以为必须"约束
2. 寻找看似无关但可能相关的元素：
   - 当前领域外的解决方案
   - 历史解决方案
   - 自然系统中的解决方案
   - 不同行业的解决方案
3. 尝试强制组合：
   - "如果把这个领域的做法用到那个领域会怎样？"
   - "如果必须同时满足两个冲突的要求会怎样？"
4. 评估意外组合：
   - 它是否真的解决了问题？
   - 它的代价是什么？
   - 是否产生新的问题？
```

### 3.6 问题重构方法

#### 3.6.1 问题反转（Problem Inversion）

**适用信号**：问题反复无法解决，或解决方案陷入局部最优。

**核心思想**：把问题反过来看，往往能发现新的解决方向。

**操作方法**：

```text
原问题 P -> 反问题 NOT P

问题反转类型：

1. 目标反转
   原：如何增加 X？
   反：如何减少 X？如何在不需要 X 的情况下达到目的？

2. 约束反转
   原：X 必须满足条件 A, B, C
   反：如果 X 不满足 A 会怎样？不满足 B 呢？

3. 参与者反转
   原：A 负责做 X
   反：如果 B 负责做 X？如果没有人负责 X？

4. 时序反转
   原：先做 A，再做 B
   反：先做 B，再做 A？如果同时做 A 和 B？

5. 视角反转
   原：从用户视角看 X 是问题
   反：从系统视角、从竞争对手视角、从一年后的视角看 X？

6. 解决方案反转
   原：问题 P 的解决方案是 S
   反：如何让 S 导致 P？如何让 P 导致 S？
```

#### 3.6.2 极端情况分析（Extreme Case Analysis）

**适用信号**：需要理解系统的边界行为和极限情况。

**核心思想**：通过分析极端情况，可以发现正常情况下看不到的模式和约束。

**操作方法**：

```text
1. 识别关键变量 V
2. 将 V 推向极端：
   - 最大值（V = ∞）
   - 最小值（V = 0）
   - 负值（V < 0）
   - 边界值（V = 临界点）
3. 推演极端情况下的系统行为
4. 识别：
   - 什么机制阻止了系统崩溃？
   - 什么假设在极端情况下不再成立？
   - 系统如何优雅地降级？

常见极端情况：
- 用户数量：0, 1, 1,000, 1,000,000, 1,000,000,000
- 响应时间：0ms, 1ms, 100ms, 10s, 10min, 永不返回
- 数据规模：0, 1, 1,000, 1,000,000, 数据无限
- 失败模式：单点失败、多点失败、网络分区、永不恢复
```

#### 3.6.3 约束消除（Constraint Elimination）

**适用信号**：当前分析受限于看似必然但实际上可选的约束。

**核心思想**：很多"约束"实际上是假设，可以通过挑战假设来打开新的可能性空间。

**操作方法**：

```text
1. 列出当前问题中的所有约束 C1, C2, C3...
2. 区分约束类型：
   - 物理约束：无法改变（光速、内存大小、物理定律）
   - 技术约束：当前技术限制，但可能改变
   - 商业约束：商业决策，可以重新评估
   - 组织约束：组织惯例，可以改变
   - 心理约束：自我设限，实际上不存在
3. 对非物理约束追问：
   - "为什么这个约束存在？"
   - "如果移除这个约束，会发生什么？"
   - "这个约束的代价是什么？收益是什么？"
4. 生成消除约束后的解决方案：
   - 新的可能性空间是什么？
   - 新的风险是什么？
   - 过渡方案是什么？
```

### 3.7 元认知方法

#### 3.7.1 认知盲区识别（Cognitive Blind Spot Identification）

**适用信号**：分析结果与事实有差距，需要识别分析过程中的认知盲区。

**核心思想**：分析者有其自身的认知偏见和盲区，需要主动识别和挑战。

**常见认知盲区**：

```text
1. 确认偏见：只寻找支持当前假设的证据
2. 可用性偏见：过度依赖容易想到的例子
3. 锚定效应：过度依赖第一个获得的信息
4. 幸存者偏差：只分析成功的案例，忽略失败的
5. 计划谬误：低估完成时间，高估成功率
6. 知识诅咒：假设别人拥有和自己相同的知识
7. 过度自信：高估自己的判断准确性
8. 事后偏见：认为结果比实际更可预测
```

**操作方法**：

```text
1. 显式列出当前的主要假设
2. 对每个假设追问：
   - "我为什么认为这个假设是真的？"
   - "有什么证据会推翻这个假设？"
   - "我是否只看了支持这个假设的证据？"
3. 寻找反例：
   - 什么案例不符合当前假设？
   - 是否有系统性地被忽略的证据？
4. 视角切换：
   - 如果我的假设是错的，会是什么样子？
   - 一个持不同观点的人会怎么看这个证据？
```

#### 3.7.2 视角切换训练（Perspective Switching Training）

**适用信号**：需要从多个角度审视问题，避免单一视角的局限性。

**核心思想**：每个视角都捕捉问题的某些方面，忽视其他方面。主动切换视角可以获得更完整的理解。

**视角清单**：

```text
1. 用户视角：用户真正需要什么？用户体验如何？
2. 业务视角：业务目标是什么？什么指标衡量成功？
3. 技术视角：技术实现如何？有什么技术约束？
4. 财务视角：成本和收益是什么？ROI 如何？
5. 时间视角：短期和长期影响是什么？
6. 竞争对手视角：竞争对手会怎么做？
7. 监管视角：合规要求是什么？风险点在哪？
8. 系统视角：整体系统如何运作？各部分如何交互？
9. 未来视角：从5年后看，现在的选择是否正确？
10. 敌人视角：如果有人想破坏系统，会攻击哪里？
```

**操作方法**：

```text
1. 显式选择一个当前未使用的视角
2. 从该视角重新审视问题
3. 记录：
   - 这个视角揭示了什么之前没看到的东西？
   - 这个视角与之前视角的主要区别是什么？
   - 哪个视角给出了最关键的洞察？
4. 综合多个视角形成完整视图
```

#### 3.7.3 思维模型检验（Mental Model Testing）

**适用信号**：基于某个心智模型得出结论，需要验证模型的有效性。

**核心思想**：心智模型是我们理解世界的方式，但模型可能不完整或错误。主动检验模型可以提高结论的可靠性。

**检验清单**：

```text
1. 模型适用性
   - 这个模型适用于当前情境吗？
   - 模型的假设在当前情境中成立吗？
   - 是否有模型不适用的边界情况？

2. 模型完整性
   - 模型考虑了所有重要因素吗？
   - 是否有模型忽略的关键变量？
   - 模型是否过于简化？

3. 模型一致性
   - 模型内部是否一致？
   - 模型的各个部分是否相互支持？
   - 有没有自相矛盾的地方？

4. 模型预测力
   - 模型能否产生可验证的预测？
   - 预测是否与实际观察一致？
   - 是否存在模型无法解释的现象？

5. 模型替代
   - 是否有其他模型能更好地解释同一现象？
   - 不同模型的预测有何不同？
   - 什么证据可以区分这些模型？
```

## 4. 表示解压（原有方法，保留）

### 4.1 概念净化

1. 收集同一词在代码、表、接口、配置和流程中的定义；
2. 区分业务身份、数据表示、技术载体和历史别名；
3. 对同名不同义拆分，对异名同义合并；
4. 给出业务定义、反例、生命周期和证据；
5. 冲突无法消解时升级为"语义分裂"，不得强行统一。

### 4.2 时间维度分析

检查创建、生效、执行、过期、关闭、重试、补偿、归档的业务时间与系统时间。输出时间事件、时效规则、允许乱序、过期后的权利义务和恢复策略。

### 4.3 能力图谱

从"谁为了什么结果使用系统"出发定义能力，而不是从 Controller、菜单或接口命名能力。能力至少包含服务对象、触发、业务结果、关键约束和实现映射。

---

## 5. 层级解压（原有方法，保留）

### 5.1 规则抽象

将散落条件归成：资格规则、计算规则、状态转换、不变式、策略和例外。先找不允许被破坏的结果，再判断条件是业务规则还是技术保护。

### 5.2 策略识别

当同一目标存在多种可替换做法，且选择随租户、场景、规模或时间变化时，将其识别为策略。稳定不变的约束不是策略，不能为了扩展性全部配置化。

### 5.3 异常归类

按业务语义区分：拒绝、可重试失败、需补偿失败、部分成功、人工介入和不可恢复失败。异常类型必须影响调用方决策，否则只是技术分类。

---

## 6. 语境解压（原有方法，保留）

### 6.1 关系还原

从直接引用扩展到业务路径：A 经 B 影响 C、谁拥有谁、谁决定谁、谁必须与谁一致。对 2 跳以上关系记录路径、传播规则、断裂后果和证据。

### 6.2 流程抽象

把方法调用序列压成业务阶段：触发、校验、决策、执行、确认、失败恢复。每阶段写清输入、业务结果、状态变化、不变式和补偿，不保留无决策价值的技术步骤。

### 6.3 边界与一致性

用"一起变化、一起成功/失败、一起过期、一起回溯"判断边界。数据库事务、服务部署或包结构只是证据，不能自动等同业务边界。

### 6.4 多实现归一

1. 对齐共同业务目的；
2. 分离共同不变式与实现差异；
3. 判断差异是策略、渠道约束、历史妥协还是语义冲突；
4. 只统一真实共性，保留有意义差异；
5. 冲突必须升级为语义分裂、边界错误或原假设失效等判断。

## 7. 输出到 L0 骨架（原有方法，保留）

| 方法产物 | L0 字段 |
|---|---|
| 净化后的业务实体与身份 | 对象 |
| 归属、路由、依赖与传播路径 | 关系 |
| 不允许破坏的规则与状态条件 | 不变式 |
| 一致变化、失败与回溯范围 | 边界 |
| 对服务对象产生的业务结果 | 能力 |
| 高频、高价值且修改痛苦的变化方向 | 演化轴 |
| 保护/有意设计/可靠性缺陷/错误抽象 | 分型 |

方法产物若不能进入至少一个骨架字段，或不影响保护、修复、演进、重构、兼容或迁移决策，应删除或降为背景资料。

## 8. 创造性洞察生成（增强版）

### 8.1 先建立归纳对象和保留样本

创造性不是脱离对象自由联想。执行 `CA0` 时先建立证据语料，并在提出核心假设前划出至少一组**未用于生成该假设**的保留样本：

- 正常主路径：系统如何兑现业务结果；
- 边界或失败路径：重复、延迟、部分成功、取消、人工补救；
- 变体：渠道、组织、客户、地区、版本或多实现差异；
- 历史样本：旧数据、旧契约、原设计决策和已废弃路径。

按任务适用性选取，不机械凑齐。没有可用保留样本时，必须设计一个未来可观察的新场景或最小实验，并把结论保持为假设；不得用生成假设时已经挑中的同一条证据冒充独立验证。

### 8.2 装配业务活模型

用一句可推演的主链描述当前理解：

```text
谁为了什么结果
  -> 在什么触发和信息下作出什么决定或承诺
  -> 对什么对象执行什么动作或交换
  -> 谁获得什么结果、承担什么义务或风险
  -> 失败如何恢复，结果怎样反馈到下一次决定
```

把事实、推断、假设和未知分别标记。若模型只能写成接口调用序列或表关系，尚未形成业务活模型，不得进入创造性推演。

### 8.3 双轨溯因链（S-M0-Δ-H-P-F-ΔH-CI）

溯因链同时适用于**业务归纳**和**架构归纳**，使用同一结构但关注点不同：

```text
业务轨（B）：
S  业务惊讶：业务失败、角色冲突、流程断点、能力缺失
M0 业务当前解释及其本来预测
Δ  业务解释缺口
H  业务候选解释
P  业务冒险预测（实施前可观察、可能失败）
F  削弱或否证业务 H 的最小事实
ΔH 业务解释增量
CI 业务反直觉洞察

架构轨（A）：
S  架构惊讶：技术债暴露、扩展失效、模式冲突、约束违反
M0 架构当前解释及其本来预测
Δ  架构解释缺口
H  架构候选解释
P  架构冒险预测（代码/部署前可观察、可能失败）
F  削弱或否证架构 H 的最小事实
ΔH 架构解释增量
CI 架构反直觉洞察
```

**统一执行规则**：
- 业务轨和架构轨独立运行，分别收敛
- 两轨结论必须互洽：架构解释不能与业务本质矛盾
- L5 架构归纳使用架构轨；ESS/BIZ 使用业务轨
- 架构轨的 H 必须回答"什么约束/决策导致了这个结构"

**解释增量（ΔH）的评估标准**（双轨通用）：

```text
+ 新解释的现象数量
- 新引入的假设数量
= 净解释力（越高越好）

新解释的现象必须包括：
- 原有 M0 能解释的部分
- M0 难以解释或需要补丁的部分
- 历史样本中的反常案例

业务轨 ΔH：回答"这个业务机制如何产生"
架构轨 ΔH：回答"这个架构结构如何形成"
```

**反直觉洞察（CI）的评估标准**（双轨通用）：

```text
- 如果 CI 为真，它是否违反"显而易见"的预期？
- CI 是否揭示了表面现象之下的深层结构？

- CI 的意外性是否来自证据，而非为了新奇而新奇？

业务轨 CI：回答"业务机制是否有反直觉的角色/责任/激励"

```

### 8.4 增强认知跳跃（整合新旧方法）

方法用于产生候选，不直接产生事实结论。按信号选择，路径 B 至少使用一种"事实内部重组"方法和一种"改变观察条件"方法；没有产生新候选也要保留淘汰理由。

**事实内部重组方法**（改变事实之间的关系）：

| 方法 | 怎么做 | 合格候选 | 防失真要求 |
|---|---|---|---|
| 跨事实组合 | 选取分属不同对象、阶段、文件、时间或边界的事实，做 AND/先后/互斥/守恒组合 | 任一单项都未直接写出的隐性契约、断点或冲突 | 必须给出完整组合链和断裂后果 |
| 多层次溯因 | 从表层现象深入到深层机制和元层假设 | 发现表面解释背后的真正原因 | 每层必须独立回答"为什么" |
| 维度分解与重组 | 分解问题维度，识别共同维度与差异维度 | 发现表面不同问题的共同根因 | 必须显式列出分解的维度 |
| 约束组合 | 将冲突约束组合在一起，分析权衡关系 | 发现约束间的协同或冲突模式 | 必须区分约束类型（物理/技术/商业/组织/心理） |

**改变观察条件方法**（改变看问题的角度）：

| 方法 | 怎么做 | 合格候选 | 防失真要求 |
|---|---|---|---|
| 反事实 | 每次只改变一个关键条件，如角色、顺序、延迟、规模、依赖或失败方式；保持其他不变量，沿活模型推演 | 暴露缺失规则、恢复边界或不同预测 | 不把虚构场景写成已经发生的事实 |
| 期望违例 | 先写明"为什么按业务承诺或同类结构应该存在"，再查当前材料是否出现 | "该有而未见"的能力、控制或反馈假设 | 未找到证据只能标"待验证缺席"，不能直接判缺陷 |
| 重新框定 | 删除表、字段、接口、组件名，连续追问"它代表谁的什么决定、承诺、义务、风险或结果" | 能改变问题边界或候选空间的业务表述 | 只换高级名词、没有新预测，不算重构 |
| 结构类比 | 映射源领域与当前业务的角色、关系、不变量、状态和失败机制，再列结构差异 | 可迁移的业务机制和待验证空缺 | 概念同名不算同构；必须写明不能迁移什么 |
| 假设考古与反转 | 从稳定路径和历史决定还原"当时必须成立什么"，再令规模、渠道、时效、组织或风险条件反转 | 原设计假设的失效点、演化轴或新机制候选 | 不能用今天的偏好倒推历史错误 |
| 因果回路与博弈 | 画出"角色行动 -> 指标/收益 -> 反馈延迟 -> 下一步行动 -> 最终结果"，尝试让参与者在规则内优化自身利益 | 代理指标失真、激励错配、正/负反馈、风险外溢和套利路径 | 不凭道德判断猜动机；必须说明角色可见信息、可选行动和收益/代价 |
| 问题反转 | 将问题反过来看（目标反转、约束反转、参与者反转、时序反转等） | 发现被忽略的解决方向或新问题定义 | 必须验证反转后的问题确实更值得关注 |
| 极端情况分析 | 将关键变量推向极端（最大/最小/负值/边界值），推演系统行为 | 发现隐藏约束、边界条件和优雅降级策略 | 必须识别阻止系统崩溃的机制 |
| 约束消除 | 区分约束类型，挑战非物理约束的存在理由 | 发现被假设而非必须的约束，打开新的可能性空间 | 必须明确区分物理约束和可改变约束 |
| 反直觉洞察 | 系统性挑战直觉假设，生成与直觉相反的解释 | 揭示不显而易见但有证据支持的结构性洞察 | 必须有证据支持，不能为反直觉而反直觉 |

**深度探索方法**（需要深入思考的方法）：

| 方法 | 怎么做 | 合格候选 | 防失真要求 |
|---|---|---|---|
| 隐喻跳跃 | 从不相关领域寻找隐喻，映射深层结构 | 发现新视角或类比 | 必须映射深层结构，不只是表面特征 |
| 元层溯因 | 对"为什么会用这个框架理解"进行溯因 | 发现分析框架本身的问题 | 元层假设必须显式标记 |
| 假设链构建 | 构建前向预测和后向条件的假设链 | 形成有内在逻辑的候选解释链 | 假设链每个节点必须可追溯 |
| 认知突破识别 | 定期检查是否发生框架转换、约束重构或简化压缩 | 识别并记录已发生的认知突破 | 不以"有洞察"代替结构验证 |
| 意外组合 | 尝试看似不相关概念的强制组合 | 突破性创新方案 | 必须评估意外组合的实际可行性 |

### 8.5 换眼镜，不换形容词（增强版）

当第一种描述只能复述材料时，至少选择两个能产生不同预测的视角重看同一活模型：

| 视角 | 追问 |
|---|---|
| 结果与价值 | 用户真正需要完成什么，什么结果值得付出成本？ |
| 角色与激励 | 谁受益、谁付款、谁承担风险、谁有权决定、谁被迫补救？ |
| 权利与义务 | 谁应在什么条件和期限内向谁交付什么，用什么证明完成？ |
| 身份与生命周期 | 哪些状态其实代表不同对象或不同阶段？对象何时产生、转移、失效？ |
| 决策与信息 | 谁在什么信息下做决定；信息晚到、错误或不完整会怎样？ |
| 控制与反馈 | 错误最早能在哪里被阻止；结果何时被谁看见并改变后续行为？ |
| 边界与权威 | 哪些事实必须一起一致；冲突时谁有最终解释权？ |
| 时间与演化 | 延迟、回放、规则版本、十倍规模或组织变化时，哪个假设先失效？ |
| 指标与博弈 | 当前指标是不是目标的代理；角色能否改善指标却伤害真实结果？ |
| **多层次视角** | **表层/深层/元层各看到了什么？** |
| **反直觉视角** | **与直觉相反的假设是什么？** |
| **未来视角** | **从三年后回看，这个决策是否正确？** |
| **竞争对手视角** | **竞争对手会如何应对这个设计？** |

两个视角若只产生同义描述，说明没有真正换眼镜，应更换视角或收敛为"当前证据下解释唯一"。

### 8.6 `CA-*` 探索记录（增强版）

`CA-*` 是可丢弃的探索痕迹，不是正式业务结论。最小记录如下：

```markdown
### CA-<编号>：<洞察主题>

- 溯因轨：业务轨 / 架构轨
- S 惊讶事实 / M0 当前解释 / Δ 解释缺口：
- 使用的认知跳跃/视角：
- 候选解释：
- 相对 M0 的解释增量与仍未解释的事实：
- 支持证据与反证：
- 区分于竞争解释的冒险预测：
- 保留样本或最小实验：
- 什么结果会推翻它：
- 决策用途：
- 是否包含反直觉洞察（CI）：
- 溯因质量评分（1-5）：
- 状态：待验证 / 增强 / 削弱 / 否证 / 转正
```

没有新预测、可证伪条件或决策用途的候选，不得转入 `EVO-T/ESS/BIZ`。

## 9. 竞争假设与证据收敛（增强版）

### 9.1 什么叫真正竞争

高影响问题至少提出两个在以下任一方面不同的解释：核心对象身份、因果机制、责任/权威、边界、不变量、价值结果或演化轴。每个解释必须对至少一个相同场景给出不同预测；"代码不好""设计不优雅""应该抽象"不是竞争假设。

答案确实唯一时，不强行凑数，但必须给出能够排除其他合理解释的证据，而不是写"未想到其他方案"。

#### 9.1.1 解释竞争预算与停止

一次 `CA3 -> CA4` 算一轮。轮次预算与停止语义以 L0 §6 为准，默认最多 3 轮；本卡只提供生成和比较方法，不得自行放宽预算。每轮记录新增因果结构、新增区分预测、被淘汰解释和下一项区分证据。已具备可验证竞争时进入独立反证；非平凡任务至少两轮且使用不同认知动作后，Reviewer 仍确认没有新增结构或预测，才可按当前空间饱和收敛；预算耗尽仍无法区分时保留未知与补证计划，禁止用"暂时最像"冒充胜出。扩轮必须记录 Referee 或人工批准及新的停止点。

### 9.2 收敛十问（增强版）

| 检验 | 必须回答 |
|---|---|
| 惊讶锚点 | `S` 为什么违背 `M0` 的预期；若没有违背，为什么需要新解释？ |
| 证据可逆 | 能否回指事实，是否把经验或缺席证据当事实？ |
| 解释压缩 | 是否用更少假设解释更多正常、异常和历史现象？ |
| 解释增量 | 相对 `M0` 新解释什么、仍解释不了什么，新增概念成本是否值得？ |
| 冒险预测 | 与最强竞争解释在哪个实施前场景下结果不同，且预测可能为错？ |
| 保留样本 | 未参与生成的样本是否符合预测；不符合如何降级？ |
| 生成能力 | 能否推出材料未直接写出的规则、场景或验证问题？ |
| 最小反例 | 哪个最小合法事实足以推翻或缩小适用范围？ |
| 机制韧性 | 角色能否博弈指标、利用规则或把风险外溢给别人；延迟反馈会不会反转结果？ |
| 决策价值 | 它是否改变保护、修复、演进、重绘、兼容或迁移判断？ |
| **反直觉性** | **新解释是否包含反直觉洞察；如果有，证据是否充分？** |
| **溯因质量** | **候选解释在多层次溯因中位于哪一层；深层解释是否比表层更有价值？** |

不能通过保留样本或区分性验证的候选不得悄悄删除反证，应标为"削弱、否证或未知"。正确但显然的解释可以胜出；新奇程度不参与排序。

### 9.3 下一步取证按信息增益选择

优先寻找能够让两个领先解释产生不同结论的证据。只增加背景细节、无论结果如何都不改变分型或方案排序的取证延后。若一次验证同时支持所有假设，它通常不是区分性验证。

## 10. 创造性业务重设计（增强版）

### 10.1 先改业务机制，再映射系统

三个产物不得混写：

```text
ESS：当前业务本质是什么，哪些不变量和边界必须保留
BIZ：为了更好地产生业务结果，目标角色、责任、决定、承诺、控制和反馈怎样协作
TGT：用什么系统、数据、交互和技术机制承载已经选定的 BIZ
```

若第一版候选已经出现数据库、MQ、微服务、缓存或框架名，先删除技术名词重写。删掉后无法说明谁的行为、结果或风险发生了什么变化，说明它只是技术改造，不是业务重设计。

### 10.2 先发现业务机会，不只修已知缺陷

业务机会通常藏在现有系统没有正式拥有的结果和代价中。优先寻找：

- 用户、客服或运营长期手工补回系统没有兑现的结果；
- 某角色承担结果和风险，却没有信息、决定权或补救入口；
- 系统已经产生高价值信息，但没有反馈给能够改变结果的人；
- 局部指标持续改善，最终履约、客户结果或总成本反而恶化；
- 高频"例外"其实是稳定存在的业务模式或未被服务的场景；
- 等待、重复确认、跨边界搬运和风险转嫁没有创造业务价值；
- 现有能力重新组合后，可以服务邻近角色或消除一次交接，但当前边界把它们隔开；
- 规则、组织或规模变化使原业务承诺仍有价值，而现有履约机制已经失效。

机会信号只生成候选。它必须回到真实业务结果、责任人、受益/受损角色、证据和最小实验；"行业都这样做"或"技术已经具备"不能独立创建业务目标。

### 10.3 业务机制变换算子（增强版）

保持已确认不变量和安全底线，每次有意识地改变一个机制，再观察因果链：

| 变换 | 创造性追问 |
|---|---|
| 目标/指标重构 | 当前 KPI 是真实结果还是代理；能否在 KPI 变好时让真实结果变差？应怎样绑定结果护栏？ |
| 责任重配 | 决策权、执行责任、结果责任和补救责任是否落在不同角色，能否重新对齐？ |
| 控制点迁移 | 判断、校验或风险阻断能否移到更早、更局部、更接近权威事实的位置？ |
| 隐性显式化 | 隐含在人工、字段或异常分支里的义务、版本、期限、策略或例外能否成为一等业务概念？ |
| 闭环反馈 | 发送/执行能否变成"承诺—履约—回执—核对—补救"的闭环？ |
| 激励对齐 | 谁能从规则漏洞、信息差或责任转嫁中获益；能否让正确结果也是参与者更合理的选择？ |
| 反馈时滞缩短 | 哪个结果反馈太晚导致过量行动、积压或误判；能否更早给出可行动信号？ |
| 稳定与变化分离 | 哪些不变量应保持稳定，哪些渠道、规则或组织差异应成为受约束变体？ |
| 协作方式反转 | 推送/拉取、中心决定/本地自治、事前审批/事后监督的另一种组合是否更符合责任和风险？ |
| 例外正规化 | 高频人工绕行是否其实是合法业务模式，应建模而不是继续当异常？ |
| 价值与风险重配 | 能否减少无价值等待、重复确认或风险转嫁，同时保持责任可追溯？ |
| 能力重组与边界重画 | 已有能力能否组合成新的业务结果；哪些责任应吸收、拆出或交给更合适的角色？ |
| **问题反转** | **如果问题反过来看，解决方案会有什么变化？** |
| **极端假设** | **如果某个约束被极端放大，会暴露什么新机会？** |
| **意外组合** | **哪些看似无关的能力或机制可以组合产生新价值？** |

变换算子只负责产生候选。是否采用取决于事实、价值、兼容、成本、风险和可验证性。

### 10.4 候选光谱与实质差异

按问题实际空间考虑：不做、直接修复、机制治理、能力提炼、控制点迁移、业务机制进化、核心抽象变化。核心重设计至少保留"不做/现状"基线、一个最小机制改进和一个因果机制不同的结构性候选；若某层不成立，写清淘汰理由，不机械凑齐全部层级。

两个候选只有技术实现不同而业务角色、责任、决定、结果和反馈完全相同，属于同一个 `BIZ-*` 下的不同 `TGT-*`，不得伪装成两个业务候选。

### 10.5 `BIZ-*` 最小语义（增强版）

```markdown
### BIZ-<编号>：<目标业务机制>

- 来源问题与 `REV/ESS/CA`：
- 服务对象、真实目标结果与价值：
- 当前代理指标、指标失真和结果护栏：
- 必须保持的不变量：
- 当前业务机制及主要代价：
- 目标机制：触发 -> 决定/承诺 -> 行动/交换 -> 结果 -> 反馈/恢复
- 改变的角色、责任、权利、义务、控制点或边界：
- 为什么能改善结果的因果链：
- 与其他候选不同的预测：
- 各角色可见信息、可选行动、收益/代价与可博弈路径：
- 反馈回路、时滞、外部性、受损角色和二阶影响：
- 最小实验、指标、停止条件和失效条件：
- 兼容/迁移前提：
- 是否包含反直觉洞察（CI）：
- 状态：探索 / 待验证 / 提议 / 待批准 / 已批准 / 已否证
```

`BIZ-*` 可以大胆。状态为"待批准"的候选可以进入提议态 `TGT-*`，用于比较系统承载代价；只有业务责任人认可目标、项目证据支持因果链且最小实验或区分性验证成立后，`BIZ/TGT` 才能升级为已批准决策或实施输入。无法验证的候选保留为机会或未知，不得包装成需求。

## 11. 反证与停止（增强版）

使用 L0 五关 + 增强三关：

L0 五关：
- 可逆：能否回到事实；
- 区分：能否区分本系统与泛化常识；
- 稳定：换一组等价证据是否仍成立；
- 最小：删除后是否损失关键结构；
- 可决策：是否改变后续行动。

增强三关（创造性）：
- 溯因深度：候选解释是否达到深层或元层，而非仅表层解释；
- 反直觉性：是否存在反直觉洞察；若存在，证据是否充分；
- 组合价值：是否有通过意外组合或约束消除产生的新机会。

继续阅读材料已不改变骨架、分型或路径判断时停止。正式报告可以展开，但必须能压回 L0 一页骨架。

## 12. 失真模式（增强版）

### 12.1 基础失真模式（原有）

- 把 Redis、MQ、微服务、表结构直接写成业务本质；
- 从单条代码事实跳到目标架构；
- 只列概念、规则和问题，不形成主结构；
- 将所有变化都解释成策略，将所有实体都解释成聚合；
- 冲突并列记录但不升级判断；
- 用领域样例替代证据；
- 为覆盖方法清单制造无决策价值的产物。

### 12.2 创造性失真模式（新增）

- 把同义改写伪装成竞争解释，或为了"有创意"机械凑候选数量；
- 没有惊讶事实和基线解释就直接发明新抽象，或用任务标题冒充 `S-M0-Δ`；
- 把重述输入、方案上线后的目标指标或永远正确的常识写成"冒险预测"；
- 先选方案再倒推业务本质，只保留支持首选方案的证据；
- 把外部类比的成熟能力直接判成当前系统缺陷；
- 用生成假设的同一条样本冒充保留样本验证；
- `ESS` 后直接跳到技术方案，没有形成目标业务机制 `BIZ`；
- 只描述收益，不写受损角色、二阶影响、失效条件和最小实验。
- 优化代理指标却不验证真实结果，忽略参与者套利、反馈时滞和成本/风险外溢。

### 12.3 增强方法失真模式（新增）

- 使用多层次溯因但各层只是同义改写，未真正深入；
- 生成反直觉洞察但只是为了新奇，没有证据支持；
- 使用意外组合但不评估组合的实际可行性；
- 使用问题反转但不验证反转后的问题确实更值得关注；
- 使用约束消除但不区分物理约束和可改变约束；
- 使用假设链构建但链的每个节点没有独立的证据支持；
- 生成多个类比但不评估类比的质量和适用边界；
- 进行视角切换但只产生同义描述，不产生真正的洞察；
- 使用认知突破识别但把普通分析进展误认为认知突破；
- 进行溯因质量评估但评分标准主观，没有明确的判断依据。

### 15.3 典型使用场景

**场景 1：追问核心假设**
```
使用第一性原理 + 元认知方法：
1. 用 §3.6.3 约束消除追问"为什么这个约束存在"
2. 用 §3.7.1 认知盲区识别检查是否受锚定效应影响
3. 用 L0 附录 D §D.3.3 批判性思维清单逐项检验
```

**场景 2：识别反馈回路**
```
使用系统性思维 + 因果回路方法：
1. 用 §8.4 的因果回路与博弈方法画出反馈回路
2. 用 L0 附录 D §D.4.2 因果回路图简化版识别增强/平衡回路
3. 检查延迟是否导致问题难以追溯
```

**场景 3：设计区分性验证**
```
使用溯因验证方法：
1. 用 §3.2.2 溯因质量评估选择最值得验证的解释
2. 用 L0 附录 E 的实验设计方法选择验证策略
3. 用 §3.2.3 元层溯因检验验证框架本身是否有效
```

### 15.4 认知框架集成

四个底层框架的协作顺序：

```text
1. 复杂系统思维：建立对系统的基本理解
   -> 使用 §3.5 组合创新发现可能性
   -> 使用 §3.6.2 极端情况分析探索边界

2. 第一性原理：追问最基本的真理
   -> 使用 §3.6.3 约束消除挑战假设
   -> 使用 §3.6.1 问题反转发现新方向

3. 批判性思维：检验推理是否有效
   -> 使用 §3.7.1 认知盲区识别避免偏见
   -> 使用 §3.7.3 思维模型检验确保模型有效

4. 系统性思维：理解系统如何运作
   -> 使用 §8.4 因果回路与博弈分析干预效果
   -> 使用 §3.3.2 反直觉洞察生成突破性洞察
```
