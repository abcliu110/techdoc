## 0. 理论要解决什么

### 0.1 唯一终点

业务系统分析的终点不是“方法走完”或“附件齐全”，而是：

> **产出可独立阅读的理解层主文档**，使读者在不打开代码的情况下，能理解关键业务如何运转、对象如何关联、受何约束、失败如何收场、变更会伤及何处，以及哪些结论仍不确定。

理解层可以是一篇文档，也可以是一组连续文档；但必须有唯一阅读入口，并保证读者可按导航读完价值、全景、活动、关系、规则、失败恢复、实现映射与未知边界。过程卡片、专项取证、验证附件可以存在，但**不能替代理解层主文档**。主文档未达到本文深度标准，分析即未完成。

**人类阅读测试**（理解层验收的最低标准）：不阅读源码，仅通过理解层文档及其关系图、活动图，读者应能回答：

1. 系统解决什么业务问题？
2. 最重要的业务活动如何运行？
3. 核心对象与影响业务的非事实表如何关联？
4. 关键规则与状态变化是什么？
5. 失败后如何发现、恢复和人工处理？
6. 改变一个关键关系、配置或流程会影响什么？
7. 哪些是事实，哪些仍是推断或未知？

**未完成分析报告（合法产物，不是失败）**：时间盒到期（执行层时限）或必须停止（证据不可得、权限缺失、范围爆炸）时，交付**未完成分析报告**——它是主文档的诚实降级版，不是替代品：

- 逐切片标记状态：已完成 / 部分（注明哪些关过了、哪些没到）/ 未开始
- 对每个 SC-P0 逐关标记：过 / 不过（原因）/ 未及
- 明确缺口：U-* 清单、未验证候选事实、未覆盖结果族
- 给出继续路径：下一轮取证做什么、需要什么授权/证据
- 明确禁止：把未完成报告包装成"已完成"（公理 8）；把未完成报告当最终交付而不声明状态

### 0.2 L1 只回答的问题

1. 分析时脑子里应有哪些对象？
2. 如何识别、如何否证？
3. 以什么顺序建立认知？
4. 什么叫“深入”，什么叫“假深入”？
5. 结论允许强到什么程度？
6. 业务内容为何是三层、边界如何判定？

L1 **不回答**：用几小时、生成几份过程文件、路由哪个专项 SOP。那些属于执行层（L2）。

### 0.3 设计原则

| 原则 | 含义 |
|---|---|
| 通用 | 概念不依赖某行业话术、某技术框架或单一案例域 |
| 可判定 | 每个核心概念都有识别问句、正反例、否证方式 |
| 可分层 | 深度靠配额与条件触发，不靠全维打满 |
| 可证伪 | 竞争解释与反例是一等公民 |
| 最小核心 | 核心对象封顶；派生技法不得挤进公理层 |
| 主文档锚定 | 一切对象最终都要能写进主文档对应章节 |

### 0.4 十公理

1. **主文档终点**：无合格理解层主文档，则分析未完成。
2. **事实先于维度**：无事件轨迹，不得建立稳定领域模型结论。
3. **切片是分析单位**：类、表、接口、菜单、目录默认不是分析单位。
4. **叙事可去技术名**：删除类名、方法名、表名、接口名后不成立，则未完成业务理解。
5. **证据有类型局限**：单类证据不得支撑高影响结论。
6. **结论级别不可跃迁**：假设不得写成根因；推断不得写成已证实规律。
7. **深度靠配额**：全覆盖且平均浅，等于失败。
8. **缺口必须显式**：未覆盖写成已覆盖，属于过程造假。
9. **竞争解释默认存在**：对核心切片，至少保留主解释与一个竞争解释或明确未知。
10. **认知不自动授权变更**：除非任务模式升级，分析结论不自动变成实施指令。
11. **间接路径必须闭合**：声称 A 与 B 间接关联时，必须还原全部有效中间对象与路径，不得压缩成无语义的直连。
12. **图是认知产物**：影响核心理解的复杂关系图与活动图是主文档组成部分，不是附件装饰。

## 1. 分析问题类型（先定问题，再定模型）

不同类型的分析问题，主对象、主证据与“完成”定义不同。未声明问题类型，不得开始深挖。

| 类型 | 典型意图 | 主对象 | 主证据偏向 | 主文档完成定义 |
|---|---|---|---|---|
| 认知重建 | 接手、讲解、建立共同语言 | 切片因果、规则、失败 | 源码/配置/契约 + 必要运行 | SC-P0 过深度八关，可独立讲述 |
| 故障定位 | 解释异常、缩小根因 | 失败轨迹、假设集 | 运行证据优先，源码次之 | 根因候选可证伪，排除项有据 |
| 迁移/重构决策 | 替换、归一、兼容 | 契约、多实现、变更影响 | 多类互证 | 差异可裁决，风险可排序 |
| 设计合理性评审 | 评现状或评方案 | 目标约束 + 已有事实模型 | 已验证事实卡，而非感想 | 条件化结论，红线与权衡分开 |
| 数据治理/语义对齐 | 口径、血缘、约束 | 维度语义、约束、分布 | Schema + 样本 + 写入路径 | 业务语义与存储语义对齐或显式裂隙 |

**规则**：一次任务只允许一个主类型；若中途发现应升级类型，必须显式记录变更原因，不得静默漂移。

### 1.1 证据可得性建模（预期证据集 / 最小证据集 / 缺失推进）

每个任务类型在启动时声明其**预期证据集**与**最小证据集**；实际证据集低于最小证据集时，按"缺失推进"规则执行，不停止、不伪造：

| 类型 | 预期证据集 | 最小证据集 | 缺失时的推进规则 |
|---|---|---|---|
| 认知重建 | SRC+CFG+CON+DAT+RUN | SRC（或 DAT） | 按 §3.2 R7 受限定级；无运行证据时"实际发生"类结论禁止，登记 U-* |
| 故障定位 | RUN 优先 + SRC | RUN 或 SRC 之一 | 只有 SRC：假设集可缩小但不得宣布根因（公理 6）；必须运行验证后升结论 |
| 迁移/重构决策 | SRC+CON+DAT 多类互证 | SRC+CON 或 SRC+DAT | 单类证据时结论降为"推断"，不得支持高影响决定 |
| 设计合理性评审 | 已验证事实卡 | 事实模型（任意类型） | 事实模型未建立时只输出"待验证假设"，不评设计（对应 SOP-09 前置） |
| 数据治理/语义对齐 | DAT+SRC | DAT 或 SRC 之一 | 只有 Schema：语义对齐结论降为"推断"，口径差异登记 U-* |

**禁止**：实际证据集低于最小证据集时仍宣布完成（属于公理 8 缺口隐藏）；也不得因证据不足而放弃分析（推进规则保证合法路径存在）。

## 2. 最小本体论（八个核心对象）

只保留八个核心对象。更多标签若不能还原到这八类，不得进入 L1 强制层。

| 对象 | 符号建议 | 一句话 |
|---|---|---|
| 分析问题 | DQ / 问题类型 | 本次要回答什么、完成线在哪 |
| 业务切片 | SC | 有边界的业务场景单元 |
| 事实 | Fact（事件/动作/状态变化） | 发生了什么 |
| 维度 | Dim（参与者、对象、配置、资源） | 谁/什么在场景中扮演稳定角色 |
| 规则 | Rule / INV | 必须满足什么、什么不变 |
| 关系 | Rel | 结构归属、轨迹先后、或事实对维度的归因 |
| 证据 | E-* | 观察依据及其局限 |
| 结论 | Claim | 带级别与范围的断言 |


### 2.0 业务内容三元：元论证、边界与完备性

本节回答理论自洽性的关键缺口：**为什么业务内容要拆成事实 / 维度 / 规则三层，边界如何判定，以及它与“八对象”是什么关系。**  
先声明：三元不是“宇宙万物分类学”，而是**对已有业务系统做可验证理解时，最小且够用的内容分解**。

#### 2.0.1 与八对象的分工（先消歧）

| 层次 | 成员 | 角色 |
|---|---|---|
| **业务内容三元** | 事实、维度、规则 | 被分析的业务世界里“有什么内容” |
| **分析装置** | 分析问题、切片、关系、证据、结论 | 分析者用来组织、连接、证明内容的工具 |

关系（Rel）不是第四种业务内容，而是**内容之间的连接方式**（结构 / 轨迹 / 归因）。  
切片（SC）不是第四元，而是**一次有界讲述中，三元内容的组合单元**。

公式（分析用，非数学恒等式）：

```text
SC ≈ 选定边界内的（事实轨迹 × 参与维度 × 生效规则）
     + 必要关系说明
     + 证据与定级结论
```

#### 2.0.2 为什么是三个，不是两个

两层常见写法是“事件 + 实体”。它能描述发生与参与者，但**无法稳定安放约束**：

| 只保留两层时 | 规则被塞去哪里 | 失败模式 |
|---|---|---|
| 规则并进事件 | “提交订单”与“金额必须 ≥ 0”混为一谈 | 把约束误当成又一次发生 |
| 规则并进实体 | “订单必须有明细”变成订单的静态属性 | 属性与义务不分，变更影响说不清 |
| 规则不建模 | 只讲流程与对象 | 主文档缺“必须/不得”，深度八关的规则关必然失败 |

因此：在“发生了什么 / 关于谁与什么 / 必须怎样”三问上，**第三层不可消掉**。  
不是因为“三”这个数字神圣，而是因为业务理解至少要同时回答：

1. **发生**（动态变化）  
2. **指称**（稳定可指的参与者与资源）  
3. **约束**（许可、禁止、口径、不变量）

缺任一问，主文档都无法独立支撑接手、排障或迁移判断。

#### 2.0.3 为什么不是四个（例如再加“目标”）

四层常见加法是“事件 + 实体 + 规则 + 目标/意图/价值”。L1 **不把目标升为与三元并列的第四业务内容层**，理由：

| 候选第四层 | L1 安放位置 | 原因 |
|---|---|---|
| 目标 / 价值 / 意图 | **分析问题（DQ）** 与主文档 §0 价值关 | 目标首先是“本次分析要解释/服务什么”，属于任务与评价，不是系统内与事实同级的存在物 |
| 指标 / KPI | 规则中的计算口径，或结论中的观察断言 | 指标是度量规则或运行观察，不是独立本体层 |
| 界面 / 交互 | 事实的触发方式，或实现锚点 | 交互是进入事实轨迹的入口，不是第四内容层 |
| 数据模型 / 表 | 维度与关系的存储投影 | 属于实现锚点，不得反客为主 |

若某任务是“设计合理性评审”，目标约束进入 DQ 与评审标准，**仍然通过对现状三元的符合/违背来检验**，而不是另建一套与三元平行的“目标宇宙”。

保持三元的方法论收益：**强制层更少，边界判定更稳，AI 更不易叠床架屋。**

#### 2.0.4 完备性：两种不同的“封闭”

必须区分：

| 主张 | L1 是否主张 | 含义 |
|---|---|---|
| **分析完备（弱）** | 是 | 对任一进入主文档的业务说法，应能归入三元之一，或标为关系/未知/实现锚点；不得长期以“说不清类别”的概念支撑高影响结论 |
| **世界完备（强）** | **否** | 不声称现实中一切商业与组织现象只有这三类 |

因此：遇到暂时无法归类的概念，正确动作是登记 `U-*` 或降为实现细节，而不是硬贴标签，也不是立刻发明第五层。

#### 2.0.5 正交性标准（三元如何互相不可替代）

用三个操作测试正交性（通过则值得独立成层）：

| 测试 | 问法 | 结果 |
|---|---|---|
| 消去测试 | 删去该层后，主文档是否仍能回答对应业务问 | 删事实→不知发生；删维度→不知对谁；删规则→不知可否 |
| 变换测试 | 固定另外两层，只改该层，业务含义是否明显变化 | 只改规则（如是否允许负库存）可改系统合法性，故规则独立 |
| 证据测试 | 该层主要靠什么被观察 | 事实偏轨迹/日志；维度偏主数据/配置；规则偏分支、校验、口径与不变量陈述 |

#### 2.0.6 边界判定程序（消除重叠）

同一句话里常混有三元。分析时**拆句归类**，不整句单贴一个标签。

**步骤 1：先找变化**  
若描述的是“从一状态到另一状态 / 一次发生 / 一次结果”，核心是**事实**。

**步骤 2：再找可跨事实指称者**  
若名词在多个事实中重复出现、可被指认、可配置或可持久，核心是**维度**。

**步骤 3：最后找义务与口径**  
若去掉情态与约束词（必须、不得、仅当、按…计算）句子不再成立，核心是**规则**。

**步骤 4：仍双属时，用主问题裁决**

| 双属现象 | 默认归属 | 说明 |
|---|---|---|
| “状态”既像事实又像维度 | 状态**值的变化**→事实；状态**机定义/枚举集合**→维度或规则依附 | 一次“已审批”是事实；“审批状态可取值”是维度属性或规则约束的对象 |
| “配置”既像维度又像规则 | 配置**项本身**→维度；配置**被解释成必须怎样**→规则 | “折扣策略 A”是维度；“策略 A 下满 100 减 20”是规则 |
| “创建订单”既是事实又含规则 | 创建这一发生→事实；创建前置条件→规则 | 事实回答发生与否；规则回答可否发生 |
| “金额”既像维度属性又像规则 | 某单金额数值的产生/变更→事实或事实结果；计价口径→规则；金额字段作为对象属性→维度属性 | 拆成“值的变化 / 口径 / 属性” |
| “权限” | 授权关系与角色→维度；“仅经理可驳回”→规则；“驳回已发生”→事实 | 三角拆开写 |

**禁止**：因为某个词在代码里是一个类/一张表，就把整类概念永久钉死在单一层。

#### 2.0.7 最小反例（边界清晰性自检）

| 表述 | 错误归类 | 正确拆分 |
|---|---|---|
| 订单必须有至少一行明细 | 事实 | 规则（完整性）+ 维度（订单、明细行） |
| 库存从 10 变为 8 | 规则 | 事实（数量变化）+ 维度（SKU/仓） |
| 客户等级为金卡 | 事实 | 维度属性；若“因升级而变为金卡”则另有升级事实 |
| 超时自动取消 | 纯维度 | 规则（时序/触发）+ 取消事实（若已发生或可发生） |
| 表 order 有字段 status | 业务事实 | 实现锚点；业务上仍要还原为状态事实或维度属性 |

若分析者能稳定做上表拆分，三元边界即达到可操作自洽；若不能，优先补判定，不优先加层。

#### 2.0.8 理论自洽性的满星标准（对本节）

本节补齐后，三元模型应能回答：

1. 为何不是两层（规则不可消）  
2. 为何默认不加第四内容层（目标等进 DQ/价值关/规则口径）  
3. 主张的是分析完备而非世界完备  
4. 重叠时有可执行的拆句与裁决程序  
5. 与八对象、切片、关系不抢定义

仍不声称：三元可取代组织理论、战略理论或全部产品设计理论——那些超出“已有业务系统认知重建”的问题域。


### 2.1 业务切片（SC）

**定义**：在明确触发、参与角色、业务结果与边界条件的情况下，可被单独讲述的业务场景单元。

**是切片**：

- 有可叙述的触发与结果（“当…则…”）
- 能指出成功与失败的业务含义
- 可以独立作为分析与验证单位

**不是切片**：

- 单个菜单项、单个按钮文案
- 单个类、单张表、单个 API
- “整个模块”“全部功能列表”

**识别问句**：

1. 谁在什么业务意图下启动？
2. 业务上成功长什么样？
3. 失败时经营侧看到什么？
4. 边界外哪些相关事故意不纳入本次 SC？

**否证**：若只能列出页面或接口名称，无法叙述触发到结果，则它不是 SC，只是入口线索。

**切片卡必填字段（SC-P0/P1 强制）**：

| 字段 | 内容 |
|---|---|
| 业务层 | 平台层 / 业务层 / 渠道层（平台型系统必须标注；单一业务系统可填"业务层"） |
| 共享资产声明 | 本切片依赖的共享维度/规则/证据（多人并行分析时明确负责切片，共享资产单独声明负责人） |
| 触发/结果/成功/失败 | 对应识别问句四项 |
| 边界外声明 | 明确不纳入本切片的相关事实 |

**共享资产规则**：切片之间共享的维度、规则、不变量、权威数据源，由首次引用它的切片声明并登记（维度必须可回溯到事实，共享资产不例外）；并行分析时共享资产由指定负责人维护，其他切片只引用不重复定义。**禁止**：每个切片各自复制一份共享维度定义（造成同一概念多版本）。

### 2.2 事实（Fact）

**定义**：业务上可观察的事件、动作或状态变化，回答“发生了什么”。

**是事实**：单据已提交/作废；额度已预占/释放；审批已通过/驳回；任务已创建/完成/超时；款项已收取/退回。

**不是事实**：实体静态属性（多属维度）；纯技术步骤（除非本身是业务承诺，否则只作实现锚点）。

**业务承诺判定问句**（区分"纯技术步骤"与"业务承诺"）：对任何一个疑似事实的表述，依次问：
1. 去掉技术词后，是否仍是**外部可观察的行为**？（如"支付超时自动退款"去掉技术词仍成立；"连接重试 3 次"去掉后不成立）
2. 是否**影响角色决策**？（收银员/顾客/后厨是否会据此改变行为）
3. 是否产生**业务后果**（钱/货/状态/合规）？

任一为"是" → 业务承诺，可作事实；全否 → 纯技术步骤，只作实现锚点。示例："超时后自动释放预占额度"——①外部可观察 ②影响角色决策 ③产生业务后果 → 是业务承诺；"线程池大小 100" → 三项全否 → 技术步骤。

**识别问句**：用动词与结果问，不用“有哪些东西”问。

| 问法 | 通常得到 |
|---|---|
| 发生了什么？产生了什么结果？ | 事实 |
| 谁做的？对什么做的？依据什么配置？ | 维度 |
| 是否允许？失败是否必须补偿？ | 规则 |

**否证**：去掉所有程序符号后，若不再存在可被业务理解的变化，则原表述只是实现转述，不是业务事实。

**候选事实（反向分析）**：在只有实现痕迹（代码/配置/Schema）可观察时，事实是从痕迹推断出的**候选事实**——定级为"推断"，必须经 §3.2 R3 的验证程序升级为事实（定级为"直接事实"或"交叉验证结论"）后才能进入主文档事实层。未验证的候选事实不得写入主文档事实层，只能保留在候选清单。**禁止**把实现痕迹直接写成事实（见 §3.5"痕迹直译"反模式）。

### 2.3 维度（Dim）

**定义**：在多个事实中重复出现、可被指称的业务实体、角色、资源或配置对象。

**关键约束**：维度从事实中派生，**不能**在零事实时先验“领域模型完成”。

**是维度**：客户、组织节点、账期、价目、仓库、审批角色、通道、模板、策略配置等。

**不是维度**：一次请求的临时局部变量、仅实现细节的传输对象字段堆。

**否证**：若某概念从未出现在任何 SC 的事实轨迹中，不得写入主文档核心概念层；最多进未知或待观察。

### 2.4 规则（Rule / INV）

**定义**：对事实与维度施加的约束、许可、计算口径或不变量。

**类型（通用，不强制用完）**：许可；完整性；计算；时序；不变量 INV。

**否证**：只描述“代码里分支很多”，给不出业务必须/不得，则尚未抽出规则。

### 2.5 关系（Rel）

L1 只承认三类关系（见第 4 章）。更多细分是派生技法，不得上升为人人强制的平行分类学。

### 2.6 证据（E-*）与结论（Claim）

见第 6 章。二者是一等对象：没有证据类型与结论级别的分析散文不合格。

### 2.7 对象最小可验证形态（P0 强制）

八对象的自由文本不足以支撑验收。对 **SC-P0** 的核心对象，强制以下最小形态（SC-P1 放宽为可选，SC-P2 清单化）：

| 对象 | 最小可验证形态 | 可检查什么 |
|---|---|---|
| 规则 BR | 前提-动作-后置三元组（When…Then…Ensure…） | 与代码分支/校验一一对应 |
| 不变量 INV | 可检查断言（数据库约束/代码校验/测试用例之一） | 断言是否真实存在且生效 |
| 状态机 SM | 状态集合 + 合法迁移表 + 非法迁移清单 | 非法迁移是否被代码阻止 |
| 关系 Rel | 六要素卡（类型/方向/基数/建立时机/变更影响/业务语义） | 六要素是否都有证据 |
| 事实 Fact | 候选事实卡（痕迹位置/推断链/置信度）或观察记录 | 是否能回溯到痕迹或观察 |
| 维度 Dim | 可回溯声明（回溯到哪个候选事实） | 是否违反"维度从事实派生" |
| 结论 Claim | 级别 + 证据 ID + 反证/未知（见 §6） | 级别是否与证据匹配 |

**作用**：验收从"人读判断"升级为"结构可查"——八关中的规则关、轨迹关、证据关按本表逐项核对；无法给出最小形态的对象，该切片不得判定深写完成。

### 2.8 对象全景卡模板（执行脚手架，P0 强制）

全景卡是对象的完整形态模板，回答"这个对象是什么、如何运转、如何失败"。**其中⑥生命时间线是叙事要求的落地模板**——叙事关/轨迹关按此模板验收。§2.7 规定了"形态"，本节给出"填什么、怎么填"。

```text
【对象全景卡：{对象名}】

① 身份：表名/类名 + 业务名称
② 结构：核心字段（写业务含义，不裸列字段名）
③ 关系：关联对象及基数（结构/轨迹/归因）
④ 行为：创建/更新/删除/查询的业务入口
⑤ 交互：谁在什么业务场景下调用它
⑥ 生命（时间线叙事——去技术名，用"→"连接）：
   触发条件 → 状态变化1 → 状态变化2 → ... → 终态
⑦ 实现：代码位置（E-SRC 定位：文件:行号）
⑧ 失败：失败模式 + 恢复路径 + 人工介入点
⑨ 证据：E-* 证据 ID + 结论级别
⑩ 未知：U-* 登记
```

**⑥生命时间线示例（合格，可去技术名；仅为表达样例，不代表任何具体系统事实）**：

```text
操作者提交业务单据后，系统创建处理任务，状态为"待处理"。
→ 系统按适用规则选择处理通道，状态变为"处理中"。
→ 处理成功：状态变为"已完成"，并向相关角色反馈结果。
→ 处理失败：状态变为"失败"，触发重试或补偿；
   仍失败则进入待人工处理。
```

**⑥生命时间线反例（不合格，调用链冒充）**：

```text
提交 → XxxController → XxxService → XxxWorker → 外部系统
（删除类名后只剩箭头，没有业务语义，不通过）
```

**使用规则**：①SC-P0 的核心对象必须按本模板填写，缺任一项该对象未深写；②⑥生命时间线必须可去技术名；③⑦实现与⑥叙事必须一一对应（每条叙事能找到代码证据）；④⑨证据/⑩未知按 §6 定级，禁止全篇确定语气。

## 3. 分析顺序与主文档锚定

### 3.1 强制顺序

```text
1. 声明分析问题类型与完成线
2. 识别切片候选，并做深度分级与配额
3. 对 SC-P0（及必要的 SC-P1）提取事实轨迹
4. 从事实派生维度
5. 抽出规则与不变量
6. 标定关系（结构 / 轨迹 / 归因）
7. 挂接证据，定级结论；登记竞争解释与未知
8. 仅在需要追溯时补实现锚点
9. 收敛为《深入业务分析》主文档
```

**禁止逆序**：先全量结构模型后补业务故事；先优化建议后补事实；先全量清单后发现没有切片。

**顺序的性质**：§3.1 是**产物组织顺序**（主文档的叙事/论证顺序），不是取证顺序。既有系统分析（认知重建）的实际取证路径是从实现痕迹出发的反向路径，按 §3.2 反向分析操作程序执行；正向顺序用于组织最终产物，反向程序用于生成产物内容。二者不冲突：产物仍按 3.1 组织，取证按 3.2 执行。

### 3.2 反向分析操作程序（R1-R7，从实现痕迹到业务语义）

**适用场景**：既有系统认知重建、迁移/重构决策中的事实建模——分析者面对的是代码、配置、Schema、运行日志，业务语义需要重构而非观察。**实现痕迹（代码/配置/Schema/日志）是反向分析的线索源，不是终点锚点；本程序的终点是产出可验证的业务语义，不是描述代码。**

**核心立场**：反向分析不改变八对象与三类关系（不新增本体），只改变**对象如何被发现与验证**：反向路径中产生的所有"事实/维度/规则/关系"都是**候选**，必须经验证升级后才能进入主文档。

#### R1 实现痕迹盘点（候选线索，非业务结论）

从可观察入口出发盘点痕迹，输出**候选线索清单**：

- 入口痕迹：Controller/消息监听/定时任务/Shell/脚本/报表入口
- 数据痕迹：核心表/字段/枚举/Schema 约束/数据分布
- 配置痕迹：配置项/开关/路由/外部依赖配置
- 运行痕迹（如有）：日志/指标/Trace/失败记录

**禁止**：把痕迹清单写成业务结论（"表存在"≠"业务概念存在"）；痕迹清单是候选线索，不是主文档内容。

#### R2 候选事实生成

从**写痕迹**（insert/update 操作、状态流转、消息发送、任务执行、外部调用）反推候选事实：

| 痕迹模式 | 候选事实 | 示例 |
|---|---|---|
| 写入口（insert/update/状态变更） | "某业务对象被创建/修改" | 业务任务创建 |
| 状态流转代码 | "某状态发生迁移" | 待处理→处理中 |
| 消息发送/订阅 | "某事件被发布/消费" | 点菜事件发布 |
| 定时任务执行 | "某周期业务被触发" | 交班汇总生成 |
| 外部副作用（HTTP/文件/命令） | "某外部动作发生" | 向外部系统发送指令 |

每个候选事实必须标注：痕迹位置（E-SRC）、推断链、当前置信度（推断）。**候选事实≠事实**。

#### R3 候选事实验证与升级/降级

| 条件 | 升级/降级 |
|---|---|
| 两类独立痕迹互证（如源码 + Schema + 配置，生成链不共享环节） | 升级为**交叉验证结论**，可进入主文档事实层 |
| 单一痕迹但语义明确（写入口 + 无歧义业务含义） | 升级为**直接事实**（限定在声明范围内） |
| 只有单一源码痕迹且语义需要推断 | 保持**推断**，不得进入事实层 |
| 与运行/数据/人员证据矛盾 | 降级或登记 X-* |
| 无法验证 | 登记 U-*，不得写入事实层 |

验证顺序优先用最小区分性证据（§6.4），不必对每个候选做全量取证。

#### R4 维度候选派生

- 从候选事实中的名词（参与者/对象/配置/资源）提取**维度候选**
- 维度候选必须回溯到至少一个候选事实；**未出现在任何候选事实中的代码实体 → 实现锚点或未知，不得进入维度层**
- 与 L1"维度从事实派生"一致：反向路径下是"从候选事实派生维度候选，验证后进入维度层"

#### R5 规则候选与关系候选

- 规则候选：从分支/校验/断言/状态机/配置口径代码提取"可能存在的业务规则"，标注推断
- 关系候选：按 R6 映射表从技术关系提取候选业务关系，标注推断
- 规则/关系候选同样按 R3 的验证程序升级/降级；**禁止**把代码分支数量直接当规则（见 §3.5）

#### R6 技术关系 → 业务关系映射表

反向分析先遇到技术关系，以下映射产生**候选**业务关系（映射本身不是结论，须回到业务语义验证）：

| 技术关系模式 | 候选业务关系 | 验证线索 |
|---|---|---|
| 调用（A 调用 B） | 轨迹关系候选（A 触发 B） | 是否构成业务叙事的先后/分支 |
| 消息发送/订阅 | 轨迹关系候选（跨系统） | 消息语义与消费行为 |
| 配置引用（A 读取 B 的配置） | 归因链接候选（A 归因到 B） | 改 B 配置是否改变 A 的行为 |
| 外键/关联表/冗余字段 | 结构关系候选 | 生命周期是否绑定 |
| 继承/接口实现 | 结构关系候选（变体）或未知 | 业务语义是否真不同 |
| 状态流转代码 | 轨迹关系候选 + 规则候选 | 状态机是否业务承诺 |

**映射规则**：①映射产出的是候选，进入主文档前必须满足 §4 的验证（类型/方向/基数/建立时机/变更影响/业务语义六要素）；②套不上三类关系时登记 U-* 或"弱相关，不建模"，**禁止硬贴**；③数据模型/表本身的存储形态（如逗号分隔字段、反规范化）是条件扩展信息，不改变关系候选的类型判定。

#### R7 证据受限的推进策略（只有源码时的合法结论）

当无法取得运行证据（E-RUN 不可得）时，推进不停止，但结论级别受限：

| 想陈述的内容 | 只有源码时合法级别 |
|---|---|
| "系统支持某能力" | 直接事实（E-SRC 范围） |
| "某业务事件可能发生/可能如此流转" | 推断（必须标注） |
| "某业务事件实际发生/实际如此运行" | **禁止**（登记 U-* 或降级为推断） |
| "性能/容量/故障实际表现" | **禁止**（登记 U-*） |

**只有源码时的完成标准**：SC-P0 的证据关按"源码证据 + 静态互证"的边界定级，不要求伪造运行证据；关键语义无法验证的登记 U-* 并在主文档 §5 写明对结论的影响。**反向分析的停止条件**：候选事实已收敛（不再产生高价值候选）、关键候选已验证或登记 U-*、继续取证的预期信息增益低于成本（对应 §5.3）。

**反向分析的自检**：产物主文档仍按 §3.1 正向顺序组织；若主文档中事实层出现无法回溯到候选事实清单的"事实"，视为造假（对应公理 6、8）。

### 3.3 主文档标准骨架（通用）

主交付**有且仅有一篇**主文档（附件另计）。推荐骨架：

```text
《{分析对象} 业务分析》理解层

0. 阅读入口 / 十分钟结论
   - 业务价值与存在理由
   - 核心切片（通常 2–3 个）
   - 最大风险 / 最大未知
   - 问题类型、深度范围、明确不覆盖项

1. 业务全景与复杂关系
   - 切片地图与分级理由
   - 切片如何组成经营过程
   - 影响核心业务的对象关系与非事实表关系

2. 核心切片深写（正文主体，应占主要篇幅）
   每个 SC-P0：
   2.1 因果叙事（可去技术名）
   2.2 正常活动图与事实轨迹
   2.3 参与维度与关键非事实表
   2.4 规则与不变量
   2.5 失败恢复活动图、补偿、人工介入
   2.6 关键关系与间接路径（只写影响理解或变更者）
   2.7 证据与结论定级
   2.8 竞争解释与未决项
   2.9 设计决策（DEC 卡，有证据时写；无证据写设计意图未知）——回答"为什么这样设计"

3. 横切约束（仅写实际碰到的）
4. 设计与实现（机制 + 决策，深度按任务类型）
   - 机制层（怎么样）：分层、并发模型、数据流、部署拓扑——按任务需要深写（认知重建=中、迁移决策=深、故障定位=浅）
   - 决策层（为什么）：DEC 卡汇总；无证据不得虚构意图
5. 风险、未知、冲突、下一步
```

理解层可按阅读需要拆成多篇，但 §0 必须是唯一入口，且上述职责不得因拆分而丢失。

**映射规则**：L1 对象若不能落入上表某节，要么不该进入强制分析，要么主文档骨架缺节——应改骨架或删对象，而不是另起平行文档冒充完成。

**设计分析要求（回答"怎么样/为什么"）**：主文档不得停留在"业务如何运转"——对每个 SC-P0 必须回答**机制如何设计**（§4 机制层：谁调度、如何并发、数据如何流、故障如何隔离）与**为何如此选择**（§2.9 DEC 卡，按 §3.6 D1-D5 程序）；只有业务叙事没有机制与决策的主文档，视为未完成（对应"决策神化/历史审判"反模式）。

### 3.4 深度八关（主文档验收）

对每个 **SC-P0**，必须同时满足：

| 关 | 名称 | 合格标准 |
|---|---|---|
| 1 | 价值关 | 说清该切片对经营/履约/风控的不可替代性或核心贡献；**遗留系统允许合法出口**："价值不明/正在退役/历史继承"，前提是给出证据（无当前调用方、功能被替代、无业务 owner），不得编造价值 |
| 2 | 叙事关 | 去技术名后叙事完整可读；SC-P0 具备正常活动图 |
| 3 | 轨迹关 | 有事件/状态变化，而非名词并列；反向分析中允许"候选事实→验证"标注来源（观察/推断/交叉验证） |
| 4 | 规则关 | 有必须/不得/口径，不只 happy path |
| 5 | 失败关 | 失败如何被发现、如何恢复、是否人工介入；SC-P0 具备失败恢复活动图 |
| 6 | 影响关 | 关键变更伤历史还是只伤未来，谁受影响 |
| 7 | 证据关 | 关键断言有证据类型、范围；假设不冒充事实；**只有源码时按 §3.2 R7 的受限级别定级，不得伪造运行证据** |
| 8 | 反例关 | 至少 1 个**中强度以上**竞争解释，或显式未知与待验 |

少任一关：该切片未深写；若全部 SC-P0 未过关：主文档不合格。

**竞争解释三强度**（反例关的最低门槛 = 中强度）：
- **强**：有独立代码/数据/运行支持，替代机制可运行，仅结论被主解释覆盖
- **中**：替代机制机制上可运行（能说清如何发生），但暂无直接证据
- **弱**：纯推测，无机制描述——**不计入反例关**

弱解释不算"已通过反例关"；只有强/中解释或显式未知（U-* + 待验设计）才算过关。

### 3.5 假深入

- 技术栈与目录巡礼代替业务故事
- 枚举/字段/接口全量代替因果
- 调用链顶替叙事
- 很多切片每段三行，无 SC-P0
- 过程件很全，主文档只是目录
- “详见附件”代替正文应写清的因果与规则
- **痕迹直译**：把实现痕迹直接写成业务事实（"有 XxxJob 方法"→"业务动作已完成"），未按 §3.2 R2/R3 走"候选事实→验证→升级"；痕迹直译同时违反公理 6（级别跃迁）与公理 8（缺口隐藏）
- **静态硬贴**：把技术关系直接当业务关系（"A 调用了 B"→"A 触发 B 的业务事件"），未按 §3.2 R6 映射 + 验证；套不上三类关系时未登记 U-*
- **决策神化**：把"现状如此"直接写成"当初有意设计"，未走 D1-D5 程序——现状可能是历史遗留、偶然事故或兼容约束，不全是设计意图
- **历史审判**：用今天的约束审判历史决策——"现在不该用文件存储"不等于"当时选择文件存储是错的"；当时合理性必须按当时约束判断

### 3.6 设计意图与决策分析（D1-D5，回答"怎么样设计"与"为什么这样设计"）

**定位**：主文档不仅要回答"系统如何运转"（业务层叙事），还要回答"机制如何设计"（怎么样）与"为何如此选择"（为什么）。设计决策是**解释性结论（Claim）**，不是新对象——必须按 §6 定级，并区分四类成因。**适用深度按任务类型**：认知重建默认中（每个 SC-P0 至少 1 张 DEC 卡）、迁移/重构决策默认深（全部核心决策点）、故障定位默认浅（仅影响根因的决策点）。

#### D1 决策点识别（从"怪点"出发）

怪点 = 代码中不寻常、不直观、或代价明显偏高的选择。识别问句：

- 这里为什么不用更简单的做法？（为什么文件存储而不是数据库？）
- 为什么是这个结构？（为什么逗号分隔 lid 而不是关联表？）
- 为什么是这个参数？（为什么重试 1→2→4 分钟？为什么 TTL 15 分钟？）
- 为什么是这里？（为什么在业务事务内创建任务？）

产出：**决策点清单**（每个决策点 = 一个待回答的"为什么"）。识别不出决策点本身是信号——要么系统过于直白，要么分析没有深入机制层。

#### D2 四类成因分类（先分类，再问为什么）

| 成因 | 含义 | 识别线索 |
|---|---|---|
| **有意决策** | 当时有人权衡过 | 设计文档/ADR/评审记录/注释/当事人访谈 |
| **历史遗留** | 当时环境如此，无记录、当事人不可追溯 | 无任何意图证据，只能按当时上下文推断 |
| **偶然事故** | 由 bug 修复/临时方案演化成正式行为 | 提交历史显示先"临时绕过"后"转正" |
| **兼容约束** | 为兼容老数据/老调用方/老设备不得不如此 | 存在历史数据兼容代码、废弃字段保留、双版本接口 |

**分类本身就是结论**，需证据；无法分类时登记 U-*，不得默认"有意决策"。

#### D3 决策证据收集（"为什么"的证据链）

| 证据源 | 能证明什么 | 不能证明什么 |
|---|---|---|
| git blame/log | 何时引入、相邻提交、当时代码状态 | 为什么引入（commit message 常只说"改了什么"） |
| 引入时 diff | 引入时的规模/可选项/上下文 | 决策时的权衡过程 |
| E-DOC（设计文档/PRD/ADR） | 当时声明的意图 | 意图是否真的被执行 |
| E-HUM（当事人访谈） | 当时的权衡与约束 | 记忆是否可靠（需交叉验证） |
| 代码注释 | 决策现场留下的"为什么" | 注释是否过时 |
| 替代方案推断 | 当时技术栈中可用的其他选项 | 是否真的考虑过 |

**规则**：git 只证明"何时引入"，意图必须由 DOC/HUM/注释/上下文推断；单一意图证据 = 推断级别，两类独立证据 = 交叉验证结论。

#### D4 决策逻辑重建（当时合理性）

- 还原**当时约束集**：当时规模（数据量/主体数/并发）、当时框架版本、当时业务需求、当时可用技术、当时团队上下文
- 判断：在当时的约束下，该选择是否合理？（合理 / 勉强 / 不合理）
- **禁止**：用今天的视角审判历史决策（"现在不用文件存储"≠"当时选择文件存储是错的"）

#### D5 决策现状评估（当前合理性）

- 检查约束是否变化：规模×10？框架升级？新需求出现？协议生态变化？
- 输出**历史合理性 vs 当前合理性分离**（可以"当时合理、现在过期"）
- 当前不合理 → 形成 I-*（技术债）或 R-*（风险），供 SOP-07 闭环，**不自动变成实施指令**（公理 10）

#### DEC 卡（设计决策卡，产出形态）

```text
DEC-xxx 决策点：当时问的问题
当时约束：规模/框架/业务/团队上下文（含证据）
可选方案：当时考虑过的替代 / 可推断的替代
选择与理由：证据（git/DOC/HUM/注释 + 定级）
成因分类：有意决策 / 历史遗留 / 偶然事故 / 兼容约束
当时合理性：合理 / 勉强 / 不合理（按当时约束）
当前合理性：仍合理 / 已过期（约束变化）
影响面：伤历史还是只伤未来（对应八关影响关）
```

**禁止**：无证据地把"现状"写成"有意设计"（决策神化）；用今天标准审判历史（历史审判）；把 DEC 卡当验收装饰品（无证据、无定级的 DEC 卡等于没有）。

## 4. 关系理论（三类，通用）

### 4.1 三类关系

| 类型 | 含义 | 主要出现在 | 典型问句 |
|---|---|---|---|
| **结构关系** | 归属、拥有、层级、配置引用、多值关联 | 维度↔维度 | A 是否拥有/包含/引用 B？生命周期是否绑定？ |
| **轨迹关系** | 触发、先后、分支、补偿、重做 | 事实↔事实 | A 是否导致/先于/补偿 B？是否同一业务主体上的序列？ |
| **归因链接** | 事实实例指向其执行所用的维度/配置 | 事实→维度 | 这次发生是否落在某配置、通道、策略、资源上？ |

不能归入三类时：**登记未知**，禁止硬贴标签。不要把结构关系写成事实轨迹；不要把一次运行归因写成永恒拥有。

**反向分析**：若关系候选来自代码技术关系（调用/引用/订阅/继承等），先按 §3.2 R6 映射表生成候选，再按本节验证；映射表产出的仍是三类关系，不新增关系类型。

### 4.2 判定顺序

```text
1. 两端首先是事实还是维度？
2. 若两端皆事实 → 只尝试轨迹关系
3. 若两端皆维度 → 只尝试结构关系
4. 若事实指向维度/配置 → 归因链接
5. 仍不成立 → U-（未知关系）或“弱相关，不建模”
```

### 4.3 关系最小字段

| 字段 | 内容 |
|---|---|
| 类型 | 结构 / 轨迹 / 归因 |
| 方向与基数 | 谁指向谁，1/N |
| 建立时机 | 设计时 / 初始化 / 配置维护 / 交易执行 |
| 变更影响 | 热生效 / 不追溯历史 / 需处理在途或历史 / 禁止 |
| 业务语义 | 一句不含技术词的说明 |

存储形态、级联、桥接、历史版本策略等为**条件扩展**，仅变更风险高或任务需要时展开。

### 4.4 核心四问 vs 条件四问

SC-P0 关键关系必答：是什么；何时建立/变更；如何被找到；变更影响历史还是未来。

条件四问（级联、约束、全部使用方、存储细节）仅在删除、迁移、数量承诺、多实现冲突等触发时展开。

### 4.5 间接关系路径闭合

如果结论声称对象 A 与对象 B 存在间接引用，不得把真实路径压缩成无中间语义的 `A → B`。必须还原并分析 A 到 B 的完整有效路径：

```text
A → 中间对象C → 关联对象D → 配置对象E → B
```

路径中的每个中间对象和每条关系边都是结论的一部分。任何一跳未说明或缺少证据时，只能写成"已发现的候选路径"或登记未知项，不得宣称 A 与 B 的关系已经完整闭合。

#### 4.5.1 中间对象纳入判据

"所有关联对象"指构成 A 到 B 业务语义路径的全部中间对象，不等于遍历整个技术调用图。对每个候选中间对象依次判断：

1. 删除该对象后，A 是否仍能以相同条件、相同语义找到 B？
2. 删除该对象后，最终业务结果、适用范围、优先级或历史解释是否变化？
3. 该对象是否承担桥接、路由、资格判断、规则解释、版本选择或权威映射职责？

任一问题回答"是"，该对象即为关系路径节点，必须进入关系分析。不改变业务语义的纯实现细节，只进入实现映射，不进入读者关系主图。

#### 4.5.2 节点与边的最小内容

| 分析项 | 必须回答 |
|---|---|
| 对象角色 | 是业务对象、配置、规则、关联对象、快照，还是纯实现载体？为什么存在？ |
| 方向与基数 | 谁引用谁，1:1 / 1:N / N:1 / N:N |
| 连接方式 | 业务标识、外键、桥接记录、配置解析、事件关联还是运行时计算 |
| 建立与维护 | 何时、由谁建立、修改、失效和删除 |
| 生效条件 | 是否允许为空、重复或多路径命中；过滤条件、版本、优先级与适用范围 |
| 权威与使用方 | 谁负责解释该关系；哪些业务活动读取或改变它 |
| 变更影响 | 影响历史、在途还是未来；是否需要兼容、迁移或重算 |
| 失败后果 | 断链、错配、重复和冲突的业务后果 |
| 证据边界 | 每个节点和边分别由什么证据支持；哪些仍是推断或未知 |

#### 4.5.3 多路径闭合

如果 A 到 B 存在多条有效路径，必须列出声明版本、配置和业务范围内的所有已知有效路径，不得只选择最容易解释的一条：

```text
路径1：A → C → B
路径2：A → D → E → B
路径3：A → 规则或配置F → B
```

对每条路径说明：适用条件、是否可能同时生效、冲突时的优先级、是否产生不同结果、当前权威路径、历史或兼容路径。动态路由、运行时配置、反射、脚本或外部系统使路径无法穷尽时，必须区分"已发现路径"与"尚未排除路径"，并登记 `U-*`。

#### 4.5.4 展示与验收

复杂间接关系采用两层展示：

1. **全景图**：可使用 `A ⇢ B` 表示间接关系，但必须标注路径 ID 并链接详细图。
2. **详细路径图**：完整展开全部中间对象和每一跳关系。

详细图旁提供路径说明表：

| 路径 ID | 起点与终点 | 中间对象 | 适用条件 | 方向/基数 | 生效时机 | 失败后果 | 证据/未知 |
|---|---|---|---|---|---|---|---|
| REL-PATH-001 | A → B | C、D、E |  |  |  |  |  |

出现以下任一情况时，关系分析不得判定完成：

- 把间接关系画成直接关系，且没有详细路径图；
- 遗漏桥接对象、配置对象、规则对象或其他改变业务语义的中间对象；
- 只写最终外键或结果，未解释完整查找和生效路径；
- 已知存在多条路径，却只分析其中一条；
- 中间关系边缺少方向、基数、生效条件、变更影响或证据；
- 动态路径无法穷尽，却宣称关系完整；
- 关系图、业务活动图、关系说明表和实现映射中的路径互相矛盾。

路径未闭合时，不得对 A 与 B 的完整基数、级联行为、权威性和变更影响作确定性结论。

### 4.6 非事实表与复杂结构关系

**非事实表**：不直接记录核心业务事件，但承载主数据、配置、规则、字典、关联、路由、快照、版本或运行控制的存储结构。它不是新的业务本体，而是维度、规则、结构关系或控制机制在存储层的投影。

识别与处理原则：

1. 不根据表名直接推断业务语义；
2. 先说明它解释、约束或连接了哪些业务事实；
3. 再判断它属于主数据、配置、规则、字典、桥接、快照、版本还是运行控制；
4. 影响核心业务活动的非事实表必须进入理解层关系展示；
5. 间接引用必须遵守 §4.5 路径闭合；
6. 星型、雪花型、SCD 等数仓术语仅在数据仓库、历史口径或迁移任务触发时使用，不得作为通用强制本体。

每个影响核心业务的非事实表至少说明：

```text
业务作用
为什么不能直接并入事实表
关联的事实对象
方向与基数
生效条件与优先级
创建、修改、失效、删除生命周期
写入者与读取者
影响哪些业务活动
缺失、重复、冲突时的业务后果
证据与未知项
```

复杂关系采用：

```text
全局关系总览
→ 主题关系子图
→ 关系语义与生命周期说明
→ 表、字段和代码实现映射
```

图中边必须写业务语义，例如"选择""生成""限制""解释""授权"，不得只写"关联"。图过大时按主题拆分，不得通过删除关键节点换取整洁。

## 5. 深度分级与配额（认知经济学）

### 5.1 切片深度级（SC-P*）

| 级别 | 含义 | 主文档要求 |
|---|---|---|
| **SC-P0** | 本任务必须讲透的核心切片 | 过深度八关；占主要篇幅；含正常与失败恢复活动图 |
| **SC-P1** | 重要但非本任务第一焦点 | 叙事 + 关键规则 + 主要失败；关系可减负；深写时同样需要活动图 |
| **SC-P2** | 边缘/低频 | 地图中点名 + 简述，可进未覆盖 |
| **SC-P3** | 本次只浅覆盖的边缘切片 | 可附录或登记未覆盖；不得因场景是异常就自动归入 P3 |

SC-P* 是**分析深度配额**，不是缺陷严重度，也不是"正常/异常"场景类型。严重度用 SEV-* 等另一套符号，禁止混用。失败、补偿和恢复是核心切片内部场景，默认跟随 SC-P0/P1 深写，不因异常而自动降级。

### 5.2 分级靠排序与名额

```text
候选分 = 不可替代性(0-5)
        + 失败不可恢复或资金/库存/合规冲击(0-5)
        + 频率、变更率或事故率(0-3)
        + 跨边界耦合或多实现纠缠(0-3)

取分最高者进入名额；其余降为 SC-P1/P2/P3
```

频率只是输入之一，不得使用固定日调用阈值作为通用 P0 标准。

**名额 = f(任务类型, 切片总数, 证据可得性)**，不再使用固定值：

| 任务类型 | 候选切片总数 | SC-P0 名额 |
|---|---|---|
| 认知重建/迁移决策 | > 15（大系统） | 3-5 |
| 认知重建/迁移决策 | 5-15（中系统） | 2-3 |
| 认知重建/迁移决策 | < 5（小系统/单功能） | 1-2 |
| 故障定位 | 不限 | 1 |
| 数据治理/语义对齐 | 不限 | 1-2 |

超出上限必须在主文档 §0 写破例理由；证据可得性差（只有 E-SRC）时按下限取，证据充分（含 E-RUN）时按上限取。

### 5.3 信息增益停止原则

若下一步取证不能提升关键结论级别，也不能减少关键未知对完成线的阻塞，则停止加深，缺口写入主文档 §5。

### 5.4 篇幅纪律

SC-P0 深写应占主要篇幅；实现锚点与清单不得反超叙事与规则；宁可显式未覆盖，不可假性全覆盖。

## 6. 证据与结论

### 6.1 证据类型

| 类型 | 可支持 | 单独不能证明 |
|---|---|---|
| E-SRC 源码与测试 | 某版本具备的实现能力 | 已部署、已被执行、覆盖所有入口 |
| E-CFG 配置与部署 | 某环境启用条件与拓扑 | 业务一定按此发生 |
| E-DAT 数据与 Schema | 样本/总体中的结构与约束迹象 | 字段名的完整业务语义 |
| E-RUN 日志/指标/追踪 | 某时间窗实际行为 | 窗外不存在其他行为 |
| E-CON 契约 | 可观察约定 | 所有调用方均已发现 |
| E-DOC 需求/设计/手册 | 意图与历史声明 | 当前实现与运行事实 |
| E-HUM 访谈与操作知识 | 角色认知与人工流程 | 无需核验的系统事实 |

### 6.2 证据最小字段

证据 ID；类型；精确定位；版本/环境/时间窗；采集或复现步骤；原始观察；覆盖范围与局限；脱敏状态。

### 6.3 结论级别

| 级别 | 定义 | 允许用途 |
|---|---|---|
| 直接事实 | 声明范围内直接观察到 | 局部判断；不可无条件外推 |
| 交叉验证结论 | 至少两类独立证据互证 | 可支持高影响判断 |
| 经验判断 | 基于实践惯例 | 只辅助比较 |
| 推断 | 推理链清楚但有缺口 | 只用于安排下一验证 |
| 假设 | 未验证候选 | 不得写为根因/规律/最终建议措辞 |

### 6.4 冲突、未知与竞争解释

- 冲突登记 X-*，不得私自挑一份证据覆盖其余。
- 未知登记 U-*，写清阻塞理解、决策还是实施。
- SC-P0 关键机制至少：主解释、竞争解释、可淘汰证据；不可淘汰则保持开放并写入 U-*。

## 7. 叙事、状态与规则

### 7.1 叙事合格标准

**叙事合格**：删除技术标识后仍能读出触发、判断、结果、后续影响。

### 7.2 切片叙事模板（执行脚手架，SC-P0 强制）

因果叙事不是自由发挥，按以下模板组织。模板给出"叙事长什么样"，执行者照模板填写即可过叙事关：

```text
谁在什么业务意图下发起：[角色] 在 [条件] 下发起 [动作]
→ 系统如何响应：[动作] → [业务判断] → [结果]
→ 涉及哪些对象：[对象1] → [对象2] → [对象3]（用业务名，非类名）
→ 成功长什么样：[成功条件]
→ 失败如何收场：[失败条件] → [恢复路径] → [人工介入点]
→ 变更影响：改这里会伤及 [谁/什么]
```

**模板示例（合格，可去技术名）**：

```text
收银员完成结账后，系统自动创建一个打印任务，状态为"等待中"。
→ 任务被投递到对应的打印队列，队列按业务类型分发。
→ 打印机从队列取出任务，状态变为"打印中"。
→ 打印成功：状态变为"成功"，任务结束。
→ 打印失败（缺纸/离线）：状态变为"失败"，系统自动重试，
   仍失败则进入待人工处理。
```

**反例（调用链冒充叙事，不合格）**：

```text
收银员点击结账 → DwdBill → PrintJobGenerator → PosPrnJobService
  → PrinterWorker → 打印机
（删除类名后只剩箭头，不通过）
```

**对象级叙事**（单个对象如何运转）用 §2.8 对象全景卡的⑥生命时间线；**切片级叙事**（一个业务场景如何完整运转）用本节模板。两级叙事配套使用：切片叙事串联多个对象，对象叙事深入单个对象。

### 7.3 状态

**状态**：多来源转换、非法转换风险、需审计或长期演进时显式写；简单一次性动作不虚构复杂状态机；状态名用业务语言。

### 7.4 规则抽取

**抽规则**：优先从"不许继续 / 必须补偿 / 必须同口径"抽取，不从分支数量抽取。

## 8. 演进、多实现与兼容（薄而硬）

1. **先分谱系，后谈合并**：入口/规则/状态/副作用不同则先并列，不因命名相似合并。
2. **变体 ≠ 冲突**：适用域不重叠是变体；重叠且争用同一业务事实才是冲突。
3. **历史合法行为默认受保护**：标为兼容关注点；是否允许破坏由任务授权与工程规则决定。
4. **缺陷不是兼容义务**：已证实的越权、错账、污染等不升格为应保留规则；修复影响仍进影响关。
5. **配置变更三问**：在途、历史可解释性、未来新语义——影响关写明。

## 10. 反模式库

| 反模式 | 表现 | 纠正 |
|---|---|---|
| 清单完成主义 | 表多、项全即完成 | 回到主文档八关 |
| 实现转述 | 调用链当故事 | 去技术名重写 |
| 先验领域模型 | 先概念后事实 | 从 SC 事实反推 |
| 假覆盖 | 全标已分析但都浅 | 配额 + 显式未覆盖 |
| 级别跃迁 | 假设当根因 | 降级并验证 |
| 单证独断 | 一份源码定全局 | 补独立证据或降级 |
| 关系硬贴 | 套不上也要套 | U- 或弱相关不建模 |
| 主文档空洞 | 附件重正文空 | 附件只供料 |
| 类型漂移 | 摸底变改造方案 | 冻结或显式升级 |
| 严重度混淆 | 缺陷优先级当切片深度 | SC-P* 与 SEV-* 分离 |
| 痕迹直译 | 代码痕迹直接当业务事实 | 候选事实→验证→升级（§3.2 R2/R3） |
| 静态硬贴 | 技术关系直接当业务关系 | R6 映射 + 验证；套不上登记 U-* |

**自学习闭环（反模式反馈通道）**：本库不是静态清单。分析实践中发现的新失败模式，按以下流程回写：
1. 分析过程中发现文档未覆盖的失败模式 → 记录（项目、任务类型、表现、纠正建议）到当次分析的 U-*/X-* 台账及 SOP-07 报告
2. 复盘时（任务结束/周会）由负责人评估是否进入本文反模式库——新增条目须满足：在至少一个真实任务中观察到、有可复现表现、有明确纠正动作
3. 本文版本号 +1 并记录来源案例
**禁止**：把单次任务的个人偏好直接写成反模式；把尚未复现的失败写进强制层。
