# 第一部分：业务如何提炼（L0 走法）

## 走法 0：先回答"为什么要提炼"

打印系统代码里有大量被压缩的业务含义：

| 你看到的技术 | 实际上它是 |
|---|---|
| `if (status == 3)` | 一个业务状态（PENDING/SUCCESS/FAILED）被压成数字 |
| `primaryPrinter: "101,102"` | "队列可路由到多台打印机、按顺序优先"被压成逗号字符串 |
| `Redis 15min TTL` | "打印内容只需临时缓存、允许短暂不准确"被压成过期配置 |
| `resolveEffectiveStatus()` | "任务有效状态由 print+status 双字段共同决定"这条不变量被压进一个方法 |

**不提炼的判断是什么状态**：你会看到"status==3"但不知道这是"已成功且允许重打"，你会以为逗号字符串是 N:N 关系但其实只是配置顺序。**提炼 = 把这些压缩点解开，还原成可见的业务结构**——对象、关系、不变式、边界、能力。没有这一步，后面所有"这个设计好不好、该不该改"都是凭感觉。

---

## 走法 1：定位压缩信号（从哪下刀）

三压缩类型的判断（L0 §2），决定解压方向。用打印系统标出真实信号：

| 压缩类型 | 信号（真实代码/产物事实） | 来源 | 解压目标 |
|---|---|---|---|
| 表示压缩 | `PrnJobStatusEnum` PENDING/SUCCESS/FAILED；`PrinterStatus` DEFAULT/FAULT/NORMAL/BUSY | DA7 §1.6（E-005/E-006） | 还原业务状态语义、时效 |
| 表示压缩 | `PosPrnQueue.primaryPrinter` 逗号分隔字符串 | DA7 §2.1（E-004） | 还原"多归属 + 顺序优先级"能力 |
| 表示压缩 | Redis count key + 15min TTL | DA7 §2.1（E-001:142） | 还原"计数允许短暂不准、DB 兜底" |
| 层级压缩 | `resolveEffectiveStatus()` 双字段组合 | DA7 §1.1（E-001:993-1012） | 还原"状态由 print+status 共同决定"规则 |
| 层级压缩 | `EscPosRenderService` 参数替换 `{@fieldName}` | DA7 §5.4（E-012） | 还原"样式模板如何渲染内容" |
| 语境压缩 | 重打依赖 `.job` 文件；文件生命周期在 DA5 §5 与 DA4 RR-05 分离表述 | DA4 BR-15 / DA5 §5 | 还原"重打 30 天边界"隐性契约 |
| 语境压缩 | 主备 failover 逻辑在 PrinterWorkerService，队列配置在 PosPrnQueue | DA7 §1.2 / DA7 §5.2 | 还原"队列→主备→设备" 2 跳路由链 |

**打刀原则**：先打"魔法值、特殊配置、历史兼容、异常分支、规整的枚举/状态机"——这些是压缩最重的地方。打印系统里最重的两个信号：`逗号分隔（多值压成字符串）` 和 `resolveEffectiveStatus（规则压成方法）`。

## 走法 2：三级上升（L1 事实 → L2 结构 → L3 判断，不许跳级）

示范一条完整的上升链：

```
L1 事实
  - E-001:993-1012 存在 resolveEffectiveStatus()
  - E-005 定义 PENDING/SUCCESS/FAILED
  - DA5 §1.1 pos_prn_job 有 print 字段和 status 字段
      │  从这个具体证据
      ▼
L2 结构
  - 任务对象有 print 与 status 两个字段，有效状态由一个方法组合计算
  - 状态机：PENDING → SUCCESS / FAILED；仅 SUCCESS 可重打，仅 FAILED 可删除（BR-03/BR-04）
      │  从两个字段/一个方法归纳出结构
      ▼
L3 判断
  - 不变式：任务的有效状态是 print+status 的**组合**，不是单独某个字段
  - 任何"只改 status 不加 print"的演进都会破坏状态语义
      │  从结构得到"不可违反"的判断
```

**跳级示范（禁止）**：如果直接说"这个状态实现有问题，应该用多态"——这是从 L1 直接跳到 L3，跳过了 L2 结构（没说明两个字段组合的状态机是什么、哪些状态合法），就会得到一个"没有证据支撑的判断"，等于虚构。三级上升保证：每个 L3 判断都能从 L2 结构找到，每个 L2 结构都能从 L1 证据找到。

## 走法 3：造骨架（最小骨架七件套）

把解压结果压成"一页能装下"的主结构（L0 §3）。打印系统的骨架：

| 骨架项 | 打印系统实例（真实） | 证据 |
|---|---|---|
| 核心对象（≤5） | 打印任务、打印机、打印队列、打印任务文件、样式类型 | DA2 §3 |
| 关键关系（含 2 跳+） | 任务→队列→打印机（主备路由链）；任务→文件（生命周期）；任务→样式类型→样式模板 | DA3 REL-09/10、OR-03/08 |
| 不变式 | 有效状态=print+status 组合；重打依赖原 .job 文件；按 mid+sid 隔离 | DA4 BR-13/15/20-22 |
| 边界 | 任务/队列/打印机按 mid+sid 隔离；一份以 .job 文件为单位的生命周期 | DA4 BR-20-22、DA5 §5 |
| 能力 | 生命周期管理、主备路由、动态重路由、重打/删除、计数、WMS 渲染 | DA1 §四、DA2 概念 |
| 演化轴 | 云打印能力（高价值，OnlineImpl 空）；样式枚举（高痛，WMS 增长）；路由模型（高变） | DA7 DEC-004/006、DA8 风险 |
| 分型 | 见走法 5 | |

**骨架判断**：核心对象为什么是"打印任务"而不是"打印任务表"？因为少了"打印任务"这个对象，它就不是打印系统了；而"表"只是它的一个存储投影。骨架的对象是业务对象，不是表。

## 走法 4：冲突必须升级

提炼时遇到的"矛盾"，不能只并排列出，要升成高一级判断（L0 律 3）。打印系统两个真实冲突：

**冲突 1：DEC-003 说"逗号分隔用于简化查询" vs DA3 REL-05 标注"打印队列↔打印机 N:N"**
- 并列表现：DEP-003 是一种设计选择，REL-05 标注 N:N
- 升级判断：这不是 N:N，是 **配置层 N:1 冒充 N:N**——多归属只存在于逗号字符串里，没有关联表、没有真实多对多语义。这是一个**建模反模式 / 错误抽象**信号：要么真实建模多对多，要么承认它只是"有序主备列表"。

**冲突 2：DEC-006 说"用枚举硬编码保证编译期检查" vs WMS 枚举从 50+ 持续增长**
- 并列表现：DEC 是"当时合理"，现状是"增长快"
- 升级判断：这是 **"有意设计过期"信号**——设计时假设"样式类型是稳定的，编译期检查收益 > 动态化成本"，但 WMS 类型增长突破了该假设。若原假设被突破，需重新评估设计是否仍成立（可能升级路径 B）。

## 走法 5：四对象分型（无分型不出方案）

对提炼出的每个对象/结构，做四对象分型（L0 §5），决定保护/保留/修复/升级：

| 对象 | 分型 | 分型理由 | 默认动作 |
|---|---|---|---|
| 任务状态 double-字段不变式 | 业务不变式 | 改了就换系统 | 保护（不因任务的某个状态表现"不优雅"去动） |
| 逗号分隔主备 | 错误抽象/建模反模式 | 配置层 N:1 冒充 N:N，扩展与并发代价高 | 评估演进或重构（升级路径 B） |
| BUSY 无超时 | 可靠性缺陷 | 能力存在（有 BUSY 状态）但脆弱（永不解除） | 架构内修复（路径 A） |
| OnlineImpl 空实现 | 能力缺口 | 契约声明存在、实现为空 | 补齐或明确范围（先取证调用方） |
| DEC-005 事务后 MQ | 有意设计 | 有 DEC 记录、当时约束明确、未突破 | 保留，记录触发条件 |

**分型为什么必须**：逗号分隔如果被当成"可靠性缺陷"去"修复"（加个逗号解析工具），就修错了——它的问题是"建模反模式"，应该评估重构；BUSY 无超时如果被当成"错误抽象"去重构，就过度设计了——它只是脆弱，架构内修复足够。**分型决定动作类型，分型错了动作就白费。**

## 走法 6：一页残酷小样（压测：压不回去 = 提炼未完成）

打印系统的一页花样本（L0 §9，5/5/3/2/1）：

```text
核心对象(≤5)：打印任务 / 打印机 / 打印队列 / 打印任务文件 / 样式类型
不变式(≤5)：
  1. 有效状态 = print + status 组合（不能单字段判断）
  2. 重打依赖原 .job 文件（文件 30 天删除 → 重打有 30 天边界）
  3. 任务/队列/打印机按 mid+sid 隔离
关键隐性关系(≤3)：
  1. 任务 → 队列 → 打印机（主备路由链，打印任务不感知设备细节）
  2. 任务 → 文件（生命周期分离，内容与元数据不同步失效）
  3. 样式类型 → 样式模板（按 mid+sid+type 加载，渲染依赖模板）
演化轴(≤2)：云打印能力（高价值，未实现）；样式枚举（高痛，增长中）
路径判断(1)：核心不变式（状态组合/重打边界/隔离）不打算改 → 大部分走路径 A；
             但"逗号分隔路由"触及主关系（2+跳）→ 该条升级路径 B
分型动作：保护(状态不变式/隔离) / 修复(BUSY超时/幂等/状态持久化) / 升级路径B(逗号路由)
```

> **压测用法**：如果这份小样写不出来，或者写出来发现"核心对象 8 个、不变式 10 条"——说明提炼还没完成，是编目不是造形。

# 第二部分：业务如何进化（统一 L1 路径 A）

## 走法 0：路径判定——这条进化走路径 A 还是路径 B？

用 L0 §7.1 核心抽象判据，把打印后台的候选动作**分成两堆**：

| 候选 | 是否动核心抽象 | 路径 |
|---|---|---|
| BUSY 超时 / 消息幂等 / 状态持久化 | 不动（仅补可靠性机制） | **路径 A：进化** |
| 云打印补齐（若不动能力语义） | 待取证（实现补齐 / 明确范围） | 路径 A/B 边界 |
| 逗号分隔路由改造 | 动主关系（2+跳的路由归属） | **升级路径 B：评估重构** |

**示范要旨**：进化不是"想改的都改"。先分派路径：能走路径 A 修复的绝不无理由进入路径 B，动了核心抽象的也绝不留在路径 A。

## 走法 2：EVO-T 相关提炼（只提炼对决策有用的）

示范：从"重打"的决策需要，提炼出隐性契约：

```
决策问题（来自 EVO-D-*）：重打能力要不要改 / 风险边界在哪？
按 L0 三压缩定位：
  - BR-15：重打必须读取原任务的 .job 文件（L1 事实）
  - BR-08/RR-05：文件 15 分钟过期改名 .del，30 天物理删除（L1 事实）
  - DA5 §5：文件生命周期独立于任务（L2 结构）
升级判断：
  - 隐性契约 EVO-T-X：重打的有效期 = 文件保留期（30 天）
    - 超过 30 天的 SUCCESS 任务实际无法重打（.job 已删）
    - 这是"看起来能重打、实际上重打无内容"的静默边界
决策用途：
  - 支撑 EVO-E-*：重打 30 天边界要显性化（要么延长保留，要么明确报错"已过期"）
```

**示范要旨**：EVO-T 不是"把概念表再抄一遍"，而是**从当前缺陷/方案的决策需要出发，提炼出会改变决策的结构**。副产物（不影响任何决策的提炼）按 L0 律 4 降为附录，不写进主结论。

## 走法 3：EVO-E 进化方案（候选含"不做" + 五查 + 验证 + 回滚）

以 EVO-D-01（BUSY 无超时）示范完整方案：

| 项 | 内容 |
|---|---|
| 目标缺陷 | EVO-D-01：BUSY 状态无超时 |
| 候选 | A. 不做（维持，依赖人工看盘发现）；**B. BUSY 加超时 → 自动转 FAULT + 告警 + 人工确认恢复（推荐）**；C. 加心跳上报 + 失联自动降级 |
| 取舍 | B 收益=卡死可自愈；代价=引入超时参数与"假 BUSY"误判风控（需人工确认恢复，保守） |
| 五查 | 数据：状态枚举新增过渡值需兼容；接口：状态查询返回需前端兼容；消息：无；定时：B 需新增超时扫描；配置：超时参数可配 |
| 验证 | 影子：超时逻辑开关灰度，观察误报率；A-B：修复前后卡死任务恢复时长对比 |
| 回滚 | 功能开关，可随时关闭 |

**“不做”为什么必须保留**：A 明确"除人工看盘外无自愈"——如果业务能接受定期人工处理、误报风险更高，A 就是合理选择。保留"不做"迫使你想清楚"现在多痛、改了值不值"，而不是默认"有缺陷就必须改"。

## 走法 4：升级信号——进化进行中碰到承重墙

路径 A 执行中，一旦命中升级信号（统一 L1 §4.6），立即停止产出新的 EVO-E，携带证据升级路径 B：

```
信号命中（真实）：EVO-D-04 逗号分隔路由
  - 处理逗号路由时发现：要支持"按场景/按权重的设备选择"，就必须改 任务→队列→打印机 的主关系（2+跳）
  - 这命中 L0 §7.1 `K2`，具体定义只回查 L0，不在样例中另写一版
升级动作：
  - 保留 EVO-D-04 及已提炼的 EVO-T（路由链结构、failover 语义）
  - 携带 DA3 关系图 + EVO-T 传递到路径 B 评估重构
  - 不再在路径 A 里硬写"把逗号改 JSON"这类方案（那是越权产出 TGT）
```

**为什么升级而不硬改**：逗号路由不是"补个可靠性机制"能解决的，它牵动了映射关系（队列怎么选设备）。在路径 A 里硬改等于偷偷改主关系；只有进入路径 B 才允许重画这张子地图。
