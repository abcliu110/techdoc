## 目的

以用户任务和关键业务切片为锚点，对前端的技术栈、系统边界、运行机制、工程化与质量属性进行可复核分析，为接手维护、故障定位、迁移改造和后续业务分析提供决策证据。执行过程遵循 SOP-00 v3.0 的“问题驱动、业务切片、螺旋验证、G0-G5 门禁”，不以遍历目录或生成清单代替分析完成。

## 适用范围

- Vue.js / React / Angular 等主流前端框架项目
- 前后端分离的 Web 应用、微前端或多应用工作区
- 小程序 / H5 / PC 桌面应用及混合容器应用
- 适用于接手摸底、重构/迁移评估、线上问题定位、质量与安全评估；单一局部改动可裁剪执行，但须说明裁剪范围
- 不直接替代后端授权、服务端数据一致性、基础设施容量或业务规则专项分析；发现跨边界问题时转交对应 SOP 并保留追踪关系

开始前按 SOP-00 的 G0 形成分析任务书；G0 未通过时只能输出探索性发现，不得给出确定性架构或改造结论。

## 0. 系统边界、运行时配置与部署基线

### 0.1 前端系统地图

先建立上下文，不急于评价目录或框架。至少识别：

- 用户、角色、终端、浏览器/设备、WebView/桌面壳及主要用户任务
- SPA/SSR/SSG、小程序、微前端主子应用、共享包、BFF、网关和 API 服务边界
- CDN/静态站点/Node 服务、域名与路径基座、反向代理、灰度单元和第三方 SDK
- 登录与身份提供方、Token/Cookie 边界、跨域边界、租户来源和敏感数据流
- 前端团队、平台团队、服务端、外部供应商的所有权与故障责任

**输出**：带版本与环境标注的系统上下文图、部署单元表、外部依赖表和信任边界说明。图中区分现状事实、推断模型和目标建议。

### 0.2 运行时配置与部署基线

| 检查项 | 必须回答 |
|--------|---------|
| 构建时配置 | 环境文件、编译常量、功能开关如何注入，是否可能将密钥打入产物 |
| 运行时配置 | 配置端点、HTML 注入、全局变量、远程开关由谁提供，失败/缓存/回退行为是什么 |
| API 定位 | base URL、网关前缀、服务发现、代理和多环境映射是否与实际部署一致 |
| 发布拓扑 | 构建产物、CDN/源站、容器或宿主、微前端版本组合、灰度与回滚方式 |
| 缓存更新 | 文件指纹、HTML/Service Worker/CDN 缓存策略是否支持原子发布与版本回退 |
| 客户端基线 | 支持的浏览器、设备、网络条件、分辨率、语言/时区及降级策略 |
| 可观测版本 | source map、release/version、环境和用户会话如何关联错误、日志、Trace 与埋点 |

必须比对源码配置、构建产物和目标环境实际配置。无法获得部署或运行配置时，结论标记为静态推断，并登记其对决策的影响。

### 1.2 依赖分析

**分析内容**：

```bash
# 查看依赖数量
npm ls --depth=0

# 查看依赖版本（检查是否有安全隐患）
npm outdated

# 检查依赖是否有漏洞
npm audit
```

**分析维度**：

| 检查项 | 说明 | 判断依据 |
|--------|------|---------|
| 依赖数量 | dependencies + devDependencies 总数 | 结合业务能力、构建体积、加载成本和维护成本判断，不以数量本身定性 |
| 直接依赖版本 | 当前版本、维护状态与升级约束 | 不以“最新”为目标；结合兼容契约、安全通告、维护状态和迁移成本评估 |
| 漏洞扫描 | 锁文件对应的扫描结果 | 结合可达性、运行环境、暴露面和项目安全目标处置，不仅按工具等级下结论 |
| 重复依赖 | 是否存在多版本或功能重叠 | 量化其对产物、运行时和维护的实际影响 |

## 2. 项目结构分析

### 2.1 目录结构

**分析内容**：

```bash
# 查看目录结构
tree -L 3 -I 'node_modules|dist|.git' .
```

**分析维度**：

| 检查项 | 说明 | 判断依据 |
|--------|------|---------|
| 目录划分 | 按功能/类型/模块划分 | 是否支持业务定位、变更隔离和所有权，而非预设唯一模式 |
| 层级深度 | 目录层级是否影响查找和边界理解 | 结合团队导航成本、模块规模与工具能力判断，不采用固定层数 |
| 命名规范 | 目录/文件命名是否一致 | 与项目既有规范和业务术语一致 |
| 空目录 | 是否有空目录 | 确认是脚手架约定、占位还是遗留内容 |

**常见项目结构模式**：

```
模式A：按类型划分（Vue 早期常用）
src/
├── components/    # 组件
├── views/        # 页面
├── router/       # 路由
├── store/        # 状态
├── utils/        # 工具
└── styles/       # 样式

模式B：按功能/模块划分（推荐）
src/
├── modules/           # 功能模块
│   ├── user/         # 用户模块
│   │   ├── components/
│   │   ├── views/
│   │   ├── store/
│   │   └── api/
│   └── order/        # 订单模块
├── shared/           # 共享资源
│   ├── components/
│   ├── hooks/
│   └── utils/
├── layouts/           # 布局
└── router/           # 路由

模式C：按职责划分（React 项目常见）
src/
├── features/          # 功能特性
├── components/       # 通用组件
├── lib/              # 库配置
├── hooks/            # 自定义 Hooks
└── utils/            # 工具函数
```

### 2.2 模块划分

**分析内容**：

```bash
# 查看功能模块
ls -la src/

# 查看各模块大小
du -sh src/*/
```

**分析维度**：

| 检查项 | 说明 | 判断依据 |
|--------|------|---------|
| 模块数量 | 功能模块及共享模块分布 | 是否与业务边界、团队所有权和发布边界相匹配，不使用固定数量判断 |
| 模块大小 | 变更热点、依赖扇入/扇出与复杂度 | 差异本身不是问题，重点识别职责混杂和变更耦合 |
| 模块命名 | 命名是否反映业务语义 | 与统一业务术语表和用户任务对应 |

## 3. 架构设计分析

### 3.0 用户任务与关键业务切片贯通

不能只分别统计页面、路由、Store 和 API。每个关键切片应从用户可观察结果出发，建立以下追踪链：

```text
业务目标/不变量 → 用户/角色任务 → 场景与触发条件
→ 页面/组件 → 路由/导航守卫 → 本地/全局/服务端状态
→ API 契约与外部 SDK → 页面/按钮/数据权限与租户上下文
→ 成功、空、失败、超时、重复、并发、撤销/恢复路径
→ 埋点、日志、错误与 Trace → 单元/组件/契约/E2E 测试 → 证据 ID
```

**切片追踪矩阵**：

| 切片 ID | 用户任务/业务结果 | 页面/路由 | 状态与缓存 | API/契约 | 权限/租户 | 埋点/可观测 | 测试 | 静态/运行证据 | 未知项 |
|---------|------------------|-----------|------------|----------|-----------|-------------|------|---------------|--------|
| SC-FE-001 | | | | | | | | | |

执行要求：

1. 至少选择能影响当前决策的高价值/高风险切片；长尾功能可分层采样，并说明总体、样本框、时间窗口和覆盖缺口。
2. 黑箱观察真实用户流程、可见状态和错误反馈；灰箱用网络请求、埋点、日志、Trace 关联链路；白箱再用页面、路由、状态、请求层和配置解释机制。
3. 源码表明的“可能路径”至少用运行证据或可复现实验校验关键边。无法动态验证时降低确定性，不得写成生产事实。
4. 覆盖正常、边界、空数据、失败、重复、并发、弱网/离线、会话过期、路由回退等适用场景；不适用项说明理由。
5. 页面、菜单或按钮隐藏仅是体验控制，不能作为服务端授权成立的证据。
6. 配置式关系由页面选择、绑定或配置时，沿“控件与候选查询 -> 权限/作用域 -> 保存请求 -> 服务端校验 -> 权威存储 -> 生效读取 -> 审计/解绑”取证并回填 DA3；前端只能证明维护入口和请求意图，不能单独证明关系已持久化或已生效。

### 3.1 状态管理架构

**分析内容**：

```bash
# Vue 项目
cat src/store/index.ts

# React 项目
cat src/store/index.tsx 或 cat src/context/
```

**分析维度**：

| 检查项 | 说明 | 良好实践 |
|--------|------|---------|
| Store 划分 | 全局 Store vs 模块 Store | 按业务模块划分 |
| State 规范 | State 变更是否可追踪 | 建议使用 mutation/action |
| 持久化 | 敏感数据是否持久化 | Token 等应加密存储 |
| 初始化 | State 初始化是否合理 | 应有默认值 |

**状态管理检查清单**：

```
□ Store 是按业务能力、页面生命周期还是数据类型划分？边界是否可解释？
□ 客户端状态、服务端状态、URL 状态、表单草稿与缓存的权威源分别是什么？
□ 状态变更、派生数据和异步副作用是否可追踪，失败后是否会留下脏状态？
□ 初始化、刷新、路由切换、账户/角色/租户切换时是否正确清理或重建状态？
□ 持久化状态的版本、迁移、过期、跨标签页同步和敏感数据保护如何处理？
```

## 7. 证据、未知项与问题闭环

### 7.1 静态与运行证据互证

证据沿用 SOP-00 的 `SRC/CFG/DAT/RUN/CON/DOC/HUM` 类型，使用稳定 ID：`E-{类型}-{序号}`。每份关键证据记录版本/环境、采集时间、复现步骤、直接性、时效性、覆盖度、可复现性、独立性、脱敏状态和适用范围。

```text
C-FE-012（交叉验证结论）← E-SRC-017 + E-CFG-004 + E-RUN-008
```

- 源码、测试、路由表和类型定义证明设计或可能路径；部署产物、运行配置、网络请求、日志、指标、Trace、埋点和真实用户样本证明特定窗口内的实际行为。
- 关键静态调用边至少以一种独立运行证据验证。未取得运行证据时标为推断/假设，说明缺口及最小验证动作。
- 当源码、文档、配置、契约与运行行为冲突时建立矛盾项，不得擅自选择一份覆盖其他证据；优先核对部署版本、灰度、缓存、功能开关和隐藏入口。
- “未观测到”不等于“不存在”；说明样本框、选择方式、时间窗口和覆盖缺口。

### 7.2 台账与闭环

| 台账 | 最小字段 |
|------|---------|
| 未知/假设/矛盾 | ID、原始观察、当前解释、支持/反对证据、区分性验证、状态、决策影响、负责人 |
| 问题/风险 | ID、类型、现象与触发条件、被破坏的不变量/契约、范围、证据与确定性、影响半径、根因层级 |
| 建议/决策 | 候选方案与不处理方案、成本、兼容/迁移影响、验证标准、发布与回滚、负责人、状态、复查日期 |

缺陷、风险、技术债、改进机会和未知项不得混写。本文件的 P0-P3 指缺陷/问题严重度（SEV-P0~P3），不自动等于固定修复时限，且与 L1 的 SC-P* 切片深度分级无关（SC-P* 是分析深度配额，禁止混用）；处置顺序结合发生可能性、暴露面、可检测性、可逆性、证据强度、成本和依赖关系判断。

- [ ] 接口契约、错误语义、缓存/离线/并发，以及性能、可访问性、兼容性、安全、可观测性适用项已检查
- [ ] 最可能推翻结论的反例已验证，未解释的强反证为零；未知项已标明是否影响当前决策
- [ ] 高影响问题和建议已形成证据、影响、根因、替代方案、验证和回滚闭环
- [ ] 另一名分析者可依据证据索引和复现步骤复核关键结论
- [ ] 新增分析的预期信息价值已低于继续投入的时间和风险成本

### 8.2 AI 分析约束

1. 不以文件名、路由名、组件名、接口名、字段名或注释直接断言业务语义；推断须标注并寻找独立证据。
2. 不把框架惯例、行业参考、工具默认值或固定阈值写成本系统事实；阈值必须关联项目目标/SLO、支持矩阵或合规要求。
3. 不因搜索不到入口就断言功能无人使用；动态路由、远程配置、微前端、反射式注册、WebView、脚本、深链和第三方容器都可能形成隐藏入口。
4. 不把前端隐藏页面/按钮当作授权成立，不输出或尝试利用敏感凭据、跨租户数据和可滥用漏洞细节。
5. 结论同时给出证据 ID、版本/环境、时间窗口、适用范围、确定性和关键未知项；证据不足时提出最小区分性验证。
6. 不机械生成大而全清单；优先处理高价值、高风险、高变化和高证据缺口切片，不直接建议重写或大规模重构。
7. 图表和报告必须区分现状事实、推断模型和目标建议；运行验证仅在授权范围内进行，生产默认只读。
