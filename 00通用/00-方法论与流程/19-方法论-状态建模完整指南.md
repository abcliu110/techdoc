## 0.1 核心结论

> 状态建模的核心思想：业务对象的状态是有限的、可枚举的，状态之间只有合法的转换路径，非法跃迁是 bug 而不是"配置问题"。状态转换是业务事实，不是技术细节。

## 1. 状态建模基础回顾

### 1.1 什么是状态

状态是业务对象在某一时刻的完整快照，它回答：

> "在此时此刻，这个业务对象在业务上处于什么情况？"

```text
好的状态定义：
├─ PENDING_APPROVAL（待审批）— 明确业务含义
├─ PARTIALLY_SHIPPED（部分发货）— 可枚举、有边界
└─ OVERDUE（已逾期）— 基于时间的事实

不好的状态定义：
├─ status = 1 — 数字不代表业务含义
├─ status = "处理中" — 模糊，什么处理？处理什么？
└─ status = "ACTIVE" — 激活了就能做所有操作吗？
```

### 1.2 什么是状态机

状态机定义了一个业务对象：
- 有哪些**有限状态**
- 在什么条件下可以**从状态A转换到状态B**
- 转换时**触发什么动作或事件**

### 1.3 状态机的形式化定义

```text
StateMachine = <States, Events, Transitions, Guards, Actions, InitialState, FinalStates>

States       — 状态的有限集合
Events       — 触发转换的事件/命令
Transitions  — 状态转换规则：State × Event → State
Guards       — 转换的前置条件
Actions      — 转换时执行的副作用
InitialState — 初始状态
FinalStates  — 终结状态集合
```

### 1.4 状态机示例：退款

```text
退款状态机

PENDING → APPROVED → PROCESSING → SUCCESS
    ↓          ↓           ↓
  REJECTED   CANCELLED   FAILED → RESULT_UNKNOWN
                              ↓         ↓
                          SUCCESS   REFUNDING → SUCCESS
```

### 1.5 状态与状态机的关系

| 概念 | 定义 | 示例 |
|---|---|---|
| **状态** | 对象在某一时刻的情况 | "订单已发货" |
| **状态机** | 状态及其合法转换规则的定义 | 订单状态机定义 |
| **状态实例** | 具体对象当前的状态值 | order.status = SHIPPED |

### 1.6 状态建模的核心原则

```text
原则1：状态是业务事实，不是技术字段
原则2：状态转换必须显式声明
原则3：每个转换有前置条件（Guard）
原则4：转换触发业务事件
原则5：状态变化不可覆盖
原则6：终结状态后不可再变
```

## 2. 状态爆炸问题（Aspect A）

### 2.1 什么是状态爆炸

当业务场景复杂时，简单枚举所有状态组合会导致状态数量指数级增长。

```text
场景：订单状态

简单模型：
- 订单状态：CREATED → PAID → SHIPPED → COMPLETED

实际场景：
- 是否有折扣（是/否） × 2
- 是否部分发货（是/否） × 2
- 是否退款（是/否） × 2
- 发票状态（未开/已开/部分开） × 3

状态组合：4 × 2 × 2 × 2 × 3 = 96 种组合！
```

### 2.2 状态爆炸的表现

```text
// 反模式：把所有维度塞进一个状态字段
enum OrderStatus {
    CREATED, PAID, PARTIAL_PAID,
    SHIPPED, PARTIAL_SHIPPED, FULL_SHIPPED,
    PARTIAL_SHIPPED_WITH_DISCOUNT,
    REFUNDED_PARTIAL_WITH_INVOICE...
    // 96种可能，还在增长
}
```

### 2.3 解决策略一：状态分离

```text
策略：把不同业务维度的状态分离到不同字段

Order
├── orderStatus: OrderCommercialState    // 商流状态
│   └── CREATED → CONFIRMED → COMPLETED / CANCELLED
├── fulfillmentStatus: FulfillmentState  // 履约状态
│   └── PENDING → ALLOCATED → PICKING → SHIPPED → SIGNED
├── paymentStatus: PaymentState          // 资金流状态
│   └── PENDING → AUTHORIZED → CAPTURED → REFUNDED
└── invoiceStatus: InvoiceState          // 票税流状态
    └── PENDING → ISSUED → PARTIAL → RED
```

每个状态机独立管理自己的状态，组合起来表示完整业务状态。

### 2.4 解决策略二：状态聚合视图

```text
// 独立状态机
OrderCommercialState    commercialState
FulfillmentState        fulfillmentState
PaymentState            paymentState
InvoiceState            invoiceState

// 聚合视图（派生，非权威）
OrderOverallStatus computeOverallStatus() {
    if (commercialState == CANCELLED) return CANCELLED;
    if (paymentState == REFUNDED) return REFUNDED;
    if (fulfillmentState == SIGNED) return COMPLETED;
    if (paymentState == AUTHORIZED) return PROCESSING;
    return PENDING;
}
```

聚合视图用于：
- 列表页筛选
- 快速判断
- 告警监控

**但聚合视图不能反向覆盖各专业状态。**

### 2.5 解决策略三：状态分层

```text
// 顶层状态（粗粒度）
OrderLifecycle
└── DRAFT → ACTIVE → CLOSED

// 中层状态（业务阶段）
OrderPhase
└── CREATION → PAYMENT → FULFILLMENT → COMPLETION

// 底层状态（具体操作）
OrderOperationState
└── 详细的操作状态
```

用户看到顶层状态，内部逻辑使用底层状态。

### 2.6 解决策略四：超状态与子状态

```text
// 超状态（Grouping State）
FulfillmentState (超状态)
├── ShippingState (子状态)
│   ├── PENDING
│   ├── PICKING
│   ├── SHIPPED
│   └── DELIVERED
└── ReturnState (子状态)
    ├── PENDING_RETURN
    ├── IN_TRANSIT
    └── RECEIVED
```

子状态有独立的转换规则，超状态提供粗粒度视图。

### 2.7 何时不需要担心状态爆炸

```text
不需要拆分的情况：
├─ 状态组合数量 < 10
├─ 组合状态有明确的业务含义
├─ 不会频繁新增组合
└─ 状态转换规则相对简单

可以考虑拆分的情况：
├─ 状态数量 > 15 且持续增长
├─ 不同维度独立变化
├─ 不同角色关注不同维度
└─ 转换规则开始互相干扰
```

## 3. 状态 vs 事件（Aspect B）

### 3.1 基本概念

```text
状态（State）
├─ 表示对象在某一时刻的快照
├─ 是名词：PENDING、COMPLETED
└─ 可以被查询

事件（Event）
├─ 表示已发生的业务事实
├─ 是过去时：OrderPlaced、PaymentCaptured
├─ 可以被记录
└─ 触发状态转换
```

### 3.2 状态和事件的关系

```text
事件触发状态转换：

状态A  --[事件]-->  状态B

OrderStatus.PENDING
    + OrderConfirmedEvent
    → OrderStatus.CONFIRMED

PaymentStatus.AUTHORIZED
    + PaymentCapturedEvent
    → PaymentStatus.CAPTURED
```

### 3.3 领域事件定义

```text
领域事件 = <eventId, eventType, occurredAt, aggregateId, payload, metadata>

eventId       — 事件唯一标识
eventType     — 事件类型：OrderConfirmed
occurredAt    — 发生时间
aggregateId   — 关联的聚合根ID
payload       — 事件数据
metadata      — 元数据（来源、版本等）
```

### 3.4 状态机 vs 事件溯源

| 维度 | 状态机 | 事件溯源 |
|---|---|---|
| 关注点 | 当前状态和转换 | 完整历史和转换链 |
| 存储 | 当前状态 | 事件序列 |
| 重建 | 直接读取 | 重放事件 |
| 查询 | 快 | 需要重建 |
| 审计 | 有限 | 完整 |
| 复杂度 | 低 | 高 |

### 3.5 实践建议

```text
// 推荐：状态机 + 领域事件结合

class Order {
    OrderStatus status;
    
    void confirm(ConfirmCommand cmd) {
        // 1. 校验前置条件
        require(status == OrderStatus.PENDING, "只有待确认订单可确认");
        
        // 2. 状态转换
        OrderStatus previousStatus = status;
        status = OrderStatus.CONFIRMED;
        
        // 3. 发布领域事件
        DomainEvents.publish(new OrderConfirmedEvent(
            this.orderId,
            previousStatus,
            this.status,
            cmd.confirmedAt(),
            cmd.confirmedBy()
        ));
    }
}
```

### 3.6 命令 vs 事件 vs 状态

```text
┌─────────────────────────────────────────────────────────┐
│                     命令（Command）                      │
│  "请做这件事" — 带有意图的操作请求                       │
│  OrderConfirmCommand、PaymentCaptureCommand              │
└─────────────────────┬───────────────────────────────────┘
                      │ 触发
                      ▼
┌─────────────────────────────────────────────────────────┐
│                     事件（Event）                         │
│  "这件事发生了" — 已发生的业务事实                      │
│  OrderConfirmed、PaymentCaptured                         │
└─────────────────────┬───────────────────────────────────┘
                      │ 导致
                      ▼
┌─────────────────────────────────────────────────────────┐
│                     状态（State）                        │
│  "现在的情况" — 对象当前的业务状态                      │
│  OrderStatus.CONFIRMED                                  │
└─────────────────────────────────────────────────────────┘
```

### 3.7 事件命名规范

```text
事件命名 = 过去时 + 业务含义

好的命名：
├─ OrderPlaced（订单已提交）
├─ PaymentAuthorized（支付已授权）
├─ InventoryReserved（库存已预占）
├─ InvoiceIssued（发票已开具）
└─ RefundApproved（退款已批准）

不好的命名：
├─ OrderSave（保存订单）— 技术命名
├─ PaymentCallback（支付回调）— 来源命名
├─ StatusChanged（状态变了）— 模糊
└─ Update（更新）— 太抽象
```

## 4. 状态持久化（Aspect C）

### 4.1 持久化策略选择

```text
策略1：直接状态存储
├─ 存储：当前状态值
├─ 优点：简单、查询快
├─ 缺点：丢失历史
└─ 适用：简单业务、历史不重要

策略2：状态 + 变更日志
├─ 存储：当前状态 + 变更记录表
├─ 优点：可审计、可追溯
├─ 缺点：两张表需要同步
└─ 适用：大多数业务

策略3：事件溯源（Event Sourcing）
├─ 存储：事件序列
├─ 优点：完整历史、可重放、可调试
├─ 缺点：查询复杂、事件重构成本
└─ 适用：复杂业务、审计要求高

策略4：混合策略
├─ 存储：当前快照 + 关键事件
├─ 优点：平衡查询和历史
└─ 适用：大多数企业应用
```

### 4.2 策略一：直接状态存储

```sql
-- 简单直接存储
CREATE TABLE orders (
    id VARCHAR(36) PRIMARY KEY,
    status VARCHAR(50) NOT NULL,
    amount DECIMAL(19,2) NOT NULL,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);
```

```java
// 代码实现
@Entity
public class Order {
    @Id
    private String id;
    
    @Enumerated(EnumType.STRING)
    private OrderStatus status;
    
    private BigDecimal amount;
    
    @Version  // 乐观锁
    private Long version;
    
    // 状态转换方法
    public void confirm() {
        if (this.status != OrderStatus.PENDING) {
            throw new IllegalStateException();
        }
        this.status = OrderStatus.CONFIRMED;
    }
}
```

### 4.3 策略二：状态 + 变更日志

```sql
-- 当前状态表
CREATE TABLE orders (
    id VARCHAR(36) PRIMARY KEY,
    status VARCHAR(50) NOT NULL,
    amount DECIMAL(19,2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

-- 状态变更日志表
CREATE TABLE order_status_history (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id VARCHAR(36) NOT NULL,
    from_status VARCHAR(50),
    to_status VARCHAR(50) NOT NULL,
    changed_by VARCHAR(100),
    changed_at TIMESTAMP,
    reason VARCHAR(500),
    metadata JSON,
    INDEX idx_order_id (order_id),
    INDEX idx_changed_at (changed_at)
);
```

```java
// 状态变更记录器
@Component
public class StatusChangeRecorder {
    
    @Transactional
    public void recordAndUpdate(Order order, OrderStatus newStatus, 
                                  String changedBy, String reason) {
        OrderStatus oldStatus = order.getStatus();
        
        // 1. 更新状态
        order.setStatus(newStatus);
        
        // 2. 记录变更历史
        StatusHistory history = new StatusHistory();
        history.setOrderId(order.getId());
        history.setFromStatus(oldStatus);
        history.setToStatus(newStatus);
        history.setChangedBy(changedBy);
        history.setChangedAt(Instant.now());
        history.setReason(reason);
        
        historyRepository.save(history);
    }
}
```

### 4.4 策略三：事件溯源

```sql
-- 事件表（Append Only）
CREATE TABLE order_events (
    sequence BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_id VARCHAR(36) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    event_data JSON NOT NULL,
    occurred_at TIMESTAMP NOT NULL,
    INDEX idx_aggregate_id (aggregate_id),
    INDEX idx_occurred_at (occurred_at)
);
```

```java
// 事件溯源聚合根
public class Order extends AbstractAggregateRoot<Order> {
    
    private String id;
    private OrderStatus status;
    private BigDecimal amount;
    
    // 应用事件重建状态
    public void apply(OrderPlacedEvent event) {
        this.id = event.getOrderId();
        this.status = OrderStatus.PENDING;
        this.amount = event.getAmount();
    }
    
    public void apply(OrderConfirmedEvent event) {
        this.status = OrderStatus.CONFIRMED;
    }
    
    // 发布事件触发状态转换
    public void confirm(String confirmedBy) {
        require(status == OrderStatus.PENDING);
        
        status = OrderStatus.CONFIRMED;
        
        // 注册事件
        registerEvent(new OrderConfirmedEvent(
            this.id, 
            OrderStatus.PENDING,
            this.status,
            Instant.now(),
            confirmedBy
        ));
    }
    
    // 从事件序列重建
    public static Order reconstruct(List<DomainEvent> events) {
        Order order = new Order();
        events.forEach(order::apply);
        return order;
    }
}
```

### 4.5 策略四：快照 + 事件

```sql
);
```

### 4.7 持久化策略选择指南

```text
选择策略一的场景：
├─ 状态简单、历史不重要
├─ 性能要求极高
└─ 审计由外部系统负责

选择策略二的场景：
├─ 需要审计轨迹
├─ 状态变更需要回溯
└─ 团队对事件溯源不熟悉

选择策略三的场景：
├─ 审计要求极高
├─ 需要业务事件调试能力
├─ 需要状态重放
└─ 团队有事件溯源经验

选择策略四的场景：
├─ 事件量大、需要优化查询
├─ 需要历史但不需要全量事件
└─ 平衡性能和功能
```

## 5. 状态可视化（Aspect D）

### 5.1 状态图表示例

#### 5.1.1 订单状态机

```text
┌─────────────┐
│    DRAFT    │ ←── 创建订单草稿
└──────┬──────┘
       │ submit()
       ▼
┌─────────────┐
│   PENDING   │ ←── 等待支付
└──────┬──────┘
       │ pay()
       ▼
┌─────────────┐
│   PAID      │ ←── 支付成功
└──────┬──────┘
       │ fulfill()
       ▼
┌─────────────┐
│  PROCESSING │ ←── 履约中
└──────┬──────┘
       │ deliver()
       ▼
┌─────────────┐
│  DELIVERED  │ ←── 已发货/已履约
└──────┬──────┘
       │ confirm()
       ▼
┌─────────────┐
│  COMPLETED  │ ←── 交易完成
└─────────────┘

--- 异常路径 ---

PENDING ──────► CANCELLED（用户取消 / 超时取消）
PAID ─────────► REFUNDING ──► REFUNDED（退款）
PROCESSING ───► RETURNING ──► RETURNED（退货）
任何状态 ────► EXCEPTION（异常，需要人工处理）
```

#### 5.1.2 退款状态机

```text
┌─────────────┐
│   PENDING   │ ←── 退款申请
└──────┬──────┘
       │ approve() / reject()
       ▼
┌─────────────┐     ┌─────────────┐
│  APPROVED   │ ──► │  REJECTED   │
└──────┬──────┘     └─────────────┘
       │ process()
       ▼
┌─────────────┐
│ PROCESSING  │ ←── 正在退款
└──────┬──────┘
       │ gateway callback
       ▼
┌─────────────┐     ┌──────────────────┐
│   SUCCESS   │     │ RESULT_UNKNOWN   │ ←── 超时未知
└─────────────┘     └────────┬─────────┘
                              │ query / reconcile
                              ▼
                    ┌─────────────┐     ┌─────────────┐
                    │   SUCCESS   │     │   FAILED    │
                    └─────────────┘     └─────────────┘
```

### 5.2 状态转换表

| 当前状态 | 允许命令 | 目标状态 | Guard 条件 | 触发动作 |
|---|---|---|---|---|
| DRAFT | submit | PENDING | 订单有效 | 发送通知 |
| DRAFT | cancel | CANCELLED | - | 释放预占 |
| PENDING | pay | PAID | 金额正确 | 确认库存 |
| PENDING | cancel | CANCELLED | 未超时 | 退款（如已预授权） |
| PAID | fulfill | PROCESSING | 有库存 | 生成发货单 |
| PAID | refund | REFUNDING | - | 发起退款 |
| PROCESSING | deliver | DELIVERED | 已发货 | 等待确认 |
| DELIVERED | confirm | COMPLETED | - | 确认收入 |
| DELIVERED | return | RETURNING | 在退货期内 | 生成退货单 |
| * | exception | EXCEPTION | - | 创建工单 |

```java
    @Test
    void concurrentConfirmationOnlyOneSucceeds() throws Exception {
        Order order = Order.createDelivered();
        int threadCount = 10;
        ExecutorService executor = Executors.newFixedThreadPool(threadCount);
        CountDownLatch startLatch = new CountDownLatch(1);
        CountDownLatch endLatch = new CountDownLatch(threadCount);
        AtomicInteger successCount = new AtomicInteger(0);
        AtomicInteger failCount = new AtomicInteger(0);
        
        for (int i = 0; i < threadCount; i++) {
            executor.submit(() -> {
                try {
                    startLatch.await();
                    order.confirm();
                    successCount.incrementAndGet();
                } catch (Exception e) {
                    failCount.incrementAndGet();
                } finally {
                    endLatch.countDown();
                }
            });
        }
        
        startLatch.countDown();
        endLatch.await();
        
        assertEquals(1, successCount.get());
        assertEquals(threadCount - 1, failCount.get());
        assertEquals(OrderStatus.COMPLETED, order.getStatus());
    }
    
    @Test
    void concurrentCancelAndPay() throws Exception {
        Order order = Order.createPending();
        ExecutorService executor = Executors.newFixedThreadPool(2);
        CountDownLatch latch = new CountDownLatch(2);
        
        executor.submit(() -> {
            try {
                order.cancel();
            } finally { latch.countDown(); }
        });
        
        executor.submit(() -> {
            try {
                order.pay(payment);
            } catch (Exception e) {
                // 期望其中一个失败
            } finally { latch.countDown(); }
        });
        
        latch.await();
        
        // 最终状态应该是 CANCELLED 或 PAID，但不会两边都成功
        assertTrue(
            order.getStatus() == OrderStatus.CANCELLED ||
```

## 7. 子状态与嵌套（Aspect F）

### 7.1 什么是子状态

子状态是嵌套在父状态内的更细粒度状态。

```text
顶层状态（OrderStatus）
└── PROCESSING（处理中）
    │
    ├── 子状态（ProcessingPhase）
    │   ├── PICKING（拣货中）
    │   ├── PACKING（打包中）
    │   └── SHIPPING（发货中）
    │
    └── 子状态（ProcessingType）
        ├── STANDARD（标准处理）
        └── EXPRESS（加急处理）
```

### 7.2 子状态的使用场景

```text
适合使用子状态的场景：
├─ 复杂业务流程有明显的阶段性
├─ 不同子状态需要不同的超时策略
├─ 不同子状态触发不同的通知
├─ 不同子状态有不同的数据要求
└─ 状态转换规则在子层面更清晰

不适合使用子状态的场景：
├─ 子状态数量爆炸
├─ 子状态之间转换规则复杂
└─ 不同角色关注不同子状态（应分离字段）
```

```java
            case PENDING -> to == PROCESSING || to == CANCELLED;
            case PROCESSING -> to == DELIVERED || to == CANCELLED;
            case DELIVERED -> to == COMPLETED || to == RETURNING;
            default -> false;

            case PACKING -> to == SHIPPING;
            case SHIPPING -> to == DELIVERED;  // 子状态完成 = 顶层状态完成
            default -> false;
        };
    }
}
```

```java
        String idempotencyKey = request.getOrderId() + "_PAYMENT";

        Payment payment = processPayment(request);
        payment.setIdempotencyKey(idempotencyKey);
        paymentRepository.save(payment);
        
        return PaymentResult.from(payment);
    }
}
```

### 9.5 快照策略

```text
快照策略选择：

策略1：每个版本都快照
├─ 优点：查询快，重建快
├─ 缺点：存储量大
└─ 适用：状态变化频繁

策略2：定时快照
├─ 每小时/每天生成快照
├─ 查询时用最近的快照 + 事件重建
├─ 优点：存储可控
└─ 适用：大多数场景

策略3：变更时快照
├─ 状态变化时生成新快照
├─ 事件表只记录增量
├─ 优点：平衡存储和查询
└─ 适用：通用场景

策略4：关键节点快照
├─ 只在关键状态生成快照
├─ 如：COMPLETED、CANCELLED
├─ 优点：存储最小
└─ 缺点：查询需要更多事件
```

### 9.6 合规审计要求

```text
财务合规要求：
├─ 所有状态变更必须留痕
├─ 变更必须有操作人、时间、原因
├─ 历史记录不可删除或修改
└─ 支持定期导出审计报告

数据合规要求（GDPR等）：
├─ 操作日志保留期限
├─ 敏感数据脱敏
├─ 用户数据删除时的日志处理
└─ 跨境数据传输限制
```

## 11. 逆向状态建模（Aspect J）

### 11.1 逆向状态的本质

```text
逆向状态不是"撤销"，而是"新的业务事实"：

错误理解：
├─ 订单取消 = 把状态改回 DRAFT
├─ 退款 = 把支付金额改回去
└─ 红冲 = 删除原发票

正确理解：
├─ 订单取消 = 新增一条"取消"状态记录
├─ 退款 = 新增一条"退款"交易
└─ 红冲 = 新增一张红字发票
```

### 11.2 取消状态机

```text
订单取消状态机

PENDING ──────────────────────► CANCELLED（用户取消）
  │                                    ▲
  │ 支付超时时                       │
  └─────────────► CANCELLED（超时取消）─┘

PAID ─────────► REFUNDING ──► REFUNDED（退款取消）
  │
  └──────────► CANCELLING ──► CANCELLED（已支付取消，需退款）

PROCESSING ──► RETURNING ────► RETURNED（退货取消）
  │
  └──────────► CANCELLING ──► 部分取消处理

COMPLETED ──► 不可直接取消
              └─► 只能走售后流程
```

### 11.3 取消实现

```java
public class Order {
    
    public void cancel(CancelReason reason) {
        switch (status) {
            case DRAFT:
                // 草稿状态取消，直接作废
                this.status = OrderStatus.CANCELLED;
                this.cancelledAt = Instant.now();
                this.cancelReason = reason;
                break;
                
            case PENDING:
                // 待支付状态取消
                this.status = OrderStatus.CANCELLED;
                releaseReservation();
                break;
                
            case PAID:
                // 已支付状态取消，需要退款
                this.status = OrderStatus.CANCELLING;
                initiateRefund(reason);
                break;
                
            case PROCESSING:
                // 处理中取消，取决于履约进度
                if (fulfillmentProgress < 50) {
                    this.status = OrderStatus.CANCELLING;
                    initiateRefund(reason);
                } else {
                    throw new BusinessException("订单已在发货中，请申请退货");
                }
                break;
                
            default:
                throw new IllegalStateException("当前状态不允许取消");
        }
    }
    
    public void onRefundCompleted() {
        if (status == OrderStatus.CANCELLING) {
            this.status = OrderStatus.CANCELLED;
            // 发送取消完成通知
        }
    }
}
```

```java
public class Order {
    
    public void requestReturn(ReturnRequest request) {
        require(status == OrderStatus.DELIVERED, "只有已发货订单可退货");
        require(request.isWithinReturnPeriod(), "超过退货期限");
        require(hasReturnableItems(request), "部分商品不支持退货");
        
        this.status = OrderStatus.RETURN_REQUESTED;
        this.returnRequest = request;
        
        DomainEvents.publish(new ReturnRequestedEvent(
            this.orderId, request.getItems()
        ));
    }
    
    public void approveReturn(Approver approver) {
        require(status == OrderStatus.RETURN_REQUESTED);
        require(hasPermission(approver, "APPROVE_RETURN"));
        
        this.status = OrderStatus.RETURN_APPROVED;
        // 计算退款金额
        calculateRefundAmount();
    }
    
    public void onReturnReceived(ReturnReceipt receipt) {
        require(status == OrderStatus.SHIPPING_BACK);
        
        // 验货
        if (receipt.isAllItemsReceived()) {
            this.status = OrderStatus.RETURNED;
            processFullRefund();
        } else if (receipt.hasDamagedItems()) {
            this.status = OrderStatus.RETURN_DISPUTE;
            // 进入纠纷处理
        } else {
            this.status = OrderStatus.PARTIAL_RETURNED;
            processPartialRefund(receipt.getReceivedItems());
        }
    }
}
```

### 11.7 逆向设计原则

```text
逆向设计原则：

原则1：原状态不可修改
├─ 原状态记录保留
├─ 新逆向状态追加
└─ 通过关联键追踪

原则2：逆向必须有业务原因
├─ 取消必须提供原因
├─ 退货必须提供凭证
└─ 红冲必须关联原发票

原则3：逆向有独立的生命周期
├─ 取消流程有审批
├─ 退货流程有验货
└─ 红冲流程有税务校验

原则4：逆向可能产生新的正向
├─ 取消后可以重新下单
├─ 退货后可以重新发货
└─ 红冲后可以重新开票

原则5：正向和逆向必须对账
├─ 取消金额 + 原金额 = 应有金额
├─ 退款金额 + 原支付 = 应退金额
└─ 红冲金额 + 原发票 = 应有发票
```

## 12. 状态超时（Aspect K）

### 12.1 超时场景

```text
超时场景类型：

1. 状态超时
   ├─ 订单待支付超时 → 自动取消
   ├─ 退款待审批超时 → 自动通过/拒绝
   └─ 合同待签署超时 → 自动作废

2. 操作超时
   ├─ 支付接口响应超时 → 查询状态
   ├─ 库存预占超时 → 释放预占
   └─ 外部履约超时 → 触发补偿

3. 业务窗口超时
   ├─ 退货期限（签收后7天）
   ├─ 发票认证期限（开票后360天）
   └─ 售后申请期限（订单完成后30天）
```

### 12.2 超时实现方式

```text
实现方式1：定时任务扫描
├─ 定期扫描过期状态
├─ 触发超时处理
├─ 优点：实现简单
└─ 缺点：有延迟，不够精确

实现方式2：延迟消息/延迟队列
├─ 状态变更时发送延迟消息
├─ 延迟时间到时检查状态
├─ 如仍为超时状态，执行超时处理
├─ 优点：精确
└─ 缺点：消息中间件依赖

实现方式3：事件驱动
├─ 状态变更时注册定时器
├─ 到期触发回调
├─ 优点：精确、无轮询
└─ 缺点：框架支持

实现方式4：TTL + 事件
├─ 数据库行设置TTL
├─ 过期触发事件
├─ 优点：数据库原生支持
└─ 缺点：精确度有限
```

```java
public class OrderStateMachine {
    
    public static StateMachineDefinition definition() {
        return StateMachineBuilder.<OrderStatus, OrderEvent>builder()
            .initial(OrderStatus.DRAFT)
            
            .transition()
                .from(OrderStatus.DRAFT)
                .to(OrderStatus.PENDING)
                .on(OrderEvent.SUBMIT)

                    delayQueue.send(createTimeoutMessage(ctx));

                .to(OrderStatus.CANCELLED)
                .on(OrderEvent.PAYMENT_TIMEOUT)
                .guard(ctx -> ctx.getOrder().isPaymentTimedOut())
                .withAction(ctx -> {
                    ctx.getOrder().cancel("支付超时");
                })
```

## 13. 状态与通知（Aspect L）

### 13.1 通知触发机制

```text
通知触发点：

1. 状态进入
   ├─ 订单进入 PENDING → 通知商家有新订单
   ├─ 订单进入 PAID → 通知仓库准备发货
   └─ 订单进入 COMPLETED → 通知用户评价

2. 状态保持
   ├─ 订单 PENDING 超过10分钟 → 提醒用户支付
   ├─ 退款 PENDING 超过24小时 → 提醒审批
   └─ 退货 SHIPPING 超过7天 → 提醒确认收货

3. 状态退出
   ├─ 订单离开 PENDING → 取消支付倒计时
   ├─ 退款离开 PROCESSING → 发送退款结果通知
   └─ 订单离开 CANCELLED → 发送取消原因

4. 状态异常
   ├─ 订单 EXCEPTION → 通知客服介入
   ├─ 发货超时 → 通知运营
   └─ 支付失败 → 通知用户重试
```

### 13.2 通知配置

```java
            .map(Order::getAmount)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
```

```java
public class OrderPaymentSaga {
    
    public void execute(CreateOrderCommand cmd) {
        // 1. 创建订单
        Order order = orderService.create(cmd);
        sagaState = SagaState.ORDER_CREATED;
        
        try {
            // 2. 预占库存
            inventoryService.reserve(order.getItems());
            sagaState = SagaState.INVENTORY_RESERVED;
            
            // 3. 发起支付
            Payment payment = paymentService.authorize(order);
            sagaState = SagaState.PAYMENT_AUTHORIZED;
            
            // 4. 确认支付
            paymentService.capture(payment);
            sagaState = SagaState.PAYMENT_CAPTURED;
            
            // 5. 完成订单
            orderService.confirm(order);
            sagaState = SagaState.COMPLETED;
            
        } catch (Exception e) {
            compensate(e);
        }
    }
    
    public void compensate(Exception cause) {
        // 补偿已执行的步骤
        switch (sagaState) {
            case PAYMENT_CAPTURED:
                paymentService.refund(payment);
            case PAYMENT_AUTHORIZED:
                paymentService.cancelAuthorization(payment);
            case INVENTORY_RESERVED:
                inventoryService.release(order.getId());
            case ORDER_CREATED:
                orderService.cancel(order);
        }
        
        sagaState = SagaState.COMPENSATED;
    }
}
```

```java
public class OrderCoordinationService {
    
    @Transactional
    public void coordinateOrderPayment(String orderId, 
                                        PaymentCallbackRequest request) {
        // 获取分布式锁
        String lockKey = "order_payment:" + orderId;
        distributedLock.execute(lockKey, Duration.ofSeconds(30), () -> {
            
            // 1. 查询当前状态
            Order order = orderRepository.findById(orderId);
            Payment payment = paymentRepository.findByOrderId(orderId);
            
            // 2. 幂等处理
            if (payment.getStatus() == PaymentStatus.CAPTURED) {
                return; // 已处理，直接返回
            }
            
            // 3. 支付状态转换
            if (request.isSuccess()) {
                payment.capture();
            } else {
                payment.fail(request.getErrorCode());
            }
            
            // 4. 订单状态同步
            if (payment.isCaptured()) {
                order.confirmPayment(payment.getId());
                fulfillmentService.prepareFulfillment(orderId);
            } else if (payment.isFailed()) {
                order.onPaymentFailed(payment.getErrorCode());
            }
            
            // 5. 发布事件
            DomainEvents.publish(new OrderPaymentProcessedEvent(
                orderId, payment.getStatus()
            ));
        });
    }
}
```

### 16.6 跨对象状态一致性保证

```text
一致性保证级别：

最终一致（Eventual Consistency）
├─ 短暂不一致可接受
├─ 通过事件异步同步
├─ 实现简单、性能好
└─ 适用：非关键状态

强一致（Strong Consistency）
├─ 操作原子完成
├─ 同一事务内更新多个对象
├─ 实现复杂、性能损耗
└─ 适用：关键业务

业务补偿（Business Compensation）
├─ 操作可能部分成功
├─ 通过补偿达到最终一致
├─ 需要设计补偿逻辑
└─ 适用：跨系统操作

Saga 编排
├─ 分布式事务替代方案
├─ 每个步骤有补偿
├─ 最终一致性
└─ 适用：微服务架构

选择原则：
├─ 强一致：支付、资金、库存（超卖不可接受）
├─ 最终一致：非关键状态、查询优化视图
├─ 业务补偿：退款、退货、外部系统调用
└─ Saga：微服务间的长事务
```

```text
├─ 优点：可视化流程、长流程、人工任务
├─ 缺点：重、不适合高频状态转换
└─ 适用：审批流、人工介入流程
```

### 17.2 无框架实现

```java
// 最简单的状态机实现
public class Order {
    
    private OrderStatus status = OrderStatus.DRAFT;
    
    private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = Map.of(
        DRAFT, Set.of(PENDING, CANCELLED),
        PENDING, Set.of(PAID, CANCELLED),
        PAID, Set.of(PROCESSING, REFUNDING, CANCELLED),
        PROCESSING, Set.of(DELIVERED, CANCELLED),
        DELIVERED, Set.of(COMPLETED, RETURNING),
        COMPLETED, Set.of(REFUNDING),
        RETURNING, Set.of(REFUNDED, RETURNED)
    );
    
    public void transitionTo(OrderStatus target) {
        Set<OrderStatus> allowed = TRANSITIONS.get(this.status);
        if (allowed == null || !allowed.contains(target)) {
            throw new IllegalStateTransitionException(
                "不允许从 " + this.status + " 转换到 " + target);
        }
        this.status = target;
    }
    
    // 具体命令方法
    public void submit() { transitionTo(PENDING); }
    public void pay() { transitionTo(PAID); }
    public void cancel() { transitionTo(CANCELLED); }
}
```

### 17.3 Spring StateMachine

```java
// Spring StateMachine 配置
@Configuration
@EnableStateMachine
public class OrderStateMachineConfig 
    extends StateMachineConfigurationAdapter {
    
    @Override
    public void configure(StateMachineConfigurationConfigurer<String, 
            OrderEvent> config) throws Exception {
        config
            .withPersistence()
                .stateMachineArgumentResolver(
                    new JpaStateMachineStore(jpaTemplate))
                .stateMachinePersistence(
                    new RepositoryStateMachineRuntimeService(
                        stateMachineRepository))
            .and()
            .withConfiguration()
                .autoStartup(false)
                .taskExecutor(taskExecutor)
                .listenerFactory(stateMachineListenerFactory);
    }
    
    @Override
    public void configure(StateMachineStateConfigurer<OrderStatus, 
            OrderEvent> states) throws Exception {
        states
            .withStates()
                .initial(OrderStatus.DRAFT)
                .states(EnumSet.allOf(OrderStatus.class))
                .end(OrderStatus.COMPLETED)
                .end(OrderStatus.CANCELLED);
    }
    
    @Override
    public void configure(StateMachineTransitionConfigurer<OrderStatus, 
            OrderEvent> transitions) throws Exception {
        transitions
            .withExternal()
                .source(DRAFT).target(PENDING)
                .event(SUBMIT)
                .guard(orderGuard())
            .and()
            .withExternal()
                .source(PENDING).target(PAID)
                .event(PAY)
                .action(paymentAction())
            .and()
            // ... 更多转换
            .withExternal()
                .source(PENDING).target(CANCELLED)
                .event(CANCEL)
                .action(cancelAction());
    }
    
    @Bean
    public Guard<OrderStatus, OrderEvent> orderGuard() {
        return ctx -> {
            Order order = ctx.getExtendedState()
                .get("order", Order.class);
            return order != null && order.isValid();
        };
    }
}
```

### 17.5 选择建议

```text
选择无框架的情况：
├─ 状态数量少（<10个状态）
├─ 状态机简单（无复杂Guard）
├─ 不需要持久化
├─ 团队偏好轻量
└─ 示例：简单订单、单一实体

选择 Spring StateMachine：
├─ 需要持久化状态机
├─ 需要状态机重启恢复
├─ 状态转换有复杂条件
├─ 需要与Spring生态集成
└─ 示例：订单、退款、工单

选择 Akka/Pekko：
├─ 高并发场景
├─ 分布式系统
├─ 需要消息驱动
├─ 需要容错恢复
└─ 示例：交易系统、游戏服务器

选择 BPMN 引擎：
├─ 有大量人工审批
├─ 需要可视化流程
├─ 流程需要经常调整
├─ 需要流程监控
└─ 示例：审批流、合同流程、客服工单

选择事件溯源框架：
├─ 审计要求极高
├─ 需要业务事件回放
├─ 需要时序查询
└─ 示例：金融系统、合规系统
```

## 18. 状态建模与其他模型的关系

### 18.1 状态机 vs Invariant

```text
状态机：定义合法转换路径
Invariant：定义任意路径的底线

关系：
├─ 状态机转换前：检查 Invariant
├─ 状态机转换后：验证 Invariant
└─ 两者共同保证业务正确性

示例：
├─ Invariant：累计退款 <= 原支付
│   ├─ 在退款转换前检查
│   └─ 防止超额退款
│
└─ State Machine：退款状态转换
    ├─ PENDING → APPROVED
    ├─ APPROVED → PROCESSING
    └─ PROCESSING → SUCCESS/FAILED
```

### 18.2 状态机 vs Saga

```text
状态机：单个对象的生命周期
Saga：跨多个对象的长事务

关系：
├─ Saga 的每一步可能触发状态机转换
├─ Saga 的补偿可能涉及多个状态机
└─ Saga 可以用状态机建模

示例（退款 Saga）：
├─ 退款状态机：PENDING → APPROVED → PROCESSING → SUCCESS
│
└─ 退款 Saga 步骤：
    ├─ Step 1: 更新订单状态（订单状态机）
    ├─ Step 2: 执行退款（支付状态机）
    ├─ Step 3: 更新发票（发票状态机）
    └─ 补偿：反向执行各步骤
```

### 18.3 状态机 vs Ledger

```text
状态机：对象生命周期
Ledger：价值变化记录

关系：
├─ 状态机转换可能产生 Ledger 分录
├─ Ledger 分录可能触发状态转换
└─ 两者都需要不可变记录

示例：
├─ 支付状态机：PENDING → CAPTURED
│   └─ 触发资金 Ledger 分录
│
└─ 退款 Ledger：
    ├─ 原支付分录（借/贷）
    └─ 退款分录（逆向借贷）
        └─ 触发退款状态机：PROCESSING → SUCCESS
```

### 18.4 状态机 vs Workflow

```text
状态机：单个对象的状态变化
Workflow：多角色、多任务的协作流程

关系：
├─ 状态机适合简单的自动化转换
├─ Workflow 适合需要人工参与的复杂流程
├─ 两者可以嵌套使用
└─ 状态机定义"对象能做什么"
  └─ Workflow 定义"谁来做什么"

示例：
├─ 订单状态机：
│   PENDING → APPROVED → PROCESSING → COMPLETED
│
└─ 审批 Workflow：
    ├─ 提交申请 → 店长审批 → 财务审批 → 执行
    └─ 每个节点可能触发状态机转换
```

### 18.5 综合示例

```text
订单退款完整模型：

State Machine（退款生命周期）
├─ 退款单状态：PENDING → APPROVED → PROCESSING → SUCCESS/FAILED
│
├─ PENDING：等待审批
├─ APPROVED：审批通过，待执行
├─ PROCESSING：正在退款
├─ SUCCESS：退款成功
└─ FAILED：退款失败

Specification（资格判断）
├─ 订单是否可以退款
├─ 退款金额是否合规
└─ 当前用户是否有权限申请

Decision Table（审批规则）
├─ 金额 <= 500 → 自动批准
├─ 金额 > 500 → 人工审批
└─ 黑名单 → 拒绝

Invariant（底线）
├─ 累计退款 <= 原支付金额
├─ 退款金额 = 可退金额
└─ 退款只能成功一次

Ledger（账务记录）
├─ 原支付分录
├─ 退款分录
└─ 优惠返还分录

Saga（跨系统协调）
├─ Step 1: 创建退款单（订单状态机）
├─ Step 2: 调用支付渠道（支付状态机）
├─ Step 3: 更新发票（发票状态机）
├─ Step 4: 更新账务（Ledger）
└─ 失败补偿：反向执行
```

## 19. 常见反模式

### 19.1 状态字段滥用

```text
反模式1：一个状态字段表示多个含义
├─ status = 1 表示"草稿"
├─ status = 2 表示"已提交且有折扣"
├─ status = 3 表示"已提交且是大客户"
└─ 需要查文档才知道什么意思

反模式2：用数字状态代替枚举
├─ status = 1, 2, 3...
├─ 任意数字都可以存入
└─ 业务含义不明确

反模式3：状态字段可写可改
├─ order.status = "COMPLETED"
├─ 任何地方都可以直接修改
└─ 无法追踪谁改的、什么时候改的

正确做法：
├─ 枚举类型明确业务含义
├─ 状态转换通过方法控制
└─ 状态变化记录审计日志
```

### 19.2 状态爆炸

```text
反模式：所有维度塞进一个状态
├─ OrderStatus = "PAID_PARTIAL_SHIPPED_DISCOUNT_VIP"
├─ 状态组合爆炸
├─ 转换规则复杂
└─ 新需求难以加状态

正确做法：
├─ 按业务维度分离状态
├─ 订单状态、支付状态、履约状态独立
├─ 派生聚合视图
└─ 保持状态机简单
```

### 19.3 状态与业务逻辑混淆

```text
反模式：在状态转换中混入业务逻辑
├─ void approve(Order order) {
│       if (order.getAmount() > 10000) {
│           sendEmail();
│           deductInventory();
│           notifyWarehouse();
│       }
│       order.status = APPROVED;
│   }
│   └─ 状态转换方法承担了太多职责

正确做法：
├─ 状态转换只改变状态
├─ 副作用通过事件触发
├─ void approve(Order order) {
│       order.status = APPROVED;
│       DomainEvents.publish(new OrderApprovedEvent(order));
│   }
│
├─ 事件监听器处理副作用
└─ @EventListener onOrderApproved() {
        sendEmail();
        deductInventory();
        notifyWarehouse();
    }
```

### 19.4 忽略状态历史

```text
反模式：不记录状态变更历史
├─ 直接 UPDATE status = 'CANCELLED'
├─ 不知道谁改的、什么时候改的
├─ 无法审计和排查问题
└─ 丢失业务上下文

正确做法：
├─ 状态变更记录完整历史
├─ 包括：操作人、时间、原因、变更前后状态
├─ 可选：变更时的业务快照
└─ 事件溯源保留完整链
```

### 19.5 状态转换缺少前置条件

```text
反模式：状态可以任意转换
├─ order.status = APPROVED; // 直接设置
├─ 任何状态都可以改成任何状态
├─ 没有前置条件检查
└─ 业务规则被绕过

正确做法：
├─ 通过方法控制状态转换
├─ public void approve() {
│       require(currentStatus == PENDING);
│       require(hasPermission());
│       currentStatus = APPROVED;
│   }
├─ 转换规则显式声明
└─ Guard 条件明确
```

### 19.6 终结状态可逆

```text
反模式：已完成或已取消的订单仍可修改
├─ COMPLETED 状态可以变成 PROCESSING
├─ CANCELLED 状态可以重新支付
├─ 违反业务常理
└─ 导致数据不一致

正确做法：
├─ 终结状态后不再允许状态转换
├─ public void transitionTo(Status target) {
│       if (this.status.isFinal()) {
│           throw new IllegalStateException("终态不可变");
│       }
│       // ...
│   }
├─ 逆向通过新的业务能力（如"售后"）
└─ 而不是修改原状态
```

## 20. AI 执行协议

### 20.1 状态建模分析算法

```text
INPUT：业务需求、用户故事、现有系统、历史数据

1. 识别业务对象
   ├─ 从需求中提取核心业务实体
   ├─ 确定实体的生命周期
   └─ 区分实体和值对象

2. 识别状态维度
   ├─ 哪些维度有独立状态变化
   ├─ 是否需要分离多个状态字段
   └─ 是否需要子状态

3. 定义状态值
   ├─ 使用业务语言命名
   ├─ 状态值是否互斥
   ├─ 是否有终结状态
   └─ 状态数量是否合理

4. 定义转换规则
   ├─ 从需求中提取转换路径
   ├─ 确定触发事件/命令
   ├─ 定义 Guard 条件
   └─ 定义转换副作用

5. 识别跨对象协调
   ├─ 哪些状态转换需要跨对象
   ├─ 使用 Saga 还是事件
   └─ 一致性要求级别

6. 定义不变量
   ├─ 状态转换前的不变量
   ├─ 状态转换后的不变量
   └─ 跨状态不变量

7. 设计持久化
   ├─ 当前状态如何存储
   ├─ 状态历史如何存储
   ├─ 是否需要事件溯源
   └─ 选择持久化策略

8. 设计异常处理
   ├─ 转换失败的恢复
   ├─ 超时状态处理
   └─ 补偿和逆向

9. 补充权限和通知
   ├─ 什么角色可以触发什么转换
   ├─ 状态变化触发什么通知
   └─ SoD 规则

10. 生成产物
    ├─ 状态图
    ├─ 转换表
    ├─ 不变量清单
    ├─ 测试用例
    └─ 代码框架
```

### 20.2 状态建模检查清单

- [ ] 每个业务实体有明确的状态定义
- [ ] 状态使用业务语言命名，不是技术术语
- [ ] 状态转换有明确的前置条件
- [ ] 状态转换有明确的副作用
- [ ] 终结状态不可再变
- [ ] 状态历史可追溯
- [ ] 跨对象状态有一致性保证
- [ ] 状态与权限正确关联
- [ ] 状态变化触发正确通知
- [ ] 超时状态有处理机制
- [ ] 逆向流程正确建模
- [ ] 不变量在状态转换时被校验
- [ ] 状态机已测试覆盖
