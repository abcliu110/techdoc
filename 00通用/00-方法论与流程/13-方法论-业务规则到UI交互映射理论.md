# 业务规则到 UI 交互映射理论

> 版本：v1.0  
> 适用对象：业务分析、产品设计、交互设计、前后端契约设计、规则平台和既有系统重构  
> 上游方法：`14-方法论-具体业务规则实现模型与选型.md`  
> 相邻方法：`07-方法论-数据模型与UI双向逆向工程.md`  
> 设计评审：`SOP-09-业务设计合理性评审.md`

## 0. AI 执行入口

### 0.1 最小输入

- 业务能力、用户任务、角色和责任边界。
- 业务事实、不变量、Policy、Rule、Decision、State 和 Process。
- 规则作用域、版本、时间、权限和例外机制。
- 页面或任务场景、设备、风险等级和可用性约束。
- API、状态转换、失败恢复和审计要求。

输入不足时，AI 只能输出候选交互契约、竞争设计和待验证问题，不能根据字段名、现有页面或行业惯例自行决定业务语义。

### 0.2 核心输出

```text
规则语义模型
+ 角色—任务—状态矩阵
+ 规则到交互义务映射
+ 交互契约与页面状态模型
+ UI—API—领域守卫追踪矩阵
+ 解释、失败与恢复设计
+ 规则配置和版本治理界面
+ 场景测试与评审结论
```

### 0.3 核心命题

> 业务规则不直接映射为控件。业务规则先约束某个角色在特定任务、状态和上下文中的信息、决策权与行动空间，再由交互设计把这些约束表达为可感知、可执行、可解释、可恢复的交互契约。

形式化表达：

```text
InteractionContract
  = Project(BusinessSemantics,
            Actor,
            Task,
            Context,
            BusinessState,
            PolicyVersion,
            DecisionAuthority,
            Risk,
            Device)
```
## 1. 问题定义：缺失的是“语义—交互桥接层”

常见设计直接从规则跳到控件：

```text
字段必填 → 加红星
没有权限 → 隐藏按钮
状态不允许 → 禁用按钮
计算规则 → 显示结果
```

这只能处理局部表现，不能回答以下问题：

1. 谁需要感知这条规则，谁只受它约束？
2. 规则影响的是输入、行动、结果、流程还是解释？
3. 应在输入前、输入中、提交前、提交后还是异步完成后表达？
4. 应隐藏、禁用、只读、警告、阻断、审批还是允许例外？
5. 规则由 UI 预检还是由服务端权威裁决？
6. 多条规则同时命中时，UI 展示候选、最终结果还是冲突？
7. 失败后用户如何恢复，而不是只得到“操作失败”？
8. 历史对象应使用当前规则还是原决策快照解释？

因此需要一个中间层：

```text
业务语义层
  Fact / Invariant / Policy / Rule / Decision / State / Process
                 ↓
交互语义层
  Actor / Task / Intent / Authority / Obligation / Feedback / Recovery
                 ↓
表现层
  Page / Field / Action / Status / Message / Timeline / Dialog
```

本文重点是中间的交互语义层。控件选择只是最后一步。

## 2. 理论基础

本文不是发明一套孤立规则，而是把多个成熟理论组合成可执行的桥接模型。

### 2.1 活动与任务理论：规则必须落到人的目标

业务系统中的 UI 不是数据表的外观，而是角色完成任务的工具。分析单位应为：

```text
Actor 在 Context 中，为达到 Goal，基于 Fact，执行 Command，
使业务对象从 State-A 进入 State-B，并承担相应 Outcome。
```

同一条规则对不同角色产生不同界面责任：

- 顾客需要知道优惠是否可用以及如何恢复资格。
- 收银员需要知道当前可以执行什么和如何处理例外。
- 运营人员需要配置规则、模拟影响和发布版本。
- 审计人员需要查看原始事实、决策依据和人工覆盖。

**适用条件：**规则会影响人的任务、责任、判断或恢复。  
**边界：**纯内部优化且不改变可观察行为时，不必映射成可见 UI。  
**反例：**数据库索引选择不是用户任务，不应生成“索引状态”字段。  
**已有机制：**JTBD、Use Case、User Story 可描述目标，但仍需本文补充规则、状态和失败语义。

### 2.2 行动循环：跨越执行鸿沟与评价鸿沟

用户需要完成两个闭环：

```text
执行闭环：目标 → 意图 → 可用动作 → 执行
评价闭环：系统状态 → 可感知反馈 → 解释 → 判断目标是否达成
```

业务规则同时影响两个闭环：

- 执行侧：哪些动作存在、能否执行、需要哪些输入。
- 评价侧：发生了什么、为什么、是否完成、下一步怎么办。

只禁用按钮而不解释，关闭了执行路径，却没有弥合评价鸿沟；只显示“成功”，却没有显示权威业务结果，则可能给出虚假完成感。

**适用条件：**规则改变用户可执行动作或结果解释。  
**边界：**低风险、立即可逆且结果直观的微交互可以使用轻量反馈。  
**反例：**标签重命名成功通常不需要展示完整决策链。  
**已有机制：**可用性启发式能检查反馈，但不能替代业务权威和规则来源分析。

### 2.3 有限状态与命令理论：UI 是状态相关的命令面

对某个业务对象，UI 的可用动作不是按钮集合，而是当前状态下合法命令的投影：

```text
AllowedCommands
  = AuthorizedCommands(Actor, Scope)
  ∩ LegalTransitions(BusinessState)
  ∩ EligibleCommands(Context, PolicyVersion)
  ∩ RiskPermittedCommands(ControlState)
```

例如“退款”按钮是否可用，可能同时取决于订单状态、支付事实、累计退款、操作者权限、时间窗和风险控制。前端只根据 `status == PAID` 判断会丢失其他条件。

**适用条件：**对象存在生命周期、合法转换或命令前置条件。  
**边界：**普通无状态查询不需要强行建立状态机。  
**反例：**搜索关键词输入不是业务状态转换。  
**已有机制：**State Machine 描述合法转换；本文负责将其投影成动作、状态、反馈和恢复。

### 2.4 决策理论：区分事实输入、系统裁决和用户决策

UI 必须区分三类内容：

```text
事实输入：用户提供系统无法自动获得的事实。
业务选择：组织允许用户在合法候选中作出选择。
系统裁决：规则根据事实和政策形成唯一结果。
```

不能让用户编辑系统裁决来绕过规则，也不能把真实业务选择伪装成系统自动决定。

例如：

- “退款原因”可能是用户陈述的事实。
- “退款方式”可能是受约束的业务选择。
- “最大可退金额”是系统裁决。
- “超过阈值是否批准”属于审批人的决策权。

**适用条件：**界面同时包含输入、推荐、选择和最终结果。  
**边界：**某些事实可由设备或外部系统自动采集，用户只需确认。  
**反例：**把折扣计算结果做成可编辑金额，会把系统裁决错误地变成用户输入。  
**已有机制：**决策表、DMN 和 Policy 负责裁决；本文负责决策权和交互表达。

### 2.5 控制论：UI 是闭环控制系统的一部分

业务操作不是“提交即结束”，而是：

```text
目标 → 操作 → 系统处理 → 观测结果 → 比较目标 → 修正/恢复
```

异步、跨系统或可能部分失败的业务尤其需要闭环：

- 当前处于什么阶段。
- 哪个结果已经成为权威事实。
- 哪些副作用仍在处理中。
- 超时后是未知、失败还是可重试。
- 谁负责重试、补偿、对账或人工介入。

**适用条件：**长流程、异步处理、外部副作用或最终一致业务。  
**边界：**同步、低风险、原子操作可以压缩反馈层次。  
**反例：**支付请求超时后直接显示“支付失败”，可能诱导用户重复支付。  
**已有机制：**工作流、Saga、任务系统提供运行机制；本文定义用户可感知状态和恢复契约。

### 2.6 信息可见性与渐进披露

规则信息是否展示，取决于用户当前任务是否需要它来：

- 形成正确预期。
- 作出合法选择。
- 理解系统决定。
- 修复失败。
- 承担审批或审计责任。

不是所有规则都要展示全文；应根据任务将信息分为：

```text
立即必要：当前动作前必须知道。
按需解释：用户质疑或需要诊断时展开。
审计细节：高权限角色或历史追溯时查看。
内部机制：不影响用户决策，不直接展示。
```

**适用条件：**规则复杂且不同角色的信息需求不同。  
**边界：**渐进披露不能隐藏会影响同意、费用、风险或不可逆结果的重要信息。  
**反例：**结算前把自动续费条件隐藏到深层帮助页。  
**已有机制：**信息架构和渐进披露负责呈现层次；业务规则决定哪些信息不能被省略。

## 3. 核心模型：规则不是控件，映射单位是交互契约

### 3.1 业务规则模型

一条可映射规则至少应具有：

```text
BusinessRule R =
  <Meaning, Type, Source, Owner,
   Scope, Applicability, Inputs,
   DecisionOrConstraint,
   Relations, EffectivePeriod,
   Version, Override, Audit>
```

如果缺少业务含义、作用域或版本，UI 无法正确判断何时、向谁以及以什么强度表达。

### 3.2 交互契约模型

```text
InteractionContract IC =
  <Actor, Task, Trigger, BusinessState,
   RequiredFacts, VisibleInformation,
   AllowedCommands, FieldPolicies,
   DecisionProjection, Feedback,
   Recovery, Explanation, Audit,
   Authority, Freshness>
```

含义：

| 元素 | 回答的问题 |
|---|---|
| Actor | 谁在使用，承担什么责任 |
| Task | 当前要完成什么业务结果 |
| Trigger | 什么事件进入该交互 |
| BusinessState | 当前权威业务状态是什么 |
| RequiredFacts | 还缺哪些事实才能决策 |
| VisibleInformation | 为完成任务必须知道什么 |
| AllowedCommands | 当前可以发出哪些业务命令 |
| FieldPolicies | 哪些字段可见、可编辑、必填或只读 |
| DecisionProjection | 系统裁决如何向用户表达 |
| Feedback | 操作后立即感知什么 |
| Recovery | 失败、冲突和未知状态如何处理 |
| Explanation | 为什么允许、拒绝或选择该结果 |
| Audit | 哪些操作和依据必须留痕 |
| Authority | UI、服务端或人工谁有最终决定权 |
| Freshness | 该状态和规则版本在何时有效 |

### 3.3 UI 状态是交互契约的渲染

```text
UIState = Render(InteractionContract, Platform, DesignSystem, Locale)
```

因此：

- 同一交互契约可以在 Web、POS、移动端产生不同布局。
- 同一业务规则可映射到多个角色页面。
- 同一页面会组合多条规则产生的契约。
- 控件不同不代表业务语义不同。
- 页面相似也不证明底层业务规则相同。

## 4. 从规则到 UI 的五级转换

### 4.1 第一级：规则语义规范化

先区分：事实、不变量、资格、选择、计算、状态、流程、权限、时间、额度、例外和审计。不得把技术配置或当前页面行为直接当成业务规则。

### 4.2 第二级：角色和任务定位

对每条规则回答：

```text
谁受规则影响？
谁需要提供事实？
谁拥有选择权？
谁拥有审批或覆盖权？
谁承担错误结果？
谁需要事后解释？
```

### 4.3 第三级：推导交互义务

交互义务只有有限几类：

| 义务 | 含义 |
|---|---|
| Acquire | 收集决策所需事实 |
| Inform | 告知适用政策、状态或后果 |
| Constrain | 限制非法输入和动作 |
| Guide | 引导完成合法任务 |
| Decide | 让有权角色在合法候选中选择 |
| Confirm | 对高风险或不可逆后果取得确认 |
| Explain | 说明命中、排除和结果原因 |
| Recover | 提供重试、撤回、补偿或人工路径 |
| Audit | 展示或记录责任、版本和历史 |

### 4.4 第四级：形成交互契约

将多个规则对同一 `Actor × Task × State` 的义务合并，解决冲突后形成唯一契约。若一条规则要求字段可编辑，另一条要求当前状态只读，必须通过业务优先级裁决，不能依赖组件最后一次赋值。

### 4.5 第五级：选择表现形式

只有完成前四级后，才选择：

```text
页面 / 工作台 / 向导 / 弹窗 / 抽屉
输入框 / 选择器 / 只读摘要
按钮 / 菜单 / 批量操作
状态标签 / 时间线 / 进度条
内联提示 / 警告 / 阻断弹窗
决策明细 / 审计日志 / 对比预览
```

表现形式由频率、风险、信息密度、设备、可访问性和设计系统决定，不由规则类型单独决定。
## 5. 规则类型到交互义务的映射

### 5.1 不变量：从“绝不能发生”映射为多层守卫

示例：累计有效退款不得超过原有效支付。

```text
业务层：Invariant(refunded <= paid)
交互义务：Inform + Constrain + Explain + Recover
UI 投影：显示已付、已退、最大可退；输入即时提示；提交前阻断
服务端：重新计算并原子校验
数据层：条件更新、唯一性或账本约束
恢复：刷新最新额度、调整金额、转人工核查
```

UI 只能提前反馈，不能成为不变量的唯一守卫，因为并发、旁路 API、旧客户端和数据变化都可能绕过它。

**适用条件：**任意合法路径都必须成立的业务底线。  
**边界：**并非所有不变量都应完整暴露内部公式；敏感风控可只给合法修复提示。  
**反例：**仅设置输入框 `max=100`，但另一个退款请求并发发生。  
**已有机制：**领域守卫、数据库约束和条件更新负责权威保护；UI 负责预防错误和解释。

### 5.2 资格规则：从“是否适用”映射为资格状态

资格结果不应只有布尔值：

```text
EligibilityResult
- eligible
- reasonCode
- missingFacts
- recoverable
- recoveryActions
- evaluatedAt
- policyVersion
```

UI 表达可分为：

- 未评估：仍缺信息。
- 评估中：远程或复杂计算。
- 有资格：展示可获得结果。
- 暂无资格但可恢复：说明补齐条件。
- 无资格且不可恢复：说明适用边界。
- 资格未知：系统暂时不能确认，避免误报为“不符合”。

**适用条件：**会员、优惠、退款、授信、审批、权限等前置判断。  
**边界：**安全策略可能不能透露完整拒绝原因，应返回可行动但不过度泄露的信息。  
**反例：**优惠券按钮消失，用户无法区分无资格、已用完、过期或系统故障。  
**已有机制：**Specification/Decision Table 负责计算资格；UI 展示状态和恢复路径。

### 5.3 分类与选择规则：从候选集合映射为选择或系统裁决

先判断决策权：

```text
用户拥有选择权 → 展示合法候选、差异、后果和默认值来源。
系统拥有裁决权 → 展示最终选择及必要解释，不伪装为用户选择。
审批人拥有裁决权 → 展示证据、建议和批准/拒绝的责任后果。
```

默认值只有在可修改且不诱导错误决策时才是便利；若默认值承载政策，就必须说明来源和影响。

**适用条件：**多个合法结果需要选择、择优或优先裁决。  
**边界：**候选很多时需要筛选、推荐或分步，而不是完整平铺。  
**反例：**系统按利润最大化自动选择方案，却用已勾选单选框制造“用户选择”的表象。  
**已有机制：**Decision Table/DMN 决定候选和命中策略；UI 负责决策权的真实表达。

### 5.4 计算规则：从公式映射为输入、预估和最终结果

计算型 UI 至少区分：

```text
用户输入事实
系统使用的基准
实时预估值
服务端最终值
舍入、税费、分摊和上下限
结果失效或重算条件
```

高影响计算应允许查看明细，但不一定暴露内部代码表达式。输入变化后，旧预估必须标记失效或重新计算。

**适用条件：**价格、税费、运费、积分、评分、额度等计算。  
**边界：**简单且直观的低风险计算不需要展开全部中间值。  
**反例：**前端计算 79.99，服务端因舍入和税制返回 80.01，却没有差异提示。  
**已有机制：**Formula/Strategy/Pipeline 负责计算；UI 负责输入来源、预估状态和结果解释。

### 5.5 状态转换规则：从状态机映射为命令面

不要把状态机简单映射成状态下拉框。每个转换应生成：

```text
当前状态摘要
+ 当前角色允许命令
+ 命令前置条件
+ 预期目标状态
+ 重要副作用
+ 确认级别
+ 处理中状态
+ 失败与恢复
+ 状态历史
```

状态下拉框只适用于真正允许任意选择且副作用受控的管理场景。大多数业务状态必须通过具名命令转换，例如“审核通过”“发货”“取消”，不能直接改成任意值。

**适用条件：**对象生命周期和转换有业务语义。  
**边界：**展示标签或纯派生状态不一定需要命令 UI。  
**反例：**管理员直接把订单从“待支付”改成“已完成”，绕过支付、库存和审计。  
**已有机制：**State Machine/Guard 维护合法转换；UI 表达命令和结果。

### 5.6 流程规则：从协作过程映射为任务、进度和等待

流程 UI 的核心不是画流程图，而是让每个参与者知道：

- 当前轮到谁。
- 需要完成什么任务。
- 依赖什么输入。
- 截止时间和升级路径。
- 当前在等待什么。
- 驳回后回到哪里。
- 部分完成和撤回如何表达。

**适用条件：**多角色、等待、审批、超时、人工介入或跨系统协作。  
**边界：**短小同步流程不必建设工作流中心。  
**反例：**审批页面只显示“处理中”，不显示当前节点、负责人和超时处理。  
**已有机制：**BPMN/Workflow/Process Manager 负责流程执行；UI 投影待办、时间线和恢复动作。

### 5.7 权限规则：从授权映射为可见信息和可执行命令

权限至少分离：

```text
CanDiscover：是否知道能力存在。
CanView：是否查看对象及字段。
CanExecute：是否发出命令。
CanApprove：是否批准他人请求。
CanOverride：是否突破普通政策。
DataScope：可作用于哪些对象和数据。
```

隐藏、禁用和只读的选择取决于任务：

- 能力与角色无关或涉及安全泄露：隐藏。
- 用户需要知道能力存在但当前条件不满足：禁用并解释。
- 用户需要查看事实但无修改权：只读。
- 有权限但数据范围不匹配：拒绝并避免泄露对象细节。

**适用条件：**角色、属性、租户、对象或数据范围影响访问。  
**边界：**前端表现不构成授权；所有命令必须服务端校验。  
**反例：**隐藏“删除”按钮但 API 仍可直接调用。  
**已有机制：**RBAC/ABAC/SoD 负责授权；UI 只投影当前主体的能力。

### 5.8 时间与版本规则：从有效期映射为时态界面

UI 应区分：

```text
业务发生时间
规则生效时间
系统处理时间
数据记录时间
当前查看时间
```

规则配置界面要表达草稿、待生效、生效中、停止新业务使用、仅服务历史对象和已退役。历史对象详情应显示原规则版本或决策快照，不能用当前规则重新解释。

**适用条件：**政策、合同、价格、权益或流程随时间变化。  
**边界：**瞬时、无历史影响的临时筛选不需要版本治理。  
**反例：**修改价格政策后，历史订单详情随当前政策发生变化。  
**已有机制：**Effective Dating/Versioned Policy 保存时态语义；UI 提供版本选择、比较和历史解释。

### 5.9 额度、库存和资源规则：从守恒关系映射为可用性

UI 不应只展示一个“余额”，而应根据任务区分：

```text
总额度 / 已分配 / 已预占 / 已使用 / 可用 / 待释放 / 调整中
```

提交后如果只是预占成功，不能显示“最终使用成功”。释放失败或数据延迟时，应表达当前不确定性和对账状态。

**适用条件：**库存、预算、次数、信用、席位和产能存在竞争或预占。  
**边界：**无并发、无预占的静态上限可以简化。  
**反例：**两个终端都看到“可用 1”，各自在前端减一并提交。  
**已有机制：**Reservation/Quota/Ledger 负责权威资源变化；UI 提供可用量、占用状态和恢复信息。

### 5.10 例外与覆盖规则：从特殊权力映射为受控路径

例外 UI 不能是“管理员可随便改”。必须包含：

```text
例外类型
适用条件
授权主体
理由和证据
影响预览
额度和时效
二次确认或审批
执行结果
撤销/复审方式
完整审计
```

**适用条件：**业务允许经授权突破普通政策。  
**边界：**核心不变量、法律和安全底线通常不能通过普通覆盖放宽。  
**反例：**管理员直接改数据库状态，没有理由、影响和审计。  
**已有机制：**Explicit Override/Approval 负责授权治理；UI 提供受控入口和责任确认。

### 5.11 异步与最终一致规则：从后台机制映射为可观察状态

异步 UI 至少需要区分：

```text
未提交
已接受
处理中
等待外部结果
部分完成
成功
明确失败
结果未知
正在补偿
需要人工处理
```

“请求已接收”不等于“业务完成”。重复提交按钮应与业务幂等键和任务查询配合，而不是仅做几秒防抖。

**适用条件：**消息、回调、批任务、外部支付、跨服务流程。  
**边界：**快速同步原子操作不必暴露内部阶段。  
**反例：**支付超时显示失败并开放再次支付，但首笔其实已经成功。  
**已有机制：**任务状态、Outbox、Saga、对账和幂等负责收敛；UI 表达阶段、未知和恢复。

### 5.12 冲突规则：从规则交集映射为裁决状态

多条规则同时适用时，UI 必须区分：

- 已批准的优先、择优或有序组合：展示最终决策和必要解释。
- 配置期非法组合：禁止发布并定位冲突。
- 运行期未知组合：阻断、挂起或转人工。
- 多候选由用户选择：展示合法候选及差异。
- 不同业务模式：先选择模式，不在同一页面混合规则。

**适用条件：**规则作用域重叠且结果、状态或副作用可能不兼容。  
**边界：**适用域互斥或语义等价时，不需要制造冲突 UI。  
**反例：**按规则加载顺序静默采用最后一个结果。  
**已有机制：**SOP-10、Decision Table 和关系模型负责裁决；UI 表达裁决结果和未知状态。
## 6. 交互时机：规则应在什么时候出现

同一规则在不同阶段承担不同责任：

| 阶段 | UI 责任 | 示例 |
|---|---|---|
| 进入任务前 | 暴露资格、前置条件和重要后果 | “只有已支付订单可退款” |
| 输入前 | 提供单位、范围、默认值来源 | 最大可退 80 元 |
| 输入中 | 即时格式、范围和依赖反馈 | 金额超过可用额度 |
| 提交前 | 汇总不可逆后果、冲突和确认 | 将释放库存并撤销权益 |
| 提交时 | 防重复、提交快照、显示接受状态 | 已提交，任务号 T-001 |
| 处理后 | 展示权威结果而非只显示 HTTP 成功 | 退款已完成 50 元 |
| 异步期间 | 显示阶段、等待对象、刷新和退出语义 | 等待支付机构确认 |
| 失败后 | 解释失败类型和恢复动作 | 刷新额度后重新申请 |
| 逆向时 | 使用原决策快照解释撤销和退款 | 按原分摊比例退回 |
| 审计时 | 展示事实、版本、裁决和覆盖历史 | 规则 v7，审批人 A |

### 6.1 过早表达与过晚表达

- 过早：在用户尚未形成任务上下文时展示大量规则，增加认知负担。
- 过晚：提交后才告知本可提前发现的资格或冲突，增加返工。
- 正确时机：在用户需要作出下一步决定之前，提供足够而非全部信息。

### 6.2 即时预检不等于最终裁决

前端预检适合格式、局部依赖和低成本预估；涉及并发资源、服务端事实、权限、动态政策或高风险结果时，必须由服务端重新裁决。UI 应能处理“预检通过但提交被拒绝”的正常竞争情况。

## 7. UI 状态代数：不要只设计成功页面

### 7.1 基础状态维度

一个业务 UI 状态通常是多个正交维度的组合：

```text
UIState =
  DataState       × 数据是否加载、为空、过期或冲突
  BusinessState   × 业务对象生命周期
  PermissionState × 可见、只读、可执行、可审批
  DecisionState   × 未评估、评估中、已裁决、未知
  OperationState  × 空闲、提交中、已接受、处理中、完成、失败
  Connectivity    × 在线、离线、重连、服务降级
  VersionState    × 当前、历史、草稿、待生效、已退役
```

不能穷举所有笛卡尔积，但必须找出会改变用户行动或业务结果的组合。

### 7.2 最小业务状态集

每个高影响任务至少检查：

```text
初始 / 空数据 / 加载中 / 可操作 / 只读
资格不足 / 权限不足 / 规则冲突 / 数据已变化
提交中 / 已接受 / 处理中 / 部分完成
成功 / 明确失败 / 结果未知 / 需人工
已过期 / 历史版本 / 对象已终止
```

### 7.3 状态合并规则

当多个规则共同影响 UI 时，不能用简单“最严格状态胜出”作为通用规律。应按语义合并：

1. 安全、权限和核心不变量先作为硬门槛。
2. 业务模式先于模式内政策选择。
3. 状态转换合法性限制动作集合。
4. 资格和资源状态继续收缩动作集合。
5. 例外机制只能在被明确授权的范围内重新开放动作。
6. 展示与解释义务不因动作被禁止而自动消失。

“最严格胜出”只适用于多个独立约束共同限制同一动作，不能用于决定业务结果或抹除合法例外。

## 8. 可见、禁用、只读、阻断和警告的理论区别

| 表现 | 语义 | 适用条件 | 不适用信号 |
|---|---|---|---|
| 隐藏 | 当前角色不应发现或当前任务完全无关 | 安全、无关能力、渐进披露 | 用户需要理解缺失原因 |
| 禁用 | 能力存在但当前暂不可执行 | 状态、资格、依赖未满足 | 没有说明恢复条件 |
| 只读 | 事实需要查看但无修改权 | 权威事实、历史快照、权限限制 | 实际存在合法修改命令 |
| 内联校验 | 输入局部不合法或不完整 | 格式、范围、字段依赖 | 需要服务端动态裁决 |
| 警告 | 风险存在但有权用户可以继续 | 可逆或已授权风险接受 | 核心不变量被破坏 |
| 确认 | 用户需要确认重要后果 | 高影响、不可逆、低频操作 | 高频低风险动作造成疲劳 |
| 阻断 | 当前操作没有合法结果 | 不变量、权限、非法组合 | 实际存在批准的例外路径 |
| 转审批 | 当前主体无最终决定权 | 阈值、职责分离、例外 | 只是技术故障 |
| 转人工 | 系统无法安全自动裁决或恢复 | 未定义冲突、外部不确定 | 普通可自动重试故障 |

设计者应先写语义，再选择表现。不能因为组件库有 `disabled` 就把所有不可执行情况都做成灰色按钮。

## 9. 规则组合到页面契约

### 9.1 页面不是规则容器，而是任务工作面

页面聚合规则的依据是一个角色在一个连贯任务中需要的事实、命令和反馈，不是把同一实体的所有规则放到同一页。

### 9.2 合并算法

对 `Actor × Task × BusinessState`：

```text
1. 收集所有适用规则。
2. 过滤作用域和有效版本。
3. 计算规则关系：互斥、优先、依赖、组合、禁止。
4. 确定事实输入、系统裁决和人工决策权。
5. 求出合法命令集合。
6. 推导字段策略和信息义务。
7. 推导失败、未知和恢复状态。
8. 生成唯一交互契约。
9. 再映射到具体页面和组件。
```

### 9.3 字段策略不是静态 Schema

同一字段在不同命令中可能具有不同策略：

```text
FieldPolicy(field, actor, command, state, version)
  → hidden / visible / editable / required / readonly / derived
```

例如 `approvalComment`：

- 创建申请时隐藏。
- 审批通过时可选。
- 审批拒绝时必填。
- 完成后只读。

这不是数据库字段是否可空的问题，而是命令契约。

## 10. UI、API 与领域层的权威边界

### 10.1 三层职责

```text
UI：低延迟反馈、任务引导、信息组织、失败恢复和解释。
API/Application：身份、命令、版本、幂等、流程和决策协调。
Domain/Data：规则、不变量、状态转换、权威事实和并发保护。
```

### 10.2 可在前端复制的规则

可以复制用于体验优化，但服务端仍权威：

- 格式和长度。
- 本地字段依赖。
- 明确且稳定的简单范围。
- 无敏感信息的即时预估。

前后端必须共享测试样例、原因码或可生成契约，避免长期漂移。

### 10.3 不应只在前端执行的规则

- 权限、租户和数据范围。
- 金额、库存、积分和额度不变量。
- 并发资源和唯一性。
- 动态政策和规则版本。
- 最终状态转换。
- 不可逆副作用。
- 涉及敏感风控的判断。

### 10.4 服务端返回业务能力，不返回组件布局

推荐返回 UI 无关的业务语义：

```json
{
  "businessState": "PENDING_REVIEW",
  "allowedCommands": ["WITHDRAW"],
  "fieldPolicies": {
    "refundAmount": {
      "editable": true,
      "required": true,
      "max": 80.00,
      "unit": "CNY"
    }
  },
  "decision": {
    "status": "INELIGIBLE",
    "reasonCode": "REFUND_EXCEEDS_AVAILABLE_AMOUNT",
    "reasonParams": {"availableAmount": 80.00}
  },
  "policyVersion": "refund-policy-v7",
  "evaluatedAt": "2026-07-31T10:00:00+08:00"
}
```

不推荐返回：

```json
{
  "showRedButton": true,
  "putFieldInSecondTab": true
}
```

例外：低代码或服务端驱动 UI 平台可以返回组件 Schema，但仍应把业务语义和表现配置分层，避免规则与某个组件库永久绑定。

### 10.5 原因码是交互契约的一部分

错误文本不应成为唯一契约。推荐：

```text
reasonCode + parameters + severity + recoverability + suggestedCommands
```

前端负责本地化和合适呈现，服务端负责稳定语义。原因码版本变化也需要兼容治理。

## 11. 决策解释模型

### 11.1 三层解释

```text
结果解释：系统决定了什么。
依据解释：哪些事实和政策导致该结果。
过程解释：候选、排除、优先级和中间值如何形成。
```

不同角色看到不同层次：

- 普通用户通常需要结果和可行动原因。
- 业务人员需要政策和资格依据。
- 客服需要可复述的排除原因和恢复路径。
- 审计人员需要规则版本、决策快照和人工覆盖。

### 11.2 解释不等于暴露内部代码

应使用规范业务词汇，不显示类名、SQL、堆栈和内部风控细节。敏感规则可以提供最低必要解释和申诉路径。

### 11.3 解释的正确性

解释必须来自实际决策结果，而不是前端根据最终值猜测。否则会出现结果正确但解释错误，或者新规则上线后解释仍沿用旧逻辑。

## 12. 失败、未知与恢复设计

### 12.1 失败分类

| 类型 | UI 应回答 |
|---|---|
| 输入错误 | 哪个输入不合法，如何修正 |
| 资格失败 | 缺少什么条件，是否可恢复 |
| 业务冲突 | 哪些规则冲突，下一步由谁裁决 |
| 并发冲突 | 什么已变化，如何刷新和重新确认 |
| 权限拒绝 | 当前不能执行什么，可向谁申请 |
| 技术失败 | 是否安全重试，是否已产生结果 |
| 外部超时 | 结果未知还是明确失败，何时查询 |
| 部分成功 | 哪些已完成，哪些待处理或补偿 |
| 补偿失败 | 当前风险、人工处理和对账编号 |

### 12.2 恢复动作模型

```text
RecoveryAction
- command
- preconditions
- risk
- idempotency
- expectedState
- owner
- deadline
- escalation
```

“请重试”只有在重试安全、幂等且能改善结果时才成立。否则应提供查询、刷新、撤回、申诉或转人工。

### 12.3 乐观 UI 的边界

乐观更新适用于低风险、可快速回滚、冲突可理解的动作。支付、退款、库存最终扣减、权限变更等高影响操作，不应在权威结果形成前显示为最终成功。
## 13. 规则配置 UI：不是普通 CRUD

面向运营人员的规则配置界面，本质上是受控业务政策发布系统，应支持：

### 13.1 规则语义

- 业务名称和目的。
- 来源、Owner 和批准人。
- 作用域和适用条件。
- 决策、参数和例外。
- 与其他规则的关系。

### 13.2 组合合法性

- 互斥规则不能同时启用。
- 依赖缺失时不能发布。
- 优先级和执行顺序不能成环。
- 生效期重叠必须有明确裁决。
- 未设计组合不能因“开关都能打开”进入生产。

### 13.3 发布生命周期

```text
草稿 → 模拟 → 待评审 → 已批准 → 待生效
→ 灰度中 → 生效中 → 停止新业务使用
→ 仅服务历史对象 → 已退役
```

### 13.4 模拟与影响分析

发布前至少支持：

- 使用典型、边界和历史样本预览。
- 显示新旧结果差异。
- 识别受影响客户、对象和时间范围。
- 检查资金、库存、权限和状态不变量。
- 展示回滚目标版本和限制。

### 13.5 适用边界

少量稳定规则可以使用简单管理页和受控发布流程，不必建设规则平台。只有规则多、变化频繁、组合复杂且组织具备 Owner、测试、审批、监控和退役能力时，复杂配置 UI 才可能有净收益。

## 14. 多客户、多版本和多实现如何映射 UI

同一业务多个实现时，不能把每个实现直接变成一个 Tab 或客户专属页面。先按 SOP-10 判断差异归宿：

| 差异性质 | UI 处理 |
|---|---|
| 语义等价实现 | 保持同一交互契约，迁移不应让用户感知无意义差异 |
| 参数差异 | 同一任务界面，按政策显示参数和结果 |
| Policy 差异 | 同一业务词汇下投影不同资格、选择和解释 |
| 流程变体 | 在公共骨架中显示合法可选步骤或模式专属流程 |
| 独立业务模式 | 先明确选择模式，再进入模式内任务，避免超级页面 |
| 外部系统差异 | 通过 Adapter 隔离，UI 只在影响任务时表达差异 |
| 历史兼容 | 旧对象保持原交互语义或明确只读/逆向处理入口 |
| 待退役实现 | 不再接受新对象，但保留历史查看、退款、撤销和审计 |

### 14.1 不按客户 ID 设计 UI

客户身份只能选择 Agreement、BusinessMode 或 Policy，不能成为界面里的隐式分支来源：

```text
错误：if customerId == A then show field X
正确：客户 A 绑定“账期销售模式”，该模式要求展示账期和授信额度
```

### 14.2 目标 UI 不应成为历史功能并集

合并多个实现时，应提取稳定任务、事实、不变量和真实变化点。把所有旧字段、按钮和状态放进一个页面，会把历史偶然复杂度永久化。

## 15. 端到端示例：合同价、会员价与优惠组合

### 15.1 业务模型

```text
Fact：顾客、商品、数量、门店、时间、合同、会员和优惠权益。
Invariant：客户应付金额不得小于零；资金分摊必须守恒。
Policy：合同价优先于会员价。
Rule R1：有效合同命中时产生合同价候选。
Rule R2：会员有效且商品参与时产生会员价候选。
Rule R3：合同价不能与商家优惠叠加。
Rule R4：平台补贴可以与合同价叠加。
Rule R5：多个合法基础价候选按已批准政策择优或优先。
Decision：最终基础价、采用权益、排除权益和资金分摊。
```

### 15.2 角色与任务

| 角色 | 任务 | 决策权 |
|---|---|---|
| 顾客 | 理解并确认本次结算 | 可选择合法优惠，但不能改政策 |
| 收银员 | 快速完成结算并处理普通异常 | 可按授权选择优惠，不可绕过不变量 |
| 运营人员 | 配置和发布组合政策 | 可提出政策，发布需审批 |
| 客服 | 解释历史订单价格 | 只读原决策快照 |
| 审计人员 | 复核政策、覆盖和资金分摊 | 只读完整证据和版本 |

### 15.3 顾客结算交互契约

```text
Actor：顾客
Task：确认价格并提交订单
RequiredFacts：会员身份、合同、商品、有效权益
AllowedCommands：选择合法优惠、移除优惠、提交订单
DecisionAuthority：基础价和组合合法性由系统裁决
VisibleInformation：原价、最终价、已采用和未采用权益
Feedback：每次选择后返回新的服务端预估
Recovery：权益不可用时可查看原因、更换优惠或继续结算
Authority：提交时服务端重新裁决并冻结决策快照
```

页面不是简单显示“应付 75 元”，而应按需解释：

```text
商品原价                  100 元
合同价格                   80 元
平台补贴                   -5 元
最终应付                   75 元

已采用
- 客户合同价格
- 平台补贴

未采用
- 会员价：合同政策优先
- 商家满减：不能与合同价格叠加
```

### 15.4 规则到交互映射

| 规则 | 交互义务 | UI 表达 | 服务端守卫 |
|---|---|---|---|
| R1 合同价资格 | Inform/Explain | 标识合同价和有效期 | 验证合同、商品和时间 |
| R2 会员价资格 | Inform | 显示会员候选或缺失资格 | 验证会员和商品范围 |
| R3 禁止叠加 | Constrain/Explain | 满减不可选并说明原因 | 冲突矩阵拒绝组合 |
| R4 允许补贴 | Guide | 平台补贴作为合法候选 | 验证资金方和额度 |
| R5 候选裁决 | Explain | 显示采用与排除结果 | 决策表/Policy 裁决 |
| 应付非负 | Constrain | 不允许形成负应付 | 不变量守卫 |
| 分摊守恒 | Audit | 普通用户不展示内部全量；审计可查看 | 分摊校验和快照 |

### 15.5 运营配置界面

运营人员不能直接编辑“规则执行顺序数字”而不知道含义。界面应表达：

- 合同价与会员价：优先、择优还是互斥。
- 合同价与商家优惠：禁止组合。
- 合同价与平台补贴：允许组合及分摊责任。
- 适用客户、门店、商品和时间。
- 历史订单是否继续绑定旧版本。
- 新旧政策样本差异。
- 发布审批、灰度和回滚。

若配置形成循环优先级或未定义资金责任，应在发布期阻断，而不是等顾客结算时按代码顺序处理。

### 15.6 并发和失效

用户停留在结算页期间，优惠可能过期或额度耗尽。因此：

1. 页面预估标明计算时间和政策版本。
2. 提交时服务端重新裁决。
3. 结果变化时不静默提交高影响差异。
4. 返回变化原因和新的合法选择。
5. 顾客重新确认后再形成订单决策快照。

### 15.7 历史解释

订单详情和退款必须读取原决策快照：

- 原规则版本。
- 当时命中的资格。
- 被排除权益及原因。
- 最终价格和资金分摊。
- 退款时的逆向计划。

不能使用当前政策重新计算后声称“历史订单当时就应该如此”。

## 16. 第二个示例：超过阈值的退款审批

### 16.1 规则

```text
R1：累计退款不得超过有效支付。
R2：退款金额不超过 500 元可自动批准。
R3：超过 500 元需要门店经理审批。
R4：发起人与审批人职责分离。
R5：支付机构结果未知时不得再次发起同一退款。
```

### 16.2 页面投影

发起人页面：

- 展示已付、已退和最大可退。
- 输入退款金额和原因。
- 金额超过 500 元时，提交动作从“立即退款”变为“提交审批”。
- 明确告知预计流程和所需材料。
- 发起人不能批准自己的申请。

审批人页面：

- 展示原支付、历史退款、申请理由和风险提示。
- 显示规则为什么要求审批。
- 提供批准、拒绝和退回补充材料三个业务命令。
- 拒绝时理由必填，批准后进入支付机构处理而非立即显示退款完成。

异步结果页面：

- 已批准。
- 正在请求支付机构。
- 支付机构已受理。
- 结果未知，正在查询。
- 已完成或明确失败。
- 转人工对账。

该例说明一条阈值规则不仅影响字段校验，还改变命令语义、流程、责任和完成状态。
## 17. AI 执行协议

### 17.1 阶段 R0：冻结范围

记录业务能力、角色、任务、版本、环境、设备、范围内外、风险和决策负责人。没有范围时只能做探索草案。

### 17.2 阶段 R1：规范化业务语义

使用第 12 篇方法论分离：

```text
Fact / Invariant / Policy / Rule / Parameter
Decision / Process / State / ExecutionPlan / Snapshot
```

每条关键规则登记来源、Owner、作用域、版本和证据。

### 17.3 阶段 R2：建立角色—任务—状态矩阵

| 角色 | 任务 | 进入状态 | 目标状态 | 决策权 | 风险 | 失败责任 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

### 17.4 阶段 R3：逐条推导交互义务

对每条规则回答：

```text
谁必须知道？
谁必须提供事实？
谁能选择、批准或覆盖？
规则收缩或扩展了哪些动作？
何时表达最有行动价值？
失败、冲突或未知时如何恢复？
是否需要解释、版本和审计？
```

输出 `Acquire/Inform/Constrain/Guide/Decide/Confirm/Explain/Recover/Audit`。

### 17.5 阶段 R4：合成交互契约

以 `Actor × Task × BusinessState` 为键，合并适用规则，解析关系，生成字段策略、允许命令、决策投影、反馈和恢复。

若规则冲突未被业务裁决，状态标记为 `UNDEFINED`，不得自行选择表现最简单的结果。

### 17.6 阶段 R5：生成 UI 状态和信息架构

先定义任务流、状态和内容优先级，再选择页面和控件。至少覆盖正常、空、加载、资格不足、权限不足、冲突、并发变化、处理中、部分完成、失败、未知和历史状态。

### 17.7 阶段 R6：定义 API 与权威边界

明确：

- 前端可做的即时预检。
- 服务端权威裁决。
- `allowedCommands`、`fieldPolicies` 和原因码。
- 规则版本、评估时间和数据新鲜度。
- 幂等、并发版本和重复提交。
- 决策快照与审计。

### 17.8 阶段 R7：建立双向追踪

```text
BR-* 业务规则
→ IO-* 交互义务
→ IC-* 交互契约
→ UI-* 页面/状态/组件
→ API-* 命令/查询/原因码
→ GUARD-* 服务端守卫
→ TEST-* 场景测试
```

任一关键 UI 约束都应能反查业务依据；任一用户可感知规则都应能正向追到 UI 或明确说明无需呈现。

### 17.9 阶段 R8：验证和评审

执行场景、状态、权限、版本、组合、失败、恢复和可用性验证。高影响设计进入 SOP-09，UI 视觉和交互质量进入第 06 篇规范评审。

## 19. 验证方法

### 19.1 场景测试

每条高影响规则至少覆盖：

- 正常命中和不命中。
- 边界值。
- 多规则重叠。
- 权限和数据范围。
- 状态转换前后。
- 规则生效期首尾。
- 历史版本。
- 重复、并发和数据变化。
- 外部超时和结果未知。
- 撤销、退款、冲正和人工覆盖。

### 19.2 契约测试

验证前后端对以下语义理解一致：

- 状态和允许命令。
- 字段策略。
- 原因码及参数。
- 幂等键和并发版本。
- 规则版本和评估时间。
- 部分成功、失败和未知状态。

### 19.3 性质测试

```text
任意 UI 路径都不能绕过核心不变量。
任意未授权主体都不能通过直接 API 获得动作权限。
相同事实、上下文和版本产生一致决策与解释。
规则版本变化不会改变已冻结历史对象的解释。
重复提交不会产生多个不可逆业务结果。
从任一可恢复失败状态至少存在一条声明的合法恢复路径。
```

### 19.4 可用性测试

业务正确不等于用户能够正确完成任务。验证：

- 用户能否发现当前可用动作。
- 是否理解为什么被拒绝。
- 是否能区分预估、已接受和最终完成。
- 是否知道下一步和责任人。
- 高风险后果是否在行动前被理解。
- 解释是否使用业务语言而非技术语言。

### 19.5 规则变更影响测试

规则变化后自动检查：

```text
规则 → 交互义务 → 页面状态 → API 原因码
→ 服务端守卫 → 测试 → 帮助/审计说明
```

避免只改后端规则而留下旧 UI 提示、旧默认值和错误恢复路径。

## 20. 常见反模式

- 业务规则直接等同于字段必填或按钮禁用。
- 按数据库表生成页面后再塞入业务规则。
- 前端复制完整规则体系，与服务端长期漂移。
- 把隐藏按钮当作权限控制。
- 把状态机做成任意状态下拉框。
- 只显示最终值，不显示高影响决策的依据。
- 只设计成功态，没有结果未知、部分完成和人工恢复。
- 所有失败都显示“操作失败，请重试”。
- 请求被接收就显示业务完成。
- 用当前规则解释历史订单和历史审批。
- 为每个客户复制一套页面，客户 ID 成为隐式业务模式。
- 合并历史实现时把所有字段、按钮和状态求并集。
- 规则配置可以任意开关组合，没有发布期冲突校验。
- 把服务端组件 Schema 和业务规则绑定为不可迁移结构。
- 为低风险简单规则展示完整决策树，造成认知负担。
- 为追求界面简洁隐藏费用、限制、不可逆后果或申诉路径。

## 21. 适用范围与停止条件

### 21.1 适用

- 复杂表单和动态字段策略。
- 价格、优惠、权益、资金、库存和额度。
- 审批、状态机、异步流程和人工介入。
- 多客户、多版本和多实现系统。
- 规则平台、运营配置和历史解释。
- 从领域设计正向生成 UI 契约。
- 对账既有 UI 与真实业务规则。

### 21.2 不适用或应简化

- 纯展示、低风险、无状态的静态内容。
- 不改变用户任务和可观察结果的内部技术优化。
- 少量稳定规则，不需要动态元数据平台。
- 尚未明确业务事实和决策权的早期探索；此时只能生成候选。

### 21.3 完成判据

- [ ] 规则没有直接跳到控件，已形成交互义务和交互契约。
- [ ] 事实输入、用户选择、系统裁决和审批权已分离。
- [ ] 每个关键角色的任务、状态、允许命令和责任明确。
- [ ] 不变量具有 UI 预防和服务端权威双层保护。
- [ ] 隐藏、禁用、只读、警告、阻断和审批均有业务理由。
- [ ] 正常、失败、未知、部分完成、历史和恢复状态已覆盖。
- [ ] 异步请求没有把“已接受”误写成“已完成”。
- [ ] 规则版本、决策快照和历史解释一致。
- [ ] 多规则冲突和多实现差异已有明确归宿。
- [ ] UI—API—领域守卫—测试可以双向追溯。
- [ ] 高影响设计通过 SOP-09，交互质量通过第 06 篇规范。
