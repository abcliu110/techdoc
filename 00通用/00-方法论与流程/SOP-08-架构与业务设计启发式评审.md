## TL;DR

**一句话**：通过启发式评审发现架构和业务设计的候选改进方向，为重构和变更提供思考素材。

**核心输入**：系统地图、代码结构、业务切片分析结果

**核心输出**：候选改进方向清单、架构反模式识别、启发式问题列表

**关键约束**：只启发不决策；具体业务合理性必须执行 SOP-09

## 目的

对现有架构和业务设计进行启发式评审，通过模式、反例和多视角挑战现状，发现候选改进方向。本文只负责**启发思考、打开方案空间**，不负责证明某种模式“更好”，也不直接形成业务合理性定论。

凡涉及业务设计选择、改造或批准，必须把本 SOP 产生的启发点作为候选方案，交由 `SOP-09-业务设计合理性评审.md` 校验红线门槛、适用条件、新增代价、反例边界、迁移、验证和退出策略。

## 适用范围

- 架构方案评审（分层、模块、依赖）
- 业务设计评审（流程、规则、状态）
- 技术选型评估
- 重构可行性分析
- 新模块设计前的现状参考

## 评审策略

**核心原则：现状是事实，启发是参考，决策靠场景**

```
现状 ≠ 错误
更好 ≠ 必须改

启发式评审的价值：
├── 发现"这个问题有更好的解法"的可能性
├── 了解业界实践，但不照搬
├── 评估"改 vs 不改"的成本收益
└── 为重构提供方向，不做具体方案
```

## 1. 分层架构评审

### 1.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 依赖方向 | 依赖是否单向？低层是否反向依赖高层？ | Controller 直接调用 DAO |
| 分层粒度 | 每层职责是否清晰？有没有"全能层"？ | Service 干了 Controller 的事 |
| 跨层调用 | 有没有绕过中间层的直接调用？ | Utils 直接读写数据库 |
| 循环依赖 | 模块之间是否有循环依赖？ | A → B → C → A |

### 1.2 现状 vs 更好的设计

```
【现状红旗】

表现层直接处理协议细节：
业务组件的方法签名包含协议对象（如 HTTP 请求对象）
直接从中提取参数并处理

问题：
- 业务逻辑和协议细节耦合
- 无法独立测试业务逻辑
- 更换协议入口需要修改业务代码

【更好的设计】

分离协议适配层和业务层：
业务组件只接收结构化的业务对象（如命令对象、查询对象）
协议适配层负责从具体协议（HTTP、RPC、消息等）转换到业务对象

好处：
- 业务逻辑可独立测试
- 协议变更不影响业务
- 同一业务逻辑可复用多个协议入口
```

### 1.3 分层模式对比

| 现状模式 | 启发模式 | 适用场景 |
|---------|---------|---------|
| 三层架构（表现层/业务层/数据层） | 洋葱架构 / 六边形架构 | 业务复杂、需高度可测试 |
| 过程式（逻辑集中在服务） | 领域对象式（领域承担业务） | 业务规则复杂、状态流转多 |
| 大服务小领域 | 小服务大领域 | 领域驱动设计 |
| 大聚合包裹所有实体 | 独立的值对象和实体 | 避免过度设计 |

> **说明**：上表中"贫血模型"、"充血模型"、"聚合根"、"值对象"是领域驱动设计中的特定术语，本质上描述的是"业务逻辑的放置位置"和"对象的职责范围"两种设计选择。

## 2. 业务边界评审

### 2.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 职责边界 | 模块/服务的职责是否单一？ | 一个模块处理多种不相关的业务能力 |
| 命名语义 | 模块名是否反映真实职责？ | 模块名与实际处理的业务不符 |
| 依赖关系 | 模块间的依赖是否清晰合理？ | 模块 A 强依赖模块 B 的内部实现 |
| 内聚度 | 相关功能是否聚在一起？ | 同一业务能力分散在多个模块 |
| 耦合度 | 模块之间是否松耦合？ | 修改 A 模块导致 B 模块报错 |

### 2.2 现状 vs 更好的设计

```
【现状红旗】

单一模块承担过多职责：
一个业务模块内包含多个不同业务能力的服务类
这些服务类处理完全不相关的业务功能

问题：
- 模块职责不单一
- 改任何一个功能都可能影响其他
- 难以独立演进
- 难以分配团队所有权

【更好的设计】

按业务能力边界拆分：
每个模块只包含单一业务能力的相关代码
按业务能力划分独立的包或模块
相关能力放在一起，无关能力分离出去

好处：
- 职责单一，变更影响可评估
- 可独立部署和扩展
- 团队所有权清晰
```

### 2.3 边界模式对比

| 现状模式 | 启发模式 | 适用场景 |
|---------|---------|---------|
| 按技术分层（Controller/Service/DAO） | 按业务能力边界（订单域/用户域/支付域） | 微服务化或业务复杂 |
| 大一统模块 | 多个小而专注的模块 | 多人协作大型系统 |
| 共享数据库 | 每个域独立数据库 | 微服务或需要独立演进 |
| 服务间同步调用 | 事件驱动解耦 | 高并发或需解耦 |

## 3. 扩展性模式评审

### 3.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 新功能位置 | 加新功能要改多少处？ | 要改 5 个类的同一段逻辑 |
| 条件分支 | 是否有大量 if/switch 硬编码？ | 一段代码有 20 个 if 判断类型 |
| 扩展点 | 有没有预留的扩展机制？ | 所有逻辑写死，无法扩展 |
| 配置驱动 | 变化点是否外置到配置？ | 改规则要改代码并重新部署 |

### 3.2 现状 vs 更好的设计

```
【现状红旗】

计算逻辑写死，使用大量条件分支：
业务方法内包含一长串 if/switch 判断
每种业务类型对应一段独立的处理逻辑
新增类型需要修改这段代码

问题：
- 每加一种类型要改代码
- 逻辑分散在不同分支
- 测试覆盖困难
- 类型组合时代码膨胀

【更好的设计】

使用可扩展的计算架构：
定义统一的计算策略接口
每种类型对应一个独立的策略实现
策略注册与查找由框架或工厂管理
新增类型只需新增策略实现，不修改既有代码

好处：
- 新增类型不修改现有代码
- 每个策略独立测试
- 策略可运行时替换
```

### 3.3 扩展性模式对比

| 现状模式 | 启发模式 | 适用场景 |
|---------|---------|---------|
| if/switch 硬编码 | 策略模式 / 规则引擎 | 类型多、变化频繁 |
| 代码配置 | 配置中心 / 数据库配置 | 需要运行时变更 |
| 单体逻辑 | 插件机制 / 扩展点 | 需要第三方扩展 |
| 继承层次结构 | 组合优于继承 | 需要灵活组合行为 |

## 4. 状态机评审

### 4.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 状态定义 | 状态是否枚举完整？有无遗漏状态？ | 文档写了 5 种状态，代码有 7 种 |
| 流转规则 | 哪些状态可以互相转换？规则明确吗？ | 任何状态都可以直接变更为任何状态 |
| 死状态 | 有没有永远无法达到的状态？ | 终态之后不会再有流转 |
| 并发安全 | 并发修改状态会出问题吗？ | 无锁的情况下直接更新状态 |
| 异常恢复 | 失败后状态如何回滚？ | 前置步骤已完成但后续步骤失败 |

### 4.2 现状 vs 更好的设计

```
【现状红旗】

状态值用裸数值管理：
业务方法接收原始数值作为状态参数
直接更新数据库，无校验

问题：
- 数值含义不明确（1 是待处理还是已完成？）
- 无流转规则校验
- 可以从终态变回初始状态

【更好的设计】

使用枚举定义状态及其流转规则：
枚举值代表具体状态
每个枚举值关联其可流转到的目标状态集合
状态转换方法校验合法性后再执行更新
非法转换抛出异常

好处：
- 状态含义明确
- 流转规则自动校验
- 无法到达非法状态
```

### 4.3 状态机模式对比

| 现状模式 | 启发模式 | 适用场景 |
|---------|---------|---------|
| 裸数值/字符串存状态 | 枚举 + 状态流转规则 | 状态有限、流转规则重要 |
| 代码校验状态 | 状态机框架（通用状态机库） | 状态多、流转复杂 |
| 无补偿机制 | 补偿事务模式 | 分布式事务 |
| 无历史记录 | 事件溯源 | 需要审计、回放 |

## 5. 数据一致性评审

### 5.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 事务边界 | 事务范围是否合理？太大还是太小？ | 一个事务操作 10 张表 |
| 分布式一致 | 跨库/跨服务操作如何保证一致？ | 无任何补偿机制 |
| 幂等性 | 重试是否安全？ | 写操作无幂等控制，重复调用会重复执行 |
| 乐观/悲观锁 | 并发场景如何处理？ | 高并发下无锁导致数据覆盖 |

### 5.2 现状 vs 更好的设计

```
【现状红旗】

同步调用多个下游操作：
一个业务方法内顺序调用多个服务或数据操作
如果某个步骤失败，前面已完成的步骤无法回滚

问题：
- 如果中间步骤失败，前面已提交的步骤无法自动回滚
- 如果后面的步骤失败，前面已完成的操作需要手动补偿
- 整体成功或失败没有明确定义

【更好的设计】

使用补偿事务或事件驱动架构：
将每个步骤封装为可独立执行、可补偿的操作
记录每步执行结果，支持失败后的逆向补偿
或者使用事件驱动：操作完成后发布事件，由订阅方异步处理后续步骤

补偿机制：定时任务扫描未完成的步骤并重试或补偿

好处：
- 最终一致性，而非强一致性
- 可重试、可补偿
- 系统更健壮
```

### 5.3 一致性模式对比

| 现状模式 | 启发模式 | 适用场景 |
|---------|---------|---------|
| 本地事务 | 分布式事务框架 | 跨库操作必须强一致 |
| 同步调用 | 消息队列 + 最终一致 | 对可用性要求高 |
| 无幂等 | 唯一键 / 去重表 / 幂等 token | 重试场景 |
| 悲观锁 | 乐观锁 + 重试 | 读多写少 |
| 无补偿 | 补偿事务模式 | 长事务 |

## 6. 可测试性评审

### 6.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 依赖注入 | 依赖是否通过构造函数注入？ | 组件内直接 new 依赖实例 |
| 单例滥用 | 是否有大量静态单例？ | 使用全局单例获取依赖 |
| 外部依赖 | 是否依赖真实的数据库/外部服务？ | 测试要连真实数据库 |
| 私有方法测试 | 是否为了测试私有方法而反射？ | 说明设计可能有问题 |

### 6.2 现状 vs 更好的设计

```
【现状红旗】

使用静态方式获取依赖：
业务组件内直接通过静态方法获取依赖实例
或者在类加载时就创建依赖实例

问题：
- 测试时无法替换为测试替身
- 必须有真实的依赖实例才能运行
- 测试依赖完整的部署环境
- 组件状态难以控制

【更好的设计】

使用依赖注入机制：
通过构造函数或参数传入依赖实例
组件本身不负责依赖的创建和获取
测试时可以注入测试替身（Mock）

好处：
- 组件可独立测试
- 依赖关系显式声明
- 便于替换和扩展
```

## 7. 性能与可扩展性评审

### 7.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| N+1 查询 | 循环内是否有数据库查询？ | for 循环里 selectById |
| 大表操作 | 是否有全表扫描或大结果集？ | 一次查 10 万条数据到内存 |
| 同步阻塞 | 是否有过长的同步等待？ | 串行调用多个外部服务 |
| 缓存策略 | 热点数据是否缓存？ | 每次都查数据库 |

### 7.2 现状 vs 更好的设计

```
【现状红旗】

循环内执行单次查询（N+1 问题）：
先查询主列表
然后在循环中为每个元素执行额外查询获取关联数据
列表越大，查询次数越多

问题：
- 性能随数据量线性下降
- 数据库连接压力随规模增长
- 难以优化或缓存

【更好的设计】

使用联表查询或批量查询：
方案一：单次联表查询，一次性获取所有需要的数据
方案二：先查主列表，再批量查询关联数据（2 次查询）
将结果在内存中组装

好处：
- 查询次数固定，不随数据量增长
- 数据库压力可控
- 性能可预测
```

## 8. 概念角色与语义正交性评审

### 8.1 评审问题清单

| 问题 | 评审重点 | 发现红旗 |
|------|---------|---------|
| 正交维度混淆 | 源码中的枚举/类名是否将两个不同维度的概念混在一起？ | 将"用途"和"样式"混用一个枚举 |
| 同名不同义 | 不同模块中相同名称的概念是否表达不同的业务含义？ | 两个 `Type` 字段含义完全不同 |
| 同义不同名 | 不同名称的概念是否实际表达相同的业务含义？ | 文档叫"标签联"，代码叫 `FoodLabel` |
| 隐式概念 | 是否存在读者需要自行推断才能理解的概念？ | 枚举值无注释，读者无法理解含义 |

### 8.2 概念维度正交性检查

**目的**：识别业务设计中相互独立的不同维度，防止混淆。

**正交维度示例**：

| 维度 A | 维度 B | 常见混淆 |
|--------|--------|----------|
| 用途（给谁用） | 样式（呈现形式） | 将用途枚举误当成样式枚举 |
| 状态 | 类型 | 将状态枚举值当成类型枚举值 |
| 主键 | 外键 | 将系统生成的主键字段当成业务分类字段 |
| 物理表 | 逻辑表 | 将分片后的物理表名当成业务表名 |

**检查步骤**：

1. 枚举所有核心枚举类/常量类
2. 列出每个枚举的所有值
3. 分析每个值属于哪个业务维度
4. 检查是否存在两个及以上正交维度被混用
5. 检查枚举名/类名是否准确反映其业务维度

### 8.3 概念角色分析卡

| 字段 | 必须回答 |
|------|----------|
| 概念 ID | `CONCEPT-xxx` |
| 概念名称 | 源码中的枚举/字段/类名 |
| 角色维度 | 这个概念解决"谁/什么/给谁/怎么用"中的哪个问题 |
| 正交关系 | 与哪些概念属于不同维度？与哪些概念可组合？ |
| 语义边界 | 什么场景下用这个概念？什么场景下不应该用？ |
| 错误模式 | 常见误用场景和后果 |
| 证据 | 源码位置、业务含义来源 |

### 8.4 概念混淆案例

```
【现状红旗】

枚举同时表示多个正交维度：
枚举类包含的取值跨越了多个独立的业务维度
例如：枚举值同时表示"用途"和"样式"，或同时表示"状态"和"类型"

问题：
- 无法表达不同维度的自由组合
- 添加新需求时必须修改既有枚举
- 枚举名无法准确描述其实际含义

【更好的设计】

正交维度分离：
定义独立的枚举类分别对应每个业务维度
维度之间通过组合而非嵌套来表达完整语义
枚举名准确反映其代表的业务维度

好处：
- 各维度独立演进
- 支持自由组合
- 语义清晰无歧义
```

## 10. 启发分级与转交规则

本 SOP 不按“是否符合业界实践”判断设计好坏，也不直接给出业务严重度。启发点只分为：

| 类型 | 含义 | 后续动作 |
|---|---|---|
| 已证实现状适配 | 当前机制与问题、约束和证据匹配 | 保留；记录适用边界和复审触发器 |
| 候选启发 | 可能带来收益，但触发条件或证据尚不足 | 进入 SOP-09 比较，不升级为缺陷 |
| 待验证风险 | 已发现失败条件或代价暴露，但尚未形成完整证据链 | 建立竞争假设和最小验证动作 |
| 已证实问题 | 已违反明确规则、不变量、契约或质量目标 | 转入 SOP-07 问题闭环，并由 SOP-09 评估替代设计 |

任何“启发模式”进入建议前必须回答：真实问题是什么、机制为什么匹配、新增什么代价、什么条件下更差、如何渐进验证、如何退出。

P0-P3 只表示经过证据确认后的业务严重度（等同 SEV-P0~P3，与 L1 的 SC-P* 切片深度分级无关），不得将“使用了非主流模式”“可维护性一般”直接判为 P0/P1。
