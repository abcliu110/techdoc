# 既有系统安全修改代码 AI 执行规范

> 本文件只承担“既有系统兼容契约”职责。工作区路由、安全底线、TDD、验证、Windows 编码和 Java/CRM 细节分别以 `D:\AGENTS.md`、`D:\agent-rules\30-verification.md`、`D:\agent-rules\40-windows-encoding.md`、`D:\agent-rules\50-domain-java-crm.md` 及项目规则为准；规则冲突时遵循更高优先级指令。

## 1. 范围与安全例外

本规范适用于维护已经存在调用方、历史数据、配置、任务或消息消费者的系统，包括老系统功能增强、历史接口维护、已上线流程修改、数据迁移和同步任务。

### 1.1 兼容契约

老逻辑是当前运行中且尚未通过明确废弃流程宣布停止的行为，包括：

- 已有线上数据依赖的业务分支；
- 公共方法和接口已有字段、状态码、错误码、枚举 code、默认值与空值语义；
- 空值、特殊枚举、历史状态和异常分支；
- 定时任务、消息消费、同步、报表、导入导出等非接口入口。

无法证实没有依赖的疑似冗余逻辑仍视为兼容契约，不能仅因“看起来没人用”而删除。

### 1.2 安全例外

已确认的越权、跨租户访问、凭据泄露、注入、任意代码或文件访问、支付或财务完整性错误，不作为必须保留的兼容契约，也不作为要求继续通过的旧行为基线。修复前仍须盘点调用方、历史数据、迁移和回滚影响；无法一次修复时先采取可逆止损，不得以兼容为由继续暴露漏洞。

安全结论必须有复现或直接证据。只有“代码风格不喜欢”“新方案更合理”或“文档没有记录”不构成安全例外。

## 2. 修改前依赖盘点

进入实现前，先完成以下最小盘点，并把未确认项写入任务记录：

1. 检查工作区状态和项目入口规则，避免覆盖人类或其他 AI 的改动。
2. 定位旧逻辑入口、调用方、返回值、异常和状态流转。
3. 盘点受影响的文件、数据库字段、索引、配置 key/默认值、定时任务、MQ/事件、导入导出和外部接口。
4. 查阅近期提交、特征化测试、接口样例、历史数据样例和项目图谱；不能用目录名称或同名表猜依赖。
5. 记录旧行为、影响边界、证据来源、未知项和回滚粒度。

未确认项的固定格式：

```text
未确认项：<依赖或历史语义>
已尝试：<搜索、测试、日志、数据或接口验证>
证据与确定性：<区分直接事实、推断、假设和未知项，并给出验证依据>
保守处理：<保留旧路径、增加隔离分支或默认关闭>
需要确认：<负责人需要作出的决定>
```

## 3. 统一变更顺序

### 3.1 既有系统

新增功能、修复 Bug、重构或改变既有行为时，顺序统一为：

```text
旧行为特征化测试 PASS
        -> 新需求或缺陷用例 RED
        -> 最小实现
        -> 新旧回归
```

旧行为本身若属于第 1.2 节安全例外，不得为了“兼容”把漏洞固化为通过基线；应先记录漏洞复现和止损验证，再建立修复后的安全基线。

全新代码没有旧行为时，从新需求用例 RED 开始。无法自动化时，先形成修复前可重复失败的手工用例，包含前置数据、输入、预期、实际、命令或接口和清理方式。

### 3.2 变更分类

- Bug 修复：保留未受影响的旧契约，明确缺陷证据、修复边界和回归路径。
- 业务变更：明确新规则、生效条件、兼容窗口和迁移策略，不能伪装成普通优化。
- 等价重写：即使声称行为不变，也必须有特征化测试或详细对照证据；不得把格式化、重命名和重构混入需求变更。

具体 TDD、验证终态和测试平台规则引用根入口及专项规则，不在本文件重复。

## 4. 兼容机制决策表

使用能解释风险的最小机制，不机械要求每次都增加抽象层：

| 证据与风险 | 首选机制 | 必须记录 |
|---|---|---|
| 单个已确认分支，调用边界稳定 | 局部条件或适配 | 旧/新分支、输入边界、回滚点 |
| 需要隔离新入口或字段映射 | 包装/适配层 | 旧入口保留时间、调用方和删除条件 |
| 需要灰度、快速关闭或分批迁移 | 功能开关 | 名称、默认值、灰度范围、下线日期、回滚方式、无调用方确认方式 |
| 多个已经存在且会继续增长的业务规则 | 策略/扩展点 | 真实规则清单、选择顺序、每个实现的兼容约束 |
| 结果可比较且无副作用的计算 | Shadow Mode | 旧结果仍是线上结果、观察周期、差异摘要和停止条件 |
| 对外接口、消息或配置契约需要并行版本 | 版本化或增量字段 | 老消费者兼容、切换窗口、回滚和支持/废弃策略；临时版本另记废弃日期 |

一个局部条件已足够时，不为了“架构完整”新增策略层。没有真实可比较计算时，不使用 Shadow Mode；有副作用的写入、扣库存、发券、发消息不得双跑。

### 4.1 功能开关生命周期

开关不是永久并行入口。关闭或回退时必须走旧路径，开关启用期间的新写入数据也必须保持旧路径可读。启用前记录默认值和灰度范围；全量后记录观测证据、期望下线日期和责任人；删除旧路径前确认无调用方、无历史数据依赖，并保留可执行回滚。无法下线时记录阻塞原因和责任人，不能默认为永久保留。

### 4.2 Shadow Mode 安全边界

Shadow 只执行无副作用、结果可比较的逻辑，线上响应和写入仍使用旧结果。差异日志只保留安全摘要，不序列化请求、响应或结果对象：

```java
if (!sameBusinessResult(legacyResult, shadowResult)) {
  log.warn(
      "shadow diff, bizKeyHash={}, fields={}, legacyDigest={}, shadowDigest={}",
      hashBizKey(request), changedFieldNames(legacyResult, shadowResult),
      safeDigest(legacyResult), safeDigest(shadowResult));
}
```

`bizKeyHash`、摘要和字段名必须经过项目认可的脱敏策略；不得记录手机号、证件、地址、邮箱、token、支付数据、业务正文或完整对象。

## 5. 契约兼容矩阵

### 5.1 API / RPC

既有接口默认保持字段名、类型、层级、分页结构、枚举 code、状态码、错误码、默认值、空值语义、排序规则和权限边界。优先新增字段或版本化接口，不删除旧字段；新增字段必须允许旧客户端忽略。无法确认调用方时按存在隐藏依赖处理。

修改前检查前端、其他服务、第三方、报表、导出、文档和测试样例；历史 HTTP 方法也是契约，不能为了统一风格直接改写。

### 5.2 消息与事件

优先新增可选字段，不复用旧字段改变含义，不修改旧枚举 code。确认旧消费者能处理新消息，或通过版本化 topic/事件类型隔离；生产者和消费者滚动发布期间必须兼容新旧格式。消费写入仍需幂等、去重和重试边界。

### 5.3 配置

配置 key、默认值、单位、含义、作用范围和优先级都是契约。新增 key 优先于改变旧 key 含义；滚动发布时记录不同实例看到的版本和回滚方式。删除或改默认值前必须搜索代码、部署、任务和运维脚本引用，不能假设所有实例同时加载新配置。

### 5.4 数据库与迁移

采用 expand/backfill/contract 顺序：

1. 先增加兼容结构，不删除旧字段或索引。
2. 部署同时兼容新旧字段和新旧写入者。
3. 用真实业务值幂等回填历史数据，记录批次、范围、重跑和失败处理。
4. 验证完整性、查询性能、报表、导出、同步和第三方读取。
5. 确认无依赖后再收紧约束或删除旧结构，并保留回滚窗口。

新增字段优先允许 `NULL`。只有默认值确实是历史和未来写入都成立的领域值时才允许使用默认值；禁止用虚假占位值掩盖未知数据。需要 `NOT NULL` 时，先完成 nullable 扩展、兼容写入、真实值回填和完整性验证，最后再收紧约束。

枚举只新增 code，不改变旧 code 含义；多租户数据的 UPDATE/DELETE 必须携带项目实际定义的租户键和足以限定目标记录的业务条件，禁止用物理主键冒充租户隔离。数据库迁移必须说明顺序、锁影响、回滚或前向修复路径。

### 5.5 定时任务与同步

定时任务和同步链路的筛选区间、游标或水位、频率、并发、幂等键、重试、补偿和重跑语义都是兼容契约。修改前必须确认是否会重扫历史数据、重复写入、覆盖新值或再次触发下游副作用；滚动发布和回滚期间必须明确新旧实例如何共享进度，以及旧版本能否识别新版本写入的数据和状态。

## 6. 回滚与交付

每次变更前明确：

- 回滚粒度：关闭开关、恢复配置、恢复文件/版本、反向迁移还是前向修复；
- 新写入数据能否被旧逻辑读取，任务或消息重跑是否幂等；
- 数据库、接口、消息和配置是否存在兼容窗口；
- 回滚顺序是否遵循服务依赖，哪些动作需要人工确认。

最终交付至少说明：

```text
变更目标：
保留的老逻辑：
新增的逻辑：
新逻辑启用条件：
兼容措施：
测试或验证：
回滚方案：
未覆盖风险：
需要人类确认的未决项：
```

验证结果必须引用实际命令、退出码、测试/断言数量、报告正文和产物可读性；不得把“文件生成”单独写成业务成功。敏感日志、响应、截图和差异样本落盘前必须脱敏，并说明存储位置、访问边界和保留期限。

## 7. 禁止事项与兼容注释

禁止：

- 未盘点入口、调用方和数据来源就改核心行为；
- 因“看起来不合理”删除历史分支或疑似冗余；
- 改旧字段、枚举 code、状态码、错误码、配置单位或默认值而不提供迁移证据；
- 在需要灰度、快速关闭或依赖未确认的场景中，无证据地默认全量启用新逻辑；把不可逆远程副作用放进本地事务假装可回滚；
- 直接拼接外部输入到 SQL；把密钥、token、支付凭证写入源码、文档或日志；
- 序列化完整请求、响应、消息、Entity、DTO、VO 或结果对象；
- 为通过验证删除失败用例、放宽断言或修改原始业务验收标准；
- 把无关格式化、重命名、大重构与兼容修复混在一起。

历史兼容注释只在行为不直观且未来维护者可能误删时添加，至少写清：保留的历史输入/输出、依赖来源、不可改变的原因、何时可以删除和验证方式。不要用注释替代测试或依赖证据。

## 8. Review 责任与参考

代码评审必须检查：依赖盘点是否完整、旧行为是否有特征化证据、接口/消息/配置/数据库兼容是否有边界、回滚是否可执行、日志和验证是否安全。评审者负责指出缺口并给出证据，不自动继承实施阶段的写测试、加开关、迁移数据或修改代码义务，除非用户明确要求实施。

评审发现问题时使用：

```text
[规范检查] 疑似违反：<候选修改>
证据：<文件、函数、行号、测试或提交>
影响：<旧契约、数据、调用方或安全边界>
建议：<保留、隔离、补测试、迁移、回滚或人工确认>
```
