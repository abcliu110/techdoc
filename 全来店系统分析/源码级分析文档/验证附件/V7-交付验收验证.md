## V7-1：六格压榨"30秒结论"验证

### 验证项：DA8 的"订单是唯一核心实体"是否有源码支持

**DA8 声称**：全来店是一个以"订单聚合体"为中心的餐饮收银终端——订单是唯一核心实体。

**源码验证**：

```
E-SRC验证：
步骤1：读取 OrderMasterDO，确认其为聚合根
OrderMasterDO 包含：
  - 所有金额字段（orderTotalAmount, actualReceiptAmount, goodsDiscountAmount 等）
  - 订单状态字段（orderStatus, isPay）
  - 关联键（billNo, orderKey）
  - 所有跨模块交互均通过 billNo 路由

步骤2：确认无其他对象同时承载金额和状态
  - OrderDetailDO：只有菜品明细，不含金额汇总
  - OrderStatusDO：只有状态，不含金额
  - OrderPay：只有单笔支付金额，不含汇总
```

**发现**：✅ 确认。OrderMasterDO 是唯一同时承载订单级别金额汇总和状态的实体，是事实上的聚合根。

**结论**：**通过** — "订单是唯一核心实体"的结论有源码支持。

## V7-2：DEC 卡推断验证

### 验证项：DEC-01（超级枚举 vs 工厂模式）的推断是否有证据

**DA8 声称**：DEC-01：为什么用"超级枚举"而不是工厂模式实现打印路由。

**源码验证**：

```
E-SRC验证：
推断：选择枚举而非工厂/策略注册的原因是性能优先（O(1)路由）

证据：
1. PrintTicketTypeEnum 是 final 类，无运行时注册机制
2. 所有枚举实例在编译时确定
3. 调用 getPrinterStrategy() 无条件分支，直接方法调用
4. 无 StrategyRegistry 或 Factory.getInstance() 调用

推断合理性：
  - 如果用工厂模式，需要在运行时查找 Map<PrintTicketType, PrinterStrategy>
  - 枚举方法直接分发，无 Map 查找开销
  - 但代价是新增票据类型需要修改枚举类
```

**发现**：⚠️ 有条件通过。推断合理，但未找到决策者注释或文档说明"为什么选择枚举"。

**结论**：**有条件通过** — 性能推断合理，但缺少决策文档证据。

## V7-4：反例发现

**DA8 声称**：isJoinReceived 多义性是"最脆弱点"之一。

**源码验证**：

```

// 语义1：是否计入实收

// 语义2：是否参与找零

进一步搜索：isJoinReceived 是否还有其他语义？
$ grep "isJoinReceived" -r service/ | grep -v ".class"
```

**发现**：⚠️ 有条件通过。isJoinReceived 确实存在多义使用，但"最脆弱点"的表述可能过度——需要验证两套语义在哪些场景下会产生不同的计算结果。

**结论**：**有条件通过** — 多义性存在，但"最脆弱点"评级需要降级为"潜在风险"。
