# 01-业务全景与能力地图

> 本文档阐述 KACI POS 系统的业务全景，覆盖业务结果族、业务分类、触发时机、核心概念关系、设计决策和角色权限。
> 适用读者：所有需要理解系统业务边界的相关方
> 前置阅读：00-阅读入口-十分钟读懂.md

## 一、业务结果族全景

业务结果族描述系统能够产出的完整业务价值，每个结果族包含：触发条件、交付物、接收角色、成功义务和失败后果。

### 1.1 核心结果族

#### 结果族 A：订单管理

| 维度 | 内容 |
|------|------|
| **触发条件** | 收银员对桌台进行开台操作，或顾客通过小程序自主下单 |
| **交付物** | 一张完整的订单（OrderMasterDO），包含账单号、桌台关联、金额汇总 |
| **接收角色** | 收银员（操作者）、顾客（被服务者）、厨房（后续流程依赖方） |
| **成功义务** | 订单必须准确记录所有菜品、做法、备注，且与桌台状态保持一致 |
| **失败后果** | 菜品漏记导致顾客投诉；金额错误导致账务纠纷；桌台状态不同步导致重复开台 |

#### 结果族 B：支付收款

| 维度 | 内容 |
|------|------|
| **触发条件** | 顾客提出结账意愿，收银员发起支付流程 |
| **交付物** | 完整的支付流水记录（OrderPay），包含支付金额、渠道、优惠分摊、找零金额 |
| **接收角色** | 顾客（付款凭证）、财务系统（账务数据）、店长（运营参考） |
| **成功义务** | 支付记录必须与订单金额精确匹配，资金必须安全入账，支持原路退款 |
| **失败后果** | 金额不匹配导致资金损失；支付丢失导致顾客付了钱但没记录；无法退款导致客诉 |

#### 结果族 C：厨房履约

| 维度 | 内容 |
|------|------|
| **触发条件** | 收银员完成落单操作，或顾客小程序提交订单 |
| **交付物** | KDS 制作单（ScreenMake），实时推送至厨房显示屏 |
| **接收角色** | 厨师（执行者）、收银员（协调者）、顾客（等待者） |
| **成功义务** | 制作单必须准确、及时传达至厨房；完成制作后必须通知收银台叫号 |
| **失败后果** | 厨房收不到单导致出菜延误；叫号错误导致菜品送错桌；制作状态不同步导致漏菜 |

#### 结果族 D：会员服务

| 维度 | 内容 |
|------|------|
| **触发条件** | 顾客提出办卡、充值、消费或查询需求 |
| **交付物** | 会员账户状态变更，包括余额更新、积分增减、消费记录 |
| **接收角色** | 顾客（权益持有者）、收银员（操作执行者） |
| **成功义务** | 余额必须精确（精确到分）；积分计算必须符合规则；消费必须扣减余额 |
| **失败后果** | 余额错误导致顾客资产损失；积分规则混乱导致促销失效；扣减失败导致亏损 |

#### 结果族 E：运营管理

| 维度 | 内容 |
|------|------|
| **触发条件** | 店长发起日结/班结操作，或系统自动触发定时任务 |
| **交付物** | 营业结算报告（Shift/Settlement），包括销售额、桌台使用率、热销菜品等 |
| **接收角色** | 店长（管理决策）、财务（账务核对）、老板（经营参考） |
| **成功义务** | 数据必须与实际交易一致；日结后数据锁定不可篡改 |
| **失败后果** | 数据不一致导致账务无法平账；数据泄露导致商业秘密外流 |

### 1.2 支撑结果族

#### 结果族 F：打印服务

| 维度 | 内容 |
|------|------|
| **触发条件** | 订单落单、结账完成、叫号通知等业务节点 |
| **交付物** | 纸质票据（厨房小票、结账单、发票、叫号单） |
| **接收角色** | 厨房（制作参考）、顾客（取餐凭证）、财务（报销凭证） |
| **成功义务** | 打印内容必须与业务数据一致；打印机故障时必须有替代方案 |
| **失败后果** | 小票内容错误导致做错菜；结账单错误导致客诉；发票打印失败导致无法报销 |

#### 结果族 G：外卖配送

| 维度 | 内容 |
|------|------|
| **触发条件** | 第三方平台（美团、饿了么）推送新订单 |
| **交付物** | 外卖订单接入、商家确认、配送创建 |
| **接收角色** | 商家（接单确认）、配送员（取餐依据）、平台（状态同步） |
| **成功义务** | 订单必须及时接单；接单后必须同步至 KDS；完成制作后通知配送 |
| **失败后果** | 接单超时导致平台处罚；配送状态不同步导致差评 |

#### 结果族 H：预订排队

| 维度 | 内容 |
|------|------|
| **触发条件** | 顾客提出预订桌位或取号等候 |
| **交付物** | 预订确认记录或排队号码 |
| **接收角色** | 顾客（等待服务）、收银员（接待执行） |
| **成功义务** | 预订必须按时提醒；排号必须公平公正；到号必须及时通知 |
| **失败后果** | 预订遗忘导致顾客白跑；排号纠纷导致现场混乱 |

## 二、业务分类表

业务按语义分为五大类别，每类内部的业务项共享相同的业务目标和约束。

### 2.1 收银订单类

**业务目标**：完成顾客从入座到离席的完整消费闭环。

| 业务项 | 触发时机 | 核心逻辑 | 依赖对象 |
|--------|---------|---------|---------|
| 开台 | 顾客入座 | 创建空白订单，绑定桌台，设置用餐人数 | 桌台（Table） |
| 加菜 | 顾客点菜 | 添加菜品至订单，检查估清，计算促销 | 商品（Goods）、估清（SoldOut） |
| 落单 | 顾客确认 | 锁定订单状态，通知厨房，打印小票 | KDS（ScreenMake）、打印（PrintJob） |
| 叫起 | 顾客催促 | 加速指定菜品制作优先级 | KDS（ScreenMake） |
| 催菜 | 顾客催促 | 标记催促状态，提醒厨房 | KDS（ScreenMake） |
| 换菜 | 顾客要求 | 退掉原菜，添加新菜 | 订单明细（OrderDetail） |
| 结账 | 顾客付款 | 计算未付金额，执行支付，记录流水 | 支付（OrderPay） |
| 反结账 | 修正错误 | 生成退款记录，恢复订单状态，红冲发票 | 支付（OrderPay）、发票（Invoice） |
| 撤单 | 取消消费 | 作废整单，恢复桌台，释放估清 | 桌台（Table）、估清（SoldOut） |
| 部分退款 | 顾客要求 | 退还指定菜品金额，重算优惠 | 订单明细（OrderDetail） |

### 2.2 厨房履约类

**业务目标**：将顾客的点餐需求准确传递给厨房，并追踪制作完成状态。

| 业务项 | 触发时机 | 核心逻辑 | 依赖对象 |
|--------|---------|---------|---------|
| KDS 分单 | 落单完成 | 创建制作单，推送至厨房显示屏 | 订单（OrderMasterDO） |
| 制作完成 | 厨师确认 | 标记制作状态，触发叫号 | 叫号单（PrintJob） |
| 叫号通知 | 制作完成 | 打印叫号单，通知收银台 | 叫号单（PrintJob） |
| 泳道配置 | 运营配置 | 按部门/品类分组显示制作单 | 部门（Department） |
| 估清设置 | 商品管理 | 设置商品可售数量，防止超卖 | 商品（Goods）、估清（SoldOut） |

### 2.3 资金会员类

**业务目标**：管理顾客资金账户和会员权益。

| 业务项 | 触发时机 | 核心逻辑 | 依赖对象 |
|--------|---------|---------|---------|
| 押金收取 | 开台配置 | 收取桌台押金，记录押金流水 | 订单（OrderMasterDO） |
| 押金核销 | 结账完成 | 押金冲抵账单或原路退还 | 订单（OrderMasterDO） |
| 会员开卡 | 新客注册 | 创建会员账户，录入基础信息 | 会员（Member） |
| 会员充值 | 储值需求 | 增加账户余额，记录充值流水 | 会员（Member） |
| 会员消费 | 刷卡支付 | 扣减账户余额，累计消费积分 | 会员（Member）、订单（OrderMasterDO） |
| 积分累计 | 支付完成 | 按消费金额计算积分，写入会员账户 | 会员（Member） |
| 余额退款 | 会员要求 | 退还会员账户余额 | 会员（Member） |

### 2.4 外卖预订类

**业务目标**：对接第三方平台，管理外卖和到店预订业务。

| 业务项 | 触发时机 | 核心逻辑 | 依赖对象 |
|--------|---------|---------|---------|
| 外卖接单 | 第三方推送 | 解析平台订单，创建本地订单 | 第三方平台 |
| 商家确认 | 接单审核 | 向平台确认接单，同步至 KDS | KDS（ScreenMake） |
| 配送创建 | 商家完成 | 创建配送任务，分配配送员 | 配送（Delivery） |
| 配送状态 | 配送进行 | 同步配送位置，通知顾客 | 第三方配送 |
| 预订管理 | 顾客预约 | 记录预订信息，设置提醒 | 桌台（Table） |
| 订金收取 | 预订确认 | 收取预订定金，锁定桌台 | 订单（OrderMasterDO） |
| 排号叫号 | 顾客取号 | 分配排队号码，按序叫号 | 叫号单（PrintJob） |
| 酒水寄存 | 顾客要求 | 记录寄存物品，生成提取凭证 | 寄存记录 |

### 2.5 运营管理类

**业务目标**：支撑门店日常运营和管理决策。

| 业务项 | 触发时机 | 核心逻辑 | 依赖对象 |
|--------|---------|---------|---------|
| 班结 | 交班时 | 汇总本班次营业额，收银员对账 | 班次（Shift） |
| 日结 | 营业结束 | 汇总全日营业额，重置估清 | 日结（Settlement） |
| 发票开具 | 顾客要求 | 开具增值税发票，记录发票信息 | 订单（OrderMasterDO） |
| 发票红冲 | 退款/错误 | 作废或冲红已开发票 | 发票（Invoice） |
| 营业报表 | 查询请求 | 汇总销售数据，生成分析图表 | 日结（Settlement） |
| 促销管理 | 运营配置 | 设置满减、折扣、优惠券规则 | 订单（OrderMasterDO） |

## 四、核心概念关系

以下关系规格（REL-*）定义了系统核心业务对象之间的关联契约。

### REL-01：订单与订单明细

**关系类型**：结构关系，1:N

**业务含义**：一个订单包含多道菜品，每道菜品是订单的一个明细行。

**字段连接**：`OrderMasterDO.billNo` → `OrderDetailDO.billNo`

**建立时机**：收银员加菜时建立（PlaceOrderService）

**约束条件**：
- 同一 billNo 下同一商品已落单则禁止重复加菜
- 套餐明细必须跟随套餐头一起操作

**级联行为**：
- 删除订单主表 → 级联删除所有明细
- 删除明细 → 不影响订单主表金额汇总（需手动重算）

**代码位置**：`service/order/PlaceOrderService.java`

---

### REL-02：订单与桌台

**关系类型**：结构关系，N:1（多订单共用一桌台）

**业务含义**：桌台是订单的承载实体，订单必须绑定桌台（或快餐 billNo）。

**字段连接**：`Table.orderKey` ↔ `OrderMasterDO.billNo`

**建立时机**：
- 开台时：`Table.orderKey = billNo`，桌台状态 → OCCUPIED
- 清台时：`Table.orderKey = ""`，桌台状态 → FREE

**约束条件**：
- 一个桌台同一时刻最多一个有效订单
- 联台时多桌台共享同一个 orderKey

**级联行为**：
- 结账完成 → 桌台状态恢复 FREE
- 撤单 → 桌台状态恢复 OCCUPIED（占用但未消费）
- 反结账 → 桌台状态恢复 PRESETTLEMENT（结账后待清台）

**代码位置**：`service/table/OpenTableService.java`，`service/table/ClearTableService.java`

---

### REL-03：菜品与打印机（间接关联，3跳）

**关系类型**：间接路由关系，N:1

**关联路径**：`菜品（Goods）` → `出品部门（Department）` → `打印队列（PrintQueue）` → `打印机（Printer）`

**业务原因**：
1. 简化配置：只需为每个部门配一个队列，而不是为每道菜单独配置打印机
2. 自然分组：同一部门的菜自动合打一张小票
3. 故障转移：队列层可以配主/备打印机，若菜品直绑打印机，坏了一台无法切换

**中间对象职责**：
- 出品部门：业务分组边界（按厨房班组划分）
- 打印队列：路由与容错（主/备打印机自动切换）

**级联行为**：
- 删除菜品 → 不影响部门/队列/打印机
- 删除部门配置 → 该部门菜品无法路由
- 删除队列 → 关联部门菜品无法打印
- 删除打印机 → 队列自动切换到备用打印机

**代码位置**：`service/print/KitchenPrintSolutionService.java`

---

### REL-04：订单与支付记录

**关系类型**：轨迹关系，1:N

**业务含义**：一个订单可能有多次支付（如先付定金、后续补款），每次支付独立记录。

**字段连接**：`OrderMasterDO.orderNo` → `OrderPay.orderNo`

**建立时机**：收银员发起支付时创建

**约束条件**：
- 同一订单的支付序号（payIndex）必须递增
- 退款时关联原支付记录（relationPayOrderId）

**金额关系**：
```
未付金额 = 订单总额 - 订单优惠 - 支付优惠 - 实收金额
```

**代码位置**：`service/pay/BasePayService.java`

### REL-05：订单明细与 KDS 制作单

**关系类型**：轨迹关系，1:N

**业务含义**：一道菜落单后在厨房产生一个制作状态追踪。

**字段连接**：`OrderDetailDO.detailId` → `ScreenMake.detailId`

**建立时机**：落单操作时（DownOrderService）

**状态流转**：待制作 → 制作中 → 已完成 → 已废弃

**代码位置**：`service/kds/DownOrderService.java`

## 五、设计决策记录（DEC 卡）

以下设计决策卡记录了系统架构中的关键选择及其权衡。

### DEC-1：离线优先架构

| 属性 | 内容 |
|------|------|
| **决策** | 所有业务操作优先访问本地 SQLite/MySQL，网络故障时仍可继续营业 |
| **证据** | `LocalServerTransactionManager.execTransaction()` 直接操作本地数据库 |
| **驱动因素** | 餐饮门店网络不稳定，不能因断网导致无法结账 |
| **权衡** | 牺牲数据实时一致性，换取高可用性；通过定时同步补偿一致性 |
| **替代方案** | 云端优先架构（网络不可用时业务中断） |

### DEC-2：枚举即工厂的策略注册

| 属性 | 内容 |
|------|------|
| **决策** | 打印票据类型用 `enum` 实现策略工厂，每个枚举值返回具体策略实例 |
| **证据** | `PrintTicketTypeEnum.PREPARE.getPrinterStrategy()` → `new EatInDevicePrinterStrategyImpl()` |
| **驱动因素** | 消除 Spring 容器依赖，编译期穷举所有票据类型，零遗漏 |
| **权衡** | 编译期固定，运行时新增票据需修改源码；换取了可预测性和零反射开销 |
| **替代方案** | Spring `@Component` 扫描（启动时反射，性能开销） |

### DEC-3：Netty Reactor + WebSocket 双通道

| 属性 | 内容 |
|------|------|
| **决策** | 使用 Netty NIO 处理 WebSocket 长连接，60 秒空闲心跳检测 |
| **证据** | `IdleStateHandler(60L, 0L, 0L)` + `PosServerChannelHandler` |
| **驱动因素** | POS Client 和 LocalServer 需双向实时通信（推送小票状态、叫号） |
| **权衡** | 连接管理复杂度增加；换取了低延迟和断线检测能力 |
| **替代方案** | 短轮询 HTTP（延迟高、资源浪费） |

### DEC-4：聚合根内聚业务逻辑

| 属性 | 内容 |
|------|------|
| **决策** | `OrderMasterDO` 包含 `cashPay()`、`payDiscount()` 等业务方法，金额计算内聚在实体内部 |
| **证据** | `OrderMasterDO.cashPay()` 直接操作 `actualReceiptAmount`、`payList` |
| **驱动因素** | 订单金额计算涉及多个字段的原子性更新，内聚更易维护和追踪 |
| **权衡** | 实体类承担了部分 Service 职责，可能导致领域模型膨胀；换取了状态变更内聚 |
| **替代方案** | 失血模型（实体仅含数据，Service 处理所有业务逻辑） |

### DEC-5：支付策略选择器路由

| 属性 | 内容 |
|------|------|
| **决策** | 10 种支付方式（现金/银行卡/储值卡/扫码/挂账等）通过 `PaySelector` Map 注册，O(1) 时间复杂度路由 |
| **证据** | `PaySelector.select(key)` → 抛异常或返回 `PayInterface` |
| **驱动因素** | 支付方式频繁扩展（现金/银行卡/储值卡/外卖平台等），需要统一抽象和灵活扩展 |
| **权衡** | 新支付方式需修改 `PaySelector` 构造函数；换取了无反射零开销查找 |
| **替代方案** | if-else 硬编码（维护成本高）或反射扫描（性能开销） |

### DEC-6：多数据库事务抽象

| 属性 | 内容 |
|------|------|
| **决策** | SQLite 用 `synchronized` 全局锁保证事务，MySQL 用 ORMLite `TransactionManager` |
| **证据** | `LocalServerTransactionManager` 中 `isSQLite` 分支逻辑 |
| **驱动因素** | 开发环境用 SQLite（零配置），生产环境用 MySQL（高并发），两套环境共存 |
| **权衡** | 两套语义需分别维护；嵌套事务在 SQLite 下串行化，可能影响高并发性能；换取了开发效率 |
| **替代方案** | 统一使用 MySQL（开发环境配置成本高）或统一使用 SQLite（生产环境性能不足） |
