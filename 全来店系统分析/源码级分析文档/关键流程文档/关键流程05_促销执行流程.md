## 一、业务因果叙事

### 场景：加菜后，订单金额从 100 元变成了 120 元，优惠怎么算？

中午，顾客点了第一道菜 100 元，收银员落单后，屏幕上显示"实付 100 元"。顾客又加了一道 20 元的菜。

**系统开始重新计算优惠。**

促销引擎看到加菜后订单总金额从 100 变成 120，触发了"满 100 减 20"的满减活动。系统重新算了一遍：120 - 20 = 100 元，和原来的实付一样。

但系统还需要重新分摊优惠金额——这 20 元的优惠，按各菜品的价格比例分摊到两道菜头上。

## 二，双层促销架构

```
┌─────────────────────────────────────────────────┐
│  ExecutePromotionService.executePromotion()        │
│                                                  │
│  第1层：POS本地促销（type 1~4）               │
│  ├── 1: 单品折扣 ── 打折                       │
│  ├── 2: 单品满减 ── 满N减M                    │
│  ├── 3: 整单折扣 ── 整单打折                   │
│  └── 4: 整单满减 ── 整单满N减M               │
│                                                  │
│  第2层：云端促销（type > 1000）               │
│  ├── 1001: 限时折扣                            │
│  ├── 1003: 特价                               │
│  ├── 1004: 满减                               │
│  ├── 1005: 组合优惠（套餐）                    │
│  ├── 1006: 满赠                               │
│  └── 1007: 买M免N                              │
│                                                  │
│  云端促销失败 → 降级到本地促销                 │
└─────────────────────────────────────────────────┘
```

## 三、优惠金额流向

```
订单总金额 (orderTotalAmount) = 288.00
    ├── 商品优惠 (goodsDiscountAmount) = 20.00    ← 单品折扣/特价
    │       用途：直接扣减商品单价
    │
    ├── 订单优惠 (orderDiscountAmount) = 10.00    ← 抹零/整单折扣
    │       特点：isJoinReceived=N，不计入实收
    │
    ├── 支付优惠 (payDiscountAmount) = 0.00       ← 优惠券/积分抵扣
    │       特点：isJoinReceived=Y，计入实收
    │
    └── 实收金额 (actualReceiptAmount) = 258.00    ← 历史已付

未付金额 = orderTotalAmount - goodsDiscountAmount - orderDiscountAmount - payDiscountAmount - actualReceiptAmount
```

## 五、失败场景

### 场景一：云端促销 SDK 超时

```
表现：优惠未计算，顾客没有享受应得优惠
原因：网络问题导致云端促销计算失败
影响：顾客可能多付钱

处理：系统降级到本地促销（type 1~4），本地没有对应规则则不加优惠
```
