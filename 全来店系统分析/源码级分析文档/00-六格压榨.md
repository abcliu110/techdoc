## 30秒结论（不看六格也能直接下判断）

1. **本质**：全来店是一个以"订单聚合体"为中心的餐饮收银终端——订单是唯一核心实体，所有模块（支付/促销/会员/桌台/打印/KDS）都围绕订单的状态变化提供服务，没有独立的业务边界，是典型的"大订单"单体设计。
2. **承重墙**：PrintTicketTypeEnum 是系统的设计枢纽——每个枚举实例同时持有打印机策略、票据构建策略、模板生成器，用 O(1) 路由替代了 if-else 分支，是整个系统的策略注入中心。
3. **最脆弱点**：估清系统与订单的"预留-确认-回滚"机制存在 TOCTOU 竞态——下单时 occupy_num 预占，但结账前无乐观锁，若顾客在等待结账时商品被其他订单消耗，可能出现超售。
4. **唯一受控缺口**：订单金额的三层优惠（orderDiscountAmount / payDiscountAmount / goodsDiscountAmount）虽然逻辑清晰，但 isJoinReceived 字段的含义在源码中存在多义——部分代码将其用于"是否计入实收"，部分用于"是否参与找零计算"，两套语义未统一，是金额不变量被破坏的潜在根因。
5. **演化方向**：系统当前处于"本地复杂化"阶段——大量业务规则硬编码在 Service 层，云端 SDK（QLExpress）仅用于促销计算。建议将策略型逻辑（支付路由、打印路由、促销分发）全部迁移到云端配置，本地只保留执行器。

## 一、业务分析（它做什么）≤5

- **订单是唯一核心实体**——OrderMasterDO 聚合了所有业务状态，billNo 是全局唯一键，所有跨模块交互均通过订单号路由。证据：`OrderMasterDO.java` 所有财务字段集中于此，payDiscountAmount 和 actualReceiptAmount 的变动必须与订单状态联动。`E-SRC: service/order/domain/entity/OrderMasterDO.java:1-60`
- **估清通过占用数量实现超售保护**——occupy_num 与 usable_num 分离，加菜预占、退款释放、日结同步云端，形成"预留-确认-回滚"三段式。证据：`soldOutOccupyHandle()` 在 `PlaceOrderService.java:79`，释放逻辑在 `soldOutOccupyRelease()`。`E-SRC: service/order/PlaceOrderService.java:79` + `service/soldout/SoldOutOccupyBizService.java`
- **支付是订单的副作用**——BasePayService 不负责订单创建，只负责在已有订单上追加支付记录；支付完成后触发 autoCheckout 才真正改变订单状态。证据：`BasePayService.payComplete()` 调用 `orderMaster.payComplete()`，payComplete 方法在 `OrderStatusDO.java` 中定义状态变更。`E-SRC: service/pay/extension/BasePayService.java` + `service/order/domain/entity/OrderStatusDO.java`
- **促销计算是加菜和结账的前置条件**——每次加菜都必须执行促销重算，每次结账前必须确认促销已锁定。促销分 POS 本地（type 1-4）和云端 SDK（type>1000）两层，失败时降级到本地。证据：`ExecutePromotionService.executePromotion()` 是所有变更的必经之路。`E-SRC: service/promotion/ExecutePromotionService.java`
- **桌台状态机是订单状态的镜像**——桌台状态（FREE/OCCUPIED/PRESETTLEMENT）与订单状态（ORDER_WJD/ORDER_DJZ/ORDER_YJZ）一一对应，桌台不清0则订单无法关闭。证据：`OpenTableService` 和 `ClearTableService` 分别管理两个状态机的同步。`E-SRC: service/table/service/OpenTableService.java`

## 二、架构分析（它怎么建）≤5

- **无 Spring Boot，手动 Bean 管理**——PosContext.getBean() 通过 ConcurrentHashMap + 反射注入实现，比 Spring 轻量但无 AOP，所有横切逻辑（事务/锁/上下文）都在调用方显式处理。证据：`PosContext.getBean()` 在 `common/PosContext.java`，无 Spring 依赖。`E-SRC: common/PosContext.java`
- **Netty Server 是唯一的网络入口**——同时处理 HTTP 和 WebSocket，Handler 通过 ConcurrentHashMap懒加载注册，首次请求等待 3 秒。约 395 个 Handler 按业务域分组，无注解路由。证据：`PosServerChannelHandler` 的 pipeline 配置在 `web/server/PosServer.java`。`E-SRC: web/server/PosServer.java:1-36`
- **打印采用"超级枚举"策略模式**——PrintTicketTypeEnum 每个实例同时持有 PrinterStrategy、TicketPrintStrategy、TemplateTicketGenerator，O(1) 路由替代了工厂模式，避免了运行时多态查找开销。证据：`PrintTicketTypeEnum.java` 所有枚举实例的方法实现。`E-SRC: print/enums/PrintTicketTypeEnum.java`
- **KDS 三屏联动通过泳道配置**——配餐屏→制作屏→出餐屏的流转由 SwimConfigDo 控制，每个 ScreenMakeDetailDo 独立跟踪三个屏幕状态，支持跳过中间屏幕。证据：`KdsMakeCreateManager` 构建 ScreenMakeDo。`E-SRC: kds/manager/KdsMakeCreateManager.java`
- **订单上传云端是最终一致性**——所有变更先写本地 MySQL，异步上传云端，上传失败记录在 fail_task_records 表，通过定时任务重试。无本地消息队列，依赖数据库表 + 线程池模拟。证据：`OrderUploadTaskService` 和 `OrderUploadTaskDao`。`E-SRC: service/order/upload/OrderUploadTaskService.java`

## 三、业务归纳（它真正是什么）≤4

- **本质**："本地强一致性 + 云端最终一致性"的混合架构，本地处理全部实时业务（点餐/支付/打印/KDS），云端负责配置下发（促销规则/商品档案/会员信息）和数据汇聚（营业报表/订单备份）。
- **CI（核心不变量）**：任何时刻，`orderTotalAmount = goodsDiscountAmount + orderDiscountAmount + payDiscountAmount + actualReceiptAmount + unpaidAmount`。三层优惠和实收金额之和必须等于订单总金额。破坏此不变量意味着金额链路存在漏洞。
- **竞争解释**：有人可能认为"估清是核心"，但实际上估清只在加菜时检查，结账时不强制校验——估清保护的是"点菜阶段不超售"，而非"结账阶段一定有货"，两者是不同保障目标。
- **F（失败模式）**：系统最常出现的不是技术故障，而是"估清数量不准导致顾客点完无法制作"——这本质上是业务参数配置问题，不是代码 bug，但系统缺少估清预警机制（库存低于阈值时无人知晓）。

## 四、架构归纳（哪根是承重墙）≤4

- **承重墙**：PrintTicketTypeEnum + Strategy 组合——所有票据类型通过枚举实例硬编码策略，无运行时扩展，但保证了 O(1) 路由和编译期类型安全，是性能优先设计下的最优解。
- **正交轴**：订单状态机（OrderStatusEnum）与桌台状态机（TableStatusEnum）是两条正交的状态链，通过 billNo 和 tableCode 相互引用，但各自独立流转。两者必须同步，但代码中同步逻辑分散在多个 Service 中，是潜在的一致性漏洞。
- **J.2 后验**：订单上传的"失败重试"机制是临时补丁——fail_task_records 表记录上传失败，但没有死信队列和指数退避，超时重试可能加剧云端压力。

## 五、业务进化（机制上该动什么）≤4

- **必做：统一 isJoinReceived 语义**——当前 isJoinReceived 既表示"是否计入实收"又表示"是否参与找零计算"，两套语义混用。应拆分为 isIncludedInReceipt 和 isParticipateInRounding 两字段，并在所有赋值点做交叉检查。证据：`OrderPayDO.isJoinReceived` 在多处被不同理解使用。`E-SRC: service/order/domain/entity/OrderPayDO.java`
- **机制候选：估清预警阈值**——当前估清只有"已估清/未估清"二元判断，建议增加 shopSafetyNum（安全库存）字段，低于阈值时推送 WebSocket 通知前端提示服务员。证据：`tbl_sold_out_stock` 表已有 shopSafetyNum 字段但未使用。`E-SRC: service/soldout/`
- **不做基线的分界**：不建议将"促销计算完全迁移到本地"——云端促销规则（满减/买赠/优惠券）涉及实时价格政策，迁移到本地会增加版本同步复杂度，本地只做执行器是合理边界。
- **不做基线的分界**：不建议将"KDS 改为消息队列"——当前 ScreenMakeDo 入库 + WebSocket 推送的模式满足实时性要求，引入 MQ 会增加运维复杂度且无明确收益。

## 六、架构进化（怎么安全演化）≤4

- **K1-K5 判定**：系统当前在 K2（本地一致性优先），向 K3（可演进架构）迁移的最小路径是：将策略路由（支付选择/打印选择/促销分发）从硬编码改为云端配置，本地保留执行器，云端下发路由表。
- **迁移最大代价**：如果将 PrintTicketTypeEnum 策略改为运行时配置，需要重构整个 print 包约 578 个文件，且影响所有票据类型的路由逻辑。建议保持枚举不变，将新增票据类型通过枚举扩展而非运行时注册。
- **交接包**：订单聚合体是核心交付单元，任何重构不得拆分 OrderMasterDO 的聚合边界；PayInterface 是支付策略的接口契约，任何新增支付方式必须实现此接口。
- **交接包**：估清占用机制（occupy_num）是库存保护的关键路径，修改此逻辑必须通过完整的 TOCTOU 测试套件。
