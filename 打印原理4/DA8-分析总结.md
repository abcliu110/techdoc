## 一、十分钟读懂打印系统

> **适用场景**：快速建立全局认知，适合新成员 onboarding 或紧急接入
> **阅读时长**：约 10 分钟

### 1.1 一句话定义

**打印系统是 POS 的「出票工厂」**：接收收银员的打印指令，从云端获取样式模板，将订单数据渲染为打印机指令，最终驱动硬件输出票据。

### 1.3 三个核心概念

| 概念 | 比喻 | 关键设计 |
|------|------|----------|
| **PrintJob** | 工单 | 文件+Redis双存储，断电不丢 |
| **PrintStyle** | 模具 | JSON行+列布局，协议解耦 |
| **Handler** | 翻译官 | 7种Handler，根据打印机类型选择 |

### 1.4 典型场景：结账打印

```
收银员点击「结账」
       │
       ▼
CloseMpScHandler（结账处理器）
       │
       ├── 计算订单金额
       ├── 保存支付明细
       ├── 更新账单状态
       └── 触发打印任务
       │
       ▼
PrintJobGenerator（任务生成器）
       │
       ├── 查询打印开关（disabledCustomer?）
       ├── 获取打印份数（numOfCustomer）
       ├── 查询 PosCustomerBillSetting
       └── 创建任务 → 写入文件
       │
       ▼
PrinterWorker（工作线程，虚拟线程）
       │
       ├── take() 从队列取任务
       ├── 渲染模板（样式+数据）
       ├── 选择 Handler（根据打印机类型）
       └── 协议转换 → 打印机指令
       │
       ▼
物理打印机输出票据
```

## 四、业务流程详解

### 4.1 顾客联生成流程

```
1. 业务事件触发 (结账)
        │
        ▼
2. PrintJobTypeSwitchService.get(mid, sid, jobType)
        │
        ├── disabledCustomer == true? ──► 结束
        │
        ▼
3. 获取 numOfCustomer (默认1)
        │
        ▼
4. PosCustomerBillSettingService.get(mid, sid)
        │
        ▼
5. 遍历设置的打印队列
        │
        ▼
6. 每个队列创建 numOfCustomer 个任务
        │
        ▼
7. 任务进入 PrinterWorker 队列
```

### 4.2 厨房联生成流程

```
1. 业务事件触发 (点菜)
        │
        ▼
2. PrintJobTypeSwitchService.get(mid, sid, jobType)
        │
        ├── disabledKitchen == true? ──► 结束
        │
        ▼
3. 获取 numOfKitchen (默认1)
        │
        ▼
4. 加载菜品、做法、口味数据
        │
        ▼
5. CookwayPrintDeptPlanner.groupByPrintDept()
        │
        ├── 有做法出品部门 ──► 按做法分单 (一菜多单)
        │
        └── 无做法出品部门 ──► 按菜品分单 (一菜一单)
        │
        ▼
6. 获取菜品/做法的 PosDept
        │
        ▼
7. 获取部门的 prnQueue
        │
        ▼
8. 每个队列创建 numOfKitchen 个任务
```

### 4.3 打印执行流程

```
1. PrinterWorker 启动，绑定打印机
        │
        ▼
2. 循环检查打印机状态
        │
        ├── 状态 != NORMAL ──► redirect() 重定向任务 ──► 等待5秒 ──► 继续
        │
        ▼
3. take() 从阻塞队列取任务
        │
        ▼
4. 检查任务超时 (30分钟)
        │
        ├── 超时 ──► 标记FAILED ──► 删除文件 ──► 结束
        │
        ▼
5. getFromFile() 加载任务文件
        │
        ├── 文件不存在 ──► 结束
        │
        ▼
6. handlePrintJob() 渲染打印
        │
        ├── 成功 ──► 删除文件 ──► 状态=SUCCESS
        │
        └── 失败 ──► prnCount+1 ──► 放回队列 ──► 10秒后重试
```

## 六、异常处理与恢复

### 6.1 常见异常场景

| 场景 | 处理方式 | 人工介入 |
|------|----------|----------|
| 菜品无出品部门 | 跳过该菜品的厨房联 | 检查菜品配置 |
| 出品部门已删除 | 跳过该部门的任务 | 重新配置部门 |
| 打印机故障 | 重定向到备用打印机 | 检查打印机电源/网络 |
| 任务超时 | 标记失败，清理任务 | 确认是否需要重打 |
| 做法无有效队列 | 按菜品出品部门打印 | 检查做法出品部门配置 |

### 6.2 降级策略

| 组件 | 降级策略 |
|------|----------|
| 主打印机 | 切换到备用打印机 |
| 备用打印机 | 任务留在队列等待 |
| Redis | 从数据库加载prnCount |
| 打印任务文件 | 任务标记失败 |

### 6.3 监控告警阈值

| 指标 | 阈值 | 告警级别 |
|------|------|----------|
| 打印失败率 | > 5% | 警告 |
| 队列积压数 | > 100 | 警告 |
| 重试次数 > 2 的任务数 | > 10 | 警告 |
| 磁盘使用率 | > 80% | 严重 |
| 打印机离线数 | > 0 | 警告 |

## 八、架构决策记录

### DEC-01: 为什么采用Job-Queue-Worker三层架构？

**决策**：采用Job-Queue-Worker三层分离架构

**理由**：
- 解耦业务和打印：业务操作不会因为打印机故障而阻塞
- 异步处理：打印任务可以异步执行，不影响业务流程
- 流量控制：队列可以缓冲任务，平滑流量高峰
- 故障隔离：单台打印机故障不影响其他打印机

**被放弃的方案**：同步调用打印机
**放弃原因**：打印耗时1-10秒，同步调用会阻塞结账流程

### DEC-02: 为什么用JSON存储主备打印机配置？

**决策**：使用JSON格式存储主备打印机列表

**理由**：
- 灵活性：支持N主N备的灵活配置
- 扩展性：新增打印机只需修改JSON
- 负载均衡：同一队列可绑定多台主打印机

**被放弃的方案**：外键字段 primary_printer_id 和 standby_printer_id
**放弃原因**：不灵活，新增需要改表

### DEC-03: 为什么按出品部门分单？

**决策**：按出品部门（PosDept）路由厨房联

**理由**：
- 物理分离：不同部门在不同位置
- 职责清晰：厨师只收到属于自己的菜品
- 效率提升：不需要从一堆菜品中挑出自己负责的

### DEC-04: 为什么做法出品部门优先于菜品出品部门？

**决策**：当菜品有做法且做法有独立出品部门时，优先按做法分单

**理由**：
- 准确性：做法决定最终出品位置（如加辣由调料区负责）
- 灵活性：支持更细粒度的分单控制

### DEC-05: 为什么用Handler多态处理不同打印机类型？

**决策**：采用Handler策略模式

**理由**：
- 封装差异：将不同打印机的差异封装在各自的Handler中
- 开闭原则：新增打印机类型只需添加新Handler
- 可测试性：可以单独测试每个Handler

### DEC-06: 为什么打印任务存储在文件而不是数据库？

**决策**：任务详情存储在文件中，数据库只存储任务元数据

**理由**：
- 性能：大字段读写文件比数据库更快
- 格式保持：JSON格式保持原始数据结构
- 清理：成功任务直接删除文件

**被放弃的方案**：仅用数据库
**放弃原因**：高并发下数据库可能成为瓶颈

### DEC-07: 为什么用Redis存储打印计数？

**决策**：使用Redis存储打印计数，设置15分钟过期

**理由**：
- 性能：Redis操作比数据库快
- 原子性：inc操作保证计数准确性
- 自动清理：过期时间自动清理历史数据

### DEC-08: 为什么主打印机故障时重定向任务而不是等待？

**决策**：主打印机故障时，立即将队列中的任务重定向到备用打印机

**理由**：
- 及时性：减少用户等待时间
- 业务连续性：用户不会因为单台打印机故障而中断

**被放弃的方案**：等待主打印机恢复后再处理
**放弃原因**：用户体验差，可能导致任务堆积

## 十一、关键发现

### 11.1 架构优势

1. **三层分离**：Job-Queue-Worker架构解耦了业务和打印执行
2. **多态设计**：Handler策略模式支持多种打印机类型
3. **灵活分发**：按出品部门/做法/传菜间多维度分发
4. **故障隔离**：主备切换保证业务连续性
5. **可观测性**：完善的日志和状态追踪

### 11.2 潜在风险

1. **配置复杂度**：出品部门、打印队列、打印机多层关联
2. **状态同步**：文件+数据库双存储需要同步维护
3. **故障定位**：异步流程长，调试困难
4. **Redis依赖**：打印计数依赖Redis可用性

### 11.3 改进建议

1. **超时可配置**：按票据类型配置超时时间
2. **任务可视化**：增加任务追踪页面
3. **批量配置**：支持批量设置打印开关
4. **监控告警**：完善打印机状态监控
