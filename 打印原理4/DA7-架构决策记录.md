### DEC-PRN-001: 为什么采用Job-Queue-Worker三层架构？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 整体架构

**上下文:**
打印任务生成和执行存在速度差异：
- 业务事件触发（点菜/结账）是一次性操作，耗时短
- 打印执行是慢速I/O操作，可能需要数秒
- 需要解耦业务层和打印执行层

**决策:**
采用Job-Queue-Worker三层分离架构：
```
业务层 → PrintJobGenerator → Prn_PrintJob → 队列 → PrinterWorker → Handler
```

**理由:**
1. **解耦业务和打印**：业务操作不会因为打印机故障而阻塞
2. **异步处理**：打印任务可以异步执行，不影响业务流程
3. **流量控制**：队列可以缓冲任务，平滑流量高峰
4. **故障隔离**：单台打印机故障不影响其他打印机
5. **可观测性**：队列长度可以监控打印系统负载

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 业务响应时间不受打印机影响 |
| 正面 | 支持打印任务持久化（重启不丢失） |
| 正面 | 便于实现重试、优先级等高级特性 |
| 负面 | 增加了系统复杂度 |
| 负面 | 任务状态需要额外同步 |
| 负面 | 调试困难（异步调用链路长） |

**权衡:**
虽然增加了复杂度，但对于餐饮POS系统来说，打印是后台操作，业务响应不应被打印阻塞。利大于弊。

### DEC-PRN-002: 为什么用JSON存储主备打印机配置？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** PosPrnQueue

**上下文:**
打印队列需要绑定主打印机和备用打印机。早期的设计方案可能是用外键字段如 `primary_printer_id` 和 `standby_printer_id`。

**决策:**
使用JSON格式存储主备打印机列表：
```java
PosPrnQueue.primaryPrinter = "[1,2,3]"  // JSON数组
PosPrnQueue.standbyPrinter = "[4,5]"    // JSON数组
```

**理由:**
1. **灵活性**：支持N主N备的灵活配置，不受字段数量限制
2. **扩展性**：新增主备打印机只需修改JSON，无需改表结构
3. **负载均衡**：同一队列可以绑定多台主打印机实现负载均衡
4. **故障切换**：可以指定多台备用打印机，依次尝试

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 配置灵活性高 |
| 正面 | 扩展成本低 |
| 负面 | 需要解析JSON，略微影响性能 |
| 负面 | 无法在数据库层面强制引用完整性 |
| 负面 | 查询主备打印机需要额外处理 |

**替代方案考虑:**
- **外键方案**：每台打印机一个字段。不灵活，新增打印机需要改表。
- **关联表方案**：pos_prn_queue_printer中间表。查询复杂，增加join操作。

**权衡:**
JSON解析的性能损耗可以忽略（毫秒级），但灵活性价值更高。

### DEC-PRN-003: 为什么按出品部门分单？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 厨房联分发

**上下文:**
餐饮系统中，厨房通常分为多个出品部门（炒菜间、凉菜间、面点间等）。每个部门在不同的物理位置，需要各自的打印机。

**决策:**
按出品部门（PosDept）路由厨房联打印任务：
```
菜品 → 出品部门 → 打印队列 → 打印机
```

**理由:**
1. **物理分离**：不同部门在不同位置，不能共用打印机
2. **职责清晰**：每个部门只收到属于自己的菜品
3. **效率提升**：厨师不需要从一堆菜品中挑出自己负责的
4. **一菜一单**：支持一道菜打印一张单子

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 部门职责清晰 |
| 正面 | 提高厨房效率 |
| 正面 | 支持灵活的部门配置 |
| 负面 | 配置复杂度增加 |
| 负面 | 需要维护菜品-部门映射 |

**代码证据：**
```java
// PrintJobGenerator.java:662-668
Long deptId = food.getPrnDeptLid();
PosDept posDept = posDeptMap.get(deptId);
Set<Long> prnQueueIdSet = toLongSet(posDept.getPrnQueue());
```

### DEC-PRN-004: 为什么做法出品部门优先于菜品出品部门？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 厨房联分发

**上下文:**
一道菜可能有多种做法（如"微辣"、"中辣"、"特辣"），不同做法可能需要送到不同的出品部门（如辣度由调料区负责）。

**决策:**
当菜品有做法且做法有独立出品部门时，优先按做法分单：
```java
// 一道菜可能生成多张票据
if (hasCookwayPrintDept) {
    // 按做法分单：一菜多单
} else {
    // 按菜品分单：一菜一单
}
```

**理由:**
1. **准确性**：做法决定最终出品位置（如加辣由调料区负责）
2. **灵活性**：支持更细粒度的分单控制
3. **兼容性**：没有做法时降级到菜品分单

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 支持复杂的厨房分工 |
| 正面 | 一道菜可以分到多个部门 |
| 负面 | 增加分单逻辑复杂度 |
| 负面 | 条码编码需要包含做法信息 |

**代码证据：**
```java
// PrintJobGenerator.java:886-956
Map<Long, List<CookwayPrintDeptPlanner.CookPrintItem>> cookwayDeptMap =
    CookwayPrintDeptPlanner.groupByPrintDept(cookMap.get(food.getLid()), tasteMap.get(food.getLid()));
```

### DEC-PRN-005: 为什么用Handler多态处理不同打印机类型？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 打印执行层

**上下文:**
系统支持8种连接方式（DRIVER/NET/COM/USB/LPT/XY_CLOUD/JB_CLOUD/DRIVER_CMD）和17种打印机型号。每种组合可能有不同的打印指令和协议。

**决策:**
采用Handler策略模式：
```
PrinterWorker → 根据type选择Handler → 具体Handler实现打印
```

**Handler选择矩阵：**
| type | Handler | 特殊型号处理 |
|------|---------|--------------|
| DRIVER | GraphicsHandler | - |
| DRIVER_CMD | PortHandlerWithDriver | - |
| NET/COM/USB/LPT | PortHandler | - |
| NET/COM/USB/LPT | JBTagPrinter | GP_3150TFN |
| NET/COM/USB/LPT | XYTagPrinter | XP_T202UA |
| NET/COM/USB/LPT | HanYinPrinter | HY58/HY80 |
| XY_CLOUD | XpCloudPrinter | - |
| JB_CLOUD | JBCloudPrinter | - |

**理由:**
1. **封装差异**：将不同打印机的差异封装在各自的Handler中
2. **开闭原则**：新增打印机类型只需添加新Handler，不修改现有代码
3. **单一职责**：每个Handler只负责一种类型的打印机
4. **可测试性**：可以单独测试每个Handler

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 易于扩展新打印机 |
| 正面 | 代码组织清晰 |
| 正面 | 便于针对性优化 |
| 负面 | Handler数量可能膨胀 |
| 负面 | 需要维护Handler与类型的映射 |

### DEC-PRN-006: 为什么打印任务存储在文件而不是数据库？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 任务持久化

**上下文:**
打印任务包含大量渲染数据（样式、字体、对齐等），数据量较大且格式复杂。

**决策:**
任务详情存储在文件中，数据库只存储任务元数据：
```
/prn_jobs/{lid}.json  → 任务详情
pos_prn_job表         → 任务元数据
```

**理由:**
1. **性能**：大字段读写文件比数据库更快
2. **格式保持**：JSON格式保持原始数据结构
3. **解耦**：数据库和文件可以独立扩展
4. **清理**：成功任务直接删除文件，无需清理数据库记录

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 任务处理速度快 |
| 正面 | 数据库表体积可控 |
| 正面 | 成功任务自动清理 |
| 负面 | 需要额外处理文件生命周期 |
| 负面 | 文件损坏风险 |
| 负面 | 分布式部署需要共享存储 |

**代码证据：**
```java
// PosPrnJobServicePlus.java:154-166
String fileName = getJobFileName(lid, JOB_FILE_EXT);
String jobStr = FileUtil.readString(fileName, StandardCharsets.UTF_8);
PosPrnJobCreateDTO job = JSON.parseObject(jobStr, PosPrnJobCreateDTO.class);
```

### DEC-PRN-007: 为什么用Redis存储打印计数？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 重试机制

**上下文:**
打印任务失败后需要重试，需要跟踪每个任务的打印次数（prnCount）。

**决策:**
使用Redis存储打印计数，设置15分钟过期时间：
```java
redisTemplatePlus.incWithExpire(KEY_FOR_COUNT_IN_REDIS + lid, 15, TimeUnit.MINUTES);
```

**理由:**
1. **高性能**：Redis操作比数据库快
2. **原子性**：inc操作保证计数准确性
3. **自动清理**：过期时间自动清理历史数据
4. **分布式**：支持多节点共享计数

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 计数操作性能高 |
| 正面 | 无需手动清理 |
| 正面 | 支持分布式部署 |
| 负面 | Redis不可用时需要降级 |
| 负面 | 15分钟内重启会导致计数丢失 |

**降级方案:**
Redis过期后重新从数据库加载prnCount。

### DEC-PRN-008: 为什么主打印机故障时重定向任务而不是等待？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 故障处理

**上下文:**
当打印机发生故障（纸用完、卡纸、离线等）时，队列中的任务如何处理？

**决策:**
主打印机故障时，立即将队列中的任务重定向到备用打印机：
```java
if (status != PrinterStatus.NORMAL) {
    redirect();  // 重定向任务到备用打印机
    Thread.sleep(Duration.ofSeconds(5));
}
```

**理由:**
1. **及时性**：不等待主打印机恢复，减少用户等待时间
2. **资源利用**：备用打印机可以立即接管任务
3. **业务连续性**：用户不会因为单台打印机故障而中断业务流程
4. **可观测性**：故障和恢复都有日志记录

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 任务及时处理 |
| 正面 | 业务不中断 |
| 正面 | 便于监控打印机状态 |
| 负面 | 可能在备用打印机上打印 |
| 负面 | 需要维护主备关系 |

**替代方案考虑:**
- **等待恢复**：等待主打印机恢复后再处理。用户体验差。
- **暂停队列**：暂停该队列的任务处理。可能导致任务堆积。

### DEC-PRN-009: 为什么打印开关按票据类型配置？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 打印开关

**上下文:**
不同业务场景（点菜/结账/退菜）需要控制不同的联打印。开关配置应该粒度如何划分？

**决策:**
打印开关按票据类型（PrnStyleTypeEnum）配置：
```java
PrintJobTypeSwitch {
    type: PrnStyleTypeEnum  // 票据类型
    disabledKitchen: Boolean  // 禁用厨房联
    disabledWaiter: Boolean   // 禁用传菜联
    disabledCustomer: Boolean // 禁用顾客联
    numOfKitchen: Integer     // 打印份数
    ...
}
```

**理由:**
1. **业务对齐**：票据类型直接对应业务场景，配置直观
2. **灵活性**：可以为不同业务配置不同的打印策略
3. **扩展性**：新增业务类型只需添加新的票据类型
4. **简洁性**：一个表控制所有开关

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 配置直观 |
| 正面 | 灵活控制 |
| 正面 | 易于理解 |
| 负面 | 无法按门店/区域精细控制 |
| 负面 | 大型连锁需要批量配置工具 |

### DEC-PRN-010: 为什么任务超时设置为30分钟？

**日期:** 2026/08/03
**状态:** Accepted
**模块:** 任务管理

**上下文:**
打印任务可能因为各种原因长期停留在队列中（如打印机长期离线）。

**决策:**
任务创建超过30分钟未处理，标记为失败：
```java
if (Duration.between(jobDate, LocalDateTime.now()).toMinutes() > 30) {
    posPrnJobServicePlus.archiveFailed(..., "Print task timeout");
}
```

**理由:**
1. **资源保护**：避免过期任务占用队列资源
2. **及时反馈**：用户能及时知道打印失败
3. **日志清理**：清理长期任务减少日志膨胀
4. **业务合理性**：30分钟内未打印的票据可能已经过时

**后果:**

| 类型 | 描述 |
|------|------|
| 正面 | 队列资源可控 |
| 正面 | 用户及时获知失败 |
| 正面 | 日志不会无限膨胀 |
| 负面 | 高峰期可能误判 |
| 负面 | 需要重试机制配合 |

**权衡:**
30分钟是一个经验值，可以根据实际业务调整。对于快餐场景可能偏长，对于正式餐厅可能偏短。
