## 1. 调查范围与证据口径

本文整理 POS 前台「充值记录 → 撤销充值」失败，报「【撤销】失败：未查到数据」的一次线上排查。

## 2. 核心结论

**POS 前台「撤销充值」失败，根因已确认：**

> 充值时走了**充值支付通道**；撤销时因本地 `dwd_apply_pay.deal_type` 被记成**消费**，退款被送到了**消费支付通道**；通道/商户不一致导致查不到原支付单，返回「未查到数据」，撤销中断。

更具体地说：

1. 充值下单时，POS 调支付接口传的是 `dealType=RECHARGE`，云端按充值通道收单成功。
2. 本地落库 `createApplyPay` 却把 `deal_type` **写死为 `CONSUME`**。
3. 撤销退款时，POS 又把本地错误的 `deal_type=CONSUME` 传给支付服务。
4. 支付服务按 `dealType` 选择通道：
   - `RECHARGE` → `channelNoForRecharge`
   - 其他/`CONSUME` → `channelNo`
5. 本案门店「充值通道 ≠ 消费通道」，因此用错误商户去退原支付单，渠道返回类似「未查到数据」。
6. POS 在支付退款失败处中断，本地 `dwd_apply_pay` 仍为未退款。
7. 后台会员储值流水显示余额可能已回滚，形成**账务半成功**风险：余额已撤、微信资金未必已退。

## 5. 功能边界：这不是普通退款

截图功能是 **POS 充值记录里的「撤销充值」**，不要与以下能力混淆：

| 能力 | 说明 |
|---|---|
| 撤销充值（本案） | 回滚一笔充值任务 + 可能原路退微信/支付宝 + 扣回会员本金/赠送 |
| 退卡 | `refundSign` 一类卡状态/退卡流程 |
| 消费退款 / 整单退 | 账单退款链路，不是充值记录页 |
| 挂账 undoRecharge | 信用账户充值撤销，不是会员储值这条 |

## 7. 根因证据链

### 7.1 门店日志（已确认）

失败堆栈关键路径：

```text
MemberForBizController.revokeBill
  -> nms4CloudPayService.refund
  -> IllegalArgumentException: 未查到数据
```

含义：

- 撤销请求已进入 POS 本地服务。
- 在支付退款阶段失败。
- 不是「前端假失败」，也不是单纯 CLS 搜不到 CRM 日志。

### 7.2 门店数据（已确认）

成功支付那行关键状态：

```text
trade_state  = SUCCESS
refund_state = 未退款
deal_type    = 1   # CONSUME 消费   ← 错误
pay_terminal_trace = 2080533567411097601
```

### 7.3 代码（已确认）

充值下单时，订单操作类型为充值（`OrderOpType=E`）会传：

```text
dealType = RECHARGE
```

但本地 `createApplyPay` 落库写死：

```text
dwdApplyPay.setDealType(DealTypeEnum.CONSUME);
```

撤销时又：

```text
refundRequest.setDealType(dwdApplyPay.getDealType()); // CONSUME
refundRequest.terminalTrace = pay_terminal_trace
```

### 7.4 云端支付选通道（已确认）

`PayChannelServicePlus.getChange` 会先按 `dealType` 选通道：

| 请求 dealType | 选中的通道 |
|---|---|
| `RECHARGE` | `channelNoForRecharge`（没有才回退普通通道） |
| `CONSUME`/其他 | `channelNo` 消费通道 |

通道退款前虽然可按 `sid + terminalTrace` 找到本地支付单记录，但真正退款使用的是 **当前 `dealType` 选中的通道商户配置**。

微信通道异常会通过 `NmsResult.error(e.getMessage())` 原文透传；POS 最终看到的「未查到数据」符合渠道/商户侧查原单失败后的透传结果。

### 7.5 门店通道配置（已确认）

凤小馆永庆坊臻品店：

| 类型 | 配置 |
|---|---|
| 消费通道 | 凤小馆永庆坊店 |
| 充值通道 | 凤小馆 |

两者不同，因此：

```text
充值收单：凤小馆（充值通道）
撤销退款：凤小馆永庆坊店（消费通道）
  -> 错商户查原单失败
  -> 未查到数据
  -> POS 撤销失败
```

## 8. 不是什么

以下判断在本案中应排除或降级：

1. **不是腾讯云 CLS 搜索坏了**  
   CRM 主题里搜不到该流水，是因为失败主要卡在门店 `pos2plugin` / 支付退款，且检索条件（pod、关键字、时间窗）也容易偏。
2. **不是随便复用了历史消费账单**  
   关键问题是支付类型字段记错，不是“拿了别的消费单当充值单”。
3. **不是最近一两天刚改坏**  
   `deal_type` 写死为消费至少可追溯到 2025-03 支付改造相关实现；本案因该店充值/消费通道分离而稳定暴露。
4. **不是所有门店、所有充值都会挂**  
   仅当「移动支付充值 + 走本地 `dwd_apply_pay` 退款 + 充值通道 ≠ 消费通道」时稳定复现。  
   现金充值、跳过退款只撤余额、充值/消费同通道门店，不一定同样失败。

## 9. 业务风险

可能出现半成功状态：

| 维度 | 本案观察 |
|---|---|
| 会员余额 | 后台储值流水显示可能已回滚到 0 |
| 本地支付退款 | `dwd_apply_pay` 仍未退款 |
| 微信资金 | 需到**充值通道「凤小馆」**核对 2000 是否已原路退回 |

风险点：

- 若余额已回滚但微信未退，顾客资金受损。
- 若运营继续在 POS 反复点撤销，可能制造更多失败请求与状态噪音。
- 仅看 POS 提示“失败”，会误判为“钱和余额都没动”，掩盖 CRM 已回滚的情况。

   OR saas_order_no = '2080533550130565122'

WHERE bill_lid = '2080533550130565122'
   OR pay_terminal_trace = '2080533567411097601'

WHERE bill_lid = '2080533550130565122'

若门店库字段名有历史差异，以实际表结构为准；排查重点不变：

1. 账单是不是充值单；
2. 成功支付 trace 是什么；
3. `deal_type` 是否被记成消费；
4. `refund_state` 是否仍未退款。

## 11. 处理建议

### 11.1 止血

1. 停止在 POS 前台对该单反复点「撤销充值」。
2. 到充值通道「凤小馆」核对该笔微信 2000 是否已退款。
3. 核对会员余额、赠送、积分与资金是否一致。
4. 若余额已回滚但微信未退，走人工退款/调账，避免二次自动撤销把状态弄得更乱。

### 11.2 代码修复方向（建议，本文未实施）

1. `createApplyPay`：当账单为充值（`order_op_type=E` / 充值场景）时，写 `deal_type=RECHARGE`，不要写死 `CONSUME`。
2. 撤销退款：优先按账单操作类型强制传 `RECHARGE`，不要只信本地可能错误的 `deal_type`。
3. 历史脏数据兼容：退款前若识别为充值单，强制纠正 `dealType=RECHARGE` 再调支付。
4. 回归范围：必须覆盖「充值通道 ≠ 消费通道」门店：
   - 微信充值成功
   - POS 撤销充值
   - 应走充值通道退款成功
   - 本地 `refund_state`、CRM 余额、渠道资金三者一致

### 11.3 配置侧观察

即使代码修了，也建议盘点：

- 哪些门店配置了独立 `channelNoForRecharge`
- 这些门店历史移动支付充值单的 `dwd_apply_pay.deal_type` 是否大量为消费
- 是否存在“余额已撤、资金未退”的历史半成功单

## 12. 一句话结论

**根因已确认：在充值/消费支付通道分离的门店，本地把充值支付单记成消费类型，撤销退款走错支付通道，渠道查不到原单，POS 报「未查到数据」，导致会员撤销储值失败；并可能伴随 CRM 余额已回滚、微信未退款的半成功风险。**
