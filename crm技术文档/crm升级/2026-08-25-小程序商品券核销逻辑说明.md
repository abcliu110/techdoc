# 小程序商品券核销逻辑说明

## 一、先记住一句话

小程序商品券有两个动作：

```text
预核销 = 先检查这张券能不能用，并暂时记住券的信息
正式核销 = 用户真正提交订单时，把券消费掉
```

只要用户已经预核销了券，创建订单时就必须正式核销。预订单也遵循这个规则。

## 二、用户实际看到的流程

以用户使用一张“券抵扣指定菜品”为例：

```text
用户打开点餐页面
    ↓
用户选择菜品和商品券
    ↓
点击“使用券”
    ↓
系统预核销券
    ↓
用户确认并提交订单
    ↓
系统正式核销券
    ↓
订单保存成功，券完成消费
```

如果用户只选择了券但没有提交订单，券还没有完成正式消费；如果提交订单时正式核销失败，订单也不能成功创建。

## 三、第一步：预核销到底做什么

预核销的入口是：

```text
ShoppingCartController.preWriteOffCoupon
    ↓
ShoppingCartServicePlus.preWriteOffCoupon
```

系统主要做四件事：

1. 检查券是否存在、是否过期、是否属于当前用户或门店。
2. 检查券是否适用于当前菜品、规格和数量。
3. 向对应的外部系统查询或准备券。
4. 把后面正式核销需要的凭证保存在购物车商品行中。

预核销成功后，商品行会有类似下面的标记：

```text
preWriteOff = true
couponWriteOffTraceNo = 本次核销追踪号
```

平台券还会保存：

```text
verifyToken
encryptedCode
platformCertificateId
platformCount
```

这些信息是“正式核销时要使用的凭证”，不是最终消费结果。

## 四、第二步：用户提交订单时发生什么

创建订单的大致流程如下：

```text
收到创建订单请求
    ↓
读取购物车
    ↓
找出所有 preWriteOff=true 的商品券
    ↓
逐张执行正式核销
    ↓
所有券都成功后，保存订单
    ↓
把核销凭证写入订单商品
    ↓
订单创建成功
```

注意：正式核销发生在订单创建过程中。只要其中一张券正式核销失败，整个订单就应该失败。

## 五、三种券分别调用哪个接口

### 1. WP：CRM 会员券

```text
预核销：查询 CRM 券状态和适用菜品
正式核销：cardOpForCustomerFeign.writeOffCouponInner
反核销：cardOpForCustomerFeign.cancelWriteOffCouponInner
```

### 2. MP：美团/餐道平台券

```text
预核销：平台 prepare
正式核销：douYinCouponFeign.verify
反核销：douYinCouponFeign.cancel
```

调用 `verify` 时使用预核销保存的 `verifyToken` 和 `encryptedCode`。

### 3. DP：抖音平台券

```text
预核销：平台 prepare
正式核销：douYinCouponFeign.verify
反核销：douYinCouponFeign.cancel
```

MP 和 DP 使用同一个适配入口，但通过平台类型区分实际的美团/餐道或抖音业务。

## 六、为什么要保存核销记录

正式核销是远程接口调用，用户可能重复点击提交，或者网络超时后再次提交。系统用核销追踪号识别同一张券的一次核销请求：

```text
第一次请求：没有记录 → 申请处理 → 调用外部正式核销
外部成功：保存 SUCCESS
重复请求：发现 SUCCESS → 直接使用已有凭证，不再次调用外部接口
```

核销记录的业务唯一范围是：

```text
商户 mid + 门店 sid + 核销追踪号 traceNo
```

这样可以避免同一张券被重复正式核销。

## 七、订单保存失败时怎么办

外部核销和本地数据库不是同一个事务，所以可能出现：

```text
外部平台已经核销成功
    ↓
本地订单保存失败
```

系统需要检查订单最终是否存在：

```text
订单不存在
    ↓
调用反核销接口，把外部券恢复为可用

订单已经存在
    ↓
不能反核销，保留正式核销结果
```

反核销结果：

```text
反核销成功 → COMPENSATED
反核销失败 → CANCEL_UNKNOWN，等待恢复或人工处理
```

## 八、一个成功例子

```text
1. 用户选择菜品 A 和商品券。
2. 点击使用券，系统预核销成功，购物车记录 preWriteOff=true。
3. 用户提交订单。
4. 系统调用正式核销接口。
5. 正式核销成功。
6. 系统保存订单和券凭证。
7. POS 收到券号、撤销凭证和核销追踪号。
8. 订单成功，券已经消费。
```

## 九、一个失败例子

```text
1. 用户预核销成功。
2. 用户提交订单。
3. 外部平台正式核销成功。
4. 本地订单保存失败。
5. 系统发现订单不存在。
6. 系统调用反核销接口。
7. 反核销成功，券恢复可用，记录为 COMPENSATED。
```

如果第 6 步反核销失败，不能把它当作成功处理，必须记录为 `CANCEL_UNKNOWN`，后续继续恢复或人工核对。

## 十、事务边界：哪些能回滚，哪些不能回滚

这条链路不是一个数据库事务，而是多个微服务之间的远程调用。必须把“本地事务”和“外部调用”分开理解。

### 10.1 订单服务自己的本地事务

订单服务在创建订单时，会在自己的数据库事务中处理：

```text
计算订单金额
保存 order_bill
保存 order_food
保存商品券凭证
绑定核销记录和订单号
```

这些数据库操作如果抛出异常，可以由订单服务回滚。回滚后，本地订单和本地核销记录不会保留本次事务中的未提交数据。

### 10.2 CRM 和扫呗不在这个本地事务里

下面的调用属于跨微服务或第三方调用：

```text
订单服务 → CRM：writeOffCouponInner
订单服务 → 扫呗：verify
订单服务 → CRM：cancelWriteOffCouponInner
订单服务 → 扫呗：cancel
订单服务 → POS：同步核销凭证
```

这些系统有自己的数据库和事务。订单服务本地事务回滚时，不能自动回滚 CRM 或扫呗已经完成的正式核销。

例如：

```text
1. 扫呗 verify 返回成功。
2. 订单服务继续保存订单。
3. 订单数据库发生异常并回滚。
4. 扫呗的券仍然可能是“已核销”。
```

所以这里不能写成“订单事务回滚后券自动恢复”，实际必须再次调用扫呗 `cancel`，这叫事务外补偿。

### 10.3 核销记录的作用

核销记录不是用来把多个微服务强行放进一个事务，而是用来记录跨服务调用的事实和处理进度：

```text
INIT              尚未调用外部核销
CLAIMED           某个订单请求已经取得处理权
SUCCESS           外部核销成功，凭证已保存
COMPENSATED       订单失败后，反核销成功
CANCEL_UNKNOWN    反核销结果未知或明确失败，需要继续处理
```

状态更新本身在订单数据库事务中完成；外部接口成功或失败则通过状态和凭证落库，保证后续可以恢复、重试和审计。

### 10.4 不同微服务的职责

| 系统 | 负责内容 | 是否受订单数据库回滚影响 |
| --- | --- | --- |
| 小程序 | 发起预核销和创建订单请求 | 不直接参与事务 |
| order 服务 | 校验购物车、调用核销、保存订单、记录状态、执行补偿 | 只能回滚自己的数据库 |
| CRM 服务 | WP 会员券查询、正式核销、反核销 | 不受 order 本地回滚自动影响 |
| 扫呗适配服务 | MP/DP 的 prepare、verify、cancel | 不受 order 本地回滚自动影响 |
| POS | 接收正式核销凭证，执行线下后续取消/退菜 | 不受 order 本地回滚自动影响 |

### 10.5 事务处理原则

```text
先取得核销记录处理权
    ↓
调用外部正式核销
    ↓
把外部结果和凭证保存到本地
    ↓
保存订单并绑定核销记录
    ↓
如果本地事务失败，查询订单最终状态
    ↓
订单不存在：调用外部反核销
订单存在：保留正式核销结果
```

这是一种“本地事务 + 事务外补偿”的最终一致性模式，不是 CRM、扫呗、order 三方共享的分布式强一致事务。

## 十一、最终判断标准

一条完整、正确的核销链路必须满足：

```text
预核销成功
    → 创建订单时正式核销
    → 正式核销成功后才能创建订单
    → 订单保存失败时尝试反核销
    → 反核销失败必须留下明确的待处理记录
```

最重要的区别是：

```text
预核销不是最终消费
正式核销才是券真正被使用
```
