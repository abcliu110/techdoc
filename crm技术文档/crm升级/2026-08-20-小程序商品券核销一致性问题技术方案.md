## 1. 背景

小程序点餐支持商品券核销功能，分为预核销和正式核销两个阶段：

- **预核销**：用户扫码/选择券，系统校验有效性并获取平台凭证，券菜品写入购物车
- **正式核销**：用户送单（创建订单）时，调用 CRM 或平台接口完成券核销

当前实现存在分布式一致性问题，可能导致"券已核销、订单未创建"的不一致状态。

## 2. 问题分析

### 2.1 当前流程

```
@Transactional
public OrderBill crtOrder(...) {
    // 1. 计算订单（orderId 已分配）
    OrderBill calcOrder = calcOrderService.calc(...);

    // 2. 持久化订单
    iOrderBillService.save(calcOrder);

    // 3. 持久化菜品
    iOrderFoodService.saveBatch(calc.getFoodList());

    // 4. 正式核销 ← RPC 调用
    writeOffPreWriteOffCoupons(request, calcOrder, cart);

    // 5. 清空购物车
    redis.delete(key);
}
```

### 2.2 问题场景

| 场景 | 描述 | 结果 |
|------|------|------|
| A | CRM 核销成功，响应丢失 → 抛异常 → ROLLBACK | **券已核销，订单不存在** |
| B | CRM 核销失败，响应丢失 → 抛异常 → ROLLBACK | 一致（券未核销） |
| C | 部分券成功，部分失败 → 补偿部分成功部分失败 | 券状态混乱 |
| D | POS 接单时凭证回写失败 → toOrder 回滚 | 券已核销，订单未创建 |

### 2.3 根本原因分析

```
时序分析：

T1: calcOrder.lid = "xxx" (内存中已分配)
T2: INSERT order → 数据库中有 order "xxx"（事务未提交）
T3: INSERT food
T4: INSERT taste
T5: RPC writeOffCouponInner(orderId="xxx") → CRM 成功，响应丢失
T6: throw → ROLLBACK → 数据库回滚，order "xxx" 不存在

问题：
- 订单在数据库中存在过（T2 INSERT 成功）
- 但事务回滚后不存在了
- CRM 无法验证 orderId 是否最终提交成功
```

**核心矛盾**：

| 实体 | 状态 |
|------|------|
| 本地事务 | INSERT 成功 → ROLLBACK → 订单不存在 |
| CRM | 核销成功 → 永久生效 |

### 2.4 修正：为什么 `saasOrderKey` 幂等不成立

```
方案 A 假设：CRM 用 orderId 做幂等，能识别"已核销"
实际情况：

T5: CRM 收到 writeOff(orderId="xxx") → 核销成功
T6: 本地 ROLLBACK → order "xxx" 不存在
T7: 补偿时调用 cancelWriteOff(orderId="xxx")
    CRM: 查询 orderId="xxx" → 不存在！
    CRM: 拒绝取消（订单不存在，无法确认归属）
```

当前 `crt_order` 每次送单都会重新生成 `saasOrderKey`。因此，重试同一购物车时，CRM、餐道或平台适配层收到的是不同订单号，无法识别为同一次券核销。问题不在于“订单号是否存在”，而在于核销操作键没有跨重试保持不变。

预核销阶段已经为每张券生成 `couponWriteOffTraceNo`，并随券菜品保存到购物车 Redis。该值比 `saasOrderKey` 更适合作为券核销操作键：它在下单前生成、每张券独立、重试时可复用，并且可以在订单事务回滚后仍定位原核销操作。

**结论**：不能再用每次送单生成的 `saasOrderKey` 作为商品券幂等键。应使用预核销生成的 `couponWriteOffTraceNo`，并把状态和第三方返回的反核销凭证写回原购物车 key 中对应的券菜品行。外部平台是否按该键返回原始结果，必须通过接口契约或沙箱验证；在未验证前，不得把“券已核销”当成可恢复成功。

## 3. 解决方案（V1.5）

### 3.1 推荐方案：原购物车券行状态 + 本地 trace 关联 + 当前请求补偿

本方案不修改前端，不修改购物车 Redis key，不把正式核销改成异步，也不要求预创建订单。核心是把预核销生成的 `couponWriteOffTraceNo` 作为本地券核销尝试的稳定关联键，并把状态和凭证写回现有购物车对象中的券菜品行。只有外部平台明确承诺按该键幂等重放或提供可验证查询时，才把它作为外部请求幂等键；未确认前，不能把同一 trace 重试视为安全。Redis 保存跨请求状态；方法内变量只保存本次送单已经成功的券，用于当前请求的异常补偿。

#### 3.1.1 `traceNo` 的定义、值和生命周期

本文的 `traceNo` 是字段 `couponWriteOffTraceNo` 的简称，不是链路追踪 ID，也不是订单号。它表示“某一张已加入购物车的商品券，从预核销到正式核销/取消核销的唯一业务流水号”。

| 项目 | 明确定义 |
|------|----------|
| **生成时机** | 预核销成功、创建券菜品行时生成一次 |
| **生成代码** | `CartProductCouponService` 调用 `IdWorkerPlus.getIdStr()`，赋值给 `OrderFoodVO.couponWriteOffTraceNo` |
| **值是什么** | `IdWorkerPlus.getIdStr()` 返回的 ID 字符串；它是系统生成的唯一流水值，不包含券码、用户、门店或订单号等业务含义。运行时实际值以该次调用返回值为准，不能由前端传入或由送单时重新计算 |
| **粒度** | 一张券菜品行一个值；同一购物车有多张券时，每张券各有自己的 `traceNo` |
| **存储位置** | 预核销后随 `OrderFoodVO` 写入现有购物车 Redis key；正式核销成功后仍写回同一购物车 key 的同一券菜品行 |
| **复用范围** | 用户因超时、网络中断或订单事务回滚再次送同一购物车时，必须读取原券菜品行中的同一个值；只有删除该券后重新预核销加入，才生成新的值 |
| **与订单号的区别** | `order.saasOrderKey` 是每次送单新建的订单操作键；`traceNo` 在同一张预核销券的重复送单中不变，可作为本地跨重试关联键；是否可作为外部幂等键必须由平台契约确认 |

示例：预核销券 A 时生成 `traceNo = "<IdWorkerPlus.getIdStr() 返回值>"`。第一次和第二次送单都必须传递该值；只有 CRM、扫呗或其他平台已确认支持按该值幂等重放时，第二次才允许用同一值重试。未确认前，第二次送单先查外部状态；无法确认归属时阻断，不能盲目再次核销，也不能改用第二次产生的 `saasOrderKey`。

#### 3.1.2 购物车券行状态和当前结构

购物车 key 和 `ShoppingCartVO` 顶层结构保持不变：

```text
ORDER_SERVICE:ShoppingCart:{sid}:{tblId}[:{openId}]
└─ ShoppingCartVO.foodList[]
   └─ OrderFoodVO（预核销券菜品）
      ├─ couponWriteOffTraceNo
      ├─ preWriteOff = true
      ├─ preWriteOffBusinessType = WP / MP / DP
      ├─ encryptedCode、verifyToken、platformCertificateId 等预核销凭证
      ├─ couponWriteOffStatus = INIT / SUCCESS / FAILED（新增可选字段）
      ├─ platformWriteOffId（SUCCESS 时保存反核销凭证）
      ├─ couponWriteOffFailureCode
      └─ couponWriteOffFailureMessage
```

状态含义：

```text
INIT       已预核销，尚未完成正式核销；或反核销已确认成功
SUCCESS    正式核销成功，platformWriteOffId 等反核销凭证已写入购物车
FAILED     本次结果明确失败，或结果未知；必须保存失败类别和原因
```

`couponBusinessType`、券码、`mid`、`sid` 作为券行数据和请求校验字段保存，不改变既有购物车 key。状态不增加名为 `PROCESSING` 的持久化状态；并发控制必须使用覆盖整个远程调用窗口的可续租购物车锁，并在锁内按最新券行版本/CAS 复核 `traceNo`、状态和消费尝试标识；若锁续租或版本校验失败，必须停止外部调用或将结果判为未知，不能依赖固定短租约。

#### 3.1.3 送单处理和内存补偿清单

方法内仍保留一个仅限本次请求的最小补偿清单，记录已经收到外部成功响应的 `traceNo`、券号、券类型和反核销凭证。它不是跨请求状态，不能替代购物车 Redis；Redis 是跨重试的状态来源。

每张券按以下顺序处理：

```text
新建订单前先按归属键查询已提交 order_food/订单；命中则返回已有订单或拒绝重复送单
读取购物车券行
  ├─ SUCCESS + 券行归属字段及 platformWriteOffId 完整且匹配
  │          → 确认是本购物车的成功记录，直接跳过正式核销
  ├─ SUCCESS 但归属字段或 platformWriteOffId 缺失/不匹配
  │          → 状态异常，阻断送单，不能直接跳过或再次核销
  ├─ INIT/FAILED → 先校验购物车范围和外部返回券身份，再按 couponNo 查询外部券状态
  │    ├─ INIT 或 failureClass=RETRYABLE_BUSINESS_FAILURE + 明确可用 → 使用 couponWriteOffTraceNo 发起正式核销
  │    ├─ FAILED(UNKNOWN) + 明确可用 → 仍禁止盲目 use；只有平台已确认同 trace 重放/查询契约时才允许继续
  │    ├─ 明确已核销且能关联本地稳定键/成功记录 → 补齐/确认 SUCCESS，跳过正式核销
  │    ├─ 明确已核销但无法证明属于本地记录 → 标记 FAILED(OWNERSHIP_UNCONFIRMED)，阻断送单
  │    └─ 查询失败/状态未知 → 标记 FAILED(UNKNOWN)，阻断送单，不能盲目重核销

外部核销成功
  → 把当前结果加入本次请求补偿清单
  → 立即修改购物车券行：SUCCESS + platformWriteOffId
  → 写回原购物车 key，并重新读取校验 traceNo、状态和凭证
  → 校验成功后才继续下一张券
```

后续券失败或订单事务异常时，反核销范围由“消费尝试 + 已提交订单绑定”共同决定：本次送单新核销成功且尚未绑定已提交订单的券必须补偿；历史 `SUCCESS` 券如果没有任何已提交订单绑定，也必须纳入可恢复补偿范围；已经绑定已提交订单的消费完成券不得因另一笔订单失败而反核销。不能把购物车中所有历史 `SUCCESS` 券全量反核销。补偿前必须再次校验 `mid + sid + channelType + couponNo + couponWriteOffTraceNo`、当前购物车范围、`attemptId` 和已提交订单绑定。反核销明确成功后，把该券行恢复为 `INIT` 并清除旧反核销凭证；反核销失败或结果未知时保留 `SUCCESS`、记录取消失败信息并阻断后续送单，不能把它伪装成 `INIT`。

`FAILED` 必须保留 `failureClass`，至少区分 `RETRYABLE_BUSINESS_FAILURE`、`UNKNOWN`、`OWNERSHIP_UNCONFIRMED` 和 `CANCEL_FAILED`。只有明确可重试的业务失败才允许重新查询后调用 `use`；`UNKNOWN`、`OWNERSHIP_UNCONFIRMED` 和 `CANCEL_FAILED` 禁止自动再次核销，只能通过外部查询、对账或人工确认解除。

#### 3.1.4 Redis 读写异常处理

Redis 写操作和外部核销不是原子操作，必须按结果分类：

| 场景 | 处理 |
|---|---|
| 外部核销前读取购物车失败 | 不调用外部核销，返回重试错误 |
| 成功后写回返回明确失败 | 使用当前调用中的反核销凭证重试写入，再回读校验 |
| 写回超时/连接断开 | 不能直接反核销；先回读，回读到 `SUCCESS` 则视为已写成功 |
| 回读到原状态 `INIT` | 只有在锁内确认版本/消费尝试未被并发覆盖，才能认定成功结果未保存并使用当前凭证反核销；无法确认是否被并发覆盖时，结果保持未知，阻断并告警 |
| 回读持续失败 | 阻断后续核销；不能当作 `INIT` 重试，告警并等待 Redis/平台查询恢复 |
| 后续券失败但 Redis 不可读 | 本次清单只能反核销本次已确认成功券；禁止继续提交/核销，不能假设没有其他成功券，待 Redis 恢复后合并核对并告警 |
| Redis 与外部查询均不可用 | 结果未知，禁止继续下单或再次核销，转人工处理 |

当前外部响应中的 `verifyId`/`ticketTransId` 在 Redis 写入和校验完成前必须保留在方法局部变量中；这不是持久化状态，而是避免“外部已成功、Redis 未确认”时失去反核销凭证的必要上下文。但 Redis 不可读时，内存清单不能替代历史 `SUCCESS`，不能据此宣称补偿闭环。

#### 3.1.5 券状态查询与本地归属判定

外部查询返回“有数据”不等于本订单已经核销。必须把“券当前已核销”和“本购物车/本订单已核销”分成两个判断：

```text
本地归属键 = mid + sid + channelType + couponNo + couponWriteOffTraceNo
本地成功证据 = 同一归属键下的 SUCCESS + platformWriteOffId（verifyId/ticketTransId 等）+ 可恢复的 attemptId/外部成功记录
```

送单前的查询判定规则如下：

| 本地券行 | 外部查询结果 | 处理 | 是否允许再次 use |
|---|---|---|---|
| `SUCCESS`，归属键匹配、`platformWriteOffId` 和可恢复 attempt 记录完整 | 无需再次查询 | 复用本地成功结果，写入本次 `order_food`，跳过核销；随后建立新的已提交订单绑定 | 否 |
| `SUCCESS`，归属键或凭证缺失/不匹配 | 任意 | 状态异常，阻断并告警，保留原始数据 | 否 |
| `INIT` 或 `FAILED(RETRYABLE_BUSINESS_FAILURE)` | `use_status = 1`（可用） | 使用稳定 `couponWriteOffTraceNo` 正式核销 | 是，仅一次 |
| `FAILED(UNKNOWN/OWNERSHIP_UNCONFIRMED/CANCEL_FAILED)` | `use_status = 1`（可用） | 仍阻断，先通过平台同键查询/重放契约、对账或人工确认 | 否 |
| `INIT` 或 `FAILED(RETRYABLE_BUSINESS_FAILURE)` | `use_status = 3`（已核销），且平台返回原稳定键/商户订单关联字段 | 补齐本地 `SUCCESS` 和完整凭证，跳过核销 | 否 |
| `INIT` 或任意 `FAILED` | `use_status = 3`，但只有券号/已核销状态，或仅返回一个无法关联的新 `verifyId` | 写入 `FAILED(OWNERSHIP_UNCONFIRMED)`，阻断送单并转人工/对账 | 否 |
| `INIT` 或任意 `FAILED` | 查询异常、券不存在、状态不明确 | 写入对应失败原因；结果未知时阻断 | 否 |

其中，`mid`、`sid`、门店/终端、券类型、券号、实际购物车范围（`tblId`/`openId`）和 `couponWriteOffTraceNo` 必须交叉校验；它们只能证明本地购物车中的目标券，不能单独证明外部核销归属。只有本地已保存的成功凭证，或外部查询明确返回原 `couponWriteOffTraceNo`/`extOrderId`/商户订单关联字段，才能把“已核销”认定为“本订单已核销”。外部仅返回一个新的 `verifyId` 不能单独证明归属。

扫呗当前查询响应的 `use_status` 只能用于判断券可用/已核销；查询结果还必须校验返回的商户、门店/终端、渠道和券号与本地券行一致。如果响应不返回原核销凭证或可关联的稳定键，不能因为查询成功或返回券数据就直接标记 `SUCCESS`，也不能在 `use_status = 3` 时再次调用 `use`。

#### 3.1.6 删除券、清空购物车和订单异常

删除操作必须区分消费完成和用户删除：

```text
用户删除单张券或清空含券菜品
  → 读取购物车并加锁
  → 对 SUCCESS 券先执行反核销
  → 反核销全部明确成功后，才从 foodList 删除或删除购物车 key
  → 反核销失败/未知：保留券行和凭证，不删除

订单创建成功
  → 提交前先按 `couponWriteOffTraceNo`（并校验 `mid/sid/channelType/couponNo`）查询已提交的 `order_food`/订单
  → 已存在已提交订单：返回已有订单或拒绝重复送单，不再次建单，也不反核销
  → 不存在已提交订单且本次订单提交成功：视为消费完成；本地事务提交后再删除购物车，不反核销

订单事务异常或后续券失败
  → 仍反核销本次已成功券
  → 成功后将券行恢复 INIT，订单事务回滚
```

当前 `/clear`、`/clearAll` 和数量减为零的删除路径存在直接删菜/删 key 行为，实施时必须接入上述反核销前置检查。所有购物车读改写、核销、反核销和删除入口必须共用同一可续租锁，并在锁内按 `foodLid + couponWriteOffTraceNo` 基于最新对象更新；如无法提供锁内版本/CAS 校验，不能使用旧快照覆盖 Redis。回写必须保留原 key 的剩余 TTL，不能因写入 `SUCCESS` 意外续期或清除 TTL。key 已过期或不存在时，禁止凭内存对象重建购物车券行或继续核销。订单提交成功但 Redis 清空失败时，必须依靠上述已提交订单闸门，避免残留 `SUCCESS` 被下一次送单复用或被用户删除时误反核销；清空动作只能在本地事务提交后执行，删除失败需告警并由已提交订单闸门保证重复送单安全。Redis 自然 TTL 到期不会触发业务回调；若 key 已自然过期，系统无法再从购物车读取凭证，因此“过期自动反核销”不属于本方案可保证能力，必须作为明确遗留风险记录。

#### 3.1.7 三类外部接口的键与字段

| 实际路径 | 正式核销请求键 | 成功返回凭证 | 取消核销使用 | 当前代码结论 |
|---|---|---|---|---|
| CRM 会员券（WP） | `CrmCouponWriteOffDTO.orderId` 使用 `couponWriteOffTraceNo` | CRM 券记录的核销状态/`orderBillId` | 同一 traceNo + 券号 | CRM 源码按相同 `orderBillId` 允许重复请求 |
| 美团经餐道/扫呗 | 扫呗 `trace_no` 使用 `couponWriteOffTraceNo` | `verify_results[].origin_code` | `verify_id`（扫呗 `canceluse` 的券凭证） | 当前 `trace_no` 每次随机生成，必须改为稳定传入；需确认重复请求返回原凭证 |
| 抖音经扫呗 | 扫呗 `trace_no` 使用 `couponWriteOffTraceNo` | `verify_results[].origin_code` | `verify_id` | 当前巨焦分支未使用 `extOrderId`，只能依赖扫呗 trace 或本地状态 |
| 餐道直连旧路径 | `WriteOffCouponDTO.extOrderId` 使用 `couponWriteOffTraceNo` | `preferential[].ticketTransId` | `ticketTransId` + 券码 | 代码存在该字段透传，但当前被 `if (true)` 分支绕过 |
| 抖音官方直连 | 当前请求只有 `verify_token`、`encrypted_codes`、`poi_id` | 官方返回的 `verify_id`/取消令牌 | `verify_id`、`certificate_id`、`cancel_token` | 当前代码没有外部业务幂等键或按键查询能力 |

`verify_token` 是 `prepare` 返回的会话令牌，`certificate_id`/`encrypted_code` 是券身份和核销输入，`verify_id`/`ticketTransId` 是核销成功后的取消凭证；这些字段不能混同为事前幂等键。

对于 `count > 1` 的券，`couponWriteOffTraceNo` 的粒度必须在实现前确定：若外部平台按一次请求核销整批数量，则一个 trace 对应一个核销批次，并保存已成功数量和完整取消凭证；若平台按券张核销，则每张券必须拆成独立券行/独立 trace。不能只保存一个券号和一个布尔 `SUCCESS`，否则部分成功无法精确补偿。

#### 3.1.8 外部查询与重试前提

必须向扫呗、餐道和抖音确认以下契约，并以沙箱重复请求验证：相同商户、门店/终端和 `trace_no`（或 `extOrderId`）重复提交，是否返回同一笔结果及同一个取消凭证；是否提供按该键查询接口；幂等记录有效期是多少。

即使查询接口能返回券详情，也只能说明“券存在/券当前状态可查询”。若只返回“券已核销”而不返回原 `verify_id`、`ticketTransId` 或可关联本地稳定键的字段，则不能自动恢复为本地 `SUCCESS`，必须写入 `FAILED(OWNERSHIP_UNCONFIRMED)` 并转对账/人工处理；禁止再次盲调核销。只有取得可验证的归属证据后，才允许补齐本地成功记录并跳过正式核销。

### 3.3 备选方案 A：预创建订单 + CRM 状态校验

**【核心改进】**：不在事务内核销，而是预创建订单，CRM 校验订单状态后再核销。

**思路**：
1. 预创建订单（状态 = PRE_CREATED），**立即提交**
2. CRM 核销前，先查询订单状态
3. 订单状态 = PRE_CREATED → 允许核销，状态更新 = WRITING_OFF
4. 核销成功后，状态更新 = CONFIRMED
5. 核销失败时，状态更新 = FAILED，释放订单

**数据库改造**：

```sql

-- 券核销状态：NONE(无券), PRE_CREATED(预创建), WRITING_OFF(核销中), CONFIRMED(已确认), FAILED(失败)
```

**流程图**：

```
用户点击送单
    ↓
① 创建订单（状态=PRE_CREATED）→ 立即提交 ✓
    ↓
② 调用 CRM 核销
    ↓
  ┌─ 成功 → ③ 更新状态=CONFIRMED
  │              ↓
  │          ④ 返回成功给用户
  │
  └─ 失败 → ③ 更新状态=FAILED → ④ 返回失败给用户
                ↓

```

### 3.4 不推荐方案 B：本地消息表 + 异步最终一致

> 本方案不满足“下单成功的前提是全部券核销成功”的当前业务要求，只能作为外部平台不提供幂等查询时的异常兜底，不能作为主流程解决方案。异步确认不能把订单提交前的核销结果变成同步确定结果。

**【针对"补偿失败"问题的改进】**

**核心思路**：
1. 不追求实时一致，接受小概率不一致
2. 核销成功后，持久化核销记录
3. 事务提交后，异步确认核销状态
4. 补偿失败时，**不重试无限次**，而是**记录异常 + 告警 + 对账**

```java
public void handleWriteOffResult(WriteOffResult result, OrderBill order, Coupon coupon) {
    if (result.isSuccess()) {
        // 核销成功：保存记录
        saveWriteOffRecord(order.getOrderId(), coupon.getCouponNo(), result.getWriteOffId());
        return;
    }

    // 核销失败（明确失败）
    if (result.isDefinitiveFailure()) {
        // 业务失败（券不存在、已使用等）：直接抛异常，事务回滚
        throw new BizException("核销失败：" + result.getMessage());
    }

    // 网络异常/超时：记录异常，进入补偿流程
    if (result.isNetworkError()) {
        // ⚠️ 关键：这里不立即补偿，而是记录异常
        // 因为无法区分"已成功但响应丢失"和"失败"
        saveWriteOffException(order.getOrderId(), coupon.getCouponNo(),
            "UNKNOWN", "核销结果未知，等待异步确认");

        // 异步任务：定时查询 CRM 券状态
        scheduleConfirmTask(order.getOrderId(), coupon.getCouponNo());
    }
}
```

```java
public void confirmWriteOffStatus() {
    // 1. 查询待确认的异常记录
    List<WriteOffException> exceptions = findPendingExceptions();

    for (WriteOffException ex : exceptions) {
        try {
            // 2. 查询 CRM 券状态
            CrmCouponStatus status = crmService.queryCouponStatus(ex.getCouponNo());

            if (status.isUsed()) {
                // CRM 显示已核销：更新记录为成功
                updateRecordSuccess(ex.getOrderId(), ex.getCouponNo());
                deleteException(ex.getId());
            } else {

                retryWriteOff(ex.getOrderId(), ex.getCouponNo());

    }
}
```

```java
public void retryWriteOff(String orderId, String couponNo) {
    WriteOffResult result = crmService.writeOff(orderId, couponNo);

    if (result.isSuccess()) {
        updateRecordSuccess(orderId, couponNo);
        deleteException(findException(orderId, couponNo).getId());
        return;
    }

    // 重新核销也失败
    if (result.isDefinitiveFailure()) {
        // 明确失败：更新异常记录，标记为需要人工处理
        updateExceptionResolution(orderId, couponNo, "NEED_MANUAL");
        sendAlert("核销异常需要人工处理", orderId, couponNo);
        return;
    }

    // 网络错误：继续等待下次调度
}
```

# V1.5 多角色对抗性评审

本节以当前 V1.5 推荐方案为准，结论优先于前面的历史评审记录。评审目标不是证明方案可行，而是主动寻找“外部券已成功、订单未成功、凭证或状态再次丢失”以及“误把其他订单已核销认成本订单成功”的反例。

## 角色一：订单架构师

**结论：主因修复有效，但必须扩大补偿边界。**

- 部分已解决：本地状态和补偿不再依赖每次送单新生成的 `saasOrderKey`，同一购物车券可以用稳定 `couponWriteOffTraceNo` 重试和定位；外部平台是否接受同一 trace 幂等重放仍待契约确认，未确认时不能宣称外部重复核销已解决。
- 已解决：每张券成功后立即回写购物车，后续请求可以读取 `SUCCESS` 和反核销凭证。
- P0 未解决：当前正式核销之后还会继续执行清空购物车、免赠处理等逻辑；如果这些后置逻辑再次抛异常，现有补偿只覆盖正式核销方法内部，不能覆盖整个订单事务后半段。实现必须保证“第一次外部成功到事务提交前”的所有异常都进入同一补偿边界。
- P0 未解决：订单成功前不能删除购物车；只有订单事务确定成功后才允许清空，否则必须保留券行和状态。

## 角色二：Redis 与并发工程师

**结论：状态放回原购物车合理，但写回必须是锁内的读改写并校验。**

- 已解决：不改变历史购物车 key 和 `ShoppingCartVO` 顶层结构，避免破坏既有客户端和清理逻辑。
- P0 未解决：现有订单/购物车锁使用固定约 15 秒租约；远程核销、反核销和 Redis 重试可能超过租约，锁提前释放后会出现两个送单同时核销同一券。实现必须改为可续租看门狗锁，或证明租约覆盖最坏时延并在超时前续租。
- P0 未解决：回写不能直接把旧的完整购物车快照覆盖 Redis。必须在锁内按 `foodLid + couponWriteOffTraceNo` 定位券行，写入后回读校验状态和凭证，避免覆盖其他合法购物车变更。
- P1 未解决：Redis 自然 TTL 到期不会触发反核销；到期后券凭证丢失，方案不能保证自动恢复，必须在上线说明中保留该遗留风险。

## 角色三：外部平台对抗者

**结论：稳定键目前尚未真正到达扫呗，方案在适配层改完前不成立。**

- 直接事实：本次订单侧已把正式 `verify/cancel` 的 `extOrderId` 改为购物车券行的稳定 trace；扫呗适配层是否继续随机生成 `trace_no` 仍需单独核对，因此订单侧修复不等于外部幂等已成立。
- P0 待确认：正式 verify 和 cancel 必须在适配层真正透传调用方的 `couponWriteOffTraceNo`；prepare/query 仍可继续使用随机请求流水号，不能混用。

# V1.7 多角色对抗性复审与修订结论

本节是对本文前述方案和 V1.6 实施后评审的权威修订。评审对象仍为 `D:\mywork\nms4cloud-order` 的 `jujiao_master` 分支，代码作者范围限定为 Git 历史中 `guoyun_liu` 的提交；工作区当前对 `CrtPostOrderServiceImpl.java` 的未提交 trace 替换只能作为待评审变更，不能反向归因给 `guoyun_liu`。除非特别注明，以下“当前代码”均指实际源码，而非方案伪代码。

## 1. 评审判定规则

- **直接事实**：由源码、Git 提交、分支差异或测试结果直接证明；文档不得把推断写成事实。
- **设计能力**：方案要求未来实现具备的行为；不能写成“已修复”。
- **当前实现**：已经存在于代码中的行为；没有 Redis 状态字段、持久化补偿或自动化测试时，必须明确标记为未实现。
- **上线阻断条件**：任一 P0 未满足时，只能称为“有条件可行”，不能宣称已解决券与订单的一致性问题。

## 2. 六角色复审

### 2.1 订单架构与事务角色

**结论：稳定 trace 修复正确，但事务补偿边界和成功绑定尚未闭环。**

- 订单侧把正式核销、反核销的外部关联参数改为 `couponWriteOffTraceNo`，修复了每次送单重新生成 `saasOrderKey` 导致跨重试无法定位的问题。
- 当前正式核销成功后仍可能执行购物车删除、免赠处理或其他后置逻辑；后置异常发生在事务提交前时，必须进入同一个补偿边界，否则仍会出现券已核销、订单回滚。
- 第一次送单回滚后遗留的 `SUCCESS` 券，下一次送单不能只依赖“是否本次请求成功”决定是否反核销。必须记录该券是否已经绑定**已提交订单**；没有已提交订单的历史 `SUCCESS` 在再次送单失败时仍必须按可补偿券处理，否则会遗留无订单的已核销券。
- 订单重复提交闸门必须原子化：`查询不存在 → 创建订单`不是幂等保证。应以 `mid + sid + channelType + couponWriteOffTraceNo`（必要时加券号/购物车范围）建立数据库唯一约束或原子占位记录，冲突时返回已提交订单或明确拒绝，不得创建两笔订单。

### 2.2 Redis、并发与故障角色

**结论：三状态模型可以保留，但当前实现没有状态持久化和可靠崩溃恢复。**

- `INIT/SUCCESS/FAILED` 足够表达业务状态，不增加持久化 `PROCESSING`；并发由可续租锁、锁内最新读和 CAS/版本校验保证。
- 当前约 15 秒固定租约不能覆盖远程核销、反核销和 Redis 重试的最坏时延；锁过期后两个请求可能并发调用外部核销。上线前必须使用可续租锁，或证明租约覆盖上界并在到期前续租。
- 外部核销成功、Redis 写回前进程崩溃时，方法内变量和内存补偿清单都会丢失。仅靠“外部成功后写 Redis”不能覆盖该窗口；必须先有可恢复的持久化尝试记录/订单占位，或采用外部可查询且可证明归属的契约。否则该场景必须标记 `FAILED(UNKNOWN)` 并阻断，不能宣称自动补偿。
- Redis 写回必须是原 key 下的锁内读改写，按 `foodLid + couponWriteOffTraceNo` 更新并回读校验，保留原 TTL；禁止旧购物车快照覆盖并发修改。

### 2.3 外部平台与适配层角色

**结论：订单服务传递稳定 trace 不等于扫呗真正使用稳定 trace。**

- 必须逐层证明订单服务 → 微信适配层 → 扫呗/餐道/抖音请求的 `trace_no`/`extOrderId` 没有被重新随机生成；适配层若仍调用 `IdWorkerPlus.get32UUID()` 覆盖流水号，订单侧改动对外部幂等无效。
- 必须以平台返回的核销记录中的原始关联字段作为归属证据。请求回显的 trace、新生成的 `verifyId`、券号、门店或 `use_status=3` 单独都不能证明是本订单核销。
- 同一 trace 重试是否返回第一次结果和同一反核销凭证、幂等有效期、按 trace 查询能力，必须由接口契约和沙箱重复请求共同确认；没有确认时，超时结果只能 `FAILED(UNKNOWN)`、阻断后续 `use` 并转对账/人工。
- 外部业务错误可能嵌套在 `extra.error_code` 等字段；适配层和订单侧必须统一解析外层 HTTP/结果状态与内层业务状态，避免把明确失败误判成“凭证缺失”或未知成功。

### 2.4 业务与用户操作角色

**结论：删除前反核销方向正确，但必须覆盖所有删除入口。**

- 单券减为零、单券删除、`/clear`、`/clearAll` 和任何清空购物车任务，在删除含 `SUCCESS` 券的行或 key 前必须先反核销；反核销失败或结果未知时保留券行和凭证，不得直接删除。
- 订单已提交但购物车清空失败时，后续删除入口必须先命中“已提交订单”闸门，确认消费完成后只清理残留，不得反核销已消费券。
- Redis 自然 TTL 到期、运维直接删 key 没有业务回调，无法保证自动反核销；该风险必须作为上线遗留项，不得写成已解决。

### 2.5 测试与回归角色

**结论：方案场景覆盖较全，但缺少实现证据的用例不能算通过。**

上线前至少必须有以下可重复用例：

1. 外部成功后 Redis 写入成功、写入明确失败、写入超时后三种回读分支。
2. 外部成功后进程崩溃/响应丢失，恢复后能查询并证明本地归属，或进入 UNKNOWN 阻断。
3. 多券部分成功、后置事务异常，所有本次消费尝试成功券均被精确补偿；已绑定已提交订单的历史 `SUCCESS` 不被误反核销，无订单绑定的历史 `SUCCESS` 可被精确恢复和补偿。
4. 两个并发送单请求只能产生一笔已提交订单；唯一约束冲突能返回已有订单。
5. 固定租约超过 15 秒的远程调用不会发生并发重复核销。
6. 本地 `SUCCESS` 的 `mid/sid/channelType/couponNo/traceNo` 任一不匹配时阻断；外部仅返回 `use_status=3` 或新 `verifyId` 时写入 `OWNERSHIP_UNCONFIRMED`。
7. `count > 1` 或批量核销部分成功时，按逐券或批次保存成功数量和逐券取消凭证，补偿结果可精确核对。

### 2.6 安全与数据完整性角色

**结论：归属校验必须是后端不可伪造的行级约束。**

- `SUCCESS`、`FAILED`、失败原因和平台凭证不得由前端提交或覆盖；状态变更只能由后端核销、反核销和恢复流程产生。
- `mid`、`sid`、门店/终端、渠道、券类型、券号、`foodLid`、购物车范围和 trace 必须交叉校验；trace 全局唯一不能替代租户/门店隔离。
- `verifyId`、`ticketTransId`、`certificateId`、`encryptedCode` 等凭证只允许脱敏日志；不得把完整请求/响应写入日志或评审文档。
- 反核销失败或未知时必须保留 `SUCCESS` 和可取消凭证，记录 `CANCEL_FAILED`，告警并阻断；不能重置 `INIT` 以制造“可再次核销”的假象。

## 3. 必须补充的状态与字段定义

方案中的“消费尝试标识”此前未定义，现明确如下：`attemptId` 是一次送单对一张券的后端生成标识，仅用于把本次外部核销成功、Redis 状态写回、订单 `order_food` 和补偿记录关联起来；它不是外部平台幂等键，也不是 `saasOrderKey`。`attemptId` 必须在外部调用前持久化到可恢复记录中，并在成功绑定已提交订单后标记完成。进程崩溃恢复时只能按 `attemptId` 和稳定 trace 找到本次尝试；找不到时不得把历史 `SUCCESS` 自动归入新订单。

`SUCCESS` 的状态完整性必须同时满足：

```text
mid + sid + channelType + couponNo + couponWriteOffTraceNo + foodLid
+ platformWriteOffId + attemptId
```

并且存在可恢复的本地外部成功记录（该 `attemptId` 已保存外部成功响应和取消凭证）。已提交订单绑定是“消费完成/允许清理购物车”的独立条件，不是第一次核销成功写入 `SUCCESS` 的前置条件；订单尚未提交时，后续重试仍可复用这份本地成功记录，但再次失败时必须能够按无已提交订单状态补偿。对于从外部查询恢复的结果，还必须由平台记录返回原稳定 trace/商户订单关联字段，才能建立本地归属；只有券号、门店、`use_status=3`、请求回显 trace 或一个新 `verifyId`，都不足以构成外部归属证据。

对于 `count > 1`，实现必须二选一并在接口契约中固定：

- **逐券模式**：每张券行一个 `couponWriteOffTraceNo`、一个 `attemptId` 和一个取消凭证；或
- **批次模式**：一个 trace 对应一个明确批次，保存成功数量、失败数量和每张已成功券的取消凭证。

禁止用一个券号、一个 trace 和一个布尔 `SUCCESS` 表示部分成功。

## 4. 最终上线判定

当前结论为：**订单服务侧稳定 trace 参数修改是必要且方向正确的局部修复；整体方案仍为有条件可行，当前不能宣称完全解决。**

以下任一项未完成，发布必须阻断：

| P0 阻断项 | 验收证据 |
|---|---|
| 适配层真实透传稳定 trace | 请求日志/Mock 断言证明扫呗正式 verify/cancel 使用传入 trace，未重新生成 |
| 外部同键重放或按键查询契约 | 沙箱重复请求返回同一结果/凭证，或查询返回原稳定键 |
| 崩溃窗口可恢复 | 进程在外部成功与 Redis 写回之间终止，恢复后能证明归属并补齐，或稳定进入 UNKNOWN 阻断 |
| Redis 状态和凭证持久化 | 每券成功立即写原购物车 key，回读校验，失败保留可恢复记录 |
| 历史 SUCCESS 与已提交订单绑定 | 数据库唯一约束/原子占位和冲突回归测试 |
| 锁续租与版本校验 | 远程调用超过 15 秒仍无并发重复核销，旧快照不能覆盖新状态 |
| 全删除入口与事务补偿 | 后置异常、减零、clear、clearAll 的自动化回归全部通过 |
| 批量券精确补偿 | 部分成功可逐张核对、逐张取消，不多取消/漏取消 |
| 已核销归属证据 | 仅有券号/状态/新凭证时阻断；只有原 trace 或本地成功凭证才跳过 use |

在以上证据完成前，文档和评审报告必须使用“未闭环”“上线阻断”措辞；不得使用“已解决重复核销”“已保证最终一致”等绝对表述。
