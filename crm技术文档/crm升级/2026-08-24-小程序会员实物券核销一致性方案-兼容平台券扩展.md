# 小程序会员实物券核销一致性方案（兼容平台券扩展）

**文档版本**：V1.0  
**创建日期**：2026-08-24  
**适用项目**：`nms4cloud-order`  
**当前实施范围**：CRM 会员商品券（`WP`）  
**明确不实施**：美团/餐道商品券（`MP`）、抖音商品券（`DP`）

> 本文是独立方案，不修改或替代《2026-08-21-小程序商品券核销一致性方案V2-核销前置》。旧文档保留作为历史方案和平台券分析参考。

## 1. 目标与边界

当前只解决会员实物券在小程序送单过程中的一致性问题：

```text
预核销取得 couponWriteOffTraceNo
  → 送单前正式核销 CRM 会员券
  → 订单事务创建订单
  → 订单事务失败时反核销
```

本方案不改变前端、不修改现有购物车 Redis key，也不实现美团、餐道、抖音的 `prepare/verify/cancel` 逻辑。

以下券类型不得进入本方案：

- `MP`：美团/餐道商品券
- `DP`：抖音商品券
- `WV`、`MV`、`DV`：现金券

遇到非 `WP` 类型时，应明确拒绝进入会员券新流程，避免误用 CRM 核销和反核销接口。平台券继续沿用原有流程，待单独完成适配器和契约确认后再接入。

## 2. 会员券现有事实

会员商品券类型为 `WP`。其正式核销和反核销均使用 CRM 接口：

- 正式核销：`couponNo + mid + sid + couponWriteOffTraceNo`，其中 `couponWriteOffTraceNo` 作为 CRM `orderId`。
- 反核销：使用同一 `couponWriteOffTraceNo` 和 `couponNo`。
- 不使用 `platformCount`、`verify_id`、平台 `certificate_id` 或平台撤销凭证。

`couponWriteOffTraceNo` 必须在预核销阶段生成并写入购物车，送单重试时保持不变；不得改用每次新建的 `saasOrderKey`。

## 3. 处理时序

正式核销必须位于完整 `preHandle` 返回之后、`crtOrder` 事务之前：

```text
完整 preHandle（后付和先付的全部校验完成）
  → 按 traceNo 原子认领核销记录
  → WP 已 SUCCESS：复用记录，跳过 CRM 重复核销
  → WP 为 INIT：调用 CRM 核销并独立事务记录 SUCCESS
  → 任一券失败：反核销本批次已成功券，订单不创建
  → 全部成功：进入 crtOrder 事务
  → calc 结果按 traceNo 回填核销信息
  → 保存订单和 order_food
  → crtOrder 失败：事务外按记录反核销
```

`crtOrder` 通过 Spring 代理调用，确保订单事务已回滚后，外层才能执行反核销。`postHandle` 失败不反核销已提交订单，只进入告警和重试处理。

### 3.1 通用接口钩子

前置核销采用 `CrtOrderService` 通用生命周期钩子。接口默认 `handle()` 的调用边界调整为：

```text
preHandle()
  → beforeCreateOrder()（默认空实现）
  → 通过 Spring 代理调用 crtOrder()
  → crtOrder 异常时调用 afterCreateOrderFailure()（默认空实现）
  → postHandle()
```

`CrtPostOrderServiceImpl` 实现 `beforeCreateOrder()`，只处理 WP 的记录认领和 CRM 正式核销；同时实现 `afterCreateOrderFailure()`，按独立记录执行事务外反核销。`CrtPreOrderServiceImpl` 继承这两个钩子，因此会在自己的完整 `preHandle()`（包括折扣和校验）返回后才核销。

`beforeCreateOrder()` 与 `afterCreateOrderFailure()` 必须在 `CrtOrderService` 中提供默认空实现，使离线、取餐及其他订单实现保持原有行为。异常捕获范围只包围代理调用的 `crtOrder()`，不能把 `postHandle()` 放入补偿范围；订单已经提交后，`postHandle()` 失败不得反核销。

## 4. 通用核销记录表

表结构一次性兼容 `WP/MP/DP`，但当前只写入和处理 `WP`。

### 4.1 主表 `coupon_write_off_record`

主表按一张预核销券一条记录，负责状态、幂等、认领和订单绑定：

| 字段 | 用途 |
|---|---|
| `trace_no` | 本地稳定幂等键，唯一索引 |
| `coupon_business_type` | `WP/MP/DP` |
| `provider` | `CRM/CAN_DAO/DOU_YIN` |
| `mid`、`sid` | 商户和门店范围 |
| `coupon_no` | WP 使用；平台券可为空 |
| `platform_certificate_id` | 平台券预留，WP 为空 |
| `platform_count` | 平台券数量预留，WP 可为空或 1 |
| `status` | `INIT/SUCCESS/FAILED` |
| `order_saas_order_key` | 订单成功后的绑定值，可空 |
| `claim_owner`、`claim_expire_time`、`version` | 并发认领和乐观条件更新 |
| `request_snapshot` | 脱敏或加密的外部请求摘要 |
| `last_error`、`retry_count` | 恢复和对账 |

WP 的唯一业务判断键是 `trace_no`；记录状态为 `SUCCESS` 时禁止再次调用 CRM 正式核销。

### 4.2 明细表 `coupon_write_off_record_detail`

明细表现在建好，当前 WP 每条主记录写一条 CRM 明细；未来平台券返回多个外部凭证时，每个凭证一条明细：

| 字段 | 用途 |
|---|---|
| `record_id`、`trace_no` | 关联主记录 |
| `verify_id` | MP/DP 预留，WP 为空 |
| `certificate_id` | 平台凭证预留，WP 为空 |
| `external_write_off_id` | 外部核销凭证 |
| `success_count`、`cancel_count` | 逐凭证数量 |
| `detail_status` | 明细核销/反核销状态 |
| `credential_json` | 平台特有凭证扩展，敏感内容加密 |
| `response_sequence` | 保留外部响应顺序 |

不能把未来多个 `verify_id` 拼成一个字符串，也不能用主表总数量对每个凭证重复反核销。

## 5. 当前 WP 实施要求

### 5.0 客人自助核销单品券完整场景

客人自助点单时，会员单品券（`WP`）按以下顺序处理：

1. 客人选择单品券后先执行预核销；预核销校验失败时直接返回错误，不能把券菜加入购物车。
2. 预核销成功后写入购物车，核销单品券菜必须与普通菜保持独立行，后续数量合并不得跨越核券标识。
3. 客人送单前，服务端逐张处理购物车中的所有 `WP` 券，业务上视为本批次批量核销。
4. 所有券核销成功后才允许继续创建订单；任何一张券核销明确失败或结果无法确认，都必须阻止送单。
5. 失败响应必须明确指出券号，固定提示为：`券XXXX核销失败，请删除此菜品!`，其中 `XXXX` 为失败券号；失败券菜由客人主动从购物车删除。
6. 本批次中在失败前已经核销成功的其他券，必须全部执行反核销；订单不创建，普通菜不删除。

1. 通过 `CrtOrderService.beforeCreateOrder()`，在完整 `preHandle` 后只处理 `WP`。
2. 核销记录的 `INIT → SUCCESS`、反核销结果更新使用独立事务。CRM 调用异常时，使用同一 `mid + sid + couponNo` 查询券状态：`YHX` 且 `orderBillId=traceNo` 记为本次成功；`WHX` 才记为 `FAILED`；查询仍失败时本次送单立即失败并返回“券{couponNo}核销失败，请删除此菜品!”，记录保持 `INIT` 供留痕，前端不得继续提交该券菜。
3. `calc()` 会重新创建 `OrderFood`，不能依赖购物车对象引用；必须按 `couponWriteOffTraceNo` 从记录表读取结果并回填 `calc` 结果后再保存。
4. 订单事务失败后，按记录中的 `couponNo + traceNo` 执行 CRM 反核销；失败或结果未知保持 `SUCCESS` 并记录错误，供恢复任务处理。
5. 订单提交成功后绑定 `order_saas_order_key`；购物车清理不作为核销成功依据。
6. `CrtOrderService` 仅增加默认空钩子和失败钩子，不改变其他实现的默认业务行为；不修改 MP/DP 既有接口调用。
7. 购物车读取时对 `WP` 预核销行进行 CRM 有效性重校验：CRM 返回失败、无数据、查不到券、调用异常或购物车缺少 `mid/sid`，均视为券已不可确认有效并移除该核券行；不得保守保留异常券行，避免继续下单。
8. WP 正式核销不在订单模块额外增加券号锁。CRM 通过 `couponNo + WHX` 条件更新券状态并校验更新行数，保证同一张券只有一个不同 `orderId` 的请求成功；并发失败由当前订单请求按核销失败处理。

### 5.1 核券菜与普通菜必须分行

小程序购物车和订单行必须与 POS 的 `DwdFood.couponLid/couponNo` 语义对齐：核券菜是独立业务行，不能因为菜品和单位相同而与普通菜合并。

合并规则固定为：

| 已有行 | 新增行 | 处理 |
|---|---|---|
| 普通菜 | 普通菜，菜品和单位相同 | 按原规则合并数量 |
| 普通菜 | WP 核券菜 | 新增独立行 |
| WP 核券菜 | 普通菜 | 新增独立行 |
| WP 核券菜 | WP 核券菜 | 新增独立行；不同券号不得合并 |

判断核券行必须使用 `preWriteOff=true`，不能只比较 `foodNo`、`foodUnit` 或菜品名称。核券行必须保留 `couponNo`、`productCouponBusinessType=WP` 和 `couponWriteOffTraceNo`；普通菜的 `couponNo` 必须为空。

例如同一菜品同时购买普通份和会员券份，订单及 POS 接收数据必须保持为两行：

```text
菜品 A  数量 1  普通菜
菜品 A  数量 1  WP 会员券核销
```

不能合并为一行后再尝试通过数量或金额推断其中哪一份使用了会员券。POS 端会依据核券标识单独计算优惠、服务费、退菜和反核销，因此上游合并会破坏券与菜品的对应关系。

## 6. 平台券扩展设计

未来接入 MP/DP 时，新增类型适配器，不改订单一致性主流程：

```text
CouponWriteOffAdapter
  ├─ CRMAdapter（当前实现，仅 WP）
  ├─ CanDaoAdapter（未来 MP）
  └─ DouYinAdapter（未来 DP）
```

适配器至少提供：

- `writeOff`：正式核销
- `cancel`：按明细凭证反核销
- `query`：超时或 `INIT` 状态查询
- `supportsIdempotentRetry`：声明是否支持同 `trace_no` 重放

平台券接入前必须单独确认：稳定 trace 是否真正透传、重复核销返回规则、查询接口、多个 `verify_id` 与数量关系、逐凭证撤销规则。未确认时，超时结果只能保持未知并阻断自动重试，不能套用 WP 规则。

## 7. 验收范围

当前只验收：

- WP 核销成功并创建订单
- WP 已 SUCCESS 重试不重复核销
- 多张 WP 部分失败时已成功券反核销
- WP 核销成功但订单事务回滚时反核销
- 反核销失败可持久化并恢复
- `MP/DP/WV/MV/DV` 不进入新 WP 流程
- 同一菜品的普通行与 WP 核券行保持分行，两个不同 WP 券行也不合并

平台券的接口契约、`verify_id` 数量映射和平台恢复测试列入后续独立需求，不作为本次上线前提。

## 8. 结论

本方案以会员实物券为唯一当前实现范围，采用稳定 `couponWriteOffTraceNo` 和独立核销记录解决订单回滚导致的 CRM 核销不一致；数据库从第一版即兼容平台券的多凭证模型，但平台券业务实现、接口契约和恢复策略后续单独评审、单独上线。
