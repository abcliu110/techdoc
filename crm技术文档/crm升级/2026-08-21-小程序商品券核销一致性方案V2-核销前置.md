**历史版本**：本文替代 2026-08-20 版技术方案（V1.7），V1.7 保留作历史参考

## 1. 背景

小程序点餐支持商品券核销，分为预核销和正式核销两个阶段：

- **预核销**：用户扫码/选择券，系统校验券有效性并获取平台凭证，券菜品写入购物车（`CartProductCouponService`，不调用正式核销接口）
- **正式核销**：用户送单（创建订单）时，调用 CRM 或平台接口完成券核销

V1.7 方案在"正式核销位于订单事务内"的前提下，用购物车券行状态、补偿、外部查询等大量机制做事后修补。经源码分析确认，**根本矛盾在于"把不可控的远程调用嵌进了必须支持回滚的本地事务"**——只要核销在事务内，本地回滚就必然丢外部成果，任何状态写回都只能降低概率、不能根除。

本文档采用**改变调用时序**的方案：把正式核销从订单事务中前置到订单创建之前，并用独立核销事实记录与恢复任务降低“券已核销、订单回滚或进程崩溃后订单消失”的不一致风险。

## 2. 问题分析

### 2.1 当前时序（源码实证）

`CrtPostOrderServiceImpl.crtOrder` 是 `@Transactional` 方法（`CrtPostOrderServiceImpl.java:184`）：

```
@Transactional
crtOrder() {
    calc 计算订单                                            ← 本地
    iOrderBillService.save(calcOrder)                       ← ① INSERT order
    iOrderFoodService.saveBatch(foodList)                   ← ② INSERT food
    iOrderTasteService.saveBatch(tasteList)                 ← ③ INSERT taste
    writeOffPreWriteOffCoupons(request, calcOrder, cart)    ← ④ 远程核销(在事务内)
    redisSecTemplatePlus.delete(key)                        ← ⑤ 清空购物车
    iOrderFreeFoodRecordService.saveBatch(freeFoodRecords)  ← ⑥ 免赠
}
```

### 2.2 核心矛盾

| 实体 | 行为 |
|------|------|
| 本地事务 | ①~③ INSERT 成功 → 事务异常 ROLLBACK → 订单/菜品消失 |
| 外部系统（CRM/扫呗/餐道/抖音） | ④ 核销成功 → 永久生效，不可回滚 |

时序 T2 事务回滚时，数据库的 INSERT 被回滚，但 CRM/平台的券核销状态无法回滚，产生"券已核销、订单不存在"的不一致。这**不是并发或某次失败的偶发问题，而是该时序下每次回滚都会出现的结构性矛盾**。

### 2.3 调用链全景（核销可插入的位置）

```
OrderBillController.crtOrder()             HTTP 入口 /crt_order          ← A
  └─ OrderBillServicePlus.crtOrder()       业务校验 + 加 Redisson 锁     ← B（锁 tryLock(10,15s)）
      └─ crtOrderInner()                   读购物车 Redis               ← C
          └─ CrtOrderService.handle()                                    ← D（接口默认方法）
              ├─ preHandle()               检查桌台/菜品/免赠，生成 saasOrderKey  ← E
              ├─ crtOrder()  @Transactional                          ← F
              │    ├─ calc / INSERT / 远程核销 / 清购物车 / 免赠
              └─ postHandle()              发 MQTT
```

核销放置位置的候选与取舍见第 4 节。

## 3. 解决方案：核销前置到完整 `preHandle` 后

### 3.1 总体思路

**把正式核销从 `crtOrder`（事务内）前置到完整 `preHandle` 返回后（事务外）**，核销事实由独立记录表承载，`crtOrder` 只负责本地落库与凭证回填。不能将正式核销直接追加到 `CrtPostOrderServiceImpl.preHandle()`，因为先付实现会先调用父类 `preHandle()`，后续子类折扣/校验尚未完成。

```
CrtPostOrderServiceImpl.handle() {
    preHandle(request, cart)                 // 完整动态分派
        └─ 后付：基础校验
        └─ 先付：基础校验 + 子类折扣/校验
    claimAndWriteOffBeforeCreateOrder(request, cart) // 后付类覆盖 handle 后调用，事务外正式核销
        └─ 全部成功 → 凭证写入独立核销记录
        └─ 任一失败 → 反核销已成功券，抛异常（订单未创建）
    crtOrder(request, cart, ctx)   @Transactional
        └─ calc → 回填凭证 → INSERT → 免赠
    事务提交成功后清空购物车
    postHandle(request, order, ctx)
}
```

### 3.2 为什么放在完整 `preHandle` 后

**时机最合适，改动最小**：

| 候选位置 | 在锁内 | 在事务内 | 能拿到购物车券行 | 改动文件数 |
|---------|:------:|:-------:|:---------------:|:----------:|
| A Controller | ❌ | ❌ | ❌（未读购物车） | 2 |
| B 锁之前 | ❌ | ❌ | 需提前读购物车 | 2 |
| C crtOrderInner 读车后 | ✅ | ❌ | ✅ | 2 |
| E 父类 `preHandle` 内 | ✅ | ❌ | ✅ | ❌ 先付子类后续逻辑尚未完成 |
| **E' 完整 `preHandle` 返回后** | ✅ | ❌ | ✅ | **后付实现覆盖 `handle`** |
| F crtOrder 内 | ✅ | ✅ | ✅ | 0（不动即现状） |

完整 `preHandle` 返回后仍在锁内、事务外，并且先付子类的折扣/校验已经结束。此时才允许正式核销。前置核销、凭证回填和订单事务失败补偿集中在 `CrtPostOrderServiceImpl`，核销凭证统一从独立记录表读取，不扩展 `CrtOrderContext`。

### 3.3 改动点

#### 改动 1：在后付实现覆盖 `handle`，在完整校验后正式核销

```java
public OrderBill handle(CrtOrderDTO request, ShoppingCartVO cart) {
    CrtOrderContext context = preHandle(request, cart);
    claimAndWriteOffBeforeCreateOrder(request, cart); // 完整 preHandle 后，事务外
    OrderBill order;
    try {
        CrtOrderService proxy = SpringUtil.getBean(this.getClass());
        order = proxy.crtOrder(request, cart, context);
    } catch (Exception cause) {
        compensateAfterCreateOrderFailure(request, cart, cause);
        throw cause;
    }
    postHandle(request, order, context);
    return order;
}
```

只在 `CrtPostOrderServiceImpl` 覆盖 `handle()`，不修改通用 `CrtOrderService` 接口。`CrtPreOrderServiceImpl` 继承该 `handle()`，其中的 `preHandle()` 仍是动态分派：会先执行 `super.preHandle()`，再执行先付子类的折扣/校验，之后才调用 `claimAndWriteOffBeforeCreateOrder()`；因此先付与后付都核销。离线、取餐等实现继续使用接口默认 `handle()`，不受影响。核销成功凭证和待补偿清单从独立核销记录表查询，不放入 `CrtOrderContext`。

覆盖后的 `CrtPostOrderServiceImpl.handle()` 异常边界必须是：

```text
context = preHandle(...)
claimAndWriteOffBeforeCreateOrder(...)
try {
  order = proxy.crtOrder(..., context)
} catch (Exception cause) {
  compensateAfterCreateOrderFailure(..., cause)
  throw cause
}
postHandle(...)
```

因此只有 `crtOrder()` 异常触发事务外补偿；`postHandle()` 异常只走消息告警/重试，不得反核销。

#### 改动 2：整批认领并执行前置核销

**本改动处理整批券的认领和核销**：先对本次购物车中全部预核销券执行原子认领，再按每条记录状态决定是否调用外部核销。它不负责处理后续订单创建失败；后者由改动 6 处理。

- 整批认领必须全部成功；任一记录认领失败，立即停止，不调用任何未认领券的外部接口
- 无记录：独立事务写入 `INIT`，写入失败立即阻断
- `INIT`：先按稳定 trace 查询外部或同键重放，结果未知时阻断
- `SUCCESS`：直接复用记录中的外部凭证，禁止再次正式核销
- `FAILED`：只有外部契约允许同 trace 重试时才重试，否则要求重新预核销生成新 trace
- 任一券正式核销失败：反核销本批次已经成功的明细，成功后记录 `FAILED`，失败/未知保持 `SUCCESS`
- 批次内失败后，覆盖后的 `handle()` 不执行 `crtOrder`，订单不会创建

`claimAndWriteOffBeforeCreateOrder` 中核销的代码结构：

```java
private void claimAndWriteOffBeforeCreateOrder(CrtOrderDTO request, ShoppingCartVO cart) {
    
    // 新增：远程核销（无事务）
    List<OrderFoodVO> preWriteOffFoods = cart.getFoodList().stream()
        .filter(f -> Boolean.TRUE.equals(f.getPreWriteOff())).toList();
    // 先原子认领本批次全部记录，再按状态决定是否调用外部接口
    claimAllRecordsOrThrow(preWriteOffFoods);
    for (OrderFoodVO food : preWriteOffFoods) {
      try {
        writeOrReuseCouponWriteOff(request, food);
      } catch (Exception e) {
        log.error("预核销券正式核销失败: couponNo={}, traceNo={}, error={}",
            food.getCouponNo(), food.getCouponWriteOffTraceNo(), e.getMessage());
        // ① 按核销记录明细反核销本批次已成功券
        compensateWrittenOffProductCouponsByTrace(request, cart, e);
        // ② 补偿完成后再向外抛出，handle() 不会执行 crtOrder，订单不创建
        throw new BizException(
            String.format("商品券核销失败[%s]: %s", food.getFoodName(), e.getMessage()));
      }
    }
}
```

这样可以保证“券 A 成功、券 B 失败”时订单不会创建，并避免把该场景误认为订单事务失败。核销成功信息已在独立表中持久化，事务外补偿和 `crtOrder` 的凭证回填均按 trace 查询该表，因此不需要修改 `CrtOrderContext` 或暴露实现类私有类型。

#### 改动 3：凭证回填 `calc` 结果后落库（不能依赖对象引用）

`writeOffSinglePreWriteOffCoupon` 核销成功后，可以把凭证暂存到传入的购物车 `OrderFoodVO`，但这不能直接保证数据库落库。源码中的 `CalcGenericOrderServiceImpl.calc()` 会新建 `List<OrderFood>`，并通过 `BeanUtilsPlus.mapBean()` 将 `OrderFoodVO` 映射为新的 `OrderFood`；因此购物车对象与 `order_food` 对象不是同一引用。

```java
// claimAndWriteOffBeforeCreateOrder 核销成功后，结果写入 coupon_write_off_record
recordService.markSuccessByTrace(...);
```

`crtOrder` 调用 `calc()` 后，必须在 `saveBatch()` 前按稳定键 `couponWriteOffTraceNo` 从核销记录表读取外部凭证，回填到 `calc.getFoodList()` 对应的 `OrderFood`，至少包括 `platformWriteOffId`、平台凭证及反核销所需字段。回填不到唯一订单菜品时必须阻断落库并对已成功券执行反核销。这里仅恢复“凭证写入本地订单”的步骤，不把远程核销重新放回数据库事务。

#### 改动 4：`crtOrder` 移除远程核销调用

`crtOrder` 删除 `writeOffPreWriteOffCoupons(request, calcOrder, cart)` 这一行；购物车删除移到订单事务成功提交后的独立步骤；calc、INSERT、免赠逻辑保持不变。

#### 改动 5：删除不再需要的旧回写方法

- `writeOffPreWriteOffCoupons`（改写成只核销不写库的版本）
- `persistProductCouponWriteOffSuccesses`（凭证已在 INSERT 时写入）

**一个技术细节**：旧的 `persistProductCouponWriteOffSuccesses` 依赖已生成订单的 `lid` 做回写，不能直接搬到前置核销阶段，因为此时订单尚未落库。V2 应将回填放在 `calc()` 之后、`saveBatch()` 之前，使用 `couponWriteOffTraceNo` 从核销记录表读取并关联，而不是依赖订单主键；不得以“购物车对象与落库对象同一引用”为依据删除该落库步骤。

#### 改动 6：订单创建失败时在事务外补偿

“所有券核销成功，但订单创建失败”与“核销批次内部失败”是两个不同异常场景，必须分开处理：

```text
claimAndWriteOffBeforeCreateOrder 成功完成全部远程核销
  → 通过 Spring 代理调用 @Transactional crtOrder
  → crtOrder 抛异常并完成事务回滚
  → handle 的 catch 按核销记录逐明细反核销
  → 保留并重新抛出原始下单异常
```

实现要求：

- `crtOrder()` 必须通过 Spring 代理调用，确保进入 `catch` 时事务已经回滚；不得使用 `this.crtOrder()` 绕过代理。
- `catch` 只包围 `crtOrder()`，不能把 `postHandle()` 放入同一补偿范围；订单已提交后 `postHandle()` 失败不得反核销。
- 反核销异常不能覆盖原始下单异常；每张券都要尝试，并记录反核销失败或结果未知。
- 核销记录表必须保存 `couponWriteOffTraceNo`、平台核销凭证、反核销凭证、券号、券类型、门店和商户信息，供事务外补偿使用。
- `claimAndWriteOffBeforeCreateOrder()` 自己处理批次内失败，不能再由外层重复补偿同一批次。

该改动需要在 `CrtPostOrderServiceImpl` 覆盖 `handle()` 并新增其内部前置核销/补偿方法；不修改通用 `CrtOrderService.handle()`。

### 3.4 改动范围汇总

| 文件 | 改动 |
|------|------|
| 核销记录实体、Mapper、Service、迁移脚本 | 新增 `coupon_write_off_record` 与唯一 trace 索引；提供独立事务状态变更和恢复查询 |
| `handler/CrtOrderService.java` | 不修改（通用接口默认流程保持不变） |
| `c/order/CrtPostOrderServiceImpl.java` | 覆盖 `handle`，在完整 `preHandle` 后正式核销；`crtOrder` 异常后事务外补偿；删远程核销调用；按 trace 回填 calc 结果后再保存；订单成功后绑定记录；删旧回写方法 |
| 恢复任务 | 扫描 `INIT` 与未绑定订单的 `SUCCESS`，查询外部/补绑定/反核销并告警 |

改动 2 只负责批次内失败；改动 6 负责订单创建失败。核销记录表同时供 `crtOrder` 回填和事务外补偿使用。

**不涉及**：前端、既有购物车 Redis key、通用 `CrtOrderService` 默认 `handle()`、其他实现中的商品券业务逻辑。新增核销记录表及恢复任务是覆盖进程崩溃窗口的必要范围。`CrtPostOrderServiceImpl` 覆盖的 `handle()` 由其 `CrtPreOrderServiceImpl` 子类继承；仍须回归先付、后付、离线和取餐等全部创建订单实现，确认非继承链实现行为未变。

### 3.5 源码结论：`calc()` 不复用原 `food` 对象引用

**实现约束**：前置核销凭证不能依赖购物车对象引用，必须从独立核销记录表读取后回填 `calc()` 产生的 `OrderFood`。

当前调用：

```java
// crtOrder 中（CrtPostOrderServiceImpl.java:191-193）
CalcOrderVo calc = calcOrderService.calc(
    new CalcOrderDTO()
        .setOrder(cart.getOrder())
        .setFoodList(cart.getFoodList()));
```

源码已确认 `CalcGenericOrderServiceImpl.calc()` 新建 `OrderFood` 列表，并通过 `BeanUtilsPlus.mapBean()` 从 `OrderFoodVO` 创建新的 `OrderFood`。因此前置核销不能只修改购物车对象；必须执行“核销记录表 → `calc()` 返回结果 → 按 `couponWriteOffTraceNo` 回填 → `saveBatch`”。回填完成前不得执行订单菜品保存。

## 4. 遗留风险与处理

### 4.1 锁租约 15 秒仍覆盖核销（方案 A 取舍）

完整 `preHandle` 和 `claimAndWriteOffBeforeCreateOrder` 均在锁内（`OrderBillServicePlus.crtOrder` L735 加锁，`tryLock(10,15s)`）。远程核销仍被锁覆盖，锁提前释放后并发请求可能重复核销。

**取舍**：前置核销仍位于现有锁内，锁租约不足时必须由核销记录的唯一 trace 和外部平台同键重放/查询共同兜底。若平台不支持幂等，仅靠锁续租（即使续到 1 小时）也无法消除“核销中途锁释放、第二请求再次核销”（详见 4.6）。并发重复核销的最终防线是“外部平台按键幂等 + 二次查询确认”，不能仅依赖锁租约。

### 4.2 核销成功、订单创建失败 → 反核销（依赖远程）

核销成功后，`crtOrder` 若抛异常（计算、DB 异常、免赠处理失败或事务提交失败等），必须由改动 6 在事务外按核销记录逐明细反核销。购物车删除改为事务提交后的独立步骤；删除失败不反核销，只告警并重试。改动 2 只处理前置核销内部“前一张成功、后一张失败”的批次失败，不能覆盖本场景。

仍需明确的边界：
1. 反核销本身是远程调用（`cancelWrittenOffProductCoupon`），可能超时、失败或结果未知
2. 反核销失败/未知时，券处于"已核销但订单未创建"状态，需持久化载体供人工对账（见 4.5）
3. 批次内失败时，反核销成功后 `preHandle` 抛异常，购物车中券菜品仍保留（未写回 `INIT`），用户可重试送单；订单事务失败时则由外层补偿完成后返回原始下单错误

### 4.3 进程崩溃窗口：使用独立核销事实表恢复（P0）

核销成功 → 订单 INSERT 前，若进程崩溃/容器重启/网络断开：

- 外部券已核销
- 订单尚未创建
- 当前请求上下文可能丢失，但核销事实应已持久化到 `coupon_write_off_record`
- 购物车 Redis 无 `SUCCESS` 状态（本方案不写回）
- 无持久化核销记录

为覆盖该窗口，本方案采用独立核销事实表 `coupon_write_off_record`，不复用购物车 Redis key，也不依赖订单事务。该表记录“外部券核销事实”，订单尚未创建时也必须存在；它不是订单表的附属数据。

#### 4.3.1 独立记录与状态

每张券以 `trace_no` 为唯一键，状态只有三种：

| 状态 | 含义 | 可否再次正式核销 |
|------|------|------------------|
| `INIT` | 已准备或外部结果未知；不能假定外部未核销 | 否，必须先查询/同键重放确认 |
| `SUCCESS` | 已确认外部正式核销成功，已保存撤销凭证 | 否，复用凭证继续下单或反核销 |
| `FAILED` | 已确认未核销，或已经成功反核销 | 需按外部平台契约决定；未确认前禁止用同一 trace 再次核销 |

反核销失败或结果未知时不得写为 `FAILED`，应保持 `SUCCESS` 并记录 `last_error`，等待恢复任务重试。

表字段至少包括：`trace_no`（唯一索引）、`mid`、`sid`、`food_lid`、购物车标识/版本、`coupon_no`、`original_coupon_code`、`coupon_type`、`write_off_count`、`status`、`platform_certificate_id`、`platform_write_off_id`、必要且脱敏或加密保存的外部请求快照、`order_saas_order_key`（可空）、`claim_owner`、`claim_expire_time`、`last_error`、`version`、`created_time`、`updated_time`。

平台请求快照必须能支持 `INIT` 状态的外部查询或同键重放：MP/DP 至少保存 `verifyToken`、`encryptedCode`、`platformCount`、价格、渠道和平台原券标识；不得假设平台券一定存在 `couponNo`。敏感凭证按现有数据安全规范加密/脱敏存储，日志不得输出完整快照。

批量券不得只保存总 `write_off_count` 和一个聚合 `platform_write_off_id`。一条正式核销响应中可能包含多个 `verify_id`，必须用子表 `coupon_write_off_record_detail`（或等价 JSON 明细字段）逐项保存 `verify_id`、凭证标识、成功数量、取消数量、明细状态和原始响应中的关联顺序；写入 `SUCCESS` 前校验所有明细成功数量之和等于请求数量。反核销与恢复任务按明细、按对应数量执行并校验累计结果，任一明细未知则保持 `SUCCESS`，禁止按总数量对每个 `verify_id` 重复取消。

`trace_no` 唯一索引只能防止重复插入，不能防止“用户重试”和恢复任务同时消费同一条 `SUCCESS`。继续创建订单或反核销前，必须通过条件更新原子认领记录：仅当状态为预期状态且 `claim_expire_time` 已过期时写入本次 `claim_owner` 与租约；未认领成功的一方读取最新状态并返回/等待。订单提交成功后仅允许认领方以条件更新绑定订单；恢复任务只能处理租约过期的记录。禁止只靠现有 15 秒购物车锁或乐观锁读取后再写。

这里的主表明确为新增的 `coupon_write_off_record`，不是 `order_bill`、`order_food`，也不是现有购物车 Redis key。`claim_owner`、`claim_expire_time`、`version` 都位于该表，用于用户重试、订单创建和恢复任务之间的原子认领。认领示例：

```sql
UPDATE coupon_write_off_record
SET claim_owner = :owner,
    claim_expire_time = :expireTime,
    version = version + 1
WHERE trace_no = :traceNo
  AND status = 'SUCCESS'
  AND order_saas_order_key IS NULL
  AND (claim_owner IS NULL OR claim_expire_time < CURRENT_TIMESTAMP)
  AND version = :oldVersion;
```

只有更新行数为 `1` 的执行者获得认领权，才能继续复用凭证创建订单或执行恢复反核销；更新行数为 `0` 时必须停止当前操作并读取最新记录，禁止继续调用外部核销/反核销。`INIT` 的创建、`INIT → SUCCESS`、`SUCCESS → FAILED` 也必须使用状态和 `version` 条件更新，防止旧请求覆盖恢复任务结果。

批量券的逐凭证明细存放在新增的 `coupon_write_off_record_detail` 表（或经评审批准的等价明细结构），通过 `record_id/trace_no` 关联主表。明细至少保存 `verify_id`、平台凭证标识、实际核销数量、已撤销数量、明细状态和响应顺序；只有主表与全部明细原子写入完成后，主表才允许进入 `SUCCESS`。主表负责状态、订单绑定和认领，明细表负责逐凭证反核销，不能用主表总数量对每个 `verify_id` 重复取消。

#### 4.3.2 正常送单时序

```text
每张预核销券取得稳定 couponWriteOffTraceNo
  → 原子认领整批记录
  → 无记录：独立事务写入 INIT；SUCCESS：复用凭证跳过 verify；INIT：先查询/同键重放确认
  → 独立事务更新 SUCCESS + 核销/撤销凭证
  → 订单事务创建订单并保存 order_food
  → 同一订单事务内以认领方条件更新绑定 traceNo 与 saasOrderKey
  → 订单提交成功后绑定与订单同时可见
  → 订单事务失败：事务外逐张反核销
       ├─ 成功：独立事务更新 FAILED
       └─ 失败/未知：保持 SUCCESS + last_error，交恢复任务
```

`INIT` 必须在外部调用前写入，覆盖“外部成功、进程崩溃、来不及写 SUCCESS”的窗口。`INIT` 创建、`SUCCESS` 写入、`FAILED` 写入必须在独立 Spring Bean 中用 `Propagation.REQUIRES_NEW` 执行，不能放入 `crtOrder()` 的订单事务；但成功订单与 `order_saas_order_key` 的绑定必须参与订单事务，保证订单提交时绑定同时生效。若订单提交后在绑定前进程崩溃，恢复任务仍需以 `order_food` 严格反查补绑。

#### 4.3.3 重入与崩溃恢复

再次送单或恢复任务按购物车中的 `traceNo` 查询记录：

| 查询结果 | 处理 |
|----------|------|
| 无记录 | 新建 `INIT` 后正式核销 |
| `FAILED` | 外部契约确认“撤销后同 trace 可再次核销”才允许重试；否则重新预核销生成新 trace，并保留旧记录关联 |
| `INIT` | 使用券号、门店、数量和 trace 查询外部或同键重放；结果未知则阻断送单并告警 |
| `SUCCESS` 且未绑定订单 | 先原子认领，再按 trace 查询 `order_food` 是否已有已提交订单；有则补绑定并返回订单，无则逐项校验购物车行与记录的门店、券类型、原券标识、数量和凭证一致，校验通过才复用已保存凭证继续创建订单 |
| `SUCCESS` 且已绑定订单 | 直接返回已绑定订单，禁止重复送单 |

恢复任务定期扫描 `INIT` 与“`SUCCESS` 但未绑定订单”的记录：前者查询外部并补写最终状态；后者只处理未被正常送单认领、且超过最小观察期的记录。任务必须先原子认领，再查询订单绑定；未找到订单时需在观察期后再次确认认领仍有效和订单仍不存在，才按已保存凭证反核销。反核销成功才更新为 `FAILED`。外部平台不支持按 trace 查询或同键重放时，`INIT` 必须保持未知并阻断，转人工处理。

### 4.4 适配层 trace 透传

订单侧已把 `verify/cancel` 的 `extOrderId` 改为 `couponWriteOffTraceNo`（`0bc8db8`）。仍需确认扫呗/餐道适配层未重新生成 `trace_no`；prepare 阶段的随机流水号不得与正式核销幂等键混用。

### 4.5 反核销失败持久化（P0）

`coupon_write_off_record` 作为反核销失败的持久化载体，不再使用”只写日志”或可选异常表。反核销失败/未知时保持 `SUCCESS`，更新 `last_error`、更新时间和重试次数；人工对账时依据该记录处理。

订单创建成功后，将 `order_saas_order_key` 绑定到记录；绑定失败由恢复任务根据 `order_food.couponWriteOffTraceNo` 补齐。

### 4.6 外部平台幂等契约（不可控前提）

本方案同样依赖外部平台是否支持"用稳定 `traceNo` 幂等重放或按键查询"：

- CRM（WP）：源码按相同 `orderId`（现已是 `traceNo`）允许重复请求，已确认
- 扫呗/餐道/抖音（MP/DP）：需确认正式 `verify/cancel` 是否真正透传 `traceNo`，以及相同 trace 重试是否返回原凭证/查询接口

未确认前，超时结果只能标记 `UNKNOWN` 并阻断/转人工，不能宣称自动恢复。锁租约、崩溃窗口、重复核销能否收敛，最终都受限于此契约。

## 5. 与 V1.7 方案对比

| 维度 | V1.7 推荐方案（购物车券行状态 + trace 关联） | V2（核销前置） |
|------|--------------------------------------------|----------------|
| 面对的问题 | 核销已在事务内，如何修补不一致 | 核销根本不该在事务内 |
| 本质 | 事后修补 | 事前规避 |
| 购物车券行状态写回 | 必须 | 不需要 |
| Redis 读写异常处理 | 必须 | 不需要 |
| 外部查询归属判定 | 必须 | 不需要 |
| 可续租锁 | 必须 | 不需要（方案 A） |
| 已提交订单幂等闸门 | 必须 | 不需要 |
| 删除入口反核销 | 必须 | 不需要 |
| 崩溃窗口可恢复 | 必须 | 需要（独立核销记录 + 恢复任务） |
| 批量券精确补偿 | 必须 | 需要 |
| 外部幂等契约 | 需要 | 需要 |
| 核心实现工作量 | 高（约 9 项） | 中（前置核销、独立记录、恢复任务） |
| 降低"回滚丢外部成果" | 否（只降低概率） | **是（事务失败补偿 + 崩溃恢复）** |

**V2 的代价**：新增独立记录表、独立事务和恢复任务；不再依赖购物车 `SUCCESS` 状态，因此不会随购物车过期/删除丢失凭证。V1.7 的购物车状态仍面临 Redis 过期/删除导致凭证丢失的问题。

## 6. 结论

**建议以 V2（完整 `preHandle` 后核销前置）为当前主方案。**

- 将远程核销移出订单事务，并以独立核销记录覆盖可捕获失败和进程崩溃恢复
- 相比 V1.7 不依赖购物车 Redis 的状态/TTL；代价是新增记录表与恢复任务
- 上线仍受外部平台 trace 查询/同键重放契约、锁租约和批量券精确补偿约束

**上线前提**：
1. 确认扫呗/餐道/抖音适配层真正透传稳定 `traceNo`
2. 确认外部平台同键重放/查询契约
3. 完成记录表迁移与恢复任务，并补充核销失败、核销成功但下单失败、反核销失败、崩溃恢复的自动化测试
