# POS 会员储值撤销负余额与一致性修复设计方案

> 日期：2026-07-21  
> 适用范围：POS 普通会员充值撤销、POS 储值方案充值撤销、原生 CRM 会员卡余额  
> 涉及仓库：`D:\mywork\nms4pos`、`D:\mywork\nms4cloud`、`D:\mywork\nms4pos-ui`

## 1. 文档目的

本文设计用于修复两个互相关联的问题：

1. 会员已经消费部分充值本金、赠送金额或积分后，撤销原充值会把会员本金、赠送金额、总余额或积分扣成负数。
2. POS 当前先撤销本地账单，再调用 CRM 撤销会员余额；CRM 失败时，本地账单已经变为取消状态。

本文给出满足当前风险要求的最小方案，不引入新的数据库表和新的分布式事务框架。

## 2. 现状与代码证据

### 2.1 POS 当前先撤销本地，再调用 CRM

普通充值撤销入口：

- `MemberForBizController.revokeCharge(...)`
- `MemberForBizController.revokeInner(...)`
- `MemberForBizController.revokeBill(...)`

当前顺序：

```text
查询 CRM 充值任务
-> 查询 POS 本地 CLOSED 充值单
-> revokeBill() 撤销本地账单/支付记录/明细
-> 调用 CRM /crm_card_op/revokeChargeSign
```

储值方案充值撤销入口 `MemberDepositPlanForBizController.revokeCharge(...)` 采用相同顺序。

直接后果：

```text
POS 本地撤销成功
-> CRM 校验失败、网络超时或服务异常
-> POS 单据为 CANCEL，但 CRM 充值任务仍为 SUCCESS
```

### 2.2 CRM 撤销按原充值金额全量反向记账

`CardBalanceService.executeInner(...)` 在撤销时把原操作符号取反，并进入 `cancelOrder(...)`。

`changeBalance(...)` 按原充值任务执行：

```text
balance           = balance           - task.amount
principal_balance = principal_balance - task.principalAmount
give_balance      = give_balance      - task.giveAmount
points            = points            - task.givePoint
```

当前撤销调用传入 `cancel=true`，余额和积分不足条件中的 `!cancel` 使校验失效；`ChargeCancel` 还被加入 `OP_ALLOWED_NEGATIVE`。

例如：

```text
原充值：本金 80，赠送 20，积分 10
当前值：本金 30，赠送 10，积分 5，总余额 40

撤销后：
本金 = 30 - 80 = -50
赠送 = 10 - 20 = -10
积分 = 5 - 10 = -5
余额 = 40 - 100 = -60
```

### 2.3 CRM 当前不满足持久幂等返回

`CrmCardOpServicePlus.revokeCharge(...)` 当前逻辑为：

```text
task.tradeState != SUCCESS -> 返回错误
task.canceled == true       -> 返回“已经撤销”错误
```

因此，第一次 CRM 已经撤销成功但 POS 未完成本地撤销时，POS 重试会被 CRM 以“已经撤销”拒绝，无法继续补齐本地状态。

`CardBalanceService` 中的 Redis 处理标记只能作为短期并发加速，不能替代数据库任务状态的持久幂等语义。

### 2.4 新储值方案一次性赠券的关联与现有撤销缺口

以下结论来自源码静态追踪，尚未在真实 CRM 数据库环境中做端到端复现；“当前只支持一次性赠券”以业务现状为准：

1. `DepositPlanChargeService.createChargeRecord(...)` 为每次储值方案购买生成独立的 `CrmDepositChargeRecord.lid`，并通过 `task_lid` 关联原充值任务；本次一次性赠券撤销仍以原充值任务 `taskLid` 为唯一订单关联键。
2. 一次性发券在 `DepositPlanCouponService.issueCoupons(...)`、`issueCouponPackages(...)` 中使用 `orderBillId=task.lid`，并设置渠道为 `CouponChannelEnum.Recharge`。
3. 源码中虽然存在 `PERIODIC` 和周期计划定时任务实现，但当前产品不支持周期性赠券；周期计划不属于本次 bug 的当前处理范围，不作为本次验收项。
4. 当前 `CardBalanceService.dealOtherItemTaskCancel(...)` 按 `orderId=taskLid` 异步调用券撤销，能够命中一次性券和券包子券，但券撤销失败只记日志，不能回滚余额撤销。
5. 当前撤销没有更新 `CrmDepositChargeRecord.tradeState`，虽然枚举已经存在 `REFUND(8)`；退款后购买记录仍可能保持 `SUCCESS`，异步赠品逻辑缺少持久状态门禁。
6. 当前 `couponOpRevoke(...)` 返回 `void`，只把 `WHX`（未核销）和 `YGQ`（已过期）改为 `YZF`（已作废）；`YHX`（已核销）不会被更新，也不会导致撤销失败。
7. 一次性赠券发放本身由 `CompletableFuture.runAsync(...)` 触发，退款只查现有券而没有共享状态门禁时，仍存在退款后异步补发一次性券的竞态。

关键源码证据位置：

```text
nms4cloud-crm-service/.../service/charge/DepositPlanChargeService.java:752-769
nms4cloud-crm-service/.../service/charge/DepositPlanChargeService.java:861-881
nms4cloud-crm-service/.../service/charge/DepositPlanCouponService.java:120-163, 423-471, 658-702
nms4cloud-crm-service/.../service/balance/CardBalanceService.java:885-898, 2129-2142
nms4cloud-crm-service/.../service/card/CrmCouponOpServicePlus.java:54-78
```

因此，本次新储值方案退款应聚焦“一次性券/券包 + 余额 + 购买记录”的一致性；周期性赠券虽有预留源码，但暂不纳入当前修改。

## 3. 修复目标

### 3.1 必须满足的目标

1. 撤销充值不能使 `balance`、`principal_balance`、`give_balance`、`points` 变成负数。
2. CRM 撤销失败时，POS 本地账单不得进入最终 `CANCEL` 状态。
3. CRM 撤销成功但 POS 本地处理失败时，重复请求能够继续完成 POS 本地撤销。
4. 同一个 CRM `taskLid` 重复撤销不能重复扣本金、赠送金额和积分。
5. 普通充值和储值方案充值使用一致的撤销语义。
6. 新储值方案退款必须撤销本次购买已发放且未核销的普通券和券包子券。
7. 本次购买发放的任一券已经核销时，CRM 必须拒绝自动退款，余额、任务、购买记录和其他券状态均保持不变。
8. 退款成功后，异步一次性赠品任务不得再次发放该次购买的权益。
9. 重复退款不能重复作废券或重复修改购买记录。
10. 保持现有 POS 前端接口、CRM 接口路径和返回包装 `NmsResult` 兼容。

### 3.2 本次不做

1. 不支持“余额不足时部分撤销”。部分撤销会使支付退款金额与会员余额回滚金额不一致。
2. 不通过 `max(value, 0)` 截断负数。截断会丢失账务差额且破坏流水可核对性。
3. 不新增独立的 CRM 预校验接口。预校验和正式撤销之间存在并发窗口，不能提供最终一致性保证。
4. 不新增分布式事务中间件和数据库表。
5. 第三方会员实现（如外部酒店会员、第三方储值平台）不直接套用原生 CRM SQL 规则，需按对应外部接口的幂等和余额规则单独验证。
6. 不对已核销赠券做自动反核销。反核销会影响原消费单、支付、库存和业绩，必须走独立且可审计的业务流程。

## 4. 核心设计决策

### 4.1 采用“CRM 正式撤销在前，POS 本地撤销在后”

目标流程：

```text
POS 前端发起撤销
-> POS 查询 CRM 充值任务，只做参数准备，不修改本地账单
-> POS 调用 CRM 正式撤销接口
-> CRM 在会员锁和数据库事务内执行幂等判断、余额校验和撤销
-> CRM 失败：POS 直接返回错误，本地账单保持 CLOSED
-> CRM 成功：POS 执行本地 revokeBill()
-> POS 本地成功：接口返回成功
```

该方案直接解决“CRM 失败但本地已取消”。

### 4.2 CRM 使用数据库任务状态作为幂等真值

幂等业务键：

```text
mid + taskLid + operation(revokeCharge)
```

其中 `taskLid` 是原充值任务 `CrmDealTask.lid`。必须先校验请求卡号/`cardLid` 与原任务一致，再执行幂等返回，避免用其他会员卡请求命中已撤销任务。

幂等状态语义：

| CRM 任务状态 | 处理方式 |
| --- | --- |
| `SUCCESS` 且未撤销 | 进入余额校验和正式撤销 |
| `REVOKED` 或 `canceled=true`，且不是新储值方案 | 返回幂等成功，不再次修改余额 |
| `REVOKED` 或 `canceled=true`，新方案购买记录已为 `REFUND` | 返回幂等成功，不再次修改余额和权益 |
| `REVOKED` 或 `canceled=true`，新方案购买记录仍为 `SUCCESS` | 历史半完成状态；不得再次扣余额，只执行权益收敛或转人工告警 |
| `USERPAYING`、失败或其他状态 | 返回不允许撤销 |

Redis 锁和 Redis 已处理标记继续保留，但只负责降低并发请求，不作为最终幂等依据。

新储值方案的幂等完成条件不是单独的 `CrmDealTask=REVOKED`，而是至少同时满足：Task 已撤销、购买记录为 `REFUND`、关联一次性券不存在可继续使用状态。否则属于待收敛的不一致状态。

### 4.3 CRM 校验与扣减必须原子执行

在 `CardBalanceService.execute(...)` 已有的会员粒度锁内，`executeInner(...)` 使用同一数据库事务完成：

1. 查询并校验原充值任务。
2. 查询会员卡最新余额。
3. 分别校验本金、赠送金额、积分和总余额。
4. 更新会员余额。
5. 生成本金/赠送/积分撤销流水。
6. 把原充值任务更新为 `REVOKED`、`canceled=true`。
7. 提交事务。

任何一步失败，事务整体回滚。

### 4.4 新储值方案按“充值事实 + 派生权益”整体撤销

新储值方案的自动退款采用单一结果语义：余额、积分、一次性券和购买记录要么全部完成撤销，要么全部不变。不能继续把券撤销作为提交后的异步附加动作。

CRM 同一事务内的目标流程为：

```text
取得会员粒度锁
-> 查询原 CrmDealTask 并做持久幂等判断
-> 按 mid + taskLid 查询并锁定 CrmDepositChargeRecord
-> 购买记录已为 REFUND：按幂等成功处理
-> 购买记录为 SUCCESS
-> 查询 orderBillId = taskLid 的一次性充值赠券
-> 存在已核销券或未知不可撤状态：整体拒绝退款
-> 校验本金、赠送金额、积分和总余额
-> 将未核销/已过期券改为 YZF
-> 扣减本金、赠送金额和积分并生成撤销流水
-> CrmDepositChargeRecord: SUCCESS -> REFUND
-> CrmDealTask: SUCCESS -> REVOKED, canceled=true
-> 提交事务
```

本次只查询 `orderBillId=taskLid`。券包无需按当前方案配置重新展开，直接按该订单号查询实际生成的 `CrmCouponOrder` 子券实例，可避免方案修改后漏撤或误撤。未来启用周期赠券时，再单独设计 `chargeRecordLid` 和周期计划的撤销契约。

`CrmDepositChargeRecord` 是新方案赠品发放与退款的共享状态门禁：

- 异步一次性发券执行前，必须锁定购买记录并确认状态仍为 `SUCCESS`。
- 退款把购买记录更新为 `REFUND` 后，任何尚未执行的一次性赠品任务都必须跳过。
- 如果发券先取得锁，退款等待其提交后再查询并撤销刚发出的券；如果退款先取得锁，发券等待后看到 `REFUND` 并跳过。

新方案权益子流程统一先锁购买记录；现有会员粒度锁继续作为余额修改的外层串行保护。

## 5. CRM 详细修改方案

### 5.1 修改 `CrmCardOpServicePlus.revokeCharge(...)`

文件：

```text
nms4cloud-app/2_business/nms4cloud-crm/nms4cloud-crm-service/
src/main/java/com/nms4cloud/crm/service/card/CrmCardOpServicePlus.java
```

修改点：

1. 调整状态判断顺序，先识别“已经撤销”的幂等请求。
2. 已撤销的普通充值直接返回幂等成功；已撤销的新储值方案先检查购买记录和关联一次性券是否已经收敛，未收敛时只执行权益收敛，不得再次扣余额。
3. 未撤销时继续调用 `CardBalanceService.execute(..., cancel=true)`。
4. POS 签名接口已经设置 `notNeedRefund=true`，继续保持由 POS 处理本地支付退款，避免 CRM 和 POS 双重退款。
5. 背景操作记录只在首次撤销成功时创建；幂等返回不得重复创建相同撤销操作记录。

伪代码：

```java
CrmDealTask task = cardBalanceService.queryTask(request.getMid(), request.getTaskLid());
Assert.notNull(task, "充值记录不存在");
Assert.isTrue(task.getCardLid().equals(request.getLid()), "充值记录与会员卡不一致");

if (TradeStateEnum.REVOKED.equals(task.getTradeState())
    || Boolean.TRUE.equals(task.getCanceled())) {
  if (isDepositPlanTask(task)) {
    reconcileDepositPlanBenefits(task, request.getOperator());
  }
  return NmsResult.data(buildIdempotentRevokeResult(task, card));
}

Assert.isTrue(TradeStateEnum.SUCCESS.equals(task.getTradeState()), "当前状态不允许撤销");

NmsResult<CardBalanceVo> result =
    cardBalanceService.execute(
        request.getMid(), task.getLid(), request.getLid(), true, request.getOperator());

Assert.isTrue(result.isSuccess(), result.getErrorMessage());
crtBackgroundRecord(...);
return result;
```

### 5.2 修改 `CardBalanceService` 的撤销幂等入口

文件：

```text
nms4cloud-app/2_business/nms4cloud-crm/nms4cloud-crm-service/
src/main/java/com/nms4cloud/crm/service/balance/CardBalanceService.java
```

在核心余额服务中增加第二层持久幂等保护：

```java
if (cancel
    && (TradeStateEnum.REVOKED.equals(task.getTradeState())
        || Boolean.TRUE.equals(task.getCanceled()))) {
  return NmsResult.data(buildIdempotentRevokeResult(task, card));
}
```

这层保护用于防止未来其他调用方绕过 `CrmCardOpServicePlus` 直接调用余额服务。

该保护只保证余额不会二次扣减；新储值方案的一次性权益收敛仍必须由上层 `revokeCharge(...)` 或同等协调方法完成，不能把余额层的幂等返回当作券已经完成。

### 5.3 增加撤销余额校验

在首次进入充值撤销、调用 `changeBalance(...)` 之前，分别校验：

```java
BigDecimal currentPrincipal = NullSafeUtils.nullSafe(card.getPrincipalBalance());
BigDecimal currentGive = NullSafeUtils.nullSafe(card.getGiveBalance());
BigDecimal currentPoints = NullSafeUtils.nullSafe(card.getPoints());
BigDecimal currentBalance = NullSafeUtils.nullSafe(card.getBalance());

BigDecimal revokePrincipal = NullSafeUtils.nullSafe(task.getPrincipalAmount()).abs();
BigDecimal revokeGive = NullSafeUtils.nullSafe(task.getGiveAmount()).abs();
BigDecimal revokePoints = NullSafeUtils.nullSafe(task.getGivePoint()).abs();
BigDecimal revokeBalance = NullSafeUtils.nullSafe(task.getAmount()).abs();

Assert.isTrue(currentPrincipal.compareTo(revokePrincipal) >= 0, "当前本金不足，不能撤销充值");
Assert.isTrue(currentGive.compareTo(revokeGive) >= 0, "当前赠送余额不足，不能撤销充值");
Assert.isTrue(currentPoints.compareTo(revokePoints) >= 0, "当前积分不足，不能撤销充值");
Assert.isTrue(currentBalance.compareTo(revokeBalance) >= 0, "当前会员余额不足，不能撤销充值");
```

校验顺序建议为：本金、赠送、积分、总余额。这样错误信息能直接说明哪个组成项不足。

### 5.4 SQL 更新增加条件保护

即使当前已有会员粒度 Redis 锁，最终更新 SQL 仍建议增加条件，防止未来存在未走同一锁的余额修改入口：

```text
WHERE mid = :mid
  AND lid = :cardLid
  AND principal_balance >= :revokePrincipal
  AND give_balance >= :revokeGive
  AND points >= :revokePoints
  AND balance >= :revokeBalance
```

只有对应撤销值大于 0 时才增加该字段条件。更新行数为 0 时抛出“会员余额不足或余额已发生变化”，整个事务回滚。

不能只保留 `balance >= task.amount`，因为总余额足够时，本金或赠送组成项仍可能不足。

### 5.5 调整允许负数规则

当前 `OP_ALLOWED_NEGATIVE` 包含 `ChargeCancel`。本次修复后：

1. `ChargeCancel` 不再作为“无需校验即可扣成负数”的依据。
2. 撤销分支使用专门的本金、赠送、积分、总余额校验。
3. 不直接删除其他操作类型的兼容逻辑。

注意：仅从 `OP_ALLOWED_NEGATIVE` 删除 `ChargeCancel` 仍不够，因为当前余额条件还有 `!cancel` 判断，撤销时依然会绕过通用校验。

### 5.6 新储值方案一次性赠券撤销

建议在 `DepositPlanCouponService` 增加一个仅供 CRM 充值撤销调用的局部方法，例如：

```java
DepositPlanBenefitRevokeResult revokeBenefits(
    Long mid, Long taskLid, Long cardLid, String operator)
```

该方法不新增对外接口，不改变 POS 请求结构，职责仅限新储值方案权益撤销。处理规则如下。

#### 5.6.1 识别新储值方案购买记录

按以下条件查询并锁定购买记录：

```text
crm_deposit_charge_record.mid = :mid
crm_deposit_charge_record.task_lid = :taskLid
crm_deposit_charge_record.card_lid = :cardLid
deleted = 0
```

- 未查到购买记录：不是新储值方案，继续保留原普通充值/旧储值规则撤销路径。
- 状态为 `SUCCESS`：允许进入首次权益撤销。
- 状态为 `REFUND`：返回幂等成功，不重复修改券。
- `USERPAYING`、`CLOSED` 或其他状态：拒绝退款。

首次撤销在同一事务中使用条件更新 `SUCCESS -> REFUND`；更新行数为 0 时重新读取状态，只有已经为 `REFUND` 才按幂等成功处理。

对于上线前已经形成的 `CrmDealTask=REVOKED`、购买记录仍为 `SUCCESS` 的记录，不能重新扣余额。处理分支为：

1. 关联券均未核销：同步作废券、把购买记录改为 `REFUND`，然后返回幂等成功。
2. 存在已核销券：保持现有财务数据不再二次变更，记录高优先级不一致告警并转人工核对原退款、券消费单和补偿责任。
3. 权益收敛失败：返回明确的“历史退款权益未收敛”错误，不能伪装成幂等成功。

#### 5.6.2 按原充值任务撤销一次性券和券包子券

本次只使用原充值任务作为券订单关联键：

```text
orderId = taskLid
```

查询 `CrmCouponOrder` 时至少限定：

```text
mid = :mid
order_bill_id = :taskLid
get_channel = Recharge
```

`CrmCouponOrder` 当前没有 `card_lid` 字段。不能只依赖可变的手机号作为唯一关联条件；应先用购买记录确认 `cardLid`，再以 CRM 内部生成且在本次购买中唯一的 `taskLid` 查询。若继续附加 `unionid=phone`，必须先验证历史会员换手机号后不会造成漏撤。

券状态处理：

| 券状态 | 自动退款处理 |
| --- | --- |
| `WHX` 未核销 | 更新为 `YZF` |
| `YGQ` 已过期 | 更新为 `YZF` |
| `YZF` 已作废 | 视为幂等完成 |
| `YHX` 已核销 | 拒绝整笔退款 |
| 其他状态 | 保守拒绝，确认其数据库实际状态语义后再放行 |

当前 `couponOpRevoke(...)` 返回 `void` 且会静默跳过 `YHX`，不适合作为新方案退款的成功判据。建议增加内部专用方法，先锁定并校验全部关联券，再执行条件更新，并比较“待作废数量”和“实际更新数量”；不修改现有对外券撤销接口契约。

#### 5.6.3 取消异步撤券作为成功条件

新储值方案的一次性券校验、券作废、购买记录 `REFUND`、余额扣减和任务 `REVOKED` 必须同步加入同一个 CRM 数据库事务。不得继续依赖 `cancelOrder(...)` 末尾的 `CompletableFuture.runAsync(...)` 作为退款完成条件。

普通充值和旧储值规则暂时保留原 `dealOtherItemTaskCancel(...)` 路径，避免扩大改动面；新方案命中购买记录后跳过其中重复的券撤销分支。周期赠券相关源码仅作为未来扩展参考，不在本次修改中增加计划取消逻辑。

### 5.7 退款与异步赠品发放的并发门禁

`DepositPlanChargeService.handlePostSuccessBenefits(...)` 当前由异步线程执行。只在退款方法中查券不够，因为异步线程可能在查询之后继续发券。

最小可靠改法是复用现有 `CrmDepositChargeRecord.tradeState`：

1. 将一次性赠品处理包装为可被 Spring 事务代理调用的公共事务方法，锁定购买记录并确认 `tradeState=SUCCESS` 后再执行发券和会员等级处理。
2. 退款权益方法锁定同一购买记录，并在事务中更新为 `REFUND`。
3. 发券与退款统一先锁定购买记录，避免退款后异步补发一次性券。

不新增通用状态机、事件总线或补偿框架。已有购买记录和 `REFUND` 枚举足以构成这次修复所需的持久门禁。

### 5.8 会员等级、有效期和销售统计

新储值方案还会在 `handleMemberUpgrade(...)` 中直接修改会员等级和 `over_time`。当前代码没有按本次购买保存升级前等级和原有效期，退款时无法区分这些值是否又被其他消费、人工调整或后续活动修改。

本次保守策略：

1. 档位包含会员升级或等级延期时，POS 自动退款先返回明确业务错误，不能只退余额、积分和券后保留等级权益。
2. 后续若要支持自动恢复，必须在权益发放时持久化本次变更前后快照和来源 `taskLid`，退款时仅在当前值仍等于本次发放后的值时条件恢复；否则转人工审核。
3. 赠送积分已记录在 `CrmDealTask.givePoint`，继续由本次核心余额撤销统一校验和扣回，不另做一套积分逻辑。
4. 购买记录退款成功后更新为 `REFUND`，现有购买限制只统计 `SUCCESS + USERPAYING`，因此退款记录不再占用购买次数。
5. 不直接递减 `crm_deposit_plan.total_sold_count/total_sold_amount`。当前代码注释明确该字段保留历史销量含义；若报表需要净销量，应单独定义退款口径，不能在本次修复中改变旧字段语义。

### 6.3 本地撤销需要可重复执行

CRM 成功后，POS 可能在本地更新过程中失败。再次请求时 CRM 会幂等成功，POS 必须能够继续完成本地撤销。

本地处理要求：

1. `DwdBill.orderStatus=CANCEL` 时直接视为本地撤销完成。
2. `DwdBill.orderStatus=CLOSED` 时执行首次本地撤销。
3. `DwdApplyPay.refundState=A` 时视为移动支付已经退款，不再次要求必须查询到 `refundState=U` 的记录。
4. 移动支付退款使用原支付流水作为退款幂等依据，响应丢失时先查退款状态或调用支付侧幂等退款。
5. `DwdPay`、`DwdFood` 更新为 `CANCEL` 应保持重复设置安全。
6. 会员卡支付的消费撤销接口也必须具备幂等语义，避免本地重试重复返还会员卡支付金额。

本次最小方案不新增本地 `REVOKING` 状态，但必须保证上述重试路径成立。若现有支付接口无法提供幂等退款或状态查询，则需把 `REVOKING` 状态和补偿任务升级为上线前必做项。

| 场景 | CRM 状态 | POS 本地状态 | 接口结果 | 恢复方式 |
| --- | --- | --- | --- | --- |
| 本金不足 | `SUCCESS` | `CLOSED` | 失败 | 用户先处理相关消费，不修改任何撤销状态 |
| 赠送不足 | `SUCCESS` | `CLOSED` | 失败 | 同上 |

## 12. 上线与回滚

### 12.1 发布顺序

建议顺序：

```text
1. 先发布 CRM：余额校验 + 数据库状态幂等 + 新方案权益撤销和发券门禁
2. 验证旧 POS 调用 CRM 兼容
3. 再发布 POS：调整为 CRM 在前、本地撤销在后
4. 最后发布 POS 前端选择状态修复
```

先发布 CRM 的原因：即使旧 POS 仍然本地先撤销，CRM 已能阻止负余额；但在 POS 新版本发布前，仍存在 CRM 拒绝后本地已取消的短暂兼容窗口，因此 CRM 与 POS 发布间隔应尽量短，并安排监控。

发布前先执行只读数据审计，至少统计：

```text
CrmDealTask 已 REVOKED，但 CrmDepositChargeRecord 仍为 SUCCESS
已退款购买仍存在 WHX/YGQ 券
已退款购买关联券已经 YHX
```

审计脚本必须按 `mid` 和业务主键限定范围，只输出脱敏业务键摘要。先人工确认样本，再以幂等批次收敛可自动处理的数据；存在 `YHX` 的历史记录不得自动改账。

### 12.2 回滚策略

1. 前端可以独立回滚，不影响 CRM 数据安全。
2. POS 顺序调整回滚会重新暴露“本地成功、CRM 失败”的风险，仅用于紧急恢复。
3. CRM 负余额校验属于财务完整性修复，不建议回滚为允许负数；出现兼容问题时优先前向修复错误判断条件。
4. CRM 幂等成功返回必须与 POS 新顺序同时保留，否则本地补偿重试会失败。
5. 不得只回滚发券状态门禁而保留 `REFUND` 写入，否则合法发券可能被错误跳过；新方案权益撤销与一次性发券门禁应作为一个 CRM 回滚单元。
6. 已成功退款产生的 `REFUND`、`YZF` 是业务事实，代码回滚不得反向恢复；需要通过前向修复继续兼容这些状态。

## 13. 可观测性要求

日志只记录必要的非敏感摘要：

```text
mid、sid、taskLid、cardLid、阶段、结果码、券数量、失败原因
```

不得记录手机号、完整卡号、支付凭证或完整请求/响应对象。

建议增加以下统计：

1. CRM 撤销余额不足次数，按本金/赠送/积分分类。
2. CRM 幂等命中次数。
3. CRM 成功但 POS 本地失败次数。
4. POS 本地补偿重试次数和最终失败次数。
5. 新方案退款因已核销券被拒绝的次数。
6. 新方案退款作废一次性券数量和幂等命中次数。
7. `REFUND` 购买记录仍产生新券的数量，该值必须为 0，出现即告警。
8. Task 已 `REVOKED` 但购买记录不是 `REFUND` 的历史半完成数量。

指标标签只使用结果类型、权益类型和阶段等低基数字段，不把 `taskLid`、会员或门店作为指标标签。业务键只允许出现在受控日志中。

## 14. 验收标准

满足以下条件才算修复完成：

1. 本金、赠送、积分任一不足时，CRM 拒绝撤销且所有相关数据不变。
2. CRM 失败时，POS 本地账单仍为 `CLOSED`。
3. CRM 成功、POS 失败后，同一请求重试能够完成本地撤销且 CRM 余额只变更一次。
4. 重复撤销不会产生重复流水、重复退款或重复背景操作记录。
5. 新储值方案退款会作废本次购买发放的全部未核销普通券和券包子券。
6. 任一赠券已核销时自动退款失败，CRM 和 POS 均不产生部分成功状态。
7. 退款与首次异步一次性发券并发时，退款成功后不会新增有效券。
8. 购买记录最终为 `REFUND`，重复退款按成功返回，购买限制不再统计该记录。
9. 包含会员升级或等级延期且无法安全恢复的方案不会被 POS 自动退款。
10. 普通充值和储值方案充值回归通过。
11. 未引入接口路径、请求字段和返回结构的不兼容变更。

### 15.2 支付侧退款幂等

未确认项：移动支付退款接口在“退款成功但 POS 未收到响应”时，使用原支付流水重试是否稳定返回幂等成功。

保守处理：上线前通过支付查询或退款重试用例确认；若无法确认，则增加本地处理中状态和补偿任务，不允许仅靠人工处理。

### 15.3 生产库约束

当前源码和仓库迁移资料中未确认 `crm_card` 对余额字段存在非负约束。即使数据库存在约束，业务层原子校验仍必须保留，以便返回明确错误并保证流水和任务状态一致。

### 15.4 周期赠券能力边界

源码中存在周期发券分支和计划表，但业务已确认当前不支持周期性赠券。本次不新增、启用或修改周期发券逻辑；未来正式开放周期赠券时，必须另行设计 `chargeRecordLid`、周期计划停止、已发批次券撤销和定时任务并发控制。

## 16. 不同角色评审结论

### 16.1 CRM 后端评审

- 通过点：余额组成项校验、购买记录持久门禁、一次性券同事务处理，能阻止负余额和退款后继续发券。
- 阻断点：不能把 `CrmDealTask=REVOKED` 单独当作新方案幂等完成；必须处理历史半完成数据。
- 必须验证：同一购买记录的一次性发券和退款使用一致的锁顺序，异常时事务确实回滚。

### 16.2 POS 评审

- 通过点：CRM 正式撤销成功后才改本地单据；CRM 因余额不足、已核销券或等级权益不可恢复而失败时，本地保持 `CLOSED`。
- 阻断点：CRM 成功而 POS 本地失败时，CRM 重试必须返回成功，不能用“已经撤销”阻断本地补偿。
- 必须验证：储值方案入口不会把普通充值单误匹配；本地退款和会员卡支付返还均可重复执行。

### 16.3 数据库评审

- 通过点：复用 `CrmDepositChargeRecord.tradeState=REFUND`，不新增事务框架和业务表。
- 阻断点：生产库必须确认 `order_bill_id` 查询索引，否则退款可能造成大表扫描。
- 必须验证：余额条件更新、购买记录状态更新和券状态更新均带 `mid` 范围，更新行数可判定并发冲突。

### 16.4 QA 评审

- 必测：一次性券、券包子券、已核销券、退款与发券并发、历史半完成状态、重复请求和异常回滚。
- 失败判据：任何 `REFUND` 购买记录产生新有效券；任何已核销券被静默改为 `YZF`；任一失败场景出现部分余额或本地单据变更。

### 16.5 运维与安全评审

- 通过点：日志只记录脱敏业务键和结果摘要，指标不使用会员、门店或交易号作为高基数标签。
- 必须补齐：上线前只读审计历史半完成退款；对 `Task=REVOKED` 但购买记录非 `REFUND`、以及 `REFUND` 后新发券设置告警。
- 人工边界：已核销券和已发生会员升级/延期但无快照的记录不得自动改账，必须保留审计和责任归属。
