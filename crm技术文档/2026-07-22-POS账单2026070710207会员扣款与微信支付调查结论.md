## 2. 核心结论

1. 一个被系统识别为会员卡 `13889923560`、OpenID `owFjH5UuZVluK9KRlRFtXmQeT4nY` 的顾客端线上会话，先后进行了两次点单。

9. 当前反馈称云端查不到该订单。必须区分查询使用的编号：`2026070710207` 是 POS 本地账单号，不是云端订单主键；云端应按三条消息中的雪花 ID 查询。如果三个雪花 ID 当前也不存在，则需继续检查软删除、历史归档、分库分表路由及所查环境。

### 4.4 POS 账单号与云端订单号不能混用

本单存在两组不同含义的编号：

| 编号 | 含义 | 应查询的位置 |
|---|---|---|
| `2026070710207` | POS 本地账单号 `dwd_bill.saas_order_key` | POS 8067 数据库 |
| `2074462348122746882` | POS 本地账单 LID / `saas_order_no` | POS 8067 数据库 |
| `2074462358141677569` | 第一次 `DO_ORDER` 的云端订单/消息 ID | 云端订单库、日志 |
| `2074462586112057345` | 第二次 `DO_ORDER` 的云端订单/消息 ID | 云端订单库、日志 |
| `2074463059848736770` | `CASH_PAY` 的云端订单/消息 ID | 云端订单库、日志 |

因此，如果在云端使用 `2026070710207` 查询不到订单，不能据此判断云端订单不存在。该编号是 POS 在门店本地生成的账单号，POS 会把同桌次的多条云端订单合并到该本地账单。

如果云端使用上述三个雪花 ID 仍然全部查询不到，则当前只能确认“云端当前不可查询到历史订单”，不能直接确认其从未存在。原因是事故发生时 POS 的处理代码会使用消息 `data.id` 调用云端 `doGetOrder`；只有成功取得完整订单，才会继续写入菜品并处理 `CASH_PAY`。8067 已保留完整菜品、支付结果和三条原始消息，构成事故时云端接口曾返回订单数据的本地证据。

云端当前查不到三个雪花 ID时，应依次检查：

1. 查询的环境、MID 和 SID 是否与事故门店一致。
2. 是否遗漏逻辑删除数据，即查询是否默认带 `deleted=0`。
3. 是否查询了错误的分库、分表或实际物理表。
4. 历史订单是否已归档、迁移或被清理。
5. 三个 ID 在订单服务日志、MQ/Netty 消息日志中是否仍有记录。

## 11. 最终微信支付是线上还是线下

结论：最终 186 元是顾客端小程序/H5 的线上手机微信支付，不是线下 POS 扫描顾客付款码。

证据：

1. POS 收到的原始消息为 `source=nms4cloud`、`msgType=CASH_PAY`。
2. 订单服务在顾客端支付后主动向 POS 发送 `CASH_PAY`。
3. POS 的 `CashPayHandler` 将该笔申请支付来源写为 `SourceEnum.Customer`。
4. `SourceEnum.Customer` 的定义是“顾客端小程序/H5”。
5. 本单 `dwd_apply_pay.pay_result`、渠道支付流水和渠道订单号均为空，符合线上支付完成后仅同步结果给 POS 的路径，不符合 POS 本地主动调用支付通道的典型记录。

## 14. 当前异常与根因候选

当前系统结果：

```text
CRM 会员账户：已扣 239 元
POS 最终支付：仅记录微信 186 元
最终消费金额：186 元
```

如果会员 239 元没有退回，则会员扣款与微信支付合计为：

```text
239 + 186 = 425 元
```

这与最终消费金额 186 元不一致。

### H1：会员退款失败后仍继续重新支付

诊断状态：**有证据候选，尚未闭环确认**。

当前源码存在以下路径：

1. 第一次支付先调用 CRM 扣款 239 元。
2. 退菜后重新支付时，系统尝试撤销旧支付。
3. 会员退款失败时，部分代码只记录日志，不向上抛出失败。
4. 系统仍可能将订单恢复为待支付并删除旧支付明细。
5. 新的微信 186 元支付继续完成。
6. POS 最终只看到微信 186 元，但 CRM 仍保留会员扣款 239 元。

该路径能够解释当前全部金额现象，但还缺本单线上退款日志和 CRM 任务状态，因此不能写成已确认根因。

### H2：订单身份映射错误

诊断状态：**有证据候选，尚未闭环确认**。

会员本人称当天未到店、未消费。当前只能确认一个绑定该会员卡和 OpenID 的线上会话发起了订单，尚不能确认操作者本人身份。

CRM 登录代码存在多映射时选卡不稳定的风险：第一轮查询会混合 OpenID、UnionID 和手机号；命中多条映射时使用第一条，但未见稳定排序及第一轮严格限定 `type/appid`。如果历史映射存在重复或冲突，可能选中错误会员卡。

必须查询线上 `crm_card_map` 才能判断本单是否发生身份错配。

## 17. 最终定性

> 2026 年 7 月 7 日，一个被系统识别为会员卡 `13889923560`、OpenID `owFjH5UuZVluK9KRlRFtXmQeT4nY` 的顾客端线上会话先后进行了两次点单，退菜前金额为 331 元。系统于 19:56:56 扣除会员全部余额 239 元。门店随后退菜 145 元，将账单改为 186 元；之后顾客端小程序/H5 在线完成微信支付 186 元，云端通知 POS 结账。POS 最终仅保留微信支付记录。
>
> 当前不能确认会员本人持手机操作，也不能从本地 8067 确认微信 186 元的实际付款人。会员 239 元为何未体现在最终 POS 支付中，最符合现有源码和数据的候选是旧会员支付撤销/退款失败后系统仍允许重新支付，但该结论必须由线上 CRM 任务和订单支付日志进一步闭环。
>
> 当前云端查不到订单不会推翻上述 POS 证据。若查询使用的是 `2026070710207`，属于编号口径错误；若三个云端雪花 ID 也不存在，则应将“云端历史订单当前不可查询”列为新的数据留存或查询路由问题继续排查。
